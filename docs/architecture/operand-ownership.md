# Operand ownership

Who owns the value handed to a call's operand, and how the caller and the node that produced the argument agree about which of them releases it. The other half of [value lifetime](value-lifetime.md), which covers a value sitting in a stack slot, a row or a list. Part of the [Dataphor architecture](../architecture.md).

## An operand's owner depends on its modifier and on its argument

A call's arguments are evaluated by the caller, pushed into the callee's slots by `CallNode`, then cleaned up by `InstructionNodeBase.CleanupOperand`, which reads the operand's modifier:

- `var` - the callee's slot is an alias of a caller's slot. Nothing is copied and nothing is released; the cleanup writes the slot's final value back with a plain `Poke`, because the caller's slot already owned it. That write-back runs on every exit path, including a `raise`, so the caller sees the callee's last assignment either way. The cleanup releases nothing, but the body can, and does: an assignment to a `var` parameter - or a `foreach` over it - releases what the slot held, and the write-back then hands the caller the replacement. That is right only while the caller's slot owns the value it passed, so **a `var` operand whose argument names a slot holding a value that slot does not own is copied for the call** (`CallNode.ReferencesABorrowedSlot`) - a `foreach` loop variable, which the loop lends the row or element the iterator owns and goes on reading ([value-lifetime.md](value-lifetime.md)). The callee's slot then owns its value, and the invariant at the foot of this page holds for `var` as it does for everything else.

  A callee cannot make that decision - an operator is compiled once, independently of its call sites - so the call site makes it, from the one fact only it has: the compiler's mark on the caller's symbol (`Symbol.IsBorrowed`), read in the `var` branch of `InstructionNodeBase.DetermineDataType` and carried on the `StackReferenceNode` that argument compiled to. `CallNode` reconciles each such operand on the way out: where the slot still holds the copy, the body never wrote to the operand, so the copy is the call's to release and the caller's own value is what the write-back stores back into the caller's slot - a no-op, exactly what the cleanup does on the non-borrowed path. Where the body did write, it released the copy itself and the slot's final value is the operator's output, which the caller's loop variable then holds until the next plain store into that slot - the next iteration's over a list, and over a cursor none at all, because `ForEachNode` fills its one row before the iteration rather than inside it. That last write-back leaks one value, because that next store displaces it without releasing it; it is the same accepted tradeoff as a direct assignment to a loop variable, measured equal to it, and recorded on the borrowed branch of `AssignmentNode`.
- `in` - the callee's slot holds a value of its own, and the cleanup releases it. `CallNode` hands the slot's current value back first, so a body that assigned to the operand released the displaced value itself and the cleanup releases its replacement.
- `const` - the callee's slot cannot be assigned to (the compiler makes a const operand's symbol constant), and whether the call owns the value is **not** a property of the modifier but of the plan node that produced the argument.

That last point is the one the engine used to be unable to express. A node that reads a stack slot, or a column of a row in one, can hand over the value it already holds rather than a copy; a node that *computes* a value - a literal, a conversion, another call - produces one nothing else holds. Only the node knows which, and the difference matters on nearly every call: the compiler promotes a by-value operand the body never assigns to to `const` (`Compiler.CompileOperatorBlock`), and every comparison, conversion, selector and property accessor generated for a scalar type declares `const` outright.

An argument that raises leaves the call unmade, and `ReleaseUncalledOperand` is that path's own rule: release the values the call owns among the arguments already evaluated, and leave every `var` operand alone - there is no callee value to write back, and writing one would run the type's constraints while an error unwinds.

## How a node says it is lending

Two virtuals on `PlanNode` (`src/engine/DAE/Runtime.Instructions/PlanNode.cs`):

- `SetByReference()` asks the node to return its value by reference rather than a copy, and answers whether it will.
- `ReturnsByReference` answers, afterwards, whether it does.

The const branch of `InstructionNodeBase.DetermineDataType` asks, once, while the call is compiled; `CleanupOperand` reads the answer back off the same node at run time and releases the value unless the node lent it. The store and the release therefore read one flag on one object.

The nodes that can lend are the three that have something to lend: `StackReferenceNode` (a variable), `StackColumnReferenceNode` (a column of a row-typed variable) and `ExtractColumnNode` (`LR.B`, a column read out of a row). The third lends only when the row it reads from outlives the call - a source row the node disposes on its way out owns its column values, so lending one would hand back a value released before it could be read. `IndexerNode` (a list element) overrides `ReturnsByReference` but deliberately has no `SetByReference`: nothing asks it, so it always copies, and the override is there so that whoever changes that meets this rule rather than a silent leak.

A node that overrides `InternalExecute(Program)` is never reached by `CleanupOperand` and owes the rule itself. Most such nodes are table nodes, where overriding that entry point is simply how a table node returns a cursor and there are no operand modifiers in play. The set to know about is the thirteen that are operator nodes. Three derive from `InstructionNodeBase` directly: `ExistsNode` (`ExtractionNodes.cs`), `TableToListNode` (`ListNodes.cs`) and `IfNilNode` (`SystemNodes.cs`). Ten more derive from one of the five argument shapes - `InstructionNode` and its nilary, unary, binary and ternary siblings - and re-override the entry point, which skips the shape's own call to `CleanupOperand` while the node still reads as an ordinary instruction node: `RowEqualNode` and `CompoundScalarEqualNode` (`RowComparisonNodes.cs`), the six comparison subclasses of `TableComparisonNode` (`TableComparisonNodes.cs`), and `RowExtendNode` and `RowRedefineNode` (`RowNodes.cs`).

There are two halves to get right, and a node of this shape can miss either. `IfNilNode` missed the release half: it called `base.DetermineDataType`, so its argument nodes were asked to lend and a lent argument was left alone correctly, but it copied the argument it chose and released nothing where the argument was the call's own - one stream for the life of the session on every call over a computed `Binary` or `Graphic` (`bug-ifnil-leaks-the-value-it-copies`). It now reads `ReturnsByReference` off the argument node it chose and releases the value only where that node gave rather than lent it, which is what a new node of this shape has to do.

`RowEqualNode` and `CompoundScalarEqualNode` miss **both** halves at once, which is `bug-row-equality-leaks-the-rows-it-compares`: their `DetermineDataType` calls `DetermineModifiers` instead of `base.DetermineDataType`, so nothing ever asks either argument node to lend and both copy the row they were given, and their `InternalExecute(Program)` override then skips the release - one managed stream per stream-backed column per side, on every comparison, whether the rows compared were computed or read out of a variable. The rest of the set is sound: `ExistsNode` and `TableToListNode` dispose the cursor they opened, the table comparisons' operands are `in` and they dispose both cursors, and `RowExtendNode` and `RowRedefineNode` are compiled from expressions rather than resolved as operator calls, so they have no operand modifiers to honour and dispose the source row they opened. **Nothing checks the set** - it was counted by hand, and counted wrong once already - so that ticket carries a guard over it as well as the two fixes.

**The invariant worth stating plainly: a node lends only when it was asked, and only the `const` branch asks.** Everything else that receives a value - a variable, a row selector, a list, a by-value operand - therefore owns what it is given, which is why `CleanupOperand` can release an `in` operand's value unconditionally and why an assignment can release what it displaces.
