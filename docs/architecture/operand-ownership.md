# Operand ownership

Who owns the value handed to a call's operand, and how the caller and the node that produced the argument agree about which of them releases it. The other half of [value lifetime](value-lifetime.md), which covers a value sitting in a stack slot, a row or a list. Part of the [Dataphor architecture](../architecture.md).

## An operand's owner depends on its modifier and on its argument

A call's arguments are evaluated by the caller, pushed into the callee's slots by `CallNode`, then cleaned up by `InstructionNodeBase.CleanupOperand`, which reads the operand's modifier:

- `var` - the callee's slot is an alias of a caller's slot. Nothing is copied and nothing is released; the cleanup writes the slot's final value back with a plain `Poke`, because the caller's slot already owned it. That write-back runs on every exit path, including a `raise`, so the caller sees the callee's last assignment either way. The cleanup releases nothing, but the body can, and does: an assignment to a `var` parameter - or a `foreach` over it - releases what the slot held, and the write-back then hands the caller the replacement. That is right only while the caller's slot owns the value it passed, so **a `var` operand whose argument names a slot holding a value that slot does not own is copied for the call** (`CallNode.ReferencesABorrowedSlot`) - a `foreach` loop variable, which the loop lends the row or element the iterator owns and goes on reading ([value-lifetime.md](value-lifetime.md)). The callee's slot then owns its value, and the invariant at the foot of this page holds for `var` as it does for everything else.

  A callee cannot make that decision - an operator is compiled once, independently of its call sites - so the call site makes it, from the one fact only it has: the compiler's mark on the caller's symbol (`Symbol.IsBorrowed`), read in the `var` branch of `InstructionNodeBase.DetermineDataType` and carried on the `StackReferenceNode` that argument compiled to. `CallNode` reconciles each such operand on the way out: where the slot still holds the copy, the body never wrote to the operand, so the copy is the call's to release and the write-back stores the caller's own value back into its slot, a no-op. Where the body did write, it released the copy itself and the slot's final value is the operator's output, which the caller's loop variable then holds until the next plain store into that slot - the next iteration's over a list, and over a cursor none at all, because `ForEachNode` fills its one row before the iteration rather than inside it. That last write-back leaks one value, because that next store displaces it without releasing it; it is the same accepted tradeoff as a direct assignment to a loop variable, measured equal to it, and recorded on the borrowed branch of `AssignmentNode`.
- `in` - the callee's slot holds a value of its own, and the cleanup releases it. `CallNode` hands the slot's current value back first, so a body that assigned to the operand released the displaced value itself and the cleanup releases its replacement.
- `const` - the callee's slot cannot be assigned to (the compiler makes a const operand's symbol constant), and whether the call owns the value is **not** a property of the modifier but of the plan node that produced the argument.

Only the node that produced the argument knows whether it already holds the value - a stack slot's, or a column of a row in one - or computed one nothing else holds, and the difference matters on nearly every call: the compiler promotes a by-value operand the body never assigns to to `const` (`Compiler.CompileOperatorBlock`), and every comparison, conversion, selector and property accessor generated for a scalar type declares `const` outright.

An argument that raises leaves the call unmade, and `ReleaseUncalledOperand` is that path's own rule: release the values the call owns among the arguments already evaluated, and leave every `var` operand alone - there is no callee value to write back, and writing one would run the type's constraints while an error unwinds.

## How a node says it is lending

Two virtuals on `PlanNode` (`src/engine/DAE/Runtime.Instructions/PlanNode.cs`):

- `SetByReference()` asks the node to return its value by reference rather than a copy, and answers whether it will.
- `ReturnsByReference` answers, afterwards, whether it does.

The const branch of `InstructionNodeBase.DetermineDataType` asks, once, while the call is compiled; `CleanupOperand` reads the answer back off the same node at run time and releases the value unless the node lent it. The store and the release therefore read one flag on one object. The question reaches whichever node is in the operand slot when asked, so a node that rewrites its own arguments must ask after the rewrite: ask first and the grant stays on the node underneath, where a consumer interposed later releases a value it was only lent (`bug-row-equality-change-breaks-implicitconversions`).

The nodes that can lend are the three that have something to lend: `StackReferenceNode` (a variable), `StackColumnReferenceNode` (a column of a row-typed variable) and `ExtractColumnNode` (`LR.B`, a column read out of a row). The third lends only when the row it reads from outlives the call - a source row the node disposes on its way out owns its column values, so lending one would hand back a value released before it could be read. `IndexerNode` (a list element) overrides `ReturnsByReference` but deliberately has no `SetByReference`: nothing asks it, so it always copies, and the override is there so that whoever changes that meets this rule rather than a silent leak.

A node that overrides `InternalExecute(Program)` is never reached by `CleanupOperand` and owes the rule itself. Most such nodes are table nodes, where that entry point is simply how a cursor is returned and no operand modifiers are in play. The set to know about is the thirteen that are operator nodes, and it is checked rather than counted: `tests/DAE.Server.Tests/OperandOwnershipShapeTest.cs` reflects every non-table `InstructionNodeBase` declaring that method and compares the set with a checked-in list of eighteen - the thirteen plus the five shapes that declare it. Three derive from `InstructionNodeBase` directly (`ExistsNode`, `TableToListNode`, `IfNilNode`); the other ten re-override the entry point from one of the five shapes, which skips that shape's own `CleanupOperand` while the node still reads as an ordinary instruction node, and are the dangerous ones - the hand count got them wrong once already. The guard reads the engine assembly only; the three nodes of this shape outside it - `InsertNode`, `CopyNode` and `CopyTablesNode` in `libraries/System.Integration` - have nothing stream-backed to release, and the fixture's `NOTE:` says when to widen it.

There are two halves to get right - reach `base.DetermineDataType`, so the question is asked, then release what the answer says this node owns - and a node of this shape can miss either. `IfNilNode` missed both in turn. The release half: it copied the argument it chose and released nothing where that argument was the call's own - one stream for the life of the session on every call over a computed `Binary` or `Graphic` (`bug-ifnil-leaks-the-value-it-copies`); it now reads `ReturnsByReference` off the node it chose. The order half: it asked before rewriting its own arguments, so a row conversion interposed afterwards destroyed the row in the variable it was lent; it now asks last, like the comparison nodes below (`bug-row-equality-change-breaks-implicitconversions`).

`RowEqualNode` and `CompoundScalarEqualNode` missed **both** halves (`bug-row-equality-leaks-the-rows-it-compares`): neither argument node was asked and neither copy released - a stream per stream-backed column per side on every comparison. Both now ask - after their own rewrite - and release each argument whose node answers `ReturnsByReference` false, raise path included. The generic-row branch hands the comparison it plans at run time a lending `ValueNode` subclass; a `NOTE:` there says why `ValueNode` itself does not lend. The rest of the set is sound: `ExistsNode` and `TableToListNode` dispose the cursor they opened; the table comparisons' operands are `in`, both cursors disposed; and the row extend and redefine nodes are compiled from expressions, with no operand modifiers to honour.

Skipping `base.DetermineDataType` *without* overriding the execute entry point costs a copy, not a stream: the argument node was never asked, so it copied, and the shape's own `CleanupOperand` releases the copy - list equality and `IndexOf` over a `list(Binary)` measured nought streams left behind. That is why the guard is one list and not two.

**The invariant worth stating plainly: a node lends only when it was asked, and only the `const` branch asks.** Everything else that receives a value - a variable, a row selector, a list, a by-value operand - therefore owns what it is given, which is why `CleanupOperand` can release an `in` operand's value unconditionally and why an assignment can release what it displaces.
