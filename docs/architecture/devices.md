# Devices

What a device does with the plan nodes it claims, and which devices ship. Part of the [Dataphor architecture](../architecture.md).

A device translates plan nodes it claims to support into a native command and leaves the rest to the engine (`Compiling/Visitors/DetermineDeviceVisitor`). `System.MemoryDevice` (in the engine) and `SimpleDevice` (memory plus file persistence) need nothing external. `SQLDevice` is the base for SQL translation (10k lines); `MSSQLDevice` and `PGSQLDevice` specialize it and call into a `SQLConnection` implementation (the Oracle, ADO and SAS device and connection libraries that did the same are parked under `legacy/libraries/` and not built). The connection base classes are in `src/engine/DAE/Connection` and `src/engine/Server/Connection`; the `Connection` library adds the generic ADO.NET connections over them, and the `ODBCConnection` library one more. Two of those reach a database through a provider that is a NuGet package rather than part of the framework: `Connection.OLEDBConnection` on `System.Data.OleDb`, which works on Windows only, and `ODBCConnection.ODBCConnection` on `System.Data.Odbc`, which needs an ODBC driver and a configured driver manager on the machine running the server. Neither package is touched until a device names its connection class, so a server registers both libraries on a machine that has neither provider installed.

**Where the SQL Server client is, and what it defaults.** The `SQLConnection` a SQL Server device uses is `Connection.MSSQLConnection`, in the server assembly (`src/engine/Server/Connection/MSSQL*.cs`), over the NuGet package `Microsoft.Data.SqlClient`. That assembly is the only one in the product that holds a SQL Server client: it is therefore also the one that clears the client's connection pools when a server is disposed (`Server.Dispose`), the engine assembly references no SQL client at all, and the SQL Server catalog store (`src/engine/Store.MSSQL`) shares this client rather than carrying one of its own - so a device and the catalog on one server reach SQL Server through the same driver.

**The connection defaults, and why they exist.** `Microsoft.Data.SqlClient` encrypts the connection by default and then checks that the server's certificate is one the machine trusts; `System.Data.SqlClient`, which this code used through release 3, did neither. A device definition or a `catalogstoreconnectionstring` written then names a server, a database and its credentials and nothing about encryption, so each of the two places a SQL Server connection string is built supplies what the old client negotiated - `Encrypt=False` - and a definition that says something about encryption overrides it. On the device that default is a parameter of `MSSQLADODotNetConnectionStringBuilder`, which gets the precedence right by construction: `SQLDevice.GetConnectionParameters` applies the device's and the device session's own `ConnectionParameters` after the builder has run. In the store it is a default in `MSSQLStore.InternalInitialize`, applied only when the connection string names neither `Encrypt` nor `TrustServerCertificate`, because a deployment that has set either has already said how that connection is protected. This is a compatibility decision rather than a view about encryption: what connected in 3.1 has to go on connecting, and a deployment that wants encryption asks for it. Which SQL Server versions the device and the store have actually been run against, and which combinations of certificate state and connection setting connect, is measured and recorded under [Which SQL Server versions work](../users-guide/dataphor-service.md#which-sql-server-versions-work).

**Where the translation is pinned.** What a SQL device sends is held to checked-in text under `tests/goldens/devices/<Device>/`, compared character for character by `DeviceTranslationGoldenTests` in `tests/DAE.Server.Tests` (one subclass per device). No database server takes part: the device's `ConnectionClass` names the recording connection of the test library `tests/libraries/TestFramework.SQLRecorder`, a `SQLConnection` that records the statements and parameters it is handed and opens nothing, and the device's own three connect-on-start settings (`ShouldDetermineVersion`, `ShouldEnsureDatabase`, `ShouldEnsureOperators`) are turned off. Two consequences are worth knowing. The goldens hold the translation for the device's *default* version assumption, because a device that never asks the server for its version never learns it - so they are not a substitute for running against a real server. And the recorder refuses any read it has not been explicitly armed to answer rather than returning an empty result, which is why only data definition and `insert` translation are covered this way: an `update` or a `delete` of a device table asks the device for the row itself, and answering that would mean being a database rather than recording one.

A device emits the same statement down two paths, and the goldens are taken off the shorter one. The `D4ToSQL` operator emits a device plan node's statement as the compiler left it; a real cursor open does not, because `SQLTable` rebuilds that statement first and can change it on the way (a deferred column becomes a `case` expression, a cursor restart appends a key condition). The golden corpus's query half goes through `D4ToSQL`, so one case reads a device table through the engine for real and asserts that what the connection was handed is the text `D4ToSQL` emits - otherwise a change to the rebuild would leave every query golden green while what a database server receives had moved.

A device's operator map is a D4 script in its own library (`Source/SystemCatalog.d4`), run once when the device registers, and each `create operator System.iFoo(table) class "SQLDevice.SQLFoo"` in it resolves its operator against the catalog before anything is translated (`Compiler.CompileDeviceOperatorMap`). A mapping that names an operator the engine no longer declares therefore fails the whole script, and the device does not register - which is why retiring a built-in operator means editing every device that maps it, in the same change.

NOTE: the parked Oracle and SAS catalogs under `legacy/libraries/` still map `System.iRedefine(table)`, which `debt-unreachable-redefine-nodes` retired from the engine along with the `MSSQLDevice` and `PGSQLDevice` mappings. Whoever revives one of those devices has to drop that line; nothing builds or runs those trees today, so nothing catches it first.
