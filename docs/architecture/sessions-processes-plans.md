# Sessions, processes, plans

How a connection becomes a session, a process, a plan and a cursor, and what compiles and executes them. Part of the [Dataphor architecture](../architecture.md).

A client **connects** and gets a *session* (`ServerSession`, one per login). A session starts *processes* (`ServerProcess`): a process is one logical thread of execution with its own transaction stack and device sessions. A process **prepares** a statement or expression into a *plan* (compile → bind → optimize into a tree of `PlanNode`s), **executes** or **opens** it, and for table results gets a *cursor*. Every one of these has a remote counterpart (`RemoteServerSession`, `RemoteServerProcess`, …) that the WCF service exposes by integer handle (`Service/HandleManager.cs`). In-process callers and tests use the `IServer*` interfaces in `src/engine/DAE/CLI.cs` directly.

A transaction level the process begins is begun on **every participant** it has used - each back-end database's session and each connection to another Dataphor server - and the commit asks them one at a time, with no protocol that can undo one that has already said yes. A commit that fails part-way therefore leaves the level committed on some participants and not on others, which the engine records on the transaction (`ServerTransaction.CommitBegun`). Such a level accepts no further work on any participant, reads included: it cannot be committed again, cannot have a level begun on top of it, and is refused with error 106213 at each seam where work reaches a participant (`ServerProcess.CheckNotHalfCommitted`). The session's only way out is to roll that level back, after which the enclosing transaction is clean and accepts work again.

Compilation is entirely in `Compiler.cs`; execution is interpretation of the plan-node tree (`PlanNode.Execute`). There is **no IL generation**: a `ShouldEmitIL` session flag is plumbed end to end but nothing reads it, and the one remaining `EmitInstructionIL` method (`ArithmeticNodes.cs`) is commented out.

## Debugger

A session can start a *debugger* (`Debug.Start()`, `src/engine/DAE/Debug/Debugger.cs`) and attach other processes, or whole sessions, to it. Execution yields to it at every breakable plan node: `PlanNode.Execute` calls `Program.Yield`, which calls `Debugger.Yield`, which parks the process on a wait handle for as long as a pause is requested. The debugger therefore pauses by *holding* every attached process inside that yield, and reports itself paused once a pause has been requested and every attached process that is running is parked - so a debugger that has requested no pause is never paused, however little is attached to it. Breakable nodes are the imperative statement nodes (`ImperativeNodes.cs`), the data-modification nodes (`DMLNode`, in `TableNodes.cs`) and the two `foreach` nodes (`ListNodes.cs`), one of which is compiled from a `foreach` *expression*. Instruction nodes are not breakable by default - `InstructionNodeBase`'s constructor says why, likening it to breaking into the processor's multiply - so a built-in operator such as an addition never stops; but `CallNode`, the invocation of a D4-defined operator, is an instruction node that opts back in. One consequence is visible to anyone stepping: a statement that calls an operator holds two breakable nodes at the same line, its own and the call's, so stepping off such a statement takes two steps.

Attaching a *session* rather than a process works in both directions: `Debugger.AttachSession` attaches every process the session is already running, and every process the session starts afterwards attaches itself, the `ServerProcess` constructor reading its session's `DebuggedByID` and finding the debugger through `Engine.GetDebugger`. `Debug.DetachSession`, and `Debug.Stop()` for every session the debugger holds, reverses both. Only a session a *client* opened can be attached at all: `ServerSession.SetDebuggedByID` refuses one whose `SessionInfo.CatalogCacheName` is empty, and that name is set for every connection the client library makes (`LocalServer.Connect`) and for none opened straight off the engine - so the server's own internal session cannot be debugged this way, and neither can a host that connects in process without going through the client.

A location is a *locator* plus a line and a line position, and there are three kinds of locator. Dynamic or ad-hoc execution gets `program:<guid>`, a fresh one for each program. A script run from a document gets `doc:<Library>:<Document>`, which is what the Frontend library's `ExecuteScript` and the IDE's editor set. An operator that a script with no document locator created gets `operator:<name><signature>`. The lines of an operator's body are compiled relative to its own `create operator` line (`Plan.CompilingOffset`), so a location inside the body is that relative line added to the line the operator's locator starts on: zero for an operator locator, which leaves the relative line as it is, and the declaration's own line for a document locator, which makes the result the line in the document. The catalog publishes both halves of each operator's locator, in `Operators.Locator` and `Operators.Line`.

A breakpoint is a locator, a line and a line position, matched exactly - except that a line position of `-1` matches any position on the line, which is what the IDE sets. Reading a paused program - its call stack, the variables of one frame, the source text behind a locator - goes through `Debug.GetCallStack`, `Debug.GetStack` and `Debug.GetSource`. The first two refuse unless the debugger is paused, and the stack window they read names variables positionally (`Location0`, `Location1`, ...) rather than by their D4 identifiers. `GetSource` needs a pause only for a `program:` locator, which it has to find among the executing programs of the attached processes; an `operator:` locator it answers out of the catalog by re-emitting the declaration, with no debugger involved at all.

Six things stop a program and five of them go through `Debugger.ShouldBreak`: a breakpoint that matches the running location; `Debug.StepInto`, which sets a stop-at-the-next-node flag on the process; `Debug.StepOver`, which records a depth; `Debug.SetBreakOnStart`, which makes `Program.ReportStart` set the step-into flag as each program the process runs starts; and `Debug.SetBreakOnException`, which makes `Program.ReportThrow` set it as an error is thrown - so that stop happens in the throwing node's own exception path, with the node already behind it. The sixth, `Debug.Pause`, asks for no decision and simply requests the pause. That difference is what the `DidBreak` column of `Debug.GetProcesses` reports: `Debugger.Yield` records a process in its broken set only when `ShouldBreak` was true. Its `Error` column carries the stopped program's error variable, which is set while a raise is unwinding and while an `except` handler runs (`RaiseNode` and `TryExceptNode`, which clears it again as the handler returns) - so break-on-exception is not the only stop that reports a value there: a breakpoint inside an `except` block does too.

Step over is depth-based, not line-based: `ServerProcess.SetStepOver` records the executing-program count and the stack call depth, and `InternalShouldBreak` stops the process when both match again, lowering each as the stack unwinds - so stepping over the last statement of an operator surfaces in its *caller*. Every step clears the pause request (`Debugger.InternalRun`), so a step with no next breakable node to reach ends the program instead of stopping it again; and a step while the debugger does not report itself paused does nothing at all, both `StepOver` and `StepInto` guarding on `IsPaused`.

Letting a held process go does not need the debugger to be run. `Debugger.Detach` disowns the process, clears its debugger and pulses the pause signal, and the wait inside `Debugger.Yield` falls out because its condition includes the process still being one the debugger holds; `Debugger.Dispose`, which is `Debug.Stop()`, does that for everything it holds. Shutdown depends on it: `Engine.TerminateProcessThread` detaches a *paused* debugged process itself for exactly this reason, so stopping a held process gets through, but it cannot unblock a process parked while the debugger does not report itself paused, and its budget - half of `ProcessTerminationTimeout` - then expires with `ProcessNotResponding`.

The IDE's debug window (`src/windows/Dataphoria/Debug/`) is the only thing that drives any of this.
