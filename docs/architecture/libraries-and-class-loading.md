# Libraries and class loading

What a library is, what registering one does, and how a D4 class name reaches a .NET type. Part of the [Dataphor architecture](../architecture.md).

A **library** is a directory `<Name>/` with `<Name>.d4l` (BOP XML: version, required libraries, files, default device, settings), `Documents/` and optionally `Upgrades/`. Registering a library (`LibraryUtility.RegisterLibrary`): register required libraries first; `Assembly.LoadFrom` each file marked `isassembly` from the library directory; register that assembly with the per-process `LibraryAssemblyResolver` (`Base.Windows/LibraryAssemblyResolver.cs`) so its private managed and native dependencies resolve from the library's own folder (and from the folders of the libraries it requires, transitively); read the assembly's `[DAERegister("…")]` attribute and call that class's static `GetClasses()` to get a *D4 class name → assembly-qualified type name* map; then run `Documents/Register.d4` with the library current, which creates the library's catalog objects (`create operator Foo(...) class "Lib.FooNode"`, `create device … class "MSSQLDevice.MSSQLDevice"`).

Everything D4 binds to C# goes through that name map (`ClassLoader.CreateObject` → `Type.GetType` → `Activator.CreateInstance` → set properties from attributes by reflection). Devices find their connection class the same way, so a device has no compile-time reference to a database driver. Assemblies are never unloaded. On the client, a class-loader miss downloads the library's files from the server and loads them (`LocalServer`, `Frontend.Client/Session.cs`), and a resolve hook (`Base.Windows/AssemblyUtility.cs`) matches assemblies by simple name.

**Upgrading a library.** Beside its descriptor and documents a library may hold an `Upgrades/` folder of numbered D4 scripts, `Upgrade.<major>.<minor>.<revision>.d4`, each the set of changes that takes the application from one revision to the next. Two version numbers decide what runs: the *descriptor* version (the `Version` column of the `Libraries` catalog table, read from the `.d4l` file) is what the files on disk claim, and the *recorded* version (the `LibraryVersions` catalog table, which `LibraryView` exposes as `LoadedVersion`) is what the catalog believes is applied. `UpgradeLibrary(name)` upgrades the library's requisites first, transitively, then runs every upgrade script of the library whose version is above the recorded version and not above the descriptor version, in version order - not in the order the directory lists the files, which would put `Upgrade.1.0.10.d4` before `Upgrade.1.0.2.d4` - and records the descriptor version once it finishes, whether or not any script ran, so a release may skip revisions. Each script runs in a transaction of its own on a session of its own owned by the library, and that transaction also advances the recorded version, so a run that fails partway leaves the recorded version at the last script that applied and the next run resumes from there. `UpgradeLibraries()` does all of that for every registered library, in requisite-first order, and stops at the first library whose upgrade fails - the libraries after it in that order are left un-upgraded, each still at its own recorded version, and nothing says which they were. `Dataphoria` calls `UpgradeLibrary` from the library node's menu.

The pending state - descriptor ahead of recorded - is what a server is in after a new version of a library has been copied over the old folder and the server restarted: loading a library reads the recorded version before loading and writes the same value back afterwards, deliberately, so that a restart does not swallow a pending upgrade. `LibraryUpgradeRestartTest` pins that preservation by raising a library's descriptor version on disk while the server is stopped and asserting, after the start, both that the upgrade is pending and that the recorded version did not move - a real stop and start being the one thing a coverage script cannot do. `InjectUpgrade(name, script)` is the other side of the same mechanism and does not apply anything: it is how a developer records a change already made on their own server, bumping the descriptor revision by one and writing the script as that revision's file - and because changing a registered library's version carries the recorded version with it, an inject leaves nothing pending. `SaveUpgrade` and `DeleteUpgrade` edit the folder without touching either version number, which is what the IDE's upgrade editor does.

**What a new version may bring, and what a restart cannot.** An upgrade's payload is whatever a release changed, not only a table: `LibraryUpgradeRestartTest` applies one that creates a device and a table in that device inside the single transaction the machinery opened for it, where the row reading back afterwards is what says the device started, and one that adds a form document, which goes through the Frontend device and lands as a file in the library's own `Documents/` folder. The one payload a restart cannot pick up in a running process is a changed **assembly**: assemblies are never unloaded, and `Assembly.LoadFrom` on another copy with the same identity returns the instance already loaded, so stopping and starting the `Server` object goes on running the old build. Only restarting the host process picks up a new one - which is what a deployment does, the installer stopping the Windows service first, and also why no in-process test can cover an upgrade whose new operators name classes that only the new assembly ships.

**What an upgrade script may do.** It runs with implicit transactions off, inside the one transaction the machinery opened for it, and it may use the catalog as any other script does - including `UpgradeLibrary` on a library that is not one of its own requisites, which `Frontend`'s `Upgrades/Upgrade.2.0.8.d4` does to pull `System.Internet` up with it. It may also discard that transaction and work outside one, which the same script does, **but it must leave a transaction open when it returns**: the machinery records the version and commits on the script's own process afterwards, so a script that rolls back and does not begin again fails with "No transaction in progress for this process" and the upgrade is reported as failed after its work has already been committed. `LibraryUpgrades.d4` pins both.

**Library DDL is not transactional.** A library's descriptor and its folder are files rather than catalog rows, so the operators that write them - `CreateLibrary`, `DropLibrary`, `RenameLibrary`, `SetLibraryDescriptor`, `SetDefaultDeviceName` and the requisite, file and setting operators beside them - take effect when they run and record nothing for a rollback to replay: a transaction that calls one and then rolls back leaves the change on disk. Registering and unregistering a library are ordinary catalog changes and *are* rolled back normally; what stands outside the transaction is the directory and the `.d4l` file, not the catalog objects `Documents/Register.d4` creates. For all but one of them the repair is to run the inverse statement - a rolled-back `CreateLibrary` leaves an unwanted library, which a drop removes, and `RenameLibrary` moves the folder rather than deleting it, so the inverse rename puts it back. `DropLibrary` is the exception: it deletes the library's folder recursively and no rollback can restore a folder, so it alone **refuses inside an explicit transaction**, with error 113251 raised before anything is removed. Explicit here means a transaction the session opened itself: a `BeginTransaction()`, a `commit` block (which the parser desugars into one), or a client's begin, and also one the engine began implicitly and then left open because implicit transactions were switched off during that statement. It does not mean the per-statement transaction the engine opens and commits around an ordinary statement, so a script, or the IDE deleting a row of `Libraries`, drops a library as before. The check is in `LibraryUtility.DropLibrary`, so the `DropLibrary` operator and a `delete` against the `System.Libraries` catalog table behave alike. One caller is refused by design: an upgrade script runs inside the transaction the upgrade machinery opened for it, which can roll back after the folder is gone, so an upgrade script cannot drop a library.
