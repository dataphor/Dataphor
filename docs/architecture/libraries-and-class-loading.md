# Libraries and class loading

What a library is, what registering one does, and how a D4 class name reaches a .NET type. Part of the [Dataphor architecture](../architecture.md).

A **library** is a directory `<Name>/` with `<Name>.d4l` (BOP XML: version, required libraries, files, default device, settings), `Documents/` and optionally `Upgrades/`. Registering a library (`LibraryUtility.RegisterLibrary`): register required libraries first; `Assembly.LoadFrom` each file marked `isassembly` from the library directory; register that assembly with the per-process `LibraryAssemblyResolver` (`Base.Windows/LibraryAssemblyResolver.cs`) so its private managed and native dependencies resolve from the library's own folder (and from the folders of the libraries it requires, transitively); read the assembly's `[DAERegister("…")]` attribute and call that class's static `GetClasses()` to get a *D4 class name → assembly-qualified type name* map; then run `Documents/Register.d4` with the library current, which creates the library's catalog objects (`create operator Foo(...) class "Lib.FooNode"`, `create device … class "MSSQLDevice.MSSQLDevice"`).

Everything D4 binds to C# goes through that name map (`ClassLoader.CreateObject` → `Type.GetType` → `Activator.CreateInstance` → set properties from attributes by reflection). Devices find their connection class the same way, so a device has no compile-time reference to a database driver. Assemblies are never unloaded. On the client, a class-loader miss downloads the library's files from the server and loads them (`LocalServer`, `Frontend.Client/Session.cs`), and a resolve hook (`Base.Windows/AssemblyUtility.cs`) matches assemblies by simple name.

**Upgrading a library.** Beside its descriptor and documents a library may hold an `Upgrades/` folder of numbered D4 scripts, `Upgrade.<major>.<minor>.<revision>.d4`, each the set of changes that takes the application from one revision to the next. Two version numbers decide what runs: the *descriptor* version (the `Version` column of the `Libraries` catalog table, read from the `.d4l` file) is what the files on disk claim, and the *recorded* version (the `LibraryVersions` catalog table, which `LibraryView` exposes as `LoadedVersion`) is what the catalog believes is applied. `UpgradeLibrary(name)` upgrades the library's requisites first, transitively, then runs every upgrade script of the library whose version is above the recorded version and not above the descriptor version, in version order - not in the order the directory lists the files, which would put `Upgrade.1.0.10.d4` before `Upgrade.1.0.2.d4` - and records the descriptor version once it finishes, whether or not any script ran, so a release may skip revisions. Each script runs in a transaction of its own on a session of its own owned by the library, and that transaction also advances the recorded version, so a run that fails partway leaves the recorded version at the last script that applied and the next run resumes from there. `UpgradeLibraries()` does all of that for every registered library; `Dataphoria` calls `UpgradeLibrary` from the library node's menu.

The pending state - descriptor ahead of recorded - is what a server is in after a new version of a library has been copied over the old folder and the server restarted: loading a library reads the recorded version before loading and writes the same value back afterwards, deliberately, so that a restart does not swallow a pending upgrade. `InjectUpgrade(name, script)` is the other side of the same mechanism and does not apply anything: it is how a developer records a change already made on their own server, bumping the descriptor revision by one and writing the script as that revision's file - and because changing a registered library's version carries the recorded version with it, an inject leaves nothing pending. `SaveUpgrade` and `DeleteUpgrade` edit the folder without touching either version number, which is what the IDE's upgrade editor does.
