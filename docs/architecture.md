# Dataphor architecture

How the system fits together as of the last 3.1-era commit (2019), written as the orientation map for the modernization. Where the modernization changes something, the change is described in [modernization-plan.md](modernization-plan.md); this document describes what exists. Paths are those of the reorganized repository; the plan's [old → new table](modernization-plan.md#repository-layout) maps the paths used before it.

## The idea in one paragraph

An application is written as a **D4 library**: scripts that declare types, tables, views, constraints, references and operators, plus optional form documents. The **Dataphor server** compiles D4, stores the resulting catalog, and executes queries by pushing as much as it can down to SQL back ends through **devices** and doing the rest itself. The **Frontend** library looks at the catalog — keys, references, metadata tags — and *derives* user-interface forms (browse, edit, add, lookups, master/detail) as XML documents. A **client** downloads a form document, builds a tree of UI nodes from it and binds the nodes to live server cursors. A customer's system is therefore mostly D4 and tags, with hand-customized forms and occasional C# extensions.

## Sessions, processes, plans

A client **connects** and gets a *session* (`ServerSession`, one per login). A session starts *processes* (`ServerProcess`): a process is one logical thread of execution with its own transaction stack and device sessions. A process **prepares** a statement or expression into a *plan* (compile → bind → optimize into a tree of `PlanNode`s), **executes** or **opens** it, and for table results gets a *cursor*. Every one of these has a remote counterpart (`RemoteServerSession`, `RemoteServerProcess`, …) that the WCF service exposes by integer handle (`Service/HandleManager.cs`). In-process callers and tests use the `IServer*` interfaces in `src/engine/DAE/CLI.cs` directly.

A transaction level the process begins is begun on **every participant** it has used - each back-end database's session and each connection to another Dataphor server - and the commit asks them one at a time, with no protocol that can undo one that has already said yes. A commit that fails part-way therefore leaves the level committed on some participants and not on others, which the engine records on the transaction (`ServerTransaction.CommitBegun`). Such a level accepts no further work on any participant, reads included: it cannot be committed again, cannot have a level begun on top of it, and is refused with error 106213 at each seam where work reaches a participant (`ServerProcess.CheckNotHalfCommitted`). The session's only way out is to roll that level back, after which the enclosing transaction is clean and accepts work again.

Compilation is entirely in `Compiler.cs`; execution is interpretation of the plan-node tree (`PlanNode.Execute`). There is **no IL generation**: a `ShouldEmitIL` session flag is plumbed end to end but nothing reads it, and the one remaining `EmitInstructionIL` method (`ArithmeticNodes.cs`) is commented out.

## Catalog and catalog store

The **catalog** is the set of all schema objects. In memory it is `Schema.Catalog`, loaded lazily: on a name-resolution miss the catalog device reads the object's *D4 script* from the store and compiles it (`ServerCatalogDeviceSession`, `NameResolutionCache`, `ClassLoader`). The **catalog store** (`Device.Catalog/CatalogStore.cs`) is a small ISAM-style layer over a SQL database: 27 `DAE*` tables — object headers and scripts (`DAEObjects`, `DAECatalogObjects`, `DAEOperators`, …), dependencies, loaded libraries and versions, registered classes, **and data that exists nowhere else**: users, roles, rights and assignments, device users with their encrypted external passwords, and server settings.

`SQLStore` (`DAE/Store`) abstracts the back end; `SQLStoreConnection` emulates nested transactions with an undo log of inverse statements; `SQLStoreCursor` implements seek/range navigation by generating `select … where … order by` statements.

**Store transactions** (`ServerCatalogDeviceSession`, "Catalog Store" and "Transaction" regions). A catalog device session takes its store connection from the pool in `CatalogStore` for each read or write and gives it back when it is done, except while it has a store transaction open:

- Reads run in autocommit; on SQLite in write-ahead-logging mode each statement reads its own committed snapshot and never waits for the writer.
- A process transaction's store write transaction begins at its first store write, or earlier, at its first statement that changes the catalog (`DDLNode.InternalBeforeExecute` → `CatalogDeviceSession.BeginStoreWriteTransaction`), and covers every open transaction level at once. On SQLite it is begun immediate, so it takes the store's single write lock and holds it until that process transaction ends; a transaction that only reads never takes it. The store's transaction count is 0, or the number of open levels down to the deepest one that has written; it never exceeds the session's open levels, and an inner level that did not write ends without touching the store.
- **Lock order: the store's write lock before the catalog's lock.** Drops and alters write the store inside `lock (program.Catalog)`, and a session holding the store's write lock may be waiting for that lock, so a session that waited for the store's lock inside it would deadlock until the busy timeout. That is why DDL statements take the store's lock before they run; in Debug builds an assertion at the store begin fails if the catalog's lock is held. DDL that already runs inside the catalog's lock skips that early begin, which can no longer come before the lock; such DDL must write nothing to the store (an application transaction's copy of a table, made inside that lock when a statement first references the table, writes none), and a store write there still meets the assertion at its first write. Other engine locks (the library list's, for instance) are not checked, and library registration still writes inside one.
- Until the store transaction ends the session keeps its connection and every store read of the session goes through it, so a transaction sees its own uncommitted writes (the dependents check of a drop, for example). A transaction that read before its first write read committed data from before its write lock; conflicting creates are caught by the store's keys and the engine's catalog lock.
- D4 queries over the catalog tables that the store answers (`CatalogDeviceTable`) open a connection of their own and see committed data only, not the calling transaction's uncommitted store writes.
- A wait for the write lock longer than the store's `BusyTimeout` (30 s by default) raises 130103. A session whose client disappears while its transaction holds the write lock blocks every other session's catalog changes until the server reclaims the connection, which releases the lock by rolling the transaction back. What keeps a connection from being reclaimed is the client's keep-alive ping and nothing else — not the network channel, which the client silently rebuilds after a fault — so a client that has stopped pinging is relinquished between 300 and 375 seconds later by the server's idle watcher (`Service/ConnectionManager.cs`; the shipped client pings every 120 seconds). Those are the numbers a deployment serves, and a host application can serve others by setting `DataphorServiceHost.ConnectionIdleTimeInSeconds` before it starts — the only caller that does is the test suite, which cannot wait five minutes to watch a reclamation happen. That the ping and nothing else holds a connection was measured across a process boundary, not only read: a client process killed outright kept its session for at least 25 seconds at the default threshold and lost it within the watcher's window at a short one (`AbandonedClientProcessTest`). Sessions reached through the **native CLI** have a watcher of their own, `Service/NativeSessionManager.cs`, because that interface hands out sessions rather than connections. Each native session carries a clock that every call naming its handle moves, and the shipped native client (`NativeCLISession`) pings every 120 seconds so that a session it holds but is not using keeps that clock moving; a session nothing has called for the threshold — also 300 seconds, settable before start through `DataphorServiceHost.NativeSessionIdleTimeInSeconds` — is stopped, which rolls its transaction back and releases the write lock. One difference from the connection watcher: a native session with a call in flight on it is never reclaimed, because every operation on it goes through one place that counts the calls in flight, which a connection has no equivalent of.

The default store is **SQLite** (`Server.DefaultCatalogStoreClassName`, returned by `Server.GetCatalogStoreClassName()` when the setting is empty), a file at `<instance>\Catalog\DAECatalog.sqlite`. The store class and connection string are per-instance settings (`catalogstoreclassname`, `catalogstoreconnectionstring`; `%CatalogPath%` is substituted). One other store ships, **SQL Server** (`Alphora.Dataphor.DAE.Store.MSSQL.MSSQLStore,Alphora.Dataphor.DAE.MSSQL`), which keeps the catalog in a SQL Server database and forces `MultipleActiveResultSets=True` into its connection string because the catalog opens a second store cursor while a first is still open; both host executables reference both store projects, because an assembly the layout ships but the host's `.deps.json` does not name cannot be loaded by class name on .NET 10. An instance whose settings still name the 3.1 SQL Server Compact store, or a `.sdf` connection string, does not start (error 115108, checked in `ServerCatalogDevice.InternalStart`); a store class that cannot be loaded raises 115107.

## Libraries and class loading

A **library** is a directory `<Name>/` with `<Name>.d4l` (BOP XML: version, required libraries, files, default device, settings), `Documents/` and optionally `Upgrades/`. Registering a library (`LibraryUtility.RegisterLibrary`): register required libraries first; `Assembly.LoadFrom` each file marked `isassembly` from the library directory; register that assembly with the per-process `LibraryAssemblyResolver` (`Base.Windows/LibraryAssemblyResolver.cs`) so its private managed and native dependencies resolve from the library's own folder (and from the folders of the libraries it requires, transitively); read the assembly's `[DAERegister("…")]` attribute and call that class's static `GetClasses()` to get a *D4 class name → assembly-qualified type name* map; then run `Documents/Register.d4` with the library current, which creates the library's catalog objects (`create operator Foo(...) class "Lib.FooNode"`, `create device … class "MSSQLDevice.MSSQLDevice"`).

Everything D4 binds to C# goes through that name map (`ClassLoader.CreateObject` → `Type.GetType` → `Activator.CreateInstance` → set properties from attributes by reflection). Devices find their connection class the same way, so a device has no compile-time reference to a database driver. Assemblies are never unloaded. On the client, a class-loader miss downloads the library's files from the server and loads them (`LocalServer`, `Frontend.Client/Session.cs`), and a resolve hook (`Base.Windows/AssemblyUtility.cs`) matches assemblies by simple name.

## Devices

A device translates plan nodes it claims to support into a native command and leaves the rest to the engine (`Compiling/Visitors/DetermineDeviceVisitor`). `System.MemoryDevice` (in the engine) and `SimpleDevice` (memory plus file persistence) need nothing external. `SQLDevice` is the base for SQL translation (10k lines); `MSSQLDevice` and `PGSQLDevice` specialize it and call into a `SQLConnection` implementation (the Oracle, ADO and SAS device and connection libraries that did the same are parked under `legacy/libraries/` and not built). The connection base classes are in `src/engine/DAE/Connection` and `src/engine/Server/Connection` (the `.cs` files of the same names under `libraries/Connection/Source` are uncompiled leftovers).

## Frontend: from schema to screen

Server side (`libraries/Frontend`, assembly `Alphora.Dataphor.Frontend.Server`): a device that exposes each library's `Documents/` folder as tables, plus the derivation pipeline `Derivation → Elaboration → Structuring → Production` that turns a query expression and a page type into a form document.

A **form document** is BOP XML describing a node tree (`.dfd`). A **customized form** (`.dfdx`, DILX) names one or more ancestor documents — themselves D4 expressions such as `.Frontend.Derive('Lib.Table', 'Browse')` — and a delta to merge onto them. The merge (`Inheritance.Merge` in `src/engine/Base/BOP`, reachable from D4 as `Frontend.Merge`, with `Frontend.Difference` for its inverse) matches nodes by `bop:name` and can add a node, change or reset an attribute and reorder siblings — but it has **no operation that removes a node**: `Inheritance.Diff` walks the children of the modified document, so a node only the ancestor has contributes nothing to the delta. A customization overrides what it inherits; it cannot delete it. `FormCustomizationTest.SyntheticRoundTrip_ElementRemoved_IsNotExpressible` pins that, so adding a deletion operation means coming past it deliberately.

Client side: `Frontend.Client.Session.SetApplication` asks the server which node types and library files the application needs; `Host.Load` evaluates the form's document expression through `Pipe` (which calls `LoadIfNecessary(expr, crc)` over the ordinary D4 session and keeps a CRC-validated cache), then `BOP.Deserializer` maps element names to .NET types via a node type table (`*.dnt`) and builds the tree. `Frontend.Client` holds the platform-neutral nodes (sources, actions, modules); `Frontend.Client.Windows` holds the WinForms implementations. A `ScriptAction` node compiles C# or VB at run time (CodeDom).

## Hosting, protocol, discovery

`DataphorServiceHost.Start()` (assembly `Alphora.Dataphor.DAE.Server.Hosting`) loads the instance from `%ProgramData%\Alphora\Dataphor\4\Instances\ServerConfigurations.config` - the folder carries the major version so that installations of different major versions do not share the list, and `InstanceManager.InstanceDirectory` or the environment variable `DATAPHOR_INSTANCE_DIRECTORY` points a process at a folder of its own, which is how a server is started without touching machine state - starts the `Server`, and serves three WCF services, all on one custom binding (binary message encoding over TCP, no security, 2 GB limits, infinite timeouts):

| Service | Address | Contract |
|---|---|---|
| Main | `net.tcp://<host>:<port>/<instance>/service` (default port 8061) | `IDataphorService`, 88 operations, handle-based |
| Native CLI | `…/<instance>/service/native` | `INativeCLIService`, 11 operations |
| Listener | `net.tcp://<host>:8060/listener/service` | `IListenerService`: instance name → URI |

The services themselves (`src/engine/Server/Service/`, `src/engine/Server/NativeCLI/NativeCLIService.cs`) are hosted on **CoreWCF**, by two .NET Generic Hosts in the process. One, inside `DataphorServiceHost`, carries the instance's own two endpoints on the instance's port. The second, inside `ListenerServiceHost`, carries the listener on the shared listener port, and is separate because one listener per machine serves every instance on it: a server that cannot take the listener port must still start and still serve its own endpoint, which on a single host a failed bind would prevent. Both hosts listen on `net.tcp://<HostName>:<port>/` with no path — for a host name CoreWCF opens two sockets on that port, `0.0.0.0` and `[::]`, so both address families are served — and register absolute endpoint addresses; the host name defaults to the machine name, and the paths are what calls are dispatched on. Kestrel opens no HTTP endpoint of its own. The one binding is therefore declared twice - the client's in `DataphorServiceUtility`, the host's in `DataphorServiceHostBinding` - because the two stacks' `Binding` types are unrelated; `CoreWcfProtocolTest` compares the two declarations so that neither can be changed alone. Each declaration is reached through a hook of its own, so a deployment can replace what a server listens with from its own start-up code as it can replace what a client connects with: `DataphorServiceHostHooks.BuildBindingCall` is the host's, `DataphorServiceUtility.BuildBindingCall` the client's, and `DataphorServiceHostHooks.ServiceBuilderHook` gets a last look at each host's CoreWCF service builder once its endpoints are added, which is where service credentials such as a server certificate are installed. Supplying a binding that way is the only route there has ever been to a secured transport: none of the product's own secured-connection settings reaches a binding, so a connection to a Dataphor server is unsecured unless a site's own start-up code supplies one - `DataphorServiceUtility.BuildBindingCall` for what a client connects with, `DataphorServiceHostHooks.BuildBindingCall` for what a server listens with. Those settings are no longer ignored in silence, though they are still not honoured. A client connection whose security mode asks for transport security is refused, with a message naming the setting and both remedies; an instance configured to require a secured connection starts anyway, and a D4 server link whose metadata asks for one connects anyway, each writing a warning to the server's log. Refusing rather than warning on the client is because the person who set an alias is the person connecting, and the cost of refusing is one failed connection; refusing to start a server would take an instance down for every client of it over a setting that has never worked. Transport security as a designed capability of the product - a credential type, a server certificate, an administrator's guide - is WS11's work; see decision D17 in [modernization-plan.md](modernization-plan.md#decisions).

Both hosts sit inside **one more Generic Host**, the host *program* (`DataphorHost`, assembly `Alphora.Dataphor.DAE.Host`), which `src/hosts/DAEServer` and `src/hosts/DAEService` are each a one-line `Main` over: the same program under the two file names existing scripts and service registrations use. Its command line is the one 3.1 took (`-i`/`-install`, `-u`/`-uninstall`, `-r`/`-run`, `-n`/`-name <instance>`); `-i` and `-u` register and remove the Windows service through `ServiceUtility`. Running as a Windows service is not a separate code path: `UseWindowsService` replaces the host lifetime only when the service control manager really started the process, so a console session and a service differ only in their lifetime and in where the host's own log lines go (a single-line console writer, or the event log the server already uses). The program's logger carries host lifecycle only - the instance starting, started, the listener state, stopping, stopped, failures; the server's own log file and event-log writes are its own and unchanged.

Stopping goes in one order, outward in: the listener host, then the instance's host (each bounded at ten seconds for Kestrel to close open connections, after which it aborts them), then the WCF service object - whose disposal signals the connection manager's idle watcher and waits up to ten seconds for a sweep it is in the middle of, so that no sweep is still reading the server when it is torn down - then the `RemoteServer`, then the engine's `Server.Stop()`, which ends the sessions and closes the catalog store. Network first so that no new work arrives, engine last. The program bounds the whole shutdown at sixty seconds; past that the host stops waiting and the process exits with the engine's stop unfinished, which is the same situation as the process being killed.

The server interfaces (`src/engine/Server/Contracts`) and the client's asynchronous copies (`src/protocol/Client/Contracts` for the main service, `src/protocol/Common/Contracts` for the listener, `src/protocol/NativeCLI` for the native CLI) are separate declarations of the same contracts; `ContractParityTest` holds them in step by comparing the two declarations of each contract by reflection. `RemoteServerObject` still derives from `MarshalByRefObject`, a leftover from the pre-WCF protocol; the remoting leases it used to manipulate are gone (`server-remove-remoting-and-dtc`) and the base class has no behaviour on .NET 10. A client alias (`Aliases.config`) is either a connection alias (host, instance, port) or an in-process alias that starts a server inside the client process.
