# Dataphor modernization plan

Master plan for bringing Dataphor from .NET Framework 4.5.2 (last release line 3.1, last commit October 2019) to a maintained product on .NET 10, so that the applications built on it — first among them a medical system that has been unable to take platform updates for over a decade — can move to current operating systems and runtimes without being rewritten.

Companion documents: [architecture.md](architecture.md) (how the system works today) and [../AGENTS.md](../AGENTS.md) (working rules for agents). The evidence behind the claims here is reproducible with [../tools/net-spike](../tools/net-spike/README.md).

## How to use this document

- Work is organized into **workstreams** (WS1…WS14). Each has an objective, the current state, the target, design notes, and a table of **work items** sized to become one ticket each (or one `plan/` ticket that splits further). Work-item slugs are suggestions for ticket slugs.
- **Decisions** (D1…) are recommended defaults. Treat them as settled unless the owner overrides one; do not reopen them inside a ticket. **Open questions** (Q1…) need the owner; a work item that depends on one says so, and should be filed to `blocked/` with the proposed default if it is reached before the answer.
- **Known defects** (K1…) are bugs already found. Each names the workstream that fixes it.
- Tickets should carry `architecture: docs/modernization-plan.md#<section-slug>` (for example `#ws3-test-suite`).
- "Verified" means observed by running code during the baseline survey; "static" means inferred from reading code.

## Goals and non-goals

Goals, in priority order:

1. **Existing applications keep working.** D4 libraries, catalog rebuild scripts and form documents built for 3.x run on the new release with no changes, or with a short documented list of them ([migration-notes.md](migration-notes.md)). Custom C# extensions are recompiled; catalogs are rebuilt, not converted.
2. **Supported platform.** Everything shipped runs on .NET 10 (long-term support until November 2028) on current Windows, builds with the `dotnet` CLI alone, and has no dependency that is out of support.
3. **A safety net.** A comprehensive automated test suite, runnable by one command, that makes later change safe.
4. **Operability.** A real installer with upgrades, a server that installs and runs as a service without hand steps, usable diagnostics, current documentation in Markdown.
5. **A cleaner codebase** — dead code removed, dependencies from NuGet, one build, one version.

Non-goals for this program: redesigning the D4 language, the wire protocol or the UI; a new web or mobile client; Linux or container support for the server (do not make it harder, do not chase it); performance work beyond "not slower than 3.1".

## Decisions

| # | Decision | Rationale |
|---|---|---|
| D1 | Target **.NET 10**, `net10.0` for engine/server/libraries and `net10.0-windows` for UI. Latest C# language version; nullable reference types stay **off**; no style or naming churn. | LTS; the code compiles as-is, so churn buys nothing and costs history |
| D2 | **.NET 10 is the only target. No .NET Framework build of anything.** | Owner's decision. It removes multi-targeting, conditional compilation for remoting/WCF hosting/SQL CE, and a doubled test matrix. The price is that there is no side-by-side reference runtime; the D4 coverage scripts (about 2,100 assertions written against the old runtime's behaviour) are the oracle instead, and Windows NLS globalization is selected explicitly so string comparison and culture behaviour match what .NET Framework did |
| D3 | **SQLite is the catalog store. SQL CE is deleted outright and existing catalogs are not migrated** — a catalog is rebuilt from the application's scripts, which is already routine maintenance for deployed applications. The SQL Server store stays if it ports trivially. | SQL CE has no modern .NET provider; the SQLite problem is solved (WS4); owner's decision on migration |
| D4 | **Keep the WCF contracts and wire format.** Server on CoreWCF, clients on the `System.ServiceModel.*` client packages. No protocol redesign in this program. Clients and server are upgraded together; interoperability with 3.1 binaries is not a requirement. | 88-operation contract with a client-side cache built around it; least change |
| D5 | **Keep WinForms** for the Windows client and Dataphoria, ported in place. Replace removed controls with their modern equivalents; do not redesign screens. | Form documents bind to these node implementations; pixel-level sameness is a feature for a validated medical application |
| D6 | **Remove** Silverlight and the WebForms web client. **Park** (exclude from the build, keep in the tree under `legacy/`) the top-level `Dataphoria/` web and cloud prototypes and the FHIR, CQF and PHINVADS libraries. | Confirmed by the owner. Anything built on the web client is rewritten separately |
| D7 | Product version **4.0**. Assembly names, namespaces, D4 class names and file formats unchanged. Sign every build (all configurations) with `Dataphor.snk`. | Names are recorded in catalogs, `.d4l` files and form documents; signing keeps one identity per assembly |
| D8 | **NUnit** stays the C# test framework; **D4 scripts** stay the main form of engine regression test. | Existing investment; scripts are runtime-independent |
| D9 | Documentation is **Markdown under `docs/`**, readable on GitHub with no site generator. A generator can be added later without changing the sources. | Lowest friction for agents and humans |
| D10 | Installer: **WiX SDK-style project**, built by `dotnet build`, one per-machine x64 MSI from a **self-contained** publish, `MajorUpgrade` with the existing `UpgradeCode`. | No runtime prerequisite on locked-down machines; upgrades work |
| D11 | Dependencies come from **NuGet with central package management**. A binary stays in git only when no package exists, with a note saying why. | Reproducible builds, vulnerability scanning |
| D12 | **No history rewrite.** Large and dead files are removed by ordinary commits. | 1,551 commits of `git blame` are an asset |
| D13 | Compiling the catalog or plans to assemblies is **research** (WS14), started only after the Windows client runs on .NET 10. | It is an optimization and a redesign; it needs the test suite and a baseline first |
| D14 | **Reorganize the repository first**, to the layout in [Repository layout](#repository-layout), by pure `git mv` commits. Assembly names, namespaces and D4 library names do not change — only directories and project file names. | Owner's request. Every later ticket then works in the final structure; moving after projects are converted would mean doing the path work twice |
| D15 | **SQL Server and PostgreSQL are the supported devices** for this program, SQL Server first. Oracle, ODBC and OLE DB support is kept only where it converts without effort; otherwise it is parked for later. | The application in hand uses SQL Server; PostgreSQL has other users (owner) |
| D16 | **Application work is deferred.** Changes an application or a custom extension could notice are recorded as they are made in [migration-notes.md](migration-notes.md). No customer names, paths or schema details are written into this repository. | Owner's sequencing: modernize Dataphor first. The repository is public |
| D17 | **4.0 provides no transport security.** The binding both halves of the protocol build is unsecured, and none of the product's own secured-connection settings - a client alias's security modes, an instance's `requiresecureconnection`, a D4 server link's `UseSecureConnection` tags - reaches a binding, as none ever did. A site that needs an encrypted channel supplies its own binding through the client hook `DataphorServiceUtility.BuildBindingCall` and the host hook `DataphorServiceHostHooks.BuildBindingCall`. The settings are kept and a request for a secured connection is **reported** rather than silently ignored: refused on the client, warned in the server's log for an instance or a server link. Transport security as a designed capability is WS11's (`security-transport-design`, `security-transport`), and fail-closed - an instance that requires security and cannot get it refusing to start - goes with it. | The settings cannot express a working configuration (there is no certificate or credential-type setting to configure a secured binding from), so making them work means designing security, which the plan already says needs owner sign-off; removing them would churn two file formats, a public C# API and two D4 metadata tags to add the same vocabulary back when WS11 lands |

**Rules for the move.**

- Delete and park first, then move what is left; there is no point relocating dead code.
- A move commit contains **only renames** (`git mv`), no content edits, so that Git records exact renames and `git log --follow` and `git blame` keep working across the move. Reference fixes (project paths, solution, scripts, documentation) go in the commits after it.
- Case-only renames (`Libraries` → `libraries`, `Tests` → `tests`, `External` → `external`) need two steps on Windows (`git mv Libraries libraries.tmp`, then to `libraries`).
- Proof that the move changed nothing: `tools/net-spike` gives the same results before and after (update its path tables in the reference-fix commit).
- The same work item updates `AGENTS.md`, `README.md`, `docs/architecture.md`, `tickets/index-config.json` and the paths cited in this plan. `README.md`'s links into `Documentation/` stay until WS8 repoints them; Appendices A and B keep the paths they were measured on.
- The server discovers libraries as the immediate subfolders of each directory in its `LibraryDirectories` setting (a semicolon-separated list), so splitting shipped, sample and test libraries into separate source folders is safe; the runtime layout recombines them.

## WS1 Build and workspace

**Objective.** One command builds everything that ships; one command tests it; both work on a clean clone with only the .NET 10 SDK.

**Current state.** 88 legacy-format csproj files with explicit file lists, seven solutions (one current), per-project `AssemblyInfo.cs` versions (`3.1.*`), signing only in Release, core assemblies built into a shared `bin` folder per area (`src/<area>/bin`), library assemblies built *into their source folders* next to the `.d4l`, third-party DLLs tracked in `external/`, packages restored to a gitignored `packages/` at the root. `Dataphor.proj` and two batch files assembled a `Deploy/` tree by wildcard copy (both since deleted).

**Target.**

- The directory structure in [Repository layout](#repository-layout).
- SDK-style projects with unchanged assembly names, sharing settings through a root `Directory.Build.props` (target framework, language version, version number, signing, deterministic builds, NLS globalization, warning baseline) and `Directory.Packages.props`. The warning baseline must leave `WFDEV006` and the `SYSLIB` obsoletion warnings visible: on .NET 10 several removed APIs compile and then throw at run time.
- One root solution, `Dataphor.slnx`, with solution filters for the engine/server set and the Windows UI set.
- `global.json` pinning the .NET 10 SDK (present since Phase 0).
- A **runtime layout** produced by the build: `artifacts/layout/<Configuration>/bin/` (hosts and core assemblies) and `artifacts/layout/<Configuration>/Libraries/<Name>/` (each library's `.d4l`, `Documents/`, `Upgrades/`, its assembly and that assembly's private dependencies). Tests, local runs and the installer all consume the layout. Nothing is built into source folders any more.
- Continuous integration on a Windows runner: build, test, publish test results and the MSI.

**Design notes.**

**Objective.** `Alphora.Dataphor.DAE` and `AlphoraDataphorServer` run correctly on .NET 10, not merely compile.

**Design notes.**

- **Remoting leftovers.** `RemoteServerObject` derives from `MarshalByRefObject` and, in `Dispose`, calls `GetLifetimeService()` and `RemotingServices.Disconnect` — both throw on .NET 10. `RemoteServer` registers a remoting tracking handler; `FileStreamProvider` implements `ISponsor`. `server-remove-remoting-and-dtc` removed all of it, keeping `MarshalByRefObject` as the base class (it still exists on .NET 10, with no behaviour). What reclaims sessions abandoned by a vanished client is settled: the server's own idle watcher (`Service/ConnectionManager.cs`), with the client's keep-alive ping as its liveness signal. `port-abandoned-session-cleanup` established that, corrected the watcher and pinned it with a test; see *Reclaiming an abandoned session* below.
- **`Delegate.BeginInvoke`** (K5) in the D4 asynchronous-execution operators: replaced by a long-running task per script (`AsyncExecution` in `SystemNodes.cs`), preserving the semantics the `DebugLibrary` script checks (exceptions surface on the target process) and the old ones the scripts rely on (errors not returned to the caller, the full timeout waited).
- **COM+ / DTC.** `ServerDTCTransaction` is a `ServicedComponent` created by reflection under an assembly name that does not exist (K11), so distributed transactions cannot have worked since the 2009 Engine/Server split. `server-remove-remoting-and-dtc` removed the class; setting `UseDTC` (process) or `DefaultUseDTC` (session) to true now raises error 106119, at the setting through `System.Processes`/`System.Sessions`, and at the next transaction when it arrives through the API.
- **Globalization.** .NET 10 on Windows uses ICU by default where .NET Framework used NLS; string comparison, casing and sort order can differ in edge cases, and D4 string semantics sit on top of them. Select NLS (`System.Globalization.UseNls`) in the props file for every executable and test host, and pin a handful of comparison cases in a test: the `Globalization` coverage script. D4's `=`, `<` and ordering are ordinal and do not depend on the setting; `CompareText` ignores case through the runtime's case table, which differs between NLS and ICU only for letters added to Unicode lately (Georgian capitals, for one), not pinned; culture-sensitive search (`IndexOf`, `Pos`, `StartsWith`) depends on it, and the script pins cases that differ under ICU.
- **Assembly loading.** Libraries load with `Assembly.LoadFrom` and are found again by name through an `AppDomain.AssemblyResolve` hook (`Base.Windows/AssemblyUtility.cs`). This works unchanged on .NET 8 in the spike. Formalize it rather than redesign it: keep everything in the default load context (library assemblies share base types such as `SQLDevice`, and `ClassLoader` resolves by name), add a resolver that probes registered library directories for managed *and native* dependencies, and keep "no unloading". Per-library collectible contexts are out of scope.
- **Configuration.** `ConfigurationManager.GetSection` (K12) and `app.config` trace switches: keep working through the `System.Configuration.ConfigurationManager` package where a setting is real, delete where it is not.
- **Windows-only API** in the server (`EventLog`, `WindowsIdentity`, `Base.Windows.PathUtility`): keep, behind the existing platform check, with the `CA1416` analyzer enabled so that new unguarded uses are flagged.
- **Obsolete but working** API (`AesManaged`, `RNGCryptoServiceProvider`, `HttpWebRequest`, `FtpWebRequest`, serialization constructors on exceptions): leave alone here; WS11 and WS7 own the ones worth changing.

### Reclaiming an abandoned session

**The mechanism is the server's idle watcher with the client's ping as its liveness signal.** Before the port, a client that vanished was noticed because the server's remote objects were .NET Remoting objects with leases, and a lease nobody renewed let the object go; `server-remove-remoting-and-dtc` removed all of that. What replaces it was already in the code: `ConnectionManager` wakes on a timer and relinquishes every connection whose last ping is older than the idle threshold, which closes that connection's sessions, aborts each process's executing thread and rolls back its open transactions.

**It is deliberately not the network channel.** The client keeps one channel per connection and silently builds a new one whenever the old one faults (`ClientServer.GetServiceInterface`), while on the server one `DataphorService` singleton serves every caller and every object is reached through an integer in a flat handle table. Nothing associates a channel with a connection, by design: that is what lets a client survive a network blip and keep using its handles. Reclaiming a client's work when its channel dropped would turn every transient disconnection into lost work, and it would be a protocol change. The binding makes the point moot anyway — `ReceiveTimeout` is `TimeSpan.MaxValue`, so an idle or half-open connection is never timed out underneath us, and a TCP connection whose peer has been powered off is not noticed at all without keep-alives the transport does not configure.

**What follows from the ping being the signal.** A connection's `IdleTime` is a time since its last *ping*: no ordinary operation moves it, and none can without new plumbing, because the handle table is flat and a session holds a reference to the server rather than to its connection. So a client that does not ping is reclaimed whatever it is doing, and a client in the middle of a long call keeps its connection only because it pings from a thread of its own — which the shipped client does, every two minutes (`port-connection-keepalive` made that ping follow the connection rather than a session). That is the protocol, not an accident of it.

**Decisions.**

- **The threshold stays at 300 seconds, with no instance-configuration setting for it.** It is 3.1's value; its usable range is narrow in a way that is easy to get wrong (the floor is the shipped client's keep-alive interval, a constant compiled into the client, so an operator who set 60 would quietly start killing live sessions); and the case that actually needed a shorter threshold — a deterministic test — is served by injecting the value instead. The revisit condition is recorded at the site.
- **The wake period is a quarter of the threshold, not equal to it.** The two were one constant, so a connection that went quiet just after a wake was reclaimed at the second wake after it crossed the threshold: the bound was 300 to 600 seconds and is now 300 to 375. The cost is four wakeups an hour rather than one.
- **Reclamation is idempotent rather than coordinated.** Barring the watcher from a connection with a call in flight would need the handle-to-connection plumbing that does not exist. Instead, relinquishing a connection twice does nothing the second time - the two steps that tear a connection down, closing its sessions and disposing it, run under one lock per connection, so the second thread finds the work claimed rather than half done - and a call in flight sees its process aborted and its handles withdrawn — which is what the existing machinery already did: `Engine.TerminateProcessThread` aborts the executing thread (waiting half of `Engine.ProcessTerminationTimeout`, then logging `ProcessNotResponding`), the handle table withdraws each handle from the object's `Disposed` event, and a later call on a withdrawn handle raises error 106205, unknown object handle. Nothing in the handle table is corrupted.
- **The idle measure is monotonic, not a difference of two wall-clock readings.** `bug-idle-clocks-use-wall-clock-time` replaced the connection's `DateTime.Now` stamp with an `Environment.TickCount64` one, and the process-termination deadline in `Engine.TerminateProcessThread` with a `Stopwatch`. The difference between two readings of the local clock is the time that passed plus however much the clock itself moved, and local time moves on its own at every daylight-saving transition and whenever an operator or a time-synchronization service corrects it: the first sweep after a forward step found every connection more than the threshold idle and relinquished all of them at once, closing live clients' sessions and rolling back their work. The boundary and the threshold are unchanged; what changed is the clock the elapsed time is measured from. The native interface's session clock was already monotonic, and the three sites point at each other so the set stays greppable.
- **Making the watcher aware of the catalog store's write lock is rejected.** It would mean the service layer asking the catalog device session which connection holds the store transaction — a new coupling across two subsystems for a case whose real remedy is the client pinging properly and catalog-changing transactions being short.

**What rests on the test and what rests on inspection.** `tests/DAE.Server.Tests/AbandonedSessionCleanupTest.cs` holds two cases, in process over a `RemoteServer` plus a `ConnectionManager` at a one-second threshold. The first pins the whole chain: a client opens a transaction that takes the catalog store's write lock, stops pinging, and is reclaimed — measured at about 1.1 seconds — after which another session's schema change succeeds, the abandoned table is gone rather than committed, and a call on the reclaimed process fails. The second is the reproduction for relinquishing a connection twice. The other half of the sweep's decision — that it spares a connection the client is pinging — is `ConnectionKeepAliveTest.TheSweepSparesAPingedConnectionAndReclaimsAnUnpingedOne`, which runs a watcher at a ten-second threshold against a client pinging every second and an unpinged control connection, and was seen to fail when the sweep was made to relinquish unconditionally. Verified by reading the code rather than by test: what a call in flight sees (the three steps above), what happens to a process that will not stop when aborted, the watcher against server shutdown, a connection established while a sweep is running, and application transactions on an abandoned process (`ServerProcess.Dispose` leaves the application transaction before rolling back, unchanged here).

**The out-of-process half, and which mechanism actually acts.** `tests/DAE.Server.Tests/AbandonedClientProcessTest.cs` (`test-client-server-abandoned`) runs the field case that needs two processes: a client program that was alive and pinging and is then killed outright, rather than a connection that was never pinged. It asserts only the end state - the killed client's session is gone and the server still answers an older connection and a new one - because the in-process fixture above already asserts the rollback, the store's write lock and the reclaimed process. Two mechanisms could have produced that end state, and it is now measured which does: **the idle watcher is the only one.** With the shipped 300-second threshold the killed client's session was still on the server 25 seconds after the kill, so CoreWCF and Kestrel do not notice the socket the dead process left behind, or noticing it does not reach the connection; with a five-second threshold the session went 4.7 to 5.1 seconds after the kill over six measured runs (four while the case was written, two in its review). The watcher's window is 5 to 6.25 seconds after the connection's *last ping*, and the client pinged every second, so from the kill the window is 4 to 6.25 seconds - which is why a measurement below the threshold is the expected thing rather than a surprise. What the case needed from the product is the new host-object property `DataphorServiceHost.ConnectionIdleTimeInSeconds`, which is how a server in a child process is given a reclamation clock a test can wait for.

**The native CLI has a watcher of its own.** `NativeServer` keeps its sessions in a dictionary keyed by a GUID, and since `native-cli-session-liveness-clock` each entry carries a monotonic clock that every call naming its handle stamps and a count of the calls in flight on it, with the client library `NativeCLISession` pinging every two minutes through `GetTransactionCount` — which is why `INativeCLIService` still needs no `Ping` operation of its own. `bug-native-cli-sessions-never-reclaimed` added the sweep that reads them: `Service/NativeSessionManager.cs` wakes on a timer and calls the new `NativeServer.ReclaimIdleSessions`, which takes every session that has had no call on it for longer than the threshold out of the table and stops it — stopping a session stops its process, which rolls back its open transactions and so releases the catalog store's write lock, no new rollback machinery being needed for it. Before that sweep a native client — including another Dataphor server connected through a server link, which is the likeliest route in a real deployment — that died inside a transaction left that transaction, and the write lock if it had changed the catalog, held until the server was stopped. Pre-existing rather than a port consequence: this interface was never .NET Remoting, so nothing here was ever leased, and the connection watcher never knew about native sessions.

**Decisions for the native interface.**

- **A second watcher beside `ConnectionManager`, not a shared abstraction extracted from it.** The thread shape is copied — one background watcher, a `ManualResetEvent`, a wake period of a quarter of the threshold with a floor of a second, an idempotent `Dispose` with a bounded join — and so are the remarks that explain it. `port-abandoned-session-cleanup` and `test-client-server-abandoned` had only just settled and tested that mechanism, and reworking a freshly-proven path for tidiness buys no behaviour. The revisit condition is at the top of the new class: if a third such watcher ever appears, extract one then. The same call is recorded for the two keep-alives, at `NativeCLISession`.
- **A session with a call in flight on it is never reclaimed — which the connection side cannot promise.** The sweep decides and removes under one lock, and the count of calls in flight is read inside it, so a session the sweep has chosen cannot take a call between the decision and the removal and a busy session is simply left alone. That is possible here and not for a connection because every native operation goes through one acquire; for a connection, "barring the watcher from a connection with a call in flight would need the handle-to-connection plumbing that does not exist" (above). The stopping happens *outside* the lock, because stopping a session's process can wait half of `Engine.ProcessTerminationTimeout` and every operation of `NativeServer` takes that lock.
- **No new error and no new error code; the server log is the operator-visible record.** A client that comes back to a reclaimed session gets the "Invalid session handle" `ArgumentException` the dictionary lookup already raises for any handle the server does not hold, wrapped as every native error is. Answering "reclaimed after N seconds of inactivity" instead would mean remembering reclaimed handles — unbounded bookkeeping, or an eviction policy for it — and a new error code is a compatibility surface. What an operator gets instead is one log line per reclaimed session naming the session's ID, user, client host name, how long it had been without a call, and how many transactions it had open; that last is what says whether anyone else was being blocked.
- **The threshold is a host-object property, `DataphorServiceHost.NativeSessionIdleTimeInSeconds`, 300 seconds by default.** The same shape and the same justification as `ConnectionIdleTimeInSeconds`, and the same number in a constant of its own (`NativeSessionManager.IdleTimeInSeconds`) rather than a shared one: the two floors are set by different clients' compiled-in keep-alive intervals — the WinForms client's for connections, `NativeCLISession.DefaultKeepAliveInterval` for native sessions — and a test has to be able to shorten one without touching the other. Whether *either* should become something an operator can set in the instance list is one question with one answer, recorded once at `ConnectionManager.IdleTimeInSeconds` and cross-referenced from the new constant.

**What rests on the tests and what rests on inspection.** `tests/DAE.Server.Tests/NativeSessionCleanupTest.cs` holds two cases, in process over a `NativeServer` plus a `NativeSessionManager` at a one-second threshold, and is deliberately a close parallel of `AbandonedSessionCleanupTest`. The first is the reproduction and was seen to fail before the watcher was wired in — the catalog change kept failing with 130103 for the case's whole 31-second wait — and passes with it, the reclamation measured at about 1.1 seconds: the abandoned transaction is rolled back rather than committed, another session's schema change then succeeds, and a call on the reclaimed handle fails. The second pins the branch that is easiest to get wrong, a session with a long call in flight on it, and was seen to fail with the in-use count removed. `NativeSessionKeepAliveTest` adds the pair that proves the compatibility claim over a real endpoint: at a three-second threshold a session the client pings every second survives three thresholds of the test making no call, and the same session with the keep-alive off does not. Verified by reading the code rather than by test: that a session acquired between the decision and the stop is impossible (the removal is inside the lock), that a brand-new session is not swept before its first call (its clock is stamped in its constructor), what a `StopSession` racing the sweep does to a server link (`NativeCLISession.Dispose` propagates and `RemoteSessionImplementation.Dispose` logs a warning and releases the local side), what happens to a session whose process will not stop (the rest of that sweep waits for it, as a connection sweep does), the sweep against server shutdown (the manager is disposed before the engine stops and its logging is guarded), and the stateless `Execute(NativeSessionInfo, ...)` overloads, whose sessions never enter the table and so cannot be swept however long they run.

**The one cost, and it is deliberate.** A client that speaks the WCF contract directly rather than using the shipped library cannot ping, so a session it holds without calling anything for five minutes is now ended where before it was kept for ever; a 3.1 client against a 4.0 server is the same case, 3.1's library having no keep-alive. An integration that needs longer has the host property, and one that holds a transaction open across five idle minutes is already blocking every other session's schema change — which is the defect being fixed. `docs/migration-notes.md` carries it. One case is worth naming because it is where "idle" and "doing nothing" differ: D4's `ExecuteAsync` runs its script on a *sibling* process of the same session, so the native session's own in-use count is zero while that work runs, and after the threshold the session is reclaimed and the sibling process aborted. No client using the shipped library reaches it, because the keep-alive keeps the clock moving.

## WS4 Catalog store

**Objective.** A reliable embedded catalog store on .NET 10. Existing catalogs are not brought across (D3).

**Diagnosis of the SQLite problem (verified).** Eight sessions each running fifteen create/query/drop cycles against a SQLite-backed server produced 39–47 failures in 60–80 seconds. Three independent causes:

1. **Lock upgrades between connections.** From its first store write onward, a catalog device session holds its own store connection and opens a store transaction for the life of every later process transaction, whether or not that transaction writes (static: the flag that marks the session as writing is never reset). SQLite transactions were begun deferred, so two sessions each take a read lock and then both try to write: one must fail with "database is locked", after waiting out the busy timeout. (Isolation level "read uncommitted" is mapped to *no* transaction at all in `SQLiteConnection`, which is harmless but means those statements autocommit.)
2. **Rollback-journal mode**, in which a writer blocks all readers.
3. **A race that has nothing to do with SQLite** (K1): one static `D4TextEmitter` shared by all sessions builds the object script that is stored in the catalog. Under concurrent DDL the text is interleaved. With SQLite the garbled script broke the generated `insert` statement ("SQL logic error … unrecognized token"); with SQL CE, which inserts through a cursor, the garbled text would be *stored* and fail only when the object is next loaded from the catalog.

| Configuration | Errors (120 cycles) | Time |
|---|---|---|
| As found | 39–47 | 60–80 s |
| + emitter fix | 33 ("database is locked" only, plus K3 once) | 72 s |
| + write-ahead logging and a 30 s busy timeout | 17 | 17 s |
| + store transactions begun immediate (write lock up front) | **0** | **1.6 s** |
| Same, 16 sessions × 25 cycles | **0** | 8 s |

**Target design.** SQLite in WAL mode; one writer at a time by construction. The spike's "begin immediate for everything" serializes even read-only store transactions and makes a long user transaction that has touched the catalog hold the write lock; the production version should (a) open the SQLite write transaction lazily, on the first store *write* inside a process transaction, (b) let reads run outside any SQLite transaction (WAL gives each statement a consistent committed snapshot, and the engine's own catalog locks already serialize conflicting DDL), and (c) map busy timeouts to a Dataphor error that names the blocking condition. As landed (`store-sqlite-concurrency`), (a) has one refinement: a statement that changes the catalog begins the write transaction before it takes the engine's catalog lock, because a session that waits for the store's write lock while holding that lock deadlocks with the session that holds the write lock, until the busy timeout. Validate against the full L1 and L2 suites and a test with a deliberately long-running DDL transaction. Choose between `Microsoft.Data.Sqlite` and `System.Data.SQLite` in the ticket (the spike used the latter, version 1.0.119, unchanged apart from one renamed property).

**No migration.** Deployed applications rebuild their catalog from scripts as routine maintenance, including the users, roles, rights and device users that live only in the store, so a new installation starts from an empty SQLite catalog and the application's own rebuild procedure populates it. SQL CE support is deleted rather than ported: the store project, its native DLLs, the `Connection.SQLCEConnection` class registration in the base `Connection` library (K19), and the server's default store class name. What the product owes this workflow is that a rebuild is fast and scriptable from the command line (WS10) and that the administration guide describes it (WS8).

**Done** (`store-rebuild-workflow`): `StoreRebuildWorkflowTest.RebuildRegistersLibrariesAndSurvivesRestart` is the live proof. On a fresh instance it registers the sample set (`System.Platform`, `SimpleDevice`, `Frontend`, `Sample.Common` and `Sample.DetailAdd` on top of the auto-registered `General`), creates two roles with a right each, a user with role membership and a device user on `SampleDevice`, and runs a `create table` and a `create view`; it then stops the server, asserts the SQLite catalog directory holds only `DAECatalog` (no WAL or journal sidecar), restarts, and asserts every library, role, user, right grant, role membership, device user, device, table and view is back and that the stored password forms round-trip. ## WS5 Client server protocol and hosting

**Objective.** A .NET 10 server process that existing and new clients can connect to, running as a console application or a Windows service.

**Current state.** Three self-hosted WCF services on a custom binding (binary encoding over TCP); see [architecture.md](architecture.md#hosting-protocol-discovery). ### CoreWCF proof

**Verdict: feasible, and done.** The client code the product ships — `ClientServer` and `LocalServer` on the binding `DataphorServiceUtility.GetBinding()` builds — completes real work against a .NET 10 server whose `IDataphorService` and `IListenerService` are hosted by **CoreWCF 1.9.1** on that same binding, with the wire unchanged. The proof was `tests/DAE.Server.Tests/CoreWcfProofHost.cs` (the host, deleted by `protocol-corewcf-host` once production code took over) and `CoreWcfProtocolTest.cs` (six cases, about a second in total): a whole session (connect, prepare and execute a statement, fetch a cursor, allocate and release a stream, shut down), a three-megabyte value in and out, a server-side engine error arriving as the engine's own `CompilerException` with its own code, the listener answering on its own port with its typed fault, one service object serving every connection, and the two ports being the ones the host asked for.

One server-side source change was needed, and it is invisible on the wire: `DataphorService` and `ListenerService` now carry CoreWCF's `[ServiceBehavior]` and throw CoreWCF's `FaultException<T>`, which in each file is a one-line change of `using System.ServiceModel;` to `using CoreWCF;`. The three contract *interfaces* are untouched.

**What the protocol is, and still is.** `DataphorServiceUtility.DefaultBuildBinding` builds one binding in code: `CustomBinding(BinaryMessageEncodingBindingElement, TcpTransportBindingElement)`; `ReaderQuotas.MaxArrayLength` and `MaxStringContentLength`, and the transport's `MaxBufferSize` and `MaxReceivedMessageSize`, all `DataphorServiceUtility.MaxMessageLength` (2147483647); `TransferMode` and security left at their defaults; `SendTimeout` and `ReceiveTimeout` `TimeSpan.MaxValue`. Three services on two ports: the main service at `net.tcp://<machine>:<port>/<instance>/service` (default 8061), the native CLI below it at `.../service/native`, and the listener at `net.tcp://<machine>:8060/listener/service`. All three contracts are `[ServiceContract(Name = …, Namespace = "http://dataphor.org/dataphor/3.0/")]` and almost every operation carries a `[FaultContract]`; the client declares the same three separately as `AsyncPattern = true` `Begin`/`End` pairs.

**The answers**, against CoreWCF 1.9.1 and `System.ServiceModel.*` 10.1.0. File paths below are in the `CoreWCF/CoreWCF` and `dotnet/wcf` repositories.

- **The custom binding, with those quotas and limits: yes.** `CoreWCF.Channels.CustomBinding` has the same `params BindingElement[]` constructor; `BinaryMessageEncodingBindingElement` exposes a settable `ReaderQuotas`; `TcpTransportBindingElement` inherits `MaxBufferSize` and `TransferMode` from `ConnectionOrientedTransportBindingElement` and `MaxReceivedMessageSize` from `TransportBindingElement`. The NetTcp listener looks for exactly a `ConnectionOrientedTransportBindingElement` inside a `CustomBinding` (`NetMessageFramingConnectionHandler.BuildAddressTable`, `src/CoreWCF.NetFramingBase/…/Framing/NetMessageFramingConnectionHandler.cs`). Verified by the host opening and the test passing, not only by reading.
- **2 GB maximum message size: yes, and nothing caps it lower.** `BuildHandshakeDelegateForDispatcher` reads `MaxReceivedMessageSize` and `MaxBufferSize` off the transport element and applies them per connection; CoreWCF's NetTcp is a Kestrel *connection handler*, not an HTTP pipeline, so Kestrel's HTTP limits are not in the path. `MaxBufferPoolSize` stays at its 512 KB default, which only bounds pooling; the host opening at all is the check that `BufferManager.CreateBufferManager(512 KB, 2147483647)` is accepted. The three-megabyte case crosses as a 6.3 MB message (a `String` is encoded UTF-16 in the row's physical form) and clears the 64 KB message, 8 KB string-content and 16 KB array defaults at once.
- **`InstanceContextMode.Single` with a supplied instance, and `ConcurrencyMode.Multiple`: yes, through CoreWCF's own attribute.** `ServiceDescription.SetupSingleton` resolves the service type from dependency injection and makes it the well-known singleton when the behaviour says `Single`, so `services.AddSingleton(instance)` is how `new ServiceHost(_service)` is spelled.
- **The `[ServiceBehavior]` on the implementation must be CoreWCF's; the contract attributes must not change.** `CustomAttributeProvider.GetDualCustomAttributes` (`src/CoreWCF.Primitives/src/CoreWCF/Description/CustomAttributeProvider.cs`) converts `System.ServiceModel` attributes to CoreWCF's, and the set it converts is `ServiceContractAttribute`, `OperationContractAttribute`, `FaultContractAttribute`, the five `Message*` attributes, `MessageParameterAttribute`, `XmlSerializerFormatAttribute` and `ServiceKnownTypeAttribute`. `ServiceBehaviorAttribute` is **not** in it, and `ServiceDescription.EnsureBehaviorAttribute` looks only for `CoreWCF.ServiceBehaviorAttribute`. So the contract interfaces keep their `Name`, `Namespace` and `[FaultContract]`s as they stand — which is what keeps the action URIs identical — while the implementation classes need CoreWCF's behaviour attribute.
- **A typed fault reaches the existing client as the same typed fault, once the service throws CoreWCF's `FaultException<T>`.** `ErrorBehavior.InitializeFault` tests against `CoreWCF.FaultException` and `FaultFormatter.Serialize` walks the base chain for `CoreWCF.FaultException<>`; a `System.ServiceModel.FaultException<DataphorFault>` is in neither hierarchy, so it would be serialized as a generic unhandled-exception fault, the client's `catch (FaultException<DataphorFault>)` would miss it, and every engine error would degrade into `ServerException.Codes.CommunicationFailure`. `CoreWCF.FaultException<TDetail>` has the same `(TDetail detail, string reason)` constructor, so no throw site changed. The detail type is still the one `[DataContract]` class `DataphorFault`, serialized by the data-contract serializer on both sides.
- **Infinite send and receive timeouts: honoured.** `TimeoutHelper.IsTooLarge` is `(timeout > MaxWait) && (timeout != TimeSpan.MaxValue)`, so `TimeSpan.MaxValue` is accepted, and `ServerSessionConnectionReaderMiddleware` copies both timeouts off the binding onto the session's transport settings. `ConnectionPoolSettings.IdleTimeout` (2 minutes) and `ChannelInitializationTimeout` (30 seconds) apply in `ConnectionReuseHandler.ReuseConnectionAsync`, which runs only for a connection whose session has already ended and which is waiting to be reused, so they do not reach an open session. **Established by inspection, not by test:** an infinite timeout cannot be demonstrated by a test that is allowed to finish, and nothing here should add a sleep to the suite.
- **The client's asynchronous contract binds with no edits.** In `dotnet/wcf`, `TypeLoader.ProcessOpMethod` sets `isAsync` from `ServiceReflector.IsBegin` and the action comes from `ServiceReflector.GetLogicalName`, which strips the `Begin` prefix, so `BeginGetServerName` sends the same action as the server's `GetServerName`. This is the property the whole wire-compatibility claim rests on, and the test establishes it empirically: no client file changed.

**Packages.** `CoreWCF.NetTcp` 1.9.1 (host) and `CoreWCF.Primitives` 1.9.1 (the fault and behaviour types), both `netstandard2.0`. A project that also carries `<FrameworkReference Include="Microsoft.AspNetCore.App" />` gets the in-box ASP.NET Core 10 assemblies in place of the `Microsoft.AspNetCore.*` 2.3.10 packages CoreWCF.NetTcp depends on, through NuGet's package-override mechanism; the test project carries it, so running the suite needs the ASP.NET Core shared runtime as well as the .NET one (every .NET SDK install has it, so CI is unaffected). Restore reports no package-audit warning for either package's closure.

**The host.** One .NET Generic Host (`HostBuilder().ConfigureWebHost(…)`), `UseKestrel()` for the `IServer` implementation, `UseNetTcp(Action<NetTcpOptions>)` with two `Listen` calls, `AddServiceModelServices()`, the pre-built `DataphorService` registered as a singleton, and `ListenerService` added by type so CoreWCF constructs it per session as `new ServiceHost(typeof(ListenerService))` does today. Not `WebHostBuilder`: .NET 10 marks `WebHostBuilder` and `IWebHost` obsolete (ASPDEPR004, ASPDEPR008), and CoreWCF configures identically under the Generic Host, which is where `host-generic-host` is going anyway.

**The dynamic port: reserved in advance, not port 0.** The host reserves two free loopback ports by binding and releasing them, then registers absolute endpoint addresses on them. A base address of `net.tcp://127.0.0.1:0/` with relative endpoint addresses does not work here for two reasons: the address table is built from the endpoint address before Kestrel binds the socket, so the real port is not known in time; and two endpoints with addresses relative to the base address would both resolve against the first base address of the scheme, putting them on one port rather than the two the product uses. `TcpListenOptions.IPEndpoint` does report the bound endpoint, and the test asserts it matches the port asked for.

**What this hands to `protocol-corewcf-host`.** Every item below has since been settled; *CoreWCF hosting*, the next subsection, records the answers. They are kept as written so that what was open when, and on what evidence, stays legible.

- **Listen on both address families.** The proof's host binds IPv4 loopback only, and a client given a host name that resolves to IPv6 first pays about **two seconds per channel open** before the stack falls back: measured on Windows 10 as 2.046 s for a TCP connect to `localhost` against a listener bound to `127.0.0.1`, versus 0.016 s for the literal. Today's `ServiceHost` on `net.tcp://<machine>:<port>/` binds the IPv6 wildcard in dual-stack mode and does not have this problem, and real clients connect by host name. Getting the listen address right is not optional.
- **Nested addresses on one port are unproven.** The native CLI endpoint `.../service/native` is a path *below* the main endpoint `.../service`. CoreWCF dispatches on `connection.Via` through a `UriPrefixTable` registered per endpoint base address (`NetMessageFramingConnectionHandler.BuildAddressTable`), which should resolve the longer registration first, but the proof hosts two sibling addresses on two ports and does not test the nested case. It is the first thing to check.
- **Streamed (non-native) values crossing the wire are unproven.** The proof's stream case exercises the handle protocol — `Allocate`, the length probe the first write makes, the close and `Deallocate` are all calls on the wire — but the bytes stay in `LocalStreamManager`'s deferred-write cache, because `CoverStream.Flush` is a no-op and no public client API forces a flush (`FlushStreams` is internal to the cursor paths). That is what the shipped client does, so the case is honest, but it means no test here shows stream *content* crossing. A cursor update carrying an overflow value is the production path that flushes; run one once the real services are hosted.
- **The binding is now declared twice**, once as `System.ServiceModel.Channels.CustomBinding` for the client and once as `CoreWCF.Channels.CustomBinding` for the host, because the two stacks have unrelated `Binding` types and `DataphorServiceUtility.GetBinding()` can only produce the client's. The proof's copy reads every limit from `DataphorServiceUtility.MaxMessageLength`, and `CoreWcfProtocolTest.TestHostBindingMatchesTheClientBinding` compares the two declarations on element list and order, the four limits, both timeouts, the transfer mode and the message version, so a one-sided edit fails the suite rather than changing the protocol quietly. That test moves with the host; a shared settings source would retire it.
- **The server assembly's dependency closure grew by 31 packages.** `CoreWCF.Primitives` brings into `AlphoraDataphorServer`'s runtime closure 31 packages that nothing else there needed, among them eight `Microsoft.AspNetCore.*` 2.3.10 assemblies, twelve `Microsoft.Extensions.*`, five `Microsoft.IdentityModel.*` (including SAML), `System.DirectoryServices` and `System.Web.Services.Description`; they are in the runtime layout's `bin/` now. `DAE.Client` references the server assembly, so the WinForms client and the IDE inherit them, and bringing the host classes back will add ASP.NET Core itself. Splitting a hosting assembly out is the alternative; it is a design call for `protocol-corewcf-host`, with WS6's `ui-client-layering` as the other interested party. (Nothing runs from `bin/` until `host-generic-host`, so this costs only disk today.)
- **The proof host is written to be moved, not rewritten**, and it is in the test project only so that CoreWCF.NetTcp and the ASP.NET Core framework reference stay out of the server assembly until the question above is settled. It takes no secure-connection settings; `RequireSecureConnection` and `RequireSecureListenerConnection` belong to `protocol-transport-security`. (`AllowSilverlightClients` was not one of them — it switched on the cross-domain access-policy service the removed Silverlight client needed — and `protocol-corewcf-host-prepare` removed it.)

**Two defects found by running the proof.** `RemoteServerProcess.Execute` converted only the parameter *descriptors* (`RemoteParamsToDataParams`) and not the parameter data, so a parameterized statement run through `IServerProcess.Execute` over the network behaved as though every parameter were nil; fixed here to use `RemoteParamDataToDataParams`, as `RemoteServerPlan.Execute` always did, with the three-megabyte case as its reproduction. And `Schema.Object`'s next-object-id counter was a process-wide static that `Engine.InitializeCatalog` reset to zero, so a process holding two engines — a client's catalog cache beside an in-process server, which is what a test or the IDE with both an embedded and a remote alias does — handed the server ids its catalog already held; the proof's client worked around it by handing the counter back, and `bug-object-id-counter-is-process-wide` has since fixed it: identifiers come from a `Schema.ObjectIDGenerator` the engine owns, one per engine, and the workaround is gone. The other half of that counter's behaviour — the reset to zero itself — is settled by `bug-client-catalog-rebuild-reuses-object-ids`: a repository engine no longer restarts its generator when `Engine.ClearCatalog` rebuilds its catalog, because the objects of the catalog being replaced are still in use (every prepared table expression a client holds owns a view in it), so reissuing their identifiers let the drop of a stale view evict a live object's entry from the catalog device's identifier-to-name index; an engine with a catalog store still resets, because the built-in objects it creates before it reads the store must land on the identifiers the store already holds for them.

### CoreWCF hosting

**Done.** `DataphorServiceHost.Start()` starts a .NET 10 server and serves all three contracts on CoreWCF at the addresses and ports 3.1 published, from the same instance configuration, through the same entry points the console host, the Windows service and `DAE.Client`'s non-embedded in-process alias already call. `tests/DAE.Server.Tests/CoreWcfProtocolTest.cs` drives the real host with the shipped client code (twelve cases, about sixteen seconds); the proof's throwaway host is gone. Four questions the proof left open were settled by measurement, and the answers are below.

**Hosting is its own assembly, `Alphora.Dataphor.DAE.Server.Hosting` (`src/engine/Server.Hosting/`).** Not part of the server assembly, because of a package-audit measurement. `CoreWCF.NetTcp` 1.9.1 depends on `Microsoft.AspNetCore.WebUtilities` 2.3.10, which NuGet's package audit reports as having a known moderate-severity vulnerability (`NU1902`). A project comes out clean only if it declares **both** `CoreWCF.NetTcp` as a direct package reference **and** `<FrameworkReference Include="Microsoft.AspNetCore.App" />`, which substitutes the in-box ASP.NET Core 10 assemblies for the 2.3.10 packages. A project that gets `CoreWCF.NetTcp` indirectly, through a project reference, reports `NU1902`, and adding the framework reference to *that* project does not help; four scratch projects established this. Putting the package in `src/engine/Server/Server.csproj` would therefore have made `Store.SQLite`, `Connection`, `MSSQLDevice`, `SimpleDevice` and the Frontend server — five library projects with nothing to do with hosting — report `NU1902`, and `AGENTS.md` forbids suppressing `NU1900`–`NU1904`. With the split, `dotnet restore Dataphor.slnx` still reports no audit warning at all. The three WCF *service* classes stay in the server assembly; only the hosts moved.

**Two Generic Hosts in the process, not one.** `DataphorServiceHost` builds one `HostBuilder().ConfigureWebHost(…)` for the instance's own two endpoints, and `ListenerServiceHost` builds a second for the listener. They cannot be one host because of what the listener is: one listener per machine serves every instance on that machine, which is why its port is fixed at 8060, so the second and later server processes on a machine normally find the port taken and must still start and still serve their own endpoint. On a single host a failed listener bind would fail the whole host, and with it the server. Measured: two Generic Hosts, each with its own `UseNetTcp` listener, coexist in one process and both serve; when the second host's port is already held by another socket, `host.Start()` throws `System.IO.IOException` ("Failed to bind to address http://[::]:*port*: address already in use"), the first host is unaffected and still answers calls, and disposing the host that failed to start is clean. `ListenerServiceHost` still swallows that error, but no longer silently: it records whether it started, and `DataphorServiceHost` writes one warning line to the server's log and reports it through the new `IsListening` property.

**The listen address is the machine name, and that is what gives both address families.** Passing `net.tcp://<machine name>:<port>/` to CoreWCF's `NetTcpOptions.Listen` makes it open two listening sockets for the one port, `0.0.0.0` and `[::]`, so every interface in both families is served — which is what the old `ServiceHost` did. Measured against the finished host (2026-11-20, Windows 10): both sockets present, and clients connecting by `127.0.0.1`, by `localhost` and by machine name all reached the endpoints, in tens of milliseconds each, even though the endpoint addresses were registered under the machine name alone — the host-name part of an address is not compared when a call is dispatched, the path is. Nothing extra is needed for both families; the only thing to avoid is a literal address, which binds that address only and leaves a client whose name resolves to the other family paying about two seconds per channel open before the stack falls back. `HostName` defaults to `Environment.MachineName` for this reason, and exists so that the tests can listen on loopback and a multi-homed machine can choose. The suite does not re-measure it: the fixture listens on the loopback literal so that no test opens a port another machine can reach.

**Two endpoints on one port, one below the other, work.** The native CLI endpoint sits at a path *below* the main endpoint (`net.tcp://host:port/<instance>/service/native` under `net.tcp://host:port/<instance>/service`), which the proof could not test and named as the first thing to check. Measured: two services, two contracts, one `Listen` call for the single port, and calls to both dispatched to the right service, from all three client host-name forms. The native CLI therefore keeps its documented address, which is the compatibility surface that matters.

**What this hands on.**

- **`ui-client-layering` (WS6).** `src/client/DAE.Client/ServerConnection.cs` creates a `DataphorServiceHost` for an in-process alias that is not embedded — the Windows client or the IDE hosting a full server with network endpoints inside its own process, which is a real feature. None of those projects is in `Dataphor.slnx` yet, so the solution build stays clean. Breaking that dependency is `ui-client-layering`'s to do; the other way out is transitive package pinning, below.
- **`host-generic-host`.** The host shape is the one to build on: the two hosts build it through one internal helper in the hosting assembly (`NetTcpServiceHost`), which is also the one place that clears the logging providers and blocks on starting and stopping, so routing the server's own log and the Windows event log through `Microsoft.Extensions.Logging` - and offering an asynchronous surface - is one file's worth of change there plus this work item's own. `DataphorServiceHost.Stop()` now waits up to ten seconds for Kestrel to close open connections before aborting them; the shutdown timeout is a constant in that helper, not configuration.
- **`protocol-transport-security`.** `RequireSecureConnection` and `RequireSecureListenerConnection` were read from the instance configuration and unused: the listener setting was passed to a `ListenerServiceHost` constructor parameter nobody read, and `DataphorServiceHost` never read the instance one. Both were left exactly so by `protocol-corewcf-host`, with the evidence intact. One thing did change for this work item: the hosts build their binding from `DataphorServiceHostBinding` rather than from `DataphorServiceUtility.GetBinding()`, so the hook `DataphorServiceUtility.BuildBindingCall` - the only way a deployment could ever have handed the *server* a secured binding, from its own host code - now reaches the client half of the protocol only, and cannot reach the host half at all, CoreWCF's `Binding` being an unrelated type. Designing what replaces it is this work item's. **Settled by `protocol-host-binding-hook`**: the host half is back, as `DataphorServiceHostHooks` in the hosting assembly - `BuildBindingCall` for the binding both hosts serve on, `ServiceBuilderHook` for a last look at each host's CoreWCF service builder, which is where a server certificate's credentials are installed (measured, not inferred from the metadata), and `HasCustomBinding` so that this work item can tell whether a site has supplied a binding of its own. ### Generic host

**Done.** `DAEServer.exe` and `DAEService.exe` are one program under two names - `DataphorHost` in `Alphora.Dataphor.DAE.Host` - and each executable is a single `Main` that calls it. Both projects are SDK-style; `src/hosts/DAEServer/CommandLineArguments.cs` (K23's copy there) and both `app.config` files are gone. `dotnet build Dataphor.slnx` now puts a runnable server into `artifacts/layout/<config>/bin/`, which had no executable before.

**What was settled.**

- **One program, two names, one code path.** The command line is the one 3.1 took, parsed once (`HostCommandLine`): `-i`/`-install` and `-u`/`-uninstall` register and remove the Windows service, `-r`/`-run`, `-n`/`-name <instance>` and no arguments run it, and anything else is rejected - which `DAEService` always did and `DAEServer`, which accepted and ignored every argument, now does too. A trailing `-n` with no value after it yields the default instance rather than an error, as both hand-written parsers did. `DAEService.exe` stays the binary a service registration names.
- **`UseWindowsService` is the whole of running as a service.** It replaces the host lifetime only when `WindowsServiceHelpers.IsWindowsService()` says the service control manager started the process, so there is one code path and `-r` is an alias for running. A console session is stopped with Ctrl+C, which the Generic Host's console lifetime handles; the old `Console.ReadLine()` is gone, reading standard input being wrong for a program whose input may be redirected or closed.
- **The host's logger carries host lifecycle only** - the instance starting, started, whether the listener is serving, stopping, stopped, failures. The server's own logging is untouched: `Server.LogMessage` writes the instance's rolling log file in the 3.1 format, which is a surface operators read and `ListLogs` serves over the protocol, and for an elevated process the Windows event log under the source the server creates. A console session gets `AddSimpleConsole` with the timestamp shape that log file uses; a service gets `AddEventLog` under the server's own source and log, and only if the source already exists - writing to a source that does not exist creates it, which would split a deployment's event log between two sources. The two CoreWCF hosts stay silent, so an in-process alias inside the Windows client or the IDE still prints nothing.
- **Shutdown is bounded at sixty seconds** (`DataphorHost.ShutdownTimeout`), a constant as `NetTcpServiceHost.StopTimeout` already is. The arithmetic: the listener's host and the instance's host each get ten seconds for Kestrel to close open connections, so twenty can pass before the engine's stop begins, and the Generic Host's default of thirty would leave it ten. Past the bound the host stops waiting and the process exits with the engine's stop unfinished - the same situation as the process being killed, which the catalog store already survives. `ConnectionManager`'s idle watcher became a background thread so that case is an abrupt stop rather than a process that never exits.

**What was measured.**

- **There is no app-local assembly probing on .NET 10.** An assembly that sits next to the executable but is not named in the executable's `.deps.json` cannot be loaded by simple name: a scratch console application with a library copied into its output folder and no reference to it fails `Type.GetType` with `FileNotFoundException`, and the engine's `AssemblyUtility.ResolveAssembly` hook only matches assemblies that are already loaded. What the server loads this way is its catalog store, resolved with `Type.GetType` from the instance's `catalogstoreclassname` setting or, where that is empty, from `Server.DefaultCatalogStoreClassName` - so both executables reference **every** store the layout ships (`Store.SQLite` and `Store.MSSQL`) although no line of their code mentions either, and `HostProgramTest` asserts that each `.deps.json` in the layout names each of them. Putting a store in the layout's `bin/` without the host reference ships one a deployment cannot name: it fails to start with 115107.
- **The framework reference on the server assembly takes nineteen files out of the layout's `bin/`.** `src/engine/Server/Server.csproj` carried `CoreWCF.Primitives` without `<FrameworkReference Include="Microsoft.AspNetCore.App" />`, so the package copies of `Microsoft.AspNetCore.*` 2.3.10 landed beside the in-box ones the hosting assembly substitutes, and a host running from `bin/` would ship them unused. With the reference added and the now-prunable `System.Diagnostics.EventLog` package reference removed (`NU1510`), `bin/` holds 74 files rather than 93, `dotnet restore Dataphor.slnx` still reports no `NU1xxx` warning, and the solution builds with 0 errors. This was the open choice `protocol-corewcf-host` left here. The consequence: the server assembly itself now needs the ASP.NET Core shared runtime, so a program that only runs a server in process needs it too.
- **`PathUtility.GetInstallationDirectory()` was one level too high for the runtime layout.** It popped a second level when the binaries' folder was named `bin`, for the 3.1 source tree's per-project output folders - a shape that no longer exists. That pop is gone, which leaves the installed case unchanged and makes the layout's default library directory `<layout>/Libraries` rather than `artifacts/layout`. Verified by running the layout's host: the default instance it created named the layout copy's own `Libraries` folder as its library directory.
- **The host runs.** `bin/DAEServer.exe -n <throwaway>` from a copy of the layout started the instance, served the instance port and the listener port, wrote the instance log, and on a console break stopped cleanly: exit code 0, the lifecycle lines in order, `ServerStopped` and `LogStopped` in the log, and the catalog store's `-wal` and `-shm` files folded back in and deleted. `Microsoft.Extensions.Hosting.WindowsServices` 10.0.15 resolves on the pinned SDK, and in a console process `IsWindowsService()` is false.
- **A plain socket is not a stand-in for "this port is held".** Holding `0.0.0.0:8061` with a .NET socket did not stop a host from binding that port and serving on it, although two Generic Hosts in one process do collide on a port (`IOException`, "address already in use", recorded under *CoreWCF hosting* above). The obvious explanation is ruled out: two plain .NET `TcpListener`s on the same address and port do fail with `AddressAlreadyInUse` on this Windows build, at `ExclusiveAddressUse`'s default of false. So it is the probe that is in doubt rather than the product, and the Kestrel-against-Kestrel measurement is the one the "two instances on one machine" story rests on; this was not chased further. If a second instance configured on a port another instance already serves is ever seen to start and then serve nothing, this is the thread to pull.

**What this hands on.**

- **`host-instance-directory`, and after it `host-instance-configuration`.** A host can now be pointed at an instance list of its own: `InstanceManager.InstanceDirectory` in process, and the environment variable `DATAPHOR_INSTANCE_DIRECTORY` from outside, which is what a process that starts one of the layout's executables sets on the child (`ProcessStartInfo.Environment`). An out-of-process test is therefore cheap, and it belongs to `test-client-server` rather than here. A variable rather than a host switch because every process that reads the list has to agree on where it is - the host, the configuration utility, the IDE, and a client opening an in-process alias - and because `HostCommandLine` is a compatibility surface not worth widening. `DataphorHost.BuildHost` keeps its factory parameter: the machine-wide list is no longer its reason, but two things remain that a `ServerConfiguration` cannot carry (`DataphorServiceHost.HostName` and `LoggingEnabled`, which the fixture needs so that no case opens a port another machine can reach or creates the Windows event-log source) and one case needs a start that throws. That decision is recorded at the parameter as an accepted tradeoff. The administrator documentation of the file and its settings landed with `host-instance-configuration`.
- **`tool-cli-server-commands`.** `ServiceUtility` plus `HostCommandLine` is the surface the `dataphor` tool's instance and service commands build on. The syntax message in `Alphora.Dataphor.DAE.Host`'s string table is the operator-facing text to revisit there, and two entries in that table are now unused.
- **`installer-msi`.** The installer calls `ServiceUtility.Install(instanceName, imagePath)` rather than `installutil`, and writes neither `app.config`. `installer-publish-profiles` decides what the install image takes from the layout's `bin/`, which now holds both executables with their `.deps.json` and `.runtimeconfig.json` (and no `.runtimeconfig.dev.json`, which names the building developer's package cache).
- **`test-client-server`.** The old `tests/DAE.Client.Tests/OutOfProcessTestFixture.cs` started `DAEServer.exe` with `RedirectStandardInput` and stopped it by closing that pipe, which no longer stops a host. Settled: the out-of-process fixture starts `tests/TestHarness` rather than the shipped executable, and that program stops both on a line on its standard input and when the input reaches end of file, so either a stop or the death of the test process stops the child. `debt-test-shipped-host-executable` in `backlog/` holds the question of covering the shipped executable itself.
- **`port-abandoned-session-cleanup`.** `ConnectionManager`'s watcher thread is now a background thread, with a `NOTE:` at the site saying why. That ticket otherwise owned the class, and has landed: see *Reclaiming an abandoned session* under WS2.

## WS11 Security

**Objective.** No known-weak defaults in a system that holds medical data, without breaking existing catalogs.

Findings (static unless noted):

- **Password storage** (K13): user passwords and device-user passwords are AES-encrypted with a key and IV compiled into `DAE/Schema/Security.cs` and duplicated in `DAE.NativeCLI/SecurityUtility.cs`; a comment marks the keys as to be moved. Anyone with the binaries can decrypt every stored password.
- The built-in `Admin` user has an empty password by default.
- The wire protocol is unencrypted and unauthenticated at the transport level by default.
- Dependencies with known vulnerabilities (Newtonsoft.Json 9.0.1, Npgsql 2.0.4).
- `System.Platform` exposes process execution with alternate credentials as a D4 operator; it is governed by D4 rights like any operator — confirm the default grants.
- The catalog store built SQL by string concatenation (inputs are engine-generated names and scripts with quote doubling). Closed by `store-parameterized-statements`: the insert, update and delete a write executes now carry their values as parameters. Three sites still render values into statement text, none of them an injection surface: a store cursor's ranged reader statement, whose origin values are integers and strings the same store read back; the undo log a nested transaction replays, built from the same engine-generated values as the write it inverts; and the four seed inserts `CatalogStore.Initialize` runs on an empty catalog, whose only non-constant value is the configured instance name.

Target: user passwords stored as salted, iterated hashes, upgraded transparently at next successful login; device-user passwords (which must be recoverable) protected by a per-instance key held outside the catalog (Windows DPAPI); installer prompts for an administrator password for a new instance; transport security designed, implemented and documented here (`security-transport-design`, `security-transport`), 4.0 having none of its own (D17); package vulnerability audit in CI; a short threat model in `docs/admin/security.md`. Every item here touches a compatibility surface and needs its own design ticket — none of it is "fix inline".

## WS14 Research compiled catalog and precompilation

**Objective.** Decide, with measurements, whether compiling catalogs or plans into assemblies is worth building.

**What exists.** Less than remembered: execution is plan-node interpretation; the IL emission path was removed before or at the 2008 open-source import, leaving a session flag (`ShouldEmitIL`) that nothing reads and one commented-out method. There is nothing to "turn back on".

**Questions to answer.**

- *Startup and load cost.* How long do registration and first use take for a large catalog on .NET 10 with the SQLite store? (System catalog start is about one second today.) If lazy loading from the store is already fast, a compiled catalog buys little.
- *Catalog as an assembly.* Generate, per library version, an assembly whose metadata describes the library's objects, loaded instead of re-compiling stored D4 scripts. Costs: a second source of truth, a build step inside the server, an invalidation story for `alter` statements, and security data still needs a store.
- *Expression compilation.* Compile scalar expression subtrees (restriction predicates, `extend` and `redefine` column expressions, aggregates) to delegates with `System.Linq.Expressions` behind the existing `PlanNode` interface. This is incremental, measurable on the memory device, and independent of how the catalog is stored — the likeliest win.
- *Ahead-of-time plans.* Precompiling whole operators is only attractive if expression compilation shows a large gain.

## Guidance for cutting tickets

- One work item → one ticket in `plan/` (if it says "design", "evaluate" or has an open choice) or `implement/` (if the scope here is already concrete). Items marked *hard* should go to `plan/` first and may split.
- Copy the prerequisites into `prereq:` using the slugs in the tables. Number Phase 1 tickets lowest.
- Anything depending on an open question that has no answer yet goes to `blocked/` stating the question number and the default from the table as the proposal.
- The order at the start is fixed: `repo-delete-dead-trees`, `library-remove-dead-devices` and `library-park-side-projects`, then `repo-move-to-new-layout`, then `build-core-sdk-projects`, `build-server-project`, `build-runtime-layout`, `test-harness-inprocess`. Nothing else can verify its work until the last of these lands, and nothing else should be in flight while paths are moving.
- WS8 items can run at any time (they write only under `docs/` and `tools/`) and, like most WS12 items, are good for lower-capability agents; WS2, WS4, WS5 and WS6 items marked *hard* are not.
- Each known defect is fixed inside the named work item with its reproduction test; do not file K-items as separate tickets unless the work item is split.
- Every ticket that changes something an application, a deployment script or a custom extension could notice appends an entry to `docs/migration-notes.md` in the same commit.

**How the board was cut (November 2026).** Phase 1, through gate G1, has one ticket per work item, numbered in the order above. Phases 2–5 are held as one umbrella ticket per workstream in `tickets/backlog/` (`feat-ws5-protocol-and-hosting` and so on), each saying which gate to promote it at. Promoted to `plan/`, an umbrella is replaced by its work items using the slugs in this document. The umbrellas stay in `backlog/` until then because the runner treats a plan ticket's prerequisite as satisfied once that prerequisite reaches `implement/`; in `plan/`, Phase 2 work would be planned before the reorganization, against old paths. A few items are grouped with the workstream whose code they wait on: `port-abandoned-session-cleanup` and `port-server-on-net10` and `test-client-server` with WS5; `test-store-contract` with WS4; `test-device-sql-golden` and `test-device-live` with WS7; `test-ui-smoke` with WS6; `build-globbing-cleanup`, `build-remove-legacy-build` and a new item, `hygiene-remove-net-spike`, with the WS12 remainder.
