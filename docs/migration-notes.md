# Migration notes: 3.1 → 4.0

A running list of every change that an existing application, a deployment or a custom C# extension can notice when moving from Dataphor 3.1 (.NET Framework) to 4.0 (.NET 10). It exists so that moving an application later is a checklist, not an investigation. It will be turned into a proper guide before release (`docs-migration-guide-custom-code` in the [plan](modernization-plan.md)).

**How to maintain it.** Any change that alters something visible from outside the engine — a D4 class name, an operator, a setting, a file location, a public C# type or member that extensions use, a deployment step — adds an entry here *in the same commit*. One line saying what changed, one saying what to do about it. Mark an entry **planned** while it is only decided and **done** once the code has changed. Keep it generic: no customer names, paths or schema.

## Platform and deployment

| Status | Change | What to do |
|---|---|---|
| planned | Everything runs on .NET 10; nothing runs on .NET Framework. | Install with the 4.0 installer (self-contained; no separate runtime needed). 3.1 can stay installed side by side |
| planned | Clients and server must be the same major version; a 3.1 client is not expected to connect to a 4.0 server. | Upgrade the server and all clients together |
| done | The embedded catalog store is SQLite; SQL Server Compact is gone and existing catalog files are not converted. The default catalog file is `<instance>\Catalog\DAECatalog.sqlite` (it was `DAECatalog.sdf`); a `DAECatalog.sdf` left in the folder is ignored, with a warning in the server log. An instance whose `catalogstoreclassname` names the SQL Server Compact store, or whose `catalogstoreconnectionstring` names a `.sdf` file with no class name set, does not start and reports error 115108 naming the settings to remove; a store class that cannot be loaded reports 115107. For extensions: `Server.GetCatalogStoreDatabaseFileName()` returns the `.sqlite` path, and the new constant `Server.DefaultCatalogStoreClassName` holds the default store's class name. | Create a new instance, or remove the two settings from the existing one, and rebuild the catalog from the application's scripts, as in a routine catalog rebuild |
| done | The Windows service is registered by the service executable itself (`DAEService.exe -i`, `DAEService.exe -u`), by the installer, or later by the `dataphor` command-line tool - never by an installer class inside the executable, which .NET 10 does not have. The switches are the ones 3.1 took, and `DAEServer.exe` takes them too. | Nothing changes for an operator registering by hand from an elevated prompt; a deployment script that called `installutil` calls `DAEService.exe -i -n "<instance>"` instead |
| done | The ASP.NET WebForms web client is removed. | Anything built on it must be rewritten against another front end |
| done | The Silverlight client is removed. | Nothing; it had no users |
| done | The `AllowSilverlightClients` instance setting is removed. It only ever switched on the cross-domain access-policy service the Silverlight client needed. | Remove the setting; an instance configuration file that still carries it loads, and the setting is ignored |
| done | The `UseServiceConfiguration` instance setting is removed, and with it the ability to declare the server's network endpoints in the host application's configuration file: a 4.0 server always builds its endpoints in code, from the instance's port number and name. The class that implemented the route is removed outright. An instance configuration file that still carries the attribute loads unchanged — the attribute is ignored, and every other setting on the instance is still read — and the attribute is dropped the next time the instance list is saved. | Remove the setting, and remove `<system.serviceModel>` sections from the host application's configuration file; set the instance's port number instead |
| planned | ClickOnce deployment of the Windows client moves to the .NET publishing tools. | Republish the client with the new profile; existing ClickOnce installations will not update themselves across this change |
| planned | String comparison and culture behaviour are pinned to Windows NLS, as on .NET Framework. | Nothing, unless a host process is built by hand: set `System.Globalization.UseNls` |
| done | The SQL Server catalog store (`Alphora.Dataphor.DAE.MSSQL`, store class `Alphora.Dataphor.DAE.Store.MSSQL.MSSQLStore`) is built and shipped again, so a deployment can name it in `catalogstoreclassname`; SQLite is still the default and still the recommendation. The store now forces `MultipleActiveResultSets=True` into whatever `catalogstoreconnectionstring` supplies, including over a setting of `False`: the catalog opens a second store cursor while a first one is still open, which SQL Server refuses without it. | Drop `MultipleActiveResultSets` from the instance's store connection string; the store sets it. Non-ASCII characters in catalog object, library or user names are safe on this store now that the SQL Server client sends text as Unicode (its own entry below), but a catalog written by an earlier build still holds the question marks that were stored in place of the characters it lost, and nothing converts them. Prefer SQLite unless a deployment needs its catalog in SQL Server |
| done | The `PGSQLConnection` library is built and shipped again, on the NuGet `Npgsql` package (10.0.4) rather than the Npgsql 2.0.4 and Mono.Security 2.0 binaries 3.1 carried. Its library folder therefore holds a different set of files: `Npgsql.dll` is the new driver, `Mono.Security.dll` is gone and the library descriptor `PGSQLConnection.d4l` no longer lists it. The D4 class name `PostgreSQLConnection.PostgreSQLConnection` is unchanged. Fifteen years of driver change sit between the two versions and an application can see some of it - how `DateTime` values and time zones are handled above all - and none of that is proved yet: the PostgreSQL *device* is not shipped again until `device-pgsql-port`, which is where the behaviour is tested against a real server and this entry gains the detail. | Nothing yet, since no shipped device uses the library until that work lands. When upgrading a 3.1 installation in place rather than installing fresh, delete the old `Npgsql.dll` and `Mono.Security.dll` from the `PGSQLConnection` library folder so that the 2009 driver cannot be loaded instead of the new one |
| done | The SQLite catalog store uses `System.Data.SQLite.Core` 1.0.119 (3.1 shipped `System.Data.SQLite` 1.0.60, 32-bit only). Its native interop (`SQLite.Interop.dll`) ships next to the server for each supported architecture, under `runtimes/<platform>/native/`. | Nothing, unless a deployment copied `System.Data.SQLite.dll` by hand: remove that step |
| done | The SQLite catalog store always runs in write-ahead-logging (WAL) mode, so that readers never wait for a writer: while the server runs, `DAECatalog.sqlite-wal` and `DAECatalog.sqlite-shm` sit beside the catalog file, and a `Journal Mode` in `catalogstoreconnectionstring` is ignored. WAL does not work on a network file system. | Keep the instance's `Catalog` folder on a local disk; copy or back up the catalog file only while the server is stopped (a clean stop folds the `-wal` file back in and deletes both); remove any `Journal Mode` setting |
| done | A session waits at most `BusyTimeout` milliseconds for another session's write lock on the catalog store, then fails with error 130103 (see the next section). The default is 30000; set it in `catalogstoreconnectionstring`, for example `Data Source=%CatalogPath%\DAECatalog.sqlite;BusyTimeout=60000`. Unless the string sets `Default Timeout`, the provider's own retry time is derived from it, so that `BusyTimeout` alone bounds the wait. | Nothing, unless sessions hit 130103 under normal load: raise `BusyTimeout` |
| done | Installing and uninstalling the Windows service no longer uses the .NET Framework installer classes, so the files `DAEService.InstallLog`, `DAEService.InstallState` and `InstallUtil.InstallLog` are neither written nor read any more. Registration goes to the Windows service control manager directly, and what it registers is what 3.1 registered: the service name and display name `Alphora Dataphor (<instance>)`, the description, one service per process, automatic start, the LocalSystem account, and the command line `"<folder>\DAEService.exe" -name "<instance>"`. A failure (no administrative rights, the service already registered, the service not registered) reaches the caller as the service control manager's own error message instead of being written to an install log. | Nothing: an existing 3.1 registration keeps working, so replacing an installation's files in place needs no re-registration. Remove the three files above from anything that collects or archives them |
| done | `ServiceUtility` and the `ServiceStatus` enum moved out of the service executable (`DAEService`) into the new assembly `Alphora.Dataphor.DAE.Host`, keeping the namespace `Alphora.Dataphor.DAE.Service` and the signature of every member the tray configuration utility and the service use; `Install` gained an overload that takes the binary path and arguments to register. Five members that only described the registry layout the class no longer touches are gone: `GetServiceAutoStartRegKeyName`, `ServiceStartModeRegName`, `ServiceAutoStartRegValueName`, `ServiceAutoStart` and `ServiceManualStart`. The service's start mode is read and written through the service control manager rather than through `HKLM\System\CurrentControlSet\Services\<name>`, and reading it no longer needs administrative rights: an unelevated process used to report an installed service as not installed, or fail outright, because the old code opened that key for write in order to read it. | Reference `Alphora.Dataphor.DAE.Host` where an extension or a host program used `ServiceUtility` from `DAEService`; replace any use of the five removed members with the service control manager (`ServiceController`, or `GetServiceAutoStart`/`SetServiceAutoStart`) |
| done | `DAEServer.exe` (the console host) and `DAEService.exe` (the Windows service) are one program under two names: the same switches, the same behaviour, the same server. `DAEService.exe` is still the binary a service registration names, and a registration 3.1 made keeps working. Running as a Windows service is no longer a separate code path - the program detects that the service control manager started it - so the public class `Alphora.Dataphor.DAE.Service.Service` in `DAEService.exe` no longer derives from `System.ServiceProcess.ServiceBase` and has no constructors, `OnStart` or `OnStop` of its own. | Nothing for an operator. Host code that drove that class (there was no reason to, from outside the executable) calls `DataphorHost.Run` in `Alphora.Dataphor.DAE.Host` instead |
| done | A console host is stopped with Ctrl+C, or by terminating the process; pressing Enter no longer stops it, because the program no longer reads standard input. Reading it was wrong for a program whose input may be redirected or closed: the host then stopped the moment it started. | Stop a console host with Ctrl+C. A supervisor that held standard input open and closed it to stop the server must send Ctrl+C or terminate the process instead |
| done | `DAEServer.exe` rejects a command line it does not recognize, printing the syntax and exiting 1; it used to accept and ignore every argument, so a mistyped switch silently started the default instance. `DAEService.exe` always rejected it. Both programs exit 0 after a clean stop and 1 after a failure they have reported. | Check scripts that pass switches to `DAEServer.exe`. What both programs accept: `-i`/`-install`, `-u`/`-uninstall`, `-r`/`-run`, and `-n`/`-name <instance>` |
| done | Neither host executable has an application configuration file any more: `DAEServer.exe.config` and `DAEService.exe.config` are neither written nor read. The first held a `<system.serviceModel>` section (see the `UseServiceConfiguration` entry above) and a .NET Framework version element. The second held the garbage-collection settings, which are now compiled into both programs, a .NET Remoting section that no longer exists, and a commented-out `dataphor configurationFileName` element meant to point a second service at a configuration file of its own - which never worked, because the code read a section named `instance` while the file declared one named `dataphor` (known defect K12). | Remove both files from a deployment. If `DAEService.exe.config` was hand-edited to add a `dataphor configurationFileName` element, the instance it was meant to configure was never configured by it: run two *named* instances instead, with `-n`/`-name` and an entry each in `ServerConfigurations.config` |
| done | Both host executables run with server, non-concurrent garbage collection, which the Windows service always asked for in its configuration file and which is now compiled in. The console host previously ran workstation, concurrent garbage collection. | Nothing, unless a machine needs the console host to use workstation garbage collection: set `DOTNET_gcServer=0` in its environment |
| done | The machine's list of server instances carries the major version in its folder: it is `%ProgramData%\Alphora\Dataphor\4\Instances\ServerConfigurations.config`, where 3.1 used `%ProgramData%\Alphora\Dataphor\Instances\ServerConfigurations.config`. Each instance's own data folder (catalog, logs, device data) defaults to a sub-folder of the versioned folder in the same way. This is what lets a 4.0 server be installed beside a 3.1 one: without it the 4.0 server reads the 3.1 instance list, writes to it, and points its catalog at the 3.1 catalog, which it cannot open. 3.1's folder and files are left exactly where they are; nothing is copied forward or removed. The client's own machine-wide and per-user alias lists (`Aliases.config`) have always carried the major version this way, and `Instances` is now a folder beside the 4.0 `Aliases.config`. | An operator upgrading does not see the instances a 3.1 installation had: register the instance again and re-enter its port number, library directories and device settings, or let the 4.0 installer create it. The settings are readable in the 3.1 file, which is untouched. Point a deployment script that edits `ServerConfigurations.config` by path at the versioned folder |
| done | An instance configured to require a secured connection (`requiresecureconnection`, `requiresecurelistenerconnection`) starts as it always did and now writes a warning to its own log naming the settings that are set. Neither setting has ever reached a binding, here or in 3.1: connections to the instance are not encrypted. The settings themselves are unchanged, so the instance configuration file loads and saves exactly as before. | Remove the settings, which changes nothing about how the instance runs; or, where the connection must really be encrypted, host the server from a program of your own that supplies a binding with transport security through `DataphorServiceHostHooks.BuildBindingCall`, with the matching `DataphorServiceUtility.BuildBindingCall` in every client |
| done | A client connection whose security mode is `Transport` is **refused**, with a `NotSupportedException` naming the setting and the two remedies, where it used to connect unencrypted in silence. This covers a connection alias's *Security Mode* and the listener's (the listener's only on an alias with no override port, which is the only path that uses the listener), and a custom extension that constructs `ClientServer`, `NativeCLIClient` or `NativeCLISession` directly. Nothing is refused where the client's binding hook `DataphorServiceUtility.BuildBindingCall` has been replaced, that binding being the site's own. | Set the alias's security mode to `Default` or `None`, both of which connect unencrypted as the `Transport` setting always did in practice; or install a binding with transport security through `DataphorServiceUtility.BuildBindingCall` from the client program's start-up code |
| done | A process can be pointed at a different instance folder with the environment variable `DATAPHOR_INSTANCE_DIRECTORY`, which names the folder itself (not a root the rest of the path is appended to). A relative value is relative to the process's current directory. It exists so that a server can be started, and a configuration tried, without reading or writing the machine's own list - a host started for an instance that is not in the list it resolves **adds a default entry and saves the file**. Every process that must see the same list has to have the variable set, the client included, because the host, the configuration utility, the IDE and a client opening an in-process alias all resolve the folder the same way. The folder is created when it is first used; a value that cannot be used is reported with the path in the message. | Nothing for a normal installation, which sets it nowhere. Set it for an isolated server used for testing or diagnosis, and set it for every process in that group. Note that the machine's listener (port 8060) serves whichever list its own process resolved, so a redirected host that holds the listener advertises its private instances |
| done | A connection whose client has stopped sending its keep-alive ping is relinquished sooner. The idle threshold is unchanged at five minutes, but the server now looks for idle connections every quarter of it rather than once per threshold, so a vanished client's connection - and the catalog store's write lock its open transaction may hold against every other session's schema changes - is released between 300 and 375 seconds after its last ping, where it was between 300 and 600. There is still no instance setting for the threshold, deliberately: its floor is the keep-alive interval compiled into the shipped client, so a lower value would start killing live sessions. | Nothing. An operator who had allowed for a ten-minute worst case can expect a little over six |

## D4, catalog and libraries

| Status | Change | What to do |
|---|---|---|
| done | The D4 class `Connection.SQLCEConnection` no longer exists; the `Connection` library no longer registers it. | Remove references to it |
| done | Distributed (DTC) transactions are not supported: setting `UseDTC` (process) or `DefaultUseDTC` (session) to true, through `System.Processes`/`System.Sessions` or the API, raises error 106119. They have not functioned since 2009. | Remove any use; leave the settings false |
| done | An update of `System.Processes` that reaches the end of the row no longer fails with "Column MaxCallDepth not found": the catalog device now reads the table's `MaxNestingLevel` column and passes a changed value to the process's maximum call depth, as it already did for `MaxStackDepth`. For the process running the update, both limits then apply only to the update statement itself; the next statement starts with the previous values. | Nothing; scripts that worked around the error by not updating `System.Processes` can use it |
| done | `LeaveApplicationTransaction` (the D4 operator and the `IServerProcess` call) raises error 125111, "Cannot leave application transaction while a transaction is open on the process.", in two cases. First, when the process has a transaction open that the leaving statement did not begin itself: one begun with `BeginTransaction`, one left open by `SetUseImplicitTransactions(false)`, or the transaction of an enclosing statement, as when the leave runs inside `Execute` or `ExecuteScript`. Second, when the leaving statement's own implicit transaction has itself already changed something in the application transaction (an insert, update or delete recorded on the AT session's current device transaction, directly or inside a nested transaction committed into it); a leave in a statement that has changed nothing still succeeds, so `LeaveApplicationTransaction();` by itself, or in a batch that only read from the application transaction, continues to work. The process stays joined and the transaction and the application transaction's work are untouched. In 3.1 the leave went ahead and silently discarded every change made in the application transaction during the open transaction, including changes made in the leaving statement itself. Ending the application transaction, and stopping a process that is still joined, leave as before. | End the transaction (commit or roll back) before leaving; code that leaves in a `finally` block inside a transaction should end the transaction first, or the 125111 error replaces the original one. A statement that changes an application transaction and then leaves in the same statement, including an operator whose body does both, must put the leave in a separate statement |
| done | `CommitApplicationTransaction` and `PrepareApplicationTransaction` work on a process with implicit transactions off and no transaction open; they used to fail with "A nil was encountered where a value was expected" (a `NullReferenceException`) when the application transaction held changes. | Nothing; code that wrapped the call in `BeginTransaction`/`CommitTransaction` only to avoid the error can keep or drop the wrapper |
| done | The FHIR, CQF and PHINVADS libraries are parked and not shipped, with every D4 class name they register (prefix `FHIR.`, `CQF.`, `PHINVADS.`). The general-purpose dynamic and JSON nodes in System.Internet keep shipping under their existing `FHIR.Core.` names. The names `FHIRCore.ObjectAsJSON*` and `FHIRCore.FHIRBaseDisplayString` were never registered by this codebase; they appear only in commented-out D4. | Check scripts for `class "FHIR…"` references outside comments; any that name a parked library need another implementation |
| done | The MySQL, DB2, DB2/400, InterSystems Caché, Linter and Fastore devices and connections, the DataDirect Oracle connection and the ODP.NET (`Oracle.DataAccess`) Oracle connection are removed, with the D4 class names they registered. | Move the data to a supported device (SQL Server, PostgreSQL, the in-memory device or SimpleDevice) before upgrading; remove `create device` statements that name these classes |
| done | Devices and connections for Oracle (through the Microsoft provider), ADO (COM) and SAS are parked and not shipped; their source is kept, unbuilt, under `legacy/libraries/`. | SQL Server, PostgreSQL, the in-memory device and SimpleDevice ship in 4.0 |
| done | The `ODBCConnection` library ships again, so the D4 class `ODBCConnection.ODBCConnection` is available as it was in 3.1. It now uses the `System.Data.Odbc` NuGet package, whose files are deployed in the library's folder; a device that names this connection class still needs an ODBC driver and a driver manager configured on the machine running the server. The `Connection` library's `Connection.OLEDBConnection` class is likewise unchanged, on the `System.Data.OleDb` package, which is Windows-only. | Nothing; an application that stopped using the ODBC connection because it was unavailable can use it again |
| planned | The PostgreSQL device moves from Npgsql 2.0 to the current Npgsql. Type mapping (notably timestamps and time zones), connection-string keywords and error details may differ. | Test against the production PostgreSQL version; specific differences will be listed here as the port finds them |
| done | The SQL Server device and the SQL Server catalog store use `Microsoft.Data.SqlClient` 7.1.2; `System.Data.SqlClient`, which is a compatibility package and no longer developed, is gone. The new client encrypts the connection by default and then checks that the server's certificate is one this machine trusts, where the old client did neither. So both the device and the store supply what the old client negotiated, `Encrypt=False`, when the definition says nothing about encryption: a device definition or a `catalogstoreconnectionstring` that names a server and a database still reaches a SQL Server whose certificate is self-signed or absent, as it did in 3.1. | Nothing, to go on connecting as before. To encrypt instead, say so and the default gives way: `'ConnectionParameters' = 'Encrypt=True'` on the device (or on a device session), and `Encrypt=True` - or `TrustServerCertificate=True` - in `catalogstoreconnectionstring`. The next entry says which server versions are supported |
| done | **SQL Server 2022 is the supported minimum** for both the SQL Server device and the SQL Server catalog store, and SQL Server 2019 also works with no extra code and no settings of its own. Older releases are not supported, although nothing refuses them and SQL Server 2016 passes the same tests today. Support follows roughly the last five years of SQL Server releases. What was run against which version, the connection settings each certificate state needs, and what the device makes of a schema it did not create are in [Which SQL Server versions work](users-guide/dataphor-service.md#which-sql-server-versions-work). | A deployment on 2019 or earlier needs nothing beyond the encryption setting in the entry above: `Encrypt=False` is what the device and the store already default to, and a connection string used by anything else - a catalog rebuild script, a monitoring query - needs `Encrypt=False` or `TrustServerCertificate=True` said in it for a server whose certificate this machine does not trust. Do not set `Encrypt=Strict`: SQL Server 2019 does not support it at all, and on 2022 it ignores `TrustServerCertificate`, so it needs a certificate the machine really trusts |
| done | Text written to SQL Server through the SQL Server device or the SQL Server catalog store now arrives as Unicode. Every string parameter is described to the server as `nvarchar` where it was `varchar`, and an `SQLText` parameter as `ntext` where it was `text`, in both of the two places a SQL Server parameter is described - the client-side parameter and the type list a server-side cursor is opened with. Before, the server converted each value to the database's collation code page on the way in, and every character that code page had no room for was stored as a question mark, silently and permanently: a value written to an `nvarchar`, `nchar` or `ntext` column - which this device accepts as a D4 string or `SQLText`, and which is the ordinary shape for a database holding text in more than one language - lost characters the column could have held. A `varchar` column still holds only what a `varchar` column can hold, because the server converts the parameter on the way into it - and that includes a table the device itself created, because the device declares a D4 string column `varchar(n)`, so text stored in a table D4 created on SQL Server still loses every character the database's code page has no room for. That remaining half is a separate defect and is not fixed here. One side effect comes with this: `nvarchar` is the higher-precedence type, so a comparison between a parameter and an indexed `varchar` column whose collation is a *SQL* collation (`SQL_Latin1_General_CP1_CI_AS` and its siblings) can no longer seek that index and scans it instead - measured on SQL Server 2016 as 625 logical reads against 3 on a 200,000-row table. | Nothing to get the correct text, and nothing at all for a schema whose text columns are `nvarchar`. If a restriction on an indexed `varchar` column gets slower, either declare that column `nvarchar` - the device already maps `nvarchar` and `nchar` to D4 `String`, so no D4 changes, although for a table the device created this means altering the column in SQL Server, D4 having no way to ask for a Unicode column - or give it a Windows collation such as `Latin1_General_CI_AS`, where SQL Server seeks the index through a conversion instead (3 logical reads, measured on the same table) |
| done | The `TestFramework` test library no longer requires `MSSQLDevice` or creates the SQL Server device `TestingDevice`, and it has no default device; registering it, or `TestFramework.Coverage.Base`, needs no database server. A library that requires `TestFramework` and leaves its default device empty, such as `TestFramework.StressTest`, now puts its tables in `System.Temp`. | Rebuild an instance that registered the 3.1 `TestFramework` |
| done | No test library creates a SQL Server device of its own any more. `TestFramework.Coverage.Devices` held the last two: its `DeviceMSSQL.d4` created `TestingDevice` (server `localhost`) and its `TestMSSQLDevice.d4` created `TestDevice` (server `.`), both on the database `DataphorTests`, and both named a machine that only their author had. Each script now expects the device to exist already and the statement that created it is gone; everything else in the two scripts, every assertion included, is unchanged. Registering `TestFramework.Coverage.Devices` therefore fails unless a device named `TestingDevice` has been created first, because its registration script sets that device as the library's default and alters it. | Create the two devices against your own server before registering the library - `create device TestingDevice reconciliation { mode = { command }, master = device } class "MSSQLDevice.MSSQLDevice" attributes { "ServerName" = "...", "DatabaseName" = "..." };` in a library the one being registered requires, and the same for `TestDevice` before running `TestMSSQLDevice`. The suite's own fixture, `tests/DAE.Server.Tests/LiveDeviceTest.cs`, does exactly that from the server `DATAPHOR_TEST_MSSQL` names |
| done | The source text kept for an operator written on one line is exact. Before, the text stored in the catalog and returned by `Script()` for an operator whose body began and ended on the same line ran on into whatever followed it on that line, and the last section of an aggregate operator ending in a string literal (`finalization class "…"`) could lose or gain characters with its indentation; such operators could then fail to load from the catalog ("Errors occurred while attempting to deserialize catalog object"). | Nothing; the catalog is rebuilt from scripts, which stores the exact text |
| done | New error 130103, "The catalog store is locked by another session's open transaction and did not become available within *n* seconds" (severity Environment), replaces the SQLite "database is locked" error wrapped in a connection error. It is raised when a statement that changes the catalog waits longer than `BusyTimeout` for another session's transaction that has changed the catalog. | Retry; if it recurs, find the session with a long-running transaction that has changed the catalog and end it — and if no transaction is long, raise `BusyTimeout`: the wait is unfair rather than queued, so sustained concurrent schema changes alone can starve a session past it |
| done | A transaction holds the catalog store's write lock only from its first statement that changes the catalog until it ends; a transaction that only reads the catalog never takes it, so a long transaction blocks other sessions' schema changes only once it has changed the catalog itself. Before, once a session had changed the catalog, each of its later transactions opened a store transaction at its start, whether or not it wrote. A transaction that has changed the catalog sees its own uncommitted changes in every catalog lookup, but a D4 query over a catalog table that the store answers (`System.Objects`, `System.Operators`, …) shows committed rows only, as in 3.1. | Keep transactions that change the catalog short; a session abandoned inside one still blocks other schema changes until the server reclaims the connection, which is within 375 seconds of its last keep-alive ping |
| done | Rolling back a transaction begun at isolation level `Browse` now also rolls back its catalog changes in the store (K26). Before, only the in-memory catalog was rolled back: the store kept the rows, and the rolled-back object came back when next resolved or after a restart. | Nothing |
| done | `SetObjectOwner` on a name that resolves to no catalog object raises error 113177, "Catalog object expected.", instead of a null-reference error. | Nothing, unless a script or client matched the old error |
| done | `SetObjectOwner` and `SetRightOwner` take the rights away from the previous owner as soon as the change commits: from then on the previous owner is refused an object right it held only as owner (error 106157). Before, a right the previous owner had already used stayed granted to it until the server restarted or something else cleared that user's cached rights. A rolled-back `SetObjectOwner` now also restores the owner the server holds in memory, under whose rights operator bodies, views and table handlers are compiled and run; before, those ran under the rolled-back owner until the server restarted. | Grant the previous owner, directly or through a role, any right it still needs after giving an object away |
| done | A change to who may use a right takes effect for every session when the transaction that makes it ends, and a rolled-back change leaves no trace: granting, revoking or reverting a right (to a user or a role), adding a user to a role or removing one, `SetObjectOwner`, `SetRightOwner`, creating or dropping an object, a right or a role. Before, the server's answer to "may this user use this right" that any session looked up while the transaction was open (a check inside the transaction itself, or in another session) could outlive the transaction until the server restarted: a revoked right stayed usable, a right granted in a rolled-back transaction stayed granted, and a right of an object created in the transaction stayed granted to every user. Dropping a role now also takes the rights it granted from its members at once; before, a member kept each one it had already used until the server restarted.
