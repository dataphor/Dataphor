# Migration notes: 3.1 → 4.0

A running list of every change that an existing application, a deployment or a custom C# extension can notice when moving from Dataphor 3.1 (.NET Framework) to 4.0 (.NET 10). It exists so that moving an application later is a checklist, not an investigation. It will be turned into a proper guide before release (`docs-migration-guide-custom-code` in the [plan](modernization-plan.md)).

**How to maintain it.** Any change that alters something visible from outside the engine — a D4 class name, an operator, a setting, a file location, a public C# type or member that extensions use, a deployment step — adds an entry here *in the same commit*. One line saying what changed, one saying what to do about it. Mark an entry **planned** while it is only decided and **done** once the code has changed. Keep it generic: no customer names, paths or schema.

## Platform and deployment

| Status | Change | What to do |
|---|---|---|
| planned | Everything runs on .NET 10; nothing runs on .NET Framework. | Install with the 4.0 installer (self-contained; no separate runtime needed). 3.1 can stay installed side by side |
| planned | Clients and server must be the same major version; a 3.1 client is not expected to connect to a 4.0 server. | Upgrade the server and all clients together |
| done | The embedded catalog store is SQLite; SQL Server Compact is gone and existing catalog files are not converted. The default catalog file is `<instance>\Catalog\DAECatalog.sqlite` (it was `DAECatalog.sdf`); a `DAECatalog.sdf` left in the folder is ignored, with a warning in the server log. An instance whose `catalogstoreclassname` names the SQL Server Compact store, or whose `catalogstoreconnectionstring` names a `.sdf` file with no class name set, does not start and reports error 115108 naming the settings to remove; a store class that cannot be loaded reports 115107. For extensions: `Server.GetCatalogStoreDatabaseFileName()` returns the `.sqlite` path, and the new constant `Server.DefaultCatalogStoreClassName` holds the default store's class name. | Create a new instance, or remove the two settings from the existing one, and rebuild the catalog from the application's scripts, as in a routine catalog rebuild |
| planned | The Windows service is registered by the installer or the `dataphor` command-line tool, not by an installer class inside the service executable. | Re-register services with the new tooling; existing command-line switches are kept as aliases where practical |
| done | The ASP.NET WebForms web client is removed. | Anything built on it must be rewritten against another front end |
| done | The Silverlight client is removed. | Nothing; it had no users |
| done | The `AllowSilverlightClients` instance setting is removed. It only ever switched on the cross-domain access-policy service the Silverlight client needed. | Remove the setting; an instance configuration file that still carries it loads, and the setting is ignored |
| done | The `UseServiceConfiguration` instance setting is removed, and with it the ability to declare the server's network endpoints in the host application's configuration file: a 4.0 server always builds its endpoints in code, from the instance's port number and name. The class that implemented the route is removed outright. An instance configuration file that still carries the attribute loads unchanged — the attribute is ignored, and every other setting on the instance is still read — and the attribute is dropped the next time the instance list is saved. | Remove the setting, and remove `<system.serviceModel>` sections from the host application's configuration file; set the instance's port number instead |
| planned | ClickOnce deployment of the Windows client moves to the .NET publishing tools. | Republish the client with the new profile; existing ClickOnce installations will not update themselves across this change |
| planned | String comparison and culture behaviour are pinned to Windows NLS, as on .NET Framework. | Nothing, unless a host process is built by hand: set `System.Globalization.UseNls` |
| done | The SQLite catalog store uses `System.Data.SQLite.Core` 1.0.119 (3.1 shipped `System.Data.SQLite` 1.0.60, 32-bit only). Its native interop (`SQLite.Interop.dll`) ships next to the server for each supported architecture, under `runtimes/<platform>/native/`. | Nothing, unless a deployment copied `System.Data.SQLite.dll` by hand: remove that step |
| done | The SQLite catalog store always runs in write-ahead-logging (WAL) mode, so that readers never wait for a writer: while the server runs, `DAECatalog.sqlite-wal` and `DAECatalog.sqlite-shm` sit beside the catalog file, and a `Journal Mode` in `catalogstoreconnectionstring` is ignored. WAL does not work on a network file system. | Keep the instance's `Catalog` folder on a local disk; copy or back up the catalog file only while the server is stopped (a clean stop folds the `-wal` file back in and deletes both); remove any `Journal Mode` setting |
| done | A session waits at most `BusyTimeout` milliseconds for another session's write lock on the catalog store, then fails with error 130103 (see the next section). The default is 30000; set it in `catalogstoreconnectionstring`, for example `Data Source=%CatalogPath%\DAECatalog.sqlite;BusyTimeout=60000`. Unless the string sets `Default Timeout`, the provider's own retry time is derived from it, so that `BusyTimeout` alone bounds the wait. | Nothing, unless sessions hit 130103 under normal load: raise `BusyTimeout` |

## D4, catalog and libraries

| Status | Change | What to do |
|---|---|---|
| done | The D4 class `Connection.SQLCEConnection` no longer exists; the `Connection` library no longer registers it. | Remove references to it |
| done | Distributed (DTC) transactions are not supported: setting `UseDTC` (process) or `DefaultUseDTC` (session) to true, through `System.Processes`/`System.Sessions` or the API, raises error 106119. They have not functioned since 2009. | Remove any use; leave the settings false |
| done | An update of `System.Processes` that reaches the end of the row no longer fails with "Column MaxCallDepth not found": the catalog device now reads the table's `MaxNestingLevel` column and passes a changed value to the process's maximum call depth, as it already did for `MaxStackDepth`. For the process running the update, both limits then apply only to the update statement itself; the next statement starts with the previous values. | Nothing; scripts that worked around the error by not updating `System.Processes` can use it |
| done | `LeaveApplicationTransaction` (the D4 operator and the `IServerProcess` call) raises error 125111, "Cannot leave application transaction while a transaction is open on the process.", in two cases. First, when the process has a transaction open that the leaving statement did not begin itself: one begun with `BeginTransaction`, one left open by `SetUseImplicitTransactions(false)`, or the transaction of an enclosing statement, as when the leave runs inside `Execute` or `ExecuteScript`. Second, when the leaving statement's own implicit transaction has itself already changed something in the application transaction (an insert, update or delete recorded on the AT session's current device transaction, directly or inside a nested transaction committed into it); a leave in a statement that has changed nothing still succeeds, so `LeaveApplicationTransaction();` by itself, or in a batch that only read from the application transaction, continues to work. The process stays joined and the transaction and the application transaction's work are untouched. In 3.1 the leave went ahead and silently discarded every change made in the application transaction during the open transaction, including changes made in the leaving statement itself. Ending the application transaction, and stopping a process that is still joined, leave as before. | End the transaction (commit or roll back) before leaving; code that leaves in a `finally` block inside a transaction should end the transaction first, or the 125111 error replaces the original one. A statement that changes an application transaction and then leaves in the same statement, including an operator whose body does both, must put the leave in a separate statement |
| done | `CommitApplicationTransaction` and `PrepareApplicationTransaction` work on a process with implicit transactions off and no transaction open; they used to fail with "A nil was encountered where a value was expected" (a `NullReferenceException`) when the application transaction held changes. | Nothing; code that wrapped the call in `BeginTransaction`/`CommitTransaction` only to avoid the error can keep or drop the wrapper |
| done | The FHIR, CQF and PHINVADS libraries are parked and not shipped, with every D4 class name they register (prefix `FHIR.`, `CQF.`, `PHINVADS.`). The general-purpose dynamic and JSON nodes in System.Internet keep shipping under their existing `FHIR.Core.` names. The names `FHIRCore.ObjectAsJSON*` and `FHIRCore.FHIRBaseDisplayString` were never registered by this codebase; they appear only in commented-out D4. | Check scripts for `class "FHIR…"` references outside comments; any that name a parked library need another implementation |
| done | The MySQL, DB2, DB2/400, InterSystems Caché, Linter and Fastore devices and connections, the DataDirect Oracle connection and the ODP.NET (`Oracle.DataAccess`) Oracle connection are removed, with the D4 class names they registered. | Move the data to a supported device (SQL Server, PostgreSQL, the in-memory device or SimpleDevice) before upgrading; remove `create device` statements that name these classes |
| done | Devices and connections for Oracle (through the Microsoft provider), ADO (COM) and SAS are parked and not shipped; their source is kept, unbuilt, under `legacy/libraries/`. | SQL Server, PostgreSQL, the in-memory device and SimpleDevice ship in 4.0 |
| planned | The PostgreSQL device moves from Npgsql 2.0 to the current Npgsql. Type mapping (notably timestamps and time zones), connection-string keywords and error details may differ. | Test against the production PostgreSQL version; specific differences will be listed here as the port finds them |
| planned | The SQL Server device uses `Microsoft.Data.SqlClient`. The intent is that existing device definitions connect unchanged, including to servers without a trusted certificate. | Test against the production SQL Server version; the minimum supported version will be documented |
| done | The `TestFramework` test library no longer requires `MSSQLDevice` or creates the SQL Server device `TestingDevice`, and it has no default device; registering it, or `TestFramework.Coverage.Base`, needs no database server. `TestingDevice` (server `localhost`, database `DataphorTests`) is now created by `TestFramework.Coverage.Devices`, so its full name is `TestFramework.Coverage.Devices.TestingDevice`. A library that requires `TestFramework` and leaves its default device empty, such as `TestFramework.StressTest`, now puts its tables in `System.Temp`. | Register `TestFramework.Coverage.Devices` where the SQL Server test device is wanted; rebuild an instance that registered the 3.1 `TestFramework` |
| done | The source text kept for an operator written on one line is exact. Before, the text stored in the catalog and returned by `Script()` for an operator whose body began and ended on the same line ran on into whatever followed it on that line, and the last section of an aggregate operator ending in a string literal (`finalization class "…"`) could lose or gain characters with its indentation; such operators could then fail to load from the catalog ("Errors occurred while attempting to deserialize catalog object"). | Nothing; the catalog is rebuilt from scripts, which stores the exact text |
| done | New error 130103, "The catalog store is locked by another session's open transaction and did not become available within *n* seconds" (severity Environment), replaces the SQLite "database is locked" error wrapped in a connection error. It is raised when a statement that changes the catalog waits longer than `BusyTimeout` for another session's transaction that has changed the catalog. | Retry; if it recurs, find the session with a long-running transaction that has changed the catalog and end it |
| done | A transaction holds the catalog store's write lock only from its first statement that changes the catalog until it ends; a transaction that only reads the catalog never takes it, so a long transaction blocks other sessions' schema changes only once it has changed the catalog itself. Before, once a session had changed the catalog, each of its later transactions opened a store transaction at its start, whether or not it wrote. A transaction that has changed the catalog sees its own uncommitted changes in every catalog lookup, but a D4 query over a catalog table that the store answers (`System.Objects`, `System.Operators`, …) shows committed rows only, as in 3.1. | Keep transactions that change the catalog short; a session abandoned inside one still blocks other schema changes until the server reclaims it |
| done | Rolling back a transaction begun at isolation level `Browse` now also rolls back its catalog changes in the store (K26). Before, only the in-memory catalog was rolled back: the store kept the rows, and the rolled-back object came back when next resolved or after a restart. | Nothing |
| done | `SetObjectOwner` on a name that resolves to no catalog object raises error 113177, "Catalog object expected.", instead of a null-reference error. | Nothing, unless a script or client matched the old error |
| done | `SetObjectOwner` and `SetRightOwner` take the rights away from the previous owner as soon as the change commits: from then on the previous owner is refused an object right it held only as owner (error 106157). Before, a right the previous owner had already used stayed granted to it until the server restarted or something else cleared that user's cached rights. A rolled-back `SetObjectOwner` now also restores the owner the server holds in memory, under whose rights operator bodies, views and table handlers are compiled and run; before, those ran under the rolled-back owner until the server restarted. | Grant the previous owner, directly or through a role, any right it still needs after giving an object away |
| done | A change to who may use a right takes effect for every session when the transaction that makes it ends, and a rolled-back change leaves no trace: granting, revoking or reverting a right (to a user or a role), adding a user to a role or removing one, `SetObjectOwner`, `SetRightOwner`, creating or dropping an object, a right or a role. Before, the server's answer to "may this user use this right" that any session looked up while the transaction was open (a check inside the transaction itself, or in another session) could outlive the transaction until the server restarted: a revoked right stayed usable, a right granted in a rolled-back transaction stayed granted, and a right of an object created in the transaction stayed granted to every user. Dropping a role now also takes the rights it granted from its members at once; before, a member kept each one it had already used until the server restarted. While the transaction is still open, each session's check of a right the transaction has changed now reads through its own store connection and bypasses the shared cache, so the changing session sees its uncommitted change and every other session sees the committed state. | Nothing, unless a user relied on keeping such a right: grant it explicitly |
| done | Inside a joined application transaction, reading a table by its bare name (`select T;`, a cursor on `T`) no longer fails with error 104137 (`Device "<no device>" does not support retrieval for the table variable …`); it reads the transaction's copy of the table, as a restricted read (`select T where …`) already did. | Nothing, unless a script worked around the error with a restriction or a copy of the table |
| done | Statements that change a table on the in-memory device (`System.Temp`, or any device of class `System.MemoryDevice`) while other sessions read or change the same table no longer fail with "A nil was encountered where a value was expected" or "Key not found", lose rows, or damage the table's index: each table serializes the statements that use it. Transactions on the in-memory device are still not isolated from each other, as in 3.1: an uncommitted change is visible to other transactions and can be overwritten by them. Reading `System.Sessions`, `System.Processes`, `System.Plans`, `System.Scripts`, `System.SessionCatalogObjects` or `System.DeviceSessions` while sessions connect and disconnect no longer fails with the same nil error; a session or process that is disconnecting or stopping at that moment is left out. Reading a catalog table in the order of its second key (`System.ServerLinks order by { Name }`) while another session reads the same table no longer fails with "Index was outside the bounds of the array". | Nothing; keep data that needs transactions isolated from each other on SQL Server or PostgreSQL |
| done | The D4 `System` library is version 4.0.0.0 (it was 3.1.<build>.<revision>, the engine assembly version, which is now 4.0.0.0). A library whose `.d4l` file requires `System` at version 3 or 3.1 fails to register with error 113207, `Library "System" is required to be version "3.*", but is available as version "4.0.0.0"` (`"3.1.*"` for a 3.1 reference); libraries that require `System` at version `*` are unaffected. | Change any `System` reference pinned to 3 or 3.1 to `*` or 4 |
| done | A library's assembly gets its private managed and native dependencies from the library's own folder in the runtime layout, and from the folders of the libraries it requires (transitively). Managed and native files are flattened into `Libraries\<Name>\`: a package's Windows runtime file (`win-x64` first, then `win`, then the generic one) is written straight into the folder, with no `runtimes\<rid>\...` subtree and no `.deps.json`. A library that ships a native dll (a C dependency, a vendor SDK, a bundled SQLite build) no longer needs a hand-written probe or a copy into the host's bin folder. The two load-context hooks are installed by `Alphora.Dataphor.Windows.AssemblyUtility`'s static constructor, which `Server` already calls before any library registers, and are off for assemblies the server did not load from a library folder (the host's bin and anything else resolves as before). | Rebuild a library whose 3.1 `.d4l` listed its dependencies as unregistered files or copied them to the host's bin folder: let the layout flatten them instead. A dll loaded through `LoadLibrary` before by hand will now resolve through `DllImport` on its base name |
| done | Text produced by the D4 emitter (`D4TextEmitter`) re-parses where it used to fail. The server stores and scripts catalog definitions through it (`ScriptObject`, `ScriptCatalog`, `ScriptDropCatalog`), so a definition that used one of six constructs came back as a script the parser could not read. The spellings that changed: the generic scalar type is written `scalar`, not `generic scalar`; the grantee of a `grant`, `revoke` or `revert` is written as a plain string (`user 'U'`), not with a trailing `i`; a hexadecimal literal is written (`0x1F`) instead of being dropped; a negative money literal is written `-$1`, not `$-1`; a qualified column extractor is written `(C.Name from X)`, not `C.(Name from X)`; and a numeric literal before a `.` is parenthesized (`(1).Max(50)`). The body of a `foreach` used as an expression is now separated from the `do` keyword by a space. | Regenerate catalog scripts produced by an earlier 4.0 preview; check code that pattern-matches emitted D4 text against the new spellings |

| done | `SQLStoreConnection.BeginTransaction` calls the protected virtual `InternalBeginTransaction` for the outermost begin; before, it called the SQL connection directly and the virtual was never called. The SQLite store overrides it to begin every store transaction immediate. | A custom catalog store that overrides `InternalBeginTransaction` must begin the SQL transaction there (the base implementation does) |
| done | Catalog store transactions begin when a process transaction first changes the catalog, not when it starts: `ServerCatalogDeviceSession` no longer begins one in its transaction begin, its writes take connections from the store's pool too, and a connection goes back to the pool when its store transaction ends. Beginning a store transaction while a store cursor's reader is still open on the connection is an internal error (new `SQLStoreConnection.OpenReaderCount`). New members `SQLStoreConnection.InDatabaseTransaction` and `CatalogStoreConnection.InDatabaseTransaction`. | A custom DDL node that overrides `InternalBeforeExecute` must call the base; extension code that writes the catalog store while holding `lock (Catalog)` should call `BeginStoreWriteTransaction` before taking the lock; read a store cursor into a list before writing |
| done | A catalog store cursor (`SQLStoreCursor`) changes exactly the row it is on, whatever index it was opened on. Its updates and deletes, and the undo of them in a nested transaction, name the row by a row key: the new overload `SQLStoreConnection.OpenCursor(tableName, columns, index, rowKey, isUpdatable)` takes it (the catalog store passes the table's primary key), and the existing overload now uses the index's columns if the index is unique, otherwise every column (before, always the index's columns, so a cursor on a non-unique index updated or deleted every row sharing the index value). The cursor orders on the index's columns followed by the row key's other columns, and `SelectKey()` returns that longer key. After `Update()` the cursor stays on the updated row and `Next()`/`Prior()` continue from its new values; after `Delete()` they continue from the deleted row's neighbours (before, the cursor was off the row and `Next()` started again at the beginning of the range). The generated `where` clause of an update or delete tests a null key value with `is null`. A cursor constructed without its column list reads the column names with one extra query before its first read. `CatalogStoreConnection.DeleteRows` names each deleted row by its primary key. | A custom catalog store needs no change: the row key is set on the cursor its `InternalOpenCursor` returns. Code that updates or deletes through a store cursor in a loop must not reposition the cursor after each write |
| done | A catalog store's generated insert, update and delete carry their values as parameters instead of SQL literals. The protected virtual `SQLStoreConnection.GenerateInsertStatement`, `GenerateUpdateStatement` and `GenerateDeleteStatement` each take a new last argument, an `SQLParameters` that the generator fills with one parameter per value, or null to render the values as literals as before. New members: the overload `ExecuteStatement(string statement, SQLParameters parameters)`, and the virtual `NativeToParameter(string name, object value)`, which returns the parameter that carries a native value - a boolean goes as the integer 1 or 0, which is what the `tinyint` columns the catalog declares need, and the PostgreSQL store overrides it because its catalog declares those columns `boolean`. `NativeToLiteralValue` stays: the undo log that a nested transaction rolls back from still holds literal statement text, and so do the ranged reader statements a store cursor opens. A null value, and a null in a key condition (`is null`), stay literal in both forms. Catalog write speed did not measurably change (the numbers are at the site, in `SQLStoreConnection.AppendValue`). | A custom catalog store that overrides one of the three `Generate...Statement` methods adds the `SQLParameters` argument and passes it on; one whose catalog declares the boolean columns as a boolean type overrides `NativeToParameter` as the PostgreSQL store does |
| done | `TableNode.DeterminePotentialDevice` is sealed. A table node subclass that determined its own potential device overrides the new `protected virtual void InternalDeterminePotentialDevice(Plan plan)` instead; the sealed method calls it and then determines the potential device of the node's application transaction populate node (`TableNode.PopulateNode`), which an override used to be able to skip. | In a custom `TableNode` subclass, rename an override of `DeterminePotentialDevice` to `InternalDeterminePotentialDevice` (protected) and keep its body; a call to `base.DeterminePotentialDevice` inside it becomes `base.InternalDeterminePotentialDevice` |
| done | `ServerCatalogDeviceSession.SetCatalogObjectOwner(int catalogObjectID, string userID)` is replaced by `SetCatalogObjectOwner(Schema.CatalogObject objectValue, Schema.User user)`, which also sets the object's `Owner` in the catalog cache, logs the change so that a rollback undoes it, and drops every user's cached answers for the object's rights. The new protected `CatalogDeviceSession.CacheCatalogObjectOwner` sets the cached owner without touching the store. | Pass the resolved object and user instead of their IDs, and do not set `Owner` before the call |
| done | New protected members of `CatalogDeviceSession`: `RightsChanged(params string[] rightNames)`, `UserRightsChanged(string userID)` and `AllRightsChanged()` drop users' cached answers to right checks now and again when the session's transaction ends. The catalog device session calls them after each store write that changes who has a right; `ClearUserCachedRightAssignments` now takes the catalog's lock. | Extension code that changes right assignments, role memberships or right owners through the catalog store directly should call the matching member after its write, or its change can stay invisible to sessions that already checked the right |
| done | When a device session's `InternalBeginTransaction` throws, `DeviceSession.BeginTransaction` removes the level it had just added to `Transactions`, and the process rolls back the new level on the remote and device sessions that had begun it and removes its own, so the caller gets the error with no transaction level begun. Before, the half-started transaction stayed open and later statements ran in it. | An override of `InternalBeginTransaction` must leave nothing begun when it throws: do the work that can fail before recording anything in the session's own state |
| done | Enumerating a `ServerChildObjects` list (`Server.Sessions`, a session's `Processes`, a process's `Plans` and `Scripts`, a script's `Batches`) walks a copy taken under the list's lock when the enumeration starts: an item added during the loop is not visited, and one removed during it is still visited, possibly while it is being disposed. Before, the loop read the live list and could skip an item, visit one twice, or fail when another thread removed one. | Code that enumerates another session's lists should allow for an item whose members a concurrent `Dispose` has cleared (read each member once and skip the item if it is null) |

## Forms and the Windows client
