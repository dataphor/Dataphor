# L1 coverage-script runner and manifest

Last of three tickets that make up this work item (after `test-common-tests-sdk` and `test-server-fixture`); it keeps the slug `test-harness-inprocess` that `test-decouple-coverage-base`, `port-engine-runtime-fixes`, `port-catalog-emitter-race`, `store-remove-sqlce-references`, `store-sqlite-concurrency` and `build-ci` wait on. Read the complete/review tickets of the two earlier pieces for what they actually built (`TestEnvironment`, `TestServerInstance`, the project file).

## Goal

Layer L1 of the plan's test suite: discover every D4 coverage script in the runtime layout's copy of `TestFramework.Coverage.Scripts/Documents`, run each as its own NUnit test case on an isolated in-process server, and check each result against a checked-in **manifest**. This makes the test half of gate G1 checkable (plan "Sequencing": *from a clean clone, `dotnet build` and `dotnet test` pass on .NET 10 with every D4 coverage script accounted for*). After this ticket every script is in the manifest as `pass` or as `known-failure` naming the ticket that owns its cause; `test-decouple-coverage-base` and `test-triage-known-failures` then replace the provisional entries.

## Settled constraints

- D2: there is no reference runtime; the scripts (about 2,100 `raise Error` assertions) are the oracle. **Never edit, skip or delete a coverage script.** A failing script is recorded in the manifest.
- Plan WS3 L1: a script that is not in the manifest fails the run; no silent skips.
- D8: NUnit; D4 scripts stay the main form of engine regression test.
- Never suppress `SYSLIB`/`WFDEV` warnings.

## Facts measured during planning

Planning ran all 136 scripts (not 135: `DistributedTransactions.d4` was added by `server-remove-remoting-and-dtc`) through a copy of the spike's coverage runner built against the repository's `Server` and `DAE.SQLite` projects, with NLS globalization on, the spike's library list copied from `artifacts/layout/debug/Libraries`, `Frontend` and `TestFramework.Coverage.Base` registered, one shared server, each script on its own 16 MB-stack thread. Findings that shape the design:

1. **All 63 of the spike's passes reproduce** (the spike's 62 plus `DistributedTransactions`), with NLS on.
2. **`DebugTest.d4` never ends, by design**: its loop adds 1, calls two identity operators and subtracts 1, so the counter never moves (it is a debugger stepping exercise). On the shared server its abandoned thread kept the SQLite catalog locked, and **every script after it that wrote to the catalog then failed with `SQLiteException: database is locked`** after the 30 s busy timeout. The engine can stop it cooperatively: every `PlanNode.Execute` calls `Program.Yield` or `Program.CheckAborted` (`src/engine/DAE/Runtime.Instructions/PlanNode.cs`, `src/engine/DAE/Runtime/Program.cs`), which throw once `ServerProcess.IsAborted` is set, and `Engine.StopProcess(int processID)` (`src/engine/DAE/Server/Engine.cs`) sets it and waits for the thread.
3. **Scripts interfere through shared catalog state.** On one shared server, `SerializationOperators`, `SerializationTables`, `SerializationViews` and `TestNetworkApplicationTransactions` failed with `An object named "General.<X>" is already defined`; each **passes when run alone on a fresh server**. (`SerializationReferences` fails alone too, on its own `General.Test`: a real failure.) Results on a shared server therefore depend on order and on which other scripts run.
4. **A fresh server per script is cheap if it starts from a snapshot.** Measured in one process: fresh start 0.95–1.2 s plus `Frontend` registration 0.25 s; versus copying a stopped, already-registered instance directory with its library copies (4.4 MB, 279 files) about 120 ms, starting on it about 130 ms, a no-op `EnsureLibraryRegistered('Frontend')` about 100 ms, stop about 1 ms; the copy's registered libraries and their documents worked from the new path. Today, registering `TestFramework.Coverage.Base` takes about 25 s because it waits for a SQL Server on `localhost` (K14) before failing; with a snapshot that cost is paid once per run, not per script.
5. **A library assembly is loaded once per process** (`Assembly.LoadFrom` in `src/engine/Server/Schema/LibraryUtility.cs`) from the first copy that registers it, and that copy's file stays locked until the process exits: after four servers, the first (template) folder could not be deleted (`UnauthorizedAccessException` on `Alphora.Dataphor.Frontend.Server.dll`); the later copies could. `test-server-fixture` already makes deletion best-effort with a stale-folder sweep at the next run.

## Design (settled)

### Server per script, from a template snapshot (open choices 4 and 5)

- `[OneTimeSetUp]` of the coverage fixture builds a **template**: a `TestServerInstance` with the coverage library set copied, started, `EnsureLibraryRegistered('Frontend');` and `EnsureLibraryRegistered('TestFramework.Coverage.Base');` each in its own `try` (a failure is written to `TestContext.Progress` with its flattened error and not thrown: until `test-decouple-coverage-base` the second one fails, and the affected scripts record that through their own errors), then stopped.
- Each case copies the template's whole directory (libraries and instance) to a new directory, starts a server on the copy (add this "from a copy of a stopped instance" constructor to `TestServerInstance`), runs the script, stops the server and disposes the directory.
- Why: no interference (finding 3), a hung script cannot poison the others (finding 2), and a case gives the same result whether it runs alone (`--filter`) or in the full run, so no deterministic-order rule and no reverse-order run are needed; NUnit's case order does not matter. Cost: about 0.4 s per script, about a minute for 136, plus the template once. The library copy guarantees the layout is never written (choice 5, copy), and scripts that create, rename or alter libraries (`LibraryCoverage`, `LibraryRename`) write only into their own copy.
- **Coverage library set** (one constant in the fixture, the spike's `COVERAGE_LIBS`, `tools/net-spike/run.py`): `Frontend`, `SimpleDevice`, `TestFramework.Coverage.Base`, `SQLDevice`, `MSSQLDevice`, `Connection`, `TestFramework`, `TestFramework.Coverage.Scripts`, `System.Internet`. A fixed list rather than all of `Libraries/`, so the set of available libraries the scripts see stays what the spike measured. `test-decouple-coverage-base` drops `MSSQLDevice` from it.
- **Logging** (choice 6): off, through `TestServerInstance` (`DATAPHOR_TEST_LOGGING=1` opts in, from `test-server-fixture`). No server change.
- **Catalog store connection string** (choice 10): the spike's, set by `TestServerInstance`.

### Running one script

On a dedicated background thread with a 16 MB stack (the spike's size; whether 1 MB suffices is unverified and not worth the risk, since a stack overflow kills the whole test host), in one session (`new SessionInfo("Admin", "")`) and one process:

1. for each library in the entry's `register` option: `EnsureLibraryRegistered('<name>');` — an exception here is wrapped so the flattened text starts with `HarnessRegister: <name>`;
2. the entry's `preamble`, if any, through `ExecuteScript` on the same process;
3. `ExecuteScript('Coverage.Scripts', '<script>');`
4. stop the process and disconnect (in `finally`).

The test thread joins the worker for the entry's `timeoutSeconds` (default 120; the longest script measured in planning took 5.7 s). On timeout: call `Engine.StopProcess(processID)` on the case's server (the worker publishes the process id after `StartProcess`; catch what `StopProcess` throws, such as `ProcessNotResponding`), join again for up to 10 s, and record the error text `HarnessTimeout: script did not finish within <N> s`, adding `; it did not stop when aborted and its server was abandoned` if the thread is still alive. An abandoned server is stopped on a background task that the test waits for at most 10 s; its directory is left for the next run's sweep. NUnit's `[Timeout]` is not used (it needs thread abort).

Then `Stop` the server; an exception from `Stop` is appended to the case's error text as `HarnessStop: <flattened>` and evaluated like any other error (a `pass` script whose server does not stop cleanly fails).

Exactly one non-`System` session exists while a script runs (the template's session is gone; `register` and `preamble` use the script's own session). `TestProcessExecutes.d4` depends on this (`Count(Sessions where User_ID <> "System") <> 1` raises; noted by `port-engine-runtime-fixes`).

### Manifest (choice 1)

`tests/DAE.Server.Tests/coverage-manifest.json`, beside the test project (the layout carries only the library), compiled into the test assembly as an `EmbeddedResource` with `LogicalName` `coverage-manifest.json` (a manifest edit rebuilds the test assembly, so nothing reads a stale copy). Strict JSON (no comments, so any tool can read it), UTF-8 without byte-order mark, LF line endings like `global.json`. One JSON array, **one entry per line**, sorted by `script` in ordinal order:

```json
[
{ "script": "AggregateOperators", "status": "pass" },
{ "script": "DebugTest", "status": "known-failure", "ticket": "test-triage-known-failures", "error": "HarnessTimeout", "timeoutSeconds": 5, "note": "infinite loop by design: a debugger stepping exercise" },
{ "script": "Lexer", "status": "known-failure", "ticket": "test-decouple-coverage-base", "error": "Unable to resolve operator reference \"NegativeTest\"" },
{ "script": "SecurityLibrary", "status": "known-failure", "ticket": "test-decouple-coverage-base", "error": "Library 'TestFramework.Coverage.Base' is not registered", "preamble": "SetUseImplicitTransactions(false);" }
]
```

Fields (anything else is an error):

| Field | Required | Meaning |
|---|---|---|
| `script` | always | Script name: the file name in `Documents/` without `.d4`, exact case |
| `status` | always | `pass`, `known-failure` or `unstable` |
| `ticket` | unless `pass` (forbidden on `pass`) | Slug of the ticket that owns the cause (no sequence prefix) |
| `error` | `known-failure` only | Ordinal, case-sensitive substring the actual error text must contain; never the full text, never a run-specific part (program GUIDs, line positions of `program:` locators, timings) |
| `timeoutSeconds` | optional | 1–600; default 120 |
| `preamble` | optional | D4 run on the script's process before it (legacy `ExecuteSecurityLibrary` ran `SetUseImplicitTransactions(false);`, because the script runs statements on a second process and would block on its own transaction) |
| `register` | optional | Library names registered in the script's server before it; each must be in the coverage library set |
| `note` | optional | Free text for the next reader (for example "no assertions") |

`unstable` exists for a script whose result was observed to vary between identical runs: it is run, never fails the run, and is reported with what it did this time. Use it only with evidence from the three-run check below.

`CoverageManifest.cs` parses with `System.Text.Json` (`UnmappedMemberHandling = Disallow`) and then validates: duplicate scripts, entries out of order, unknown status, a missing or forbidden field, an empty `error`, a `timeoutSeconds` out of range, a `register` name outside the library set, a `ticket` that is not a lower-case hyphenated slug. All problems are collected and reported together. The format is described in the XML doc comment of the manifest class and in one paragraph of AGENTS.md.

### Error matching and outcomes (choice 2)

The **error text** of a case is the exception and each `InnerException` below it as `<TypeName>: <Message>`, joined with ` <= `, carriage returns and line feeds replaced by spaces (the shape of the spike's `Flat`, without its truncation), plus the harness's own `HarnessTimeout`/`HarnessRegister`/`HarnessStop` texts. Matching is a substring test rather than D4 error codes because not every failure carries one (a script's `raise Error('…')`, a timeout, a .NET exception), and a substring can name the type when it helps (`CompilerException: Unable to resolve…`). The engine's messages come from neutral resources only; confirm there are no satellite resource folders in `artifacts/bin` for the engine and server and put a `NOTE:` at the matcher (if localized resources ever ship, matching must pin the UI culture or move to codes).

| Manifest | Run | NUnit outcome |
|---|---|---|
| `pass` | succeeds | Passed |
| `pass` | fails | **Failed**, with the error text |
| `known-failure` | fails, text contains `error` | Warning (`Assert.Warn`): `known-failure (<ticket>): <error text>` |
| `known-failure` | fails, other text | **Failed**: expected substring and actual text |
| `known-failure` | succeeds | **Failed**: "now passes; change its manifest entry to pass" (so a fix is never unnoticed) |
| `unstable` | either | Warning: `unstable (<ticket>): passed` or `…: failed: <error text>` |

`NUnit3TestAdapter` reports NUnit's Warning to VSTest as Skipped by default, so in the `dotnet test` summary "Skipped" counts the known and unstable cases. There are no other skips in the suite (no `[Ignore]`, no `Assume`). State this in AGENTS.md.

**Summary.** `[OneTimeTearDown]` writes one block with `TestContext.Progress`: total cases; `pass` cases passed / failed; `known-failure` matched / mismatched / unexpectedly passing, with counts per `ticket`; `unstable` per ticket; discovery problems. Check that it is visible in plain `dotnet test Dataphor.slnx` output. If it is not shown at the default verbosity, document the command with `--logger "console;verbosity=normal"` in AGENTS.md instead of looking for another channel.

### Discovery (choice 3)

`CoverageScripts` (`[TestFixture]`), one method with `[TestCaseSource(nameof(Cases))]`, test name = script name (`TestCaseData.SetName`; names with dots such as `Transaction.Atomicity.Run` are fine for `--filter Name=…`). `Cases` reads the embedded manifest and lists `*.d4` (top level only) in `<layout>\Libraries\TestFramework.Coverage.Scripts\Documents`, the layout path coming from `TestEnvironment` (the `DataphorLayoutDir` assembly metadata). It starts no server: NUnit evaluates it at discovery and again at execution. It yields, in ordinal order of the union of names:

- a case per script that has both a file and an entry, run as above;
- a **failing** case named after the script for a file with no entry ("not in the manifest") and for an entry with no file ("script file missing");
- instead of all of the above, a single failing case `Harness.ManifestInvalid` listing every manifest problem, or `Harness.LayoutMissing` when the folder is missing or holds no `.d4` file. A run never yields zero cases.

- **Snapshot with assemblies.** `Frontend` (with `Alphora.Dataphor.Frontend.Server.dll`) is registered in the template, so the 63 passes cover a library with an assembly restored from a copy. Also check once, by hand, that a library registered in the template with its own assembly still works in a copy after the template folder's assembly is the loaded one: register `System.Internet` in the template temporarily and run `Internet` without its `register` option; report the result and revert.
- **Three full runs.** Run the suite three times; a script whose outcome differs between runs gets `unstable` with the slug that owns the nondeterminism (`test-triage-known-failures` unless another fits), and the handoff names it. `port-engine-runtime-fixes` expects `Transaction.Isolation.Run` may depend on timing.
- **Hangs.** `DebugTest` must stop within its 5 s plus the abort wait, and the next case must be unaffected. Verify from the timings in the output.
- **SQL Server on the developer's machine.** Until `test-decouple-coverage-base` lands, registering `TestFramework.Coverage.Base` makes `TestFramework` create a SQL Server device for database `DataphorTests` on `localhost` with integrated security (K14). On a machine where that connects, the template registers it, the 25 scripts above pass, the run fails on "now passes", and a local SQL Server was touched. Put a `NOTE:` at the template registration naming `test-decouple-coverage-base`; run this ticket on a machine without a default local SQL Server instance (say which in the handoff).
- **Template registration time.** About 25 s today, once per run, waiting for that SQL Server; a single-script run (`dotnet test tests/DAE.Server.Tests --filter Name=Lexer`) pays it too. Document the single-script command in AGENTS.md.
- **Discovery failure paths.** The three hand checks of the Done-when list: remove a manifest entry; add a script file to `tests/libraries/TestFramework.Coverage.Scripts/Documents/` (the build copies it into the layout) with no entry; and change a passing script's entry to `known-failure`. Each must make the run fail with a clear case. Revert each; no permanent test for them.
- **Stack overflow** in a script kills the test host; VSTest reports the crash and the run fails. Visible, not silent; the 16 MB stack makes it unlikely.
- **Isolation, elevated.** Run once in an elevated shell: before and after, check that the event-log source `Dataphor` does not exist (`[System.Diagnostics.EventLog]::SourceExists("Dataphor")` returns false, or it existed before and gained no entries), `%ProgramData%\Alphora` did not appear or change, `artifacts/layout` has no new or changed files, and nothing listened (`Get-NetTCPConnection -State Listen -OwningProcess <testhost pid>` during the run, or by inspection: no code path opens a listener). Report each. Leftover folders under `%TEMP%\Dataphor.Tests` after the run are expected (finding 5) and are swept by the next run; report how many and confirm the next run removes them.
- **Globalization.** Quote `System.Globalization.UseNls` from `DAE.Server.Tests.runtimeconfig.json` (Debug and Release).
- **Public logs.** CI logs are public; the harness prints only paths under the run's temp folder and the layout, and no connection string other than the SQLite one.
- **Parallelism.** None. Cases run one at a time; `TestServerInstance` already carries the `NOTE:` about static engine state.
