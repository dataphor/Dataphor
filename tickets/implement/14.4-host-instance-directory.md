## What this is

Two changes at one code site — the computation of the folder that holds the machine's list of server instances.

**1. The folder gets the major version in it (known defect K27).** `InstanceManager.GetInstanceDirectory` builds the folder from `PathUtility.CommonAppDataPath(String.Empty, VersionModifier.None)`, which produces `%ProgramData%\Alphora\Dataphor\Instances` with no version in it, and `Server.InstanceDirectory` (`src/engine/Server/Server/Server.cs`, about line 728) repeats the same expression to default an instance's own data folder. A 4.0 server installed beside a 3.1 server therefore reads 3.1's instance list, writes to it, and defaults its catalog and per-instance data into 3.1's folders. Both call sites move to `VersionModifier.MajorSpecific`, giving `%ProgramData%\Alphora\Dataphor\4\Instances` — which is where the client has always kept its own machine-wide list of aliases (`src/client/DAE.Client/AliasManager.cs`, `Aliases.config`, `MajorSpecific`).

**2. A server can be pointed at a different folder.** Today the folder is computed and there is no way to override it, so nothing can start a server without touching machine state: `DataphorServiceHost.Start()` loads the machine list and, when the named instance is not in it, *adds a default entry and saves the file*. That is why no test starts the built executables out of process, and why an operator diagnosing a deployment has nowhere else to put a configuration to try. An override settable in process, and an environment variable that sets it from outside, fix both.

### Why this is not a decision for the owner

The plan ticket this one comes from proposed routing the version change to `blocked/` as a change to the on-disk instance layout. It was re-read against the specification, which answers it:

- Open question Q9 (`docs/modernization-plan.md`, answered, "Still open: none") — *"Catalogs are rebuilt from scripts, not migrated; install side by side."*
- WS9's target — *"A 3.x installation is left alone and can remain installed side by side; the new instance starts with an empty catalog that the application's rebuild scripts populate"*, and *"Instance data under `%ProgramData%\Alphora\Dataphor` is never removed on upgrade or uninstall."*
- Known defect K27 names this exact site (`GetInstanceDirectory` passes `VersionModifier.None`) as the defect, and the WS5 work-item table assigns it to this work item.

So the specification requires side-by-side installation, records the shared folder as the defect that prevents it, and names this work item as its owner. That is the explicit authorization the project's compatibility rule asks for, and the owner has already answered the upgrade question the change turns on. Nothing is silent and nothing is contradictory, so there is nothing to put in front of a human.

**What it costs, stated plainly because it is real:** an operator upgrading from 3.1 does not see their existing instances. A 4.0 server started with no instance registered creates a default one, and port numbers, library directories and device settings have to be re-entered by hand or by the installer. This is the already-decided upgrade story: the catalog lives under the instance folder, and an inherited instance list would point a 4.0 server at a 3.1 catalog it cannot open. 3.1's files are left where they are. This goes in `docs/migration-notes.md`, and the WS9 installer work has to create and populate the versioned folder.

**Rejected alternatives,** recorded so they are not re-litigated: copying 3.1's file forward on first start (keeps the operator's settings, but adds a migration step that can half-succeed and silently adopts settings 4.0 no longer honours); keeping the shared folder and refusing a file an older version wrote (smallest change, but makes side-by-side installation impossible, which contradicts Q9); doing nothing (the defect). Reversibility is high — two call sites — except that an instance registered at the new folder has to be registered again if it is reverted.

## The override: shape and why

`InstanceManager` gains a settable path and an environment variable that supplies its default:

```csharp
/// <summary>The environment variable that redirects the instance directory for a process that sets it.</summary>
public const string InstanceDirectoryVariableName = "DATAPHOR_INSTANCE_DIRECTORY";

/// <summary>
/// The folder holding this machine's instance list (ServerConfigurations.config) and, by default, each instance's
/// own data folder.
/// </summary>
/// <remarks>
/// Not to be confused with ServerConfiguration.InstanceDirectory, which is one instance's own data folder and is
/// defaulted to a sub-folder of this one. Resolved, in order: a value set here; the environment variable
/// DATAPHOR_INSTANCE_DIRECTORY; %ProgramData%\Alphora\Dataphor\&lt;major version&gt;\Instances. Reading it does not
/// create the folder; GetInstanceDirectory does. Setting it discards the loaded list, so Load must be called again.
/// </remarks>
public static string InstanceDirectory { get; set; }
```

`GetInstanceDirectory()` keeps its signature and meaning — resolve, create, return — so every caller (`LoadMachineInstanceConfiguration`, `SaveMachineInstanceConfiguration`) is unchanged. `Server.InstanceDirectory`'s default calls `InstanceManager.GetInstanceDirectory()` instead of repeating the path expression, so the per-instance folder follows the override and the path is computed in one place rather than two.

**An environment variable rather than a host command-line switch.** Every process that reads the instance list has to agree on where it is: the host, the configuration utility, Dataphoria, and the client when an alias asks for an in-process server (`src/client/DAE.Client/ServerConnection.cs` calls `InstanceManager.GetInstance`). A switch would redirect only the host, leaving a client in the same test unable to see the list the host just wrote. A switch would also mean a new case in `HostCommandLine.GetCommand`, which rejects an unrecognized first argument — that parser is the compatibility surface a 3.1 script and an existing service registration rely on, and it is not worth widening for this. The variable also costs a test nothing: `ProcessStartInfo.Environment` sets it on the child it starts.

**Resolving a relative or unusable value.** The resolved path is passed through `Path.GetFullPath`, so a relative value means relative to the process's current directory; an unusable value surfaces from `Directory.CreateDirectory` with the path in the message, which is the diagnosis an operator needs.

**The override is the whole folder,** not a root under which `Alphora\Dataphor\<major>\Instances` is appended. A test or an operator names a folder and that is the folder.

### A non-creating path, in `PathUtility`

`PathUtility.BuildAppPath` calls `Directory.CreateDirectory` before returning, so resolving the default path today creates it. `InstanceManager.InstanceDirectory`'s getter must not have that side effect, or reading it from a test writes to `%ProgramData%`. Add an overload:

```csharp
public static string CommonAppDataPath(string applicationName, VersionModifier versionModifier, bool ensureExists)
```

with the private `BuildAppPath` taking the same flag and the existing two-argument overload passing `true`. No existing behaviour changes; there is no ambiguity with `CommonAppDataPath(string, bool)` because the arity differs, and the one new call site passes `ensureExists: false` by name so it reads. This is a public addition to `Alphora.Dataphor` (`Base.Windows`), so it gets a migration-notes entry.

## `DataphorHost.BuildHost` keeps its factory parameter

`host-generic-host`'s review says this work item "retires it". It does not, and the reason was checked rather than assumed. `BuildHost(string instanceName, Func<DataphorServiceHost> startServer)` exists so that `tests/DAE.Server.Tests/HostProgramTest.cs` can hand in a server of its own. The override removes one of the three things the factory carries (that `DataphorServiceHost.Start()` writes the machine list) and leaves two that it cannot:

- `DataphorServiceHost.HostName` and `LoggingEnabled` are properties of the host object, not settings in the instance list. The fixture sets `HostName` to `127.0.0.1` so that no case opens a port another machine can reach, and `LoggingEnabled` to false so that an elevated run does not create the Windows event-log source. Neither can be expressed in a `ServerConfiguration`, so neither survives a plain `BuildHost(instanceName)`.
- `AServerThatFailsToStartFailsTheHost` needs a start that throws. Without the factory it would have to make a real server fail, which is slower and more fragile than a thrown exception.

So the parameter stays, and the plan paragraph that gives the machine-wide list as its reason is corrected rather than the code. Record the decision at the site as an accepted tradeoff, next to the existing explanation of the parameter — one `NOTE:` saying the redirection exists and still does not replace the factory, and why, so the next reader does not re-open it.

## Edge cases & interactions

- **Setting the override after the list is loaded.** `InstanceManager` caches the list in a static. The setter discards it (`_instances = null`), so the next `Instances` access throws `InstanceConfigurationNotLoaded` rather than silently serving the list from the old folder, and `GetInstance` reloads as it already does for an unloaded list. *Verified by:* the save-and-load test below exercises set-then-`Load`; the throw is the existing `CheckLoaded` behaviour and needs no new case.
- **The variable is read per resolution, not cached.** Changing it mid-process changes where the next resolution looks; the loaded list is not reloaded by itself. *Verified by:* the precedence test, and stated in the remarks.
- **An explicit value beats the variable.** A process that sets the property is not overridden by whatever the environment happens to carry. *Verified by:* the precedence test.
- **Tests share one static.** `InstanceManager` is static, so a fixture that sets the override must restore it in teardown and must not be `[Parallelizable]`, like `HostProgramTest` and `TestServerInstance`. *Verified by:* inspection of the new fixture.
- **The listener reports whatever list its own process resolved.** `ListenerService.LoadConfiguration` serves `InstanceManager.LoadConfiguration()`, and the listener is one per machine on port 8060. A host running with a redirected folder, if it is the one holding the listener, advertises its private instances. That is what a test wants and is the existing one-listener-per-machine design, not a new property. *Verified by:* inspection; `CoreWcfProtocolTest` already records that the listener reads the machine-wide file.
- **A service's environment is not a new way in for an unprivileged user.** A Windows service receives the machine environment, which requires administrative rights to change, and the service's own configuration already requires those rights. *Verified by:* inspection; no code acts on it.
- **Clients and the configuration utility need no source change.** `ConfigurationUtility/MainForm.cs`, `Dataphoria.cs`, `EditAliasForm.cs` and `ServerConnection.cs` all go through `InstanceManager`, so they follow the new folder and the override without being touched. Two of those projects are unconverted and build only through the spike; do not go editing them. *Verified by:* inspection of the call sites listed above.
- **A `ServerConfigurations.config` an older release wrote still loads if it is put in the new folder.** An attribute the current `ServerConfiguration` does not declare is recorded as a deserialization error that `InstanceConfiguration.Load` never consults, and every other setting on the instance is still read; `LoadReadsAFileCarryingSettingsThatNoLongerExist` in `tests/DAE.Server.Tests/InstanceConfigurationTest.cs` pins it. Nothing here changes that and no new case is needed. *Verified by:* that existing test.
- **The two folders can coexist.** The client's `Aliases.config` already sits at `%ProgramData%\Alphora\Dataphor\4\`, and `Instances` becomes a sub-folder beside it — a directory next to a file, no collision. *Verified by:* inspection of `AliasManager.GetMachineAliasConfigurationFileName`.

## Tests

Three cases, in a new `tests/DAE.Server.Tests/InstanceManagerTest.cs`. `InstanceConfigurationTest` is about what BOP does with the file and is left alone.

- **`TheDefaultInstanceDirectoryIsVersioned`** — with no override and no environment variable, the resolved path is under a folder named for the assembly's major version and is not the unversioned 3.1 path. This is K27's characterization: a return to `VersionModifier.None` fails here. It must not create anything, which is what the `ensureExists: false` resolution is for.
- **`AnExplicitInstanceDirectoryBeatsTheEnvironmentVariable`** — the variable alone redirects the resolved path; an explicit value set on the property wins over it. One case, because precedence is one behaviour.
- **`ASavedInstanceListIsReadBackFromTheOverriddenDirectory`** — point the override at a folder from `TestEnvironment.NewDirectory`, `Load`, add an instance, `Save`, assert `ServerConfigurations.config` is in that folder, then `Load` again and assert the instance comes back. This is the behaviour `test-client-server` and anyone diagnosing a deployment depends on, and it is the only case that proves the redirection reaches the file rather than only the string.

Restore the property and the variable in `[TearDown]`, and no `[Parallelizable]`.
