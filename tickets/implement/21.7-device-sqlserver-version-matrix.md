## What this is

Decision Q12 is answered and is not open here: support the SQL Server versions of roughly the last five years - **SQL Server 2022 and later are the supported minimum and are tested; SQL Server 2019 is documented as working if it needs no extra code** - and because the production version is unknown, the device keeps 3.1's connection defaults so an older server still connects where the driver allows. What is missing is the evidence: nobody has run the product against any of those versions on .NET 10.

So this ticket is a measurement and a document, not a feature. `test-device-live` (prerequisite) gives it everything it needs to run: one environment variable naming a server, the device-coverage script running against it, the three transaction-atomicity scripts, and the catalog store contract's fourteen cases. This ticket points all of that at one SQL Server version after another and writes down what happened.

### Which versions, and how to get them

- **SQL Server 2022** - the supported minimum. Must pass.
- **SQL Server 2025**, if a release exists by the time this runs - the newest. Must pass, or the failure is a defect.
- **SQL Server 2019** - documented as working if it needs no extra code. Run it; if something needs code, the answer in the document is "not supported" rather than a patch, unless the code is small and obviously right.
- **Whatever this machine has** - SQL Server 2016 LocalDB is installed (`sqllocaldb info` shows `MSSQLLocalDB`), and `store-mssql-port` already proved the catalog store against it. It is below the supported minimum, so a failure on 2016 is information rather than a defect; record it as such. It is also the cheapest first run, so use it to shake out the harness before reaching for containers.

Docker is installed on this machine (`docker --version` reports 24.0.6) and Microsoft publishes `mcr.microsoft.com/mssql/server` images for 2019 and 2022, which is the practical way to get the other versions: a container with a password, a published port, and `DATAPHOR_TEST_MSSQL` pointing at it. **If the Docker daemon is not running or the image cannot be pulled, do not fake the result** - run what you can, record exactly which versions were and were not reached, and say so in the document and the handoff. A matrix with an honest hole is worth something; an undocumented guess is worth less than nothing.

### What to record

For each version actually run: the version string the server reports, the database collation, which of the four script passes and the fourteen store-contract cases passed, and the text of every failure. For the connection settings, the thing a deployment needs to know is narrow and specific: with the driver now encrypting by default and the device defaulting that off (`device-mssql-port`), which combinations of server version, certificate state and device settings connect and which do not. That is a small table and it is the part of this ticket a deployment will actually read.

`docs/users-guide/dataphor-service.md` is where a deployment reads about the service and its stores and already carries the SQL Server store's requirements; the version table belongs there or on a page it links to. `docs/architecture/devices.md` gets at most a sentence pointing at it.

## Edge cases & interactions

- **A failure on a supported version is a defect, and this ticket does not have to fix it.** Triage each: fix it here only when the fix is local and obvious (the project rules' "bugs met along the way"); otherwise file a `fix/` ticket naming the version, the script and the statement, and record the failure in the matrix with the slug beside it. A matrix row that says "fails, see `bug-...`" is a complete row.
- **The device creates a database if one is absent** (`ShouldEnsureDatabase`), and on a container that is the normal path. On a shared or customer-like server it is not something to do by accident. Keep every run against a server the variable explicitly names, and leave the databases the runs create named after the pass.
- **Collation decides what a `varchar` column loses.** `device-mssql-string-parameters` measured non-ASCII loss against a Latin-1 code page. A container's default collation is not necessarily the one a customer runs, so record the collation with every row; a pass on one collation is not a pass on all of them. If a run is on a different collation and the non-ASCII case behaves differently, that is a finding worth its own line.
- **`datetime` versus `datetime2`, `date` and `time`.** `MSSQLTypes.cs` maps D4's `DateTime`, `Date` and `Time` all onto the server's `datetime`, with `TODO` comments from 2008 about the newer types, and `MSSQLDevice.IsValidDomainName` accepts `date` and `time` columns with a comment marking them as 2008-and-later. Every version in this matrix has all of them, so a reconciliation against a schema using `date`, `time` or `datetime2` is reachable on all of them - include a case and record what happens. Do not implement the missing `datetime2` mapping here; if it is broken, that is a ticket.
- **`IsMSSQL70` still exists** and changes what the device emits. Nothing in the matrix is SQL Server 7.0, so the flag should be false everywhere; confirm it is, and record whether `DetermineVersion` reads the version correctly through the new client on each server - that call is the first thing the device does and the first thing that can fail against an unexpected version string.
- **The server-side cursor path is the least-exercised code in the device** (`sp_cursoropen`, `sp_cursorfetch` in `MSSQLCommand.cs`), and the system stored procedures it uses are undocumented. If any version's run fails there, say so prominently: it would be the strongest argument for the client-side cursor path, which the device chooses by whether the statement starts with `select`.
- **No new test, in the usual case.** The scripts and fixtures exist; this ticket runs them against more servers and writes down the result. Add a case only where a version difference is itself the behaviour worth pinning, and prefer a row in the matrix to a test that can only run where that version is installed. Say in the handoff what you added and what you deliberately did not.
- **CI runs one version at most.** Whatever `test-device-live` arranged in `.github/workflows/build.yml` stays as it is; this ticket does not add a matrix to CI. If the version CI supplies turns out to be below the supported minimum, say so in `AGENTS.md` beside the variable, so a green CI is not read as proof against 2022.
- **Nothing here may change the device's defaults.** Q12's answer fixes them. If a version needs a different default to connect, that is a documented setting for a deployment to add, not a change to what the device does by default; a proposal to change the default would be a `blocked/` ticket, not an edit.
