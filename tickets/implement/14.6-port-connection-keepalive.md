## Why this exists

The server reclaims a client's work by watching one clock per *connection*. `RemoteServerConnection` carries a `LastActivityTime` (`src/engine/Server/Server/RemoteServerConnection.cs`, about line 136) and a server-side watcher relinquishes any connection whose clock is older than five minutes. Nothing in the server moves that clock except `Ping()`, which only the client calls. So the clock is a *last ping* time, not a last activity time, and the client's pinging is the whole liveness signal.

On the client the ping is started by `LocalSession` — one keep-alive thread per **session**, pinging every 120 seconds (`src/protocol/Client/Server/LocalSession.cs`, `StartKeepAlive`/`KeepAlive`, `LocalKeepAliveInterval`). But the thing the server measures is the **connection**, which `LocalServer` establishes in its own constructor, before any session exists (`src/protocol/Client/Server/LocalServer.cs`, about line 53). The two do not line up, and three things follow:

- **A connection with no open session is not pinged at all.** That is the window between constructing a `LocalServer` and opening the first session, and the window after the last session is disconnected while the `LocalServer` is kept. `ServerConnection` in `src/client/DAE.Client` builds the `LocalServer` once and hands sessions out of it, so a program that closes its last `DataSession` and opens another more than five minutes later finds its connection handle gone, and the next call fails with the server's unknown-object-handle error. This is 3.1's behaviour too, so it is not a port regression, but it is wrong whenever that path runs and the fix is local.
- **Each session runs a thread pinging the same connection.** Ten sessions on one connection means ten threads doing identical work every two minutes.
- **The keep-alive thread is a foreground thread** (`new Thread(new ThreadStart(KeepAlive)).Start()`, with no `IsBackground`). A `LocalSession` that is never disposed therefore keeps the client process alive after its `Main` returns. The server-side watcher thread was made a background thread for exactly this reason (see the `NOTE:` in `src/engine/Server/Service/ConnectionManager.cs`); the client half never was.

One sentence fixes all three: the keep-alive belongs to the object that owns the connection.

## What to build

**The ping moves from `LocalSession` to `LocalServer`.** One keep-alive per connection, started once the connection is established in the `LocalServer` constructor and stopped in `LocalServer.Dispose` before the connection is relinquished, on a **background** thread. `LocalSession` loses `StartKeepAlive`, `KeepAlive`, `StopKeepAlive`, `_keepAliveSignal`, `_keepAliveReferenceLock` and the `LocalKeepAliveInterval` constant, and its constructor and `Dispose` lose the two calls. Move the strategy comment with the code and correct it: the interval it describes is the client's, the five minutes it alludes to is the server's, and the two are related only by the server's threshold having to exceed the client's interval.

`LocalServer` is reference-counted and shared (`AddReference`/`RemoveReference`, used by `ServerFactory`), which is the right granularity: one shared `LocalServer` is one connection and gets one keep-alive.

**The interval stays 120 seconds** and keeps its name, as `LocalServer.DefaultKeepAliveInterval`. `LocalSession.LocalKeepAliveInterval` is a public constant on a public class, so moving it is a visible change and needs a `docs/migration-notes.md` entry — the same entry can carry the behaviour change, since both matter to the same reader.

**One new public constructor overload** `LocalServer(IRemoteServer server, bool clientSideLoggingEnabled, string hostName, int keepAliveIntervalSeconds)`, with the existing three-argument constructor delegating to it with the default. This is what lets a test watch the ping without waiting two minutes; it is additive, and it is also what a host embedding the client would want. Refuse an interval below one second with an argument exception rather than spinning.

**`LocalServer.Dispose` must tolerate a connection the server has already reclaimed.** It calls `_server.Relinquish(_serverConnection)` unguarded (about line 80). Against a server that has already relinquished the connection — which is precisely what this whole mechanism does — the service's handle lookup raises an unknown-object-handle error and `Dispose` throws, so a client that was idle too long fails on disconnect as well as on use. Catch and ignore around that one call, following the precedent already in `LocalSession.StopProcess`, and say in a comment why releasing something already released is benign here. Do not widen the catch to the rest of `Dispose`.

## The test this owes

One new fixture, `tests/DAE.Server.Tests/ConnectionKeepAliveTest.cs`, at the lowest layer that shows the behaviour — a `LocalServer` over an in-process `RemoteServer`, no WCF host and no network:

- `TheConnectionIsPingedWithNoSessionOpen` — start a `TestServerInstance`, wrap its `Server` in a `RemoteServer`, construct a `LocalServer` over it with a one-second keep-alive interval and **never open a session**. Read the server's own clock through `((RemoteServerConnection)localServer.ServerConnection).LastActivityTime` (both the class and the property are public, so the test needs no access to internals), and assert it advances past the value captured at construction within a bounded wait of a few seconds. Then open a session, dispose it, and assert the clock still advances afterwards. On the current code the first assertion fails: nothing pings a sessionless connection.
- `DisposingAfterTheServerHasReclaimedTheConnectionDoesNotThrow` — establish a `LocalServer` as above, relinquish its connection behind its back (`remoteServer.Relinquish(localServer.ServerConnection)`), then dispose the `LocalServer` and assert it completes. No timing involved. On the current code this throws.

Nothing else is owed. The move itself is not separately tested: there is no third behaviour in it, and a test that counted threads would be testing the implementation.

**Watch the process-wide object-id counter.** `LocalServer`'s constructor starts an internal `Engine` of its own for the client-side catalog cache, and starting an engine resets the process-wide next-object-id counter (`bug-object-id-counter-is-process-wide`), which would leave the fixture's own server handing out identifiers it has already used. `CoreWcfProtocolTest.cs` has the three-line save-and-restore for this as `WithTheObjectIDCounterRestored` (about line 753); reuse the pattern, and if it is cleaner to move the helper to `TestEnvironment` so both fixtures call one copy, do that and say so. Follow `CoreWcfProtocolTest`'s lead in not marking the fixture parallelizable.

## Edge cases and interactions

| Case | How it is covered |
|---|---|
| Connection established, no session ever opened, held longer than the server's threshold | The first test above |
| Last session disconnected, connection kept | Second half of the first test |
| Many sessions on one connection | By inspection: one keep-alive on the `LocalServer`, started once, so the count cannot depend on sessions |
| A ping that fails (the channel is gone, the server has reclaimed the connection) | By inspection: the loop's single surrounding `catch` ends the thread, which is the existing behaviour and the right one — a client whose pings cannot land has nothing to keep alive. Keep it, and keep swallowing rather than logging: `LocalServer` has no log of its own on this path |
| `LocalServer.Dispose` racing its own keep-alive thread | Stop the keep-alive **before** relinquishing, so the thread cannot ping a connection that is being released; the signal-then-null pattern already in `LocalSession` is sound and moves as it is |
| A leaked `LocalServer` holding the client process open | The thread becomes a background thread; by inspection |
| Reference-counted sharing (`ServerFactory`) | By inspection: the keep-alive starts in the constructor and stops in `Dispose`, which `RemoveReference` already drives at the last release |
| `LocalServer` built against something other than the product's server (the client's own `ClientServer`, or a `RemoteServer` directly as the test does) | Both reach `IRemoteServerConnection.Ping`, which is on the contract; no path is special-cased |
