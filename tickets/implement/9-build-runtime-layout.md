# Runtime layout under artifacts/layout

## Goal

`dotnet build Dataphor.slnx` (Debug or Release) produces, besides the per-project outputs in `artifacts/bin/`:

```
artifacts/layout/<debug|release>/
  bin/                     core and server assemblies + their package runtime files (SDK copy-local shape)
  Libraries/<Name>/        <Name>.d4l, Documents/, Upgrades/, other tracked library files,
                           the library's assembly (+ .pdb) and that assembly's private package dependencies
```

`Libraries/` recombines the three source trees (`libraries/`, `samples/`, `tests/libraries/`) into one directory, as the server expects (it treats each immediate subfolder holding `<Name>.d4l` as a library). Nothing is written into source folders. `test-harness-inprocess` copies libraries from here into its temporary directories; `installer-publish-profiles` builds the install image from here later. This ticket also converts the last live K15 project (`TestFramework.Coverage.Base`) to SDK style.

The configuration folder is lower case (`debug`, `release`) to match the SDK's `artifacts/bin/<project>/<debug|release>/` pivots. Every consumer finds the folder through one MSBuild property, `DataphorLayoutDir`, never by spelling the path.

## Facts established while planning (verified, not assumed)

- **`Assembly.LoadFrom` on a second copy of an assembly the host already lists returns the host's assembly.** A throwaway `net10.0` console app that referenced Newtonsoft.Json 13.0.4 and called `Assembly.LoadFrom` on an identical copy in another folder got the already-loaded assembly back (`ReferenceEquals` true, `Location` = the app's own copy). The same happened for an assembly in the app's dependency list that had not been loaded yet. So System.Internet's `.d4l` listing `Newtonsoft.Json.dll`, with that file in its library folder while the server also has it in `bin/`, registers without a conflict. Central package management keeps the two copies at the same version.
- **An assembly loaded with `LoadFrom` finds its unlisted dependencies in its own folder.** A throwaway library using `OleDbConnection`, loaded with `LoadFrom` by a host that does not reference `System.Data.OleDb`, created the connection object when the folder held the package's **Windows** runtime files (`runtimes/win/lib/net10.0/System.Data.OleDb.dll` and `…/System.Diagnostics.PerformanceCounter.dll`, plus `System.Configuration.ConfigurationManager.dll` and `System.Security.Cryptography.ProtectedData.dll`). With the generic `lib/net10.0/` files instead, it threw `PlatformNotSupportedException` ("System.Data.OleDb is not supported on this platform"). The same failure happened when only PerformanceCounter was the generic file. Consequence: **the test host does not need to reference Connection's dependencies**, but a library folder must hold the Windows runtime asset wherever a package ships one. A flat library folder has no `.deps.json` to choose for it, so the layout has to choose.
- **What `ResolvePackageAssets` gives each project** (checked on `DAE.Connection.csproj` with `dotnet msbuild -t:ResolvePackageAssets -getItem:…`): `RuntimeCopyLocalItems` (generic `lib/` files, no `RuntimeIdentifier`), `RuntimeTargetsCopyLocalItems` (`runtimes/<rid>/…`, with `RuntimeIdentifier` `win`, `win-x64`, `unix`, …), `NativeCopyLocalItems`, all with `NuGetPackageId`, `AssetType` (`runtime` | `native`) and `DestinationSubPath` metadata. They are populated for class libraries even though class libraries do not copy packages to their own output (`artifacts/bin/DAE.Connection/debug/` has no package DLLs). The closure includes packages that arrive through project references.
- **Private packages per library, computed from the deps files** as "packages in the library's closure minus packages in the closures of the projects it references": Connection → `System.Data.OleDb`, `System.Configuration.ConfigurationManager`, `System.Diagnostics.PerformanceCounter`, `System.Security.Cryptography.ProtectedData`; System.Internet → `Newtonsoft.Json` (the package it references directly; `Base` and `DAE` do not have it); MSSQLDevice → none (it gets OleDb through Connection, whose folder already has it); SQLDevice, SimpleDevice, Frontend, System.Platform, System.Integration, TestFramework.Coverage.Base → none. No library has a private **native** asset today. The SQL Server `sni.dll` native files belong to `System.Data.SqlClient`, which the server already has, so they go to `bin/`.
- **`TestFramework.Coverage.Base` does not use WinForms.** Its only WinForms use, `Application.StartupPath` in `TestNodes.cs:751`, is inside the `/* … */` block on lines 633–766 and is not compiled. The `System.Windows.Forms` reference is dead, so the converted project targets plain `net10.0` with no source change.
- No library in the layout requires one of the libraries left out (checked every `.d4l`'s `libraries.libraryreference`): only `Sample.Shipping`, `ODBCConnection`, `PGSQLConnection` and `PGSQLDevice` mention Shipping, ODBC or PGSQL.
- Tracked non-source files in library folders besides `.d4`/`.dfd`/`.dfdx`: `.d4l.info` (2), `.dnt` (4), images (`.png`, `.jpg`, `.ico`), `.txt`, one `.chm`. All are copied.

## Design (settled)

### Mechanism: one writer, items supplied by each project

- **`Directory.Build.targets` (new, repository root)** defines, for every SDK project:
  - the property `DataphorLayoutDir` = `$(ArtifactsPath)\layout\$(Configuration.ToLowerInvariant())\`. It is in `.targets`, not `.props`, so `Configuration` is final. Item definitions in a project body still see it, because MSBuild evaluates all properties before any items. `test-harness-inprocess` uses it, for example in an `AssemblyMetadata` item.
  - a target `GetDataphorLayoutItems` that **returns items and copies nothing**. It depends on `ResolvePackageAssets` and the reference-resolution targets, and returns:
    - the project's own output: its assembly (`$(TargetPath)`), its `.pdb` when one exists, and any satellite assemblies at their culture subfolder. Never its `.deps.json`. Use the standard output groups (`BuiltProjectOutputGroup`, `DebugSymbolsProjectOutputGroup`, `SatelliteDllsProjectOutputGroup`) or equivalent, tagged `DataphorLayoutKind=Output`;
    - its package runtime files (`RuntimeCopyLocalItems`, `RuntimeTargetsCopyLocalItems`, `NativeCopyLocalItems`, `ResourceCopyLocalItems`), tagged `DataphorLayoutKind=Package`, keeping `NuGetPackageId`, `AssetType`, `RuntimeIdentifier` and `DestinationSubPath`. Each also gets `DataphorPrivate=true` when its `NuGetPackageId` is **not** among the package ids of the projects this project references. Get those ids by calling a small companion target (for example `GetDataphorPackageIds`) on `@(_MSBuildProjectReferenceExistent)` with the same global-property handling that `GetCopyToOutputDirectoryItems` uses in `Microsoft.Common.CurrentVersion.targets` (`%(SetConfiguration)`, `%(SetPlatform)`, `%(SetTargetFramework)`, `%(GlobalPropertiesToRemove)`). Matching that handling is what keeps a referenced project from being evaluated a second time with different global properties.
    - for a project whose directory is named `Source` and whose parent folder `<F>` contains `<F>.d4l`: metadata `DataphorLibrary=<F>`. A project the layout treats as a library that does not fit this shape is a build error.
- **`tools/layout/Layout.csproj` (new, in `Dataphor.slnx` under a `/tools/` solution folder)** is the only project that writes into `$(DataphorLayoutDir)`. It is a plain `Microsoft.NET.Sdk` class library with no `Compile` items; its own empty `Layout.dll` in `artifacts/bin/Layout/` is ignored. (Rejected: `Microsoft.Build.NoTargets`, an extra MSBuild SDK to pin in `global.json` that would only save that empty DLL. Also rejected: a per-project copy target, option (a) in the planning ticket, because several projects would then write the same files into `bin/` concurrently in a parallel build.) It has:
  - `ProjectReference` items with `ReferenceOutputAssembly=false` and `Private=false`, in two groups distinguished by metadata (for example `DataphorLayoutRole=Bin` or `Library`):
    - **Bin:** `Base`, `Base.Windows`, `DAE`, `Server`, `Store.SQLite` (`DAE.SQLite.csproj`), `Common`, `NativeCLI` (`DAE.NativeCLI.csproj`), `Client`. That is every converted project that is not a library.
    - **Library:** `DAE.Connection`, `DAE.Device.SQL`, `DAEDeviceMSSQL`, `DAE.Device.Simple`, `Frontend.Server`, `System.Platform`, `System.Internet`, `System.Integration`, `DAE.Diagnostics` (TestFramework.Coverage.Base).
  - a **D4 library folder item list** made by globbing `libraries\*\*.d4l`, `samples\*\*.d4l`, `tests\libraries\*\*.d4l` (item = the folder), with an explicit `Exclude` for the four libraries whose C# project is not converted. Each exclusion gets an XML comment naming its owner: `PGSQLConnection` and `PGSQLDevice` (`device-pgsql-port`), `ODBCConnection` (`device-connection-cleanup`), `Sample.Shipping` (`test-samples-corpus`). Registering any of them would fail on the missing assembly, so they stay out until converted (the planning ticket's default).
  - a target that runs after `Build` (and so after every referenced project has built) and:
    - calls `GetDataphorLayoutItems` on its project references with the same global-property handling as above;
    - **bin/**: takes every `Output` and every `Package` item of the Bin projects to `bin\<DestinationSubPath or file name>`. Package files keep the SDK's copy-local shape (generic files at the root, `runtimes/<rid>/…` subtrees as-is, the SQLite native interop under `runtimes/*/native/`), because a host's `.deps.json` will later expect that shape. Duplicates with the same destination and the same source are collapsed. The same destination from two different source files is a build error (a version split).
    - **Libraries/&lt;F&gt;/** for each D4 library folder: every file under the source folder except `Source\**`, `bin\**`, `obj\**`, `*.dll`, `*.pdb` and `*.exe`, at its relative path. Assemblies come only from builds; the exclusion keeps a stale legacy-build DLL on someone's disk from reaching the layout. Then, for the library project whose `DataphorLibrary` is `<F>`: its `Output` items, and its `Package` items with `DataphorPrivate=true`, **flattened into the folder** with one file per destination file name, choosing `RuntimeIdentifier` `win-x64` first, then `win`, then none, and dropping other RIDs. The product targets Windows x64 (D1, D10); the generic file is the one that throws `PlatformNotSupportedException` (verified above). A private `AssetType=native` file is a **build error** naming the library and `port-library-loading`, which owns native probing.
    - two source folders with the same name in different trees (for example a `samples/X` and a `tests/libraries/X`) are a build error;
    - **checks every `.d4l`**: read `files.filereference/@filename` with `XmlPeek` (namespace `Alphora.Dataphor.DAE.Schema,Alphora.Dataphor.DAE`) and fail the build if a listed file is not in that library's computed file set. This turns the server's registration-time `FileNotFoundException` (`FileUtility.IsAssembly`, `src/engine/Base.Windows/PathUtility.cs` ~42–60) into a build error. It catches a converted library project missing from the Library list, a wrong RID choice that drops a file, and a library added to the layout before its project is converted;
    - **copies** with `SkipUnchangedFiles=true` and **no hard or symbolic links** (`UseHardlinksIfPossible` and `UseSymboliclinksIfPossible` false). A server pointed at the layout rewrites `.d4l` files in place, and a link would carry that write back into the source tree or the NuGet cache;
    - **mirrors**: deletes every file under `$(DataphorLayoutDir)` that is not in the computed set, and removes `Libraries\<X>` folders that are not in the library list. Before any deletion, guard that `$(DataphorLayoutDir)` is non-empty and lies under `$(ArtifactsPath)`; otherwise fail.
  - a hook after `Clean` that deletes `$(DataphorLayoutDir)`.
  - a `NOTE:` comment: when a `net10.0-windows` project (a UI host) joins the Bin list, switch `Layout.csproj` to `net10.0-windows` or skip target-framework negotiation for that reference. A `net10.0` project cannot reference a `net10.0-windows` one, even with `ReferenceOutputAssembly=false`.
- `Layout.csproj` needs no `NoWarn` and no package references.

### What `bin/` is in Phase 1

The core and server assemblies with their package runtime files, and **no** host: no `.exe`, `.deps.json` or `.runtimeconfig.json`. Nothing in Phase 1 runs from `bin/`. The test host references the engine projects directly and gets its own output. `host-generic-host` adds the first host and its `.deps.json`, and `installer-publish-profiles` decides the shape of the install image. Say this in the plan's WS1 design notes and in AGENTS.md so nobody tries to run from `bin/` yet.

### Default library directory (no code change)

`ServerConfiguration.DefaultInstance` resolves `PathUtility.GetInstallationDirectory()` + `Libraries`. For `artifacts/layout/<config>/bin/` that is `artifacts/layout/Libraries`, one level above the layout's folder. Accepted: every consumer sets `LibraryDirectories` explicitly. Changing `PathUtility` is deployment-visible and belongs to `host-instance-configuration` (`feat-ws5-protocol-and-hosting`). `port-engine-runtime-fixes` already points there. With no `.d4l` edit and no change in how the server locates libraries, no migration-notes entry is owed.

## Edge cases & interactions

- **Clean clone, both configurations.** Delete `artifacts/layout` (never `git clean`), then `dotnet build Dataphor.slnx` and `-c Release`. Both layouts appear, and `git status` shows only this ticket's edits: no file in a source folder. Verified by running it.
- **Incremental rebuild leaves nothing stale.** Put a stray `Documents\Stray.d4` into the layout's `Libraries\Connection\` and a stray `Libraries\Stray\` folder into the layout, not into the source tree, then rebuild: both are gone. A file deleted from a source `Documents/` is the same case seen from the other side. Verified by running it.
- **Building one project alone** (`dotnet build libraries/Connection/Source/DAE.Connection.csproj`) does not touch the layout: only `Layout.csproj` writes there. Check by inspection, and by comparing layout timestamps before and after.
- **No double builds.** The calls from `Layout.csproj` into its references must not evaluate a project with a second set of global properties. The symptoms would be a project listed twice in the build output, or intermittent file-in-use errors. Check once with `-bl` and the binary log, or by reading the console output of a `-v n` build, and report it.
- **Parallel build.** Only `Layout.csproj` writes the layout, and it builds after its references through `ProjectReference`, so the layout never races the compilers. A Debug and a Release build write to separate folders. Two simultaneous builds of the same configuration are no more supported than for `artifacts/bin/`.
- **RID choice.** Check after the build that `Libraries\Connection\System.Data.OleDb.dll` and `System.Diagnostics.PerformanceCounter.dll` are byte-identical (hash) to the `runtimes\win\lib\net10.0\` files in the NuGet cache, not the `lib\net10.0\` stubs. Verified by running the hash comparison; the mechanism itself was verified during planning (above).
- **Expected library folder contents** (from the deps files at planning time; investigate any difference rather than adjusting the expectation): Connection: its `.d4l`, `Documents/`, `Upgrades/`, `Alphora.Dataphor.DAE.Connection.dll` + `.pdb`, `System.Data.OleDb.dll`, `System.Diagnostics.PerformanceCounter.dll`, `System.Configuration.ConfigurationManager.dll`, `System.Security.Cryptography.ProtectedData.dll`. System.Internet: its D4 files, `System.Internet.dll` + `.pdb`, `Newtonsoft.Json.dll`. Every other C# library: its D4 files and its own `.dll` + `.pdb` only. D4-only libraries: their tracked files only. List the resulting tree (file names per library folder) in the handoff.
- **`.d4l` check works.** Temporarily take one library project out of the Library list, or exclude a package file, and confirm the build fails naming the `.d4l` and the missing file; then restore it. Verified by running it once; not a standing test.
- **Native private asset.** None exists today. The build-error branch is verified by inspection only.
- **Mirroring safety.** The deletion step is guarded against an empty or out-of-artifacts `DataphorLayoutDir`. Verify by reading the target.
- **A server writing into the layout.** The layout is build output, but a server pointed at it writes there: it saves changed `.d4l` files into the library folders, and library operators in the coverage scripts create, rename and alter libraries. (It does not need to create `General/`, because the shipped `General` library is in the layout.) The next build restores the source copy (a changed size or timestamp defeats `SkipUnchangedFiles`), and the mirror deletes anything new. AGENTS.md says to point a server at a **copy**; `test-harness-inprocess` copies.
- **Newtonsoft.Json in two places.** System.Internet registers from the layout: the spike's `REGISTERED System.Internet` line. The planning experiment shows why: `LoadFrom` returns the host's assembly.
- **Connection's dependencies at run time.** Registering Connection does not load OLE DB, so `REGISTERED Connection` proves only the assembly. Creating an OLE DB connection would load `System.Data.OleDb` from the folder through `LoadFrom`'s same-folder lookup, as verified in planning. No end-to-end OLE DB test is owed here (no provider in CI; plan D15 keeps OLE DB only where it converts without effort).
- **Coverage unchanged.** The spike's `--smoke --coverage` gives `pass=63 fail=14` with the plan Appendix A failing set. Smoke and concurrency are as AGENTS.md describes (concurrency 10–25 errors, varying). Any other change in coverage is a defect in the layout, not a new baseline.
- **Library name collisions across trees** are a build error (inspection; no such collision exists today).
- **Future converted libraries** must be added to the Library list in `Layout.csproj`; the `.d4l` check fails the build if one is forgotten. Add one bullet to AGENTS.md "Converting another project": add the project to `tools/layout/Layout.csproj` (Library list for a library project, Bin list otherwise), and for a library whose folder was excluded, remove the exclusion.

## Tests

No new automated test: the layout is build wiring (project rule: no tests for wiring), and the `.d4l` check fails the build on the defect class that matters (a missing listed file). The characterization is the spike's coverage run from the layout plus the two registration lines, and EngineCheck `RESULT: pass` in Debug and Release. `test-harness-inprocess` makes the coverage run permanent.
