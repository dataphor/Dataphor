# Lazy catalog-store write transactions and read-your-writes (K10, second half)

**Context.** After `store-sqlite-wal-busy`, the SQLite catalog store runs in WAL mode, every store transaction begins `IMMEDIATE` (takes the write lock up front), and a lock wait past `BusyTimeout` raises `StoreException` 130103. That removes the "database is locked" failures, but it is the spike's "begin immediate for everything": a session that has written to the store once begins a store write transaction at the start of *every* later process transaction and holds the write lock for its whole length, even when the transaction only reads. One long user transaction then blocks every other session's DDL. This ticket implements the plan's target design ([WS4](../../docs/modernization-plan.md#ws4-catalog-store)): the store write transaction opens on the first store *write* inside a process transaction; reads run outside SQLite transactions; a transaction that has written reads through its own write connection.

## How it works today (verified; line numbers approximate)

- `ServerProcess.InternalBeginTransaction` (`src/engine/DAE/Server/ServerProcess.cs` ~1263) calls `BeginTransaction` on every device session, including the catalog device session. Implicit transactions only start at nesting 0 (~1793). A device session connected inside an open transaction is caught up by `ServerProcess.DeviceConnect` (~546).
- `ServerCatalogDeviceSession` (`src/engine/Server/Device.Catalog/ServerCatalogDeviceSession.cs`, regions "Catalog Store" ~68 and "Transaction" ~1620):
  - `AcquireCatalogStoreConnection(bool isUpdatable)` increments `_acquireCount`; if no connection is held, `true` connects a dedicated one (`Device.Store.Connect()`) and `false` takes one from the pool (`Device.Store.AcquireConnection()`). On the first-ever `true` it sets `_isUpdatable` and begins `ServerProcess.TransactionCount` store transactions to catch up.
  - `ReleaseCatalogStoreConnection` decrements and returns the connection to the pool at 0 unless `_isUpdatable`.
  - `_isUpdatable` is never reset, so after its first write the session keeps its connection for life and `InternalBeginTransaction` / `InternalAfterCommitTransaction` / `InternalAfterRollbackTransaction` begin, commit and roll back a store transaction for every later process transaction (the condition is `_catalogStoreConnection != null && _isUpdatable`). This is the mechanism to remove.
  - Every store-writing method calls `AcquireCatalogStoreConnection(true)` at its entry, before its own `try`; read methods call it with `false`.
- `CatalogStoreConnection` (`src/engine/DAE/Device.Catalog/CatalogStore.cs` ~740) flushes its cursor cache at the outermost begin, commit and rollback, and caches closed cursors only while `TransactionCount > 0`.
- `SQLStoreConnection` counts nesting; only 0 → 1 issues the SQL begin; nested levels push a `BeginTransactionOperation` marker into an undo log, and `SQLStoreCursor` logs undo statements when `TransactionCount > 1`.
- `CatalogDeviceTable` (D4 queries over catalog tables translated to store SQL) opens its own connection with no SQLite transaction and reads committed data only.

## Design (settled in planning)

**Lazy begin lives in `ServerCatalogDeviceSession`, not in the SQLite store.** Rejected alternative: keep the logical nesting in the SQLite store connection and issue `BEGIN IMMEDIATE` before the first write statement. That would put the SQL begin *after* the logical begin, so `CatalogStoreConnection` would cache cursors opened in autocommit mode (it caches whenever its logical count is above 0) and carry them across the `BEGIN` — the stale-snapshot upgrade the plan warns about. Beginning the store transaction itself at the first write keeps the logical and the SQL begin together, keeps the store layer generic (the SQL Server store gets lazy transactions too), and needs no knowledge of which statements write.

Rules, with the invariant they keep — **the store connection's `TransactionCount` is either 0 or equal to the number of process transaction levels open when the session last wrote, and never exceeds the session's current nesting**:

1. **Begin.** `InternalBeginTransaction` no longer begins a store transaction (it still calls the base, the in-memory DDL undo log).
2. **First write in a transaction.** `AcquireCatalogStoreConnection(true)` connects or keeps the session's connection as today and then, every time (not only the first time), begins store transactions until the store's count equals `ServerProcess.TransactionCount`, using each level's isolation (`ServerProcess.Transactions[index].IsolationLevel`; the SQLite store makes every one a write transaction begun immediate). With no process transaction open the write autocommits, as today.
3. **Commit / rollback.** `InternalAfterCommitTransaction` / `InternalAfterRollbackTransaction` commit or roll back the store only if the store has a level for the process level being ended (store count equals the session's nesting before the pop). Find out whether `ServerProcess.TransactionCount` / the device session's `Transactions.Count` has already been decremented when these hooks run, and write the comparison against the right one; add an `Error.AssertFail` that the invariant holds after each end.
4. **Release at the outermost end.** When the store's count returns to 0 and no acquire is outstanding (`_acquireCount == 0`), reset `_isUpdatable` and give the connection back to the pool (`Device.Store.ReleaseConnection`). This replaces "owned for life": a session holds a dedicated connection only while it has a store write transaction open, which also stops sessions that once wrote from using up `SQLStore.MaxConnections` (60) for good. Assert the connection is out of transaction before it goes back to the pool.
5. **Read-your-writes.** Rule: *once a process transaction has begun a store transaction, every store read of that session goes through the session's own connection until the store transaction ends.* Enforced where it is today: `AcquireCatalogStoreConnection(false)` returns the held connection whenever one is held, and rule 4 keeps it held until the store transaction ends. Before the first write, reads go to the pool (or the held connection) in autocommit, each statement on its own committed WAL snapshot.
6. **No open reader across the lazy begin.** A store write method can be entered while an outer read method of the same session still has a cursor open on the same connection (an `Acquire(false)` → loop → `Acquire(true)` nesting). Beginning `IMMEDIATE` on a connection with an active read statement upgrades that statement's snapshot, and fails (`SQLITE_BUSY_SNAPSHOT`, reported as 130103) if another session committed since. Find out whether any such nesting exists in `ServerCatalogDeviceSession` / `CatalogStoreConnection` (search the write methods' callers for ones called inside an open cursor loop); fix any you find by reading into a list first; and add an assertion at the lazy begin that the connection has no open reader (add an open-reader count to `SQLStoreConnection` — readers come from `ExecuteReader` — if there is no cheaper signal).
7. **`CatalogDeviceTable` keeps its behaviour**: a D4 query over a catalog table that the store answers sees committed data only, not the calling transaction's own uncommitted store writes. That is what 3.1 did; changing it would need `CatalogDeviceTable` to borrow the session's write connection and its cursor rules. Leave a `NOTE:` at its `InternalOpen` saying so.

**Abandoned sessions.** A session whose client vanishes while its transaction holds the store write lock blocks every other session's DDL (each fails with 130103 after the busy timeout) until the server reclaims the session. This ticket makes that rarer (only transactions that wrote hold the lock); reclaiming is `port-abandoned-session-cleanup` (`feat-ws5-protocol-and-hosting`), where the arm is already filed. Say so in `docs/architecture.md`.

## Tests (add to `tests/DAE.Server.Tests/CatalogStoreConcurrencyTest.cs`)

- **`LongDDLTransactionBlocksOnlyWriters`** — the long-running DDL transaction, and the reproduction for this half of K10. Setup: session B runs one `create table` and commits (so it is a session that has written before, the case the eager design blocks). Session A begins an explicit transaction, runs `create table TA`, and holds the transaction open. While A holds it:
  - session B begins an explicit transaction and reads: resolves and counts an existing table, selects from a catalog table (`System.Objects` or another one answered from the store), evaluates an existing operator; then commits. Must complete, without error, well inside the default 30 s timeout (assert under 10 s);
  - session C, which never wrote, does the same reads in implicit transactions; same expectation;
  - session D runs `create table TD` on a thread with the default timeout; it must still be waiting after 1 s, and must complete successfully once A commits.
  After A commits: `TA` and `TD` resolve from B. On `store-sqlite-wal-busy`'s code B's explicit transaction blocks behind A (and fails with 130103 or times the assertion out): run it there first and record that. The short-timeout "fail with the busy error" variant is `StoreLockWaitReportsStoreLocked`, landed by `store-sqlite-wal-busy`; do not duplicate it.
- **`TransactionReadsItsOwnStoreWrites`** — read-your-writes. In one explicit transaction: create table T, insert into it and read it back; create view V over T; then attempt `drop table T`, which must fail because V depends on T. Confirm first that the dependents check reads `DAEObjectDependencies` from the store (`SelectObjectDependents` or similar in `ServerCatalogDeviceSession`); if it is answered in memory instead, pick another check that reads the store and name it in the test comment. Then create and call an operator. Roll back. T, V and the operator no longer resolve, and no row for them remains in `DAECatalogObjects` (read the file directly, as `ConcurrentDDLTest.ReadStoredScripts` does, after stopping the server).
- **`BusyAtTransactionStartLeavesNoTransaction`** (*added by `store-sqlite-wal-busy`*, which verified the failure with a probe). Server with `BusyTimeout=1000` appended to the catalog connection string. Session B runs `create table B1` (B has now written). Session A begins an explicit transaction and runs `create table A1`. B runs `create table B2`: must fail with 130103, and afterwards B must not be in a transaction (`processB.InTransaction` false). A commits; B runs `create table B3`; B disconnects; after a restart B3 resolves and B2 does not. On `store-sqlite-wal-busy`'s code the 130103 is raised by the catalog device session's begin at the start of B's implicit transaction, and B is left in a half-started transaction for good (`InTransaction` true, count 1): B3 then runs inside it, is written to the store in autocommit, and is rolled back in memory only when B disconnects. Rule 1 removes this route (the store begin moves into the statement); the general engine defect, a failed begin of any participant leaving the process half-begun, is `bug-process-begin-leaves-partial-transaction`.
- `ConcurrentDDLWithQueriesAndDrops` and `ConcurrentDDLTest.ConcurrentSessionsStoreTheirOwnScripts` (both require zero errors after `store-sqlite-wal-busy`) must still pass: lazy begin moves the write lock later, so any lock-upgrade path that remains shows up there. Record their times beside the previous ticket's.

## Edge cases & interactions

- **First write at a nested level** (outer transaction read only, inner one writes): catch-up begins all levels at once; the SQL begin happens at level 1, markers are pushed for the rest; rolling back the inner level replays only its own undo log; committing the outer commits SQLite. Verified by inspection and the invariant assertion. Note that statement-level writes (`CatalogStoreConnection.InsertRow`/`DeleteRows`) are never undo-logged at nested levels on this store — a pre-existing defect filed as `bug-store-nested-rollback-keeps-rows`; do not fix it here.
- **Nested process level without a write after a written outer level**: store count stays below the process count; the inner commit or rollback must not touch the store. Invariant assertion.
- **Lazy begin fails with 130103** (another session holds the lock): `AcquireCatalogStoreConnection` has already incremented `_acquireCount` and is called outside its caller's `try`, so a throw would leak the count and the connection. Make the acquire undo its own increment (and release or drop a connection it just took) when the catch-up throws. The store's count stays at whatever levels did begin (normally 0), so the process rollback that follows is consistent. Verified by inspection; `StoreLockWaitReportsStoreLocked` (B retries on the same session after the failure) exercises the path. *Added by `store-sqlite-wal-busy`:* that ticket already made the acquire clean up (a `try`/`catch` around its body releases the acquire, or only undoes the count when no connection was taken) and sets `_isUpdatable` only after the catch-up begins succeed, because `StoreLockWaitReportsStoreLocked` otherwise left the store's count at -1 after the rollback and B's retry ran in autocommit. Keep both properties when rewriting the method.
- **Read before the first write, write after, in one transaction**: the read ran on a committed snapshot that another session may have changed before this session's `BEGIN IMMEDIATE`. The guard against a conflicting create is the store's primary keys (reported as a user error) and the engine's catalog locks; same exposure as 3.1. By inspection; say so in the architecture paragraph.
- **Cursor cache across the outermost commit/rollback and the release to the pool**: flushed at the outermost end (existing code); the connection goes back to the pool with an empty cache. By inspection plus the assertion in rule 4.
- **`DeviceConnect` catch-up** (catalog device session connected inside an open transaction): it calls `BeginTransaction` per level, which now opens nothing in the store; the first write catches up. By inspection.
- **Writes outside any process transaction** (server start-up, `SaveServerSettings` with no transaction): autocommit per statement, as today. By inspection.
- **K3-like races**: write transactions now start later and overlap more; any "Collection was modified" or similar from shared engine state during the concurrency tests is a new defect: capture the innermost stack and follow the pre-existing-failure procedure if it is outside this change, rather than tolerating it.
- **Engine-only servers** (`IsEngine`) have no store; nothing changes.
