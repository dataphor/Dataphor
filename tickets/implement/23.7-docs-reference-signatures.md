## What this is

The first of two tickets for the plan's WS8 work item `docs-reference-generator` ("Markdown emitter for the catalog documentation operator; regenerate and diff"). This one settles where the generator lives, builds it, and does the operator and scalar-type half of the comparison. `docs-reference-generator` - the second ticket, which generates the missing system tables reference and closes the plan row - follows it and depends on it.

Every operator page under `docs/reference/system-library/operators/` carries a `**Declarations**` block holding that operator's D4 signature, and every page under `types/` carries a `**Type Declaration**` block and usually a `**Declarations**` block too. Those blocks are the 3.x published record: `docs-reference-tooling` extracted them from the 2007 help file, because the DocBook sources had placeholders where the signatures belong - the old publishing tool filled them from a live catalog at publication time. Nothing has ever compared them with the engine this port ships. An operator signature is a compatibility surface the port must not have changed, so a disagreement between a page and the running catalog is evidence about the port, and today there is no way to see one.

## The decision this ticket exists to make, and the answer

The plan ticket asked where the Markdown emitter should live, and offered three options: move `legacy/libraries/Documentation` back into the build as a shipped library; write the generator against the in-process test harness; or write only a check that reports differences without generating anything.

**Answer: a test fixture in `tests/DAE.Server.Tests`, which generates and compares. `legacy/libraries/Documentation` stays parked and is not moved.** The measurements that decide it, all read from the tree at commit `b23059fa`:

**The engine already ships the operator the parked library provided.** `System.Script(const AName : Name) : String` (declared in `src/engine/DAE/Schema/SystemCatalog.d4:519`, implemented by `SystemScriptNode` in `src/engine/Server/Runtime.Instructions/CatalogNodes.cs:279`) calls `program.Catalog.EmitStatement(..., EmitMode.ForCopy, ...)` and emits the result with `D4TextEmitter`. That is exactly, line for line, what the parked library's `DocOperator.WriteDocbookDeclarations` does to produce a declaration block (`legacy/libraries/Documentation/Source/Samples.cs:439-467`). So the generated half of the reference needs no new D4 operator, no new assembly and no new class registration: a `select` over the `Operators` system table with `Script(...)` added to it produces every declaration the pages carry. An administrator can already do this against their own catalog, which was the one thing moving the library into the build would have bought.

**There is almost nothing in the parked library worth porting.** It is 1,859 lines, and the part that reads catalog facts is the two statements above. The rest is DocBook machinery - an XSL and XPath template processor that splices hand-written XML fragments into generated XML - and the Markdown pages already hold that prose, so the machinery has no job. Three further measurements say the same thing. `DocOperator.WriteDocbookData` hard-codes the absolute path `c:\src\Alphora\Docs\DocbookManuals\OperatorDocs\` twice and **silently emits nothing for an operator with no prose file there** (`Samples.cs:405-413`), so the tool as written cannot produce a complete listing - it is an instance of the very defect the plan ticket warned about. `DocLibrary` is a server-side instruction node that drives `Alphora.Dataphor.DAE.Client.DataView` (`Samples.cs:572-650`), so shipping it would pull the client stack into the server's library set. And `DocOperatorOrdered`, which the plan ticket asked about, is inside a `/* */` comment that runs from `Samples.cs:508` to `:566`: it is not compiled, not registered and not a question.

**What is given up by not moving the library.** Three D4 class names (`DocSamples.DocOperator`, `DocSamples.DocLibrary`, `DocSamples.ObjectMetaDataNode`) and the assembly name `DocSamples` do not become compatibility surfaces, which is a gain, not a loss. The real loss is that there is no single D4 operator an administrator invokes to write a whole reference page set - they get `Script`, which answers one object at a time. The plan's WS10 table has a row for `dataphor docs generate`; if that command is ever built, the page-assembly code moves out of the test project into the command's project and this fixture references it from there. That direction is the right one and is recorded in the plan text this ticket writes; nothing is built for it now.

**Why a test and not a program under `tools/`.** The point of the work item is that the reference stops drifting from the product without anyone noticing. A test runs in CI on every push (`.github/workflows/build.yml`); a program under `tools/` runs when someone remembers. The repository already has this exact machinery twice - `FrontendDerivationGoldenTest` and the two `*DeviceTranslationGoldenTests` generate from a server and compare with checked-in files, with an environment variable that rewrites them - so this is the established mechanism here rather than a new one.

## What the generator is

One D4 query per object kind, run on an in-process server, plus C# that assembles and compares text. For operators:

```d4
select
    Operators
        where Library_Name = 'System'
        add { Script(Name) Declaration }
        order by { OperatorName, Name }
```

`Operators` (`SystemCatalog.d4:1581`) carries `OperatorName` - the name without the signature, which is the name a page is named after - beside `Name`, which is the signature-qualified name `Script` needs. So grouping the overloads of one name is a grouping on a column, and **the backward-navigable cursor the old script's comment demanded is not needed**: it was an artifact of walking a cursor that had only `Name` in it. Ordering by `{ OperatorName, Name }` fixes the order of overloads within a page.

Two things to measure before writing much: whether `Script` resolves a signature-qualified operator name through its `Name` overload (which calls `Compiler.ResolveCatalogIdentifier`) or needs the `String` specifier overload (`Compiler.ResolveCatalogObjectSpecifier`) - force the overload explicitly either way rather than relying on the implicit `Name`-to-`String` conversion - and whether the emitted text for one object is bare (`Catalog.EmitStatement` returns a `Block`, and `D4Emitter.EmitBlock` writes a bare sequence of terminated statements, so it should be) or carries a wrapper.

Scalar types are the same shape over the `ScalarTypes` system table; a type's emitted `create type` statement is what the pages' `**Type Declaration**` block holds, and the selector and comparison operators a `representation` generates are what its `**Declarations**` block holds. The generated operator set therefore includes those generated operators, which is correct and is also why a type's page has two blocks.

## What gets committed, and the three things the fixture asserts

New goldens tree, `tests/goldens/reference/system-library/`, reached through `TestEnvironment.GoldensDirectory`:

- `operators/<OperatorName>.d4` - the generated declarations for one documented operator name, every overload, in the order above, **exactly as the emitter writes them**: tabs for indentation and CRLF line endings, because that is what `TextEmitter.Indent()` and `TextEmitter.NewLine()` produce (`src/engine/DAE/Language/Emitter.cs:27-35`). 290 files, one per operator page that has a declarations block.
- `types/<TypeName>.d4` - the generated `create type` statement and the generated operator declarations for one documented scalar type. 20 files.
- `operator-inventory.txt` - one line per operator name in the System library with its overload count, sorted. This is the only place an operator with no documentation page is visible at all, and it is what tells a later reader that the reference is incomplete and by how much. One file rather than a file per name: the 290 documented names are worth a reviewable file each, the rest are worth a line each.

`DATAPHOR_UPDATE_REFERENCE_GOLDENS=1` writes all of the above, deletes files no case produces, and then **fails the run anyway**, exactly as the two existing update variables do, so an update can never be mistaken for a pass. It is the fifth such variable; the sentence in `AGENTS.md` that counts them ("one of the four other variables the suite reads") has to change, and `docs/contributing/build-and-test.md` needs the same entry.

The fixture, one case per documented name:

1. **Generated text equals the golden**, character for character. This is the standing regression net: a change to a documented operator's signature anywhere in the engine becomes a reviewable diff in a file rather than a wrong page a customer finds.
2. **The golden equals the page's block**, after normalization (below). A failure here means the page and the engine disagree *and nobody has recorded why*.
3. **The set of disagreements is exactly a recorded table in the fixture.** Each entry carries the object name, a verdict and one line of reason. This is the port evidence, and it is what makes assertion 2 green on a difference that has been looked at while still failing on one that has not.

### The verdicts

`Stale` - the page publishes something no catalog has ever had, so the page is wrong and is corrected in this ticket. `Changed` - the signature really did change between 3.x and this port, so the page is updated to the generated text **and `docs/migration-notes.md` gains an entry in the same commit** (project rule: a change an application could notice). `Defect` - the port changed a signature it should not have; the page is left alone, the entry names the ticket filed for it. `Unread` - see below.

One `Stale` entry is already known and is the first case to look at: `docs/reference/system-library/operators/System.Execute.md` publishes a one-argument `System.Execute(const AScript : String)` overload that does not exist and, per `docs-reference-operators`, never did - `git show 361ebd83:Dataphor/DAE/Schema/SystemCatalog.d4`, the 2008 open-source import, already lacks it. `docs-reference-operators` deliberately published what shipped rather than correcting it, leaving this case as the demonstration that the comparison works.

### If the difference set is too large to classify in one run

Classify as many as the run allows, record the rest as `Unread`, make the fixture call `Assert.Warn` for as long as any `Unread` entry remains, naming the follow-up ticket - the shape `LivePGSQLDeviceTest` already uses for a roll-up it reports rather than fails on - and file that follow-up ticket into `tickets/fix/`. Do not leave an unrecorded difference, and do not guess a verdict: an unexamined `Stale` that is really a `Defect` is a port regression published as documentation.

### The normalizer, and why assertion 2 needs one

The committed blocks cannot be compared with the emitter's output character for character, and the reason is measured rather than suspected. The emitter indents with tabs and ends lines with CRLF; **no page under `docs/reference/system-library/operators/` contains a single tab** (measured with `grep -l`, 0 of 322 files), and the pages are LF. The 3.x text reached the pages through the help file, the DocBook `<programlisting>` and pandoc, which expanded the tabs to spaces at tab stops - which is why `System.Abs.md` has one space before `class` while `System.Execute.md` has four before each tag, from the same emitter at different nesting depths.

So assertion 2 compares text normalized by: converting line endings to LF, expanding tabs, collapsing runs of horizontal whitespace to one space, trimming each line, and dropping blank lines - **and nothing else**. Do not normalize inside string literals, and do not normalize case, punctuation, operand names or type names: those are the content. State in the fixture's remarks that the normalizer exists because of the pandoc round trip and not because the two forms are allowed to drift, and that assertion 1 is the one that is exact.

## Which catalog, and determinism

The fixture derives from `InProcessTestFixture` with an **empty `Libraries` list and an empty `LibrariesToRegister` list**, so the server carries nothing but the built-in System library. The System library's operator and type set is then a function of the engine alone, which is what makes "the diff is clean" mean something - the plan ticket's worry about an unpinned library set is answered by registering nothing rather than by filtering. Filter on `Library_Name = 'System'` rather than on the old script's `'System.'.Pos(Name) = 0`, which is a name-prefix test that another library could satisfy.

The generated text has to be stable across runs on the same catalog or the goldens churn. The old DocBook emitter wrote no timestamp into its output (measured: `Samples.cs` emits no date anywhere - the plan ticket's worry about a `<date>` element was mistaken), and `Script` emits only catalog facts, so there is nothing to strip. The order is fixed by the query's ordering. Confirm stability the way `FrontendDerivationGoldenTest` did: generate twice in one instance and once more on a second instance, and assert the three agree; if a field does drift, name it in the fixture's remarks rather than adding a normalizer pre-emptively.

## Edge cases & interactions

- **Seven operator pages and one type page have no declarations block, and that is correct.** Measured: `System.ActualDate`, `System.ActualDateTime`, `System.ActualTime`, `System.IsNotNil`, `System.MonthsBetween`, `System.YearsBetween` (added to the DocBook after the help file was published, so no signature was ever published for them) and `System.iXor` (converted from its single 2004 file, which had no signature block), plus the type `System.GroupName`. These are absences, not disagreements: the fixture asserts the set of pages with no block is exactly this list of eight, and generates a golden for them anyway, so the next reader can see what the engine says. A page that loses or gains a block without the list changing fails the run. Verified by inspection of the fixture's list against the tree - no test of its own.
- **A page may name an object the catalog does not have.** `System.GroupName` is the likely case: the plan records that the pre-3.0 group-based security operators no longer exist, and `GroupName` was added to the DocBook after publication. A page with no catalog object is a third outcome beside "agrees" and "differs", and it needs its own recorded list with a reason each - a missing object is either a page documenting something this release removed (which belongs in `docs/migration-notes.md` if it is not there already) or a defect.
- **The 25 category pages are not objects.** `docs/reference/system-library/operators/` holds 322 files: 297 operator pages and 25 category index pages (`System.MathOperators.md` and the like) that list links and have no declarations. Drive the fixture from the pages that *have* a block plus the recorded list of eight that should not, and assert that the remainder is exactly the 25 category pages named in `system-library/README.md` - otherwise a new page silently escapes the comparison.
- **Both directions of every set must be asserted.** Every recorded entry must match something and everything must be covered by a case or a recorded entry - the convention `CoverageManifest`, `FormCustomizationTest.Exclusions` and `FrontendDerivationGoldenTest` all follow. A difference table entry that no longer matches a difference is a fixed page nobody noticed, and it must fail.
- **Writing into `docs/`.** This fixture reads `docs/` through `TestEnvironment.RepositoryDirectory` (over the `DataphorRepositoryDir` assembly metadata - never spell the path), and the update variable writes into `tests/goldens/`, not into `docs/`. Page corrections in this ticket are hand edits with a verdict behind each one; nothing mechanically rewrites a documentation page, because the prose around the block is hand-written and a rewriter that got it wrong would destroy it. Keep each page's LF endings and absence of a byte-order mark when editing.
- **The pages stay the 3.x record except where a verdict says otherwise.** The plan is explicit that the published signatures are the baseline this work item measures against; overwriting all 290 blocks with generated text would compare 4.0 against 4.0 on the next run and prove nothing. So a page changes only with a `Stale` or `Changed` verdict recorded beside it. Update the two sentences that promise otherwise - `docs/reference/README.md` and `docs/reference/system-library/README.md` both say `docs-reference-generator` "will emit signatures from a running server instead" - to say what actually landed and where the generated text is.
- **Timing.** This fixture starts one server and runs about 310 cases of string comparison, so it should cost a few seconds. If a per-case `Script` call turns out to dominate, run the query once in the fixture setup and hold the results, rather than once per case.
- **Test class name and the suite's five-part split.** The parts in `AGENTS.md` are partitioned by the first letter of the test class name, and the partition holds for any name, so no part command changes. But note which part a new class lands in when reporting what was run.
- **Privacy.** The server starts on this repository's own built-in library and nothing else, so no deployment's library names can reach a golden. Say so in the fixture's remarks.
- **Do not change the engine to make generation convenient.** `Operators`, `ScalarTypes` and `Script` are all shipped surfaces that answer the question as they stand.

## Tests

The fixture *is* the test, and it is the characterization test the project's testing rule asks for: the behaviour being re-hosted is the 3.x publishing tool's declaration generation, and this pins it against the one small, fixed catalog of a bare engine. Nothing else earns a test here - not that the goldens tree exists, not that the update variable writes files, not the normalizer in isolation (it is exercised by all 310 cases).
