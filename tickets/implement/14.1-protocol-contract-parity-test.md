## What this is

The three service contracts are each declared twice: once on the server, synchronously, and once on the client as an asynchronous copy. They are separate interfaces in separate assemblies with no compiler relationship, and the wire only works because the two declarations agree. Today nothing checks that. A hand edit to one side — an operation added, a parameter type changed, a `Name` or `Namespace` touched — compiles cleanly and breaks at run time, on a customer's network, as a WCF action mismatch rather than as anything that names the mistake.

This ticket adds the reflection test the plan calls for: *server and client contract declarations match operation for operation*. It needs no server and no socket, so it is independent of CoreWCF and lands before `protocol-corewcf-proof`.

The pairs, with today's operation counts (all three pairs agree at the moment, so the test passes on the first run and its job is to keep doing so):

| Server declaration | Client declaration | Operations |
|---|---|---|
| `Alphora.Dataphor.DAE.Contracts.IDataphorService` (`AlphoraDataphorServer`) | `IClientDataphorService` (`AlphoraDataphorClient`) | 88 |
| `INativeCLIService` (`AlphoraDataphorServer`) | `IClientNativeCLIService` (`Alphora.Dataphor.DAE.NativeCLI`) | 11 |
| `IListenerService` (`AlphoraDataphorServer`) | `IClientListenerService` (`AlphoraDataphorCommon`) | 3 |

All six interfaces sit in the namespace `Alphora.Dataphor.DAE.Contracts`, so the pairs are told apart by assembly, not by namespace.

## What "match" means

The wire identity of a WCF operation is its action URI, which comes from the contract's `Namespace` and `Name` and from the operation name; the body comes from the parameter and return types. So the test compares, for each pair:

- **Contract identity.** `ServiceContractAttribute.Name` and `.Namespace` equal on both sides. Both are `IDataphorService` / `INativeCLIService` / `IListenerService` and `http://dataphor.org/dataphor/3.0/` today.
- **The operation set.** Every method on the server interface carrying `[OperationContract]`, by name, against the client's operations. A client operation is an `[OperationContract(AsyncPattern = true)]` method called `Begin<Name>` paired with an `End<Name>` method that carries no attribute; its operation name is `<Name>`. Report the two directions separately — present on the server and missing on the client, and the reverse — because the fix differs.
- **The signature.** For operation `X`: the server's parameter list must equal the client's `BeginX` parameter list with the trailing `AsyncCallback` and `object` dropped, element for element by type and position; and the server's return type must equal `EndX`'s return type. Compare types by identity where both sides see the same type (the descriptor and structure types live in `DAE.csproj`, which both reference) and report a mismatch otherwise — do not fall back to comparing type names, which would hide exactly the kind of drift this test is for. Parameter *names* are not part of the wire and are not compared.
- **The declared faults.** The set of `FaultContractAttribute` detail types on each operation, compared as a set. The server's `IDataphorService` uses `DataphorFault`, `IListenerService` uses `ListenerFault`, and the clients use the same two types from the same assemblies, so these compare by identity too. A fault declared on one side only is a real difference: it changes what the other side does with the error.

Report every difference found in one failure message, listing contract, operation and what differs, rather than failing on the first. When three operations drift together the reader wants all three.

## Edge cases & interactions

- **An operation that exists on one side only.** The honest answer is a failure, and it must say which side. Verified by running the test with one operation temporarily commented out of the client interface during development — do not leave that in the tree.
- **`[OperationContract]` on a method that is not part of a pair.** A client `Begin` without its `End`, or an `End` without a `Begin`, is a malformed contract; fail with that wording rather than silently skipping the operation. By inspection of the pairing code plus one assertion at the pairing site.
- **Overloads.** `IDataphorService` has none today, so the test may key operations by name — but it must *check* that assumption rather than rely on it: if two operations on either side share a name, fail saying so. A future overload needs an explicit `[OperationContract(Name = …)]` on the wire anyway.
- **An operation with no explicit `Name`.** WCF takes the operation name from the method name, which for the client means the `Begin` method minus the prefix. If either side ever sets `OperationContractAttribute.Name` explicitly, that is the name to compare; read it when present and fall back to the method name. Today no operation sets it, so the fallback is the live path and the explicit path is covered by inspection.
- **`ServiceKnownType` and inherited contracts.** Neither is used on these six interfaces. Do not build machinery for them; if a future contract adds one, this test will not notice, which is a gap worth a `NOTE:` at the comparison site rather than speculative code.
- **The three fault utility types** (`DataphorFaultUtility`, `ListenerFaultUtility`, `NativeCLIFaultUtility`) convert exceptions to faults and back, and are not part of the contract shape. Out of scope.
- **`protocol-corewcf-proof` runs alongside this.** It may bring one or two excluded files back into `src/engine/Server/Server.csproj`, but the three server contract files are already compiled, so there is no conflict in either direction.
- **The client contracts are a compatibility surface** (the project rules name `src/engine/Server/Contracts` and `src/protocol/Client/Contracts` explicitly). This ticket must not change any declaration to make the test pass. If the test finds a real mismatch, that is a defect: report it in the handoff and file it rather than editing either side here.
