## Diagnosis (fix stage)

The coverage script `ApplicationTransactions` fails at line 41 with `Application Transaction read is not repeatable.` because the harness runs it nested in one statement (`process.ExecuteScript("ExecuteScript('Coverage.Scripts', '<name>');")` in `CoverageScripts.RunInProcess`). That statement's implicit transaction stays open for the whole script, and leaving an application transaction (AT) while a process transaction is open throws away the AT work done in it.

Traced with a scratch in-process test (since removed) and a temporary stack trace in `ApplicationTransactionDeviceSession.InternalRollbackTransaction`: `LeaveApplicationTransaction` → `ServerProcess.DeviceDisconnect` → `Device.Disconnect` → `ApplicationTransactionDeviceSession.Dispose` → `EnsureTransactionsRolledback` → rollback of the open device transaction holding the insert (2 operations). Results of the minimal script from the fix ticket, run several ways:

| How it was run | Result |
|---|---|
| Each statement its own batch, implicit transactions on (`IServerProcess.ExecuteScript`, as Dataphoria runs a script) | pass |
| Same, after a batch `BeginTransaction();` | pass: with implicit transactions on, `ServerProcess.EndTransactionalCall` commits every transaction opened during the call, so the D4 `BeginTransaction()` does not outlive its batch. This explains the fix ticket's puzzling observation; nothing was open at the leave. |
| Implicit transactions off, batch by batch | pass |
| Implicit transactions off, `BeginTransaction();` then batch by batch | **fails at "D"** (row lost): the rule is real and not specific to nesting |
| Whole text nested in one `Execute('…')` | **fails at "D"** |
| Whole text in one `begin … end` block | fails earlier, at "C": the block is compiled before `JoinApplicationTransaction` runs, so its table references bind to the real table. A different, compile-time effect, and the reason the script's header says its batches must run as a whole *script*, not as one block. |

The whole 707-line `ApplicationTransactions.d4`, run through `IServerProcess.ExecuteScript` on a fresh in-process server, **passes** (about 0.5 s), now that `engine-at-cursor-no-device` has landed.

The engine behaviour is legacy: the leave/disconnect/dispose code is unchanged since `v3.1` (only `ab33bb27`, cosmetic), and the legacy NUnit test for this script was ignored from 2007 with "Doesn't work through ExecuteScript". So the harness is what is wrong for this script. Whether the engine should keep AT work across a leave inside an open transaction is a D4 semantics question, filed as `engine-at-leave-discards-transaction-work` in `blocked/` with a proposed behaviour; it does not block this ticket.

## What to build

A manifest option that runs a script's text batch by batch on the test process instead of nested in one `ExecuteScript` statement.

- **Manifest field** `batches` on `CoverageEntry` (`[JsonPropertyName("batches")] public bool? Batches`). Allowed value `true` only (reject `false` as redundant, so there is one way to say the default); not allowed on a `fragment` entry (add it to `ValidateFragment`'s list). Document it in the `<remarks>` list on `CoverageManifest`, next to `preamble`: the script's text is read from the script server's copy of the scripts library and run through `IServerProcess.ExecuteScript` on the test process, one implicit transaction per batch, as Dataphoria runs a script; use it only for a script that depends on batch boundaries (one that leaves an application transaction it changed, or that must see a batch's work committed), and say why in `note`.
- **Harness** (`CoverageScripts.RunInProcess`): when `entry.Batches == true`, replace the nested call with `process.ExecuteScript(text)`, where `text` is the file `Libraries/TestFramework.Coverage.Scripts/Documents/<script>.d4` under the script's own server folder (`instance.Directory` plus `TestServerInstance.LibrariesFolderName`, `ScriptsLibrary`, `Documents`, `ScriptExtension`), read with `File.ReadAllText` (detects a byte-order mark). Reading the server's copy rather than the layout keeps it the same text `ExecuteScript('Coverage.Scripts', …)` would load. The worker's abort-on-timeout path is unchanged: it aborts the process, whichever way the script runs. Registration and preamble run before it as today.
- **Manifest entry**: `{ "script": "ApplicationTransactions", "status": "pass", "batches": true, "note": "…" }` with a note saying the script leaves and rejoins an AT, and run nested the outer statement's open transaction discards the AT work at each leave (`engine-at-leave-discards-transaction-work`).
- **NOTE at the engine site**, in `ApplicationTransactionUtility.LeaveApplicationTransaction` above the `DeviceDisconnect` call (preserve the file's tabs, CRLF and byte-order mark): `// NOTE: disconnecting disposes the AT device session, which rolls back any transaction still open on it, so leaving inside an open process transaction discards the AT work done in that transaction (legacy 3.1 behaviour); whether to keep it is engine-at-leave-discards-transaction-work.`

No new unit test: the `ApplicationTransactions` case itself, now passing through the new option, is the characterization of both the option and the AT behaviour it covers. The manifest validation rules are new branches, but the run already fails on an invalid manifest; a dedicated validation test is not owed.

## Edge cases

- `StreamAllocation` runs every script of the library through `Execute`, nested; once its library name is repaired it will fail in `ApplicationTransactions` this way. `test-pre-3-1-scripts-policy` (blocked) proposes retiring it; leave its entry as it is.
- `RemoteATOperatorEvaluation` and `TestNetworkApplicationTransactions` pass nested today; leave them nested.
- In a full run `ApplicationTransactions` runs on a template copy with `Frontend` and `TestFramework.Coverage.Base` registered; the scratch pass was on a bare server. If the full-run result differs, diagnose before flipping the entry.
- `store-at-enlist-inside-catalog-lock` (fix) hits a Debug assertion when a table is first enlisted in an AT inside a running statement and the catalog store has no transaction yet. Run batch by batch, compilation happens before each batch's implicit transaction, so this script should not reach it; if it does, the entry stays `known-failure` pointing at that ticket.
