**Not converted, and `reference-pages.tsv` records the reason for each:** `ADOConnectionLibraryReference.xml`, `DB2DeviceReference.xml`, `MSOracleConnectionLibraryReference.xml`, `OracleDeviceReference.xml` and `SASDeviceReference.xml`. Those libraries are parked under `legacy/libraries/` (ADOConnection, MSOracleConnection, OracleDevice, SASDevice) or gone from the tree entirely (DB2Device), and documenting a library nobody can load would be worse than documenting nothing. `SystemLibraryReference.xml` is also not converted - `docs-reference-operators` wrote `reference/system-library/README.md` by hand instead, for the reason recorded there.

**A library's operators and types are sections of its own page, not pages of their own.** This differs from the System library, where 297 operators cannot share a page; the largest library here has 36 operator sections and the rest have eight or fewer, so one page per library keeps the `DR<Name>Library.html` to `reference/libraries/<Name>.md` link rule intact and needs no new folder convention. `reference-pages.tsv` maps each operator section to the library's page, and the splitter concatenates them in source order.

## Where the library facts come from: this repository, not the published help file

Each library chapter's *Definition* section has its Version, Requisites and Files replaced by generated-content placeholders, and the chapter also carries generated *Registered Assemblies*, *Registered Classes* and *Schema* sections - 23 to 29 placeholders per chapter.

**The published help file's values are wrong for this release.** Its `DRSimpleDeviceLibrary-Definition.html` gives Version 2.1.0.0; `libraries/SimpleDevice/SimpleDevice.d4l` says 3.0.0.0. So, unlike the operator signatures that `docs-reference-operators` took from it, these facts are not copied from the help file. Read them from the tree, where they are authoritative and trivially available:

- **Version, Requisites and Files** come from the library's own `.d4l` descriptor: the `<library version=…>` attribute, the `<libraries.libraryreference>` elements and the `<files.filereference>` elements. All 13 descriptors read `3.0.0.0` except `General`, which reads `*`.
- **Registered Classes and Registered Assemblies** come from the library's `Source/Register.cs`, whose `DAERegister.GetClasses()` returns them. These class names are a compatibility surface and have not changed; a library with no `Register.cs` registers nothing and the section is not emitted.
- **The Schema section** - the library's full list of defined objects - is not filled. There is no reliable in-tree source for it short of loading the library into a server, which is `docs-reference-generator`'s job, and the help file's version is a bare list of names. Remove the section rather than emit an empty heading, and say so once in `reference/libraries/README.md`.

Fill these by hand in a short `library-facts.tsv` beside the other tables, or have `reference_split.py` read the `.d4l` directly - the implementer's call, but **pick one and write it down**: 13 libraries is small enough that a reviewed table is defensible, and a parser that silently reads a descriptor wrong is not. Either way the result must be visible in `git diff` as data, not buried in a script.

## The three hand-written pages

`PGSQLDevice`, `PGSQLConnection` and `System.Platform` ship with no DocBook chapter. Each gets a short page in the same shape as the converted ones - what the library is for, its Version, Requisites and Files from its `.d4l`, its registered classes from its `Register.cs`, and a *See Also* pointing at the relevant converted guide pages (`docs/developers-guide/devices.md`, `docs/architecture/devices.md`). Keep them short and factual; do not invent behaviour. Where the PostgreSQL device's behaviour is still being settled by WS4 tickets, describe what the descriptor and the registered classes say and nothing more.

## Edge cases & interactions

- **The 27 cross-library operator links.** The sources hold 121 occurrences of `O-Frontend.*`, `O-MSSQLDevice.*`, `O-SQLDevice.*` and `O-SimpleDevice.*` across 27 distinct targets. Each needs a `reference-links.tsv` row pointing at the library page plus the heading anchor of that operator's section, because the built-in rule would send it to `reference/system-library/operators/Frontend.*.md`, which nothing creates. The anchors only exist once the library pages have been rendered, so expect to run the conversion, read the headings it produced, fill the rows, and run again. *Verified by 0 unresolved and by the link checker.*
- **Library names differ between the DocBook and the tree.** `SystemIntegration` against `System.Integration`, `SystemInternet` against `System.Internet`. The page name follows the **shipped** descriptor, so `reference/libraries/System.Integration.md`; and the legacy link `DRSystemIntegrationLibrary.html` therefore needs a `reference-links.tsv` row, because the built-in rule would give `reference/libraries/SystemIntegration.md`. The same applies to `DRSystem.InternetLibrary.html`. *Verified by the link checker and by reading the two rows.*
- **Five `DR*` link targets name libraries that are not documented** (`DRDB2DeviceLibrary.html`, `DRDB2DeviceLibrary-Settings.html`, `DROracleDevice.html`, `DROracleDevice-Settings.html`, `DRMSSQLDeviceLibrary-Example.html` and friends). `docs-reference-tooling` gave them empty targets with that reason; confirm each is unlinked rather than pointing at a missing page, and that the prose around it still reads sensibly - a sentence that says "see the DB2 device" about a device that no longer exists needs the sentence cut, not just the link. **Report any such sentence in the handoff rather than rewriting the reference's meaning quietly.** *Verified by reading the pages that carry those links.*
- **A device library's settings table is reference content, not a generated block.** `SQLDeviceSettings.xml` (17 KB) and the `-Settings` sections of the device chapters are hand-written and must land. Do not confuse them with the generated *Schema* section. *Verified by reading `reference/libraries/SQLDevice.md`.*
- **`ExtDoc` placeholders.** 23 of the 1,291 generated-content instructions are `ExtDoc`/`D4ExtDoc`, the splice points where the old generator inserted the per-operator fragments from `DocBookManuals/OperatorDocs/`. In these chapters the prose is already inline, so they are removed - but check that removing one does not take real content with it. *Verified by the splitter failing on any surviving placeholder and by reading a chapter that had one.*
- **Images.** The library chapters are the part of the reference most likely to carry a figure, and the DocBook trees have their own image folders (`Docs2.0/Images`, `DocBookManuals/images`). Any image a landed page uses goes to `docs/images/` through the usual name rule; `docs/images/` has no orphan today and should still have none. *Verified by the report's missing and unreferenced image lists and by `git status docs/images`.*
- **Letter case and dots.** `System.Integration.md`, `System.Internet.md`, `System.Platform.md`, `PGSQLDevice.md` - all from the page map, never from a name transformation (`page_name` would give `pgsql-device`). *Verified by the link checker on Linux in CI.*
- **Do not touch the library descriptors or any `.cs` file.** This ticket reads `libraries/**/*.d4l` and `libraries/**/Register.cs`; it writes nothing there. *Verified by `git status libraries` being clean.*
- **No compatibility surface and no migration note.** Documentation only. The registered class names quoted into the pages are a compatibility surface being *described*, not changed; if one in the tree disagrees with what the published chapter said, report it in the handoff - that is evidence about the port, the same way a changed operator signature is. *Verified by the handoff naming any disagreement found.*
