## The one thing that is wrong

A stack slot owns the value in it, so whatever takes a value out of a slot releases it (`Stack.PokeOwned`, and `Stack.ReleaseAbove` at the end of a scope). A `foreach` loop variable is the single exception: the loop *lends* its slot the row or element the iterator owns and goes on reading that value, so an assignment to the loop variable inside the body must release nothing.

The engine gets that exception wrong at both ends of the loan, and both ends are the same decision - how a `foreach` borrows a slot it does not own:

- **It never hands the slot back.** The compiler marks the slot (`plan.Symbols.SetIsBorrowed`) and nothing ever unmarks it, so after the loop has finished - when the slot owns its value again, because nothing is pointing at it any more - every assignment to that variable still releases nothing.
- **It never pays for what it takes.** All three `foreach` runtime nodes lend the slot with the raw `Stack.Poke`, which does not release what it displaces, so starting a loop over a variable that already has a value orphans that value outright.

Both reach only the form that names a variable the enclosing block already declared - `foreach LB in ...`, not `foreach var LB in ...`. The allocating form pushes its own symbol and slot and pops both, so the mark dies with the symbol and the slot it displaces is the `null` it just pushed. Of the four `SetIsBorrowed` call sites in `Compiler.cs`, only the two non-allocating ones (`SetIsBorrowed(node.Location)`, at lines 1340 and 1435) can outlive their loop; the two allocating ones (`SetIsBorrowed(0)`) are correct as they stand. That answers the first of the three questions the fix ticket left open.

`bug-a-list-value-never-releases-its-elements` has landed, which is what this ticket was waiting for: the list branch of `foreach` now nulls the loop variable's slot on the way out, as the cursor branch always did, so the slot no longer holds a value the list owns and an ordinary owned assignment after the loop is the right thing. That was the second open question, and it is now measured rather than reasoned: **the slot is nil after every one of the four forms, on normal exit, after a `break`, and after a raise caught outside the loop.** The third question - whether a borrowed mark is ever wanted beyond the loop for some other reason - is no: `Symbol.IsBorrowed` has exactly one reader, `AssignmentNode.DetermineDataType`, and once the loop has nulled the slot there is nothing to protect.

## Measured

On `modernization` at `42383e93`, in-process server, reading `Diagnostics.StreamCount()` either side of each script through a throwaway fixture on `InProcessTestFixture` (added, run, removed; not in the tree). The count must come back to where it started. "Forms" below means the four the compiler can produce: the statement and the expression shape of `foreach`, each over a list and over a cursor.

### Arm 1 - the mark outlives the loop

| script | streams left behind |
|---|---:|
| `begin var LB : Binary; LB := Binary('0002'); LB := Binary('0003'); end;` (control, no loop) | 0 |
| statement form over a list, then 1 / 2 / 3 / 5 assignments | 0 / 1 / 2 / 4 |
| statement form over a cursor, then 2 assignments | 1 |
| expression form over a list, then 2 assignments | 1 |
| expression form over a cursor, then 2 assignments | 1 |
| statement form over a list inside a nested inner block, then 2 assignments in the outer block | 1 |
| statement form over a `var` parameter inside an operator body, then 2 assignments | 1 |
| the allocating form (`foreach var LE in ...`), then 2 assignments to a different variable | 0 |

*n* assignments after the loop leak *n* minus 1, because the slot is nil coming out of the loop and so the first assignment displaces nothing. The mark survives a nested block and an operator body, because it belongs to the symbol, not to the statement.

### Arm 2 - the loop orphans what the variable already held

| script | streams left behind |
|---|---:|
| `var LB : Binary := Binary('00FF'); foreach LB in { Binary('0001') } do begin end;` | 1 |
| the same over a three-element list | 1 |
| the same in the expression form | 1 |
| the same over a **nil** list | 0 |
| `var LR : row { B : Binary } := row { Binary('00FF') B }; foreach LR in cursor(table { row { Binary('0001') B } }) do begin end;` | 2 |
| the same with a row of three `Binary` columns | 6 |
| the same over an empty cursor (`... where false`) | 2 |
| the allocating form, with the same value held in a different variable | 0 (list) / 1 (cursor - see below) |

One orphan per loop, not per iteration: only the first lend displaces a value the slot owns, and the later ones displace elements the list owns. A nil source lends nothing and so orphans nothing.

**The cursor branch's two streams per stream-backed column are two different defects, one each.** Patching a release-before-lending into the cursor branch of `ForEachNode` experimentally halved those numbers - 2 to 1, and 6 to 3 - and the residual is exactly the cost of a second, unrelated defect found while measuring this one: **a cursor copies every stream-backed value on the stack when it opens and never gives the copies back**, one stream per such value per cursor opened, filed as `bug-a-cursor-copies-the-stack-and-never-gives-it-back`. It is not a prerequisite for this ticket and this ticket should not wait for it; it only means the cursor-branch reproduction below has to be written so that it does not depend on that other leak being gone.

### Why a release-before-lending needs a guard

Nested `foreach` loops over **one** variable are legal D4, run correctly today, and leak nothing:

| script | result |
|---|---|
| `foreach LB in {2 elements} do foreach LB in {2 elements} do ...` | 4 iterations, 0 streams left behind |
| the same over two cursors of two rows each | 4 iterations, 0 streams left behind |
| the outer loop reading `LB` after the inner loop has run | nil - the inner loop's exit nulls the slot the outer loop was lending |

The inner loop lends a slot the outer loop is already lending, and the value it displaces is an element the outer loop's list still owns. A release-before-lending with no guard would release it there - a double release, which is worse than the leak it is replacing. So the runtime has to know whether the slot it is about to lend is already borrowed, and the compiler is the only thing that knows: it reads the symbol's mark at the site, which is the same read arm 1 needs in order to restore it. That is why the two arms are one change and not two.

## The shape to build

One read at each of the two non-allocating compile sites serves both arms:

- Read `plan.Symbols.Peek(node.Location).IsBorrowed` **before** marking the slot. The site already peeks that symbol for its type check, so this is free.
- Keep that value on the node as a compile-time field - `_targetIsBorrowed`, the same name and shape `AssignmentNode` already uses, carried through `InternalClone` and not touched by `InternalBindingTraversal` (which never calls `DetermineDataType`, so a rebind cannot recompute it).
- Restore the flag to that value once the body has been compiled, in the `finally` that already runs there. Save-and-restore rather than clear: the inner of two loops over one variable must leave the mark set for the outer loop's body.
- At run time, once `stackIndex` is known and **before** the iteration begins - once per loop, never inside it - release the slot's current value unless the node's flag says the slot is already lent. `program.Stack.PokeOwned(stackIndex, null, program.ValueManager)` nulls the slot and releases what it held, and is a no-op on the `null` the allocating form has just pushed, so the call needs no allocating/non-allocating branch of its own.

This is the first of the two shapes the fix ticket sketched - release the displaced value, keep the lending model - and it costs one release per loop. The other shape (refuse to lend into a non-nil slot and copy the row or element instead) costs a copy per iteration and changes what the loop variable is; it is not worth that.

There are three copies of the lending code to change - `ForEachNode` in `ImperativeNodes.cs`, `ListForEachNode` and `TableForEachNode` in `ListNodes.cs` - the same forty lines three times over, each with a cursor branch and a list branch. `TableForEachNode` is unreachable today: `Compiler.CompileForEachExpression` always builds a `ListForEachNode` (`// TODO: Determine whether to use the TableForEachNode...`) and nothing in `src/`, `libraries/` or `tests/` names the class. Change it with its siblings anyway so the three copies stay in step, and say at the class that the compiler cannot reach it, pointing at `debt-ws12-hygiene-remainder` as the sweep that owns dead code - a future reader fixing two of three copies is the thing to prevent.

## What the tests have to say

Three behaviours, in `tests/DAE.Server.Tests/AssignmentValueOwnershipTest.cs`, beside the ownership cases that are already there; its class comment is the running account of this rule and needs the new cases added to it. `StreamValues.d4` already covers the nil loop variable, so no new D4 block is needed.

- **Assignments after a `foreach` release what they replace.** All four forms, several assignments each so that a per-assignment regression reports a count rather than an off-by-one, in one `Assert.Multiple` so that a form-specific regression is not hidden by another form's failure - the shape `AssigningToTheVariableOfAForEachOverACursorLeavesTheLoopIntact` already uses. Count back to baseline.
- **A `foreach` over a variable that already has a value releases it.** On the list branch, count back to baseline. On the cursor branch, **do not hard-code a residual**: run the same loop twice, once with the value in the loop variable's own slot and once with it in a second variable the loop never touches, and assert the two leave the same number of streams behind. Both carry the per-cursor snapshot cost of the other ticket, so the difference between them is this defect alone - and the case keeps passing, as nought equals nought, once that ticket lands.
- **Nested loops over one variable leave the outer loop's element alone.** The 2 by 2 shape above: four iterations, and the count back to baseline. This is the case a release-without-the-guard breaks, so it is the one to check in both directions - with the guard removed it must fail.

`AssigningToTheVariableOfAForEachOverACursorLeavesTheLoopIntact` must keep passing unchanged: an assignment to the loop variable *inside* the body still releases nothing, which is what the mark is for.

## Documentation to correct

Four places state the current behaviour as deliberate and will be wrong:

- `Symbols.SetIsBorrowed`'s remark - "There is no call that clears the mark ... the mark stands for the rest of the scope."
- `Symbol.IsBorrowed`'s remark, on where the mark is set and read.
- `AssignmentNode.InternalExecute`'s `NOTE:` - "What such an assignment displaces is leaked ... it is the foreach nodes that would have to stop lending a slot they go on reading to fix that, not this site ... the leak buys nothing but is not worth a copy per row to close." The foreach nodes are exactly what this ticket changes, and it closes the leak without a copy per row.
- The borrowed-slot paragraph in the container section of `docs/architecture/value-lifetime.md`, which describes the lend but not what happens to the value the slot already held. Run `python tools/docs-size-check/check_size.py` after editing it.

Adding a `SetIsBorrowed(int offset, bool value)` overload and leaving the existing one-argument form delegating to it keeps `Symbols` additive, so no `docs/migration-notes.md` entry is needed; changing the existing signature instead would need one. Nothing in this change is visible to a D4 script - the loop variable is nil after the loop either way, and the values released were unreachable - so there is no behavioural entry to write.
