## What this is

The second half of the plan's "the existing `Timing`/`Timings` scripts plus a small benchmark project record a baseline on .NET 10 so that later regressions are visible". `test-perf-timing-scripts` does the scripts; this adds the benchmark project and its numbers.

The two timing scripts measure the engine's interpreter and its in-memory table handling from inside an already-running server. Three costs they cannot show are the ones this project measures:

- **Engine start** — how long a server takes to come up, which is what every test, every tool invocation and every service restart pays.
- **A representative mix of database work** on the in-memory device — create a table, fill it, update it, read it back, delete from it, drop it — as one number that moves when the compiler or the memory device gets slower.
- **The catalog store, cold and warm** — the cost of the first start against a fresh SQLite catalog (the catalog is created and the system library registered) against a later start that loads an existing one. This is the number `research-catalog-load-profile` will build on; that work item is named inside `tickets/backlog/feat-ws14-research-precompilation.md` and is not yet a ticket of its own.

## Shape of the project

`tests/Dataphor.Benchmarks/`, assembly `DAE.Benchmarks`, an `Exe` on `net10.0`. `tests/TestHarness/DAE.Test.Harness.csproj` is the precedent to copy in every respect except its contents: a non-test program that lives under `tests/`, is listed in `Dataphor.slnx` under the `/tests/` folder so that it is compiled and type-checked by `dotnet build Dataphor.slnx` and by CI, and is deliberately absent from `tools/layout/Layout.csproj` because nothing ships it.

**In the solution, not outside it.** A benchmark project left out of `Dataphor.slnx` is never compiled by any command anyone runs, and rots inside a release. It is not a test project — no `Microsoft.NET.Test.Sdk`, no NUnit — so `dotnet test Dataphor.slnx` neither discovers nor runs it; set `<IsTestProject>false</IsTestProject>` so that stays true however the SDK's defaults change. Run it by hand.

References, following the harness project:

- `src/engine/DAE/DAE.csproj` and `src/engine/Server/Server.csproj` — the engine it starts.
- `src/engine/Store.SQLite/DAE.SQLite.csproj`, **not compiled against and not optional**: the server resolves its catalog store from a class name through `Type.GetType`, and on .NET 10 an assembly beside the executable that is not named in the executable's `.deps.json` cannot be loaded by simple name. Without the reference a server started here fails with error 115107. The harness project's csproj carries the same reference with the same comment.
- `tools/layout/Layout.csproj` with `ReferenceOutputAssembly="false" Private="false"` — so the runtime layout exists before this program runs and a benchmark never measures against a stale or missing layout, the way `DAE.Server.Tests.csproj` does it.
- `CoreWCF.NetTcp` as a `PackageReference` plus `<FrameworkReference Include="Microsoft.AspNetCore.App" />`. This is not optional either and it is not about hosting: a project that picks up `CoreWCF.NetTcp` only through a project reference reports the package-audit warning `NU1902` for its `Microsoft.AspNetCore.*` dependencies, and declaring the package directly lets NuGet's package-override substitute the in-box ASP.NET Core 10 assemblies. Both `DAE.Server.Tests.csproj` and the harness project carry this with the measurement recorded in `Server.Hosting.csproj`. Warnings stay visible in this repository and `NU1900`–`NU1904` may not be suppressed, so getting this right is the only way to a clean build.
- An `AssemblyMetadata` item recording `$(DataphorLayoutDir)`, as `DAE.Server.Tests.csproj` does, so that the program finds the layout's `Libraries/` folder without any path being spelled in code.

Add `BenchmarkDotNet` to `Directory.Packages.props` (versions live there; `PackageReference` items carry no version).

## Why BenchmarkDotNet, and how it has to be configured

BenchmarkDotNet earns its place for the statistics, the outlier handling and the exporters — the markdown export is what gets carried into `docs/perf-baseline.md`. Two of its defaults have to be changed, and both reasons are worth knowing before any code is written.

**Use an in-process toolchain (`InProcessNoEmitToolchain`).** By default BenchmarkDotNet generates a project per benchmark and builds it with the SDK. A generated project under this repository's tree inherits `Directory.Build.props`, which switches the SDK's default compile items **off** (because uncompiled files sit beside compiled ones in this codebase) and redirects `ArtifactsPath` — so the generated project compiles nothing and the run fails in a way that looks like a BenchmarkDotNet bug. An in-process toolchain generates and builds nothing, which sidesteps that entirely. It also costs nothing here: every iteration starts a Dataphor engine, so process-level isolation buys little, and the engine has process-wide static state in any case (see below).

**Use `RunStrategy.Monitoring` with a small, explicit iteration count** (one warmup, a handful of iterations, `InvocationCount` and `UnrollFactor` both 1). BenchmarkDotNet's default job is built for operations measured in microseconds: it runs a pilot to find how many invocations fit in a time slice, then many warmup and measurement iterations. Against an operation that costs seconds — starting a server is seconds — the default job would run for a very long time and tell you nothing extra. State the chosen counts as constants with this reasoning beside them.

Judge the total wall clock against the rule in the root `AGENTS.md`: anything that routinely needs more than about ten minutes is not agent-runnable and has to be documented as a run-by-hand step rather than attempted inside a ticket. Measure what the run actually costs and say so in the project's `README.md` and in `docs/perf-baseline.md`.

## Starting servers from the benchmark

The benchmark needs what the test suite's `TestServerInstance` provides: a fresh temporary directory, a copy of the library folders it needs taken from the runtime layout, an instance directory of its own, and the SQLite catalog store. **Write a small helper of its own, `BenchmarkServerInstance`, rather than referencing `tests/DAE.Server.Tests`.** Referencing the test project would drag NUnit and the test SDK into a console program, and the two types the benchmark would want (`TestServerInstance` and `TestEnvironment`) call `TestContext.Progress` on their cleanup and keep-files paths, which is not a thing a program outside an NUnit run can rely on. The helper is on the order of eighty lines and reads its layout directory from this project's own `AssemblyMetadata`, so nothing is shared and nothing is fragile.

Leave an accepted-tradeoff `NOTE:` at the helper recording that it duplicates part of `TestServerInstance` on purpose, why, and the revisit condition: if a third consumer appears, extract the instance helpers into a small support project that both the tests and this program reference.

Two things the helper must get right:

- **Never point a server at the layout or at the repository.** A running server writes into its library directory — it creates `General/` and may rewrite `.d4l` files — so each instance gets a *copy* of the library folders it needs. This is the rule in the root `AGENTS.md` under *Rules that are easy to break*, and the whole suite follows it.
- **Hand the process its object-id counter back after each instance.** Starting an engine sets the engine's process-wide object-id counter from that engine's own catalog (`bug-object-id-counter-is-process-wide`), so a program that starts dozens of engines in one process leaves later ones allocating ids an earlier catalog already holds. `TestEnvironment.WithTheObjectIDCounterRestored` documents the problem and the fix — read it and do the same thing here, with `Schema.Object.GetNextObjectID` and `SetNextObjectID`.

Also set logging off on every instance. A logging server in an elevated process creates the Windows event-log source `Dataphor Server` and writes to the event log; CI runners are elevated, and a benchmark has no business doing that.

## The three measurements

Four benchmark methods, because the catalog store scenario is naturally two:

- **`EngineStart`** — per iteration: a fresh instance directory with a copy of the minimum set of library folders, `Start()`, `Stop()`. Measures the whole cost of coming up, including registering the system library on a new catalog. This overlaps the cold catalog case below, deliberately: one is the number someone asks about when a test run feels slow, the other is the number someone asks about when the store is the suspect.
- **`DdlDmlMix`** — per iteration, on a server started outside the measured region: create a table on the in-memory device, insert a fixed number of rows (state the number — a thousand is a reasonable start, and it must be a named constant, not a literal buried in a D4 string), update them, read them back through a cursor, delete them, drop the table. One number for a mix, not six numbers for six operations: the point is a tripwire, and `Timings` already measures the individual table operations at 10,000 rows.
- **`CatalogStoreCold`** — per iteration: a server started on a *new* instance directory, so the SQLite catalog is created and written, then stopped. This is the store's write path.
- **`CatalogStoreWarm`** — per iteration: a server started on an instance directory that a previous start already populated, then stopped. This is the store's read path, and it is the one `research-catalog-load-profile` extends to realistic catalogs. The populated directory is set up outside the measured region and must be restored between iterations if a start changes it.

Each iteration gets its own instance, as above: sharing one across iterations would measure a warm engine in one iteration and a cold one in the next.

## Publishing the numbers

`docs/perf-baseline.md` already exists after `test-perf-timing-scripts`, with a hand-written head and the timing scripts' numbers. Add a section for these four, in the same shape and with the same cautions: the configuration (Release — a benchmark on a Debug build measures the wrong thing, and the timing-script numbers in the same document are Debug, so say which is which for every table), the machine class, what else was running, and the date.

Carry BenchmarkDotNet's markdown export in by hand, as `docs/coverage-report.md` carries the coverage tool's output in by hand. Say in the document how to regenerate it — the exact command, and that the export lands under `BenchmarkDotNet.Artifacts/` beside the working directory, which must not be committed. Check `.gitignore` covers it; `artifacts/` is ignored but BenchmarkDotNet's own folder is not, so either point its artifacts path inside `artifacts/` (preferable — then nothing new is ignored) or add the folder to `.gitignore` with a reason.

Write a `README.md` in the project folder: what it measures, how to run it, why it is in-process, why `RunStrategy.Monitoring`, what a run costs in wall clock, and the fact that `dotnet test` does not run it.

**No migration note.** A benchmark program changes no public type or member, no D4 semantics, no file format and no contract, and nothing ships it.

## Edge cases & interactions

- **The generated-project trap is the likeliest way this ticket goes wrong.** If a run fails with a compile error inside BenchmarkDotNet's generated project, the cause is this repository's `Directory.Build.props`, not the benchmark code; the in-process toolchain is the fix, and it should be in place from the first commit rather than discovered. Verified by the run itself succeeding.
- **`NU1902` on the first build.** Expected if the `CoreWCF.NetTcp` package reference and the framework reference are missing, and it may not be suppressed. Verified by a clean `dotnet build Dataphor.slnx` with no new warning.
- **Engine static state across iterations.** The object-id counter is the known one and is handled above; the catalog emitter and the keyword tables were the other two and are fixed (`port-catalog-emitter-race`). If a later iteration fails where the first succeeded, suspect shared state before suspecting the benchmark. Verified by the run: every iteration of every benchmark must succeed, and a run where the first iteration is much cheaper than the rest (or the reverse) is a finding to report, not a number to publish.
- **Temporary directories and mapped assemblies.** A library assembly loaded from an instance's copy stays mapped until the process exits, so a directory holding one cannot be deleted during the run. The suite's answer is to sweep stale directories on the next run; this program should delete what it can, ignore what it cannot, and put its directories somewhere a sweep will find them rather than leaving them in the repository or the working directory.
- **Release versus Debug.** The timing scripts' numbers in the same document come from a Debug test run and these come from Release. They are not comparable with each other and must never be put in one table.
- **Wall clock of the whole run.** If the four benchmarks together need more than about ten minutes, the run is a documented by-hand step and not something a later ticket should put in CI. Measure it and say so.
- **Nothing in CI.** This project is built by CI and run by nobody automatically. That is the intended state: say it in the `README.md` so the next reader does not take the absence for an oversight.
- **A representative mix is a judgement, and the judgement must be visible.** Put the D4 the `DdlDmlMix` benchmark runs in one place, named, with a sentence on why those operations — so that the next person to change it can see what the baseline numbers were measured against. A silent change to the mix invalidates every recorded number.
