## The question, and the answer

Before the port, a client that vanished — a crashed process, a pulled cable, a workstation switched off — was eventually noticed because the server's remote objects were .NET Remoting objects with leases, and a lease nobody renewed let the object go. `server-remove-remoting-and-dtc` removed all of that (known defect K6: the lease calls throw on .NET 10) and kept `MarshalByRefObject` as an inert base class. The plan has carried "what reclaims an abandoned session now" as an open design point ever since. This ticket closes it.

**The answer is the idle reaper that is already there, with the client ping as its liveness signal, corrected and pinned by a test.** It is not the network channel, and it must not be. `ClientServer` keeps one channel per client and silently builds a new one whenever the old one faults (`GetServiceInterface`, `ChannelFaulted` in `src/protocol/Client/Client/ClientServer.cs`), while on the server one `DataphorService` singleton serves every caller and every object is reached through an integer in a flat handle table (`InstanceContextMode.Single` on `DataphorService`; `src/engine/Server/Service/HandleManager.cs`). Nothing associates a channel with a connection, by design: that is what lets a client survive a network blip and keep using its handles. Reclaiming a client's work when its channel drops would turn every transient disconnection into lost work, and it would be a protocol change. The binding makes the point moot anyway — `ReceiveTimeout` is `TimeSpan.MaxValue` (`DataphorServiceUtility.DefaultBuildBinding`), so an idle or half-open connection is never timed out underneath us, and a TCP connection whose peer has been powered off is not noticed at all without keep-alives the transport does not configure.

So the mechanism is: the client says "still here" on an interval, the server reclaims whatever has not said it for long enough. `port-connection-keepalive` fixes the client half (the ping follows the connection rather than a session). This ticket fixes and proves the server half.

## What is there now, established by reading the code

`ConnectionManager` (`src/engine/Server/Service/ConnectionManager.cs`), constructed by `DataphorService`, runs a background thread that wakes every 300 seconds and relinquishes every `RemoteServerConnection` whose `LastActivityTime` is older than 300 seconds. `RemoteServer.Relinquish` closes the connection's sessions, disowns it and disposes it. Each session's disposal runs `ServerSession.StopProcesses`, which aborts each process's executing thread through `Engine.TerminateProcessThread` and then disposes the process; `ServerProcess.Dispose` rolls back every active transaction before unpreparing deferred constraint checks (`src/engine/DAE/Server/ServerProcess.cs`, about line 114). The chain is complete on paper, and four things about it needed establishing. All four were checked by reading the code; what the test establishes is listed separately below.

- **`LastActivityTime` is a last-*ping* time.** `RemoteServerConnection` sets it in its constructor and then only in `Ping()`; no ordinary operation touches it, and no ordinary operation *can* without new plumbing — the handle table is flat and `RemoteServerSession` holds a reference to the `RemoteServer`, not to the connection it belongs to, so there is no handle-to-connection path to stamp. This is why the client's ping is the signal and why `port-connection-keepalive` matters.
- **A long single call is not at risk** so long as a session is open, because the client pings from its own thread while the call is in flight. A client that does not ping is reclaimed whatever it is doing; that is the protocol, and the `Ping` operation is part of the service contract. Say so plainly in the documentation rather than pretending activity is tracked.
- **The reclamation bound is 300 to 600 seconds, not 300.** The wake period and the idle threshold are the same constant, so a connection that goes quiet just after a wake is reclaimed at the second wake after it crosses the threshold. That matters because of the next point.
- **Reclaiming a connection is not safe against being done twice.** `RemoteServerConnection` has a `_disposed` field that is written and never read, and `Dispose` is not guarded: a second disposal dereferences the `_sessions` and `_server` fields it nulled on the first and raises a `NullReferenceException`. So the reaper and a client's own `CloseConnection` arriving together, or the reaper and `RemoteServer.CloseConnections` at shutdown, produce an exception instead of a no-op. The shutdown race is real: `ConnectionManager.Dispose` only signals its thread and never waits for it, so a sweep in flight can still be running while `DataphorServiceHost.Stop` goes on to dispose the `RemoteServer` — and a sweep that then reads `_remoteServer.Server`, which is null after that disposal, raises inside its own logging call, is swallowed by the outer `catch`, and silently kills the watcher thread.

## Decisions this ticket makes

**The idle threshold stays at 300 seconds, and no instance-configuration setting is added for it.** Three reasons, and they should be written down where the next person asks. It is 3.1's value and this is a port. Its usable range is narrow in a way that is easy to get wrong: the floor is the shipped client's keep-alive interval (120 seconds, a constant compiled into the client), so an operator who sets 60 quietly starts killing live sessions, and the only honest setting would need a validated floor and a paragraph explaining the relationship. And the thing that actually needed a shorter interval — a deterministic test — is better served by injecting the value than by exposing it. Record the condition under which to revisit as a `NOTE:` at the site: *if a deployment reports schema changes blocked for minutes by vanished clients, the next step is an instance-configuration setting with a floor above the client's keep-alive interval, which is an additive `[DefaultValue]` property on `ServerConfiguration` plus the user-guide section and a migration note.* That is a tripwire, not a ticket.

**Shortening the DDL-lock window by making the reaper aware of the catalog store's write lock is rejected.** It would mean the service layer asking the catalog device session which connection holds the store transaction — a new coupling across two subsystems for a case whose real remedy is the client pinging properly and transactions that change the catalog being short. The remedy stays what `store-sqlite-concurrency` already documents.

**The wake period is separated from the idle threshold**, at a quarter of it with a one-second floor. The threshold nobody depends on changes; the bound on reclamation becomes 300 to 375 seconds instead of 300 to 600, which is the difference between a vanished client blocking other people's schema changes for up to five minutes and for up to ten. The cost is four wakeups an hour instead of one, each an array copy under the server's lock and one `DateTime` comparison per connection. This is an operator-visible timing change and needs a `docs/migration-notes.md` entry.

**Reclamation becomes idempotent rather than coordinated.** Barring the reaper from touching a connection with a call in flight would need the same handle-to-connection plumbing that does not exist. The cheaper and better answer is that reclaiming a connection twice, or while a call is in flight, is defined: the second attempt does nothing, and an in-flight call sees its process aborted and its handles withdrawn, which is already how the existing machinery behaves — `Engine.TerminateProcessThread` aborts the executing thread (waiting up to half of `Engine.ProcessTerminationTimeout`, 15 seconds by default, and logging `ProcessNotResponding` if the thread will not stop), and `HandleManager` withdraws each handle from its `Disposed` event, so a later call on a reclaimed handle raises the service's unknown-object-handle error rather than reaching a disposed object. Nothing in the handle table is corrupted. Verify that reading rather than assuming it, and say so in the handoff.

**The test lives in process, at the `RemoteServer` plus `ConnectionManager` layer.** It needs no WCF host: what is under test is the server's reclamation, and the lowest layer that shows it is the one the project rules ask for. The across-a-process-boundary case — a real client process killed outright — belongs to `test-client-server`, which this ticket does not duplicate; its ticket has been amended to say so.

## What to build

**`ConnectionManager`.**

- Separate the wake period from the idle threshold: keep `public const int IdleTimeInSeconds = 300` as the default (a public constant; leave it alone), hold the threshold in an instance field, and wake every `Math.Max(1, idle / 4)` seconds. Put the resulting bound in the class remarks: between the threshold and the threshold plus one wake period.
- Add `public ConnectionManager(RemoteServer remoteServer, int idleTimeInSeconds)`, with the existing constructor delegating to it. Additive, and needed by the test; refuse a value below one second. A migration-note entry covers it.
- Pull the sweep into one non-public method that takes the cutoff, so the thread body is a call to it. Do not make it public: nothing outside needs to force a sweep, and the test drives the real thread through a short threshold.
- Make the sweep survive a server that has stopped: take the `Server` reference once, skip the sweep when it is gone, and keep the per-connection `catch` from depending on it. The watcher thread must not die silently because the server it was logging to has been disposed.
- Make `Dispose` wait for the watcher, bounded (ten seconds is the right order; `NetTcpServiceHost.StopTimeout` is the nearby precedent), and make it idempotent. The thread stays a background thread, so the bounded wait cannot hold the process open — keep the `NOTE:` that explains why it is a background thread, and amend it: it no longer says this class may be reworked, because it has been. `DataphorService.Dispose` already runs before `RemoteServer.Dispose` in `DataphorServiceHost.Stop`, so with the wait in place a sweep can no longer overlap the server's teardown; state that ordering dependency in a comment at the `Dispose` site, because it is what makes the wait sufficient.

**`RemoteServerConnection`.** Guard `Dispose(bool)` on the existing `_disposed` field so a second disposal does nothing at all, including not re-raising `Disposed`. Correct the `LastActivityTime` documentation: it is the time of the last ping, the client is what moves it, and the reaper is what reads it.

**`RemoteServer`.** `Relinquish` should tolerate being handed a connection that has already been relinquished (which the guard above makes true once the collection no longer holds it), and should raise a typed server error rather than a `NullReferenceException` when handed something that is not a `RemoteServerConnection` — it casts with `as` and dereferences without checking. Keep `CloseSessions` outside the server's lock, as it is: closing sessions can take as long as a process termination and must not hold up `Establish` for every other client.

## The test this owes

One new fixture, `tests/DAE.Server.Tests/AbandonedSessionCleanupTest.cs`. `tests/DAE.Server.Tests/CatalogStoreConcurrencyTest.cs` is the template for the store-lock mechanics — `BusyAtTransactionStartLeavesNoTransaction` (about line 147) shows how to shorten the busy timeout, and `LongDDLTransactionBlocksOnlyWriters` shows the shape of "one session holds the write lock, another is blocked".

**`AnAbandonedTransactionIsRolledBackAndTheCatalogWriteLockReleased`** — the characterization test the plan and the WS5 test-layer table both ask for. Order matters, because the reaper reclaims on a clock:

1. A `TestServerInstance` whose catalog store connection string carries `;BusyTimeout=1000`, set before the server starts, as `CatalogStoreConcurrencyTest` does.
2. A `RemoteServer` over `instance.Server`. Establish connection A, connect a session on it, start a process, begin an explicit transaction and run `create table` — which takes the catalog store's write transaction and holds it until the transaction ends. **No `ConnectionManager` yet.**
3. An ordinary in-process session (`instance.Connect()`) runs its own `create table` and must fail with `StoreException` 130103 after about the busy timeout. Assert the error code — this is what establishes that the lock is genuinely held, so the final assertion means something. Dispose that session.
4. Now construct `new ConnectionManager(remoteServer, 1)`. Connection A has never been pinged, so it is reclaimed on the watcher's first wake.
5. Wait, bounded (thirty seconds is generous; expect one to two), for a fresh in-process session's `create table` to succeed, retrying on 130103 only. Fail with a message saying how long it waited. Report the observed time in the handoff.
6. Assert the abandoned work was rolled back, not committed: the table A created does not resolve, and the table created in step 5 does. Mind what `bug-ddl-rollback-keeps-cached-plans` records — a rolled-back create leaves cached plans behind — and follow `TransactionReadsItsOwnStoreWrites`, which checks with expression text not compiled inside the transaction.
7. Assert a call on A's process now fails rather than reaching a disposed object.

For step 2, the straightforward route is the remote CLI directly: `RemoteServer.Establish`, `RemoteServerConnection.Connect`, `IRemoteServerSession.StartProcess`, then `Execute` with `ProcessCallInfo.Empty` and empty parameter and cleanup structures (`DataphorService.GetRemoteProcessCleanupInfo` shows how the service builds the latter). If that plumbing proves awkward, build A through a `LocalServer` over the same `RemoteServer` instead, which gives an ordinary `IServerProcess` at the cost of a second engine and the object-id counter workaround (`bug-object-id-counter-is-process-wide`; `CoreWcfProtocolTest.WithTheObjectIDCounterRestored`, about line 753). Either is acceptable — say in the handoff which was used and why. **If the `LocalServer` route is taken, connection A will be pinged and never reclaimed**, which is exactly what `port-connection-keepalive` landed: that client keeps its connection alive for as long as it holds it, with no session open and whether or not individual pings fail — both confirmed by test in its review. So the `LocalServer` route needs the ping out of the way: construct it with a keep-alive interval longer than the test will run (the fourth constructor argument, `LocalServer(IRemoteServer, bool, string, int)`, accepts up to 2,147,483 seconds). The remote CLI route pings only if you call `Ping` yourself, and is the simpler choice for that reason.

**`RelinquishingAConnectionTwiceDoesNothing`** — the reproduction for the double-reclamation defect. Establish a connection on a `RemoteServer`, relinquish it, relinquish it again, and assert the second call completes. No timing. Fails with a `NullReferenceException` on the current code; confirm that before the fix.

Nothing else is owed. The watcher's wake arithmetic is exercised by the first test; the `Dispose` wait, the stopped-server guard and the typed error for a foreign connection are each a guard with no branching behaviour of its own and are verified by inspection — say so rather than adding a test per guard.

## Edge cases and interactions

| Case | How it is verified |
|---|---|
| Abandoned explicit transaction holding the catalog store write lock | The first test |
| Reclaiming a connection twice | The second test |
| Reclaiming a connection with a call in flight | By inspection, written up: the process's thread is aborted by `Engine.TerminateProcessThread`, the handle is withdrawn by `HandleManager`'s `Disposed` hook, and the next call on it raises the unknown-object-handle error. Confirm each of the three by reading the code and state it in the handoff |
| A process that will not stop when aborted | By inspection: `TerminateProcessThread` waits half of `Engine.ProcessTerminationTimeout` and then raises `ProcessNotResponding`, which `ServerSession.StopProcesses` logs before disposing the process anyway. Note the consequence — the sweep is serial, so one wedged process delays every other connection's reclamation by up to that wait — as a `NOTE:` at the sweep |
| Rollback running on the reaper's thread rather than the thread that opened the transaction | The first test exercises exactly this; if it turns out the store or the device session objects to it, that is a finding to report, not something to work around in the test |
| A connection with no session, never pinged | Reclaimed, correctly. It is `port-connection-keepalive` that stops a *live* client being in that state |
| Reaper versus shutdown | By inspection, after the bounded wait in `Dispose` and the ordering comment; the stopped-server guard covers what remains |
| A connection established while a sweep is running | By inspection: `GetCurrentConnections` and `Establish` both take the server's lock, and a connection established after the snapshot is simply not in it |
| Sessions reached through the native CLI | **Not covered by this mechanism at all** — see *Out of scope* |
| Application transactions on an abandoned process | By inspection: `ServerProcess.Dispose` leaves the application transaction before rolling back (`InternalLeaveApplicationTransaction`), which is pre-existing behaviour this ticket does not change |

## Out of scope, and handed on

- **Native CLI sessions are not reclaimed by anything.** `NativeServer` keeps its sessions in a dictionary keyed by a GUID with no liveness tracking, no idle sweep and no ping in `INativeCLIService`, so a native client — including another Dataphor server connected through a server link — that dies inside a transaction leaves that transaction, and the catalog store write lock if it has changed the catalog, held until the server is stopped. Pre-existing and not a port consequence (nothing there was ever leased), and the fix is a new liveness scheme rather than a local correction, so it is filed as `bug-native-cli-sessions-never-reclaimed` in `backlog/`. Do not fix it here; do mention it in the write-up, because a reader of "what reclaims an abandoned session" needs to know which door is still open.
- **The client process actually dying**, as opposed to a connection going quiet, belongs to `test-client-server` across a process boundary. Its ticket records the split.
- `port-server-on-net10` closes out WS2 after this and is an audit, not a place to defer findings to.
