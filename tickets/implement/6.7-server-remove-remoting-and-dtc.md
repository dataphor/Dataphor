# Remove remoting lifetimes (K6) and the DTC transaction class (K11)

First half of `build-server-project`, split off because both changes are source deletions that the spike can already build and run today (the server is still a legacy project wrapped by the spike, compiled against `tools/net-spike/stubs/Server.cs`). After this ticket the only stubs left for the server are the WCF hosting types, which `build-server-project` removes by leaving those files out of compilation. K-numbers refer to the known-defects table in plan Appendix A.

Do not convert any project to SDK style here. `src/engine/Server/Server.csproj` stays legacy; edit its `Compile` list only to drop the deleted file.

## K6: .NET Remoting lifetime, tracking and sponsor code

On .NET 10, `GetLifetimeService`, `InitializeLifetimeService` and `RemotingServices.Disconnect` throw `PlatformNotSupportedException`, and the `System.Runtime.Remoting.*` namespaces other than the base `MarshalByRefObject` do not exist. In-process, nothing marshals these objects; under WCF (the protocol since 2009) the remoting lease and tracking paths were already dead. Remove:

- `src/engine/Server/Server/RemoteServerObject.cs`: the `using System.Runtime.Remoting*` lines, the constant `LeaseManagerPollTimeSeconds`, the static constructor (it sets `LifetimeServices` lease times), and the `finally` blocks in `RemoteServerObject.Dispose(bool)` and `RemoteServerChildObject.Dispose(bool)` that cancel the lease and call `RemotingServices.Disconnect`. `Dispose` keeps calling `DoDispose()` (which raises `Disposed`); drop the now-empty `try`/`finally`. Leave the `using System.Reflection` only if something else still needs it.
- `src/engine/Server/Server/RemoteServer.cs`: the `using` lines for `System.EnterpriseServices` (~15, unused), `Remoting = System.Runtime.Remoting` (~19), `System.Runtime.Remoting.Lifetime` (~20) and `System.Runtime.Remoting.Services` (~21); `ITrackingHandler` from the class declaration (~42); `TrackingServices.RegisterTrackingHandler` in the constructor (~50) and `UnregisterTrackingHandler` in `Dispose` (~94; keep the `finally { base.Dispose(disposing); }`); `DisconnectedObject`, `DisposeConnection`, `UnmarshaledObject` and `MarshaledObject` (~237–287). `DisconnectedObject` was how a remoting client's abandoned connection got disposed; what replaces that under WCF is `port-abandoned-session-cleanup`'s job, not this ticket's.
- `src/engine/Server/Server/RemoteServerConnection.cs`: `using System.Runtime.Remoting.Lifetime` (~11), the `InitializeLifetimeService` override and the constants `InitialLeaseTimeSeconds` / `RenewOnCallTimeSeconds` (~133–153, the "Lifetime Management" region; keep `LastActivityTime` and `Ping`, which are not remoting).
- `src/engine/Server/Streams/FileStreamProvider.cs`: `using System.Runtime.Remoting.Lifetime` (~11), `ISponsor` from `FileStreamHeader`'s base list (~15) and the explicit `ISponsor.Renewal` (~41–45).
- `src/engine/Server/Runtime.Instructions/SecurityNodes.cs:10`: the unused `using System.Runtime.Remoting.Messaging;`.

**Decision: keep `MarshalByRefObject`** as the base of `RemoteServerObject` and `RemoteServerChildObject`. It still exists on .NET 10 with no behaviour, removing it changes a public type hierarchy that custom extensions could see, and nothing gains from removing it now. `src/engine/DAE/Server/Engine.cs:35` and the `IPing` comment in `src/engine/DAE/Contracts/RemoteCLI.cs` stay as they are.

Two files outside the server mention remoting but are not compiled (`src/engine/DAE/Runtime.Instructions/GeneratorNodes.cs` is not in `DAE.csproj`; `libraries/Frontend/Source/Application.cs` is not in `Frontend.Server.csproj`). Leave them; the "no compiled source references remoting" check below is over compiled files only.

## K11: distributed (DTC) transactions

`ServerProcess.InternalBeginTransaction` (`src/engine/DAE/Server/ServerProcess.cs` ~1263) creates `ServerDTCTransaction` by reflection under the assembly name `Alphora.Dataphor.DAE.Server`, which does not exist (the server assembly is `AlphoraDataphorServer`). `Type.GetType` returns null, `Activator.CreateInstance(null)` throws `ArgumentNullException`, and the class does not implement `IServerDTCTransaction` anyway. So every transaction begun with `UseDTC` set has failed since the 2009 engine/server split. The flag still reaches it from:

- D4: `update System.Processes set { UseDTC := true } where ID = ProcessID()` → `ServerCatalogDeviceSession.UpdateProcesses` (~2561) → the `ServerProcess.UseDTC` setter.
- D4: `update System.Sessions set { DefaultUseDTC := true } where ID = SessionID()` → `ServerCatalogDeviceSession.UpdateSessions` (~2524) → `SessionInfo.DefaultUseDTC`; every process started afterwards on that session copies it into `ProcessInfo.UseDTC` (`src/engine/DAE/SessionInfo.cs` ~305).
- API: `ProcessInfo.UseDTC` / `SessionInfo.DefaultUseDTC` passed to `Connect`/`StartProcess` (in-process, NativeCLI, WCF), and server links via the metadata tag `DefaultUseDTC` (`src/engine/Server/Server/RemoteSessionImplementation.cs` ~118). These never go through a setter that can check; the failure surfaces at the next `BeginTransaction`.

Changes:

- Delete `src/engine/Server/Server/ServerDTCTransaction.cs` and its `Compile` entry in `src/engine/Server/Server.csproj` (legacy file: UTF-8 with BOM, CRLF — preserve).
- Delete `src/engine/DAE/Server/IServerDTCTransaction.cs` (public, implemented by nothing) and its entry in `src/engine/DAE/DAE.csproj`.
- `ServerProcess`: delete the `_dTCTransaction` field (~1112) and the DTC blocks in `InternalBeginTransaction` (~1265–1270), commit (~1326–1337) and rollback (~1376–1386); keep the non-DTC logic of those methods exactly as it is (read each block before cutting: the commit/rollback ones are nested inside the `_transactions.Count == 1` handling).
- `ServerProcess.UseDTC` setter: inside the lock, **first** `if (value) throw new ServerException(ServerException.Codes.DTCNotSupported);`, then the existing `InTransaction` check, then the assignment. The order matters: every D4 statement runs inside an implicit transaction (`BeginTransactionalCall`, ~1828, with `UseImplicitTransactions` defaulting to true), and the coverage runner executes each script inside an outer `ExecuteScript` call, so a D4 `update System.Processes` always reaches the setter with `InTransaction` true. With the old order a D4 user got `TransactionActive`, which is misleading. Drop the `Environment.OSVersion.Version.Major < 5` test. Setting `false` behaves as before.
- `ServerProcess.InternalBeginTransaction`: as its first statement, before `_transactions.BeginTransaction`, `if (UseDTC) throw new ServerException(ServerException.Codes.DTCNotSupported);`. This is the backstop for the API and session-default paths; raising before any state changes means `BeginTransactionalCall`'s `catch { EndCall(); throw; }` leaves the process as it was.
- `ServerCatalogDeviceSession.UpdateSessions` (~2524): when the new `DefaultUseDTC` is true, throw `DTCNotSupported` instead of assigning, so the D4 user gets the error at the `update` rather than at every later process. False keeps assigning.
- Do **not** touch the `UseDTC`/`DefaultUseDTC` properties on `ProcessInfo`/`SessionInfo`, the WCF data-contract members, `RemoteSessionImplementation`, or the `UseDTC`/`DefaultUseDTC` columns of `System.Processes`/`System.Sessions` in `src/engine/DAE/Schema/SystemCatalog.d4`. They are compatibility surfaces; `false` must keep working everywhere.
- Error code — **decision: reuse `ServerException.Codes.DTCNotSupported` (106119)**, already in `src/engine/DAE/Server/ServerException.cs:75` and already this exception's meaning. Reword its message in `src/engine/DAE/Server/ServerException.resx` (`<data name="106119">`; ASCII, CRLF) to: `Distributed transactions (UseDTC) are not supported.` The code number is the compatibility surface and stays; the old text ("…only available on Windows 2000 or later") would now be false. A new code would leave 106119 orphaned for no gain.
- Remove the DTC sentences from the "DAE Server Transaction Management" comment in `src/engine/DAE/Server/Engine.cs` (~51–56): keep the description of the DAE as an optimistic two-phase commit coordinator and drop the parts about the DTC and simulated nesting under it.
- `src/engine/DAE/SessionInfo.cs`: leave the `DefaultUseDTC`/`UseDTC` summaries and `Description` attributes unless one claims DTC works; if so, append "Not supported; setting it to true raises an error." Keep the file's BOM and line endings.
- User documentation: `docs/users-guide/process-defaults.md` (the `DefaultUseDTC` section, ~47–51) and `docs/developers-guide/modeling-process-logic.md` (~777): say that the setting exists for compatibility, must be false, and that true raises error 106119; the Dataphor Server coordinates distributed transactions itself. If you change a link, run `python tools/docs-link-check/check_links.py` as its README describes (you should not need to).

## Characterization test

New script `tests/libraries/TestFramework.Coverage.Scripts/Documents/DistributedTransactions.d4` (documents are discovered from the folder; the `.d4l` needs no change). Match the neighbouring scripts' style (tabs, CRLF, no BOM — check one neighbour with `file`). It asserts, each in its own `begin … end` block with the `try … except on E : Error do` pattern and `raise Error('…')` on mismatch (see `Exceptions.d4` for reading `.Code`):

- `update System.Processes set { UseDTC := true } where ID = ProcessID();` raises an error whose code is 106119; afterwards `System.Processes where ID = ProcessID()` still shows `UseDTC = false`.
- `update System.Processes set { UseDTC := false } where ID = ProcessID();` succeeds.
- `update System.Sessions set { DefaultUseDTC := true } where ID = SessionID();` raises 106119; `DefaultUseDTC` stays false; setting it to false succeeds.

The error may arrive wrapped by the catalog device's update path. Run it first and look at what D4 sees: if the top-level `E.Code` is not 106119, assert that 106119 is the code of `E` or of `E.InnerError` (whichever the engine produces — write the assertion for what you observe and say in a comment which layer wraps it). The script must fail if the error is missing or carries another code (in particular 106116, `TransactionActive`, which is what the old setter order produced).

Wire it into `tests/DAE.Server.Tests/CoverageTest.cs` as `[Test] public void ExecuteDistributedTransactions() { ExecuteScript("Coverage.Scripts", "DistributedTransactions"); }` next to the other transaction tests (UTF-8 BOM, CRLF — preserve). The spike's coverage runner parses that file, so this is what makes the spike run it; `test-harness-inprocess` will find it the same way.

The API path (`ProcessInfo.UseDTC = true` at `StartProcess`) has no D4 surface; verify it by inspection (the backstop in `InternalBeginTransaction`). A C# test for it belongs to the harness tickets, not here.

## Edge cases & interactions

- Setter order inside a transaction: D4 `update … UseDTC := true` must give 106119, not `TransactionActive` — covered by the test.
- `UseDTC := true` fails, then the script continues: the process must not be left with `UseDTC` true (the exception is thrown before assignment) — covered by the test's follow-up read.
- A process started with `UseDTC` true via the API: first `BeginTransactionalCall` throws 106119 before `_transactions.BeginTransaction`; `EndCall` runs in the `catch`; the process stays usable once the flag is cleared (by inspection).
- Commit/rollback paths with the DTC blocks removed: the `_transactions.Count == 1` branches must still prepare/commit/rollback device and remote sessions exactly as before — by inspection, and the spike's smoke and coverage runs exercise them heavily.
- `RemoteServer` disposal without the tracking handler: `Dispose(bool)` still closes connections and detaches from the server (by inspection; the in-process smoke run does not construct `RemoteServer`, so a hosted test is `test-client-server`'s).
- `RemoteServerChildObjects` relies on `Disposed` being raised from `Dispose` to disown children: keep `DoDispose()` on every path.
- Server links (`ServerLink`, `RemoteSessionImplementation`): a link whose metadata sets `DefaultUseDTC = true` now fails at the remote process's first transaction with 106119 rather than `ArgumentNullException` (by inspection; `ServerLink.d4` coverage stays as it was).
