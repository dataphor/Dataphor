## What this is

The first of four tickets for the PostgreSQL work item (decision D15: the PostgreSQL device has users and is to be made to work again). This one is the bottom layer and nothing else: the connection library.

`libraries/PGSQLConnection` is small - `PostgreSQLConnection.cs` (56 lines) and `PostgreSQLCommand.cs` (96 lines) over `DotNetConnection`/`DotNetCommand`, plus `Register.cs` registering the one class alias `PostgreSQLConnection.PostgreSQLConnection`. What makes it a ticket of its own is what it builds against: `external/Npgsql.dll` version 2.0.4 and `external/Mono.Security.dll` version 2.0, two checked-in binaries from about 2009, referenced by `HintPath` from a .NET Framework project file that is not in `Dataphor.slnx`. `PGSQLConnection.d4l` lists both DLLs as library files, and `tools/layout/Layout.csproj` removes the library from what it assembles, naming `device-pgsql-port`.

The work: an SDK-format project referencing the current `Npgsql` package, Mono.Security gone (Npgsql has not needed it since it took over TLS itself), the `.d4l` naming only what the layout will provide, the project in the solution and in the layout's Library list, the exclusion removed, and the two binaries deleted from `external/`.

Fifteen years of driver changes sit between 2.0.4 and the current release, and the plan says the device's behaviour is driven by live tests rather than by getting it to compile. That is true of the *device*; this ticket's job is narrower and should be finished cleanly: **the library compiles against the current driver, registers in a server, and every API difference is understood rather than worked around.** Three are known from reading the code:

- **`NpgsqlParameter.Precision` and `Scale`** are set for `SQLNumericType` and for an eight-byte `SQLIntegerType`. Both members still exist on `NpgsqlParameter` but have been deprecated at points in the driver's history; check what the pinned version says and, if they are obsolete, use whatever replaced them rather than suppressing the warning (`AGENTS.md`: warnings stay visible).
- **`NpgsqlParameter.Size`** is set from `SQLStringType.Length`. Confirm it still means what it meant.
- **`NpgsqlDbType.Timestamp`** is the mapping for D4's `DateTime`. Npgsql 6 changed what it does with `DateTime.Kind`: a `DateTime` whose `Kind` is `Utc` is rejected for `timestamp without time zone`, and `timestamptz` expects `Utc`. D4's `DateTime` has no time zone, so `timestamp` is the right target - but what the engine hands over, and what `Kind` it carries, has to be checked. This one is a behaviour question, not a compile question, and it is the single most likely source of a defect in the whole PostgreSQL port. If it cannot be settled by reading, say so and leave it to the live ticket rather than guessing.

## Edge cases & interactions

- **The `.d4l` is a published file of a shipped library and the layout checks it.** It lists `Alphora.Dataphor.DAE.Connection.PGSQL.dll`, `Npgsql.dll` and `Mono.Security.dll`, the last two with an `environments.string` of `WindowsServer`. The layout fails the build when a listed file is not provided, so `Mono.Security.dll` must come out; `Npgsql.dll` stays only if the package's assembly is actually flattened into the library folder, which happens when the package is *private* to this library (no project it references has it). It is - nothing else in the solution uses Npgsql - but verify it by listing `artifacts/layout/<config>/Libraries/PGSQLConnection/` after a build. Modern Npgsql also brings its own dependencies; every one of them lands in the folder too, and the `.d4l` need not list them (the check is one-way), but a deployment reading the descriptor will see only what is listed, so decide deliberately whether to list the driver assembly and say why.
- **The `environments.string` element is part of the `.d4l` format**, which is a compatibility surface. Keep whatever shape you keep valid; `BOP` round-trips these files and `FormDocumentCorpusTest` does not cover `.d4l`, so the proof that the file still loads is a server registering the library.
- **Deleting from `external/` is a one-way door for the parked trees.** Check that nothing under `legacy/` references `external/Npgsql.dll` or `external/Mono.Security.dll` by `HintPath` before deleting them; `legacy/` is excluded from the build, so a stale `HintPath` there breaks nothing, but the next reader deserves to know. Report what the grep found.
- **`src/engine/Store.PGSQL` references this library's `PostgreSQLConnection`** (`PGSQLStoreConnection.InternalCreateConnection`), and `src/engine/Store.PGSQL/DAE.PGSQL.csproj` is still in the legacy format and not in the solution. `store-pgsql-port` owns it and depends on this ticket. Do not pull the store in here; the two are separable and the store is where the catalog-store contract applies.
- **The connection string keywords are the device's business, not this library's,** but one is worth naming because it decides whether anything connects at all: `PostgreSQLDeviceSession` puts a tag called `SearchPath` into the connection string, and `PostgreSQLConnectionStringBuilder` maps it to the keyword `SearchPath`. Modern Npgsql spells it `Search Path` and **throws on an unrecognised keyword** rather than ignoring it, so a connection string carrying `SearchPath=` fails outright. That fix belongs to `device-pgsql-device-golden` or the live ticket, whichever first creates a device; record the observation here so it is not rediscovered.
- **`PostgreSQLConnection.InternalWrapException` flattens every driver exception into a plain `Exception`** with a comment saying it does so "so that it crosses the boundary". That predates the current serialization rules and loses the driver's error code, which is what a caller would need to tell a constraint violation from a connection failure - the SQL Server connection class distinguishes them (`IsUserCorrectableError`). Do not change it here: it is behaviour, the device is not yet testable, and a change would be invisible until the live ticket. Record it as a `NOTE:` at the site saying what is lost and which ticket would notice.
- **Registration must not need a PostgreSQL server.** Registering the library loads the assembly and its driver; the driver connects only when a device asks it to. Confirm by registering the library once on a `TestServerInstance` - this is also the only end-to-end proof this ticket can offer, so do it and report it.
- **No new test.** Nothing here has behaviour of its own to characterize: the class is a thin override of `DotNetConnection` and the registration is wiring. The characterization tests for PostgreSQL translation and execution are `device-pgsql-device-golden`'s and `device-pgsql-port`'s. Say so, and say that the library's own behaviour is unproved until a device uses it.
- **A migration note is owed.** A deployment that ships `Npgsql.dll` 2.0.4 and `Mono.Security.dll` in a library folder will get different files, and the driver's own behaviour differs from 2009 in ways an application can see (time zone handling above all). One line now, pointing at the live ticket for the behaviour detail.
