# SQLite catalog store: WAL, immediate write transactions, busy error (first half of K10; K26)

**Context.** The server keeps its catalog (object scripts, users, rights, loaded libraries, settings) in the *catalog store*, SQLite by default. Under concurrent DDL the store fails with "database is locked" (K10 in the plan's [Known defects](../../docs/modernization-plan.md#known-defects); diagnosis and measurements in [WS4](../../docs/modernization-plan.md#ws4-catalog-store)). The spike removed every failure with write-ahead logging (WAL), a busy timeout, and beginning every store transaction with `BEGIN IMMEDIATE`. This ticket lands that configuration in production form, so that the *default* store (no connection-string options) is correct, plus the busy error and the rollback fix K26. The follow-up `store-sqlite-concurrency` then makes write transactions lazy, so that a session's read-only transactions stop taking the write lock.

## Decisions (settled in planning)

- **Provider: stay on `System.Data.SQLite.Core` 1.0.119** (already in `Directory.Packages.props`). It is the spike's validated configuration; the code already uses its error enum (`SQLiteErrorCode`) and its value conversions. `Microsoft.Data.Sqlite` would mean rewriting `SQLiteCommand.PrepareParameters`, the error mapping and `SQLiteStoreCursor` conversions for no gain in this design. No version change, so no new licence question.
- **Provider facts relied on** (from the package's own XML docs, `System.Data.SQLite.xml` in the 1.0.119 NuGet package): `BeginTransaction(IsolationLevel.Serializable)` takes the write lock immediately (`BEGIN IMMEDIATE`); `ReadCommitted` defers it (`BEGIN`), which is the lock-upgrade failure; other levels throw unless the `MapIsolationLevels` flag is set. `BusyTimeout` (milliseconds, default 0) sets SQLite's busy handler; the provider additionally retries busy statements until the command timeout (`Default Timeout`, seconds, default 30).
- **WAL and timeout are applied in code, not by the default connection string.** `SQLiteStore.InternalInitialize` (runs before the store is marked initialized, so `ConnectionString` may still be set) rewrites `ConnectionString` through `SQLiteConnectionStringBuilder`: `JournalMode = Wal` always (the design is wrong without it, so a configured `Journal Mode` is overridden — say so in a comment and in migration notes); `BusyTimeout = 30000` when the string does not set it; `DefaultTimeout` = `ceil(BusyTimeout / 1000)` seconds when the string does not set it, so that one setting, `BusyTimeout`, bounds the wait. `Server.GetCatalogStoreConnectionString()` and its default (`Data Source=<instance>\Catalog\DAECatalog.sqlite`) do not change. Every store connection (`SQLiteStoreConnection.InternalCreateConnection`, `SQLiteStore.GetSQLConnection` used by `CatalogDeviceTable`) is built from `Store.ConnectionString`, so all of them get the options.
- **Every store transaction is a SQLite write transaction begun immediate, whatever the D4 isolation level.** Today `SQLStoreConnection.BeginTransaction` calls `_connection.BeginTransaction(level)` directly and never calls its own `protected virtual InternalBeginTransaction`. Route the level-0 → 1 begin through `InternalBeginTransaction(isolationLevel)` (the base implementation keeps today's behaviour for other stores), and override it in `SQLiteStoreConnection` to call `Connection.BeginTransaction(SQLIsolationLevel.Serializable)`. Leave `SQLiteConnection`'s own "read uncommitted means no transaction" mapping alone: `CatalogDeviceTable` relies on it for its read-only connections, and they must stay outside transactions.
  - This settles **K26** (plan Known defects): under `Browse` the store used to open no SQLite transaction, so a rolled-back transaction undid the in-memory catalog but not the store. Now the store rolls back too. Visible only as "rollback now also rolls back the stored catalog"; migration-notes line.
  - Until `store-sqlite-concurrency` lands this is the spike's "begin immediate for everything": a session that has written to the store once begins a store write transaction at the start of each later process transaction and holds the write lock for its length, even when the transaction only reads. Accepted for one ticket; the follow-up removes it.
- **Busy error: new `StoreException` code 130103 `StoreLocked`**, severity `Environment`, message "The catalog store is locked by another session's open transaction and did not become available within {0} seconds." (`{0}` = `BusyTimeout` / 1000, from the connection's connection string). Raised in `SQLiteConnection.InternalWrapException` when the innermost provider exception is a `SQLiteException` whose `ResultCode` is `Busy` or `Locked` (mask to the primary code if extended codes ever appear; see the existing `NOTE:` on `IsUserCorrectableError`), with the provider exception as inner exception. `SQLiteConnection` is used only by the store (checked: no other project references it), so a store error there is correct. 130103 is free (`StoreException.cs` uses 130100–130102; prefix 130 is `DAE.Store` in `docs/reference/Error Message Prefix Codes.txt`). Add the resource string to `StoreException.resx` beside the others. Not done: naming the session that holds the lock — the store does not know sessions; nice to have, not required by the plan.
- **Local disk.** WAL needs the `-wal` and `-shm` files beside the catalog file and does not work on network file systems. Comment at the WAL line, migration-notes line; the admin guide arm is already filed on `docs-admin-guide` (`feat-ws8-documentation-remainder`).

## Edge cases & interactions

- **User-supplied connection string with its own `BusyTimeout` / `Default Timeout` / `Journal Mode`.** Timeouts are kept as given; journal mode is forced to WAL. By inspection; the busy test covers a user-set `BusyTimeout`.
- **Effective wait bound.** Confirm, with the busy test's elapsed time, that the provider's retry loop does not extend the wait well past `BusyTimeout` (that is why `DefaultTimeout` is derived). If it does, fix the derivation, not the test bound.
- **Where busy can surface:** on `BEGIN IMMEDIATE` (`SQLConnection.BeginTransaction` → `WrapException`), on a write outside any process transaction (autocommit, e.g. server-internal writes with no transaction), and in principle on a read during WAL recovery. All go through `InternalWrapException`, so all get 130103. `IsTransactionFailure` stays false: a busy begin leaves no SQLite transaction to mark failed. By inspection.
- **A failed immediate begin.** `SQLConnection.BeginTransaction` sets `_inTransaction` only after `InternalBeginTransaction` returns, so a busy failure leaves the connection out of transaction; but `SQLStoreConnection.BeginTransaction` must not increment `_transactionCount` or push its `BeginTransactionOperation` marker when the begin throws (check the order there and make it so). Otherwise the next commit or rollback on that connection is unbalanced. By inspection plus the busy test (B's retry on the same session must work).
- **`CatalogDeviceTable`** opens its own connection with `ReadUncommitted` (no SQLite transaction) and reads committed data; unchanged. With WAL it never blocks behind a writer. By inspection.
- **Restart and direct file reads under WAL.** `ConcurrentDDLTest` and `CatalogStoreTest` open the catalog file directly after `Server.Stop()`; they already ran under WAL through the old harness string, so nothing should change. If a read-only open fails for want of the `-shm` file, open it read-write instead.
- **Other stores.** `SQLStoreConnection.InternalBeginTransaction`'s base body is today's call, so the SQL Server and PostgreSQL stores (not built yet) keep their behaviour. By inspection.
- **Server start.** `CatalogStore.Initialize` runs the creation script on its first connection in autocommit; WAL is set by the provider on open, before the first statement. The default-store test (`CatalogStoreTest.DefaultStoreIsSQLite`) covers a fresh catalog.

## Source hygiene

`SQLiteStoreConnection.cs`, `SQLiteCommand.cs` and `SQLiteStoreCursor.cs` have no byte-order mark, and `SQLiteStoreConnection.cs` stores its copyright sign as the single Latin-1 byte `0xA9`, not UTF-8: an editor that re-encodes the file breaks that byte. After editing, check with `git diff` that only your lines changed and that the header line is untouched. `SQLiteConnection.cs`, `SQLiteStore.cs`, `SQLStoreConnection.cs`, `StoreException.cs` and the test files are UTF-8 with BOM, CRLF.
