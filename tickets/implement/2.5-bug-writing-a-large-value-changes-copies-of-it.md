## What is wrong

The engine keeps values too large to carry around inline - the two D4 types for them are `Binary` and `Graphic` - in a managed stream owned by the server. Copying such a value does not copy its bytes: the copy is a **reference** to the original's stream, and the two are meant to be separated the first time either one is written. That separation only works in one direction. Writing through a copy separates it and leaves the original alone, which is correct. Writing through the **original** changes what every outstanding copy of it reads.

`ServerStreamManager.Change(ServerStream)`, `src/engine/DAE/Streams/ServerStreamManager.cs` around line 438, is the one site. Every write through a managed stream calls it first (`ServerStream.Write`, `WriteByte` and `SetLength` all do) and it is where the separation happens, but it handles only the case where the stream being written is itself a reference. When the stream being written is a *source* that has references, it does nothing, and the write lands in the provider's stream that every reference is reading through - a reference's stream is created as a cover over its source's, in `InternalOpen`.

## Reachable from D4, in every shape a value gets copied

Confirmed 2026-11-24 against the current `modernization` head, by a throwaway NUnit fixture on `InProcessTestFixture` (built, run, then removed - it is not in the tree). Each of these failed before the fix and passes after it, for `Binary` and for `Graphic`:

- a copy taken at declaration - `var LB : Binary := LA;`
- a copy taken by a later assignment - `var LB : Binary; LB := LA;`
- a copy taken into a row - `var LR : row { B : Binary } := row { LA B };`

In each case, writing a different value through `LA.Value` afterwards left the copy reading the value written through `LA`, where it should have read the value it was taken from. So this is data corruption in ordinary use, not something confined to callers of the class API: copying a stream-backed value goes through `DataValue.CopyNative` / `DataValue.CopyValue`, both of which call `StreamManager.Reference` for a stream identifier, and writing through a representation reaches the `Scalar.AsByteArray` setter, which writes into the existing stream.

## The fix, measured

Separate every reference from the stream being written, before the write lands, the same way the existing branch separates a single reference from its source. Add an `else if` to `Change`, after the `if (_referencingHeaders.TryGetValue(...))` block:

```csharp
				else if (header.References.Count > 0)
				{
					// The stream being written is the source of one or more references. Each reference must keep the
					// value it was taken from, so give each one a provider stream of its own, holding this stream's
					// current contents, before the write lands. A reference that is not open has no stream to repoint:
					// it is no longer a referencing header, so its next InternalOpen opens the entry made here.
					long savePosition = stream.Position;
					for (int index = header.References.Count - 1; index >= 0; index--)
					{
						StreamID referenceStreamID = header.References[index];
						StreamHeader referenceHeader = GetStreamHeader(referenceStreamID);

						// dereference this stream
						header.References.RemoveAt(index);
						_referencingHeaders.Remove(referenceStreamID);

						// copy the data from this stream into the reference
						_defaultProvider.Create(referenceStreamID);
						InternalCopy(header, referenceHeader);
						if (referenceHeader.Stream != null)
							referenceHeader.Stream.SourceStream = _defaultProvider.Open(referenceStreamID);
					}

					// InternalCopy read this stream to the end through a cover over it, which moved the position of
					// the stream the caller is about to write at. Put it back, or the write lands past the old value
					// instead of over it.
					stream.Position = savePosition;
				}
```

Two things about it that are not obvious and were found by running it:

**The position restore is load-bearing.** `InternalCopy` opens the copy source through `InternalOpen(header, true)`, which is a `CoverStream` over `header.Stream`; a cover sets its source's position before every read, and `ServerStream.Position` passes straight through to the provider's stream. So reading this stream to the end leaves the provider's stream positioned at the end, and the `_sourceStream.Write` that `ServerStream.Write` performs immediately after `Change` returns then appends instead of overwriting. Without the restore the two existing source-write tests fail with the source reading back its *old* value - the new bytes are sitting past the end of it. Any other shape of fix pays the same tax: the stream the caller is about to write through must come out of `Change` positioned where the caller left it.

**A reference that is not open must be skipped, not crashed on.** The existing branch above can write `header.Stream.SourceStream` unconditionally because the stream being written is by definition open; the references separated here need not be, so the `if (referenceHeader.Stream != null)` guard is required. A reference whose `Stream` is null is already out of `_referencingHeaders` by then, so its next `InternalOpen` takes the `else` arm and opens the provider entry this loop created. A reference that has references of its own needs nothing: they read through *its* `ServerStream`, so they follow the repoint.

Measured with the prototype in place: the whole of `ServerStreamManagerTest` green including the previously ignored case, `StreamBackedRepresentationWriteTest` and `AssignmentValueOwnershipTest` green, the D4 cases above green, and the coverage scripts `ScalarAllocation`, `SerializationTypes`, `Types`, `Types.CompoundEquality` and `Types.Length` green (`StreamAllocation` is skipped as a recorded known failure, unchanged).

## The alternative, and why not

The other shape is re-parenting: leave the provider's stream with the references and give the source a fresh one, which is what `Deallocate` in the same file already does when it hands a deallocated stream's provider entry to one of its references. It costs one copy regardless of how many references are outstanding, where the loop above costs one per reference. It was not chosen because it is the larger change on the more delicate path - it calls `Reassign` on the source's provider, mixes an externally registered provider with `_defaultProvider`, and leans on `MoveReferences`, which repoints a moved reference at a raw provider stream rather than at a cover over its new source's `ServerStream` and adjusts no open counts. The loop above touches the source's provider entry and its open stream not at all, which is why `WritingASourceThatHasReferencesLeavesItReadingItsOwnNewValue` holds under it without any further work. Record the cost as a tripwire (below) rather than paying that risk now.

## Tripwires to record at the site

Two `NOTE:` lines in `Change`, not tickets:

- The cost: one copy per outstanding reference on the first write to a source, where the re-parenting shape above would cost one copy regardless. And because a representation write truncates before it writes - `ServerStream.SetLength` then `ServerStream.Write`, each of which calls `Change` - the separating copy happens on the `SetLength` and copies contents that the write then replaces in full. `Change` is idempotent, so the second call costs a dictionary lookup and nothing else; nothing here was measured. If copying a large value many times before writing the original ever shows up as slow, the re-parenting shape and a check for a `SetLength` to zero are the two things to reach for.
- The bookkeeping: repointing a reference's `SourceStream` drops the cover stream it was holding over this stream without closing it and without the matching `InternalClose`, so this header's open count stays one high per reference separated. That is the same thing the branch above it does and what the two `// TODO: Shouldn't this close the old stream?` comments in `MoveReferences` and `Deallocate` are about; it is inert today because `MemoryStreamProvider.Close` is a no-op and `Deallocate` removes a header whatever its count. If the file-backed provider is ever switched on (`UseFileStreamProvider`, commented out at the top of the file), these counts are what decides when a file handle is released and this becomes real.

## Compatibility and migration notes

This changes what an existing application sees: a library that reads a copy after writing the original currently gets the new value and will get the old one. No D4 syntax, operator signature, class name, file format, error code or contract shape changes. The old behaviour is not something an application could sensibly have been written around - it is the data-corruption case - but it is visible, so add a row to the `## D4, catalog and libraries` section of `docs/migration-notes.md` in the same commit, status `done`: what changed (a copy of a `Binary` or `Graphic` value now keeps the value it was taken from when the original is written, where before it followed the original), and what to do (nothing, unless an application relied on the old behaviour to see a write through an earlier copy, which should be rewritten to read the variable that was written).
