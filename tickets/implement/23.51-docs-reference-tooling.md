## What this is

The first of five tickets that convert the old reference material into `docs/reference/` and repair the 203 links that point at it (known defect **K17**). This one lands the tooling and the three tables everything after it reads, proves them on a small sample run into a scratch folder, and records the decisions in the plan. **It publishes no page under `docs/`.** The link checker stays at "203 pending" when it is done, which is what CI already expects.

The four tickets after it are `docs-reference-operators`, `docs-reference-libraries`, `docs-reference-chapters` and `docs-convert-legacy-reference` (which finishes the work item and keeps its slug).

## The decisions planning settled, and the evidence

Measured 2026-11-26 at commit `bd4b4144`. Record all four in the plan's WS8 **Design notes** paragraph as part of this ticket, so they survive the board.

**The prose comes from `legacy/Documentation/Docs2.0/`, not from `DocBookManuals/OperatorDocs/`.** For `System.Abs` the 2007 `Docs2.0` text is the edited form of the 2004 `OperatorDocs` text and is word for word what the published help file shows, so `Docs2.0` is the lineage that actually shipped. It also covers more (339 operator sections against 275 files) and its *See Also* links already use the `O-<Name>.html` and `T-<Name>.html` spellings that `LEGACY_RULES` in `convert.py` resolves, where `OperatorDocs` uses an `SLR<Name>.html` scheme that nothing maps. The 52 `OperatorDocs` files with no matching `Docs2.0` section are mostly scalar types (which live in `SystemTypes.xml`) and the pre-3.0 `System.Group*` security operators that no longer exist. `OperatorDocs` is used for exactly one page - see *the one real gap* below.

**Operator and type signatures come from the published help file, extracted once into a committed table.** Every operator section in `Docs2.0` has its *Declarations* block replaced by a `<?DocLib D4Field Declaration?>` placeholder that the old generator filled from a live catalog at publishing time; `SystemOperators.xml` alone holds 596 of them. `legacy/Documentation/Dataphor.chm` is those same sources already published, so its 339 `O-*` pages carry the filled blocks. `O-System.Abs.html` holds exactly what the page needs:

    create operator .System.Abs(const AValue : System.Decimal) : System.Decimal
     class "System.DecimalAbsNode";
    create operator .System.Abs(const AValue : System.Integer) : System.Integer
     class "System.IntegerAbsNode";

Extract them once into `tools/docs-convert/declarations.tsv` rather than reading the help file on every run, for three reasons: a rerun then needs only Python, Node and pandoc and not Windows' `hh.exe`; a human can review the 370-odd signature blocks going into the documentation as a table; and the extraction becomes one reviewable step instead of a hidden dependency on a 3.2 MB binary.

These signatures are the 3.x published record. Operator signatures are a compatibility surface this port must not have changed, so they are the right content *and* the baseline that `docs-reference-generator` later diffs against a running 4.0 catalog - that diff is what the plan's "regenerate and diff" row is for, and it only works if the committed pages carry signatures. **This settles the question of where signatures come from, and `docs-reference-generator` adopts this answer rather than re-deciding it:** this chain writes the prose and the 3.x facts; that work item generates the 4.0 facts and reports the differences.

**Library facts are *not* taken from the help file.** Its `SimpleDevice` *Definition* page gives Version 2.1.0.0 where the shipped `libraries/SimpleDevice/SimpleDevice.d4l` says 3.0.0.0, so those blocks are known-stale rather than merely possibly-stale. `docs-reference-libraries` reads version, requisites and files from each library's own `.d4l` descriptor in this repository. Nothing in this ticket needs that, but the extractor must not be written as though it serves library pages too.

**The page layout is one page per operator name, per type and per library, plus a page per operator category.** 339 operator sections resolve to 297 distinct operator names and 25 categories: 13 names are documented by two to four sections, because the printed reference listed an operator under every category it belonged to (`System.iIndexer` has four, `System.iIn` and `System.IndexOf` three each), and 16 of those extra sections are short cross-references ("`in` is a table, row, and list operator. See System.iIn table operator"). All sections of one operator name merge onto that name's page. The 25 category sections become pages: they are the index structure, and three pending links want them.

**The one real gap.** `System.iXor` is documented nowhere in `Docs2.0` and nowhere in the help file; its only source is the single 2004 file `legacy/Documentation/DocBookManuals/OperatorDocs/System.iXor.xml`. That one file is converted, with no *Declarations* section. Three further pending links (`System.AggregateOperators`, `System.CursorOperators`, `System.ListOperators`) want category pages, which exist. One (`System.SecurityOperartors`) is a misspelling in the AsciiDoc source, and `docs-convert-legacy-reference` corrects it.

**Six operator sections have no signature available at all** - `System.ActualDate`, `System.ActualDateTime`, `System.ActualTime`, `System.IsNotNil`, `System.MonthsBetween` and `System.YearsBetween` were added to the DocBook after the help file was published. Their pages carry no *Declarations* heading rather than an empty one.

## What this ticket builds

### 1. `tools/docs-convert/reference_split.py`

A new script beside `convert.py`, with two modes. It exists because `convert.py`'s DocBook stage writes **one page per input file** and fails outright when two sources resolve to the same output, so the only way to get 300-odd pages out of one 702 KB file - and to merge four sections onto one page - is to reshape the input first. Doing it here leaves `convert.py`'s one-file-one-page invariant untouched.

**`reference_split.py declarations <decompiled-chm-dir> --out declarations.tsv`** reads the `O-*.html` and `T-*.html` pages of the decompiled help file and writes one row per section id with the contents of its *Declarations* block. Columns `id`, `declaration`. A declaration is a multi-line D4 script, so newlines are escaped as `\n` and backslashes as `\\`; the mode must decode every row it wrote, compare it against what it extracted, and fail if any row does not round-trip. Decompile the help file with `hh.exe -decompile <dir> legacy\Documentation\Dataphor.chm` (Windows, built in; it writes 3,330 files, so send it to a scratch folder outside the repository and **do not commit the dump or leave it in the tree**).

**`reference_split.py split FILE.xml ... --pages reference-pages.tsv --declarations declarations.tsv --out WORKDIR`** reads the reference DocBook, substitutes or removes the generated-content placeholders, groups sections onto target pages, and writes one DocBook file per page into `WORKDIR` plus the `--pages` map that `convert.py docbook` then reads. `--seed-pages` writes a seeded `reference-pages.tsv` from the section ids instead (operator `O-<Name>` to `operators/<Name>.md`, type `T-<Name>` to `types/<Name>.md`), so the 360-odd rows get reviewed rather than typed.

Things the split has to get right, each a measured fact rather than a guess:

- **Each page is one DocBook document whose root is `<article>`**, carrying the id and title of the first section it holds and that section's children as its body, so the operator name is the page's single `#` heading and *Remarks*, *Example* and *See Also* land below it. A bare `<section>` as document root may work with pandoc's DocBook reader but could not be verified here (pandoc is not installed on this machine), and the `<article>` wrapper is accepted for certain. Check the heading levels of the sample output before converting anything at scale.
- **Keep the ids.** `convert.py docbook --global-ids` resolves a fragment-only reference by looking for the id in every page, and the reference sources use those.
- **Drop the DOCTYPE.** Seven source files declare one pointing at a DTD path that does not exist (`FrontendOperators.xml`, `SystemTypes.xml`, `ProgrammingTopics.xml`, `MSSQLDeviceOperators.xml`, `MSSQLDeviceTypes.xml`, `SimpleDeviceOperators.xml`, `SystemIntegrationOperators.xml`). All 30 reference files parse with `xml.etree.ElementTree` as they stand and only `&amp;`, `&lt;` and `&gt;` appear as entities, so no DTD is needed - but a DOCTYPE copied into the split output would be followed by pandoc.
- **Processing instructions must survive parsing.** `ElementTree` silently discards them unless the parser is built as `ET.XMLParser(target=ET.TreeBuilder(insert_comments=True, insert_pis=True))`. Losing them would look like success and would drop every signature.
- **Handle all 1,395 placeholders.** Across the 30 reference files: 1,291 `<?DocLib ?>` instructions in six kinds - `D4Field` (692), `D4ExpressionBlock` (544), `ExtDoc` (23), `D4ExpressionIf` (16), `D4ExpressionField` (15), `D4ExtDoc` (1) - and 104 `<?xm-replace_text ?>` leftovers from the XMetaL editor. A `D4Field Declaration` inside a `<formalpara>` whose title is *Declarations* is replaced by the row from `declarations.tsv`; with no row, **the whole `formalpara` is removed**, heading and all. Every other kind is removed together with any enclosing block that would otherwise render empty. Nothing may be left to render as literal text: the mode fails if any `<?DocLib ?>` or `<?xm-replace_text ?>` survives into the output.
- **Several sections per page.** `reference-pages.tsv` maps section id to output page; rows sharing an output are concatenated in source order into one `<article>`, the first section's title as the page title and the rest as body sections. A row with an empty output is not converted. **A section id with no row is an error**, so nothing is dropped by omission.
- **Category pages.** A category section's own text is a bare XMetaL placeholder in the source - the paragraph was never written - so a category page is its title plus a list of links to the operator pages of the sections nested under it, which the split knows from the document structure. Where a category has no prose, do not invent any.

### 2. One change to `convert.py`: `--legacy-map TSV`

The reference sources carry 539 links into the converted guides and 60 more to other reference chapters, and `convert.py` today reports every one as "legacy page with no rule", because `LEGACY_RULES` only knows the operator, type, library, Frontend-node and Data-Access-Component spellings. Add `--legacy-map TSV`, consulted in `Resolver.legacy()` before `legacy_target()`: a map hit supplies the target, which may carry a `#fragment` (only the path part is made relative to the current page); an empty target unlinks the reference and keeps its text, as `xref-fixes.tsv` already does; a miss falls through to the built-in rules unchanged. Match the legacy page name case-insensitively on the `.html` suffix, because one source link is spelled `DFRTagReference.HTML` and the current `\.html$` pattern misses it.

### 3. `tools/docs-convert/reference-links.tsv` - the cross-link map

Columns `legacy_page`, `target`, `reason`. 116 distinct targets, which break down as:

| Kind | Occurrences | Distinct | How to resolve each |
|---|---|---|---|
| `D4LG*`, `DDG*`, `DUG*` named chunks | 539 | about 90 | The decompiled help file has a page of that exact name whose `<title>` and `rel="up"` chain name the section; find the heading of that title under `docs/developers-guide/` or `docs/users-guide/` and write `page.md#anchor` |
| `bk0*` positional chunks | 49 | 15 | Not in this help file - resolve from the link text, which names the section (`Compiler`, `Query Processor`, `Navigational Access`, `Versioning`, `Library Settings`) |
| `DR*` reference chapters | 11 | 10 | Pages this chain creates, or the ones it does not (see below) |
| `FTRTagsDescriptions-*`, `DFRTagReference.HTML` | 2 | 2 | `docs/reference/tags.md`, by heading |
| `http(s):` | 9 | - | Left alone; `convert.py` already keeps and lists external links |

Where a target genuinely cannot be resolved, the row gets an empty target and records why - the link becomes plain text and the reader loses nothing but a hyperlink. Five of the `DR*` targets name device libraries this release does not ship (`DRDB2DeviceLibrary*`, `DROracleDevice*`); those rows are unlinked with that reason.

Attribute values in the sources sometimes carry a trailing newline (`url="…Conveyors.html\n"`), so strip whitespace before matching.

## Edge cases & interactions

- **Do not write `tools/docs-convert/legacy-links.tsv`.** That file is the AsciiDoc run's output and CI's `--pending` list; the DocBook runs pass `--legacy-table` to a scratch path or omit it. Overwriting it would replace CI's pending list with the reference's own internal links. *Verified by reading the command and by `git status` after each run.*
- **Letter case.** Page names here are mixed case (`System.Abs.md`, `System.iLike.md`) and the link checker compares against the real directory listing, because Windows ignores case and GitHub does not. The names come from the committed page map, never from a transformation. *Verified by the link checker, which CI runs on Linux.*
- **Dots in page names.** `convert.py`'s `page_name` rule would turn `System.Abs` into `system-abs`; it is not used, because every page comes from an explicit `--pages` row. *Verified by a unit test that a seeded map keeps its source spelling.*
- **`declarations.tsv` escaping.** The round-trip check inside the extractor is the guard, and it is part of the mode rather than a separate step. *Verified by a unit test and by the mode's own check.*
- **A `--legacy-map` row for a page the built-in rules already handle** would silently retarget an operator link, because the map is consulted first. Report any map row whose key matches a built-in rule, and any row that matched nothing, the way `xref-fixes.tsv` reports unused rows. *Verified by a unit test for the override report.*
- **pandoc and Node version pins.** `convert.py` stops if pandoc's or a pinned package's major.minor version differs, because another version writes different Markdown. This ticket needs pandoc 3.14 and `npm ci --prefix tools/docs-convert`; the Node side is not used by the DocBook stage, but the version check still runs. If the pinned pandoc cannot be installed, that is a blocker to report, not a reason to pass `--allow-tool-versions`. *Verified by the run succeeding.*
- **The new tests do not run in CI.** `debt-tool-tests-not-run-by-ci` (backlog) owns that gap; do not fix it here, and say in the handoff that the tool tests were run by hand.
- **No compatibility surface, no migration note.** Documentation tooling only: no public type or member, no file format, no D4 semantics. Say so in the handoff rather than leaving it implied.
- **Privacy.** The decompiled help file has 3,330 pages nobody has read recently. It is this project's own published documentation, but read the pages the extractor touches before committing `declarations.tsv`: nothing but D4 `create operator` and `create type` statements belongs in it.

## Tests

Two files, both running without pandoc, Node or the help file.

- `tools/docs-convert/test_reference_split.py` - new. One case per branch with judgement in it: several section ids mapping to one page produce one document in source order; a `D4Field Declaration` with a row is substituted and one without a row removes its whole `formalpara`; a surviving placeholder is an error; a section id absent from the page map is an error; the declaration escape round-trips a multi-line value.
- `tools/docs-convert/test_convert.py` - add cases for `--legacy-map`: a hit with a fragment, a hit with an empty target (unlinked), a miss falling through to `LEGACY_RULES`, and an uppercase `.HTML` suffix.

Nothing else. No test asserts a page count or that a particular page exists - the link checker already fails when a referenced page is missing, and a counted number is a number the next ticket changes.
