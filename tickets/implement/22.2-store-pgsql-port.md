## What this is

A *store* is where the server keeps its own catalog; a *device* is a D4 object mapping tables onto an external DBMS. They are different things that happen to share a connection library, and this ticket is the store. `src/engine/Store.PGSQL` - three source files and an embedded `SystemStoreCatalog.sql` - is the PostgreSQL version of the thing `src/engine/Store.SQLite` (the default) and `src/engine/Store.MSSQL` already are. Its project is in the .NET Framework format and not in `Dataphor.slnx`.

`store-mssql-port` did the identical job for SQL Server and is the template to follow in every particular, including the conditions it discovered. The plan's WS7 row sets the bar for this one: port it **"if it then needs only the store contract tests to pass"**. That is the decision rule, and it is meant to be applied honestly - if making this store work needs changes to the store contract, to the engine's catalog code, or to anything beyond this folder and its project file, stop and park it, saying exactly what it needed. Decision D15 puts PostgreSQL support in scope; it does not promise the store.

### What `store-mssql-port` established

- The port was the project file alone: not one line of the three store source files changed to compile. Expect the same here and treat a needed source change as a signal, not a chore.
- `MSSQLStore.InternalInitialize` forces `MultipleActiveResultSets=True` because the catalog opens a second store cursor while a first is open. **`PostgreSQLStore.InternalInitialize` sets `_supportsMARS = false`** and `_supportsUpdatableCursor = false`, so this store takes a different path through `SQLStore` - and `_supportsMARS` false also turns off `CatalogStore.UseCursorCache`, which both other stores use. That is the single biggest unknown in this ticket: the contract's 14 cases are what will say whether the non-MARS path works, and that path is exercised by nothing today.
- A store that ships must be *loadable*: on .NET 10 there is no app-local probing, so both host executables reference every shipped store project so that its assembly is named in their `.deps.json`. `HostProgramTest.TheHostsDependencyFilesNameTheAssembliesTheServerLoadsByName` iterates every store the layout ships and is the guard; it is held as a list of *types* so the compiler keeps it honest. Add this store to it.
- The contract fixture is a subclass: `MSSQLStoreContractTests` is a second subclass of `StoreContractTests`, with **no new cases** - that is the point, and the project's testing rule for a re-hosted subsystem. Add `PGSQLStoreContractTests` the same way, gated on an environment variable, skipping case by case and saying so when it is unset. Use the same variable `device-pgsql-port` defines (`DATAPHOR_TEST_PGSQL`) if it has landed, or define it here in `TestEnvironment` for both to share; one variable for "a PostgreSQL server this machine may be tested against" is what a developer will expect.
- Emptying the database belongs at the *start* of a case, not in teardown, so that `DATAPHOR_TEST_LOGGING` leaves a finished run's rows to look at without poisoning the next case. The SQL Server fixture's review found that the other way round broke the very flag that exists to diagnose it.

### The PostgreSQL-specific things to check

- **`PGSQLStoreConnection.InternalCreateConnection` has a dead `#else` branch returning `new SqlConnection(...)`** - a SQL Server connection in the PostgreSQL store - guarded out by `USESQLCONNECTION`, which is defined at the top of the file. It is unreachable, and it is the kind of thing that becomes reachable by accident. Delete the dead branches and the `#define` with them if nothing else needs them, or leave them and say why; either way do not leave a reader to work out that the PostgreSQL store does not open SQL Server connections.
- **`HasTable` lower-cases the table name** before querying `PG_TABLES`, which is PostgreSQL's identifier folding showing through. Check the rest of the store agrees about case - a store that creates `DAEObjects` and looks for `daeobjects` works only because of that one lower-casing.
- **`NativeToParameter` and `NativeToLiteralValue` override the base** because this store's catalog declares its boolean columns `boolean` where the others use an integer. Read `SystemStoreCatalog.sql` against those overrides; a mismatch would show up as a contract failure that looks like a cursor problem.
- **`ShouldEnsureDatabase`** exists on this store as on the others, but there is no `EnsureDatabase` call in `InternalInitialize` - the property is set and never read. Either the store cannot create its own database (in which case the fixture must create it, as the SQL Server fixture's `RequireServer` does for the database it drops) or the property is dead. Find out which and say so; a property that promises something it does not do is worse than its absence.
- **Non-ASCII text.** The SQL Server store loses characters outside the server's code page on write (`device-mssql-string-parameters`). PostgreSQL databases are normally UTF-8 and Npgsql sends text as Unicode, so this store should not have that problem - which makes it worth one explicit check rather than an assumption, because "the other store has a known text-loss bug" is exactly the sort of thing a reader will want settled for this one. If the contract gains a non-ASCII case from `device-mssql-string-parameters`, this store answers it for free.

## Edge cases & interactions

- **Parking is a legitimate outcome and must be done properly.** If the store needs more than its project file and this folder, leave the project unconverted, leave the layout exclusion in place, and file what it needs - as a `fix/` ticket if the cause is a defect, or a `backlog/` `debt-` ticket if it is work - naming the contract cases that failed and what they failed on. Do not half-land it: a store in the layout that cannot pass its contract is worse than one that is absent, because a deployment could configure it.
- **`SQLStore`'s non-MARS path is shared code.** If a contract case fails there, the fix may touch `src/engine/DAE/Store/` rather than this folder - which is outside this ticket's bar. Weigh it: a one-line fix with a reproduction is a bug met along the way; anything structural is a ticket and this store waits for it.
- **The layout and the hosts both change.** A new shipped assembly lands in `artifacts/layout/<config>/bin/` and in both `.deps.json` files. Report the `bin/` file count before and after, and run `HostProgramTest`.
- **Npgsql's package files are not private to a host.** The connection library owns the package (from `device-pgsql-connection-port`); this store references that library, so the driver arrives through it. Check what that means for the layout: a library's package files land in the library folder when private to it, and `bin/` gets what a project in the Bin list brings. A store assembly in `bin/` that needs a driver assembly only present in a library folder would fail at run time in a way no build check catches. **Verify it by configuring an instance on this store and starting it**, which is the one end-to-end check this ticket can make cheaply and which the SQL Server store's review found nobody had made.
- **`catalogstoreclassname` and `catalogstoreconnectionstring` are instance settings a deployment writes.** `docs/users-guide/dataphor-service.md` already carries the SQL Server store's assembly-qualified class name, an example entry and its caveats; this store gets the same treatment, including whether the server creates the database and whether the connection string needs anything particular.
- **No new contract cases.** The 14 existing ones are the contract; adding a case here would mean adding it for all three stores, which is a different ticket's business. If this store needs a case of its own to show something, that is a sign it is not merely a third implementation of the same contract - say so.
- **A migration note is owed.** A second non-default store becomes configurable again; one line, naming the class and pointing at the users-guide entry, as the SQL Server store's did.
