## Decision: a `fragment` status

`Transaction.Atomicity.SetTwo`, `Run` and `Cleanup` are steps of a sequence. `Transaction.Atomicity.TestDAE` runs `SetOne`, `SetTwo` and `Run` with the default device set to `System.Temp`, then `Cleanup`; the three `*MSSQL*` scripts run the same steps on a SQL Server device. On its own, `SetTwo` fails because the tables `SetOne` creates do not exist, `Cleanup` because the tables both create do not exist, and `Run` because of both. Running them alone tests nothing, and a `known-failure` entry for them would claim a defect that does not exist.

Rejected: a "run these scripts first" option per entry (it would duplicate `TestDAE`'s own case and make a fragment's result depend on another script's); leaving them `known-failure` against a ticket that can never fix them.

A helper that passes on its own stays `pass` (`Transaction.Atomicity.SetOne`, and the `Serialization*` scripts that `Serialization` runs): it does test something standalone, its own DDL.

### Manifest format

- `status`: `fragment` (new, beside `pass`, `known-failure`, `unstable`).
- `partOf` (new field, required on `fragment` and allowed only there): a non-empty array of script names. Each must have a manifest entry, must not be the fragment itself, and must not be a `fragment` entry.
- On a `fragment` entry, `ticket`, `error`, `timeoutSeconds`, `preamble` and `register` are not allowed; `note` is.
- Discovery check: each script named in `partOf` must mention the fragment by name as a D4 string literal (`"<name>"` or `'<name>'`) in its file text. If it does not, discovery yields a failing case for the fragment: `<fragment> is listed as part of <parent>, but <parent>.d4 does not mention it; correct partOf or the entry's status.` This keeps an entry from going stale when a parent script changes. (It is a text check, so a mention in a comment satisfies it; good enough to catch a rename or a removal.)

### Harness behaviour

- A `fragment` case starts no server and runs nothing. It reports through `Assert.Warn` (VSTest shows it as Skipped, like known and unstable cases) with the text `fragment: run by <parent>, <parent>; not run on its own`.
- The summary gains one line after `unstable`: `  fragment: <n> (run only as part of other scripts)`.
- A fragment case still counts in `Cases`. A `fragment` entry whose file is missing is a `FileMissing` discovery problem as now.

### Manifest entries

## Edge cases & interactions

- `test-case-result-helpers` makes `Transaction.Atomicity.TestDAE` pass and changes `Run`'s standalone error; it has this ticket as `prereq:` so that `Run` is already a `fragment` when it lands. If the order is ever reversed, `Run`'s `known-failure` entry would mismatch.
- `Transaction.Atomicity.TestMSSQLDAE` mentions `Cleanup` twice, once in a comment; the text check passes either way.
- Strict JSON: `partOf` must be added to `CoverageEntry` with `[JsonPropertyName("partOf")]`, or `UnmappedMemberHandling.Disallow` rejects it.
- A filtered run selecting only fragment cases (`--filter Name=Transaction.Atomicity.Run`) must not fail; whether the template still builds for it follows the existing rule (it builds when discovery yields any script case) and needs no change.
- Validation collects every problem, as now; the new rules add messages in the same style ("Entry N (name): …").
