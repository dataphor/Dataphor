## Background

`Transaction.Atomicity.TestDAE` (through the step script `Transaction.Atomicity.Run`) and `Transaction.Isolation.Run` record each case through a table `CurrentCaseItems` (`delete CurrentCaseItems;` at the start, `select CurrentCaseItems;` at the end) and an operator `RaiseCurrentCaseItem(<case name> : String, <passed> : Boolean, <message> : String)`. Neither has ever been defined in this repository (not at tag `v3.1`, not in the 2008 initial commit), so both scripts fail at compile time with `Unknown identifier "CurrentCaseItems"`. The fix is to add the two to the helper library `TestFramework.Coverage.Base`, which the coverage template registers. Never edit the coverage scripts.

## The definitions (tried in the fix stage)

Append to the end of `tests/libraries/TestFramework.Coverage.Base/Documents/Tables.d4`. That file is UTF-8 without a byte-order mark, CRLF line endings, tab indentation; keep all three. `Register.d4` runs `Tables` after `DiagnosticsLogic`, and the operator refers to the table, so both go in `Tables.d4` and `Register.d4` does not change.

```
// Case results recorded by the transaction coverage scripts (Transaction.Atomicity.Run, Transaction.Isolation.Run).
create table CurrentCaseItems
{
	Name : String,
	Passed : Boolean,
	Message : String,
	key { Name, Message }
};

// Records a case result; raises an error naming the case when it did not pass.
create operator RaiseCurrentCaseItem(const AName : String, const APassed : Boolean, const AMessage : String)
begin
	insert table { row { AName Name, APassed Passed, AMessage Message } } into CurrentCaseItems;
	if not APassed then
		raise Error(AName + ": " + AMessage);
end;
```

- The table goes in the library's default device (`Temp`, from `defaultdevicename` in `TestFramework.Coverage.Base.d4l`). It must be a database table: a library operator cannot refer to a session table.
- Raising when the case did not pass is what makes a failed case fail the script: `Run`'s closing `if exists CurrentCaseItems then raise …` is commented out, so recording alone would leave a failed case green. All 11 calls in `Run` are outside its `try … except` blocks, so nothing in the script swallows the error. `Isolation.Run` calls it once per case with `<expected> = <observed>` as the flag.
- Each coverage case runs on its own server copied from the template, so rows one case leaves in `CurrentCaseItems` are not visible to another case.

## Observed with these definitions (fix stage, 3 identical runs of `--filter "Name=Transaction.Atomicity.TestDAE|Name=Transaction.Isolation.Run"`)

- `Transaction.Atomicity.TestDAE`: passed every time. The template still registered, so the new D4 compiles.
- `Transaction.Isolation.Run`: failed every time at its first case, with `DataphorException: Lost Update (Browse, Browse): LostUpdate did not behave properly with Browse, Browse as Isolation settings.`

## Cause of the isolation failure

The script's table `TestIsolation` goes in the memory device `System.Temp`. The first case has process 1 update the row and sleep 1 s before committing; process 2 then updates the same row with a 200 ms timeout, and the script expects that update to fail (blocked by process 1's uncommitted change). It succeeds at once, because nothing locks a memory-device row for a transaction:

- `MemoryDeviceSession.InternalUpdateRow` / `InternalInsertRow` / `InternalDeleteRow` (`src/engine/DAE/Device.Memory/MemoryDevice.cs`) change the shared `NativeTable` directly. `InternalBeginTransaction` ignores the isolation level; the per-transaction code is behind `#if USEMEMORYDEVICETRANSACTIONS`, which nothing defines, and it logs operations for undo, not locks.
- The engine's table nodes (`TableNode.Update` and friends) take no row locks either; on a SQL device the locking comes from the database server.
- `docs/developers-guide/devices.md` describes the memory device as providing "full transactional support, and minimal concurrency protection".

So the failure is deterministic and is not a timing problem; it is the memory device's lack of locking, the site of `bug-memory-device-concurrent-access` (backlog). The fix stage appended this script to that ticket as a second arm ("transaction isolation"), noting that it is a wider requirement than that ticket's first arm (serializing concurrent statements inside the index) and that the documentation does not promise it.
