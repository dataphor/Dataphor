## What happens

An operator parameter declared `var` gives the operator a slot that is an alias of the caller's: the caller's variable and the parameter name the same value, and whatever the operator leaves in the parameter is handed back to the caller's variable when the call returns. A body that assigns to such a parameter releases the value it displaced, which is right while the caller's variable owns that value - the ordinary case.

A `foreach` loop variable does **not** own its value. The loop lends its variable the row or element the iterator owns and goes on reading it. So when the caller passes its own loop variable to a `var` parameter, the operator's assignment releases a value the loop is still using, and the loop then reads a released one:

```
create operator ZFixup(var ARow : row { ID : Integer, B : Binary })
begin
	ARow := row { 9 ID, Binary('0009') B };
end;

var LR : row { ID : Integer, B : Binary };
foreach LR in cursor(table { row { 1 ID, Binary('00F1') B }, row { 2 ID, Binary('00F2') B }, key { ID } }) do
	ZFixup(var LR);
// "A nil was encountered where a value was expected" on the second row
```

Reproduced again on `modernization` at `ticket(review): bug-a-cursor-copies-the-stack-and-never-gives-it-back`, through a throwaway `InProcessTestFixture` case reading `Diagnostics.StreamCount()` either side of each script (added, run, removed). Column three is from the prototype described under *The fix* below, which was then reverted.

| Shape | Today | With the fix |
|---|---|---|
| Loop over a cursor of two rows, body calls an operator that assigns its `var` row parameter | raises `A nil was encountered where a value was expected`, one value left behind | no error, two values left behind |
| Loop over a list of `Binary`, body calls an operator that assigns its `var` parameter | raises `Runtime error: StreamID (10) not found`, two values left behind | no error, two values left behind |
| A `foreach` *inside* the callee over the `var` parameter, caller looping over a list of `Binary` | raises `Runtime error: StreamID (16) not found` | no error, balanced |
| Cursor of two rows where the operator only *reads* its `var` row parameter | balanced, no error | balanced, no error |
| List of `Binary` where the operator only *reads* its `var` parameter | balanced, no error | balanced, no error |
| An ordinary variable as the argument rather than the caller's loop variable | balanced, no error | balanced, no error |
| For comparison, the same two loops assigning to the loop variable **directly** rather than through a call | no error, two values left behind | no error, two values left behind |

The last row is the measurement that settles how much of this ticket is in scope. Assigning to a loop variable has always leaked the value assigned - the loop overwrites the slot on the next iteration with a plain store, because the slot's value is the iterator's - and that leak is recorded as an accepted tradeoff in the `NOTE:` on the borrowed branch of `AssignmentNode`. With the fix the two call shapes leak exactly as much as the equivalent direct assignment and no more, which is the bar: **this ticket removes the double release and the read of a released value; it does not change how much a loop body that overwrites its own loop variable leaks.**

**Older than the loop work.** The release is the one in `AssignmentNode`, and that line is untouched by the loop tickets - the shape has failed since `bug-assigning-a-binary-variable-leaks-its-stream` taught assignment to release what it replaces. The loop work added one more way to reach it, which is the third row above.

## Why the callee cannot tell today

Which slots hold a value they do not own is a compile-time fact: the compiler marks the loop variable's symbol (`Symbol.IsBorrowed`) while it compiles the loop's body, and `AssignmentNode` reads that mark as it is compiled. An operator is compiled once, independently of its call sites, so the callee's parameter symbol carries no such mark however the caller passes its argument, and the run-time stack has no per-slot ownership bit to carry one.

Two rules that are each right on their own, with nothing connecting them:

- the `var` rule ([operand-ownership.md](../../docs/architecture/operand-ownership.md)) - the callee's slot is an alias of the caller's, so the cleanup releases nothing and writes the slot's final value back to the caller;
- the slot rule ([value-lifetime.md](../../docs/architecture/value-lifetime.md)) - a slot owns the value in it, so a write to it releases what it displaced, unless the compiler marked that slot as holding a value it does not own.

## The fix

**Give the callee a slot it really does own.** Where the argument of a `var` operand names a caller slot that holds a value it does not own, the call copies the value for the callee's slot; the callee's own assignments, and any `foreach` inside it, then release that copy, which is theirs to release, and the caller's loop keeps the row or element the iterator owns. This restores the invariant the rest of the design rests on - *everything that receives a value owns what it is given* - rather than adding a second kind of slot at run time, and it needs no run-time ownership bit, no change to `AssignmentNode`, `ForEachNode` or `CleanupOperand`, and nothing at all on the ordinary, non-borrowed path.

It was prototyped end to end and measured as the table above shows; all 39 cases of the three ownership fixtures and all 123 runnable coverage scripts passed with it in place. Four sites:

- **`StackReferenceNode`** (`ImperativeNodes.cs`) gains a public field beside `ByReference` - `ReferencesBorrowedSlot` - carried in `InternalClone` with the others. The node is built per call site, which is the granularity the fact needs: the same operator may be called with a borrowed argument from one site and an owned one from another.
- **`InstructionNodeBase.DetermineDataType`** (`InstructionNode.cs`), `Modifier.Var` branch, sets it from `plan.Symbols[location].IsBorrowed` right after it sets `ByReference`. That branch has already type-tested the node and read the same symbol's `IsConstant` on the line above, so nothing new is needed to reach it.
- **`CallNode.InternalExecute(Program, object[])`** (`ImperativeNodes.cs`) pushes a copy for such an operand. There is already a reason to copy an operand - `ReferencesAnEarlierOperandsSlot`, for one variable passed twice by reference - so this is a second arm on the same decision: add a sibling predicate (`ReferencesABorrowedSlot(int index)` - the node is a `StackReferenceNode`, `ByReference`, and `ReferencesBorrowedSlot`) and keep the copies in a lazily allocated `object[]` so the hand-back can see them.
- **The hand-back**, in that method's `finally`, reconciles the borrowed operands and is what keeps the read-only path free. For an operand copied because its caller slot is borrowed: if the slot's final value is still the copy, the body never replaced it, so release the copy and leave `arguments[index]` holding the caller's original value - the cleanup's write-back then stores the caller's own value back into its own slot, which is a no-op and exactly what the cleanup does on the unchanged non-borrowed path. Otherwise the body replaced the copy and released it, and `arguments[index]` takes the slot's final value as it does today, so the caller sees the operator's output. The same-value test is `Stack.IsSameValue`, today `private static` in `Runtime/Stack.cs`: make it `public static`, which the `NOTE:` on `ReferencesAnEarlierOperandsSlot` already anticipated - it asks for the same-value test of `Stack.PokeOwned` to be shared out.

Only `CallNode` acts on the flag, and that is deliberate: a built-in C# instruction node with a `var` operand never pushes a slot and never releases the value it was handed - it returns a replacement, which the cleanup writes back - so there is nothing there to make safe. Worth a one-line `NOTE:` at the predicate so that a future built-in which did release its `var` operand's input meets the rule rather than a silent double release.

### Alternatives weighed and rejected

- **Mark the operand slot and make writes inside the callee leave the value alone** (a run-time per-slot ownership bit). Rejected on two counts. It is the bigger change - `Push`, `Pop`, `PopWindow` and `PopFrame` on the generic `Stack<T>` are non-virtual and shared with the compiler's `Symbols`, and the stack snapshot a cursor owns would have to carry the bits - and it is worse at the thing it is for: a bit that stays set makes *every* write in the callee leak, where the copy makes only the final write-back leak. `AB := X; AB := Y;` leaks both values with the bit and only the first with the copy, which is what a plain assignment to any owned variable does.
- **The loop stops lending and starts owning**, holding a copy of the row or element for the life of each iteration. Removes the class outright and would also collect the leak this ticket leaves behind, but at a row copy per iteration of every `foreach` in every D4 script, which is the engine's hottest imperative loop. Too expensive for the shape it fixes, and it changes what the body of a loop may do to its variable - a decision rather than a fix.

## What to pin

One case beside `AForEachOverAnOperandLeavesTheCallersValueAlone` in `tests/DAE.Server.Tests/AssignmentValueOwnershipTest.cs`, which already covers the three modifiers with an ordinary variable as the argument. The new case is the same seam with the caller's own loop variable as the argument, over a cursor of at least two rows and over a list - two of those shapes raise today and one leaks - and it asserts:

- no error, for each shape, which is the defect;
- that the two shapes whose body assigns leave behind exactly what the equivalent direct assignment to a loop variable leaves behind, measured in the same case with the `StreamsLeftBy` helper the fixture already has for this purpose rather than against nought. `AssertShapeLeavesNoStreams` is the wrong helper for those two: the residual leak is the accepted tradeoff on the borrowed branch of `AssignmentNode`, and a case that asserted nought there would be asserting a fix this ticket is not making;
- and that the read-only and inner-`foreach` shapes balance, with `AssertShapeLeavesNoStreams` - these are the cases that catch a regression in which the fix pays a copy per call on the read path.

Rewrite, rather than append to, the paragraph of the fixture's class summary that describes this seam: it currently names this slug as the open defect.
