## What this is

The second of four tickets building the test plan's layer 4. `test-client-server-fixture` built the child-process server and the client helper; this ticket adds the coverage that needs them, and then removes `tests/DAE.Client.Tests`, which is the remaining half of known defect **K18**.

## Part one: the coverage

Two cases, added to `tests/DAE.Server.Tests/OutOfProcessProtocolTest.cs` against the fixture's existing child server. No second child process.

### A cursor fetched across many batches, navigated and changed through

This is the content of `tests/DAE.Client.Tests/CLI/CLITest.cs`'s `TestCLI`, which has never run on .NET 10. It is worth having because the client fetches rows in blocks of `SessionInfo.FetchCount` (default 20, `src/engine/DAE/SessionInfo.cs`) and a cursor over more rows than that exercises the client-side buffer, the refetch at a batch boundary, and bookmarks and in-place changes that cross one. `CoreWcfProtocolTest`'s cursor case reads two rows and so never leaves the first block.

One case, `ACursorCrossesFetchBatchesAndChangesThroughItself`, doing what the old test did, in this order, with NUnit assertions carrying messages rather than the old `throw new Exception`:

- create a table and insert `FetchCount` rows, read the session's actual `FetchCount` from `SessionInfo` rather than assuming 20;
- open the cursor with `capabilities { navigable, backwardsnavigable, bookmarkable, searchable, updateable }` and sum the identifiers forwards — the sum must be the arithmetic series, which is how the old test checked that every row arrived exactly once;
- `Reset` and walk forwards again, asserting each row's identifier in order;
- `Reset`, step to the second row, `Update` it to a new value and read it back; `Delete` it and assert what the cursor then shows; `Insert` a row and assert the cursor shows it;
- walk the whole cursor again taking a bookmark at the fifth row, then `GotoBookmark` and assert the row it lands on, then `DisposeBookmark`;
- delete every row, insert ten times `FetchCount` rows, and repeat the forward sum and the ordered walk — this is the part that crosses many batch boundaries, which is the point.

**Do not re-port the old project's other two cases.** `TestDeleteAtEOF` and `TestDeleteAtBOF` are already in the suite, in process, as `CursorTest.TestDeleteAtEOF` and `CursorTest.TestDeleteAtBOF` — same expressions, same assertions. They are cursor-at-boundary behaviour, not wire behaviour, and the lowest layer that shows them is where they already are. Add a remark on `CursorTest` naming the old file they came from, so the connection is not lost when it is deleted.

### One connection seeing another connection's schema change

`LocalServer` holds a client-side catalog cache and starts an engine of its own to compile against it, refreshed against the server's `CacheTimeStamp`. Nothing covers it: every fixture in the suite has at most one client-side engine, and in process a second one cannot exist without disturbing the first (`bug-object-id-counter-is-process-wide`). Two client connections to a child server is the configuration the product actually runs in, and the first place this behaviour is reachable.

One case, `ASchemaChangeOnOneConnectionIsVisibleOnAnother`, with two `ProtocolClient`s against the same child server:

- on connection A, create a table and insert a row; on connection B — connected **before** A's statement ran, so that B's cache predates it — compile and run an expression naming that table and assert the row comes back. Compiling is the point: a stale client-side cache fails at compile time with an unresolved identifier, not at execution.
- then on B, create a second table; on A, read it. Both directions, because the cache is per connection and a refresh in one is no evidence about the other.
- then on A, drop the first table, and on B assert that compiling the same expression now fails. A cache that only ever grows would pass the first two halves and fail here, which is the part worth having.

Build B's client **after** A's, so that `ProtocolClient`'s object-id-counter restoration is actually load-bearing (`test-client-server-fixture` reworded its remark for exactly this case); if it turns out not to be needed here, say so in the handoff rather than quietly removing it, because `bug-object-id-counter-is-process-wide` records the workaround as this layer's inheritance.

### What this ticket deliberately does not add

Say it in the fixture's remarks, so a reviewer does not read it as an omission:

- **Streams, the message-size quotas and fault typing** are pinned by `CoreWcfProtocolTest` against the real host over a real socket. The client-side stream manager and the server-side one are separate objects whether or not they share a process, so moving the host to another program exercises no new code in that path. One test per behaviour.
- **The abandoned-session clock** belongs to `test-client-server-abandoned`; the in-process lock-release assertions belong to `AbandonedSessionCleanupTest` and are not repeated anywhere.

## Edge cases & interactions

How each is covered: **(test)** a case asserts it, **(seam)** an assertion or guard in code, **(inspection)** read and reasoned about, no test.

- **`FetchCount` is not 20.** *(seam)* Read it from the session rather than hard-coding it, as the old test did. A future change to the default must change what the test inserts, not break it.
- **The arithmetic-series check passes for the wrong reason.** *(test)* The old test checked only the sum; a cursor that returned the right rows in the wrong order would pass it. The ordered walk after the first `Reset` is what closes that, and it is in the case for that reason — keep both.
- **`Update`, `Delete` and `Insert` through a cursor shift what "the current row" is.** *(test)* Assert the row the cursor shows after each, as the old test did; these are the assertions that encode the behaviour and must not be loosened to make a run green.
- **A bookmark taken in one fetch batch and used from another.** *(test)* Take it at the fifth row of the ten-times-`FetchCount` walk so it is certainly in a batch the cursor has since left, and dispose it.
- **A cursor left open when a case fails.** *(seam)* `CloseCursor` in a `finally`, and the row from `Plan.RequestRow` released in a `finally`, as both the old test and `CursorTest` do.
- **The client-side cache refresh direction.** *(test)* Both directions and a drop, as above. A cache that refreshes only on connect would pass a single-direction case.
- **Two client-side engines in the test process.** *(seam)* `ProtocolClient`'s object-id-counter restoration. Report in the handoff whether it was actually needed; this is the suite's only place with two live client engines.
- **Table names colliding between cases.** *(seam)* The fixture's child server is shared by every case in it and its catalog persists for the fixture's life, so each case needs its own names (or names derived from the case). `SchemaCacheInvalidationTest` solves this with a counter and a `Unique` helper; do the same rather than trusting case order.
- **Case order.** *(inspection)* NUnit's order within a fixture is not something to rely on. No case may depend on another's objects existing or not existing.
- **The deleted project's binaries.** *(inspection)* `nunit.mocks.dll` and `pnunit.framework.dll` are checked-in binaries; `hygiene-large-binaries` set the expectation for these. They go with the folder; check `.gitattributes` has no entry naming them.
- **Nothing else references the deleted project.** *(seam)* Grep the whole tree for `DAE.Client.Tests` after deleting and confirm the only remaining mentions are historical ones in `tickets/complete/` and in this ticket's own handoff.
