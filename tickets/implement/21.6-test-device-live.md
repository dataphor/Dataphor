## What this is

Layer L3's second half: the SQL Server device executing against a real server. The suite has never run it on .NET 10. Four D4 scripts and one deleted C# fixture are waiting for it, and three other places in the suite carry a note saying this ticket owns them.

### What has to run

**The three coverage scripts that need a SQL Server device.** `Transaction.Atomicity.TestMSSQL`, `Transaction.Atomicity.TestDAEMSSQL` and `Transaction.Atomicity.TestMSSQLDAE` are recorded in `tests/DAE.Server.Tests/coverage-manifest.json` as `known-failure` with the error `Unknown identifier "Coverage.Base.CoverageDevice"` and the ticket slug `feat-ws7-devices-and-libraries`, which retires with this cut. Each does `SetDefaultDeviceName("Coverage.Base.CoverageDevice")` and then runs the shared atomicity fragments (`Transaction.Atomicity.SetOne`, `SetTwo`, `Run`, `Cleanup`) against it, so what they test is the engine's transaction atomicity *across a device boundary* - the one thing the memory device cannot show.

The device they want is commented out in `tests/libraries/TestFramework.Coverage.Base/Documents/Device.d4`, and **it must stay commented out**: `test-decouple-coverage-base` took the SQL Server device out of that helper library precisely so the suite needs no DBMS (defect K14), and the coverage template registers that library before every one of the 147 script cases. Restoring the definition there would make the entire suite need a SQL Server.

**The device-coverage script.** `tests/libraries/TestFramework.Coverage.Devices/Documents/TestMSSQLDevice.d4` creates a device, runs the device-coverage harness (`TestDevice(ObjectName('TestDevice'), nil)`) and raises with the message of every failed device case. It is not in `TestFramework.Coverage.Scripts/Documents/`, so the coverage runner never sees it; what used to run it was `tests/DAE.Server.Tests/CoverageDeviceTest.cs`, deleted by `test-server-fixture` - read it at `git show 02841882^:Tests/DAE.Server.Tests/CoverageDeviceTest.cs`. That test reset a database named `DataphorTests` on `localhost`, registered `TestFramework.Coverage.Devices` and ran the script. Its replacement does the same against the configured server, on `TestServerInstance`.

### The design

**One environment variable, the one that already exists.** `DATAPHOR_TEST_MSSQL` names a SQL Server (not a database) for `MSSQLStoreContractTests`, which puts its own database on whatever is set - for example `Data Source=(localdb)\MSSQLLocalDB;Integrated Security=SSPI`. Reuse it rather than adding a second: one variable for "a SQL Server this machine may be tested against" is what a developer will expect, and `AGENTS.md` already documents it. Parse it with the client's own connection-string builder to get the data source, the integrated-security flag and any credentials, and build the device's tags (`ServerName`, `UseIntegratedSecurity` or `UserName`/`Password`) from them; the database is this pass's own, named by the pass (as the store contract names its own `DataphorStoreContract`), and the SQL Server device creates a database that does not exist by default (`ShouldEnsureDatabase`), so nothing has to create it by hand.

Put the parsing in one place - `TestEnvironment` is where the suite's environment knowledge lives - so the coverage runner and the new fixture read the same thing.

**A manifest status for "needs a database server".** The manifest's vocabulary today is `pass`, `known-failure`, `unstable` and `fragment` (`CoverageManifest.cs` documents the format). Add a fifth meaning *this script needs a configured database server*: with no server configured the case reports Inconclusive with the reason, as the three sample-corpus cases do; with one configured it must pass, and a failure fails the run. That is exactly what the plan's L3 row asks for - "live tests skipped *visibly* (reported as inconclusive, counted)" - and it keeps a green run's definition honest, because a script that silently stopped being run is the failure mode this manifest exists to prevent.

An entry with the new status also needs the device created before the script runs. The manifest already supports `preamble` (D4 run first) and `register` (libraries registered first). Have the runner, for an entry with the new status, prepend a device-creation preamble built from the configured connection - `SetLibrary('Coverage.Base'); create device CoverageDevice ... class "MSSQLDevice.MSSQLDevice" attributes { ... }` - before any `preamble` the entry carries, and register `MSSQLDevice` for it. Document the shape on `CoverageManifest` with the rest of the format. Note the commented-out definition in `Device.d4` names the class as `"MSSQLDevice"`, which is not a registered class alias; the alias is `"MSSQLDevice.MSSQLDevice"`.

**A C# fixture for the device-coverage script**, `LiveDeviceTest`, which registers `TestFramework.Coverage.Devices` on a `TestServerInstance` and runs `TestMSSQLDevice`, reporting Inconclusive with the reason when no server is configured. Both `TestMSSQLDevice.d4` and `DeviceMSSQL.d4` hard-code `ServerName` (`"."` and `"localhost"`) and `DatabaseName` `"DataphorTests"`, which no configurable run can honour, and D4 has no way to read an environment variable. So **the fixture creates the device and the scripts stop creating one**: drop the `SafeDrop`/`create device` block from each script and leave everything after it (`EnsureDeviceStarted`, `SetDefaultDeviceName`, the cases and the failure roll-up) untouched. That is a change to how the device is obtained, not to an assertion; every expected value in those scripts stays exactly as it is, which the project rules require.

**A server in CI.** The GitHub `windows-latest` runner image has carried SQL Server Express LocalDB; confirm it on the actual image rather than from here, by reading `sqllocaldb info` in a first run. If it is there, start it and set `DATAPHOR_TEST_MSSQL` for the test step in `.github/workflows/build.yml`, which turns on both the store contract's 14 cases and this pass. If it is not, **leave CI without a server, say so in the workflow with a comment and in the handoff, and let the cases report Inconclusive there** - a red CI because a runner image changed is worse than a documented gap. Either way report what the step added to CI's wall clock; CI runs the whole suite twice (Debug and Release) and takes about 18 minutes today.

## Edge cases & interactions

- **The coverage template must still need no database.** The template instance is built once and copied per script; if the device-creation preamble ever ran there, every one of the 147 cases would need a server. Prove it the obvious way: run the whole coverage pass with `DATAPHOR_TEST_MSSQL` **unset** and confirm the counts are unchanged except that the three entries moved from Skipped-as-known-failure to Skipped-as-inconclusive.
- **A connection attempt against an absent server is slow.** The samples measurement is the warning: 54.6 s for two attempts. Anything that connects must be behind the variable, and nothing may try to connect to decide whether to try - the variable being set is the only test.
- **The three scripts share fragments with their memory-device siblings.** `Transaction.Atomicity.SetOne`, `SetTwo`, `Run` and `Cleanup` are `fragment` entries whose `partOf` lists all four atomicity scripts, including `Transaction.Atomicity.TestDAE`, which passes today on the memory device. Changing a fragment to suit the SQL Server variants would change the passing one too. Change no fragment; if one needs changing, that is a finding, not a fix to slip in.
- **These scripts have never passed on .NET 10, so expect failures that are not about the device.** They may fail on a real engine defect, on the new client, or on something the scripts themselves assume about a 2008-era SQL Server. Triage each: a defect in our code becomes a `fix/` ticket naming the script and the statement; a script that predates 3.1 and asserts something no longer true belongs with `test-pre-3-1-scripts-policy`, which already owns that question for sixteen scripts; and the manifest records whatever the truth turns out to be, as a `known-failure` with a ticket slug and the error text if it cannot be fixed here. **Do not leave a script recorded as passing that does not pass, and do not change an expected value to make one pass.**
- **The device-coverage script is large and its failure message is a roll-up.** `TestMSSQLDevice` collects every failed device case into one error. Make the fixture surface the whole message, not a truncation: the first run's output is the data that tells whoever reads it what the device actually does wrong, and a clipped message wastes the run.
- **A timeout is a likely first result.** The coverage runner's default is 120 s per script and entries may carry `timeoutSeconds`. A device script against LocalDB may need more; set it per entry with a measured number rather than raising the default.
- **`bug-binary-comparison-needs-the-mssql-device` (backlog) is the mirror of this gap** - a server with the shared SQL device library registered and the SQL Server one not registered answers `<>` on two `Binary` values with a class-alias error. Registering `MSSQLDevice` for the live cases changes which configuration those cases run in, so a case here may pass where the memory-device sibling fails, or the reverse. Do not fix that ticket here; if a live run touches it, add the observation to it as an arm.
- **`DATAPHOR_TEST_LOGGING` interacts with everything live.** With it set, instances are kept; a device that created a database on a real server leaves that database behind, exactly as `MSSQLStoreContractTests` leaves its own. Follow that fixture's rule: empty or drop at the *start* of a case rather than at the end, so a kept run can be looked at and the next run is not poisoned. Its review notes say why.
- **Two runs against one server at once would collide** on the pass's fixed database name, as the store contract fixture's own `NOTE:` says of its database. Record the same `NOTE:` here rather than inventing per-run names; nothing in the suite runs in parallel.
- **New tests, and they are the point.** Everything here is the project rules' characterization test for a subsystem that is being re-hosted and has no coverage. What must not appear is a new assertion invented in C# about what the device ought to do: the scripts are the oracle (decision D2). The fixture's job is to run them and report.
