## What is wrong

A call evaluates its arguments, runs the operator, and then cleans each argument up - releasing the value where the call owns it, writing it back where the operand was passed by reference. The cleanup (`InstructionNodeBase.CleanupOperand`) lives in a `finally`, but **the arguments are evaluated before the `try` that `finally` belongs to**. So when evaluating argument 2 raises, nothing cleans up argument 1, and whatever argument 1 produced is orphaned: the engine holds its large values - `Binary` and `Graphic` - in a stream the server owns, and an orphaned stream is given back only when the process ends.

The one site is the argument-evaluation prologue of the execute shapes in `src/engine/DAE/Runtime.Instructions/InstructionNode.cs`, each of which reads

```
object argument1 = Nodes[0].Execute(program);
object argument2 = Nodes[1].Execute(program);
try { ... } finally { CleanupOperand(...); CleanupOperand(...); }
```

Three of the four shapes have the defect. `UnaryInstructionNode` does not and needs no change: it has one argument, so nothing can have been evaluated before the argument that raises.

## Measured

Verified 2026-11-24 against the current `modernization` head (`67cdbfb4`), through a throwaway fixture on `tests/DAE.Server.Tests` that read `Diagnostics.StreamCount()` either side of each script. The fixture was removed again and is not in the tree. **Each of the three shapes is reachable from ordinary D4 and each orphaned exactly one stream per run:**

| Shape | D4 that reaches it | Streams held afterwards |
|---|---|---|
| `InstructionNode` - a call of a declared operator, through `CallNode` | `ZProbeTwoConst(Binary('0001'), ZProbeRaises())`, where `ZProbeTwoConst(const AB : Binary, const AC : Binary) : Integer` and `ZProbeRaises() : Binary` raises | +1 (the `Binary('0001')`) |
| `BinaryInstructionNode`, through `BinaryEqualNode` (`src/engine/DAE/Runtime.Instructions/BinaryNodes.cs`) | `Binary('0001') = ZProbeRaises()` | +1 |
| `TernaryInstructionNode`, through `ListInsertNode` (`src/engine/DAE/Runtime.Instructions/ListNodes.cs`) | `Insert(var LList, Binary('0002'), ZProbeRaisesInt())` with `var LList : list(Binary) := { Binary('0001') }` | +1 (the `Binary('0002')`) |

Each script raised, as it should. Every repetition costs another stream.

Two facts from the same session, which the test cases below rest on:

- `Insert` is declared in `src/engine/DAE/Schema/SystemCatalog.d4` as `Insert(var AList : list, AValue : generic, const AIndex : Integer)`, so its middle operand is by value and the call owns the `Binary` handed to it, and its first operand is `var` - which is why that one script exercises both arms of the rule at once.
- Nothing is lost today beyond the memory. With a `var` operand *after* the raising argument - `ZProbeVarLast(Binary('0002'), ZProbeRaises(), var LB)` - the caller's `LB` still read its original value afterwards and the error still reached the caller. That is worth keeping true; see the next section.

This is older than the ownership work: before `bug-an-operator-argument-is-released-by-the-wrong-owner` a `const` argument's value was never released on *any* path, so the error path was no worse than the normal one. That ticket closed the normal path and left this one, which is why it is worth closing now: the normal path being right is what makes this the only shape in which a call still orphans an argument.

## Expected behaviour

A statement that raises while working out a call's arguments leaves the server holding no more streams than before the statement, exactly as a statement that raises inside the operator's body already does. Nothing else about the call changes: the caller's own variables keep their values, and the error the caller sees is the one the argument raised.

## What makes this more than moving two lines into the `try`

**A by-reference operand must not be written back when the call never happened.** `CleanupOperand`'s `Modifier.Var` branch pokes the value it is given into the caller's slot, after passing it through `ValueUtility.ValidateValue`. On an argument-evaluation failure there is no callee value to write back - the callee's slots were never pushed, and `argumentValue` for an argument never evaluated is null. Poking that into the caller's slot would nil the caller's variable, turning a leak into data loss; and `ValueUtility.ValidateValue` (`src/engine/DAE/Runtime/ValueUtility.cs`) runs the scalar type's constraints and its validate handlers, which is user D4, so running it while an error unwinds could also raise and replace the error the caller should have seen. **So the cleanup that runs on an argument-evaluation failure is not the cleanup that runs after the call:** it releases the values the call owns and leaves every `var` operand alone.

**Only the arguments actually evaluated may be released.** A failure at argument 2 of 3 must release argument 1 and nothing else.

**It is the hottest path in the engine.** Every operator call in every D4 statement runs one of these shapes, so whatever the fix costs is paid per call. The shape below was chosen so that **the normal path executes exactly the instructions it executes today**: entering a `try` region costs nothing at run time when nothing is thrown, and the only new code sits inside a `catch` that runs only while an error propagates.

## The shape to build

One new method on `InstructionNodeBase`, beside `CleanupOperand`, carrying the whole failure-path rule once rather than three copies of a switch:

```csharp
/// <summary>Releases the value evaluated for an operand of a call that never happened, because a later argument raised.</summary>
protected void ReleaseUncalledOperand(Program program, Schema.SignatureElement signatureElement, PlanNode argumentNode, object argumentValue)
{
	switch (signatureElement.Modifier)
	{
		case Modifier.Var :
			// Nothing, deliberately. No callee slot was ever pushed, so there is no callee value to hand back and the
			// caller's slot still holds and owns what it held before the call. CleanupOperand's write-back would poke
			// the value of an operand that may never have been evaluated - null - into the caller's variable, and would
			// run the type's constraints and validate handlers (ValueUtility.ValidateValue) while an error unwinds.
		break;

		case Modifier.In :
			DataValue.DisposeValue(program.ValueManager, argumentValue);
		break;

		case Modifier.Const :
			if (!argumentNode.ReturnsByReference)
				DataValue.DisposeValue(program.ValueManager, argumentValue);
		break;
	}
}
```

The `In` and `Const` branches are the same rule as `CleanupOperand`'s, for the same reasons recorded there, and should stay readable as the same rule - a reader comparing the two methods should see one modifier handled differently and the rest identical. `Modifier.Out` falls through to nothing in both, as it does today.

Then, per shape, a `catch` around the evaluation of every argument after the first. `Operator` can be null, and the existing `finally` in each shape already guards on that; the failure path guards the same way, because without an operator there are no modifiers to read and nothing can be released. Release order among the evaluated arguments is immaterial - the values are independent - so keep `CleanupOperand`'s forward order.

`BinaryInstructionNode`:

```csharp
object argument1 = Nodes[0].Execute(program);
object argument2;
try
{
	argument2 = Nodes[1].Execute(program);
}
catch
{
	if (Operator != null)
		ReleaseUncalledOperand(program, Operator.Signature[0], Nodes[0], argument1);
	throw;
}
```

`TernaryInstructionNode` - one `catch` over both later arguments, with `argument2` left null when it was the one that raised, which `DataValue.DisposeValue` treats as nothing to release (it falls through every type test):

```csharp
object argument1 = Nodes[0].Execute(program);
object argument2 = null;
object argument3;
try
{
	argument2 = Nodes[1].Execute(program);
	argument3 = Nodes[2].Execute(program);
}
catch
{
	if (Operator != null)
	{
		ReleaseUncalledOperand(program, Operator.Signature[0], Nodes[0], argument1);
		// null when argument 2 was the argument that raised, which releases nothing.
		ReleaseUncalledOperand(program, Operator.Signature[1], Nodes[1], argument2);
	}
	throw;
}
```

`InstructionNode`, the general shape - the existing loop counter becomes the count of arguments evaluated, so the normal path gains no store:

```csharp
object[] arguments = new object[NodeCount];
int evaluated = 0;
try
{
	for (; evaluated < arguments.Length; evaluated++)
		arguments[evaluated] = Nodes[evaluated].Execute(program);
}
catch
{
	if (Operator != null)
		for (int index = 0; (index < evaluated) && (index < Operator.Operands.Count); index++)
			ReleaseUncalledOperand(program, Operator.Signature[index], Nodes[index], arguments[index]);
	throw;
}
```

The second bound is there because the existing `finally` iterates `Operator.Operands.Count` while the evaluation loop iterates `NodeCount`; the failure path must release no more than the normal path cleans up, whatever the relationship between those two turns out to be.

Use `catch { ...; throw; }` rather than `catch (Exception)`, so the error and its stack trace reach the caller unchanged. If a release inside the `catch` were itself to throw it would replace the original error - the existing `CleanupOperand` in the `finally` has had exactly that exposure since the beginning, so this adds no new risk and needs no wrapper.

## Edge cases and interactions, all checked

- **An operand whose node lends rather than gives.** A `const` operand given a variable is handed the stack slot's own value (`PlanNode.ReturnsByReference`), and that must not be released on the failure path any more than on the normal one. The rule is in [docs/architecture/value-lifetime.md](../../docs/architecture/value-lifetime.md); going through the node's own answer, as above, is what honours it.
- **`CallNode` pushes nothing until all arguments are evaluated** (`CallNode.InternalExecute` receives the finished `arguments` array), so a failure in the prologue leaves the stack untouched and no operand slot exists to hand a value back from. The fix is entirely in the execute shapes; `CleanupOperand` itself needs no new branch.
- **The `IsBreakable` window.** Each shape pushes its stack window inside the `try`, after argument evaluation, so an argument-evaluation failure has no window to pop.
- **`CleanupOperand` has exactly one set of callers.** Grepped: only the four shapes in `InstructionNode.cs`. `AggregateCallNode` derives from `PlanNode` and evaluates nothing through this path, so it is out of scope.
- **A `NOTE:` on `CleanupOperand` records this defect and names this ticket.** Remove it when the fix lands.

## The test

`tests/DAE.Server.Tests/AssignmentValueOwnershipTest.cs` already owns the operand half of the ownership rule and already has the helpers: `AssertShapeLeavesNoStreams(shape, script)` for a script inside an `Assert.Multiple`, and `AssertRaisingScriptLeavesNoStreams(script, errorText)` for one that must raise. Follow the file's idiom (see `AConstOperandReleasesTheValueComputedForIt`): **one case, `Assert.Multiple` over the three shapes**, so a shape-specific regression is not hidden by another shape's failure and the three edited sites are each pinned.

The three shapes are the three rows of the table above. Two points of substance:

- The declared-operator shape should put the `var` operand **after** the raising argument - `ZProbeVarLast(Binary('0002'), ZProbeRaises(), var LB)` with `ZProbeVarLast(const AB : Binary, const AC : Binary, var AD : Binary) : Integer` - and assert afterwards that the caller's `LB` is neither nil nor changed. That is what pins the write-back half of the rule: the case passes today on the value and fails on the count, and it fails on the value under the naive fix that simply moves the argument evaluation inside the existing `try`.
- Every script must assert that it raised, or catch its own error in D4 and assert that it caught one, so that a case which silently stopped raising cannot pass while testing nothing - the standard this file already holds itself to.

The nil test in D4 is `IsNil(LB)`; `LB is nil` is a syntax error.
