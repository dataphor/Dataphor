## What this is

The ticket that finishes the PostgreSQL work item. Its two prerequisites leave the connection library and the device library building against the current driver with their translation pinned by golden files; what is left is the part the plan says cannot be done by reading: *"Fifteen years of driver changes sit in between - type mapping (timestamps and time zones, numerics, booleans, large objects), parameter handling, connection-string keywords, error codes - so this is driven by the live tests, not by getting it to compile. The device has had little maintenance since 2017; expect to find its own defects too."*

So: run it against a real PostgreSQL server, fix what breaks, and write down the oldest version it supports.

### How to get a server, and what to do when there is none

Follow the pattern `test-device-live` (prerequisite) established for SQL Server: **one environment variable** names the server, the live cases report Inconclusive with the reason when it is unset, and the parsing lives in `TestEnvironment` beside the SQL Server one. Name it for PostgreSQL (`DATAPHOR_TEST_PGSQL`) and document it in `AGENTS.md` beside the others.

Docker is installed on this machine (`docker --version` reports 24.0.6) and the official `postgres` image is the practical way to get a server: a container with a password and a published port, and the variable pointing at it. **If the Docker daemon is not running or the image cannot be pulled, do not fake a result.** Do everything that does not need a server - the harness, the Inconclusive paths, every defect findable by reading - report exactly what could not be run, and say in the handoff and in the plan row that the device is not yet proved live. That is a complete delivery of what was possible; a matrix of guesses is not.

### What to run

The suite has a device-coverage harness already: `tests/libraries/TestFramework.Coverage.Devices` holds `TestDevice(...)`, a D4 operator that runs a table of device cases against a named device and collects the failures, plus `TestMSSQLDevice.d4` which drives it for SQL Server. There is also `DeviceOracle.d4`, a parked sibling, which shows the intended shape: one driver script per device. **Add the PostgreSQL one**, in the same style, and a `LivePGSQLDeviceTest` fixture that registers the library and runs it against the configured server, as `test-device-live`'s fixture does for SQL Server. Reuse, do not re-invent: the device cases are the oracle, and a C# assertion invented here about what PostgreSQL ought to do would be a new specification rather than a test (decision D2).

Expect the first run to fail in bulk. That is the information this ticket exists to produce.

### The defects to expect, from reading

Each of these is a specific thing to check, not a guess at a cause:

- **Timestamps and time zones.** `PostgreSQLCommand.PrepareParameters` maps D4's `DateTime` to `NpgsqlDbType.Timestamp`. Npgsql 6 changed the rules: `timestamp without time zone` rejects a `DateTime` whose `Kind` is `Utc`, and `timestamptz` requires one. D4's `DateTime` carries no zone. Find out what `Kind` the engine's conveyor produces and make the mapping right for it; this is the most likely single source of failure in the port.
- **The locking clause on the key-check select.** The device translates a retrieve that needs an update lock into a `for update` clause on the select (`PostgreSQLRetrieve`, where the `NOTE:` at the site says the same). Unlike SQL Server's `(updlock)`, which rides on the table reference, that is a clause of the select statement - and the engine puts this select inside an `exists` in the select list of the statement in front of every insert into a device table, so the clause ends up nested there: read `tests/goldens/devices/PGSQL/DML.Insert.sql`, which pins exactly that text. Settle both halves: whether PostgreSQL accepts a locking clause in that position at all, and whether it takes the lock the key check needs. A rejection affects every insert into a PostgreSQL device table rather than an edge case, so run an insert early.
- **Numerics.** An eight-byte `SQLIntegerType` is mapped to `NpgsqlDbType.Numeric` with precision 20 and scale 0 rather than to `bigint`, deliberately (D4's `ULong` does not fit `bigint`). Check it still round-trips, and check `SQLNumericType`'s precision and scale still arrive.
- **Booleans.** `PGSQLStoreConnection` has an override saying this back end's boolean columns are declared `boolean` where the other stores use an integer, so a parameter must carry the `bool` itself. The device's side of the same question is in `PostgreSQLTypes.cs`; check the two agree.
- **Large objects.** `SQLBinaryType` maps to `bytea`. The 2009 driver and the current one handle large values differently (streaming, size limits); the device's deferred-stream path (`SQLCursor.InternalOpenDeferredStream`) is where that shows.
- **Error codes.** `PostgreSQLConnection.InternalWrapException` flattens every driver exception into a plain `Exception`, losing the code that would distinguish a constraint violation from a connection failure - the SQL Server connection class distinguishes them (`IsUserCorrectableError`, `IsTransactionFailure`) and the engine's error severity depends on it. The prerequisite recorded this as a `NOTE:` rather than changing it. This is the ticket that can see the difference: decide, measure, and fix it if the live cases show the severity being wrong.
- **Identifier folding.** PostgreSQL folds unquoted identifiers to lower case. `PostgreSQLStoreConnection.HasTable` already lower-cases a name before looking it up, which suggests the device has had to deal with this; check how the device's emitter quotes identifiers and whether reconciliation finds tables it created.
- **Isolation levels.** `PostgreSQLConnection.InternalBeginTransaction` maps `ReadUncommitted` and `RepeatableRead` both onto `ReadCommitted`, with a comment about "this Optimistic system". PostgreSQL has had real `repeatable read` and `serializable` for many years. Leave the mapping alone unless a live case shows it wrong - a change there is a semantic change to what a D4 transaction means against this device - and if a case does show it wrong, say so and consider whether it is this ticket's to change or a question for `blocked/`.

### The version to document

The plan asks for the minimum supported PostgreSQL version to be documented. Decide it the way Q12 decided SQL Server's: the versions of roughly the last five years, tested where a server can be had. Record the version string of every server actually run against, with what passed and what failed, in `docs/users-guide/dataphor-service.md` beside the SQL Server matrix.

## Edge cases & interactions

- **A failure is not automatically ours.** Three kinds will turn up and must be told apart in the handoff: a defect in our code (fix it, with its reproduction); a device case that asserts something that was true of PostgreSQL 8 and is not true now (that is the same question `test-pre-3-1-scripts-policy` owns for the engine's pre-3.1 scripts - route it there as an arm, and never edit an expected value to make a case pass); and a device feature that was never finished (record it, do not implement it here).
- **Fix locally, file what is structural.** The project rules are explicit: a defect with a local, obvious fix is fixed in the ticket that meets it, with its reproduction; one whose fix changes a design or a compatibility surface becomes its own ticket. A type mapping is usually the first; an isolation-level mapping or an error-severity contract is the second.
- **The golden files are the regression net for every fix.** Any change to translation shows up as a golden diff from `device-pgsql-device-golden`. Read every diff; a fix that changes generated SQL for the SQL Server device too would show in *its* goldens, and that would be a mistake in the fix rather than in the goldens.
- **The catalog store is in scope only conditionally.** The plan says to port the PostgreSQL catalog store "if it then needs only the store contract tests to pass". `store-pgsql-port` holds that work and depends only on the connection port, so it may well have landed before this ticket runs. If it has, run its 14 contract cases against the same server and report them with the rest; if it has not, say so and leave it.
- **One server, one database, no parallel runs.** Follow `MSSQLStoreContractTests`' rules: a database named after this pass, emptied at the *start* of a case rather than at the end so a kept run (`DATAPHOR_TEST_LOGGING`) can be looked at, and a `NOTE:` saying two simultaneous runs against one server would collide.
- **Connecting to an absent server is slow**, and the samples measurement (54.6 s for two attempts) is the warning. Nothing may connect to decide whether to connect; the variable being set is the only test.
- **CI stays as it is unless a server is free.** The `windows-latest` runner image has carried PostgreSQL as a stopped service; if it does, starting it and setting the variable is a small step with a real payoff, and the cost in wall clock must be reported. If it does not, leave CI alone with a comment saying why.
- **New tests, and they are the point** - the characterization tests for a subsystem being re-hosted. What must not appear: a mock of anything this repository owns, or a case that passes because the device silently did nothing.
