## What this is

`System.Data.SqlClient` is the .NET Framework-era SQL Server driver, shipped now only as a compatibility package and no longer developed. `Microsoft.Data.SqlClient` replaces it. The plan's WS7 table and decision D15 both say to move, and the migration notes already carry the change twice as `planned` (one line about device definitions, one about a custom extension that reaches through a Dataphor connection to the client's own types).

### Every site

The repository has one SQL Server client and five places that use it:

| Site | What it does | Package reference |
|---|---|---|
| `src/engine/Server/Connection/MSSQLConnection.cs`, `MSSQLCommand.cs`, `MSSQLServerCursor.cs` | the `SQLConnection` implementation the SQL Server device uses, including its server-side cursors over `sp_cursoropen`/`sp_cursorfetch` | `Server.csproj` |
| `src/engine/Store.MSSQL/MSSQLStore.cs`, `MSSQLStoreConnection.cs` | the SQL Server catalog store | none of its own - it uses the one `Server.csproj` brings (the project file says so) |
| `libraries/Connection/Source/Operators.cs` | `ClearAllPoolsNode`, behind the D4 operator `Connection.ClearAllPools()` | `DAE.Connection.csproj` |
| `src/engine/DAE/Server/Engine.cs` | `Engine.Dispose` clears the client's pools, as 3.1 did | `DAE.csproj` - the engine's **only** reason to reference a SQL client |
| `src/engine/Store.PGSQL/PGSQLStore.cs`, `PGSQLStoreConnection.cs` | a `using` and a dead `#else` branch (`USESQLCONNECTION` is defined) | none |

Each of the four project files carries a comment saying the move is this ticket's; the comments go with the change. `Directory.Packages.props` loses `System.Data.SqlClient` and gains `Microsoft.Data.SqlClient` at the current stable version - record which version you used and in which document.

**The engine must not keep a SQL Server client.** `Engine.Dispose`'s `SqlConnection.ClearAllPools()` is the only thing in `DAE.csproj` that needs one, and a bare `Engine` cannot have opened a SQL Server connection: the connection classes are in the server assembly. Move the call into a `Dispose(bool)` override on `Server` (`src/engine/Server/Server/Server.cs`, which derives from `Engine` and does not override it today), after `base.Dispose(disposing)` so the ordering is what it is now, and drop the package from `DAE.csproj`. Say in the handoff why that is the right home rather than a hook or an interface: the assembly that owns the client owns clearing its pools.

### The compatibility trap, and how to answer it

`Microsoft.Data.SqlClient` defaults `Encrypt` to on and validates the server's certificate; `System.Data.SqlClient` did neither. A device definition that connected in 3.1 - server name, database name, integrated security and nothing else - would stop connecting against a server with a self-signed or absent certificate, which is the normal state of an internal SQL Server. The plan's decision is already made and is not open here: **keep 3.1's connection defaults unless the device's own settings say otherwise, and document it.**

The device side has a clean place for that. `MSSQLDeviceSession.InternalCreateConnection` builds the connection string in three steps: the device's own tags (`ServerName`, `DatabaseName`, `ApplicationName`, and either `IntegratedSecurity` or user name and password) are mapped through a `ConnectionStringBuilder`; `ConnectionStringBuilder.Map` then applies its `_parameters` over the result; and `SQLDevice.GetConnectionParameters` then applies the device's `ConnectionParameters` setting and the device session's, over everything. So adding the compatibility default to `MSSQLADODotNetConnectionStringBuilder._parameters` (in `libraries/MSSQLDevice/Source/Device.MSSQL/MSSQLConnectionStringBuilder.cs`) gives exactly the precedence wanted: the default applies, and a device definition that sets `'ConnectionParameters'='Encrypt=True'` - or `Strict`, or `TrustServerCertificate=False` - overrides it. None of the tags the device session produces is named `Encrypt` or `TrustServerCertificate`, so nothing collides.

Choose between `Encrypt=False` and `TrustServerCertificate=True` and say why in a comment at the site and in the migration note. They are not the same: the first negotiates no encryption, which is what 3.1 did; the second encrypts but accepts any certificate. "Keep the old defaults" points at the first; a reader will want to know the choice was deliberate.

The **store** needs the same treatment and has no device settings: `catalogstoreconnectionstring` is written by a deployment as raw text. `MSSQLStore.InternalInitialize` already forces `MultipleActiveResultSets=True` into the connection string with a comment saying why, so the precedent and the place both exist - default the same setting there **only when the connection string sets neither `Encrypt` nor `TrustServerCertificate`**, so a deployment that has chosen is left alone. `docs/users-guide/dataphor-service.md` is where a deployment reads about that setting and already says what the store needs; it gains a sentence.

## Edge cases & interactions

- **`MSSQLConnection.IsZombied` reads a non-public property by reflection.** `transaction.GetType().GetProperty("IsZombied", BindingFlags.Instance | BindingFlags.NonPublic).GetValue(...)`, used by both `InternalCommitTransaction` and `InternalRollbackTransaction`, with a long comment explaining why. If `Microsoft.Data.SqlClient`'s `SqlTransaction` has no such member, `GetProperty` returns null and every commit and rollback through this connection throws `NullReferenceException` - which no test in the suite would catch, because nothing drives the device live. **Verify the member exists on the package version you pin**, and if it does not, use the documented behaviour instead: a zombied `SqlTransaction` reports a null `Connection`. Either way, make the failure loud rather than a null dereference - a missing member must throw something that names what it was looking for. A unit-level case here is not possible without a server; verify by inspection of the package's public and non-public surface and record what you found, and have `test-device-live` confirm it live.
- **The library-loading probe shares a package with the new client, and that breaks a passing test.** `tests/libraries/LibraryLoadingProbe` references `Microsoft.Data.SqlClient.SNI.runtime` **as a deliberately private package**, so the layout flattens its native dll into the library's own folder and `LibraryLoadingTest` asserts the library-local native resolver finds it. `Microsoft.Data.SqlClient` may bring that same package into `Server.csproj`'s closure - and `Directory.Build.targets` marks a package file private only when *no project this one references has the package*, so the probe's copy would stop being private, land in `bin/` instead, and `LibraryLoadingTest.ProbeNativeResolver` would fail. Check the assembled layout after the swap. If it happens, point the probe at a different native-RID package, keep the `NOTE:` in its project file explaining what the package is for, and say in the handoff which package you chose. Verified by the existing test, which is the reproduction.
- **Central package management allows one version per package id.** If both the probe and the client need `Microsoft.Data.SqlClient.SNI.runtime`, they get the same version (4.0.0 is pinned today for the probe alone). The layout also fails the build when two different files would land at one destination, which is the guard that catches a version split.
- **The dependency closure grows.** `Microsoft.Data.SqlClient` brings more than `System.Data.SqlClient` did (configuration, identity and SNI packages, depending on version). Two things read that closure: the runtime layout's `bin/` and the two host executables' `.deps.json`, which `HostProgramTest.TheHostsDependencyFilesNameTheAssembliesTheServerLoadsByName` asserts over every store the layout ships. Run that test, report the `bin/` file count before and after, and name any new assembly a deployment will now see.
- **Server-side cursors are the least-tested path in the change.** `MSSQLCommand`'s `sp_cursoropen` route builds internal parameters in a fixed order and depends on `SqlParameter.Direction = ReturnValue` and on `SqlDbType.NVarChar` out parameters behaving as they did. None of it runs anywhere in the suite. Do not pretend otherwise: say in the handoff that it compiles and is unverified, and leave the live proof to `test-device-live`, which owns running the device-coverage script.
- **The golden translation goldens are the net for this change.** `test-device-sql-golden` (prerequisite) pins the generated SQL through a recorder that replaces the client entirely, so a green golden run after the swap says the translation did not move. It says nothing about execution. State both halves.
- **`SqlDbType` is `System.Data.SqlDbType` in both clients**, so the long type-mapping `switch` in `MSSQLCommand.PrepareParameters` should need only the `using`. Read it rather than assuming; `SqlDbType.Image` and `SqlDbType.Text` are deprecated server types and remain in the enumeration.
- **The `varchar` parameter mapping is a known defect and is not this ticket's.** `PrepareParameters` maps a string parameter to `SqlDbType.VarChar` and `GetParamTypeDescriptor` writes `varchar(n)`, which loses every character outside the server's code page. `device-mssql-string-parameters` owns the fix and its reproduction. Change nothing about it here, so that the client swap stays a swap.
- **`PGSQLStore.cs`'s `using System.Data.SqlClient` is dead** (`USESQLCONNECTION` is defined, and the `#else` branch that used `SqlConnection` is not compiled; the project is not in the solution yet either). Drop the `using` and leave the dead branch to `store-pgsql-port`, or leave the file alone entirely - either is defensible; say which you did and why.
- **Error numbers and severities are unchanged.** `IsTransactionFailure` and `IsUserCorrectableError` switch on SQL Server error numbers, which belong to the server, not the client. Nothing to change; confirm by reading, and note that `SqlError`/`SqlException` keep their shape under the new namespace.
- **No new test, and say why.** The project rules ask a characterization test of a subsystem being re-hosted *unless one already covers it*. Two things cover this one: the golden translation pass that the prerequisite adds, and `MSSQLStoreContractTests`, whose 14 cases run the catalog store contract against a real SQL Server when `DATAPHOR_TEST_MSSQL` is set and skip visibly when it is not. Run both. If a case has to be added anywhere, it is in the store contract fixture, which is the only live SQL Server path the suite has today.
- **Migration notes.** Two `planned` rows become `done`: the device-definition row (which must now say exactly what the default is and how a deployment overrides it) and the namespace row for custom extensions. Add a third if the `ClearAllPools` move changes anything an extension could notice - a custom host that constructs a bare `Engine` and opens SQL Server connections through the server assembly's `MSSQLConnection` would no longer have its pools cleared on dispose. Decide whether that is worth a line and say so either way.
- **`docs/architecture/third-party-code.md`** names the third-party libraries and their versions; the SQL client belongs in it. It is 101 words of its 1,500-word cap.
