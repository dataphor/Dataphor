## What this is

This is the first half of `host-generic-host`, split out so that each half is one coherent change. It moves the Windows service *registration* code off .NET Framework and into a shared assembly; the second half, `host-generic-host`, then builds the server host program on top of it. Nothing about how the server runs changes here.

Today the code that installs, uninstalls and inspects the Windows service lives inside the service executable, `src/hosts/DAEService/` (assembly `DAEService`), in two files:

- `ServiceUtility.cs` — a static class with the members the rest of the product calls: `GetServiceName`, `Install`, `Uninstall`, `GetServiceStatus`, `GetServiceAutoStart`, `SetServiceAutoStart`, plus the `ServiceStatus` enum and the constant `EventLogSource`.
- `ServiceInstaller.cs` — `ProjectInstaller`, a `System.Configuration.Install.Installer` subclass that `ServiceUtility.Install` drives through a `TransactedInstaller`, and which after installing reaches into the registry to append `-name "<instance>"` to the service's `ImagePath`.

`System.Configuration.Install`, `TransactedInstaller`, `Installer`, `ServiceProcessInstaller` and `ServiceInstaller` do not exist on .NET 10. That is the whole of the `DAE.Service` project's compile failure: the spike reports seven errors for it, all of them this.

Two callers matter. The service executable's own `-i` and `-u` switches, and the tray configuration tool `src/windows/ConfigurationUtility` (project `DAE.Service.ConfigurationUtility.csproj`), which has a **project reference to the service executable** and calls `ServiceUtility.Install` and `ServiceUtility.Uninstall` from its Install/Uninstall button (`MainForm.cs`, around lines 435 and 457), `ServiceUtility.GetServiceStatus` and `GetServiceAutoStart` from `ApplicationForm.cs`, and `GetServiceName` and `SetServiceAutoStart` from `MainForm.cs`. Those six members and the `ServiceStatus` enum are the entire surface that tool uses — verified by listing every reference to the assembly from that folder. The tool's own port to .NET 10 is WS6's; it must keep compiling against the same type names and signatures.

## What to build

### A new shared assembly for the host code

Create `src/hosts/Host/`, project file `DAE.Host.csproj`:

| Setting | Value |
|---|---|
| `AssemblyName` | `Alphora.Dataphor.DAE.Host` |
| `RootNamespace` | `Alphora.Dataphor.DAE.Service` |
| `OutputType` | `Library` |
| `TargetFramework` | `net10.0`, from `Directory.Build.props` |
| `DefineConstants` | `TRACE`, plus `DEBUG;TRACE` in Debug, set outright — the convention in `AGENTS.md` |

Follow the conversion rules in the root `AGENTS.md`: explicit `Compile` and `EmbeddedResource` items, no `OutputPath`, package versions in `Directory.Packages.props`, no `NoWarn`.

`RootNamespace` is deliberately `Alphora.Dataphor.DAE.Service` rather than something matching the folder name, for two reasons: the types that move keep the namespace their callers already use, and the embedded resource `Strings.resx` keeps the manifest name `Alphora.Dataphor.DAE.Service.Strings` that `Strings.cs` looks it up by (`EmbeddedResourceUseDependentUponConvention` is off repository-wide, so resource names follow `$(RootNamespace).<file>`). Record both reasons in a comment in the project file.

Why a new assembly rather than keeping the code in `DAEService` and referencing that executable from the host: after `host-generic-host` three programs need this code — `DAEServer.exe`, `DAEService.exe` and, in WS10, the `dataphor` command-line tool (`tool-cli-server-commands`, whose prerequisite is `host-generic-host`) — and an executable project used as a library dependency by two other executables is a shape every later ticket would have to work around. The cost is one additive assembly name and one migration-notes line for the public types that move; the alternative was weighed and rejected.

Add the project to `Dataphor.slnx` (a new `/hosts/` folder) and to the **Bin** list in `tools/layout/Layout.csproj`.

### Files that move into it, unchanged except where stated

- `ServiceUtility.cs` → rewritten, below.
- The `ServiceStatus` enum, declared at the top of `ServiceUtility.cs` → moves with it, unchanged: `Running, Stopped, Unavailable, Unassigned`, in namespace `Alphora.Dataphor.DAE.Service`.
- `Strings.cs` and `Strings.resx` → move unchanged. The resource holds four strings that are used (`ServiceStarting`, `ServiceRunning`, `ServiceStopping`, `InvalidCommandLine`) and one that is not (`CCreatedSettingsFile`); leave all five, because `host-generic-host` uses three of them and localization of this resource is out of scope. Preserve the files' encoding and line endings.

### Files that are deleted

- `src/hosts/DAEService/ServiceInstaller.cs` and `ServiceInstaller.resx` — the installer class and its designer resource. Nothing replaces `ProjectInstaller`; registration becomes `ServiceUtility`'s own code.
- `src/hosts/DAEService/Service.resx` — the designer resource of the `Service` component class, which holds nothing but the default designer header.
- `src/hosts/DAEService/ServerServices.cs` — a stray that is not in the project's compile list and is not valid C#: it declares a constructor named `ServerService` inside a class named `ServerServices`, has an indexer getter with no `return`, and names a type `ServerService` that exists nowhere in the tree. Delete it and say so in the handoff.

Remove the corresponding `Compile` and `EmbeddedResource` items from `DAE.Service.csproj` and drop its now-unused `System.Configuration.Install` reference. Leave that project in legacy format: `host-generic-host` converts it. Add a project reference from it to `..\Host\DAE.Host.csproj` so `Service.cs` still finds `ServiceUtility` and `Strings`, and delete the `using System.Configuration.Install;` line from `Service.cs` — nothing in that file uses it any more, and on .NET 10 a `using` of a missing namespace is a compile error, which would keep the spike's error count for this project artificially high.

### Repointing the configuration utility

In `src/windows/ConfigurationUtility/DAE.Service.ConfigurationUtility.csproj`, change the `ProjectReference` from `..\..\hosts\DAEService\DAE.Service.csproj` to `..\..\hosts\Host\DAE.Host.csproj`. That is the whole change: the namespace, type names and member signatures the tool uses are unchanged, so no `.cs` file in that folder is edited. The project is still in legacy format and is not in `Dataphor.slnx`; WS6 converts it.

### `ServiceUtility` rewritten

Keep the class `public static`, in namespace `Alphora.Dataphor.DAE.Service`, with these members and these signatures:

| Member | Behaviour |
|---|---|
| `public const string EventLogSource = "Dataphor Server"` | unchanged. It is the same string as `Engine.ServerSourceName`; keep the local constant so this assembly needs no reference to the engine |
| `public static string GetServiceName(string instanceName)` | unchanged: `String.Format("Alphora Dataphor ({0})", instanceName)` |
| `public static ServiceStatus GetServiceStatus(string instanceName)` | unchanged implementation: `ServiceController.Status`, mapping Running and Stopped and returning `Unavailable` for everything else and for any exception |
| `public static bool GetServiceAutoStart(string instanceName)` | **new implementation:** `new ServiceController(GetServiceName(instanceName)).StartType == ServiceStartMode.Automatic`; any exception, the service not being installed included, returns `false`, as the missing registry key did |
| `public static void SetServiceAutoStart(string instanceName, bool autoStart)` | **new implementation:** `ChangeServiceConfig` with `dwStartType` `SERVICE_AUTO_START` (2) or `SERVICE_DEMAND_START` (3) and `SERVICE_NO_CHANGE` for every other field. A service that is not installed returns without doing anything and without throwing, exactly as the missing registry key did |
| `public static void Install(string instanceName)` | **new implementation:** registers the service, below |
| `public static void Install(string instanceName, string imagePath)` | **new overload:** the same, with the service binary and its arguments supplied; the single-argument form calls this with the default path |
| `public static void Uninstall(string instanceName)` | **new implementation:** `OpenService` with `DELETE` access, then `DeleteService` |

These members are removed, with one migration-notes line between them: `GetServiceAutoStartRegKeyName`, `ServiceStartModeRegName`, `ServiceAutoStartRegValueName`, `ServiceAutoStart`, `ServiceManualStart`. They exist only to describe the registry layout this class no longer touches.

**What `Install` must register,** so that an in-place upgrade over an existing 3.1 registration is a no-op and the service starts the same way:

| Property | Value | Where it comes from |
|---|---|---|
| service name and display name | `GetServiceName(instanceName)` | `ProjectInstaller.Prepare` set both to this |
| description | `Provides platform services for Dataphor applications.` | `ProjectInstaller.Prepare`; set it with `ChangeServiceConfig2` and `SERVICE_CONFIG_DESCRIPTION` |
| service type | `SERVICE_WIN32_OWN_PROCESS` (0x10) | what `ServiceInstaller` produced |
| start type | `SERVICE_AUTO_START` (2) | `_serviceInstaller.StartType = ServiceStartMode.Automatic` |
| error control | `SERVICE_ERROR_NORMAL` (1) | the installer's default |
| account | LocalSystem, that is `lpServiceStartName` null | `_serviceProcessInstaller.Account = ServiceAccount.LocalSystem` |
| binary path and arguments | `"<folder>\DAEService.exe" -name "<instance>"` | the quoted path the base installer wrote, plus the suffix `ProjectInstaller.Install` appended by rewriting `ImagePath` |

`<folder>` is `AppContext.BaseDirectory` — the folder holding this assembly, which is the folder holding both executables and the configuration utility in every deployment. So the single-argument `Install` is correct whether it is called from the service, from the console host or from the tray tool. The calling process's own path is *not* usable here, which is why the image path is computed rather than taken from `Environment.ProcessPath`.

**The binary registered is `DAEService.exe`,** and that settles the "one executable or two" question this work item had open. After `host-generic-host` both `DAEServer.exe` and `DAEService.exe` run the same program and either can run as a service; nothing is deleted and nothing is renamed. `DAEService.exe` stays the registered binary because an existing 3.1 installation's service already names it with exactly this argument shape, so replacing the files in place needs no re-registration and no migration step, and because the WiX installer registers that name today (WS9). The `Install(instanceName, imagePath)` overload is there for the installer and for WS10's `dataphor server install`, either of which may want to register a different binary.

**Win32 entry points and constants**, so they do not have to be re-derived: `advapi32.dll` — `OpenSCManager`, `CreateService`, `OpenService`, `ChangeServiceConfig`, `ChangeServiceConfig2`, `DeleteService`, `CloseServiceHandle`. `SC_MANAGER_CONNECT` 0x0001, `SC_MANAGER_CREATE_SERVICE` 0x0002, `SERVICE_ALL_ACCESS` 0xF01FF, `SERVICE_CHANGE_CONFIG` 0x0002, `DELETE` 0x10000, `SERVICE_NO_CHANGE` 0xFFFFFFFF, `SERVICE_CONFIG_DESCRIPTION` 1. Errors: `ERROR_ACCESS_DENIED` 5, `ERROR_SERVICE_DOES_NOT_EXIST` 1060, `ERROR_SERVICE_EXISTS` 1073. Every handle is closed on every path, failures included.

**Failures throw `System.ComponentModel.Win32Exception` built from `Marshal.GetLastWin32Error()`** — no new Dataphor error codes, because error codes are a compatibility surface and nothing here needs one. Both existing callers already show the exception's message to the operator: the configuration utility through `Application.OnThreadException`, the service's switches by letting it reach the console. Declare `SetLastError = true` on every import and capture the error code immediately after each call.

**Platform annotation.** These are Windows-only APIs in a `net10.0` project, so `CA1416` applies. Annotate the Windows-only members with `[System.Runtime.Versioning.SupportedOSPlatform("windows")]` — the documented fix — and do **not** add a `NoWarn`: `AGENTS.md` forbids suppressing `CA1416`.

## Edge cases & interactions

| Case | What must happen | How it is verified |
|---|---|---|
| `GetServiceStatus` and `GetServiceAutoStart` called for an instance whose service is not installed | `Unavailable` and `false`, no exception. The configuration utility calls both on a timer for whatever instance is selected, so a throw here is a dialog storm | test, below |
| `GetServiceAutoStart` called from a process that is not elevated | returns the real start mode. Today it cannot: it opens `HKLM\System\CurrentControlSet\Services\<name>` **for write** in order to read it, so a non-elevated configuration utility either sees `null`, and reports the service as not installed, or gets a `SecurityException`. `ServiceController.StartType` needs only query access, which an unelevated process has. This is a defect fixed in passing; list it in the handoff and give it a migration-notes line | test, below, plus inspection of the access rights requested |
| `Install` or `Uninstall` from a process that is not elevated | `Win32Exception` with `ERROR_ACCESS_DENIED`, surfaced to the operator. The old code failed here too, so this is not a regression | by inspection; the manual check in `host-generic-host` runs the elevated path |
| `Install` when the service is already registered | `ERROR_SERVICE_EXISTS` reaches the caller as a `Win32Exception`. The old `TransactedInstaller` also failed, after writing a log file | by inspection, and the manual check |
| `Uninstall` when the service is not registered | `ERROR_SERVICE_DOES_NOT_EXIST` reaches the caller. The old installer threw as well | by inspection, and the manual check |
| An instance name whose characters end up in the service name | the service name is `Alphora Dataphor (<instance>)`, which contains spaces and parentheses. `CreateService` takes the name as a string parameter, so no quoting is involved and the name is byte for byte what 3.1 registered. This is the reason for not shelling out to `sc.exe` | by inspection |
| The service binary path contains spaces | the registered `ImagePath` is `"<quoted path>" -name "<instance>"`. The quotes are not optional: without them the service control manager splits the path at the first space, and the default install folder has a space in it | by inspection, and the manual check |
| `ServiceUtility` reached from a non-Windows process | every Windows-only member is annotated `[SupportedOSPlatform("windows")]`; the product is Windows-only and nothing in this assembly runs elsewhere | by the annotation |
| The configuration utility and the service executable both still compiling | the configuration utility is repointed to the new project and no `.cs` file in it changes; `DAE.Service.csproj` keeps `Service.cs` compiling against the moved types | `python tools/net-spike/run.py <work-dir> --smoke`, whose per-project error counts cover both |
| Two instances installed side by side | each has its own service name and its own `-name` argument; nothing in this class is per-machine state any more, where the old code shared `DAEService.InstallLog` in the binaries folder | by inspection |

## Tests

One test file, `tests/DAE.Server.Tests/ServiceUtilityTest.cs`, with a project reference added from `tests/DAE.Server.Tests/DAE.Server.Tests.csproj` to `DAE.Host.csproj`:

- **One test** that `GetServiceStatus` returns `Unavailable` and `GetServiceAutoStart` returns `false`, without throwing, for an instance name no service can be registered under — generate the name with a GUID so the test cannot collide with a real installation. This pins the catch-and-return-a-default behaviour the configuration utility's timer depends on, which is real branching and the thing most easily lost in the rewrite.

Nothing else is tested, deliberately:

- `GetServiceName` is a format string; a test of it would be a test of a constant.
- `Install`, `Uninstall` and `SetServiceAutoStart` need administrative rights and change machine state. There is no honest way to test them in the suite, and mocking the service control manager would test the mock. They are verified by hand, from an elevated prompt, and until `host-generic-host` has produced a runnable .NET 10 `DAEService.exe` there is no binary worth registering — so that manual check belongs to that ticket. Say so in the handoff rather than leaving the impression the path is covered.
