## What is wrong

The main service contract is declared twice — synchronously on the server in `src/engine/Server/Contracts/IDataphorService.cs`, and as an asynchronous copy on the client in `src/protocol/Client/Contracts/IClientDataphorService.cs`. On three of the 88 operations the two copies disagree about errors:

| Operation | Server declares | Client declares |
|---|---|---|
| `Start` | `[FaultContract(typeof(DataphorFault))]` | nothing |
| `Stop` | `[FaultContract(typeof(DataphorFault))]` | nothing |
| `GetState` | `[FaultContract(typeof(DataphorFault))]` | nothing |

Every other operation declares the same fault on both sides. `tests/DAE.Server.Tests/ContractParityTest.cs` records exactly these three in its `KnownFaultDifferences` list, naming this ticket, so it stays green on them and fails on any other drift.

The three are the same three members of `ClientServer` (`src/protocol/Client/Client/ClientServer.cs`) that each wrap their call in `catch (FaultException<DataphorFault>)` and translate the fault detail back into the server's own Dataphor exception. A Windows Communication Foundation client only deserializes a fault into `FaultException<TDetail>` when the operation's contract declares that detail type; without the declaration the client is handed a plain `FaultException`, so those three `catch` blocks are dead code and the error arrives stripped.

## Measured, both directions

Reproduced on 2026-11-20 against a real hosted server, through the test host that `protocol-corewcf-host` landed (that ticket is complete, so no `prereq:` remains). A throwaway case started a `DataphorServiceHost` on a free loopback port, connected a `ClientServer`, called `Stop()` over the wire to stop the engine, overwrote the instance's catalog store file (`<instance directory>\Catalog\DAECatalog`) with text so that the store could not be opened, and called `Start()` over the wire. The probe was not committed.

As the contract stands today, the caller of `ClientServer.Start()` gets:

```
type:     System.ServiceModel.FaultException
message:  Exceptions occurred while executing SQL command.
is FaultException<DataphorFault>:  False
is CommunicationException:         True
is DataphorException:              False
inner exception:                   none
```

With `[FaultContract(typeof(DataphorFault))]` added to `BeginStart` on the client interface and nothing else changed, the same call gets:

```
type:     Alphora.Dataphor.DAE.Connection.ConnectionException
message:  Exceptions occurred while executing SQL command.
code:     127105      severity: Application
inner exception:  Alphora.Dataphor.DataphorException: file is not a database
```

So the fix works exactly as the declaration rule predicts, and what is lost today is narrower than this ticket's earlier wording claimed: the fault *reason* text does carry the server's message, so the user is not left with a networking message. What is lost is the exception **type**, the error **code**, the **severity**, and the **underlying cause** — here "file is not a database", the one sentence that says what is actually wrong with the instance. A caller cannot branch on the error, log its code, or show its real cause.

## Second arm, at the same three members

While reading the site: of the eight members of `ClientServer` that catch `FaultException<DataphorFault>`, five follow it with `catch (CommunicationException)`, which reports the failure through `ReportCommunicationError()` and rethrows it as `ServerException.Codes.CommunicationFailure`. The three that do not are `Start`, `Stop` and `State` — the same three. The probe output above confirms the consequence is live: the escaping exception is `CommunicationException`-derived, so a dropped connection during any of these three calls reaches the caller as a raw `System.ServiceModel` exception instead of the `ServerException` every other call on the same object produces.

This is one root cause with two arms — the three administrative operations were written with incomplete error handling on both halves — so it is fixed in one commit at one site, not split. `ReportCommunicationError()` is deliberately a no-op (its body is commented out upstream, with the reason at the site), so nothing about channel recovery changes; only the exception type the caller sees.

## What correct looks like

A `DataphorException` raised by the server inside `Start`, `Stop` or `GetState` reaches the client as that same Dataphor exception — same type, code, severity and cause — exactly as it does for the other 85 operations. A transport failure during one of those three calls reaches the caller as `ServerException.Codes.CommunicationFailure`, as it does for the other five members of `ClientServer`.

The declarations stay in step afterwards because `ContractParityTest` fails on a `KnownFaultDifferences` entry whose difference is no longer there: removing the attribute again, on either side, fails the test.

## Compatibility

Two things to weigh, and the reason this was filed rather than fixed inline.

The client contract file is a named compatibility surface (see the compatibility rules in `tickets/rules/10-dataphor.md`). Operation names, parameter types and action URIs do not change, so the wire for a successful call is untouched; what changes is the fault declaration, which appears in the contract's generated metadata and changes how an error is delivered.

An application that today catches whatever these three calls throw will start seeing a different exception type from them. That is the point of the fix, but it is a behaviour an application can notice, so it needs a `docs/migration-notes.md` entry in the same commit — in the **Custom C# extensions** section, which is where the other WCF client entries live, with status `done`.

## Verification

A hosted behavioural case, not a declaration test: `ContractParityTest` holds the two declarations in step but cannot see what the wire does with them. Put the case in `tests/DAE.Server.Tests/CoreWcfProtocolTest.cs`, next to `TestServerErrorArrivesAsTypedFault`, which establishes the same property for the other 85 operations.

It needs a host of its own rather than the fixture's, because it stops the engine: follow `TestTheInstancePortBeingTakenStopsTheServer`, which builds one through `NewHost()`, `Configuration(...)` and `WithTheObjectIDCounterRestored(...)` over a `TestEnvironment.NewDirectory` it deletes afterwards. `ShouldListen` false, so no listener port is involved. Drive it with a bare `ClientServer` — its constructor opens the channel — rather than a `ProtocolClient`, so no client-side engine is started and the object-id counter dance is only the host's.

The recipe the probe used, which is deterministic: stop the engine over the wire, overwrite every file matching `DAECatalog*` under the instance directory with text, then call `Start()` and assert on what comes back. Assert that it is a `DataphorException` and **not** a `FaultException` and not a `CommunicationException` (the two shapes the defect produced), and that the code is `ConnectionException.Codes.SQLException` and the inner exception survived — the code and the cause are the part the client loses today, so an assertion only on the type would still pass against the old behaviour reached by a different route. The probe took about 5 seconds.

One test for the behaviour is enough; `Stop` and `GetState` carry no logic of their own beyond the declaration this case exercises, and the declaration side of all three is `ContractParityTest`'s. The missing `catch (CommunicationException)` of the second arm gets no test: provoking a transport failure mid-call is a timing exercise, and what it would assert is wiring that the five existing members already establish the shape of.

No change to `tests/DAE.Server.Tests/coverage-manifest.json` — that manifest lists D4 coverage scripts, not NUnit cases.
