## What this is

The first of two tickets that together finish the work item `protocol-corewcf-host` (the second is `protocol-corewcf-host` itself, which does the actual hosting). This one clears two things out of the way so that the hosting ticket's diff is only about hosting:

- two instance settings that are dead and that the plan has already decided to remove, and
- the physical location of the two source files that the hosting ticket rewrites, which has to change because they are moving into a new assembly (see the next ticket for why) and the project rules keep a file move and a file edit in separate commits.

Nothing here changes how a server behaves. Everything here is either a setting nobody can use or a file that is not compiled today.

## Decision 1: the two dead settings go, rather than staying as properties that do nothing

`ServerConfiguration` (the class behind the machine's instance list, `%ProgramData%\Alphora\Dataphor\Instances\ServerConfigurations.config`) carries two settings that cannot work in 4.0:

- **`UseServiceConfiguration`** told the old host to read its network endpoints out of the application's `.config` file instead of building them in code. The plan's WS5 target says plainly that this route is removed, open question Q8 records its use as unknown and assumed nil, and the client half of it already refuses to connect (`ClientServer.Open` throws `NotSupportedException` telling the user to connect by host, instance and port). `CustomServiceHost`, the only class that implemented it, is deleted here.
- **`AllowSilverlightClients`** existed solely for the cross-domain access-policy service that the removed Silverlight client needed. `docs/migration-notes.md` already carries a **planned** entry saying this setting is removed; this ticket makes it true.

The alternative was to keep both as properties that are read and written but ignored. Rejected: the only thing that forces the instance editor's two checkboxes to be removed is the properties going away, and a checkbox that writes a setting the server ignores is worse than no checkbox. Note that **`RequireSecureConnection` and `RequireSecureListenerConnection` stay exactly as they are** — they are the subject of `protocol-transport-security`, which needs them intact as evidence. Only the two settings named above go.

### Why removing them is safe for a deployed configuration file, measured

The instance list is read by BOP, the repository's XML object serializer. An attribute in the file that no longer matches a property does **not** fail the load: `Deserializer.ReadObject` catches the "member not found" error per attribute, adds it to the deserializer's `Errors` list and carries on, and `InstanceConfiguration.Load` never looks at `Errors`. Checked by running it, not by reading: deserializing `<thing … portnumber="8061" useserviceconfiguration="True" allowsilverlightclients="False" />` onto a class with neither property returned the object with `PortNumber` set to 8061, threw nothing, and left two `Member (…) not found for class (…)` entries in `Errors`. So an existing `ServerConfigurations.config` that carries either attribute still loads, every other setting on the instance is still read, and the attribute disappears from the file the next time the instance list is saved.

That behaviour is the compatibility claim this ticket rests on, so it gets one test (below).

## Decision 2: the client constructors that take an endpoint configuration name stay as they are

The plan's work-item row says "client constructors fixed", and the question the plan ticket left open was whether to delete them or leave them throwing. **Leave them throwing; nothing is owed here.** Three reasons:

- They already throw `NotSupportedException` with a message that tells the caller what to do instead (`ServiceClient<T>(string)`, `DataphorServiceClient<T>(string)`, `NativeCLIClient(hostName, instanceName, endpointConfigurationName)`), and `docs/migration-notes.md` already records that, plus the alias-level consequence.
- Deleting them is not the smaller change. `src/client/DAE.Client/ServerConnection.cs` calls `new ClientServer(hostName, clientConfigurationName)` when a connection alias carries the "Config Name" setting, so deleting the constructors means editing live client code and the alias handling as well, in a file WS6 owns.
- An alias that carries the setting still loads and still reports a clear error at connect time, which is better for a user than the setting silently doing nothing.

So this ticket changes no client file. Say so in the handoff, so the next reader does not go looking.

## What has to be true afterwards

- `dotnet build Dataphor.slnx` builds with no new warnings, and `dotnet restore Dataphor.slnx` still reports no package-audit warning (`NU19xx`) at all.
- An instance configuration file that still carries `useserviceconfiguration` or `allowsilverlightclients` loads, and the instance's other settings are read from it.
- The instance editor form no longer offers the two checkboxes, and `src/windows/Frontend.Client.Windows` still compiles in the net-spike build (it is not in `Dataphor.slnx`, so the solution build does not cover it).
- `src/engine/Server/Service/` holds neither host class and no `CustomServiceHost.cs`; `src/engine/Server.Hosting/` holds the two host files, byte-for-byte as they were, compiled by nothing.
- `src/engine/Server/Server.csproj`'s compile list no longer carries comment lines for files that are not in that folder any more.

## Edge cases and interactions

| Case | How it is covered |
|---|---|
| A deployed `ServerConfigurations.config` carrying either removed attribute | The test below. This is the compatibility surface; everything else here is internal |
| An instance configuration file carrying an attribute for a setting that never existed (a typo, a hand edit) | Same mechanism, same outcome — the test's fragment can carry a third, invented attribute to make the general claim rather than a special case for these two |
| Saving the instance list after loading such a file | The attribute is dropped, because the serializer writes properties and there is no longer one. By inspection; no test (it is the serializer's defined behaviour, not this change's) |
| `ShouldListen`, `OverrideListenerPortNumber`, `RequireSecureConnection`, `RequireSecureListenerConnection` | Untouched. Verify by reading the file after the edit that only the two intended properties are gone |
| The moved files no longer compiling against `ServerConfiguration` (they still read `instance.UseServiceConfiguration`) | Deliberate and harmless: neither file is in any compile list, and the next ticket rewrites both. Do **not** "fix" them here — editing a file in the same commit that moves it is what the project rules forbid, and it is the next ticket's work |
| `CustomServiceHost` referenced from anywhere else | Checked: the only references are the two host files being moved. Re-check with a repository-wide search before deleting |
| The layout build (`tools/layout/Layout.csproj`) | No new assembly here, so nothing to add. The build fails if a `.d4l` lists a file the layout does not provide; nothing in this ticket touches a library |

## The one test

`tests/DAE.Server.Tests/InstanceConfigurationTest.cs`, one case: write a small `ServerConfigurations.config` to a temp file whose single instance element carries the normal settings plus `useserviceconfiguration`, `allowsilverlightclients` and one invented attribute; load it through `InstanceConfiguration.Load`; assert the instance is there, its name, port number, listener settings and library directory are the values in the file, and that loading did not throw. This pins the claim that an older instance configuration file still works, at the lowest layer that shows it.

Do not add a test for the properties being gone (the compiler says so), for the checkboxes, or for the file moves.
