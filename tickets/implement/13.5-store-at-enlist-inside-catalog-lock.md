description: When a table is first used inside an application transaction while a statement is already running (for example a script run through the D4 Execute operator), the engine creates the transaction's private copy of the table while holding the catalog lock and then waits for the catalog store's write lock, an order that can deadlock and that fails a Debug build with an internal error. The copy never writes the store, so the early store begin should be skipped when the catalog lock is already held.

## The defect

An application transaction (AT) is a long-lived, client-side editing transaction. The first time a statement references a table while the process has joined an AT, the compiler enlists the table (`Compiler.ResolveCatalogIdentifier`, about line 1994), and `ApplicationTransaction.AddTableVar` (`src/engine/DAE/Device.ApplicationTransaction/ApplicationTransaction.cs`, line 943) takes `lock (process.Catalog)` and, inside it, has `ApplicationTransactionDevice.CopyTableVar` (line 1195) compile and run a `create table .AT_<name>` statement for the AT's private copy, plus `alter table` and `attach` statements for its defaults and event handlers.

Every DDL node first runs `DDLNode.InternalBeforeExecute` (`src/engine/DAE/Runtime.Instructions/DDLNodes.cs`, line 26), which calls `ServerCatalogDeviceSession.BeginStoreWriteTransaction` (`src/engine/Server/Device.Catalog/ServerCatalogDeviceSession.cs`, line 176). That begin exists (from `store-sqlite-concurrency`, defect K10) so that a statement takes the catalog store's write lock *before* the engine's catalog lock: a session that waits for the store's write lock while holding the catalog lock deadlocks, until the busy timeout (error 130103), with a session that holds the store's write lock and wants the catalog lock. Here the begin runs inside the catalog lock. In Debug builds `BeginStoreTransactions` (line 168) asserts against exactly this, and the statement fails with `Internal Error: The catalog store's write transaction is beginning inside the catalog's lock.`; in Release the session waits for the store's write lock while holding the catalog lock.

It needs a process transaction open with no store transaction yet. A batch run directly on a process compiles before its implicit transaction begins, so the enlistment happens outside any transaction and the begin does nothing; a nested statement (`Execute('…')`) compiles inside the outer statement's transaction.

## Reproduction (verified in the fix stage, Debug)

In an `InProcessTestFixture` test, each line run with `ExecuteScript`:

```
create table T { ID : Integer, key { ID } };
create table TID { ID : Guid, key { } };
TID := table { row { BeginApplicationTransaction() ID } };
JoinApplicationTransaction(TID[].ID, false);
Execute('select T where ID = 1;');
```

The last line fails with the internal error above, with the stack `BeginStoreTransactions` ← `BeginStoreWriteTransaction` ← `DDLNode.InternalBeforeExecute` ← … ← `ApplicationTransactionDevice.CopyTableVar` ← `ApplicationTransaction.AddTableVar`. The ticket's original form, `Execute('begin var LCursor : cursor(typeof(T)) := cursor(T capabilities { navigable, updateable }); LCursor.Close(); end;');`, fails the same way. A coverage script cannot show it: the harness's own outer statement has already opened the store transaction by then.

## Why the copy's DDL needs no store transaction

The copy's objects are AT objects (`TableVar.IsATObject` is true when the `DAE.SourceTableName` tag is set, which `CopyTableVar` sets; AT event handlers carry `DAE.ATHandlerName`; AT operators have a source operator name), and `CatalogDeviceSession.ShouldSerializeCatalogObject` returns `!objectValue.IsATObject`, so inserting, updating or deleting them never reaches the store. `CreateTable` otherwise only creates the device table on the AT device, which is in memory. AT operator copies (`CopyOperator`, line 1835) already run in a loading context, which `DDLNode.InternalBeforeExecute` skips.

## The fix (trial-verified)

In `ServerCatalogDeviceSession.BeginStoreWriteTransaction`, do nothing when the caller already holds the catalog's lock:

```csharp
if (!ServerProcess.ServerSession.Server.IsEngine && (OpenTransactionLevels > 0) && !Monitor.IsEntered(Catalog))
```

The early begin exists only to take the store's lock before the catalog's lock; inside the catalog's lock it can no longer do that, so it only adds the forbidden wait. A statement there that really writes the store still goes through `AcquireCatalogStoreConnection(true)` → `BeginStoreTransactions`, so the Debug assertion keeps catching a real store write inside the catalog's lock. In the fix stage this one-line change made both reproductions pass, and `ConcurrentDDLTest`, `CatalogStoreConcurrencyTest`, `CatalogStoreTest` and the `ApplicationTransactions` and `TestNetworkApplicationTransactions` coverage scripts passed with it (23 + 2 tests, Debug). The trial edit was reverted; nothing from it is in the tree.

Rejected alternatives:

- Begin the store write transaction before `lock (process.Catalog)` in `ApplicationTransaction.AddTableVar` and the other `lock (process.Catalog)` sites in that file (lines 920, 945, 993, 1389, 1479). It would take the store's write lock for a statement that only reads (any first reference to a table in an AT) and hold it until the process transaction ends, serializing every other session's DDL behind it, which is what K10's lazy begin was built to avoid.
- Skip the begin in `DDLNode.InternalBeforeExecute` when the plan is in the AT creation context. `CopyTableVar` pushes that context on its own `Plan`, but the `Program` that runs the statement creates a separate `Plan` (`Program.Plan`), so the node cannot see it; and the context is also pushed while recompiling operator bodies (`Compiler.cs`, about lines 6606 and 7034), whose DDL can write the store.
- Have each DDL node report whether its target is an AT object. `AlterTableVarNode` resolves its table only at execution, and the check would have to be repeated in every node class that the copy can emit; the lock check covers them all in one place.

Release behaviour after the fix: the AT copy no longer waits for the store's write lock inside the catalog's lock. A DDL statement that does write the store inside the catalog's lock (none is known) waits there, as it did before K10, and fails the assertion in Debug.
