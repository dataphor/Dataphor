## What happens

Comparing two records (D4 calls them rows) with `=` or `<>` leaks one managed stream per stream-backed column per side, on every comparison. `Binary` and `Graphic` are the two types the engine keeps in a managed stream, and they are what an application stores a picture, a document or an attachment in; the engine does not reclaim such a stream until the session ends. The equality the compiler generates for a compound scalar type - a type whose single representation has more than one property - leaks the same way, and that arm is now measured rather than inferred.

Row equality is not an exotic shape: it is what a transition constraint, a key comparison and `in` over a row-valued list all compile to, so this runs inside ordinary application code rather than only where a script says `=` between two rows.

**Measured on `modernization` at `cdb56b30`**, through a throwaway case on `InProcessTestFixture` reading `Diagnostics.StreamCount()` either side of each script. Ten iterations of a comparison in a loop:

| shape | streams left behind |
|---|---|
| `row { X : Binary }` held in a variable, `LR = LR` | 20 |
| two *computed* `row { X : Binary }` values compared | 20 |
| `row { X : Binary, Y : Binary }` in a variable | 40 |
| `LR <> LR` (inequality, same node) | 20 |
| a `row`-typed operand compared inside an operator (the run-time branch, below) | 20 |
| compound scalar with a `Binary` property, computed values | 20 |
| compound scalar with a `Binary` property, held in a variable | 20 |
| control: `LR.X = LR.X` (column equality, not row equality) | 0 |
| control: a list of `Binary` compared with `=`, and `IndexOf` over one | 0 |

## Root cause

One site - `src/engine/DAE/Runtime.Instructions/RowComparisonNodes.cs` - and two nodes in it with the identical mistake, each missing **both** halves of the const-operand rule that `docs/architecture/operand-ownership.md` describes.

`RowEqualNode.DetermineDataType` and `CompoundScalarEqualNode.DetermineDataType` call `DetermineModifiers(plan)` where almost every other instruction node calls `base.DetermineDataType(plan)`. The `const` branch of `InstructionNodeBase.DetermineDataType` is the only place that asks an argument node to lend its value (`PlanNode.SetByReference`), and `DetermineModifiers` alone does not reach it - so neither argument node is ever asked, both answer `ReturnsByReference` false, and both *copy* the row they were given. `iEqual(const ALeftValue : row, const ARightValue : row)` (`src/engine/DAE/Schema/SystemCatalog.d4`) declares those `const` modifiers; for a compound scalar type the equality operator is generated by `Compiler.CompileComparisonOperator` and declares `const` as well.

Each node then overrides `InternalExecute(Program)` directly, which is the shape that bypasses `InstructionNodeBase.CleanupOperand` - so nothing releases the copies either. The two mistakes compound: the first makes a value the call owns, the second drops it.

`CompoundScalarEqualNode` additionally wraps both native values with `DataValue.FromNative` and disposes neither wrapper. `FromNative` sets `ValuesOwned = true` on the wrapper it returns, so disposing one as it stands would release the underlying native row's column values - which for a lent argument belong to the caller. That is why the design below clears `ValuesOwned` on each wrapper and keeps the one release decision on the argument node.

## The fix, prototyped and measured

The whole design below was applied to a working tree, measured (every leaking shape in the table above went to 0), run against the targeted tests (all green, listed under *What to run*), and then reverted - the tree is clean. Treat it as a verified starting point rather than a sketch; the comments are the implementer's to write.

**`RowEqualNode`.** Three changes.

`DetermineDataType` calls `base.DetermineDataType(plan)` instead of `DetermineModifiers(plan)`. Everything after it is unchanged: `base` sets `_dataType` from the operator and the override immediately replaces it with `SystemBoolean`, and `base` guards its whole body on `Operator != null`, which matters for the run-time branch below.

`InternalExecute(Program)` becomes the ownership wrapper, and the comparison itself moves into a private method so the run-time branch can reach it:

```csharp
public override object InternalExecute(Program program)
{
	object leftValue = Nodes[0].Execute(program);
	object rightValue;
	try
	{
		rightValue = Nodes[1].Execute(program);
	}
	catch
	{
		if (!Nodes[0].ReturnsByReference)
			DataValue.DisposeValue(program.ValueManager, leftValue);
		throw;
	}
	try
	{
		return InternalCompare(program, leftValue, rightValue);
	}
	finally
	{
		if (!Nodes[0].ReturnsByReference)
			DataValue.DisposeValue(program.ValueManager, leftValue);
		if (!Nodes[1].ReturnsByReference)
			DataValue.DisposeValue(program.ValueManager, rightValue);
	}
}
```

`InternalCompare(Program, object, object)` holds what `InternalExecute` held before - the nil propagation, the `_comparisonNode` stack push, and the `else` branch. The `catch` is the same rule `InstructionNodeBase.ReleaseUncalledOperand` applies on the shapes' own error path: the first argument has been evaluated and the second raised, so the call never happens and the value the node owns must still be released. Read `Nodes[index].ReturnsByReference` at run time rather than remembering what `base.DetermineDataType` asked, for the reason `IfNilNode`'s comment gives: the `DetermineDataType` override may replace either argument node afterwards, and `Compiler.ConvertNode` genuinely wraps it.

**The run-time branch is reachable and was leaking too.** When either operand's type is a generic `row` - which an operator declared `operator F(const A : row, const B : row)` produces, and which the measurement above exercises from D4 - the node builds a fresh `RowEqualNode` over two `ValueNode`s wrapping the values it just evaluated, and executes it. `ValueNode` returns `_value` as it stands and answers `ReturnsByReference` false, so with the release above in place the inner node would release the values the outer node still owns, and the outer would then release them again. The prototype's answer is a small private node class, used only there:

```csharp
/// <summary>A ValueNode over a value the node that built it still owns, so the consumer must not release it.</summary>
private class BorrowedValueNode : ValueNode
{
	public BorrowedValueNode(Schema.IDataType dataType, object tempValue) : base(dataType, tempValue) { }
	public override bool ReturnsByReference { get { return true; } }
	public override bool SetByReference() { return true; }
}
```

The two `new ValueNode(...)` calls in the run-time branch become `new BorrowedValueNode(...)`. The inner node then releases nothing it was handed, and still correctly releases the output of a conversion node if its own `DetermineDataType` inserts one.

The wider alternative - giving `ValueNode` itself a `SetByReference`, so any const operand handed a plan literal borrows it rather than copying and releasing - is deliberately **not** taken here. It is probably the right answer and it is cheaper, but its blast radius is every call in the engine with a literal argument, which is not something to change inside a leak fix. Leave a `NOTE:` at the new class saying so, so the next reader meets the choice rather than re-deriving it.

**`CompoundScalarEqualNode`.** The same two halves, plus the wrappers. `DetermineDataType` calls `base.DetermineDataType(plan)`. `InternalExecute(Program)` keeps its structure and gains the same outer `try`/`catch`/`finally` keyed on `Nodes[index].ReturnsByReference` over the two *native* values it evaluates (`DataValue.DisposeValue` handles a `NativeRow` by recursing into its values, so a compound scalar's native value is released correctly). The nil propagation moves inside that `try`, so a nil on either side still releases the other. Each `DataValue.FromNative` result is held as `IDataValue`, gets `ValuesOwned = false`, and is disposed in a `finally`: the wrapper frees itself and the one release of the underlying value stays with the argument node.

## The class behind it, which is the arm worth having

Overriding `InternalExecute(Program)` silently opts a node out of operand cleanup, and nothing checks which nodes have done so. The architecture page listed four such nodes when this was first reviewed; there are thirteen that are operator nodes, and the nine the list missed are the dangerous ones - they derive from one of the five argument shapes (`InstructionNode` and its nilary, unary, binary and ternary siblings) and re-override the entry point, so they read as ordinary instruction nodes while skipping their own shape's cleanup call. That miscount is how these two nodes went unexamined, and a hand-maintained prose list will miscount again.

So: a test that reflects over the engine assembly and compares the set against a checked-in list. The predicate was prototyped and gives exactly eighteen types - the five shapes plus the thirteen reviewed nodes, matching the page:

- every type in `typeof(InstructionNodeBase).Assembly` where `typeof(InstructionNodeBase).IsAssignableFrom(type)`,
- excluding `typeof(TableNode).IsAssignableFrom(type)` - a table node overrides that entry point because that is how a table node returns a cursor, and it has no operand modifiers in play,
- that declares the method itself: `type.GetMethod("InternalExecute", BindingFlags.Public | BindingFlags.NonPublic | BindingFlags.Instance | BindingFlags.DeclaredOnly, null, new Type[] { typeof(Program) }, null) != null`.

The eighteen, for the checked-in list: `BinaryInstructionNode`, `CompoundScalarEqualNode`, `ExistsNode`, `IfNilNode`, `InstructionNode`, `NilaryInstructionNode`, `RowEqualNode`, `RowExtendNode`, `RowRedefineNode`, `TableEqualNode`, `TableGreaterNode`, `TableInclusiveGreaterNode`, `TableInclusiveLessNode`, `TableLessNode`, `TableNotEqualNode`, `TableToListNode`, `TernaryInstructionNode`, `UnaryInstructionNode`. The failure message is the point of the test: a node not on the list must tell its author to apply the const-operand rule by hand, naming `docs/architecture/operand-ownership.md`, and to add itself to the list once it has; a node on the list that no longer has the shape must say to remove it. The test needs no server, so it belongs in its own fixture with no base class rather than on `InProcessTestFixture`.

**One list, not two.** The ticket this came from asked whether the same pass should also flag a subclass whose `DetermineDataType` never reaches `base.DetermineDataType` - the first half of the defect, invisible from the execute side. It can be done: an IL scan of the method body for a `call` to a base `DetermineDataType` was prototyped and does find both of these nodes. It is **not** worth having, and that was measured rather than argued. Six non-table subclasses skip `base.DetermineDataType` without overriding the execute entry point (`BaseListIndexOfNode`, `DistinctListNode`, `ListEqualNode`, `RowProjectNode`, `RowRemoveNode`, `RowRenameNode`), and for those the shape's own `CleanupOperand` still runs: the argument node was never asked, so it copied, and the cleanup releases the copy. Balanced. Measured: list equality over a `list(Binary)` held in a variable, the same computed, and `IndexOf` over one each left **0** streams behind. So skipping `base.DetermineDataType` on its own costs a copy, not a stream; it is only a leak in combination with the execute override, which the one list already catches. A second check would need its own thirteen-entry list of legitimate non-callers, doubling the maintenance for a condition that is not a defect.

Record that copy cost as one line on the architecture page - the concern is architectural with no single code site - rather than as a ticket.
