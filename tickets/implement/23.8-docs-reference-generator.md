## What this is

The second and final ticket for the plan's WS8 work item `docs-reference-generator`, and the one that closes its row in the WS8 work-item table. `docs-reference-signatures` lands first: it settles that the generator is a test fixture in `tests/DAE.Server.Tests` driving the shipped `System.Script` operator, builds the generator and the goldens tree, and does the operator and scalar-type comparison. This ticket reuses all of that machinery for the one piece of the 3.x reference that is missing outright.

**The gap.** The System library defines the system tables - `Operators`, `TableVars`, `Devices`, `Libraries` and the rest - which are how a D4 script reads the catalog as data. The reference does not document them, and `docs/reference/system-library/README.md` says so under a heading of its own, naming this work item as the owner: the `SystemTables` chapter is a four-line stub in both copies of the old DocBook saying the section was generated, and the published help file lists the table names with nothing under them. So unlike every other part of the reference, there is no 3.x text to convert and nothing to compare a hand-written replacement against. The only source is a running server.

## What gets generated

`src/engine/DAE/Schema/SystemCatalog.d4` declares 60 tables and views (measured with `grep -c`); the catalog device creates more in C#, so the generated set is whatever the catalog actually holds and the count is the first thing to measure. For each one, `Script(Name)` emits the full `create table` or `create view` statement with its columns and their types, its keys, its references and its tags - which is the columns-and-keys half of what the missing chapter was meant to say, in the same emitter's own words that every operator page's declarations block already uses.

**Descriptions do not exist and are not invented.** The old chapter was to carry a sentence per table and per column. There is no source for them: `SystemCatalog.d4` carries not one `Catalog.Comment` tag (measured, `grep -c` returns 0, against 17 in `DataTypes.d4` where the scalar types do carry them), so the running catalog has nothing to report either. Each generated page therefore gives the definition and nothing else, and the section index says plainly that the descriptions were never written down. Do not write a sentence per table from a reading of the code and present it as reference material; a reader who needs the narrative is pointed at the D4 catalog chapter of the Developer's Guide (`docs/developers-guide/d4-catalog.md`), which the current README already points at.

## Page shape, and the decision behind it

**One page per table, under `docs/reference/system-library/tables/`, plus a section index.** This matches the operator and type pages next to it, keeps each page's link target stable for the cross-references a later guide pass will want, and keeps any one page far below the documentation set's size limits. The alternative - one long page listing all 60-odd - was rejected because the architecture pages' 1,500-word cap is the house style for exactly this situation and a single page of 60 emitted `create table` statements would be several times that.

A page is: the table's name as its title, one sentence of framing that is the same on every page (what a system table is and that the definition below is generated), the fenced `d4` block holding the emitted definition, and a link back to the section index and to the D4 catalog chapter. Nothing else, so that a regenerated page is byte-identical to the committed one and the comparison means something.

**These pages are generated, so they are compared whole, not block by block.** That is the one place this ticket differs from `docs-reference-signatures`: there, a page is mostly hand-written prose with one generated block inside it, so only the block is compared and nothing rewrites the page. Here the whole page is generated, so the fixture compares the whole file, and `DATAPHOR_UPDATE_REFERENCE_GOLDENS=1` - the same variable `docs-reference-signatures` introduces - rewrites these pages in place and deletes the ones no table produces. Say this on the pages themselves and in the fixture's remarks, because a hand edit to a generated page under `docs/` will be silently reverted by the next update run and a reader has no other way to know.

That makes these pages their own goldens: no copy under `tests/goldens/` for them. A second copy of a fully generated file would only be a thing to keep in step.

## Edge cases & interactions

- **Views and tables both.** `SystemCatalog.d4` declares both, and some of what a script reads is a view over tables. Include both, and make the page say which it is; a view whose definition names tables that have pages should link to them if that is cheap, and plainly not bother if it is not.
- **Which catalog, again.** Same answer as `docs-reference-signatures`: `InProcessTestFixture` with no libraries and nothing registered, so the set is a function of the engine alone. A system table that only appears once a library is registered must not be in this set, and if one is found, leave it out and say so in the index rather than pinning a page to a library.
- **Tables the catalog holds that no library declares in D4.** The catalog device creates some structures in C#. Whatever the catalog reports is what gets a page - the set is read, not listed by hand - but assert the set against a committed list so that a table appearing or disappearing is a reviewable change rather than a silent one.
- **The documentation link and size checks gate this.** Roughly 60 new pages and one index: `python tools/docs-link-check/check_links.py docs` must stay at 0 errors, every link in the generated pages included, and `python tools/docs-size-check/check_size.py` covers the architecture pages rather than these, but run it anyway since the plan is edited. A generated page is also a generated *link*, so a link the generator emits to a page that does not exist fails CI on a push - check the emitted links before committing, not after.
- **Line endings and byte-order mark.** Everything under `docs/` is LF with no byte-order mark; the emitter produces CRLF. The generator converts on write, and the fixture compares after the same conversion, so a Windows checkout and the Ubuntu runner the documentation workflow uses agree.
- **Determinism.** Same requirement and same reasoning as the first ticket: fix the order with an explicit ordering on the query, write no timestamp, and confirm two runs on two instances agree before committing. A generated page set that churns makes every later diff unreadable.
- **The `TableVars` page documents the table this generator reads.** Harmless, and worth a sentence on that page, because it is the entry point a reader asking "how do I find this out myself" wants.
- **Privacy.** As before: the server carries this repository's own built-in library and nothing else, so no deployment's names can reach a page.
- **Do not extend the engine.** `TableVars`, `Script` and the catalog tables answer this as they stand.
