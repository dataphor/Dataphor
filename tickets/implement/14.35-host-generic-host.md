## What this is

The server has two executables over the same hosting class, neither of them converted to the SDK project format and neither of them buildable for .NET 10:

- `src/hosts/DAEServer` → `DAEServer.exe`, a console program. `Program.Main` scans the arguments for `-n` or `-name`, starts a `DataphorServiceHost`, blocks on `Console.ReadLine()` and stops it. Its vendored `CommandLineArguments.cs` is compiled but nothing in the project calls it, and it is the file that fails on C# 14 because it uses `field` as an identifier inside a property accessor (known defect K23) — four errors.
- `src/hosts/DAEService` → `DAEService.exe`, a Windows service whose `Service` class derives from `System.ServiceProcess.ServiceBase`, with `-r` to run it in a console. Its installer half is already gone: `host-service-registration` rewrote `ServiceUtility` on the service control manager and moved it, with `Strings` and the `ServiceStatus` enum, into the new assembly `Alphora.Dataphor.DAE.Host` (`src/hosts/Host/DAE.Host.csproj`).

`protocol-corewcf-host` already did the network half: `DataphorServiceHost.Start()` starts a .NET 10 server and serves all three contracts on CoreWCF at the addresses and ports 3.1 published, through two .NET Generic Hosts built by one internal helper, `NetTcpServiceHost`. What is missing is the *program*: the thing that owns the process, decides whether it is a console session or a Windows service, shuts the server down in order when asked, and logs.

This ticket builds that program once, in `DAE.Host`, and reduces both executables to a one-line entry point over it. Both file names stay — `DAEServer.exe` and `DAEService.exe` run the same program, as the plan's WS10 section requires of them ("thin shims with their old names and switches for existing scripts and service registrations"). It also makes the build's runtime layout runnable for the first time: `artifacts/layout/<config>/bin/` has no `.exe`, `.deps.json` or `.runtimeconfig.json` today, and the sentence in `AGENTS.md` that says nothing runs from there until this work item comes out when it does.

## The program

### Command line

One parser for both executables, in `DAE.Host`:

```csharp
namespace Alphora.Dataphor.DAE.Service
{
    public enum HostCommand { Run, Install, Uninstall }

    public sealed class HostCommandLine
    {
        public HostCommand Command { get; }
        public string InstanceName { get; }        // never null; Engine.DefaultServerName when not given
        public static HostCommandLine Parse(string[] args);
    }
}
```

The behaviour to reproduce, taken from the two `Main` methods as they stand:

- The instance name comes from `-n` or `-name`, compared case-insensitively, anywhere in the arguments, and its value is the following argument. The scan runs over `i < args.Length - 1`, so a trailing `-n` with no value after it yields **no** instance name rather than an error, and the default is used. Keep that: it is what both programs do today and a 3.1 script could rely on it.
- The command comes from `args[0]` alone: `-i` or `-install` → `Install`; `-u` or `-uninstall` → `Uninstall`; `-r` or `-run` → `Run`; `-n` or `-name` → `Run`; no arguments → `Run`.
- Anything else throws `ArgumentException` with `Strings.Get("InvalidCommandLine")`, which is what `DAEService` does today. `DAEServer` today accepts any arguments silently and starts the default instance; with one parser it no longer does. That is the intended behaviour and gets a migration-notes line.
- The default instance name is `Engine.DefaultServerName`.

### Entry point

```csharp
public static int Run(string[] args);     // in DataphorHost, namespace Alphora.Dataphor.DAE.Service
```

`Install` and `Uninstall` call `ServiceUtility.Install`/`Uninstall`, print one line of confirmation, and return 0; a failure prints the exception message and returns 1 — no stack trace, because the operator at a prompt is the reader. `Run` builds and runs the Generic Host. A bad command line prints the message and returns 1. Exit code 0 means a clean stop, 1 means the program reported a failure.

### The host

```csharp
public static IHost BuildHost(string instanceName, Func<DataphorServiceHost> hostFactory);
```

`hostFactory` defaults, from `Run`, to a factory that returns `new DataphorServiceHost { InstanceName = instanceName }`. It is a parameter so the tests can supply a host configured against a temporary instance without touching the machine's instance list; `BuildHost` is public for the same reason, and the repository has no `InternalsVisibleTo` convention to follow instead. Say so in the doc comment.

The builder:

- `new HostBuilder()`, not `Host.CreateDefaultBuilder`: nothing here reads `appsettings.json`, environment-variable configuration or command-line configuration, and the default builder would add all three plus providers this program does not want. `NetTcpServiceHost` already uses a bare `HostBuilder` for the same reason; follow it.
- `.UseWindowsService(options => options.ServiceName = ServiceUtility.GetServiceName(instanceName))`, from the package `Microsoft.Extensions.Hosting.WindowsServices`. This is the whole of "the same executable runs as a Windows service": the extension checks `WindowsServiceHelpers.IsWindowsService()` and only then replaces the host lifetime, so there is **one** code path and `-r` is simply an alias for running. Verified on .NET 10 against the pinned SDK: the package resolves at 10.0.15, `UseWindowsService` and `WindowsServiceHelpers.IsWindowsService()` are present, and in a console process `IsWindowsService()` is false.
- One hosted service, registered with `AddHostedService`, that owns the `DataphorServiceHost`.
- `services.Configure<HostOptions>(options => options.ShutdownTimeout = ShutdownTimeout)`, with `ShutdownTimeout` a constant in `DataphorHost` — see *Shutting down*.
- Logging, below.

### The hosted service

`IHostedService`, not `BackgroundService`: there is no loop to run, only a start and a stop.

- `StartAsync` logs the instance name, calls `DataphorServiceHost.Start()` **synchronously** and logs that the server started, then logs whether the listener service is serving (`IsListening` is false when its port was already taken, which is normal for the second server on a machine; `DataphorServiceHost` already writes the detail to the server's own log). A failure is logged and rethrown, so the process exits 1 in a console and the service control manager reports a start failure. Synchronous is deliberate: `Service.OnStart` was synchronous, so the time the service control manager waits for a start is unchanged, and a server start that is slow because it is registering libraries was already the case.
- `StopAsync` logs that the server is stopping, calls `DataphorServiceHost.Stop()`, and logs that it stopped. It is null-safe and idempotent: a start that failed leaves nothing to stop, and `Start` already calls `Stop` on its own failure path.

### Logging

The host's `ILogger` is for **host lifecycle only** — the instance being started, started, the listener state, stopping, stopped, and failures. The server's own logging is not routed through `Microsoft.Extensions.Logging` and is not touched:

`Server.LogMessage` writes the instance's rolling log file in the 3.1 format (`src/engine/Server/Server/Server.cs`, `GetLogFileName`, `MaxLogs`, an auto-flushing `StreamWriter`) and, for an elevated process, the Windows event log under the source `Dataphor Server` in the log `Dataphor`, creating the source if it is missing. That log file is a surface operators read and `ListLogs` serves over the protocol, so re-implementing it on a logging provider would change a compatibility surface for no gain. **The event-log source creation in `Server.StartLog` keeps its existing guards — `!IsEngine && IsAdministrator()` — and is not made unconditional.** This is also what keeps the test fixture's logging-off server from touching the event log.

Providers:

- `ClearProviders()` first, then in a console session (`!WindowsServiceHelpers.IsWindowsService()`) `AddSimpleConsole` with `SingleLine = true` and `TimestampFormat = "yyyy/MM/dd HH:mm:ss.ffff "`, the same timestamp shape `Server.LogMessage` writes, so an operator watching the window and an operator reading the log file see the same thing. The three lines the old console host printed ("Server starting...", "Server started.", "Server stopping...") are these messages.
- As a Windows service, `AddEventLog` with `SourceName` `"Dataphor Server"` and `LogName` `"Dataphor"` — the source and log the server already uses, so no new event source is introduced. Add the provider only when `EventLog.SourceExists` says the source is there, inside a `try`/`catch` that skips the provider if the check itself fails; a host whose event log is unavailable must still start. The source is created by the server's own `StartLog`, which runs elevated in a service.
- Minimum level `Information`. The two CoreWCF hosts keep `NetTcpServiceHost`'s `ClearProviders()` and stay silent, so an in-process alias started inside the Windows client or the IDE still prints nothing.

### Shutting down

`DataphorServiceHost.Stop()` already stops things in the right order, and this ticket changes none of it: the listener host, then the instance's own host (each bounded at `NetTcpServiceHost.StopTimeout`, ten seconds, after which Kestrel aborts the connections still open), then the WCF service object — whose `Dispose` disposes the `ConnectionManager` and so signals its idle watcher — then the `RemoteServer`, then the engine's `Server.Stop()`, which ends the sessions and closes the catalog store. Network first so no new work arrives, engine last. The ticket's earlier description of `Stop` closing the hosts with `BeginClose` and never waiting is out of date; `protocol-corewcf-host` replaced it.

What this ticket adds:

- `DataphorHost.ShutdownTimeout`, a constant, set to **60 seconds** and applied through `HostOptions.ShutdownTimeout` (whose default is 30). The two bounded host stops can take twenty seconds between them before the engine's stop even begins, so the default is too short. Put the arithmetic in the comment.
- **What happens when it expires:** the Generic Host stops waiting, logs that shutdown timed out, and the process exits with the engine's stop unfinished. That is the same situation as the process being killed, which the catalog store already has to survive; an operator who sees the message should treat the instance as having stopped abruptly rather than cleanly. The timeout is a constant rather than a setting, as `NetTcpServiceHost.StopTimeout` already is.
- **`ConnectionManager`'s idle watcher becomes a background thread.** `src/engine/Server/Service/ConnectionManager.cs` starts it with `new Thread(new ThreadStart(LifetimeWatcher)).Start()`, which is a *foreground* thread: if the shutdown timeout ever expires before `DataphorService.Dispose` has signalled it, the process would not exit at all — a hang instead of an abrupt stop. Set `IsBackground = true` and leave a `NOTE:` at the site saying why, and that `port-abandoned-session-cleanup` may rework this class. The thread does nothing but wait on a `ManualResetEvent` and reap idle connections, so nothing is lost by letting the runtime drop it at process exit. This is the one edit outside the hosting code, and `port-abandoned-session-cleanup` is the plan ticket that otherwise owns this file — flag the overlap in the handoff.
- **Ctrl+C is the way to stop a console host, and pressing Enter no longer is.** The Generic Host's console lifetime handles Ctrl+C and the process-exit signal; the old `Console.ReadLine()` is gone. Reading standard input is wrong for a program that may be run with input redirected or closed — `ReadLine` returns immediately and the server would stop the moment it started — and a supervisor that wants to stop the server sends Ctrl+C or terminates the process. This gets a migration-notes line. `tests/DAE.Client.Tests/OutOfProcessTestFixture.cs` starts `DAEServer.exe` with `RedirectStandardInput` and is the one place in the tree that relied on the old behaviour; that project is unconverted and blocked, and `test-client-server` owns it — note it in the handoff rather than editing it here.

## Assemblies the server loads by name

**Measured, and the thing most likely to make a host that builds fail to start:** on .NET 10 an assembly that sits next to the executable but is not named in the executable's `.deps.json` cannot be loaded by simple name. A scratch console application with a `ProbeLib.dll` copied into its output folder but no reference to it fails `Type.GetType("ProbeLib.Thing,ProbeLib", true, true)` with `FileNotFoundException`. There is no app-local probing to fall back on, and the engine's `AssemblyUtility.ResolveAssembly` hook only matches assemblies that are *already loaded*.

The server loads exactly one assembly from `bin/` this way: the catalog store. `ServerCatalogDevice.InternalStart` takes `Server.GetCatalogStoreClassName()`, which defaults to `Server.DefaultCatalogStoreClassName` = `"Alphora.Dataphor.DAE.Store.SQLite.SQLiteStore,Alphora.Dataphor.DAE.SQLite"`, and `CatalogStore.Initialize` resolves it with `Type.GetType(_storeClassName, true, true)`. So both executables must reference `Store.SQLite` even though no line of their code mentions it; put a comment in each project file saying exactly that. Library assemblies are a different case and need nothing: the server loads them from a path with `Assembly.LoadFrom` and `LibraryAssemblyResolver` probes their folders.

`ServerProcess.RemoteSessionClassName` names `AlphoraDataphorServer`, which both executables reference through `DAE.Host`, so server links need nothing extra.

## `GetInstallationDirectory` and the default library directory

`ServerConfiguration.DefaultInstance` — which `DataphorServiceHost.Start()` calls when the named instance is not in the machine's instance list, so on every first run — sets `LibraryDirectories` to `Path.Combine(PathUtility.GetInstallationDirectory(), "Libraries")`. `GetInstallationDirectory` (`src/engine/Base.Windows/PathUtility.cs`) takes the directory of `AppContext.BaseDirectory`, pops one level if that directory is named `bin`, and then pops one more:

| Binaries in | Result today | Should be |
|---|---|---|
| `<install>\Dataphor\` (what the WiX installer produces: `ProgramFilesFolder\Dataphor\Dataphor\`, with `Libraries` beside it) | `<install>` | `<install>` — correct |
| `artifacts\layout\<config>\bin\` (the runtime layout, with `Libraries` beside `bin`) | `artifacts\layout` — **wrong, one level too high** | `artifacts\layout\<config>` |
| `<tree>\<project>\bin\` (the 3.1 source tree's per-project output, which no longer exists: output now goes to `artifacts/bin/<project file name>/<config>/` and nothing runs from there) | `<tree>` | — |

The second pop exists only for the third shape. Remove the `bin` special case: one pop then serves both shapes that exist, and the installed case is unchanged. There are exactly two call sites, both in `ServerConfiguration`. It is a public member, so it gets a migration-notes line.

The consequence is worth a sentence in `AGENTS.md`'s runtime-layout paragraph: starting `bin\DAEServer.exe` from the layout with no instance configuration creates a default instance whose library directory is the layout's own `Libraries\`, and a running server writes into its library directory — so a local run that matters should still point at a copy, as that paragraph already says for tests.

## What must still be true afterwards

- `DAEServer.exe -n <instance>`, `DAEServer.exe -name <instance>` and `DAEServer.exe` with no arguments start the same instance, from the same `ServerConfigurations.config`, on the same addresses and ports as before; `DAEService.exe` with the same switches does the same thing.
- A service registered by `ServiceUtility.Install` — `"<folder>\DAEService.exe" -name "<instance>"` — starts, serves, and stops from the service control manager.
- Ctrl+C in a console and a stop from the service control manager both go through `DataphorServiceHost.Stop`: catalog store closed, services closed, sessions ended.
- A server whose *listener* port is already taken still starts and still serves its own endpoint, and the host reports that the listener is not serving. This is `protocol-corewcf-host`'s behaviour and must not regress.
- A server whose *instance* port is already taken fails to start, reports why, and exits 1 (or reports a start failure to the service control manager); `DataphorServiceHost.Start` already stops what it built before rethrowing.
- `dotnet build Dataphor.slnx` puts a working host into `artifacts/layout/<config>/bin/`, and `dotnet restore Dataphor.slnx` reports no `NU1xxx` warning.
