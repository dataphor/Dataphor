## What this is

`libraries/Frontend` is the server side of the UI layer: it derives forms from the schema, holds the Frontend device that serves documents, and runs the customization merge. Its project, `Source/Frontend.Server.csproj`, compiles seventeen files. Nine more `.cs` files sit in the same folder and are compiled by nothing. They are what is left of the web client, which decision D4 removed:

| File | Lines | What it is |
|---|---:|---|
| `Application.cs` | 282 | `System.Web` + `System.Web.Security` session/application plumbing |
| `Customization/Customizer.cs` | 145 | an `IHttpHandler` serving customized documents |
| `Customization/DilxModule.cs` | 132 | an `IHttpModule` |
| `Customization/DilxUtility.cs` | 75 | `System.Web.Hosting` path helpers for the above |
| `Customization/LinkTable.cs` | 111 | a lookup table used only by the three above |
| `Export.cs` | 49 | a `System.Web.UI` data export page |
| `FrontendUtility.cs` | 15 | one constant, `CXmlContentType`, used only by `Customizer.cs` |
| `ImageHandler.cs` | 50 | an `IHttpHandler` serving images |
| `LoginPage.cs` | 125 | a `System.Web.UI.Page` login form |

Seven of the nine use `System.Web` directly. The other two, `LinkTable.cs` and `FrontendUtility.cs`, do not, but a grep of the whole tree finds no reference to either outside the seven - `LinkTable` is named only by `Application.cs`, `Customizer.cs`, `DilxModule.cs`, `DilxUtility.cs` and itself, and `FrontendUtility.CXmlContentType` only by `Customizer.cs` - so all nine go together or none does. That set of nine is also exactly what `debt-ws12-hygiene-remainder`'s `build-globbing-cleanup` arm counts for this library, and that arm waits on this ticket: `ASP.NET` is not on .NET 10, so switching the project to default globbing before the files go would compile seven files that cannot compile.

`test-frontend-derivation-golden` and `test-frontend-document-corpus` have landed, so the library's behaviour is held by 416 golden derived forms, a document corpus of 76 files and the customization merge round trip. That is the safety net the plan's WS7 row asked for before this deletion.

## Edge cases & interactions

- **The file set is the whole decision.** Delete all nine or none; a half-deletion leaves `LinkTable` or `FrontendUtility` as genuine orphans rather than as part of a coherent removed feature. Re-run the two greps yourself before deleting and record what they returned.
- **`Source/app.config` and `Source/EveryNode.dil` are not in this set.** `app.config` names `.NETFramework,Version=v4.5.2` and nothing reads it; `EveryNode.dil` is a form document fragment that nothing in the tree references. Both are strays rather than web leftovers, and `build-globbing-cleanup` owns strays. Leave them, and say in the handoff that you left them and why, so the next reader does not take their survival as a judgment that they are needed.
- **The project file carries a comment naming this ticket.** Whatever form the `Frontend.Server.csproj` comment about the excluded files takes, it goes with the files; the project then compiles exactly the `.cs` files beside it, which is what `build-globbing-cleanup` needs.
- **Public types disappear from a shipped assembly.** All nine files declare public types in `Alphora.Dataphor.Frontend.Server` and `...Server.Customization`, and the assembly is `Alphora.Dataphor.Frontend.Server`. Nothing in the repository uses them, but they are not in the assembly today either - the files are not compiled - so **no type that currently ships is removed**. Check that claim rather than taking it from here: list the assembly's public types before and after, or simply confirm the nine files have no `Compile` entry. If the claim holds, no migration note is owed; say so explicitly in the handoff, because "we deleted public classes from the Frontend library" is the sort of line a reader will expect a note for.
- **The library's `Documents/` folder still holds `Web.NodeTypes.dnt`.** That is a document, not C#, and it is a published artifact of the `.dnt` format, which is a compatibility surface. Do not touch it here. Whether the web node-type document should go is a separate question with a separate blast radius; if you think it should, say so in the handoff rather than doing it.
- **No new test.** Nothing is added or changed; the existing L5 passes are the guard, and the project rules give no test for deletions of uncompiled code. The build is what proves the project still compiles.
- **Architecture text.** `docs/architecture/frontend.md` is the page that owns this subject. If it mentions the web leftovers, correct it; if it does not, add nothing - a page does not need a sentence about files that no longer exist. Run `python tools/docs-size-check/check_size.py` if you edit it.
