## What this is

The second of four PostgreSQL tickets: the device library itself, compiled, in the layout, and its translation pinned by golden files - with no PostgreSQL server involved.

`libraries/PGSQLDevice` is 3,100 lines over six files plus the PostgreSQL dialect's own syntax tree and emitter (`Source/Language.PGSQL/`), an embedded `SystemCatalog.d4` operator map and an embedded `SystemCatalog.sql`. Its project is still in the .NET Framework format and the layout excludes the library, naming `device-pgsql-port`. The conversion is the ordinary one; what makes this ticket worth separating from the live work is that **the golden harness makes the device testable without a server**, and the harness was built to take the device as a parameter precisely so this would be cheap.

`test-device-sql-golden` (prerequisite) leaves a `TestFramework.SQLRecorder` library whose connection class records statements instead of sending them, an abstract `DeviceTranslationGoldenTests` fixture holding the corpus and the golden machinery, and one subclass for SQL Server. This ticket adds the second subclass. The recipe transfers directly: the PostgreSQL device has the same three startup settings that must be off (`ShouldDetermineVersion`, `ShouldEnsureDatabase`, `ShouldEnsureOperators` - all defaulting to true, all connecting), and its `ConnectionClass` and `ConnectionStringBuilderClass` are overridable in exactly the same way (`PostgreSQLDeviceSession.InternalCreateConnection`).

The value is not in the files but in what producing them forces: every case of the shared corpus has to generate *something*, and a corpus case that the PostgreSQL device cannot translate at all is a finding. A device that has had almost no maintenance since 2017 will have some.

**The connection-string defect this ticket was written to fix does not exist - do not change the keyword legend.** The plan expected `PostgreSQLConnectionStringBuilder`'s `SearchPath` keyword to be rejected by the current driver, which spells it `Search Path`. The review of `device-pgsql-connection-port` measured the whole string `PostgreSQLDeviceSession.InternalCreateConnection` builds from the device defaults against the pinned driver, with the search path both empty and set: every keyword is accepted, `SearchPath` included, because the driver's keyword lookup ignores the spacing. The legend's tag names are a compatibility surface - they are what a device's D4 definition writes - so leave them alone. What *is* newly fatal is an **extra** keyword: `SQLDevice.GetConnectionParameters` merges a deployment's `ConnectionParameters` tag into the string verbatim, and the driver now throws on a keyword it does not recognise where the 2009 driver ignored one. That one needs a live connection to matter, so it belongs to `device-pgsql-port`. Still worth doing here: the recorder records the connection string it is handed, so pin the generated connection string in the golden fixture - the only check available for it without a server.

## Edge cases & interactions

- **Every corpus case must be accounted for, in both directions.** The shared corpus was written for SQL Server. A case this device cannot translate must be recorded as such - the fixture's unsupported-boundary mechanism, not a silently missing golden file - with a one-line reason, and the set assertions must still hold in both directions. A corpus that quietly covers less for one device than for the other is the failure mode to avoid; `FrontendDerivationGoldenTest`'s expected-failure table is the shape to copy, including that it drains when a defect is fixed.
- **`debt-unreachable-redefine-nodes` already touched this device's operator map.** `docs/architecture/devices.md` records that `System.iRedefine(table)` was retired from the engine and from this device's and the SQL Server device's maps, and carries a `NOTE:` that the parked Oracle and SAS catalogs under `legacy/` still map it. A device's operator map is run as a D4 script when the device registers, and a mapping naming an operator the engine no longer declares fails the whole script, so the device would not register. Registering the device is therefore the first thing to prove, and the embedded `SystemCatalog.d4` is the first place to look if it fails.
- **`SystemCatalog.d4` is a `String.Format` template, not a whole script.** `ParserRoundTripCorpusTest` formats the three device templates before parsing them, including this one, and has entries for them. Any edit to the template has to keep its placeholders in step with the `String.Format` call in `PostgreSQLDevice.RegisterSystemObjectMaps`, and that test is the guard.
- **`Mono.Security` and the 2009 driver are already gone** by the prerequisite. Nothing in this library should reference either; if something does, that is a finding about the prerequisite's completeness, not a reason to add a reference back.
- **The device's own `.d4l` lists one assembly** (`AlphoraPGSQLDevice.dll`) and requires `System`, `SQLDevice` and `PGSQLConnection`. The layout's `.d4l` check is what fails until the project is in the Library list, which is the signal the two halves are in step.
- **The golden files pin the dialect, not the server.** PostgreSQL's identifier folding (unquoted identifiers fold to lower case, quoted ones do not) is a real behaviour difference from SQL Server and will show in the generated text. Read every golden file before checking it in; a case whose text looks wrong *is* probably wrong, and this is the cheapest point in the whole PostgreSQL port at which to notice.
- **No live claim may be made.** A green golden run says the device generates the text it generates. It says nothing about whether PostgreSQL accepts it, which is `device-pgsql-port`'s subject. Say both halves plainly in the handoff; the temptation to call the device "working" after this ticket is the one thing that would make the split harmful.
- **The catalog store is separate.** `store-pgsql-port` owns `src/engine/Store.PGSQL`; nothing here touches it.
- **New tests, and they are the point** - the project rules' characterization test for a subsystem being re-hosted, at the lowest layer that shows the behaviour, which for translation is the generated text. No test for the project conversion itself.
