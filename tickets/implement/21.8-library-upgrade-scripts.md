## What this is

The remainder of WS7's `library-upgrade-scripts` work item. Most of it landed with `debt-library-upgrades-coverage` (2026-11-23), which documented the mechanism in `docs/architecture/libraries-and-class-loading.md` and added the `LibraryUpgrades` coverage script - 425 lines, nine sections, one behaviour each, from the ordinary apply through version ordering, requisite order, the nil-version inject, the two liberties the shipped `Frontend` upgrade script takes, and partial failure with a resume afterwards. Its review named exactly what it could not cover and parked it here. Two things, plus one it grouped with them.

**The restart, which is the assumption the whole script rests on.** An upgrade is pending when a library's files on disk claim a newer version than the catalog records as applied. A coverage script cannot produce that state honestly: on a registered library, raising the descriptor version carries the recorded version with it, so every section of `LibraryUpgrades.d4` stands in for "new files arrived and the server was restarted" with `update LibraryVersions set { Version := ... }`, each such line carrying a comment saying so. What makes that stand-in legitimate is a deliberate piece of `src/engine/Server/Schema/LibraryUtility.cs`: `LoadLibrary` reads the recorded version before loading and writes the same value back afterwards, precisely so that a restart does not swallow a pending upgrade. Nothing anywhere pins that. If it regressed, every section of the script would still pass and the premise underneath them would quietly be false.

A C# fixture is the shape, because only a C# fixture can stop and start a server. `tests/DAE.Server.Tests/LibraryAttachTest.cs` is the precedent and the pattern to copy: a `TestServerInstance` of its own per case, `instance.Server.Stop()` then `instance.Server.Start()` (its `AttachedDirectorySurvivesARestart` case does exactly this), and a helper that builds a library folder the server itself wrote rather than a hand-written `.d4l` - writing one by hand would pin the fixture's idea of the format instead of the server's.

What the case has to show: a library registered at one version, an upgrade script saved for the next revision, the library's **descriptor** raised to that revision on disk the way a new release would raise it (the files arriving is the real event, not a catalog edit), the server restarted, and then - after the restart - the upgrade still pending, `UpgradeRequired` still true, and `UpgradeLibrary` still applying it. The negative half matters as much: the recorded version after the restart must be the old one, because a restart that recorded the descriptor version would make the upgrade vanish.

**An upgrade whose payload is a real application change.** Every section of the coverage script upgrades one small memory-device table. A customer's upgrade script does more: it adds a device, a table in a device, an operator over a class in the library's own assembly, a form document, a constraint, a right. The failure modes are different - an upgrade that creates a device has to start it, one that adds an operator over a class needs the assembly the library's new version ships, one that adds a form document touches the Frontend device rather than the catalog. Cover at least a device-and-table payload and a form-document payload; an assembly payload is the interesting one and also the hardest, because a loaded library assembly is never unloaded from a process (`LibraryLoadingTest` owns that ground) - if it cannot be done honestly in one process, say so rather than writing a case that only looks like it covers it.

**And the one grouped with them:** `UpgradeLibraries()` across several libraries stops at the first failure and leaves the libraries after it un-upgraded at their own recorded versions, with nothing saying which they were. The review documented that from reading `UpgradeLibraries(Program, string[])`, which has no catch around its loop, and did not run it. A section with two independent pending libraries, the first failing, and assertions on which recorded versions moved, covers it. That one is a coverage-script section, not a C# case.

## Edge cases & interactions

- **Raise the descriptor version the way a release does.** The point of the restart case is that the *files* claim a newer version. Writing the new version into the library's `.d4l` on disk while the server is stopped is the honest stand-in for a new release being unpacked; a `SetLibraryDescriptor` call on the running server is not, and in any case `SetLibraryDescriptor` refuses to raise a registered library's version (the coverage script's header records that). Say in the fixture which one you did and why.
- **A library with files is a different animal from one without.** `LibraryAttachTest`'s remarks say no library there has files, because an attached library with an assembly loads it on registration and a loaded assembly is never unloaded. The same constraint lands on any upgrade case whose payload is an assembly: each case gets its own `TestServerInstance`, and a second case cannot re-load a changed copy of the same assembly name in the same process. Design around it or report it as the reason a case is not there.
- **`DATAPHOR_TEST_LOGGING` keeps instance folders.** A case that rewrites a `.d4l` between stop and start leaves a folder whose descriptor differs from the layout's copy. Harmless - the folders are per-run copies - but worth a sentence so a developer reading a kept folder is not confused by it.
- **A server that rewrites `.d4l` files is the normal case.** A running server writes into its library directory, which is why the suite copies library folders per instance; a case that edits a descriptor is editing the *copy*. Never point an instance at the runtime layout or the repository (`AGENTS.md`, *Rules that are easy to break*).
- **The upgrade machinery's transaction contract is already pinned** by the coverage script's `UpgradeNested`/`UpgradeNesting` section: an upgrade script may upgrade a library that is not one of its requisites, and it must leave a transaction open when it returns (removing the closing `BeginTransaction()` from the shipped `Frontend` pattern fails with *No transaction in progress for this process*, measured). A restart case must not accidentally re-pin that; keep the two subjects apart.
- **Two things in the engine are documented as unreachable and should stay that way.** `GatherDependents` and `UpgradeUtility.GetRequisitesFileNameFromVersion`/`GetRequisitesFileName` have no caller and carry `NOTE:` comments saying so; `InjectUpgradeNode`'s descriptor-restoring catch is reachable only through a file-system failure. Do not reach for them to raise a coverage number.
- **`LoadUpgrade` on a missing file throws a raw `FileNotFoundException` carrying a server file path, and `DeleteUpgrade` on the same missing file is silently a no-op.** The earlier ticket left both alone deliberately - unchanged from 3.1, reachable only from the IDE, and both the message and the silence are themselves a compatibility surface. Leave them; do not add a case that freezes the unhelpful message.
- **No engine behaviour change is expected.** If the restart case fails, that is a real defect in `LibraryUtility.LoadLibrary`'s read-and-write-back and the fix belongs here with its reproduction, which is the case you just wrote. If it passes - the likely outcome - the value delivered is that it can no longer regress silently, which is the whole point; say that plainly rather than dressing it up.
- **Architecture text.** `docs/architecture/libraries-and-class-loading.md` already has three paragraphs on the mechanism and was 742 words of its 1,500-word cap. Add only what the new cases establish: that the restart preservation is now pinned by a test, and whatever the real-payload cases turn out to show. Run `python tools/docs-size-check/check_size.py` afterwards.
