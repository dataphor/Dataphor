## What this is

The last of four tickets building the test plan's layer 4, and the one that finishes the work item, so it keeps the slug `test-client-server`. The first three built a child-process server, the coverage that needs it, and the killed-client case. This one spends that machinery on the hardest thing in the layer: the `ServerLink` coverage script.

A *server link* is a D4 object naming another Dataphor server; `ExecuteOn` and `EvaluateOn` run statements and expressions on it, and `select … on <link>` reads from it. The script `tests/libraries/TestFramework.Coverage.Scripts/Documents/ServerLink.d4` is about 240 lines and some thirty assertions covering the whole feature: default and tagged links, session-info propagation, link users and their credentials, `alter server`, parameters in and out, every shape of non-scalar result, `like` types across the link, and the `ServerLinks`, `ServerLinkUsers` and `RemoteSessions` system tables. Its own first comment says what it needs: *"Assumes a running default Dataphor instance."* There has never been one in the test run, so the script has never passed, and the whole feature is uncovered.

`tests/DAE.Server.Tests/coverage-manifest.json` records it as a known failure owned by this slug, matching on `SocketException`. **The script must not be edited** — it is an assertion of correct behaviour and there is no reference runtime to re-derive it from (project rules; plan decision D2).

## What the script actually needs, established from the code

Every link in the script resolves the same way, because none of them sets a port override:

- `create server Test;` with no tags and `create server Test tags { HostName = "localhost", InstanceName = "Dataphor" }` are **the same link**. The parser always builds a `MetaData` object (`Parser.MetaData` assigns one before reading tags), so `Schema.ServerLink.ApplyMetaData` always runs, and its defaults are `HostName` `"localhost"` and `InstanceName` `Engine.DefaultServerName`, which is `"Dataphor"`. So the script needs an instance **named `Dataphor`** on **`localhost`** and nothing else.
- The connection is made from inside the server running the script: `RemoteSessionImplementation` builds a `NativeCLISession`, and `NativeCLIClient.GetNativeServerURI` with no port override calls `ListenerFactory.GetInstanceURI(hostName, 0, instanceName, true)`. So resolution goes through a **listener**, and the port it asks on is `overridePortNumber == 0 ? DataphorServiceUtility.DefaultListenerPortNumber : overridePortNumber` in `DataphorServiceUtility.BuildListenerURI` — that is, **8060**, a compiled-in constant.
- The listener answers out of the instance list **its own process** resolves (`ListenerService.GetConfiguration` → `InstanceManager.LoadConfiguration`), and builds the reply from the **client's** host name plus the configured port (`ListenerService.GetInstanceURI` → `DataphorServiceUtility.BuildNativeInstanceURI`). So the listener need not know its own address, and the instance it names can be on any port.

## The three decisions this ticket had to make, and the answers

### 1. The second server runs in a child process

Not in the test process. Two servers in one process share the engine's static state, and in particular `Schema.Object`'s object-id counter: the second engine's `InitializeCatalog` resets it to zero while the first is still allocating from it (`bug-object-id-counter-is-process-wide`). The coverage harness already builds a fresh server **per script**, each resetting that counter, so a long-lived in-process linked server would be stomped by every later script's start. A child process has its own counter and its own catalog and interacts with the harness not at all — which is exactly what the previous three tickets built.

### 2. The listener port is dynamic, and the client side of it becomes settable

Taking port 8060 was rejected. The plan's own cross-cutting requirement for WS3 is explicit — *"no test touches `%ProgramData%`, the registry or a fixed port"* — and the failure mode is worse than a collision: on a machine with a real Dataphor 4 installation, a real listener already holding 8060 would answer the script's lookup and point it at a **real instance**, and the script creates users, tables, types and operators. A test must not be able to do that.

So: `DataphorServiceUtility` gains a settable process-wide default for the listener port, consulted by `BuildListenerURI` when a caller passes no override.

- `public const int DefaultListenerPortNumber = 8060` **stays exactly as it is** — it is a public constant an extension may compile against, and it remains the default value.
- Add `public static int ListenerPortNumber { get; set; }`, initialised to `DefaultListenerPortNumber`, and have `BuildListenerURI` use it in place of the constant when `overridePortNumber == 0`. Document it the way the hooks on that class are documented: set it from start-up code before anything connects, and it is a process-wide setting, not a per-connection one.
- **Client side only.** No host change: `ListenerServiceHost` already resolves a concrete port before it calls `BuildListenerURI` (`overridePortNumber == 0 ? DataphorServiceUtility.DefaultListenerPortNumber : overridePortNumber`), and a server's listener port is already settable per instance through `ServerConfiguration.OverrideListenerPortNumber`, which is the configured route and the one the child will use. Say this at the site, so the asymmetry reads as deliberate.
- **Not added to `RevertHooksToDefault`.** That method exists to put the *binding and endpoint hooks* back, and it clears the memoized binding with them; a port is not a hook and folding it in would make an unrelated call change where clients look for a listener. The fixture restores it itself.
- The default is unchanged, so a normal deployment sees nothing. `docs/migration-notes.md` gains one entry for the new member, since an extension could set it.

The two callers that pass no override are `ClientServer.Open` and `NativeCLIClient.GetNativeServerURI`; nothing in the suite today resolves through the listener without an explicit port (`CoreWcfProtocolTest` passes `_host.ListenerPortNumber` in both of its listener cases), so setting it for one case disturbs nothing. Verify that rather than taking it on trust.

### 3. The harness starts the linked server for the scripts that declare they need one

`coverage-manifest.json` already carries optional per-script facts — `preamble`, `batches`, `register`, `timeoutSeconds` — and this is one more:

- `CoverageEntry` gains `[JsonPropertyName("linkedServer")] public bool? LinkedServer`, allowed only as `true` and only on a non-`fragment` entry, following `batches`' shape and validation (the manifest's serializer options set `UnmappedMemberHandling.Disallow`, so the field has to be declared before it can appear).
- `CoverageManifest`'s own remarks — which are the manifest's documentation — gain the bullet describing it: *a second Dataphor server, in a child process, named `Dataphor`, hosting a listener on a dynamically chosen port, started before the script and stopped after it; use it only for a script that creates a server link with no port override, and say why in `note`.*
- `CoverageScripts.Execute` starts it for such an entry, around the script's own server, and stops it in a `finally`; so the cost falls on the one case that needs it and the other scripts are untouched. Set `DataphorServiceUtility.ListenerPortNumber` to the child's listener port while it runs and restore it afterwards, in the same `finally`.
- `AGENTS.md`'s *D4 coverage scripts* paragraph describes the manifest's statuses and fields; add the field there too.

The child's configuration: instance name `Dataphor`, a reserved free port, `ShouldListen = true` with `OverrideListenerPortNumber` set to a second reserved free port, its own library copy and instance folder, logging off — that is, `OutOfProcessInstance` with a listener, which it does not do yet (every fixture so far sets `ShouldListen = false`). Give it the two parameters rather than a second helper.

**Its host name is the machine name, not the loopback literal**, and this is the one deliberate exception to the suite's "no port another machine can reach" convention. The reason is measured and recorded in the plan under *CoreWCF hosting*: a **name** makes CoreWCF open both `0.0.0.0` and `[::]`, while a **literal** binds that address only and leaves a client whose name resolves to the other family paying about two seconds per channel open before the stack falls back. The script connects to `localhost`, which this ticket cannot change, and it opens on the order of thirty remote sessions; two seconds each would take it past its 120-second harness timeout. So the child binds all interfaces, on two dynamically chosen high ports, for the few seconds the script runs. State this in the code at the site with the reason, and in the handoff.

## What "done" means

**The linked server exists and the script runs. Whatever it then reports is triaged, not hidden.** The script has never completed on .NET 10, so it may well fail on something real — a defect in the server-link path, a parameter-marshalling difference, a behaviour the port changed. Two acceptable outcomes:

- It passes: flip the manifest entry to `"status": "pass"` and drop `ticket`, `error` and `note` (the format requires `ticket` and `error` to be absent on `pass`).
- It fails on its own causes: keep it `known-failure`, with the **new** error substring and a **new** owning ticket, and file one ticket per cause in `tickets/fix/` describing the failure — not in `backlog/`, because a script that now runs and fails is a live defect. The entry's `ticket` then names the one that owns the cause; say in the handoff what the script got through before it stopped.

What is **not** acceptable: editing the script, loosening an assertion in it, leaving the entry pointing at this slug after this ticket completes, or reporting the case as skipped for any reason other than a manifest status.

Also to be cleaned up when it passes: `tickets/.pre-existing-known.md` carries a `one-off` record for this script — that on machines where a loopback connect to a closed port is never refused, it fails with a 120-second harness timeout instead of its recorded `SocketException`, adding about two and a half minutes to the run. A script with a listener to reach does not connect to a closed port, so the record describes a failure mode that no longer exists; remove the bullet and say so in the handoff. If the script does **not** end up passing, re-read that record before concluding anything about a timeout, and update it rather than removing it.

Cost: one child server inside the coverage run, plus the script. `ServerLink` runs in suite part 3 (the scripts whose names do not begin A–R). Measure part 3 before and after; on machines affected by the record above it should get *shorter*. If the script needs longer than the 120-second default, raise `timeoutSeconds` on its entry and say why in `note`.

## Edge cases & interactions

How each is covered: **(test)** the script or a case asserts it, **(seam)** an assertion or guard in code, **(inspection)** read and reasoned about, no test.

- **A real Dataphor listener on 8060 on the build machine.** *(seam)* Nothing in this design touches 8060: the child's listener is on a reserved free port and the client side is pointed at it. Check by hand, with a real listener running if one can be arranged, that the script still reaches the child and not the real one.
- **`DataphorServiceUtility.ListenerPortNumber` left set after the case.** *(seam)* Restored in the same `finally` that stops the child, so a failure inside the script cannot leak it into later cases. A leak would silently break any later listener lookup; there is none in the suite today, which is why the restore has to be in code rather than left to case order.
- **The static is process-wide while other coverage cases run.** *(inspection)* The coverage fixture is not `[Parallelizable]` and `Execute` runs one script at a time, so the window is one case. Confirm that is still true in `CoverageScripts` rather than assuming it.
- **The child failing to take its listener port.** *(seam)* `DataphorServiceHost` deliberately starts anyway when the listener port is held (`TestTheListenerPortBeingTakenDoesNotStopTheServer`), and reports it through `IsListening`; the harness's `READY` line already carries `listening=<true|false>`. The fixture must **fail the case** when it is false, rather than letting the script fail later with a socket error that looks like the old known failure.
- **The script's `localhost` resolving to the family the child did not bind.** *(seam)* The machine-name host name, above. If the script is slow in a way that suggests per-connection fallback, that is the first thing to check; record the measured script time either way.
- **The script leaves state in the child.** *(inspection)* It creates and drops users, tables, types and operators on the link, and `CreateServerLinkUserWithEncryptedPassword` sets a password on the far side. The child is fresh per coverage run and is thrown away with its folder, so accumulation does not matter; but the script must be the *only* user of that child, so do not share it with another script even if a second one later declares the field.
- **Native sessions on the child are never reclaimed** (`bug-native-cli-sessions-never-reclaimed`): the script's links hold native sessions on the child, and nothing there times them out. Harmless — the child is killed at the end of the case — but worth a sentence in the handoff, because it means the case cannot be turned into a long-running or repeated one without that ticket landing first.
- **The child's own listener answers for every instance in the list it resolves.** *(inspection)* Its list is the private one the fixture wrote, holding one instance. Nothing else can be discovered through it.
- **`EnsureLibraryRegistered` and the template.** *(inspection)* The child needs no libraries: everything the script uses is in `System`, and the server creates `General` itself. Do not give it the coverage libraries; that would double the start cost for nothing.
- **Manifest validation.** *(seam)* `linkedServer` must be rejected on a `fragment` entry and when written as `false`, the way `batches` is, and the manifest's "fields, and nothing else" list has to carry it or the strict-JSON check rejects the file. There is already a test path for manifest problems — one invalid field fails the run with a problem list, which is the behaviour to preserve, not a new test to write.
- **The script's timeout and the harness's abort path.** *(inspection)* `CoverageScripts` abandons a server whose script will not stop, with a `NOTE:` saying no script reaches that today. A script waiting on a network call is a new way to reach it. If the abort path does run, the child server must still be stopped and the static still restored — check that the `finally` ordering gives that.
- **Part 3's time.** *(seam)* Measure it. `AGENTS.md` says a part past about eight minutes gets split by letter; if this pushes it there, split it in this ticket and update both `AGENTS.md` and `tickets/rules/10-dataphor.md`, which both carry the commands.

## Tests

The `ServerLink` coverage script itself is the test, and it is the whole point: some thirty assertions over a feature with none today. Nothing else is added. No unit test for the new static (a setter), none for the manifest field (the manifest's own validation covers a bad entry), and no second out-of-process case — the previous three tickets own those.
