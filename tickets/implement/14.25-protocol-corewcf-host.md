## What this is

`protocol-corewcf-proof` showed that one client session works over the existing protocol against a CoreWCF host built for the occasion, and its write-up (the *CoreWCF proof* subsection under WS5 in `docs/modernization-plan.md`) settled the binding, the instancing, the message-size limits, the fault types and the timeouts. **Read it before starting; this ticket must not re-open any of it.**

This ticket turns that into the real thing: all three services, every operation, started and stopped by the same `DataphorServiceHost` entry points that the console host and the Windows service already call, at the same addresses and ports, from the same instance configuration. `protocol-corewcf-host-prepare` has already removed the two dead settings and moved the two host source files into `src/engine/Server.Hosting/`, where they are not compiled by anything yet.

The four questions the proof left open are all answered below, by measurement. The answers are not up for re-litigation in the implementation; what is left is the writing.

## Decision 1: hosting goes into its own assembly, not back into the server assembly

The proof flagged this as a design call: the server assembly already grew by 31 packages when `CoreWCF.Primitives` arrived, and hosting needs `CoreWCF.NetTcp`, which brings ASP.NET Core with it. **Measured, the cost of putting `CoreWCF.NetTcp` into `src/engine/Server/Server.csproj` is unacceptable, so hosting gets its own assembly.**

The measurement. `CoreWCF.NetTcp` 1.9.1 depends on `Microsoft.AspNetCore.WebUtilities` 2.3.10, which NuGet's package audit reports as having a known moderate-severity vulnerability (`NU1902`). A project is clean only if it declares **both** `CoreWCF.NetTcp` as a direct package reference **and** `<FrameworkReference Include="Microsoft.AspNetCore.App" />`, which substitutes the in-box ASP.NET Core 10 assemblies for the 2.3.10 packages. Any project that gets `CoreWCF.NetTcp` indirectly, through a project reference, reports `NU1902` — adding the framework reference to that project does *not* help. Four scratch projects were built to establish this: direct package plus framework reference, clean; project reference plus framework reference, warns; project reference alone, warns; project reference plus its own direct package plus framework reference, clean. `dotnet restore Dataphor.slnx` reports no audit warning at all today, so the comparison is against zero.

Putting the package in the server assembly would therefore make `Store.SQLite`, `Connection`, `MSSQLDevice`, `SimpleDevice` and `Frontend` (server side) — five library projects with nothing to do with hosting — report `NU1902`, and the root `AGENTS.md` forbids suppressing `NU1900`–`NU1904`. The only way to silence them would be to give each a package reference and a framework reference it has no use for.

So: **a new project `src/engine/Server.Hosting/Server.Hosting.csproj`, assembly name `Alphora.Dataphor.DAE.Server.Hosting`**, holding the two host classes and the host-side binding, referencing the server assembly. The five library projects stay clean; the test project already carries both the package and the framework reference and stays clean.

What this does **not** fix, and must be said plainly in the plan: `src/client/DAE.Client/ServerConnection.cs` creates a `DataphorServiceHost` for an in-process alias that is not embedded (the Windows client or the IDE hosting a full server with network endpoints inside its own process — a real feature). So `DAE.Client`, and through it the Windows client and the IDE, must reference the hosting assembly and will report `NU1902` and require the ASP.NET Core shared runtime at run time. None of those projects is in `Dataphor.slnx` yet, so the solution build stays clean; the question of breaking that dependency belongs to WS6's `ui-client-layering`, and this ticket hands it over in writing. The other way out — turning on transitive package pinning in `Directory.Packages.props` to pin `Microsoft.AspNetCore.WebUtilities` — belongs to `security-dependency-audit`, which that file's comment already names.

## Decision 2: `DataphorServiceHost` keeps its own host inside it, and there are two of them

The plan ticket's instruction was to keep `DataphorServiceHost` self-contained unless the proof found that impossible, so that `DAEServer`, the Windows service and `DAE.Client` keep working unchanged and `host-generic-host` reshapes them next. It is possible, and it is what to do.

But it cannot be **one** .NET Generic Host for all three services, because of the listener. `ListenerServiceHost` deliberately swallows the error from opening its port: one listener per machine serves every instance on that machine, which is why its port is fixed at 8060, and a server whose listener could not start must still start and still serve its own endpoint. With all three endpoints on one host, a taken listener port would fail the whole host and the server with it.

So: **two Generic Hosts in the process.** One carries the instance's own two endpoints (the main service and the native CLI service, both on the instance's port) and belongs to `DataphorServiceHost`. The second carries the listener on the shared listener port and belongs to `ListenerServiceHost`, whose constructor starts it and swallows a failure exactly as today.

Measured: two Generic Hosts, each with its own `UseNetTcp` listener, coexist in one process and both serve. When the second host's port is already held by another socket, `host.Start()` throws `System.IO.IOException` ("Failed to bind to address http://[::]:<port>: address already in use"), the first host is unaffected and still answers calls, and calling `Dispose()` on the host that failed to start is clean.

## Decision 3: the listen address is the machine name, and that is what gives both address families

The proof's host bound IPv4 loopback only and measured the cost: a client given a name that resolves to IPv6 first pays about two seconds per channel open before the stack falls back, and a client using the machine name cannot connect at all.

Measured answer: pass `net.tcp://<machine name>:<port>/` to CoreWCF's `NetTcpOptions.Listen`, and CoreWCF binds `[::]` in dual-stack mode — the same thing today's `ServiceHost` does. With that, clients connecting by `127.0.0.1`, by `localhost` and by the machine name all reached the endpoints in single-digit milliseconds, even though the endpoint addresses were registered under the machine name only: the host name part of the address is not compared when a call is dispatched, the path is. Nothing extra is needed to get both address families — just do not use a literal address.

## Decision 4: the two endpoints on one port, one of them below the other, work

The proof could not test the native CLI endpoint, which sits at a path *below* the main endpoint (`net.tcp://host:port/<instance>/service/native` under `net.tcp://host:port/<instance>/service`), and called it the first thing to check.

Measured answer: **it works.** Two services, two contracts, one `Listen` call for the single port, endpoint addresses `/<instance>/service` and `/<instance>/service/native`, and calls to both were dispatched to the right service — from all three client host-name forms. So the native CLI keeps its documented address, which is the compatibility surface that matters here.

## What the code has to look like

### The new project

`src/engine/Server.Hosting/Server.Hosting.csproj`, following the conversion rules in `AGENTS.md`: `AssemblyName` `Alphora.Dataphor.DAE.Server.Hosting`, `RootNamespace` `Alphora.Dataphor.DAE`, `DefineConstants` set outright to `TRACE` with `DEBUG;TRACE` in Debug, no `OutputPath`, explicit `Compile` items (default items are off), project references to `..\Server\Server.csproj` and `..\..\protocol\Common\Common.csproj` plus whatever else the compiler asks for, package reference `CoreWCF.NetTcp` (already in `Directory.Packages.props` at 1.9.1) and `<FrameworkReference Include="Microsoft.AspNetCore.App" />`. A short comment block explaining the framework reference and the audit measurement above, in the style of the comments already in `Server.csproj`. A minimal `Properties/AssemblyInfo.cs` with only `AssemblyTitle` and `AssemblyDescription`, to match the tree; everything else comes from `Directory.Build.props`.

The classes keep the namespace `Alphora.Dataphor.DAE.Service`. Their type names and namespace do not change; only the assembly they live in does.

### `DataphorServiceHost`

The surface the console host, the Windows service and `DAE.Client` already use stays: the parameterless constructor, `InstanceName` (settable only while inactive), `Server`, `IsActive`, `Start()` and `Stop()`. Two members are added:

- **`HostName`**, settable only while inactive, defaulting to `Environment.MachineName`. It is the host name in both the listening address and the endpoint addresses, so with the default the addresses a 4.0 server publishes are byte-for-byte what 3.1 published. It exists because the tests must listen on loopback rather than on every interface of the build machine, and because a server on a multi-homed machine may need to choose.
- **`Start(ServerConfiguration instance)`**, which hosts the configuration it is given and never touches `InstanceManager`. `Start()` becomes: resolve the instance from the machine instance list exactly as today — load it, and when the named instance is not there, build a default one, add it and save the list — and then call `Start(instance)`. This is the seam the tests use, and `test-client-server` will want it too, because the old out-of-process test fixture's worst habit was registering an instance in the machine-wide list (known defect K18).

`Start(instance)` does what the current code does, in the same order, with the same log messages: create the `Server`, apply the configuration, create the `RemoteServer` and the `NativeServer`, start the engine server, then build the services and open the endpoints. The host is one `HostBuilder().ConfigureWebHost(…)` as in the proof's `CoreWcfProofHost`: `UseKestrel()`, `UseContentRoot(AppContext.BaseDirectory)`, the server-URLs setting left empty **so that Kestrel opens no HTTP endpoint of its own**, status messages suppressed, one `Listen` call for `net.tcp://<HostName>:<instance.PortNumber>/`, `AddServiceModelServices()`, both service objects registered as singletons so that CoreWCF uses the instances built here, and two endpoints:

| Endpoint | Address | Contract |
|---|---|---|
| Main | `DataphorServiceUtility.BuildInstanceURI(HostName, instance.PortNumber, instance.Name)` | `IDataphorService` |
| Native CLI | `DataphorServiceUtility.BuildNativeInstanceURI(HostName, instance.PortNumber, instance.Name)` | `INativeCLIService` |

Logging providers are cleared for now, as in the proof. Wiring the server's own log and the Windows event log through `Microsoft.Extensions.Logging` is `host-generic-host`'s item in the plan; do not start it here.

Then, when `instance.ShouldListen`, construct the `ListenerServiceHost`. Its failure is still swallowed, but no longer invisibly: `DataphorServiceHost` asks it whether it started and, when it did not, writes one line through the engine server's log saying that the listener service is not running because its port is already in use, with the reported message. That is the only behaviour this ticket adds, and it is worth it — the swallow is correct but silent, and it is the one thing most likely to confuse someone diagnosing a failed discovery call.

`Stop()` keeps its signature and its order: listener first, then the instance's host, then the service, the `RemoteServer` and the engine server. The host is stopped with a bounded wait and then disposed, as the proof does (`StopAsync` with a ten-second timeout, then `Dispose`), because Kestrel's graceful shutdown waits for open connections and a client channel may still be open. `Stop()` is also called from `Start`'s own failure path, so every stage must tolerate a half-built state: a host that was built but never started, an engine server that was created but never started, a null service.

### `ListenerServiceHost`

Constructor becomes `ListenerServiceHost(string hostName, int overridePortNumber, bool requireSecureConnection)`:

- `useServiceConfiguration` is gone with the feature.
- `useCrossDomainService` is gone with `AllowSilverlightClients`, which `protocol-corewcf-host-prepare` removed. It was the cross-domain access-policy switch for the removed Silverlight client, not a transport-security setting, so this does not take anything away from `protocol-transport-security`.
- **`requireSecureConnection` stays, and stays unused.** `protocol-transport-security` owns that question and needs the evidence intact: the setting is still read from the instance configuration and still passed down to a parameter nobody reads, and `DataphorServiceHost` still never reads `instance.RequireSecureConnection`. Do not start honouring either here, and do not delete either.

The port is `overridePortNumber == 0 ? DataphorServiceUtility.DefaultListenerPortNumber : overridePortNumber`, as today. The body builds its own Generic Host for the one `IListenerService` endpoint at `DataphorServiceUtility.BuildListenerURI(hostName, listenerPort)`, with `ListenerService` registered by type and not as an instance, so that CoreWCF constructs it per session exactly as `new ServiceHost(typeof(ListenerService))` does today. Starting it stays inside a `try`/`catch` that swallows, because the port being taken by another process's listener is the normal case; add a read-only member saying whether it started and what was reported, for `DataphorServiceHost` to log. `Dispose` stops and disposes the host, and must be safe after a failed start.

### The binding

`src/engine/Server.Hosting/DataphorServiceHostBinding.cs`: `public static class DataphorServiceHostBinding` in namespace `Alphora.Dataphor.DAE.Service`, with `public static CoreWCF.Channels.Binding Build()`. Move the body from `CoreWcfProofHost.BuildBinding` unchanged — every limit read from `DataphorServiceUtility.MaxMessageLength`, both timeouts `TimeSpan.MaxValue` — and move its comment with it. Each host builds one and uses it for all of its endpoints.

This is the second declaration of the one binding the protocol is specified by; the client's is `DataphorServiceUtility.DefaultBuildBinding`. The two stacks have unrelated `Binding` types, so the settings are necessarily written twice, and the test that compares them (see below) is what stops a one-sided edit from changing the protocol quietly.

### `NativeCLIService`

Back into `src/engine/Server/Server.csproj`'s compile list, beside `DataphorService.cs` and `ListenerService.cs`, with the same one-line change those two already had: `using System.ServiceModel;` becomes `using CoreWCF;`, so that the `[ServiceBehavior]` is the one CoreWCF recognises and the eleven `FaultException<NativeCLIFault>` throws are CoreWCF's. The proof established why this matters: a `System.ServiceModel` fault thrown from a CoreWCF service reaches the client as an untyped unhandled-error fault, so every native-CLI error would arrive as a communication failure instead of the typed exception the client rebuilds. Copy the explanatory comment from `DataphorService.cs`. The contract interface `Contracts/INativeCLIService.cs` does not change. This file needs no new package: `CoreWCF.Primitives` is already referenced.

With that, the server project's compile list and the comment block above it are both clean — no comment claiming anything is still left out.

## What must still be true afterwards

- An existing client, with no edits and no configuration change, connects to a 4.0 server on the default ports and completes what it does today: sessions, prepared plans, cursors with their capabilities, streams, catalog cache synchronization, the debugger operations and native-CLI calls.
- The addresses and default ports are byte-for-byte what `DataphorServiceUtility` builds today, including the instance name segment and the `/service/native` suffix.
- The process listens on exactly two ports — the instance port and the listener port — and no HTTP port.
- A server whose listener port is already taken still starts, still serves its own endpoint, and says in its log why discovery is unavailable from it.
- `dotnet restore Dataphor.slnx` still reports no `NU19xx` warning, and `dotnet build Dataphor.slnx` no new warning.
- A server link from one Dataphor server to another goes out through `NativeCLIClient` from inside the server process (`src/engine/Server/Server/RemoteSessionImplementation.cs`), so the native service has to be reachable and not merely hosted. Its acceptance is the `ServerLink` coverage script, which `test-client-server` owns and which needs a second hosted instance. **Leave `ServerLink`'s `known-failure` entry in `tests/DAE.Server.Tests/coverage-manifest.json` exactly as it is** — a known failure that starts passing fails the run, and flipping it is not this ticket's call. Say in the handoff what remains for it: the native endpoint is hosted and reachable, and what is missing is a second server for the script to link to.

## Tests

The proof's host, `tests/DAE.Server.Tests/CoreWcfProofHost.cs`, is retired: it existed to keep CoreWCF out of the server's dependency closure until this ticket settled where hosting belongs, and its job is now done by production code. Delete it, and retarget `tests/DAE.Server.Tests/CoreWcfProtocolTest.cs` onto the real `DataphorServiceHost` through `Start(ServerConfiguration)`, with `HostName` set to the loopback literal and the instance's port and listener port set to free ports reserved the way the proof reserved them. Reuse `TestEnvironment` / `TestServerInstance` for the temp instance directory and the copied library folders rather than writing new plumbing, and keep the fixture's workaround for the object-id counter.

The six existing cases carry over, adapted — among them `TestHostBindingMatchesTheClientBinding`, which now compares `DataphorServiceHostBinding.Build()` with `DataphorServiceUtility.GetBinding()`, and `TestListensOnlyOnTheReservedPorts`, which now asserts the instance port and the listener port and no other.

Five cases are added, each pinning something this ticket is the first to make true:

- **The native CLI answers on its nested address.** A native-CLI client against `…/<instance>/service/native` starts a session and executes a statement, and a main-service call on the same port still works. This is the address compatibility surface.
- **A native-CLI error arrives as the typed exception.** A statement that fails in the engine, called through the native CLI, reaches the client as a `NativeCLIException` carrying the engine's own error, not as a communication failure. This is the one behaviour the `using CoreWCF;` change in `NativeCLIService.cs` exists for.
- **Stream content crosses the wire.** The proof's stream case exercised the handle protocol but left the bytes in the client's deferred-write cache, because nothing in the shipped client's public surface forces a flush. The production path that does is a cursor update carrying an overflow value: `LocalCursor.Insert` and `Update` call `LocalProcess.EnsureOverflowReleased`, which calls `LocalStreamManager.Release`, which flushes the cached stream to the server and closes it. So: open an updatable cursor on a table with a column whose values are not native, insert a row whose value for that column was written through a stream, then read it back through a fresh cursor and compare the bytes.
- **The listener's port conflict is survivable.** With the listener port held by another socket, the server starts, its own endpoint answers, and the host reports the listener as not started.
- **`ShouldListen` false hosts no listener.** The instance serves, and nothing is listening on the listener port.

Nothing else. In particular: no test that the host starts, no test per contract operation, no test for the project references or the layout entry — the build covers those.
