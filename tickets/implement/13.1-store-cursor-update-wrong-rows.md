## What happens

`SetObjectOwner('<table>', '<user>')` fails with `DataphorException: constraint failed  UNIQUE constraint failed: DAERights.Name` on the SQLite catalog store. Reproduced in this fix run with the manifest entry's own command:

```
dotnet test tests/DAE.Server.Tests --filter Name=SecurityLibrary --logger "console;verbosity=normal"
SecurityLibrary: known-failure (store-cursor-update-wrong-rows): DataphorException: constraint failed  UNIQUE constraint failed: DAERights.Name
```

The failing statement is line 108 of `tests/libraries/TestFramework.Coverage.Scripts/Documents/SecurityLibrary.d4` (`SetObjectOwner('TestOwnedTable', 'TestUser');`).

## Two causes, both in the generic store cursor

`CatalogStoreConnection.SetCatalogObjectOwner` (`src/engine/DAE/Device.Catalog/CatalogStore.cs`, about line 2529) changes the owner of each of the object's rights:

```
SQLStoreCursor rights = OpenMatchedCursor("IDX_DAERights_Catalog_Object_ID", true, catalogObjectID);
while (rights.Next()) { rights[1] = userID; rights.Update(); }
```

`IDX_DAERights_Catalog_Object_ID` is not unique: a table has six rights rows (`…Alter`, `…Delete`, `…Drop`, `…Insert`, `…Select`, `…Update`) with the same `Catalog_Object_ID`. `DAERights`' primary key is `Name`.

**Cause 1 — the row is identified by the index's columns.** `SQLStoreCursor`'s constructor sets `_key` to the columns of the index it was opened on (`SQLStoreCursor.cs`, about line 30). `InternalUpdate` passes `_key` to `SQLStoreConnection.PerformUpdate` → `GenerateUpdateStatement`, whose `where` clause is built from it, so the statement is `update DAERights set Name = '<this right>', Owner_User_ID = …, Catalog_Object_ID = n where Catalog_Object_ID = n`. It writes this right's name into all six rows and fails on the primary key. The same `_key` feeds `InternalDelete` → `GenerateDeleteStatement`, `Insert` → `LogInsert` (whose undo is a keyed delete), and `LogUpdate` (whose undo is a keyed update). On a non-unique index each of those touches every row that shares the index value.

**Cause 2 — an update loses the cursor's position.** Verified by experiment (since reverted): with the `where` clause changed to name every column, `SetObjectOwner` on a freshly created table no longer collided but never returned; a counter in `InternalUpdate` showed the cursor updating the first right (`General.TOTAlter`, already owned by the new user) over and over. `InternalUpdate` and `InternalDelete` dispose the reader, clear the buffer and return `false`, so after `Update()` the cursor is on no row; the next `Next()` goes through `InternalNext` → `EnsureReader(_isOnRow ? SelectKey() : _startValues, true, !_isOnRow)`, which reopens the reader at the start of the range, inclusive. Any loop that updates rows that stay in the range never ends. (Today cause 1 hides this: the first update already fails.)

## Why it is a porting defect

The 3.1 default catalog store was SQL Server Compact, whose cursor overrode the row operations with positioned operations on its updatable result set (`git show v3.1:Dataphor/DAE.SQLCE/SQLCEStoreCursor.cs`): `InternalUpdate` called `_resultSet.Update()` and returned `true` (still on the row), `InternalDelete` called `_resultSet.Delete()` and returned `true`. The index's key never reached a `where` clause and an update kept the cursor's place. The SQLite store (plan decision D3) sets `_supportsUpdatableCursor = false` and uses the generic `SQLStoreCursor` path, as the SQL Server and PostgreSQL stores already did; that path was written against unique indexes and its post-update reposition is commented out (`//EnsureReader(RowToKey(FEditingRow), true, true);`). `SetCatalogObjectOwner` is unchanged since 3.1.

## Callers (checked)

Every cursor update or delete in the engine goes through `CatalogStore.cs`. All `Update()` calls except `SetCatalogObjectOwner`'s are on a primary-key cursor, matched on the full key, update once and close (`PK_DAEServerInfo`, `PK_DAERights`, `PK_DAERoleRightAssignments`, `PK_DAEUserRightAssignments`, `PK_DAEUsers`, `PK_DAEDeviceUsers`, `PK_DAELibraryDirectories`, `PK_DAELibraryOwners`, `PK_DAELibraryVersions`, `PK_DAEObjects`, `PK_DAEDevices`, `PK_DAEScalarTypes`, `PK_DAEApplicationTransactionTableMaps`). Cursor inserts are on primary-key cursors (`InsertRow`, `PK_DAEBaseCatalogObjects`, `PK_DAECatalogObjectNames`, `PK_DAEOperatorNames`, `PK_DAEOperatorNameNames`). `DeleteRows` deletes through a cursor only when `DeleteThroughCursor` (`SupportsUpdatableCursor`) is true, which no current store sets; its statement path (about line 903) reads the matching rows from a cursor on the given index and deletes each with `PerformDelete(…, indexHeader.Columns, row)`, i.e. keyed by the index's columns: on a non-unique index the first statement deletes every matching row and the rest delete nothing. The result is right today, but the statement should name the row by its primary key so that it agrees with the cursor and with any undo logging that `bug-store-nested-rollback-keeps-rows` (backlog) adds there.

So the defect is reachable today only through `SetCatalogObjectOwner` (D4 `SetObjectOwner`, and any owner change that reaches it), but the fix belongs in the cursor, not at that call site.

All 27 tables in `src/engine/Store.SQLite/SystemStoreCatalog.sql` have a primary key, and every `StoreTableHeader` in `CatalogStore.BuildTableHeader` names it (`PrimaryKeyName`).

## Expected behaviour

- An update or delete through a store cursor changes exactly the row the cursor is on, whatever index it was opened on: the statement's `where` clause names the table's primary key columns, from the row's values before the edit (`_currentRow`); the `set` clause carries the new values. The same for the undo log's inverse statements (`LogInsert`'s delete names the inserted row's key; `LogUpdate`'s inverse update names the row by its new key values and sets the old ones; `LogDelete` re-inserts the full row).
- After `Update()` the cursor is still on the updated row (as the 3.1 SQL Server Compact cursor was): `Next()` returns the row that follows it in the cursor's order and `Prior()` the one before it, using the row's new values. If the update moved the row out of the cursor's range, `Next()`/`Prior()` behave as from that position and the range check ends the scan as usual.
- After `Delete()` the cursor is between the deleted row's neighbours: `Next()` returns the row after it, `Prior()` the row before it. (Today `Next()` restarts at the start of the range, which is right for a loop that deletes every row and revisits rows for one that skips some.)
- `SetObjectOwner` on a catalog object with several rights succeeds and changes every right's owner; in a nested transaction that is rolled back, every right's owner is restored.

## Design (recommended)

- **Row identity.** Give the cursor a second column list, the row key: the table's primary key columns. `CatalogStoreConnection.OpenCursor` has them (`Store.GetIndexHeader(tableHeader.PrimaryKeyName).Columns`) and passes them through `SQLStoreConnection.OpenCursor` / `InternalOpenCursor` to the `SQLStoreCursor` constructors (and the `SQLiteStoreCursor`, `MSSQLStoreCursor` constructors and the SQLite and SQL Server `InternalOpenCursor` overrides; the PostgreSQL store has neither). `InternalUpdate`, `InternalDelete`, `Insert`'s `LogInsert`, `Update`'s `LogUpdate` and `Delete`'s `LogDelete` pass the row key instead of `_key`. For a caller that does not supply one, a reasonable default is the index's columns when the index is unique and otherwise all columns (with `is null` for a null value in the generated `where`), but no current caller needs it.
- **Unique order.** Order and seek the reader on the index's columns followed by the row-key columns not already in the index (`GetReaderStatement` already builds a lexicographic seek over any column list). The cursor's positioning key (`_key`, `SelectKey`, `RowToKey`, `_keyIndexes`) becomes that extended list. Range values (`_startValues`/`_endValues`) stay prefixes of the index's columns; `CompareKeys(object[])` compares only over the given key's length, so range checks are unchanged. With a unique order, an exclusive re-seek from the current row never skips a duplicate, which is what the non-unique buffer (`_buffer`, used when `!_index.IsUnique`) exists to compensate for; the implementer may keep the buffer as it is or retire it, but must not leave the two disagreeing.
- **Position after a write.** After `PerformUpdate`, keep the edited row as the cursor's current row (no reader open; `InternalGetValue` must then read it, the way it reads `_editingRow` today) and return `true`, so `Next()`/`Prior()` reopen the reader exclusively after/before its positioning key. After `PerformDelete`, remember the deleted row's positioning key as a crack and return `false`; `Next()`/`Prior()` must then seek exclusively from that key, not from `_startValues`/`_endValues`. Any of `First`, `Last`, `SetRange`, `FindKey`, `FindNearest` clears that crack.
- **`DeleteRows`' statement path** (`CatalogStore.cs`, about line 903): key each `PerformDelete` by the table's primary key (`Store.GetIndexHeader(tableHeader.PrimaryKeyName).Columns`), for both arms.
- **Compatibility.** `SQLStoreConnection`, `SQLStoreCursor` and their `OpenCursor` / `InternalOpenCursor` members are public or protected in `Alphora.Dataphor.DAE`; a custom catalog store (a subclass of `SQLStore`/`SQLStoreConnection`) would notice a changed signature. Prefer adding overloads over changing the existing ones; either way add an entry to `docs/migration-notes.md` describing the new row-identity parameter and the cursor's new position after `Update`/`Delete`. No D4 semantics, error codes or file formats change.

## Bug met along the way (fix here)

`SystemSetObjectOwnerNode.InternalExecute` (`src/engine/Server/Runtime.Instructions/SecurityNodes.cs`, about line 518) throws `CatalogObjectExpected` with `objectValue.Name` when `objectValue` is null, so `SetObjectOwner` on a name that does not resolve fails with a `NullReferenceException` instead of the schema error. Observed in a scratch run. Local fix: pass `(string)arguments[0]`. Reproduction: `SetObjectOwner('NoSuchObject', 'Admin')` reports `SchemaException` code `CatalogObjectExpected`, not a null reference; it fits in the same test class as the reproduction below.

An observation not investigated, for whoever writes the test: in a scratch test that ran `SetUseImplicitTransactions(false); CreateUser(…); create table TOT { ID : Integer, key { ID } };` through `TestServerInstance.ExecuteScript` and then `SetObjectOwner('TOT', …)` through a second `ExecuteScript` (new session), the second session did not resolve `TOT` and `DAECatalogObjects` in the catalog file had no row for it. With implicit transactions on (the default) both worked. Write the reproduction with the default; if the implicit-transactions-off behaviour looks wrong, that is its own ticket.
