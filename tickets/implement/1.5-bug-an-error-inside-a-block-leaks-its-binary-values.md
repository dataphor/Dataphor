## What is wrong

The engine keeps values too large to carry around inline - the two D4 types for them are `Binary` and `Graphic`, and rows, lists and tables are structured values with the same problem - in a stream or a buffer the server owns, and releases a variable's value when the variable goes out of scope. `Diagnostics.StreamCount()` reports how many streams the server is holding; with nothing running it is 0.

A variable goes out of scope when its block ends, and the release is a statement the compiler **appends to the end of that block**. So the release only happens when control reaches the end of the block. Any other way out skips it, and the value is held for the life of the session.

"Any other way out" is not only an error. The engine implements D4's `exit`, `break` and `continue` as .NET exceptions (`ExitError`, `BreakError`, `ContinueError` in `src/engine/DAE/Runtime.Instructions/ImperativeNodes.cs`), so each of them skips the releases too. **A `continue` in a loop whose body declares a `Binary`, `Graphic` or row variable leaks that variable once per iteration** - ordinary, non-error D4, and the shape a filtering loop is naturally written in.

## Where it comes from, and the two sites

Two compiler helpers in `src/engine/DAE/Compiling/Compiler.cs` build the releases, and both wrap the statement in a plain `BlockNode` whose later children are `DeallocateVariableNode`s - so the releases are *statements after* the statement, not a `finally` around it:

- `CompileDeallocateFrameVariablesNode` - the variables of a **frame**. A D4 `begin ... end` *statement* compiles to a `FrameNode` (`CompileDelimitedBlock`), and so do a `try ... except` handler and an aggregate operator's aggregation block.
- the inline loop in `CompileOperatorBlock` (near line 6358 today) and `CompileDeallocateVariablesNode` - the variables an operator **body** or an aggregate **finalization** block leaves in the call's stack *window*, above the operand and result slots. An operator's `begin ... end` body is not a `FrameNode`: the parser hands the body's statement list over directly (`Parser.Block()` returns a `Block`, not a `DelimitedBlock`), so an operator's own locals are window leftovers rather than frame variables. That is why the operator-body row of the table above leaks through a different site from the rest.

`Stack.PopFrame` and `Stack.PopWindow` do pop on every path - they are called from `finally` blocks - but they only null the slots and lower the count. Nothing disposes what the slots held.

## The fix

**The rule: a construct that opens a scope releases the values of the slots it finds above its own entry depth, on every path out.** The release moves from a statement at the end of the block to the `finally` that already pops the scope, and from a compile-time list of positions to a run-time comparison of stack depths. Measuring the depth at run time is what makes it right for a block that raised before it had declared all of its variables, and for an operator body whose compile-time symbol frame does not line up with its run-time frame.

One helper carries it. In `Alphora.Dataphor.DAE.Runtime.Stack` (`src/engine/DAE/Runtime/Stack.cs`, beside `PokeOwned`, whose remarks state the ownership rule this follows):

```csharp
/// <summary>Releases the values of the slots above the given depth, leaving each slot null.</summary>
public void ReleaseAbove(int depth, IValueManager manager)
{
    for (int offset = 0; offset < Count - depth; offset++)
    {
        object value = this[offset];
        if (value != null)
        {
            Poke(offset, null);
            DataValue.DisposeValue(manager, value);
        }
    }
}
```

The slot is nulled before the value is disposed, so a dispose that throws cannot leave a disposed value reachable from the stack, and a second pass over the same region releases nothing.

Five call sites, each of which already has the `finally` to put it in:

- **`FrameNode.InternalExecute`** (`ImperativeNodes.cs`) - take `program.Stack.Count` before `PushFrame`, and `ReleaseAbove` that depth in the existing `finally` before `PopFrame`. This is the D4 `begin ... end` statement, and therefore most of the table above.
- **`ErrorHandlerNode.InternalExecute`** (same file) - the same shape. It covers the error variable the handler pushes as well as any variables the handler statement declares.
- **`CallNode.InternalExecute`** (same file) - `ReleaseAbove(stackDepth, …)` in the `finally` that already hands the operand slots back to the instruction's cleanup, after that hand-back. `stackDepth` is already recorded there, just above the operand and result slots, so the operands and the result are below it and are not touched; the result has already been read by the `return` in the `try`.
- **`AggregateCallNode.InternalExecute`** (`AggregateNodes.cs`) - twice. Once around the per-row aggregation block, beside its `PushFrame`/`PopFrame`; once around the whole initialization/aggregation/finalization sequence, releasing above the `stackDepth` recorded just after the result slot is pushed. The second one needs a new `try`/`finally` wrapped around that sequence - **re-indent the body rather than leaving it at its old indentation**.
- the aggregate column slots the loop pokes row values into sit *below* the aggregation frame and below that `stackDepth`, so neither call touches them. They hold values borrowed from the row the cursor selects into, and releasing one would be a use-after-free.

With those in place every compiled release is redundant, so **delete them**: the `DeallocateVariableNode` class, `Compiler.CompileDeallocateFrameVariablesNode`, `Compiler.CompileDeallocateVariablesNode`, the inline loop in `CompileOperatorBlock`, and the eight call sites of those three (six in `Compiler.cs`, two in `DDLNodes.cs`'s `AlterAggregateOperatorNode`). Leaving them as a fast path would leave two mechanisms for one invariant, and one of them is wrong at the edges - see the next section.

### Why one mechanism rather than two, and what the deletion also fixes

The compiled releases are not merely redundant; in two places their compile-time positions do not describe the run-time stack, and the only reason nothing has gone wrong is that the shapes involved are rare or unreachable:

- **The `try ... except` handler's releases never ran at all.** The handler compilation wraps the `ErrorHandlerNode` in the release block, but `ErrorHandlerNode` pushes and pops its own frame, so the releases would have run after the frame holding their slots was gone - and `TryExceptNode.InternalExecute` reaches the `ErrorHandlerNode` through `GetErrorHandlerNode` and executes *that*, skipping the wrapper. Dead code with wrong offsets inside it. Nothing leaked measurably, because the error variable is not stream-backed (last row of the table).
- **An aggregate operator's aggregation block releases past its own variables.** `Compiler.cs` pushes the operand symbols *into* the symbol frame it then compiles the aggregation block in, so `plan.Symbols.FrameCount` counts them; at run time the operand slots are pushed *before* `PushFrame` and are not in the frame. The top-relative offsets therefore run off the end of the block's own variables into the aggregate column slots, which are borrowed from the row. Read from the code, not measured - a `Binary` aggregate operand is the shape that would show it and it is not reachable through `group`, because a `Binary` column cannot be sorted (`Unable to construct a sort for data type "System.Binary"`), so finding a reachable shape is itself work. Both of these simply stop existing when the positions do.

## What the fix deliberately does not cover

- **`foreach` over a list leaks one value per loop**, and that is a different site: `ForEachNode`'s list branch evaluates the list, pokes each element into the loop variable's slot, and never disposes the list. Measured before and after at 1 stream for `begin var LB : Binary; foreach LB in { Binary('0001'), Binary('0002') } do begin end; end;` - unchanged by this work. Worth its own ticket once someone has read that branch properly; do not fold it in here.
- `bug-an-operator-argument-is-released-by-the-wrong-owner` (`tickets/fix/`) and the `F(var LB, LB)` write-back loss recorded as a `NOTE:` in `CallNode` are both still open. **So the `DEBUG`-only stream-count check that the `NOTE:` above `Program.Stop` (`src/engine/DAE/Runtime/Program.cs`) is waiting for still cannot be added.** That note names this ticket as its blocker; once this lands that is misleading, so **update the note to name what actually still blocks it** - the operator-argument ticket and the `foreach`-over-a-list leak above - rather than deleting it or acting on it.

## Tests

Its reproduction, in `tests/DAE.Server.Tests/AssignmentValueOwnershipTest.cs`: that fixture already owns the `Diagnostics.StreamCount()` instrument, already explains the ownership rule these cases are the other half of, and its class remarks explicitly name this bug as the reason none of its scripts leaves a block by a raise. Those remarks need rewriting once they do.

Four cases are enough, each pinning a distinct exit path rather than a distinct variable type (the type only decides whether the value is stream-backed, which `Binary` settles):

- a block that declares a `Binary` and raises, the error escaping to the caller;
- the same raise caught by a D4 `try ... except` outside the block, so that the released-on-the-error-path claim is not only about an error that reaches the client;
- a `foreach` body that declares a `Binary` and `continue`s, asserting the exact count over several iterations, because this is the one that leaks per iteration and the assertion is arithmetic;
- an operator body (not a `begin ... end` statement) that declares a `Binary` and raises, because that is the second of the two sites and the first three cases do not reach it.

Assert the exact count, as the rest of the fixture does, and assert the error was raised where the script catches it - a case that silently stopped raising would otherwise pass. No case needs a loop count of 100: the per-iteration leak shows at three.

No new test file, so nothing to add to the `<Compile Include>` item group in `tests/DAE.Server.Tests/DAE.Server.Tests.csproj`; if that changes, remember the group is explicit and a file left out of it compiles into nothing with no error.

## Cost

Unmeasured, and it needs measuring: the release used to be compiled only for the variables whose type `IsDisposable`, so a block with none did no work at exit, and now every frame exit walks its own slots and calls `DataValue.DisposeValue`, which falls through a handful of type tests for a native value. A block that declares nothing still does nothing (the loop does not run), so the shape to measure is a tight loop over a block that declares one or two non-disposable variables, in Release, in-process - the method `bug-assigning-a-binary-variable-leaks-its-stream` used for the same question: three timed runs per pass, three passes each way, first run of each pass discarded as warm-up, and report the spread, not one number. If it turns out to be material, the fast path to restore is a compile-time `bool` on `FrameNode` set from the frame's symbol disposability in `CompileFrameNode` and `CompileDelimitedBlock`; prefer not to, and say what you measured either way.

## Compatibility and documentation

Nothing an application can see changes except the engine's memory use: no D4 semantics, operator signature, class name, assembly name, file format, error code, WCF contract or port. A caught error still leaves every variable still in scope holding its value.

`docs/migration-notes.md` needs entries under *Custom C# extensions*, because all of these are public and an extension could be using them: `Alphora.Dataphor.DAE.Runtime.Stack.ReleaseAbove` added; `DeallocateVariableNode`, `Compiler.CompileDeallocateFrameVariablesNode` and `Compiler.CompileDeallocateVariablesNode` removed, with one line on what replaces them (an extension that builds its own scope should release above its entry depth in its own `finally`).

Nothing under `docs/architecture/` yet. No page in that set describes the stack, the streams or who releases a value, and the review of `bug-assigning-a-binary-variable-leaks-its-stream` concluded that writing that page should wait until the rule is finished - `bug-an-operator-argument-is-released-by-the-wrong-owner` is still open, so it is not. That ticket names the page as its own deliverable.

## How this was arrived at

The shape above was prototyped in full against `21d467bc` - the helper, the five call sites, and the deletion of all of the compiled releases - and then removed again; the tree this ticket lands in has none of it. Measured on that prototype: the whole suite green in Debug in the three parts the root `AGENTS.md` gives (895 / 72 / 50 passed, 0 failed, 34 / 11 / 12 skipped, the same skips `bug-assigning-a-binary-variable-leaks-its-stream` recorded), and the right-hand column of the table above. The suite covers the parts of this that are easiest to get wrong - the `AggregateOperators` coverage script exercises an aggregate whose initialization block leaves variables for its aggregation and finalization blocks to use, which is exactly the region the second aggregate call site must not release early.

`bug-assigning-a-binary-variable-leaks-its-stream`, which wrote down the ownership rule this follows and which this ticket's `prereq:` named, has landed (`tickets/complete/`).

`tickets/fix/3-bug-an-operator-argument-is-released-by-the-wrong-owner.md` also edits `CallNode`'s neighbourhood and `Compiler.cs`, at different sites (`CleanupOperand`, and the by-value-to-`const` promotion). It is sequenced after this one; expect to touch the same two files, not the same lines.
