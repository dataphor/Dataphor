## The fact this ticket rests on

**As the product ships, none of the secured-connection settings do anything.** They are read, stored, passed down several layers and exposed as public properties, and never reach a binding. Verified by reading every use:

| Setting | Where a user sets it | What the code does with it |
|---|---|---|
| `SecurityMode`, `ListenerSecurityMode` | a client alias, in `Aliases.config` (`src/client/DAE.Client/Alias.cs`), through the alias editor | handed to `ClientServer`'s constructor, stored in a field, exposed as a property. `ClientServer.Open` ignores it and always calls `DataphorServiceUtility.GetBinding()` |
| `RequireSecureConnection` | the instance configuration, `ServerConfigurations.config`; the checkbox in `EditInstanceForm` | nothing reads it; `DataphorServiceHost.Start` never mentions it |
| `RequireSecureListenerConnection` | the same | handed to `ListenerServiceHost`'s constructor as `requireSecureConnection`, whose body never uses it |
| `UseSecureConnection`, `UseSecureListenerConnection` | **D4**, as metadata tags on `create server` (`src/engine/DAE/Schema/ServerLink.cs`) | turned into `ConnectionSecurityMode.Transport` and handed to `NativeCLIClient` (`src/engine/Server/Server/RemoteSessionImplementation.cs`), which stores it in a field and exposes a property. The binding comes from `GetBinding()` regardless |

So a user who asks for a secured connection anywhere in this product gets an unsecured one and no hint. That is the defect. Whether a *secured* connection should be possible at all is a separate, larger question, settled below and handed on.

## The decision

The plan's work item offers two outcomes: "make the secured-connection options work on CoreWCF, or document their removal (Q8)". **Neither is taken; a third is, and this section is the reasoning the implementer should not re-open.**

**Not made to work, because the settings cannot express a working configuration and the design is not this workstream's.** Both stacks have the pieces — `WindowsStreamSecurityBindingElement`, `SslStreamSecurityBindingElement`, `TcpTransportSecurity` and `NetTcpSecurity` are all declared in CoreWCF.NetTcp 1.9.1 and in System.ServiceModel.NetTcp 10.1.0 (checked by reading both assemblies' metadata names), so the libraries are not the obstacle. The obstacle is that there is nothing to configure them *from*: the server has no certificate setting and no credential-type setting, and a client's `Transport` does not say which credential it means. Making the settings work therefore means inventing a security design — which credential type, where a server's certificate comes from, whether a client's identity is checked, what happens off a Windows domain — and the plan is explicit that WS11's security items "need owner sign-off" and that "none of it is 'fix inline'". It also means the binding stops being one process-wide memoized singleton and becomes per-endpoint on both sides. That is a feature, in a workstream whose stated job is to not change the protocol.

**Not removed, because removal costs compatibility churn and buys nothing.** The settings sit on three surfaces — two BOP files, a public C# API that custom extensions use, and two D4 metadata tags — and they are the vocabulary in which a user says "I want this protected". The WS11 work that delivers transport security will want exactly that vocabulary. Removing it now, from three surfaces, to add it back later, is motion without progress.

**What is done instead: the settings stop lying.** Each of the three surfaces gets the strongest honest response available at that surface, matched to who set it and who is harmed by refusing:

| Surface | Response | Why this one |
|---|---|---|
| A client connection asking for `Transport` (an alias, or a direct caller of `ClientServer` or `NativeCLIClient`) | **refused**, with a message naming the setting and the remedy | The person who set it is the person connecting, the cost is one failed connection, and they can fix it by editing the alias. Silently connecting unsecured defeats exactly what they asked for |
| An instance configured to require a secure connection | **starts, and logs a warning** naming both settings and the remedy | Refusing to start would take the instance down for every client on upgrade, for a setting that never worked, and the server has no way to offer the security it would be demanding. Cost, stated plainly: an operator who does not read the log still gets an unsecured server |
| A D4 server link whose tags ask for a secured connection | **connects unsecured, and the server logs a warning** naming the link and the tag | The library is a customer artifact that the person running the query cannot edit; breaking a running application to report a setting that never worked is the wrong trade. The tag keeps its meaning and keeps round-tripping through the catalog and the emitter |

**And the capability stays reachable.** The three client hooks on `DataphorServiceUtility` and the host hooks `protocol-host-binding-hook` restores are the supported route to a secured channel, from a site's own host code. They are the only route there has ever been. Every message and every document this ticket writes names them, so "we provide none" is a statement about the product's settings, not about what is possible.

**Handed to WS11.** Transport security as a designed capability — credential type, certificate configuration, an admin guide — becomes WS11 work: see the tasks below for the plan rows to add, and the arm already parked on `tickets/backlog/feat-ws11-security.md`. The fail-closed stance goes with it: once a server *can* be secured, an instance that requires security and cannot get it should refuse to start, and that is harmless then because the operator has a working configuration to move to.

Q8 is not re-opened. The plan already answered it ("proceed as if neither is used"), and this decision is taken on that answer.

## What to change

### The client refuses what it cannot honour

In `src/protocol/Common/Contracts/DataphorServiceUtility.cs`:

- `public static bool HasCustomBinding` — false while `BuildBindingCall` is the product's own `DefaultBuildBinding`. Hold the default in a `static readonly` field and compare by reference; mind static-initialiser order. This mirrors `DataphorServiceHostHooks.HasCustomBinding` from the prereq ticket, and exists for the same reason.
- `public static void CheckSecurityMode(ConnectionSecurityMode mode, string settingName)` — does nothing unless `mode` is `Transport`; does nothing when `HasCustomBinding`, because then the site's own binding owns security and the product must not second-guess it; otherwise throws `NotSupportedException`. Model the message on the one `ClientServer.Open` already throws for `ClientConfigurationName`: name the setting as a user sees it, say that this version's built-in connection carries no transport security so the request cannot be honoured, and give both remedies — clear the setting, or supply a binding through `DataphorServiceUtility.BuildBindingCall` from the host application's own start-up code. `NotSupportedException` rather than a new error code, following that precedent: `Common` has no reference to the engine assembly where `ServerException` lives, and this is the same category of failure.

In `ClientServer.Open`, in the branch that builds a channel factory: check `SecurityMode` before anything else, and check `ListenerSecurityMode` only on the path that actually uses the listener (`_overridePortNumber == 0`) — refusing for a setting the connection never consults would be gratuitous. Both checks must happen before the listener is contacted, so that no unsecured discovery call is made on the way to refusing.

In `src/protocol/NativeCLI/NativeCLI.cs`, the same, with one wrinkle: the six-argument `NativeCLIClient` constructor contacts the listener from inside its own base-constructor argument (`GetNativeServerURI` → `ListenerFactory.GetInstanceURI`), which runs before any statement in the constructor body. So add a static overload of `GetNativeServerURI` taking both modes, which checks them (listener mode only when `overridePortNumber <= 0`) and then does what it does today, and have the constructor call that.

**A bug met along the way, fixed here with its reproduction.** The four-argument constructor forwards its caller's `securityMode` into the *listener's* slot and leaves the connection's at `Default`:

```csharp
public NativeCLIClient(string hostName, string instanceName, int overridePortNumber, ConnectionSecurityMode securityMode)
    : this(hostName, instanceName, overridePortNumber, ConnectionSecurityMode.Default, 0, securityMode) { }
```

Dormant today, because neither mode is honoured; observable after this change, as the wrong setting named in the refusal. Pass `securityMode` as the connection's mode and `Default` as the listener's, and pin it with a case.

### The server reports

In `DataphorServiceHost.Start(ServerConfiguration)`, once the engine server has started and its log is available, and only when `DataphorServiceHostHooks.HasCustomBinding` is false: if either `RequireSecureConnection` or `RequireSecureListenerConnection` is set, `_server.LogMessage(LogEntryType.Warning, …)` naming the settings that are set, stating that nothing in the server acts on them and that connections to this instance are not secured, and giving the two remedies. Follow the shape of the listener warning already in that method.

`ListenerServiceHost`'s `requireSecureConnection` constructor parameter then has no reason to exist — the caller reports it, and the class has no log of its own — so drop it and the doc comment that explains why it was kept. That is a second change to this constructor's signature in two tickets; `docs/migration-notes.md` already carries an entry for the first, so amend that entry rather than adding a contradicting one.

### The server link warns

In `RemoteSessionImplementation`'s constructor: pass `ConnectionSecurityMode.None` for both modes, and when either `serverLink.UseSecureConnection` or `serverLink.UseSecureListenerConnection` is set and `DataphorServiceUtility.HasCustomBinding` is false, log a warning through the engine reachable from the process (`process.ServerSession.Server.LogMessage(LogEntryType.Warning, …)`) naming the server link and the tag that is set. The connection then proceeds unsecured, as it does today.

`src/engine/DAE/Schema/ServerLink.cs` is **not** changed: the tags keep being read into their properties, so a library that sets one keeps its meaning, the properties stay available to the WS11 work, and the catalog and the D4 emitter keep round-tripping the tag as metadata exactly as now.

## Edge cases & interactions

| Case | How it is handled, and how that is verified |
|---|---|
| `Transport` requested where a site has installed its own binding hook | No refusal and no warning anywhere: the hook owns security. This is the one deployment that could ever have had a secured channel, and it must not be broken by this ticket. Covered by a case on the client; by inspection on the server (the `HasCustomBinding` guard). |
| `Default` versus `None` | Neither is refused and neither warns. `Default` means "whatever the server's default is", which is unsecured; `None` says so outright. Only `Transport` is a request the product cannot honour. Covered by a case. |
| A listener security mode set on a connection that never uses the listener (`OverridePortNumber` set) | Not refused — the setting is not consulted on that path. Covered by a case, because the opposite choice is the easy mistake to make here. |
| The refusal arriving before any network traffic | Both the alias path and the native-CLI path must refuse before the listener is contacted; on the native-CLI path that means checking inside the `GetNativeServerURI` overload, since the base-constructor argument runs first. Covered by a case that refuses with no server running at all. |
| An instance configuration file carrying the two settings | Unchanged on both sides: the properties stay, so the file loads and saves exactly as it does today, and `InstanceConfigurationTest.LoadReadsAFileCarryingSettingsThatNoLongerExist` keeps asserting both values. Nothing in this ticket touches a BOP surface. |
| A library whose `create server` carries the tag | The server still starts and the library still registers: the tags are read when the catalog object is created, and nothing connects then. Only an actual remote session (the first `EvaluateOn` or equivalent) warns. By inspection of `CreateServerNode` and `RemoteSessionImplementation`. |
| A tag whose value is not a boolean (`UseSecureConnection = "yes"`) | Unchanged: `Convert.ToBoolean` still throws from `ApplyMetaData`, as it does today. Not this ticket's to fix. |
| `ServerLink.ResetServerLink` resetting only four of its seven fields | **Checked and it is not a defect — do not file it.** `alter server` calls `ResetServerLink` and then `ApplyMetaData`, and `ApplyMetaData` assigns all seven fields from the tags with a default for each, so no field can go stale; `AlterNode.AlterMetaData` never nulls a `MetaData`, so the one path where `ApplyMetaData` does nothing is a link that never had tags. `ResetServerLink` is redundant, not wrong. Recorded here so the reviewer does not re-derive it. |
| Warning volume on the server-link path | One warning per remote session, and a remote session is per server link per user session — bounded by sessions, not by statements. Left undeduplicated for simplicity; if a deployment ever finds it noisy, dedupe on the `ServerLink`. Worth a `NOTE:` at the site. |
| A custom C# extension calling the client constructors | Nothing is removed and no signature changes, so such an extension still compiles. It fails at run time only if it asks for `Transport`, which never worked. Migration note. |
| The dormant Windows UI (`EditInstanceForm`, `EditAliasForm` in `src/windows/`, not in `Dataphor.slnx`) | Compiles unchanged, because nothing is removed. Do not edit those files; WS6 owns them. |

## Tests

New cases, in one new fixture `tests/DAE.Server.Tests/ConnectionSecurityModeTest.cs`. Each drives real client code and needs no server, because the refusal happens before a connection is opened — so the fixture is cheap. It touches the process-wide binding hook, so it is not `[Parallelizable]` and its teardown calls `DataphorServiceUtility.RevertHooksToDefault`, with the comment the project's other static-state fixtures carry.

- A `ClientServer` whose `SecurityMode` is `Transport` is refused, and the message names that setting. With an explicit `OverridePortNumber`, so no listener is contacted.
- A `ClientServer` whose `ListenerSecurityMode` is `Transport` is refused when the listener would be used, and is **not** refused when `OverridePortNumber` is set.
- `Default` and `None` are not refused.
- With a `BuildBindingCall` installed (returning the default binding is enough), `Transport` is not refused.
- A `NativeSessionCLIClient` built through the four-argument constructor with `Transport` is refused, and the message names the *connection's* setting rather than the listener's — the reproduction of the argument-order bug above.

**Not tested, with the reason, so the reviewer need not re-litigate it:** the two server-side warnings. Asserting a log line needs a server with logging on, and the root `AGENTS.md` records that the default suite run deliberately runs its servers with logging off, because a logging server in an elevated process creates and writes the `Dataphor Server` Windows event-log source. The server-link warning additionally needs a second hosted instance, which `test-client-server` owns. Both warnings are verified by inspection, and the handoff should say so in those words.
