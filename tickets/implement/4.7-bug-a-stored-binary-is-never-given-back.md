## The reported defect does not exist

The fix stage reproduced every number in the original report and then measured the same statements from outside a single statement. The result: **a committed insert, update or delete of a stream-backed value leaves the server holding exactly as many managed streams as before it** - which is the behaviour the original ticket asked for as its expected behaviour. There is nothing to fix in the engine.

Terms, for a reader without the earlier context. The engine keeps a value of either of its two large types - `Binary` and `Graphic`, what an application uses for pictures, documents and attachments - in a *managed stream*: a block of memory the server owns, with a count of how many holders it has. `Diagnostics.StreamCount()` reports how many such streams the server holds, and in a server with nothing running it is 0. "Balanced" below means that count is the same before and after.

## What was measured

Measured 2026-11-24 against `modernization` at `149c726d`, through the in-process engine harness (`tests/DAE.Server.Tests/InProcessTestFixture.cs`), reading `StreamCount()` between statements in a session with nothing else running. The table in every case is an ordinary one on the in-memory device - `create table T { ID : Integer, B : Binary, key { ID } };` - and the same numbers came out for a `Graphic` column and for a table created `in System.Temp`.

Each statement run on its own, which is what an application does:

| what was run | change in the count |
|---|---:|
| `insert table { row { 1 ID, Binary('ABEiM0RVZnc=') B } } into T;` | 0 |
| `update T set { B := Binary('qrvM3Q==') } where ID = 1;` | 0 |
| `delete T where ID = 1;` | 0 |
| fifty such inserts, then fifty such updates, each its own statement | 0 |
| then `delete T;`, every row | 0 |
| a whole `begin ... end` block of ten such inserts, run to completion | 0 |
| a `Graphic` column, and a table created `in System.Temp`, through all of the above | 0 |

Measured *inside* one statement - a `begin ... end` block, with the reads taken between the writes - the count does rise, and comes back to 0 when the block ends:

| inside one block | count held |
|---|---:|
| after one insert | 1 |
| after an update of that same row | 2 |
| after deleting that row | 2 |
| after ten inserts | 10 |
| after `delete T;`, all ten rows | 10 |
| after `drop table T;` in that same block | 0 |
| once the block has finished, measured from outside | 0 |

And inside a transaction opened through the client interface (`IServerProcess.BeginTransaction`), which is how a client holds a transaction open across statements:

| | count held |
|---|---:|
| after ten inserts, transaction still open | 10 |
| after `delete T;`, every row, transaction still open | 10 |
| after `CommitTransaction` | 0 |
| one insert, then `RollbackTransaction` | 0 |

So the rule is: **one managed stream per logged write of a stream-backed value, held for the life of the transaction that made the write, and given back when that transaction commits or rolls back.** An ordinary statement is its own transaction, so an ordinary statement is balanced. Only a transaction a caller deliberately holds open accumulates, and it gives everything back when it ends.

## Where the stream goes, and why the original reading looked table-bound

The holder is the device session's undo log, and the stack trace says so exactly. `Schema.DeviceSession.InsertRow` (`src/engine/DAE/Schema/Device.cs`, at the end of the method) records what would undo the insert:

```
Transactions.CurrentTransaction().Operations.Add(new DeleteOperation(table, (IRow)row.Copy()));
```

`row.Copy()` on a row with a stream-backed column calls `StreamManager.Reference` for that column (`DataValue.CopyNative`), which is the extra stream. `UpdateRow` does the same with its new row, which is why an update adds one too; a delete adds none, because the row it copies came out of the table, where the value is stored as plain bytes rather than in a stream. The memory device needs this log: it keeps no undo information of its own (its whole transaction-logging body is inside `#if USEMEMORYDEVICETRANSACTIONS`, which no project defines), so the engine's log is the only thing that can roll one of its statements back. `DeviceTransaction.Dispose` releases the whole log when the transaction ends, which is the release.

Three things in the original report are explained by this and were not defects:

- **"Only dropping the table gives them back."** `DeviceSession.Execute` calls `RemoveTransactionReferences(dropTableNode.Table)` for a `DropTableNode`, which disposes exactly that table's undo entries. Inside one long statement that is the first thing that releases them, so a drop looked like the releaser and the holder looked like part of the table. Measured here: a drop inside the block returned all of them at once, and the block ending returned them anyway.
- **"A rolled-back insert costs nothing."** Rollback disposes the log. That is the same release as commit, reached sooner.
- **"A value that arrives already native costs nothing."** A value read out of another table is stored as bytes, so `row.Copy()` clones bytes and takes out no stream.

The original measurements were all taken inside the `begin ... end` row section of the `StreamValues.d4` coverage script, which is one statement, so they were reading the undo log of a transaction that was still open. The one number that does not reproduce is "insert, update, then delete left three held": it is two, as the table above shows.

One trap worth knowing for anyone measuring this again. D4's `BeginTransaction()` is an operator, and used as a *standalone statement* it has no effect that outlives that statement: the engine wraps each statement in an implicit transaction and commits back down to the depth it started at, so `BeginTransaction();` on its own line is committed by its own statement. Use it inside a `begin ... end` block, as `StreamValues.d4` does, or hold the transaction through `IServerProcess.BeginTransaction` from the host. A sequence of three separate statements - begin, insert, rollback - does not roll the insert back, and that is the implicit-transaction design, not a defect in the memory device.

## What to change

Two tracked files state the withdrawn claim as fact, and must stop:

- `tests/libraries/TestFramework.Coverage.Scripts/Documents/StreamValues.d4`, in two places: the bullet in the header comment that ends "leave one stream held until the table is dropped - that is bug-a-stored-binary-is-never-given-back", and the "What is not asserted, and why" paragraph above the row section, which says a committed insert "raises the count by one per row and keeps it until the table is dropped". Replace both with the rule measured above, stated as the rule rather than as a defect.
- `src/engine/DAE/Runtime/Program.cs`, the `NOTE:` above `Program.Stop` that lists three leaks blocking a debug-only stream-balance check and says to add the check "once all three have landed". This slug is not one of them. Check the other two against the board when you do this: `bug-an-argument-is-orphaned-when-a-later-one-raises` has landed (`tickets/complete/`), and `bug-a-loop-variable-stays-borrowed-after-the-loop` and `bug-ifnil-leaks-the-value-it-copies` are open in `tickets/fix/`, so the list should name those two. Do not add the check itself here - that is the remaining tickets' call, and this ticket has no standing to decide it.

And the rule needs to be asserted, at the lowest layer that shows it, which is the coverage script. The script's row section currently cannot assert the committed-insert balance because the whole section is one `begin ... end` block, where the undo log legitimately still holds the value; the assertion belongs at the script's *top level*, where each statement is its own transaction. Top-level `var` declarations in a D4 script persist across the statements after them - the script already relies on this for `LScriptStart` - so a top-level section can record a count, run a write as its own statement, and assert the balance in a following statement.

The arms worth asserting, and nothing more than these:

- A committed insert of a stream-backed value, as its own top-level statement, is balanced. Then an update of that column, as its own statement, balanced. Then a delete of the row, balanced. Then the table dropped, still balanced. This is the one that was missing, and the one a future regression in the undo log's release would break.
- Inside a block, a transaction opened with `BeginTransaction()`, an insert, and `RollbackTransaction()` leaves the count where it was. The script already asserts this; keep it and say in the comment beside it that it is the same release as a commit, reached sooner, so a reader does not read rollback as special.

Do not assert the within-statement counts (the second table above). They are the undo log's bookkeeping, correct but incidental, and pinning them would make an ordinary change to how the log copies a row fail a coverage script for no benefit. Say what they are in the comment instead.

Also leave a short `NOTE:` at `DeviceSession.InsertRow` in `src/engine/DAE/Schema/Device.cs`, at the line that takes the reference, recording what the copy costs for a stream-backed column and that it is released when the transaction ends. That is the site a future reader arrives at with this question, and the measurement above is the answer; it also stops the next investigation retracing this one.

## What not to do

- Do not weaken or remove the balance assertions in `AssignmentValueOwnershipTest` or in the `StreamValues` coverage script, and do not make `StreamCount()` stop counting anything. They are the instrument that made this answerable.
- Do not change an expected value in a D4 coverage script to make it pass; nothing here requires that, and the project rules forbid it.
- Do not touch the memory device, `NativeTable` or `NativeRowTree`. The original ticket named them; none of them is involved. `debt-memory-device-transaction-isolation` in `tickets/backlog/` is the open ticket over those files, about transaction isolation, and is unaffected by this.
