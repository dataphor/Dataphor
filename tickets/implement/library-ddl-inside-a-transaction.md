## What this is

A Dataphor *library* is the unit an application is shipped in: a folder in the server's library directory holding a descriptor file (`<name>.d4l`), the library's D4 documents and its upgrade scripts. The operators that create, delete or reconfigure a library write that folder and the descriptor file as they run and record nothing for a rollback to replay, so a transaction that calls one and then rolls back leaves the change standing. `DropLibrary` is the one case where that loses something: it deletes the library's folder recursively (`src/engine/Server/Schema/LibraryUtility.cs:279`), and a rollback cannot put a folder back.

The owner's decision (2026-11-23, recorded on the plan ticket) was: write the rule down, make `DropLibrary` refuse inside a transaction the session opened itself, and leave `CreateLibrary`, `SetLibraryDescriptor` and `SetDefaultDeviceName` alone — on condition that the planner first verify no caller that ships runs `DropLibrary` inside such a transaction. That survey is below and the condition is met, so all three items go ahead.

## Caller survey (2026-11-25): no shipped caller drops a library inside an explicit transaction

Two code sites reach the destructive work, both through `LibraryUtility.DropLibrary`: the `DropLibrary` operator (`src/engine/Server/Runtime.Instructions/LibraryNodes.cs:122`) and the catalog device's delete handler for the `System.Libraries` table (`src/engine/Server/Device.Catalog/ServerCatalogDeviceSession.cs:734`), which is what a `delete Libraries` statement or a cursor delete on that table runs. Everything below reaches one of those two.

- **The IDE's library tree (`src/windows/Dataphoria`).** Its Delete action (Del key, `LibraryNode.DeleteDocument` at `src/windows/Dataphoria/ObjectTree/Nodes/LibraryNode.cs:694`) opens a derived form over `.System.Libraries` in Delete mode; accepting it calls `MainSource.DataView.Delete()` (`src/windows/Frontend.Client.Windows/Form.cs:941`), which reaches `DataSet.Delete()` (`src/client/DAE.Client/DataSet.cs:1579`) and then the server cursor's `Delete()`. Nothing on that path opens a transaction: `DAEDataSet` begins one only in `InternalPost`, `InternalChangeColumn` and `InternalInitializeRow`, never around a delete, and `ServerCursor.Delete()` (`src/engine/DAE/Server/ServerCursor.cs:820`) opens a transactional call of its own, so the only transaction standing is the implicit one the engine begins for that call. The form also opens no application transaction: `DataView` begins one only when its open state is Insert or Edit (`src/client/DAE.Client/View.cs:645`) and a Delete-mode form opens in Browse. The library tree's other actions do not drop: Detach runs `DetachLibrary`, and the two context-menu script items only *emit* text (`ScriptLibrary`, `ScriptDropLibrary`).
- **The IDE's script execution, and `D4Runner`.** Both go through `ScriptExecutionUtility` (`src/client/DAE.Client/ScriptExecutionUtility.cs`), which contains no transaction handling at all, and neither Dataphoria nor any host under `src/hosts` mentions `BeginTransaction` or `UseImplicitTransactions`. Statements a user types run in the engine's per-statement implicit transaction.
- **Shipped libraries, forms and D4 documents (`libraries/`, `samples/`).** The only `DropLibrary` word in either tree is `libraries/Security/Upgrades/Upgrade.2.0.1.d4:6`, and that calls `ScriptDropLibrary`, which returns the text of a drop script for the library's catalog objects — it drops no library. No shipped D4 file deletes from `System.Libraries` either; `libraries/Frontend/Documents/Register.d4` only *references* that table. `libraries/Frontend/Upgrades/Upgrade.2.0.8.d4` is the one shipped D4 file that calls `BeginTransaction`, and it drops nothing.
- **The client and the CLI paths.** `DataSession` (`src/client/DAE.Client/Session.cs:101`) contains no transaction code; a client that wants a transaction has to ask for one. `NativeCLI` and the WCF client expose `BeginTransaction` but call no library operator themselves.
- **The coverage scripts.** Every library script except one drops inside the harness's single implicit transaction — the harness runs each script as a nested `ExecuteScript` inside one statement of its own, so `TransactionCount()` is 1 from the script's first line to its last (measured, `debt-library-administration-coverage`). The exception is `LibraryUpgrades.d4`, whose manifest preamble turns implicit transactions off and whose transaction the harness then commits (`tests/DAE.Server.Tests/CoverageScripts.cs:418`), so it drops with no transaction open at all. Neither shape is an explicit transaction. No library script carries `batches: true`, and none calls `BeginTransaction`.
- **The C# tests.** `tests/DAE.Server.Tests/CatalogRollbackSnapshotTest.cs` names `DropLibrary` only in prose; it deliberately leaves the library dimension out. No other fixture drops a library inside a transaction.
- **The upgrade machinery — the one place a transaction would be in the way.** Each upgrade script runs inside a transaction the machinery opens with a D4 `BeginTransaction()`, on a session whose implicit transactions are off (`src/engine/Server/Runtime.Instructions/LibraryNodes.cs:1042` and `:1084`). That transaction is explicit by the mark below, so a `DropLibrary` **inside an upgrade script** will be refused once the guard lands. No shipped upgrade script drops a library, and neither does any upgrade script in the coverage suite, so nothing in this repository is affected — but a customer's upgrade script could be, and that is exactly the case the guard is for: such a script runs in a transaction that can roll back, and a drop inside it has already erased the folder. This is the one entry in the survey that needs saying out loud in `docs/migration-notes.md`.

## The mark that distinguishes the two kinds of transaction

A statement runs inside a transaction the engine began for it unless the session turned that off: `ServerProcess.BeginTransactionalCall` begins one when none is open and stamps `ImplicitCallDepth` on it (`src/engine/DAE/Server/ServerProcess.cs:2246`). A transaction begun by a `BeginTransaction()` statement or by a client's `BeginTransaction` call leaves `ImplicitCallDepth` at 0. So the mark to test is **`ImplicitCallDepth == 0` on any open transaction**, and not the nesting count: under the coverage harness a script's statements run two calls deep inside one implicit transaction, so a guard on the count — including the existing `InTransactionBeyondCurrentCall`, which compares the stamp against the current call depth — would refuse every coverage script that drops a library.

One shape falls on the explicit side without anyone typing `BeginTransaction`: when a statement switches implicit transactions off, the implicit transaction it opened outlives its call and `ServerProcess` resets its `ImplicitCallDepth` to 0, with the engine's own comment calling it "an ordinary open transaction" from then on (`src/engine/DAE/Server/ServerProcess.cs:2319`). Treat it as explicit, which is what that reset already means: it is a transaction that will outlive the statement and can be rolled back, so a drop inside it is the case the guard exists to stop. The coverage harness already works around the same shape by committing that transaction after a preamble.

## What to build

**One: the rule, in the architecture documentation.** `docs/architecture/libraries-and-class-loading.md` (742 words of a 1,500-word limit, so there is room) gets a short section saying that a library's descriptor and folder are files rather than catalog rows; that `CreateLibrary`, `DropLibrary`, `RenameLibrary`, `SetLibraryDescriptor`, `SetDefaultDeviceName` and the requisite and file operators beside them take effect when they run and are not undone by a rollback; that registering and unregistering a library are catalog changes and *are* undone normally; that a rolled-back `DropLibrary` has already deleted the library's folder, which is why it now refuses inside an explicit transaction while the others do not; and that `RenameLibrary` moves the folder rather than deleting it, so the inverse rename repairs it. Keep it to one paragraph and a sentence or two, in the page's voice, and say why the other operators are left alone (a rolled-back `CreateLibrary` leaves an unwanted library, which a drop removes; nothing is lost).

**Two: the guard.** A new public read-only property on `ServerProcess`, beside `InTransaction`:

```csharp
/// <summary>Whether a transaction open on this process was begun explicitly - by BeginTransaction rather than by the engine for a statement - counting an implicit transaction the engine has left open because implicit transactions were switched off during its call.</summary>
public bool InExplicitTransaction { get; }   // any open transaction with ImplicitCallDepth == 0
```

It has to be public: `LibraryUtility` is in `AlphoraDataphorServer` and `ServerProcess` in `Alphora.Dataphor.DAE`, and there is no `InternalsVisibleTo` between them. Giving the predicate one named home rather than scanning `Transactions` at the call site also keeps the two kinds of transaction named in one place.

Then, as the first statement of `LibraryUtility.DropLibrary` — before the `lock`, so both call sites are covered by one check and the refusal does not depend on catalog state:

```csharp
if (program.ServerProcess.InExplicitTransaction)
    throw new Schema.SchemaException(Schema.SchemaException.Codes.CannotDropLibraryInExplicitTransaction, libraryName);
```

**Three: the error code.** `CannotDropLibraryInExplicitTransaction = 113251` in `src/engine/DAE/Schema/SchemaException.cs` (113250 is the highest in use; follow the file's shape, a `/// <summary>Error code …</summary>` line carrying the message) and the matching `<data name="113251">` at the end of `src/engine/DAE/Schema/SchemaException.resx`. Message, in the voice of its neighbours: `Library "{0}" cannot be dropped inside an explicit transaction, because dropping a library deletes its directory and a rollback cannot restore it.` `docs/reference/error-codes.md` lists prefix ranges only and needs no edit.

**Four: the migration note.** One entry in the "D4, catalog and libraries" section of `docs/migration-notes.md`, marked `done`: `DropLibrary` — and a `delete` against the `System.Libraries` catalog table, which runs the same code — now raises 113251 instead of running when the session has a transaction of its own open; the per-statement transaction the engine opens is not one, so an ordinary script or an IDE delete is unaffected. Name the two caller shapes that *are*: a library upgrade script, which runs inside a transaction the upgrade machinery opened, and a session that has called `SetUseImplicitTransactions(false)`, which keeps the transaction that statement left open. What to do: drop the library outside the transaction, or commit first. Mention the new `ServerProcess.InExplicitTransaction` in the same entry for extensions that call `LibraryUtility.DropLibrary` directly.

## Edge cases & interactions

- **A statement's own implicit transaction** (`TransactionCount()` 1, stamp equal to the call depth) — must still drop. Verified by every existing `DropLibrary` in the coverage scripts; they all run in exactly this shape and are in the test set above.
- **No transaction at all** (implicit transactions off and none opened, which is `LibraryUpgrades.d4` after its preamble) — must still drop. Verified by that script staying green.
- **A script two calls deep inside one implicit transaction** — the coverage harness's shape, and the reason the predicate reads the stamp rather than the nesting count. Verified by the same scripts; a predicate built on `InTransactionBeyondCurrentCall` or on `Transactions.Count` would fail them all, which makes this a real tripwire rather than a hypothetical.
- **An explicit transaction nested inside the harness's implicit one** — refused, and the refusal must leave the library and its folder in place (the check runs before anything is removed, as `DetachLibrary`'s refusal does). The new D4 arm.
- **An implicit transaction the engine has left open after implicit transactions were switched off** — refused. The new C# test.
- **Both call sites.** The guard sits in `LibraryUtility.DropLibrary`, so the `DropLibrary` operator and a `delete` against `System.Libraries` behave the same. By inspection: those are the only two callers (`grep -rn "LibraryUtility.DropLibrary" src/`), and the single check covers both.
- **Error ordering.** The guard runs before the library is resolved, so inside an explicit transaction a drop of a library the catalog has never heard of now reports 113251 rather than 113104 ("object not found"). That is the intended trade — the refusal is a property of the statement and not of the catalog — and it is reachable only inside an explicit transaction, where the old behaviour was to run. Say so in the migration note; verified by inspection of the ordering, not by a test of its own.
- **The upgrade machinery.** Its transaction is explicit, so an upgrade script that drops a library will now fail. Nothing in this repository does, and the migration note is the whole mitigation. Do not weaken the guard to exempt it: an upgrade script's transaction is precisely one that can roll back after the folder is gone.
- **`RenameLibrary` and the rest stay as they are.** `RenameLibrary` moves the folder (`Directory.Move`, `src/engine/Server/Runtime.Instructions/LibraryNodes.cs:165`) and `CreateLibrary` creates one; both are repaired by running the inverse statement, so neither gets a guard. Covered by the documentation paragraph, not by code.
- **Compatibility surfaces.** No operator signature, class name, file format or WCF contract changes; one new error code and one new public property, both additive. The refusal itself is the compatibility change and the migration note carries it.
