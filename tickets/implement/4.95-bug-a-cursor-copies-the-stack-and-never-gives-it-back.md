## What is wrong

`Cursor`'s constructor (`src/engine/DAE/Runtime.Data/CursorValue.cs`) calls `SnapshotContext`, which walks the whole current stack window and pushes `DataValue.CopyValue(...)` of every slot onto a private stack it keeps in `_context`:

```csharp
_context = new Stack(program.Stack.MaxStackDepth, program.Stack.MaxCallDepth);
_context.PushWindow(0);
for (int index = program.Stack.Count - 1; index >= 0; index--)
    _context.Push(DataValue.CopyValue(program.ValueManager, program.Stack.Peek(index)));
```

A copy of a stream-backed value - a `Binary` or a `Graphic`, and a row or list holding one - is a new stream the server has to be told to release. `Cursor.Dispose` never releases them; it does `_context = null` and nothing else. So **one stream per stream-backed value in scope, per cursor opened, held until the session ends.**

Every cursor pays this, not just a `foreach`: the snapshot is swapped in and out around each cursor operation (`SwitchContext`, which `CursorNodes.cs` calls in pairs around `Next`, `Prior`, `Select`, `Fetch` and the rest), so an explicit D4 cursor costs the same as the implicit one a `foreach` over a table opens.

## Measured

On `modernization` at `3593336a`, in-process server, reading `Diagnostics.StreamCount()` either side of each script through a throwaway fixture on `InProcessTestFixture` (added, run, removed; not in the tree). "after" is with both arms of the fix below prototyped end to end.

| script | before | after |
|---|---:|---:|
| `begin var LB : Binary := Binary('00FF'); end;` (control, no cursor) | 0 | 0 |
| a `foreach` over `cursor(table { row { 1 ID } })` with no stream-backed variable in scope (control) | 0 | 0 |
| one `Binary` variable declared **before** the loop | 1 | 0 |
| three `Binary` variables declared before the loop | 3 | 0 |
| one `Binary` variable declared **after** the loop | 0 | 0 |
| one `Binary` variable, then **two** cursor loops | 2 | 0 |
| one variable holding a `row { B : Binary }`, declared before the loop | 1 | 0 |
| one `Binary` variable and an explicit `cursor(...)` closed with `Close(LC)` | 1 | 0 |

The pattern is exactly the snapshot: a variable declared after the cursor opened is not on the stack to be copied and costs nothing, and two cursors cost two copies.

## What the research settled

**The snapshot has to stay a copy; the fix is to release it.** `SwitchContext` installs the snapshot as the program's stack for the duration of each cursor operation, so that the cursor's plan reads the variables it was compiled against at the offsets it was compiled with. A cursor outlives the scope that opened it - `var LC : cursor(table { ID : Integer }) := cursor(...)` holds only an integer id, and nothing closes the cursor when the block ends - and that scope releases its own variables on the way out, so a snapshot of live values would leave the cursor reading released streams. The copy is the isolation. Releasing it in `Dispose` is the missing half.

**`_context` holds the snapshot at dispose time.** `SwitchContext` *swaps*, so an unbalanced switch would leave the program's own live stack parked in `_context` and a blind release there would release the program's variables. Every one of the 62 `SwitchContext` call sites is a `switch; try { ... } finally { switch; }` pair - `CursorNodes.cs` (one per cursor operator), `ImperativeNodes.cs` (`ForEachNode.CursorNext`, `CursorSelect`) and `ListNodes.cs` (three node classes) - so the swap is balanced on every path including a raise, and `CloseCursor` is only ever reached outside such a region. Checked by reading all of them, not assumed.

**Nothing releases a snapshot value twice.** A plan node that reads a slot hands the value over only when it was asked to lend (`PlanNode.SetByReference`, `docs/architecture/operand-ownership.md`), and a lent value stays the slot's to release - so a snapshot slot read by the cursor's plan is still released once, here. The one site that writes *into* a slot during a switch is the `var` operand write-back in `InstructionNodeBase.CleanupOperand`, which is an ownership return: either the slot still holds what it held, or the body's assignment released the displaced value through `Stack.PokeOwned` and the slot now owns the replacement. Either way the snapshot owns one value per slot at dispose time.

**The value manager has to be captured when the snapshot is taken, and that alone is not enough.** `Dispose` disposes `_table` before it drops `_context`, so `_table.Program` is not reachable for the release; capture `program.ValueManager` in `SnapshotContext` instead. But the captured manager is the *process's* (`ServerProcess.ValueManager`), and a `Row` or `ListValue` sitting in the snapshot carries that same manager inside itself, so there is no longer-lived manager to substitute. That matters because **the session's cursor manager is disposed after the session's processes are** (`ServerSession.Dispose` disposes `_processes` in an inner `finally` and `_cursorManager` in the one outside it), and `ServerProcess.InternalDispose` ends by nulling `_serverSession`, `_valueManager` and `_streamManager`. So a cursor the script never closed is disposed with its process already gone, and `ServerProcess.IStreamManager.Deallocate` dereferences a null `_serverSession`.

That is not theoretical: the release on its own turns an unclosed cursor at session end into a `NullReferenceException` out of `Engine.Disconnect`. Measured - a script that does `var LB : Binary := Binary('00FF'); var LC : cursor(table { ID : Integer }) := cursor(table { row { 1 ID } });` and never calls `Close`, followed by stopping the process and disconnecting the session, passes today, fails with the release alone, and passes again with the second arm below. Reordering `ServerSession.Dispose` does not fix it either, because a process is usually stopped before its session is disconnected and is already gone by then.

So this ticket has two arms at one site: **release the snapshot in `Cursor.Dispose`, and make a cursor not outlive the process whose values it is holding.**

## The shape to build

**Arm one - release the snapshot.** In `SnapshotContext`, keep `program.ValueManager` in a field beside `_context`. In `Dispose`, release through it before nulling `_context`:

```csharp
if (_context != null)
{
    _context.ReleaseAbove(0, _valueManager);
    _context = null;
}
```

`Stack.ReleaseAbove(0, manager)` is the right instrument rather than a loop: it nulls each slot before disposing its value, so a dispose that throws cannot leave a disposed value reachable and a second pass releases nothing. The snapshot's `PushWindow(0)` was pushed at count 0, so `Base` is 0 and the window-relative `Count` is the number of values pushed - every one of them is released. Nothing reads the stack with `AllowExtraWindowAccess` on at dispose time, which is the condition `ReleaseAbove`'s own `NOTE:` states. The existing `try`/`finally` structure of `Dispose` can stay as it is: the captured manager does not depend on `_table`, so it does not matter that the table is disposed first - say so in the comment, because the reason the order is free is the whole point of capturing the manager.

**Arm two - a cursor does not outlive its process.** Add a method to `CursorManager` that disposes the cursors belonging to one process, and call it from `ServerProcess.InternalDispose` while the process is still usable - in the same `finally` that disposes each plan's `ActiveCursor`, which runs after the transaction rollback and before `CloseDeviceSessions`, so the cursor's table is closed against device sessions that are still open:

```csharp
// CursorManager
public void CloseProcessCursors(ServerProcess process)
{
    for (int index = _cursors.Count - 1; index >= 0; index--)
    {
        Cursor cursor = _cursors[index];
        if ((cursor.Table != null) && (cursor.Table.Program != null) && (cursor.Table.Program.ServerProcess == process))
            cursor.Dispose();
    }
}
```

```csharp
// ServerProcess.InternalDispose, in the finally that disposes plan.ActiveCursor
if (_serverSession != null)
    _serverSession.CloseProcessCursors(this);
```

Backwards through the list, because `Cursors` is a `DisposableList` that disowns a disposed member. Go through a small `internal` method on `ServerSession` rather than the `CursorManager` property, which creates a manager when there is none - a process dispose must not create one. `CursorValue.cs` has no `using` for `Alphora.Dataphor.DAE.Server` today; the prototype spelled `ServerProcess` out in full rather than adding one, either is fine.

This is the arm that deserves the comment: a `Cursor` holds an `ITable` bound to a program on a process and a snapshot of that process's values, so it is unusable the moment the process is gone; closing it with the process is what makes releasing the snapshot safe, and it also removes the quieter hazard that `_table.Dispose()` has always run against a dead process on that path.

**Optional third arm, small and worth it.** `SnapshotContext` is `public` and nothing outside the constructor calls it; a second call would orphan the first snapshot outright. Narrowing it to `private` makes that unrepresentable. It is a public member of a public type whose constructor is `protected internal`, so an external subclass is possible in principle and this needs a `docs/migration-notes.md` line under *Custom C# extensions*; `protected` is the middle option. If that trade reads badly, leave it public with a `NOTE:` saying it must be called once, from the constructor.

## Expected behaviour

Opening and closing a cursor leaves the stream count where it found it, whatever the variables in scope are holding: every row in the table above comes back to 0. A session disconnected with a cursor still open still disconnects cleanly.
