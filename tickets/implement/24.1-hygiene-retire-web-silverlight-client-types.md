## What this is

The `Frontend` library keeps a catalog table, `Frontend.ClientTypes`, listing the kinds of client an application can be opened with, and a document per client type naming the user-interface node classes that client provides. Release 4.0 ships one client, the Windows Client. The library still describes three.

Two things to remove, together, because they are two halves of the same statement:

- **The rows.** `libraries/Frontend/Documents/Register.d4` creates `ClientTypes` and then, guarded by `if not exists (ClientTypes)`, inserts three rows: `Windows`, `Web` and `Silverlight` (the table and the insert are at about lines 276–295). Remove the `Web` and `Silverlight` rows and keep `Windows`, the guard and the table definition exactly as they are.
- **The documents.** `libraries/Frontend/Documents/Silverlight.NodeTypes.dnt` and `libraries/Frontend/Documents/Web.NodeTypes.dnt` map node names to types in two assemblies that no longer exist (`Alphora.Dataphor.Frontend.Client.Silverlight` and `...Client.Web`). Delete both files. `Windows.NodeTypes.dnt` stays.

`repo-delete-dead-trees` deleted the two clients but deliberately left this behind, because it changes a library catalog table and a library document set rather than deleting a dead project. `library-frontend-web-leftovers` left `Web.NodeTypes.dnt` for the same reason and names this ticket as its owner.

## What an application can notice

One thing, and it needs a `docs/migration-notes.md` entry under *D4, catalog and libraries*.

`Frontend.ClientTypes` is read by name in the library operators `GetNodeTypes`, `GetApplicationNodeTypes`, `GetLibraryNodeTypes` and `GetLibraryFiles`, each of which takes a client type identifier. Two consequences, and they differ:

- **A catalog built from scripts after this change has two fewer rows in `ClientTypes`.** An application that reads the table to offer a choice of client sees one entry. An application that passes the literal `Web` or `Silverlight` to one of those operators now gets an error from the restriction `ClientTypes[AClientType]`, where before it got a row back; that is the observable difference, and it belongs in the entry.
- **The node-type documents are looked up defensively.** `GetNodeTypes` and `GetLibraryNodeTypes` build a document name from the client type identifier and wrap each load in `if DocumentExists(...)`, so a request for a client type whose document is gone returns an empty `<nodetypes>` element rather than failing. Deleting the two documents on its own therefore breaks nothing; it is the missing rows that change an answer.

**No upgrade script, and no library version bump.** The insert is guarded by `if not exists (ClientTypes)`, so it only ever runs when a catalog is first built; an existing 3.x catalog is unaffected either way. The settled direction (plan decision, and the whole of WS4) is that catalogs are **rebuilt from scripts rather than migrated**, so there is no upgrade path for this change to serve. Raising the version in `libraries/Frontend/Frontend.d4l` to carry an `Upgrades/Upgrade.*.d4` that deletes two rows would change a shipped library version — a compatibility surface — to serve a migration the release does not support. Say this in the migration-notes entry so that an operator keeping a 3.x catalog is told the rows stay there.

## What not to touch

- **`Setup/Files.wxs`.** It lists both `.dnt` files under a deployment folder, and the whole `Setup/` folder is deleted by the WS9 installer work. Leave it alone; removing two lines from a file that is about to go is churn, and the new installer harvests from the runtime layout rather than from a hand-written file list.
- **`libraries/Frontend/Upgrades/Upgrade.2.0.9.d4` and `Upgrade.2.0.12.d4`.** Both mention a `ClientApplications_ClientTypes` reference. Upgrade scripts are the historical record of what past releases did and are never edited.
- **`libraries/Frontend/Frontend.d4l`.** It lists only the library assembly, not its documents, so nothing there names the deleted files and nothing needs to change.

## Edge cases & interactions

- **The derived-form goldens must not move.** `tests/goldens/frontend/Frontend/ClientTypes.*.xml` holds the eight derived pages for this table. Derivation reads the *schema*, not the rows, and this change does not touch the table definition or its tags, so every golden must come out byte-identical. If one moves, something other than the rows changed — stop and find out what. Run the golden fixture; do not update a golden.
- **The runtime layout mirrors deletions.** `tools/layout/Layout.csproj` copies each library folder and then deletes from the layout anything the build did not put there, so the two documents disappear from `artifacts/layout/*/Libraries/Frontend/Documents/` on the next build without a clean. Nothing in that project file names the documents individually, and the `.d4l` file-list check only covers files a `.d4l` lists, so neither gate is affected. Confirm by building and looking in the layout folder.
- **The library registers in several fixtures.** `FrontendFixture` (which backs the derivation goldens and `FormCustomizationTest`) and `SamplesCorpusTest` both register `Frontend` on fresh servers, so a `Register.d4` that no longer parses or no longer runs fails many cases at once. That is the safety net for the edit.
- **`Register.d4` is in the parser corpus.** `ParserRoundTripCorpusTest` parses every `.d4` in the repository, so a malformed table literal fails there too, without a server.
- **Formatting.** `Register.d4` is UTF-8 without a byte-order mark, tabs, CRLF. The three rows sit on three lines inside one table literal; deleting two means the remaining row must not keep a trailing comma.
- **A grep for the two names afterwards** still finds the error-code reservations, the migration notes, the user-guide history and `Setup/`. Those are deliberate; see the list in `hygiene-silverlight-conditionals`.

```
dotnet build Dataphor.slnx
dotnet test tests/DAE.Server.Tests --no-build --filter "FullyQualifiedName~FrontendDerivationGoldenTest"
dotnet test tests/DAE.Server.Tests --no-build --filter "FullyQualifiedName~FormCustomizationTest|FullyQualifiedName~FormDocumentCorpusTest|FullyQualifiedName~SamplesCorpusTest|FullyQualifiedName~ParserRoundTripCorpusTest"
dotnet test tests/DAE.Server.Tests --no-build --filter "Name=LibraryCoverage|Name=LibraryFilesCoverage|Name=LibraryUpgrades"
```

`FrontendDerivationGoldenTest` is the large one (416 cases); run it on its own so its result is unambiguous. Do not set `DATAPHOR_UPDATE_FRONTEND_GOLDENS`. Name the filters in the handoff.
