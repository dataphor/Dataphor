## What this is

Layer L3's first half, as the plan's WS3 table describes it: "golden translation tests for the SQL Server device; the harness takes the device as a parameter so PostgreSQL reuses it". The subject is the step between a compiled D4 plan and the text sent to a database server - `libraries/SQLDevice/Source/SQLDevice.cs` (10k lines) building a SQL syntax tree, and the dialect emitter in `libraries/MSSQLDevice/Source/Language.TSQL/Emitter.cs` turning it into T-SQL. Nothing in the suite runs a line of it: `debt-sql-translation-coverage` measured `src/engine/DAE/Language.SQL/` at 0.0 % of 1,031 coverable lines and the `Alphora.Dataphor.DAE.Device.SQL` assembly at 0.2 % of 6,143.

That backlog ticket covers the **base emitter** as a unit test over hand-built syntax trees, and says explicitly that a dialect subclass is not its business and belongs "with whatever ticket makes those devices testable". This is that ticket, one level up: real D4, through the real compiler, against a real `MSSQLDevice`, with the generated SQL compared character for character against files under `tests/goldens/devices/`. The two are complements, not alternatives.

### The two seams, both measured

Measured 2026-11-25 on `modernization` at `e54e3dca`, with a throwaway NUnit fixture and a throwaway recording connection class (both since removed):

**1. `D4ToSQL` gives query translation with no connection at all.** `libraries/SQLDevice/Documents/Register.d4` registers `D4ToSQL(const ADeviceName : System.Name, const AQuery : System.String) : System.String` (class `SQLDevice.D4ToSQLNode`, and `grant usage ... to role User`). It parses and compiles the D4, checks the plan is device-supported, and returns `sQLDevice.Emitter.Emit(...)` without executing anything. For a device table `Employee { ID : Integer, Name : String, Salary : Money, key { ID } }` it returned, for example:

```
select 
	"T1"."ID" as "ID", "T1"."Name" as "Name"
	from "Employee" as "T1" 
	where ("T1"."Name" = 'a''b')
order by "ID" asc
option (fast 1);
```

That is golden text as it stands - quoting, clause order, the literal escape, the `order by` the key supplies and the `option (fast 1)` hint all visible. A query the device cannot translate raises instead (`SQLException.Codes.QueryUnsupported`, or `QuerySupportedByDifferentDevice` when the plan lands elsewhere), which is worth a case or two of its own: the supported/unsupported boundary is as much a part of the device's behaviour as the text it produces.

**2. The device still has to start and its tables still have to exist, and both of those connect.** Three things in `MSSQLDevice` connect on start - `DetermineVersion`, `EnsureDatabase`, `EnsureOperators` - each gated by a device attribute (`ShouldDetermineVersion`, `ShouldEnsureDatabase`, `ShouldEnsureOperators`, all defaulting to true). With all three set to `"False"` the device started against `ServerName = "no.such.server"` with no connection attempted. `create table ... in <device>` then still failed: `CatalogDeviceSession.CreateDeviceTable` prepares a `CreateTableNode` and executes it on the device, and `SQLDeviceSession.InternalExecute`'s `DDLNode` branch calls `RequestConnection` **before** it tests the reconcile mode, so even `reconciliation { mode = { none } }` opens a connection and then does nothing with it.

So the harness needs a `SQLConnection` implementation that records instead of connecting. With one in place (`ConnectionClass` pointing at it), everything worked: the device started, `create table` succeeded, and the recorder captured the DDL the device generates -

```
EXECUTE create table "Employee"
(
	"ID" integer not null, 
	"Name" varchar(20) not null, 
	"Salary" money not null
);
EXECUTE create unique clustered index "UIDX_Employee_ID" on "Employee"("ID");
```

- which is a second golden set worth having for its own sake: DDL translation is what a device does to a customer's database the first time a table is created in it, and it is as untested as the query path.

### The shape to build

**A new test-only library, `tests/libraries/TestFramework.SQLRecorder`.** Its assembly (`DAE.SQLRecorder.csproj`, assembly name `Alphora.Dataphor.DAE.SQLRecorder`) holds:

- `RecordingConnection` - a `SQLConnection` subclass whose constructor records the connection string and reports itself idle, whose transaction methods do nothing, whose `IsConnectionValid()` is true, and whose command records `Statement` on execute. `SQLConnection`, `SQLCommand` and `SQLCursor` are all in `src/engine/DAE/Connection/`, so the project needs Base and DAE and nothing else to compile them; it needs `Server.csproj` only if you choose to derive from `DotNetConnection`, which you should not. **Note one C# detail measured: `SQLCommand.InternalClose()` is `protected internal`, so an override from another assembly must be declared `protected`, not `protected internal`** (CS0507 otherwise).
- A plan node or two so that a D4 expression can read back what was recorded and clear it - the fixture runs inside the server, and a static list in the library assembly is not reachable from the test assembly, because the server loads the library's own copy from the runtime layout. An operator returning the recorded statements as a single `String` (newline separated) and one that clears the list is enough; `tests/libraries/LibraryLoadingProbe` is the model for a library whose whole purpose is to be reached from a test.
- `Register.cs` registering the connection class under an explicit alias (the `Connection` library's `DAERegister` is the model: `classes.Add(new SettingsItem("SQLRecorder.RecordingConnection", typeof(RecordingConnection).AssemblyQualifiedName))`). The by-type-kind registration that `TestFramework.Coverage.Base` uses does not pick up `SQLConnection` subclasses, so the entry must be explicit.
- `TestFramework.SQLRecorder.d4l` requiring `Connection`, and a `Documents/Register.d4` declaring the two operators.

Put the project in `Dataphor.slnx` and in the Library list of `tools/layout/Layout.csproj`.

**A device-agnostic fixture, with one subclass per device.** `tests/DAE.Server.Tests/StoreContractTests.cs` and its two subclasses are the precedent in this repository: the cases live in an abstract base, and a subclass supplies the thing under test. Here the base, `DeviceTranslationGoldenTests`, holds the corpus and the golden machinery; the subclass supplies the device library name, the `create device` statement and the golden folder name. `MSSQLDeviceTranslationGoldenTests` is the only subclass today; `device-pgsql-device-golden` adds the second.

The device must be created in a library that requires the device's library: creating it in `General` failed with *Object "General.GoldenDevice_SQLDevice.MSSQLBinary_Map..." cannot reference object "SQLDevice.MSSQLBinary" ... because the referenced library is not required*, because the device's own system catalog maps a type the shared library declares. `SetLibrary('MSSQLDevice')` in the same script as the `create device` worked; a throwaway library created at run time with the right requisites would also work. Note that `SetLibrary` does not survive into the next session, so the `create device`, the `create table`s and anything else that depends on the current library have to be in one script.

**Golden files** under `tests/goldens/devices/<Device>/<Case>.sql`, matching the convention `tests/goldens/frontend/<Library>/<Surface>.<PageType>.xml` set, with `DATAPHOR_UPDATE_DEVICE_GOLDENS=1` rewriting them and then **failing the run anyway**, exactly as `DATAPHOR_UPDATE_FRONTEND_GOLDENS=1` does, so an update can never be mistaken for a pass. Document the variable in `AGENTS.md` beside the other four.

### What the corpus should cover

Worst-first by what a wrong answer would do to a real database. One case per behaviour, each a named D4 expression or statement with one golden file:

- **Identifier and literal quoting**, including a string literal containing a quote and an identifier needing delimiters.
- **The statement forms the device generates**: the `select` behind a device table read and behind a restriction, projection, rename, extension, join of each kind, aggregation, `group by`, `union`/`difference`, and the `create table` / `create index` / `drop table` DDL the recorder captures.
- **Expression emission and parenthesisation**, where SQL's precedence differs from the plan tree's shape - the other place a mistake silently changes meaning rather than failing.
- **Order and the `option (fast 1)` hint**, which is where the device's key and order handling shows.
- **Type mapping in generated text**: a column of each D4 type the device maps (`varchar(n)`, `money`, `datetime`, `uniqueidentifier`, `image`, `binary(n)`, `decimal(p,s)`), read off the generated `create table`.
- **The unsupported boundary**: two or three expressions the device refuses, asserted on the error rather than on text.

Say at the top of the file, and in the goldens' own README if you write one, why the expected values may never be edited to make a change pass: there is no reference runtime, so the text a working system produces *is* the specification (decision D2, and the project rules).

### DML and cursors: one arm, with a fallback

An `insert` into a device table got as far as the engine's key check and then needed a *cursor*: the recorder was asked to open

```
select case when not(exists((select * from "Employee" as "T1" (updlock) where ("T1"."ID" = @P1)))) then 1 else 0 end as "dummy1" from (select 0 as "dummy1") as "dummy1"
```

which the throwaway recorder refused. So covering `insert`/`update`/`delete` translation means the recorder's cursor can answer that shape - one row, one column, a canned value - and the statement text and its parameters then get recorded like any other. Try it: the parameter list is as much a part of the translation as the text, and `store-parameterized-statements` made parameters the normal path. If a canned cursor turns out to need more knowledge of the engine's expectations than is reasonable here, **stop, leave DML to `test-device-live`, and record a `NOTE:` at the recorder saying what was asked of it and what it could not answer.** Queries and DDL are the required scope; DML is the arm that may be cut.

## Edge cases & interactions

- **A recorder that silently swallows a statement is worse than no test.** Every command path that the recorder cannot honestly serve must throw, not return an empty result: a cursor it has no canned answer for, a parameter direction it does not handle. A golden file produced by a device that quietly did nothing would be a test that pins a lie. Verified by a case: point one of the corpus's cases at a shape the recorder refuses and assert it refuses.
- **`varchar(20)` is the default string width.** The probe's `Name : String` column became `varchar(20)` because no `Storage.Length` tag was set. Include at least one column with an explicit `Storage.Length` tag so the golden shows both, and do not read the default as a bug - it is the device's documented mapping.
- **The device connects for DDL even when its reconcile mode says not to.** `SQLDeviceSession.InternalExecute`'s `DDLNode` branch calls `RequestConnection` before testing `Device.ReconcileMode`. That is why `mode = { none }` did not avoid a connection. Record a `NOTE:` at that site saying so - it is knowledge, not work: a device defined offline with `mode = { none }` could create its D4 tables with no server if the request moved inside the guard, and nothing today wants that. Do not move it in this ticket.
- **The three `Should*` attributes are the device's own settings, not test-only switches.** A deployment can set them, and the version the device determines changes what it emits for some operators (`IsMSSQL70`). A golden set produced with `ShouldDetermineVersion = "False"` therefore pins the translation for the device's *default* version assumption. Say that at the top of the fixture, and name it as the reason the goldens are not a substitute for `test-device-live`.
- **One server for the whole fixture.** Each case is a D4 compile, not a server start. Use one `TestServerInstance` carrying `Connection`, `SQLDevice`, the device's library and `TestFramework.SQLRecorder`, created once for the fixture, with the device and its tables created once. Report the measured cost; the budget is seconds, not minutes, and the fixture lands in test-suite part 1 (class name beginning with `D`), whose timing `AGENTS.md` records.
- **The golden sets must agree exactly in both directions,** as the frontend goldens do: a case with no golden file, and a golden file no case produces, each fail the run. That is what keeps a renamed case from quietly losing its coverage.
- **Adding a library changes the layout.** The new library folder appears in `artifacts/layout/<config>/Libraries/`, and the layout's `.d4l` check requires every file the descriptor lists to be there. Keep the descriptor to the one assembly.
- **`Microsoft.Data.SqlClient` is coming.** `device-mssql-port` swaps the SQL Server client underneath this, and these goldens are the net that catches a translation change it did not intend. Nothing here may depend on which client is in use: the recorder replaces the client entirely, and the fixture must not reference either client package. Verified by the project file having no client package reference.
- **Determinism.** The frontend goldens needed no normalizer because derivation is deterministic across processes. Check the same here before trusting it: generated aliases (`T1`, `UIDX_...`) and any name built from an object ID would make a golden churn. Run the fixture twice in separate processes and compare, and say in the handoff what you found. If something does churn, normalize it in the fixture with a comment saying what and why, rather than loosening the comparison.
