## What this is

The third of four tickets building the test plan's layer 4, and the one case in it that needs **two** child processes: a server, and a client that is killed while it holds a session in a transaction.

`port-abandoned-session-cleanup` settled the behaviour and keeps the detailed assertions in process: `tests/DAE.Server.Tests/AbandonedSessionCleanupTest.cs` drives a `RemoteServer` plus a `ConnectionManager` at a one-second threshold with no host and no port, and asserts that a connection that is never pinged is relinquished, that the transaction it left open is rolled back, that the catalog store's write lock is released so another session's `create table` succeeds, and that a call on the reclaimed process fails. **None of that is repeated here.** What is left for this layer is the one thing a second process is needed for: a client that *was* alive and pinging and is then **killed outright**, rather than a connection that merely never pinged.

Why that is a different case, and worth one test:

- The liveness signal is the client's keep-alive ping, sent from a background thread in `LocalServer` every `DefaultKeepAliveInterval` (120 s) unless its constructor is given another. A connection that never pinged and a connection whose pings stop are the same thing to `ConnectionManager`, but only the second is what happens in the field, and only the second shows that the pings really do stop when the process dies.
- An abruptly killed process leaves its socket to be closed by the operating system. Whether CoreWCF and Kestrel notice that and tear the connection down — which would relinquish it by the client's own close path rather than by the idle watcher — is **not known** and is one of the facts this ticket is to establish. The case must therefore assert the **end state**, not the mechanism, and the handoff must say which mechanism actually ran. If the channel's death alone reclaims the connection, that is a better answer than the watcher and should be recorded as such; it does not make the case redundant, because nothing shows it today.

## The product change: reaching the reclamation clock from a child process

`ConnectionManager`'s idle threshold is 300 seconds (`ConnectionManager.IdleTimeInSeconds`), and the wake period is a quarter of it, so a reclamation takes between 300 and 375 seconds. No test can wait that long. Since `port-abandoned-session-cleanup`, `ConnectionManager` takes the threshold as a constructor argument and refuses anything below one second — but the host constructs the manager itself, three objects down: `DataphorServiceHost.Start` builds a `DataphorService`, whose constructor calls `new ConnectionManager(_remoteServer)`.

**Settled: a property on the host object, threaded through to the constructor that already exists.** This is the established shape for exactly this situation — `host-instance-directory` recorded that `DataphorServiceHost.HostName` and `LoggingEnabled` are host-object properties rather than instance settings, and that this is why `DataphorHost.BuildHost` keeps its factory parameter. The connection idle threshold joins them.

- `DataphorServiceHost.ConnectionIdleTimeInSeconds`, an `int` defaulting to `ConnectionManager.IdleTimeInSeconds`, settable only while inactive (`CheckInactive()`, like `HostName` and `LoggingEnabled`), passed to the service in `Start(ServerConfiguration)`.
- `DataphorService` gains `DataphorService(RemoteServer, int)`; the existing one-argument constructor delegates with `ConnectionManager.IdleTimeInSeconds`, so nothing that constructs it today changes. `ConnectionManager` itself is untouched: its two-argument constructor and its refusal below one second are what this reaches.
- No new environment variable and no new command-line switch. The test harness is a program of the suite's own and sets the property directly, so nothing has to be smuggled in from outside; `HostCommandLine` stays as it is, and `ServerConfiguration` — an on-disk compatibility surface — gains nothing.

Weighed and rejected: a settable static default on `ConnectionManager` (a mutable global for something that is per server, and it would reach the in-process fixture too); a `ServerConfiguration` setting (an addition to the instance-list format and to the administrator documentation, making a diagnostic knob into an operator-facing setting, and the `[DefaultValue]` tripwire in `src/engine/Server/Server/ServerConfiguration.cs` would then oblige a user-guide change in the same commit); an environment variable (needed only if the child were the shipped executable, which `test-client-server-fixture` recorded as not being started by the suite).

This does not foreclose anything `bug-native-cli-sessions-never-reclaimed` has to decide. That ticket asks "where the clock lives" for the native call interface, and whether either clock should become an operator setting. A host-object property answers neither question; it makes the existing connection clock reachable by the process that owns the host. An arm has been appended to that ticket saying so.

**`docs/migration-notes.md` gains one entry**: the new property on `DataphorServiceHost` and the new constructor overload on `DataphorService`, both additive, with the sentence that a custom host which wants the old behaviour has to do nothing.

## The harness's client mode

`tests/TestHarness` (built by `test-client-server-fixture`) gains a second mode:

```
DAE.Test.Harness client --host <name-or-address> --port <n> --instance <name>
                        [--keep-alive-seconds <n>] --hold-transaction <table-name>
```

It builds the shipped client stack exactly as the fixture's `ProtocolClient` does — a `ClientServer` wrapped in a `LocalServer`, with the keep-alive interval from `--keep-alive-seconds` — connects as `Admin`, starts a process, begins a transaction, creates the named table inside it, writes one line to standard output (`HOLDING <table-name>`), and then **blocks forever** without committing, with the keep-alive thread still pinging. It never prints anything after that and never exits of its own accord: the parent kills it. Failures go to standard error with a non-zero exit code, as in `serve` mode.

`--hold-transaction` taking the table name rather than inventing one keeps the case's names in the case.

## The case

`tests/DAE.Server.Tests/AbandonedClientProcessTest.cs`, one fixture, one case, its own child server because its threshold differs from the shared fixture's.

`AKilledClientProcessIsReclaimedAndTheServerKeepsServing`:

1. Start a child server with `--idle-seconds 3` (the threshold; the wake period is then one second, so reclamation falls between 3 and 3.75 seconds).
2. Open an **observing** connection from the test process with a keep-alive interval of one second — not the 120-second default, which at a 3-second threshold would have the observer itself reclaimed mid-case. This is the sharpest edge in the ticket.
3. Start the client child, wait for its `HOLDING` line, and from the observer assert the child's session is there (`select Sessions` lists it; take the count or the session identifiers before and after rather than matching on a user name, since the observer is also `Admin`).
4. `Kill(entireProcessTree: true)` the client child and wait for its exit.
5. Poll the observer until the child's session is gone, bounded well above the window (thirty seconds, so a slow machine does not make it flaky) and failing with what the observer last saw.
6. Assert the server is still serving: the observer still answers, and a fresh connection can be opened and can execute a statement.

What the case must **not** assert, because `AbandonedSessionCleanupTest` already does and a second copy would be two tests for one behaviour: that the transaction was rolled back, that the catalog store's write lock was released, or what a call on the reclaimed process sees. One sentence in the fixture's remarks pointing at that file.

Cost: one server child plus one client child, and a wait of a few seconds. Expect well under 20 seconds; it joins suite part 1 with the rest of the layer. Measure and report it.

## Edge cases & interactions

How each is covered: **(test)** a case asserts it, **(seam)** an assertion or guard in code, **(inspection)** read and reasoned about, no test.

- **The observer being reclaimed instead of the subject.** *(seam)* Its keep-alive interval must be below the server's threshold, with margin. State the relationship at the site: the server's threshold has to exceed the client's interval by enough to survive a late or lost ping, which is the same rule `LocalServer`'s own strategy comment states.
- **Killed before the transaction is open.** *(seam)* The parent waits for `HOLDING`, which the child writes only after the `create table` inside the transaction has run. Never a sleep.
- **The child client failing to connect at all** (wrong port, server not ready). *(seam)* The parent fails with the child's standard error and exit code, and must distinguish that from "connected but never printed `HOLDING`".
- **Which mechanism reclaimed the connection.** *(test asserts the end state; inspection records the mechanism.)* Determine it while implementing — the cheapest way is to run the same case with a long threshold and see whether the session still disappears, which isolates the channel-close path from the watcher — and say in the handoff which one ran and whether the other works too. If the channel close reclaims it immediately, consider whether the threshold can be raised in the case (a slower, more realistic clock) and say so.
- **Reclamation happening twice** (the channel close and the watcher both acting). *(inspection)* `port-abandoned-session-cleanup` made `RemoteServerConnection.Dispose` idempotent under a lock and pinned it with `RelinquishingAConnectionTwiceDoesNothing`, precisely for the two-reclaimer case. Read that work before concluding anything about a double reclamation seen here; if one is seen and it is *not* clean, that is a real defect and its own ticket, not something to absorb.
- **`ConnectionManager`'s refusal below one second.** *(inspection)* The property must not let a caller get past it with a lower value by a different route; it is passed straight through, so the refusal still applies and the host fails to start with it. No separate test — `port-abandoned-session-cleanup` owns that constructor's validation.
- **An orphaned client child.** *(seam)* Unlike the server child, the client has no standard-input stop path to fall back on, because its whole purpose is to be killed. Teardown must kill it on every path, including when the case fails before step 4; and it holds no temporary folder of its own, so there is nothing else to clean.
- **The killed child's temporary state.** *(inspection)* The client writes nothing to disk. The server child's folder is deleted by `OutOfProcessInstance` as usual, after the server exits — note that it exits with the abandoned transaction's table in its catalog, which is fine for a temporary instance.
- **Thirty-second poll against the runner's idle timer.** *(inspection)* Harmless: the suite prints per-case progress and the poll is inside one case.
- **Does a shortened threshold change anything else in the child?** *(inspection)* `ConnectionManager`'s wake period is derived from the threshold, and nothing else reads it. Confirm by reading the file rather than assuming.
- **The default stays 300 seconds everywhere else.** *(seam)* The one-argument `DataphorService` constructor and the unset host property both resolve to `ConnectionManager.IdleTimeInSeconds`; `HostProgramTest` and `CoreWcfProtocolTest` exercise hosts that never set it, so a mistake here shows up as those fixtures' connections being reclaimed.

## Tests

The one case above, plus nothing. No test for the new property's default (the compiler and the existing fixtures cover it); no test for `DataphorService`'s delegating constructor (wiring); no second copy of the in-process reclamation assertions.
