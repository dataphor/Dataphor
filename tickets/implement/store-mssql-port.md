## The decision this ticket carries out

The plan's WS4 row asked whether the SQL Server catalog store ports cheaply enough to keep, or should be parked. **It ports, and it is cheap.** The planning pass did the whole port in the working tree, ran the store contract against a local SQL Server, and then put the tree back as it was; this ticket does that work for real. Every number below was measured on 2026-11-22 against SQL Server 2016 LocalDB (`MSSQLLocalDB`, version 13.1.4001.0) on the development machine.

What was measured:

- **The project file is the whole port.** Converting `DAE.MSSQL.csproj` to the SDK format and trimming `Properties\AssemblyInfo.cs` the way `Store.SQLite` already is builds the assembly with **zero errors and zero warnings attributed to the project**. Not one line of `MSSQLStore.cs`, `MSSQLStoreConnection.cs` or `MSSQLStoreCursor.cs` has to change to compile.
- **No SQL-client package change here.** The store needs `System.Data.SqlClient` only for the `using` at the top of `MSSQLStore.cs`, and it gets it transitively from `Server.csproj`, which already references that package for the SQL Server connection classes in `src/engine/Server/Connection/`. Moving the repository's SQL Server code to `Microsoft.Data.SqlClient` is `device-mssql-port`'s job (WS7), and this store follows along when that lands, because it shares that client. **Do not swap the package in this ticket.** That also means the encrypt-by-default trap the plan records against `device-mssql-port` does not bite yet: `System.Data.SqlClient` does not encrypt by default.
- **The store needs one connection-string option it does not currently set.** See the next section.
- **The contract passes.** With that option set, all 14 tests of `StoreContractTests` pass against the SQL Server store, the restart round trip `SeedSchemaReopens` included. Fixture total 4.9 s over three runs; slowest single test 227 ms.

## The one code change: the store must ask for multiple active result sets

`MSSQLStore.InternalInitialize` reads `MultipleActiveResultSets` out of the connection string the user supplied and reports it as `SupportsMARS`, whose only reader is `CatalogStore.UseCursorCache`. So a connection string without that option turns the catalog's cursor cache off and otherwise carries on.

That is not enough, and 3.1 was wrong about it. The catalog opens a second store cursor while a first one is still open, cursor cache or not - `src/engine/DAE/Device.Catalog/CatalogStore.cs` does it in several places (reading `PK_DAECatalogObjects` and opening `PK_DAEBaseCatalogObjects` inside the loop, and the same shape around `PK_DAECatalogObjectNames` and `PK_DAEOperatorNameNames`). SQL Server refuses a second reader on one connection unless the connection asked for multiple active result sets, and the error it gives names nothing a user could act on: *"There is already an open DataReader associated with this Command which must be closed first."* Measured: with the option absent, 13 of the 14 contract tests pass and `TwoCursorsOpenOnOneTableInOneTransaction` fails with exactly that message.

So the store sets the option itself, the way `SQLiteStore.NormalizeConnectionString` forces write-ahead logging: in `InternalInitialize`, put `MultipleActiveResultSets=True` into the connection string, assign the result back to `ConnectionString` (the base's setter allows this because `InternalInitialize` runs before the store is marked initialized), and set `_supportsMARS` true. Forced, not defaulted - a configuration that set it to `False` was broken, and `SQLiteStore` has the precedent of ignoring a setting the store cannot work under. Every store connection, the catalog device's own included, is built from `ConnectionString`, so all of them get it.

Measured: with this change and a connection string that says nothing about the option, all 14 contract tests pass, `TwoCursorsOpenOnOneTableInOneTransaction` included.

## The contract fixture

`tests/DAE.Server.Tests/StoreContractTests.cs` holds the abstract fixture and, at the bottom, the SQLite subclass. Add a SQL Server subclass beside it. The shape below is what was run; it needs only `CreateStore` and `DisposeStore`, as the base's own comments say.

- **Gate on an environment variable with `Assert.Ignore`, not a compile switch**, so the skip reason names the variable a developer has to set. Call it `DATAPHOR_TEST_MSSQL`. The variable names a *server*: `Data Source=(localdb)\MSSQLLocalDB;Integrated Security=SSPI` is what the planning pass used, and it needs no `MultipleActiveResultSets` now that the store sets it.
- **One database for the whole fixture, with a fixed name.** A `[OneTimeSetUp]` drops a leftover database from an earlier crashed run and a `[OneTimeTearDown]` drops this run's. A fixed name means a crash leaves one database behind, not one per run.
- **Let the store create the database.** Leave `ShouldEnsureDatabase` at its default, so `InternalInitialize` runs its own `create database` probe against `master` - which is what a server does, and the only place the store builds a connection string of its own (it rewrites `Initial Catalog` or `Database` to `master` for the probe and nothing else). `[OneTimeSetUp]` then only has to drop, and the fixture exercises more of the store. Measured: all 14 pass this way too, same 4.9 s.
- **Drop the database with `alter database ... set single_user with rollback immediate` first.** A pooled connection from an earlier run blocks `DROP DATABASE` otherwise.
- **Swap the database into the supplied string with `DbConnectionStringBuilder`**, removing `Database` and setting `Initial Catalog`, since either spelling may be in what the developer supplied.
- **Empty the database in `DisposeStore`, not in `CreateStore`.** The base calls `CreateStore` a second time on the same directory for `SeedSchemaReopens`, which asserts the reopened store still has the tables the first one wrote - so dropping tables in `CreateStore` fails that test. Dropping them after each test (`select name from sys.tables`, then `drop table` each; the contract's tables and the catalog seed have no foreign keys, so order does not matter) leaves the database empty for the next one. Keep the `Directory.Delete(directory, true)` the SQLite subclass does, so the base's per-test directory does not pile up.
- **One database per *test* was measured and rejected.** `create database` took 98, 161 and 202 ms over three rounds; the `single_user` plus `drop database` pair took 21 ms once and 3.0 s twice. Fourteen tests would add anywhere from 1.5 s to 45 s to a 4.9 s fixture, with the three-second case being the common one.
- **Nothing SQL Server-specific is needed for the restart round trip.** The plan asked for one; it is already the base's `SeedSchemaReopens` and runs on any subclass.

Add the project reference to `tests/DAE.Server.Tests/DAE.Server.Tests.csproj` next to the `Store.SQLite` one. While there: the comment above those two lines says the store projects are "Not compiled against", which stopped being true when `test-store-contract` added the SQLite subclass. Fix the comment.

## Edge cases & interactions

- **A developer with no SQL Server.** The fixture must report *Skipped* with the variable named, and the rest of the suite must be unaffected. Check by running `dotnet test --filter FullyQualifiedName~MSSQLStoreContractTests` with the variable unset.
- **A leftover database from a crashed run.** Covered by the drop-before-create in `[OneTimeSetUp]`; verify by creating the database by hand and running the fixture.
- **A connection string that already sets `MultipleActiveResultSets`.** Forcing it writes over whatever was there. Verify by inspection of the four lines, plus one fixture run with the option already set to `True` in the variable (both were done in planning and both passed).
- **A connection string that names no database at all.** `InternalInitialize` skips its `create database` probe when the string has neither `Initial Catalog` nor `Database`; the MARS change must not disturb that. By inspection - the probe is already guarded and the new lines sit above it.
- **Non-ASCII text through the store's writes is lost. Pre-existing, not this ticket's to fix.** `MSSQLCommand.PrepareParameters` and `GetParamTypeDescriptor` both map a string parameter to `varchar`, while every text column in the store's `SystemStoreCatalog.sql` is `nvarchar`. Measured: a string written through a store cursor comes back with `café` and `Über` intact and the two Chinese characters of the probe string replaced by question marks. The mapping predates parameterized writes (a quote-doubled `varchar` literal loses the same characters) and is shared with the catalog *read* path and with the SQL Server device, so it is recorded as an arm on `feat-ws7-devices-and-libraries`, where `device-mssql-port` owns that file. **Do not write a test for it here** - the reproduction belongs with the fix. The contract's `AwkwardStringRoundTripsThroughWrites` passes, because every character in it is ASCII.
- **One parameter type per distinct string length.** `PrepareParameters` declares each string parameter's size as that value's own length, so SQL Server sees a different parameter signature per distinct length and caches a plan per length. Conditional, and not this store's to decide; the same arm records it.
- **SQL Server version.** This was proved on SQL Server 2016 LocalDB, below the 2022 minimum the plan sets (Q12). That is a weaker proof, not a wrong one, and `device-sqlserver-version-matrix` owns the version question. Say so in the handoff; do not go looking for a newer server inside this ticket.
- **CI.** The fixture self-skips, so nothing has to change in the workflow. Supplying LocalDB in CI belongs to `test-device-live`.

## Keeping it in the build

Put `src/engine/Store.MSSQL/DAE.MSSQL.csproj` in `Dataphor.slnx` under `/engine/`, next to `Store.SQLite`, and in the `Bin` list of `tools/layout/Layout.csproj`. Not behind a solution filter: the project builds clean in about a second, the test project has to reference it anyway, and a filter would mean nobody's build ever compiles it. The layout entry is what lets a deployment actually name this store in `catalogstoreclassname`, and nothing in it can collide - the store brings no package of its own.

The plan's "Done when" for WS4 does not ask for this store, and SQLite stays the default. Nothing else in the repository changes its store.
