## What this is

The second of three tickets closing the debugger's test gap. `debt-debugger-breakpoint-script` lands `DebugBreakpoints.d4`, which stops a process at a breakpoint and reads the paused program. This ticket adds a second script, `DebugStepping.d4`, for everything else a human does with a stopped program: move it one statement at a time, stop a program that is only running, stop a program on an error, and let it go again without leaving it stuck.

**Read `DebugBreakpoints.d4` first and reuse its shape.** The locator convention, the bounded polling idiom and the traps (poll the process and not the debugger; the paused-only columns are nil when a process is not paused) are all written down in that ticket's body and should by now be in the script and in the *Debugger* section of `docs/architecture/sessions-processes-plans.md`. The two scripts are deliberately separate files rather than one long one: each is self-contained, each gets its own case name in the run, and a failure in one does not hide the other.

## What the script must do

Same shape as `DebugBreakpoints.d4`: the script's own session, a second process from `StartProcess()` attached with `Debug.AttachProcess`, and a target operator created at the **top level** of the script (so its batch commits before the second process has to resolve it) doing **integer arithmetic only** and no table access. Stepping needs two operators: an outer one that calls an inner one, so that stepping over the call and stepping into it are distinguishable.

The cases:

- **Break on start.** `Debug.SetBreakOnStart(true)`, then `ExecuteAsync` a call on the attached process. The process pauses at the first statement of the script it was given (`Program.ReportStart` sets step-into when the flag is on), with `DidBreak` false - this is a pause the debugger asked for, not a breakpoint - and a `Locator` that starts with `program:`. Assert the flag also shows in `Debug.GetDebuggers()` for this session. `SetBreakOnStart` is at 0 % today.
- **Step into enters the called operator.** From that pause, `Debug.StepInto(LProcessID)` repeatedly until the reported `Locator` is the outer operator's locator, then once more past the call to the inner operator until it is the inner operator's locator. Bound the loop by a count as well as a budget and raise a named error when it runs out. Assert the location actually changed at each step: `Debugger.StepOver` and `Debugger.StepInto` do nothing at all when the debugger is not paused (both guard on `IsPaused`), so "the call returned" proves nothing.
- **Step over does not.** From a pause on the statement that calls the inner operator, `Debug.StepOver(LProcessID)` lands on the *next* statement of the outer operator with the same locator, never inside the inner operator. This is the pair the whole feature rests on; assert both halves in the same case so a reader can see the contrast.
- **Pause stops a program that is only running.** The target operator needs a bounded loop with enough iterations to still be running when the script calls `Debug.Pause()` - a counter to a few hundred thousand, measured on the machine, not an unbounded wait - and the loop must terminate on its own even if `Pause()` never takes effect, so a failure here is an assertion and not a `HarnessTimeout`. Assert the process reports `IsPaused` with `DidBreak` false, then `Debug.Run()` and assert it finishes.
- **Break on exception breaks at the raise.** `Debug.SetBreakOnException(true)` (already covered as a setter by `DebugLibrary.d4`; nothing has ever checked it works), then `ExecuteAsync` a script on the attached process that raises an error inside the target operator. Assert the process pauses, that the paused row's `Error` column is not nil, and that the `Line` is the raising statement's line. Then `Debug.Run()` and let the error propagate on the worker, where it is discarded (`SystemExecuteAsyncNode` deliberately does not return it).
- **Detaching a paused process releases it.** With a process paused, `Debug.DetachProcess(LProcessID)`: the process disappears from `Debug.GetProcesses()` at once, and then `StopProcess(LProcessID)` returns **without error**. That return is the assertion. `Debugger.Detach` disowns the process and pulses, and `Debugger.Yield`'s loop falls out because its condition includes `_processes.Contains(process)`; if that did not work, `Engine.TerminateProcessThread` would spin for half of `ProcessTerminationTimeout` - 15 s of the 30 s default - and raise `ProcessNotResponding`. So the failure is bounded and names itself. This is the failure mode a human meets as a server that will not shut down.
- **Stopping the debugger releases a paused process too.** Same again with `Debug.Stop()` instead of `Debug.DetachProcess`: `Debugger.Dispose` runs, detaches everything it holds and sets both signals. Assert `Debug.GetDebuggers()` has no row for this session and that `StopProcess` then returns without error.

## Edge cases & interactions

- **A step can finish the program instead of pausing again.** `Debug.StepOver`/`StepInto`/`Run` all clear the pause request (`InternalRun`), so the process resumes and only pauses again at the next breakable node - and if there is none left, it ends. Give each target operator enough statements after the stepping point, and treat "the process is gone" as a distinct, named failure of a step case rather than as a timeout.
- **`IsPaused` is false immediately after a step or a run**, because `Debugger.IsPaused` requires `_isPauseRequested`. That is what makes "poll until `IsPaused` is true again" a sound wait after a step; do not try to detect the step by comparing locations without waiting first.
- **Step over is depth-based, not line-based.** `ServerProcess.SetStepOver` records the executing-program count and the stack call depth and `InternalShouldBreak` breaks when both match again, lowering each as the stack unwinds. So stepping over the last statement of an operator surfaces in the *caller*, with the caller's locator - correct behaviour, and worth asserting once rather than treating as a miss.
- **Break-on-start fires per program, not per process.** `Program.ReportStart` runs for each program the process executes, so with the flag left on a process pauses again at the start of the next thing it is told to run. Turn it off once the step cases are done, or expect a pause the next case did not ask for.
- **`DidBreak` separates the two kinds of pause.** `Debugger.Yield` adds a process to `_brokenProcesses` only when `ShouldBreak` is true, and `InternalRun` clears that set. So `DidBreak` is true for a breakpoint and for break-on-exception, false for `Pause()`; assert the right one in each case, and note that the column is nil when the process is not paused.
- **The `Error` column carries a CLR exception into a D4 `Error` value** (`DebugGetProcessesNode`, `row[6] = process.Error`). Nothing in the repository has ever read it with a value in it, so the break-on-exception case is the first thing to exercise that assignment. If it throws, that is a real defect this ticket met: fix it here with its reproduction if the fix is local, and file it as its own ticket if the fix changes a design or a compatibility surface.
- **`Debug.Pause()` with no attached process still sets the pause request**, and `Debugger.IsPaused` then reports true because both of its counts are zero. Do not assert on the debugger's own `IsPaused` to decide whether anything is actually stopped - use the process's row, as `DebugBreakpoints.d4` does.
- **Every wait is bounded and raises its own error.** `Debug.WaitForPause()` has no timeout and must never be the thing that blocks; it is already covered by `DebugBreakpoints.d4`, so this script need not call it at all.
- **Each case cleans up after itself**: detach the process, stop it, clear `SetBreakOnStart` and `SetBreakOnException`, so a case that fails leaves the next one diagnosable. The script's server is its own, so nothing escapes the case.
- **Part 2 of the three-part run grows again.** `DebugStepping` starts with D, so it lands in part 2 with `DebugBreakpoints`. The `Pause()` case is the one with real wall-clock cost; keep its loop to the smallest count that is reliably still running, measure it, and record the number in the handoff.
