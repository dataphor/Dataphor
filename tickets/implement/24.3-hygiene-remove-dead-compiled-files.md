## What this is

Five files that every build compiles and that nothing in the repository, the libraries, the samples or the tests refers to. They were found by running the test suite with the coverage collector switched on: each came back at 0 % and was then confirmed dead by searching the whole tree for its type names.

| File | Compile entry | What it is | Coverable lines |
|---|---|---|---|
| `src/engine/Base/IndexList.cs` | `Base.csproj` | `public class IndexList`, a keyed list over a node tree | counted with the next two |
| `src/engine/Base/TemporaryStream.cs` | `Base.csproj` | `public class TemporaryStream : Stream` | counted with the others |
| `src/engine/DAE/Streams/CopyOnWriteStream.cs` | `DAE.csproj` | `public class CopyOnWriteStream : StreamBase` | 494 across these three |
| `src/engine/DAE/Debug/DebugContext.cs` | `DAE.csproj` | `public class DebugContext` and `DebugContexts`, a compile-time script and locator holder | 11 |
| `src/engine/Server/Connection/GenericDotNetConnection.cs` | `Server.csproj` | `public class GenericDotNetConnection` and `GenericDotNetCommand`, a wrapper over the framework provider-factory interface | 111 |

The first three were measured 2026-11-21 by `test-coverage-gap-analysis`; `DebugContext.cs` 2026-11-23 by `debt-debugger-coverage`; `GenericDotNetConnection.cs` by the review of the hygiene umbrella. Re-confirmed 2026-11-26: for each of the five, a search of the whole tree for its type names finds nothing outside the file itself but its `Compile` entry. (`NativeRowIndexList` and `IndexedDictionary` are unrelated types whose names merely contain the string `IndexList`, so search for the whole name.)

All five are `public`, and all five are genuinely unreachable from D4: none of them derives from a type that the class registration picks up. The registration in each assembly (`DAERegister.GetClasses()`, in `src/engine/DAE/Register.cs` and `src/engine/Server/Register.cs`) walks the assembly types and registers, under the D4 name `System.<TypeName>`, every subclass of `PlanNode`, `Schema.Device`, `Conveyor`, `Schema.DeviceOperator` and `Schema.DeviceScalarType` — and nothing else. A plain class, a `Stream`, a `StreamBase` and a connection class are none of those, so no D4 statement can name any of them and no D4 class name disappears. That is the check that makes this change safe to make at all; redo it rather than trusting this paragraph if the registration has changed.

Unlike the files `build-globbing-cleanup` will delete, all five of these **are** compiled, so no other ticket owns them and switching a project to default globbing later would not have dropped them.

## The one that was weighed separately, and the decision

`GenericDotNetConnection.cs` was flagged for a second look because a generic provider-factory connection is the kind of class a customer custom device could plausibly have taken as a starting point, where the other four are internal plumbing. **It goes.** The reasons, so the review does not reopen it:

- It is registered under no D4 class name (see above), so no `create device ... class "..."` and no device `ConnectionClass` setting can name it. A device chooses its connection class by D4 class name — `SQLDevice.ConnectionClass`, read by the SQL Server and PostgreSQL device sessions — and that lookup goes through the class registration, which never saw this type.
- The base class a custom connection would actually derive from, `DotNetConnection`, is public and stays, in the same folder, along with `DotNetCommand` and `DotNetCursor`.
- Its own documentation comment says use of it is not recommended "for anything, ever" and then lists three behaviours it cannot provide that the engine needs.

It is **not** in the coverage area map exclusions — it is still counted, in the *Device connections (engine)* area — so nothing has to be undone there, and that area rate improves by 111 dead lines once it goes. Neither is `DebugContext.cs`, which is still counted in the *Debugger* area.

## The one that stays, and why

`TableForEachNode`, in `src/engine/DAE/Runtime.Instructions/ListNodes.cs`, is dead in the same sense: the compiler cannot reach it, because `Compiler.CompileForEachExpression` always builds a `ListForEachNode` and has an unresolved `TODO` beside that line asking whether the table-sourced form should be used instead. A comment on the class hands the decision to the hygiene umbrella. **The decision is to keep it**, for a reason the other five do not share: it derives from `TableNode`, which derives from `PlanNode`, so the class registration above publishes it under the D4 class name `System.TableForEachNode`. D4 class names are a compatibility surface that this project does not change without a ticket that says so explicitly — the comparable case, `debt-unreachable-redefine-nodes`, went to the owner for a decision and shipped with a migration note. There is a second, weaker reason: the class is the only implementation of the option that compiler `TODO` leaves open, so deleting it would also delete the parked half of an unmade design decision.

So: rewrite that comment into an accepted-tradeoff note at the site, in the shape the project uses for a declined finding — `// NOTE: accepted tradeoff — ...` — saying what was declined (deleting this unreachable class along with the other dead compiled files), why (the class registration publishes every `PlanNode` subclass under a D4 class name, and removing one is a compatibility-surface change), and the revisit condition (a ticket that deliberately retires the class name, the way the unreachable `redefine` implementation was retired, or the compiler `TODO` being settled). Keep the part of the existing comment that says the class is held in step with its two siblings by hand, which is still true and still the reason not to let it drift. Do not repoint it at a ticket slug that will not exist.

## Edge cases & interactions

- **Redo the registration check before deleting.** The argument that no D4 class name disappears rests on the five base types listed in `DAERegister.GetClasses()`. Read both copies of that method (engine and server) and confirm the list, rather than taking this ticket's word for it.
- **`StreamBase` and `Stream` are not the same thing.** `CopyOnWriteStream` derives from the engine's `StreamBase` and `TemporaryStream` from the framework `Stream`; neither is a `Conveyor`, which is the stream-adjacent type the registration does pick up. Check the declaration, not the file name.
- **`Base.csproj` lists `TemporaryStream.cs` immediately before `IndexList.cs`.** Delete both entries, and do not reorder the rest of the list: these project files keep the legacy compile order on purpose.
- **An empty folder.** `src/engine/DAE/Debug/` and `src/engine/Server/Connection/` keep other files, so nothing is emptied here.
- **The coverage tool tests are not run by CI**, so run them by hand after editing the map.
- **Formatting.** `DebugContext.cs` and `GenericDotNetConnection.cs` have a UTF-8 byte-order mark; `IndexList.cs` does not. All use tabs and CRLF, as do the project files. `ListNodes.cs` is the only file being *edited* rather than deleted: change the comment block and nothing else in it.
- **This ticket shares two files with `hygiene-remove-rest-leftovers`** (`areas.json` and `docs/coverage-report.md`), which is why it names that ticket as a prerequisite. Read the current content of both before editing; do not restore an entry that ticket removed.
