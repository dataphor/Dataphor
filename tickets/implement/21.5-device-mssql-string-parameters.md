## What happens

`src/engine/Server/Connection/MSSQLCommand.cs` maps every string parameter to single-byte SQL Server text, in two places that must agree:

- `PrepareParameters` sets `SqlDbType.VarChar` with the parameter's own size, for the client-side path;
- `GetParamTypeDescriptor` writes `varchar(n)` into the `@paramdef` string that `sp_cursoropen` is given, for the server-side cursor path.

SQL Server converts a `varchar` value to the database's collation code page on its way in. Any character the code page has no room for becomes `?`, and the loss is silent and permanent - there is no error, and reading the row back returns the question marks.

**Measured** against SQL Server 2016 LocalDB while `store-mssql-port` was being planned (2026-11-22): a string written through a catalog store cursor into an `nvarchar` column came back with `café` and `Über` intact - a Latin-1 code page holds those - and the two Chinese characters of the probe string replaced by `?`.

It is not new. Before `store-parameterized-statements` the same values went in as quote-doubled `varchar` literals, so the behaviour is 3.1's as well; and the catalog *read* path has always declared `SQLStringType(200)` against the same columns (`ServerCatalogDevice.TranslateScalarParameter`). It is also not confined to the catalog store: every text column a user's SQL Server tables expose through the SQL Server device goes through the same two methods.

**Two places it bites.**

- *The catalog store.* `src/engine/Store.MSSQL/SystemStoreCatalog.sql` declares 41 `nvarchar` columns - object names, library names, display names, descriptions. A D4 object whose name or description contains a character outside the server's code page is stored corrupted. `docs/users-guide/dataphor-service.md` currently warns a deployment about this as a limit of the store; the warning should become a historical note once the fix lands.
- *A user's own tables.* The device maps D4's `String` to `varchar(Storage.Length)` (`MSSQLTypes.cs`), but its reconciliation **accepts `nvarchar` and `nchar` columns as `String` too** (`MSSQLDevice.FindScalarType`, `MSSQLDevice.IsValidDomainName`). So an application mapping D4 tables onto an existing `nvarchar` schema - the ordinary case for a database that holds non-English text - loses data on every write through a parameter.

## Expected behaviour

A string value written through the SQL Server device or the SQL Server catalog store arrives at the server unchanged, whatever characters it holds, when the receiving column can hold them. A `varchar` column still loses what a `varchar` column cannot hold - that is the column's own definition, not ours.

The change is to send the parameter as Unicode: `SqlDbType.NVarChar` in `PrepareParameters` and `nvarchar(n)` in `GetParamTypeDescriptor`, which must move together or the two paths disagree. SQL Server converts `nvarchar` to `varchar` on its way into a `varchar` column, so a schema that uses `varchar` is unaffected except for the characters it could never hold anyway.

**The performance question that comes with it, and how to settle it.** An `nvarchar` parameter compared against a `varchar` column is the higher-precedence type, so SQL Server converts the *column*, which can turn an index seek into a scan. That is a real risk for an application whose SQL Server schema is `varchar` and whose D4 restrictions compare a parameter against an indexed text column. Before changing the mapping, decide and record one of:

- send Unicode always, and accept the risk for `varchar` schemas (simplest, and correct for the Unicode case);
- send Unicode only where the device's own type map says the column is `nvarchar`, which means plumbing the column's native type down to the parameter and is a larger change than it looks;
- send Unicode always but measure the plan shape on an indexed `varchar` column first and say what it costs.

Pick one, say why in a comment at the site, and if you accept a cost, record it as an accepted tradeoff `NOTE:` naming the revisit condition. Do not leave the question open in the handoff.

**A second thing on the same lines, conditional.** Each string parameter's declared size is that value's own length - `DotNetCommand.SetParameters` grows a size that is too small to fit the value - so SQL Server caches a query plan per distinct string length. Declaring the column's width instead would collapse that. **Measure before changing it**: count the cached plans for one statement executed with strings of several lengths. If the churn is real, fix it here; if it is not, record a `NOTE:` at `SetParameters` saying what was measured and when, and leave the `TODO` comment that is already there alone.

It is the right layer for three reasons: it needs no device and no translation, it runs against both stores so the SQLite store answers it too (and should already pass), and it is the path that was measured. The device's own equivalent needs a live device and belongs to `test-device-live`.

## Edge cases & interactions

- **The two methods must agree.** `PrepareParameters` serves the client-side path and `GetParamTypeDescriptor` the `sp_cursoropen` path; a change to one alone gives a device whose behaviour depends on which cursor location it chose (`MSSQLCommand.DetectCursorLocation` picks by whether the statement starts with `select`). Change both, and say in the handoff how you convinced yourself both paths were exercised - the store contract case runs one of them.
- **`SQLTextType` maps to `text`, and `GetParamTypeDescriptor` already asks whether it should be `ntext`** in a comment that has been there since 2008. The same argument applies to it, and `text`/`ntext` are deprecated server types besides. Decide whether this ticket touches `SQLTextType` or leaves it, and say which; if you leave it, leave a `NOTE:` at the comment so the next reader knows the question was weighed rather than missed.
- **`Storage.Length` is a character count either way.** `varchar(n)` counts bytes and `nvarchar(n)` counts characters, so the same `n` means a different maximum byte length. A value that fit a `varchar(20)` column may need `nvarchar(20)`; nothing here shrinks, so this is the safe direction. Confirm the device's `create table` generation still writes what it wrote - the golden files from `test-device-sql-golden` are the check, and the native domain name (`MSSQLTypes.cs`) is **not** part of this change: a device that declares its columns `varchar` keeps declaring them `varchar`, and only the *parameter* becomes Unicode.
- **`ServerCatalogDevice.TranslateScalarParameter` passes `SQLStringType(200)`** for catalog reads, which is where the 200-character columns come from. It needs no change if the parameter type is what moves, but read it to be sure the read path and the write path now agree about the same column.
- **Other devices are not affected.** The PostgreSQL command maps a string to `NpgsqlDbType.Varchar`, which is Unicode in PostgreSQL; ODBC maps to `OdbcType.VarChar`, which has the same problem against SQL Server through ODBC but is a different driver, a different device and not reached by anything today. Mention them so the next reader does not have to look, and file nothing.
- **A migration note is owed.** Text that used to arrive as question marks now arrives intact, which changes what a database receives; and a deployment whose SQL Server schema is `varchar` with indexed text columns may see a different query plan. Both belong in `docs/migration-notes.md`, with the remedy for the second (the tradeoff you recorded). `docs/users-guide/dataphor-service.md`'s non-ASCII warning for the SQL Server store becomes historical - correct it in the same change.
- **The fix is unverifiable without a server, and that is acceptable.** The new contract case is skipped where `DATAPHOR_TEST_MSSQL` is unset, which is how CI runs. Run it locally against LocalDB and say which server version and which database collation you ran against - the collation is what decides which characters a `varchar` column would have lost, so it is part of the measurement, not background.
