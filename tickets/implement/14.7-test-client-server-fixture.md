## What this is

The first of four tickets that build the test plan's layer 4 (`docs/modernization-plan.md#ws3-test-suite`, the `L4 Client/server` row). This one builds the machinery and proves it: a server running as a **separate program**, reached over a real network connection by the client code the product ships. The three that follow reuse what it builds — `test-client-server-cursors` (cursors and the client-side catalog cache), `test-client-server-abandoned` (a client program killed outright) and `test-client-server` (the `ServerLink` coverage script).

Nothing here changes the product. Every file this ticket touches is a test file, a test project file, the solution file, or documentation.

### What already exists, and what is genuinely missing

`tests/DAE.Server.Tests/CoreWcfProtocolTest.cs` already drives the **real** host (`DataphorServiceHost`) with the **real** client stack (`ClientServer` wrapped in `LocalServer`) over a real `net.tcp` socket — twelve cases covering a whole session, a three-megabyte value in both directions, typed faults, the native call interface, streams and the listener. It does all of that with the host in the *test's own process*.

So what the process boundary adds is narrower than it looks, and this ticket should claim only what it actually establishes:

- A server started as its own program, from an instance list of its own, serves the shipped client stack — and stops when it is asked to.
- The two engines are genuinely separate. In one process they are not: starting a second engine resets a counter the first is still using (`bug-object-id-counter-is-process-wide`), which is why `CoreWcfProtocolTest` hands that counter back around building its client.
- It is the only place a *second server*, or a *second client program*, can exist without the two sharing the engine's process-wide state. The third and fourth tickets need exactly that.

What it does **not** add, and what this ticket must therefore not duplicate: streams over the wire, the message-size quotas, and fault typing. Those already run against a real host over a real socket; moving the host into another program changes no part of that path. Say so where a reader will look for them, rather than writing a second copy.

## The design, settled

### A test host program, not the shipped executable

The child server is a small console program of the suite's own, `tests/TestHarness` (assembly `DAE.Test.Harness`), which builds a production `DataphorServiceHost`, sets the two properties that are host-object properties rather than instance settings, and starts it through the production entry point `Start()`.

The shipped executable `artifacts/layout/<config>/bin/DAEServer.exe` was weighed and rejected **for the suite**, for one reason that cannot be worked around from outside it: a hosted server logs unless its host turns logging off, and `Server.StartLog` creates the Windows event-log source `Dataphor Server` and writes to the Windows event log when the process is elevated (`src/engine/Server/Server/Server.cs`, `StartLog` and `LogMessage`, both gated on `IsAdministrator()`). Continuous-integration runners are elevated. Every in-process fixture in this suite sets `DataphorServiceHost.LoggingEnabled = false` for exactly this reason, and the shipped host has no way to be told the same thing — not a command-line switch (`HostCommandLine` is a compatibility surface), not an instance setting (`ServerConfiguration` carries neither `LoggingEnabled` nor `HostName`, which `host-instance-directory` recorded as the reason `DataphorHost.BuildHost` keeps its factory parameter). A test must not create machine state, so the suite does not start it.

That leaves a real gap — nothing in the suite shows that the published executable launches — and it is filed as `debt-test-shipped-host-executable` in `backlog/`, which also names the knob it needs. What is covered already: `HostProgramTest` pins the program's start-and-stop behaviour in process, and asserts that each executable's dependency file names the catalog-store assembly.

### The harness program

One program with two modes, so that there is one project, one path to resolve, and one place where a child process learns how to behave. This ticket writes the `serve` mode; `test-client-server-abandoned` adds the `client` mode.

```
DAE.Test.Harness serve --instance <name> [--host-name <name-or-address>] [--logging]
```

- The instance's settings come from an instance list of the parent's writing, through the documented redirection: the parent sets `DATAPHOR_INSTANCE_DIRECTORY` on the child (`InstanceManager.InstanceDirectoryVariableName`) to a private folder holding a `ServerConfigurations.config` it wrote, and the child calls `DataphorServiceHost.Start()` — the same call the shipped host makes. Nothing reads or writes this machine's own instance list.
- `--host-name` defaults to `Environment.MachineName`, which is the product default. The fixtures pass the loopback literal `127.0.0.1`, so no port this suite opens is reachable from another machine. (`test-client-server` is the one ticket that needs the default; the reason is in that ticket.)
- Logging is **off** unless `--logging` is given, which is the opposite of the shipped host's default and is the whole reason this program exists. The fixture passes `--logging` when `DATAPHOR_TEST_LOGGING=1`, so the suite's existing diagnosis switch reaches the child too.
- On success it writes one line to standard output — `READY <instance> <port> listening=<true|false>` — and then reads standard input. On any failure it writes the exception to standard error and exits with a non-zero code.
- **A line on standard input, or end of input, stops the server and exits.** End of input matters as much as the line: when the parent process dies its child's input pipe closes, and that is what keeps a crashed or killed test run from leaving an orphaned server holding a port and a temporary folder. (`DataphorHost` deliberately dropped `Console.ReadLine` for the shipped host, because a server's input may be redirected or closed; for a program whose only caller is a test fixture that is the right mechanism rather than the wrong one. The plan's note under *CoreWCF hosting* — that closing the redirected input pipe no longer stops the shipped host — is about `DAEServer.exe`, not about this program.)

### The fixture helper

`tests/DAE.Server.Tests/OutOfProcessInstance.cs`, an `internal sealed class` beside `HostedInstance.cs` and shaped like it, owning one child server for the life of a fixture:

- a fresh temporary root from `TestEnvironment.NewDirectory`, holding `Instances\` (the private instance list), `Libraries\` (from `TestEnvironment.CopyLibraries`, so the child rewrites `.d4l` files in a copy and never in the runtime layout) and `Instance\` (the instance's own folder, named outright in the configuration);
- a free loopback port from `HostedInstance.ReserveLoopbackPorts`, and `ShouldListen = false`, so the child takes no listener port and cannot collide with a listener on this machine;
- the instance list written with `InstanceConfiguration.Save(Path.Combine(directory, InstanceManager.InstanceConfigurationFileName))` — a plain file write that needs no change to the static `InstanceManager.InstanceDirectory` in the test process, so no other fixture can be disturbed by it;
- the child started with its standard output and error **drained asynchronously** (`OutputDataReceived`/`ErrorDataReceived`, or two reader tasks), because a child that fills a pipe buffer nobody reads stops;
- readiness by waiting for the `READY` line, bounded (a first start creates a catalog store, so allow generously, and count the wait from process start) — and on timeout or early exit, failing with **everything the child said** plus its exit code, never with a bare timeout;
- teardown: write a line to the child's input, wait a bounded time for exit, then `Kill(entireProcessTree: true)` and wait again; then `TestEnvironment.TryDeleteDirectory`. Teardown must run on the failure path of setup too, as `HostedInstance`'s does.

Properties for the fixtures: `InstanceName`, `HostName`, `PortNumber`, `RootDirectory`, and the child's captured output for a diagnostic message.

### The client helper

`CoreWcfProtocolTest`'s own size note asks for this: *"what is left of the bulk is the cases themselves plus the client plumbing, ProtocolClient. If that grows, it is the next thing to move."* It is about to grow, so move it.

Extract the nested `ProtocolClient` into `tests/DAE.Server.Tests/ProtocolClient.cs` as an `internal sealed class` taking host name, instance name, port number and (for `test-client-server-abandoned`) a keep-alive interval, and have `CoreWcfProtocolTest` use it with no change in behaviour. Keep the object-id-counter restoration around building the `LocalServer`, and **rewrite its remark**: out of process the server's engine is no longer in this process, but a second `LocalServer` in the test process still starts a second client-side engine, which is what `test-client-server-cursors` needs for the catalog cache. The reason changes; the three lines do not.

### Where the tests live, and what they cost

In `tests/DAE.Server.Tests`. It already holds `CoreWcfProtocolTest`, `HostProgramTest` and `ContractParityTest`, and it is the project that owns `TestEnvironment`, `TestServerInstance`, `HostedInstance` and the coverage harness that `test-client-server` has to change. A separate project would mean either a copy of `TestEnvironment` or a fourth project to share it, for the sake of a name. The project's name is already wider than its contents; renaming it is nobody's ticket and not this one's.

Budget: **one child server process** for this fixture, shared by this ticket's cases and `test-client-server-cursors`'. A start is a server start plus a catalog store creation — the coverage template, which does more, takes a few seconds. Expect this fixture to add well under a minute to suite part 1 (`NUnit.Where=class != …CoverageScripts`), which has room: it ran 3 m 33 s on the slow machine against a 10-minute limit. **The three-part split in `AGENTS.md` does not change, and no fourth part is needed.** Measure it and give the number in the handoff; if part 1 passes about 8 minutes, that is when it gets split, by the rule already written there.

## The cases

Two, and only two. Each is a fact the process boundary establishes and nothing else in the suite does.

- **`AServerInAnotherProgramServesTheShippedClient`** — the whole round trip against the child: connect as `Admin`, start a process, create a table, prepare a statement and execute the **same prepared plan more than once** (which nothing covers today — `CoreWcfProtocolTest` prepares and executes once), read the rows back through a cursor, stop the process, disconnect, and assert the server is still serving afterwards by connecting again. The D4 stays on built-in operators and types over the memory device, for the reason `CoreWcfProtocolTest` records: a class alias the client-side engine cannot find sends `LocalServer` down the library-download path.
- **`TheChildServerStopsWhenItIsAsked`** — the teardown path as a case rather than only as a `finally`: the child exits with code 0 after a line on its input, within the bounded wait, and the port stops listening. This is the only place in the suite where `DataphorServiceHost.Stop()` runs in a program whose exit can be observed; `NetTcpServiceHost.Stop` gives Kestrel ten seconds to close open connections, and a client channel is open when it runs.

No case asserts anything about streams, message size or fault typing. Put one sentence in the fixture's remarks naming `CoreWcfProtocolTest` as where those live and why they are not repeated, so the next reader does not read the omission as an oversight.

## Edge cases & interactions

How each is covered: **(test)** a case asserts it, **(seam)** an assertion or guard in the fixture code, **(inspection)** read and reasoned about, no test.

- **An orphaned child server** after a crashed, killed or timed-out test run — holding a port, a temporary folder and a catalog. *(seam)* The child stops on end of input, so the parent's death is enough; teardown also kills the process tree. Both paths exist because either alone can fail: a child wedged before it reads input would not notice the pipe close.
- **A child that fails to start** (port taken between reservation and bind, a bad configuration, a missing catalog-store assembly). *(seam)* Readiness fails with the child's own standard output, standard error and exit code. The existing `NOTE:` on `HostedInstance.ReserveLoopbackPorts` already records the reservation window; do not restate it, reuse the method.
- **A child that starts but never prints `READY`.** *(seam)* The bounded wait, with the same diagnostic. Distinguish "exited" from "still running" in the message.
- **A full pipe buffer.** *(seam)* Output drained asynchronously from the moment the process starts. This is easy to get wrong by reading `StandardOutput` synchronously while also waiting for exit.
- **Temporary folder still locked at teardown**, because the child had not finished exiting. *(seam)* Delete only after the exit wait; `TestEnvironment.TryDeleteDirectory` already reports and leaves a folder it cannot remove for the next run's sweep.
- **`DATAPHOR_TEST_LOGGING=1`.** *(seam)* The child gets `--logging`, and its folder is kept, like every other fixture's. Check by hand that the instance log appears in the kept folder, and that a *default* run creates no `Dataphor Server` event-log source (the suite's standing requirement).
- **Environment inherited by the child.** *(inspection)* `ProcessStartInfo.Environment` starts from the parent's, so a developer who has `DATAPHOR_INSTANCE_DIRECTORY` set for their own use has it overwritten — which is what we want — but check that nothing else the suite sets leaks meaning into the child.
- **The object-id counter.** *(inspection)* Only client-side engines live in the test process now. Keep the restoration in `ProtocolClient` for the second client engine `test-client-server-cursors` adds, and state the new reason at the site.
- **Two fixtures in this project each owning a child.** *(inspection)* Separate processes share no engine state; nothing in this project is `[Parallelizable]`, and these fixtures must not become so either — say why on the class, as the others do.
- **`InstanceManager`'s static state.** *(seam)* This fixture never sets `InstanceManager.InstanceDirectory`; it writes the child's list as a file. `CoreWcfProtocolTest` does set it, and restores it; nothing here should depend on either.
- **The harness project must stay out of the runtime layout.** *(seam)* `tools/layout/Layout.csproj` lists its projects explicitly and test projects are not listed; adding it there would also break the layout's `.d4l` check. Confirm the layout's file count is unchanged after the build.
- **Resolving the harness program's path.** *(seam)* Do not spell it. Preferred: a target in `DAE.Server.Tests.csproj` that asks the harness project for its `TargetPath` through the `MSBuild` task (passing the same `Configuration`) and records the answer as `AssemblyMetadata`, the way the project already records `DataphorLayoutDir`; the executable is that path with the `.exe` extension. Acceptable fallback if target ordering fights the SDK: record `$(ArtifactsPath)` and compose `bin/DAE.Test.Harness/<configuration>/DAE.Test.Harness.exe`, the output shape `AGENTS.md` documents. Either way a missing file must fail with a message naming the project and the build command, as `TestEnvironment.FindLayoutDirectory` does for the layout.
- **The harness needs the ASP.NET Core shared runtime and the package-audit dance.** *(inspection)* It references `Server.Hosting`, so it needs `<PackageReference Include="CoreWCF.NetTcp" />` plus `<FrameworkReference Include="Microsoft.AspNetCore.App" />` or it reports `NU1902`, which `AGENTS.md` forbids suppressing. Copy the comment and the items from `src/hosts/DAEServer/DAEServer.csproj`, and reference `DAE.SQLite.csproj` for the same reason that project does (the catalog store is loaded by name, and there is no app-local probing on .NET 10). Confirm `dotnet restore Dataphor.slnx` still reports no `NU1xxx` warning.
- **A server writes into its library directory.** *(seam)* The child's `LibraryDirectories` points at the copy, never at the layout or the repository. It will create `General` there.
- **Signing and project conventions.** *(inspection)* `Directory.Build.props` signs and versions everything; set `DefineConstants` outright, no `OutputPath`, explicit `Compile` items (default items are off repository-wide).

## Tests

The two cases above, and nothing else. No test for the harness program's argument parsing (it is a test tool, and a wrong argument fails the fixture that passes it immediately and loudly); no test for the path-resolution target (the fixture fails with its own message if it is wrong); no second copy of the stream, quota or fault cases.
