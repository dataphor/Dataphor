## What this is

The machine's list of server instances is a file — `ServerConfigurations.config`, XML written by BOP — that existing deployments hand-edit and that the configuration utility and the server itself both write. It is a compatibility surface, and the administrator documentation does not describe a single one of its settings. `docs/users-guide/dataphor-service.md` mentions the file once, in passing, in the "Installing Multiple Instances" section. This work item writes the missing reference section.

It also fixes something wrong in the same chapter. The "Configuration" sub-section of "Service Configuration Utility" has a seven-row table purporting to describe the instance's settings. Four of its rows do not correspond to anything in the product: *Catalog Store Database Name* and *Catalog Store Password* are from the SQL CE era (the store now takes one connection string, and `store-remove-sqlce-references` removed SQL CE), and *Tracing Enabled* and *Log Errors* have no counterpart in `ServerConfiguration` at all. Measured by reading `src/windows/ConfigurationUtility/ConfigForm.cs` against `src/engine/Server/Server/ServerConfiguration.cs`: the form still carries the 3.1 fields (`tbCatalogStoreDatabaseName`, `tbCatalogStorePassword`, `cbCatalogStoreShared`, `chkLogErrors`, a *Catalog Directory* box) and the class carries none of them. The form itself belongs to `ui-config-utility`, which has not run yet, so this work item does not touch the form, the screenshots or the utility's behaviour — it replaces that stale table with a sentence saying the Configure form edits the named instance's entry in the file, and a pointer to the new section, which is then the one place the settings are described.

## Where the section goes

In `docs/users-guide/dataphor-service.md`, a new top-level section after "Installing Multiple Instances", which already sends the reader to the file. `docs/users-guide/dataphor-server.md`'s "Hosting a Dataphor Server" section gets a sentence linking to it, since that is where a reader arrives looking for how an instance is configured. Both files are converted Markdown under `docs/`; the AsciiDoc under `Documentation/` is not edited.

## What the section has to say

**About the file.** Where it lives — `%ProgramData%\Alphora\Dataphor\4\Instances\ServerConfigurations.config`, machine-wide, one file for every instance on the machine, created on demand. That the folder carries the major version, so a 3.1 installation on the same machine has its own and the two do not interfere (`host-instance-directory` makes this true; confirm the path from the code rather than from this ticket). That the `DATAPHOR_INSTANCE_DIRECTORY` environment variable points a process at a different folder, what it is for (an isolated server for testing, or trying a configuration without touching the machine's own), and that every process meant to see that list has to have it set. That both the configuration utility and the server write the file: a server started for an instance that has no entry **adds one with default settings and saves the file**, which is how a first start produces a working instance and also why a typo in an instance name leaves a stray entry. That settings are read when the instance starts, so a change needs a restart.

**Every setting**, each with what it does, its default, why an operator would change it, and what happens when it is absent from the file. Read each default out of the code, not out of this list; the values below are what the code said when this ticket was written and are here so the writer knows where to look.

| Setting | Where the default is | Value when this was written |
|---|---|---|
| `Name` | `ServerConfiguration.DefaultInstance`, `Engine.DefaultServerName` | the instance name; `Dataphor` when the host is given none. Names are matched without regard to case and must be unique in the file |
| `PortNumber` | `ServerConfiguration.DefaultPortNumber` | 8061; the in-process local instance uses 8062 (`DefaultLocalInstanceName` `LocalInstance`, `DefaultLocalPortNumber`). Must be unique on the machine |
| `ShouldListen` | `ServerConfiguration._shouldListen` | true. Turns off this instance's registration with the machine's listener, so clients must name its port rather than discover it |
| `OverrideListenerPortNumber` | `ListenerServiceHost`, `DataphorServiceUtility.DefaultListenerPortNumber` | 0, meaning the standard listener port (8060). The listener is one per machine, shared by every instance |
| `LibraryDirectories` | `ServerConfiguration.DefaultInstance`, `Server.GetDefaultLibraryDirectory` | `<installation>\Libraries` as written by a default entry; `<binaries>\Libraries` when the setting is empty. Semicolon-separated; a relative entry is resolved against the binaries' folder; the server creates a missing directory and **writes into it**, so two instances must not share one |
| `InstanceDirectory` | `Server.InstanceDirectory` | empty, meaning a folder named after the instance inside the instances folder. Everything the instance writes goes here: `Catalog\`, `Log\`, device data. A full path moves it, for example onto another volume |
| `CatalogStoreClassName` | `Server.DefaultCatalogStoreClassName` | the SQLite store, `Alphora.Dataphor.DAE.Store.SQLite.SQLiteStore,Alphora.Dataphor.DAE.SQLite`. A name the runtime cannot load stops the start with error 115107; a SQL CE name stops it with error 115108 (`store-remove-sqlce-references`) — both worth stating, because an upgraded file is where a SQL CE name comes from |
| `CatalogStoreConnectionString` | `Server.GetCatalogStoreConnectionString`, `GetCatalogStoreDatabaseFileName` | empty, meaning `Data Source=<instance>\Catalog\DAECatalog.sqlite`. `%CatalogPath%` in a supplied string is replaced with the instance's catalog folder — document that, it is the only way to move the catalog file without hard-coding a path |
| `DeviceSettings` | `Schema.DeviceSettings`, `DeviceSetting` | empty. A list of device name / setting name / value entries applied to the server as it starts; it is how a device is pointed at a particular database server per instance without editing D4 |
| `RequireSecureConnection`, `RequireSecureListenerConnection` | `ServerConfiguration` | false. **Stored and accepted, but nothing acts on them today**: say so plainly rather than describing an effect the server does not have. `protocol-transport-security` decides whether they come to mean something or go away, and amends this section either way; it runs after this one, so write what is true now and do not wait for it |

**What happens to a file an earlier release wrote.** Both directions, because an upgrading operator meets both:

- A setting in the file that the current server does not have is ignored, and every other setting on that instance is still read — the file is not rejected and nothing else is lost. This is pinned by `LoadReadsAFileCarryingSettingsThatNoLongerExist` in `tests/DAE.Server.Tests/InstanceConfigurationTest.cs`. Name the two settings a 3.1 file is likely to carry (`UseServiceConfiguration`, `AllowSilverlightClients`, both removed by `protocol-corewcf-host-prepare`) so a reader recognises them.
- The setting is then **gone from the file the next time anything saves it**, because a save writes the properties the server has. State this as what happens; it is established by reading the serializer, and `protocol-corewcf-host-prepare` weighed a test for it and declined one on the grounds that such a test would pin BOP rather than anything the product changed. Do not assert anything stronger than the code supports — before writing this paragraph, read `Serializer` in `src/engine/Base/BOP/` and check whether a property equal to its `[DefaultValue]` is written at all, since `ShouldListen`, `OverrideListenerPortNumber` and the two security settings carry that attribute and the answer decides whether an unset setting appears in a saved file.

Write it as administrator documentation: plain sentences, no ticket slugs, no class or method names where a plain phrase will do, no mention of this repository's workstreams. A table of settings with a paragraph each is the right shape; the existing chapter mixes Markdown tables and raw HTML tables (from the AsciiDoc conversion) — a Markdown table is fine for a new section.

## Edge cases & interactions

- **A default this ticket copies out of the code and gets wrong is worse than no documentation.** Every value in the section is read from the source file named beside it in the table above, in the tree as it stands after `host-instance-directory`. *Verified by:* reading each site; the reviewer will re-check them.
- **The file path.** `host-instance-directory` moves it; take the path from `InstanceManager` rather than from the table above. *Verified by:* reading `InstanceManager.InstanceDirectory`.
- **`protocol-transport-security` has not run.** It owns the fate of the two security settings and its plan ticket already commits to amending "a line in the user-guide section that `host-instance-configuration` writes". Do not block on it and do not describe a future state. *Verified by:* inspection of `tickets/plan/14.5-protocol-transport-security.md`.
- **`ui-config-utility` has not run.** The Configure form's fields do not match the settings, and this ticket does not change the form, its screenshots or the options table below it — only the one stale settings table. *Verified by:* inspection; the screenshots stay as they are.
- **Links.** `docs/` has a link checker and a known set of pre-existing failures; a new section introduces anchors and one cross-file link. *Verified by:* `python tools/docs-link-check/check_links.py`, whose output must show no new error in the two files touched.
- **No code changes, so no migration-notes entry and no new test.** Documentation is not a surface an application or an extension notices, and there is nothing here for a test to pin. If something turns out to need a code change, it belongs in its own ticket unless it is a one-line obvious fix.
