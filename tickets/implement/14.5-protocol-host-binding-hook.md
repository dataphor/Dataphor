## Why this exists

The client half of the protocol has always had three public extension points on `DataphorServiceUtility` (`src/protocol/Common/Contracts/DataphorServiceUtility.cs`):

| Member | What it replaces |
|---|---|
| `Func<Binding> BuildBindingCall` | the whole binding a client connects with |
| `Func<EndpointIdentity> BuildEndpointIdentityCall` | the identity a client requires of the server (a client-only concept) |
| `Action<ServiceEndpoint> ServiceEndpointHook` | a last look at each endpoint the client builds |

Nothing in this repository sets any of them. They exist so that a deployment can supply its own binding from its own host code, and that is the only route there has ever been to an encrypted Dataphor connection: none of the product's own "use a secure connection" settings reach a binding at all (established by `protocol-transport-security`, which this ticket is split from).

`protocol-corewcf-host` moved the server's binding out of `DataphorServiceUtility.GetBinding()` and into `DataphorServiceHostBinding.Build()` in the new hosting assembly, because CoreWCF's `Binding` type is unrelated to `System.ServiceModel`'s and the two stacks cannot share one declaration. That was right, and the two declarations are held in step by a test. The cost, recorded in `docs/migration-notes.md` and handed here: **`BuildBindingCall` now reaches only what a client connects with, never what a server listens with, and there is no host-side replacement.** So a site that had secured its 3.1 server by installing that hook cannot secure its 4.0 server at all. That is a lost capability, not a design choice, and it is this ticket's whole subject.

## What to build

The host's mirror of the client's hook surface, in the hosting assembly, in a class of its own beside the binding declaration. `DataphorServiceHostBinding` stays what its own class remark says it is — a pure declaration of the host's half of the one binding, which `CoreWcfProtocolTest.TestHostBindingMatchesTheClientBinding` compares against the client's — and the extension point goes next to it:

```csharp
namespace Alphora.Dataphor.DAE.Service
{
    /// <summary>The host's half of the protocol's extension points; the client's half is DataphorServiceUtility.</summary>
    public static class DataphorServiceHostHooks
    {
        /// <summary>Builds the binding every endpoint of a host in this process is served on.</summary>
        public static Func<CoreWCF.Channels.Binding> BuildBindingCall = DefaultBuildBinding;

        /// <summary>A last look at each host's service builder, after that host's endpoints have been added.</summary>
        public static Action<CoreWCF.Configuration.IServiceBuilder> ServiceBuilderHook = DefaultServiceBuilderHook;

        /// <summary>False while the binding is the product's own; how a caller tells whether a site has replaced it.</summary>
        public static bool HasCustomBinding { get; }

        public static void RevertHooksToDefault();
    }
}
```

Shape it on `DataphorServiceUtility` deliberately — the same member names where they mean the same thing, a `RevertHooksToDefault` that reverts under a lock, mutable static fields read when a host is built — so that the two halves read as one extension point rather than as two inventions.

- `DefaultBuildBinding` is `DataphorServiceHostBinding.Build()`, unchanged.
- `DefaultServiceBuilderHook` does nothing, exactly as the client's `DefaultServiceEndpointHook` does nothing.
- `ServiceBuilderHook` is where a certificate can be installed: CoreWCF's `IServiceBuilder` carries `ConfigureServiceHostBase<TService>` and `ConfigureAllServiceHostBase` (both present in CoreWCF.Primitives 1.9.1 — checked by reading the assembly's metadata names), which is how service credentials are reached. There is no per-endpoint object to hand out as the client's `ServiceEndpointHook` gets — CoreWCF's `AddServiceEndpoint` returns the builder, not an endpoint — so the builder is the unit, and the hook is called once per host after that host's endpoints are added.
- `HasCustomBinding` exists so that a caller can tell whether the binding is still the product's. `protocol-transport-security` needs exactly that: it reports a "require a secure connection" setting as having no effect, and must not report that at a site which has supplied a binding of its own. Implement it by holding the default in a `static readonly` field and comparing by reference rather than comparing against a method group, and mind static-initialiser order — the field the comparison reads has to be initialised before the field it is compared with.

Both hosts then take their binding from `DataphorServiceHostHooks.BuildBindingCall()` instead of calling `DataphorServiceHostBinding.Build()` directly, and both call `ServiceBuilderHook(builder)` as the last thing inside the `addEndpoints` action they hand to `NetTcpServiceHost.Build`.

## Edge cases & interactions

| Case | How it is handled, and how that is verified |
|---|---|
| A hook that throws, on the instance's host | `Start`'s existing outer `catch` stops the server and rethrows; the start fails as any host failure does. By inspection of `DataphorServiceHost.Start`. |
| A hook that throws, on the listener's host | `ListenerServiceHost` calls `BuildHost` **before** its `try`, so a hook failure propagates instead of being swallowed as "the listener port is already taken". Confirmed by reading the constructor; keep it that way and say so in a comment, because moving the build inside the `try` would silently turn a misconfigured hook into a missing listener. Covered by a case. |
| A hook returning null | The endpoints would fail deep inside CoreWCF with no useful message. Fail at the call site instead, naming the hook. Covered by a case. |
| Two hosts in one process (the instance's and the listener's) | Each builds its own binding from the hook, as each builds its own today; nothing is memoized, unlike the client's `GetBinding`. Keep it so — a hook may legitimately return a different binding per call — and note it at the site. |
| A hook installed after a host has started | No effect on the running host, as on the client. Documented in the class remark, not enforced. |
| The binding parity test | `TestHostBindingMatchesTheClientBinding` still compares `DataphorServiceHostBinding.Build()` with `DataphorServiceUtility.GetBinding()`, which are still the two *default* declarations. It must not be rewritten to go through the hook, or it would be comparing whatever a test installed. By inspection. |
| Static state leaking between fixtures | The hooks are process-wide. Any fixture touching them reverts in teardown and is not `[Parallelizable]`, as `CoreWcfProtocolTest`, `HostProgramTest` and `InstanceManagerTest` already are not, each with a comment saying why. |
| `USENAMEDPIPES` | Untouched; the existing `NOTE:` on `NetTcpServiceHost.ListenAddress` already owns it. |

## Tests

Two cases, in a fixture of their own. Neither is a wiring test: the first establishes that a replaced binding reaches the wire, which is the entire capability, and the second that the builder hook is reached by both hosts — there is no behavioural way to observe that one without a certificate, and an extension point that is never called is the defect this ticket exists to fix.

- **A replaced binding changes what the server accepts.** Install a `BuildBindingCall` returning a binding the shipped client cannot talk to — a text message encoder in place of the binary one is cleanest, the mismatch being unambiguous and needing no large payload — start a host, and assert that a client built from `DataphorServiceUtility.GetBinding()` cannot complete a call. Revert, start again, assert it can. If the encoder mismatch turns out to surface as a hang rather than a failure, use a binding whose `MaxReceivedMessageSize` is a few kilobytes and send a larger string instead; say in the handoff which was used and why.
- **Both hosts reach `ServiceBuilderHook`, and the listener's failure is not swallowed.** Count the invocations across a start with the listener on (two hosts, so two calls); then install a throwing hook and assert the start fails, rather than producing a server with `IsListening` false.

**Where they go.** `CoreWcfProtocolTest` cannot host them: its `[OneTimeSetUp]` starts one host that every case shares and that assumes the default binding. That fixture's own `NOTE:` ("979 lines … if more hosted cases land here, move that plumbing to a file of its own and leave the cases behind") asks for the extraction this needs, so do it: move the nested `HostedInstance` class and the `ReserveLoopbackPorts` and `ServerConfiguration` helpers into `tests/DAE.Server.Tests/HostedInstance.cs` as an internal type, leave the cases behind in `CoreWcfProtocolTest`, update that `NOTE:` to the newly measured line count, and write the new cases in `tests/DAE.Server.Tests/HostBindingHookTest.cs` against the extracted type. Keep the extraction a pure move — no behaviour change, no renamed members — and run the whole of suite part 1 after it, because every hosted case in the project depends on it.
