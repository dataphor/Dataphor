## Design: wrappers reference the converted projects in place

The spike keeps wrapping only what is still in legacy format (Server, Store.SQLite, the libraries that need the server, the UI and host projects, the tests) and references the converted projects' real project files. With K4 fixed in the repository, a Debug server start through the real Base works.

- **Detection.** `convert.py` treats a listed project as converted when its root element is `Project` with an `Sdk` attribute and no MSBuild 2003 namespace. It writes no wrapper for it and prints one line saying it is used in place.
- **References.** A wrapper's `ProjectReference` to a converted project points at the real project file by absolute path; references between wrappers stay as today (`..\<Name>\<Name>.csproj`).
- **Package versions.** `convert.py` reads the `PackageVersion` items from the repository's `Directory.Packages.props` and uses those versions for any package in `PACKAGE_MAP` or `ALWAYS` that is listed there, so wrappers never pin below the converted projects. Wrappers live outside the repository and do not use central package management themselves, so they keep `Version=` attributes.
- **Build loop.** `run.py` builds a converted project with `dotnet build <repo path>` (same quiet flags and `summ.py` summary as the wrappers) and a wrapper as today. Output of converted projects goes to the repository's `artifacts/` (git-ignored); say so in the README, which currently claims the spike never writes into the repository.
- **Locating assemblies.** `find_dll` for a converted project asks MSBuild for the output path (`dotnet msbuild <project> -getProperty:TargetPath -p:Configuration=Debug`) rather than walking a wrapper's `bin`. `COVERAGE_LIBS` keeps its shape; `DAE.Device.SQL` is now converted, the others are still wrappers.
- **Patches and stubs.** Remove the three landed `PATCHES` entries and the `"DAE"` entry of `STUBS`; delete `stubs/Engine.cs` (it only existed for the dead `using`). Keep the Store.SQLite (`ResultCode` and K10 "begin immediate"), K1 (`ServerCatalogDeviceSession.cs`), Frontend `IStreamProvider` and Connection K19 patches, and the `Server` stub, for `build-server-project` to retire. Add a guard: `run.py` exits with a clear message if a `PATCHES` file or a `STUBS` key belongs to a converted project, because the real project compiles the repository file and would silently ignore the override.
- **`--tfm`.** The converted projects target `net10.0` only. Keep the option for wrappers, and say in the README that a framework below `net10.0` cannot reference the converted projects (restore fails with `NU1201`); the plan's D1 settles `net10.0`.
- `projects.txt` keeps listing the converted projects, so `--only` and the per-project summary lines still cover them.

Keep the change small: `convert.py` and `run.py` are throwaway and are deleted once `test-harness-inprocess` and the remaining conversions land. Do not copy the spike's `ALWAYS` list, `NoWarn` list or resource naming into anything in the repository.

## Edge cases & interactions

- **Wrapper pins a lower package version than a converted project** — `NU1605` error. Handled by reading `Directory.Packages.props`; verified by the full spike run restoring and building the Server wrapper (which references Common and NativeCLI) with 0 errors.
- **A patch or stub aimed at a converted project** — silently ignored without the guard. Verified by the guard (an assertion at the seam), by inspection of the remaining `PATCHES`.
- **Configuration flow** — wrappers build Debug, and `ProjectReference` passes `Configuration=Debug` to the real projects; `find_dll` asks for the Debug `TargetPath`. Verified by the coverage run finding `Alphora.Dataphor.DAE.Device.SQL.dll` in `artifacts/bin/DAE.Device.SQL/debug/`.
- **Stale wrapper output** — a work directory from an earlier spike run still has `out/Base`, `out/DAE`, … wrappers; nothing references them any more, but `find_dll` must not pick a stale DLL from them. Use a fresh work directory for the gate run, and have `find_dll` resolve converted projects only through MSBuild.
- **Spike hosts and NLS** — `Smoke` and `Cov` are built in the work directory, outside the repository, so they do not inherit `Directory.Build.props` and run without NLS, as the 62/14 baseline was measured. Do not change that here; `test-harness-inprocess` measures with NLS on.
- **Repository writes** — after the spike run, `git status --porcelain --ignored` shows no new entry other than `artifacts/` (and the existing `tickets/` ignores).

No new tests: the spike's coverage run and the engine check are this ticket's verification, and `test-harness-inprocess` turns them into the permanent suite.
