## What this is

The codebase was written for a named organization before it was open-sourced, and that name was written into a handful of comments, one sample schema tag, one sample script and one build property. The repository is public now and the project rule is that no tracked file, ticket or commit message carries such a name. Six files still do.

**Read the name off the first site rather than being told it**, and keep it out of this ticket, out of your commit message and out of your handoff — describe each change generically ("the inherited organization name", "a host name that is not ours"). That is why the sites below are given as a path and a line and not as quoted text.

The six, measured 2026-11-26 by this planning pass:

| `src/engine/DAE/Device.Catalog/CatalogStore.cs` line 6 | trailing comment on a `#define` | an internal proposal number, attributed to the organization |
| `src/engine/DAE/Language.D4/MetaData.cs` line 12 | comment block above two `#define`s | the organization named as the owner of a large catalog |
| `libraries/System.Integration/Source/IntegrationNodes.cs` line 171 | a `TODO` comment | the organization and a project number |

A seventh site was in `legacy/Documentation/`, which `docs-remove-old-sources` has since deleted, so nothing is owed there.

To confirm nothing is missed, search the whole tracked tree case-insensitively for the token you found at the first site. Most of the hits are false positives and must be left alone: identifiers in which the token is a substring (several interface names in the client and Windows-client assemblies), base64 image data inside a `.resx`, United States place names in a sample ZIP-code data file, and the vendored WiX 3.5 binaries under `Utilities/Wix`, which are third-party files that the WS9 installer work deletes wholesale. Six files have a real occurrence; the table above names all of them.

## What each replacement should say

**The three comments carry no behaviour**, and two of them are already published in generalized form, so make the code agree with the documentation rather than inventing new wording:

- `CatalogStore.cs` line 6 comments the `REQUIRECASEMATCHONRESOLVE` switch. The `docs/reference/compiler-defines.md` row for that switch already describes it without the name ("Introduced for an internal proposal, numbered 26889 in the inherited index"). Rewrite the comment to match, keeping the proposal number, which is not an identifying detail on its own, and keeping the sentence that says what the switch does.
- `MetaData.cs` line 12 is the last line of the comment above `USETAGNAMECACHE`. The published note for that switch already says the measurement was taken on "a large customer catalog". Rewrite the line the same way.
- `IntegrationNodes.cs` line 171 is a `TODO` about cross-process row copies for streamed types. Keep the whole technical point — what is wanted, and the question about the existing marshalling call on the next line — and drop the attribution and the project number, which identify nothing useful.

**The two sample documents need thought rather than a substitution**, because both are read by the test suite:

- `samples/Sample.Demo/Documents/Events.d4` line 33 sets `FlowBreak` on a derived form group, and the group is named by a dotted path whose middle segment is the organization name. Replace that one segment with a neutral one and leave every other segment exactly as it is, so the tag stays a well-formed group name. It makes no difference to any form rendered from this repository either way: a group tag only has an effect when the group name matches the name the derivation generates, and the current name cannot match anything here, because the library whose name it is built from is not in this repository. Say that in the handoff, so nobody later reads the rename as a behaviour change.
- `samples/Sample.Shipping/Documents/RunTest.dfd` line 15 is a script action whose embedded C# loads a form by `Form('<library>', '<document>')`, where the library and application names are the organization's. Replace them with obviously generic placeholder names and change nothing else in the action: no reformatting, no re-encoding of the XML entities, and do not delete the action. Deleting it was considered and rejected — this document is the sample's own hand-run test runner, the action already cannot run here whatever the names say, and removing one of its actions is an editorial change to a sample that a privacy fix has no business making.

**The build property has no reader**, so remove it: delete the `<PublishUrl>` line from `src/windows/Dataphoria/Dataphoria.csproj`. It is a publish target for a deployment mechanism this project does not use (`GenerateManifests` is `false` in the same property group), nothing in the tree reads it, the project is not in `Dataphor.slnx`, and the net-spike harness compiles it from a generated wrapper that does not copy the property. The WS6 port of this project replaces the file anyway. Leave the other publish properties alone; none of them names anything that is not ours.

## Edge cases & interactions

- **Three test passes read the two sample documents**, and they are the verification for that half of the change: `ParserRoundTripCorpusTest` parses every `.d4` in the repository and round-trips it through the emitter, so it covers the `Events.d4` tag; `FormDocumentCorpusTest` reads every `.dfd` and `.dfdx` and checks it parses as the format its extension claims, which covers `RunTest.dfd`; and `SamplesCorpusTest` registers both sample libraries on servers of their own. `FormCustomizationTest` differences and re-merges every `.dfdx`, and neither edited document is a `.dfdx`, so it is unaffected — run it anyway, because it is cheap and it is the pass that would notice a document the BOP deserializer no longer likes.
- **`Sample.Demo` registers only its base script.** Its event script, which holds the tag being edited, is one of six that `SamplesCorpusTest` deliberately does not run — the fixture says so and lists them. So the tag edit is checked by the parser corpus, not by a server. Do not add a case to make it run; that is a different question and a different ticket.
- **Entity encoding in the `.dfd`.** The script action is one long attribute value with `&#xD;&#xA;` and `&quot;` throughout. Edit the two names inside it and let every other character stand; an XML tool that rewrites the file will re-encode the whole attribute and produce a diff nobody can review.
- **No migration-notes entry.** Nothing here is visible to an application, a deployment script or a custom C# extension: three comments, one tag in a sample library that is not registered by the product, one script action in a sample, and one unread build property. If the sample tag turns out to matter after all — it does not, for the reason above — say so in the handoff rather than adding an entry speculatively.
- **No new test.** There is no behaviour to characterize: the changes are comments, a sample metadata tag with no live consumer, a placeholder in a sample script and a dead build property. The existing corpus passes above are what hold the two document edits honest.
- **Formatting.** `CatalogStore.cs` and `Dataphoria.csproj` have a UTF-8 byte-order mark; `MetaData.cs`, `IntegrationNodes.cs` and `Events.d4` do not; `RunTest.dfd` is ASCII. All six use CRLF, and the source files use tabs. Preserve each file as it is and change only the lines named.
- **One more pass of the search afterwards.** When the six edits are in, repeat the case-insensitive search and confirm every remaining hit is one of the false-positive categories listed above. List the categories in the handoff so a later reviewer does not have to rediscover them.
