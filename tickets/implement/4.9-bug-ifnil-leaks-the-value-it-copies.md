## What happens

`IfNil(AValue, AReplacement)` returns its first argument unless that argument is nil, in which case it returns the second. It is an ordinary system operator, declared in `src/engine/DAE/Schema/SystemCatalog.d4` line 20 as `IfNil(const ANilableValue : generic, const AReplacementValue : generic) : generic` and implemented by `IfNilNode` in `src/engine/DAE/Runtime.Instructions/SystemNodes.cs` line 888.

The engine keeps a `Binary` or a `Graphic` value - the types an application uses for pictures, documents and attachments - in a *managed stream*, a block of memory the server owns and that nothing but an explicit release gives back. `IfNil` copies whichever argument it chose and returns the copy, and never releases the value it copied. Where that value was one the call owned - anything computed rather than read out of a variable - the original stream is orphaned for the life of the session. One stream per call.

The whole of the node's execution today is six lines:

```csharp
public override object InternalExecute(Program program)
{
    object result = Nodes[0].Execute(program);
    if (result == null)
        result = Nodes[1].Execute(program);
    return DataValue.CopyValue(program.ValueManager, result);
}
```

## Reproduced

A temporary fixture over the in-process engine, three cases, each a loop of 20 calls that reads the result afterwards and measures `Diagnostics.StreamCount()` before and after:

| Case | Streams left behind |
|---|---|
| `IfNil(Binary('0001'), Binary('0002'))` - a computed first argument | 20 |
| `IfNil(LNil, Binary('0002'))` where `LNil` is a nil `Binary` variable - the replacement path | 20 |
| `IfNil(LS, Binary('0002'))` where `LS` is a `Binary` variable holding a value | 0 |

Exactly one stream per call on both paths that choose a computed value, and nothing on the path that chooses a variable's value - which is the shape the fix must not start releasing. The fixture was removed again; *What to pin* below says what goes back in its place, in the fixture that owns this family of cases.

## Why the copy is there, and which of the two fixes to make

A value `IfNil` returns has to be one the caller owns, because the caller releases it. The two arguments are `const`, and whether the call owns a `const` argument's value is a property of the plan node that produced it, not of the modifier - the rule `bug-an-operator-argument-is-released-by-the-wrong-owner` established and [architecture/operand-ownership.md](../../docs/architecture/operand-ownership.md) records. A node that reads a variable, or a column of a row in one, *lends* the value it already holds; a node that computes one - a literal, a conversion, another call - produces one nothing else holds. So the copy is right for a lent value and wasteful for an owned one, and it is the owned case that leaks.

`IfNilNode` already has the answer to hand. It calls `base.DetermineDataType`, whose `const` branch asks each argument node to lend (`PlanNode.SetByReference`), and `PlanNode.ReturnsByReference` carries what each one said. Nothing reads that answer at run time.

Two fixes were weighed:

- **Copy, then release the original where the node gave rather than lent it.** This is the one to make. It is the single idiom every other consumer of a value in the engine already uses - `InstructionNodeBase.CleanupOperand`'s const branch, `ListSelectorNode.InternalExecute`, `ForEachNode` and `ListForEachNode` all read `ReturnsByReference` off the node and release only when it answers false - so the fix adds no new rule to the engine, it applies the existing one at a site that skipped it. The number of allocations is exactly today's, and what the caller receives does not change.
- **Return the value as it stands where the node owns it, and copy only a lent one.** Rejected. It saves one stream allocation and one copy per call on the computed path, but then `IfNilNode` is sometimes handing back a value it does not own, so it would have to answer `ReturnsByReference` for its own consumer - and which of its two arguments it chose is known per execution, where `ReturnsByReference` is settled once at compile time. There is no measurement behind the saving, and the common use of `IfNil` in the shipped D4 (`SystemCatalog.d4` lines 1102, 1112, 1114 and 1267) is over `String` and `Boolean`, where neither copy touches a stream at all.

The mismatch the second option runs into - an ownership that is per-execution against a `ReturnsByReference` that is per-compilation - is a tripwire, not work: it costs nothing today, because nothing in the engine needs to express it. Record it as a `NOTE:` at `IfNilNode` rather than filing it.

## The change, verified

Applied to `IfNilNode.InternalExecute` and run against the three cases above: all three at nought streams, and the neighbouring fixtures (`AssignmentValueOwnershipTest`, `ContainerValueOwnershipTest`, `BufferedOperatorColumnOwnershipTest`) and the two coverage scripts that exercise `IfNil` (`NilLibrary`, `_3VLProofs`) all still pass - 34 tests, Debug.

```csharp
public override object InternalExecute(Program program)
{
    PlanNode chosen = Nodes[0];
    object result = chosen.Execute(program);
    if (result == null)
    {
        chosen = Nodes[1];
        result = chosen.Execute(program);
    }
    object copy = DataValue.CopyValue(program.ValueManager, result);
    if (!chosen.ReturnsByReference)
        DataValue.DisposeValue(program.ValueManager, result);
    return copy;
}
```

Three things about it that are load-bearing rather than stylistic, and that the comment on it should say:

- **Copy before release, never the other way round.** Releasing the original first would leave the copy reading a stream the manager no longer knows about, which is the failure the `const` operand work met once already and which reports as `StreamID (n) not found`.
- **The node whose answer is read is the one left in `Nodes[index]` at run time, not the one the compiler asked.** `IfNilNode.DetermineDataType` may replace either argument node after `base.DetermineDataType` has asked it to lend: `Compiler.Upcast` is a no-op today (`USETYPEINHERITANCE` is off, `Compiler.cs` line 12044) and returns the node unchanged, but `Compiler.ConvertNode` genuinely wraps it in a conversion call. That is still correct, and for the reason the rule exists: a conversion node computes a new value from the one it was lent, its own `const` cleanup leaves the lent value alone, and it answers `ReturnsByReference` false - so the value `IfNilNode` sees is one it owns and must release.
- **Both halves of the nil case are safe.** `DataValue.CopyValue` and `DataValue.DisposeValue` both fall through to nothing for a null, so `IfNil(nil, nil)` needs no special case.

## What to pin

Cases in `tests/DAE.Server.Tests/AssignmentValueOwnershipTest.cs`, beside the four operand-ownership cases that already live there (`AConstOperandReleasesTheValueComputedForIt` onwards), using the fixture's own helpers and its `AssignmentCount` loop count:

- **The release.** One case with the two shapes the leak has, through `Assert.Multiple` and `AssertShapeLeavesNoStreams`, the way `AConstOperandReleasesTheValueComputedForIt` does it: a computed first argument, and a nil first argument with a computed replacement. Each asserts the result is still readable afterwards as well as the count, because a release without an independent copy would hand back a released stream and the count would balance all the same.
- **The loan.** One case passing a *variable* as the chosen argument, asserting both that the count balances and that the caller's variable is still readable afterwards. This is the case the wrong fix breaks, and it passes today.

The fixture's class `<summary>` is a running account of which rule each group of cases pins; add a sentence for these in the same voice, after the sentence about the four operand cases.
