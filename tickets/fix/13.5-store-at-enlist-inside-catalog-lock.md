description: When a table is first used inside an application transaction while a statement is already running (for example a script run through the D4 Execute operator), the engine creates the transaction's copy of the table while holding the catalog lock. It then waits for the catalog store's write lock, the order that the store-concurrency work forbids because it can deadlock, and a Debug build fails with an internal error.

## What happens

On a Debug build, after these statements, each run directly on a process:

```
create table Test { ID : Integer, key { ID } };
create table ATID { ID : Guid, key { } };
ATID := table { row { BeginApplicationTransaction() ID } };
JoinApplicationTransaction(ATID[].ID, false);
```

a nested script that is the first to reference `Test` in the AT fails:

```
Execute('begin var LCursor : cursor(typeof(Test)) := cursor(Test capabilities { navigable, updateable }); LCursor.Close(); end;');
```

with `RuntimeException: Runtime error: Internal Error: The catalog store's write transaction is beginning inside the catalog's lock.` Verified in the `engine-at-cursor-no-device` fix stage with a scratch in-process test, using the script's full cursor block. That any first reference does the same (for example `Execute('select Test where ID = 1;')`) is inferred from the stack below, not run.

## Cause

`ApplicationTransaction.AddTableVar` takes `lock (process.Catalog)` and, inside it, executes the `create table` statement for the AT's copy of the table. `DDLNode.InternalBeforeExecute` (added by `store-sqlite-concurrency`, K10) begins the catalog store's write transaction before every DDL node, precisely so that it is *not* begun inside the catalog lock. `ServerCatalogDeviceSession.BeginStoreTransactions` asserts that order in Debug builds. In Release the assertion is compiled out, and the session waits for the store's write lock while holding the catalog lock. That is the wait which deadlocks, until the busy timeout (error 130103), against another session that holds the store write lock and wants the catalog lock.

It fires only when a process transaction is open and the store has no transaction yet (`ServerCatalogDeviceSession.cs`, line 166). That is why the run needs a nested statement: when a batch runs directly, compilation happens before the batch's implicit transaction begins, so the store write autocommits. In the harness's `ApplicationTransactions` run, an earlier `create table` in the same outer statement has already opened the store transaction, so the assertion stays quiet there. This is a porting defect: the lazy store transaction and its assertion are new in 4.0, and the AT enlistment path predates them.

Does the AT copy's DDL write the store at all? Check before choosing a fix. AT objects may not be persisted, in which case the DDL only needs to skip `BeginStoreWriteTransaction`, for example when the plan is in the AT creation context (`plan.PushATCreationContext()` in `CopyTableVar`). If it does write, the store write transaction has to begin before `lock (process.Catalog)` in `ApplicationTransaction.AddTableVar` (and the similar `lock (process.Catalog)` sites in the same file, about lines 919, 992, 1388 and 1478).

## Expected behaviour

Enlisting a table in an application transaction from inside a running statement neither trips the assertion nor waits for the store's write lock while holding the catalog lock.

## Verification

- The reproduction above, as an in-process test in `tests/DAE.Server.Tests` (`InProcessTestFixture`), on a Debug build. A coverage script cannot reproduce it, because the harness's own outer statement opens the store transaction first.
- The concurrency checks that guard K10 still pass: `ConcurrentDDLTest` and `CatalogStoreConcurrencyTest`.
