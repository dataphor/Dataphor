## What happens

An operator parameter declared `var` gives the operator a slot that is an alias of the caller's: the caller's variable and the parameter name the same value, and whatever the operator leaves in the parameter is handed back to the caller's variable when the call returns. A body that assigns to such a parameter releases the value it displaced, which is right while the caller's variable owns that value - which is the ordinary case.

A `foreach` loop variable does **not** own its value. The loop lends its variable the row or element the iterator owns and goes on reading it. So when the caller passes its own loop variable to a `var` parameter, the operator's assignment releases a value the loop is still using, and the loop then reads a released one:

```
create operator ZFixup(var ARow : row { ID : Integer, B : Binary })
begin
	ARow := row { 9 ID, Binary('0009') B };
end;

var LR : row { ID : Integer, B : Binary };
foreach LR in cursor(table { row { 1 ID, Binary('00F1') B }, row { 2 ID, Binary('00F2') B }, key { ID } }) do
	ZFixup(var LR);
// "A nil was encountered where a value was expected" on the second row
```

Measured, not inferred, all on `modernization` at `ticket(implement): bug-a-loop-variable-stays-borrowed-after-the-loop`, through a throwaway case on `InProcessTestFixture` reading `Diagnostics.StreamCount()` either side of each script (added, run, removed):

| Shape | What happened |
|---|---|
| Loop over a cursor of two rows, body calls an operator that assigns its `var` row parameter | raises `A nil was encountered where a value was expected` on the second row |
| The same over a cursor of one row | no error, one value left behind - the loop has no second row to read |
| Loop over a list of `Binary`, body calls an operator that assigns its `var` parameter | raises `Runtime error: StreamID (6) not found` |
| A `foreach` *inside* the callee over the `var` parameter, caller looping over a list of `Binary` | raises `Runtime error: StreamID (12) not found` |
| Cursor of two rows, and of one row, where the operator only *reads* its `var` row parameter | balanced, no error |
| Cursor of one row where the operator assigns a *column* of its `var` row parameter | balanced, no error |
| The same calls with an ordinary variable as the argument rather than the caller's loop variable | balanced, no error |
| Loop over a list of `Integer`, body assigns its `var` parameter | balanced - only the values the engine has to release are affected |

The one-row cursor shape is quieter than the others only because a `Row` can be disposed twice without complaint; the list shape releases a stream twice and the stream manager reports it.

**Older than the loop work.** The release is `AssignmentNode`'s, and that line is untouched by the loop tickets - the shape has failed since `bug-assigning-a-binary-variable-leaks-its-stream` taught assignment to release what it replaces. The loop work added one more way to reach it: a `foreach` *inside* the callee over the `var` parameter releases the same value for the same reason, which before leaked instead and now raises `StreamID (n) not found`. Both are the one defect.

## Why the callee cannot tell

Which slots hold a value they do not own is a **compile-time** fact: the compiler marks the loop variable's symbol (`Symbol.IsBorrowed`) while it compiles the loop's body, and the assignment node reads that mark as it is compiled. An operator is compiled once, independently of its call sites, so the callee's parameter symbol carries no such mark however the caller passes its argument - and the run-time stack has no per-slot ownership bit to carry one either.

So there are two rules that are each right on their own, and nothing connects them:

- The architecture's `var` rule ([operand-ownership.md](../../docs/architecture/operand-ownership.md)): the callee's slot is an alias of the caller's, so the cleanup releases nothing and writes the slot's final value back to the caller.
- The slot rule ([value-lifetime.md](../../docs/architecture/value-lifetime.md)): a slot owns the value in it, so a write to it releases what it displaced - unless the compiler marked that slot as holding a value it does not own.

A `var` parameter is a slot of the first kind that the second rule treats as a slot of the second kind.

## What to work out

The question to settle is **where the fact that an operand's value is not the slot's to release has to live so that the callee can see it**, and the obvious candidates are worth weighing against each other rather than patching the assignment site:

- The caller tells the callee. `CallNode` knows the argument node (`StackReferenceNode`, by reference, at a known location) and the compiler knew whether that location was borrowed; one of the two could mark the operand slot so that writes inside the callee leave the value alone. This needs somewhere to put the mark that survives to run time, since `Symbol` is a compile-time structure, and it must be per call rather than per plan - the same operator may be called with a borrowed argument from one site and an owned one from another.
- The caller passes a copy. A `var` argument taken from a borrowed slot could be copied for the call and the write-back release the copy; the loop then keeps its own value. This costs a copy per such call and changes nothing the caller can see, but the copy has to be released on every exit path.
- The loop stops lending and starts owning - a borrowed slot holds a copy for the life of the loop. That removes the whole class, at a copy per iteration, and changes what the body of a loop may do to its variable; it is the biggest of the three and the one that would want a decision rather than a patch.

Note also that a call that *reads* a `var` parameter is already correct, so whatever is chosen must not cost anything on that path.

## What to pin

A case beside `AForEachOverAnOperandLeavesTheCallersValueAlone` in `tests/DAE.Server.Tests/AssignmentValueOwnershipTest.cs`, which already covers the three modifiers with an ordinary variable as the argument: the same three with the caller's own loop variable as the argument, over a cursor of at least two rows and over a list, asserting no error and the stream count back where it started. Two of the shapes raise today, which is this defect; one leaks.
