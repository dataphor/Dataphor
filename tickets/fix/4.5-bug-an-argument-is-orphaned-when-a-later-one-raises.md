## What is wrong

A call evaluates its arguments, runs the operator, and then cleans each argument up - releasing the value where the call owns it, writing it back where the operand was passed by reference. The cleanup lives in a `finally`, but **the arguments are evaluated before the `try` that `finally` belongs to**. So when evaluating argument 2 raises, nothing cleans up argument 1, and whatever argument 1 produced is orphaned: the engine holds large values such as `Binary` and `Graphic` in a stream the server owns, and an orphaned stream is given back only when the process ends.

The one site is the argument-evaluation prologue of the four execute shapes in `src/engine/DAE/Runtime.Instructions/InstructionNode.cs` - `UnaryInstructionNode`, `BinaryInstructionNode`, `TernaryInstructionNode` and `InstructionNode` - each of which reads

```
object argument1 = Nodes[0].Execute(program);
object argument2 = Nodes[1].Execute(program);
try { ... } finally { CleanupOperand(...); CleanupOperand(...); }
```

`InstructionNode`, the general shape, is also what a call of a user-declared operator runs through (`CallNode`), so this reaches ordinary D4 and not only built-in operators.

### Measured

Verified 2026-11-24 on the current `modernization` head, through a throwaway case on `tests/DAE.Server.Tests/AssignmentValueOwnershipTest.cs` (added, run, removed again - it is not in the tree) reading `Diagnostics.StreamCount()` either side of the script:

```
create operator ZProbeRaises() : Binary begin raise Error('probe'); end;
create operator ZProbeTwoConst(const AB : Binary, const AC : Binary) : Integer begin result := 0; end;
begin var LI : Integer := ZProbeTwoConst(Binary('0001'), ZProbeRaises()); end;
```

The script raises, as it should, and the server is holding **one stream more** afterwards than before - the `Binary('0001')` built for the first argument. Every repetition costs another.

This is older than the ownership work: before `bug-an-operator-argument-is-released-by-the-wrong-owner` a `const` argument's value was never released on *any* path, so the error path was no worse than the normal one. That ticket closed the normal path and left this one, which is why it is worth closing now rather than later: the normal path being right is what makes this the only shape in which a call still orphans an argument.

## Expected behaviour

A statement that raises while working out a call's arguments leaves the server holding no more streams than before the statement, exactly as a statement that raises inside the operator's body already does. Nothing else about the call changes: the caller's own variables keep their values, and the error the caller sees is the one the argument raised.

## What makes this more than moving two lines into the `try`

**A by-reference operand must not be written back when the call never happened.** `CleanupOperand`'s `Modifier.Var` branch pokes the value it is given into the caller's slot. On an argument-evaluation failure there is no callee value to write back, and `argumentValue` for an argument never evaluated is null - poking that into the caller's slot would destroy the caller's variable, turning a leak into data loss. So the cleanup that runs on an evaluation failure is not the same cleanup that runs after the call: it releases the values the call owns and leaves every by-reference operand alone.

**Only the arguments actually evaluated may be released.** A failure at argument 2 of 3 must release argument 1 and nothing else; releasing an unevaluated null is harmless today but the count of evaluated arguments is what the fix has to carry, not a guess.

**It is the hottest path in the engine.** Every operator call in every D4 statement runs one of these four shapes, so whatever the fix costs is paid per call. Measure it: `tests/DAE.Server.Tests/PerfBaselineTest.cs` runs the coverage corpus's timing scripts and is the instrument already in the tree.

## Edge cases & interactions

- **An operand whose node lends rather than gives.** A `const` operand given a variable is handed the stack slot's own value (`PlanNode.ReturnsByReference`), and that must not be released on the failure path any more than on the normal one. The rule is in [docs/architecture/value-lifetime.md](../../docs/architecture/value-lifetime.md); the failure path has to honour it, which argues for going through `CleanupOperand`'s own const test rather than releasing blindly.
- **`CallNode` pushes nothing until all arguments are evaluated**, so a failure in the prologue leaves the stack untouched and no operand slot exists to hand a value back from. The fix is entirely in the four execute shapes; `CleanupOperand` itself needs no new branch.
- **The `IsBreakable` window.** Two of the four shapes push a stack window inside the `try`. An argument-evaluation failure happens before that, so there is no window to pop either.
- **A `NOTE:` already sits on `CleanupOperand`** recording this and naming this ticket; remove it when the fix lands.
