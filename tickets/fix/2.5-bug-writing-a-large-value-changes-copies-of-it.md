## What happens

The engine keeps values too large to carry around inline - the two D4 types for them are `Binary` and `Graphic` - in a managed stream owned by the server. Copying such a value does not copy its bytes: the copy is a **reference** to the original's stream, and the two are meant to be separated the first time either one is written. That separation only works in one direction. Writing through the copy separates it and leaves the original alone, which is correct. **Writing through the original changes what every outstanding copy of it reads.**

So a routine that keeps a value aside before changing it - the obvious way to write an undo, a before-image or a comparison - finds that what it kept aside has changed too.

## The measurement

Verified 2026-11-23 against the current `modernization` head, at the level of the class itself, by the test named below. With one stream allocated and written, then two references taken from it, then a write through the source and a write through one of the references:

- the source reads back the value written through it - correct;
- the reference that was written reads back its own new value - correct;
- the **untouched** reference reads the source's **new** value, where it should read the value it was taken from. Expected `"This is the value for stream 1"`, got `"This is the new value for stream 1"`.

That third assertion is 3.1's own, from the diagnostic operator `TestStreamManager()`, so it is the record of what correct looks like rather than a new expectation.

## Root cause - one site

`ServerStreamManager.Change(ServerStream)`, `src/engine/DAE/Streams/ServerStreamManager.cs` line 438. Every write through a managed stream calls it first (`ServerStream.Write`, `WriteByte` and `SetLength` all do), and it is where the separation happens. It handles exactly one of the two cases:

- **The stream being written is a reference.** It gives that stream a provider stream of its own, copies the source's bytes into it, and takes the stream out of the source's reference list. This is the case that works.
- **The stream being written is a source that has references.** Nothing happens. The write then lands in the provider's stream, which is the very stream each reference is reading through - a reference's own stream is created as a cover over the source's, in `InternalOpen` - so every reference sees the new bytes.

The second case is the whole of the defect, and the information needed to detect it is already in hand at that point: `header.References` is non-empty.

Two shapes of fix are available and the ticket does not prescribe one. Either separate each reference from the source before the write lands, which is what the existing branch does for a single stream; or leave the provider's stream with the references and give the source a fresh one, which is the re-parenting `Deallocate` in the same file already performs when it hands a deallocated stream's provider entry to one of its references. The second does one copy regardless of how many references there are.

## How a D4 application reaches it

Inferred from the code rather than run, so this part is not verified and is worth confirming first:

- A reference is taken wherever the engine copies a stream-backed value - `DataValue.CopyNative` and `DataValue.CopyNativeAs` (`src/engine/DAE/Runtime.Data/DataValue.cs`, around lines 542 and 657) both call `StreamManager.Reference` when the value they are copying is a stream identifier, as does `Scalar.CopyNativeAs` (`src/engine/DAE/Runtime.Data/ScalarValue.cs`, around line 879). Assigning one `Binary` variable to another, putting one in a row, and passing one to an operator all go through that path.
- An in-place write on the original happens through a representation's write accessor - `MyPicture.Value := '<base64>'` - which reaches the setter of `Scalar.AsByteArray` (`ScalarValue.cs`, around line 659) and writes into the existing stream. That is the same setter `bug-binary-write-accessor-keeps-the-old-values-tail` is about, so the two meet in the same place from different directions.

What would confirm it: a D4 block that gives a `Binary` variable a value, assigns it to a second variable, writes a different value through the first variable's `Value` representation, and then reads the second variable. If the second variable has changed, this is reachable from the language and the severity is data corruption in ordinary use; if it has not, the copy path a variable assignment takes does something else and the defect is confined to callers of the class API.

## Expected behaviour

A copy of a stream-backed value reads the value it was taken from until something is written through that copy, whichever of the two is written first and however many copies are outstanding.

## Tests this owes

Its reproduction is **already in the tree and marked**: `ServerStreamManagerTest.WritingASourceAndOneOfItsTwoReferencesLeavesThreeDistinctValues` in `tests/DAE.Server.Tests/ServerStreamManagerTest.cs`, carrying 3.1's three assertions unchanged and `[Ignore]`d with this ticket's slug as the reason. Remove the `[Ignore]` with the fix; do not weaken the assertion.

The two tests beside it stay green meanwhile and the fix must keep them that way: `WritingThroughAReferenceLeavesTheSourceWithItsOwnValue` pins the direction that works, and `WritingASourceThatHasReferencesLeavesItReadingItsOwnNewValue` (added by the review of `debt-restore-stream-and-conveyor-tests`) pins the half of the ignored assertion that still holds - a source with a reference outstanding reads back its own write. That second one is the guard on the re-parenting shape of the fix, which hands the provider's stream to a reference and so has to leave the source's own open stream pointing somewhere.

If the D4 route above is confirmed, the fix also owes that D4 case as a coverage script assertion - `debt-streams-coverage` is the ticket that adds the script, and it already names this area.

## Compatibility

Fixing this changes what an existing application sees: a library that reads a copy after writing the original currently gets the new value and will get the old one. The old behaviour is not something an application could sensibly have been written around, but it is a visible change, so this needs a `docs/migration-notes.md` entry in the same commit.
