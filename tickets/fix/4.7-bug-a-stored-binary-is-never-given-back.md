## What happens

The engine keeps a value of either of its two large types - `Binary` and `Graphic`, the types an application uses for pictures, documents and attachments - in a *managed stream*: a block of memory the server owns, with a count of how many holders it has. `Diagnostics.StreamCount()` reports how many such streams the server is holding, and in a server with nothing running it is 0.

Writing one of those values into a table column raises that count by one, per row, and the server never gives it back while the table exists. Deleting the row does not. Updating the column takes out another one on top of the first. Only dropping the table returns them, all at once.

So an application that inserts a document, replaces it, and deletes the row has left the server holding three blocks of memory for a row that no longer exists, and will keep holding them until the table is dropped - in practice, until the server stops.

## Reproduction

Verified on 2026-11-24 against `modernization` at `b9d8ed93`, by running D4 through the coverage harness and reading `Diagnostics.StreamCount()` between statements, in a session with nothing else running. The numbers are the change in the count:

| D4 | streams | expected |
|---|---:|---:|
| `insert table { row { 1 ID, Binary('ABEiM0RVZnc=') B } } into T;` | +1 | 0 |
| then `delete T where ID = 1;` | +1 (unchanged) | 0 |
| ten such inserts in a `for` loop | +10 | 0 |
| then `delete T;` (all ten rows) | +10 (unchanged) | 0 |
| then `drop table T;` | back to 0 | 0 |
| `update T set { B := Binary('qrvM3Q==') } where ID = 1;` | +1 | 0 |
| the same insert inside `BeginTransaction(); ... RollbackTransaction();` | 0 | 0 |
| `insert (TOther where ID = 9) into T;` - the value read out of another table | 0 | 0 |
| a `Binary` read out of a table column into a variable | 0 | 0 |

The table in every row of that table is an ordinary one on the default in-memory device - `create table T { ID : Integer, B : Binary, key { ID } };` - and the same numbers come out for a `Graphic` column and for a table created `in System.Temp`.

Two lines of that table say where the boundary is. A value that arrives **already native** - read out of another table rather than built by a selector or held in a variable - costs nothing, so it is specifically the value that arrives *in a stream* whose stream is kept. And a rolled-back insert costs nothing, so whatever the rollback path does with the row it inserted is the thing the commit path is not doing.

The simplest script that shows it, runnable as-is through the in-process engine harness:

```
create table T { ID : Integer, B : Binary, key { ID } };
begin
	var LBefore : Integer := StreamCount();
	insert table { row { 1 ID, Binary('ABEiM0RVZnc=') B } } into T;
	delete T where ID = 1;
	if StreamCount() <> LBefore then
		raise Error('A row that was inserted and deleted left ' + ToString(StreamCount() - LBefore) + ' stream(s) behind.');
end;
```

## Expected behaviour

A table that holds a `Binary` or `Graphic` column stores the bytes; the stream the value arrived in is not the storage and must not be held once the insert or update has finished with it. Concretely, after a statement that inserts, updates or deletes rows, the server is holding exactly as many managed streams as it was holding before the statement - the same rule that now holds for assignment, for operator arguments and for leaving a block (`bug-assigning-a-binary-variable-leaks-its-stream`, `bug-an-operator-argument-is-released-by-the-wrong-owner`, `bug-an-error-inside-a-block-leaks-its-binary-values`). Reading such a column back must keep working and must keep costing no stream, and a copy of a stored value must still be independent of it.

Dropping the table must keep giving back whatever the table legitimately holds, so that fixing this cannot turn into a double release.

## Where to look

This is a `fix/` ticket: the reproduction above is solid and the root cause is not yet pinned. What is known from reading, and what to confirm:

- `MemoryDeviceSession.InternalInsertRow` (`src/engine/DAE/Device.Memory/MemoryDevice.cs`) calls `NativeTable.Insert(ServerProcess.ValueManager, row)` and nothing else: its whole transaction-logging body is inside `#if USEMEMORYDEVICETRANSACTIONS`, which no project defines (the block would not even compile - it still uses the old `ATable`/`ARow` parameter names). So the device itself logs nothing and the rollback that *does* release must be the engine's own undo, which is the asymmetry to explain first.
- `NativeTable.IndexInsert` builds the index key and data rows with `ValuesOwned = false` and fills them from `row.GetNativeValue(columnIndex)` - which for a stream-backed column is the stream identifier itself, not bytes - then hands them to the index as `NativeRow`s. Whether the index copies those values (and so takes out a reference of its own) or keeps the identifier it was given decides whether this is a leak at the insert or a value the stored row is holding. The `drop table` result above says the stored rows do hold stream identifiers, and the "a read out of a column costs no stream" result says reading one back does not reference it, and those two facts need reconciling before a fix is written.
- `InsertNode.InternalExecute` (`src/engine/DAE/Runtime.Instructions/TableNodes.cs`) disposes the source row in a `using`, so the *source* value looks accounted for; the delete and update paths in `NativeTable` are where to look for the half that never happens.

## Impact, and what not to do

An in-memory table is the engine's own storage for session tables, temporary tables and anything not mapped to a SQL device, so this is reachable by ordinary application D4 and not by a corner case. The cost is one block of memory per stored value per table lifetime, and a `Binary` is as large as whatever was put in it.

Do not "fix" it by making `StreamCount()` stop counting these, and do not weaken the balance assertions in `AssignmentValueOwnershipTest` or in the `StreamValues` coverage script - those are the instrument. The fix owes a reproduction test at the lowest layer that shows it; the script above is the language-level shape, and a `NativeTable`-level test is likely to be the sharper one once the site is known.

## How it was found

Writing the `StreamValues` coverage script (`debt-streams-coverage`). That script asserts the balance for variables, copies, copy-on-write, equality, a rolled-back transaction and nil, and it deliberately does **not** assert the balance for a committed insert: its row section drops its table before its closing assertion and names this ticket at the site, so that the gap is recorded rather than either failing the whole script or being written into it as an expectation. When this lands, that section is where the assertion belongs; see the comment above it in `tests/libraries/TestFramework.Coverage.Scripts/Documents/StreamValues.d4`.
