## What happens

```
create type Degrees
{
	representation Degrees { Degrees : Integer, Minutes : Integer, Seconds : Decimal },
	...
};
if not(Degrees(10, 5, 12.4) = Degrees(10, 5, 12.4)) then raise Error("eq");
```

fails with `CompilerException: Unknown identifier "right.Degrees".` The type is created and its selectors and property accessors work; only `=` fails.

Found by `test-triage-known-failures`. The coverage script `Types.Coordinate` fails with that error. Bisecting with scratch coverage scripts: the first 67 lines (the type `Degrees` and a selector and `.AsString` check) pass; adding line 69's `Degrees.AsString(…) = Degrees(10, 5, 12.4)`, or the single line above, fails. `right.Degrees` appears nowhere in the script: it is generated by the engine.

## Site

A type with one representation of several properties and no equality operator of its own gets a generated `iEqual` whose class is `System.CompoundScalarEqualNode` (`Compiler.cs`, about line 5280). `CompoundScalarEqualNode.DetermineDataType` (`src/engine/DAE/Runtime.Instructions/RowComparisonNodes.cs`, about lines 250–270) compiles `Compiler.BuildRowEqualExpression(plan, "left", "right", …)`, which refers to `left.<property>` and `right.<property>`. Under `USENAMEDROWVARIABLES` (defined at the top of that file) it pushes the left row as `new Symbol(Keywords.Left, …)` but the right row as `new Symbol(String.Empty, …)` (about line 261), so `right.<property>` cannot resolve. The two sibling nodes in the same file push `Keywords.Right` (`RowEqualNode` about line 75, and the node at about line 319).

## Is it a porting defect?

No. The file at tag `v3.1` has the same line and the same `#define USENAMEDROWVARIABLES`; the port changed nothing in it but its path. So `=` on such a type never compiled on 3.1 either. The fix makes something work that 3.1 rejected with an internal-looking compiler error; it removes no behaviour an application could rely on.

## Expected behaviour

`=` and `<>` on two values of a compound type compare them property by property, with nil handling as `BuildRowEqualExpression` already generates. `Types.Coordinate` then runs further.

## Edge cases & interactions

- A compound type whose property name equals the type name (`Degrees.Degrees` here) or a keyword: resolution of `right.Degrees` must find the property, not the type.
- Nested compound types (`Coordinate` has two `Degrees` properties): equality of the outer type calls the inner type's generated equality.
- The comparison (`?=`) and sort paths for compound types: check whether they share the defect; same file.
