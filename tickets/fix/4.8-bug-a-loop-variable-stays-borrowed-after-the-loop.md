## What is wrong

A stack slot normally owns the value in it, so an assignment releases the value it displaces (`Stack.PokeOwned`). A `foreach` loop variable is the exception: the loop *lends* it the row or element the iterator owns, and an assignment to it inside the loop body must release nothing. The compiler marks that slot for the exception - `plan.Symbols.SetIsBorrowed(...)`, four call sites in `src/engine/DAE/Compiling/Compiler.cs`, one per `foreach` form - and `AssignmentNode` reads the mark and uses a plain `Poke`.

The mark is never taken off. When the `foreach` names a variable the enclosing block declared (`foreach LB in ...`, as opposed to `foreach var LB in ...`), that variable's symbol stays borrowed for the rest of the block, so **every assignment to it after the loop has finished releases nothing** - and after the loop the slot does own its value again, because nothing else is pointing at it.

## Measured

On `modernization` at `6518e4a6`, on an in-process server, reading `Diagnostics.StreamCount()` either side of each script through a throwaway fixture on `InProcessTestFixture` (added, run, removed; not in the tree). The count must come back to where it started.

| script | streams left behind |
|---|---:|
| `begin var LB : Binary; LB := Binary('0002'); LB := Binary('0003'); end;` (control, no loop) | 0 |
| `begin var LB : Binary; foreach LB in { Binary('0001') } do begin end; LB := Binary('0002'); LB := Binary('0003'); end;` | 2 |
| `begin var LR : row { B : Binary }; foreach LR in cursor(table { row { Binary('0001') B } }) do begin end; LR := row { Binary('0002') B }; LR := row { Binary('0003') B }; end;` | 1 |

The control is the same two assignments with no loop in front of them, and it balances - so the loop is what makes the assignments after it stop releasing. The cursor row costs one stream per row rather than two because one of its two values is the list element that `bug-a-list-value-never-releases-its-elements` accounts for; the shape of the defect is the same on both branches, and the cursor form is the one an application is far more likely to write. Every further assignment to the variable costs another.

## Why it waits for the list ticket

Today the list branch of `foreach` leaves the loop variable's slot holding the list's last element - a value the list owns - and `bug-a-list-value-never-releases-its-elements` is what makes that slot nil on the way out, as the cursor branch already does. Unmark the symbol before that lands and the first assignment after a list `foreach` releases a value the list still points at, which is a second release rather than a leak. After it lands, the slot is nil at the end of every `foreach` form and an ordinary owned assignment is the right thing.

## Expected behaviour

Assignments to a variable after a `foreach` that used it release what they displace, exactly as they do for a variable no loop ever touched: both scripts in the table leave the count where they found it. Assignments to the loop variable *inside* the body still release nothing - that is what the mark is for, and the existing cases in `tests/DAE.Server.Tests/AssignmentValueOwnershipTest.cs` that loop and assign to the loop variable must keep passing.

## Where to look, and what is not yet settled

`Symbols.SetIsBorrowed(int offset)` (`src/engine/DAE/Compiling/Symbols.cs`) only sets the flag; there is no way to clear it or to read and restore it. The obvious correction is for each of the four `Compiler.cs` sites that marks a slot it did not push to restore the flag's previous value once the loop's body is compiled - but the four sites are four different `foreach` forms (statement, list-returning expression, table-returning expression, and the non-allocating variants of each), and only two of them have been measured here. What this ticket owes before it becomes an implement ticket: whether all four forms reach the defect, whether the slot really is nil after each of them once the list ticket has landed, and whether a borrowed mark is ever wanted beyond the loop for some other reason.

## A second arm at the same construct: the loop orphans whatever the variable already held

Found by reviewing `bug-a-list-value-never-releases-its-elements`, static (read from the code, not run): all three `foreach` branches lend the slot with the raw `Stack.Poke`, which does not release the value it displaces. So a loop over a variable that already has a value - `var LB : Binary := Binary('0001'); foreach LB in LL do ...` - orphans that first value as the loop starts, and nothing ever gives it back: the slot is nil by the time the scope ends. One stream per such loop, on the list branch (`ForEachNode` and `ListForEachNode`) and on the cursor branch (which pokes a row it allocated) alike.

It is the same construct and the same slot as the mark above, which is why it belongs here rather than in a ticket of its own: both are about a `foreach` borrowing a slot that is not its own, and whoever settles the mark has to settle what happens to the displaced value at the same time. The measured table above does not show it - every script there declares the loop variable without a value. What would confirm it: the same scripts with `var LB : Binary := Binary('0001');` in place of `var LB : Binary;`, which should leave one more stream behind than the table says. One thing to budget for either way: the list branch of `foreach` is written out three times - `ForEachNode` in `src/engine/DAE/Runtime.Instructions/ImperativeNodes.cs`, and `ListForEachNode` and `TableForEachNode` in `src/engine/DAE/Runtime.Instructions/ListNodes.cs` - as the same forty lines with the same slot handling, so every change to how a loop borrows its variable has to be made in three places and kept in step. If this ticket ends up changing all three, extracting the shell first is probably cheaper than editing it three times.

Two shapes a fix could take, for whoever picks this up: release the displaced value before lending (`PokeOwned` with the element would be wrong, because the element is not the slot's to own - it would have to be an explicit release followed by a plain `Poke`), or refuse to lend into a slot that is not nil and copy instead. The first keeps the lending model and costs one release per loop; the second costs a copy per iteration.

## How this was found

Probing `bug-a-list-value-never-releases-its-elements`: assigning twice to a list loop variable after the loop left two streams behind, and the same two assignments with no loop left none. The cursor form was then measured to check whether lists were the cause; they are not.
