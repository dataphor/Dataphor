## What happens

```
create table Test { ID : Integer, key { ID } };
create table ATID { ID : Guid, key { } };
ATID := table { row { BeginApplicationTransaction() ID } };
JoinApplicationTransaction(ATID[].ID, false);
begin
	var LCursor : cursor(typeof(Test)) := cursor(Test capabilities { navigable, updateable });
	try
		LCursor.Insert(row { 1 ID });
	finally
		LCursor.Close();
	end;
end;
```

fails with `RuntimeException: Device "<no device>" does not support retrieval for the table variable "General.Test".`

Found by `test-triage-known-failures`. The coverage script `ApplicationTransactions` (707 lines) fails with it at its first test. Bisecting with scratch coverage scripts: the first 29 lines (above, plus `LeaveApplicationTransaction()`) fail the same way; the script's second section, an `insert` statement into `Test` inside a joined application transaction followed by an `exists` check (lines 58–72), passes. So the failing path is the cursor, not application transactions as a whole.

## Not the harness

The legacy test was ignored with "Doesn't work through ExecuteScript" (the harness, like the legacy test, runs each script through the D4 `ExecuteScript` operator, nested inside one statement). A temporary harness switch that ran the script's text directly on the process (batch by batch, as Dataphoria does) gave the same error, so the site is in the engine.

## Site

The error is thrown by `BaseTableVarNode.InternalExecute` (`src/engine/DAE/Runtime.Instructions/TableNodes.cs`, about line 1879), which runs only when a table variable's node was not handed to a device: `DetermineDevice` (about line 1828) never set `_device`. Inside a joined application transaction, a table reference is redirected to the transaction's copy of the table (`src/engine/DAE/Device.ApplicationTransaction/`). For an `insert` statement that works; for the cursor's plan, some node in the redirected tree is executed directly with no device. Which node, and why the cursor's compile path skips device determination for it, is the fix stage's question.

## Is it a porting defect?

Probably not. The application-transaction device and the cursor and table nodes are unchanged since tag `v3.1` apart from one commit that removed compiler warnings (4 lines), and the legacy test was ignored from 2007 on. The presumption of the plan (D2) is still a porting defect until the fix stage shows the cause does not depend on anything the port changed (the store, the runtime, threading).

## Expected behaviour

A cursor opened on a table inside a joined application transaction reads and writes the transaction's copy: the insert goes to the transaction, `exists (Test)` is false after `LeaveApplicationTransaction()` and true again after rejoining, as the script's assertions say.

## Edge cases & interactions

- `StreamAllocation`, once its text is repaired (see `test-pre-3-1-scripts-policy`), runs every script of the library through `Execute`, including `ApplicationTransactions`, and fails with this same error; no separate cause.
- `RemoteATOperatorEvaluation` and `TestNetworkApplicationTransactions` pass; read them for what application-transaction paths already work.
- Later sections of `ApplicationTransactions` (update and delete enlistment, commit and rollback, operators evaluated in the transaction) are unreached; after the fix, re-point the manifest entry at each next cause or flip it to `pass`.
