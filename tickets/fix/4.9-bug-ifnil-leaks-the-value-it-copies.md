## What happens

`IfNil(AValue, AReplacement)` returns its first argument unless that argument is nil, in which case it returns the second. It is an ordinary system operator, declared in `src/engine/DAE/Schema/SystemCatalog.d4` as `IfNil(const ANilableValue : generic, const AReplacementValue : generic) : generic` and implemented by `IfNilNode` in `src/engine/DAE/Runtime.Instructions/SystemNodes.cs`.

The engine keeps a `Binary` or a `Graphic` value - the types an application uses for pictures, documents and attachments - in a *managed stream*, a block of memory the server owns. `IfNil` makes a copy of whichever argument it chose and returns the copy, and never releases the value it copied. Where that value was one the call owned - anything computed rather than read out of a variable - the original stream is orphaned for the life of the session. One stream per call.

**Measured, not inferred.** A temporary case in `tests/DAE.Server.Tests/AssignmentValueOwnershipTest.cs` called `IfNil(<an operator returning Binary>, Binary('0002'))` twenty times in a loop, reading the result each time, and asserted that `Diagnostics.StreamCount()` was back where it started: it finished 20 streams higher - exactly one per call. The case was removed again; `## What to pin` below says what to put back.

## Why the copy is there, and why that is the question

A value that `IfNil` returns has to be one the caller owns, because the caller will release it. The two arguments are `const`, and whether the call owns a `const` argument's value is a property of the plan node that produced it, not of the modifier - the rule `bug-an-operator-argument-is-released-by-the-wrong-owner` established and [architecture/value-lifetime.md](../../docs/architecture/value-lifetime.md) records. A node that reads a variable, or a column of a row in one, *lends* the value it already holds; a node that computes one - a literal, a conversion, another call - produces one nothing else holds. So the copy is right for a lent value and wasteful for an owned one, and it is the owned case that leaks.

`IfNilNode` already has what it needs to tell them apart: it calls `base.DetermineDataType`, so the const-operand rule asks each argument node whether it will lend (`PlanNode.SetByReference`), and `PlanNode.ReturnsByReference` carries the answer. Nothing reads that answer at run time.

That leaves a choice the fix has to make deliberately, because the two are not equivalent:

- **Copy, then release the original where the node gave rather than lent it.** Smallest change, same allocations as today, no change to what the caller receives.
- **Return the value as it stands where the node owns it, and copy only a lent one.** Saves a stream allocation and a copy on what is the common case, but then `IfNilNode` is sometimes handing back a value it does not own, so it has to answer `ReturnsByReference` for its own consumer - and the shape of that answer is per-execution, which `ReturnsByReference` is not: it is settled at compile time.

The second is the better-performing and the harder one, and the mismatch between a per-execution ownership and a compile-time `ReturnsByReference` is worth settling before it is reached again.

## Scope

`IfNilNode` is the one node found with this shape. The other plan nodes that derive from `InstructionNodeBase` directly rather than through one of the arity shapes - `ExistsNode`, `TableToListNode` and the `TableNode` family - were read and each disposes what it opens. The arity shapes themselves (`UnaryInstructionNode` through `InstructionNode`) go through `InstructionNodeBase.CleanupOperand`, which is where the operand rule lives; `IfNilNode` overrides `InternalExecute` and so never reaches it.

Whether the class is larger than one node was not established. The generalisation worth weighing while fixing this: a test that calls every system operator whose signature admits a `Binary` and asserts the stream count comes back, which would cover this whole family at once rather than one node at a time.

## What to pin

A case in `tests/DAE.Server.Tests/AssignmentValueOwnershipTest.cs`, beside the operand-ownership cases that already live there, using the fixture's own `AssertScriptLeavesNoStreams`: `IfNil` over a computed `Binary` in a loop leaves the stream count where it found it, and the value it returns is still readable afterwards. Both halves matter - releasing the original without the copy being independent would return a released stream, which is the failure the `const` work already met once.

The nil path needs the same case with the first argument nil, so the replacement value's ownership is covered too, and a case passing a *variable* as the chosen argument, which must leave the caller's variable readable - that is the one the wrong fix breaks.
