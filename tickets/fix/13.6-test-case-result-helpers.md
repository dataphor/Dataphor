## What happens

`Transaction.Atomicity.TestDAE` (through the step script `Transaction.Atomicity.Run` it runs) and `Transaction.Isolation.Run` fail at compile time with `Unknown identifier "CurrentCaseItems"`. Both use a table `CurrentCaseItems` (`delete CurrentCaseItems;` at the start, `select CurrentCaseItems;` at the end) and an operator `RaiseCurrentCaseItem(<case name> : String, <passed> : Boolean, <message> : String)`, called 11 times in `Run` and 3 times in `Isolation.Run`.

Neither is defined anywhere: not in any `.d4` or `.cs` file of the repository, and not at tag `v3.1` or in the 2008 initial commit (`git log -S CurrentCaseItems` finds only these scripts). The only trace is a comment in `tests/libraries/TestFramework.Coverage.Devices/Documents/Logic.d4` ("Used by the RunCurrentCaseItem to rebuild the test tables …"), from a case-tracking form framework (`TestFramework.Coverage`'s `Cases` forms) that recorded results in a table for a person to read. So these scripts never ran in this repository's history. Not a porting defect: the test libraries are missing a piece.

## Decision: define the two in the helper library

Define both in `TestFramework.Coverage.Base` (the helper library the coverage template registers), not in the scripts (never edit a coverage script to make it pass):

- `CurrentCaseItems`: a table in the library's default device `Temp`, with columns `Name : String`, `Passed : Boolean`, `Message : String`, key `{ Name, Message }`. A persistent table, not a session table: a library operator cannot reference a session table (tried: `Object "…RaiseCurrentCaseItem…" in library "General" cannot reference object "Object_…" because it is not contained within a library.`).
- `RaiseCurrentCaseItem(const AName : String, const APassed : Boolean, const AMessage : String)`: inserts the row, then raises `Error(AName + ": " + AMessage)` when `APassed` is false. The name says "raise", the callers in `Run` call it only on failure with `false`, and `Isolation.Run` calls it once per case with `<expected> = <observed>` as the flag; raising on false turns each failed case into a script failure the harness can see. Rejected: recording only (a failed case would leave the script green, since `Run`'s closing `if exists CurrentCaseItems then raise …` is commented out of the script).

## What the planning run observed with these definitions (scratch scripts, since removed)

- `Transaction.Atomicity.TestDAE` with the two defined: **passes**.
- `Transaction.Isolation.Run` with the two defined: fails at its first case, `Lost Update (Browse, Browse): LostUpdate did not behave properly with Browse, Browse as Isolation settings.` That case starts two processes; the first updates the row and sleeps 1 s before committing, the second (after 400 ms) updates the same row with a 200 ms timeout, and the script expects the second to fail. On the memory device (`System.Temp`, where the script's table goes) it did not. The memory device does no row locking of its own (`bug-memory-device-concurrent-access`, backlog, which says 3.1 behaved the same), and the script's isolation expectations may assume a device that locks. The script is also timing-based (`Sleep(400)`, a 200 ms timeout).

## Expected outcome

- `Transaction.Atomicity.TestDAE` → `pass`. Run it at least three times in full runs; it uses only the memory device.
- `Transaction.Isolation.Run`: diagnose far enough to name the cause of the first failing case. If it is the memory device's missing locking, add the script as an arm of `bug-memory-device-concurrent-access` and point the manifest entry at it; if it is a defect elsewhere, file a ticket for it. If it varies between identical runs, the entry is `unstable` (with the evidence). Do not loosen the script's timing.
- The `*MSSQL*` variants stay with `feat-ws7-devices-and-libraries`; they now get past the missing helpers when a SQL Server device exists.

## Edge cases & interactions

- `Transaction.Atomicity.Run` is a `fragment` entry after `test-triage-known-failures` (this ticket's prereq), so its standalone error, which changes from `CurrentCaseItems` to the missing `ListIntegerTestTableOne`, does not matter.
- `CurrentCaseItems` is a database table shared by every session of a server: each coverage case runs on its own server copied from the template, so cases cannot see each other's rows. Rows left by a run stay in that server's copy only.
- `Run` starts with `delete CurrentCaseItems;` while a case's own rows are inserted inside `try … commit` blocks some of which fail by design: an error raised by `RaiseCurrentCaseItem` inside such a block must still reach the harness (check that no `try … except` in `Run` or `Isolation.Run` swallows it).
- Registering the helper library is part of the template; if the new D4 fails to compile, every coverage case fails with the template error, which is the check that the definitions are right.
- No migration note: test libraries only.
