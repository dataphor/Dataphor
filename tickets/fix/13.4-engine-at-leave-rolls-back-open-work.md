## What happens

With `engine-at-cursor-no-device` fixed (without it, the script stops earlier, at line 20), the coverage script `ApplicationTransactions` fails at line 41 with `Application Transaction read is not repeatable.` The minimal form, run as the harness runs scripts (nested in one statement, through `Execute('…')` or `ExecuteScript('Coverage.Scripts', …)`):

```
create table Test { ID : Integer, key { ID } };
create table ATID { ID : Guid, key { } };
ATID := table { row { BeginApplicationTransaction() ID } };
JoinApplicationTransaction(ATID[].ID, false);
insert row { 1 ID } into Test;
if not exists (Test) then raise Error("A");      // passes: the row is in the AT
LeaveApplicationTransaction();
if exists (Test) then raise Error("C");          // passes: the real table is untouched
JoinApplicationTransaction(ATID[].ID, false);
if not exists (Test) then raise Error("D");      // FAILS nested: the AT copy is empty again
```

Verified in the `engine-at-cursor-no-device` fix stage with a scratch in-process test. The same text run batch by batch on the process (`IServerProcess.ExecuteScript`, as Dataphoria runs a script) passes. So does the whole 707-line `ApplicationTransactions` script, once the cursor fix is in. The row loss does not depend on cursors: a plain `insert` statement loses its row the same way.

## Likely mechanism (static, not traced)

`ApplicationTransactionUtility.LeaveApplicationTransaction` (`ApplicationTransaction.cs`, about line 150) calls `process.DeviceDisconnect(transaction.Device)`. Disconnecting disposes the process's `ApplicationTransactionDeviceSession`, and its `Dispose` (about line 2230) calls `EnsureTransactionsRolledback()`. That rolls back the session's open transactions and drops the AT operations recorded in them. Run batch by batch, each batch's implicit transaction has committed the insert before `LeaveApplicationTransaction()` runs. Nested in one statement, the outer statement's transaction is still open, so leaving discards the work. To confirm, break in `ApplicationTransactionDeviceSession.InternalRollbackTransaction` during the nested run.

One observation does not fit cleanly: the same text run batch by batch after an explicit `BeginTransaction();` passed, although that should also leave the insert uncommitted at the leave. Find out why before deciding, because it decides whether "work done inside an open transaction is discarded on leave" is the real rule.

## Is it a porting defect?

Probably not. The legacy NUnit test for this script was ignored from 2007 with "Doesn't work through ExecuteScript", and the script's header says "All batches in this script must run on the same process, i.e. they must be run as a whole script". Both suggest the authors knew the script depends on batch boundaries. The leave/dispose code is unchanged since `v3.1`. Under plan decision D2 it is still presumed a porting defect until the mechanism above is confirmed.

## The decision this ticket has to make

- **Harness (recommended if the mechanism is confirmed and is legacy behaviour):** let a manifest entry ask for its script to run batch by batch on the test process, as Dataphoria runs it, instead of nested in `ExecuteScript`. Document the option on `CoverageManifest`, use it for `ApplicationTransactions`, and flip that entry to `pass`. This changes no engine behaviour.
- **Engine:** if leaving an AT is meant to keep the work done in it, silently discarding that work when a process transaction is open is a data-loss defect. Changing it changes D4 behaviour that applications may rely on (when an AT's changes become durable relative to process transactions). Under the project rules that is a compatibility question for `blocked/`, with proposed wording. It is not something to change inside this ticket.

The harness option does not stop the engine question from being raised later. If you take it, record the engine behaviour as a `NOTE:` at `LeaveApplicationTransaction`: leaving inside an open process transaction discards the AT work done in that transaction.

## Edge cases & interactions

- `StreamAllocation` runs every script of the library through `Execute`, nested. Once its text is repaired (`test-pre-3-1-scripts-policy`), it will reach `ApplicationTransactions` and fail this way, whichever option is taken here, unless the engine changes.
- `RemoteATOperatorEvaluation` and `TestNetworkApplicationTransactions` pass nested today; they do not leave and rejoin.
- The rest of `ApplicationTransactions` (update and delete enlistment, commit and rollback, operators evaluated in the AT) passed when the script ran batch by batch with the cursor fix. Nested, nothing after line 41 has been observed.
