## What happens

The engine keeps values too large to carry around inline - the two D4 types for them are `Binary` and `Graphic` - in a managed stream owned by the server, and releases a variable's stream when the variable leaves scope. `Diagnostics.StreamCount()` reports how many of those streams the server is holding; with nothing running it is 0.

Leaving a scope **normally** releases them. Leaving it because of an **error** does not. A D4 block that declares a `Binary` or `Graphic` variable, gives it a value, and then raises leaves that value's stream held for the life of the session - whether the error escapes to the client or is caught by a D4 `try ... except` a few lines later.

Failed requests are ordinary in a running server: a constraint violation, a bad argument, a lock timeout. Each one that happened to be holding a picture or a document in a local variable costs the server that value's bytes, permanently, until it is restarted.

## The measurement

Verified 2026-11-23 against the current `modernization` head, through a throwaway NUnit fixture on `InProcessTestFixture` that read `Diagnostics.StreamCount()` between D4 statements (built, run, then removed again; the fixture is not in the tree), starting from a server holding 0 streams.

- `begin var LB : Binary := Binary('0001'); raise Error('boom'); end;` - the error escaping to the caller - leaves **1** stream held.
- The same block wrapped in a D4 `try ... except on E : Error do begin end; end` leaves **1** stream held.
- The same block without the `raise` leaves **0**, which is the behaviour this ticket wants on the error path too.

## Where it comes from

A block's variables are released by `DeallocateVariableNode` statements that the compiler puts in the block, and an error skips the rest of the block, so those statements never run. The frame itself is popped by `FrameNode.InternalExecute` (`src/engine/DAE/Runtime.Instructions/ImperativeNodes.cs`, around line 123) from a `finally`, so it is popped on both paths - but `Stack.PopFrame` (`src/engine/DAE/Stack.cs`, around line 166) only nulls the slots and lowers the count. Nothing disposes what they held.

This is a different site from `bug-assigning-a-binary-variable-leaks-its-stream`, which is about a slot being **overwritten** rather than **discarded**, and the two fixes do not overlap. It waits on that ticket because that one writes down the ownership rule - "the value in a stack slot is owned by that slot", and one helper that every site which removes a value from a slot goes through - and this fix should be the same rule applied to the discard path rather than a second, differently-shaped answer.

## What a fix has to be careful about

Not every slot a frame pops owns its value, and two things in the engine already dispose slot values, so a blanket "`PopFrame` disposes everything it pops" is not obviously safe and should be established rather than assumed:

- `DeallocateVariableNode` disposes a slot's value **without nulling the slot**, so on the normal path the slot still holds the value it just disposed when the frame is popped. Disposing again there would be a double free.
- Operator arguments are pushed as stack slots too, and `InstructionNode.CleanupOperand` owns their disposal - a `const`/`in` argument is disposed there and a `var` argument is an alias of the caller's slot, which must not be disposed at all. Those slots live in the callee's stack *window* rather than in a frame, and `PopWindow` is a separate method from `PopFrame`, but whether that separation holds on every path is the thing to check.

So the shape of the fix is the open question: dispose at the frame pop, or make the error path run the deallocations it skipped, or null the slot where it is already disposed so that a disposing pop is safe. Whichever it is, the same question exists for `PopWindow` and for a program torn down while a frame is still live, and the answer should cover all of them rather than one.

## Expected behaviour

In a session with nothing else running, `Diagnostics.StreamCount()` comes back to the value it had before a block that declared `Binary` or `Graphic` variables, whether that block ended normally, raised, or had its error caught by a D4 `try ... except`. Reading any variable still in scope after a caught error still gives its value.

## Tests

Its reproduction, at the engine level: a fixture on `InProcessTestFixture` that reads `StreamCount()` around the two scripts in the measurement above, because the assertion is arithmetic on an exact number. `bug-assigning-a-binary-variable-leaks-its-stream` adds a fixture over the same instrument; these cases belong beside it rather than in a second file of their own.

`tests/DAE.Server.Tests/DAE.Server.Tests.csproj` lists its sources explicitly in a `<Compile Include>` item group - a new file not added there compiles into nothing and NUnit discovers no tests, with no error.

## Compatibility

Nothing an application can see changes except the engine's memory use. A change to a public member of `Stack` - which a custom C# extension could be using - needs an entry in `docs/migration-notes.md` in the same commit.

The fix pass on `bug-assigning-a-binary-variable-leaks-its-stream`, which found this while measuring that one's error paths. The two share an instrument and an invariant but not a site.
