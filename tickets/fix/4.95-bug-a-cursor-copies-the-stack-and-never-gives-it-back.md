## What is wrong

`Cursor`'s constructor (`src/engine/DAE/Runtime.Data/CursorValue.cs`) calls `SnapshotContext`, which walks the whole current stack window and pushes `DataValue.CopyValue(...)` of every slot onto a private stack it keeps in `_context`:

```csharp
_context = new Stack(program.Stack.MaxStackDepth, program.Stack.MaxCallDepth);
_context.PushWindow(0);
for (int index = program.Stack.Count - 1; index >= 0; index--)
    _context.Push(DataValue.CopyValue(program.ValueManager, program.Stack.Peek(index)));
```

A copy of a stream-backed value - a `Binary` or a `Graphic`, and a row or list holding one - is a new stream the server has to be told to release. `Cursor.Dispose` never releases them; it does `_context = null` and nothing else. So **one stream per stream-backed value in scope, per cursor opened, held until the session ends.**

Every cursor pays this, not just a `foreach`: the snapshot is swapped in and out around each cursor operation (`SwitchContext`, which `CursorNodes.cs` calls in pairs around `Next`, `Prior`, `Select`, `Fetch` and the rest), so an explicit D4 cursor costs the same as the implicit one a `foreach` over a table opens.

This was found while measuring `bug-a-loop-variable-stays-borrowed-after-the-loop`, whose cursor-branch numbers it was inflating; it is a different site and a different root cause, which is why it is its own ticket. It is nobody's prerequisite: the loop-variable ticket is written so that its reproduction does not depend on this one landing.

## Measured

On `modernization` at `42383e93`, in-process server, reading `Diagnostics.StreamCount()` either side of each script through a throwaway fixture on `InProcessTestFixture` (added, run, removed; not in the tree). The loop variable in every row below is the allocating form (`foreach var LR in ...`), so the loop's own slot starts nil and the loop-variable defect is out of the picture; the cursor sources have no `Binary` column of their own, so the only stream-backed values anywhere are the variables named.

| script | streams left behind |
|---|---:|
| `begin var LB : Binary := Binary('00FF'); end;` (control, no cursor) | 0 |
| `begin foreach var LR in cursor(table { row { 1 ID } }) do begin end; end;` (control, no stream-backed variable) | 0 |
| one `Binary` variable declared **before** the loop | 1 |
| three `Binary` variables declared before the loop | 3 |
| one `Binary` variable declared **after** the loop | 0 |
| one `Binary` variable, then **two** cursor loops | 2 |
| one variable holding a `row { B : Binary }`, declared before the loop | 1 |
| one `Binary` variable, loop over a stored table rather than a table selector | 1 |
| one `Binary` variable, `foreach var LR in table { row { 1 ID } }` with no explicit `cursor(...)` | 1 |

The pattern is exactly the snapshot: a variable declared after the cursor opened is not on the stack to be copied and costs nothing; two cursors cost two copies; a bare table source costs the same as an explicit `cursor(...)`, because the compiler wraps it in a cursor definition either way.

## What this ticket owes before it becomes an implement ticket

The leak is certain and the site is named. What is not settled is how to give the copies back safely, and that is the research:

- **Does the snapshot need to be a copy at all?** Establish what the snapshot is for before changing how it is released - `SwitchContext` makes the cursor's plan run against the stack as it was when the cursor opened, so the copy is presumably isolation from later changes to those variables. If that is right, the fix is to release the copies rather than to stop making them.
- **What does `_context` hold at dispose time?** `SwitchContext` *swaps* `_context` with the program's live stack, so releasing `_context` blindly in `Dispose` would release the program's own values if a switch were ever left unbalanced. The pairs in `CursorNodes.cs` and in the three `foreach` nodes all look balanced through `try`/`finally`, but that has to be checked rather than assumed, and the release wants a shape that cannot do the wrong thing if one is not - `Stack.ReleaseAbove`, which the scope nodes use, releases above a recorded depth and nulls as it goes.
- **Which value manager releases them, and is it still alive?** `Dispose` disposes `_table` before it drops `_context`, and the value manager reachable today is `_table.Program` - so the release has to happen before the table goes, or the manager has to be captured when the snapshot is taken.
- **Does anything hand a snapshot value out?** A value copied into the snapshot and then poked back onto the program's stack during a switch would be released twice. Trace what the cursor's plan can do with a slot it reads from the snapshot.

## Expected behaviour

Opening and closing a cursor leaves the stream count where it found it, whatever the variables in scope are holding: every row in the table above comes back to 0.

## Tests

The reproduction belongs with the other ownership cases, in `tests/DAE.Server.Tests/AssignmentValueOwnershipTest.cs` - one case: a block that declares a stream-backed variable, opens a cursor over a source with no stream-backed column of its own, and leaves the count where it found it. More than one variable, so a per-variable regression reports a count rather than an off-by-one. No new D4 coverage block: the shape is the same engine path and one case at the lowest layer that shows it is enough.

Watch for an interaction when this lands: the cursor-branch case in `bug-a-loop-variable-stays-borrowed-after-the-loop` is written as a control-versus-case comparison precisely so that it keeps passing both before and after this ticket, but re-run that fixture and confirm it.
