## What happens

`SetObjectOwner('<table>', '<user>')` fails with `DataphorException: constraint failed  UNIQUE constraint failed: DAERights.Name` on the SQLite catalog store.

Found by `test-triage-known-failures`. The coverage script `SecurityLibrary` (run with implicit transactions off, as its manifest entry says) fails with that error. Bisecting the script by prefixes as scratch coverage scripts: lines 1–107 pass, lines 1–109 fail. The statement in between is line 108:

```
create table TestOwnedTable { ID : Integer };          // line 104
...
SetObjectOwner('TestOwnedTable', 'TestUser');           // line 108
```

The error text has no D4 locator because it comes from the store's SQL statement, not from D4.

## Site

`CatalogStore.SetCatalogObjectOwner` (`src/engine/DAE/Device.Catalog/CatalogStore.cs`, about line 2529) changes the owner of each of the object's rights by opening an updatable cursor on `IDX_DAERights_Catalog_Object_ID` and calling `Update()` for each row. That index is not unique: a table has one `DAERights` row per right (select, insert, update, delete, alter, drop, …), all with the same `Catalog_Object_ID`. `DAERights`' primary key is `Name` (`src/engine/Store.SQLite/SystemStoreCatalog.sql`, `PK_DAERights`).

`SQLStoreCursor` takes `_key` from the columns of the index it was opened on (`SQLStoreCursor.cs` constructor, about line 30). `InternalUpdate` (about line 778) passes that key to `SQLStoreConnection.PerformUpdate` → `GenerateUpdateStatement` (`SQLStoreConnection.cs`, about line 408), whose `where` clause is built from `_key`. So the statement is `update DAERights set Name = '<this right>', Owner_User_ID = …, Catalog_Object_ID = n, … where Catalog_Object_ID = n`, which writes this right's name into every right of the object, and the second row collides on the primary key. `InternalDelete` → `GenerateDeleteStatement` uses the same key, so a delete through a cursor on a non-unique index would delete every row sharing the value, and the nested-transaction undo log (`LogUpdate`, `LogDelete`) generates its inverse statements from the same key.

## Is it a porting defect?

Yes, by the evidence. The 3.1 catalog store was SQL Server Compact, whose cursor overrode `InternalUpdate` with a positioned update on the open result set (`Dataphor/DAE.SQLCE/SQLCEStoreCursor.cs:133` at tag `v3.1`), so the index's key never reached a `where` clause. The SQLite store that replaced it (plan decision D3) uses the generic `SQLStoreCursor` path, where `SupportsUpdatableCursor` is false and every update and delete becomes a keyed statement. `SetCatalogObjectOwner` itself is unchanged since 3.1.

## Expected behaviour

An update or delete through a store cursor changes exactly the row the cursor is on, whatever index the cursor was opened on: the statement's `where` clause names the table's primary key (or every column, for a table without one), from the row's current values. The undo log's inverse statements identify rows the same way. `SetObjectOwner` on a table, operator, type or any other catalog object with several rights then succeeds, and every right's owner changes.

## Edge cases & interactions

- Every other caller that updates or deletes through a cursor opened on a non-unique index (`OpenMatchedCursor(…, true, …)` / `OpenRangedCursor(…, true, …)` in `CatalogStore.cs`) has the same defect; list them and confirm each is covered by the fix at the cursor, not patched one by one.
- An update that changes primary-key columns: the `where` clause must use the old values (`_currentRow`), the `set` clause the new ones.
- `bug-store-nested-rollback-keeps-rows` (backlog) touches the same files and the same undo log; it is a different defect (writes that bypass the cursor are not logged), but its fix and this one must agree on how a logged row is identified.
- The SQL Server and PostgreSQL catalog stores (not converted yet) share `SQLStoreCursor`; the fix applies to them too.
