## What happens

Comparing two records (D4 calls them rows) with `=` or `<>` leaks one managed stream per stream-backed column per side, on every comparison. `Binary` and `Graphic` are the two types the engine keeps in a managed stream, and they are what an application stores a picture, a document or an attachment in; the engine does not reclaim such a stream until the session ends.

```
var LR : row { X : Binary } := row { Binary('0001') X };
var LN : Integer := 0;
for LI : Integer := 1 to 10 do
	if LR = LR then                                       -- 20 streams held for the session
		LN := LN + 1;
```

A comparison between two *computed* rows leaks the same amount. Row equality is not an exotic shape: it is what a transition constraint, a key comparison and `in` over a row-valued list all compile to, so this runs inside ordinary application code rather than only where a script says `=` between two rows.

**Measured, not inferred.** On `modernization` with `ticket(implement): bug-ifnil-leaks-the-value-it-copies` landed, through a throwaway case on `InProcessTestFixture` reading `Diagnostics.StreamCount()` either side of each script (added, run, removed). Ten iterations of the loop above: `row { X : Binary }` left 20 streams behind whether the two rows were computed or read out of a variable; `row { X : Binary, Y : Binary }` left 40; `row { X : Binary, N : Integer }` left 20. Three controls in the same run left none: `LR.X = LR.X` (column equality rather than row equality), `LR2 := LR` (row assignment), and `LR2 := row { Binary('0001') X }` (a computed row assigned and then released).

## Root cause

One site, missing both halves of the const-operand rule that `docs/architecture/operand-ownership.md` describes.

`RowEqualNode.DetermineDataType` (`src/engine/DAE/Runtime.Instructions/RowComparisonNodes.cs`) calls `DetermineModifiers(plan)` where almost every other instruction node calls `base.DetermineDataType(plan)`. The `const` branch of `InstructionNodeBase.DetermineDataType` is the only place that asks an argument node to lend its value (`PlanNode.SetByReference`), and `DetermineModifiers` alone does not reach it - so neither argument node is ever asked, both answer `ReturnsByReference` false, and both *copy* the row they were given. `iEqual(const ALeftValue : row, const ARightValue : row)` (`src/engine/DAE/Schema/SystemCatalog.d4`) is where those `const` modifiers are declared.

The node then overrides `InternalExecute(Program)` directly, which is the shape that bypasses `InstructionNodeBase.CleanupOperand` - so nothing releases the copies either. The two mistakes compound: the first makes a value the call owns, the second drops it.

Confirmed by experiment, not only by reading. Adding `Nodes[0].SetByReference(); Nodes[1].SetByReference();` after `DetermineModifiers` - the lending half alone - took the variable shape from 20 streams to 0 in the probe above and left the computed shape at 20, which is exactly the split the two halves predict. The probe was then reverted.

`CompoundScalarEqualNode`, in the same file, has the identical shape: `DetermineModifiers` in place of `base.DetermineDataType`, an `InternalExecute(Program)` override, and `const` operands on the equality operator the compiler generates for a compound scalar type (`Compiler.CompileComparisonOperator`, `src/engine/DAE/Compiling/Compiler.cs`). It was read rather than measured - a reproduction needs a compound scalar type with a stream-backed property - so treat it as the second arm to confirm rather than as a second verified defect. It also wraps both native values with `DataValue.FromNative` and disposes neither wrapper.

## The class behind it, which is the arm worth having

Overriding `InternalExecute(Program)` silently opts a node out of operand cleanup, and nothing checks which nodes have done so. The architecture page listed four such nodes when this review started; there are thirteen that are operator nodes, and the nine the list missed are the dangerous ones - they derive from one of the five argument shapes (`InstructionNode` and its nilary, unary, binary and ternary siblings) and re-override the entry point, so they read as ordinary instruction nodes while skipping their own shape's cleanup call. That miscount is how the two row-equality nodes went unexamined, and a hand-maintained list will miscount again.

So the arm that retires the class: a check over the set rather than a point fix. A test that reflects over the engine assembly, finds every `InstructionNodeBase` subclass that declares `object InternalExecute(Program)` other than the five shapes themselves, and compares that to a checked-in list of nodes whose ownership has been reviewed. A new node of this shape then fails a test with a message telling its author to apply the rule and add itself to the list, rather than leaking silently for a decade. The list is cheap to maintain because it only changes when someone writes a node of this shape.

The same reflection pass should also flag an `InstructionNodeBase` subclass whose `DetermineDataType` override never reaches `base.DetermineDataType` - that is the first half of this defect and is not visible from the execute side at all - if that can be checked without parsing source.

## What to pin

- The reproduction above, as a case beside the `IfNil` cases in `tests/DAE.Server.Tests/AssignmentValueOwnershipTest.cs`: both shapes (computed rows and a variable's row) and a multi-column row, asserting the stream count balances. Both shapes are needed, because the two halves of the fix each cover only one of them.
- A case that reads the comparison result and the caller's variable afterwards, not only the count: lending without releasing and releasing without copying both balance the count, and only a read distinguishes them. The `IfNil` cases are the model.
- The reflection check described above, with its list.

## Scope note

Do not widen this into a rework of how a call and its operands agree about ownership. `bug-a-loop-over-a-read-only-parameter-orphans-a-computed-argument` (in `backlog/`) and `bug-a-var-parameter-written-in-the-body-can-release-a-callers-loop-value` (in `fix/`) are the two tickets at that seam, and both are about `CallNode`'s hand-back of an operand slot's final value. This one is narrower and independent: two nodes that never joined the rule at all, plus a check so the next one cannot.
