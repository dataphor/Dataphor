## What landed

The last of the four tickets that build the test plan's layer 4 (client/server). It gives the `ServerLink` coverage script the second Dataphor server its own first comment has always asked for — *"Assumes a running default Dataphor instance"* — and the script runs for the first time in the history of the automated suite. It was `[Ignore("Integration test, needs server setup")]` in the legacy hand-wired list (confirmed in git at `3c3aea68^`), so none of its assertions had ever been checked by a test run.

**The product gained one member**, `DataphorServiceUtility.ListenerPortNumber` (`src/protocol/Common/Contracts/DataphorServiceUtility.cs`): a settable process-wide default for the port a **client** looks on for a listener when the caller passes no override, consulted by `BuildListenerURI` where the constant used to be read. `public const int DefaultListenerPortNumber = 8060` is untouched and is still the initial value, so a deployment that sets nothing behaves exactly as before. It is deliberately not added to `RevertHooksToDefault` (a port is not a hook, and that method clears the memoized binding with the hooks it restores) and deliberately has no host-side counterpart (`ListenerServiceHost` resolves a concrete port before it calls `BuildListenerURI`, and a server's listener port is already an instance setting, `ServerConfiguration.OverrideListenerPortNumber`). All three reasons are recorded at the site, and `docs/migration-notes.md` has the entry.

Why it was needed rather than simply taking port 8060: WS3's own cross-cutting requirement is that no test touches a fixed port, and the failure mode here is worse than a collision — on a machine with a real Dataphor 4 installation, a real listener holding 8060 would answer the script's lookup and point it at a **real instance**, in which the script then creates users, tables, types and operators.

**The test side.** `OutOfProcessInstance` can now serve a listener: a third constructor parameter `shouldListen`, a second reserved port exposed as `ListenerPortNumber`, `ShouldListen`/`OverrideListenerPortNumber` written into the child's instance list, and `CheckReadyLine` now requiring `listening=true` for such a child — so a child whose listener port was already taken (which `DataphorServiceHost` tolerates by design) fails the case at the start with the child's own output attached, rather than later as a socket error on the client. A listening child listens on `Environment.MachineName` rather than the loopback literal, which is the suite's one deliberate exception to "no port another machine can reach"; the reason, the measurement behind it and the fact that it is forced are at the `HostName` property and in the plan.

**The manifest** gained `linkedServer` (`true` only, forbidden on a `fragment` entry, `false` rejected as `batches` is), described in `CoverageManifest`'s remarks and in `AGENTS.md`. `CoverageScripts.Execute` starts the child for such an entry around the script's own server work, points `DataphorServiceUtility.ListenerPortNumber` at it, and restores that static in a `finally` nested inside the `using` that stops the child — so both are undone on every path out, including the one where the script times out and its server is abandoned with its worker thread still running.

## What the script reported

**125 of its 126 statements pass. One fails, and it caught a real defect.**

The failing assertion is at line 34:

```
create server Test tags { HostName = "localhost", InstanceName = "Dataphor", DefaultMaxCallDepth = "128" };
if (EvaluateOn('Test', 'select Processes[ProcessID()].MaxNestingLevel') as Integer) <> 128 then
	raise Error("Server link with Session Info failed");
```

Measured, on one process against the child server: the remote value is **100**, the product default. The cause is not the tag — the same statement under a link name no earlier link used returns **128**. It is that the block before it creates a link called `Test`, uses it, and drops it; nothing closes the cached connection when a link is dropped (`ServerProcess.RemoteDisconnect` exists for exactly that and has **no caller in the tree**; `DropServerNode.InternalExecute` carries the original author's `// TODO: Prevent dropping when server sessions are active`), and the cache matches links by **name** (`RemoteSessions.IndexOf` compares with `Schema.Object.Equals`). So the second `Test` link reuses the first one's connection, with the first one's host, instance, credentials and session info. `Count(RemoteSessions where Process_ID = ProcessID())` is 1 at that point, which is the dropped link's session still sitting there.

Filed as **`tickets/fix/engine-server-link-session-outlives-drop.md`** with the measurement and the three questions a fix has to settle (whose cached connections a drop closes, what happens to one enlisted in an open transaction, and whether the cache should key on identity instead of name — the last of which needs the close to land with it, because nothing on the far side reclaims a native session). `alter server` carries the same author's TODO and the same gap, which that ticket also names. The manifest entry is now `known-failure` on the substring `Server link with Session Info failed`, owned by that slug — **this slug no longer appears in the manifest.**

**How the whole script was accounted for.** The coverage run stops at the first failure, so I ran the script's text batch by batch on one process in a throwaway fixture, reporting each failure instead of stopping: 126 batches, exactly one failing (line 34). That fixture and its project entry are deleted; nothing of it is in the tree. So the layer's coverage claim is measured, not assumed: default and tagged links, session-info propagation, link users and their credentials (including `CreateServerLinkUserWithEncryptedPassword`, `SetServerLinkUserID`/`Password` and `ChangeServerLinkUserPassword`), `alter server`, parameters in and out, every shape of non-scalar result, `like` types across the link, `select … on <link>`, and the `ServerLinks`, `ServerLinkUsers` and `RemoteSessions` system tables all execute.

**Caveat for the reviewer, stated plainly:** that batch-by-batch probe ran one implicit transaction per batch, whereas the real case runs the whole script nested in one `ExecuteScript` statement whose transaction stays open. The real case therefore still stops at line 34 and the 90-odd statements after it have never been checked *in the nesting the harness uses*. They will be the moment the fix lands and the entry flips to `pass`, and that could surface more. The manifest entry's `note` and the fix ticket both say the entry becomes `"status": "pass"` in the same commit as the fix.

## Verification, and what rests on inspection

Measured on this machine, 2026-11-21, `Debug`:

- `dotnet build Dataphor.slnx -t:Rebuild`: **0 errors, 143 warnings** — the unchanged pre-existing set; a rebuild reports no warning from any file this ticket touches.
- Suite in three parts, each in the foreground, all green on the final tree: part 1 **13 + 438 passed, 0 failed** (5 m 11 s); part 2 **67 passed, 11 skipped, 0 failed** (3 m 45 s); part 3 **48 passed, 14 skipped, 0 failed** (3 m 38 s). The skips are the manifest's known, unstable and fragment entries, as always.
- **Part 3 before and after**: 3 m 52 s before (measured on this machine by `test-client-server-abandoned`), 3 m 38 s and 3 m 42 s after, over two runs. The `ServerLink` case itself went from **6 s to 7 s** — the extra second is the child server's start. The script is not slow, so there is no sign of the per-connection address-family fallback the host-name choice exists to avoid.
- **The child binds all interfaces, and that is why.** Its host name is the machine's, so CoreWCF opens both `0.0.0.0` and `[::]`; the script connects by `localhost`, which this ticket cannot change, and opens on the order of thirty remote sessions, so a literal address that forced a two-second fallback per channel open would take it past its 120-second timeout. Two dynamically chosen high ports, held for the seven seconds the case runs.
- **Port 8060 is not touched — verified by hand, not reasoned about.** With a socket holding `0.0.0.0:8060` in another process for the length of the run, the case behaves identically (7 s, same known failure). Nothing in the path resolves through the product's default listener port.
- **Manifest validation, both arms verified by hand** (not as a new test, per the ticket): `"linkedServer": false` fails the run with `Entry 95 (ServerLink): "linkedServer" is false; leave the field off for the default…`, and moving the field onto a `fragment` entry fails with `"linkedServer" is not allowed on a fragment entry; it is not run.` The entry was restored and the suite re-run afterwards.
- **No other caller resolves through a listener with a zero override in a path the suite runs** — checked, not assumed. The two product callers that can are `ClientServer.Open` (only when `_overridePortNumber == 0`) and `NativeCLIClient.GetNativeServerURI`; every `ClientServer` in `tests/` and `tests/TestHarness` passes a real instance port, and `CoreWcfProtocolTest`'s two listener cases pass `_host.ListenerPortNumber`. So the static reaches nothing but the one case that sets it.
- **One case at a time** — `CoverageScripts` is not `[Parallelizable]` and there is no assembly-level parallelism; the fixture now carries the suite's usual explicit `// Not [Parallelizable]:` comment saying so and why it now matters.

Rests on inspection rather than a test: the `finally` ordering on the abort path (read, not provoked — no script reaches the abandon path today); a child whose listener port is already held failing the case through `CheckReadyLine` (the comparison is there, the condition was not arranged); and that the child needs no libraries beyond what the server builds itself.

## Interactions a reviewer should know

- **`bug-native-cli-sessions-never-reclaimed`.** The script's links hold native sessions on the child and nothing there times them out. Harmless as the case stands — the child is killed at the end of it — but it means this case cannot become a long-running or repeated one until that ticket lands, and it is also why the fix ticket says a key-by-identity change must land together with a close rather than instead of one.

## Review suggestions

- The judgement most worth a second opinion is **filing the line-34 failure rather than fixing it here**. It is three or four lines to make the script pass (call `RemoteDisconnect` from `DropServerNode` when the dropping process has a session for the link), and that is exactly why I did not: it fixes the dropping process only, leaves every other session's cached connection wrong in the same way, and says nothing about the name-based match or about a connection enlisted in an open transaction. The original author's two `TODO`s ask for the opposite answer (refuse the drop). Weigh whether the partial fix plus a narrower ticket would be better than a `known-failure` plus the whole question.
- Check that `CoverageScripts.Execute`'s split into `Execute`/`RunScript` reads the way the file's other code does, and that the `using`-outside/`try`-inside ordering is what you would want if the abandon path ever runs.
- The `HostName` property now returns one of two things depending on a constructor flag. Consider whether a reader meeting `instance.HostName` elsewhere in the suite is well enough warned by its remarks.
