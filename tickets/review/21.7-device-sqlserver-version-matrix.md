## What this was

A measurement, not a feature. Decision Q12 already said SQL Server 2022 is the supported minimum and 2019 is documented as working if it needs no extra code; nobody had run the product against any version on .NET 10. This pointed the suite's live SQL Server passes at one version after another and wrote down what happened.

## The result

**Four servers reached, all four pass.** Each run is the live set: the three transaction-atomicity scripts, the fifteen catalog-store contract cases, the six text-parameter cases, the three new version cases, `LiveDeviceTest`, plus the two passes that need no server but share the variable (`MSSQLStoreConnectionStringTest`, `StoreRebuildWorkflowTest`). A run takes 47-68 s. The totals differ between rows only because the first two servers were run with a narrower filter, before those last two passes were added to the set; nothing failed on any of the four.

| SQL Server | Hosting | Version reported | Collation | Result |
|---|---|---|---|---|
| 2022 | Linux container, SQL login, port 14220 | 16.0.4325.4, Developer | `SQL_Latin1_General_CP1_CI_AS` | 42 passed, 4 skipped, 1 m 08 s |
| 2019 | Linux container, SQL login, port 14190 | 15.0.4510.2, Developer | same | 30 passed, 1 skipped, 58 s (narrower filter) |
| 2019 | Windows LocalDB `ProjectModels`, integrated security | 15.0.4382.1, Express | same | 30 passed, 1 skipped, 47 s (narrower filter) |
| 2016 | Windows LocalDB `MSSQLLocalDB`, integrated security | 13.0.4001.0, Express | same | 42 passed, 4 skipped, 59 s |

The 4 skips are `LiveDeviceTest` (its recorded known failure against `test-pre-3-1-scripts-policy`), the sample-corpus-adjacent cases that are skipped either way, and the `StoreRebuildWorkflowTest` cases that are. The two narrower-filter rows were measured before the final two code edits and were not re-run; the two rows at 42/4 are the final build. **A reviewer re-measuring should re-run 2019.**

**2025 was not reached.** Microsoft's 2025 Linux images pull fine and the server process then stops at startup with a fatal error (`SIGHUP`) before accepting any connection - tried `2025-latest` (Ubuntu 24.04) and `2025-CU11-ubuntu-22.04`, as `mssql` and as root. The host is Docker 24.0.6 on WSL2, kernel 5.10.102.1, on an Intel Xeon E3-1505M v6 (AVX2, no AVX-512); 2019 and 2022 start on the same host, so the 2025 image wants something this host has not got. **Nothing about Dataphor was learned either way** and 2025 stays unmeasured; the honest hole is recorded in the user's guide, the plan row and Q12. What would close it: a Docker host on a newer kernel, or a SQL Server 2025 instance on Windows.

**2017 was not reached.** A full instance (`MSSQL14.MSSQLSERVER`) is installed on this machine but stopped and set to manual start, and starting a Windows service needs elevation this run did not have. It sits between 2016 and 2019, both of which pass.

**The encryption question `device-mssql-port` and `test-device-live` both left open is closed.** A container with a self-signed certificate is exactly the server neither could find. Measured on 2019 and 2022, with the connection string the fixtures use verbatim:

| In the connection string | 2019 | 2022 |
|---|---|---|
| nothing about encryption | fails: *the certificate chain was issued by an authority that is not trusted* | same |
| `Encrypt=False` | connects | connects |
| `TrustServerCertificate=True` | connects | connects |
| `Encrypt=True;TrustServerCertificate=True` | connects | connects |
| `Encrypt=Strict` | fails before login (*unsupported version of SQL Server … wait operation timed out*) | fails before login (*connection forcibly closed*) |

And the device's own default carries it: with `TrustServerCertificate=True` in the variable (so the fixtures' own housekeeping connects) the device gets no `Encrypt` of its own, and it connected to the 2022 container through its builder's `Encrypt=False`. `Encrypt=Strict` carried onto the device still fails, as `test-device-live` measured on 2016.

**Confirmed on every version reached**: `DetermineVersion` parses `serverproperty('productversion')` correctly (the new case asserts the device's `MajorVersion` equals the server's), `IsMSSQL70` is false, `ShouldEnsureDatabase` creates an absent database (so the `sysdatabases` compatibility view still answers on 2022), and the server-side cursor path works - `sp_cursoropen`/`sp_cursorfetch`, driven by the text-parameter fixture's explicit server-side cases and by every device read whose statement begins with `select`.

## What to test, validate and use

**The new fixture, `tests/DAE.Server.Tests/MSSQLVersionMatrixTest.cs`** (3 cases, ignored with the rest where `DATAPHOR_TEST_MSSQL` is unset). It drops its database `DataphorVersionMatrix` first, so starting the device is what creates it; then it creates a table on the server through a connection of its own and runs `Reconcile`.

- `TheDeviceReadsTheServerVersion` - the device's `MajorVersion` equals the major of what the server reports, and `IsMSSQL70` is false. Reads the device object out of the catalog **by reflection**, because the device assembly is loaded from the runtime layout and this project cannot reference it; that is the one thing in the fixture a reviewer should weigh. It also writes the version, edition and collation to `TestContext.Out`, so the TRX of any run records which server it was pointed at - which is how a CI run says what it tested.
- `TheDeviceCreatesTheDatabaseItIsGiven` - asserts the database exists after the device started, by reading its collation. Close to wiring; kept because `EnsureDatabase` reads a compatibility view a later SQL Server could drop, and that is a version question.
- `ReconcilesAPreExistingSchema` - the substantive one. A table with `int`, `datetime`, `date`, `time`, `datetime2`, `datetimeoffset`, `varchar(30)` and `nvarchar(30)` columns; asserts exactly which reach the reconciled table variable, as which D4 type, with which `Storage.Length`. **It pins two known-wrong behaviours deliberately**, each naming its owning ticket in the `ExpectedColumns` remarks; a fix to either makes this case fail with a message saying so.

**Two defects found, both on every version, both reachable by any deployment pointing a device at an existing schema:**

- `datetime2` and `datetimeoffset` columns are **dropped from the reconciled table variable with nothing said about it** - `ShouldIncludeColumn` has had both commented out since 2008 and `SQLDevice.GetDeviceTables` skips a column the filter rejects in silence. Filed as `bug-mssql-device-drops-datetime2-columns`, with the rung above it (any unknown type is dropped the same silent way) stated in the ticket rather than split off.
- An `nvarchar(30)` column reconciles with `Storage.Length` **60**, because `sys.columns.max_length` counts bytes. This was **already an arm** of `bug-mssql-device-text-columns-lose-characters` as a static reading; appended there as a fourth arm, now verified, with the consequence that arm lacked: the `LengthValid` constraint the engine compiles from that number admits strings the server will not store, so the rejection arrives from SQL Server on the write rather than from Dataphor on the edit. **No new ticket** - the site was already claimed.

**One behaviour recorded as behaviour, not a defect**: a reconciled table variable is named `Library.dbo.Table`, the SQL schema included, unless the device's `Schema` attribute names that schema.

**Two bugs met along the way:**

- `TestEnvironment.MSSQLDeviceAttributes` emitted `"UserName"` and `"Password"` device attributes, and `MSSQLDevice` has no such properties - every run until now used integrated security, so nothing had tried it. The first container run failed with `Class "MSSQLDevice" does not contain a property named "UserName"`. **Fixed here**: those attributes are gone and a new `TestEnvironment.MSSQLDeviceUser(deviceName)` returns a `CreateDeviceUser('Admin', …)` statement instead, empty for integrated security, called by all three device-creating sites (`LiveDeviceTest`, `CoverageScripts.LiveDevicePreamble`, the new fixture). That is what the `NOTE:` at that site recommended for this day, and it keeps the password out of the stored device definition. Its reproduction is the container runs themselves, which are the only thing that exercises a SQL login; no unit test was added for it, because the thing it got wrong is a property name on a class in another assembly and the live run is what checks that.
- `Schema.Device.RequiresAuthentication`'s setter ignores its argument (`set { _requiresAuthentication = false; }`), so the property can be turned off and never on. Found while working out whether a device would consult a device user. **Not fixed**: correcting it changes behaviour for any definition that sets it, which is a compatibility surface. Filed as `bug-device-requires-authentication-setter-ignores-value`, `repro: static`.

**Repeating the measurement.** `AGENTS.md` now carries the `docker run` line and the filter, beside `DATAPHOR_TEST_MSSQL`. The containers `dataphor-mssql-2019` (port 14190) and `dataphor-mssql-2022` (port 14220) are **left on this machine, stopped**, with their databases intact - `docker start dataphor-mssql-2022` brings one back in seconds. Remove them when done (`docker rm -f`); the 2025 images pulled for this were removed already. The LocalDB instance `ProjectModels` was started for the 2019 Windows row and has been stopped again; `MSSQLLocalDB` is left running with the suite's four `Dataphor*` databases on it, which is the state a local run expects.

## What a reviewer should look at hardest

- **The reflection in `TheDeviceReadsTheServerVersion`.** It is the only way this project can see a device-internal decision, and the fixture says so - but if there is a cleaner observable (a D4-visible consequence of `MajorVersion`, say) it is worth preferring. The assertion itself is sound: it compares the device's value with the server's own answer rather than with a literal.
- **Whether `TheDeviceCreatesTheDatabaseItIsGiven` earns its place.** It is one assertion over a `databasepropertyex` read, and the device's start would fail anyway if the database were absent. The argument for it is the compatibility view; the argument against is that it is wiring. Cut it if the second argument wins.
- **The explicit transaction in the fixture's `Reconcile`.** Reconciling writes table variables into the catalog, and those writes belong to the statement that opened the cursor: without `BeginTransaction`/`CommitTransaction` around it the reconciliation reported no errors and left nothing behind, which is how the first run of this case failed. Worth checking whether that is a property of `Reconcile` that belongs in `docs/architecture/catalog-and-store.md` beside the existing store-transaction rule, rather than only in this fixture's comment.
- **The honesty of the 2025 row.** It claims a host limitation, not a product one, on the evidence that the process dies before any client connects and that 2019 and 2022 start on the same host. If that reads as too strong a claim, weaken it - the ticket's instruction was that a matrix with an honest hole beats a guess.
- **The `docs/users-guide/dataphor-service.md` section placement.** It is a new `##` section before `## Uninstalling`, linked from the catalog-store paragraph above it and from `docs/architecture/devices.md`. The page is now 4,900 words; the 1,500-word cap applies only to `docs/architecture/`, and `python tools/docs-size-check/check_size.py` reports 13 files checked, 0 over.
- **Whether the two 2019 rows should be re-measured** on the final build before this is called done (see the table note above).

## Tests

|---|---|

Nothing else was added. In particular: no test per SQL Server version (a test that can only run where one version is installed is worth less than a row in the matrix), no test for the `CreateDeviceUser` fix (its oracle is a live server that needs a SQL login, which is the container run), and no test for the `RequiresAuthentication` setter (not fixed here).
