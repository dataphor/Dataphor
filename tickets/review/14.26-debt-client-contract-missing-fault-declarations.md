## What landed

One root cause with two arms, fixed at one site: the three administrative operations of the main service contract — `Start`, `Stop` and `GetState` — had incomplete error handling on both halves of the client.

**Arm one, the fault declaration.** `[FaultContract(typeof(DataphorFault))]` added to `BeginStart`, `BeginStop` and `BeginGetState` in `src/protocol/Client/Contracts/IClientDataphorService.cs`. The server has always declared it on all three; a Windows Communication Foundation client only deserializes a fault into `FaultException<TDetail>` when the operation's contract declares that detail type, so without it the three `catch (FaultException<DataphorFault>)` blocks in `ClientServer` were dead code and the server's exception type, error code, severity and inner exception were all discarded. The server side was left alone, as the ticket required: removing the attribute there would have made the two copies agree while leaving the client unable to read an error the server still sends.

**Arm two, the communication catch.** `catch (CommunicationException ce)` added after the existing typed catch in `ClientServer.Start()`, `ClientServer.Stop()` and the `ClientServer.State` getter, in the same shape the other five members of the class use (`ReportCommunicationError()`, then `ServerException.Codes.CommunicationFailure` with `ErrorSeverity.Environment` and the caught exception as inner). The typed catch stays first because `FaultException<T>` derives from `CommunicationException`; there is a one-line comment at the `Start()` site saying so, since the ordering is load-bearing and silent if reversed. `ReportCommunicationError()` is still a deliberate no-op, so nothing about channel recovery changed.

**The parity record drained.** The three `KnownFaultDifferences` entries in `tests/DAE.Server.Tests/ContractParityTest.cs` are gone, and the comment above the array no longer names this ticket; the array is now empty and the comment says what an entry is for, so the mechanism stays available for the next difference. The test fails on an entry whose difference is no longer there, so this could not have been skipped.

**Two documents that said something now false.** `AGENTS.md` and the `protocol-contract-parity-test` row in `docs/modernization-plan.md` both described the list as recording three differences. Both now say it is empty and what it is for. This was not in the ticket's TODO; it is here because leaving them would have left two documents asserting a state the code no longer has.

**Migration note.** One entry appended to the **Custom C# extensions** section of `docs/migration-notes.md`, status `done`.

Measured size: 127 insertions, 16 deletions across seven files (`git diff --stat`), of which 100 insertions are the new test and its helper.

## The pre-fix shape turned out to be different from the ticket's prediction

Worth reading before reviewing the test's assertions, because it changes which of them does the work.

The ticket expected the pre-fix failure to be a bare `System.ServiceModel.FaultException` and said to assert against that shape and against `CommunicationException`. That was the shape *before either arm*. With arm two in the same commit, an undeclared fault is a bare `FaultException`, which **is** a `CommunicationException`, so it now falls into the new catch and the caller gets `ServerException` with code 106211 (`CommunicationFailure`) — itself a `DataphorException`.

Confirmed by measurement, not by reading: with `[FaultContract(typeof(DataphorFault))]` removed from `BeginStart` alone and everything else in place, the new test fails on the **error-code** assertion (`Expected: 127105  But was: 106211`), and the three assertions before it pass. Restored, it passes. So:

- the error-code assertion is the one that separates fixed from broken, and its failure message names `CommunicationFailure` as the shape an unrecognised fault takes;
- the `Is.Not.InstanceOf<FaultException>` and `Is.Not.InstanceOf<CommunicationException>` assertions pin the *other* half — that no `System.ServiceModel` exception escapes these three members — which is the property arm two establishes and which the two neighbouring cases (`TestServerErrorArrivesAsTypedFault`, `TestNativeCliErrorArrivesAsTheTypedException`) assert in the same words. They are not redundant with the code assertion, but they are not what catches a reverted arm one either. **A reviewer may reasonably want them trimmed; the argument for keeping them is the consistency with the two neighbours and the fact that reverting arm two alone would be caught by nothing else.**

## Test added

| Test | What it verifies |
|---|---|
| `CoreWcfProtocolTest.TestAnAdministrativeErrorArrivesAsTypedFault` | A store failure raised inside `Start` on a real hosted server reaches `ClientServer.Start()` as the server's own `DataphorException`, with the store's error code (`ConnectionException.Codes.SQLException`, 127105) and its inner exception intact, and with no `System.ServiceModel` exception escaping. Hosted, because `ContractParityTest` holds the two declarations in step but cannot see what the wire does with them. |

No other test added. `Stop` and `GetState` carry no logic beyond the declaration this case exercises, and the declaration side of all three is `ContractParityTest`'s. The missing communication catch of arm two has no test of its own: provoking a transport failure mid-call is a timing exercise, and what it would assert is the shape the five existing members of the same class already establish.

How the case works, since the recipe is not obvious: its own host (it stops the engine, so it cannot use the fixture's), `ShouldListen` false, built through `NewHost()` / `Configuration(...)` / `WithTheObjectIDCounterRestored(...)` over a `TestEnvironment.NewDirectory` it deletes afterwards. It drives a bare `ClientServer` rather than a `ProtocolClient`, so no client-side engine starts. It calls `Stop()` over the wire (which releases the catalog store's file handles), overwrites every file matching `DAECatalog*` under the instance directory with text through the new private helper `RuinTheCatalogStore`, then calls `Start()`. Deleting the files instead would not work: a missing SQLite database is created empty and the server rebuilds its catalog and starts. The helper asserts it found at least one file, so a future change to where the store puts its files fails loudly rather than making the case prove nothing. Runs in about 3 seconds.

- **The assertion set of the new test**, with the pre-fix measurement above in hand. The question is whether the two `Is.Not.InstanceOf` assertions earn their place now that the code assertion is what separates the two behaviours.
- **The reworded `KnownFaultDifferences` comment.** The array is empty, so the matching code in `CompareFaults` and the unmatched-entry report in `CompareOperations` are now unreached until someone adds an entry. The fixture's own class-level `<remarks>` already records that the comparison's branches — the known-difference matching among them — have no test of their own and were confirmed against synthetic broken interface pairs that were not committed. Nothing new was parked at that site; the existing note covers it.
- **Whether the two documentation edits are wanted.** They are outside the ticket's TODO. The alternative was leaving `AGENTS.md` and the plan each claiming three recorded differences.
- **The migration note's wording**, in particular the "what to do" column: it tells an extension author to catch `DataphorException` and `ServerException` instead of `FaultException` or `CommunicationException`. The two new exception shapes are the behaviour an application can notice, which is the reason the entry exists.
- **The neighbours in `ClientServer.cs`.** Two open plan tickets touch the same file and neither claims this site: `protocol-transport-security` (the two unused secure-connection settings) and `test-client-server` (a second hosted instance).
