## What landed

`System.Data.SqlClient` is gone from the tree; `Microsoft.Data.SqlClient` 7.1.2 is the one SQL Server client, pinned in `Directory.Packages.props`. `Microsoft.Data.SqlClient.SNI.runtime` moved 4.0.0 -> 7.1.2 with it, because the client depends on that package and central package management allows one version per package id.

Six files changed a `using` and nothing else: the three connection classes in `src/engine/Server/Connection/`, `MSSQLStore.cs`, `MSSQLStoreConnection.cs` (whose `using` is inside the uncompiled `#else` branch, changed so the branch stays coherent) and `libraries/Connection/Source/Operators.cs`. The long `SqlDbType` switch in `MSSQLCommand.PrepareParameters` needed nothing - `SqlDbType` is `System.Data.SqlDbType` on both clients, and `Image` and `Text` are still in the enumeration - and `IsTransactionFailure`/`IsUserCorrectableError` needed nothing either: they switch on SQL Server error numbers, and `SqlException.Errors`/`SqlError.Number` keep their shape under the new namespace. Both were read rather than assumed; both compile with no new warning.

**The engine no longer references a SQL client.** `Engine.Dispose`'s `SqlConnection.ClearAllPools()` moved to a new `Dispose(bool)` override on `Server` and the package reference left `DAE.csproj`. The server assembly is where the connection classes are, so it is the assembly that can have opened a SQL Server connection and the one that should clear its pools; a hook or an interface on `Engine` would have been machinery for a dependency that simply pointed the wrong way. The call is after `base.Dispose(disposing)`, so the order is 3.1's, and in a `finally`, because the statement it moved out of was in one: a `Stop()` that throws on the way down cleared the pools before the failure propagated, and still does.

**`MSSQLConnection.IsZombied`.** `SqlTransaction.IsZombied` is present on 7.1.2 as an internal instance `Boolean` property and is found by `BindingFlags.Instance | BindingFlags.NonPublic` - verified by reflecting over the pinned package before the code was written, and then exercised for real (see below). The reflection stays, but the lookup is now a cached static `PropertyInfo` and both ways it can fail - the member gone, or a transaction from some other client - throw a `DataphorException` (severity System) naming the property, the declaring type, the assembly and which half failed, instead of dereferencing null on every commit and rollback.

**The compatibility default, in the two places a connection string is built.** `Encrypt=False`, not `TrustServerCertificate=True`: only the first is what 3.1 negotiated; the second encrypts and then accepts any certificate, which is a *new* behaviour and would quietly change what every existing deployment does. On the device it is a parameter of `MSSQLADODotNetConnectionStringBuilder`, which gets the precedence right by construction - `SQLDevice.GetConnectionParameters` applies the device's and the device session's own `ConnectionParameters` after the builder has run, so `'ConnectionParameters' = 'Encrypt=True'` wins. In the store it is a conditional default in `MSSQLStore.InternalInitialize`, applied only when the connection string names neither `Encrypt` nor `TrustServerCertificate`, because a deployment that set either has already said how that connection is protected. Each site carries the reasoning and the override.

**The library-loading probe.** The ticket predicted this and it happened: `Microsoft.Data.SqlClient` pulls `Microsoft.Data.SqlClient.SNI.runtime` into `Server.csproj`'s closure, the layout then stops treating that package as private to `LibraryLoadingProbe` (which referenced the server assembly), the native dll lands in `bin/` instead of flat in the library's folder, and `LibraryLoadingTest.NativePrivateDependencyResolvesFromLibraryFolder` fails. Confirmed by building the layout and finding `Microsoft.Data.SqlClient.SNI.dll` gone from `artifacts/layout/debug/Libraries/LibraryLoadingProbe/`. The fix was not a different package: the probe never used the server assembly at all (its nodes need only `DAE` and `Base`), so the unused `ProjectReference` is gone and the package is private again, with a `NOTE:` in the project file saying why the reference must not come back. Side effect, documented there too: `Newtonsoft.Json.dll` now also lands in the probe's folder as `Newtonsoft.Json.Bson`'s own dependency. It is never the copy the resolver finds - the host's `bin` has that one and the resolver hook runs only after ordinary probing has missed - so the managed arm still proves what it did.

**`PGSQLStore.cs`** lost its unconditional dead `using`; `PGSQLStoreConnection.cs` was left alone, because its `using` sits inside the uncompiled `#else` branch next to the `SqlConnection` call it guards, and that branch is `store-pgsql-port`'s. So one grep hit for the old namespace remains in the tree, deliberately, in a project that is not in the solution.

## Tests

Five cases added, both groups pinning behaviour this ticket introduced that nothing else covers. The project rule asks a characterization test of a re-hosted subsystem *unless one already covers it*: the client swap itself is covered (the device translation goldens and the live store contract, both run below), but the connection-string defaults are new behaviour on a branch, and deleting either one line would silently stop every existing customer device definition and catalog connection from reaching an ordinary internal SQL Server.

| Test | What it pins |
|---|---|
| `MSSQLStoreConnectionStringTest.AConnectionStringThatSaysNothingAboutEncryptionGetsTheOldClientsBehaviour` | a release-3 `catalogstoreconnectionstring` comes out of `InternalInitialize` with `Encrypt=False` |
| `...AConnectionStringThatAsksForEncryptionKeepsIt` | a deployment's `Encrypt=True` survives - the store defaults, it does not force |
| `...AConnectionStringThatTrustsTheServerCertificateIsLeftAlone` | `TrustServerCertificate=True` counts as having chosen, so no `Encrypt` is added beside it |
| `...MultipleActiveResultSetsIsForcedOverADeploymentsFalse` | the other rewrite in the same method is still *forced*, which is the difference the fixture exists to hold |
| `MSSQLDeviceTranslationGoldenTests.EveryConnectionCarriesTheDevicesCompatibilityDefaults` | every connection string the device built for a definition naming only server, database and integrated security carries `Encrypt=False` |

The store fixture needs no server: with `ShouldEnsureDatabase` off, initializing the store only rewrites its connection string. Every assertion reads the result back through `DbConnectionStringBuilder` rather than matching text, because that class lower-cases the keywords it parsed out of the supplied string and leaves the ones the store added alone - the first draft asserted on text and failed for exactly that reason. The device case went in through a new `protected virtual string[] RequiredConnectionStringText` on the shared base, empty by default, so `device-pgsql-device-golden`'s subclass can state its own defaults or none.

## What is *not* verified, plainly

- **The compatibility trap itself never fired here.** The only SQL Server on this machine is LocalDB, and this driver treats a local connection's certificate as trusted: measured, `Encrypt` unset, `Encrypt=False` and `Encrypt=True` all connect to `(localdb)\MSSQLLocalDB`. So the live run proves the new client works; it does **not** prove the default is needed, and it does not exercise the override. Both belong to `test-device-live`, against a server with a self-signed or absent certificate - and that is the run that would catch it if `Encrypt=False` were the wrong spelling for this driver version.
- **The device's server-side cursors compile and are unverified.** `MSSQLCommand`'s `sp_cursoropen`/`sp_cursorfetch` route, its fixed internal-parameter order, its `ParameterDirection.ReturnValue` and its `NVarChar` out parameters, and `MSSQLServerCursor`'s fetch loop: nothing in the suite drives any of it, before or after this change. `test-device-live` owns the proof.
- **No device ran against a real SQL Server at all.** The goldens replace the client; the store contract exercises the client but not the device.
- The `varchar` parameter mapping is untouched, deliberately, so that this change stayed a swap. `device-mssql-string-parameters` owns it.

## For the reviewer to weigh

- **The probe's dropped `Server.csproj` reference.** The alternative was pointing the probe at a different native-RID package. Rejected: `System.Data.SQLite.Core` would put a second copy of `SQLite.Interop.dll` in a process whose catalog store already has one loaded, and `runtime.native.System.Data.SqlClient.sni` says in its own description that it is not meant to be referenced directly. Dropping an unused reference seemed the smaller and more honest change, and the test is its own guard if someone adds it back. Worth a second opinion.
- **The device's default is on `MSSQLADODotNetConnectionStringBuilder` only.** A device that keeps `Connection.MSSQLConnection` but names the OLE DB or ODBC connection-string builder gets no compatibility default. That pairing is one the device's own comment calls out as wrong ("use with ADO and OLE DB"), and nothing here changes it - but it is the one configuration where this ticket's answer does not reach.
- **The store's condition is on two keys.** `Encrypt` covers a deployment that wrote `Encrypt=Strict`; `TrustServerCertificate` covers the other way of letting an untrusted certificate through. Whether any third keyword should also count as "has chosen" is a judgement.
- **`Server` now overrides `Dispose(bool)`**, which it did not before. A subclass of `Server` that overrides it must call base - as it had to before - but this is a new link in that chain, and a migration note records it.
- The fixture helper comment in `StoreContractTests` that said connecting through `SqlConnection` directly would be "obsolete on this client package" is no longer true and was rewritten; it now says what the helper's raw connections do and do not get.

## Tripwires parked, not filed

- **The client's dependency closure.** `NOTE:` in `src/engine/Server/Server.csproj`: eight of the added assemblies exist for authentication methods nothing here uses - the Microsoft Entra ID path - and they ship because they are in the package's dependency graph, not because anything loads them. Fine now; if the installer's size or a deployment's dependency audit objects, the question is whether a trimming step belongs in WS9's installer, since NuGet has no supported way to prune a package's own dependencies.
