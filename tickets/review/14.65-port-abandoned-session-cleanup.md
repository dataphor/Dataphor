## What landed

The answer the plan ticket proposed held up: the mechanism is the idle reaper that was already in `ConnectionManager`, with the client's ping as its liveness signal. Nothing new was invented; the reaper was corrected, documented and pinned by a test.

**`src/engine/Server/Service/ConnectionManager.cs`** — rewritten around the same loop.

- The idle threshold is now an instance field, with `public const int IdleTimeInSeconds = 300` as its default (the constant is untouched). The new constructor `ConnectionManager(RemoteServer, int)` takes the threshold and refuses anything below one second with `ArgumentOutOfRangeException`, following `LocalServer`'s interval constructor; the old constructor delegates to it.
- The wake period is separated from the threshold at `Math.Max(1, idle / 4)`, so reclamation happens between the threshold and the threshold plus a quarter of it (300 to 375 seconds at the default) rather than between the threshold and twice it.
- The sweep is extracted into the private `RelinquishIdleConnections(DateTime)`. It reads `_remoteServer.Server` once and returns if it is null, so a sweep overlapping the server's teardown can no longer raise inside its own logging and silently kill the watcher thread.
- `Dispose` is idempotent and waits up to `WatcherStopTimeoutInSeconds` (10 s, matching `NetTcpServiceHost.StopTimeout`) for the watcher. The thread stays a background thread, so a wait that gives up cannot hold the process open; the amended `NOTE:` at the thread says so and no longer says the class may be reworked.
- Two `NOTE:`s: the revisit condition for a future operator setting (at the `IdleTimeInSeconds` constant), and the serial-sweep consequence (at the sweep) — one wedged process delays every later connection's reclamation by up to half of `Engine.ProcessTerminationTimeout`.

**`src/engine/Server/Server/RemoteServerConnection.cs`** — `Dispose(bool)` returns at the existing `_disposed` field, so a second disposal does nothing at all, including not re-raising `Disposed`. `LastActivityTime` now documents what it is (a last-*ping* time) and why nothing else can move it.

**`src/engine/Server/Server/RemoteServer.cs`** — `Relinquish` checks the cast instead of dereferencing it, raising error 106191 (`TypedObjectContainer`, the code a `RemoteServerConnections` container already raises for the same mismatch) for a connection that is not one of ours. Its remarks record that it is idempotent, which step tolerates having been taken already, and why `CloseSessions` stays outside the server's lock.

## The four facts the plan ticket asked to be checked

All four held, read against the current code. Two refinements:

- **`LastActivityTime` is a last-ping time.** Confirmed: set in the constructor and in `Ping()` and nowhere else, and there is no handle-to-connection path to stamp from an ordinary call.
- **A long single call is not at risk while the client pings.** Confirmed, but the ticket's wording "so long as a session is open" is now wrong: since `port-connection-keepalive` the ping belongs to the connection, so a connection with no session open is pinged too. Corrected in the code comments and the plan text.
- **The bound was 300 to 600 seconds.** Confirmed: the wake period and the threshold were the same constant.
- **Reclaiming twice was unsafe.** Confirmed, and reproduced by test: the second `Relinquish` reached `RemoteServerConnection.Dispose`, dereferenced the `_sessions` field the first had nulled, and raised a `NullReferenceException` wrapped as a `DataphorException`.

On the shutdown race the plan ticket described, one correction worth a reviewer's attention: it is narrower than stated but real. `RemoteServer.Dispose` nulls `_connections` **before** `_server`, so a sweep that starts after `Dispose` has finished sees an empty snapshot and does nothing. The window is a sweep that takes its snapshot (under the server's lock) just before `Dispose` nulls `_connections` — `Dispose` does not take that lock — and then logs after `_server` has gone. The bounded join plus the ordering in `DataphorServiceHost.Stop` (`_service.Dispose()` before `_remoteServer.Dispose()`) closes that for the hosted path; the stopped-server guard covers a host that disposes them in the other order.

## What an in-flight call on a reclaimed connection sees

Three steps, each read in the code:

1. `ServerSession.StopProcesses` calls `Engine.TerminateProcessThread` (`src/engine/DAE/Server/Engine.cs:474`), which sets `IsAborted` and spins for half of `Engine.ProcessTerminationTimeout` (15 s by default) waiting for the executing thread; if the thread will not stop it raises `ProcessNotResponding`, which `StopProcesses` logs before disposing the process anyway.
2. `ServerProcess.Dispose` rolls back every open transaction before unpreparing deferred constraint checks, and leaves an application transaction first (`InternalLeaveApplicationTransaction`) — pre-existing behaviour, unchanged here.
3. Disposal raises `Disposed`, and `HandleManager.ObjectDisposed` removes that object's handle from both of its dictionaries, so the next call on it reaches `HandleManager.GetObject`, which raises error 106205, unknown object handle. The same happens at all three levels (connection, session, process), because each is an `IDisposableNotify` that the handle table hooked when it handed out the handle.

Nothing in the handle table is corrupted: the handle is withdrawn, not left pointing at a disposed object.

## Tests

Both in `tests/DAE.Server.Tests/AbandonedSessionCleanupTest.cs`, in process over a `RemoteServer` plus a `ConnectionManager` at a one-second threshold. No WCF host, no port.

| Test | What it verifies |
|---|---|
| `AnAbandonedTransactionIsRolledBackAndTheCatalogWriteLockReleased` | The whole chain: a connection that is never pinged is relinquished; the explicit transaction it left open is rolled back rather than committed (the table it created does not resolve, with an expression never compiled before); the catalog store's write lock is released, so another session's `create table` succeeds; and a call on the reclaimed process fails instead of reaching the disposed objects behind it. It also asserts, before the watcher exists, that the lock was genuinely held (error 130103 at the busy timeout), so the final wait cannot pass on a server where no lock was ever taken |
| `RelinquishingAConnectionTwiceDoesNothing` | The reproduction for the double-reclamation defect; no timing |

**Route taken for the abandoned client: the remote CLI directly** (`RemoteServer.Establish` → `IRemoteServerConnection.Connect` → `IRemoteServerSession.StartProcess` → `BeginTransaction` → `ExecuteScript(script, ProcessCallInfo.Empty)`). `IRemoteServerProcess.ExecuteScript` takes a script and a call info and nothing else, so no parameter or cleanup structures were needed and `GetRemoteProcessCleanupInfo` never came into it. The `LocalServer` route was not needed: it would have pinged the connection (the thing this case must not have) and started a second engine, bringing the object-id-counter workaround with it.

**Observed reclamation time: about 1.1 seconds** at a one-second threshold, measured as the time from the watcher starting to another session's `create table` succeeding; the lock-held assertion before it took about 1.2 s, which is the store's busy timeout. The whole fixture runs in about 9 s.

**Both cases were confirmed to fail before the change.**

- `RelinquishingAConnectionTwiceDoesNothing`: with the `_disposed` guard removed, it fails with `NullReferenceException` at `RemoteServer.Relinquish`. The guard was then restored.
- `AnAbandonedTransactionIsRolledBackAndTheCatalogWriteLockReleased` cannot run against the pre-change code at all — the injectable threshold is part of the change, and at 300 seconds no test can wait for a sweep. The negative control run instead: with the threshold set to 600 seconds the case fails at its wait ("still held the catalog store's write lock 5.8 s after the idle watcher started"), which shows the wait really depends on reclamation happening rather than on anything else in the fixture.

**Nothing else is owed, by the ticket's own judgement and mine.** The watcher's wake arithmetic is exercised by the first case. The bounded `Dispose` wait, the stopped-server guard and the typed error for a foreign connection are each a guard with no branching behaviour of its own, verified by inspection. The rollback running on the reaper's thread rather than the thread that opened the transaction is exercised by the first case and raised no objection from the store or the device session.

## Bugs met along the way

**`RemoteServerConnection.Disconnect` had the same defect as `Relinquish`, one method away**: it cast with `as` and then tested the *parameter* rather than the cast result, so a session object from elsewhere passed the test and raised a `NullReferenceException` on the null local. Fixed the same way, with the same typed error; a null session stays a no-op as it was. Dormant in the product (the service reaches it only through the handle table, which returns `RemoteServerSession`), so no test — the same reasoning the ticket applies to the other guards.

## What a reviewer should look at hardest

- **A call on a dead remote CLI object raises `NullReferenceException`, not a Dataphor error.** The first test records this (the message prints it) and does not assert the type. Every `Remote*` object nulls its inner reference on disposal and no member checks for it, so this is class-wide and pre-existing, not something this change introduced. It is effectively unreachable in the product — over the wire the handle table withdraws the handle first (step 3 above), and the only in-process client of the remote CLI is `LocalServer`, which pings its connection and so is never reaped — which is why no ticket was filed. If a reviewer disagrees that it is unreachable, the ladder rung is a representation change across the `Remote*` family, not a point fix.
- **`RemoteServer.AttachServer` has no callers**, so `FServerDisposed` is unreachable: a `RemoteServer` never learns that its engine has been disposed. `DetachServer` *is* called from `Dispose` and unsubscribing a handler that was never added is harmless, so this is dead code rather than a defect. Noticed while establishing the shutdown window above; left alone deliberately, because deleting three methods from a public-ish server class is not this ticket's business.
- **The claim that the shutdown window is now closed rests on `DataphorServiceHost.Stop`'s ordering**, which is stated in a comment at `StopLifetimeWatcher` rather than enforced anywhere. A host that disposed the `RemoteServer` before the service would still race, and only the stopped-server guard catches it.
- **The threshold decision.** No instance setting was added, with the reasoning recorded as a `NOTE:` at the constant. If a reviewer thinks an operator setting is owed now rather than on the recorded revisit condition, that is a judgement call to make here, not later.

## Tripwires recorded

Findings parked at their sites rather than filed:

- `ConnectionManager.IdleTimeInSeconds` — the revisit condition for an operator-settable threshold, with what the change would involve.
- `ConnectionManager.RelinquishIdleConnections` — the sweep is serial, so one process that will not stop when aborted delays every later connection's reclamation.
- `tests/DAE.Server.Tests/ConnectionKeepAliveTest.cs` — that fixture's existing `NOTE:`, which said this ticket *would* make `Relinquish` idempotent and that its in-process path would then stop exercising the client's guard, is amended to the past tense now that it has happened. The case is kept; it still asserts the client's contract.

## Out of scope, as the ticket set it

- **Native CLI sessions are reclaimed by nothing.** Confirmed by reading `NativeServer`: sessions in a dictionary keyed by a GUID, no liveness tracking, no sweep, no ping in `INativeCLIService`. A native client that dies inside a catalog-changing transaction holds the store's write lock until the server is stopped. Pre-existing and owned by `bug-native-cli-sessions-never-reclaimed` (now in `plan/`, not `backlog/`); named in both documents so that a reader of "what reclaims an abandoned session" knows which door is still open.
- **A client process killed outright** belongs to `test-client-server`, whose ticket already records the split and the fact that `ConnectionManager` takes the threshold as a constructor argument since this change.
