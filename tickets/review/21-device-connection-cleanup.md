## Drift in the deleted copies - what the diff was

All six `.cs` copies had drifted, and in every case the live file is the newer one: the deleted copies are pre-modernization originals. Three signatures, all in the same direction.

- **Old naming conventions.** The copies use the Hungarian prefixes the port removed - `FResourceManager` for a field, `AErrorCode` for a parameter, `LIndex` for a local. The live files use `_resourceManager`, `errorCode`, `index`. That accounts for most of the changed-line counts: `ConnectionException.cs` 84 changed lines, `DotNetConnection.cs` 381, `MSSQLConnection.cs` 670, `SQLConnection.cs` 1067, `SQLTypes.cs` 33, `ODBCConnection.cs` 110.
- **One file split into several.** The copy of `SQLConnection.cs` is the old monolith holding `SQLCommand`, `SQLCursor`, `SQLParameter`, the schema types and the enumerations; under `src/engine/DAE/Connection` those are separate files (`SQLCommand.cs`, `SQLCursor.cs`, `SQLParameter.cs`, `SQLSchema.cs`, `SQLUtility.cs`). Same for `DotNetConnection.cs` and `MSSQLConnection.cs`, whose command and cursor classes are now `DotNetCommand.cs`, `DotNetCursor.cs`, `MSSQLCommand.cs`, `MSSQLServerCursor.cs`. So a symbol that looks missing from the live file is in a sibling file, not gone.
- **Content only the live file has.** `ConnectionException.cs` and its `.resx` are the clearest: the live pair carries two error codes the copies do not (127123 `ProviderFactoryAlreadyConstructed` and 127124 `ProviderInvariantNameRequired`, added for the generic connection), and the copy carries a `[Serializable]` the port removed. Nothing was found that only a stale copy had.

Nothing was lost by deleting them, and the drift is not evidence of an edit made on the wrong file: it is the shape of a file that stopped being touched before the port started. `libraries/Connection/Source/Register.cs` still says `typeof(MSSQLConnection)`, which resolved to the compiled class in the server assembly before and still does, so the class alias `Connection.MSSQLConnection` is unchanged.

## Tests

One test added; it is the only one.

- `tests/DAE.Server.Tests/LibraryLoadingTest.cs`, `ODBCConnectionLibraryRegistersWithoutADriverManager` - registers `ODBCConnection` on an in-process server and asserts it does not throw. **It verifies two things the build cannot:** that the library's one private managed package resolves from the flat library folder through `LibraryAssemblyResolver` (the same guard the fixture's existing `Connection` arm gives that library's four), and that registration does not reach the ODBC driver manager. `"ODBCConnection"` joined the fixture's `Libraries` list; it is not in `LibrariesToRegister`, so the registration is the test's own act.

**This departs from the ticket, which said to add no test and do a throwaway run instead.** The reason: the project's testing rule says a ticket that re-hosts a subsystem owes a characterization test for it, and this re-hosts the ODBC connection onto .NET 10 and a NuGet package. The behaviour at risk - a private package resolving from a flat folder - is not something the compiler or the layout's `.d4l` check sees, and the ticket itself named the gap. One line of fixture change and four lines of test, in a fixture that already does exactly this for its sibling library. A reviewer who disagrees should cut it on the grounds that the `.d4l` check plus the Connection arm already cover the class, not on its cost.

What is still untested, and deliberately: nothing opens an ODBC connection or runs a statement through one. That needs a driver and a data source on the machine, so it belongs with whoever gives ODBC a live test, next to the live SQL Server and PostgreSQL device tests.

**Run:** `dotnet build Dataphor.slnx` in Debug and Release - 0 errors, 144 warnings in each, the same set as before and none from the new project - then `dotnet test tests/DAE.Server.Tests --no-build --filter "FullyQualifiedName~LibraryLoadingTest|FullyQualifiedName~HostProgramTest|FullyQualifiedName~FormCustomizationTest"` - 34 passed, 0 failed, 0 skipped, 7 s. That is the ticket's named filter: `LibraryLoadingTest` is the arm above, `HostProgramTest` reads the layout and the hosts' dependency files, `FormCustomizationTest` reads the library set. No coverage-manifest entry changed, so no coverage script was run.
