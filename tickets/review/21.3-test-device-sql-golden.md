## What landed

Two pieces, as the implement ticket laid out.

**A test-only library whose connection class records instead of connecting**, `tests/libraries/TestFramework.SQLRecorder` (assembly `Alphora.Dataphor.DAE.SQLRecorder`, project `Source/DAE.SQLRecorder.csproj`, 508 lines of C# across four files):

- `RecordingConnection` is a `SQLConnection` registered under the name `SQLRecorder.RecordingConnection`, which is what a `create device` statement's `ConnectionClass` attribute carries. It records the connection string, reports itself idle, does nothing for begin/commit/rollback and is always valid.
- `RecordingCommand` records `EXECUTE <statement>` on execute, with a `PARAMETERS` line naming each parameter's name, direction and SQL type. It records the emitted statement, not what a client would do to it afterwards (whitespace, parameter markers), because the emitted text is what a golden is for. Parameter *values* are deliberately not recorded: the name and type are the device's translation, the value is the test's own data.
- Cursors are answered only from an armed canned row (`Recorder.ArmCursor(fragment, columnName, value)`), and every other read throws with a message naming the statement and what is armed. The knowledge of what the engine asks for lives in the test, not in the recorder.
- `Register.cs` registers the plan nodes by type (as `LibraryLoadingProbe` does) plus one explicit entry for the connection class, because the by-type loop only picks up plan nodes. `Documents/Register.d4` declares four operators: `SQLRecorderStatements()`, `SQLRecorderConnections()`, `SQLRecorderClear()` and `SQLRecorderArmCursor(String, String, Integer)`. Operators rather than a public static, because the server loads the library's own copy of the assembly and a test assembly cannot reach that static.

**A device-agnostic fixture and one subclass**: `tests/DAE.Server.Tests/DeviceTranslationGoldenTests.cs` (649 lines) holds the corpus, the golden machinery and the four cases; `MSSQLDeviceTranslationGoldenTests.cs` (59 lines) supplies the device library, the `create device` statement, the golden folder name and the expressions the device refuses. The fixture derives from `InProcessTestFixture` for the server and library plumbing but keeps a session and process of its own for the whole fixture, because `SetLibrary` is session state that does not survive into the next session and the device, its tables and every query have to compile with the device's library current.

**25 golden files** under `tests/goldens/devices/MSSQL/`, each the generated SQL with the emitter's hard-coded CRLF turned into newlines (`.gitattributes` checks `tests/goldens/**` out as LF, so a CRLF golden would fail every comparison on a fresh checkout) and one newline at the end. Nothing else is normalized.

**Wiring**: the project in `Dataphor.slnx` and in the Library list of `tools/layout/Layout.csproj`; the assembly on the `ignored` list of `tools/coverage-report/areas.json`; the two fixture files in the explicit `Compile` list of `DAE.Server.Tests.csproj`.

## Use cases: how to exercise it

```
dotnet build Dataphor.slnx
dotnet test tests/DAE.Server.Tests --no-build --filter "FullyQualifiedName~MSSQLDeviceTranslationGoldenTests" --logger "console;verbosity=normal"
```

To regenerate the files after a deliberate translation change (and then read every difference before committing it):

```
DATAPHOR_UPDATE_DEVICE_GOLDENS=1 dotnet test tests/DAE.Server.Tests --no-build --filter "FullyQualifiedName~MSSQLDeviceTranslationGoldenTests.EveryGenerated"
```

That run writes the files, deletes the ones no case produces, and then **fails anyway**, exactly as `DATAPHOR_UPDATE_FRONTEND_GOLDENS=1` does.

To see the pass catch something, change one character of any golden and run it: the failure names the case, the file and the first line that differs.

## Tests added, and what each verifies

| Case | What it holds |
|---|---|
| `EveryGeneratedStatementMatchesItsGolden` | The whole corpus: 9 statement cases (the `create table` + `create unique clustered index` pair for four tables, the `alter table ... add`, the `drop table`, and the parameterized `insert` with the key-check select the engine puts in front of it) and 16 query cases, each compared character for character with its file. Also both directions of the set: a case with no golden and a golden no case produces each fail. One test rather than one per case because the statement cases have to run in order and the set comparison needs every case's answer - the same reason `FrontendDerivationGoldenTest` is one test. |
| `TheDeviceRefusesWhatItCannotTranslate` | The supported/unsupported boundary, by error code (codes are a compatibility surface): `minus` raises `SQLException.Codes.QueryUnsupported` (126125), and an expression over a table in the server's own default device raises `QuerySupportedByDifferentDevice` (126124). A refusal that came back as text instead would fail. |
| `ReadingADeviceTableIsRefusedRatherThanAnsweredWithNothing` | The property every golden above rests on: a read the recorder has no answer for throws rather than returning an empty result. A recording connection that quietly came back empty would make a device that generated nothing look like one that generated the right thing. |
| `TheDeviceConnectedOnlyThroughTheRecorder` | That the recorder is the connection the device actually used, and that the server it tried to reach is the unreachable placeholder - the evidence that these files were produced with no database server anywhere. |

No test was added for the recorder's own plumbing (that `Register.cs` registers the class, that an operator returns a string): that is wiring, and the four cases above fail loudly if any of it is wrong.

## Measurements

- **Build**: `dotnet build Dataphor.slnx` and `-c Release` both 0 errors, 144 warnings - the same count as before the change, so the new project adds none.
- **Targeted tests** (the filters the project rules ask for, named here):
  - `--filter "FullyQualifiedName~MSSQLDeviceTranslationGoldenTests"` - 4 passed, 7.5 s of wall clock for the `dotnet test` invocation, of which the four cases are about 0.2 s; the rest is VSTest startup and the fixture's server start.
  - `--filter "FullyQualifiedName~LibraryLoadingTest|FullyQualifiedName~HostProgramTest"` - 7 passed (these are what read the layout, and a new library folder changes it).
  - `--filter "FullyQualifiedName~DeviceClassAttribute"` - 8 passed, and `--filter Name=Devices` (the device coverage script) 1 passed, run because the comment-only edit to `libraries/SQLDevice/Source/SQLDevice.cs` is in that file.
  - All three combined: 12 passed, 14 s.
- **Determinism, across processes**: three separate `dotnet test` processes. Two clean comparison runs passed against the checked-in files, and a regeneration in a third process left all 25 files byte-identical (sha256 of every file matched). So nothing in the generated text varies by process: the `T1`/`T3` aliases and the `UIDX_<table>_<columns>` index names are built from per-plan counters and from names, not from object IDs, and **no normalizer is needed** beyond the line endings. If one ever is, normalize in the fixture with a comment saying what and why rather than loosening the comparison.
- **Golden review**: every one of the 25 files was read before being checked in. Worth knowing what they show - the `create table` type mapping is `integer` / `decimal(28, 8)` / `varchar(n)` / `datetime` / `uniqueidentifier` / `image` / `money`; `Boolean` maps to `integer` and both `Date` and `Time` map to `datetime`; `Length(String)` emits `DataLength`, which the device's own catalog script already explains (T-SQL's `LEN` drops trailing blanks); and the emitter's cosmetic quirks (a doubled space before `is null`, a trailing space after a `from` item) are now pinned, which is what a golden is for.

## What is deliberately not here

- **Update and delete translation.** Attempted and cut, as the implement ticket's fallback allows. The insert path works: the engine checks the key with a one-column select the case arms, then issues the parameterized `insert`, and both are in `DML.Insert.sql`. An `update` or a `delete` of a device table instead asks the device for the row itself - measured: `select "T1"."ID", "T1"."Note", "T1"."Amount" from "Ledger" as "T1" (updlock) where ("T1"."ID" = 1) option (fast 1)` - and answering that means returning typed values for every mapped column, which is a database rather than a recorder. Recorded as a `NOTE:` at `RecordingCommand.InternalOpen` naming what was asked and what could not be answered, and pointed at `test-device-live`. If a fake is ever wanted instead, the arming operator is where a multi-column typed canned row would go.
- **Device-specific scalar types.** The corpus uses only system types so that it compiles unchanged on the PostgreSQL device. So `SQLDevice.MSSQLBinary` and the `binary(n)` mapping the implement ticket listed are not covered; everything else on its type list is. If a device wants cases of its own, `Cases()` is private and static today and would become a virtual with a subclass hook - deliberately not added speculatively.
- **A README in `tests/goldens/`.** The never-edit rule is stated in the fixture's class remarks, in the failure message the pass prints, in `AGENTS.md` and on `docs/architecture/devices.md`. No tree under `tests/goldens/` has a README today, and adding one only for `devices/` would be inconsistent; say so or add both if you disagree.
- **`master = device`** in the `create device` statement, copied from the existing examples. `ReconcileMaster` is read only by startup reconciliation (`grep ReconcileMaster` finds no use in `libraries/SQLDevice`), and the mode deliberately leaves `startup` out, so it has no effect here.

## Review findings

- **Tripwire, parked as a `NOTE:` at `libraries/SQLDevice/Source/SQLDevice.cs`** (the `DDLNode` branch of `SQLDeviceSession.InternalExecute`): the connection is requested before the reconcile mode is tested, so a device whose mode leaves out `command` opens a connection and then does nothing with it. Nothing today wants otherwise and nothing was moved; the note says what would have to move if a device defined offline with `reconciliation { mode = { none } }` should be able to create its D4 tables with no server (the `catch` reads `header.Connection`, so it has to move too). This is the reason the recorder exists rather than a `mode = { none }` device.
- **Tripwire, parked as a `NOTE:` at `RecordingCommand.InternalOpen`**: what the canned cursor answers, what an update or delete asks for instead, and where a multi-column canned row would be added if one is ever wanted. See *What is deliberately not here*.
- **Deviation from the implement ticket**: its Phase 1 says the `.d4l` should require `Connection`. It requires only `System`. The recorder's classes derive from `SQLConnection`, `SQLCommand` and `SQLCursor`, which are in the engine assembly (`src/engine/DAE/Connection/`), not in the `Connection` library, so the requisite would have been a dependency the library does not have. The fixture still carries the `Connection` folder, because the device's library requires `SQLDevice` which requires `Connection`. Reinstate it if there is a reason I did not find.
- **Deviation from the implement ticket**: it says the project needs "Base and DAE and nothing else", and also that it would need `Server.csproj` for one reason. Neither reference to `Server` is needed: `DAERegisterAttribute` lives in `src/engine/DAE/Server/`, which is the **DAE** project. The project references Base and DAE only, and nothing else - in particular no SQL Server or PostgreSQL client package, which `device-mssql-port` will swap underneath this.
- **Drive-by documentation fix**: the "Converted so far" list in `AGENTS.md` omitted `LibraryLoadingProbe`, which is converted and in the solution. Added beside the new library, because the list is used as the answer to "has this been converted yet". It is still the only omission I found: `tests/libraries/TestFramework.Perf` and the other test libraries have no C# project at all.
- **No migration note.** Nothing an application, a deployment script or a custom C# extension could notice changed: no public type or member of a shipped assembly, no shipped library, no format, no error code. The only new surface is a test-only assembly with operator names that did not exist before. Say so if you read the rule differently.
- **The ninth exception-chain walker did not arrive.** `FrontendFixture.FlattenMessages` carries a `NOTE:` saying the assembly should grow one shared helper when an eighth *implementation* of the exception-chain walk appears. This fixture adds none: it calls that public static one (as `SamplesCorpusTest` already does) and `InProcessTestFixture.FindError` for the error-code cases. The count is unchanged.

## What a reviewer should look hardest at

- **The goldens themselves.** 25 files, 166 lines. They are the deliverable; the C# is scaffolding. Read each one and ask whether the SQL is what a SQL Server should be sent. Anything wrong in them is a device defect this pass has just made visible for the first time, and belongs in its own ticket rather than in an edited expected value.
- **The arming mechanism.** `SQLRecorderArmCursor` is the one place where a test tells the recorder to answer something. The risk it is guarding against is a canned answer outliving the case that armed it; `SQLRecorderClear()` clears armings as well as recordings, and the fixture clears before every statement case. Check that reasoning rather than taking it.
- **Whether the corpus has a hole worth a case.** The implement ticket's list is covered except the two items under *What is deliberately not here*. A behaviour a reviewer can name that no file shows is worth adding now, while the corpus is cheap to extend.
