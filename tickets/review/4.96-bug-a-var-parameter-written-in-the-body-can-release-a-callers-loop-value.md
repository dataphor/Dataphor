## What was wrong, in one paragraph

An operator parameter declared `var` gives the callee a slot that is an alias of the caller's: nothing is copied, and whatever the callee leaves in the parameter is written back to the caller's variable when the call returns. A body that assigns to such a parameter therefore releases the value it displaced, which is right while the caller's slot owns that value - the ordinary case. A `foreach` loop variable does not own its value: the loop lends its slot the row or element the iterator owns and goes on reading it. So where the caller passed its own loop variable, the callee's assignment released a value the loop was still using and the next iteration read a released one - `A nil was encountered where a value was expected` over a cursor, `StreamID (n) not found` over a list. Neither end could see the problem alone: the mark that says a slot holds a value it does not own (`Symbol.IsBorrowed`) is compiled per plan, and an operator is compiled once, independently of its call sites, so the callee's parameter symbol carries no mark however the caller passes its argument.

The fix gives the callee a slot it really does own. Where the argument of a `var` operand names a borrowed caller slot, the call pushes a **copy**; the callee's own assignments, and any `foreach` inside it, then release that copy, and the caller's loop keeps the row or element the iterator owns. Nothing changes on the ordinary, non-borrowed path, and `AssignmentNode`, `ForEachNode` and `CleanupOperand` are untouched.

## What changed

Four code sites, exactly as the implement ticket's design named them.

**`StackReferenceNode`** (`ImperativeNodes.cs`) gains the public field `ReferencesBorrowedSlot` beside `ByReference`, carried in `InternalClone`. The node is built per call site, which is the granularity the fact needs - the same operator may be called with a borrowed argument from one site and an owned one from another.

**`InstructionNodeBase.DetermineDataType`** (`InstructionNode.cs`), `Modifier.Var` branch, sets it from `plan.Symbols[location].IsBorrowed` right after it sets `ByReference`. That branch had already type-tested the node and read the same symbol's `IsConstant` on the line above, so nothing new was needed to reach it. The branch runs for built-in instruction nodes too; only `CallNode` acts on the flag (see the `NOTE:` on the predicate for why that is enough today).

**`Stack.IsSameValue`** (`Runtime/Stack.cs`) is now `public static` instead of `private static`, with a sentence saying who else asks. The clause of the `NOTE:` on `CallNode.ReferencesAnEarlierOperandsSlot` that asked for this test to be shared out is retired; the rest of that `NOTE:` - the one value such a call still loses - is unchanged and was reflowed only because the sentence shortened.

**`CallNode.InternalExecute(Program, object[])`** (`ImperativeNodes.cs`) is where the work is, in two halves.

- The push loop gains a sibling arm to the existing `ReferencesAnEarlierOperandsSlot` one: a new private `ReferencesABorrowedSlot(int)` (a `StackReferenceNode`, `ByReference`, and `ReferencesBorrowedSlot`), and a copy pushed for such an operand, kept in a lazily allocated `object[] borrowedCopies` so the hand-back can see it. The loop body became a block rather than a one-statement ternary; behaviour on the non-borrowed path is identical.
- The hand-back in that method's `finally` reconciles each borrowed operand. Where the slot still holds the copy, nothing in the body wrote to the operand: the copy is this call's to release, and `arguments[index]` goes on naming the caller's own value, so `CleanupOperand`'s write-back stores the caller's value back into the caller's slot - a no-op, exactly what it does on the unchanged non-borrowed path. Where the body did write, it released the copy itself and `arguments[index]` takes the slot's final value as before, so the caller sees the operator's output. The same-value test is `Stack.IsSameValue`; `borrowedCopies == null` short-circuits the whole thing for every call that has no such operand.

**Ordering note worth a reviewer's eye.** The borrowed arm is checked *before* the repeat arm, so an operand that is both - one borrowed variable passed twice by reference - takes the borrowed arm and is reconciled rather than left to the last write-back. That is a deliberate choice (it is strictly better in that shape: the caller ends up with its own value rather than an unreleased copy), it is stated in a comment at the site, and it is reasoned rather than tested - see *For the reviewer*.

**Two `NOTE:` edits in `AssignmentNode`.** The owned branch's `NOTE:` named this ticket as the open defect behind its release; that sentence is gone. The borrowed branch's `NOTE:` - the accepted tradeoff that an assignment to a loop variable leaks what it displaces - now also says that the `var` write-back reaches the same slot the same way and leaks the same one value, and points at the reconcile site.

## Tripwires parked

- **The residual leak**, as the implement ticket directed: not a ticket. The `var` write-back hands the caller's loop variable the operator's output and the next iteration overwrites that slot with a plain store, so one value per iteration is leaked - the same accepted tradeoff as a direct assignment to a loop variable, and measured equal to it by the test above. Recorded by extending the `NOTE:` on the borrowed branch of `AssignmentNode`, with a pointer from the reconcile site in `CallNode`.
- **A built-in C# instruction node with a `var` operand** does not act on the mark, because such a node never pushes a slot and never releases the value it was handed - it returns a replacement, which `CleanupOperand` writes back. A `NOTE:` on `ReferencesABorrowedSlot` says so, so that a future built-in which did release its `var` operand's input meets the rule rather than a silent double release.

## For the reviewer

- **`AssignmentValueOwnershipTest.cs` is now 1,559 lines**, past the roughly-1,500 threshold its own head `NOTE:` sets for splitting. The split was left alone deliberately, as the implement ticket directed: that `NOTE:` defers it while sibling ownership tickets still have cases in flight against the file, and `bug-row-equality-leaks-the-rows-it-compares` is still open in `tickets/fix/` and will add to this file. The new case sits immediately after `AForEachOverAnOperandLeavesTheCallersValueAlone`, the case it is the limit of.
- **`operand-ownership.md` has 108 words of headroom.** The next ticket to add to that page may have to split it; nothing here forces that now.
- **The one-borrowed-variable-passed-twice shape is reasoned, not tested.** `F(var LB, var LB)` where `LB` is the caller's loop variable now takes the borrowed arm for both operands, so both copies are reconciled and the caller keeps its own value; the pre-existing one-value loss that the `ReferencesAnEarlierOperandsSlot` `NOTE:` describes for the general repeat shape is unchanged in substance. No case covers it, because a call that always loses one of its two writes is a programming error either way and the existing fixture case for the repeat shape (`TheSameVariablePassedTwiceByReferenceStillRuns`) is outside a loop. Worth a second opinion on whether the ordering should be the other way round.
- **Table-typed `var` parameters: measured, not covered by a committed test.** `DataValue.CopyValue` on a table value allocates a native table, and the `NOTE:` at the head of `TableValue` records (2026-11-24) that such a copy's disposal does nothing - so a table-typed borrowed `var` operand looked like it might trade one leak for another. It does not: a throwaway probe in this fixture, a `foreach` over a list of two tables carrying five stream-backed rows each, passing the loop variable to a `var` table parameter, both read-only and assigning, **ran correctly and left 0 streams behind** in both shapes. The probe was deleted. A committed case was not added because the shape appears nowhere in the corpus and the measurement says there is nothing to pin; a reviewer who disagrees has the script above to work from.
- **`Binary` and rows of `Binary` only, no `Graphic`.** Same path through the value manager, and the whole fixture is `Binary` for the same reason, but it is a gap rather than a decision.
- **One narrow exception path is not handled.** If `DataValue.CopyValue` itself threw partway through the push loop, a copy already pushed would be discarded by the window pop without being released. That shape is pre-existing on the repeat-operand arm, needs a copy to fail (which for a stream means the stream is already missing - the very defect being fixed here), and leaks on an error unwind only; no code was added for it and no `NOTE:` was written, because the claim would be about a path neither arm has ever been seen on.
- **Source hygiene held.** `ImperativeNodes.cs` and `AssignmentValueOwnershipTest.cs` still tabs, CRLF, UTF-8 byte-order mark; `InstructionNode.cs` and `Stack.cs` still tabs, CRLF, no byte-order mark; both docs still CRLF, no byte-order mark; every file still ends in a newline. `git diff --check` reports the CR of every added line as trailing whitespace, which is what it does for every commit in this repo, not something introduced here.
