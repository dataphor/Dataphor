## What landed

Tests and documentation only. **No engine source changed** - `git diff` touches no file under `src/` or `libraries/`. The behaviour was already right; what was missing was anything that would notice if it stopped being right.

Three things, which were the three gaps `debt-library-upgrades-coverage` parked here.

**A new C# fixture, `tests/DAE.Server.Tests/LibraryUpgradeRestartTest.cs` (3 cases, about 14 s).** Built on the `LibraryAttachTest` pattern: a `TestServerInstance` per case, libraries the server itself created, `Server.Stop()` then `Server.Start()`. Each case registers a library at 1.0.0, saves an upgrade script for 1.0.1 at an explicit version (which moves neither version number), stops the server, raises the library's **descriptor** version on disk, starts the server again, and then upgrades.

**How the descriptor is raised, and why that way.** The `.d4l` is rewritten while the server is stopped, read and written back through the engine's own BOP deserializer and serializer (`Schema.LibraryUtility.LoadFromStream` and `SaveToFile`) rather than as text, so the fixture pins no idea of the descriptor format of its own. That is the honest stand-in for an installer unpacking a new release over the old folder, because the *files* are what claims the new version. `SetLibraryDescriptor` on the running server is not: it refuses to raise a registered library's version at all.

**The first case is the premise of the whole coverage script.** `LibraryUpgrades.d4` cannot produce a pending upgrade honestly, so each of its sections stands in for "the new files arrived and the server was restarted" with `update LibraryVersions set { Version := ... }`. What makes that legitimate is one line of `LibraryUtility.LoadLibrary`: it reads the recorded version before loading and writes *the same value* back afterwards, so a restart does not swallow a pending upgrade. Nothing pinned it. The case asserts, after the restart, that the descriptor version is 1.0.1, that the recorded version is **still** 1.0.0, that `UpgradeRequired` is true, that the library is still registered, and then that `UpgradeLibrary` applies the upgrade and records 1.0.1.

That negative assertion is the point, and it is **measured, not assumed**: with `LoadLibrary`'s last line changed to record `library.Version` instead of the value it read, all three cases of the fixture fail - the first on the recorded version (`Expected "1.0.0.*" / But was "1.0.1.*"`), the other two on the upgrade no longer being pending at all. The probe was applied, built, run and reverted; `LibraryUtility.cs` is byte-identical to `HEAD`.

**Two cases carry a payload a release really ships**, rather than the one table in the default memory device that every section of the coverage script upgrades:

- a **device and a table in it**: the upgrade runs `create device PayloadDevice class "System.MemoryDevice"`, creates a table in that device and inserts a row. The row reading back afterwards is what says the device started, and a device created inside the single transaction the upgrade machinery opened is something no section of the script reaches. The device's catalog name was measured, not chosen: `UpgradeDevicePayload.PayloadDevice`.
- a **form document**: the upgrade calls `Frontend.CreateAndSave(..., 'dfd', ...)` on a library that requires `Frontend`. This payload goes through the Frontend device rather than the catalog, and the case asserts the document exists, loads back character for character, and **is a file** at `<library folder>\Documents\PayloadForm.dfd` - which is the second reason this fixture is C#, a script having no way to see a server-side path. The instance carries `Frontend` and `SimpleDevice`.

**A tenth section in `LibraryUpgrades.d4` (+50 lines)**, for `UpgradeLibraries()` across several libraries. Two libraries that require nothing of each other, both pending, the first one's upgrade raising. It asserts that the error carries the failing script's own message, that the error **does not name** the second library, that the failing library stayed at the version the run started from, that the second library is still at its own recorded version, that the table its upgrade would have created does not exist, and that it still reports an upgrade as required. The ordering is registration order, which the pass itself measures: had the two been visited the other way round, the second library would have been upgraded and its table would exist. Both closing sweeps carry the two new library names. The script still runs in 3-4 s against a 120 s default timeout, so its manifest entry needed no `timeoutSeconds`.

**Documentation.** `docs/architecture/libraries-and-class-loading.md` gained a sentence on the restart preservation now being pinned (with the sensitivity measurement) and a short paragraph on what a new version's payload may be and the one thing a restart cannot pick up. 1,262 words of the 1,500 cap; `python tools/docs-size-check/check_size.py` reports 13 files, 0 over. The plan's WS7 `library-upgrade-scripts` row is marked **Done** and says which gaps closed and what stays open. No `docs/migration-notes.md` entry is owed: nothing an application, a deployment script or a C# extension could notice changed.

## The gap this did not close, and cannot in one process

**An upgrade whose payload needs a new build of the library's own assembly.** The ticket asked for an attempt and for an honest report if one process cannot host it. It cannot, for two separate reasons, and both are written into the fixture's remarks and the architecture page:

- The realistic case is unreachable in principle. Assemblies are never unloaded, and `Assembly.LoadFrom` on another copy with the same identity returns the instance already loaded - so a `Server.Stop()`/`Start()` in this process goes on running the old build. A real deployment picks up a new one because the installer restarts the Windows service, not because the `Server` object restarted. A case over it in this fixture would look like coverage and prove nothing.
- The narrower case - a version that *adds* an assembly where the old version had none - would work, that load being the only one, but there is no assembly in the suite to give it. Every library assembly in the runtime layout belongs to a library that registers it, and borrowing one (`LibraryLoadingProbe`'s was the candidate) would repoint the process-wide `LibraryAssemblyResolver` entry for that assembly - keyed by `Assembly`, and **overwritten** on registration - at this fixture's temporary folder, which would make `LibraryLoadingTest`'s own cases depend on test order. An assembly of this fixture's own means a new project in the build, in the layout's library list and on `tools/coverage-report/areas.json`.

**For the reviewer to weigh:** whether that gap clears the filing bar as a `debt-` ticket. The argument for: it is a real customer scenario (a release that ships a changed assembly), it has a vehicle (the suite's out-of-process harness, `tests/TestHarness`, which today has no notion of restarting and reloading), and nothing on the board owns it - `debt-test-shipped-host-executable` is about launching the shipped executable at all, not about an assembly across a restart. The argument against: the cost is a new test library assembly plus a restart mode in the harness, to cover one branch of library loading that `LibraryLoadingTest` already covers from the other side. This stage left it as prose rather than filing it unilaterally.

## Things to look at closely

- **Is the first case's negative assertion the right one?** It asserts the recorded version is unchanged after the restart. The alternative framing - assert only `UpgradeRequired` - would be weaker, because `UpgradeRequired` is derived from the two versions and a fixture that got both wrong in the same direction would still pass. The measurement above says the current framing is sensitive; check that it is sensitive to the *right* thing.
- **The coverage section's dependence on registration order.** `UpgradeLibraries()` visits `Catalog.LoadedLibraries` in insertion order through `GatherRequisites`, which for two independent libraries is registration order. That is an engine detail rather than a stated contract. If it ever changed the section would fail loudly with a message naming what happened, which is the behaviour wanted - but the comment in the script is the only place that says the order is not a contract.
- **`Frontend.LoadDocument` round-tripping the form character for character.** It passed, so the document survives the write-and-read through the Frontend device unchanged, including the XML attribute quoting. Worth confirming that is a property of the device rather than an accident of this particular string (the form deliberately contains no apostrophe, so the D4 literal nesting in the upgrade script needed no doubling).
- **The three-second cost of `UpgradeRequired(...)` before each payload upgrade** is a guard, not an assertion of the case's subject: it fails the payload cases early and clearly when the restart preservation is what broke, rather than leaving them failing on a missing table. Decide whether that duplication across three cases is worth keeping.
- **`Could not delete ...; the next test run deletes it`** appears for the form-document case and for the coverage template, naming `Alphora.Dataphor.Frontend.Server.dll` and `Alphora.Dataphor.DAE.Connection.dll`. That is the documented behaviour of the suite for any instance carrying a library with an assembly (`AGENTS.md`, under the test-run description) and not new here, but it is new for *this* fixture, so it is worth knowing it is expected rather than a leak.
- **`DATAPHOR_TEST_LOGGING=1` keeps the instance folders**, and a kept folder's `.d4l` then holds the raised version rather than the version the runtime layout's copy carries. The folders are per-run copies, so that is a difference to read rather than to repair; the fixture's remarks say so.
