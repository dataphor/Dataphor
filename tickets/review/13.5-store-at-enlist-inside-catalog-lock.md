description: When a table is first used inside an application transaction while a statement is already running (for example a script run through the D4 Execute operator), the engine made the transaction's private copy of the table while holding the catalog lock and then waited for the catalog store's write lock, an order that can deadlock and that failed a Debug build with an internal error. The copy writes nothing to the store, so the early store begin is now skipped when the catalog lock is already held.

## What was wrong

An application transaction (AT) is a long-lived editing transaction. The first time a statement references a table while the process has joined an AT, `ApplicationTransaction.AddTableVar` takes `lock (process.Catalog)` and, inside it, `ApplicationTransactionDevice.CopyTableVar` compiles and runs `create table .AT_<name>` (plus `alter table` / `attach` statements) for the AT's private copy. Every DDL node's `DDLNode.InternalBeforeExecute` calls `ServerCatalogDeviceSession.BeginStoreWriteTransaction`, which exists (K10, `store-sqlite-concurrency`) to take the store's write lock *before* the catalog's lock. Called inside the catalog's lock with a process transaction open and no store transaction yet, it did the forbidden wait: Debug failed with `Internal Error: The catalog store's write transaction is beginning inside the catalog's lock.`; Release could deadlock until the busy timeout (130103) against a session holding the store lock and wanting the catalog lock.

It needs a statement that compiles inside an already-open process transaction, which is what `Execute('…')` does; a batch run directly on a process compiles before its implicit transaction begins, so it never hit this.

The copy's objects are AT objects (`IsATObject`), which `CatalogDeviceSession.ShouldSerializeCatalogObject` never writes to the store, so the copy needs no store transaction at all.

## The change

- `ServerCatalogDeviceSession.BeginStoreWriteTransaction` (`src/engine/Server/Device.Catalog/ServerCatalogDeviceSession.cs`, about line 181): added `&& !Monitor.IsEntered(Catalog)` to its condition. Inside the catalog's lock the early begin can no longer come before that lock, so it does nothing. A statement there that genuinely writes the store still goes through `AcquireCatalogStoreConnection(true)` → `BeginStoreTransactions`, whose Debug assertion is unchanged and still catches it.
- Comments updated to say this: the remark on `AcquireCatalogStoreConnection`, the comment in `BeginStoreTransactions`, a new comment above `BeginStoreWriteTransaction` (the existing `NOTE:` about processes with implicit transactions off is kept below it), and the comment on `DDLNode.InternalBeforeExecute`.
- New `NOTE:` (tripwire) at `ApplicationTransaction.AddTableVar`: the copy's DDL depends on writing no store rows; if AT objects ever become persistent, the store write must begin before that lock.
- `docs/architecture.md`, lock-order bullet under **Store transactions**: one sentence on DDL already inside the catalog's lock skipping the early begin.
- No migration note: nothing an application or extension can observe changes, except that the internal error no longer occurs.

## Known gaps and things for the reviewer to check

- The test only fails before the fix on **Debug**: in Release there is no assertion, and with a single session there is no contention for the store lock, so the forbidden wait succeeds at once. The Release deadlock (a second session holding the store's write lock and wanting the catalog lock) is not reproduced by any test; it is the same shape `CatalogStoreConcurrencyTest` covers for ordinary DDL, and building a reliable two-session interleaving for the AT path did not seem worth the test's run time and flakiness.
- Only the `select` form of the reproduction is tested; the ticket's original cursor form (`Execute('begin var LCursor : cursor(typeof(T)) := cursor(T capabilities { navigable, updateable }); LCursor.Close(); end;')`) goes through the same `AddTableVar` path and was verified in the fix stage, not re-tested here.
- `Monitor.IsEntered(Catalog)` skips the early begin for *any* DDL that runs inside the catalog's lock, not just AT copies. The fix-stage analysis knows of no other DDL that runs inside that lock and writes the store; if one exists, it would now wait for the store lock inside the catalog lock in Release (as it did before K10) and fail the assertion in Debug. Worth a look at the other `lock (process.Catalog)` sites in `ApplicationTransaction.cs` (about lines 920, 993, 1389, 1479): they also copy AT objects (operators, which already run in a loading context, and table maps), so they should be covered by the same reasoning.
- Rejected alternatives (begin the store transaction before `lock (process.Catalog)` in `AddTableVar`; check the AT creation context in `DDLNode`; per-node AT checks) are described in the fix stage's reasoning, summarized in the `NOTE:` comments; none were tried here.
