## The two answers the ticket asked for

**Does a property equal to its `[DefaultValue]` get written on save? No.** `Serializer.ShouldPersist` (`src/engine/Base/BOP/Serializer.cs:108-126`) returns false when the value equals the attribute's value, and `WriteValue` writes nothing. Confirmed by running: an entry with `ShouldListen` true and the other three at their defaults saved as `<serverconfiguration catalogstoreclassname="" catalogstoreconnectionstring="" instancedirectory="" librarydirectories="…" name="Dataphor" portnumber="8061" />` — four attributes absent. The five settings with no `[DefaultValue]` are always written, and a null string is written as `""`. The section says this, and the example illustrates it with a `shouldlisten` that is present on one entry and absent from the other.

**What a save does to a file an earlier release wrote.** It drops the settings the server no longer has, drops the four `[DefaultValue]` settings that are at their defaults, and drops any entry that could not be read at all (nameless, or a duplicate name). The section says all three. No test was added for the save side: `protocol-corewcf-host-prepare` already weighed one and declined it on the grounds that it would pin BOP rather than anything the product changed. **Do not re-file it** — nothing about that reasoning has changed, and the behaviour is now confirmed by having been run rather than only read.

## Where I disagree with the ticket, and wrote something else

**`ShouldListen`.** The ticket's table said it "[t]urns off this instance's registration with the machine's listener, so clients must name its port rather than discover it". That is not what the code does. The listener service answers instance lookups by loading the instance list file (`ListenerService.GetConfiguration`), so *every* entry in the file is discoverable through whichever process is hosting the listener; `ShouldListen` only decides whether *this* server tries to host it (`DataphorServiceHost.cs:168`). Setting it false on one instance therefore does not hide that instance as long as another instance on the machine hosts the listener. The section says this, and also says the consequence the ticket was reaching for: where no process hosts the listener, clients cannot look instances up by name. **Worth re-checking** — it is the one place the section contradicts its ticket.

## Where the section is deliberately weaker than it could be

- **Port 0.** The section says an entry written by hand without `portnumber` reads as 0, which "is not a port a client can be directed to", and to always give one. I did not start a server on port 0 to see what happens. `NetTcpServiceHost.Build` passes the number straight to Kestrel's `Listen` with no guard, so a port-0 server would plausibly bind an operating-system-assigned port while its registered endpoint address and the listener's answer both say `:0` — but that is inference, so the section does not claim it. If a reviewer wants the stronger sentence, it needs a run. (The machine's own 3.x instance list has two entries with `portnumber="0"`, so this is not hypothetical for upgraders.)
- **`DATAPHOR_INSTANCE_DIRECTORY`.** Described as `InstanceManager.ResolveInstanceDirectory` implements it. I confirmed the resolved default by running, not the redirection itself — `host-instance-directory` owns and tests that.
- **Error 113248** for a device setting that cannot be applied: read from the code, not reproduced.
