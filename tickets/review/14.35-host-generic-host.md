## What landed

The server has one host program again, and it runs. `DataphorHost` in `src/hosts/Host` (assembly `Alphora.Dataphor.DAE.Host`) owns the process: it parses the command line, registers or removes the Windows service, or builds and runs a .NET Generic Host around a `DataphorServiceHost`. `src/hosts/DAEServer/Program.cs` and `src/hosts/DAEService/Service.cs` are each a single `Main` that calls `DataphorHost.Run(args)`, so `DAEServer.exe` and `DAEService.exe` are the same program under the two names existing scripts and service registrations use. Both projects are now SDK-style and in `Dataphor.slnx`, and both are in the runtime layout, which has an executable in `bin/` for the first time.

Walkthrough of the new code, in the order a reader should take it:

- **`HostCommandLine.cs`** — one parser for both executables. `Parse` returns a command (`Run`, `Install`, `Uninstall`) and an instance name that is never null. It reproduces the two hand-written parsers it replaces, including the quirk that a trailing `-n` with no value after it yields the default instance rather than an error.
- **`DataphorHost.cs`** — `Run` dispatches; `Install`/`Uninstall` call `ServiceUtility` and report one line; `RunServer` builds the host and runs it. `BuildHost(instanceName, startServer)` is the host: `UseWindowsService`, the logging configuration, a sixty-second `HostOptions.ShutdownTimeout`, and one `IHostedService` (`DataphorHostedService`, same file) that owns the running server for the life of the host.
- **`ConnectionManager.cs`** (the one edit outside the hosting code) — the idle watcher thread is now a background thread, with a `NOTE:` at the site saying why and that `port-abandoned-session-cleanup` otherwise owns the class.
- **`PathUtility.GetInstallationDirectory()`** — the second level it popped for a binaries folder named `bin` is gone. That folder shape (the 3.1 source tree's per-project output) no longer exists, and the pop put the runtime layout's default library directory one level too high.
- **`Server.csproj`** — took `<FrameworkReference Include="Microsoft.AspNetCore.App" />` and dropped the now-prunable `System.Diagnostics.EventLog` package reference. This is the choice `protocol-corewcf-host` left open: it takes the audit-flagged ASP.NET Core 2.3.10 assemblies out of the layout's `bin/`, which a host running from there would otherwise ship.
- **`Directory.Build.targets`** — `GetDataphorLayoutItems` now also returns an executable project's application host, `.deps.json` and `.runtimeconfig.json` (and deliberately not `.runtimeconfig.dev.json`).

Deleted: `src/hosts/DAEServer/CommandLineArguments.cs` (the vendored parser nothing in that project called - known defect K23's copy there; the live copy in `D4Runner` stays), `src/hosts/DAEServer/app.config` and `src/hosts/DAEService/app.config` (the second one being K12's other half).

## One deviation from the implement ticket, and why

The ticket specified `BuildHost(string instanceName, Func<DataphorServiceHost> hostFactory)` where the factory only *creates* the host and `StartAsync` calls `DataphorServiceHost.Start()`. That cannot be tested as written, and the ticket's own test requirement exposes it: the parameterless `Start()` reads the machine-wide instance list and, when the name is not in it, **adds a default instance and saves the file**. A test must not touch that file, and `Start()` is not virtual, so a factory that only creates a host gives a test no way in.

So the delegate's contract is "create, configure and start the server, and return it", named `startServer`. The program passes a factory that does `new DataphorServiceHost { InstanceName = … }` then `Start()`; the tests pass one that starts from a `ServerConfiguration` of their own through the existing public `Start(ServerConfiguration)`. Everything else the ticket asked for holds: the start is synchronous, it happens only from `StartAsync` (the test asserts the server is not running until the host is started), a failure is logged and rethrown, and `StopAsync` is null-safe. The parameter's doc comment says all of this. `host-instance-configuration` is the work item that makes this moot, by giving the program a way to name a configuration file; the plan's new *Generic host* subsection records that hand-on.

## Gaps - read these before reviewing

- **The elevated service checks were not run.** This session is not elevated, and they change machine state. They are the manual check `host-service-registration` deferred to this work item, and they are still owed: from an elevated prompt, against the built layout, `DAEService.exe -i -n <test instance>`; check the entry, display name and start mode in the services snap-in; start and stop it there; check the instance's log under `%ProgramData%`; `DAEService.exe -u -n <test instance>` and check it is gone. Then the same once through `DAEServer.exe -i` to confirm the two names behave identically, and once with an instance name containing a space. Nothing in the code path differs from what was exercised unelevated except the service control manager calls themselves and the Windows service lifetime, which no automated test on an unelevated machine can reach.
- **Ctrl+C was not literally pressed.** The stop above was a console break delivered to the process group, which reaches the same `ConsoleLifetime` registration (`SIGQUIT` beside `SIGINT`). A human pressing Ctrl+C is worth one confirmation during the elevated pass.
- **No out-of-process test of the layout's host.** It would need a test instance written into the machine-wide `ServerConfigurations.config`, which no test should do. `host-instance-configuration` owns the configuration-file switch that makes it cheap; the ticket said not to add it here, and it was not added.
- **`tests/DAE.Client.Tests/OutOfProcessTestFixture.cs` starts `DAEServer.exe` with `RedirectStandardInput`** and stopped it by closing the pipe. That no longer stops a host. The project is unconverted and does not build, so nothing fails today; `test-client-server` owns it and the plan's new subsection says so. Not edited here.
- **`src/engine/Server/Service/ConnectionManager.cs` is `port-abandoned-session-cleanup`'s file.** The change here is two lines and a `NOTE:`; expect a small conflict if that ticket has a branch.
- **An unexplained observation, not chased.** Holding `0.0.0.0:8061` with a plain socket (`SO_REUSEADDR` off) did **not** stop Kestrel from binding the same port - the host started and served normally. The plan records the opposite for one Kestrel host against another (`IOException`, "address already in use"), so the two cases differ. If a second instance really can bind an instance port another process holds, it would serve nothing and say nothing, which matters for the "two instances on one machine" story. It was the test rig that was wrong rather than the product, as far as this ticket established; worth one person's judgment about whether it deserves a ticket of its own.

## Smaller judgment calls made here, all open to being reversed

- **`Alphora.Dataphor.DAE.Host`'s string table.** Two entries that nothing read and that contradicted the new behaviour are gone (`ServiceRunning`, whose text told the operator to press Enter, and `ServiceStopping`). `ServiceInstalled` and `ServiceUninstalled` were added for the registration confirmations. `InvalidCommandLine` was rewritten: it was a ragged multi-line value naming `DAEService` alone, which `DAEServer` now prints too. `ServiceStarting` and `CCreatedSettingsFile` are now unused - the first is what `ServiceUtilityTest` reads to pin the resource's manifest name, the second was already dead. `tool-cli-server-commands` owns the operator-facing text next.
- **Host lifecycle messages are message templates in code, not resources.** They carry the instance name as a structured value. The server's own log file and event-log writes are untouched, as the ticket required.
- **`System.Diagnostics.EventLog` was removed from `Directory.Packages.props`** as well as from `Server.csproj`: no project references it any more (the ASP.NET Core shared framework provides it). A later project that needs it adds the line back.
- **A run failure is reported once, not three times.** The hosted service logs it with the instance name and the Generic Host logs it again as "Hosting failed to start"; `RunServer` therefore returns 1 without printing a third copy. It still prints and returns 1 if `BuildHost` itself throws, when no logger exists yet.
- **`AddSimpleConsole` with `SingleLine = true`**, as the ticket specified, so the console and the instance log read alike. The cost, seen in the second-host run: an exception's stack trace arrives as one very long line. The instance log has the same error in its own format.
- **`[SupportedOSPlatform("windows")]`** on `DataphorHost`, on each executable's `Main` and on `HostProgramTest`, following `ServiceUtilityTest`'s existing convention, so the Windows-only service and event-log calls raise no `CA1416`.
- **`tools/net-spike/README.md`'s `DAE.Client.Tests` row** said it was blocked by a missing NUnit package reference; the run shows two missing types in its fixture instead, and the row now says that.
- **`docs/users-guide/dataphor-service.md`'s "Installing Multiple Instances"** was rewritten around named instances: its old procedure turned on the `DAEService.exe.config` route that K12 shows never worked, and told the operator to copy the whole service directory. The rest of that page is `docs-admin-guide`'s.
