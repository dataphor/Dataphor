## What landed

**The defect, reproduced before anything was changed.** `MSSQLCommand` describes a parameter to SQL Server in two places, and the cursor location decides which one a statement goes through: `PrepareParameters` configures the provider's own `SqlParameter` for the client-side path, and `GetParamTypeDescriptor` writes a T-SQL type into the `@paramdef` string that `sp_cursoropen` is given for the server-side path. Both said single-byte - `varchar(n)` for a string, `text` for an `SQLText` - and SQL Server converts such a value to the database's collation code page on its way in, so every character that code page had no room for was stored as a question mark, with no error raised and nothing left to read back. Measured on SQL Server 2016 SP1 Express LocalDB (13.0.4001.0), database collation `SQL_Latin1_General_CP1_CI_AS`: the probe `"中文 αβγ Привет é"` came back as `"?? aß? ?????? é"` - Chinese and Cyrillic gone outright, Greek best-fitted to Latin letters, the one accented Latin letter intact because code page 1252 holds it. All four of the new non-ASCII cases failed that way before the change and pass after it.

**The fix: both descriptions moved together.** `PrepareParameters` says `SqlDbType.NVarChar` and `SqlDbType.NText`; `GetParamTypeDescriptor` says `nvarchar(n)` and `ntext`. They had to move together or the device's behaviour would depend on whether its statement happened to begin with `select` (`DetectCursorLocation`).

**The precedence question was settled on measurements, not on judgement.** An `nvarchar` parameter is the higher-precedence type, so SQL Server converts the *column* rather than the parameter, which can turn an index seek into a scan. Measured on the same server, 200,000 rows, an index on a `varchar(50)` column, one row matched:

| Parameter | Column's collation | Plan | Logical reads |
|---|---|---|---|
| `varchar(11)` | `SQL_Latin1_General_CP1_CI_AS` | Index Seek | 3 |
| `nvarchar(11)` | `SQL_Latin1_General_CP1_CI_AS` | Index Scan with `CONVERT_IMPLICIT(nvarchar(50), column)` | 625 |
| `nvarchar(11)` | `Latin1_General_CI_AS` (a Windows collation) | Index Seek through `GetRangeThroughConvert` | 3 |

So the regression is real and specific to **SQL** collations, and a deployment that meets it has two remedies, both measured: declare the column `nvarchar` (the device already maps `nvarchar` and `nchar` to D4 `String`, so no D4 changes), or give the column a Windows collation. Unicode was kept, because a character lost on the way in cannot be recovered where a slow query can be seen and fixed, and the alternative - sending Unicode only where the receiving column is `nvarchar` - means carrying each column's native type down to its parameter, which neither `SQLParameter` nor the SQL syntax tree the devices build has any room for. The decision, the measurement and the revisit condition are in an accepted-tradeoff `NOTE:` on `GetParamTypeDescriptor`; the remedies are in `docs/migration-notes.md`.

**`SQLTextType` was changed too, and the 2008 question at the site is answered.** `GetParamTypeDescriptor` carried `// Q: Should this be NText or text` since 2008. It is `ntext` now, for the same reason, and with none of the precedence cost - a `text` column can be neither compared nor indexed in T-SQL, so no plan can change shape over it. Two things were checked against the live server first, because the argument depends on them: `ntext` is accepted as an `sp_executesql` parameter declaration, and an `ntext` parameter inserts into a `text` column without an explicit conversion. The device reconciles `ntext` columns to the same D4 `SQLText` scalar type it maps to `text` (`MSSQLDevice.FindScalarType`), so an application mapping onto an existing `ntext` column was losing characters the column could hold; that is the case the change rescues, and a `text` column loses what a `text` column cannot hold either way.

**One latent break came with the change and is guarded.** `nvarchar` counts characters to 4,000 where `varchar` counted bytes to 8,000, so a width that was a legal `varchar(n)` is not always a legal `nvarchar(n)`: a D4 string column with a `Storage.Length` tag between the two limits produced `nvarchar(5000)`, which the server refuses outright ("The size (5000) given to the parameter '@PP1' exceeds the maximum allowed (4000)"). `NVarCharDescriptor` substitutes `nvarchar(max)` past the limit, and for a length of zero or less. Verified load-bearing: with the guard removed, the server-side case fails with exactly that error while the client-side case still passes, because the provider maps a `Size` over 4,000 to max itself.

**Read and write paths now agree about the same column.** `ServerCatalogDevice.TranslateScalarParameter` passes `SQLStringType(200)` for catalog reads against `nvarchar(200)` columns; it needed no change, and the parameter it produces is now `nvarchar(200)` against an `nvarchar` column rather than `varchar(200)`. Neither form scans - a `varchar` parameter against an `nvarchar` column converts the *parameter*, the harmless direction - so this is a correctness alignment, not a plan change.

**The plan-per-string-length question was measured and left alone.** One insert statement executed with strings of five distinct lengths left 6 cached plans behind; the same five values with one fixed declared size left 2. So the churn is real, and bounded by the widest catalog text column, `nvarchar(500)`. It arises at `SQLStoreConnection.NativeToParameter`, which declares each value's own length, not at `DotNetCommand.SetParameters`, where the ticket pointed: that method only grows a declared size that is too small for its value, and neither caller ever produces one - a device declares the *column's* width (`SQLString.GetSQLType` over the `Storage.Length` tag) and the store declares the exact length. It was not changed because the fix worth having is to declare the column's width, and `NativeToParameter` is handed a name and a value but no column; bucketing the length would collapse the entries but would change what every store declares for every string on the strength of a plan-cache count no deployment has reported as a cost. The measurement and that reasoning are in the `NOTE:` there, and `SetParameters` now carries one line pointing at it.

**Device translation goldens are unchanged, and that is expected rather than lucky.** The golden pass runs the device over `TestFramework.SQLRecorder`'s recording connection, which prints the device's own abstract SQL type (`String(30)`) and never reaches `MSSQLCommand`. `git status tests/goldens/` is empty after the change.

That is 24 passed and 21 skipped: nothing that needs a server runs, and each skip says which variable to set. With a server, which is the only way `MSSQLCommand` is driven at all:

```
sqllocaldb start MSSQLLocalDB
DATAPHOR_TEST_MSSQL='Data Source=(localdb)\MSSQLLocalDB;Integrated Security=SSPI' dotnet test tests/DAE.Server.Tests --no-build --filter "FullyQualifiedName~StoreContractTests|FullyQualifiedName~MSSQLTextParameterTest|FullyQualifiedName~MSSQLStoreConnectionStringTest|FullyQualifiedName~MSSQLDeviceTranslationGoldenTests"
```

45 of 45 passed, 5 s, on the development machine. To see the defect itself rather than its absence, revert the two `SqlDbType` lines and the two descriptor strings in `MSSQLCommand.cs` and run the same command: the four non-ASCII cases fail with the probe string beside what came back.

| `MSSQLTextParameterTest.AStringParameterTooWideForNVarCharStillReachesTheServer` (2 cases) | that a parameter declared wider than `nvarchar`'s 4,000-character limit is still describable and still carries its value, on both paths - the `nvarchar(max)` substitution above, which the server-side case fails without |

The three measurements behind the decisions - the plan shapes, the two conversions `ntext` depends on, and the plan-cache counts - were made by hand against LocalDB and are **not** tests. They are recorded where the decisions are: the `NOTE:` blocks at the two sites, this handoff, and the plan's WS7 row. Turning the plan-shape one into an assertion would be a performance test against a particular server and collation, which is `device-sqlserver-version-matrix`'s territory if anyone wants it.

Why no test lower than these: the defect is in what the connection class tells the server, so the lowest layer that shows it is a live SQL Server. There is no in-process substitute - the recording connection used by the golden pass stops above `MSSQLCommand` by design - and a D4 script through the engine harness would need a live SQL Server device, which is `test-device-live`'s.

## What this does not show, and other things to know

- **One server, one collation.** Everything live was run against SQL Server 2016 SP1 Express LocalDB (13.0.4001.0) with collation `SQL_Latin1_General_CP1_CI_AS`. Nothing was run against 2019 or 2022, against a case-sensitive collation, or against a collation whose code page is not 1252 - and the collation is what decides which characters a `varchar` column would have lost, so it is part of the measurement rather than background. `device-sqlserver-version-matrix` owns the matrix and already carries a line telling it to record the collation with every row.
- **The device itself is not driven live by anything.** The new fixture drives `MSSQLCommand` through `MSSQLConnection`, which is the code the device and the store share, but no test writes a row to a SQL Server table *through the device* and reads it back. `test-device-live` owns that, and it is where the `ntext` half would get its end-to-end proof: no test writes an `SQLText` value to a `text` or `ntext` column.
- **CI runs none of the 21 gated cases.** `DATAPHOR_TEST_MSSQL` is unset there, by design. The 6 new cases add to the suite's skipped count when no server is configured; `AGENTS.md` now describes both fixtures that read the variable and gives the two counts.
- **Existing damage is not repaired.** A catalog or a customer table written by an earlier build still holds the question marks that were stored in place of the characters it lost, and nothing converts them. Both documentation entries say so.
- **The ODBC connection has the same mapping and was not touched.** `ODBCCommand.PrepareParameters` maps a string to `OdbcType.VarChar`, which has this problem against SQL Server through ODBC - but it is a different driver, a different device, and nothing in the product reaches it today. Per this ticket's instruction nothing was filed for it; `tickets/backlog/bug-odbc-money-parameter-precision.md` already names the relationship from the other side, and its reader will find this decision through that cross-reference. PostgreSQL is unaffected: `NpgsqlDbType.Varchar` is Unicode in PostgreSQL.
- **The plan-cache measurement was made with `sp_executesql` by hand, not through `MSSQLCommand`.** The paramdef shape our client sends is the same one, and the mechanism being measured is the server's plan cache rather than our code, but the number was not taken through our own path.
- **Source hygiene.** The new test file is UTF-8 **with** a byte-order mark where its two sibling SQL Server fixtures have none, deliberately: it holds non-ASCII string literals, and a mark removes any question about how a tool reads them. `StoreContractTests.cs`, which gained the same literals, already had one. Every edited file keeps the mark, line endings and indentation it had.

## For the reviewer

Four judgement calls worth a second opinion, each argued above and at its site:

- Sending Unicode always, rather than only where the column is `nvarchar`, with the measured 208x logical-read regression on an indexed `varchar` column in a SQL collation accepted and documented.
- Changing `SQLTextType` as well as `SQLStringType`, on two conversions checked against a live server but with no end-to-end device proof.
- `nvarchar(max)` as the substitution past 4,000 characters, rather than clamping to 4,000 (which would silently truncate a declared width) or refusing.
- Leaving the plan-per-length churn alone with its measurement recorded, rather than bucketing the declared length.

Also worth checking: that the non-ASCII case belongs in the *shared* store contract rather than only in the SQL Server subclass - the argument is that it needs no device and no translation, it answers for every store the contract is run against, and `store-pgsql-port` is already written expecting it.
