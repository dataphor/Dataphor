## Outcome: withdrawal, not a fix. The engine was not changed.

No engine behaviour was touched. The fix stage had already measured that a committed insert, update or delete of a `Binary` or `Graphic` value leaves the server holding exactly as many managed streams as before it; the original report measured those statements from *inside* one open transaction (the `begin ... end` row section of the `StreamValues` coverage script), where the device session's undo log legitimately still holds one stream per logged write. The rule that holds is:

> One managed stream per logged write of a stream-backed value, held for the life of the transaction that made the write, released when that transaction commits or rolls back. An ordinary statement is its own transaction, so an ordinary statement is balanced.

The implement stage's job was therefore to stop two tracked files from asserting the withdrawn claim as fact, and to pin the real rule with a test. Both done. The four diffs are comments plus one new test section plus one manifest flag.

## What changed

**`tests/libraries/TestFramework.Coverage.Scripts/Documents/StreamValues.d4`**

- The header bullet that said a write into a column "leaves one stream held until the table is dropped - that is bug-a-stored-binary-is-never-given-back" is replaced by a bullet stating the measured rule.
- The "What is not asserted, and why" paragraph above the row section now explains that the section is one statement, so the undo log correctly holds one stream per logged write while it runs, that the exact within-statement counts are deliberately *not* pinned (incidental bookkeeping - pinning it would make an ordinary change to how the log copies a row fail a coverage script), and that the balance that matters is asserted at the script's top level.
- The rolled-back-transaction case is kept unchanged; its comment now says rollback is not a special release - it disposes the undo log, which is what a commit does, reached sooner - and warns that a standalone `BeginTransaction();` statement has no effect outliving itself.
- **New top-level section** after the row section: its own table `TStreamCommitted`, then insert, update, delete and drop each as its own top-level statement, each followed by a balance assertion against a floor recorded after the table was created (not against 0), plus read-back assertions so a balanced-but-wrong write cannot pass.

**`tests/DAE.Server.Tests/coverage-manifest.json`** - the `StreamValues` entry now carries `"batches": true`. **This is the one judgement call in the ticket and the thing most worth a reviewer's attention.** The ticket assumed the script's top level already gives each statement its own transaction. Under the manifest's *default* route it does not: the runner executes `ExecuteScript('Coverage.Scripts', 'StreamValues');`, which makes the entire file one statement inside one transaction, so the new section failed exactly as a leak would (`A committed insert of a Binary left 1 stream(s) held.`) on the first run. `batches: true` is the manifest's existing, documented mechanism for precisely this - two entries already use it for the same class of reason (`ApplicationTransactions`, `ServerLink`, both for "nested in one statement, this falls inside that statement's open transaction") - and with it the script passes. The script's new section carries a comment saying the entry has to stay that way and that the section must move to a host test if it is ever turned back.

**`src/engine/DAE/Runtime/Program.cs`** - the `NOTE:` above `Program.Stop` listed three leaks blocking a debug-only stream-balance check. Checked against the board: `bug-an-argument-is-orphaned-when-a-later-one-raises` is in `tickets/complete/`, and `bug-a-loop-variable-stays-borrowed-after-the-loop` and `bug-ifnil-leaks-the-value-it-copies` are open in `tickets/fix/`. The note now names those two, and records that the third candidate was measured and is not a leak, pointing at `DeviceSession.InsertRow` and the coverage script. The check itself was not added - that is the remaining two tickets' call.

**`src/engine/DAE/Schema/Device.cs`** - a `NOTE:` at the `row.Copy()` line in `DeviceSession.InsertRow` recording that the copy references the column's stream rather than copying its bytes, so the undo entry costs one managed stream per logged insert of a stream-backed value, that it is released by `DeviceTransaction.Dispose` on either commit or rollback, and why the memory device needs the log at all (its own transaction logging is all inside `#if USEMEMORYDEVICETRANSACTIONS`, which no project defines). That is the site a future reader arrives at with this question.

## Tests
