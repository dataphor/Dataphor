## What landed

`libraries/PGSQLConnection` is an SDK project on the NuGet `Npgsql` package, in `Dataphor.slnx` and in the layout's Library list; `external/Npgsql.dll` (2.0.4) and `external/Mono.Security.dll` (2.0) are deleted. No line of `Register.cs` changed and no D4 class name moved: the library still registers `PostgreSQLConnection.PostgreSQLConnection`. `PostgreSQLConnection.cs` and `PostgreSQLCommand.cs` changed only by added comments - the code compiles against the current driver unchanged, with zero warnings from this project's own sources and no suppression anywhere.

### The version pin is the one substantive decision, and it is not the newest release

`Directory.Packages.props` pins `Npgsql` **10.0.4**, not the current 11.0.0, and the comment there says why. 11.0.0 targets `net10.0` and compiles fine, but it depends on `Microsoft.Extensions.Logging.Abstractions` and `System.Diagnostics.DiagnosticSource` **11.0.0**, which are higher versions of assemblies the host's shared frameworks (`Microsoft.AspNetCore.App` and `Microsoft.NETCore.App`, both at 10.0.x) already provide. A flat library folder has no `.deps.json`, so the default load context binds those names from the framework and the folder's own copy is unreachable: `Assembly.LoadFrom`'s resolve handler then fails with `FileLoadException` ("the located assembly's manifest definition does not match the assembly reference"). Measured, twice, in a throwaway console host carrying the same two framework references the Dataphor host declares: with 11.0.0 the driver threw while **constructing** an `NpgsqlConnection` (`SetupDataSource` → `NpgsqlTracingOptionsBuilder.Build`), before connecting to anything; with 10.0.4 the same probe built a connection, a command and one parameter of each of the twelve `NpgsqlDbType` values `PrepareParameters` uses, and resolved `Microsoft.Extensions.Logging.Abstractions` 10.0.0 from `Microsoft.AspNetCore.App`.

That is a constraint on the *layout*, not on this library, so it is recorded as a `NOTE:` in `tools/layout/Layout.csproj` beside the existing flat-folder note, and as a third measured fact in the plan's runtime-layout paragraph. **The thing to check**: whether the reviewer agrees 10.0.4 is the right pin, and whether the note is in the right place. The alternative readings are (a) take 11.0.0 and teach the layout to beat a framework-provided assembly, which a flat folder cannot do by construction, or (b) take 11.0.0 and move the repository to .NET 11, which is far outside this ticket.

### What the layout assembles

`artifacts/layout/<debug|release>/Libraries/PGSQLConnection/` holds exactly four files in both configurations: `Alphora.Dataphor.DAE.Connection.PGSQL.dll`, its `.pdb`, `Npgsql.dll` and `PGSQLConnection.d4l`. The two `Microsoft.Extensions` abstractions the package depends on are **not** there, and that is correct: their versions match what the frameworks provide, so conflict resolution leaves them out and the framework's copies load. (With the 11.0.0 pin the folder had three extra assemblies and did not work, which is how the constraint above was found.)

### The `.d4l` decision

`Mono.Security.dll` is dropped, as the ticket required - the driver has carried its own TLS since 3.x and the layout would fail the build on a listed file it does not provide. **`Npgsql.dll` is kept**, with its `environments.string` of `WindowsServer` unchanged. Reasons: the file is provided (the package is private to this library, so it is flattened into the folder); the entry already existed in a shipped library's descriptor and the `.d4l` format is a compatibility surface; and the entry has a real effect - `LibraryUtility.RegisterLibraryFiles` runs `Assembly.LoadFrom` over every listed file under `LOADFROMLIBRARIES`, so the driver is loaded while the library registers rather than lazily. The driver's own dependency assemblies are not listed and need not be: the layout check is one-way, and `Assembly.LoadFrom` probes the loaded file's own folder for dependencies (the fact the plan recorded when flat folders were designed). Precedent cuts both ways here, which is why it is called out: `System.Internet.d4l` lists `Newtonsoft.Json.dll` the same way, while `ODBCConnection.d4l` lists only its own assembly although `System.Data.Odbc.dll` sits in its folder.

## Driver differences: what was settled, and what was not

The ticket asked for every API difference to be understood rather than worked around. All three it named are settled by reading the pinned 10.0.4 source (verified at the `a445c040` commit the package records, and the two behavioural ones re-checked against 11.0.0 to be sure they are not version-specific), and recorded in a `<remarks>` on `PrepareParameters`:

- **`Size`** still means the ADO.NET thing, and the driver now *acts* on it: `NpgsqlParameter.Bind` truncates a string, char array or byte array longer than `Size` for a text or bytea parameter, where 2.0.4 only recorded the number. Nothing truncates here, for two independent reasons: the truncation is guarded by `_size > 0`, and `DotNetCommand.SetParameters` raises `Size` to each string value's own length before every execution.
- **`Precision` and `Scale`** exist, are not `[Obsolete]`, and compile without a warning (both are `byte`, and `SQLNumericType`'s fields are `byte` too, so nothing needed a cast). The driver stores them and reads them nowhere but `Clone`, so they document intent and decide nothing - including the `Precision = 20` on the eight-byte integer arm, which sends a plain `numeric`.
- **`NpgsqlDbType.Timestamp`** is `timestamp without time zone`, which refuses only a `DateTime` whose `Kind` is `Utc` (`timestamptz` is the one that demands `Utc`). It is the right target for D4's `DateTime`, and no engine value can trip it: `DateTimeConveyor` rebuilds every `DateTime` from its ticks, giving `Kind` `Unspecified`, and the one place that does not - `DateTime.Today`, behind the `Date` and `ActualDate` operators - gives `Local`, which `timestamp` accepts. Nothing under `src/` or `libraries/` calls `DateTime.UtcNow` or `ToUniversalTime`. So the plan's "single most likely source of a defect" is answered, and answered negatively.

**Worth re-deriving if you doubt it**, because it is the one conclusion this ticket reached by reading rather than by running: the Kind argument depends on the claim that no engine-produced `DateTime` is ever `Utc`, which rests on `DateTimeConveyor` (`src/engine/DAE/Streams/Conveyor.cs:342`) and the nilary date/time nodes (`src/engine/DAE/Runtime.Instructions/DateTimeNodes.cs:1536`). A value arriving from a custom C# extension could be `Utc`; nothing in the tree produces one.

## Two defects recorded, not fixed

Both are behaviour in the *device*, which no shipped code can reach until `device-pgsql-device-golden` creates one, so each is a `NOTE:` at the site rather than a ticket or a change here. Say if you think either deserves a ticket of its own instead.

- **The connection string will not be accepted.** `PostgreSQLDeviceSession` puts a tag named `SearchPath` into the connection string and `PostgreSQLConnectionStringBuilder` maps it to the keyword `SearchPath`; the current driver spells it `Search Path` and **throws on an unrecognised keyword** where 2.0.4 ignored one. A device connection therefore fails before reaching a server. `NOTE:` at `PostgreSQLConnection.CreateDbConnection`, which is where the exception surfaces.
- **A D4 `Time` parameter will be refused.** The driver maps PostgreSQL `time` to `TimeOnly`, `TimeSpan` and `long` only; 2.0.4 took a `DateTime`, and `PostgreSQLTime.FromScalar` in `PGSQLDevice` hands one over. `NOTE:` at the `SQLTimeType` arm of `PrepareParameters`. Not fixed here because what to send is the device scalar type's decision and `PrepareParameters` sets types, not values.

## Tripwires and accepted tradeoffs recorded

- `tools/layout/Layout.csproj`: a library folder cannot carry a *different version* of an assembly one of the host's shared frameworks provides - the measured constraint behind the Npgsql pin, and a check to make before giving any new package to a library.
- `PostgreSQLConnection.InternalWrapException`: flattening every driver exception into a plain `Exception` loses `PostgresException.SqlState`, the only thing that distinguishes a constraint violation from a connection failure (`MSSQLConnection.IsUserCorrectableError` makes that distinction). Left as 3.1 had it, as the ticket directed; the `NOTE:` says what is lost, that the stated reason predates the current serialization rules, and that `device-pgsql-port` is the first ticket that could see the difference.
- `PostgreSQLCommand.PrepareParameters`: the `Size` truncation is harmless only because `DotNetCommand.SetParameters` raises `Size` to the value's length - recorded in the remarks so a change to that backstop is understood to matter here.

Every behavioural claim above comes from reading the driver's source or from the throwaway probe described earlier, not from a database.
