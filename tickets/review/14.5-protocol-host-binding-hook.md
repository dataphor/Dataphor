## What landed

`DataphorServiceHostHooks`, a new public static class in the hosting assembly (`src/engine/Server.Hosting/DataphorServiceHostHooks.cs`, namespace `Alphora.Dataphor.DAE.Service`), is the host's mirror of the client's `DataphorServiceUtility` hook surface. Both hosts in the assembly now take their binding from it and both call its builder hook once their endpoints are added. A deployment can again replace what a Dataphor server listens with from its own start-up code, which is the only route there has ever been to a secured Dataphor connection.

| Member | What it does |
|---|---|
| `Func<CoreWCF.Channels.Binding> BuildBindingCall` | the binding every endpoint of a host in this process is served on; default is `DataphorServiceHostBinding.Build` |
| `Action<CoreWCF.Configuration.IServiceBuilder> ServiceBuilderHook` | a last look at each host's service builder, once that host's endpoints are added; default does nothing |
| `bool HasCustomBinding` | false while `BuildBindingCall` is still the product's own |
| `void RevertHooksToDefault()` | puts both back, under a lock, as the client's does |
| `internal Binding BuildBinding()` | what the two hosts actually call: invokes the hook and refuses a null binding by naming the hook |

`DataphorServiceHostBinding` is untouched as a declaration; its class remark now says it is the hook's default and that a deployment replaces the hook, not it. `CoreWcfProtocolTest.TestHostBindingMatchesTheClientBinding` still compares the two *default* declarations and was not rewritten to go through the hook.

## Three decisions a reviewer should weigh, not re-derive

**One internal reader instead of two call-site null checks.** The ticket said both hosts take their binding from `DataphorServiceHostHooks.BuildBindingCall()` and fail on a null binding "at the call site". Both hosts call `DataphorServiceHostHooks.BuildBinding()` instead — an internal method that invokes the field and throws `InvalidOperationException` naming `DataphorServiceHostHooks.BuildBindingCall`. It is still the call site of the hook, and it keeps one message and one place for the "nothing is memoized, a hook may return a different binding per call" remark rather than two copies of each. `BuildBindingCall` is still the public field a site replaces. If the reviewer wants the duplication back, it is a four-line change in each host.

**No private `DefaultBuildBinding` wrapper.** The ticket described `DefaultBuildBinding` as being `DataphorServiceHostBinding.Build()`. The default is held as the method group directly (`private static readonly Func<Binding> _defaultBuildBindingCall = DataphorServiceHostBinding.Build;`), so there is no method whose whole body is one forwarding call and the reader lands on the real declaration. The client's own `DefaultServiceEndpointHook` has no such shortcut available, so `DefaultServiceBuilderHook` does exist, mirroring it.

**`HasCustomBinding` asks about the binding alone, deliberately.** A site that installs only a `ServiceBuilderHook` still reports `HasCustomBinding == false`. That is right and the remark at the member says why: transport security lives in a binding element, so credentials installed over the product's unsecured binding secure nothing and are not a reason for `protocol-transport-security` to stay quiet. The reviewer should confirm that reading agrees with what `protocol-transport-security` goes on to build.

Static-initialiser order is load-bearing: `_defaultBuildBindingCall` and `_defaultServiceBuilderHook` are declared **before** the two public fields that start out holding them, because C# runs static field initialisers in textual order and the other order leaves both hooks null. There is a comment saying so. Reordering those five lines is the way to break this file.

## Tests added

In `tests/DAE.Server.Tests/HostBindingHookTest.cs`, a fixture of its own because `CoreWcfProtocolTest`'s one shared host starts before any case runs and assumes the default binding. Not `[Parallelizable]`; `[TearDown]` calls `RevertHooksToDefault` on every path. Four cases, not the two the ticket's *Tests* section named — the extra two are the ones its edge-case table marked "covered by a case".

| Case | What it establishes |
|---|---|
| `TestAReplacedBindingChangesWhatTheServerAccepts` | the capability itself: with a replaced `BuildBindingCall`, a client assembled as a connection alias assembles one cannot complete a call, and with the default it can |
| `TestBothHostsReachTheServiceBuilderHook` | the hook is called exactly twice for a start with the listener on — once per host — and a hook that throws fails the start |
| `TestTheListenerHostsBindingHookFailureIsNotSwallowed` | a hook that works once and then throws lands its failure on the *listener's* host and reaches the caller; this is what guards the comment in `ListenerServiceHost`'s constructor |
| `TestANullBindingIsRefusedByName` | a hook returning null fails with the hook's name in the message, not deep inside CoreWCF |

**Which replaced binding was used, and why.** The text message encoder in place of the binary one — the ticket's first choice. It works and it fails fast: the host starts on it, and the client's call comes back in under a second as `ServerException` with code `CommunicationFailure`. The `MaxReceivedMessageSize` fallback was not needed. The case asserts that exception type and code as well as the failure, so it cannot pass for an unrelated reason; the whole case runs in about 6 seconds including two engine-server starts.

**A gap to know about.** No case proves a server *certificate* can be installed through `ServiceBuilderHook` — that needs a certificate, and the suite has none. What is established is that both hosts reach the hook with their builder; that CoreWCF reaches service credentials through `IServiceBuilder.ConfigureServiceHostBase<TService>` and `ConfigureAllServiceHostBase` is from reading the CoreWCF.Primitives 1.9.1 metadata, not from running it. A real secured deployment is WS11's, through `protocol-transport-security`.

## Review findings

- **Tripwire, parked as a `NOTE:` in `src/engine/Server.Hosting/ListenerServiceHost.cs`** at the `ServiceBuilderHook` call: that call necessarily runs while the host is *starting* — CoreWCF builds the endpoint pipeline then — which on this class is inside the `try` that swallows a failed start. So a builder hook that throws there is reported as a listener that did not start. Harmless as things stand, because the instance's host is built and started first and a throwing hook fails the whole server start before the listener is reached; it would bite only a hook that throws *selectively* for the listener's host. The note says the fix is to narrow that catch to the bind failure it exists for, not to move the call. The binding hook has no such asymmetry: `BuildHost` is outside the `try` on purpose, there is a comment saying so, and `TestTheListenerHostsBindingHookFailureIsNotSwallowed` fails if anyone moves it.
- The lock in `RevertHooksToDefault` guards nothing that is read under it — it mirrors the client's, where the same lock also guards the memoized client binding. The remark at the method says exactly that rather than implying a synchronisation guarantee the class does not give.
