## What landed

One new fixture, `tests/DAE.Server.Tests/ContractParityTest.cs`, with three tests — one per contract pair. No production source is edited, so there is no `docs/migration-notes.md` entry.

| Test | Server declaration (assembly) | Client declaration (assembly) | Operations compared |
|---|---|---|---|
| `DataphorServiceDeclarationsMatch` | `IDataphorService` (`AlphoraDataphorServer`) | `IClientDataphorService` (`AlphoraDataphorClient`) | 88 |
| `NativeCLIServiceDeclarationsMatch` | `INativeCLIService` (`AlphoraDataphorServer`) | `IClientNativeCLIService` (`Alphora.Dataphor.DAE.NativeCLI`) | 11 |
| `ListenerServiceDeclarationsMatch` | `IListenerService` (`AlphoraDataphorServer`) | `IClientListenerService` (`AlphoraDataphorCommon`) | 3 |

Each test compares, and reports every difference it finds in one failure message rather than stopping at the first:

- **Contract identity** — the effective `Name` and `Namespace` of the `[ServiceContract]`. "Effective" means the attribute's value where it sets one and the value WCF would use otherwise (the interface's own name; `http://tempuri.org/` for the namespace), so dropping either attribute argument is itself a difference rather than a comparison of two nulls.
- **The operation set**, in both directions separately, because an operation the client is missing and one the server is missing are fixed on opposite sides.
- **The signature** — parameter types position by position, and the return type, compared by type identity and never by name. A reported mismatch names each type's assembly, because two same-named types from different assemblies are one of the drifts the test exists to catch.
- **The declared faults** — the set of `[FaultContract]` detail types, also by identity.

A client operation is read as an `[OperationContract(AsyncPattern = true)]` method named `Begin<Name>` paired with an `End<Name>`; its wire parameters are Begin's without the trailing `AsyncCallback` and `object`, and its return type is End's. The pairing and the one-operation-per-name assumption are checked rather than relied on: a `Begin` with no `End`, an unattributed method that is not the `End` half of a pair, an `End` half that does not take exactly `(IAsyncResult)`, an operation declared without `AsyncPattern`, an `AsyncPattern` method not named `Begin…`, a `Begin` not ending in `(AsyncCallback, object)`, and two operations resolving to one wire name all produce their own message.

Two project references were added to `tests/DAE.Server.Tests/DAE.Server.Tests.csproj` (`Client.csproj` and `DAE.NativeCLI.csproj`) and the new file to its `Compile` list. `AlphoraDataphorCommon`, which holds `IClientListenerService`, arrives transitively.

## The mismatch the test found

**The three pairs do not fully agree, contrary to the implement ticket's expectation.** Operation sets, parameter types and return types match exactly on all three pairs. Fault declarations do not: `IDataphorService.Start`, `Stop` and `GetState` each carry `[FaultContract(typeof(DataphorFault))]` on the server and nothing on the client, while all 85 other operations agree. The server raises `FaultException<DataphorFault>` from all three (`DataphorService.cs:85-119`) and the client catches `FaultException<DataphorFault>` around all three (`ClientServer.cs:359-405`) — a catch that cannot fire, because WCF only deserializes a fault into the typed `FaultException<T>` when the operation declares that detail type.

The ticket forbade editing either declaration to make the test green, so the three differences are **recorded** in the fixture's `KnownFaultDifferences` list — the same idiom the repository already uses for a known difference in `coverage-manifest.json` and `ParserRoundTripCorpusTest`'s `AllowList` — and the defect is filed as `tickets/backlog/debt-client-contract-missing-fault-declarations.md`, named in the comment above the list. An entry is matched only by its exact server-only and client-only fault sets, and an entry whose difference is no longer there fails the test with a message saying to remove it, so the fix cannot land without draining its entry.

**This is the main judgment call in the change and the first thing to review.** The alternative was to let `DataphorServiceDeclarationsMatch` fail in the tree and in CI until the backlog ticket lands. Recording was chosen because leaving the suite red indefinitely conflicts with the stage's own requirement that build and tests pass, and because it is what this repository already does with a known failure. If the reviewer disagrees, the change is three deleted array entries and a red test.

## Verification done

**Full build and the first suite part, in the foreground.** `dotnet build Dataphor.slnx`: 0 errors, no new warning from the new file. `dotnet test Dataphor.slnx --no-build -- "NUnit.Where=class != Alphora.Dataphor.DAE.Server.Tests.CoverageScripts"`: `DAE.Server.Tests` 388 passed, 0 failed, 0 skipped (3 m 4 s); `Common.Tests` 13 passed. The coverage-script parts were not run: this change cannot touch them (no production source, no server), and each costs several minutes.

**Every kind of difference was confirmed to fail, by running it.** Two of them against the real contracts, by temporary edits that were reverted (`git status` shows no change under `src/`; the full suite above ran after the revert):

- Removed `[OperationContract(AsyncPattern = true)]` from `BeginGetCacheTimeStamp` in `IClientDataphorService.cs` — the realistic drift, since the method stays and `ClientServer` still compiles. Reported: `IClientDataphorService.BeginGetCacheTimeStamp carries no [OperationContract] and is not the End half of a Begin/End pair.` and `IDataphorService: the server declares operation "GetCacheTimeStamp" and the client does not.`
- Changed `BeginGetInstanceURI`'s second parameter from `string` to `object` in `IClientListenerService.cs` — also compiles, since the one caller passes a string. Reported: `IListenerService.GetInstanceURI: parameter 2 differs - server String (from System.Private.CoreLib), client Object (from System.Private.CoreLib).`

The rest were confirmed with a throwaway fixture (deleted, not committed) that invoked the fixture's private comparison over eight purpose-built broken interface pairs and printed each message: contract `Name` and `Namespace` differing; an operation on each side only; a parameter type changed; a parameter count changed; a return type changed; a fault on one side only; the six malformed-client shapes listed above; duplicate operation names on both sides; three stale `KnownFaultDifferences` entries; and the "no operations found" guard. All eight failed with the intended message.

**That throwaway run found and fixed a real defect in the first draft.** `Type.GetMethod(string)` throws `AmbiguousMatchException` on an overload, so an overloaded client contract ended the comparison with a reflection error instead of reporting the overload — exactly the assumption the ticket said to check rather than rely on. Both lookups now go through a private `FindMethods` that returns every method of that name, and an overloaded `End` half gets its own message. Two overloads sharing a wire name are now reported on both sides, with their parameter lists.

## Review findings

- **Tripwire parked** at the `CompareOperations` doc comment in `ContractParityTest.cs`: `[ServiceKnownType]` and base contract interfaces are not compared, because none of the six interfaces uses either. A contract that starts using one would pass here while differing on the wire. Not speculative machinery, per the ticket; the `NOTE:` says so at the site.
- **Ticket filed:** `tickets/backlog/debt-client-contract-missing-fault-declarations.md`, for the fault mismatch above. It is `debt-` rather than `bug-` because the path is dormant — the WCF host classes are out of `src/engine/Server/Server.csproj` until `protocol-corewcf-host`, so no client can reach a server in this tree — and it names the `docs/migration-notes.md` entry the fix owes, since an application would see a different exception type from those three calls.

## Gaps and things to look at

- **The recorded fault differences**, as above. This is the decision to re-weigh first.
- **The comparison logic itself has no committed test.** The implement ticket explicitly asked for the confirmation to be by temporary local edit and not committed, and that is what was done, so the eight synthetic pairs are gone. The counter-argument is real: the logic has branching (pairing, overload detection, known-difference matching) and one silent-failure mode — a reading bug that finds nothing. The only guard against that is a check that the server side yielded at least one operation; the client side needs no guard, because zero client operations would surface as every server operation being missing. A reviewer who wants the synthetic pairs committed has the full list in the paragraph above, and they reached the real code by `typeof(ContractParityTest).GetMethod("AssertDeclarationsMatch", BindingFlags.NonPublic | BindingFlags.Static)`.
- **The explicit `[OperationContract(Name = ...)]` path is read but unexercised.** No operation on any of the six interfaces sets it, so the fallback to the method name is the live path; the explicit branch is one `??` on each side, covered by inspection only. This is what the ticket expected.
- **A declaration test cannot see the wire.** That the action URI really is derived from contract namespace, contract name and the `Begin`-stripped operation name is WCF's rule, assumed here and on `protocol-corewcf-proof`'s list to confirm against CoreWCF. This test holds the two declarations in step; it does not prove either is what goes out.
- **The `DAE.NativeCLI.csproj` reference is redundant** — `Server.csproj` already brings that assembly in transitively. It is explicit because this project now compiles against it, with a comment in the csproj saying so; dropping it would also build. The `Client.csproj` reference is not redundant.
- **Two statements in the implement ticket were wrong** and are worth not propagating: the three pairs do not all agree (faults, above), and the six interfaces are not all in `Alphora.Dataphor.DAE.Contracts` — `IClientNativeCLIService` is in `Alphora.Dataphor.DAE.NativeCLI`. Neither affects the test, which keys on types rather than namespaces.
- **Placement.** The fixture is in `tests/DAE.Server.Tests` as the ticket directed, and runs in the first suite part. `test-client-server` may move it later; nothing here pre-empts that.
- `tickets/.garden-report.md` was already modified in the working tree when this run started and was left alone.
