## What landed

The decision the implement ticket carried was taken as written and is **not** re-opened here: the secured-connection settings are neither made to work nor removed. Each of the three surfaces that offers one now gives the strongest honest response available at that surface, and a site that needs an encrypted channel still supplies its own binding through the client and host hooks, which is the only route there has ever been. Decision **D17** in the plan records this; the plan's WS5 row is marked Done, Q8's answer now says which way the work item went, and WS11 gained the two rows that own transport security as a designed capability.

### The client refuses

`DataphorServiceUtility` (`src/protocol/Common/Contracts/DataphorServiceUtility.cs`) gained two members:

- `HasCustomBinding` - false while `BuildBindingCall` is still the product's own `DefaultBuildBinding`, compared by reference against a `static readonly` field declared before `BuildBindingCall` so that static-initialiser order cannot leave either null. This mirrors `DataphorServiceHostHooks.HasCustomBinding`, which `protocol-host-binding-hook` added for the same purpose. `RevertHooksToDefault` now restores from the same field.
- `CheckSecurityMode(ConnectionSecurityMode mode, string settingName)` - does nothing for `Default` or `None`, does nothing when `HasCustomBinding`, and otherwise throws `NotSupportedException` naming the setting, saying this version's built-in connection carries no transport security, and giving both remedies (clear the setting, or supply a binding through `DataphorServiceUtility.BuildBindingCall`). `NotSupportedException` rather than a new error code, following the `ClientConfigurationName` refusal a few lines away in `ClientServer.Open`: `Common` has no reference to the engine assembly where `ServerException` lives.

`ClientServer.Open` calls it for `SecurityMode` before anything else, and for `ListenerSecurityMode` only inside the `_overridePortNumber == 0` branch, which is the only path that consults the listener. Both calls happen before `ListenerFactory.GetInstanceURI`, so a refused connection makes no unsecured discovery call. A connection alias reaches this through `src/client/DAE.Client/ServerConnection.cs`, which hands the alias's two modes straight to that constructor (read, not changed).

`NativeCLIClient` (`src/protocol/NativeCLI/NativeCLI.cs`) gained a `GetNativeServerURI` overload taking both modes, which checks them (the listener's only when `overridePortNumber <= 0`) and then delegates to the existing overload. The six-argument constructor calls it. The overload exists because that constructor reaches the listener from inside its own base-constructor argument, which runs before any statement in the constructor body - a check in the body would arrive after the discovery call it is meant to prevent.

**One bug fixed along the way, with its reproduction.** The four-argument `NativeCLIClient` / `NativeSessionCLIClient` / `NativeStatelessCLIClient` constructor forwarded its caller's `securityMode` into the *listener's* slot and left the connection's at `Default`. Dormant while no mode was honoured anywhere; observable from this change on as the wrong setting named in a refusal, or as no refusal at all. It now passes `securityMode` as the connection's mode and `Default` as the listener's.

### The server reports

`DataphorServiceHost.Start(ServerConfiguration)` calls a new private `ReportUnhonouredSecuritySettings(instance)` as the first thing inside the inner try, once the engine server has started and its log is available. It returns at once when `DataphorServiceHostHooks.HasCustomBinding`, and otherwise writes one `LogEntryType.Warning` naming whichever of `requiresecureconnection` / `requiresecurelistenerconnection` is set (the file's own lower-case attribute spellings, which is what an operator searches the instance list for), stating that nothing in the server acts on them and that connections to the instance are not secured, and giving the two remedies. The server starts either way: refusing to start would take an instance down for every client of it on upgrade, over a setting that has never worked.

`ListenerServiceHost`'s `requireSecureConnection` parameter and its doc comment are gone - the caller reports the setting now, and the class has no log of its own. The existing migration-notes entry for that constructor was amended rather than contradicted by a second one. The two call sites in `HostBindingHookTest` were updated; a tree-wide grep found no other caller (nothing in `DAE.Client`, `Dataphoria` or `ConfigurationUtility` constructs it), so no project outside `Dataphor.slnx` is affected by the signature change.

### The server link warns

`RemoteSessionImplementation`'s constructor now passes `ConnectionSecurityMode.None` for both modes and, before building the session, calls a new private static `ReportUnhonouredSecuritySettings(process, serverLink)`: silent when `DataphorServiceUtility.HasCustomBinding` or when neither tag is set, otherwise one warning through `process.ServerSession.Server.LogMessage` naming the link, which tag is set, and the instance and host it connects to. The connection then proceeds unsecured, as it does today. Reported before the connection is opened, so a link that then fails to connect has still said what it was asked for and did not do.

`src/engine/DAE/Schema/ServerLink.cs` is **not** changed, as the ticket required: the tags keep being read into their properties, so a library that sets one keeps its meaning, the properties stay available to the WS11 work, and the catalog and the D4 emitter keep round-tripping the tag as metadata.

### Documentation

- `docs/architecture.md` - the hosting binding is described as "no security" without the "by default" qualifier, and the paragraph on the two binding hooks now states the posture: a connection is unsecured unless a site's own start-up code supplies a binding, the settings are reported rather than ignored, why the client refuses where the server warns, and that the designed capability is WS11's (pointing at D17).
- `docs/users-guide/dataphor-service.md` - the `requiresecureconnection` / `requiresecurelistenerconnection` quick-reference row and the paragraph below it now say that a server writes a warning as it starts when either is set, and what an operator should do about it.
- `docs/users-guide/aliases.md` - a new paragraph under *Out-Of-Process Aliases* in the chapter's own voice: Default and None connect in the clear, Transport is refused with a message rather than connecting in the clear in silence, the listener's setting is only consulted on an alias with no override port, and an encrypted connection needs a binding supplied by the host program. Nothing else in that chapter was touched; its stale catalog-store text is still WS8's.
- `docs/migration-notes.md` - four new entries, filed by surface: the instance-configuration warning and the client refusal under *Platform and deployment*, the server-link warning under *D4, catalog and libraries*, and the four-argument constructor's fixed argument order under *Custom C# extensions*. The existing `ListenerServiceHost` constructor entry was amended for the dropped parameter.
- `docs/modernization-plan.md` - the WS5 `protocol-transport-security` row marked **Done** with the outcome and a pointer to D17; decision **D17** added after D16; Q8's answer amended to record which way the work item went; the WS11 target bullet amended and the rows `security-transport-design` and `security-transport` added. The *CoreWCF hosting* handoff bullet for this work item also carries a "Settled by" clause, matching the convention the other bullets in that list use.

## Tests

New fixture `tests/DAE.Server.Tests/ConnectionSecurityModeTest.cs`, five cases, 1.2 s total. No server and no port opened: every case is settled before a connection is opened, which is the property the refusal has to have. Not `[Parallelizable]`, because one case installs a process-wide client binding hook; teardown calls `DataphorServiceUtility.RevertHooksToDefault`.

| Case | What it verifies |
|---|---|
| `TestAConnectionAskingForTransportSecurityIsRefused` | A `ClientServer` whose `SecurityMode` is `Transport` (with an override port, so no listener is involved) is refused with `NotSupportedException`, and the message names the setting and `BuildBindingCall` |
| `TestTheListenersSecurityModeIsCheckedOnlyWhereTheListenerIsUsed` | `ListenerSecurityMode` of `Transport` is refused on the path that uses the listener - with no listener running anywhere, so a refusal arriving *after* the discovery call would fail on the exception type - and is **not** refused when an override port is given |
| `TestUnsecuredModesAreNotRefused` | `Default` and `None` both connect; only `Transport` is a request this version cannot honour |
| `TestASiteSuppliedBindingSuppressesTheRefusal` | With `BuildBindingCall` replaced, `Transport` is not refused; and `HasCustomBinding` reads true with a hook installed and false after `RevertHooksToDefault` |
| `TestTheNativeClientsSecurityModeIsTheConnections` | The reproduction of the argument-order bug: a `NativeSessionCLIClient` built through the four-argument constructor with `Transport` is refused, and the message names the connection's setting rather than the listener's |

The reproduction was **confirmed to fail without the fix**: with the old argument order restored and the solution rebuilt, `TestTheNativeClientsSecurityModeIsTheConnections` fails with nothing thrown (the mode landed in the listener's slot, which an override port means is never checked). The fix was then restored and the case passes.

**Not tested, deliberately, so the reviewer need not re-litigate it: the two server-side warnings.** Asserting a log line needs a server with logging on, and the root `AGENTS.md` records that the default suite run deliberately runs its servers with logging off, because a logging server in an elevated process creates and writes the `Dataphor Server` Windows event-log source. The server-link warning additionally needs a second hosted instance, which `test-client-server` owns. Both are therefore **verified by inspection only** - the code path, the `HasCustomBinding` guard and the message text were read, not executed. A reviewer who wants them exercised should say so rather than assume they were.

## For the reviewer

Things already checked, with the answer, so they are not re-derived:

- **`ServerLink.ResetServerLink` resets only four of its seven fields - not a defect, do not file it.** `alter server` calls `ResetServerLink` and then `ApplyMetaData`, and `ApplyMetaData` assigns all seven fields from the tags with a default for each, so no field can go stale; `AlterNode.AlterMetaData` never nulls a `MetaData`, so the one path where `ApplyMetaData` does nothing is a link that never had tags. `ResetServerLink` is redundant, not wrong.
- **A tag whose value is not a boolean** (`UseSecureConnection = "yes"`) still throws from `Convert.ToBoolean` inside `ApplyMetaData`, exactly as it does today. Not this ticket's to fix.
- **A library whose `create server` carries a tag** still registers and the server still starts: the tags are read when the catalog object is created, and nothing connects then. Only an actual remote session warns.
- **The instance configuration file is untouched on both sides.** No BOP surface changed, and `InstanceConfigurationTest.LoadReadsAFileCarryingSettingsThatNoLongerExist` still asserts both values (it passed in the run above).
- **The dormant Windows UI** (`EditInstanceForm`, `EditAliasForm` under `src/windows/`, not in `Dataphor.slnx`) was not edited; nothing was removed, so it still compiles. WS6 owns those files.
- **The spike was not run.** The only removed API is `ListenerServiceHost`'s third constructor parameter, and a tree-wide grep found no caller outside the hosting assembly and `HostBindingHookTest`; every other change is additive or internal to a constructor's delegation. Say so if you want the spike run anyway.

Tripwire parked in the code, indexed here rather than analysed again:

- `src/engine/Server/Server/RemoteSessionImplementation.cs` carries a `NOTE:` on warning volume - one warning per remote session, which is one per server link per user session, so the volume is bounded by sessions rather than by statements; left undeduplicated for simplicity, with "dedupe on the `ServerLink`" as the remedy if a deployment ever finds it noisy.

Worth a reviewer's attention, in order:

- The two warning messages and the refusal message are the whole user-visible deliverable of this ticket. Read them as the person who has to act on them, and say if a remedy is unclear or a setting is named in a way that does not match what that person sees.
- `CheckSecurityMode`'s `settingName` is passed differently by the two client surfaces - the alias-editor labels from `ClientServer`, the property names from `NativeCLIClient`. That is deliberate (a native-CLI caller has no alias), but it is the kind of thing worth a second opinion.
- `ReportUnhonouredSecuritySettings` exists twice, once per side, with no shared helper. They log through different objects, name different settings and carry different remedies, so there is nothing real to share; check that judgment.
