## What was wrong

`SetObjectOwner('<table>', '<user>')` failed on the SQLite catalog store with `UNIQUE constraint failed: DAERights.Name`. `CatalogStoreConnection.SetCatalogObjectOwner` updates a table's six rights through a store cursor opened on `IDX_DAERights_Catalog_Object_ID`, which all six share. The generic `SQLStoreCursor` (used by every store since SQL Server Compact went) had two defects:

- **Row identity.** It named the row in `update`/`delete` statements, and in the inverse statements of the nested-transaction undo log, by the columns of the index it was opened on. On a non-unique index that touches every row sharing the value.
- **Position after a write.** `Update()` and `Delete()` left the cursor on no row, and the next `Next()` reopened at the start of the range, so a loop that updates rows that stay in the range never ends.

## What changed

**Row key.** A cursor now has a row key: the columns that identify a row. `CatalogStoreConnection.OpenCursor` passes the table's primary key through a new overload, `SQLStoreConnection.OpenCursor(tableName, columns, index, rowKey, isUpdatable)`. That overload calls the existing `InternalOpenCursor` and then sets the key on the cursor it returns (internal `SQLStoreCursor.SetRowKey`). This differs from the fix ticket's recommended route (new constructor and `InternalOpenCursor` overloads in each store): a custom store that overrides the old `InternalOpenCursor` keeps its own cursor class this way, where a new virtual would silently bypass it. So the SQLite and SQL Server store files are unchanged. When no row key is given (the old `OpenCursor` overload), the cursor uses the index's columns if the index is unique, otherwise every column. Updates, deletes, `LogInsert`, `LogUpdate` and `LogDelete` all use the row key. Generated `where` clauses write `is null` for a null key value (`SQLStoreConnection.AppendKeyCondition`).

**Unique order.** The cursor orders and seeks on the index's columns followed by the row key's columns the index lacks (`_key`, `_keyColumns`, built lazily in `EnsureKeys`). An exclusive seek from a row's key therefore finds exactly the next row, so the non-unique row buffer (`_buffer`, `ClearBuffer`, `CompareRows`) is **retired**. Range values are still prefixes of the index's columns. `SelectKey()` returns the longer key.

**Position after a write.**
- `InternalUpdate` returns `true`. The cursor stays on the updated row, held in `_detachedRow`, which `InternalGetValue` reads while no reader is open. `Next()`/`Prior()` reopen exclusively from its new key.
- `InternalDelete` records the deleted row's key in `_deletedKey`. `Next()`/`Prior()` seek exclusively from it.
- `First`, `Last`, seeks and `Insert` clear both.

**Small fixes in the same code** (each needed for the above or found next to it):
- The indexer's setter now always saves the row as it was before the first edit (`_currentRow`). Before, outside a nested transaction, `InternalUpdate` took `_currentRow` from `InternalSelect()`, which returns the edited values, so an update that changed a key column at transaction level 1 named the row by its new values.
- `Update()` with no edits no longer throws a null reference (`_editingRow ?? _currentRow`).
- `InternalSeek` always disposes the reader first. Before, `EnsureReader` kept a reader opened at the same origin, so a second `FindKey`/`SetRange` to the same key did not reposition.
- A cursor built without its column list (the constructors that take none; no caller in the repository) reads the column names with `select * from <table> where 0 = 1` before its first statement. Before, it learned them from its first reader, which the unique order needs before that reader is built.

**`DeleteRows`' statement path** (`CatalogStore.cs`, about line 900) names each row by the table's primary key. The one-statement arm now applies only when given a full primary key (`indexName == PrimaryKeyName`), not any unique index. That is the same set for every current caller, all of which pass `PK_*` names.

**Bug met along the way:** `SystemSetObjectOwnerNode.InternalExecute` dereferenced a null object to build the `CatalogObjectExpected` error. It now passes the name argument.

**Migration notes:** a D4 row (the unknown-object error is now 113177, not a null reference) and a custom C# extensions row (row key, new overload, cursor order and `SelectKey`, position after `Update`/`Delete`, `is null`, the column probe, `DeleteRows`).

## Tests added

All three are in `tests/DAE.Server.Tests/CatalogStoreTest.cs`. Each was checked to fail without its part of the fix.

- `SetObjectOwnerChangesEveryRight`: creates a user and a table and runs `SetObjectOwner` on a task with a 30 s limit (on timeout it abandons the server through `TestServerInstance.Abandon`). It then checks in the catalog file that the table still has six rights with the same distinct names, all owned by the new user, and that the catalog object row has the new owner.
  - At HEAD it fails with the `UNIQUE` error.
  - With only the position fix removed (`InternalUpdate` returning `false`) it fails at the 30 s limit.
- `NestedRollbackRestoresEveryRightsOwner`: through the process API, begins a transaction, sets the owner to `Admin`, begins a nested transaction, sets it to the user, rolls back the nested transaction and commits the outer one. It checks that all six rights and the object row are owned by `Admin`.
  - At HEAD it fails with the `UNIQUE` error.
  - With `LogUpdate` keyed by the index's column it fails with the `UNIQUE` error during the rollback.
  - Note for test writers: the ticket suggested one D4 script with `BeginTransaction()` / `RollbackTransaction()` statements. With implicit transactions on (the default), each statement of `ExecuteScript` is its own transactional call that ends every level it began, so such a script never nests. The first version of this test passed vacuously that way: the rollback ended an implicit level and the owner stayed changed. The process API is the dependable way.
- `SetObjectOwnerOfUnknownObjectReportsCatalogObjectExpected`: `SetObjectOwner('NoSuchObject', 'Admin')` reports `SchemaException` 113177. At HEAD it fails with a `NullReferenceException`.

Coverage: `SecurityLibrary` now passes. Its manifest entry is flipped to `pass`, keeping its `preamble` and `note`.

## Known gaps and things to look at

- **Untested positions.** Nothing in the repository deletes through a store cursor (no store sets `SupportsUpdatableCursor`), and nothing calls `Prior()` after an update, updates a row out of its range, or builds a cursor without its columns. The `_deletedKey` path, `Prior()` from `_detachedRow`, and the column probe are reviewed by reading only. They are recorded as an arm of `test-store-contract` in `tickets/backlog/feat-ws4-store-followups.md`.
- **SQL Server store.** Not built in `Dataphor.slnx` and not in the spike's list; its files are unchanged, and it gets the row key through the base overload. Not run.
- **Tripwire (`NOTE:` in `SQLStoreCursor.EnsureKeys`): cost of the extra order terms.** On SQLite, the primary-key terms after a non-unique index's columns sort each run of equal index values before its first row comes back. Measured with Python's sqlite3 (SQLite 3.50, in memory) on 100,000 catalog-object rows of one owner: the first row took 24 ms instead of 0, and the whole scan 83 ms instead of 62. `EXPLAIN QUERY PLAN` shows a range search on the index plus "USE TEMP B-TREE FOR LAST TERM OF ORDER BY", so the sort is per run and the scan streams. Also for the OR form an exclusive re-seek generates. The note says what to do if it ever shows up as slow.
- **Tripwire (`NOTE:` on `SQLStoreCursor.GetReaderStatement`): nulls in a seek origin.** A null key value compares as unknown, so a seek from a row with a null key value finds nothing past it. This was already true for direction changes. Every catalog cursor is ranged on non-null values, which excludes such rows.
- **Filed: `bug-set-object-owner-rollback-keeps-owner` (backlog, `repro: verified`).** After the nested rollback in the test above, the store is back to `Admin` but the in-memory catalog object still has the new owner. A temporary line printed `Server.Catalog`'s owner; it was not kept. `ChangeObjectOwner` sets `Owner` in memory with nothing to undo it.
- **Updated: `bug-store-nested-rollback-keeps-rows`.** Its "related" paragraph now says the row identity has landed and what its fix can rely on.
- **Not investigated (from the fix ticket):** with implicit transactions off, a table created in one `ExecuteScript` session was not visible to a second session and had no `DAECatalogObjects` row. The tests here use the default. `SecurityLibrary`, which runs with implicit transactions off, passes.
