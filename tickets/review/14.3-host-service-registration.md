## What landed

The Windows service registration code no longer uses the .NET Framework installer classes, and it no longer lives inside the service executable.

**New assembly.** `src/hosts/Host/DAE.Host.csproj` → `Alphora.Dataphor.DAE.Host`, `net10.0`, `RootNamespace` `Alphora.Dataphor.DAE.Service` (the project file records both reasons: the moved types keep their callers' namespace, and the embedded `Strings.resx` keeps the manifest name `Alphora.Dataphor.DAE.Service.Strings` that `Strings.cs` looks it up by). It is in `Dataphor.slnx` under a new `/hosts/` folder, in the **Bin** list of `tools/layout/Layout.csproj`, and in `tools/net-spike/projects.txt`. Its one package is `System.ServiceProcess.ServiceController` 10.0.15, added to `Directory.Packages.props`. It references no other project in the repository.

**Moved into it:** `ServiceUtility.cs` (rewritten), the `ServiceStatus` enum (unchanged, with it), `Strings.cs` and `Strings.resx` (unchanged; all five strings kept). Moves were made with `git mv`, so the history follows.

**Deleted:** `ServiceInstaller.cs` (the `ProjectInstaller` class — nothing replaces it), `ServiceInstaller.resx`, `Service.resx` (designer header only), and `ServerServices.cs`, the stray that was not in the project's compile list and was not valid C# (a constructor named `ServerService` in a class named `ServerServices`, an indexer getter with no `return`, and a type name that exists nowhere in the tree).

**`ServiceUtility` rewritten** against `advapi32` (`OpenSCManager`, `CreateService`, `OpenService`, `ChangeServiceConfig`, `ChangeServiceConfig2`, `DeleteService`, `CloseServiceHandle`), every import `SetLastError = true`, the error code captured into a local immediately after each call, every handle closed on every path including the failure paths, and every Windows-only member annotated `[SupportedOSPlatform("windows")]` (no `NoWarn` anywhere). Signatures are as the ticket specified: `EventLogSource`, `GetServiceName`, `GetServiceStatus`, `GetServiceAutoStart`, `SetServiceAutoStart`, `Uninstall`, `Install(string)` and the new `Install(string, string)`. Failures surface as `System.ComponentModel.Win32Exception`; no new Dataphor error codes. The five registry-layout members are gone.

What `Install` registers: name and display name `Alphora Dataphor (<instance>)`, the 3.1 description, `SERVICE_WIN32_OWN_PROCESS`, `SERVICE_AUTO_START`, `SERVICE_ERROR_NORMAL`, LocalSystem (`lpServiceStartName` null), and the command line `"<AppContext.BaseDirectory>\DAEService.exe" -name "<instance>"`.

**Callers.** `DAE.Service.csproj` lost the four file items and its `System.Configuration.Install` reference and gained a project reference to `..\Host\DAE.Host.csproj`; `Service.cs` lost the dead `using System.Configuration.Install;`. `DAE.Service.ConfigurationUtility.csproj`'s project reference moved from the service executable to `DAE.Host.csproj` — no `.cs` file in that folder changed. Both projects stay in legacy format (`host-generic-host` and WS6 own their conversions).

**Documentation:** two `done` entries in `docs/migration-notes.md` under *Platform and deployment* (the install-log files are gone and an existing registration keeps working; the types moved, the five members went, and reading the start mode no longer needs administrative rights); the three install-file rows removed from `docs/users-guide/dataphor-service.md`; the spike README's `DAE.Service` row and project count updated with a new `DAE.Host` and `DAE.Service.ConfigurationUtility` row; `AGENTS.md`'s layout table, "Converted so far" list and spike expectation sentence updated.

## Deviations from the implement ticket, each deliberate

- **`Service.cs` got one more edit than the ticket named.** `ProjectInstaller.Prepare` used to default a null instance name to `Engine.DefaultServerName` ("Dataphor"), and deleting it would have made the documented `DAEService.exe -i` (no `-name`) register `Alphora Dataphor ()`. The default is now applied at the two call sites in `Main` (`instanceName ?? Server.Engine.DefaultServerName`), the file that already does exactly this in its `-run` branch and already references the engine. The alternative — defaulting inside `ServiceUtility` — would have meant either a reference from this assembly to the engine or a second copy of the constant.
- **`src/windows/ConfigurationUtility` was added to `tools/net-spike/projects.txt`,** as was the new `DAE.Host`. The ticket expected the spike's per-project error counts to cover the configuration utility, but that project was never in the spike's list, and without `DAE.Host` in the list the `DAE.Service` wrapper would have silently dropped the project reference and reported invented errors. Both are now measured (counts below).
- **`src/hosts/Host/Properties/AssemblyInfo.cs` added** (`AssemblyTitle`, `AssemblyDescription` only), following `Server.Hosting`, the last new assembly; everything else comes from `Directory.Build.props`.
- **`GetServiceStatus` and `GetServiceAutoStart` dispose their `ServiceController`** (`using`). The old `GetServiceStatus` did not, and the configuration utility calls it on a timer. No behaviour change; the mapping and the catch-and-default are as specified.
- **`ERROR_ACCESS_DENIED` and `ERROR_SERVICE_EXISTS` are not declared.** Nothing branches on them — they reach the caller inside the `Win32Exception` — and an unused private constant is dead code. `ERROR_SERVICE_DOES_NOT_EXIST` is declared, because `SetServiceAutoStart` branches on it.

One test added.

| Test | What it verifies |
|---|---|
| `tests/DAE.Server.Tests/ServiceUtilityTest.UnregisteredServiceReportsDefaults` | For an instance name generated from a GUID (so it cannot collide with a real installation), `GetServiceStatus` returns `Unavailable` and `GetServiceAutoStart` returns `false` without throwing — the catch-and-return-a-default branch the configuration utility's timer depends on, and the one most easily lost in the rewrite |

## Known gaps — treat this as a starting point

- **No code path that registers a service has been run.** `Install`, `Uninstall` and `SetServiceAutoStart` are unexercised: until `host-generic-host` produces a runnable .NET 10 `DAEService.exe` there is no binary worth registering, so the elevated manual check (install, confirm name/description/start type/account/`ImagePath` in `services.msc` and the registry, start, stop, set auto-start both ways, uninstall) belongs to that ticket. A reviewer reading this code should read it as unrun code.
- **The unelevated `GetServiceAutoStart` fix is argued, not demonstrated.** Showing it needs a registered service and a non-elevated process; the same manual check covers it.
- **The resource manifest name has no permanent guard.** It was verified once, by inspecting the built assembly. `tools/net-spike/EngineCheck`'s `ExpectedResources` dictionary is where the converted assemblies' resource names are pinned, and `DAE.Host` was deliberately not added to it (the ticket set the verification scope, and the harness is throwaway); adding it is one dictionary entry plus one project reference, and would also move the "seventeen converted assemblies" counts in `AGENTS.md` and the spike README.
- **A tripwire is recorded in the code, not here:** a `NOTE:` at the `SetServiceDescription` call inside `Install` — the description is a second call, so a failure there leaves the service registered without one and throws, and the next `Install` then fails with `ERROR_SERVICE_EXISTS`. The handle has full access, so there is no known way for it to fail; if one turns up, delete the service before rethrowing.
- **`Setup/Files.wxs` still installs `DAEService.InstallLog`** (a harvested file row) — a file nothing writes any more. `Setup/` is replaced wholesale by WS9 (`installer-msi`), and the WiX 3.5 tree does not build in this repository today, so it was left alone.
- `docs/architecture.md` was not changed: its assembly table covers the engine, protocol and client assemblies, not the host programs, and the host program itself is `host-generic-host`'s to describe.
- `host-generic-host` (already in `implement/`, sequence 14.35) was written against exactly these paths and names and needs no adjustment.
