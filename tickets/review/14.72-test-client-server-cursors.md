### `ACursorCrossesFetchBatchesAndChangesThroughItself`

The content of the deleted `CLI/CLITest.TestCLI`, rewritten with NUnit assertions carrying messages instead of `throw new Exception`. In order: create a table and insert `FetchCount` rows; open the cursor with `capabilities { navigable, backwardsnavigable, bookmarkable, searchable, updateable }`; sum the identifiers forwards against the arithmetic series; reset and walk forwards asserting each identifier in order; reset, step to the second row, `Update` it and read it back, `Delete` it and assert what the cursor then shows, `Insert` a row and assert the cursor shows it; walk again taking a bookmark on the fifth row, `GotoBookmark`, assert the row, `DisposeBookmark`; then delete every row, insert ten times `FetchCount` rows, and repeat the forward sum, the ordered walk and the bookmark round trip — the part that crosses many batch boundaries.

Three things a reviewer should check rather than take on trust:

- **The fetch count is read, not assumed.** `process.ProcessInfo.FetchCount`, not the literal 20 and not `SessionInfo.DefaultFetchCount`. `ProcessInfo(SessionInfo)` copies the value from the session's `SessionInfo` (`src/engine/DAE/SessionInfo.cs:309`) and `LocalCursor` reads it from `ProcessInfo` (`src/protocol/Client/Server/LocalCursor.cs:36`), so this is literally the block size the client-side buffer will use. The ticket's wording said "from `SessionInfo`"; the two are the same number and this is the one the code under test reads. There is also an assertion that it is greater than 1, because a fetch count of 1 turns the buffer off (`LocalCursor.UseBuffer`) and the case would then establish nothing.
- **The bookmark is taken twice, not once.** The ticket's ordered list put the bookmark in the first pass (where the old test had it) and its edge-case list asked for it on the fifth row of the ten-times pass, "so it is certainly in a batch the cursor has since left". With the default fetch count of 20, a 20-row cursor never leaves its first block, so the first-pass bookmark crosses no boundary. Both are therefore done — the first-pass one is the faithful port, the second-pass one is the case that actually exercises a discarded block. Cost of the extra one is a few milliseconds.
- **Which row the cursor shows after each change** is asserted exactly as the old test asserted it (`AssertChangesThroughTheCursor`): an update that moves the row to the front of the order leaves the cursor on it, a delete leaves the cursor on the row that followed, an insert leaves it on the row inserted. These are the behavioural record and must not be loosened. The method also puts the identifier back that the update moved out of the way, so the walks after it can assert `1..n` without knowing what happened inside.

The long walks select into one row requested from `cursor.Plan.RequestRow()` and release it in a `finally`; the mutation steps use `cursor.Select()` inside `using`, as the old test did. `CloseCursor` is in a `finally` in a single helper (`OnCursor`).

### `ASchemaChangeOnOneConnectionIsVisibleOnAnother`

Two `ProtocolClient`s against the same child server, both built before any of the statements run, B after A. On A: create a table and insert a row; on B: read it back. Then on B: create a second table; on A: read it. Then on A: drop the first table; on B: assert that reading it now raises `CompilerException` with code `UnknownIdentifier`.

**Correction to the ticket's mechanism, worth a reviewer's eye.** The ticket said "a stale client-side cache fails at compile time with an unresolved identifier". That is not where the compile happens: `PrepareExpression` sends the text to the server, which compiles against its own catalog and returns a `PlanDescriptor` carrying the table variable's definition and a cache time stamp; the client then applies that fragment to its own catalog (`src/protocol/Client/Server/LocalPlan.cs`, `GetDataType`). So what the first two halves pin is the download-and-apply path, and a client whose cache never refreshed fails in `GetDataType` with `ServerException.Codes.CacheDeserializationError`, not with an unresolved identifier. The unresolved identifier is what the **drop** half gets, from the server's compiler, and `UnknownIdentifier` is the code `CoreWcfProtocolTest.TestServerErrorArrivesAsTypedFault` already pins for that shape. The assertions are unchanged in substance; the class remarks state the mechanism as it actually is rather than as the ticket described it.

Per-case object names come from a `Unique(prefix)` counter on the fixture, as `SchemaCacheInvalidationTest` does: the child server is shared by every case in the class and its catalog lives as long as the fixture, so no case may depend on NUnit's order.

### Was `ProtocolClient`'s object-id-counter restoration needed? Measured: no, not by these cases.

The ticket asked for this explicitly. Experiment: remove `TestEnvironment.WithTheObjectIDCounterRestored` from `ProtocolClient`'s constructor, rebuild, run the protocol fixtures.

- `OutOfProcessProtocolTest` — all four cases, including both new ones — **passes either way**. Each client allocates only into its own client-side catalog and clears that catalog before it allocates, so two client-side engines in this process do not collide.
- `CoreWcfProtocolTest` **fails three cases** without it (`TestWholeSessionOverTheWire`, `TestStreamContentCrossesTheWire`, `TestLargeMessageInBothDirections`), each with `UNIQUE constraint failed: DAEObjects.ID`. That fixture hosts a server in the test's own process and then connects to it, which is the arrangement the workaround was written for.

The restoration is **kept** — it belongs to the helper, not to a case, and the fixture it protects is in the same project. What changed is the record: the comment in `ProtocolClient.cs` previously claimed the restoration was "what the client-side catalog cache cases need", which the measurement contradicts, so it now says what was measured instead.

### Tripwire found along the way

`LocalServer.EnsureCacheConsistent` throws the client's cached catalog away and rebuilds it (`Engine.ClearCatalog` → `InitializeCatalog` → `Schema.Object.SetNextObjectID(0)`), **in the middle of preparing an expression**, where no caller can save and restore the counter. So the construction-time workaround does not cover every reset. Harmless as the suite stands (each client clears before it allocates) and conditional on a future arrangement, so it is parked, not filed:

- `NOTE:` at the workaround site in `tests/DAE.Server.Tests/ProtocolClient.cs`, with the condition that would trip it.
- An arm appended to `tickets/plan/bug-object-id-counter-is-process-wide.md` — the same root cause and a file already in that ticket's `files:` — adding two things to its *done* condition: the workaround has moved to `ProtocolClient.cs`, and removing it is not sufficient unless the cache-rebuild path also allocates from its own engine's counter. That ticket's "workaround now in the tree" section still named `CoreWcfProtocolTest`; corrected.

## For the reviewer

Known gaps and judgment calls, stated rather than papered over:

- **The drop half of the cache case may be weaker than it reads.** It asserts that `select <dropped table>` raises `UnknownIdentifier` on the other connection, and that failure comes from the *server's* compiler. A client holding a stale table variable in its own catalog would therefore still fail this way, so the case does not by itself prove the client discarded the dropped object — what it proves is that no stale client-side plan or cached descriptor short-circuits the prepare. Worth deciding whether that is the assertion wanted, or whether something reading `LocalServer.Catalog` directly would be stronger. It would also be a test reaching into the client's internals, which is why it was not written that way.
- **`AssertABookmarkSurvivesTheWalk` asserts the identifier equals the bookmark position**, which only holds because both passes fill the table with `1..n` in order. That coupling is intended (it is also how the old test read) but it is a coupling.
- **Two bookmarks instead of one**, as explained above — a reviewer who reads the ticket's ordered list alone will see one more bookmark round trip than it asked for.
- **The fixture is still not `[Parallelizable]`**, and these cases are the reason it must not become so: three client-side engines now start in it.
- The `<see cref="OutOfProcessProtocolTest.ACursorCrossesFetchBatchesAndChangesThroughItself"/>` in `CursorTest`'s remarks is a cross-file doc link; it resolves today, and will go stale if that case is ever renamed.
