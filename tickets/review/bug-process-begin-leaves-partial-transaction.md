## What was wrong

A process transaction has participants: the process itself, each remote session (a server link) and each device session the process has connected, the catalog device session among them. `ServerProcess.InternalBeginTransaction` pushed the process transaction and then began each remote session and each device session in list order, undoing nothing if one threw. `Schema.DeviceSession.BeginTransaction` likewise pushed its `DeviceTransaction` before calling the device's `InternalBeginTransaction` and kept it when that threw. The result: the process stayed one level deeper, the sessions before the failing one and the failing one itself kept the new level, and the sessions after it never began it. `BeginTransactionalCall` only begins an implicit transaction when none is open, so every later statement ran inside the half-started transaction, and work on a session that never began the level was not undone by the eventual rollback.

## What changed

- **`Schema.DeviceSession.BeginTransaction`** (`src/engine/DAE/Schema/Device.cs`): if `InternalBeginTransaction` throws, the level just added to `Transactions` is removed (`_transactions.EndTransaction(false)`; it holds no operations yet) before the error is wrapped and rethrown. The abstract `InternalBeginTransaction` now documents the contract: an override that throws must leave nothing begun. The in-tree overrides (catalog, application transaction, memory, SQL device) already meet it.
- **`ServerProcess.InternalBeginTransaction`** (`src/engine/DAE/Server/ServerProcess.cs`): counts the remote and device sessions that began. On failure it marks the new process transaction `InRollback`, rolls back only the sessions that began this level (new private `RollbackBegunParticipants`: device sessions in reverse with the catalog device session last, then remote sessions in reverse; rollback errors are logged through `Server.LogError`, not thrown), removes the process transaction and rethrows the original error with `throw;`. `InternalRollbackTransaction` is unchanged. A `NOTE:` at the `catch` records that a connection or transaction failure during a begin sets `StopError`, which here unwinds only the begin's own level (the next `BeginTransactionalCall` clears it) rather than the whole transaction stack as it would during a statement.
- **`ServerTransaction.InvokeDeferredHandlers`** (`src/engine/DAE/Server/ServerTransaction.cs`): comment only. The ticket said the nested begin sat inside the `try` and had to move above it; at HEAD it was **already above the `try`**, so there was nothing to move. The added comment says why it must stay there (the `catch` would otherwise roll back the enclosing transaction once the begin is atomic). The deferred-handler test pins this order.
- **Docs**: Known defects row K30 in `docs/modernization-plan.md`; a **done** entry under "Custom C# extensions" in `docs/migration-notes.md` stating the new `InternalBeginTransaction` contract.

## Tests added (`tests/DAE.Server.Tests/TransactionBeginTest.cs`, new, in the project's `Compile` list)

The fixture registers a test device class (`FailingBeginDevice`, a `MemoryDevice` whose `MemoryDeviceSession` subclass throws from `InternalBeginTransaction` when a static `FailAtLevel` equals the level being begun) directly with the class loader, creates `FailTable` on it and three tables on the default memory device, one of them (`HandledTable`) with a deferred after-insert handler that logs into `HandlerLog`. Each test's `[SetUp]` deletes from `FailTable` first, so the process connects the failing session before the memory device's session; that order is what makes the memory session one that a half-done begin never reached. The switch is set and reset in a `finally` by `AssertBeginFails`, which also checks the error text reaches the caller.

- `TestImplicitBeginFails`: a statement whose implicit begin fails throws the device's message and leaves `TransactionCount` 0; the next insert commits its own implicit transaction (`InTransaction` false) and the memory table holds exactly that row. On HEAD: `TransactionCount` was 1.
- `TestNestedBeginFails`: inside an explicit transaction with inserts into both devices, a nested `BeginTransaction` failing at level 2 throws and leaves `TransactionCount` 1; one rollback ends the transaction and both inserts are gone. On HEAD: `TransactionCount` was 2.
- `TestDeferredHandlerBeginFails`: inside an explicit transaction, an insert into `HandledTable`, then `CommitTransaction` with the device failing at level 2 (the deferred handlers' nested transaction): the commit throws the device's message, `TransactionCount` is still 1 and the inserted row is still there; rolling back leaves neither the row nor a log row. On HEAD: `TransactionCount` was 2. If the deferred handlers' begin were moved inside its `try`, this test would see `TransactionCount` 0.

All three were run against the HEAD engine files (fix temporarily reverted, then restored) and failed as listed; with the fix they pass. `dotnet build Dataphor.slnx` succeeds; `dotnet test Dataphor.slnx`: Common.Tests 13 passed; DAE.Server.Tests 145 passed, 25 skipped (the coverage manifest's known-failure, unstable and fragment entries), 0 failed.

## Known gaps and things for the reviewer to look at

- **Remote sessions that fail at begin are not rolled back.** Only sessions whose `BeginTransaction` returned are counted as begun. A remote session whose call failed after the remote server began the level (a lost reply) keeps that level on the other server; the engine cannot tell. Remote sessions are a call to another server and are not exercised by the new tests (no test harness for server links).
- **Unwind reads `DeviceSessions` by index.** It assumes the list does not change between the begin loop and the unwind; nothing in-tree connects or disconnects a device session during a begin (a change would already break the `foreach`).
- **Pre-existing, not changed, worth a look (static, not reproduced):** `CatalogDeviceSession` keeps deferred device stops in one list that is not per level: any rollback, at any nesting level, clears it (`ClearDeferredDeviceStops`, `src/engine/DAE/Device.Catalog/CatalogDeviceSession.cs` about line 1488), and any commit, nested or not, executes it (about line 1442). So a nested rollback inside a transaction that dropped a device loses the deferred stop. Ordinary nested rollbacks already hit this; the new unwind of a failed nested begin is one more nested rollback of the catalog session. Not filed; decide whether it passes the filing bar.
- `Assert.Catch` is called with an `Action` to avoid the obsolete `TestDelegate` overload (CS0618); `ApplicationTransactionTest` still uses the old overload (pre-existing warning).
- The test fixture's static `FailAtLevel` is shared by every session of the test device across the server; only this fixture creates that device, and NUnit runs this suite's fixtures sequentially today.
