## Background

The coverage script `ApplicationTransactions` joins an application transaction (AT), changes data in it, leaves it, rejoins it and checks the changes are still there. The harness ran every script nested inside one statement, `ExecuteScript('Coverage.Scripts', '<name>');`, whose implicit transaction stays open for the whole script. Leaving an AT disconnects the AT device session, and disposing that session rolls back any transaction still open on it, so each leave inside the outer statement threw away the AT work and the script failed at line 41 (`Application Transaction read is not repeatable.`). That engine behaviour is unchanged since 3.1; whether to change it is the D4-semantics question in `engine-at-leave-discards-transaction-work` (blocked). The fix stage's diagnosis table showed the script passes when run batch by batch, one implicit transaction per batch, the way Dataphoria runs a script.

## What changed

- `CoverageManifest.cs`: new optional entry field `batches` (`bool?`). Validation: only `true` is accepted (`false` is rejected as redundant with leaving the field off); not allowed on a `fragment` entry. Documented in the `<remarks>` field list next to `preamble`.
- `CoverageScripts.cs` (`RunInProcess`): when `entry.Batches == true`, the harness reads the script's file from the script server's own copy of the library (`<instance>/Libraries/TestFramework.Coverage.Scripts/Documents/<script>.d4`, via the new `ServerScriptPath`) with `File.ReadAllText` and runs it with `process.ExecuteScript(text)`. Registration, preamble and the timeout/abort path are unchanged.
- `coverage-manifest.json`: `ApplicationTransactions` is now `pass` with `"batches": true` and a note pointing at `engine-at-leave-discards-transaction-work`.
- `ApplicationTransaction.cs` (`ApplicationTransactionUtility.LeaveApplicationTransaction`): a `NOTE:` above the `DeviceDisconnect` call recording the rollback-on-leave behaviour and the blocked ticket. File's tabs, CRLF and byte-order mark preserved (verified: every line still ends CRLF).

No migration note: the harness option is test-only, and the engine change is a comment.

## Tests

No new test, as the ticket planned. The `ApplicationTransactions` case is the characterization: it now runs through the new option and passes, and it covers the AT join/leave/rejoin behaviour the script checks.

Validation rules were checked by hand, not by a kept test: with the manifest temporarily edited to `"batches": false` on `ApplicationTransactions` and `"batches": true` on the fragment `Transaction.Atomicity.Cleanup`, `Harness.ManifestInvalid` failed with exactly those two problems; the manifest was then restored and rebuilt.

## For the reviewer

- The `store-at-enlist-inside-catalog-lock` Debug assertion did not fire in this script batch by batch (the run is Debug and passed), as the fix stage predicted.
- `batches` reads the text with `File.ReadAllText` (default UTF-8, byte-order mark detected). The Frontend `ExecuteScript` operator loads the document through `FrontendDevice.LoadDocument`; I did not compare that loader's decoding with `File.ReadAllText`. For this ASCII script it cannot matter; a non-ASCII script in a legacy code page would be the case where they differ.
- The batched path runs with `ProcessInfo.Language` as the process has it (D4). The nested path switches to RealSQL for a `sql` document type; a `.d4` file never is one, so the batched path does not repeat that switch.
- The batched path loses the `doc:Coverage.Scripts:<name>` debug locator the nested operator passes, so an error's locator names the batch's own position rather than the document. Error-text matching does not use locators (the manifest rules forbid matching on them), so no entry is affected.
- Left as the ticket said: `StreamAllocation` (nests every script, will fail in `ApplicationTransactions` this way once its library name is fixed; `test-pre-3-1-scripts-policy`), and `RemoteATOperatorEvaluation` / `TestNetworkApplicationTransactions` stay nested and pass.
