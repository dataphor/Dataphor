## What landed

One test case, two new product members that make it reachable, and a second mode on the suite's own test program. `dotnet build Dataphor.slnx`: **0 errors, 0 warnings**. All three suite parts green in Debug (0 failed: 13 + 438, 67, 48; 5 m 01 s, 5 m 32 s, 3 m 49 s). The new case also passes in a **Release** build.

### The product change

- `DataphorServiceHost.ConnectionIdleTimeInSeconds` — `int`, default `ConnectionManager.IdleTimeInSeconds` (300), settable only while inactive through `CheckInactive()`, exactly like `HostName` and `LoggingEnabled`. Passed to the service in `Start(ServerConfiguration)`.
- `DataphorService(RemoteServer, int)` — the existing one-argument constructor now delegates to it with `ConnectionManager.IdleTimeInSeconds`, so the one existing construction site (`DataphorServiceHost.Start`) is the only caller that changed. `ConnectionManager` itself is untouched; its two-argument constructor and its refusal below one second are what this reaches.
- Nothing was added to `ServerConfiguration`, `HostCommandLine` or the environment, as the ticket settled.
- `docs/migration-notes.md` gained one entry for the two additive members under *Custom C# extensions*.

### The harness's client mode

`tests/TestHarness` gained `--idle-seconds <n>` on `serve`, and the whole `client` mode:

```
DAE.Test.Harness client --host <name-or-address> --port <n> --instance <name> [--keep-alive-seconds <n>] --hold-transaction <table-name>
```

It builds the shipped client stack the way `ProtocolClient` does (a `ClientServer` wrapped in a `LocalServer` at the given keep-alive interval), connects as `Admin`, starts a process, begins a transaction, creates the named table in it, prints its holding line, and then blocks for ever. Nothing is disposed and no path leads out of that method, which is the point.

### The case

`tests/DAE.Server.Tests/AbandonedClientProcessTest.AKilledClientProcessIsReclaimedAndTheServerKeepsServing` — one fixture, one case, its own child server at a five-second connection idle threshold, an observing client at a one-second keep-alive interval, and a child client killed with `Kill(entireProcessTree: true)`. It asserts, in order: the observer agrees the child's session is on the server; after the kill the session goes; the observer still answers; and a connection opened afterwards answers too. It does **not** re-assert the rollback, the catalog store's write lock or what a call on the reclaimed process sees — `AbandonedSessionCleanupTest` owns all three in process, and the new fixture's remarks point at it.

`OutOfProcessInstance` gained a second constructor taking the idle threshold (`ServerDefaultConnectionIdleTime`, 0, means "leave the child's own default alone" and passes no option), and the nested helper `HeldTransactionClient` that starts, waits for, diagnoses and kills the client child.

## The two questions the ticket asked to answer

**Which mechanism reclaims the connection: the idle watcher, and only the idle watcher.** Measured by running the same case against a child server left at the shipped 300-second threshold: the killed client's session was **still on the server 25 seconds after the kill**. So CoreWCF and Kestrel either do not notice the socket a killed process leaves behind or noticing it does not reach the connection; the channel-close path reclaims nothing. At a five-second threshold the session went 4.9, 5.0, 5.1 and 5.1 s after the kill across four runs — inside the watcher's 5-to-6.25-second window, as its wake period of a quarter of the threshold predicts. Recorded in the plan's *Reclaiming an abandoned session* section and in the fixture's remarks. Because the channel's death does nothing, there is no "slower, more realistic clock" available: a case that waits for this at all has to shorten the threshold.

**Timings.** The case is 11–12 s (three consecutive Debug runs: 12 s, 12 s, 11 s; Release 11 s), of which about 5 s is the child server's first start and 5 s the reclamation window. It joins suite part 1; that part was 5 m 01 s with it.

**Not flaky in three consecutive runs** (`--filter Name=AKilledClientProcessIsReclaimedAndTheServerKeepsServing`), all green, reclamation measured at 4.9/5.1/5.1 s.

## Three deviations from the ticket, each deliberate

**1. The threshold is 5 seconds, not 3.** The observing client is a client of the same server and is measured by the same clock, so the margin between the server's threshold and the observer's one-second ping is the case's sharpest edge — the ticket says so. Three seconds leaves two pings' worth of slack; five leaves four. The case runs in suite part 1 on a machine that is starting servers in other fixtures at the same time, and two seconds of case time is the cheaper side of that trade. The relationship and the reasoning are stated at `IdleThresholdSeconds`, and a read that fails during the poll reports the margin explicitly rather than surfacing as an unexplained unknown-handle error.

**2. The holding line carries the session identifier: `HOLDING <table-name> <session-id>`,** not just the table name. The child evaluates `SessionID()` inside its transaction and prints it. This is what lets the observer watch for that one session with a scalar count instead of reading `System.Sessions` as a table — see the next point. It also makes the assertion sharper than the ticket's ("the child's session, by its own identifier, is on the server" rather than "exactly one session appeared"), and it removes the before/after session-list bookkeeping the ticket described.

**3. The observer asks `Count(Sessions where ID = n)`, not `select Sessions`.** This is the one that matters, because the first version of the case did read the table and **failed** — and the failure is a real, pre-existing product defect, not this case's problem:

- Reading a table over the wire makes the server send a catalog fragment that the client applies as a view in its own catalog cache, dropping it again when the plan is disposed. Eight such reads followed by a change to the server's catalog — which this case produces by design, when the abandoned `create table` is rolled back — make the next read fail with error 106185, "Errors occurred while deserializing client cache time stamp", wrapping `An item with the same key has already been added. Key: 984` from `CatalogDeviceSession.CacheCatalogObject`.
- Deterministic: the same colliding identifier and the same count of reads on every run, and reproducible with **one** client, no second process, no abandoned transaction at all (eight reads, one `create table`, one more read).
- **A Release build does not fail; it silently replaces.** The `#if !DEBUG` block at the top of `CacheCatalogObject` removes any object already in the cache by name before adding, which is what lets the collision through unreported. So in a shipped client this is a quiet wrong state in the client-side catalog cache; in a Debug build of the same client it is an exception.
- The site is already claimed: `tickets/plan/bug-object-id-counter-is-process-wide.md` has a section on exactly this code path (`LocalServer.EnsureCacheConsistent` → `Engine.ClearCatalog` → `InitializeCatalog` → `SetNextObjectID(0)`) which said it was "harmless as the tests stand" because "nothing does that today". That is now falsified, so the finding went on as an **arm** rather than a new ticket, with the reproduction, the Debug/Release asymmetry, and the two header fields it contradicted corrected (`likelihood: unusual` → `normal-use`, and the `tradeoffs:` sentence that said only a two-engine process is affected).
- A scalar count sends no catalog fragment and has nothing to do with the defect. The reason is recorded at `AbandonedClientProcessTest.SessionCount`, so nobody "simplifies" it back to a cursor.

**What a reviewer should decide:** whether building the case on the scalar count is the right call, or whether the case should read the table and be left failing until the defect is fixed. The judgement made here was that the case's subject is reclamation, not the catalog cache, and that a case which fails for an unrelated reason in Debug and passes in Release is worth nobody's time.

## What to check rather than take on trust

- **The idle threshold really reaches the child.** `OutOfProcessInstance` passes `--idle-seconds` only when the caller asked for a value; with no value no option is passed and the child runs the product's 300 seconds. `HostProgramTest` and `CoreWcfProtocolTest` exercise hosts that never set the property, and they are green, so a mistake that shortened the default would have shown up as their connections being reclaimed.
- **The value is not validated twice.** The host passes it straight through; below one second the `ConnectionManager` constructor refuses it and the child fails to start with that error on its standard error, which `OutOfProcessInstance` reports. There is no separate test for that — `port-abandoned-session-cleanup` owns the constructor's validation — and no test for the new property's default, which the compiler and the fixtures above cover.
- **Nothing else in the child depends on the threshold.** Read rather than assumed: `ConnectionManager` derives `_wakePeriodInSeconds` from it (`Math.Max(1, idleTimeInSeconds / 4)`) and nothing else in the class or the assembly reads either field.
- **Double reclamation was not observed.** With the channel-close path doing nothing there is only one reclaimer here, so the idempotence `port-abandoned-session-cleanup` pinned (`RelinquishingAConnectionTwiceDoesNothing`) is not exercised by this case and is not claimed to be.
- **The client child's exit code is -1** on every run, which is what `Kill` leaves; it is printed in the progress line but not asserted, because a process that blocks for ever can end no other way.
- **Teardown kills the client on every path.** `HeldTransactionClient.Kill` is idempotent and is called from `Dispose`, from the case, and from the constructor's own failure path, so a case that fails before the kill still takes the child with it.

## Known gap: an orphaned client child

Unlike the server child, the client child has **no standard-input stop path** — the ticket settled that, because its whole purpose is to be killed. So a test host that is itself killed outright between starting the child and killing it leaves a `DAE.Test.Harness.exe` sleeping for ever; NUnit teardown covers a failing or throwing case, but not a kill of the test process (which is what the ticket runner does on a timeout). Recorded as a `NOTE:` at the site in `tests/TestHarness/Program.cs` with the remedy if strays are ever actually seen: give the client mode the serve mode's end-of-input exit, which cannot affect a case (the case kills the child while its parent is alive and holding its input pipe open), and have the fixture assert the child's exit code shows a kill rather than a graceful exit. Not done now because it adds an ordering dependency — kill before disposing the `Process` object, or closing its standard input would end the child gracefully and the case would pass for the wrong reason.

## Tests

One case, `AKilledClientProcessIsReclaimedAndTheServerKeepsServing`, verifying that a client process killed while holding a session in a transaction has its session reclaimed by the server and that the server keeps serving an older connection and a new one. Nothing else: no test for the new host property's default, none for the delegating `DataphorService` constructor, and no second copy of the in-process reclamation assertions.
