# Review: remove remoting lifetimes (K6) and the DTC transaction class (K11)

First half of `build-server-project`, split off because both are source deletions the spike could already build and run. K-numbers are the known-defects table in plan Appendix A. No project changed format; `Server.csproj` stays legacy.

## What changed

**K6, .NET Remoting lifetime, tracking and sponsor code** (all of it throws `PlatformNotSupportedException` or does not exist on .NET 10):

- `RemoteServerObject.cs`: the remoting `using`s and the now-unused `System.Reflection`, `LeaseManagerPollTimeSeconds`, the static constructor that set `LifetimeServices`, and the lease-cancel/`RemotingServices.Disconnect` `finally` blocks in both `Dispose(bool)` methods. Both still call `DoDispose()` (raises `Disposed`, which `RemoteServerChildObjects` relies on to disown children). `MarshalByRefObject` stays as the base class, as the ticket decided.
- `RemoteServer.cs`: `ITrackingHandler` and its three members, `DisposeConnection`, tracking-handler registration/unregistration, and the `System.EnterpriseServices` and remoting `using`s. `Dispose(bool)` keeps `finally { base.Dispose(disposing); }`.
- `RemoteServerConnection.cs`: the `InitializeLifetimeService` override, the two lease constants, and the lease "Strategy" comment. `LastActivityTime` and `Ping` stay in the "Lifetime Management" region.
- `FileStreamProvider.cs`: `ISponsor` and `ISponsor.Renewal`. `SecurityNodes.cs` (server copy): the unused `System.Runtime.Remoting.Messaging` `using`.

**K11, distributed (DTC) transactions:**

- Deleted `src/engine/Server/Server/ServerDTCTransaction.cs` and `src/engine/DAE/Server/IServerDTCTransaction.cs` with their `Compile` entries (both are staged as deletions).
- `ServerProcess`: the `_dTCTransaction` field and the DTC blocks in begin, commit and rollback are gone. In commit, the whole `try { DTC commit } catch { RollbackTransaction(); throw; }` wrapper went with it, because the DTC commit was the only thing in that `try`. The non-DTC logic is unchanged.
- `ServerProcess.UseDTC` setter: `if (value) throw DTCNotSupported` comes **before** the `InTransaction` check (the Windows-version test is gone). `false` behaves as before.
- `ServerProcess.InternalBeginTransaction`: `if (UseDTC) throw DTCNotSupported` is now the first statement. This is the backstop for the API and session-default paths, and it runs before any transaction state changes.
- `ServerCatalogDeviceSession.UpdateSessions`: `DefaultUseDTC := true` throws `DTCNotSupported`; `false` still assigns.
- Error 106119's message is now `Distributed transactions (UseDTC) are not supported.` The code is unchanged.
- The `Engine.cs` transaction-management comment no longer describes the DTC. In `SessionInfo.cs`, the `ProcessInfo.UseDTC` summary and `Description` say it is not supported, and its remarks no longer mention Windows 2000. The `DefaultUseDTC` text made no claim, so it is unchanged.
- User docs (`process-defaults.md` DefaultUseDTC section, `modeling-process-logic.md` transaction paragraph) now say: the setting is kept for compatibility, must be false, true raises 106119, and the server coordinates distributed transactions itself. No links changed.
- Untouched, as required: the `UseDTC`/`DefaultUseDTC` properties, the WCF data-contract members, `RemoteSessionImplementation`, and the `System.Processes`/`System.Sessions` columns.

**Bug met along the way, fixed here (local fix):** `ServerCatalogDeviceSession.UpdateProcesses` read `oldRow["MaxCallDepth"]`, but the `System.Processes` column is `MaxNestingLevel` (`CatalogDevice.PopulateProcesses` fills it from `process.MaxCallDepth`). So every `update System.Processes` that got as far as the last column failed with `Column "MaxCallDepth" not found`, including the `UseDTC := false` case this ticket has to support. It now reads `MaxNestingLevel`, so updating that column sets the process's maximum call depth. The catalog's column name is the D4 compatibility surface and was kept. Reproduction: the second block of the new script failed with exactly that error before the fix. Migration note added.

**Spike:** `stubs/Server.cs` now holds only the `System.ServiceModel*` namespaces. The remoting and `System.EnterpriseServices` stubs are deleted, and the server still builds with 0 errors. `run.py` is unchanged. The README's stub description and Server result row are updated.

**Docs:** `migration-notes.md` has the DTC row set to done, plus done rows for the removed remoting members, the removed `IServerDTCTransaction`/`ServerDTCTransaction`, and the `MaxNestingLevel` fix. In `modernization-plan.md`, K6 and K11 are fixed (owner this ticket), the WS1 `build-server-project` row notes that K6/K11 landed first, and the WS1/WS2 prose that said `build-server-project` would remove this code now says it is done.

## Test added

- `tests/libraries/TestFramework.Coverage.Scripts/Documents/DistributedTransactions.d4` (tabs, CRLF, no BOM, ASCII), wired as `ExecuteDistributedTransactions` in `tests/DAE.Server.Tests/CoverageTest.cs` next to `ExecuteApplicationTransactions`. It checks three things:
  - `UseDTC := true` on `System.Processes` raises 106119, and afterwards `UseDTC` is still false.
  - `UseDTC := false` succeeds. This is also the reproduction of the `MaxNestingLevel` bug.
  - `DefaultUseDTC := true` on `System.Sessions` raises 106119, `DefaultUseDTC` stays false, and setting false succeeds.
- Error shape, observed with a probe run: the top-level `E.Code` is 104229 (`RuntimeException.RuntimeError`). `PlanNode.Execute`'s exception handler re-raises any non-user-severity error with the statement location, so 106119 is `E.InnerError.Code`. The script asserts on the inner code. It fails if no error is raised (code stays 0) and if the inner code is anything else, including 106116 `TransactionActive`, which the old setter order produced.

## Known gaps and things for the reviewer to look at

- **API path verified by inspection only.** No D4 surface sets `ProcessInfo.UseDTC = true` at `StartProcess`, so the `InternalBeginTransaction` backstop has no test. It throws before `_transactions.BeginTransaction`, and `BeginTransactionalCall`'s `catch { EndCall(); throw; }` leaves the process as it was. Such a process cannot run any D4 with implicit transactions on until the flag is cleared (`SetUseImplicitTransactions(false)` and then `update System.Processes set { UseDTC := false }`, or reconnecting with false). The C# test belongs to the harness tickets. The same applies to server links whose metadata sets `DefaultUseDTC = true`: they now fail with 106119 at the remote process's first transaction instead of with `ArgumentNullException`.
- **The negative case was not re-run.** I did not put the old setter order back to watch the script fail. The probe showed the error shape, and the assertion's failure conditions (code 0 or any other inner code) can be checked by reading it.
- **Multi-column updates are not atomic (pre-existing).** `UpdateProcesses`/`UpdateSessions` apply columns in order. An update such as `set { DefaultIsolationLevel := …, UseDTC := true }` applies the isolation level and then raises 106119. That was already true of any column that fails, so I did not reorder anything.
- **`Server.csproj` still has `<Reference Include="System.EnterpriseServices" />` and `System.Runtime.Remoting`.** The ticket limited edits to the `Compile` list, and `build-server-project` drops these references when it converts the project.
- **Abandoned remoting connections are no longer disposed.** `RemoteServer.DisconnectedObject` did that, and nothing replaces it here. That is `port-abandoned-session-cleanup`'s job. The in-process smoke run does not construct `RemoteServer`, so its disposal is checked by inspection only.
- **Line endings of the new file in the repository.** The new `.d4` is CRLF in the working tree, like its neighbours (which are stored CRLF). With `core.autocrlf=true` here, git may store the new file as LF.
- **Left as they were:** the plan's Appendix C "Compile results" row for Server (a historical spike measurement), the mention in the DocBook manual under `legacy/`, and one line in `tickets/implement/11-port-engine-runtime-fixes.md` (~112) saying `build-server-project` removes these `using`s. It is now this ticket, and the outcome that line expects holds.
