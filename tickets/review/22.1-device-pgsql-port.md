## What this was

The PostgreSQL device had been built and its generated SQL pinned by checked-in golden files, but nothing in the repository had sent a statement to a PostgreSQL server since about 2017. This ticket built the harness that does, ran it against four PostgreSQL versions in containers, fixed what it could fix locally, filed what it could not, and wrote down the supported version floor.

**PostgreSQL 14 is now the documented minimum.** The device behaves identically on 13.23, 14.25, 16.16 and 18.7, so the floor is a support decision rather than the point where the device stops working.

## How to run it

```
docker run -d --name pg-18 -e POSTGRES_PASSWORD=<a throwaway password> -p 15418:5432 postgres:18
dotnet build Dataphor.slnx
DATAPHOR_TEST_PGSQL='Host=localhost;Port=15418;Username=postgres;Password=<the same>' dotnet test tests/DAE.Server.Tests --no-build --filter "FullyQualifiedName~LivePGSQLDeviceTest" --logger "console;verbosity=normal"
```

Pick a port outside this machine's excluded ranges (`netsh interface ipv4 show excludedportrange protocol=tcp`); Hyper-V reserves blocks that `docker run -p` cannot bind, and the failure reads as a permissions error rather than a port clash. With the variable unset every case reports Inconclusive with the reason, which was checked.

## What landed

**The harness.** `TestEnvironment` gained a `DATAPHOR_TEST_PGSQL` region beside the SQL Server one: the variable, the parsed host/port/login, the whole D4 of a device definition plus its device user, and the statement that empties the device's database. Two things about it are deliberate and worth a reviewer's attention.

- It parses the variable with the framework's `DbConnectionStringBuilder`, **not** with Npgsql, because this test project must not reference the PostgreSQL driver: the driver arrives with the library `libraries/PGSQLConnection`, and whether the runtime layout puts it where that library can find it is one of the things a live run proves. A package reference here would satisfy the load from the test assembly's own folder instead, because the library resolver is an `AssemblyResolve` handler and only fires after the default load path has failed. The cost is that every keyword spelling the driver accepts has to be listed by hand.
- For the same reason, emptying the database goes out **over the device's own connection**, as a `SQLDevice.SQLExecute` of a `do` block, rather than over a connection of the harness's own as the SQL Server passes use. That means the device has to be started first, which is also what creates the database and the support functions - so the emptying drops tables only, never the `DAE_` functions.

**The driver script.** `tests/libraries/TestFramework.Coverage.Devices/Documents/TestPGSQLDevice.d4`, the sibling of `TestMSSQLDevice.d4`. **One statement of the sibling is deliberately absent** and this is the judgement call most worth checking: the sibling raises an error naming every catalog object called `TestFramework.Coverage.Devices.TestDevice*`, which can never succeed, because the library's own `Logic.d4` creates an operator whose catalog name is exactly that - it is why `LiveDeviceTest` is a recorded known failure and never reaches the corpus at all. Copying it into a new script would have meant writing a script that cannot pass, so it is left out with the reason in the file header, and `test-pre-3-1-scripts-policy` still owns whether the sibling may be repaired. Everything else is identical, including the `DeviceOperators` check (which does pass).

**The fixture.** `LivePGSQLDeviceTest`, three cases:

| Case | What it verifies |
|---|---|
| `TheDeviceReadsTheServerVersion` | The device parses what `version()` returns and its `MajorVersion` matches the server's. This is the reproduction of fix 1 below: on a fresh server the device's database does not exist yet, so the pre-fix code failed the device's start outright. It also writes the version string to the test output, so a TRX records which server a run proved. |
| `TheDeviceCoverageCorpusRunsAgainstTheServer` | The 1,180-case corpus. The reproduction of fixes 2 to 5. Recorded as a known failure in the shape `LiveDeviceTest` uses: it must fail, and the roll-up must match each of five patterns (one per owning ticket), or the run fails; the whole roll-up is reported as a warning. |
| `TheDeviceCreatesATableWithAByteArrayColumn` | A table with an `SQLDevice.MSSQLBinary` column can be created. The reproduction of fix 6, which the corpus cannot reach. Confirmed to fail without the fix: *42601: type modifier is not allowed for type "bytea"*. |

No other tests were added. The translation goldens already cover what the device generates, nothing else changed behaviour, and the corpus is the oracle for everything about values (decision D2) - there is deliberately no new C# assertion about what PostgreSQL ought to do with a value.

**Six defects fixed, each with its reproduction.**

1. **`DetermineVersion` connected before the database existed.** `PostgreSQLDevice.InternalStarted` determined the version first and created the database second, and `DetermineVersion` connected to the device's own database - so the first start of a device against any server failed with *3D000: database "..." does not exist*. It now swaps to the stock `postgres` database around its connection, which is what its own `EnsureDatabase` does and what the SQL Server device does in both places (there it is `master`). Its `cursor.Next()` is also guarded now, as the SQL Server device's is.
2. **`DAE_TooManyRows` was missing** from `libraries/PGSQLDevice/Source/SystemCatalog.sql`. Every row-extractor translation calls it whether or not the source can have more than one row, so `row from <table>` could not run at all; its absence failed about a hundred corpus cases. Added, modelled on the SQL Server copy, deliberately **not** marked immutable (PostgreSQL would constant-fold an immutable function of constant arguments at plan time and raise on every row extraction).
3. **A `Money` literal reached the server as a bare numeric.** PostgreSQL has no `money`/`numeric` comparison operator at all, so `where ("T1"."Salary" > 1000.0)` against a `money` column failed outright - which the goldens pinned as correct, because no server had seen them. `PostgreSQLMoney` now sets `UseParametersForLiterals`, which is the designed knob for this, and the parameter is already typed `NpgsqlDbType.Money`. **This moved two goldens** (`Query.Restrict.Comparison.sql`, `Query.Extend.sql`), both from a bare decimal to `@P1`, and no MSSQL golden moved - which is the check that the fix is device-local.
4. **A `date` column read back as `DateOnly`** and was cast straight to `DateTime`. The current driver returns `DateOnly` where Npgsql 2.0.4 returned `DateTime`. `PostgreSQLDate.ToScalar` now accepts both.
5. **A `Time` value could not be written.** `PostgreSQLTime.FromScalar` handed a `DateTime` to a `time` parameter, which the driver refuses. It now hands over a `TimeOnly` keeping the full time of day, and `ToScalar` reads `TimeOnly` and `TimeSpan` as well as `DateTime`. The stale `NOTE:` in `PostgreSQLCommand.cs` that predicted this is updated.
6. **`SQLDevice.MSSQLBinary` was declared `bytea(30)`.** PostgreSQL takes no type modifier on `bytea`, so every create-table statement carrying such a column was invalid. Now `bytea`; the declared length still bounds the parameter through `SQLByteArrayType`.

**Documentation.** A new *Which PostgreSQL versions work* section in `docs/users-guide/dataphor-service.md` with the version table, what still fails, what is unproved and the connection settings; three entries updated in `docs/migration-notes.md` (what an application can see, in detail); the PostgreSQL paragraph of `docs/architecture/devices.md` rewritten and its open Boolean question closed; `AGENTS.md` given the new variable, what it gates and the container recipe; and the plan's D15, WS7 library row and `device-pgsql-port` work-item row brought up to date.

**CI.** A guarded step starts the PostgreSQL 14 service the `windows-latest` image carries and sets the variable, mirroring the LocalDB step exactly - `continue-on-error`, and the variable left empty when the step fails so the live cases report Inconclusive instead of failing.

**Four tickets filed, three arms appended** - see the next section. The arms matter more than the tickets, because they move three defects off the SQL Server device.

## Tickets filed and arms appended

Four defects could not be fixed locally, each because its fix is a decision about something a deployment already has. All four are in `tickets/backlog/` with severity, likelihood and the decline argument:

- `bug-pgsql-device-time-is-timestamp` - the device declares a `Time` column `time` while all eleven operators it registers over that column are written for `timestamp`, so a `Time` value can be written but not compared. The fix is either the column type or eleven translation strings, and both are compatibility surfaces.
- `bug-pgsql-connection-discards-the-error-code` - `InternalWrapException` flattens away `PostgresException.SqlState`, so the device cannot tell a user-correctable error from one that has aborted the transaction; and a PostgreSQL transaction *is* aborted after any statement error, which nothing reports, which is the sixty-case cascade above. Two halves, the first small.
- `bug-pgsql-device-money-loses-precision` - a `Money` column is PostgreSQL `money`, which holds two decimal places, so a value with more is silently rounded. The corpus cannot see it because both sides of its comparison are rounded by the same cast.
- `bug-pgsql-device-identifier-case` - the device creates tables quoted in mixed case and reconciles a single table by a lower-cased name, so a per-table reconciliation never finds a table the device made. Three ways out, each favouring one kind of schema.

Three failure families were **not** filed, because they already have owners and reproduce identically on the PostgreSQL device - which is itself the finding, since the two devices share only `libraries/SQLDevice` and the engine:

- `bug-mssql-device-live-coverage-failures` - both of its arms. The ordering family's membership changes between identical runs on PostgreSQL too, which strengthens the tie-in-the-test-data reading; and the PostgreSQL run shows *why* the current-date-and-time arm fails, which the SQL Server run could not: the device translates the assertion's `DateTime()` into the database server's own clock (`now()::timestamp`) while the stored value came from the engine's, so the case compares two clocks and two time zones. That is a new question the arm did not ask.
- `bug-binary-comparison-needs-the-mssql-device` - device case 70, the same message. Since it fails identically on a device with a different column type, a different driver and different SQL, the cause cannot be the SQL Server device, which is what that ticket's slug says and its body does not.
- `bug-mssql-device-text-columns-lose-characters` - the mirror image of its case-insensitivity arm: `System.UserID` compares case-*sensitively* on PostgreSQL where the corpus expects insensitive, because PostgreSQL compares by the database collation. The two arms are one question - a comparison pushed into a database is that database's comparison - and the arm says so.

## What a reviewer should push on

**The corpus cannot run to its end, and the complete failure picture is therefore indirect.** This is the one measurement in this ticket that is not a single clean run, and it deserves the most scepticism. A PostgreSQL transaction is unusable after any statement error; the corpus runs inside one transaction; so the first *server-side* failure - the `Time` one - is followed by about sixty cascaded failures and hides whatever those cases would have said. The complete picture was read off the run taken **before** fix 5, when the `Time` failure was still client-side (the driver refused the parameter before sending it) and therefore poisoned nothing: 26 failures, being 11 `Time`, 10 ordering, 2 `UserID`, 1 `Binary` key and 2 current-date-and-time. Everything else in the corpus passed. After fix 5 the same build reports 68 to 72 failures, of which about sixty are the cascade. Both numbers are in the handoff deliberately; if a reviewer wants the clean number re-derived, the cheapest route is to land `bug-pgsql-device-time-is-timestamp` and re-run.

**The CI step is the least verified thing here.** That the `windows-latest` image carries PostgreSQL 14.25 as a disabled service named `postgresql-x64-14`, with the user `postgres` and the password `root`, was read from the published runner-image manifest, not from a run. The wall-clock cost on CI is therefore unmeasured - the figure in the workflow comment is the 13 s the fixture took locally plus "a few seconds" for the service start. If the service name or the credentials are wrong, `continue-on-error` keeps the job green and the variable empty, so the failure mode is a documented gap rather than a red build; but the first CI run after this lands should be read.

**The password in the workflow.** `root` is the runner image's own published default for a service on an ephemeral machine, and PostgreSQL has no integrated-security equivalent to fall back on, so there is no way to make the step work without it. A reviewer who disagrees should remove the step rather than try to hide the value.

**Three judgement calls worth a second opinion.** The omitted statement in `TestPGSQLDevice.d4`, above. The decision to pin five known-failure patterns in the fixture rather than a case count, which follows from the ordering family's membership changing between identical runs. And `UseParametersForLiterals` on `PostgreSQLMoney` as the fix for defect 3 - `ToLiteral` looks like the natural place and is not (it is consulted only for cursor key parameters, never for a literal operand of a translated expression), so the knob is the right one, but it changes generated SQL and a reviewer should read both golden diffs.

**Things left unproved, stated plainly.**

- **The streamed read path.** Nothing in the corpus stores a value large enough to need `SQLCursor.InternalOpenDeferredStream`, so large `Binary` and `SQLText` values are untested beyond about 200 bytes. The corpus's largest `Binary` case (a 384-character hex literal) passes.
- **`PostgreSQLMSSQLBinary.ToLiteral`** base64-encodes its value into `cast('<base64>' as bytea)`, which is not a PostgreSQL `bytea` literal (those are hex `\x...` or the escape format). It is reached only for a cursor key parameter on a column of that type, which fix 6 has only just made creatable, so nothing has exercised it. Recorded here rather than filed: it is one line in a path no deployment can have reached, and whoever takes `bug-pgsql-device-identifier-case` or the `Time` ticket will be in the same file.
- **The catalog store.** `store-pgsql-port` has not landed - `src/engine/Store.PGSQL` is not in `Dataphor.slnx` - so its 14 contract cases were not run. That ticket is next in sequence and can use the same variable and the same container.
- **Encryption.** The servers measured accept unencrypted connections, which is what the driver then used, so nothing about TLS was tested. The user's guide says so and names where the keyword would go.
- **Isolation levels.** `PostgreSQLConnection.InternalBeginTransaction` still maps `ReadUncommitted` and `RepeatableRead` onto `ReadCommitted`. No live case showed it wrong, so it is unchanged, as the ticket instructed.
