# Review: finish the core SDK conversion (spike, coverage check, build documentation)

Second half of the work item `build-core-sdk-projects` (plan WS1); it keeps the slug, so tickets waiting on `build-core-sdk-projects` wait on this one. The first half, `build-core-sdk-convert` (in `complete/`), converted ten projects to SDK-style project files and left the spike in `tools/net-spike` unable to run.

## What changed

**`tools/net-spike/convert.py`**
- `is_converted(path)`: a project file whose root is `<Project Sdk="…">` with no MSBuild 2003 namespace. Such a project gets no wrapper; the script prints `<Name>: SDK-style, used in place`.
- A wrapper's `ProjectReference` to a converted project points at the real project file by absolute path; references between wrappers stay `..\<Name>\<Name>.csproj`.
- `central_versions(repo)` reads the `PackageVersion` items of `Directory.Packages.props`. Each wrapper `PackageReference` takes that version when the package is listed there, and otherwise keeps the spike's own version. Wrappers still write `Version=` attributes because they sit outside the repository and do not use central package management. Result for the Server wrapper: System.ServiceModel.* 10.1.0, Newtonsoft.Json 13.0.4, System.Data.SqlClient 4.9.1.
- `compiled_files(path)`: the Compile items of an SDK-style project, used by the guard below.

**`tools/net-spike/run.py`**
- `CONVERTED` (name → real project path) is filled from `projects.txt` with `is_converted`.
- `build()` runs `dotnet build <repo project>` for a converted project, with the same quiet flags, log file and `summ.py` summary as for a wrapper.
- `find_dll()` gets a converted project's assembly from `dotnet msbuild <project> -getProperty:TargetPath -p:Configuration=Debug`, and never walks a work-directory `bin` folder for it. A wrapper with the same name left over from an older work directory therefore cannot be picked up.
- Removed the three landed `PATCHES` entries (`ServiceClient.cs`, `ClientServer.cs`, `ThreadUtility.cs`) and the `"DAE"` entry of `STUBS`. Deleted `stubs/Engine.cs`. Kept: the Store.SQLite patch (`ResultCode`, K10 "begin immediate"), K1 (`ServerCatalogDeviceSession.cs`), the Frontend `IStreamProvider` patch, the Connection K19 patch, and the `Server` stub.
- Guard `check_overrides()`, which runs before patches are applied: it exits with a message if a `STUBS` key is a converted project, or if a `PATCHES` file is among a converted project's Compile items. A real project compiles the repository file and would silently ignore the override.
- `sys.dont_write_bytecode = True` before `from convert import …`. Without it the import left `tools/net-spike/__pycache__/` in the repository; it is ignored by git, but it is an extra entry in `git status --ignored`.
- `--only` help text now says "projects", not "wrapper projects".

## Known gaps and things for the reviewer to check

- **The guard looks only at Compile items and `STUBS` keys.** None of the spike's overrides target an `EmbeddedResource`, so a resource override would not be caught. `compiled_files` reads literal `Include` paths. The converted projects list plain relative paths; a wildcard or `$(Property)` include (for example after `build-globbing-cleanup`) would not match. The spike should be gone by then.
- **Packages missing from `Directory.Packages.props` keep the spike's versions.** These include System.Configuration.ConfigurationManager 8.0.1, System.Data.Odbc/OleDb 8.0.1, System.Data.SQLite.Core 1.0.119, System.Resources.Extensions 8.0.0 and Npgsql 8.0.6. That is harmless while no converted project references them. It will need care when `build-server-project` adds, for example, `System.Data.SQLite.Core` centrally; the code already takes the central version once it is listed.
- **The `net8.0` half of Appendix A can no longer be reproduced.** Every wrapper that references a converted project fails restore with `NU1201` below `net10.0`. The README says so. Appendix A's opening paragraph still describes the original two-framework run; that text is historical and I left it as it was.
- **Converted projects are built twice in a run**: once directly, in the project loop, and again as references of wrappers, which is incremental. The `artifacts/` output is shared with a developer's own `dotnet build Dataphor.slnx`, so a spike run and an IDE build at the same moment could contend for the same files. Nothing was done about it; the spike is throwaway.
- **Spike hosts still run without NLS** (`Smoke`/`Cov` are built in the work directory and do not inherit `Directory.Build.props`). This is unchanged, as the ticket asked.
- The AGENTS.md layout-table row for `tools/` still says the spike runs "without modifying the repo". No source is modified, but build output now lands in `artifacts/`. That table was out of scope, so I left it.
