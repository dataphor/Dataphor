## The three new splitter capabilities, and why each was needed

**`(drop)` as a page-map `output`** removes a section and everything under it. Every library chapter ends in a generated *Schema* section - the forms, roles, devices, types and tables the library defines - filled from a live catalog at publication time. Without this, each page would carry five or six headings saying "The following lists the forms defined in the X library" above nothing. 95 sections are dropped, each listed in the report with the row's reason; a page inside a dropped section is an error, with a test for both halves.

**`--include FILE.xml`** splices a file in at the `<?DocLib ExtDoc … FILE.xml?>` instruction that names it. `SQLDeviceSettings.xml` (17 KB, hand-written, the settings every SQL device accepts) is a bare `<para>` with no section of its own, so no page map can address it, and both device chapters' prose depends on it: MSSQLDevice's settings section says "Setting available to all SQL devices are listed in the next table" and SQLDevice's says "For a list of additional settings available for specific SQL devices see:". Instructions that are removed rather than spliced are now listed.

**`--facts TSV`** fills the *Definition* section's five generated blocks - version, requisites, files, registered assemblies, registered classes - from `library-facts.tsv`, and writes the library's name where `<?DocLib D4Field LibraryName?>` stood. Each block is an instruction followed by a one-row template, which the split repeats per fact so the hand-written column headings survive; a block the table has no row for is removed with its heading.

Two smaller repairs the library chapters forced, both in the same module:

- **A declaration is looked up by the id of the nearest enclosing section**, not by the page's own id. A library's operator sections are nested under their category rather than being pages, and without this every one of them would have lost its signature block. For a page whose sections are all pages - all 342 of the core library's - it is the same id, which the byte-identical rerun confirms.
- **A section title is stripped of its index terms and the source's line breaks, and a `<bridgehead>` left with nothing under it is dropped.** The first produced headings like `##   Definition`; the second left eight dangling `**See Also**` paragraphs, one per chapter, whose list of links was an unwritten placeholder.

## Where I departed from the ticket, and why

Each of these is a place a reviewer should form their own view.

1. **`SQLDeviceSettings.xml` lands on two pages, not one.** The ticket's source table listed it only under SQLDevice. `MSSQLDeviceReference.xml` splices it too, and its own sentence promises it ("listed in the next table"), so splicing it into both is what the 2007 build did. The alternative - rewriting that sentence - would change the reference's meaning.
2. **Registered classes could not come from `Register.cs` for most libraries, so most pages have no *Registered Classes* section.** The ticket's premise was that `DAERegister.GetClasses()` returns them. Nine of the eleven `Register.cs` files in `libraries/` build the list by reflecting over every type in the assembly (`type.IsSubclassOf(typeof(PlanNode))` and friends), so the names depend on the build, not on any readable file. Only `Connection` (3 names) and `ODBCConnection` (1) name theirs literally. `System.Internet` names 21 literally **and** reflects, so its list would be incomplete, and an incomplete list published as "the classes registered in the System.Internet library" is worse than none - its section is omitted too. The omission is explained once in `reference/libraries/README.md`, the same way the Schema omission is.
3. **Registered assemblies came from the `.d4l`, not from `Register.cs`.** A library's registered assemblies are exactly its `files.filereference` entries marked `isassembly="True"`: `LibraryUtility.RegisterLibraryFiles` (`src/engine/Server/Schema/LibraryUtility.cs:428-449`) loads each file and calls `RegisterAssembly` only for the ones whose `IsAssembly` is set. Each assembly's simple name equals its file name without `.dll` for all 13 libraries, checked against the `<AssemblyName>` in each `.csproj`.
4. **31 distinct link targets needed rows, not 27.** The ticket's 27 counted only `O-Frontend.*`, `O-MSSQLDevice.*`, `O-SQLDevice.*` and `O-SimpleDevice.*`. The run also needed `O-System.Operators.html` (3 links, retargeted to `reference/system-library/README.md#operators` - the 2007 wrapper section is not a page, the hand-written section index is), the three `O-System.Integration.*`, and an unlink for `DRDB2DeviceLibrary.html`, which the built-in `DR<Name>Library.html` rule was sending to a page nothing creates. `O-SQLDevice.D4ToSQL.html` needed no row: its only link sits inside a `<programlisting>`, so the conversion renders it as text.
5. **`DRMSSQLDeviceLibrary-Example.html` stays unlinked.** The ticket said to fill it in. There is no Example section in the 2007 MSSQLDevice chapter - the id was never created - so there is nothing to point at; the row's reason now says that instead of "docs-reference-libraries fills this row in". Filling it would also have changed two more core-library operator pages, breaking the ticket's own check.
6. **Six chapters lose their whole *Documentation* subtree, not just *Connectivity* and *Translation*.** In `Connection`, `Frontend`, `General`, `ODBCConnection`, `Security` and `System.Internet`, every section under *Documentation* (*Settings*, *Connectivity*, *Translation*, *Example*) holds nothing but `<?xm-replace_text {Section Introductory Paragraph}?>`, and the chapter's own `<?DocLib D4ExpressionIf TableDee add{ 'False' Result}?>` says the 2007 build suppressed the subtree as well. `MSSQLDevice`, `SimpleDevice` and `SQLDevice` have `'True'` there and keep theirs.
7. **`SecurityLibraryReference.xml` is an un-instantiated template.** Its chapter id is the literal string `DocLib:D4Field_ChapterID`, four of its section ids are the same shape, and the library name appears 31 times as a placeholder - in its title, its prose and its *Files* heading. The page map keys on those literal ids and the facts table's `library` row supplies the name, which is what the old tool's `add { "Security" LibraryName }` did. The ugly ids never reach the output: the conversion writes no `<a id>` anchors and uses ids only to resolve references.
8. **The operator and type sections are nested, not flat.** The ticket described concatenating them in source order as sections of the page. Nesting them under their category (`## Operators` → `### Document Operators` → `#### Frontend.CopyDocument`) is what makes the 26 links to `#document-operators` and the 21 to `#crc-operators` land on a heading that has its operators under it; flat `##` headings would have left those two landing spots holding nothing but a *See Also*. This is the change that required the declaration lookup above.
9. **The 206 page-map rows were generated by a throwaway script from per-chapter rules and then reviewed, not typed.** The script is not committed: every row's `reason` column states the rule it came from, and the split's report lists all 95 dropped sections, so the result is re-derivable from the table itself. If that is not enough for a reviewer, the rules are: the chapter root is the page; anything with `Schema` in its id is dropped except `DRSystemIntegrationLibrary-Schema-Operators`, which is a separate file's root; `Connectivity` and `Translation` are dropped everywhere; the whole `Documentation` subtree is dropped in the six chapters named above; everything else is a nested section.

## Known gaps, and the sentences the sources left stranded

The ticket asked for these to be reported rather than quietly rewritten.

**Sentences that now name something that does not exist:**

- `SimpleDevice.md`, *Definition* → *See Also*: "[SQLDevice](SQLDevice.md) | [MSSQLDevice](MSSQLDevice.md) | OracleDevice | DB2Device". The last two are plain text; the libraries are parked under `legacy/libraries/` or gone.
- `SQLDevice.md`, *Settings*: "For a list of additional settings available for specific SQL devices see:" followed by three bullets, of which only "MSSQL device settings" is a link. No PostgreSQL bullet exists, which is the gap a reader will actually notice.

Both are 2007 text. Cutting the dead names would read better; it is also an editorial change to published reference prose, and a hand-edit to a generated page is lost on the next rerun, so the honest fix is either a `reference-links.tsv` convention that can delete a list item (there is none) or a pass after `docs-remove-old-sources` makes these ordinary documents.

**Source warts carried through faithfully**, each verified to be in the DocBook rather than introduced here:

- `Frontend.Image`'s example is headed "Using Frontend.GetLibraryNodeTypes".
- `SQLDevice.SQLQuery`'s example is headed "Using SQLDevice.SQLExecute".
- `System.Integration.Copy`'s *See Also* runs two links together with no separator (the source has two adjacent `<ulink>`s).
- `SQLDevice.AvailableTables`'s example body is the sentence "See example SQLDevice.D4ToSQL." inside a code fence, because the source put a `<ulink>` inside a `<programlisting>`.
- `Frontend.CreateAndSave`'s example writes "the text document" and its output shows "my text document".
- `SQLDeviceTypes.xml`'s root title is "Sclar Types"; the page map corrects it to "Scalar Types", as the core library's equivalent row already did.
- The common SQL settings table renders with a trailing empty column: the source declares `cols="4"` and gives every row three cells. Parked as a `NOTE:` in `tools/docs-convert/README.md` with the condition that would make it worth fixing in `convert.py`.

**Pages that are thin, and why:** `General.md` (296 bytes) and `Security.md` (319 bytes) are a title, a sentence and a Definition section. Both 2007 chapters were stubs - `General` has no contents in the tree either, and `Security`'s chapter is the template described above with every prose section unwritten. `reference/libraries/README.md`'s index gives each a one-line description, which is the only place a reader learns what `Security` is for.

**`PGSQLDevice`'s settings are documented nowhere.** The generic SQL device settings apply, and the device adds `Server`, `Port`, `Database` and `SearchPath`, which appear only in `PostgreSQLDeviceSession.cs`. The page shows `Server` and `Database` in the example it took from `libraries/PGSQLDevice/Documents/PGSQL.ReadMe.txt`, and names no others, because the ticket said to describe what the descriptor and the registered classes say while WS4 is still settling the device. Someone will want a settings table there eventually; it is not this ticket's to invent.

**No disagreement found between the registered class names in the tree and the published chapters.** The published *Registered Classes* lists were generated, not written, so the help file's copies are not in the DocBook sources and there was nothing to compare against. The one comparison that was possible went the other way: the published `DRSimpleDeviceLibrary-Definition.html` gives version 2.1.0.0 where the shipped descriptor says 3.0.0.0, which is the reason the ticket gave for reading these facts from the tree, and which this run did not independently re-verify (it would need the help file decompiled again).

## Tests

Five added, all in `tools/docs-convert/test_reference_split.py`, one per new branch. Each pins logic whose failure mode is a wrong or missing published fact, which is why they are here rather than left to the link checker.

| Test | What it pins |
|---|---|
| `test_a_dropped_row_takes_the_section_and_everything_under_it` | `(drop)` removes the section and its subtree and reports it; a page inside a dropped section is an error and nothing is written |
| `test_an_included_file_is_spliced_in_where_its_instruction_stood` | an `--include`d file's content lands at its `ExtDoc` instruction; an instruction naming a file that was not included is removed and listed |
| `test_the_facts_table_fills_the_definition_blocks_and_removes_the_ones_it_has_no_row_for` | the one template row is repeated per fact with the right cells, the version and the library name are substituted, and a block with no facts goes with its heading |
| `test_a_declaration_is_taken_from_the_section_that_holds_it` | a nested operator section gets its own signature, not the page's |
| `test_an_informal_heading_left_with_nothing_under_it_is_dropped` | a dangling `<bridgehead>` goes; one that still has its paragraph stays |

`library-facts.tsv` itself has no test: it is 55 rows of reviewed data read from 13 descriptors and 11 `Register.cs` files, and the ticket is explicit that a reviewed table takes none. Its risk is a wrong value, which a test written from the same reading would not catch; the `reason` column names the file and attribute each value came from so a reviewer can check it directly.

Nothing else is tested. The conversion itself is a document conversion whose gate is the link checker, which failed 144 times on the first run and is how the 31 legacy-map rows were found.

## Which tests were run, and which were not

Build, the Python tool tests, the link checker and the documentation size checker - the whole set of gates that can fail on this diff, each run after the last edit. No `--filter`ed .NET fixture and no D4 coverage script was run, deliberately: the diff holds no `.cs`, no `.d4`, no project or build file, and no change to the coverage runner or manifest. It is Markdown under `docs/`, three tab-separated tables, one Python module and its tests. CI runs the whole suite in Debug and Release on the push that carries this.

The tool tests are still not run by CI - `debt-tool-tests-not-run-by-ci` owns that gap - so both this stage and the review stage have to run them by hand.
