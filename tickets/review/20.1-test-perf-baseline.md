## What landed

A new program, `tests/Dataphor.Benchmarks` (assembly `DAE.Benchmarks`, `Exe` on `net10.0`), built with BenchmarkDotNet 0.15.8. It starts in-process Dataphor engines and measures four things:

| Benchmark | Measures | Published number (Release, slow machine class) |
|---|---|---|
| `EngineStart` | a fresh instance directory, `Start`, `Stop` - the whole cost of coming up | 2,759 ms |
| `DdlDmlMix` | create a table on the in-memory device, insert 3,000 rows one at a time, update them all, read them all back through a cursor, empty the table, drop it | 180 ms |
| `CatalogStoreCold` | a server started on a new instance directory, then stopped - the store's write path | 2,809 ms |
| `CatalogStoreWarm` | a server started on an instance directory a previous start populated - the store's read path | 301 ms |

The whole run takes **about 100 seconds** (99 s and 104 s measured), so it is inside what a ticket can run rather than a by-hand-only step.

`docs/perf-baseline.md` gained three sections for these (the numbers with their machine and configuration head, what they do not mean, how to regenerate), and its existing timing-script sections were retitled so that the two sources are told apart (`## This baseline` → `## The timing scripts`, and likewise for the two sections after it). The plan's `test-perf-baseline` work-item row is now **Done**; `AGENTS.md` and `docs/README.md` gained a pointer each.

## The one result worth reading

A cold start costs about 2.8 s and a warm one about 300 ms, so **about nine tenths of a cold start is creating the SQLite catalog and registering the system library**, not the engine's own startup. That is the empty-catalog case of what `research-catalog-load-profile` is meant to measure on realistic catalogs.

## How to validate it

Each of these was run and is reported honestly below; re-run what you want to confirm.

- **Build, Debug and Release.** `dotnet build Dataphor.slnx` and `dotnet build Dataphor.slnx -c Release`: 0 errors, and **no warning from the new project** - in particular no `NU1902` (the `CoreWCF.NetTcp` package reference plus `<FrameworkReference Include="Microsoft.AspNetCore.App" />` are there for that reason, as in `DAE.Server.Tests` and `TestHarness`) and no `CS8002` (BenchmarkDotNet is strong-named). Check with `dotnet build tests/Dataphor.Benchmarks/DAE.Benchmarks.csproj -c Release 2>&1 | grep -iE "Benchmark|NU19|CS8002"`.
- **A full run.** `artifacts/bin/DAE.Benchmarks/release/DAE.Benchmarks.exe`. Expect four benchmarks, every iteration of every one succeeding, about 100 s, and **no `MinIterationTime` warning** in the summary (outlier *hints* are normal). A run where one benchmark's first iteration is much cheaper or dearer than the rest, or which drifts across the ten, would mean engine static state is leaking between iterations - neither of the two runs taken showed that.
- **Filtering and the exit code.** `--filter '*CatalogStore*'` runs two; `--filter '*NoSuchThing*'` prints "No benchmark ran" and **exits 1**, as does a run whose iterations threw. No arguments runs everything (BenchmarkDotNet would otherwise prompt interactively, which a scripted run cannot answer).
- **It is compiled but not run by the suite.** It is in `Dataphor.slnx` under `/tests/`, so every build type-checks it; `dotnet test` does not discover it (`<IsTestProject>false</IsTestProject>`, no test SDK, no NUnit). Confirm the three suite parts are unchanged: **693 passed, 0 failed, 24 skipped** (13 Common.Tests + 564 part 1, 67 part 2, 49 part 3; the 24 skips are the coverage manifest's 21 known failures and 3 fragments), measured at 5 m 25 s, 3 m 30 s and 3 m 30 s.
- **Nothing ships it and nothing litters.** `tools/layout/Layout.csproj` is untouched and lists its projects explicitly, so `artifacts/layout/*/bin` holds no `DAE.Benchmarks` or `BenchmarkDotNet` file - check with `ls artifacts/layout/release/bin | grep -i benchmark`. BenchmarkDotNet's artifacts are pointed at `artifacts/benchmarks/`, inside the already-ignored `artifacts/`, so no `.gitignore` change was needed and `git status` is clean after a run. `%TEMP%\Dataphor.Benchmarks` is empty after a run that deleted all its instance directories.

## Decisions a reviewer should weigh

- **A new third-party dependency.** `BenchmarkDotNet` 0.15.8 is in `Directory.Packages.props` for this one project. It earns its place for the statistics, the outlier reporting and the markdown export that `docs/perf-baseline.md` carries; if that is judged too much for four numbers, hand-rolled `Stopwatch` timing is the alternative and this is the moment to say so.
- **Two of the four measure nearly the same thing, on purpose.** `EngineStart` and `CatalogStoreCold` differ only in whether the instance-directory setup is inside the measured region; the ticket asked for both, as the numbers two different questions ask for. They came out within 2 % of each other, which is what that predicts.
- **`MixRowCount` is 3,000, not the thousand the ticket suggested.** Measured reason: at 1,000 rows an iteration took 55-104 ms and at 2,000 rows 97-221 ms, and BenchmarkDotNet warns below 100 ms (`MinIterationTime`). 3,000 clears the floor in every iteration. This is why the mix lifts the in-memory device's row cap in its setup - `System.Temp` holds 1,000 rows per table by default and would otherwise fail with error 114113.
- **`IterationCount` is 10, not "a handful".** At five iterations the 99.9 % confidence interval on the engine-start benchmarks came out wider than half the mean. Ten keeps the run near 100 s and the interval usable.
- **The object-id counter is restored per instance, in `Dispose`,** rather than by a `TestEnvironment.WithTheObjectIDCounterRestored`-shaped wrapper: a benchmark's start and its stop are in different methods, so there is no single call to wrap. Same fix, different shape, and the reasoning is on the field.
- **Three source files, not the two the ticket's `files:` named.** `Program.cs` holds the entry point and the BenchmarkDotNet configuration, `EngineBenchmarks.cs` the four measurements and the D4 the mix runs, `BenchmarkServerInstance.cs` the instance helper **and** a `BenchmarkEnvironment` static type beside it (the layout path, the artifacts path, the temporary-directory sweep and the copy helpers). Splitting the host configuration from the measurements seemed worth one extra file; say so if not.
- **No new test, deliberately.** The project rules ask for a characterization test from a ticket that ports or changes a subsystem's behaviour. This one changes no engine behaviour: it is a program outside the suite that drives paths the suite already covers (server start and stop, and D4 DDL/DML the coverage scripts exercise far harder). The verification is the run itself - every iteration of every benchmark must succeed, and two full runs did. `BenchmarkServerInstance` is the one piece with branching, and it is a copy of `TestServerInstance`/`TestEnvironment`, so a test of it would be a test of a copy. If the reviewer disagrees, the thing worth pinning is `BenchmarkEnvironment.DeleteStaleRunDirectories`, and the honest fix would be to extract the shared helper (see the tradeoff note below) and test it once.
- **No migration note.** Nothing public changed: no type or member an extension uses, no D4 semantics, no file format, no contract, and nothing ships this program.

## Notes parked in the code and the documents

- **Accepted tradeoff, at `BenchmarkServerInstance`:** it duplicates the part of `tests/DAE.Server.Tests/TestServerInstance.cs` and `TestEnvironment.cs` a benchmark needs, because referencing the test project would drag NUnit and the test SDK into a console program and both of those types write to `TestContext.Progress`. Revisit condition is stated: if a third consumer appears, extract the instance helpers into a small support project both reference.
- **Accepted tradeoff, at the stale-directory sweep:** a folder whose process id has been reused by a running process stays until a later run (carried over from `TestEnvironment`, which has the same note).
- **Tripwire, at `Program.IterationCount`:** four benchmarks at ten iterations cost about 100 s and the cost is proportional; past about ten minutes the run stops being agent-runnable and becomes a by-hand step, which the two documents would then have to say.
- **Tripwire, in `docs/perf-baseline.md`:** nothing gates on these four numbers - they have no machine-readable copy and no comparison step, unlike the timing scripts. A change that makes one much worse is caught by somebody running the program and reading that section. Giving them a checked-in baseline and a comparison the way `PerfBaselineTest` has one is a separate change, and the document says that is where to record it if it happens.

## Things that could still be wrong

- **The spread is wide.** `EngineStart` ranged from 2.24 to 3.16 s inside one run, and the means moved by up to 12 % between two runs minutes apart. The published numbers are one run's; the document says so and quotes the second run. Nobody should read a 1.3× difference as a regression.
- **`DdlDmlMix` is a judgement.** Six operations chosen to stand for "what an application does to a table", measured as one number. The D4 is in one named place with the reasoning beside it, but a reviewer who thinks the mix is wrong should say so now rather than after numbers are recorded against it - changing the script or the row count invalidates every recorded number.
- **The machine identity is deliberately not in the tracked file.** BenchmarkDotNet's export header names the exact processor, Windows build and SDK build; that header is not carried into `docs/perf-baseline.md`, for the same reason the document uses the label `dev-slow` rather than a machine name (the repository is public). It is in the run's log under the git-ignored `artifacts/benchmarks/`. If that is judged over-cautious, the header is one paste away.
- **Logs from this run** are in `tickets/.logs/20.1-test-perf-baseline.run2.log` and `.run3.log` (16 KB each, pruned automatically) if the per-iteration numbers behind the claims above are wanted.
