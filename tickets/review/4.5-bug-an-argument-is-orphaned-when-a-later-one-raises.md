## What landed

A call evaluates its arguments, runs the operator, and cleans each argument up afterwards in a `finally` - releasing the value where the call owns it, writing it back where the operand was declared `var`. The arguments were evaluated **before** the `try` that `finally` belongs to, so when argument 2 raised, nothing cleaned up argument 1 and whatever argument 1 had produced was orphaned: a `Binary` or a `Graphic` lives in a stream the server owns, and an orphaned stream is given back only when the process ends.

Three changes, all in `src/engine/DAE/Runtime.Instructions/InstructionNode.cs`:

- **`InstructionNodeBase.ReleaseUncalledOperand`**, a new `protected` method beside `CleanupOperand`, carrying the failure-path rule once instead of three copies of a switch. Its `in` and `const` branches are `CleanupOperand`'s own rule verbatim; its `var` branch deliberately does **nothing**, with a comment saying why.
- **A `catch` around the evaluation of every argument after the first** in the three execute shapes that can have one - `BinaryInstructionNode`, `TernaryInstructionNode` and the general `InstructionNode` - releasing the arguments already evaluated and rethrowing with a bare `throw;` so the original error and its stack trace reach the caller unchanged. Each guards on `Operator != null`, as the existing `finally` does.
- **`UnaryInstructionNode` and `NilaryInstructionNode` are untouched.** `UnaryInstructionNode` gained a two-line comment saying why the one-argument shape needs no failure path, so a later reader does not take it for an oversight.

The `NOTE:` on `CleanupOperand` that recorded this defect is gone, replaced by two lines pointing at the new method and saying that the two are not the same rule.

`docs/architecture/value-lifetime.md` records the rule in one new paragraph of *An operand's owner depends on its modifier and on its argument*. No `docs/migration-notes.md` entry: there is no language, API or file-format change, and the only difference an application or a C# extension could see is memory the server stops holding on an error path. The new method is additive on a public type.

## Why `var` does nothing - the half that is not about memory

This is the part worth a reviewer's attention, because the obvious fix is wrong. `CleanupOperand`'s `Modifier.Var` branch pokes the value it is given into the caller's slot, after passing it through `ValueUtility.ValidateValue`. On an argument-evaluation failure there is no callee value to write back - the callee's slots were never pushed, and `argumentValue` for an argument never evaluated is `null`. Poking that into the caller's slot nils the caller's variable, turning a leak into data loss; and `ValueUtility.ValidateValue` runs the scalar type's constraints and validate handlers, which is user D4, so running it while an error unwinds could also raise and replace the error the caller should have seen.

**This was confirmed, not reasoned about.** A temporary variant of the general shape - the naive fix, the existing after-the-call cleanup run over every operand on the failure path - was built and run against the new test: it failed with `a declared operator's call: the script raised. ... The failed call nilled the caller's variable.` and *also* left a stream behind, because the plain `Poke` orphaned the value the caller's slot had held. The variant was removed again and is not in the tree.

## The test, and that it has teeth

One case added to `tests/DAE.Server.Tests/AssignmentValueOwnershipTest.cs`: `ACallWhoseLaterArgumentRaisesReleasesTheArgumentsAlreadyEvaluated`, an `Assert.Multiple` over the three shapes, so a shape-specific regression is not hidden by another shape's failure. Each script catches its own error in D4 and asserts that it caught one, which is the standard the rest of that file holds itself to. It declares three probe operators: `ZProbeRaises() : Binary`, `ZProbeRaisesInt() : Integer`, and `ZProbeVarLast(const AB : Binary, const AC : Binary, var AD : Binary) : Integer`.

| Shape | D4 the case runs | What it pins |
|---|---|---|
| `InstructionNode`, through `CallNode` | `ZProbeVarLast(Binary('0002'), ZProbeRaises(), var LB)` | the `Binary('0002')` is released, **and** the caller's `LB` is neither nil nor changed |
| `BinaryInstructionNode`, through `BinaryEqualNode` | `Binary('0001') = ZProbeRaises()` | the `Binary('0001')` is released |
| `TernaryInstructionNode`, through `ListInsertNode` | `Insert(var LList, Binary('0002'), ZProbeRaisesInt())` over `var LList : list(Binary) := { Binary('0001') }` | the `Binary('0002')` is released and the `var` list is left alone (`LList.Count() = 1` afterwards) |

The declared-operator shape puts its `var` operand **after** the raising argument on purpose: that is the arrangement in which the write-back half of the rule is visible at all, and it is what the naive variant above fails on.

**Both directions were measured.** With `ReleaseUncalledOperand` temporarily neutered (an early `return` at the top), the case failed three times, once per shape, each on the count and each by exactly one stream - `Expected: 0 / But was: 1`, `Expected: 1 / But was: 2`, `Expected: 2 / But was: 3` - which reproduces the ticket's own measurement. The neuter was removed again; `grep -n TEMPORARY` on the file is empty and `git status` shows only the three intended files.

## Performance, read honestly

`PerfBaselineTest` once, recording only (no `DATAPHOR_PERF_BASELINE` label), 28 s: `Timing` 18,000 ms against the recorded 17,764, and `Timings` 2,907 ms against the recorded 3,959 with blocks 376/1,293/1,009/200 against 663/1,711/1,346/204. **Do not read that as evidence of anything.** `docs/perf-baseline.md` records about plus or minus 12 % of run-to-run spread on `Timing` on this machine, so the instrument can only catch a gross regression, and `Timings` came in faster than either of its two recorded runs, which says more about the spread than about this change.

The argument that this costs nothing is structural, not measured: **the normal path executes exactly the instructions it executed before.** Entering a `try` region costs nothing at run time when nothing is thrown; the only new code is inside a `catch` that runs only while an error propagates. In the general shape the existing loop counter was reused as the count of arguments evaluated, so even the normal path's stores are unchanged.

## Where to look hardest

- **The second bound in the general shape.** `for (int index = 0; (index < evaluated) && (index < Operator.Operands.Count); index++)` - `evaluated` is the count actually evaluated, and the operand count mirrors what the existing `finally` iterates (which uses `Operator.Operands.Count` while the evaluation loop uses `NodeCount`). The intent is that the failure path releases no more than the normal path cleans up, whatever the relationship between those two turns out to be. Whether those two can ever differ was not established either way in this ticket.
- **A release inside a `catch` can replace the original error.** If `DataValue.DisposeValue` threw while unwinding, the caller would see that instead of the argument's error. The existing `CleanupOperand` in each `finally` has had exactly that exposure since the beginning, so this adds no new class of risk and no wrapper was added - but it is a judgement call, not a proof.
- **`ReleaseUncalledOperand`'s `In` branch releases unconditionally**, like `CleanupOperand`'s. That rests on the same by-inspection invariant recorded in the `NOTE:` on `CleanupOperand`'s `in` branch - a node lends only when asked, and only the `const` branch asks. Nothing new was verified about that invariant here; the new method inherits it.
- **`AggregateCallNode` was left out of scope**, as the ticket specified: it derives from `PlanNode` and evaluates nothing through these shapes. Not re-checked in this ticket.
- **`docs/architecture/value-lifetime.md` is now at 1,497 words of its 1,500-word cap** (`python tools/docs-size-check/check_size.py` passes). The section was tightened to fit the new paragraph, as the ticket asked, and the page was deliberately not split here. The next sentence anyone adds to that page forces the split - that is three words of headroom, not a comfortable margin.

## Not done, and deliberately

- No `docs/migration-notes.md` entry, for the reason above. Worth a second opinion: the new `protected` member is additive, but a custom C# extension deriving from one of these shapes does now see its earlier arguments released on an error path where they previously leaked.
- Part 1 of the suite was not run locally (CI covers it), and no `--filter` run of the frontend or engine fixtures outside the three ownership fixtures named above.
