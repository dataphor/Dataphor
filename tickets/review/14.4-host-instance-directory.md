## What landed

Two changes at one code site — the computation of the folder that holds the machine's list of server instances — plus the documentation they oblige.

**The folder carries the major version (known defect K27).** `InstanceManager.GetInstanceDirectory()` resolved `PathUtility.CommonAppDataPath(String.Empty, VersionModifier.None)`, giving `%ProgramData%\Alphora\Dataphor\Instances` with no version in it, and `Server.InstanceDirectory` repeated the same expression to default an instance's own data folder. The resolution is now `VersionModifier.MajorSpecific`, so the folder is `%ProgramData%\Alphora\Dataphor\4\Instances` — beside the 4.0 `Aliases.config` the client has always kept there — and `Server.InstanceDirectory` calls `InstanceManager.GetInstanceDirectory()` instead of repeating the expression, so the path is computed in one place.

**A process can be pointed at a different folder.** `InstanceManager` gained the settable static property `InstanceDirectory` and the constant `InstanceDirectoryVariableName` (`DATAPHOR_INSTANCE_DIRECTORY`). Resolution order: a value set on the property, then that environment variable, then the versioned default; the result goes through `Path.GetFullPath`, so a relative value is relative to the process's current directory. Reading the property resolves without creating anything; `GetInstanceDirectory()` creates and returns, with its signature and meaning unchanged, so `LoadMachineInstanceConfiguration` and `SaveMachineInstanceConfiguration` are untouched. Setting the property discards the loaded list (`_instances = null`), so the next `Instances` access throws `InstanceConfigurationNotLoaded` rather than serving instances from the old folder, and `GetInstance` reloads as it already does for an unloaded list.

Supporting it, `PathUtility` gained `CommonAppDataPath(string applicationName, VersionModifier versionModifier, bool ensureExists)`; the private `BuildAppPath` takes the flag and every existing overload passes `true`, so no existing behaviour changes. The one new call site passes `ensureExists: false` by name. Without it, merely reading the resolved default path would create a folder under `%ProgramData%`.

`DataphorHost.BuildHost` keeps its `startServer` factory parameter. The redirection removes the machine-list reason for it but leaves two it cannot carry — `DataphorServiceHost.HostName` and `LoggingEnabled` are properties of the host object, not settings in a `ServerConfiguration`, and `HostProgramTest` needs both — plus one case that needs a start that throws. The decision is recorded at the parameter as an accepted-tradeoff `NOTE:`, and the plan paragraph that gave the machine-wide list as the parameter's reason was corrected rather than the code.

Documentation: `docs/migration-notes.md` (the versioned folder and what an operator and an installer each have to do; the environment variable; the new public members on `InstanceManager`; the new `PathUtility` overload), `docs/architecture.md` (the `DataphorServiceHost.Start()` paragraph and all four on-disk rows), `docs/modernization-plan.md` (K27 now `fixed`, a `host-instance-directory` row in the WS5 table, the `host-instance-configuration` row reduced to the documentation that is left, and the *Generic host* hand-on bullet rewritten), `AGENTS.md` (both places that named the unversioned path, with the variable as the way a local run avoids the machine list), `docs/users-guide/dataphor-service.md` (the path in "Installing Multiple Instances"; its settings section belongs to `host-instance-configuration`).

## Tests

New fixture `tests/DAE.Server.Tests/InstanceManagerTest.cs`, three cases, no `[Parallelizable]`, the property and the variable restored in `[TearDown]`:

- `TheDefaultInstanceDirectoryIsVersioned` — with no override and no variable, the resolved path is `<common application data>\Alphora\Dataphor\<assembly major version>\Instances` and not the unversioned 3.1 path. This is K27's characterization: a return to `VersionModifier.None` fails it. It also asserts that resolving the path does not change whether the folder exists, which is what the `ensureExists: false` resolution is for.
- `AnExplicitInstanceDirectoryBeatsTheEnvironmentVariable` — the variable alone redirects the resolved path, and a value set on the property wins over it. One case, because precedence is one behaviour.
- `ASavedInstanceListIsReadBackFromTheOverriddenDirectory` — points the override at a fresh folder, loads, adds an instance, saves, asserts `ServerConfigurations.config` is in that folder, then loads again and asserts the instance and its port come back. The only case that shows the redirection reaches the file rather than only the resolved string.

No new case for a file an earlier release wrote: `LoadReadsAFileCarryingSettingsThatNoLongerExist` in `InstanceConfigurationTest` already pins that and nothing here changes it. No case for the `InstanceConfigurationNotLoaded` throw after a set: that is the existing `CheckLoaded` behaviour.

## How to validate by hand

- `dotnet build Dataphor.slnx`, then the three suite parts `AGENTS.md` prescribes. All three were run green (416 + 13 in part 1; 67 passed / 11 skipped in part 2; 48 passed / 14 skipped in part 3 — the skips are the coverage manifest's known, unstable and fragment entries).
- Check that a test run leaves `%ProgramData%\Alphora\Dataphor` with no `4` folder in it. Before this change the suite created the unversioned folder; after it, nothing under `%ProgramData%` is touched at all (see the gap below about `CoreWcfProtocolTest`).
- Start a host against a redirected folder from a copy of the runtime layout: set `DATAPHOR_INSTANCE_DIRECTORY` to an empty temporary folder, run `bin\DAEServer.exe -n <name>`, and confirm that `ServerConfigurations.config`, `<name>\Catalog\` and `<name>\Log\` appear there and that the machine's own folder is untouched. **Not done in this ticket** — see the gaps.
- An upgrade check worth a human's eyes: on a machine with a 3.x installation, confirm that the 3.x `Instances` folder and its `ServerConfigurations.config` are not read, written or removed, and that a 4.0 server with no instance registered creates its own in the versioned folder.

## Known gaps and things to weigh

- **One change is outside the ticket's TODO list: `tests/DAE.Server.Tests/CoreWcfProtocolTest.cs` now points `InstanceManager.InstanceDirectory` at a folder of its own in `[OneTimeSetUp]` and clears it in `[OneTimeTearDown]`.** Why: `TestListenerAnswersOnItsOwnPort` reaches `ListenerService.LoadConfiguration`, which resolves the machine's instance folder and so creates it — measured, by deleting `%ProgramData%\Alphora\Dataphor\4` and running that one case, which recreated it. That contradicts the plan's own isolation claim ("no test touches `%ProgramData%`", WS3), it was invisible before only because the unversioned folder already existed on the machine, and the fix is what this ticket's redirection is for. The case asserts nothing about which instances are listed, so an empty list of its own changes nothing it checks. The reviewer may reasonably judge this belongs in a ticket of its own instead; it is three lines and is called out here rather than buried.
- **`TestListensOnlyOnTheReservedPorts` flaked once** during these runs: one full part-1 run counted a third listening port, numbered just above the two the fixture had reserved, and the same assertion passed on three immediate repeats. The fixture's existing `NOTE:` predicted exactly this and names the remedy (narrow the assertion to Kestrel's own default HTTP ports); the observation is now recorded in that `NOTE:` with its date. Nothing in this ticket widens the measurement window — the redirection happens before it. Whether the tripwire having tripped is past the filing bar is a judgment for the reviewer; no ticket was filed.
- **No out-of-process test was added.** The redirection makes one cheap (`ProcessStartInfo.Environment` sets the variable on the child), but that work is `test-client-server`'s, and the plan bullet now says so. Nothing here starts a built executable.
- **The upgrade cost is real and was not mitigated, by design.** An operator upgrading from 3.1 does not see their existing instances and re-enters port numbers, library directories and device settings, by hand or through the installer. 3.1's files are left exactly where they are. The three alternatives (copy the file forward on first start; keep the shared folder and refuse an older file; do nothing) were weighed in the implement ticket and rejected there; `docs/migration-notes.md` carries the operator-facing version.
- **The WS9 installer work has to create and populate the versioned folder.** The migration note says so; no installer code was changed here, and `Setup/` is being replaced.
- **Nothing was verified through the spike.** `ConfigurationUtility/MainForm.cs`, `Dataphoria.cs`, `EditAliasForm.cs` and `ServerConnection.cs` all go through `InstanceManager` and so follow the new folder and the override without source changes, but two of those projects build only through `tools/net-spike`, which was not run: every change here is additive to the public surface (`GetInstanceDirectory()` keeps its signature, the `PathUtility` overload differs in arity), so there is nothing for it to catch. Worth a glance if the reviewer disagrees.
- **A deliberate asymmetry in the property.** `InstanceManager.InstanceDirectory`'s getter resolves the whole order rather than reporting what was set, so a caller cannot ask "was an override set?" and a test restores by clearing rather than by putting a saved value back. That is what makes the getter useful to an operator reading a diagnostic, and the remarks say it; if the reviewer wants both, it needs a second member.
- **The listener still advertises whatever list its own process resolved.** A redirected host that happens to hold the machine's listener port (8060) serves its private instances to anything that asks. That is the existing one-listener-per-machine design, it is what a test wants, and the migration note states it; no code guards against it.
