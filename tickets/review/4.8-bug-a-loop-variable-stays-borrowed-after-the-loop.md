## What was built

A `foreach` whose loop variable is a variable the enclosing block already declared (`foreach LB in ...`, not `foreach var LB in ...`) borrows that variable's stack slot: it lends the slot the row or element the iterator owns and goes on reading it. The engine got both ends of that loan wrong, and both are the same decision, so both are fixed here.

**The mark now ends with the loop.** `Symbols` has a new overload `SetIsBorrowed(int offset, bool value)`; the existing one-argument form is unchanged and delegates to it. The two non-allocating compile sites (`Compiler.CompileForEachStatement`, `Compiler.CompileForEachExpression`) read the symbol's current mark before setting it and restore that value in the `finally` that already runs after the body is compiled. Restore, not clear: the inner of two loops over one variable has to leave the outer loop's mark standing. Consequence: an assignment to the variable *after* the loop releases what it replaces, where it used to release nothing for the rest of the scope.

**The loop now pays for the loan.** `ForEachNode`, `ListForEachNode` and `TableForEachNode` release the value their loop variable's slot already holds, once per loop, before the iteration starts (`program.Stack.PokeOwned(stackIndex, null, program.ValueManager)`), in both the cursor and the list branch of each. It is a no-op on the `null` the allocating form has just pushed, so there is no allocating/non-allocating branch.

**The guard the release needs, and a second one the work turned up.** Each node carries a compile-time flag saying whether the release happens at all. The compiler answers two questions at the site:

- *Is an enclosing loop over the same variable already lending this slot?* Nested loops over one variable are legal D4 and run correctly; the inner loop displaces an element the outer loop's source still owns, so releasing it there is a release too many. This is the question the ticket named.
- *Is this slot a `const` operand of the enclosing operator?* **This one was not in the ticket and is the finding of the stage.** A `foreach` may name one of the operator's own parameters as its loop variable - nonsense code, but legal and compiling today - and a `const` operand's slot holds a value that may have been lent to the call by the argument that produced it. Releasing it leaves the caller naming a released stream. Measured, not reasoned: before the guard, `ZFEConst(LB)` failed with `StreamID (6) not found`, and so did the by-value shape.

A by-value (`in`) operand used as a loop variable needed the matching half: the compiler promotes an `in` operand the body never *assigns* to to `const` and then passes it by reference, and the promotion is decided after the body is compiled, so the compile-time const test cannot see it. The foreach sites therefore now call `plan.Symbols.SetIsModified(node.Location)` - the loop writes that slot, which is exactly what the promotion is a promise it does not - so such an operand stays `in`, is copied for the call, and the slot's value is the callee's own to release. Side effect worth a reviewer's eye: the operator's recorded operand modifier now keeps the `in` the source declared instead of showing `const`, which an emitted catalog script would show. Recorded in `docs/migration-notes.md`.

Because the node's flag now carries two reasons, it is named for what it does - `ReleaseTargetBeforeLending` - rather than for one of them; the ticket suggested mirroring `AssignmentNode._targetIsBorrowed`.

**Clone.** The three nodes had no `InternalClone` at all, so a clone lost `Statement`/`Expression`, `VariableType` and `Location` as well. Each now copies all of its compile-time state, not only the new flag; copying only the flag would have read as complete clone support when it is not. `Clone` is unreachable for these nodes today (it is reached only from the nodes that copy a comparison or a call's result allocation, neither of which can hold a `foreach`), so there is no test - the remark at each override says so.

**`TableForEachNode` is dead code.** `Compiler.CompileForEachExpression` always builds a `ListForEachNode`, and nothing in `src/`, `libraries/` or `tests/` names the type. It was changed in step with its two siblings anyway, with a `NOTE:` at the class recording that the compiler cannot reach it and naming `debt-ws12-hygiene-remainder` as the sweep that owns deciding whether it goes.

## What to test, and what it proves

Four cases in `tests/DAE.Server.Tests/AssignmentValueOwnershipTest.cs`, whose class comment is the running account of this rule and carries them.

| Case | What it pins |
|---|---|
| `AssigningAfterAForEachReleasesTheValueItReplaces` | All four forms the compiler can produce - the statement and expression shape, each over a list and a cursor - assign many times after the loop and leave the stream count where they found it. Fails on all four without the compiler's restore: 99, 9, 99 and 9 streams left behind, the "assignments minus one" the slot being nil on the way out predicts. |
| `AForEachOverAVariableThatAlreadyHasAValueReleasesIt` | The list arm counts back to baseline. The cursor arm asserts that two shapes leave the *same* number behind - the value in the loop variable's own slot, and the same value in a variable the loop never touches - because both pay the per-cursor cost of `bug-a-cursor-copies-the-stack-and-never-gives-it-back` (open) and the difference between them is this defect alone. Without the release: 1 stream on the list arm, and 2 against 1 on the cursor arm. |
| `NestedForEachesOverOneVariableLeaveTheOuterLoopsValueAlone` | Two loops over one variable, 2 by 2 over lists and over cursors: four iterations, count back to baseline. **Checked in both directions:** with the already-lent guard removed, the list arm fails with `StreamID (706) not found` and the cursor arm with `A nil was encountered where a value was expected`. |
| `AForEachOverAnOperandLeavesTheCallersValueAlone` | A loop over the enclosing operator's own operand, one shape per modifier. Each asserts the caller's value as well as the count, because the failure being guarded against balances the count and shows up as the caller's next read failing. Also the reproduction of three leaks this change fixes incidentally: by-value and `var` shapes each leaked one stream per call before it. |

## Known gaps, honestly

- **One shape still leaks, and it is older than this change.** A `foreach` over a `const` parameter whose argument was *computed* rather than read out of a variable orphans that argument: the loop nulls the slot, and `CallNode` hands the cleanup the slot's final value, so nothing releases the computed one. Measured at one stream per call both before and after this change. The loop cannot release it (the same value may be a caller's), so the fix is at the call site and is a design question; filed as `backlog/bug-a-loop-over-a-read-only-parameter-orphans-a-computed-argument` with the class behind it, which is that a call's operand cleanup reads the slot's final value and so anything that takes a value out of an operand slot without releasing it orphans that value. Named in the `NOTE:` at `Program.Stop` as a blocker that no ordinary program reaches.
- **The `var`-parameter and operator-body shapes the ticket measured are not pinned as separate cases.** The ticket's arm-1 table included a loop inside a nested block and one inside an operator body with a `var` parameter. Both go through the same symbol, and `AForEachOverAnOperandLeavesTheCallersValueAlone` covers the operator-body shape for all three modifiers, so no case was added for the nested block.
- **No test for `TableForEachNode`.** The compiler cannot build one, so the only way to exercise it would be to construct the node by hand, which tests the test.
- **No test for `InternalClone`.** Unreachable, as above.
- **`docs/architecture/value-lifetime.md` was split to make room, which is more than a paragraph edit.** The page stood at 1,497 words against its 1,500-word cap and its own `NOTE:` said the next addition of any size had to split it rather than tighten it, naming the hand-over protocol as one of the seams. The two operand sections moved verbatim into a new page, `docs/architecture/operand-ownership.md` (693 words), leaving `value-lifetime.md` at 1,062; `docs/architecture.md`'s index entry names both, and the three code comments that pointed at the old page for the operand rule (`Stack.PokeOwned`, `InstructionNodeBase.CleanupOperand`, `PlanNode.ReturnsByReference`) now point at the right one. The `NOTE:` that parked the cap is gone, its split having happened. `python tools/docs-size-check/check_size.py` reports 13 files, 0 over. `tools/docs-link-check/check_links.py` reports the same 203 pre-existing errors as before the change (one more file, four more links). A landed `migration-notes.md` entry still links the old page for the operand rule; the link resolves and that page points on to the new one, so a landed record was left as it is - a reviewer may prefer it updated. `tickets/complete/4.7-bug-a-stored-binary-is-never-given-back` asked whoever split the page to fold in a fact about a device session's undo log; that was **not** done here (it is another subject, and that fact is recorded at its code site), but the room now exists.
- **The four documentation sites the ticket named are corrected**, plus three it did not: the `NOTE:` at `Program.Stop`, which listed this defect as one of two blocking a `DEBUG` stream-count check, and the two pointer comments above.
- **The `migration-notes.md` entry is one row** covering the new overload, the mark's narrowed extent, the release, the `const` guard and the promotion change. The ticket reasoned that no entry was owed; it is owed now, because the promotion change is visible in an operator's recorded signature and the new node properties are public surface.

## Worth a reviewer's attention

- The restore in the `finally` uses `node.Location`, a top-of-stack offset, and assumes the body's compile left the symbol stack balanced. The `plan.Symbols.Pop()` it sits beside makes the same assumption, and an unbalanced compile means a plan that is being discarded anyway - but it is an assumption.
- `SetIsModified` at the lending site is the half of this change with the widest reach: `IsModified` has exactly two readers (the operand promotion in `CompileOperatorBlock`, and the marking of a variable passed `var` to a call), so the effect is confined to promotion, but a reviewer should satisfy themselves that is still true.
- The cursor arm of `AForEachOverAVariableThatAlreadyHasAValueReleasesIt` is deliberately a comparison rather than a count. It passes today at 1 against 1 and will pass at 0 against 0 once `bug-a-cursor-copies-the-stack-and-never-gives-it-back` lands. If a reviewer would rather see the number, it has to wait for that ticket.
