## What landed

The engine keeps values too large to carry inline - the D4 types `Binary` and `Graphic`, and rows, lists and tables - in a stream or buffer the server owns, and a variable's slot owns its value. Releasing a scope's variables used to be a *statement the compiler appended to the end of the compiled block*, so only control reaching that end ran it. A raise, and equally D4's `exit`, `break` and `continue` (which the engine implements as .NET exceptions), skipped it and the values were held for the life of the session. A `continue` in a loop whose body declared one leaked once per iteration.

The release now lives in the `finally` that already pops the scope, and is driven by a run-time comparison of stack depths rather than a compile-time list of positions.

**One new public helper.** `Alphora.Dataphor.DAE.Runtime.Stack.ReleaseAbove(int depth, IValueManager manager)` releases the values of the slots above `depth`, nulling each slot before disposing its value. `Stack.Count` is window-relative and is read the same way at entry and exit, so the two depths are comparable; a scope needs no agreement with the compiler about where its variables sit. That is what makes it right for a block that raised before declaring all its variables, and for an operator body whose compile-time symbol frame does not line up with its run-time frame.

**Five call sites**, each in a `finally` that already existed except where noted:

- `FrameNode.InternalExecute` (`ImperativeNodes.cs`) - the D4 `begin ... end` statement.
- `ErrorHandlerNode.InternalExecute` (same file) - the handler's own variables and the copy of the error it pushes.
- `CallNode.InternalExecute` (same file) - above `stackDepth`, after the operand hand-back. An operator body is not a `FrameNode`, so its locals are leftovers in the call's stack window; this is the site that owns them.
- `AggregateCallNode.InternalExecute` (`AggregateNodes.cs`) - twice: around the per-row aggregation block, and around the whole initialization/aggregation/finalization sequence. The second needed a **new** `try`/`finally`; the body was re-indented into it.

**The compiled releases are deleted**, all of them: `DeallocateVariableNode`, `Compiler.CompileDeallocateFrameVariablesNode`, `Compiler.CompileDeallocateVariablesNode`, the inline release loop in `CompileOperatorBlock`, and all eight call sites (six in `Compiler.cs`, two in `DDLNodes.cs`). Two of them were not merely redundant - the `try ... except` handler's wrapper never executed at all (`TryExceptNode` reaches the handler through `GetErrorHandlerNode`), and an aggregate operator's aggregation-block releases ran past its own variables into the aggregate column slots - and both simply stop existing.

Deleting them left three `Symbol resultVar` locals (one in `DDLNodes.cs`, two in `Compiler.cs`) whose only remaining use was the `Symbols.Push` next to them; those are now inlined, matching the idiom in `BindOperatorBlock` beside them. `CompileOperatorBlock`'s `int stackDepth` local became unused and is gone, and the comment above the operand-promotion loop no longer points at the deleted loop.

The `NOTE:` above `Program.Stop` no longer names this ticket: it now names the two leaks that still block its `DEBUG` stream-count check - `bug-an-operator-argument-is-released-by-the-wrong-owner`, and `foreach` over a list never releasing the list.

## How to check it by hand

`Diagnostics.StreamCount()` reports how many streams the server is holding; with nothing running it is 0. Each of these left a stream behind before the change and leaves none now:

```
begin var LB : Binary := Binary('0001'); raise Error('boom'); end;
begin var LB : Binary := Binary('0001'); exit; end;
begin var LB : Binary; while true do begin var LC : Binary := Binary('0001'); break; end; end;
foreach var LI in { 1, 2, 3 } do begin var LB : Binary := Binary('0001'); continue; end;   -- three before, none now
create operator ZF() begin var LB : Binary := Binary('0001'); raise Error('boom'); end;  ZF();
```

A caught error still leaves every variable *still in scope* holding its value - only the scope that ends releases.

No new test file, so `DAE.Server.Tests.csproj` is untouched (confirmed: `git status` shows no change to it).

**The four cases were confirmed load-bearing.** The five `ReleaseAbove` calls were temporarily replaced with a no-op shim, the solution rebuilt, and the fixture run: all four failed, as did eight of the ten pre-existing count cases (the compiled releases being gone, nothing released anything). ## What the reviewer should look at hardest

- **`AggregateCallNode`'s outer release.** It is above the `stackDepth` recorded just after the result slot is pushed, which the aggregate column slots are *also* above. They are safe only because the inner `finally` pops them before the outer one runs - they hold values borrowed from the row the cursor selects into, and releasing one would be a use-after-free. That ordering argument is the most load-bearing thing in the change, and it is only a comment. The `AggregateOperators` coverage script exercises an aggregate whose initialization block leaves variables for the later blocks, which is the region the outer release must not take early; it passes.
- **`CallNode`'s release runs after the operand hand-back in the same `finally`.** If it ran before, the hand-back would read slots already nulled.
- **Borrowed slots.** The surface is the `foreach` loop variable, and the loop pushes that slot *before* executing the body, so a body that is a block has its entry depth above it and never releases it. The one shape worth a second opinion is the list branch, below.

## The `foreach`-over-a-list branch, deliberately not fixed

`ForEachNode`'s list branch still leaks the list it evaluated; the ticket scoped that out and it needs its own ticket. Probed here (throwaway fixture, built, run, removed), stream counts before → after:

| script | leak |
|---|---|
| `begin var LB : Binary; foreach LB in { Binary('0001'), Binary('0002') } do begin end; end;` | 1 |
| the same with a raise inside the loop body | 1 |
| `begin foreach var LB in { Binary('0001'), Binary('0002') } do begin end; end;` | 2 |
| the same with `continue` | 2 |
| a script-declared loop variable that already held a value | 2 |

The first row is the ticket's recorded measurement and is unchanged. The other four were not measured before the change, so read them as today's state rather than as a before/after. **None of the five errored** - which is the question that mattered here, because the list branch, unlike the cursor branch, does not null the slot it borrowed, so a loop over a script-declared variable leaves that variable holding an element the list owns, and the scope that declared the variable then releases it. That is safe only while the list itself is never released. A `NOTE:` at that site records it, so whoever closes the list leak nulls the slot in the same change.

## Cost

**Not separable from run-to-run noise on this machine.** The old release was compiled only for variables whose type `IsDisposable`, so a block with none did no work at exit; now every frame exit walks its own slots and calls `DataValue.DisposeValue`, which falls through a handful of type tests for a native value.

Method, following `bug-assigning-a-binary-variable-leaks-its-stream`: a tight D4 loop of 2,000,000 iterations over `begin var LA : Integer := 1; var LB : Integer := 2; end;` (two slots, neither disposable), Release, in-process through a throwaway fixture on `InProcessTestFixture`, three timed runs per pass with the first discarded as warm-up, five passes each way, the `ReleaseAbove` calls swapped for a no-op shim for the other arm. Ten samples each:

- with `ReleaseAbove`: 614, 617, 628, 630, 633, 639, 640, 709, 843, 982 ms - mean 694
- without: 581, 598, 622, 663, 709, 748, 749, 783, 1200, 1421 ms - mean 807

The arm *without* the extra work measured slower on average, so the difference is below the noise floor; the machine drifted badly over the session (the worst passes in both arms were consecutive). Best-of-arm is 614 against 581 ms, so the added work is bounded at about 16 ns per block exit of two slots on a roughly 310 ns iteration. **No fast path was added**, and a block that declares nothing still does nothing - the loop does not run. If the reviewer wants a tighter number it needs a quieter machine, not more passes: the effect being hunted is a few percent against ±100% noise.

The probe fixture was removed; `git status` shows only the seven intended files.

## Compatibility and documentation

Nothing an application can see changes except the engine's memory use: no D4 semantics, operator signature, class name, assembly name, file format, error code, WCF contract or port.

`docs/migration-notes.md` has two new rows under *Custom C# extensions*: `Stack.ReleaseAbove` added, with what a custom node that opens a scope should do; and `DeallocateVariableNode`, `CompileDeallocateFrameVariablesNode` and `CompileDeallocateVariablesNode` removed, with what replaces them.

Nothing under `docs/architecture/`, as the ticket directed: no page in that set describes the stack, the streams or who releases a value, and `bug-an-operator-argument-is-released-by-the-wrong-owner` - which is still open in `tickets/fix/` - names that page as its own deliverable. The ownership rule is still not finished, so writing the page now would mean writing it twice.
