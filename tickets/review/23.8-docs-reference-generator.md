## What landed

`ReferenceSignatureGoldenTest` (the fixture `docs-reference-signatures` built) gains one case, `EverySystemTableHasAGeneratedPage`, and `docs/reference/system-library/tables/` gains 56 generated files: one page per table variable a bare engine's catalog reports, plus a generated section index. The case compares every file in that folder, whole, with what the catalog generates for it, and holds the two recorded table-variable sets against the catalog in both directions. `DATAPHOR_UPDATE_REFERENCE_GOLDENS=1` - the variable the first ticket introduced - now also writes these pages and deletes the ones no table produces.

**The measurements the work rests on**, all taken against a server carrying no library at all (empty `Libraries`, empty `LibrariesToRegister`), so the set is a function of the engine:

- **55 table variables**, all with `Library_Name = 'System'`: **48 base tables** (from `BaseTableVars`) and **7 views** (from `DerivedTableVars`).
- `src/engine/DAE/Schema/SystemCatalog.d4` has **62** `create table`/`create view` lines (`grep -c "^\s*create \(table\|view\)"`). The 7 that do not reach a catalog reconcile exactly: six (`SourceDerivedReferences`, `TargetDerivedReferences`, `DerivedReferences`, `DerivedReferenceColumns`, `DerivedReferenceParents`, `DerivedReferenceDerivedParents`) are inside the block comment at lines 1853-1915, as `System.GroupName`'s `create type` is in `DataTypes.d4`; the seventh, `Generators`, is created by the body of `EnsureGenerators` in the calling library's own namespace rather than by the script. 62 - 7 = 55.
- **0** `Catalog.Comment` tags in `SystemCatalog.d4`, against **17** in `DataTypes.d4`. That is the measurement behind writing no descriptions: the catalog has none to report.
- **57** references in the System library (`select References where Library_Name = 'System'`).

**Three of the implement ticket's premises were wrong, and the corrections are recorded in the plan's *Design notes, the reference generator*:**

- `Script(Name)` on a table variable does **not** emit its references. It emits the columns with their types and tags, the keys, the orders, the constraints and the table's own tags; the ticket said references too. A reference is a catalog object of its own in this release, and the `References` system table carries each one's id, name, library, owner and generated flags - not the two tables it connects - so nothing a script selects reports that pairing. `Script` of the reference's own name does, one at a time.
- There is **no `Columns` system table**. `docs/reference/system-library/README.md` said the generator would be "pointed at the `TableVars` and `Columns` system tables"; `select Columns` fails with `Unknown identifier "Columns"`. A table's columns are reported only by `Script`.
- The ticket said 60 tables and views in `SystemCatalog.d4`; the grep gives 62, and the catalog gives 55.

## What a reviewer should look at first

**The page shape, and the one decision that departs from the ticket.** The ticket said "One page per table, under `docs/reference/system-library/tables/`, plus a section index", and separately that `docs/reference/system-library/README.md`'s *What is missing: the system tables* section "becomes the tables section, with the index". Those two readings conflict: the index cannot be both a generated file compared whole and a list inside a hand-written page. It landed as a **generated `tables/README.md`**, and the system-library README's section was replaced by three sentences of hand-written prose that link to it. The reason: the ticket's own rule for this folder is that the whole file is generated and compared whole, and generating a region inside a hand-maintained README is the block-within-a-page shape the ticket explicitly assigned to the *other* ticket. A reviewer who prefers the 55-entry list in the system-library README should say so - the generator would then have to write a region of that file, and the comparison would have to become block-scoped for it.

**The `**Built From**` section is a fifth page element.** The ticket's shape was title, framing sentence, definition, links back, "nothing else" - and then invited linking a view's source tables "if that is cheap". It was cheap, so 5 of the 7 view pages carry it: a qualified-identifier scan of the emitted text, kept only where the catalog has a table variable of that name. `System.ListLogs` and `System.ViewLog` get no section, because both are built from an operator call rather than from a table. Nothing asserts the scan is complete - it produces links and no verdict - and a name it finds is in the definition printed on the page either way. Cut it if you disagree; the pages regenerate.

**The `System.TableVars` page carries one sentence no other page carries**, as the ticket asked: it is the table the generator reads, so the page says `select TableVars` and the full `add { Script(Name) Definition }` expression that produces these pages. That is the one special case in the generator (`GeneratorTableName`).

**Line endings.** The ticket said "everything under `docs/` is LF with no byte-order mark". That is wrong in general - `docs/architecture/*` and `docs/reference/README.md` are CRLF - but it is true of `docs/reference/system-library/`: all 343 files there were LF with no mark before this change (measured), and the 56 new ones match. The emitter writes CRLF, so the generator converts on write and **the comparison normalizes both sides to LF before comparing**. That matters more than it looks: `core.autocrlf` is `true` in this clone, so a fresh checkout hands the working tree CRLF versions of these LF files, and a comparison that did not normalize would fail on every page for everyone who cloned.

## Use cases, and how to exercise them

- **Read a page.** `docs/reference/system-library/tables/System.TableVars.md` is the one to read first (simple table, keys, `Storage.Name` tags, and the generator sentence); `System.Objects.md` for a table with a multi-line tag block and a nilable column; `System.LibraryView.md` for the largest view; `System.TableDee.md` for the nilary key and a transition constraint; `System.ServerSettings.md` for a table whose only key is `key { }`.
- **Regenerate and confirm nothing moves.** `DATAPHOR_UPDATE_REFERENCE_GOLDENS=1 dotnet test tests/DAE.Server.Tests --no-build --filter "Name=EverySystemTableHasAGeneratedPage"` reports *wrote 0 ... deleted 0* on a clean tree and fails anyway, as every update run does. Confirmed here.
- **Determinism across two instances** is `TheSameCatalogAlwaysGeneratesTheSameDeclarations`, extended by this ticket: it now asks the same catalog twice and a second, independently started `TestServerInstance` once, for the table definitions and for which table variables are views. Green.
- **Break a page.** Append a sentence to a page, delete another, drop a stray `notes.txt` in the folder: the run reported all three, naming each (*is not what the catalog generates*, with the first differing line; *there is no "tables/System.TableDum.md"*; *is a generated page nothing produces*). An update run then rewrote the edited page **byte-identical to a backup taken before the edit** and recreated the deleted one. Verified.
- **Break the recorded sets.** Removing `System.Users` from `SystemTables`, adding a name the catalog does not have, and moving `System.ViewLog` into `SystemTables` produced exactly the three intended messages, including *the catalog reports it as a view. Move the entry to SystemViews.* Verified. Note that an update run does **not** repair these lists - that is the point of them: a table arriving, leaving or changing kind has to be a C# diff a human reads, not a page that quietly appears.

## Known gaps, stated plainly

- **The pages carry no prose about what each table is for.** That is the decision, with its measurement, and the index says so and points at the Developer's Guide. A reviewer who thinks the reference should carry a sentence per table is asking for new material to be written, not for this generator to be changed - and there is no source to write it from.
- **A regenerated page set is only as reviewable as its diff.** 56 files is a large first commit; after this, a change to a system table is a one-page diff. Nothing enforces that a reviewer actually reads an update run's diff beyond the update always failing and saying so.
- **The fixture is now 1,464 lines** and holds two passes with different comparison rules (block-scoped for the published pages, whole-file for the generated ones). It is one coherent subject - what the reference says against what the catalog says - but if it grows a third pass, splitting the generated-page machinery into its own fixture is the obvious cut, and the shared pieces (`Rows`, `Trim`, `Report`, `FirstDifference`, the update variable) would have to move with it.
