## What landed

The test plan's layer 4 machinery (`docs/modernization-plan.md#ws3-test-suite`, the `L4 Client/server` row) and the two cases that prove it. Nothing in the product changed: every file touched is a test file, a test project file, the solution file or documentation.

### New: the suite's own server program

`tests/TestHarness/DAE.Test.Harness.csproj` and `Program.cs` - a console program with one mode:

```
DAE.Test.Harness serve --instance <name> [--host-name <name-or-address>] [--logging]
```

It builds a production `DataphorServiceHost`, sets the two properties that are host-object properties rather than instance settings (`LoggingEnabled`, default **off**, which is the opposite of the shipped host; `HostName`, default `Environment.MachineName`), and starts it through the production `Start()`. Everything else about the instance comes from an instance list the caller writes and points the child at with `DATAPHOR_INSTANCE_DIRECTORY`. On success it writes `READY <instance> <port> listening=<true|false>` to standard output, then reads standard input; a line, **or end of input**, stops the server and exits 0. Any failure goes to standard error with a non-zero exit code.

**The shipped executable is not started, and will not be.** A hosted server logs unless its host turns logging off, and `Server.StartLog`/`Server.LogMessage` create the Windows event-log source `Dataphor Server` and write to the Windows event log when the process is elevated - which CI runners are. `DAEServer.exe` has no way to be told to be quiet: not a command-line switch (`HostCommandLine` is a compatibility surface), not an instance setting (`ServerConfiguration` carries neither `LoggingEnabled` nor `HostName`). `debt-test-shipped-host-executable` in `backlog/` owns covering the published executable and names the knob it needs. `HostProgramTest` still pins the program's start-and-stop behaviour in process and asserts each executable's dependency file names the catalog-store assembly.

### New: the fixture helper

`tests/DAE.Server.Tests/OutOfProcessInstance.cs`, an `internal sealed class` beside `HostedInstance.cs` and reusing its port reservation and its `ServerConfiguration` builder. Per instance: a fresh temporary root from `TestEnvironment.NewDirectory` holding `Instances\` (a private instance list, written with `InstanceConfiguration.Save` - the static `InstanceManager.InstanceDirectory` of the *test* process is never touched), `Libraries\` (a copy, so the child rewrites `.d4l` files and creates `General` there and never in the runtime layout) and `Instance\` (catalog and log); one free loopback port and `ShouldListen = false`; the child started with its standard output and error drained asynchronously from the moment it starts; readiness by the `READY` line, bounded at 120 s and counted from process start; teardown as a line on the input, a 60 s wait, then `Kill(entireProcessTree: true)` and a 15 s wait, then the directory delete. Every failure path reports the child's own standard output, standard error and state through `Diagnostic(...)`.

### Moved: the client plumbing

`ProtocolClient` is out of `CoreWcfProtocolTest` and into `tests/DAE.Server.Tests/ProtocolClient.cs`, now taking a host name and a keep-alive interval (defaulted to `LocalServer.DefaultKeepAliveInterval`; `test-client-server-abandoned` needs its own). The object-id-counter restoration stayed and its remark was rewritten: out of process the *server's* counter is out of reach, but the reset still moves the counter shared with every other engine in the test process - an in-process hosted server, and the second client `test-client-server-cursors` needs.

### Documentation

`AGENTS.md` *Build and test* gained an **Out-of-process client/server tests** paragraph (what the layer is, what the harness program is, why it is not `DAEServer.exe`, how its path is found). The plan's WS3 work-item table gained a `test-client-server-fixture` row. No `docs/migration-notes.md` entry: nothing here is a surface an application, a deployment script or a custom extension can notice.

## Tests added, and what each verifies

Two, in `tests/DAE.Server.Tests/OutOfProcessProtocolTest.cs`. Both pass.

- **`AServerInAnotherProgramServesTheShippedClient`** (1 s) - that a server started as its own program, from an instance list of its own, serves the client stack the product ships: connect as `Admin`, start a process, `create table`, prepare one statement and execute **that same plan three times** with different parameters (nothing else in the suite executes a prepared plan more than once, so nothing else holds the server to keeping a plan handle usable between calls or the client to using the handle it has), read the three rows back in key order through a cursor; then a second connection on a fresh client finds the same rows, which is how the server says it survived the first client. D4 stays on built-in operators and types over the memory device, for the reason `CoreWcfProtocolTest` records.
- **`TheChildServerStopsWhenItIsAsked`** (6 s) - that the program stops *by itself*, with exit code 0, within the bounded wait, and its port stops answering. It runs with a client channel still open, which is the state Kestrel's graceful shutdown has to get out of (`NetTcpServiceHost.StopTimeout`, ten seconds, then abort). Every other fixture's teardown depends on this working.

No case asserts anything about streams, the message-size quotas or fault typing, and the fixture's own remarks say so and name where those live. `CoreWcfProtocolTest` already runs all three against the real host with the real client over a real socket, and moving the host into another program changes no part of that path; a second copy would cost suite time and establish nothing.

No test was added for the harness program's argument parsing (a wrong argument fails the fixture that passes it immediately and loudly - verified by hand), nor for the path-recording MSBuild target (`TestEnvironment.FindTestHarnessPath` fails with its own message naming the project and the build command).

## Known gaps and places to look hard

Flagged honestly; the reviewer should treat each as an open question rather than a settled one.

- **The part 1 numbers do not add up, and I cannot close the gap.** The fixture measures 14 s on its own, but the bands above differ by about 50 s at their midpoints (14 s to 85 s at the extremes). Five runs in total is not enough to separate that from this machine's own spread, which the `store-parameterized-statements` handoff measured at roughly 30 s on the same command, and both of today's baselines are themselves well above the 2 m 54 s - 3 m 35 s band that handoff recorded, so the machine is slower now than it was then. What I ruled out by reading: the stop case's client is now disposed through a plain `using` (see below), so no client-side engine or keep-alive thread is left running for the rest of the suite. What I did not do: repeat the pair enough times to bound it. If the reviewer wants the number, it is several more runs of each, ideally on an otherwise idle machine.
- **Two child-server starts, where the ticket budgeted one.** `TheChildServerStopsWhenItIsAsked` owns its own child. Sharing the fixture's would make the other cases depend on the order NUnit happens to run them in, which is not guaranteed within a fixture without `[Order]`. The alternative - ordering the cases - buys about two seconds and costs a real coupling, so I took the extra start. Worth a second opinion.
- **The six seconds of the stop case are not the ten-second path.** The child exits in about six seconds with an open channel, so the case shows the program stopping by itself inside the bounded wait; it does **not** show what happens when Kestrel's full `StopTimeout` elapses and the connection is aborted. If that path matters, it needs a client that is wedged rather than idle, which is `test-client-server-abandoned`'s territory.
- **The harness references `Client.csproj` and nothing in it compiles against that yet.** The ticket asked for it, for the `client` mode `test-client-server-abandoned` adds; the project file says so at the site. If the reviewer would rather that reference arrive with the code that needs it, it is a two-line removal.
- **I went one step beyond "extract `ProtocolClient` unchanged".** The session-and-process scaffolding that was the body of `CoreWcfProtocolTest.OnWire` moved onto `ProtocolClient.OnProcess`, so the new fixture does not carry a second copy of it. `CoreWcfProtocolTest`'s own call sites and behaviour are unchanged (its twelve cases pass), and its size note was rewritten with the new count. Check that the shared method has not quietly changed what the twelve cases do.
- **I added a guard the ticket did not ask for.** `Program.RequireInstance` reads the instance list and fails if the named instance is not in it, *before* starting the host. Without it `DataphorServiceHost.Start()` would register a default configuration for an unknown name - and that configuration's library directory is the runtime layout's own, which a running server writes into. The production path is unchanged when the instance is there, which it always is for this fixture; the guard only forecloses the branch that could damage the layout. Judge whether the cost (the list is read twice, once here and once by `Start()`) is worth it.
- **The readiness check is tight on purpose.** `OutOfProcessInstance.CheckReadyLine` requires the child's line to be exactly `READY <instance> <port> listening=false`, which is what makes the ready line evidence that the child found the configuration this fixture wrote and took no listener port. It also means a future change to that line's format breaks the fixture loudly; `tests/TestHarness/Program.cs` and that method are the pair to keep in step, and the fixture spells the command-line strings itself because the test project does not compile against the harness.

## Checked by hand

- **The child dies with its parent.** Run from a shell with standard input at end of file, the harness printed its `READY` line and exited 0 without being asked - which is the mechanism that keeps a crashed, killed or timed-out test run from leaving a server holding a port and a folder. The kill-of-the-process-tree in `Stop` is the second belt and was not separately provoked.
- **Nothing of this fixture is left behind by a default run.** No `DAE.Test.Harness` process, and no folder of either out-of-process instance under `%TEMP%\Dataphor.Tests` (a whole-suite run left two folders there, `LibraryLoadingTest` and `RebuildRegistersLibrariesAndSurvivesRestart` - the documented, pre-existing case of a folder holding a library assembly that stays mapped until the test process exits, which the next run sweeps).
- **No machine state.** `%ProgramData%\Alphora\Dataphor\4` does not exist (what is under `%ProgramData%\Alphora` is a 3.x installation that predates this repository checkout: `Dataphor\3` and an unversioned `Instances`, untouched). The event-log source `Dataphor Server` has no registry key under `HKLM:\SYSTEM\...\EventLog\Application`. `EventLog.SourceExists` could not give a clean answer because an unelevated process cannot search the Security log; the session was **not** elevated, so the code that would create the source - gated on `IsAdministrator` - did not run at all. **An elevated run of the suite has not been tried here**; that is the condition under which a regression in this area would show, and it is the same gap `host-generic-host` recorded for its service checks.
- **`DATAPHOR_TEST_LOGGING=1`.** Both cases pass; the kept folder holds `Instance\Log\Dataphor.log` (the child's own instance log), `Instance\Catalog\DAECatalog`, `Instances\ServerConfigurations.config` and `Libraries\General\General.d4l` - the library the child created, in its copy. The written instance list was read and is the expected one instance with `shouldlisten="False"` and the reserved port.
- **The harness error paths.** A missing instance and a missing mode each print the whole exception to standard error; the message names the folder, the instance and the variable to set.
- **`docs` link check** (`python tools/docs-link-check/check_links.py docs`): 203 errors, all pre-existing missing reference stubs; this change adds no links.

## What the reviewer may want to look at next

- `tests/TestHarness/Program.cs` - the argument loop, and whether `Console.In.ReadLine()` is the right stop signal for a program whose only caller is a fixture (the plan's *CoreWCF hosting* note about the shipped host dropping `Console.ReadLine` is about `DAEServer.exe`, deliberately not about this program).
- `OutOfProcessInstance.WaitForReadyOrExit` - polled (50 ms) rather than driven by `Process.Exited`, because that event fires on a thread-pool thread and could reach a disposed object. Check the reasoning, and that the poll cannot mask a child that prints `READY` and then dies.
- `OutOfProcessInstance.Stop` - the one `catch (InvalidOperationException)` around `Kill`, for the child exiting between the wait and the kill; and the unbounded `WaitForExit()` that follows, which is reached only once the process is known to be gone and is there to drain the asynchronous readers so the captured output is complete.
- `DAE.Server.Tests.csproj`'s `_DataphorRecordTestHarnessPath` target - the `MSBuild` task route the ticket preferred, verified in the generated `DAE.Server.Tests.AssemblyInfo.cs`; it asks the harness project for `GetTargetPath` with the same `Configuration` and records the answer as `AssemblyMetadata`, and `TestEnvironment` changes the extension to `.exe`.
