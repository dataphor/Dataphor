## The one real blocker, and what is behind it

`TestMSSQLDevice.d4`'s third statement cannot succeed on any version:

```
if exists (Objects where Name like 'TestFramework.Coverage.Devices.TestDevice%') then
	raise Error(Concat(...));
```

The library's own `Logic.d4` creates `create operator TestDevice(ADeviceName : Name, AID : Integer)`, and an operator's catalog name is its name with its object id appended, so `Objects` always holds a row matching that pattern. Verified by running it: the script fails with `TestFramework.Coverage.Devices.TestDevice0000018614`, the operator the script itself calls two statements later. It is not an expected value and asserts nothing about the engine; its two neighbours are a commented-out `raise Error('WTF')` and a live one. **It was not edited**: whether a coverage script's statements may be repaired is the owner's call, and `test-pre-3-1-scripts-policy` owns it - a third arm was added there with this evidence and the proposed one-statement change.

So `LiveDeviceTest` proves, today: the libraries register, both devices are created from a definition naming only a server and a database and connect, the corpus library's tables and its 1180 rows are created on one of them through the device, and the script runs as far as its own broken statement. It does **not** yet run the corpus.

**What the corpus does, measured with that statement disabled by hand** (four runs, 2026-11-25, SQL Server 2016 LocalDB; about 10 s for the whole corpus): 8 to 12 of the 1180 cases fail and the set varies between identical runs. Four families, all filed:

| Family | Where it went |
|---|---|
| a table keyed on a `System.Binary` column refuses a second, different value as a duplicate | arm on `bug-binary-comparison-needs-the-mssql-device` (its existing cause, third instance) |
| a `System.String` column on the device compares case-insensitively (2 cases) | arm on `bug-mssql-device-text-columns-lose-characters` (same site: what the device thinks a text column is) |
| a table on the device sorts differently from the same rows in memory (`Next() returned an unexpected row`, 5-10 cases, varying) | new `tickets/backlog/bug-mssql-device-live-coverage-failures.md`, arm one |
| the current date and time does not survive the round trip (1 case) | same ticket, arm two |

The varying set is diagnosed in that ticket: the ordering cases compare the memory device's cursor with the device's cursor over the same four rows, and the `Byte` pair's data has a tie in the ordering column, so that pair was never deterministic. The `String` pair has no tie - it is ordinal against collation.

## Encryption: half proved, half not

`Encrypt` and `TrustServerCertificate` in the variable reach the device as its `ConnectionParameters`, which `SQLDevice.GetConnectionParameters` applies after the connection-string builder has run. **Proved live**: `Encrypt=Strict` in the variable makes `Transaction.Atomicity.TestMSSQL` fail to connect to LocalDB 2016 (`provider: SSL Provider, error: 0`, the TDS 8 handshake that server cannot do), where the device's own `Encrypt=False` default connects and `Encrypt=True` also connects. So the carry-through works and overrides the default.

**Not proved**: that `Encrypt=False` is what a server with an untrusted certificate needs. No SQL Server reachable over a network was available from this machine, and LocalDB treats a local connection's certificate as trusted whatever `Encrypt` says - the measurement the ticket itself predicted. That half passes to `device-sqlserver-version-matrix`, which is recorded in the plan's `device-mssql-port` row.

What the live run *did* close from that row: the device's server-side cursor path. Every device read whose statement begins with `select` takes it, and three coverage scripts now read from a live SQL Server device.

## Things a reviewer should look at hard

- **The current library is left at `TestFramework.Coverage.Base` for the three live scripts.** The preamble sets it and does not put it back, which is the one way those three differ from the other 144. The reason is in the code: the engine refuses a reference from an object in `General` (which requires nothing) to a device in a library `General` does not require, and the scripts spell the device `Coverage.Base.CoverageDevice`, which resolves only as a suffix of its real name. The first arrangement, which restored `SetLibrary('General')`, failed with `Object "General.ListIntegerTestTableOne" ... cannot reference object "TestFramework.Coverage.Base.CoverageDevice" ... because the referenced library is not required by the referencing library`. Judge whether leaving the library set is acceptable or whether the device belongs somewhere else.
- **The device under test is started in the fixture, not by the script.** A `NOTE:` at `LiveDeviceTest.Registration` records why, with the measurement: a SQL device first started *inside* the nested script's single transaction has no rows in `DeviceOperators` for the rest of that transaction, although starting it is what creates its operator maps - and the script's next statement asks for exactly those. Started in its own statement, they are there. That looks like a defect rather than a rule and I could not name the site, so it is parked as the `NOTE:` rather than filed; a reviewer who can name it should file it.
- **Two databases are left on the configured server** (`DataphorCoverageScripts`, `DataphorDeviceCoverage`), emptied at the start of each pass and never dropped, unlike the store contract's. The reason is in `EmptyMSSQLDatabase`'s remarks: what the device left is the evidence. Weigh it. A `NOTE:` there also records that the fixed names are a shared resource, as the store contract's is.
- **The samples' 58 s.** Attempting the three samples costs 58 s per configuration and the only thing it establishes is that the failure is still the recorded one. The ticket asked for it explicitly and the tradeoff is recorded as a tripwire at the site; if a reviewer thinks CI wall clock matters more, that is the first thing to cut.
- **The CI step cannot be verified from here.** I read the runner image manifest rather than running on a runner, which is what the ticket asked for only as a fallback. The first CI run after this lands is the measurement: read the `Start SQL Server LocalDB` step's output and whether it was yellow. Added wall clock is estimated at about 95 s per configuration from the local numbers above (58 s of it the samples), so roughly 3 minutes on an 18-minute two-configuration run; CI's own numbers are unmeasured.
- **`needs-database-server` carries no `ticket`/`error`.** It cannot record a script that needs a server *and* fails for a known cause. Nothing needs that today - all three pass - so the arm was not built. If a fourth such script arrives failing, the choice is a `ticket`/`error` pair on this status or an orthogonal field beside `pass`/`known-failure`; the second is the cleaner shape and was not taken because nothing yet needs it.

## Tests added, and what each verifies

Everything here is the project rules' characterization test for a subsystem being re-hosted that had no coverage. No new assertion about what the device ought to do was written in C#: the scripts are the oracle (decision D2).

| Test | What it verifies |
|---|---|
| `LiveDeviceTest.TheDeviceCoverageCorpusRunsAgainstTheServer` | that `TestFramework.Coverage.Devices` registers against a configured SQL Server, that both of its devices are created from a minimal device definition and connect, and that `TestMSSQLDevice` fails in exactly the recorded way - failing the run if it starts passing or fails differently. Inconclusive with the reason where no server is configured. |
| the three `needs-database-server` manifest entries | engine transaction atomicity across a device boundary, which the memory device cannot show. The first proof of it on .NET 10. |
| `SamplesCorpusTest`'s three attempted samples | that each still fails to register for the recorded reason - its own device naming its own server - rather than for some new one. |
| `SamplesCorpusTest.EverySampleIsAccountedFor`, new clause | that `NeedsADatabaseServer` and `FailsWithADatabaseServer` hold the same samples, so neither list can rot into a case with nothing to read. |

No test was added for the manifest's new status as such (the status's behaviour *is* the three entries), for `TestEnvironment`'s parsing (it is exercised by every live pass, and a wrong value shows up as a connection failure naming it), or for the CI step.
