## What landed

One new D4 coverage script, `tests/libraries/TestFramework.Coverage.Scripts/Documents/LibraryAdministration.d4`, its manifest entry `{ "script": "LibraryAdministration", "status": "pass" }` in ordinal position between `Lexer` and `LibraryCoverage`, and two comment changes in `src/engine/Server/Runtime.Instructions/LibraryNodes.cs`. No engine behaviour changed, in either stage. No migration note: nothing an application, a deployment script or a C# extension can notice moved.

The script covers, in eight sections: library settings (insert, change the value, rename, move to another library, delete, and read back by name); resolving a setting through the current session's library path, including the ambiguity error when two libraries at the same level define it; detaching a library and getting it back with a directory rescan; the three operators that now only say "use the other one instead"; registering a library that is already registered; the five errors an administrator meets, each pinned by its error code and its message; file references, through both the `LibraryFiles` table and the library descriptor, including the one refusal `RemoveLibraryFile` makes; and the level and recursion behaviour of `RequiredLibraries` and `DependentLibraries`. Every library it touches is one it creates, each section drops what it created, and a final statement asserts that none of the thirteen names is left in `Libraries`.

The implement stage (`ticket(implement): debt-library-administration-coverage`) wrote the script and found no engine defect: every behaviour the ticket named works, including the two it was unsure about. The review stage added two measurements, one defect record and five corrections, below.

## Review findings

**How this was checked.** The implement-stage diff was read before its handoff. The four claims the handoff asked a reviewer to re-derive were re-derived from the engine source: the row counts and levels in `SystemRequiredLibrariesNode.PopulateRequiredLibraries` and `SystemDependentLibrariesNode.PopulateDependentLibraries` (3/1 and 2/1 are right, and the two chains really are the two different shapes the script's comments claim); the error-text search; the reachability of `LibraryAlreadyRegistered`; and the `LibraryFileEnvironments` gap. Three facts the handoff asserted were then measured rather than reasoned about, by probing through the real harness: what the detailed error description actually looks like, whether a setting can be moved between libraries, and what the transaction state inside a coverage script is. The whole library area was re-run afterwards (see *Validation*).

**Fixed in this pass.**

- **The stale comment the ticket asked to annotate is now simply correct.** `LibraryNodes.cs` carried `// operator RefreshLibraries(const ALibraryName : Name);` above `SystemRefreshLibrariesNode`, and the implement ticket asked for a `NOTE:` recording that no such signature exists. A note saying "the line above is wrong" keeps the misinformation and adds a second thing to read, so the comment now says `// operator RefreshLibraries();`, which is what `src/engine/DAE/Schema/SystemCatalog.d4:894` declares. The ticket's actual constraint - do not change the operator or its D4 declaration, because the signature is a compatibility surface - is untouched: a C# comment is not a compatibility surface.
- **The five error-code assertions now pin the code as a code.** They searched the flattened error text for the digits alone (`IndexOf(LCaught, '113196')`), and that text also carries absolute source paths and `:line NNN` fragments; the handoff flagged the doubt for a reviewer. Measured format: `ExceptionUtility` prints each link of the chain as `<severity>:<code> ---> <message>` (`src/engine/Base/ExceptionUtility.cs:111`, reached because the file defines `INVERTEXCEPTIONDESCRIPTIONS` at its top). The assertions now look for `':113196 --->'` and so on, which no line number or path can match, and the script's header comment says why.
- **A setting moved between libraries is now covered, and the comment that was ambiguous about it is precise.** Two different methods are called `UpdateLibrarySetting`. The script's comment said renaming a setting reaches "the arm of UpdateLibrarySetting that removes the old tag and adds a new one"; that is true of `SystemSetLibraryDescriptorNode.UpdateLibrarySetting`, which branches on the setting's name, and false of `ServerCatalogDeviceSession.UpdateLibrarySetting`, which every update of the table arrives through and which branches on the **library** name instead. Nothing reached that second method's remove-and-add arm. Measured: `update LibrarySettings ... set { Library_Name := ... }` moves the row and carries its value across. The script now does that, with a comment naming which method each arm belongs to.
- **The one refusal `RemoveLibraryFile` makes is now covered**, with the `LibraryFileEnvironments` table that causes it. The handoff called this the clearest remaining gap and left the judgement to review: it is three statements of setup, it is in the subsystem this ticket exists to cover, and it pins an error an administrator can actually meet, so it was covered here rather than queued. Measured: the environment row inserts; the file row then refuses to delete, with code 104232 and `File 'AdminNotes.txt' in library '.AdminFiles' cannot be removed because it has environments defined.`; removing the environment lets the file go.
- **The script's claim about transactions is now the measured one.** It said only that it opens no explicit transaction. Probed with `TransactionCount()`: the harness runs each coverage script as a nested `ExecuteScript` inside one statement of its own, so one implicit transaction is open from a script's first line to its last and no statement inside it begins another. The script's header says that, because the next reader of a library script needs it.

**Recorded as a `NOTE:`, not filed.** The refusal message above names the library as `.AdminFiles` - with the leading dot of the engine's rooted-name form - because `RemoveLibraryFile` formats the `libraryName` its callers passed through `EnsureRooted`. It is cosmetic, it is the only message in that file built that way, and error message text is the kind of thing an application may be matching on, so the `NOTE:` at `src/engine/Server/Runtime.Instructions/LibraryNodes.cs:486` records the cause and the reason it was left alone, and the script asserts the part of the message that does not depend on it.

**Considered and deliberately not pursued.**

- **`LibraryAlreadyRegistered` (113187) is unreachable from every in-tree caller** - the handoff's finding, re-derived and confirmed: `SystemRegisterLibraryNode` checks `IsLoadedLibrary` first, and both `LibraryUtility.EnsureLibraryRegistered` overloads check `ResolveLoadedLibrary(..., false) == null` first. It gets neither a comment nor a ticket, because it is not dead code in the sense that matters: `LibraryUtility.RegisterLibrary` is `public static` and a custom C# extension can call it, so the guard is that method's own argument check and removing it would be a regression. The script pins the observable behaviour instead.
- **`UpdateLibraryFile` and `UpdateLibraryFileEnvironment` are still unrun.** Both are unconditional remove-then-add glue with nothing to decide, and a test of either would verify wiring. Left alone on purpose.
- **`RefreshLibraries`'s removing half** (`RemoveLibrary`, `EnsureLibraryUnregistered`, the `oldLibraries` loop) still needs a folder deleted behind the server's back, which no D4 script can do. It belongs to `debt-library-attach-from-a-directory`, as the script's comment says.

**Tickets filed: none.** Every finding was either fixed here or recorded at its site; nothing left over was both past the filing bar and unowned. Each remaining gap in the file already has an owner - `debt-library-attach-from-a-directory`, `debt-library-upgrades-coverage`, and `test-pre-3-1-scripts-policy` for the two empty scripts.

**One sibling ticket was given a measured answer it was going to have to find.** `tickets/plan/library-ddl-inside-a-transaction.md` carries an owner condition that it verify no shipped caller drops a library inside an explicit transaction, with "the coverage scripts and tests that drop libraries" on its checklist. The transaction measurement above answers that item and makes the ticket's design constraint load-bearing: a guard that refuses whenever *any* transaction is open would break every coverage script that drops a library, so the mark to test is the transaction's own implicit flag and not the nesting count. That paragraph is now in the ticket.

**Tests: two added, none cut.** The two added are the two contracts above that nothing verified - a setting moving between libraries, and the refusal on removing a file that has environments - each at the layer the behaviour lives at and each written from a measurement. Nothing in the implement stage's script restated the implementation or verified a mock, and the assertions are not vacuous: each compares a measured value, or requires a message that an absent error would not produce. The existing `LErrorHit` try/except idiom in `LibraryCoverage.d4` is the neighbour's shape; the new script's variant of it also pins the message, which is stricter, so it was left as it is rather than made uniform downwards.

**Checked and found nothing to report:** the script's cleanup (every library it creates is dropped, in dependency order, and the detached library is re-attached before being dropped so its folder goes with it); its session hygiene (`SetLibrary('General')` restores exactly what the harness connected with - `Engine.InternalConnect` puts a session with no `DefaultLibraryName` in `General`); source hygiene (tabs, CRLF and no byte-order mark in the script; the byte-order mark preserved in the `.cs` file); the manifest entry's ordinal position; and the documentation (nothing under `docs/` describes library settings, file references or `RefreshLibraries`, and `docs/coverage-report.md` is a dated measurement that a new script does not make stale).
