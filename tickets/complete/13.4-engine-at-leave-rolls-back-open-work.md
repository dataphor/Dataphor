## Background

The coverage script `ApplicationTransactions` joins an application transaction (AT), changes data in it, leaves it, rejoins it and checks the changes are still there. The harness ran every script nested inside one statement, `ExecuteScript('Coverage.Scripts', '<name>');`, whose implicit transaction stays open for the whole script. Leaving an AT disconnects the AT device session, and disposing that session rolls back any transaction still open on it, so each leave inside the outer statement threw away the AT work and the script failed (`Application Transaction read is not repeatable.`). That engine behaviour is unchanged since 3.1; whether to change it is the D4-semantics question in `engine-at-leave-discards-transaction-work` (blocked). Run batch by batch, one implicit transaction per batch (the way Dataphoria runs a script), the script passes.

## What changed (`ticket(implement): engine-at-leave-rolls-back-open-work`)

- `CoverageManifest.cs`: new optional entry field `batches` (`bool?`), documented in the `<remarks>` field list. Only `true` is accepted; it is not allowed on a `fragment` entry.
- `CoverageScripts.cs` (`RunInProcess`): when `batches` is `true`, the harness reads the script from the script server's own copy of the library (`ServerScriptPath`) and runs its text with `process.ExecuteScript(text)`, so each batch gets its own implicit transaction. Registration, preamble and the timeout/abort path are unchanged.
- `coverage-manifest.json`: `ApplicationTransactions` is `pass` with `"batches": true` and a note pointing at `engine-at-leave-discards-transaction-work`.
- `ApplicationTransaction.cs` (`LeaveApplicationTransaction`): a `NOTE:` above the `DeviceDisconnect` call recording the rollback-on-leave behaviour and the blocked ticket.

No migration note: the harness option is test-only, and the engine change is a comment.
