## What landed

The test plan's layer 4 machinery (`docs/modernization-plan.md#ws3-test-suite`, the `L4 Client/server` row) and the two cases that prove it. Nothing in the product changed: every file touched is a test file, a test project file, the solution file or documentation. The implement stage is commit `ticket(implement): test-client-server-fixture`; review changed four things in that work and parked one tripwire, all listed under *Review findings*.

**The suite's own server program.** `tests/TestHarness` (assembly `DAE.Test.Harness`) is a console program with one mode, `serve --instance <name> [--host-name <name-or-address>] [--logging]`. It builds a production `DataphorServiceHost`, sets the two properties that are host-object properties rather than instance settings (`LoggingEnabled`, default off, which is the opposite of the shipped host; `HostName`, default `Environment.MachineName`), and starts it through the production `Start()`. Everything else about the instance comes from an instance list the caller writes and points the child at with `DATAPHOR_INSTANCE_DIRECTORY`, so no run reads or writes the machine's own instance list. On success it writes `READY <instance> <port> listening=<true|false>` to standard output and then reads standard input; a line, **or end of input**, stops the server and exits 0. `Program.RequireInstance` refuses a name the list does not hold, before the host starts, because `DataphorServiceHost.Start()` would otherwise register a default configuration whose library directory is the runtime layout's own — which a running server writes into.

The shipped `DAEServer.exe` is deliberately not started: a hosted server logs unless its host turns logging off, and `Server.StartLog`/`Server.LogMessage` create the Windows event-log source `Dataphor Server` and write to the Windows event log when the process is elevated, which continuous-integration runners are. The shipped host has no way to be told to be quiet — neither a command-line switch (`HostCommandLine` is a compatibility surface) nor an instance setting (`ServerConfiguration` carries neither `LoggingEnabled` nor `HostName`). `debt-test-shipped-host-executable` in `backlog/` owns covering the published executable and names the knob it needs.

**The fixture helper.** `tests/DAE.Server.Tests/OutOfProcessInstance.cs`, beside `HostedInstance.cs` and reusing its port reservation and its `ServerConfiguration` builder. Per instance: a fresh temporary root from `TestEnvironment.NewDirectory` holding `Instances\` (a private instance list written with `InstanceConfiguration.Save`, so the static `InstanceManager.InstanceDirectory` of the *test* process is never touched), `Libraries\` (a copy, so the child rewrites `.d4l` files and creates `General` there and never in the runtime layout) and `Instance\` (catalog and log); one free loopback port and `ShouldListen = false`; the child started with both its output streams drained asynchronously from the moment it starts; readiness by the `READY` line, bounded at 120 s; teardown as a line on the input, a 60 s wait, then `Kill(entireProcessTree: true)` and a 15 s wait, then the directory delete. Every failure path reports the child's own standard output, standard error and state through `Diagnostic(...)`.

**The client plumbing moved.** `ProtocolClient` is out of `CoreWcfProtocolTest` and into `tests/DAE.Server.Tests/ProtocolClient.cs`, now taking a host name and a keep-alive interval (defaulted to `LocalServer.DefaultKeepAliveInterval`; `test-client-server-abandoned` needs its own). The session-and-process scaffolding that was the body of `CoreWcfProtocolTest.OnWire` moved onto `ProtocolClient.OnProcess`, so the new fixture carries no second copy of it. The object-id-counter restoration stayed, with its remark rewritten for the out-of-process case.

**Documentation.** `AGENTS.md` *Build and test* gained an **Out-of-process client/server tests** paragraph; the plan's WS3 work-item table gained a `test-client-server-fixture` row. No `docs/migration-notes.md` entry: nothing here is a surface an application, a deployment script or a custom extension can notice.

## Tests

Two cases in `tests/DAE.Server.Tests/OutOfProcessProtocolTest.cs`.

- **`AServerInAnotherProgramServesTheShippedClient`** (1 s) — a server started as its own program, from an instance list of its own, serves the client stack the product ships: connect as `Admin`, start a process, `create table`, prepare one statement and execute that same plan three times with different parameters, read the three rows back in key order through a cursor; then a second connection on a fresh client finds the same rows, which is how the server says it survived the first client. Nothing else in the suite executes a prepared plan more than once, so nothing else holds the server to keeping a plan handle usable between calls.
- **`TheChildServerStopsWhenItIsAsked`** (6 s) — the program stops by itself, with exit code 0, within the bounded wait, and its port stops answering. It runs with a client channel still open, which is the state Kestrel's graceful shutdown has to get out of. Every other fixture's teardown depends on this working.

Streams, the message-size quotas and fault typing are deliberately not repeated here; `CoreWcfProtocolTest` runs all three against the real host with the real client over a real socket and the process boundary changes no part of that path.

## Review findings

Read the implement diff first, with the handoff set aside until afterwards, then read the supporting code it reuses (`HostedInstance`, `TestEnvironment`, `DataphorServiceHost.Start`), the build plumbing's actual output, and the documentation it touched and should have touched. Built, ran the fixture alone, and ran all three suite parts.

### Checked and sound

- **The build plumbing does what it claims.** The generated `DAE.Server.Tests.AssemblyInfo.cs` carries `DataphorTestHarnessPath` pointing at the real harness output, so the `MSBuild`-task route to `GetTargetPath` works and no path is spelled in code. The harness's `runtimeconfig.json` carries `System.Globalization.UseNls = true` from `Directory.Build.props` — which matters, because the child server's string comparison and culture behaviour must be the product's, and it is inherited rather than restated. It also carries the ASP.NET Core framework reference the CoreWCF host needs.
- **No continuous-integration change is needed.** `dotnet test Dataphor.slnx` picked up exactly the two test containers; the new `Exe` project in the solution adds no third, so `.github/workflows/build.yml` stays as it is.
- **The extraction went beyond "move unchanged", and is still equivalent.** `ProtocolClient.OnProcess` was compared call for call with the `OnWire` body it replaced — same calls, same try/finally shape — and `CoreWcfProtocolTest`'s cases all pass. Its size `NOTE:` claims 754 lines, which is what `wc -l` reports.
- **Documentation is current, including the files this change did not have to touch.** Checked and correctly left alone: `docs/architecture.md` (keeps no inventory of test projects), the plan's *Repository layout* tree (its `tests/` line already covers a C# test project), `tools/net-spike/projects.txt` (the legacy-to-SDK conversion list, which a project born SDK-style does not join) and `docs/migration-notes.md` (nothing here is a surface an application, a deployment script or a custom extension can see).
- **The suite leaves nothing of this fixture behind.** After a full run: no `DAE.Test.Harness` process, and no out-of-process instance folder under `%TEMP%\Dataphor.Tests`. The one folder left is the documented pre-existing case — the coverage-script template, holding library assemblies that stay mapped until the test process exits, which the next run sweeps.
- **`RequireInstance` is worth its extra read.** The guard the implementer added without being asked forecloses the one branch that could write into the runtime layout; one read of a one-instance file at startup is not a price worth that branch.

### Open questions from the handoff, closed

- **The part 1 timing gap is this machine's spread, not the fixture.** The handoff could not reconcile a fixture that measures 14 s with bands about 50 s apart at their midpoints. Part 1 as it stands now ran in **4 m 35 s** — inside the handoff's *baseline* band (4 m 13 s to 4 m 46 s) and below all three of its "as it stands" runs (5 m 00 s to 5 m 38 s). Six runs of the same command now span 4 m 13 s to 5 m 38 s, which is a wider spread than the fixture's whole cost, so there is nothing left to attribute. Part 1 is well under the 8-minute threshold `AGENTS.md` sets for splitting it further.
- **Two child-server starts, not one, is the right call.** Sharing the fixture's child would have the stop case destroy the server the other cases use, and NUnit guarantees no order within a fixture without `[Order]`. Two seconds is the right price for not having that coupling.
- **Three gaps the handoff flagged are each already owned by a ticket on the board**, so nothing was re-filed: the ten-second Kestrel abort path and the unused `Client.csproj` reference and keep-alive parameter belong to `test-client-server-abandoned` in `implement/`; the shipped executable and the untried elevated run belong to `debt-test-shipped-host-executable` in `backlog/`, which already names `OutOfProcessInstance.cs` among its files.
- **The tight readiness check stays tight.** Requiring the line to be exactly `READY <instance> <port> listening=false` is what makes it evidence that the child found the configuration this fixture wrote and took no listener port. Both sides of the duplicated command-line strings point at each other in comments; removing the duplication would mean the test project referencing the harness assembly and copying it into the test output, which trades a documented pair of constants for two copies of a program and a question about which one runs.

### Minor, fixed in this pass

All three in `tests/DAE.Server.Tests/OutOfProcessInstance.cs`, the class whose whole job is to say why a child failed.

- **A child that printed its ready line and then exited passed the constructor.** `WaitForReadyOrExit` returns true on a ready line even when the process has since gone, and `CheckReadyLine` only inspects the line — so every case would then have failed on a refused connection rather than on what actually happened. `Start` now checks the process after the ready line and reports it through `Diagnostic`. This is the question the handoff asked the reviewer to look at, and the answer was yes.
- **`DescribeState` reported "was never started" for a child that was started and then could not be accounted for** — the stop line ignored, the 60 s wait elapsed, the kill not seen to land. That is precisely the path this diagnostic exists for, and it was sending the reader to the opposite conclusion. It now distinguishes never-started from not-seen-to-exit, with a `_wasStarted` flag.
- **Two members had no caller**: `RootDirectory` (removed) and a `public` `InstancesFolderName` used only inside the class (made private).

### Tripwire parked

- `Process.WaitForExit()` with no timeout — in `Stop`, and referred to from `WaitForReadyOrExit` — waits for both pipes to reach end of file, which needs the last handle to them closed. It would therefore not return if the child ever started a process that outlived it and inherited those handles, which would hang a test run outright. The test server starts none today, so this is conditional; the comment at the site claimed outright that the wait "cannot block", which is only true while that stays so. Replaced with a `NOTE:` saying what the wait depends on and to bound it if a future harness mode spawns a child.

### Tests: none added, none cut

The two cases are behaviour tests against a real child process and neither restates the implementation or verifies a mock, so there was nothing to cut. Nothing was added: the deliberate non-duplication claim was checked against `CoreWcfProtocolTest` and holds (`TestLargeMessageInBothDirections`, `TestStreamContentCrossesTheWire` and the four fault cases are all there, against the real host over a real socket). Neither defect found needed a reproduction — both are diagnostic-message defects on paths only a broken child reaches, and a test for either would have to fake a child that lies about itself.

### Nothing filed

No ticket was filed from this review. The two defects found were minor and fixed here; the one conditional concern is a tripwire by the stage's own rule; and every larger gap the handoff named already has an open ticket that owns it.
