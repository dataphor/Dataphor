# Complete: SQLite catalog store — WAL, immediate write transactions, busy error (first half of K10; K26)

## What changed

- **Connection options applied by the store** (`SQLiteStore.InternalInitialize` → `NormalizeConnectionString`). Every store connection is built from `Store.ConnectionString`, which is rewritten once, before the store is marked initialized:
  - `Journal Mode=Wal` always. A configured journal mode is overridden; `JournalMode` (the no-space spelling, which the provider also accepts) is removed first, because when both spellings are present the spaced one wins.
  - `BusyTimeout=30000` (`SQLiteStore.DefaultBusyTimeout`) unless the string sets it.
  - `Default Timeout` = `(BusyTimeout - 1) / 1000` seconds (0 when `BusyTimeout` is 0) unless the string sets `Default Timeout` or `DefaultTimeout`. **Deviation from the ticket**, which said `ceil(BusyTimeout / 1000)`: the provider retries a busy statement until the command timeout has passed and each retry waits up to `BusyTimeout` again, so a command timeout equal to `BusyTimeout` can double the wait whenever the first busy report arrives at exactly the timeout (tick-count granularity). A command timeout below `BusyTimeout` stops after the first report. Measured: with `BusyTimeout=1000`, B fails after 1,173–1,198 ms with the derived value (0 s), and 1,183–1,191 ms with `Default Timeout=1` forced (3 runs); old code (provider default 30 s): 30,129 ms. So `ceil` does not double the wait in practice either; the derivation removes the edge case.
  - The keywords are set through the builder's indexer, not its typed properties: the typed setters wrote `JournalMode=`/`DefaultTimeout=` on .NET Framework (checked in PowerShell 5.1) and the spaced forms on .NET 10, and a user's `journal mode=Delete` beside a `JournalMode=Wal` keeps the rollback journal. Checked on .NET 10 with a throwaway probe (not kept) that normalized eight strings and opened each: `PRAGMA journal_mode` was `wal` for all of them (none, `journal mode=Delete`, `JournalMode=Delete`, both spellings at once, `BusyTimeout=1000`, `busytimeout=5000;DefaultTimeout=7`, `Default Timeout=3`, `BusyTimeout=0`), user timeouts were kept and the derived ones were 29 or 0.
- **Every store transaction begins immediate** (K10 lock upgrades; K26). `SQLStoreConnection.BeginTransaction` now calls its protected virtual `InternalBeginTransaction` for the 0 → 1 begin (it called the SQL connection directly before; the base body is the old call, so other stores are unchanged). `SQLiteStoreConnection` overrides it with `Connection.BeginTransaction(SQLIsolationLevel.Serializable)`, which the provider issues as `BEGIN IMMEDIATE`. `SQLiteConnection`'s "read uncommitted means no transaction" mapping is untouched, so `CatalogDeviceTable`'s read-only connections stay outside transactions. The count and the undo-log marker were already pushed only after the begin returns; a comment now says why.
- **Busy error 130103 `StoreLocked`** (`StoreException`, resource string beside the others), severity Environment, message "The catalog store is locked by another session's open transaction and did not become available within {0} seconds." Raised from `SQLiteConnection.InternalWrapException` when the first `SQLiteException` in the chain has primary result code `Busy` or `Locked` (masked with `0xFF`). `{0}` is `BusyTimeout` in seconds as a double ("1", "1.5", "30"). `SQLiteConnection`'s constructor now parses `BusyTimeout` *before* connecting (it chains to the parameterless `DotNetConnection` constructor and calls `InternalConnect` itself), because opening can itself report busy and would otherwise format "0 seconds".
- **Bug met on the way, fixed here** (`ServerCatalogDeviceSession.AcquireCatalogStoreConnection`, not in the ticket's file list). A session's first catalog write begins store transactions to catch up with the process's open levels. The old code set `_isUpdatable` before those begins, so when the immediate begin timed out (130103) the process rollback that followed ended a store transaction that never began: the store connection's count went to −1, and every later transaction of that session ran its store writes in autocommit (rolled back in memory, kept in the store). `StoreLockWaitReportsStoreLocked` hits this path. Now `_isUpdatable` is set only after the begins succeed, and a `try`/`catch` undoes the acquire (release, or only the count when no connection was taken) because callers acquire before their own `try`. The follow-up's planned cleanup arm is marked as already done in `12.5-store-sqlite-concurrency.md`.

## Known gaps and things to look at

- **Half-started process transaction after a busy begin (reachable now; filed).** A session that has written to the catalog before begins a store transaction at the start of *every* later transaction (the eager design this ticket lands). If that begin times out, `ServerProcess.InternalBeginTransaction` leaves the process transaction pushed: the session stays `InTransaction` with count 1 for good, later statements run inside it uncommitted, their store writes go to the store in autocommit, and the disconnect rolls them back in memory only. Verified with a throwaway probe (steps in the backlog ticket). Not fixed here: the general defect is any participant's failed begin (device or remote session), and the fix is transaction coordination in `ServerProcess`/`Device.cs`. The catalog-store route closes with `store-sqlite-concurrency` (store begin moves into the first write); a test for it is added to that ticket (`BusyAtTransactionStartLeavesNoTransaction`), and the engine defect is `tickets/backlog/bug-process-begin-leaves-partial-transaction.md`. Reviewer: judge whether this window is acceptable, given that `store-sqlite-concurrency` is next in the queue.
- `Locked` (SQLITE_LOCKED) also maps to 130103 as the ticket asked, though in SQLite it usually means a conflict on the same connection (shared cache, or a drop under an open statement), not another session; its message would then be misleading. Not seen in any run.
- The message reads "within 1 seconds" (the ticket's wording, singular not handled).
- No test pins the connection-string rewriting, as the ticket decided; the busy test pins a user-set `BusyTimeout` and the probe above covered the rest once. Whether WAL is actually on is not asserted by any kept test (the concurrency tests would also pass on the rollback journal with immediate begins and a 30 s timeout).
- The error does not name the session holding the lock (the store does not know sessions); nice to have, not required.
- `StoreLockWaitReportsStoreLocked` takes ~1.2 s of fixed wait; the suite grew by about 6 s overall.

## Review findings

Read the diff of `ticket(implement): store-sqlite-wal-busy` before the handoff, then the code around each change: `SQLStore`/`SQLStoreConnection` begin, commit and rollback; `SQLConnection.BeginTransaction` and `WrapException`; `DotNetConnection.InternalConnect`; `CatalogStore`'s connection pool; `ServerCatalogDeviceSession`'s acquire, release and transaction hooks; `Server.GetCatalogStoreConnectionString`.

**Checked and correct (no change):**

- Connection-string rewriting runs in `InternalInitialize`, before `SQLStore.Initialize` marks the store initialized, so the `ConnectionString` setter does not throw; every store connection (pooled and dedicated) is built from that string, and nothing else in the server opens the catalog from `GetCatalogStoreConnectionString`.
- Busy-wait bound: no store or connection code sets a per-command `CommandTimeout` (`SQLCommand.DefaultCommandTimeout` is -1, so `DotNetCommand` leaves the provider's `Default Timeout` in effect), so the derived `(BusyTimeout - 1) / 1000` applies to every store statement. Re-measured: B fails after 1,196 ms with `BusyTimeout=1000`.
- `BEGIN IMMEDIATE` failing: `SQLConnection.BeginTransaction` sets `InTransaction` only after the begin returns, and `SQLStoreConnection` counts the level only then, so a timed-out begin leaves nothing to roll back. Nested store levels never reach the database, so only the first begin of the catch-up loop can fail, as the new comment says.
- `AcquireCatalogStoreConnection`'s new `catch`: when `Connect()` itself throws, only the count is undone; when a begin throws on a connection just taken, `ReleaseCatalogStoreConnection` returns it to `CatalogStore`'s pool, which accepts any connection (the pool only adds; its count is 0 after the failed begin); when an earlier acquire still holds the connection, the count drops and the connection stays. Correct in all three.
- `SQLiteConnection` now parses `BusyTimeout` before connecting; the old `DotNetConnection(string)` constructor did nothing besides `InternalConnect`, so the change keeps behaviour.
- Error 130103: code in the `130` (DAE.Store) range next to 130102; `docs/reference` lists prefixes only, so no reference entry is owed. Migration-notes rows read against the sections they sit in ("see the next section" is right) and the default file name (`DAECatalog.sqlite`).
- Compatibility: no D4 semantics, class names, file formats or contracts changed; the new error code and the now-called `InternalBeginTransaction` virtual are in the migration notes.
- The implementer's known gap, a process left half-begun when a store begin times out at the start of a transaction: reachable on this commit only for a session that has written to the catalog before and then meets another session's lock for longer than `BusyTimeout`. Accepted for this window: `store-sqlite-concurrency` is next in the queue (sequence 12.5), carries the test `BusyAtTransactionStartLeavesNoTransaction` for it, and the general engine defect is filed as `bug-process-begin-leaves-partial-transaction` with triage fields and a verified reproduction.
