## What landed

The PostgreSQL device had been built and its generated SQL pinned by checked-in golden files, but nothing in the repository had sent a statement to a PostgreSQL server since about 2017. This work item built the harness that does, ran it against four PostgreSQL versions in containers, fixed what could be fixed locally, filed what could not, and wrote down the supported version floor. **PostgreSQL 14 is the documented minimum**; the device behaves identically on 13.23, 14.25, 16.16 and 18.7, so the floor is a support decision rather than the point where the device stops working.

The implement stage is commit `ticket(implement): device-pgsql-port`. Review added three fixes, one refactor and one ticket, all listed below.

**The harness.** `TestEnvironment` gained a `DATAPHOR_TEST_PGSQL` region beside the SQL Server one: the variable, the parsed host/port/login, the whole D4 of a device definition plus its device user, and the statement that empties the device's database. Two deliberate choices run through it. The variable is parsed with the framework's `DbConnectionStringBuilder` rather than with Npgsql, because the test project must not reference the PostgreSQL driver - the driver arrives with the library `libraries/PGSQLConnection`, and whether the runtime layout puts it where that library can find it is one of the things a live run proves. For the same reason the database is emptied over the device's own connection, as a `SQLDevice.SQLExecute` of a `do` block, which means the device has to be started first - and starting it is what creates the database and the `DAE_` support functions, so the emptying drops tables only.

**The driver script.** `tests/libraries/TestFramework.Coverage.Devices/Documents/TestPGSQLDevice.d4`, the sibling of `TestMSSQLDevice.d4`. One statement of the sibling is deliberately absent: the sibling raises an error naming every catalog object called `TestFramework.Coverage.Devices.TestDevice*`, which can never succeed, because the library's own `Logic.d4` creates an operator whose catalog name is exactly that - which is why `LiveDeviceTest` is a recorded known failure and never reaches the corpus at all. The reason is in the file header, and `test-pre-3-1-scripts-policy` still owns whether the sibling may be repaired.

**The fixture.** `LivePGSQLDeviceTest`, three cases: the device reads and parses the server's version and its `MajorVersion` matches; the 1,180-case device-coverage corpus runs against the server, recorded as a known failure that must match five named patterns; and an `SQLDevice.MSSQLBinary` column can be created, written and read. No other tests were added - the translation goldens already cover what the device generates, and the corpus is the oracle for everything about values (decision D2).

**Nine defects fixed, each with its reproduction.** Six in the implement stage: `DetermineVersion` connected to a database that did not exist yet; `DAE_TooManyRows` was missing from `SystemCatalog.sql`, so `row from <table>` could not run at all; a `Money` literal reached the server as a bare numeric, which PostgreSQL cannot compare with `money`; a `date` column read back as `DateOnly` and was cast straight to `DateTime`; a `Time` value could not be written at all; and `SQLDevice.MSSQLBinary` was declared `bytea(30)`, which PostgreSQL rejects. Three more in review - see the findings below.

**Documentation.** A *Which PostgreSQL versions work* section in `docs/users-guide/dataphor-service.md` with the version table, what still fails, what is unproved and the connection settings; the PostgreSQL entries of `docs/migration-notes.md`; the PostgreSQL paragraph of `docs/architecture/devices.md`, with its open Boolean question closed; `AGENTS.md` given the new variable and the container recipe; and the plan's D15, WS7 library row and work-item row brought up to date.

**CI.** A guarded step starts the PostgreSQL 14 service the `windows-latest` image carries and sets the variable, mirroring the LocalDB step: `continue-on-error`, with the variable left empty when the step fails so the live cases report Inconclusive rather than failing.

## Tickets filed, and arms appended to existing ones

Five defects could not be fixed locally, each because its fix is a decision about something a deployment already has. All five are in `tickets/backlog/` with severity, likelihood and the decline argument:

- `bug-pgsql-device-time-is-timestamp` - the device declares a `Time` column `time` while all eleven operators it registers over that column are written for `timestamp`, so a `Time` value can be written but not compared.
- `bug-pgsql-connection-discards-the-error-code` - `InternalWrapException` flattens away `PostgresException.SqlState`, and nothing reports that a PostgreSQL transaction is aborted after any statement error, which is the sixty-case cascade in the corpus run.
- `bug-pgsql-device-money-loses-precision` - a `Money` column is PostgreSQL `money`, which holds two decimal places, so a value with more is silently rounded.
- `bug-pgsql-device-identifier-case` - the device creates tables quoted in mixed case and reconciles a single table by a lower-cased name, so a per-table reconciliation never finds a table the device made.
- `bug-mssql-binary-column-cannot-take-a-value` (filed by review) - the SQL Server device's `MSSQLMSSQLBinary` is the untouched twin of the PostgreSQL class review fixed, and fails the same way.

Three failure families were **not** filed, because they already have owners and reproduce identically on the PostgreSQL device - which is itself the finding, since the two devices share only `libraries/SQLDevice` and the engine. Arms were appended to `bug-mssql-device-live-coverage-failures` (both of its arms, and the PostgreSQL run shows *why* the current-date-and-time arm fails: the device translates the assertion's `DateTime()` into the database server's own clock), `bug-binary-comparison-needs-the-mssql-device` (device case 70, which moves the cause off the SQL Server device) and `bug-mssql-device-text-columns-lose-characters` (the mirror image: `System.UserID` compares case-*sensitively* on PostgreSQL, so the two arms are one question).

## Review findings

The implement diff was read first, then the handoff. The device's own sources were read whole (`PostgreSQLDevice.cs`, `PostgreSQLTypes.cs`, `PostgreSQLCommand.cs`, `PostgreSQLConnectionStringBuilder.cs`), together with the shared machinery the fixes lean on - `SQLDevice.FromScalar`, `PrepareSQLParameters`, `SQLScalarType`, `SQLBinary`, `SQLCommand.FinishParameter`, `SQLDeviceCursor.PrepareStatement` - and the SQL Server device's counterparts of everything changed. Every claim in the handoff about where a knob is read was traced to the code that reads it.

### Found and fixed in this pass

- **An `SQLDevice.MSSQLBinary` column could be created but never written.** The implement stage's sixth fix made the column creatable for the first time, which made two further defects reachable, both of them older than this work item. `PostgreSQLCommand.PrepareParameters` had no branch for `SQLByteArrayType` - the parameter type such a column binds - so every value raised *unknown SQL data type* from the connection class before reaching the server; every other connection class in the tree has had that branch since 3.1. And `PostgreSQLMSSQLBinary` cast the value straight to `byte[]`, where a D4 value of a type declared `like System.Binary` arrives stream-backed, so the insert threw *Unable to cast object of type StreamID to type System.Byte[]* from `DeviceSession.InsertRow`. Fixed by adding the `bytea` branch (with `Size` deliberately unset, because the column has no length to bound and the current driver truncates to `Size`) and by deriving `PostgreSQLMSSQLBinary` from the shared `SQLBinary`, which already converts both shapes in both directions - so the three operators the class used to copy are now its base's, and large values gain the stream allocation the base does on the way back. The reproduction is `LivePGSQLDeviceTest.TheDeviceRoundTripsAByteArrayColumn`, which replaces the implement stage's create-only case: it fails with each fix removed and passes with both.
- **The SQL Server twin of the second half is unfixed**, and is `bug-mssql-binary-column-cannot-take-a-value`. It is a separate ticket rather than an inline fix because it is another device's compatibility surface and its reproduction needs a live SQL Server; the ticket carries the architecture rung as well as the instance - one implementation of "a D4 Binary value in either shape" instead of a copy per device, which is what the PostgreSQL side now has.
- **The two stock-database swaps were duplicated and inconsistent.** `DetermineVersion`, rewritten by the implement stage, and `EnsureDatabase`, untouched, both point the device at the stock `postgres` database around one statement, but in opposite orders: the new one swaps before opening the session, the old one after. The old order worked only because a device session opens its connection lazily. Extracted into `ExecuteAgainstStockDatabase`, which both now call, so the ordering is right by construction and the reason is written once.
- **Three documentation statements were wrong or stale.** The migration note said the declared length of a byte-array column "bounds the parameter rather than the column", which the first finding above shows it does not; the user's guide said the device installs "forty-odd" `DAE_` support functions, where the script defines fifty-seven; and the CI step's cost comment said "the fixture's two cases" where there are three. The `PostgreSQLMoney` comment's claim that `ToLiteral` "is only consulted for cursor key parameters" was also narrowed to what is true - `PrepareSQLParameters` computes it for a non-cursor execute too and discards it; what matters, and what the comment now says, is that it is never substituted into a statement while `UseParametersForCursors` is on.

### Checked and sound

- **Every one of the implement stage's six fixes is at the right site.** `UseParametersForLiterals` really is the knob - `SQLDevice.FromScalar` is the only reader, and it chooses between a literal and a plan parameter exactly as the comment says; the parameter then carries `SQLMoneyType`, which `PostgreSQLCommand` sends as `NpgsqlDbType.Money`. A null `Money` literal still works, because `PrepareSQLParameters` binds null before calling `ParameterFromScalar`. The two moved goldens are the only two that move, and no MSSQL golden moves, which is the check that the fix is device-local. `DAE_TooManyRows` matches what `SQLDevice.TranslateExtractRowNode` emits and the message is the text of error 105199, as the SQL Server copy's is; the "deliberately not immutable" reasoning is correct - an immutable function of constant arguments would be folded at plan time and raise on every row extraction.
- **The judgement call in `TestPGSQLDevice.d4` is right.** The omitted statement cannot succeed against any device or version, for the reason the file header gives, and the rest of the script is the sibling line for line - including the `DeviceOperators` check, which passes. Nothing was copied that could not pass.
- **Pinning five failure patterns rather than a case count is right**, and the measurement behind it was reproduced: the ordering family's membership does change between identical runs, so a case id could not be pinned. The roll-up this review measured on PostgreSQL 18.7 has 71 failed cases, inside the handoff's stated 68-72, of which about sixty are the transaction-abort cascade - so the handoff's two numbers and its account of why the clean figure had to be read off a pre-fix run are both accurate.
- **The four filed tickets and the three appended arms are accurate and well-aimed.** Each names one site, each carries its decline argument, and the three arms are evidence appended to the ticket that owns the class rather than new tickets for the instance - which is the right call, and in two cases the evidence moves the cause off the SQL Server device.
- **The harness's deliberate oddities are justified and the justifications are true.** The library resolver really is an `AssemblyResolve` handler, so a package reference in the test project would have satisfied the load from the wrong folder; `SearchPath` really is passed through to the driver by the device's own connection-string builder, which a golden pins; the device user really is the only place a password can go without landing in the text of a device definition.
- **Resource cleanup and error handling in the new test code.** Every cursor, process and session is closed in a `finally`, the fixture disposes its server instance if one-time setup throws, and the three cases guard on the variable before touching anything. `DetermineVersion`'s new `cursor.Next()` guard covers the shapes `version()` can actually return.
- **File sizes.** The files this work item touched are 131 to 754 lines (`wc -l`); `TestEnvironment.cs`, the largest, is a region-per-server harness and the new region reads like the SQL Server one beside it. Nothing needs splitting.

### Recorded as tripwires rather than tickets

- **The inherited `ToLiteral` for a byte-array column emits base64 inside a cast**, which is not a `bytea` literal (those are hex or the escape format) and is not valid T-SQL either. It is unreachable while `UseParametersForCursors` is on, which both devices leave on, so it is a `NOTE:` on `PostgreSQLMSSQLBinary` rather than work - and the shared `SQLBinary` is wrong in the same way, which is why the note points at both and `bug-mssql-binary-column-cannot-take-a-value` carries the question.
- The implement stage's own tripwires were read and left as they are: the fixed database name shared between concurrent runs (`TestEnvironment.PGSQLEmptyDatabaseStatement`), and the streamed read path, encryption and isolation levels, which the user's guide states plainly as unproved.

### Considered and left alone

- **`DetermineVersion` will still throw on a version string whose major part is not a number** - `Convert.ToInt32` over, say, `"9beta.1"`. No PostgreSQL release reports such a string, and swallowing it would leave the device claiming the default major version 9 rather than saying it cannot identify the server, which is the worse of the two. Left as it is.
- **The CI step is still the least verified thing here**, as the handoff says: that `windows-latest` carries PostgreSQL 14.25 as the disabled service `postgresql-x64-14` with the user `postgres` and the password `root` was read from the runner-image manifest, not from a run, and the wall-clock cost on CI is unmeasured. Nothing about it can be checked from here, and `continue-on-error` makes the failure mode a documented gap rather than a red build. The first CI run after this lands should be read. The password is the image's published default for a service on an ephemeral machine and there is no integrated-security equivalent to fall back on, so the step stands or is removed; it is not something to hide.
- **The catalog store** (`store-pgsql-port`, next in sequence) was not run, because `src/engine/Store.PGSQL` is not yet in `Dataphor.slnx`. It can use the same variable and the same container.
