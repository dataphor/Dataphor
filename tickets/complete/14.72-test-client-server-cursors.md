## What landed

The two cases that only mean something when the client and the server are separate programs, added to the fixture `test-client-server-fixture` built, and the old client test project deleted with everything its deletion obliged. Nothing in the product changed: every file touched is a test file, the legacy solution file, the spike's project list, documentation or a ticket. The implement stage is commit `ticket(implement): test-client-server-cursors`; review changed four things in that work and filed nothing, all listed under *Review findings*.

**`OutOfProcessProtocolTest.ACursorCrossesFetchBatchesAndChangesThroughItself`** is the content of the deleted `CLI/CLITest.TestCLI`, rewritten with NUnit assertions that carry messages. The client reads a cursor in blocks of `ProcessInfo.FetchCount` and holds one block at a time in a buffer of its own, so a cursor over more rows than that is the only thing that exercises the refetch at a block boundary. In order: create a table and fill it with one block of identifiers; open the cursor with the capabilities the navigation, bookmark and update steps need; add the identifiers up against the arithmetic series; walk forwards asserting each identifier in order; update, delete and insert through the cursor, asserting after each change which row the cursor then shows; take a bookmark on the fifth row, walk to end of file, go back to it; then refill the table with ten blocks and repeat the sum, the ordered walk and the bookmark round trip — the part that crosses many boundaries. The block size is read from `process.ProcessInfo.FetchCount` rather than assumed, with an assertion that it is greater than one, because a fetch count of one turns the client-side buffer off and the case would then establish nothing.

**`OutOfProcessProtocolTest.ASchemaChangeOnOneConnectionIsVisibleOnAnother`** runs two client connections against the one child server: a table one creates becomes visible to the other, in both directions, and a table one drops stops resolving on the other. Each client-side `LocalServer` keeps a catalog cache in an engine of its own and refreshes it when a prepare comes back carrying a catalog fragment and a newer cache time stamp; nothing else in the suite reaches that, because every other fixture has at most one client-side engine. Per-case object names come from a counter on the fixture, since the child server's catalog lives as long as the fixture and NUnit guarantees no order within a class.

**`tests/DAE.Client.Tests` deleted whole** — the project that registered an instance in the machine's instance list, started a built `DAEServer.exe` from a hard-coded path and used the default port, which is why it could not be made to run (plan defect K18, now `fixed`). Its cursor case became the case above; its two cursor-at-boundary cases were already in the suite in process as `CursorTest.TestDeleteAtEOF` and `TestDeleteAtBOF`, which now carry a `<remarks>` saying so; its `DataView` and ADO.NET provider cases, whose subjects are unconverted, are an arm on `feat-ws6-windows-client-and-ide` in `backlog/`. Everything the deletion obliged went with it: the project entry, its twelve configuration lines and its nested-project line in `Dataphor.sln`; its line in `tools/net-spike/projects.txt` and its row in that tool's README; the project counts in `AGENTS.md`; and five places in `docs/modernization-plan.md`, including the K18 row. No `docs/migration-notes.md` entry: a deleted test project and a line in a solution file that already does not build are invisible outside this repository.

**The process-wide object-id counter.** `ProtocolClient`'s restoration of it is kept — measured as load-bearing for `CoreWcfProtocolTest`, which hosts a server in the test process and connects to it, and not needed by the out-of-process cases, which allocate only into their own client-side catalogs. The comment at the site now records that measurement instead of the claim it used to make, and carries a `NOTE:` for the second reset the wrapper cannot cover. `tickets/plan/bug-object-id-counter-is-process-wide.md` gained a matching arm.

## Tests

| Test | What it verifies |
|---|---|
| `OutOfProcessProtocolTest.ACursorCrossesFetchBatchesAndChangesThroughItself` | A cursor over ten times the client's fetch-block size, over the wire to a server in another program: every row arrives exactly once (the sum), in the cursor's order (the walk), the refetch at a block boundary neither loses nor repeats a row, a bookmark taken in a block the client has since discarded still positions the cursor, and update, delete and insert through the cursor leave it on the row the behaviour says they should. This is the characterization test the deleted project owed. |
| `OutOfProcessProtocolTest.ASchemaChangeOnOneConnectionIsVisibleOnAnother` | Two client connections to one server: each one's client-side catalog cache refreshes to see a table the other created, in both directions, and a table one drops stops resolving on the other. |

No test was added for the deletion itself, and no existing expected value was changed.

## Review findings

Read the implement diff first with the handoff set aside, then the deleted `CLI/CLITest.cs` side by side with its replacement, then the client code the cases actually exercise (`LocalCursor`, `LocalPlan.GetDataType`, `LocalServer.EnsureCacheConsistent`, `Engine.InitializeCatalog`), then every document the change touched and the ones it should have. Built, ran the three affected fixtures, ran one deliberate probe against the product to check that a case was load-bearing, and ran all three suite parts.

### Checked and sound

- **The port is faithful, step for step.** Compared against `HEAD~1:tests/DAE.Client.Tests/CLI/CLITest.cs`: the same expressions, the same capabilities, the same order of steps and the same expected values — including the three that are the behavioural record and the only record of it (an update that moves the row to the front of the order leaves the cursor on it; a delete leaves the cursor on the row that followed; an insert leaves it on the row inserted). The one addition, a second bookmark round trip in the ten-block pass, is the case the handoff explains and costs milliseconds.
- **The arithmetic actually closes.** The mutation helper updates identifier 2 to -1, deletes it, and re-inserts 2, so the table is `1..n` again and the walks after it can assert the order without knowing what happened inside. Traced by hand, and confirmed by the ordered walk and the fifth-row bookmark that follow it.
- **The second pass genuinely crosses block boundaries.** `SessionInfo.DefaultFetchCount` is 20 and `ProcessInfo(SessionInfo)` copies it, so the second pass is 200 rows over ten blocks. `LocalCursor.Next` calls `ClearBuffer` and refetches at each boundary, and `ClearBuffer` dereferences every bookmark in the block it discards — but `GetBookmark` increments `LocalBookmark.ReferenceCount` first, so the bookmark the case takes survives the discard, and `GotoBookmark` then falls through the buffer scan to `SourceGotoBookmark`. That reference-counted path is reachable nowhere else in the suite, which is the case's whole justification, and it holds.
- **The cache case is load-bearing, measured rather than argued.** Temporarily forced `if (_descriptor.CacheChanged)` false in `src/protocol/Client/Server/LocalPlan.cs` (reverted; the file is byte-identical to `HEAD`) and re-ran the case: it fails in `LocalExpressionPlan.GetDataType` with `ServerException.Codes.CacheDeserializationError` wrapping a client-side `CompilerException` from `Compiler.ResolveCatalogIdentifier` — exactly the mechanism the case's `<remarks>` describes, and the handoff's correction to the ticket's wording is right. Without the refresh the case fails; with it, it passes.
- **The handoff's own doubt about the drop half is accurate, and the half is still worth keeping.** It asserts that selecting the dropped table raises `UnknownIdentifier` on the other connection, and that error comes from the *server's* compiler, so the case does not prove the client discarded the dropped object — what it proves is that no stale client-side plan or cached descriptor short-circuits the prepare. Left as it is: every stronger reading requires the test to reach into `LocalServer.Catalog`, which makes a test of the client's internals out of a test of its behaviour, and the two positive halves already pin the refresh (above).
- **Nothing is left of the deleted project.** No `A0EC803A` GUID anywhere in `Dataphor.sln` and its `GlobalSection` blocks are intact; `tools/net-spike/projects.txt` is 32 lines; `.gitattributes` names only the blanket `*.dll binary`, so the two deleted binaries needed nothing there. `tools/net-spike/run.py` has `PATCHES = []`, so dropping a project from the list needs no other edit.
- **`AGENTS.md`'s corrected counts are the measured ones.** Reading the first line of each project in `projects.txt`: 23 SDK-style, 9 legacy, so "the other 9 of its 32" is right.
- **Documentation is current, including what was correctly left alone.** `docs/architecture.md` mentions neither the deleted project nor cursor batching, so it needed nothing. The plan's old-to-new path table still lists `Tests/DAE.Client.Tests`, which is the record of the reorganization move and must stay. The historical spike-measurement paragraph keeps its dated claim with the project marked as since deleted, which is the honest treatment of a measurement. `docs/migration-notes.md` is correctly untouched.
- **The deliberate omissions are each right, and now stated in the fixture's remarks.** Streams, message-size quotas and typed faults belong to `CoreWcfProtocolTest` against the real host over a real socket, because the client-side and server-side stream managers are separate objects whether or not they share a process; the abandoned-session clock needs a client that can be made to stop pinging and gets its own fixture; `TestDeleteAtEOF` and `TestDeleteAtBOF` were already in the suite in process, confirmed by reading both files.
- **Error paths clean up.** Cursor closed in a `finally` in one helper, bookmark disposed in a `finally`, the walk's requested row released in a `finally`, both clients in nested `using`, both processes through `OnProcess`'s own `finally`. A failure anywhere in either case leaves no cursor, row, bookmark, session or channel behind.
- **The fixture must stay non-parallelizable and says so at the site.** Three client-side engines now start in it, and the per-case name counter is a plain increment. The existing comment above `[TestFixture]` already carries the stronger reason (the shared object-id counter), so nothing was added to it.
- **Size is in band.** `OutOfProcessProtocolTest.cs` is 500 lines after this pass (524 before it), against `CoreWcfProtocolTest.cs` at 754 and `StoreContractTests.cs` at 688 in the same project. Not a size finding.
- **The cross-file `<see cref>` in `CursorTest`'s remarks is established practice here**, not a new liability: the same file set already points across files this way, Roslyn's rename carries `cref` references, and the project generates no documentation file, so this is exactly as durable as every other cross-reference in the project.

### Minor, fixed in this pass

- **The same cursor walk was written out three times** in `OutOfProcessProtocolTest.cs` — request a row from the plan, `while (cursor.Next())`, select into it, release it in a `finally` — once each for the sum, the ordered walk and the bookmark round trip. Extracted to one `Walk(cursor, onRow)` that returns how many rows it passed, so the row's lifetime is owned in one place instead of three; the three callers are now one or two lines each.
- **The sum had a hidden precondition the other two walks did not.** It walked from wherever the cursor happened to be, while the other two reset first, so reordering the calls inside a case would have silently summed a suffix. The reset moved into `Walk`, which makes all three independent of where the walk before them left the cursor.
- **Two near-identical cursor-read helpers sat in the same file**, one reading a string column and one an integer column, each with its own open-and-close discipline. Collapsed onto one `ReadRows(process, expression, ofRow)`; both named entry points stay, one line each, so the cases read as they did.
- **A sentence about `LocalServer`'s host-name argument sat in the middle of the object-id-counter argument** in `ProtocolClient.cs`, between the measurement and the `NOTE:`. Moved to sit next to the statement it describes, so the counter discussion reads as one thing.

### Tests: none added, none cut

Nothing was cut: both cases are behaviour tests against a real child process over a real connection, neither restates the implementation or verifies a mock, and the one that could look redundant (the first pass's single-block bookmark) is the faithful port of a deleted assertion at a cost of milliseconds. Nothing was added, and the one candidate was weighed and declined — in-place changes are only made in the first block, never in a refetched one. `LocalCursor.Update` and `Delete` take their buffer-dependent branch, `SyncSource(true)`, which round-trips through `GotoBookmarkIndex` whenever the source cursor's index differs from the buffer's; in the covered case the cursor sits at buffer index 1 with the source cursor at 20, so that branch does run, and a mutation in a later block takes the same branch with different numbers. A new case there would cost a round trip and pin behaviour no reference runtime can confirm, for a code path already covered.

### Tripwires

- One was parked by the implement stage and is correct as parked: `LocalServer.EnsureCacheConsistent` throws the client's cached catalog away and rebuilds it in the middle of preparing an expression, where no caller can save and restore the process-wide object-id counter, so `ProtocolClient`'s construction-time workaround does not cover every reset. Verified the chain by reading the code (`ClearCatalog` → `InitializeCatalog` → `Schema.Object.SetNextObjectID(0)`). It is harmless while every client clears its cache before it allocates, which is why it is a `NOTE:` at the site plus an arm on `bug-object-id-counter-is-process-wide` rather than a ticket.
- Nothing new was parked by this pass.

### Nothing filed

No ticket was filed from this review. Everything found was minor and fixed here; the one conditional concern already has its `NOTE:` and its arm; and the gaps the handoff named are each either answered above or owned by a ticket already on the board (`feat-ws6-windows-client-and-ide` for the unconverted client subjects, `bug-object-id-counter-is-process-wide` for the counter).
