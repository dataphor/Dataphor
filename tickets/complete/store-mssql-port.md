## What landed

`ticket(implement): store-mssql-port` brought the store back into the build, into the runtime layout and under the store contract, and the planning pass's measurement held: not one line of `MSSQLStore.cs`, `MSSQLStoreConnection.cs` or `MSSQLStoreCursor.cs` had to change to compile.

- **`src/engine/Store.MSSQL/DAE.MSSQL.csproj`** rewritten in SDK format, modelled on `src/engine/Store.SQLite/DAE.SQLite.csproj`: the same `DefineConstants` block, project references to `Base`, `DAE` and `Server`, the three `Compile` items plus `Properties\AssemblyInfo.cs`, and `SystemStoreCatalog.sql` as an `EmbeddedResource`. No SQL-client package of its own; the swap to `Microsoft.Data.SqlClient` stays with `device-mssql-port`, which owns the repository's SQL Server client.
- **`Properties/AssemblyInfo.cs`** trimmed to title, description, `ComVisible` and the existing `Guid`, as in every other converted project.
- **`MSSQLStore.InternalInitialize`** forces `MultipleActiveResultSets=True` into `ConnectionString` and sets `_supportsMARS` true, instead of reading the option and reporting whatever it found. The catalog opens a second store cursor while a first is still open, and SQL Server otherwise fails with *"There is already an open DataReader associated with this Command which must be closed first."*, which names nothing a deployment could act on. A configured `False` is overwritten: the store cannot work under it. `SQLiteStore.NormalizeConnectionString` forcing write-ahead logging is the precedent.
- **`Dataphor.slnx`**, the `Bin` list of **`tools/layout/Layout.csproj`**, and — added in review — the project references of both host executables carry the store.
- **`tests/DAE.Server.Tests`** references the project and gains `MSSQLStoreContractTests`, a second subclass of the existing `StoreContractTests`, so the 14 cases that already describe the catalog store contract run against a second store. No new test *cases*: that is the ticket's point and the project's testing rule for a re-hosted subsystem. The fixture skips itself, case by case, where `DATAPHOR_TEST_MSSQL` is unset, so CI is unchanged.
- **Documentation.** `docs/migration-notes.md` has the entry under *Platform and deployment*; `AGENTS.md` moves `Store.MSSQL` into the converted list and — added in review — documents `DATAPHOR_TEST_MSSQL`; `docs/architecture.md` and `docs/users-guide/dataphor-service.md` name the second store that now ships, both added in review.

### How to run the SQL Server fixture

```
$env:DATAPHOR_TEST_MSSQL = 'Data Source=(localdb)\MSSQLLocalDB;Integrated Security=SSPI'
dotnet test tests\DAE.Server.Tests\DAE.Server.Tests.csproj --no-build --filter 'FullyQualifiedName~MSSQLStoreContractTests'
```

The variable names a **server**, not a database: the fixture puts its own database, `DataphorStoreContract`, into whatever is set. `sqllocaldb start MSSQLLocalDB` first if LocalDB is not running. `AGENTS.md` now says this too, which is where a developer will look for it.

## Review findings

Read the implement diff before the handoff, then re-derived its claims from the tree rather than from the summary: where the forced connection-string option is read afterwards (`MSSQLConnection`'s own constructor, and `CatalogStore.UseCursorCache`), whether the mutated `DbConnectionStringBuilder` could damage a deployment's connection string, whether the trimmed `AssemblyInfo.cs` matches `Store.SQLite`'s and what `Directory.Build.props` generates, whether the embedded resource still resolves under the name `CatalogStore.Initialize` asks for, whether the new fixture's shared database is actually isolated per case, and what the layout shipping a second store assembly implies. Checked the four documents the change touched and the two it should have.

**Found and fixed inline — the store shipped but could not be loaded.** The layout's `bin/` holds `Alphora.Dataphor.DAE.MSSQL.dll`, but neither `DAEServer.deps.json` nor `DAEService.deps.json` named it. On .NET 10 there is no app-local probing, which the plan's own WS4 measurement already records, so `CatalogStore.CreateStore`'s `Type.GetType` would have thrown `FileNotFoundException` and an instance whose `catalogstoreclassname` named this store would have failed to start with error 115107 — the one capability the ticket exists to deliver. Both host projects now reference the store project, as `Store.SQLite` already did, and the comment at both sites says the rule applies to every shipped store rather than to the default one. Verified: both dependency files name the assembly after a build.

The reproduction is in the existing guard rather than a new case. `HostProgramTest.TheHostsDependencyFilesNameTheAssembliesTheServerLoadsByName` checked only the assembly named by `Server.DefaultCatalogStoreClassName`, so it passed while the second store was unloadable; it now iterates every store the layout ships, held as a list of *types* so the compiler keeps it honest, and still asserts that the default store's assembly is among them. Confirmed it fails before the host references and passes after.

**Found and fixed inline — the diagnostic flag broke the fixture it exists to diagnose.** `MSSQLStoreContractTests.DisposeStore` emptied the shared database only when `TestEnvironment.KeepFiles` was false, so with `DATAPHOR_TEST_LOGGING=1` set — exactly what a developer sets to look into a failing case — every case after the first met the previous case's `T` and failed on `create table`. The fixture now empties the database at the *start* of a case, in `CreateStore`, guarded on the per-case directory so that `SeedSchemaReopens`' second `CreateStore` on the same directory still reopens what it wrote. That also makes `KeepFiles` mean what it says here: the finished run's rows are left to look at. Verified both ways — 14 of 14 green with the flag set, and the kept database holds `T` afterwards, which is what the old code left behind mid-fixture.

That change left both fixtures' `DisposeStore` identical to each other (delete the case's directory), so the abstract hook is gone and the base's `[TearDown]` owns the directory. `SQLStore` is not `IDisposable` and holds nothing else to release, so nothing is dropped by retiring it. The base class's remark that "each test gets its own database" was made false by the new fixture and now describes both shapes; `CreateStore`'s contract says where emptying belongs and why. Smaller things in the same file: the fixture's two near-identical connection-string helpers collapsed into `ConnectionStringFor(databaseName)`, and `[OneTimeSetUp] CreateDatabase` renamed `RequireServer`, since it requires the variable and drops a leftover database and creates nothing.

**Found and fixed inline — documentation.** `docs/users-guide/dataphor-service.md` is where a deployment reads what to put in `catalogstoreclassname`, and it named SQLite as the only store there is; it now carries the SQL Server store's assembly-qualified class name, an example instance entry, that the server creates the database if it is absent, that the connection string should not set `MultipleActiveResultSets`, and the non-ASCII limit. `docs/architecture.md`'s catalog-store paragraph names the second store and why the hosts reference both. `AGENTS.md` documented `DATAPHOR_TEST_LOGGING` as the suite's only environment variable; `DATAPHOR_TEST_MSSQL` gates 14 cases that otherwise skip in silence, so it is documented beside it. The plan's WS4 row and its "no app-local assembly probing" measurement both said the server loads exactly one assembly by name and that the hosts therefore reference `Store.SQLite`; both now say every shipped store, and the row records what review found.

**Checked and found sound, no change.** Forcing the option is safe where the connection string is read again: `MSSQLConnection`'s constructor matches `"True"` case-sensitively and now always sees it, which incidentally fixes a deployment that wrote `true`. `ConnectionString` is assigned *before* the `_shouldEnsureDatabase` block rewrites the builder to `master`, so the store keeps the real database name — the order is load-bearing and correct. The generic `DbConnectionStringBuilder` round-trip does not lose or requote anything in a LocalDB or integrated-security string, and the base's setter permits the write because `InternalInitialize` runs before `_initialized`. Forcing the option also turns on `CatalogStore.UseCursorCache` for this store, which looked like an unexercised path until it turned out that SQLite sets `_supportsMARS` true as well: SQL Server now takes the cursor-cache path the default store has always taken, rather than a path of its own. The embedded resource name still resolves, as `SeedSchemaReopens` passing proves. The trimmed `AssemblyInfo.cs` matches `Store.SQLite`'s exactly in what it keeps and what it leaves to `Directory.Build.props`. The project's explicit `Compile` list covers every `.cs` in the folder, and `EnableDefaultItems=false` makes that the right shape. Nothing in the suite runs in parallel, so the shared database is not a within-run hazard.

The fixture's `[OneTimeSetUp]` dropping the database even under `KeepFiles` is deliberate and left: it is what guarantees a run does not inherit another's rows, and it matches how `TestEnvironment` sweeps earlier runs' directories.

The `create database` probe swallowing its own exception (`catch { }`, pre-existing, with the reason written at the site) means a genuinely unreachable server shows up as a later and less pointed failure. Left alone: the comment there is the rationale, the ticket does not touch it, and with the database emptied at the start of a case an unreachable server now fails at `DropTables` with the connection error rather than later still.

**Tripwires, recorded as comments rather than tickets.** The fixture's fixed database name is its one shared resource — two runs against the same server at the same time would empty each other's database mid-case; the `NOTE:` at the fixture says what to do if that day comes. `DropTables` drops every table in one batch and relies on nothing the contract or the catalog seed creates having a foreign key, which the handoff asked to be said louder than it was; the `NOTE:` at that method now says a contract case that added one would break the teardown rather than itself, and what to do.

**Not filed as tickets, by design.** The `varchar` parameter mapping that loses non-ASCII text through this store's writes, and the one-parameter-type-per-string-length plan churn behind it, are pre-existing, shared with the SQL Server device, and already recorded as an arm on `feat-ws7-devices-and-libraries` with the measurement; the reproduction belongs with the fix. The version question — proved on SQL Server 2016 LocalDB, below the 2022 minimum of decision Q12 — is `device-sqlserver-version-matrix`'s. Supplying LocalDB in CI is `test-device-live`'s. Nothing drives this store through a running server; the contract runs below the catalog, as designed, and a server booting on a SQL Server catalog is not proved here.
