## What landed

Four changes, in `ticket(implement): engine-server-link-session-outlives-drop`.

**The cache of connections to other servers is keyed by the link, not by its name.** `RemoteSessions.IndexOf(Schema.ServerLink)` (`src/engine/DAE/Server/RemoteSession.cs`) compared with `Schema.Object.Equals`, which compares names, so a link created after a drop under the dropped link's name matched the dropped link's connection: the work went to the first link's server, on the first link's credentials, and the new link's host name, instance name, port, link users and session-info tags were ignored for the life of the process. It now compares `ServerLink.ID`.

**`drop server` and `alter server` close the issuing process's connection to the link.** `DropServerNode.InternalExecute` and `AlterServerNode.InternalExecute` (`src/engine/DAE/Runtime.Instructions/DDLNodes.cs`) call the new `CatalogDeviceSession.CloseRemoteSession`, which gives `ServerProcess.RemoteDisconnect` the caller it was written for and had never had. The drop's call is after `CheckNotSystem`/`CheckNoDependents`, so a refused drop closes nothing, and outside `lock (program.Catalog)`, because the close makes a network call.

**Inside an open transaction the close waits for the outermost commit**, and a rollback discards it, mirroring a dropped device's deferred stop - because the process enlists its remote sessions in its own commits and rollbacks. The level bookkeeping the device stops already had was factored into one generic nested type, `DeferredTeardowns<T>`, now used by both lists (`src/engine/DAE/Device.Catalog/CatalogDeviceSession.cs`).

**A connection's teardown completes whatever the network does.** `NativeCLISession.Dispose` clears its session handle and disposes its WCF client in a `finally` around `StopSession`, and `RemoteSessionImplementation.Dispose` catches a failed remote stop and logs one warning naming the link and the far instance. Before this, a failed `StopSession` left the handle set, the client undisposed - leaking the WCF channel and its cached channel factory - and the entry in the process's list, so `ServerProcess.Dispose` could throw out of a process teardown.

`tests/DAE.Server.Tests/ServerLinkConnectionTest.cs` is the reproduction: an in-process server, a second Dataphor server in a child process, six cases - the re-created link connecting afresh, the drop and the alter each closing the connection, the deferral to the commit, the discard on rollback, and a process whose far server has gone still stopping. The `ServerLink` coverage script's manifest entry is re-pointed: still `known-failure`, now owned by `bug-right-check-fails-for-granted-right`, failing at line 43 instead of line 34. K35 in the plan's *Known defects* table and an entry in `docs/migration-notes.md` record the behaviour change.

## Review findings

### Fixed in this pass

- **The plan still described the defect as open, in the one place a reader would look for its status.** `docs/modernization-plan.md`, WS3 *Client/server tests*, *What the script found*: "It stays a recorded known failure against `engine-server-link-session-outlives-drop`, which has the measurement and the three questions a fix has to settle", and then that the defect "makes the tags on every link after the first inert ... the script may fail in new places once the reuse stops". All of that is now history. The implement pass added K35 and the migration note but left this paragraph, which is the one the test-suite workstream points at. Rewritten to say the defect is fixed (naming K35), that the tags are no longer inert, and that the whole-script run now stops later and in a new place - line 43, `bug-right-check-fails-for-granted-right` - with the blocks after it still unrun.
- **The `RemoteSessions.IndexOf` remark argued its case without naming the ticket that would otherwise contradict it.** The implement ticket asked for a comment saying why identity and not name *and* why `bug-object-id-counter-is-process-wide` does not reach it; the handoff claims the comment does both. It made the uniqueness argument ("object ids are unique within one engine's catalog") but never named that bug, so a future reader holding it has to re-derive the answer at the one site where keying by id is load-bearing. Added the clause: the ids that bug collides are the ones allocated after a second engine in the same process resets the shared counter, and a server whose catalog persists refuses the colliding object at its store before there is a link to connect to - which is that ticket's own recorded visible failure.

### Filed

- **`tickets/backlog/bug-server-link-user-change-keeps-old-connection.md`** (verified repro). Half the rule this ticket established holds. `alter server` now ends the issuing process's connection so the next use re-reads the link's settings; the six D4 operators that change *which credentials the link connects with* - `CreateServerLinkUser`, `CreateServerLinkUserWithEncryptedPassword`, `SetServerLinkUserID`, `SetServerLinkUserPassword`, `ChangeServerLinkUserPassword`, `DropServerLinkUser` in `src/engine/DAE/Runtime.Instructions/SystemNodes.cs` - do not, so a password rotation or a change of account has no effect on the session performing it. Reproduced in a throwaway case: with credentials the far server refuses, the rotating process goes on working on its old connection while a second process on the same session is refused. `DropServerLinkUser` carries the original author's `// TODO: Prevent drop if user has active sessions on this server?` at that exact site. Filed as the invariant rather than as six call sites: every one of those operators, and `alter server` too, ends by calling `UpdateCatalogObject(serverLink)`, and across the tree those seven are the only `Schema.ServerLink` arguments that method ever gets - so one condition at that site is the shape the ticket recommends, with what it has to settle named. Backlog rather than `fix/`: the shape is settled, the timing is a maintainer's call, and only an already-connected session is affected.

### Checked and left alone

- **`DeferredTeardowns<T>` is correct, and the sharing was the right call.** Walked `Commit` and `Rollback` against the two methods they replaced: the `level > 1` handoff, the `entry.Level >= level` comparison and the return of `_entries` to null are each line-for-line equivalent, and the one behavioural difference - the holder object now always exists rather than being created on first `Add` - costs one small object per catalog device session with the entry list still lazy. The four cases of `DeferredDeviceStopTest` (nested commit defers, nested rollback keeps the outer stop, nested rollback discards its own, a failed drop keeps the device) pass unchanged, which is the evidence the device behaviour did not move. The handoff flagged this as the one place it exceeded the ticket and asked for it to be weighed: the alternative was a second copy of level logic that has already needed a fix of its own (`bug-catalog-deferred-device-stops-ignore-nesting`), so sharing is right and the type's own remarks say so.
- **Where the deferral lives.** `ServerProcess` owns `RemoteSessions`, so a deferred-close list could have gone there instead of on the catalog device session, and `ServerProcess` has per-level commit and rollback hooks of its own. Considered and accepted as written: the bookkeeping, its one prior fix and the drop's only route to it (`program.CatalogDeviceSession`) are all already on the device session, and splitting the two kinds of deferred teardown across two owners is what the shared type exists to avoid.
- **The ordering in `InternalCommitTransaction`.** The handoff asked for this to be checked against what `ClearChangedRights` and `InternalAfterCommitTransaction` assume. Verified against `ServerProcess.InternalCommitTransaction`: it commits every remote session first, then the non-catalog device sessions, then the catalog device session last - so by the time the deferred close runs, the remote transaction for that level has committed, the store has committed, and neither the rights clearing nor `InternalAfterCommitTransaction` makes a catalog change the close could disturb, nor does the close make one of its own. The close is also the last thing in that method, after the device stops, which is the only ordering that keeps a network call out of the middle of a commit.
- **The `Contains` guard in `InternalCloseRemoteSession` is in the right place.** It keeps error 106120 (`NoRemoteSessionForServerLink`) meaning what it meant - raised only by a caller asking to disconnect a link it has no session for - and it also makes two alters of the same link in one transaction idempotent at the commit. One benign consequence of guarding at the commit rather than at the defer: an `alter server` inside a transaction followed by the *first* use of that link in the same transaction opens a connection with the new settings, and the commit then closes it. One wasted reconnect, no wrong result, and moving the guard earlier would not remove the need for it at the commit. Left as written.
- **The empty `catch { }` in `ReportFailedRemoteStop`.** Deliberate, commented, and the guard is real rather than theoretical: this disposal can be part of a server's own shutdown, and `ServerProcess.ServerSession` is cleared on that path, so the logging call itself can throw. A throw from inside the catch block that exists to keep a teardown from failing would defeat the whole arm. Left as written.
- **`NativeCLISession.Dispose`'s `finally` cannot swallow the failure it is meant to report.** `ServiceClient<T>.Dispose` catches its own exceptions internally (two `catch (Exception)` blocks around the channel close and the factory release), so `_nativeCLI.Dispose()` does not throw, the original `StopSession` failure is the one that propagates to `RemoteSessionImplementation`, and `_sessionHandle = null` / `_nativeCLI = null` are always reached. A second `Dispose` is a no-op. One pre-existing gap noticed on that path and deliberately not touched: `ServiceClient.CloseChannel` calls `Close()` on an open channel and `Abort()` otherwise, and if `Close()` throws the channel is left neither closed nor aborted. The realistic path takes the `Abort()` branch, because the failed call faults the channel first; the file is outside this diff and already carries its own `// TODO: Log exception` markers, so this is recorded here rather than as a new comment in it.
- **No other cache of remote sessions, and no other name-keyed session cache.** `Plan.RemoteConnect` and `Program.RemoteConnect` both delegate to `ServerProcess.RemoteConnect`; the one other apparent cache, `OnTable` in `src/engine/DAE/Runtime.Data/SystemTableValues.cs`, is inside `#if OnExpression` and is not compiled. Re-confirmed the implement ticket's claim that `Schema.DeviceSessions.IndexOf` compares `this[index].Device == device` - reference equality - so the device cache was never name-keyed.
- **A rolled-back drop still finds its connection.** Keying by id would have been undone by an undo that re-created the link as a new object; `DropCatalogObjectInstruction` holds the `Schema.ServerLink` instance itself and re-inserts that, so the id is preserved and `TestRolledBackDropKeepsTheConnection` pins real behaviour rather than passing because a second connection happens to report the same call depth.
- **The lazy `RemoteSessions` list.** Confirmed: a `drop server` on a process that never used a link now allocates an empty list. `CatalogDevice.PopulateRemoteSessions` already does the same for every process on every read of `System.RemoteSessions`, so this adds nothing new.
- **Two delegate allocations per catalog-device-session commit**, from passing `InternalStopDevice` / `InternalCloseRemoteSession` as method groups at the two `Commit` call sites where the old code passed none. Binding the teardown once at construction would remove them, but the field declarations sit 3,200 lines from the constructor and moving the binding there would separate each list from its own teardown method. Judged below the threshold for even a tripwire - two short-lived objects against the `Program`, plan and row allocations every statement already makes - and recorded here rather than as a comment, so the next reader meets the measurement rather than a caution.
- **One dormant leak, unchanged by this diff and not filed.** A `create server` undone by a rollback removes the link from the catalog while leaving the process holding a connection opened against it, until the process ends. Pre-existing, unreachable for new work (the link and its id are gone, so nothing can match that session), and reclaimed by `CloseRemoteSessions` at process teardown. Keying by id neither caused nor worsened it.
- **The accepted tradeoff at `AlterServerNode.InternalExecute`** - only the issuing process's connection, with "a deployment that needs an alter to take effect everywhere at once" as the revisit condition - was weighed in the fix stage and is recorded at the site and in the migration note. Not re-opened; the new ticket says the same tradeoff applies to it and should be recorded, not re-decided.
- **Compatibility.** No operator signature, D4 class name, assembly name, file format, error code, WCF contract shape or port changed. `CloseRemoteSession` is an additive public member on `CatalogDeviceSession`; `RemoteSessions.IndexOf` changes semantics but `ServerProcess.RemoteSessions` is `internal`, so no extension holds one. The migration-notes entry states the behaviour change, the deferral, the unreachable-server case and the other-process exception, and is accurate against the code.
- **Docs read, not assumed.** `docs/migration-notes.md` and K35 are accurate; `docs/architecture.md` says nothing about the remote-session cache that this change contradicts; the only stale text was the plan paragraph fixed above. The coverage manifest's new entry matches the observed behaviour - `ServerLink` reported as Skipped in suite part 3, which is how a correctly recorded known failure shows.
- **Source hygiene.** Tabs, CRLF and byte-order-mark state are unchanged in all five source files and the project file, checked byte by byte against the commit's parent (the `.md` and `.json` files are stored LF and checked out CRLF, which is the repository's own configuration, not an edit). The new comments say why rather than narrating statements. `CatalogDeviceSession.cs` is 3,888 lines and `DDLNodes.cs` 3,277 - both already that size before this ticket, which added about 27 net lines to the first and 13 to the second. No split filed: there is no anchor in the current release for breaking up two of the engine's oldest files, and this change is not what made them large.

### Tests

**Nothing cut and nothing added.** The six cases each pin a distinct contract - identity over name, the immediate close on drop, the immediate close on alter, the deferral to the commit, the discard on rollback, and a teardown surviving a dead far server - none restates the implementation or verifies a mock, and the handoff's claim that each fails when its own fix is removed was spot-checked by reading what each asserts against what each change does. Three cases on the drop path is not duplication: immediate, deferred and discarded are three different rules. No nested-transaction case was added for the remote close, because the nesting is now the shared `DeferredTeardowns<T>` level logic that `DeferredDeviceStopTest` already pins at the level below. No case for the WCF client disposal, agreeing with the handoff: observing a closed channel needs reaching into WCF state the suite has no access to, and the arm is exercised by `TestStoppingAProcessWhoseOtherServerHasGoneDoesNotThrow` even though it is not asserted there. The one case this review wrote - the link-user rotation - was run and removed rather than committed, because it tests a defect this ticket does not fix; its reproduction is in the new backlog ticket instead.

### The open question the handoff asked a reviewer to settle

Whether "reclaiming a connection must never fail the statement that reclaims it" is honestly met. **Met, for everything inside this ticket's site.** The teardown path completes whatever the network does, and the `drop server` path does not fail *because of the close*: it fails before it starts, at the transaction begin every statement makes on every connection the process holds, which is why `select 1 + 1` fails too. That is a different site (`ServerProcess.InternalBeginTransaction`), it is filed with a verified reproduction as `tickets/plan/bug-dead-remote-session-blocks-every-statement.md`, and scoping it out was the right call rather than an omission - as that ticket records, the fix has to decide what a dead transaction participant means, which is a change to the transaction protocol.
