## What landed

Two changes at one code site - the computation of the folder that holds the machine's list of server instances - plus the documentation they oblige. Implemented by `ticket(implement): host-instance-directory`, reviewed and amended as the findings below record.

**The folder carries the major version (known defect K27, now `fixed`).** `InstanceManager.GetInstanceDirectory()` resolved `PathUtility.CommonAppDataPath(String.Empty, VersionModifier.None)`, giving `%ProgramData%\Alphora\Dataphor\Instances` with no version in it, and `Server.InstanceDirectory` repeated the same expression to default an instance's own data folder. The resolution is now `VersionModifier.MajorSpecific`, so the folder is `%ProgramData%\Alphora\Dataphor\4\Instances` - beside the 4.0 `Aliases.config` the client has always kept there - and `Server.InstanceDirectory` calls `InstanceManager.GetInstanceDirectory()` instead of repeating the expression, so the path is computed in one place. 3.1's folder and files are left exactly where they are.

**A process can be pointed at a different folder.** `InstanceManager` gained the settable static property `InstanceDirectory` and the constant `InstanceDirectoryVariableName` (`DATAPHOR_INSTANCE_DIRECTORY`). Resolution order: a value set on the property, then that environment variable, then the versioned default; the result goes through `Path.GetFullPath`, so a relative value is relative to the process's current directory. Reading the property resolves without creating anything; `GetInstanceDirectory()` creates and returns, with its signature and meaning unchanged, so `LoadMachineInstanceConfiguration` and `SaveMachineInstanceConfiguration` are untouched. Setting the property discards the loaded list (`_instances = null`), so the next `Instances` access throws `InstanceConfigurationNotLoaded` rather than serving instances from the old folder.

Supporting it, `PathUtility` gained `CommonAppDataPath(string applicationName, VersionModifier versionModifier, bool ensureExists)`; the private `BuildAppPath` takes the flag and every existing overload passes `true`, so no existing behaviour changes. Without it, merely reading the resolved default path would create a folder under `%ProgramData%`.

`DataphorHost.BuildHost` keeps its `startServer` factory parameter. The redirection removes the machine-list reason for it but leaves two it cannot carry - `DataphorServiceHost.HostName` and `LoggingEnabled` are properties of the host object, not settings in a `ServerConfiguration`, and `HostProgramTest` needs both - plus one case that needs a start that throws. The decision is recorded at the parameter as an accepted-tradeoff `NOTE:`, and the plan paragraph that gave the machine-wide list as the parameter's reason was corrected rather than the code.

Documentation: `docs/migration-notes.md` (the versioned folder and what an operator and an installer each have to do; the environment variable; the new public members on `InstanceManager`; the new `PathUtility` overload), `docs/architecture.md` (the `DataphorServiceHost.Start()` paragraph and all four on-disk rows), `docs/modernization-plan.md` (K27 `fixed`, a `host-instance-directory` row in the WS5 table, the `host-instance-configuration` row reduced to the documentation that is left, and the *Generic host* hand-on bullet rewritten), `AGENTS.md`, `docs/users-guide/dataphor-service.md` (the path in "Installing Multiple Instances"; its settings section belongs to `host-instance-configuration`).

## Tests

`tests/DAE.Server.Tests/InstanceManagerTest.cs`, four cases, no `[Parallelizable]`, the property and the variable restored in `[TearDown]`:

- `TheDefaultInstanceDirectoryIsVersioned` - with no override and no variable, the resolved path is `<common application data>\Alphora\Dataphor\<assembly major version>\Instances` and not the unversioned 3.1 path. K27's characterization: a return to `VersionModifier.None` fails it. It also asserts that resolving the path does not change whether the folder exists, which is what the `ensureExists: false` resolution is for.
- `AnExplicitInstanceDirectoryBeatsTheEnvironmentVariable` - the variable alone redirects the resolved path, and a value set on the property wins over it. One case, because precedence is one behaviour.
- `ASavedInstanceListIsReadBackFromTheOverriddenDirectory` - points the override at a fresh folder, loads, adds an instance, saves, asserts `ServerConfigurations.config` is in that folder, then loads again and asserts the instance and its port come back.
- `AnInstanceWithNoDirectoryOfItsOwnLandsUnderTheResolvedInstanceDirectory` - **added in review**; see the findings. Starts an in-process server whose configuration leaves `InstanceDirectory` unset, as `ServerConfiguration.DefaultInstance` does, against a redirected instance folder, and asserts that the server's own data folder is `<redirected>\<instance name>` and that its SQLite catalog file was created under it. Four seconds.

`tests/DAE.Server.Tests/CoreWcfProtocolTest.cs` points `InstanceManager.InstanceDirectory` at a folder of its own in `[OneTimeSetUp]` and clears it in `[OneTimeTearDown]`, because `TestListenerAnswersOnItsOwnPort` reaches `ListenerService.LoadConfiguration`, which resolves the machine's instance folder and so creates it. That was measured by deleting `%ProgramData%\Alphora\Dataphor\4` and running that one case, which recreated it. The fixture asserts nothing about which instances are listed, so an empty list of its own changes nothing it checks, and the plan's WS3 isolation claim ("no test touches `%ProgramData%`") now holds in fact: after the whole suite, `%ProgramData%\Alphora\Dataphor` still held only the machine's 3.1 `3` folder and the pre-existing unversioned `Instances` folder, and no `4`.

No new case for a file an earlier release wrote: `LoadReadsAFileCarryingSettingsThatNoLongerExist` in `InstanceConfigurationTest` already pins that. No case for the `InstanceConfigurationNotLoaded` throw after a set: that is the existing `CheckLoaded` behaviour.

## Review findings

Read the implement diff first, then the handoff. Checked by reading and running: the resolution order and its three branches; path shape (the default resolves with no trailing separator, so the saved file name and the per-instance sub-folder compose correctly, and an override that ends in a separator also composes); what the setter's discarding of the loaded list does to each of the callers of `InstanceManager` in the tree; that `GetInstanceDirectory()` keeps its signature and that `Load`/`Save` are untouched; that `ensureExists` defaults to the old behaviour on every pre-existing `PathUtility` overload; that `VersionModifier.MajorSpecific` resolves to `4` from the `AssemblyVersion` in `Directory.Build.props` and so puts `Instances` beside the client's machine-wide `Aliases.config`; that no test fixture relies on the default instance folder (every one sets its server's `InstanceDirectory` explicitly); that `FileStreamProvider`, the one other writer under `%ProgramData%` in the server, is compiled out (`UseFileStreamProvider` is not defined); and that nothing in the tracked tree still names the unversioned path except the two places that describe it as history.

**Fixed in this pass (four, all minor).**

- **`AGENTS.md` claimed more for the environment variable than it does.** The new sentence said `DATAPHOR_INSTANCE_DIRECTORY` "does both" of the two things a test must do - a temporary instance directory *and* a library directory pointed at a copy. It does only the first: the default configuration a host registers for an unknown instance still points `LibraryDirectories` at the layout's own `Libraries\`, which the same commit's other `AGENTS.md` paragraph says correctly. An agent trusting the short version would run a host against the repository's own layout and have it rewrite `.d4l` files there. Corrected, and the reason spelled out at the site.
- **`docs/migration-notes.md` contradicted itself.** The *Forms and the Windows client* entry on settings folders still ended "Instance configuration and instance directories carry no version and do not move", which is exactly what this ticket reversed two sections above. Rewritten to point at the new entry.
- **A stale remark in `CoreWcfProtocolTest.cs`.** The class remark was updated for the redirection but the one on `TestListenerAnswersOnItsOwnPort` still said "ListenerService reads the machine-wide `ServerConfigurations.config`, so that list is whatever is installed here" - no longer true of this fixture, and the next reader would have taken it as the reason the case asserts nothing about the list. Rewritten.
- **A test contract left unverified: the `Server.cs` half of K27.** Three cases pinned where the *list* is read and written; nothing pinned where an instance's *own data* goes, which is the half with the worse consequence (before this change a 4.0 server pointed its catalog, its logs and its library data into a 3.1 installation's folders). Added `AnInstanceWithNoDirectoryOfItsOwnLandsUnderTheResolvedInstanceDirectory` at the lowest layer that shows it - an in-process server, no client - and named it beside the other case in the plan's K27 row.

**The tripwire that had tripped, resolved rather than re-filed.** `TestListensOnlyOnTheReservedPorts` asserted that the set of ports that started listening on the machine while the fixture's host was built is *exactly* the two the fixture reserved. The `NOTE:` at the site named both the failure mode (an unrelated process opening a socket in that window) and the remedy (narrow the assertion to Kestrel's own default HTTP ports), and the implement run tripped it: one run counted a third port, numbered just above the two the fixture had reserved, and three immediate repeats passed. The revisit condition the `NOTE:` stated has therefore tripped, so the pre-named remedy was applied rather than filed: the case now asserts that the host's two ports are in the set and that no Kestrel default HTTP port (5000, 5001) is, which is the regression it exists to catch - `NetTcpServiceHost.Build` clears the server-URLs setting precisely so Kestrel opens no HTTP endpoint of its own. The remaining assertions (neither port is 8060 or 8061) are unchanged. The `NOTE:` became the field's remarks, recording the flake and why the assertion is shaped the way it is.

**Weighed and left alone.**

- **The extra change in `CoreWcfProtocolTest.cs` was in scope, not scope creep.** The implement handoff flagged it and offered to split it out. It is a measured, three-line fix for a defect that this ticket's own change made visible and that contradicted a claim in the plan; the project rules put a local, obvious fix in the ticket that meets it. Kept, and it is what makes the WS3 isolation claim true.
- **`InstanceManager.InstanceDirectory`'s getter does not echo its setter** - it resolves the whole order, so a caller cannot ask "was an override set?", and a test restores by clearing rather than by putting a saved value back. A property whose getter and setter disagree is a real API smell, but the asymmetry is what makes the getter useful as a diagnostic, and the member's own remarks state it plainly. Reporting what was set needs a second member and no caller wants one today; left as it is, documented where a reader meets it.
- **The static resolution is not synchronized** (`_instanceDirectory` and `_instances` are plain statics, and setting the property writes both without a lock). `_instances` was already unsynchronized before this change, and in practice the folder is set once before anything starts; no new hazard worth a guard or a note.
- **The property's remarks and the `PathUtility` overload's remarks each say "why", not "what"**, and nothing in the diff narrates its own statements; the files stay small (`wc -l`: `InstanceManager.cs` 244 lines, `PathUtility.cs` 205, `InstanceManagerTest.cs` 168).
- **`docs/users-guide/dataphor-service.md` does not mention `DATAPHOR_INSTANCE_DIRECTORY`.** Deliberate, and agreed: the variable is a testing and diagnosis facility rather than an installation setting, `docs/migration-notes.md` carries it for anyone upgrading, and that file's settings section belongs to `host-instance-configuration`.

**Nothing filed.** No finding reached the filing bar: the four above were fixed in this pass, the tripwire's own named remedy was applied at its site, and the rest are decisions already recorded in the code or the documentation. No new ticket, and no new `NOTE:` beyond the reshaped one on `_portsOpenedByTheHost`.
