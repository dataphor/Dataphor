# Complete: lazy catalog-store write transactions and read-your-writes (K10, second half)

## What changed

**Store transactions follow the session's writes, not its transactions** (`ServerCatalogDeviceSession`, regions "Catalog Store" and "Transaction").

- `InternalBeginTransaction` override removed: a process transaction no longer begins a store transaction. `_isUpdatable` ("owned for life") is gone.
- `AcquireCatalogStoreConnection(true)` → `BeginStoreTransactions()`: begins store levels until the store's count equals `OpenTransactionLevels` (the device session's `Transactions.Count`, minus one while a commit is between its store commit and the device session's pop, see below), each with `ServerProcess.Transactions[level].IsolationLevel`. Only the 0 → 1 begin reaches SQLite (`BEGIN IMMEDIATE`). Outside any process transaction, writes autocommit.
- **Every acquire takes a pooled connection** (`Device.Store.AcquireConnection()`); the old `Device.Store.Connect()` for writes is gone. Necessary, not cosmetic: with connections now returned to the pool after each write transaction, `Connect()` on every first write would create a new connection each time and the pool would grow until `SQLStore.MaxConnections` (60) raised MaximumConnectionsExceeded.
- `ReleaseIdleCatalogStoreConnection()`: the connection goes back to the pool when `_acquireCount == 0` and the store's count is 0, called from `ReleaseCatalogStoreConnection` and from both end hooks. **Deviation from rule 4's "assert the connection is out of transaction"**: if the store's count is 0 but the database connection is still in a transaction (a commit or rollback that failed in SQLite), the connection is disposed instead of pooled (new `CatalogStoreConnection.InDatabaseTransaction` / `SQLStoreConnection.InDatabaseTransaction`). An assertion there would throw from a rollback path after the real error had already surfaced; pooling would hold the write lock for good.
- End hooks: `InternalAfterCommitTransaction` / `InternalAfterRollbackTransaction` end the store level only when the store's count equals `Transactions.Count` (`StoreHasEndingLevel`). **Both `ServerProcess.TransactionCount` and the device session's `Transactions.Count` still include the ending level when these hooks run** (`DeviceSession.CommitTransaction` pops after `InternalCommitTransaction` returns; `ServerProcess` pops after all sessions). `CheckStoreTransactionLevels` asserts (always on) that the store's count never exceeds the session's open levels, before each begin and after each end.
- `_endingTransaction` (set after the store commit, cleared by a new `InternalCommitTransaction` override's `finally`): `CatalogDeviceSession.InternalCommitTransaction` runs `ExecuteDeferredDeviceStops` after the commit hook and before the pop; a store write there would otherwise begin a level nobody ends. No shipped device's `Stop` writes the catalog store (checked: Memory, Frontend, SimpleDevice, catalog), so this guards custom devices.
- The rollback hook releases in a `finally`, so a failed store rollback still gives the connection back (or disposes it).
- Acquire failure cleanup (from `store-sqlite-wal-busy`) kept: the `catch` calls `ReleaseCatalogStoreConnection()`, which undoes the count and pools a connection it just took; a failed begin leaves the store's count where it was (0), so the process rollback that follows is consistent.

**Deviation from the settled design — DDL takes the store's lock before the catalog's lock** (`DDLNode.InternalBeforeExecute` → new virtual `CatalogDeviceSession.BeginStoreWriteTransaction`, overridden in `ServerCatalogDeviceSession` as acquire(true) + release). The ticket's design (begin only at the first store write) **deadlocked**: the drop and alter nodes write the store inside `lock (program.Catalog)` (`DDLNodes.cs`, 11 sites), so a session whose first write was a drop waited for the write lock while holding the catalog's lock, and the lock's holder, running its next DDL statement, waited for the catalog's lock. Measured with that design: `ConcurrentDDLWithQueriesAndDrops` 42 of 120 cycles failed with 130103 after 30 s each, 264 s in total. The eager design never hit this because a session's later transactions took the store lock before any statement ran. Now a DDL statement (outside a loading context, so that loading an object from the store never takes the write lock) begins the store write transaction before it runs; nested DDL finds it begun. A **Debug-only** assertion (`Error.DebugAssertFail(!Monitor.IsEntered(Catalog), …)` at the 0 → 1 begin) flags any path that begins it inside the catalog's lock: with the pre-acquire disabled it failed all 120 cycles deterministically (checked once, restored), and it never fires in the full suite (coverage scripts included). The plan's WS4 target-design paragraph and K10 row now record this refinement. Consequences a reviewer should weigh:
- A DDL statement that would not write the store (a session-scoped object, a drop that fails its dependents check) still takes the write lock for the rest of its transaction.
- Only the catalog's lock is checked. Library registration writes inside `lock (program.Catalog.Libraries)` (`LibraryNodes.cs`, `LibraryUtility`); if a write-lock holder can wait for that lock, the same deadlock is possible (recorded in `docs/architecture.md`).
- A process with implicit transactions off still runs DDL in autocommit and waits for the write lock inside the catalog's lock, as before (`NOTE:` on `BeginStoreWriteTransaction`).

**Rule 6 (no open reader across the lazy begin).** New `SQLStoreConnection.OpenReaderCount` (incremented in `ExecuteReader`, decremented in `SQLStoreCursor.DisposeReader` through `ReaderClosed()`); `CatalogStoreConnection.BeginTransaction` asserts (always on) that it is 0 at the outermost begin, after `FlushCache` closes cached cursors. `SQLConnection`'s own active-cursor tracking was not usable: with MARS (SQLite has it on) `SetActiveCursor(null)` removes the *current* active cursor, not the closing one. Search of the session's read methods: every `CatalogStoreConnection` read returns a list except `SelectLibraryDirectories/Owners/Versions`, which return cursors; Owners and Versions loops only fill a native table; `AttachLibraries` held its cursor across `LibraryUtility.AttachLibrary` (which runs library-added handlers) and now reads into a list first. No nesting that actually writes was found; the assertion never fired in the suite.

**Rule 7.** `NOTE:` on `CatalogDeviceTable.InternalOpen`: committed data only.

## Known gaps and things to look at

- The DDL pre-acquire changes *when* the lock is taken from "first store write" to "first DDL statement or first store write"; judge whether that is acceptable against the plan's wording (the plan now says so).
- `BeginStoreWriteTransaction` runs on every DDL node execution (an acquire and release on a pooled connection when the transaction already holds the lock). Not measured on its own; the concurrency timings show no slowdown.
- The Debug-only lock-order assertion means Release builds would only show a missed path as a 30-s wait and 130103 under contention. Chosen over an always-on assertion so that a missed path never fails a DDL that would have worked without contention.
- No test exercises a commit or rollback that fails inside SQLite (the dispose-instead-of-pool path) or a store write during deferred device stops (the `_endingTransaction` path); both by inspection.
- First write at a nested level, an inner level without writes after a written outer level, and `DeviceConnect` inside an open transaction: by inspection plus the always-on level assertion, which the suite never tripped.

**Checked, no defect found:**

- Transaction-level bookkeeping in `ServerCatalogDeviceSession`, traced against `DeviceSession.CommitTransaction`/`RollbackTransaction` (`src/engine/DAE/Schema/Device.cs`) and `CatalogDeviceSession.InternalCommitTransaction`: first write at an inner level (begins every missing level, each with its process level's isolation), an inner level without writes after a written outer level (the end hooks skip the store), a level that wrote and ended followed by a new inner level, deferred device stops between the store commit and the pop (`_endingTransaction`; outermost → autocommit), and a commit that fails in SQLite (the store's count is already 0, the device level is not popped, the process rollback finds no store level and the release disposes the connection instead of pooling it). The always-on level assertion holds in each.
- Pooled write connections: `CatalogStoreConnection` caches cursors only while a store transaction is open and flushes them at the outermost commit or rollback, so a connection returned to the pool carries no open reader or cached cursor. The pool never shrinks, but it is now bounded by concurrent sessions instead of growing by one dedicated connection per writing session, so there is no new resource concern.
- Lock order beyond `DDLNodes.cs`: every other `lock (Catalog)` / `lock (program.Catalog)` site that writes the store (`ServerCatalogDeviceSession` security and rights methods, `CatalogDeviceSession.DeleteCatalogObject`/`DeleteRole`/`DeleteRight`) releases the lock before the write; `SystemRoleExistsNode`, `SystemClearLibraryNode` and the compiler's locks (`Compiler.cs`) only read, and reads never wait for the write lock.
