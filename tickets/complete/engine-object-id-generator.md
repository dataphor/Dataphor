## What landed

`ticket(implement): engine-object-id-generator` is the first of four steps towards `bug-object-id-counter-is-process-wide`. It introduces the type that will own catalog identifier allocation, puts one on `Engine`, gives the compiler and the run time a way to reach it, and converts the allocation sites that already had an engine in hand. **Nothing about the running system changes**, by design: every engine's generator is literally the same object as the counter the unconverted sites still use, so the sequence of identifiers handed out is unchanged.

### The generator

`src/engine/DAE/Schema/ObjectIDGenerator.cs` (new, listed in `src/engine/DAE/DAE.csproj`, which names its compile items explicitly):

- `Allocate()` - `Interlocked.Increment` over a private `int`, so the first identifier is 1 and 0 is never handed out. That is what lets the next two tickets use 0 to mean "no identifier". Refuses exhaustion rather than wrapping into the negative identifiers that mean something else.
- `Allocate(MetaData)` - honours a `DAE.ObjectID` tag and removes it, else allocates. The body that used to be `Schema.Object.GetObjectID(MetaData)`, moved unchanged.
- `Reset()` - back to zero, so the next identifier is 1 again. For the engine whose built-in objects must be numbered identically on every load of its catalog store.
- `EnsureAllocatedThrough(int)` - raises the counter to the given identifier if it is below it, never lowers it.
- `SetLastAllocated(int)` - internal, and not in the ticket's design: `Schema.Object.SetNextObjectID` must keep being able to move the counter *down*, because `tests/DAE.Server.Tests/TestEnvironment.cs` and `tests/Dataphor.Benchmarks/BenchmarkServerInstance.cs` read the counter and put it back. It carries a `NOTE:` saying it goes when that method goes. Reviewed and kept: the alternative is leaving `SetNextObjectID` on a separate static counter, which is exactly the two-counters state the staging exists to avoid.

`Reset`, `SetLastAllocated` and `EnsureAllocatedThrough` take a private lock; `Allocate` stays lock-free, as today.

### Where it lives, and how call sites reach it

- `Engine.ObjectIDGenerator`, a `readonly` field assigned in the `Engine` constructor from `Schema.Object.SharedObjectIDGenerator` (a new `internal static readonly` instance next to the counter it replaces) and never reassigned. Both sites carry a comment saying the sharing is the transition and which ticket ends it.
- `Plan.GetNextObjectID()` and `Plan.GetObjectID(MetaData)`, which go through `ServerProcess.ServerSession.Server.ObjectIDGenerator` - the same expression `Plan.Catalog` and `Plan.IsEngine` already use, so a plan always numbers from the engine whose catalog it compiles against.
- `Schema.Object.GetNextObjectID()`, `GetObjectID(MetaData)` and `SetNextObjectID(int)` stay on the public surface and delegate to that shared instance, so the sites not yet converted draw from the same counter.

### The three guards

`Schema.Object.SaveObjectID`, `ServerCatalogDeviceSession.InternalInsertPersistentObject` and `CatalogDeviceSession.CacheCatalogObject` refuse an object whose identifier is 0, with the new `SchemaException` code 113249. Nothing can produce such an object today; `engine-object-id-keys-and-orders` and `engine-object-id-transient-tablevars` inherit the guards, which is what catches a site they miss.

### Call sites converted (about 40)

`Compiler.cs` (5 `GetNextObjectID`, 27 `GetObjectID`), `AdornNode.cs` (1; the commented-out one at line 178 left alone), `RenameNode.cs` (2), `TableNode.cs` (2), `DDLNodes.cs` (1, via `program.Plan`), `ServerProcess.cs` (1), `Engine.cs` (3 allocations plus the reset in `InitializeCatalog`, which stays exactly where and when it was, comment included), `Server.cs` (1 allocation plus `LoadServerState`), `TestNodes.cs` (8, via `program.Plan`).

Also: the dead three-argument `Schema.Property(int, string, IDataType)` constructor is deleted. It chained to `base(name)` and so threw away the identifier it was given; nothing called it.

### Two error codes, not one

The ticket asked for one code at 113249 for both the guards and the overflow check. The two conditions cannot share a message - one names an object, the other names no object at all - so there are two: `ObjectIDRequired = 113249` ("Object "{0}" has not been given an object identifier.") and `ObjectIDsExhausted = 113250` ("The object identifiers of this catalog have been exhausted."). Reviewed and kept. `docs/reference/error-codes.md` lists prefix ranges only and needed no edit.

### One identifier changes after a store load

`Server.LoadServerState` used to call `SetNextObjectID(GetMaxObjectID() + 1)`, which made the *next* allocated identifier `max + 2`, because the counter holds the last identifier allocated rather than the next one. `EnsureAllocatedThrough(GetMaxObjectID())` makes it `max + 1`. No identifier collides either way - the old code reserved one it never handed out - and `docs/migration-notes.md` carries the note.

## Review findings

Read the implement diff before the handoff, then re-derived its claims from the tree: the one-counter invariant the whole chain rests on, the reset's placement, every remaining user of the three statics, whether the deleted constructor is reachable reflectively as well as by name, whether the guards' `== 0` is the right test against what the next ticket in the chain will produce, and the five documents the change touched or should have. Ran the build, the three suite parts, the spike smoke and the engine check.

**Checked and found sound, no change.** The chain's central claim holds: `Engine._objectIDGenerator` is `readonly`, assigned once from `Schema.Object.SharedObjectIDGenerator`, never reassigned, and the three `Schema.Object` statics all delegate to that same instance - so no catalog can be fed by two counters during the transition. A grep for the three statics across `src`, `libraries`, `tests`, `tools` and `samples` finds only the sites the chain's later tickets own: `Schema.Object(string name)` (`Schema.cs:232`), the `ResultTableVar` constructor (`TableVar.cs:2896`), and the two save-and-restore workarounds in `TestEnvironment.cs` and `BenchmarkServerInstance.cs`. Every conversion swapped a static for an accessor onto that same instance, so the sequence of numbers is identical; `LoadServerState` is the only behavioural delta and it is documented. `Engine.InitializeCatalog` still resets as its first act, before `CreateCatalogDevice`. `ServerSession.Server` is typed `Engine` and a `Plan` always has a `ServerProcess`, so the two new `Plan` members have no null case. The deleted `Schema.Property` constructor is unreachable by name (one `new Schema.Property` in the tree, the two-argument call at `Compiler.cs:4714`) and reflectively: `Schema.Property` is not a class `plan.CreateObject` instantiates, and its `[Reference]` attributes are `MemoryUtility.ReferenceAttribute`, not BOP's, so no persisted artifact is deserialized through a constructor signature. The guards' `== 0` is right rather than `<= 0`, because `engine-object-id-keys-and-orders` gives unnumbered objects `Schema.Object.UnassignedID`, which that chain defines as 0; the guard in `CacheCatalogObject` sits ahead of the `#if !DEBUG` replace-by-name block, so it cannot be masked in a release build. `docs/reference/error-codes.md` lists prefix ranges only and `docs/architecture.md` never mentions object identifiers, so neither is out of date; `docs/modernization-plan.md:461` still correctly names `bug-object-id-counter-is-process-wide` as the owner of a fix that is not finished, so the plan needs no edit either.

**The step also fixes a latent defect the handoff reports only as a changed number.** On an empty or first-run store `GetMaxObjectID()` returns 0, so the old `SetNextObjectID(GetMaxObjectID() + 1)` *lowered* the counter to 1, and the next allocation would have been 2 - colliding with the built-in objects `InitializeCatalog` had just created. That is reachable: `Engine.ClearCatalog` calls `LoadServerState()` unconditionally (`Engine.cs:1345`), where `Engine.Start` guards it with `!_firstRun`. `EnsureAllocatedThrough` cannot lower the counter, so the path is now safe, and the new test pins that half of its contract.

**Found and fixed inline - the exhaustion guard was not permanent.** `Allocate`'s overflow check threw, but `Interlocked.Increment` had already wrapped `_lastID` negative, so after another two billion calls the counter would climb back through 1 and hand out identifiers the catalog already holds - the exact silent corruption the check exists to refuse. It now pins the counter at `Int32.MaxValue` on the wrap, so every later call throws. No test can observe the difference (telling the two apart takes another two billion calls and the counter is not readable), and the fixture's remarks say so rather than implying coverage.

**Found and fixed inline - source hygiene.** The `SetLastAllocated` block, the member added after the ticket's design, was written with bare LF line endings in a CRLF file; the file is now CRLF throughout, byte-order mark kept. The `_syncRoot` doc comment named two of the three methods it serializes and did not say the lock deliberately does not cover `Allocate`; rewritten. `using System.Threading;` in `Schema.cs` became unused when the `Interlocked` and `lock` bodies moved out, and is removed - no other `System.Threading` type appears in the file and the build's warning count is unchanged. The new `Schema\ObjectIDGenerator.cs` compile item was out of `DAE.csproj`'s alphabetical order and is moved before `Schema\Operator.cs`.

**Tripwire, parked at the site.** `Allocate(MetaData)` returns a tag-supplied identifier without raising the counter, as it always has. Every path that loads objects carrying `DAE.ObjectID` tags today is a catalog store load, and `Server.LoadServerState` raises the generator past the store's maximum afterwards; a new load path that does not would let the generator reissue an identifier a loaded object already holds. Recorded as a `NOTE:` on that method, where whoever adds such a path will meet it.

**One test added, for the contract the rest of the chain rests on.** `tests/DAE.Server.Tests/ObjectIDGeneratorTest.cs`, three cases against a generator each case constructs itself, so none of them touches the counter the rest of the suite allocates from: identifiers start at 1, which is what leaves 0 free to mean "unassigned" for the next two tickets; `EnsureAllocatedThrough` raises the generator and a lower maximum does not pull it back; and exhaustion raises 113250. The project's testing rule asks a bug fix for its reproduction, and this is the lowest layer that shows any of it - the implementation's remaining uncovered path (the identifier-0 guards) is unreachable by construction until `engine-object-id-keys-and-orders` lands, and the behavioural characterization belongs to `bug-object-id-counter-is-process-wide`, where the behaviour changes. No test was added for the conversions themselves: they change no behaviour, and the allocation they re-plumb runs for every catalog object the suite's 781 passing tests create.

**No tickets filed.** The two departures from the ticket are sound and are recorded above with their reasons; the remaining gaps are already owned by tickets on the board - `engine-object-id-keys-and-orders`, `engine-object-id-transient-tablevars` and `bug-object-id-counter-is-process-wide` for the rest of the chain, and `bug-client-catalog-rebuild-reuses-object-ids` for the reset that a repository engine should not be doing at all.
