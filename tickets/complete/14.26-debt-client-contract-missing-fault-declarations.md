## What landed

One root cause with two arms, fixed at one site: the three administrative operations of the main service contract - `Start`, `Stop` and `GetState` - had incomplete error handling on both halves of the client. Implemented by `ticket(implement): debt-client-contract-missing-fault-declarations`; the review pass below added one test, retired some duplication and parked one tripwire.

**Arm one, the fault declaration.** `[FaultContract(typeof(DataphorFault))]` added to `BeginStart`, `BeginStop` and `BeginGetState` in `src/protocol/Client/Contracts/IClientDataphorService.cs`. The server has always declared it on all three; a Windows Communication Foundation client only deserializes a fault into `FaultException<TDetail>` when the operation's contract declares that detail type, so without it the three `catch (FaultException<DataphorFault>)` blocks in `ClientServer` were dead code and the server's exception type, error code, severity and inner exception were all discarded. The server side was left alone, as the ticket required.

**Arm two, the communication catch.** `catch (CommunicationException ce)` added after the existing typed catch in `ClientServer.Start()`, `ClientServer.Stop()` and the `ClientServer.State` getter, in the same shape the other five members of the class use (`ReportCommunicationError()`, then `ServerException.Codes.CommunicationFailure` with `ErrorSeverity.Environment` and the caught exception as inner). The typed catch stays first because `FaultException<T>` derives from `CommunicationException`; a one-line comment at the `Start()` site says so, since the ordering is load-bearing and silent if reversed. `ReportCommunicationError()` is still a deliberate no-op, so nothing about channel recovery changed.

**The parity record drained.** The three `KnownFaultDifferences` entries in `tests/DAE.Server.Tests/ContractParityTest.cs` are gone; the array is now empty and the comment above it says what an entry is for, so the mechanism stays available for the next difference. The test fails on an entry whose difference is no longer there, so this could not have been skipped.

**Documents.** `AGENTS.md` and the `protocol-contract-parity-test` row in `docs/modernization-plan.md` both described the list as recording three differences; both now say it is empty and what it is for. One entry appended to the **Custom C# extensions** section of `docs/migration-notes.md`, status `done`, naming both behaviour changes an extension can notice.

## Review findings

**Verified the central claim by measurement, not by reading.** With `[FaultContract(typeof(DataphorFault))]` removed from `BeginStart` alone and everything else in place, `ContractParityTest.DataphorServiceDeclarationsMatch` reports `IDataphorService.Start: the declared faults differ - server DataphorFault, client none`, and `TestAnAdministrativeErrorArrivesAsTypedFault` fails on its error-code assertion (`Expected: 127105  But was: 106211`). Restored, both pass. The handoff's account of the fix is accurate.

**One claim in the handoff is wrong, and it was the argument for keeping two assertions.** The handoff said that reverting arm two alone "would be caught by nothing else", offering that as the reason the case's two `Is.Not.InstanceOf` assertions earn their place. Measured: with arm two's `catch (CommunicationException)` removed from `ClientServer.Start()` and nothing else changed, the whole fixture stayed green. In that case's scenario the error arrives as a *typed* fault, so the typed catch above arm two takes it and arm two never runs - those assertions cannot see arm two at all. The assertions were kept anyway: they are worded exactly as the two neighbouring cases word them, and each names a distinct failure shape in its message. The comment at the site is accurate as written and was left alone; only the handoff's justification was wrong, and it does not survive into the code.

**Arm two had no coverage anywhere - fixed in this pass.** Arm two changes behaviour an application can notice (it has a `docs/migration-notes.md` entry), and `grep -rn "CommunicationFailure" tests/` returned only failure-message text: nothing in the suite asserted that a transport failure is translated, for these three members or the other five. The implement ticket declined a test on the grounds that "provoking a transport failure mid-call is a timing exercise" - true, but it need not be mid-call. `TestAnAdministrativeOutageArrivesAsACommunicationFailure` stops the host and *then* calls `Start()` on a `ClientServer` whose channel factory is already built; `NetTcpServiceHost.Stop` blocks until the host has stopped, so the port is closed before the call returns control, and connecting to a closed loopback port is refused at once. No timing window. Measured load-bearing: removing arm two's catch from `Start()` fails it; restored, it passes. The project's testing rule ("a ticket that changes the behaviour of a subsystem owes a characterization test for it unless one already covers it") is the reason this was added rather than noted.

**The new hosted case duplicated a helper that existed, and left dead code behind it.** It hand-rolled the whole of `HostedInstance`: the temporary directory, `TestEnvironment.CopyLibraries`, the port reservation, `NewHost()`, `Configuration(...)`, the `host.Stop()` finally, `TestEnvironment.TryDeleteDirectory` and the object-id counter guard - which is exactly what the fixture's `WithASecondHost` does. It could not use it because `HostedInstance` kept its directory private and the case needs that path to reach the catalog store. Worse, `WithASecondHost` had been left with no callers at all by the previous review's helper extraction (`ticket(review): protocol-corewcf-host`), so the duplication also left dead code in the fixture. Fixed: `HostedInstance.RootDirectory` added in the same style as its other accessors, and both hosted cases now go through `WithASecondHost` - 28 lines out of the first case, and the helper is live again. With `ShouldListen` false the helper reserves one loopback port it never binds; `OverrideListenerPortNumber` is read only inside `if (instance.ShouldListen)` in `DataphorServiceHost.Start`, so that is waste and not behaviour, and it was not worth a conditional to avoid.

**A comment said something untrue.** "The constructor opens the channel" - `ClientServer`'s constructor builds a `ChannelFactory`; the channel itself is created lazily by `GetServiceInterface()` on the first call. Reworded to say that.

**The class of defect is drained, not just this instance.** Checked the other two contract pairs: `IClientListenerService` declares `ListenerFault` on all three of its operations and `IClientNativeCLIService` declares `NativeCLIFault` on all twelve of its own, and neither `ListenerClient` nor `NativeCLI` has a typed catch without a matching declaration. So no dead typed catch remains anywhere in the client, and `ContractParityTest` - with its list now empty - is the boundary invariant that keeps it that way. Nothing to file.

**Checked, nothing found:** all eight members of `ClientServer` carry both catches, and across the whole protocol client (`src/protocol/Client/Client/*.cs`) `catch (FaultException<DataphorFault>` and `catch (CommunicationException ce)` both occur 87 times - no member is left with one and not the other. No in-repo caller catches `FaultException` or `CommunicationException` around these three calls, so the behaviour change is visible only to out-of-repo extensions, which is what the migration note is for. `DataphorServiceHost.Stop` is idempotent (every stage null-guarded, the host error rethrown through `ExceptionDispatchInfo` at the end), so the second `Stop()` that `HostedInstance.Dispose()` makes after a case has stopped the host itself is safe. The new migration-notes entry is under **Custom C# extensions** with status `done`, and no other document and no `K` defect entry in the plan mentions the three differences. All edited files keep their UTF-8 byte-order mark, CRLF endings and tab indentation (checked byte-wise: zero lone line feeds, zero space-indented lines).

**Considered and not changed.** `RuinTheCatalogStore` hard-codes the `DAECatalog*` glob rather than deriving it from `TestServerInstance.CatalogStoreConnectionString`; its `Assert.That(files, Is.Not.Empty, ...)` already fails loudly if the store ever moves, and deriving the name would couple the case to the SQLite connection-string builder for nothing. With `KnownFaultDifferences` empty, the matching branch in `CompareFaults` and the unmatched-entry report in `CompareOperations` are unreached until someone adds an entry; the fixture's existing class-level `NOTE:` already records that the comparison's branches have no test of their own and were confirmed against uncommitted synthetic interface pairs, so nothing new was parked there.

**Tripwire parked.** `tests/DAE.Server.Tests/CoreWcfProtocolTest.cs` is 979 lines (`wc -l`, 2026-11-20) - the largest file in the test project and half again the next - and most of the bulk is host and client plumbing rather than cases. A `NOTE:` at the fixture declaration says to move that plumbing to a file of its own if more hosted cases land. Fine as it stands; no ticket.

**No tickets filed.** Nothing found reached the filing bar: the one real gap (arm two unverified) was cheap to fix here, and everything else was either resolved inline or is conditional.
