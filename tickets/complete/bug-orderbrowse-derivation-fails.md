## What landed

**One line of product code.** `OrderBrowseDocumentBuilder.GetColumnTitle` (`libraries/Frontend/Source/Production/DocumentBuilder.cs`) looked a column up in the elaborated expression's column collection under the column's own name (`ID`). That collection is keyed by the *elaborated* name - the column's name qualified with its elaborated table's name, so `Main.ID` - so the lookup missed and the indexer raised Frontend error 200127, `Elaborated column "ID" not found`. The name is now qualified with `DerivationUtility.MainElaboratedTableName` before the lookup, as the two sibling lookups in `SearchStructureBuilder.Build` already did.

`GetColumnTitle` is reached for every visible column of every visible order, so deriving the `OrderBrowse` page - the order chooser a user opens to sort a browse list - failed for 47 of the 52 surfaces of the derivation golden corpus. The five that derived were the surfaces with no visible order column, so nothing reached the lookup; their goldens carry an empty order selector and are unchanged by this work.

**47 new goldens**, `tests/goldens/frontend/*/*.OrderBrowse.xml`. These are the reproduction, at the lowest layer that shows the defect: before the fix each of those 47 cases threw, and with the expected-failure table now empty a regression fails the pass with the error rather than quietly leaving a file missing.

**The expected-failure row is drained.** `FrontendDerivationGoldenTest.ExpectedFailures` is `[]`, with its `NOTE:` rewritten to say that an empty array is where the next derivation defect gets recorded. The `ExpectedFailure` type and its `"*"` matching stay as the recording mechanism.

**Prose.** The class remarks' corpus and determinism paragraphs, `AGENTS.md`'s *Derived form goldens* paragraph, the plan's `test-frontend-derivation-golden` work-item row, the plan's *Known defects* table (new row **K36**) and `docs/migration-notes.md` under *Forms and the Windows client* (a `done` entry, nothing for an application to do).

**Not a porting defect.** The unqualified lookup is in the initial open-source commit and was only ever touched by an identifier rename. It is a 3.1-era defect that nothing exercised, because the derivation engine had no automated coverage until `test-frontend-derivation-golden`. K36 says so.

**The fix is right, not merely non-throwing - checked two ways.** By construction: `InterfaceBuilder` builds the main elaborated table variable under the name `DerivationUtility.MainElaboratedTableName`, and `ElaboratedTableVarColumn` keys a main-table column as `Schema.Object.Qualify(column.Name, <that name>)`, which is the expression the fix now writes - the same call, so the two agree for any column name, including one that itself contains a qualifier. By output: for all 52 surfaces, every order-column title in an `OrderBrowse` golden also appears as a grid column `title` in that surface's `Browse` golden, which has been checked in and passing since the goldens were created. That is 0 mismatches over every title of every order of the corpus, and it is why the oddities in these titles (`Role_Name`, `Application_ID`, `Master_ID`) are not findings: the working `Browse` page titles those columns identically.

**The defect class is now closed by inspection, which is why no `debt-` ticket was filed.** Only five sites in the Frontend library index an elaborated column collection by name (found by grepping `libraries/Frontend/Source/` for indexing and `IndexOf` against `ElaboratedExpression.Columns` and `RootExpression.Columns`), and after this fix all five qualify. The ladder's higher rungs have nothing left to retire: a representation change (a typed key, or a `MainColumn(name)` accessor that qualifies internally) would be a refactor of five correct call sites, and the generalized test that would catch the class - all 416 derivations compared against checked-in output - is exactly what `test-frontend-derivation-golden` already landed, and it is what caught this one.

**Tripwire, recorded at the site.**

- `GetColumnTitle` assumes every order column is in the elaborated expression. A column tagged `Frontend.Include = "false"` and left visible is in the order but not in the collection, so the fixed lookup would throw `Elaborated column "Main.<name>" not found` - the same error, from a different cause. Fine today: no library in the repository tags a *column* that way for a derivable page type (the `Frontend.Include = "false"` tags in `Sample.Shipping` are all on references, which is a different code path, and the one on a column is scoped to the `Preview` page type, which the engine refuses to derive at all). It is also not this site's assumption alone - the `Browse` page's search builder makes it over every column of every visible order and every key, without the visibility filter, so an application with such metadata loses `Browse` first, and that has been true since 3.1. Recorded as a four-line `NOTE:` above `GetColumnTitle` naming the condition and the tag, because the error message does not mention the `Include` tag and that is what made this bug's original diagnosis slow. Not filed: data-conditional, not reachable by any library here, and what it would need is a message change in two places, not a defect to repair.

- *Resource cleanup, type safety, performance.* The change adds one string concatenation per visible order column in one page type. Nothing is allocated that was not already, nothing is disposable, no type changed.

**Known gaps, carried forward as they are.**

- `GetDefaultOrderTitle` appends " (descending)" for a descending order column, and no table variable in the eight corpus libraries declares one, so the word appears in none of the 416 goldens. Read and correct, but not covered. Nothing was added to force it: a library with a descending order would cover it for free, and a synthetic surface built only to reach one line would be a test of the corpus rather than of the engine.
- With `ExpectedFailures` empty, the "no expected-failure row covers it" message in `Unexpected` has never run in a green state. It is read-only string formatting reached only by a failing derivation, and the next derivation defect will exercise it on the way to being recorded.
- The corpus derives every surface as a master. An `OrderBrowse` page derived with detail keys takes the same lookup, and the detail-key columns are forced into the elaborated expression, so it is correct by the same argument - but that is argued, not measured. Covering it belongs to the golden pass's scope, not this fix's.

**Worth a second opinion, left alone deliberately.** `System.Internet/XMLElementParent.OrderBrowse.xml` reads `by Element ID, Element ID`: its order is `{ Parent_Element_ID, Element_ID }` and both columns take their title from the same domain, so the two order columns read identically in the chooser. This is the engine's existing titling behaviour, not an artifact of the fix - the same surface's `Browse` golden has carried two `title="Element ID"` grid columns since the goldens were created, and that page worked in 3.1. Deciding that an order column's title should be disambiguated would change titling for forms that work today, which is a compatibility surface; it is a separate ticket if anyone wants it.
