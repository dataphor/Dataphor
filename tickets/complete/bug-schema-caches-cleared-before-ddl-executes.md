## The defect

Each catalog keeps two memos shared by all sessions: the **conversion path cache** (`Catalog.ConversionPathCache`, class `ScalarConversionPathCache` in `ScalarType.cs`: for a pair of scalar types, the chain of implicit conversions between them) and the **operator resolution cache** (`Catalog.OperatorResolutionCache`: for an operator name and argument types, the overload chosen and the conversions applied). They were cleared only while the compiler compiled `create`/`drop conversion` and `create`/`drop operator`; the catalog changes later, when the plan executes. A session that compiled in that window recomputed the answer from the unchanged catalog, cached it, and every session kept using it after the change. Known-defects row K32 in `docs/modernization-plan.md`.

## What landed (`ticket(implement): bug-schema-caches-cleared-before-ddl-executes`)

- `CatalogDeviceSession.AddImplicitConversion` clears both caches whole under its catalog lock (a new conversion can shorten a cached path between types it does not touch); `RemoveImplicitConversion` clears the entries that use the conversion; `CreateOperator` / `DropOperator` clear the operator name's resolutions after the catalog change.
- `Compiler.FindScalarConversionPath` now looks up, traces and caches under `lock (plan.Catalog)` and then the cache instance lock (the same order as `ResolveOperator`), so a trace neither reads a conversion list while DDL changes it nor caches a path read before a change after the change's clear.
- `create type ... like` adds and removes its temporary narrowing conversion on the shared like type's list under the catalog lock.
- The compile-time conversion clears in `CompileCreateConversionStatement` / `CompileDropConversionStatement` were removed (path tracing reads only committed conversion lists, so those clears could only evict answers that were still right); the compile-time operator clears stay, because the compiling plan resolves against the shared cache before its own new operator.
- `SchemaCacheInvalidationTest` (two tests) prepares the DDL, evaluates on another session, executes, then checks the new answer; both failed before the fix.

## Review findings

**Read first:** the implement diff, with the handoff second. Checked against `ResolveOperator`, `TraceScalarConversionPath`, the cache `Clear` overloads, `CompileCreateOperatorStatement` and `CompileCreateScalarTypeStatement`.

- **Correctness of the clears — no defect found.** Traced the create-operator race: `ResolveOperator` looks up, resolves and adds under `lock (plan.Catalog)`, and `InsertCatalogObject` changes the catalog under the same lock, so a resolution is either computed after the insert or added before it and removed by the following by-name clear; clearing outside the lock is sound. `OperatorResolutionCache.Clear(Conversion)` inspects every match's paths (not only the chosen one), so a removal that resolves an ambiguity is also caught. The conversion path cache stores only successful paths, so a removal cannot turn a cached "no path" into a wrong answer.
- **Removal of the compile-time conversion clears — agreed.** Within one plan, a conversion created at compile time is never visible to path tracing until execute (tracing reads only the scalar types' lists, not the plan catalog), so nothing compiled in the same plan depended on those clears. The `create type ... like` compile-time clear (~line 5806) and the operator compile-time clears are untouched.
- **Lock order / deadlock — no defect found.** The only taker of the conversion cache instance lock is `FindScalarConversionPath`, now always inside the catalog lock; `TraceScalarConversionPath` takes no lock and loads nothing; `ResolveOperator` already took catalog then cache. The application-transaction monitor → catalog order already existed in `ResolveOperator`.
- **Loading-time overhead (tripwire).** `AddImplicitConversion` flushes both caches whole on every lazily loaded conversion too. Not measured beyond the suite run time (see below). Parked as a `NOTE:` at the clear in `CatalogDeviceSession.AddImplicitConversion` with the revisit condition (skip when `ServerProcess.InLoadingContext()` if warm-up shows churn).
- **New defect found, verified, pre-existing (not introduced here): the shared operator resolution cache keeps operators from a failed or never-executed `create operator`.** While compiling `create operator`, the new operator is put in the plan's private catalog before its body compiles; a call in the body to the operator's own signature resolves to it and is stored in the shared cache. If the statement then fails to compile, the entry stays and every session can call an operator that does not exist. Verified with a throwaway probe test (removed afterwards): after `create operator G(Integer)` failed on an unresolved call in its body, `G(5)` on another session returned `5`; a variant without a base case overflowed the stack and killed the test host. Its fix site is the cache add in `Compiler.ResolveOperator`, the same site as the already-filed `backlog/bug-operator-resolution-cached-while-loading`, so it is appended there as arm 2 (with the static conversion-path variant from `create type ... like`); that ticket's description, `repro:` (now verified) and `tradeoffs:` were updated to cover both arms. Invariant stated there: the shared caches hold only answers computed from the shared catalog.
- **Tests — kept both.** Each is the reproduction of one arm of the bug, failed at the parent commit, and runs in milliseconds; no test restates the implementation. No test for the locking arms (timing only, as the handoff and K32 say). No test added by the review; the new defect's reproduction belongs to the ticket that fixes it.
- **Docs.** K32 row in `docs/modernization-plan.md` matches the code. The remarks on `ScalarConversionPathCache`, `OperatorResolutionCache` and `InvalidateCachesAfterUndo` describe the new clear sites and locks correctly. `docs/architecture.md` does not describe these caches; nothing to update. No migration note needed: no public signature changed, and the only observable change is that compiles after conversion/operator DDL see the change.
- **Source hygiene.** Edited files keep tabs, CRLF and their byte-order-mark state; comments state reasons, not narration. The braceless `if (...) lock (...) { }` in the `create type ... like` `finally` is consistent with the surrounding style; left as is.
- **Minor fixed inline:** only the `NOTE:` tripwire above. Nothing else needed changing.
- **AGENTS.md run time.** The handoff noted the suite takes longer than AGENTS.md's "about 3.5 minutes"; that predates this ticket and is not changed here.
