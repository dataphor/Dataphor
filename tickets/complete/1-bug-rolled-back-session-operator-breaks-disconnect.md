## What was wrong

A *session operator* belongs to one session and goes away when the session ends (`create session operator F() : Integer begin result := 1; end;`). The engine gives it a unique global name of its own in the catalog (`Object_<guid>`) and keeps a per-session entry mapping the name the user typed (`General.F`) to that global name. Every overload of the same session operator shares that one global name and that one entry.

Creating one inside a transaction and rolling the transaction back removed the operator from the catalog but left the session entry behind. The session then held an alias for an operator that no longer existed, and disconnecting it threw `Object "Object_<guid>" not found` (`SchemaException`, code 113104) out of `Engine.Disconnect`.

The cause was an ordering disagreement inside one method. `CatalogDeviceSession.CreateOperator` inserted the catalog object *first* and recorded the session-operator instruction *second*; a rollback replays the undo log backwards, so the session entry's undo ran while the catalog object was still present. `Engine.DropSessionOperator` removes the entry only once the operator's global name is gone from the catalog — that guard was false, so the entry survived. The forward `DropOperator` already did the two steps in the opposite order, which is why dropping a session operator worked and undoing its creation did not.

## What changed

**`src/engine/DAE/Device.Catalog/CatalogDeviceSession.cs`, `CreateOperator`** — the `CreateSessionOperator` call and its `CreateSessionOperatorInstruction` recording now come *before* `InsertCatalogObject`, with a comment stating why the order matters and naming the guard in `Engine.DropSessionOperator`. The undo log now replays in the same order as the forward `DropOperator` does its work: catalog object cleared first, session entry removed second. The `Catalog.OperatorResolutionCache.Clear` call stayed immediately after `InsertCatalogObject`, where it was.

Nothing else in the engine changed behaviour. The guard in `Engine.DropSessionOperator` was deliberately left alone — it is load-bearing, because overloads share one global name and one session entry, so dropping or undoing one overload must not remove the entry while another overload is still in the catalog. The session *object* path (`CreateTable`, `CreateView`, `CreateConstraint`, `CreateReference`) was left alone because `Engine.DropSessionObject` guards on the entry's own global name rather than on catalog membership, and every session object gets a fresh global name per create, so its undo is order-independent.

**`src/engine/DAE/Server/ServerSession.cs`** — one `NOTE:` tripwire added in review, comment only, above the loop in `DropSessionObjects` that resolves each session operator. See the review findings below.

**`docs/migration-notes.md`** — one row under *D4, catalog and libraries*, in terms of what a user sees: the rollback no longer leaves the session unable to disconnect. No application action needed.

## Tests

All in `tests/DAE.Server.Tests/CatalogStoreTest.cs`, which already held four other rollback cases. Each connects its own session so the test can read `ServerSession.SessionOperators` and so the disconnect itself is under test.

| Test | Cases | What it verifies |

| `InnerRollbackKeepsOuterSessionOperator` | the inner level creates an unrelated session operator; the inner level creates an *overload* of the outer one | a session operator created at an outer level keeps its entry, and stays callable through it, when an inner level is rolled back |

## Review findings

Read the implement-stage diff (`ticket(implement): bug-rolled-back-session-operator-breaks-disconnect`) before the handoff summary, then the surrounding code: all four session-entry helpers and the four `DDLInstruction` classes behind them in `CatalogDeviceSession.cs`; `InsertCatalogObject`, `DeleteCatalogObject`, `CacheCatalogObject` and `ClearCatalogObject`; `InternalBeginTransaction`, `InternalCommitTransaction` and `InternalRollbackTransaction`; every `SessionObjectName != null` site in the file (tables, views, operators, constraints, references); `Engine.DropSessionObject` and `Engine.DropSessionOperator`; `ServerSession.DropSessionObjects` and `ServerSession.Dispose`; `Catalog.Adding` / `Removing` and `OperatorMaps.RemoveOperator`; the session-operator and session-table naming in `Compiler.cs`; and `CreateOperatorNode` in `DDLNodes.cs`.

**Found and fixed in this pass (one, minor): the guard the fix rests on was not covered by any test.** `Engine.DropSessionOperator`'s `if (!Catalog.OperatorMaps.ContainsName(...))` is the single reason the reorder is correct rather than merely different, and the handoff names it as load-bearing and deliberately untouched — but nothing asserted it. Measured by neutering it to `if (true)`, rebuilding and re-running: all four of the handoff's cases still passed. In particular the "two overloads in the same transaction" case does not reach it, because the entry ends up removed either way and only the order of removal differs. `InnerRollbackKeepsOuterSessionOperator` is now two `[TestCase]`s — the inner level creating an unrelated session operator, and the inner level creating an overload of the outer one — and both assert that the outer operator is still callable after the inner rollback (`process.Evaluate("OuterSOp()", null)`). With the guard neutered the overload case fails with `Unable to resolve operator reference "OuterSOp" with signature "()"` (error 105149) and the other four pass; with the guard in place all five pass. No test method was added: the file gains one case and one assertion.

**Parked as a tripwire (one).** `ServerSession.DropSessionObjects` resolves every session-operator entry *before* it emits any drop, so a single entry naming an operator that is not in the catalog throws and aborts the whole disconnect: none of the session's objects is dropped, and its tables and operators outlive the session until the server restarts. That is why this defect's symptom was total rather than one leaked alias. Nothing produces such an entry now, so this is not work — a `NOTE:` at that loop records what the blast radius would be and says that the fix, if one ever appears, is to skip and log the entry rather than fail the disconnect. Not filed as a ticket: there is no reachable path to it.

**Checked and correct, nothing to do.**

- *The reorder is sound in every undo shape, not only the reported one.* Traced by hand and then by test: a single create; two overloads in one transaction; create-then-drop in one transaction; a create at an outer level with an unrelated create at an inner level; and a create at an outer level with an *overload* at an inner level. `OperatorMaps.RemoveOperator` drops the whole map once its last signature goes, so `ContainsName(OperatorName)` is a correct test for "gone from the catalog", and the guard therefore keeps the entry alive exactly while another overload still exists. Both directions now agree: the forward `CreateOperator` records entry-then-catalog and the undo of `DropOperator` restores entry-then-catalog; the forward `DropOperator` does catalog-then-entry and the undo of `CreateOperator` now does catalog-then-entry.
- *Nested levels fold correctly.* `InternalCommitTransaction` removes only the innermost `BeginTransactionInstruction` marker when `Transactions.Count > 1`, so instructions recorded at a committed inner level become part of the enclosing level's log and replay in the same relative order. A session operator created at an inner level that commits and is then rolled back with the outer level is undone by the same sequence.
- *The session object path really is order-independent, as the handoff claims.* `Engine.DropSessionObject` matches on the entry's own `GlobalName`, and the compiler mints a fresh guid for every `create session table` and `create session view`, so no two session objects ever share an entry. Checked the one shape that could have broken it — create, drop and re-create a session table of the same name in one transaction, then roll back — and the backwards replay removes the second entry before the undo of the drop re-adds the first, so the unconditional `Schema.Objects.Add` in `CreateSessionObject` never meets a duplicate.
- *There is no second path to fix.* `CatalogDeviceSession.CreateOperator` has exactly one caller, `CreateOperatorNode.InternalExecute`.
- *The "`InsertCatalogObject` throws" gap the handoff flagged is correctly judged not worth guarding.* `ServerProcess.cs:1235` records that every D4 statement runs inside an implicit transaction, so in normal operation the `CreateSessionOperatorInstruction` is always recorded and a failing insert is undone. The only uncovered case is a loading context, where no instruction is recorded either way and a failing catalog insert aborts the load before anything can observe the entry. Agreed; no `try`/`catch` added, and the order was not reverted.
- *Concurrency is not made worse.* `SessionOperators` is private to one session and read only by that session's own plans and its disconnect, so moving the entry's insertion earlier does not widen any window another session can see. Within one session the previous order had the mirror-image window: the operator in the catalog with no alias to reach it by.

No other file under `docs/` mentions session operators, `DropSessionOperator` or the DDL instruction log (checked by grep), so nothing else was out of date. `docs/architecture.md` does not describe the undo log. The review's comment-only addition to `ServerSession.cs` owes no migration note: no application, script or extension can notice it.
- *Source hygiene at byte level.* Tabs, CRLF and byte-order-mark state unchanged in all three source files (all three carry a byte-order mark), no lone LF anywhere. `CatalogDeviceSession.cs` is 4,211 lines, of which this ticket added 5; its size predates the ticket by a wide margin and splitting it is not this ticket's business. The new comment in `CreateOperator` is five lines for a two-statement reorder and earns them: it states an invariant that nothing in the code expresses.
