## What landed

The one case of the test plan's layer 4 that needs two child processes, the two additive product members that make it reachable, and a second mode on the suite's own test program.

`tests/DAE.Server.Tests/AbandonedClientProcessTest.AKilledClientProcessIsReclaimedAndTheServerKeepsServing` starts a child server whose connection idle threshold is five seconds and a child client that connects with the shipped client stack, opens a transaction, creates a table in it, reports which server session holds it and then blocks for ever. The case kills that client outright — with its keep-alive thread still pinging, which is a crashed process rather than a connection that was never pinged — and then watches, through an observing client of the same server, the killed session go and the server go on answering both that older connection and a new one. The rollback, the catalog store's write lock and what a call on the reclaimed process sees are deliberately not repeated: `AbandonedSessionCleanupTest` asserts all three in process, at the lowest layer that shows them.

The product gained `DataphorServiceHost.ConnectionIdleTimeInSeconds` (settable while inactive, default the product's five minutes) and `DataphorService(RemoteServer, int)`, which the existing one-argument constructor now delegates to with that same default. Both are additive; `ConnectionManager` is untouched, and its own note already said that a shorter threshold belongs on a constructor argument rather than in an operator's instance list, which is why this is a host-object property beside `HostName` and `LoggingEnabled` and not a `ServerConfiguration` setting. `tests/TestHarness` gained `--idle-seconds` on its `serve` mode and a whole `client` mode, and `OutOfProcessInstance` gained a constructor taking the threshold plus the nested helper that starts, waits for, diagnoses and kills the client child.

**What was measured rather than assumed: the idle watcher is the only thing that reclaims an abandoned connection.** Against a child server left at the shipped 300-second threshold the killed client's session was still on the server 25 seconds after the kill, so neither CoreWCF nor Kestrel notices the socket a dead process leaves behind in a way that reaches the connection. At a five-second threshold the session went 4.7 to 5.1 seconds after the kill. That is recorded in the plan's *Reclaiming an abandoned session* section, in `docs/architecture.md`, and in the fixture's own remarks. It also means there is no slower, more realistic clock available: a case that waits for this at all has to shorten the threshold.

## Review findings

### Fixed in this pass

- **`AGENTS.md` described a program that no longer exists.** Its *Out-of-process client/server tests* paragraph said the harness "sets the two host-object properties that are not instance settings" — there are three now — and said nothing about the `client` mode, the `HOLDING` line, or the second fixture that starts child processes. Rewritten: both modes, the idle-seconds option and why the client mode has no stop path on its standard input.
- **`docs/architecture.md` stated the reclamation window as an invariant.** Its catalog-store section gave 300 to 375 seconds flatly; that is now the default only, since a host can set its own threshold. Added that, the one caller that does, and the fact that "the ping and nothing else holds a connection" is now a cross-process measurement rather than a reading of the code.
- **The plan's measurement sentence conflated two clocks.** It said the session went "4.9 to 5.1 seconds after the kill, inside the watcher's 5 to 6.25-second window". That window is measured from the connection's last *ping*, and the client pings every second, so from the kill the window is 4 to 6.25 seconds. The first review run measured **4.7 s**, below the stated window and perfectly correct — exactly the reading that would send a future maintainer hunting. Corrected in both places in the plan and in the fixture's remark on `IdleThresholdSeconds`.
- **The two child-process classes each carried their own copy of the output capture.** `OutOfProcessInstance` and its nested `HeldTransactionClient` had the same lock, the same two `StringBuilder`s, byte-identical `OnErrorDataReceived` bodies, the same null-guard in `OnOutputDataReceived` and the same `Diagnostic` format string differing only in the noun. Extracted as `OutOfProcessInstance.ChildOutput`, which both now hold; `test-client-server` adds more children to this file, and a third copy was the next thing to drift.
- **A silently tolerated failure could have let the case pass having shown something else.** `HeldTransactionClient.Kill` swallows `InvalidOperationException` so that teardown is safe on every path, and its comment already said that for this child an already-gone process "means it failed before it was killed" — but nothing could tell. A client that died on its own after printing its holding line also stops pinging, so its session is reclaimed exactly the same way and the case would still have gone green without ever having killed a live client. Added `HadAlreadyExited`, set from `Process.HasExited` immediately before the kill, and one assertion on it in the case.

### Checked and left alone

- **Compatibility.** Both new members are additive and both default to the 300 seconds the product has always served; no D4 surface, class name, file format, error code, WCF contract, port or on-disk layout is touched, and nothing was added to `ServerConfiguration`, the host command line or the environment. The migration-notes entry is present and accurate. `ConnectionManager`'s own `NOTE:` — no instance setting for the threshold, deliberately, with the revisit condition spelled out — is respected rather than re-opened, so no accepted tradeoff was overturned.
- **The new property is validated once, in `ConnectionManager`, not in the setter.** A value below one second therefore fails inside `Start()`, after the engine has started and been stopped again, rather than at the point of the mistake. Deliberate and documented at the site: the error does reach the caller (the harness child prints it on standard error, which `OutOfProcessInstance` reports), and a second floor in the setter is a floor that can drift from the real one. Left as written.
- **`ServerDefaultConnectionIdleTime = 0` as the "leave the product's threshold alone" sentinel** rather than a nullable. Documented at the constant and at the parameter, three call sites, and zero is not a value the option could legitimately carry. Not worth the churn.
- **The open question the handoff asked a reviewer to settle — the scalar count instead of a cursor over `System.Sessions` — was the right call.** The case's subject is reclamation, and a case that fails in a Debug build and passes in a Release build for a reason that has nothing to do with its subject is worth nobody's time. The defect itself is not buried: it is an arm on `tickets/plan/bug-object-id-counter-is-process-wide.md`, carrying the reproduction (eight table reads, one catalog change, one more read — one client, one engine, no second process), the colliding identifier, the Debug/Release asymmetry that explains why it has never been reported, and the two header fields it falsified; and the reason the case uses a count is recorded at `AbandonedClientProcessTest.SessionCount` so nobody simplifies it back. Re-verified that the arm sits on an open ticket whose `files:` now names both code sites. Nothing further to file.
- **Memory publication across the output-reader threads.** `_sessionID` is a plain write followed by the volatile write of `_holdingLine`, read in the opposite order — a correct release/acquire pair, and documented as one. Same shape for `_readyLine`.
- **Resource cleanup.** Every `Process` goes through a `using` in `Stop`/`Kill`; `Kill` is idempotent and is reached from `Dispose`, from the case and from the constructor's own failure path; the case's `using` nesting takes the client before the server and the temporary folder last. Confirmed empirically: no `DAE.Test.Harness` process survived the full suite run.
- **Timing margin.** Five seconds against a one-second ping leaves four pings of slack for the observing client, which is a client of the same server measured by the same clock; if that observer's own read ever fails, `SessionCount` reports the margin explicitly rather than surfacing an unexplained handle error. The 30-second wait for the reclamation is about five times the 6.25-second upper bound.
- **The short threshold reaches only the child that asks for it.** `--idle-seconds` is passed only when a caller gave a value, and `OutOfProcessProtocolTest`, `HostProgramTest` and `CoreWcfProtocolTest` all run hosts that never set the property and are green, which a mistake in the default would have broken.
- **Error paths, read and not re-tested.** A child that prints `READY` and then exits, one that never prints it, a client that exits before `HOLDING`, a broken stop pipe, a child that will not stop when asked: each has its own message carrying everything the child said.
- **File size.** `OutOfProcessInstance.cs` is 670 lines after this pass (up 23: the duplication is gone, the documentation of the shared helper and the new property more than replaced it). Within this project's norm for a test file — `CoreWcfProtocolTest.cs` is 754 and `StoreContractTests.cs` 688 — so not split. Moving `HeldTransactionClient` to a file of its own would also separate it from the harness command-line constants this file declares once, and a move is its own commit here in any case.

### Tests

**Nothing cut and no case added.** The one case covers one behaviour, nothing in it restates the implementation or verifies a mock, and the handoff is right that the new host property's default and the delegating `DataphorService` constructor need no tests of their own — a constant and a one-line delegation, covered by the compiler and by the three green fixtures that run at the default. The single assertion added above pins a precondition of the existing case rather than a new behaviour, and costs no runtime.

### Parked as a tripwire, not filed

- **The orphaned client child.** A test host killed outright between starting the client child and killing it leaves a `DAE.Test.Harness.exe` sleeping for ever, because the client mode has no end-of-input stop path — deliberately, since being killed is the only way it is meant to end. Already a `NOTE:` at the site in `tests/TestHarness/Program.cs` with the remedy and the reason it was not taken, and accepted as recorded: the ticket runner's kill is a tree kill, so reaching this needs a non-tree kill of the test host, and the `HadAlreadyExited` assertion added above closes the "would pass for the wrong reason" half of the same note's worry. Left as the author wrote it.

### Nothing in these categories

- **No major findings and no new tickets.** The one real defect this ticket met was already filed, at the right site, on an open ticket, with its reproduction — there was nothing left to raise. No finding in the product change rose above documentation accuracy, which is what an additive property delegating to a constructor that already took the value should look like.
- **No conditional concerns of my own to park.** The one that exists is the author's, above.
