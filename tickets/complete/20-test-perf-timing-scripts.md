## What landed

**The missing operator, in a test-only D4 library.** `tests/libraries/TestFramework.Perf/` is two text files and no C# project: a `.d4l` descriptor requiring only `System`, and a `Documents/Register.d4` that binds `BenchmarkExecute(const AString : String) : TimeSpan` to the engine node `System.SystemBenchmarkExecuteNode`, which has always been there and needed no change. It carries the determinism tag set the engine's own `Execute` operator carries, because with `IsLiteral` left at its default the compiler may evaluate a benchmark while compiling it and the deterministic and repeatable flags invite the plan cache to hand one measurement back for several calls. The library joins the runtime layout through the existing `tests/libraries/*/*.d4l` glob in `tools/layout/Layout.csproj` with no edit to that file, and is registered only by the two consumers that name it.

That `Register.d4` also runs `alter device System.Temp alter class { alter "MaxRowCount" = "-1" };`. Without it `Timings` fails at its 1,001st row: the engine's in-memory device caps a table at 1,000 rows (`Engine.TempDeviceMaxRowCount`, error 114113) and the script inserts 10,000. The script's own recorded numbers are for 10,000 rows, so it ran with the cap lifted; coverage scripts are never edited, so the lift went into the new library, as `TestFramework.Coverage.Devices` already does in its own `Register.d4`.

**The perf pass.** `tests/DAE.Server.Tests/PerfBaselineTest.cs`, one fixture over `InProcessTestFixture` and one test method looping a scenario table, in the shape of `FrontendDerivationGoldenTest`. It reads each script's text from its own server's copy of `TestFramework.Coverage.Scripts` and runs it through `IServerProcess.PrepareScript` batch by batch: a statement batch is timed with a `Stopwatch`, and an expression batch whose value is a `TimeSpan` is recorded by its value rather than by the wall clock around it. Three behaviours, by two environment variables: record and pass by default (writing `artifacts/perf/perf-run.json`), compare when `DATAPHOR_PERF_BASELINE=<label>` names a label (warn past 3×, fail past 10×), and rewrite that label's entry and then fail when `DATAPHOR_UPDATE_PERF_BASELINE=1` joins it. The comparison itself is a pure static method taking the numbers, the whole baseline file, the label and the two factors.

**The baseline and the documents.** `tests/goldens/perf/perf-baseline.json` carries one label, `dev-slow`, with `Timing` at 16,144 ms. `docs/perf-baseline.md` is new, modelled on `docs/coverage-report.md`, with the numbers, what they do not mean, how to regenerate and compare, the reasoning behind the two factors, the `Timings` finding, and the 3.1 comparison as a written procedure with an empty results table. `docs/README.md` lists it, `AGENTS.md` records the two environment variables and a corrected, honest account of what the three suite parts cost, and `docs/modernization-plan.md` records what half of the `test-perf-baseline` work item this was (added at review; see below).

## What did NOT land, and why

`Timings` is not a baseline scenario and is not a passing coverage case. Running the script for the first time - which nothing had ever done, because the operator did not exist - showed that three of its four blocks are fast and the third does not finish. Its third block drains a 10,000-row table one row at a time with `while exists (T) do delete T return 1 by { ID };`, and the cost of that statement grows with the number of rows in the table, so the loop is quadratic: 397 / 1,885 / 7,866 / 34,308 / 150,879 ms at 250 / 500 / 1,000 / 2,000 / 4,000 rows, about 4.4 times per doubling, so about a quarter of an hour at the script's 10,000 rows against the 8 seconds the script's own 2008 comments record. Blocks 1 and 2 took 431 ms and 1,461 ms against the roughly 5 s and 9.5 s those comments record - several times *faster* - so the drain is a genuine outlier and not a Debug-build or slow-machine artefact.

The manifest entry for `Timings` is therefore a `known-failure` against `bug-engine-delete-quota-scans-the-table` with the error `HarnessTimeout: script did not finish within` and `timeoutSeconds: 15` - short on purpose, so the suite does not pay for the grind. The known-failure count across the suite is unchanged at 21: `Timings` was already one, and its cause has moved from "nothing declares the operator" to the measured one. `PerfBaselineTest`'s scenario table has one row, with a remark saying that adding `Timings` back is one line once the defect is fixed.

So the plan's requirement that "the existing `Timing`/`Timings` scripts ... record a baseline on .NET 10" is half met, and the other half is gated on `bug-engine-delete-quota-scans-the-table`. The benchmark-project half of the same plan row is `test-perf-baseline`, which keeps that slug and is in `implement/`.

## Review findings

The implement diff was read first, independently of the handoff. Everything below was run on 2026-11-22 in Debug on the same slow development laptop the baseline was recorded on.

### What was checked

- **Build.** `dotnet build Dataphor.slnx`: 0 errors, 143 warnings - the count `port-server-on-net10` recorded, so the new file and the new library add none.
- **The whole suite, in the three parts the root `AGENTS.md` prescribes, each as its own foreground run.** All green: part 1 **577 passed, 0 failed** (5 m 19 s), part 2 **67 passed, 11 skipped** (3 m 13 s), part 3 **49 passed, 13 skipped** (3 m 31 s). 693 passed, 0 failed, 24 skipped, which is exactly the manifest's 21 known failures and 3 fragments. These three runs each beat the best-of-several figures `AGENTS.md` now records; that document was deliberately left alone, because replacing a best-of-several figure with one faster run is the thing its own "do not read one measurement as the part's cost" paragraph warns against.
- **Every behaviour the handoff asked to be poked at, run by hand.** The record-and-pass default (13,854 ms and 15,799 ms on two runs, passing both times). The labelled comparison against `dev-slow` (14,889 ms, passed). An unknown label (failed, naming the command that would record one, rather than passing quietly). The update variable with no label (failed, saying the label is required). The full update path: it rewrote only `Timing`'s number, kept the hand-written `note` verbatim, left the file LF with no byte-order mark, disturbed no other field or label, and failed with a message saying an update always fails - restored afterwards from a copy taken before the run, not with git. And the two coverage cases: `Timing` passed in 16 s, `Timings` skipped reading `known-failure (bug-engine-delete-quota-scans-the-table): HarnessTimeout: script did not finish within 15 s`, which also confirms the operator now resolves - a script that still could not compile would fail with a resolution error, not a timeout.
- **The docs link checker** over `docs/`: 203 errors, 0 of them in `perf-baseline.md` - unchanged, and all pre-existing and owned by the documentation conversion.
- **The engine claims the design rests on, read in source rather than taken on trust.** `MemoryDevice` guards its cap with `MaxRowCount >= 0`, so `-1` is unlimited and the engine's own error 114113 text recommends exactly the statement `Register.d4` uses. `LibraryUtility.RegisterLibrary` leaves the newly registered library current *on the registering session*, which is why the fixture's explicit `SetLibrary` is needed at all - `InProcessTestFixture` registers on the instance's session and tests run on another. `SystemBenchmarkExecuteNode` returns a native `TimeSpan`, so `AsNative as TimeSpan?` is the right read. `ServerBatch.IsExpression()` is a type test, so calling it twice per batch costs nothing.
- **Resource cleanup on every path**: the script unprepared in a `finally`, each plan unprepared in a `finally`, the evaluated value disposed, a table-valued plan opened and closed. Nothing leaks on the failure path, and a batch that raises stops the whole pass rather than leaving a later scenario to measure a dirty catalog, which is the right call and is explained at the site.
- **Source hygiene.** `PerfBaselineTest.cs` is 586 lines, inside the band of the fixtures beside it (754, 715, 688, 611), so there is no size debt to split. Tabs, CRLF and the byte-order mark were preserved in both files edited at review. The comments in the new code say why rather than narrating statements.

### Fixed in this pass

- **The baseline schema check only guarded the comparing path.** `Update` reached `ReadBaseline` without it, so an update run against a file of a later schema would have rewritten it as schema 1 and silently discarded whatever that shape carried - while the reader's own comment claimed that "a reader that meets another version says so rather than guessing". The check moved into `ReadBaseline`, where both paths get it, and the duplicate left the test method: four lines shorter and one hole smaller. Latent only, since schema 1 is the only shape there has ever been.
- **`docs/modernization-plan.md` still named the wrong owner for `Timings`.** Its WS2 audit line said that residual known failure was owned by `test-perf-baseline`; the manifest entry this change rewrote moved it to `bug-engine-delete-quota-scans-the-table`. The line now says so, with a clause recording that it read differently when the audit was taken. The `test-perf-baseline` work-item row in the WS3 table was also annotated with what landed and what keeps the slug, which is that table's convention for a work item delivered in parts and the one document the change should have touched and did not.

### Tripwire parked

- **No wall-clock cap on a scenario, and a line is printed only when a batch *ends*.** Harmless while every batch is seconds, but a batch that runs away prints nothing for its whole duration, and the ticket runner kills a command that is silent for ten minutes - which is how the `Timings` problem was found in the first place. `NOTE:` on `Measure` saying to give the loop a timeout of its own, the way a coverage entry has `timeoutSeconds`, if a scenario is ever added that can legitimately run for minutes.

### Tickets filed

**None.** Nothing found reached the filing bar: the one latent defect was four lines to fix here, the one conditional concern is a tripwire, and the substantive defect this work uncovered already has its own ticket (`bug-engine-delete-quota-scans-the-table`, which a concurrent board move promoted from `backlog/` to `fix/` while this review ran, and which was left where it was put).

### Considered and declined

- **The server-wide device setting in a library registration**, which the handoff flagged for a reviewer's judgement. The manifest has a `preamble` field that exists for exactly this and would scope the lift to the one case. Declined: the repository already carries the same pattern in `TestFramework.Coverage.Devices`'s `Register.d4`, the blast radius is the two servers that register this library and both want the lift, and the `preamble` route would duplicate the statement in two places once `Timings` is also a perf scenario. The comment at the site says what it does, why it is there and who it reaches.
- **The unreached `Schema.TableType` branch in `ExecuteBatch`**, which the handoff offered for deletion. Kept: five documented lines that turn an obscure future failure - `Evaluate` on a table-valued plan - into an open-and-close, against a reader's mild surprise at a branch no scenario reaches.
- **`Timing` running twice per suite.** The site carries an accepted-tradeoff `NOTE:` that weighs both alternatives and names a revisit condition (if the scenario table grows enough that the duplication is minutes rather than seconds). The call is already made and that condition has not tripped.
- **Two fixtures in one file**, `PerfComparisonTest` beside `PerfBaselineTest`. They are a pure method and its only test, and the file is in band.

### The escalation the ticket asked for, and the decision not to take it

The implement ticket said to file the `Timings` cost question to `blocked/` if the script took more than 240 s, and the implementer routed a measured defect to the backlog instead, explicitly inviting the reviewer to overrule that. **Not overruled.** The rule assumed the time was real work and that the cost was the question; the measurements say otherwise - three of four blocks total under two seconds, the fourth is quadratic where it was linear in 2008, and the suite pays a bounded 15 s whichever way the question is answered. `blocked/` is for a decision a human has to take, and there is none here. The backlog ticket carries the curve, four controls that rule out the order clause, per-row deletion, the device, the transaction and the quota expression itself, a named code site as the lead, and an explicit line separating what was measured from what was inferred.

### Tests

Neither test was cut and none was added. `ComparingTellsTheBandsApart` pins the band policy on logic with real branching, at the lowest layer that shows it, with factors of its own rather than the pass's, and mocks nothing the repository owns. `TheTimingScriptsRunAndTheirNumbersMatchTheBaseline` is the characterization this project's testing rule asks of a ticket that re-hosts a subsystem's behaviour. No defect was found that lacked a test: the one latent defect fixed above is a dormant branch of a file-format reader for a format with one version, where a test would cost more than it holds. The four environment-variable paths and the update's diff were exercised by hand rather than automated, because each depends on machine state the suite deliberately does not gate on, and they are better as the documented procedure in `docs/perf-baseline.md` than as cases.

### Not re-verified

The 250-to-4,000-row drain curve and the four controls behind `bug-engine-delete-quota-scans-the-table`. Reproducing them costs about four minutes of engine time, and they are that ticket's evidence rather than this change's behaviour; what this change owns is the `Timings` case failing in its recorded way inside its 15 s timeout, and that was run.
