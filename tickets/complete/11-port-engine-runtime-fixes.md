# Complete: engine runtime fixes (K2, K5 engine sites, K22, K28 found here, NLS pin)

Implement-stage handoff below, followed by the review pass. Everything was built and run.

## What changed

**K2, operator source text** (`SourceUtility.CopySection`). The end of a section is now counted from the start of its first line, not from its start column. Before, a section that began and ended on one line overshot by its start column: a one-line operator at the end of a script raised "Index and length must refer to a location within the string" (reported as an internal compiler error), and one followed by more text was stored, and returned by `Script()`, with that text appended. Confirmed before the fix: the end-of-script case raised exactly that (`OperatorSourceText@16`), and the mid-script case stored `create operator K2Mid() : Integer bbegin result := 2; end; create table K2After { ID : Integ`.

**K28, new, met along the way** (`Statement.SetEndPosition`, `Lexer`). Fixing K2 broke the system catalog: the stored text of the `Concat` aggregates ended in `"System.EmptyFinalizationNod`, and every script that used `Concat` after a catalog reload failed ("Errors occurred while attempting to deserialize catalog object id (3707)", seen in `Globalization`). Cause: `SetEndPosition` set a statement's end to the last token's start plus the length of its *value*, and a string token's value has no quotes, so a section ending in a string (`finalization class "…"`) ended two characters early. K2's overshoot equalled the system catalog's two-tab indentation and hid it. The tokenizer now records the position just after each token (`Tokenizer.EndLine`/`EndLinePos`, copied to `LexerToken`), and `SetEndPosition` uses it. `PlanNode.SetLineInfo` and `OperatorBlock.SetLineInfo` already treat `EndLinePos` as an absolute column of `EndLine`, which is what both fixes assume. Other consumers of end positions (checked): the debugger's "after node" location (`Program.GetLocation`, `Debugger` call stack), which now lands after a closing quote instead of two columns before it. Logged as K28 in the plan; a local fix, so done here rather than ticketed.

**K5, `Delegate.BeginInvoke`** (`SystemNodes.cs`). A new internal helper `AsyncExecution.Start(Action)` runs the work with `Task.Factory.StartNew(…, TaskCreationOptions.LongRunning, TaskScheduler.Default)` (a dedicated thread: scripts may sleep or sit paused in the debugger) and swallows any exception inside the task body, so nothing reaches the thread and nothing is left for `UnobservedTaskException`. I chose `LongRunning` over `Task.Run` for that reason.
- `ExecuteAsync`: the worker runs `Execute` and then, in a `finally`, the old cleanup (unprepare, stop the process if the operator started it).
- `ExecuteWithTimeout`: still sleeps the full timeout and then checks `Task.IsCompleted`; a script that raises counts as finished and the operator returns normally, as before. `_done`/`_script` are now locals.
- `ExecuteMultiple`: `Task.WaitAll` replaces the busy-wait on a non-volatile flag; `_doneList`/`_done` are gone. Zero sessions used to hang forever and now returns at once (no test).
- `NOTE:`s at each site: errors deliberately not returned (changing it is a D4 semantics change), the fixed-length wait, unpreparing after a timeout (it waits for the statement in progress, since the process is held one statement at a time; later statements of that script then meet a disposed script), and that the no-process-ID form of `ExecuteWithTimeout` starts a process it never stops (old behaviour, kept).

**K22** (`PathUtility`). `GetBinDirectory` returns `AppContext.BaseDirectory`; the `RelativeSearchPath` branch is gone; `GetInstallationDirectory` reads `AppContext.BaseDirectory` too. No failure to reproduce: on .NET 10 the old branch never ran.

**Harness fix** (`CoverageScripts.RunInProcess`). A manifest `preamble` of `SetUseImplicitTransactions(false);` ran inside its own call's implicit transaction, and the engine never ends that transaction once implicit transactions are off, so the whole script ran inside it (`TransactionCount()` was 1) and tables it created were invisible to other sessions and processes. The harness now commits whatever transaction the preamble leaves open; `CoverageManifest`'s format comment says so. `SecurityLibrary`, the other script with that preamble, is still a known failure on its earlier, unrelated error.

**Dead `using` inventory** (no edits, as the ticket expected). Searched `src`, `libraries` and `tests` for `using System.Runtime.Remoting`, `System.EnterpriseServices`, `System.Configuration.Install` and `System.Data.SqlServerCe`, and checked each hit against the project compile lists. Engine, server, protocol and store: only `DAE/Runtime.Instructions/GeneratorNodes.cs` (not compiled, a stray) and `protocol/Client/Server/ServerFactory.cs` (compiled, but its whole content is a block comment). The `SecurityNodes.cs`, `RemoteServer*`, `ServerDTCTransaction` and `FileStreamProvider` ones are gone. Outside that scope: `libraries/Frontend/Source/Application.cs` (not compiled); `src/client/DAE.Client/DataphorConnectionFactory.cs` (`System.Runtime.Remoting`, compiled by the legacy `DAE.Client.csproj`, WS6); `src/hosts/DAEService/{Service,ServiceInstaller,ServiceUtility}.cs` (`System.Configuration.Install`, legacy `DAE.Service.csproj`, already in the plan for WS5).

## Found, filed

- **K29, `bug-memory-device-concurrent-access` (backlog, repro verified).** The memory device does no locking: sessions writing one shared memory table at the same moment race in its index. My first `AsyncExecution` (three sessions inserting into one table) lost a row in about 1 of 4 runs, with a `NullReferenceException` in `NativeRowTree.Compare` during key validation (captured by temporarily logging the swallowed errors). Same in 3.1. The committed script gives each session its own table, chosen by `SessionID() mod 3` (session IDs come from an interlocked counter, and `ExecuteMultiple` connects its sessions one after another). Second arm in the same ticket, static: the catalog device enumerates server session and process lists without a lock.

## Known gaps and judgment calls for the reviewer

- **The lexer change is broader than the ticket.** It changes `EndLinePos` (and `EndLine` for strings spanning lines) for every statement or expression whose last token is a string literal, in the D4 parser and the SQL parsers that share `Statement`. The full suite is green; the consumers I found are listed above. Migration-notes entry added (parser positions; new `LexerToken`/`Tokenizer` members).
- **Migration notes**: added an entry for K2 as well (the exact source text now stored and returned by `Script()`), which the ticket did not foresee; none for K5, as the ticket said.
- **`AsyncExecution` timing**: the `ExecuteAsync` case sleeps 1 s before it reads `Processes`, because neither the memory table nor the server's process list is safe to read while the worker changes them (K29). A machine slow enough that the worker is still running after 1 s would poll `Processes` concurrently; I have not seen it.
- **`CompareText` and NLS**: `CompareText` is `OrdinalIgnoreCase`, and the probe showed NLS and ICU disagree for letters added to Unicode lately (Georgian U+10D0 vs U+1C90 equal under ICU, not under NLS). Not pinned: the NLS answer comes from Windows' own casing table and may differ between Windows versions, and it may not match what .NET Framework did either. The plan's Globalization note says so.
- **`ExecuteWithTimeout` without a process ID** leaks a process per call until the session ends (old behaviour, `NOTE:` at the site). Not filed; whether it deserves a ticket is your call.
- **Plan and docs**: K2, K5 and K22 rows now say fixed; K28 and K29 rows added; the WS2 current state and the BeginInvoke and Globalization design notes are updated.

**Correctness, checked.**
- K2 (`CopySection`): the end is now counted from the start of the section's first line, which matches how `PlanNode.SetLineInfo` and `Operator` treat `EndLinePos` (an absolute column of `EndLine`). The declaration section (start to the block's start) and the aggregate's initialization and aggregation sections use the same rule and stay correct. No issue.
- K28 (tokenizer end position): `_line`/`_linePos` after the last `Advance` are those of the next character, so the recorded end is one past the token in every branch. The look-ahead buffer copies the end into each `LexerToken`, so `SetEndPosition` reads the end of the current token, not of a look-ahead one. Consumers checked: `CopySection`, the compiler's source-context offsets, `Program.GetLocation` and the debugger's after-node location. **Found (minor, fixed):** the change is wider than the handoff and migration note said: the old end also fell short for numeric literals whose value omits a prefix or suffix (`0x` hexadecimal, `$` money, the `d`/`f` suffixes).
