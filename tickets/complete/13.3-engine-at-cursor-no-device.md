## What was wrong

When a process is joined to an application transaction (AT), each table node in a statement carries a *populate node*: the same expression compiled against the real tables, which runs before the node executes and copies the real rows into the AT's copy of the table. `TableNode.DeterminePotentialDevice` ran device determination on the populate node, but `BaseTableVarNode` and `OnNode` overrode that method without calling base, so for a bare table reference (`select Test;`, `cursor(Test …)`) the populate node's inner `BaseTableVarNode` had no potential device, was flagged `NoDevice`, and threw 104137 ("Device "<no device>" does not support retrieval…") when it ran. A restricted read (`Test where ID = 1`) worked because the outer `RestrictNode` inherits the `TableNode` method. This was a defect in 3.1 as shipped (commit 423f8bc7), not a porting defect.

## What changed

- `TableNode.DeterminePotentialDevice` is now `sealed override`. It calls a new `protected virtual void InternalDeterminePotentialDevice(Plan plan)` (default: `base.DeterminePotentialDevice(plan)`, i.e. `PlanNode`'s child-device logic) and then always runs `_populateNode.DeterminePotentialDevice(plan)`. A short comment above it says why it is sealed.
- `BaseTableVarNode` and `OnNode` (`TableNodes.cs`) override `InternalDeterminePotentialDevice` instead; their bodies are unchanged. Within the repository these were the only table-node overrides (`grep -rln "override void DeterminePotentialDevice" --include=*.cs src libraries samples tests` now lists `DDLNodes.cs`, which is not a table node, and `TableNode.cs`).
- `coverage-manifest.json`: `ApplicationTransactions` stays `known-failure`, re-pointed to `engine-at-leave-rolls-back-open-work` with error `Application Transaction read is not repeatable` (the script now gets past line 20 and fails at line 41 on that separate cause).
- `docs/migration-notes.md`: a `done` row under "D4, catalog and libraries" (bare-name reads inside a joined AT no longer raise 104137), and a `done` row under "Custom C# extensions" (the method is sealed; a custom `TableNode` subclass renames its override to `InternalDeterminePotentialDevice` and its `base.` call to `base.InternalDeterminePotentialDevice`).

Both edited `.cs` files keep CRLF and no byte-order mark (the fix ticket said `TableNodes.cs` had one; it does not, and still does not).

## Review findings

Reviewed the diff of `ticket(implement): engine-at-cursor-no-device` before the handoff, then read the surrounding code (`TableNode.PrepareJoinApplicationTransaction`, `InternalBeforeExecute`, `BindingTraversal`, `PlanNode.DeterminePotentialDevice`, the `InferPopulateNode` overrides in `OrderNodes.cs`, the callers in `Compiler.cs` and `CursorNodes.cs`).

- **Correctness of the fix.** Confirmed: before the change `BaseTableVarNode` and `OnNode` replaced `TableNode.DeterminePotentialDevice` without calling it, so a bare table reference's populate node never had its potential device set. Sealing the method and moving the two overrides to `InternalDeterminePotentialDevice` (bodies unchanged) makes the populate-node pass unconditional for every table node. No issue found.
- **Other overrides.** `grep -rn DeterminePotentialDevice --include=*.cs src libraries samples tests`: the only remaining overrides are in `DDLNodes.cs` (`CreateTableNode`, `DropTableNode` and one other DDL node, none of them `TableNode` subclasses). `SQLDevice.cs:2025` only calls it on an alter-table node. Nothing else in the repository is affected by the seal.
- **Repeated determination.** An `OrderNode`/browse node takes its source's populate node through `InferPopulateNode`, so the same populate node now has its potential device determined twice (once through the child, once through the outer node), and `Compiler.cs` already re-runs `DeterminePotentialDevice` after `InferPopulateNode`. The method only sets `_potentialDevice`/`NoDevice` from the table variable and children; it starts no device and allocates nothing, so a repeat is harmless. No change.
- **Global context.** `BindingTraversal` pushes the global context around the populate-node pass; `DeterminePotentialDevice` does not. `BaseTableVarNode`'s body reads only its table variable (and the current statement for an error), so no context is needed. Agree with leaving it; no tripwire, since nothing here depends on context.
- **Compatibility surface.** The seal breaks compilation of a custom C# `TableNode` subclass that overrides `DeterminePotentialDevice`; the migration note under "Custom C# extensions" states the rename and the `base.` call change. The D4 note under "D4, catalog and libraries" is accurate: error 104137 is `RuntimeException.Codes.NoSupportingDevice` (`RuntimeException.cs:131`). No D4 semantics, class names, or error codes changed.
- **Tests.** No new test, and none needed: the reproduction is the `ApplicationTransactions` coverage script, whose cursor on a bare table at line 20 is the failing case. Its manifest entry is now `known-failure` on `engine-at-leave-rolls-back-open-work` with the line-41 text, so a regression (104137 at line 20) would fail the run. The fix stage also recorded that the whole script passes batch by batch with this fix, which is the strongest evidence the change is complete. The bare `select T;` form goes through the same `BaseTableVarNode` populate path and is not covered separately; not worth a test on its own.
