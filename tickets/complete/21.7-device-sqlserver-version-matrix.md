## What landed

A measurement, not a feature. Decision Q12 already said SQL Server 2022 is the supported minimum and 2019 is documented as working if it needs no extra code; nobody had run the product against any version on .NET 10. This pointed the suite's live SQL Server passes at one version after another and wrote down what happened.

**Four servers reached, all four pass.** Each run is the live set: the three transaction-atomicity coverage scripts, the fifteen catalog-store contract cases, the six text-parameter cases, the three new version cases, `LiveDeviceTest`, plus the two passes that need no server but share the variable (`MSSQLStoreConnectionStringTest`, `StoreRebuildWorkflowTest`). About a minute per server.

| SQL Server | Hosting | Version reported | Collation | Result |
|---|---|---|---|---|
| 2022 | Linux container, SQL login, port 14220 | 16.0.4325.4, Developer | `SQL_Latin1_General_CP1_CI_AS` | passes |
| 2019 | Linux container, SQL login, port 14190 | 15.0.4510.2, Developer | same | passes |
| 2019 | Windows LocalDB `ProjectModels`, integrated security | 15.0.4382.1, Express | same | passes |
| 2016 | Windows LocalDB `MSSQLLocalDB`, integrated security | 13.0.4001.0, Express | same | passes, and is below the supported minimum, so that is information rather than a promise |

Review re-measured 2016 LocalDB and the 2019 and 2022 containers on the final build, so three of the four rows stand on the code as it shipped; only the 2019 LocalDB row stands on the implement stage's earlier run, and it is the same product version as the container row beside it.

**2025 was not reached.** Microsoft's 2025 Linux images pull fine and the server process then stops at startup with a fatal error before accepting any connection - tried `2025-latest` (Ubuntu 24.04) and `2025-CU11-ubuntu-22.04`, as `mssql` and as root. The host is Docker 24.0.6 on WSL2, kernel 5.10.102.1, on an Intel Xeon E3-1505M v6 (AVX2, no AVX-512); 2019 and 2022 start on the same host, so the 2025 image wants something this host has not got. Nothing about Dataphor was learned either way and 2025 stays unmeasured; the honest hole is recorded in the user's guide, the plan row and Q12. What would close it: a Docker host on a newer kernel, or a SQL Server 2025 instance on Windows.

**2017 was not reached.** A full instance is installed on the measuring machine but stopped and set to manual start, and starting a Windows service needs elevation the run did not have. It sits between 2016 and 2019, both of which pass.

**The encryption question `device-mssql-port` and `test-device-live` both left open is closed.** A container with a self-signed certificate is exactly the server neither could find. Measured on 2019 and 2022, with the connection string the fixtures use verbatim:

| In the connection string | 2019 | 2022 |
|---|---|---|
| nothing about encryption | fails: *the certificate chain was issued by an authority that is not trusted* | same |
| `Encrypt=False` | connects | connects |
| `TrustServerCertificate=True` | connects | connects |
| `Encrypt=True;TrustServerCertificate=True` | connects | connects |
| `Encrypt=Strict` | fails before login (*unsupported version of SQL Server … wait operation timed out*) | fails before login (*connection forcibly closed*) |

And the device's own default carries it: with `TrustServerCertificate=True` in the variable (so the fixtures' own housekeeping connects) the device gets no `Encrypt` of its own, and it connected to the 2022 container through its builder's `Encrypt=False`. `Encrypt=Strict` carried onto the device still fails, as `test-device-live` measured on 2016.

**Confirmed on every version reached**: `DetermineVersion` parses `serverproperty('productversion')` correctly (the new case asserts the device's `MajorVersion` equals the server's), `IsMSSQL70` is false, `ShouldEnsureDatabase` creates an absent database (so the `sysdatabases` compatibility view still answers on 2022), and the server-side cursor path works - `sp_cursoropen`/`sp_cursorfetch`, driven by the text-parameter fixture's explicit server-side cases and by every device read whose statement begins with `select`.

**One behaviour recorded as behaviour, not a defect**: a reconciled table variable is named `Library.dbo.Table`, the SQL schema included, unless the device's `Schema` attribute names that schema.

## The new fixture

`tests/DAE.Server.Tests/MSSQLVersionMatrixTest.cs`, 3 cases, ignored with the rest where `DATAPHOR_TEST_MSSQL` is unset. It drops its database `DataphorVersionMatrix` first, so starting the device is what creates it; then it creates a table on the server through a connection of its own and runs `Reconcile`.

| Test | What it verifies |
|---|---|
| `TheDeviceReadsTheServerVersion` | the device determines the server's major version from `serverproperty('productversion')` and is not in SQL Server 7.0 mode - the first device statement against a server, and the one that fails on an unexpected version string. It also writes the version, edition and collation to the test's own output, so the TRX of any run records which server it was pointed at, which is how a CI run says what it tested |
| `TheDeviceCreatesTheDatabaseItIsGiven` | starting the device creates an absent database, which goes through the `sysdatabases` compatibility view |
| `ReconcilesAPreExistingSchema` | which columns of a table the device did not create reach the reconciled table variable, as which D4 type and length - the first live exercise of `ShouldIncludeColumn`, `FindScalarType` and the `sys.columns` query, and the characterization that pins both reconciliation defects below |

`ReconcilesAPreExistingSchema` pins two known-wrong behaviours deliberately, each naming its owning ticket in the `ExpectedColumns` remarks; a fix to either makes the case fail with a message saying so.

Nothing else was added. In particular: no test per SQL Server version (a test that can only run where one version is installed is worth less than a row in the matrix), no test for the `CreateDeviceUser` fix below (its oracle is a live server that needs a SQL login, which is the container run), and no test for the `RequiresAuthentication` setter (not fixed here).

## Defects found

**Two in the device, both on every version, both reachable by any deployment pointing a device at an existing schema:**

- `datetime2` and `datetimeoffset` columns are **dropped from the reconciled table variable with nothing said about it** - `ShouldIncludeColumn` has had both commented out since 2008 and `SQLDevice.GetDeviceTables` skips a column the filter rejects in silence. Filed as `bug-mssql-device-drops-datetime2-columns`, with the rung above it (any unknown type is dropped the same silent way) stated in the ticket rather than split off.
- An `nvarchar(30)` column reconciles with `Storage.Length` **60**, because `sys.columns.max_length` counts bytes. This was already an arm of `bug-mssql-device-text-columns-lose-characters` as a static reading; appended there as a fourth arm, now verified, with the consequence that arm lacked: the `LengthValid` constraint the engine compiles from that number admits strings the server will not store, so the rejection arrives from SQL Server on the write rather than from Dataphor on the edit. No new ticket - the site was already claimed.

**Two met along the way:**

- `TestEnvironment.MSSQLDeviceAttributes` emitted `"UserName"` and `"Password"` device attributes, and `MSSQLDevice` has no such properties - every run until now used integrated security, so nothing had tried it. The first container run failed with `Class "MSSQLDevice" does not contain a property named "UserName"`. **Fixed**: those attributes are gone and a `CreateDeviceUser('Admin', …)` statement takes their place, which is what the `NOTE:` at that site recommended for this day and keeps the password out of the stored device definition.
- `Schema.Device.RequiresAuthentication`'s setter ignores its argument (`set { _requiresAuthentication = false; }`), so the property can be turned off and never on. **Not fixed**: correcting it changes behaviour for any definition that sets it, which is a compatibility surface. Filed as `bug-device-requires-authentication-setter-ignores-value`, `repro: static`.

## Review findings

The implement diff was read before the handoff, then the claims in it were checked against the engine source and against three live servers.

**Fixed in this pass (three findings, all minor).**

- **An assertion that could not fail.** `TestEnvironment.QueryMSSQL` returned `Convert.ToString(cursor[0])`, and the cursor hands a null column back as `DBNull.Value`, which `Convert.ToString` turns into the empty string. So `databasepropertyex` of a database that does not exist came back as `""` rather than null, and `TheDeviceCreatesTheDatabaseItIsGiven`'s `Assert.That(_collation, Is.Not.Null)` would have passed for a device that never created its database - the one thing that case exists to catch. `QueryMSSQL` now asks `cursor.IsNull(0)` and returns null, which is what its own summary promised; the case can now fail. (`SQLCursor`'s header says a null column comes back as a null reference, but `DotNetCursor.InternalGetColumnValue` returns `IDataRecord.GetValue`, so every caller in the engine asks `IsNull` first. This helper was the one that did not.)
- **A comment asserting engine behaviour the engine does not have, and the ceremony around it.** `Reconcile()` wrapped its cursor in an explicit `BeginTransaction`/`CommitTransaction` with a rollback arm, on the stated grounds that the catalog writes "belong to the statement that opened the cursor, which closing the cursor would otherwise roll back". That is not what happens: `ServerProcess.BeginTransactionalCall` begins an implicit transaction for a call that finds none open and `EndTransactionalCall` *commits* it when the call returns, and the whole reconciliation runs inside the open call (`SystemReconcileNode.InternalExecute` does all of it, then returns the error list as a `LocalTable`). Checked by running the case with the explicit transaction removed, against SQL Server 2016 LocalDB: all three cases pass and the reconciled table variable is in the catalog. The transaction and its rollback arm are gone, which is also how a deployment reconciles - a `Reconcile('Device')` typed into a script has no transaction of its own - and the comment now says where the commit comes from. The likelier cause of the run the implement stage was debugging is the `Library.dbo.Table` naming it discovered in the same sitting.
- **Two facts in the plan row that did not match what was measured.** The row claimed "30 passed, 1 skipped, 46-58 s each" for all four servers, where the handoff's own table has two different counts and a wider spread, and it claimed CI's LocalDB "is 2016 on the runner image", where `AGENTS.md` says - correctly - that LocalDB stops at 2019 and which build a runner carries has never been read off one. Both corrected in `docs/modernization-plan.md`, and the row now records the review's re-measurement.

**Structure: the device definition and its device user are now one operation.** The defect fixed in implement was a device-definition detail that only a SQL-login run exercises, and the fix left three call sites each emitting the attributes and the device user as two separate calls, each repeating the `create device … class "MSSQLDevice.MSSQLDevice"` literal - so a fourth site could emit a definition with no device user, pass on integrated security, and fail only against a login, which is the same shape again. `TestEnvironment.MSSQLDeviceDefinition(deviceName, databaseName, reconciliationMode)` now returns the whole thing, `MSSQLDeviceAttributes` and `MSSQLDeviceUser` are private, and `LiveDeviceTest`, `CoverageScripts.LiveDevicePreamble` and the new fixture each pass their reconciliation mode and nothing else. The registered class name is spelled in one place.

**Checked and left alone, with the reason.**

- **The reflection in `TheDeviceReadsTheServerVersion`**, which the handoff asked to be weighed. Kept. The device assembly is loaded from the runtime layout, so this project cannot reference it, and `MajorVersion` has no D4-visible read-back - the nearest observable consequence is which catalog views the reconciliation query uses, which `ReconcilesAPreExistingSchema` already exercises without naming a version. The assertion compares the device's value with the server's own answer rather than with a literal, and the fixture fails with a message naming the property if it is ever renamed. The `IsMSSQL70` assertion beside it is derived from the same field and so cannot fail independently; one line, and it says what the case is for, so it stays.
- **Whether `TheDeviceCreatesTheDatabaseItIsGiven` earns its place**, also asked. Kept, and the first fix above is why: with the null handling corrected it is a real postcondition - the setup drops the database, so its existence afterwards is the device's `EnsureDatabase` path, which reads a compatibility view a later SQL Server could drop. That is a version question, which is this fixture's subject.
- **Whether `Reconcile`'s transaction behaviour belongs in `docs/architecture/catalog-and-store.md`**, also asked. No: there is no such behaviour to document, per the second fix above. The existing "Store transactions" bullet about catalog reads seeing only committed data is unrelated and already correct.
- **The honesty of the 2025 row**, also asked. Left as it stands. It claims a host limitation rather than a product one, and says so in those words, on the evidence that the process dies before any client connects and that two other versions start on the same host. The row also says plainly that 2025 is unmeasured, which is the claim that matters to a deployment.
- **The fixture drops its database with `set single_user with rollback immediate`**, which would disconnect another run's sessions on a shared server. The `NOTE:` at `TestEnvironment.EmptyMSSQLDatabase` already owns that class for the suite's fixed database names, and the fixture's own comment points at it; nothing added.
- **The user's guide page is 4,900 words.** The 1,500-word cap is `docs/architecture/` only, and `tools/docs-size-check/check_size.py` agrees (13 files, 0 over). Correct as placed.
- **The measurement date** is written as 26 November 2026 in the user's guide, the plan and the two new tickets, where the commit is dated the 25th in local time; the implement run crossed midnight UTC, so both spellings describe the same run and changing five files to pick one is churn. Left.
- **The handoff reports the build as "0 errors, 0 warnings"**, which is true of an incremental build and not of a clean one: `dotnet build Dataphor.slnx` from scratch reports 127 warnings, all pre-existing (`CA1416` in the OLE DB connection class, two obsolete-NUnit-API warnings in fixtures this ticket never touched). No warning comes from anything in this diff.

**Nothing filed, nothing blocked, no tripwire added.** The two device defects were already filed by implement, one of them onto an existing ticket's site rather than as a new one, and both sit above the filing bar. Everything the review itself found was minor and is fixed above; nothing turned out to be conditional, so there was nothing to park as a `NOTE:`.

## Repeating the measurement

`AGENTS.md` carries the `docker run` line and the filter, beside `DATAPHOR_TEST_MSSQL`. The containers `dataphor-mssql-2019` (port 14190) and `dataphor-mssql-2022` (port 14220) are left on the measuring machine, stopped, with their databases intact - `docker start dataphor-mssql-2022` brings one back in seconds; remove them when done (`docker rm -f`). The 2025 images pulled for this were removed already. `MSSQLLocalDB` is left running with the suite's `Dataphor*` databases on it, which is the state a local run expects.

One procedural gotcha, met twice and recorded as a tripwire rather than a ticket: the suite's database names are fixed, and every LocalDB instance puts a new database's files in the user's profile folder - so once one LocalDB instance holds `DataphorCoverageScripts`, a second instance cannot create it. Drop the suite's `Dataphor*` databases from the first instance before pointing the variable at a second one. A `NOTE:` at `TestEnvironment.EmptyMSSQLDatabase` beside the existing shared-name note, and a sentence in `AGENTS.md`; not fixed, because giving the create an explicit file path would move where a run leaves its evidence, which is what those fixed names are for.
