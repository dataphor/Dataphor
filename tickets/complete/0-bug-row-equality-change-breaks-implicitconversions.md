## What landed

An operator call can hand a value to an argument slot without copying it, if the plan node that produced the argument says it is only lending the value rather than giving it. The question is asked once, while the call is compiled. Three nodes in the engine rewrite their own argument nodes - wrapping one in an implicit conversion, for example - and all three used to ask *before* that rewrite, so the permission to lend was granted to a node that was no longer the argument. The conversion built over it ends in a node that destroys the row it is handed, so the row in the caller's variable was destroyed and the next read of that variable failed.

All three now ask last.

- **Implement stage** (`ticket(implement): bug-row-equality-change-breaks-implicitconversions`) - `RowEqualNode.DetermineDataType` and `CompoundScalarEqualNode.DetermineDataType` in `src/engine/DAE/Runtime.Instructions/RowComparisonNodes.cs` moved their `base.DetermineDataType(plan)` call from the top of the method to the bottom, with `_dataType` assigned after it. One test added, `RowEqualityWithAnImplicitConversionLeavesTheCallersRowsAlone` in `tests/DAE.Server.Tests/AssignmentValueOwnershipTest.cs`, verified by reverting the fix and watching it fail. A tripwire `NOTE:` on `RowExtendNode.InternalExecute` (`src/engine/DAE/Runtime.Instructions/RowNodes.cs`) recorded why the alternative fix - gating that node's unconditional release - was not taken. One sentence added to `docs/architecture/operand-ownership.md`.
- **Review stage** - found the same defect in `IfNilNode` (`src/engine/DAE/Runtime.Instructions/SystemNodes.cs`), reproduced it, and fixed it the same way; removed two redundant lines left in the implement diff; settled the one gap the handoff flagged by measurement; and corrected three pieces of documentation the change had falsified. Details below.

Nothing about the D4 language, an operator signature, a registered class name, a file format or a contract shape changed. A comparison, and `IfNil`, answer exactly what they always did; the difference is that a script that used to fail with an unhelpable error now runs.

## Review findings

The implement diff was read before the handoff summary. The engine was then surveyed for every other node of the same shape, two candidate defects were reproduced by running them, and one unmeasured claim in the handoff was settled by instrumenting the branch it was about.

### Found and fixed in this pass

- **`IfNilNode` had the same defect, and it was reachable from a plain D4 script.** `IfNilNode.DetermineDataType` called `base.DetermineDataType(plan)` first and then rewrote either argument node with a conversion - the identical shape to the two nodes the ticket fixed, and the handoff did not look for it. `IfNil` over two rows whose columns differ by a convertible type destroyed the row in the variable it was lent: a throwaway script comparing `row { N : Long }` with `row { N : Byte }` failed on the next read of that variable, with the same `NullReferenceException` in `ExtractColumnNode.InternalExecute` that the original bug produced. The `base` call now runs after the rewrite, as in the two comparison nodes, and the method's trailing `_dataType` assignment restores the data type `base` overwrites. Fixed here rather than filed, under the project rule for a defect with a local, obvious fix met along the way.

  One test added for it, `IfNilWithAnImplicitConversionLeavesTheCallersRowAlone`, beside the two existing `IfNil` ownership cases. It is a **verified reproduction**: with the `base` call put back at the top of the method and the engine rebuilt, it fails; with the fix, it passes. The nilable argument is left unassigned so that the side the conversion wraps is the one actually evaluated, and the row carries a `Binary` column so that `AssertScriptLeavesNoStreams` has a stream to count as well as a row to read.

- **The comment at `IfNilNode.InternalExecute` argued the opposite of the truth.** It said the early ask was "still correct" because a conversion computes a new value from the one it was lent and its own cleanup leaves the lent value alone. That holds for a scalar conversion, which is an operator call whose own const-operand cleanup honours the loan, and not for a row conversion, which `Compiler.ConvertRowNode` builds out of `RowExtendNode` through `EmitRedefineNode` - and that node releases the row it is handed unconditionally. Rewritten to say what is now true: the node asked is the node executed, because the rewrite happens first.

- **Two redundant lines in the implement diff.** Both new overrides opened with `DetermineModifiers(plan);` and then called `base.DetermineDataType(plan)`, whose own first statement is `DetermineModifiers(plan)`. The duplicate is harmless - the method reads two flags from `Modifiers`, defaulting each to its current value, so it is idempotent - and nothing between the two calls reads either flag (`IgnoreUnsupported` and `ShouldSupport` are read only during device determination, much later). It was a leftover from the shape the method had before the previous ticket, unexplained by the comment beside it, and is removed.

### Checked and sound

- **No fourth node of this shape.** Every `public override void DetermineDataType(Plan plan)` in `src/engine/DAE/Runtime.Instructions` was parsed and checked for an assignment to `Nodes[...]` after its `base.DetermineDataType` call. Exactly one hit outside the ticket's own two: `IfNilNode`, above. So the class is exhausted as of this commit.
- **The reordering is safe in both comparison nodes.** `base.DetermineDataType` only sets `_dataType` and mutates the argument nodes, and the rewrite block between the method's start and the `base` call reads `Nodes[0].DataType` and `Nodes[1].DataType` but never `this.DataType`, so nothing depends on a value `base` would have set earlier. `base` sets `_dataType` from `Operator.ReturnDataType` and the overrides overwrite it with `SystemBoolean` afterwards, which is why the assignment follows the call. The symbol-stack pushes inside the rewrite are all unwound by their own `finally` blocks before `base` runs.
- **The one behaviour the reordering does change is a pre-existing shape, not a new one.** The const branch of `base.DetermineDataType` unwraps a `ParameterNode` argument, which now happens after the rewrite rather than before, so a `ParameterNode` could in principle be left nested inside a conversion. That is the ordering the original engine had before `bug-row-equality-leaks-the-rows-it-compares` introduced the `base` call at the top, so the change restores it rather than introducing it; and the unwrapped node is asked nothing in that case, so the worst outcome is a copy, not a destroyed value.
- **Both halves of the previous ticket's fix are intact.** The ask still happens - a variable's row is still lent rather than copied, which is what `RowEqualityGivenVariablesLeavesTheCallersRowsAlone` reads - and `InternalExecute` still releases each argument whose node answers `ReturnsByReference` false, raise path included. `OperandOwnershipShapeTest`, which reflects every non-table instruction node overriding `InternalExecute(Program)` and compares the set with a checked-in list, passes unchanged: no override was added or removed.
- **`Compiler.Upcast` is a no-op in this build.** Its whole body is behind `#if USETYPEINHERITANCE`, which is defined nowhere, so every `Upcast` call in all three methods returns its argument node unchanged. `Compiler.ConvertNode` is the only rewrite that actually replaces a node, which is why the defect needs a conversion to appear.
- **The tripwire `NOTE:` on `RowExtendNode.InternalExecute` reads correctly cold** (the handoff asked for this to be confirmed). It names the condition under which the unconditional release is right, the ticket that found the case, and where to fix such a case instead. Two clauses were appended: that the case has now occurred twice, and that a third node of the shape is the point at which to weigh gating the release as well.
- **The handoff's factual correction to the fix ticket is right.** `Compiler.ConvertNode` is built over the very node that was asked to lend, so the destroyed row is the one on the side the conversion wraps, not the unconverted side. `RowEqualNode` tries `FindConversionPath` from the left type first, and the `Long` side of `ImplicitConversions.d4`'s row case is the left one, which is the side the fix ticket observed breaking.
- **Source hygiene.** No byte-order mark and CRLF in the three engine files, byte-order mark and CRLF in the test fixture and the two documentation pages, tab indentation throughout - all preserved, nothing reformatted or re-encoded. The scratch fixture and project entry used to run the throwaway probes were removed and the project file restored to its committed bytes.

### Settled by measurement

- **`CompoundScalarEqualNode`'s conversion branch is unreachable, so it needs no test** - the one gap the handoff left open. The branch was instrumented with a throw, the engine rebuilt, and a script that declares two compound scalar types with a widening conversion between them and compares a value of each was run: the throw was never hit, and the comparison answered equal with both values intact. The reason is in the declarations. The equality generated for a compound scalar type is declared over one concrete type, so operator resolution converts a differently-typed argument before the node is built and both operands arrive with one `Is` the other; `iEqual(const row, const row)` is declared over the *generic* row type, so resolution has nothing to convert and `RowEqualNode` does the per-column conversion itself - which is why only that node's branch is live. Recorded as a `NOTE:` at the branch, so the next reader does not reason from it as a live path. The move made there stands as defensive consistency with its sibling.

### Documentation corrected

- **`docs/architecture/operand-ownership.md`** said `IfNilNode` "missed the release half" of the rule. It missed both halves, in two tickets; the paragraph now says so and names where the order half was fixed. The page was at 1,498 words against its 1,500-word cap, so an equivalent amount was trimmed from two over-long sentences elsewhere on the page; it is now **1,494 words**, and `python tools/docs-size-check/check_size.py` reports 13 files checked, 0 over the limit.
- **`docs/migration-notes.md`** carries the obligation this rule puts on a custom C# extension that subclasses `InstructionNodeBase` and overrides `InternalExecute(Program)`. As written it said to reach `base.DetermineDataType` so each argument is asked to lend - which is exactly the instruction that produced this bug three times in the engine's own code. One sentence added: a node that rewrites its own argument nodes must reach `base.DetermineDataType` *after* the rewrite. No new entry: nothing an application, a deployment script or an extension can observe changed state, and the two existing entries' accounts of what the engine now does both remain true.

### Recorded, not filed

- **Gating `RowExtendNode`'s release on its source's `ReturnsByReference`.** A guard there, or at `Compiler.EmitRedefineNode`, would catch this whole class at plan-build time rather than as a destroyed row at run time, and the class recurring twice in two consecutive stages is a fair argument for it. It is not filed, because it is conditional by the review rules: both known instances are fixed, no live path now reaches that release over a lending node, and the concern only becomes work if a fourth node of the shape appears. The `NOTE:` at the site is where that is recorded, and it now says what would make it worth doing. The three row nodes that release their source unconditionally are `RowExtendNode`, `RowRedefineNode` and `RowRenameNode`, which are the `add` / `remove` / `rename` chain a row conversion is rewritten into; `RowRedefineNode` is already slated for deletion by `debt-unreachable-redefine-nodes` in `tickets/plan/`.
- **`AssignmentValueOwnershipTest.cs` is now 1,857 lines.** Its own `NOTE:` says it is past the roughly 1,500 lines at which it should be split along the three rules its summary names, and defers the split to whichever of two backlog tickets with cases in flight against the file is taken first. Those two tickets are still in `backlog/`, and this ticket and the implement stage have added 88 lines between them. Not acted on - the deferral and its owner are already recorded at the site, and splitting a fixture under a bug ticket would bury the fix - but the drift is worth a maintainer's eye. As the implement stage did, the new case documents itself in its own doc comment rather than growing the class summary.

### Nothing found

- **Error handling and resource cleanup**: the change is to compile-time ordering and adds no resource, no `try` and no new failure path. The one existing failure path in the touched methods, `Compiler.CheckConversionContext` throwing where no conversion exists, is unaffected by where `base` is called, because the exception leaves the plan unbuilt either way.
- **Performance**: no run-time work was added or removed. The one change to the number of calls made is the removal of a duplicate `DetermineModifiers`, which happens once per plan compilation and reads two flags.
- **Scalability, type safety and the modular/DRY angles**: nothing new was introduced to assess. The engine code is three comment edits, two line deletions and one statement moved.
