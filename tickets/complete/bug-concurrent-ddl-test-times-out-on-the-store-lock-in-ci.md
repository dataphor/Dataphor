## What landed

`ConcurrentDDLTest.ConcurrentSessionsStoreTheirOwnScripts` gives its own server instance a 120-second catalog-store busy timeout (`instance.Server.CatalogStoreConnectionString = TestServerInstance.CatalogStoreConnectionString + ";BusyTimeout=120000"`, set before `Start()`), using the same per-instance idiom `CatalogStoreConcurrencyTest`, `NativeSessionCleanupTest` and `AbandonedSessionCleanupTest` already use. The shared default in `TestServerInstance` and the store's own `DefaultBusyTimeout` are untouched, so no other fixture and no deployment moves.

Nothing holds the lock too long: the measurements in the fix stage put the longest single hold under half a second and the longest wait near four seconds, because SQLite's busy wait is a sleep-and-retry loop rather than a queue — one 3.8-second wait was measured to span 100 other acquisitions of the same lock against 15 competitors. On the CI machine, about six times slower, that starvation tail crossed the 30-second default and 16 of the run's 720 statements raised 130103. So the fix is to the test's own configuration, and the knowledge that the default bounds an unfair wait rather than a long transaction is recorded as a tripwire at `SQLiteStore.DefaultBusyTimeout` and in the 130103 bullet of `docs/architecture/catalog-and-store.md`.

The load was not reduced (`SessionCount` 16, `CycleCount` 15, `OperatorStatementCount` 400 all unchanged) and the assertion was not loosened: every exception from a thread still lands in `failures` and the test still asserts `failures` is empty, so a 130103 here now is real news. Both were checked directly against the diff and the file, since both are the shortcuts the fix ticket explicitly forbade.

Implement commit: `ticket(implement): bug-concurrent-ddl-test-times-out-on-the-store-lock-in-ci`. The review stage added two corrections, below.

## Review findings

**Checked.** The implement diff read before the handoff summary: 12 inserted lines across the test, the store constant's comment and the architecture page, no production behaviour. That the appended keyword actually takes effect, by following the path `Server.CatalogStoreConnectionString` → `GetCatalogStoreConnectionString()` → `ServerCatalogDevice` → `SQLiteStore.NormalizeConnectionString`, where `ContainsKey("BusyTimeout")` suppresses the default and derives `Default Timeout` = 119 s, just under the 120 s as that method's own comment intends; `CatalogStoreConcurrencyTest.StoreLockWaitReportsStoreLocked` independently proves the path by timing out on purpose at 1000. The `NOTE:` sitting after the `<summary>` rather than before it, which matches the two other instances in `src/` (`Base/StreamUtility.cs`, `Server.Hosting/NetTcpServiceHost.cs`) and costs no build warning. The `tickets/.pre-existing-known.md` entry for this test, which records a different, already-resolved one-off (the shared name-resolution path) and needed no update. The barrier path in `RunConcurrently`, because a longer timeout matters more if a failure can hang the run: a session that fails before signalling calls `RemoveParticipant`, so it cannot. Whether an NUnit timeout could cheaply guard the "hangs two minutes per statement on a real deadlock" tradeoff: there is no `[Timeout]` or `CancelAfter` anywhere in this fixture set, so adding one here would be inventing a convention, and the Debug lock-order assertion the comment names is real and active in the job that failed.

**Minor, fixed in this pass.**

- The test's comment said the write lock is busy "about two thirds" of the concurrent phase. The fix stage's own table gives 19.8-20.2 s held within a 26.9-27.8 s phase — 71-75 %, since the lock is exclusive and the holds cannot overlap. (The fix ticket's "63 % duty cycle" was an arithmetic slip, which the comment then rounded toward.) Corrected to "about three quarters". The same sentence also left the CI consequence implicit: as written it read as though the 30 s default *does* bound the tail at CI speed, when the point is that it did not. It now says the tail crossed 30 s and 16 of the run's 720 statements raised 130103.
- `docs/migration-notes.md`, the 130103 row: the operator action read "Retry; if it recurs, find the session with a long-running transaction that has changed the catalog and end it". This ticket's measurements show that advice can send an operator hunting for a transaction that does not exist, since sustained concurrent schema changes alone can starve a session past the timeout with nothing held long. Added the second case — raise `BusyTimeout`, because the wait is unfair rather than queued. Documentation accuracy on an existing row, not a new behaviour entry; the code change remains unobservable to applications, deployment scripts and extensions.

**Major: none filed, and the reason.** The one candidate is the starvation itself: at CI's measured six-times slowdown the 30-second production default sits only about 1.3x above the tail this load produces, which is thin. It is correctly a tripwire rather than a ticket. 130103 is a documented, retryable error with an operator remedy, and the triggering condition is a load level — sixteen sessions doing nothing but create schema objects, with 400-statement operator bodies — not a dormant code path that is wrong the moment it runs. It is parked at `SQLiteStore.DefaultBusyTimeout` and in the architecture page with the engine-side fix named (a fair gate in front of the store write transaction, not a bigger timeout) and a revisit condition (an application seen taking spurious store-lock timeouts under sustained concurrent DDL). The migration-note correction above closes the operator-facing half of it.

**Conditional/speculative: nothing new parked.** The one tripwire in this area is the implement stage's, named above; the review found no second conditional concern to record.

**Accepted tradeoffs: none met.** No `NOTE:` at any site the diff touches records a previously declined finding, so nothing here was already decided.

**The implementer's flagged gaps, dispositioned.**

- *The bare literal 120000.* Left as it is. All three sibling fixtures pass a bare `BusyTimeout=1000` the same way, so a named constant for one call site would break the idiom to gain nothing — and tying it to `SQLiteStore.DefaultBusyTimeout` would be actively wrong, since the whole point of the value is that it is not the default.
- *The comment carrying measurements that cannot be re-run.* Kept, and corrected. They are the only place the decision's basis sits next to the decision, and the fixture already does this at `OperatorStatementCount`, whose comment records the calibration runs behind the load. Trimming them to the mechanism would leave a future reader with no way to judge whether 120 s is still right.
- *The failure not re-reproduced at the new setting.* Accepted. Confirming it would mean re-instrumenting the store to lower the timeout again; the real confirmation is CI's Debug job staying green, which is where this class of failure was seen in the first place.

**Tests: none added, none cut.** The diff adds no tests, which is right — the reproduction of this bug *is* `ConcurrentSessionsStoreTheirOwnScripts`, and the fix is to that test's own configuration; the engine-side bound on 130103 is already owned by `StoreLockWaitReportsStoreLocked` at `BusyTimeout=1000`. A test asserting that a shorter busy timeout fails would pin SQLite's behaviour rather than the engine's. Nothing in the diff restates the implementation or verifies a mock, so there was nothing to remove.
