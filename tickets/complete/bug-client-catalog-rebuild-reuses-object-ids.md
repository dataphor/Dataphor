description: A program connected to a Dataphor server keeps a local copy of the server's schema and rebuilds it from scratch when the server's schema changes. It used to number the rebuilt copy from one again, so a rebuilt item could be given the same identifier as an item the program was still using, and discarding the old item then made the new one unfindable. The rebuilt copy now carries on numbering from where it left off.

## What landed

`Engine.InitializeCatalog` guards its identifier-generator reset with `if (!IsEngine)`, so an engine that persists its catalog still starts its numbering again from one - the built-in objects it creates before it reads its store must land on the identifiers the store already holds - while a repository engine, the catalog cache `LocalServer` starts on the client side of every network connection, no longer does. `Engine.ClearCatalog` runs that method again whenever the server's catalog moves on, and the objects of the catalog being replaced are still in their clients' hands (every prepared table expression the client holds owns a view in it), so restarting the generator reissued their identifiers; dropping one of the stale views then removed the *rebuilt* object's entry from the catalog device's identifier-to-name index, leaving a live object in the catalog that `ResolveCatalogObject(int)`, `ResolveCachedCatalogObject(int)` and `MarkViewForRecompile(int)` could no longer find.

Delivered by `ticket(implement): bug-client-catalog-rebuild-reuses-object-ids`: the guard, the comment at the site stating the settled rule in both directions, matching remarks on `Schema.ObjectIDGenerator`, a tripwire `NOTE:` at `CatalogDeviceSession.ClearCatalogObject` (the index entry is removed by identifier without checking that it still names the object being cleared), an accepted-tradeoff `NOTE:` at the `#if !DEBUG` replace-by-name in `CacheCatalogObject`, the engine-layer reproduction in `ObjectIDPerEngineTest`, `AbandonedClientProcessTest.SessionCount` restored to a cursor over `System.Sessions`, and a sentence in the WS2 record of `docs/modernization-plan.md`. The review pass added the migration-notes entry, a tripwire about the full server's own reset, and the clean-ups below.

**One tripwire recorded**, at the reset site in `Engine.InitializeCatalog`: on an engine with a store the reset runs only at start-up today, because nothing rebuilds a full server's catalog while it runs - the D4 `ClearCatalog` operator throws `NotSupportedException`, and `ClearCatalog`'s only caller in the tree holds a repository engine - and if a rebuild on a live full server is ever made to work, the fix used here is not available to it, because its store load needs the fixed numbering. Without that line the new comment reads as though a full server resets on every rebuild and that this is safe generally.

**Considered and left alone, with reasons.**

- **`IsEngine` as the predicate.** It reads as "is a definition repository" rather than "has no catalog store", which is the property that matters, and the handoff flagged it. Kept: the store-bearing component that could answer the question directly, the catalog device, does not exist yet at this point in `InitializeCatalog` - the reset has to precede its creation - `IsEngine` is the engine's established vocabulary with some forty uses, `Server` is its only subclass, and a second predicate meaning `!IsEngine` would be one concept under two names. The comment at the site already states the mapping in both directions.
- **The accepted tradeoff at `#if !DEBUG`.** Reviewed as a decision and agreed; its factual claim was verified rather than taken on trust (`USEOBJECTVALIDATE` is defined in both configurations, so `Catalog.Add` does throw on the duplicate name and the release-only replace is what keeps it from throwing). Not re-filed, per the rule on declined findings.
- **Making `ClearCatalogObject` check the index entry's name before removing it** - the boundary invariant behind the tripwire. Declined: skipping the removal silently would hide the very reissue it is meant to catch, the precondition is now guaranteed by the generator's contract, and the tripwire says what a future reader would need. A check that *throws* is a different proposal and belongs to whoever has a reason to want one.
- **Identifier exhaustion, now that a repository engine's generator never goes back.** A rebuild costs about 360 identifiers permanently, so some six million rebuilds in one client process would be needed to reach `Int32.MaxValue`; identifiers already accumulated between rebuilds, `Allocate` already refuses to wrap and says so loudly, and the generator's own remarks already cover exhaustion. Nothing added.

**Tests: one added by the implement pass, kept; nothing cut, nothing else added.** The engine-layer case is the reproduction at the lowest layer that shows the defect, and it is verified to fail without the fix. No test was added for the eviction itself, nor an over-the-wire reproduction - the suite still has none of the latter, and the handoff is explicit about that. A client holding prepared table expressions across a server schema change is a new out-of-process fixture; against a reproduction that already fails in 333 ms at the engine layer it would buy only the client's share of the path, which the restored `SessionCount` now walks on every run of the abandoned-client case. Not filed as a ticket: a conditional gap in the coverage of a path that is covered, with its reproduction in hand, is not work the board needs.

**No tickets filed and nothing routed to `blocked/`.** No finding was above the filing bar: three were comment and test hygiene fixed in place, the fourth was a document entry, and the two architecture-level candidates are answered above - one by the generator's contract, one by a decision already recorded at its site.
