## What landed

**The fix is one line.** A client outside the server asks the server three questions about the row a user is editing: what should this column default to, what follows from the user changing this column, and is this row acceptable. The third takes two rows — the row as it was and the row as the user has it now — and the row to check is the second one. `RemoteServerCursor.Validate`, the server's entry point for that call, passed them to its own body the other way round, so the row checked and the row sent back were both the stored row.

```
src/engine/Server/Server/RemoteServerCursor.cs:733
-   return InternalValidate(newRow, oldRow, column);
+   return InternalValidate(oldRow, newRow, column);
```

Three consequences, each wrong in a different direction: a new value the server will refuse on saving was reported as acceptable when the user left the field; a stored value that already fails a check was reported against the user, on a field they may never have touched; and where a validate handler changes the row — which makes the call report that it changed something, on which the client writes the returned row over the row the user is editing — the user's edit was silently replaced by the stored value. Only a client outside the server reached it, and only for a validation the client is not allowed to answer itself; everything in process was always correct.

**A new shared fixture, `tests/DAE.Server.Tests/ClientStackTestFixture.cs`** — the first thing in this suite that stands the shipped client stack up in process: a `LocalServer` over a `RemoteServer` over the in-process server, with a client session and process per test beside the engine-side pair. That is what makes `RemoteServerCursor` and `LocalCursor` reachable from a test at all, and what lets a case ask the same question of both sides and compare. Two queued tickets build on it (`bug-attached-handler-never-reaches-a-remote-client`, `bug-remote-form-is-never-told-about-a-type-change`).

**Three cases in `tests/DAE.Server.Tests/RemoteValidateTest.cs`**, one per consequence: the new row is the row validated, the old row is not validated, and the validated row is the row returned. Each asks the question twice — once through the client stack, once on the engine's own cursor — and asserts the two agree *and* names the verdict it expects, so neither agreement nor disagreement can be reached by accident.

Implement stage: `ticket(implement): bug-remote-validate-validates-the-wrong-row`. Review changed the tests, the fixture and one document; the engine fix was confirmed correct and left exactly as it landed.

## Review findings

The implement diff was read before the handoff. The fix was checked by reading the whole call chain; the tests were checked by reading them, by running them, and by two deliberate mutations (each built, run, then reverted, with `git diff` confirming the engine source byte-identical to HEAD afterwards).

### Checked and sound

- **The fix is right, and it is the only site.** The argument order is consistent end to end: the WCF contract (`IDataphorService.Validate`), its asynchronous client copy (`IClientDataphorService.BeginValidate`), the service dispatch (`DataphorService.Validate`), the over-the-wire client (`ClientCursor.Validate`), the client-side caller (`LocalCursor.Validate`, which also writes the returned body back over the new row) and `InternalValidate`, which builds both the validated row and the returned row from its second argument. No other implementation of the call had the swap.
- **The siblings really are correct.** `Default` takes one row, so it has no order to get wrong; `Change` passes its two straight through and `InternalChange` builds the returned row from the new one. Both re-read, neither tested, as the fix ticket asked.
- **The round trip still holds, and gives the measurements the fix ticket recorded.** With the swap put back and nothing else changed, all three cases fail: old 5 / new −1 accepted with −1 in the row where a refusal is required; old −1 / new 5 refused where acceptance is required; and the handler's edit coming back as the stored 10 instead of the user's 20. This matters more than usual, because the remote path is reached only when the validation is not remotable — a case that accidentally took the client-side shortcut would pass either way and pin nothing.
- **The same defect class does not exist elsewhere in the tree.** A scan for an adjacent pair of same-typed row arguments passed in reverse (`newRow, oldRow`) found two sites, and both are correct by design: `ApplicationTransaction`'s update `Undo`, which must update new → old to undo an update that went old → new, and `SQLStoreConnection.LogUpdate`, which records the *inverse* statement in the undo log — confirmed by its neighbours (`LogInsert` generates a delete, `LogDelete` generates an insert) and by the log being replayed backwards on rollback. So the swap was a genuine one-off with no class behind it: the architecture ladder bottoms out at the point fix that landed, and there is no invariant, type change or general test to file for it.
- **Docs.** The `docs/migration-notes.md` row is in the same section as its sibling defect's (*D4, catalog and libraries*), and the K44 row in `docs/modernization-plan.md` has the five cells its table header declares.

### Fixed in this pass

- **The fixture duplicated `InProcessTestFixture` instead of deriving from it.** Roughly 45 of its 143 lines re-implemented, verbatim in behaviour, what that base class exists to do: the `Libraries` override, the `TestServerInstance` field and property, the instance's creation and disposal, the engine-side session and process per test, and `ExecuteScript`. It now derives from it and adds only the client stack, which also gets it the base's `LibrariesToRegister` hook for free. 143 → 116 lines. The engine-side session and process are the base's own, named `EngineSession` and `EngineProcess` for the side of the stack they are on, because in a fixture with two of everything a bare `Session` or `Process` does not say which one a test reached — the hazard being a future case that silently tests the engine where it meant to test the client. The setup methods are deliberately named apart from the base's rather than hiding them, with a comment saying why: NUnit runs a base class's setup first and its teardown last, which is exactly the order this stack needs, but only while the names differ.
- **The fixture's teardown leaked on its own error path.** The two disposals were a plain sequence, so a failure in `LocalServer.Dispose` would have skipped `RemoteServer.Dispose` *and*, with the refactor, would now skip the base fixture's disposal of the server and its temporary directory — leaving a running engine and an undeleted instance folder behind a single failure. Nested `try`/`finally` now, as the per-test teardown already had.
- **Two of the three cases could have passed while broken.** They asserted only that the client stack agrees with the engine, and the refusal arm of the test helper is reached through a `catch` that any exception at all satisfies — so a fault that broke both paths the same way would have passed by agreeing with itself. The third case already guarded against this by naming its expected values; the other two now do too, each naming the verdict it requires and the accepted case naming the value that must survive in the row. With the fix reverted they fail on those named expectations rather than on bare disagreement.
- **Nothing checked the test's own premise — that the remote call was made at all.** The cases reach the server only because each table tags its edited column `DAE.IsValidateRemotable = "false"`; were that tag to stop applying, the client would answer out of its own copy of the table variable, get the right answer, and leave three green cases exercising nothing above the engine. The test helper now asserts the plan's flag directly, on both the client's and the engine's plan (the client's copy is built from the engine's when the plan is prepared). Measured: with the tag dropped from the two-column table, both cases that use it fail on that assertion, where before they passed.
- **`AGENTS.md` had nothing about the new fixture.** It documents the suite's reusable test machinery, including a paragraph on the out-of-process client/server tests, and the next agent looking for a way to reach the client stack in process had no way to find this. A paragraph was added beside that one: what the fixture stands up, why it is not the WCF path, what it therefore cannot show, and the two-engines-per-test cost.
- **A test filter in a queued ticket that selects nothing.** `bug-remote-form-is-never-told-about-a-type-change` asks for `--filter "...|Name=CursorTest"`; `Name` matches a test *method*, so that clause matches no test. The implement handoff had already established this for its own run. Corrected in that ticket, with the reason, so the next agent does not spend a run discovering it again.

### Considered and left as it is

- **A refusal records only that the row was refused, not which error said so.** The handoff raised this itself. Left deliberately: the client stack wraps the engine's exception, so the two messages are not meant to be identical, and the claim these cases make is about which row is checked and which is returned — the verdict and the row carry that. Comparing error codes would pin a different property (that the client reports the *same* violation), and the named verdict expectations added above close the vacuity risk that was the real reason to want it.
- **One test helper serving a two-column and a three-column table**, setting `Note` only when a value is passed and reading it back only when the row type has the column. Flagged by the handoff as possibly too clever. Five lines, and two helpers over two shapes would be worse; left.
- **The outcome's row values are typed `object`.** That is what the row indexer hands back, and a cast to `int?` would throw rather than fail an assertion if the shape were ever wrong. Left.

### Not covered, and not filed

- **`Default` and `Change` through the client stack.** The handoff names this as the architecture-rung option it did not take, and it is a real gap — nothing would catch a future swap in those two. No ticket, because the work is already queued and would be duplicated: `bug-remote-form-is-never-told-about-a-type-change` adds one case per proposal call on this very fixture, which is that general coverage.
- **Nothing exercises this over the wire.** `OutOfProcessProtocolTest` drives a real client against a server in another process but makes no proposal call, so the WCF layer's marshalling of the two row bodies is still untested. Not filed: it is below the bar — `ContractParityTest` holds the two contract declarations in step, `CoreWcfProtocolTest` covers the transport, and the protocol layer marshals only the calls `RemoteServerCursor` and `LocalCursor` already make, which the cases above now pin. Recorded here rather than as a comment because it is a coverage limit, not a condition that might trip.

### Tripwires parked

None, and the reason is not that nothing was looked for: a tripwire is a cost or a risk that is fine now and becomes work only if some condition trips later, and this change has none. The fix removes a behaviour rather than adding a conditional cost, and the fixture's two non-obvious constraints — the teardown order and the two engines live in every test — are plain comments at their sites because they describe what the code does now, not something that might change.
