## What landed

A client outside the server never sees an event handler. A handler is not remotable (`Schema.EventHandler.DetermineRemotable` sets `IsRemotable = false`, and the `TRIGGERSREMOTABLE` compiler constant that would make it otherwise is defined nowhere), so `Schema.TableVar.IncludeHandlers` filters handlers out of the catalog a client is sent. What the client gets instead, with every prepared plan, is a verdict per column: whether it may answer a `Change`, `Default` or `Validate` proposal out of its own copy of the schema or has to call the server. `ServerProcess.CopyDataType` emits that as `DAE.IsChangeRemotable`, `DAE.IsDefaultRemotable` and `DAE.IsValidateRemotable` tags, and `LocalCursor.Change`/`Default`/`Validate` read it back through `TableVar.Is*CallRemotable`. Attaching a handler has to flip the verdict to "call the server", or the handler does not run for that user at all.

It does flip, on the live catalog object. But the verdict is built when the plan is compiled and kept with the plan in the server's plan cache, which is keyed by statement text and evicted only by `Catalog.PlanCacheTimeStamp` — and `CreateEventHandlerNode` and `AlterEventHandlerNode` moved no counter at all. So a client re-preparing a statement text that had been prepared before the attach was handed the pre-attach verdict and went on answering the proposal itself, out of a copy with no handler.

`ticket(implement): bug-attached-handler-never-reaches-a-remote-client` made all three nodes that change a handler list bump `Catalog.PlanCacheTimeStamp` and `Catalog.CacheTimeStamp`, gated on `ServerProcess.ShouldAffectTimeStamp`. The review folded the three identical bumps into one `DDLNode.InvalidateCachesForHandlerChange`, which the three nodes now call and which carries the explanation once.

- `PlanCacheTimeStamp` is the fix. A re-prepare then recompiles and emits the post-attach verdict, and the client builds a fresh table variable from it, because a cursor plan's catalog object is named from the plan's own id (`RemoteServerPlan.GetCatalog`) and so is never a cached object the client could reuse.
- `CacheTimeStamp` is for a plan the client still holds **open**, which no eviction can reach. Nothing consults it per plan yet: `bug-remote-form-is-never-told-about-a-type-change` is what teaches the proposal calls to, and names this ticket as its prerequisite for exactly this bump.
- `DerivationTimeStamp` deliberately stays put. Confirmed in review rather than assumed: the Frontend's derivation reads column metadata, keys and references, and nothing under `libraries/Frontend/Source` mentions a handler list or any of the proposal characteristics.
- The gate is `DropEventHandlerNode`'s existing one and exists because these same three nodes attach and drop the handlers the server generates on the copy an application transaction makes of each table it joins (`ApplicationTransactionDevice.AddTableVar`, `ServerSession.DropSessionObjects`), and because loading a stored handler from the catalog runs `CreateEventHandlerNode` in a time-stamp-safe context too (`ServerCatalogDeviceSession.LoadPersistentObject`). A form's edit cycle is made of application transactions, so an ungated bump would flush every session's plans on every edit.

Measured, 2026-11-23, against an in-process server with the shipped client stack in front of it. A table whose `Amount` column gains a change handler that writes 99, asked what follows from the user changing `Amount` from 1 to 2 through `select Tbl capabilities { updateable }`, prepared once before the attach and again after it: before the fix the client said "nothing changed, 2" where the engine said "changed, 99"; after it both say "changed, 99". The same question worded `select Tbl where ID >= 0 capabilities { updateable }`, which no plan had been compiled for, answered "changed, 99" either way — which is why nothing that connects, does one thing and disconnects ever saw this.

`tests/DAE.Server.Tests/RemoteEventHandlerCacheTest.cs`, new, on the client-stack fixture. Each case asks the same question of the client's `LocalCursor` and of the engine's own cursor, asserts the two agree, and names the resulting value, so a regression breaking both the same way cannot pass.

## Review findings

**What was checked.** The implement diff was read before the handoff summary. Every factual claim the handoff rests on was traced to the code rather than taken on trust: `EventHandler.DetermineRemotable` and the undefined `TRIGGERSREMOTABLE`; `TableVar.IncludeHandlers`; the three tags `ServerProcess.CopyDataType` emits and their three readers in `LocalCursor`; `CatalogDeviceSession.AttachEventHandler`/`MoveEventHandler`/`DetachEventHandler` each calling `tableVar.DetermineRemotable`; the three time-stamp-safe contexts the gate depends on; and both counters incrementing under the catalog's own lock. Beyond the handoff: whether a fourth statement changes a handler list and was missed (`DropTableVarNode.DropEventHandlers` compiles real `detach` statements through `DropEventHandlerNode`, and the handler statements nested inside `alter table` and `alter type` go through the same three nodes, so there is no fourth site); the rollback path (`CatalogDeviceSession.InvalidateCachesAfterUndo` bumps both counters again after an undo, so a rolled-back attach over-invalidates rather than under-invalidating, and `CatalogRollbackSnapshotTest`'s attach and detach cases cover it); concurrency on the new fixture's counter assertions (the fixture is not parallelizable and holds its own server); and what the `CacheTimeStamp` half actually costs a connected client today. `docs/architecture.md` was read and owed nothing: it describes neither the proposal mechanism nor event handlers.

**Major findings: none, and no ticket filed.** The two things the handoff asked to be challenged — the `invoke` arm and whether `CacheTimeStamp` should move at all yet — were both settled inside this pass rather than deferred, and the one documentation error found was user-facing and fixed here.

**Minor findings, fixed in this pass.**

- **`docs/migration-notes.md` claimed the fix reaches a form that was already open.** The entry's opening sentence said "without the user reopening it" and its "what to do" column said a form "now runs a handler attached while the form was open" — both contradicted by the entry's own body and by the code: an open plan's verdict was resolved when the plan was prepared, and nothing re-sends it. All three places now say what actually changed — a form opened *after* the attach — and name reopening as the workaround for one already open, with the open-form half pointed at `bug-remote-form-is-never-told-about-a-type-change`. This was the one finding with a reader outside the repository.
- **The `invoke`/`AlterEventHandlerNode` arm, which the handoff left reasoned rather than measured, is now settled.** Nothing a client is told can differ after a reorder: each `DAE.Is*Remotable` answer is an and-reduction over the handlers of one event and each `Should*` flag an or-reduction over the same set, so the recompute `MoveEventHandler` does gives back exactly what was there. The firing order a reorder *does* change is read live from the catalog as the modification runs, by the server, for a client and a local caller alike (`TableNode.ExecuteChangeHandlers` and siblings), and `EventHandlers.d4`'s `TestFiringSequence` already asserts it. The bump is kept — `invoke` is a schema-definition statement nobody runs in a loop, and leaving one of the three statements with a different rule is the asymmetry this defect was — but its comment now says plainly that it is conservative and is the one of the three that can go. No test was added: a case asserting that nothing changes would pin a non-behaviour, and the behaviour a reorder does have is already covered one layer down.
- **The three bumps were three copies of the same five lines, each carrying its own copy of the reasoning** — about 45 lines of duplicated prose across the file. Folded into `DDLNode.InvalidateCachesForHandlerChange`, so the explanation lives once, the log line has one shape, and a fourth statement that ever changes a handler list cannot be given a different rule by accident. `DDLNodes.cs` grew by 7 lines net.
- **`DerivationTimeStamp` staying put was confirmed, not changed.** The handoff invited a second opinion on the asymmetry with the neighbouring `alter` and `drop` nodes, which move all three counters. It is correct here for a reason those nodes do not share: a handler contributes nothing to a derived form.
- **The test fixture's own remarks re-derived the whole mechanism** a third time, after the code comment and the plan record. Trimmed to what the fixture pins, pointing at the helper for the why.

**Tripwires, parked at their sites rather than filed.**

- `DDLNode.InvalidateCachesForHandlerChange`: what the `CacheTimeStamp` half really costs. The handoff described it as a client refetching its catalog copy; it is more than that — `LocalServer.EnsureCacheConsistent` clears the client's whole internal catalog, drops every session's session objects and disconnects each process from the catalog device, and the next prepare rebuilds. Every `alter` and `drop` of a table, view, type or operator already pays exactly that, and attach and detach are schema definition rather than anything on an edit path, so the half is kept; the note names it as the first thing to look at if attaching handlers in bulk ever shows up as slow for connected clients, and records that `PlanCacheTimeStamp` alone is what the measured defect needed.
- `Schema.TableVar.DetermineRemotable`: the three `all*Remotable` summaries are not reset before the loop that ands them down, unlike the three table-level flags just above, so a table variable whose last handler is detached keeps saying "not all columns are remotable" for the life of the catalog object. Unobservable today and in the safe direction — nothing reads these on the server, `CopyDataType` sends the per-column flags rather than these, and a client builds a fresh table variable per plan — so it is a note at the site rather than a ticket, with what would have to change for it to start mattering. It sits on the line `bug-type-change-handler-never-runs-for-a-client` will edit.

**Considered and left alone.** `InvalidateCachesForHandlerChange` is a new `protected` member on the public `DDLNode`, which the project's rule on public surfaces could be read to cover. No `docs/migration-notes.md` entry: it is purely additive, no existing extension can fail to compile or behave differently because of it, and an entry about a helper on an abstract DDL node base class is noise in a document an application author reads. The plan's K45 record names it instead.

**Tests: none cut, none added.** The four cases were weighed individually. The two attach cases are the reproduction and were each seen to fail against the unfixed engine. The detach case passes either way and the handoff invited cutting it; it is kept because it is the only coverage the event-handler nodes have of the detach direction, which is a contract in its own right, and its comment now says so instead of implying it guards this change. The gate case asserts on counters rather than on behaviour, which is the only observable there, and it is the case that stops the worst plausible regression. Nothing was added, because the one defect found in this pass was in a document and the one contract left unverified — the reorder — is covered a layer down.

**Still open, by design.** A handler attached to a scalar *type* is not reached by this fix and is a different defect with a different cause (`Schema.TableVarColumn.SetIsChangeRemotable(ScalarType)` walks the column's own handlers instead of the type's, where its two siblings read the type correctly). It was verified during the implement stage and filed as `bug-type-change-handler-never-runs-for-a-client`, which has since been routed to `blocked/` for the human call its `tradeoffs:` line names — fixing it moves every change proposal on a column of such a type to the server. A form that was already open when a handler was attached is likewise still not reached; `bug-remote-form-is-never-told-about-a-type-change` owns that and names this ticket as its prerequisite.
