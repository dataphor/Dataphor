## What was wrong

Beside each table, and beside each of its columns, the engine keeps a one-bit summary of the definition: is there a default worth asking for, a check worth running, a change handler worth calling. In the code these are `ShouldDefault`, `ShouldValidate` and `ShouldChange`. They are derived from the definition, never stored, and they exist as a fast path — `TableNode.Default`, `Validate` and `Change` each return without doing anything when their flag is false, and `ServerProcess` decides what to tell a remote client about a table from the same family.

Nothing invalidates the summary when the definition changes; it is recomputed as a side effect of compiling an expression over the table, which in practice happens often enough that it is usually right. A rollback was the gap. The undo log restored the definition — a column's default object, a column's constraint — and the summary kept the value computed from the half-altered definition the rollback had just thrown away. After a rolled-back `alter table T { alter column C { drop default } }` the server went on skipping that default; after a rolled-back `alter column C { drop constraint X }` it went on skipping that column's check.

The effect reached any cursor that was open across the rollback — an open form, in practice — and lasted as long as that cursor did, because opening one afresh recomputes the summary on its way in. The fix ticket said the staleness lasted until the server was restarted; it does not, and the narrower claim is the one this was judged on.

## What changed

**`src/engine/DAE/Device.Catalog/CatalogDeviceSession.cs`** — a private `RedetermineRemotable`, two overloads (one taking the table variable, one taking a column), called last in eight `Undo` methods so that the recompute sees the whole restored definition: `AttachTableVarConstraintInstruction` / `DetachTableVarConstraintInstruction`, `AttachTableVarColumnInstruction` / `DetachTableVarColumnInstruction`, `AttachTableVarColumnConstraintInstruction` / `DetachTableVarColumnConstraintInstruction`, `SetTableVarColumnDefaultInstruction` and `SetTableVarColumnIsNilableInstruction`. It goes through `Schema.TableVar.DetermineRemotable` rather than setting the flags, so the whole derived family — `IsDefaultRemotable`, `IsValidateRemotable`, `IsChangeRemotable` as well as the three `Should…` flags — comes out as a restart would compute it.

No public signature changed. The implement stage found that the design question the fix ticket left open — how an undo holding only a `Schema.TableVarColumn` reaches its table variable — did not need answering: the column already carries a public back-reference to its table variable (`src/engine/DAE/Schema/TableVar.cs:311`), maintained by the collection that owns it.

**`src/engine/DAE/Runtime.Instructions/DDLNodes.cs`** — one `NOTE:` above `AlterColumns`, comment only. The forward path has no recompute of its own for a default or a column constraint and is right today only because something in the statement recomputes anyway; the note says what was measured and what was not pinned, so that a future reader does not take the forward path for deliberate.

**`docs/migration-notes.md`** — one row under *D4, catalog and libraries*, in terms of what a form sees, saying that the effect was limited to a cursor open across the rollback and how narrow the window is.

## Tests

`tests/DAE.Server.Tests/ColumnChangeRollbackTest.cs`, new, over `InProcessTestFixture` (one in-process server per fixture, no database server needed). Each case opens a cursor before the transaction and asks through it after the rollback, which is the only state the defect is visible in.

| Test | What it verifies |
|---|---|
| `TestRolledBackDropDefaultStillDefaultsANewRow` | after a rolled-back `alter column C { drop default }` the engine still proposes the default for a new row |
| `TestRolledBackDropColumnConstraintStillRefusesTheValueItRejects` | after a rolled-back `alter column C { drop constraint X }` the engine still refuses a value the constraint rejects, naming the constraint |
| `TestNestedRollbackLeavesTheOuterLevelsDefault` | an inner rollback lands on the outer level's definition and the outer rollback then on the original — which recomputing from the restored definition gives and replaying a recorded flag value would not |

The fixture is separate rather than cases in `CatalogStoreTest.cs` as the fix ticket suggested, following the two sibling rollback tickets: these cases read nothing from the catalog store, and `CatalogStoreTest` starts a fresh server per case. Confirmed in review as the right call.

## Review findings

Read the implement-stage diff (`ticket(implement): bug-rolled-back-column-default-is-never-applied`) before the handoff, then the surrounding code: `TableVarColumn` and `TableVar` in `src/engine/DAE/Schema/TableVar.cs` (both `DetermineShouldCallProposables`, every `SetIs…Remotable`, and the `DetermineRemotable` overrides on `BaseTableVar`, `ResultTableVar` and `DerivedTableVar`); the `ShouldDefault` / `ShouldValidate` / `ShouldChange` guards and the insert path in `TableNode.cs`; `AlterColumns`, `CreateColumns` and `AlterTableNode.InternalExecute` in `DDLNodes.cs`; `CompileAlterTableStatement` and the create-table and create-view paths in `Compiler.cs`; `ServerProcess`'s use of the family; all 88 `DDLInstruction` classes in `CatalogDeviceSession.cs` and the session mutators behind them; and every reader of `IsNilable` in `src/`.

**Verified the fix end to end, which is the first thing a reader of this ticket should be told.** All nine calls were disabled, the solution rebuilt, and the three cases run: all three failed (`Expected: "abc" But was: null`; the constraint case raising nothing at all; the nested case `Expected: "outer" But was: null`). Restored, all three pass. The implementer's claim that the tests were red first is accurate, and the fix is load-bearing for each of them.

**Found and fixed in this pass (three, all minor).**

- *The migration note overstated how often this bit.* It said a stale summary cost every column of the table its default, not only the altered one — true of a stale summary, but it left the impression that dropping any column's default did this. Measured by giving the table a second column with a default of its own and dropping only the first's: with the fix disabled, the case passes. The table-level summary is the logical *or* over the columns, so it only falls to false when the dropped default or check was the last one on the table. The note now says so, and the test's doc comment records why `Name`'s default is the table's only one. This matters because the note is what an application owner reads to decide whether they were affected.
- *The `AlterColumns` tripwire asserted a mechanism that does not hold as stated.* It said the statement "always compiles at least one" expression over its own table. It does not: the only such compilation in `AlterColumns` is the existence check that guards making a column non-nilable, and a bare `drop default` or `drop constraint` compiles nothing over the table. Something in the statement does recompute the summary — that is not in doubt, because with the fix disabled the summary is already false when the rollback runs, and the only thing that lowers it is `DetermineRemotable` — but which site was not pinned, and a tripwire naming a wrong reason is worse than one naming none. Rewritten to state the measurement, to say plainly that the forward path is right by accident, and to keep the actionable half: call `table.DetermineRemotable` there if a stale summary is ever seen after a *committed* alter.
- *Call style.* The two helpers were `private static`, taking the session as a first parameter, and were called as `RedetermineRemotable(session, _tableVar)` on the line after `session.DetachTableVarConstraint(_tableVar, …)` — two conventions in adjacent lines. They are now instance methods on the session, called `session.RedetermineRemotable(_tableVar)`, which is how every other line in these `Undo` bodies reads and how the file's own `AttachEventHandler` reaches the same recompute. The long doc comment the implementer invited trimming was tightened by about a third; its content is the part worth keeping and it stays.

**Found and filed (one, major, verified).** The handoff's reason for leaving the scalar-type instructions out of scope is wrong, and the hole is real. It argued that the forward path does not recompute the summaries of the tables that use a type either, so a rolled-back `alter type … { drop constraint }` leaves nothing stale. But a column of type `T` counts toward `ShouldValidate` when `T` itself carries a constraint, and *any read of such a table inside the transaction* recomputes the summary from the definition without the constraint — after which the rollback restores the constraint and leaves the summary false. Measured 2026-11-23 against this branch with the fix in place: a type with a positivity constraint, a table with a column of it, a cursor opened first, then in one transaction `alter type … { drop constraint … }` followed by a `select` of the table, rolled back — the engine then accepts `-5` through that cursor without complaint. Without the read inside the transaction it does not reproduce. Filed as `bug-rolled-back-type-constraint-stops-the-column-check`, framed at the class rather than as the point fix, because the point fix needs the undo to find every table using a type and the engine has no index for that: the ticket's three options are a dependents walk, a validity stamp against the catalog cache timestamp that every DDL statement already bumps, or not caching the summary at all — the last two retiring the class and superseding the eight recomputes that landed here rather than adding to them. It was filed into `backlog/` with the triage metadata and the honest decline argument, because which of the three to take is a maintainer's call rather than a reviewer's; a gardening pass has since promoted it into `fix/`, which is the board's decision and was left alone. The conclusion the handoff reached — out of scope for this ticket — was right; only its reason was not.

**Checked and correct, nothing to do.**

- *No undo instruction was missed.* Of the 88, the ones that restore something the summary reads are the eight fixed, the event-handler trio and the scalar-type ones. The event handlers were already correct before this ticket and still are: `AttachEventHandler`, `MoveEventHandler` and `DetachEventHandler` each call `tableVar.DetermineRemotable(this)` inside the session mutator, so the forward and undo paths both get it. The scalar-type ones are the filed hole. Keys, orders, references, metadata and the rest feed nothing in `DetermineShouldCallProposables`, which reads only the column's default, constraints, event handlers and scalar type, and the table's row constraints and event handlers. `RemoveDependenciesInstruction.Undo` already ended with a `DetermineRemotable` of its own, which is the precedent for recomputing inside an `Undo`.
- *Views cannot be made worse.* Only the two table-variable constraint instructions can hold one (`AlterViewNode` passes a `Schema.DerivedTableVar` to the shared `DropConstraints` / `CreateConstraints`; the column-level instructions are reached only from `AlterTableNode`, which works on a `Schema.BaseTableVar`). On a view the recompute is monotone: `DerivedTableVar.DetermineRemotable` passes `false` to `DetermineShouldCallProposables`, so it can raise a flag and not lower one, and the three `Is…Remotable` it recomputes from the view's metadata tags are idempotent — a view inherits those tags from its source when it is created and a constraint alter does not change them. A flag left raised costs a call that finds nothing to do. `ResultTableVar`, the one `TableVar` subclass whose override recomputes no `Should…` flag at all, is never reached from these instructions.
- *The column overload's null guard is defensive, not load-bearing.* `TableVarColumn._tableVar` is maintained by `TableVarColumns.Adding` / `Removing` and is null only while the column is detached; the reverse-order replay has always re-attached the column before any change to it is undone. Kept, with the reasoning in its doc comment.
- *The recompute on `SetTableVarColumnIsNilableInstruction` really is a no-op today, and stays.* Every reader of `IsNilable` in `src/` was checked: the client's required-field test in `DataSet.cs`, key nilability in `Compiler.cs`, statement emission, and the catalog view — none of them derived. It costs one walk of a table's columns on a rollback that nothing else measures, and the uniform rule (every instruction that restores part of a column's definition recomputes) is worth more than the saving. Its comment says this.
- *Nothing stale can store a bad value.* The insert path's `BeforeInsert` calls `PreparedValidate` unconditionally, not behind `ShouldValidate`, so a column or scalar-type constraint is always enforced when the row is actually saved. That is what bounds the severity of this whole family to "the error arrives on save instead of beside the field", and it is what both the test's doc comment and the migration-notes row say.
- *Documentation.* `docs/architecture.md` does not describe the proposable summary or the remotable family, and this change does not alter any mechanism it does describe. `docs/modernization-plan.md`'s known-defect table has no row for either sibling rollback ticket, so the precedent is that these do not get one; nothing was added. The one migration-notes row is the only entry this change owes.
- *Source hygiene at byte level.* Tabs, CRLF and byte-order-mark state unchanged in all four files (`CatalogDeviceSession.cs` and the test file have a byte-order mark, `DDLNodes.cs` and `docs/migration-notes.md` do not), no lone LF anywhere, and the new test file matches its siblings.

**Checked on the tests, nothing added and nothing cut.** The three cases are one reproduction each of a behaviour this change alters, which is what the project's testing rule asks for, and none of them restates the implementation or verifies a mock. The nested case earns its place: it pins that the recompute reads the restored definition rather than replaying a recorded flag, which is the design decision the fix rests on. Nothing was added for the five call sites with no reproduction behind them (the two table-variable constraint instructions, the column attach/detach pair, and the nilability one) — the handoff is right that nothing observable goes stale there today, and a test asserting a flag value rather than a behaviour would be a test of the implementation. The one defect found in review has its reproduction described in the ticket filed for it, where the fix that makes it pass can add it.

**Noticed and not acted on.** The forward and undo paths recompute in different places — the undo at each of eight instructions, the forward path incidentally during compilation — where the file's own event-handler mutators do it once, inside the mutator, and get both for free. Moving the eight into their mutators would do the same here and make the `AlterColumns` tripwire unnecessary. Considered and declined: the surrounding design deliberately recomputes once per statement at the DDL node (`CreateColumns` ends with exactly that call) rather than once per mutation, so putting it in the mutators would add work the compiler already does, inside loops over columns and constraints, on every catalog load. The filed ticket's second and third options reach the same end properly. `CatalogDeviceSession.cs` is 4,206 lines (`wc -l`), of which this change added 37; the size predates it by a wide margin and splitting it is not this ticket's business.

**Empty categories, with reasons.** No tripwire was parked for a conditional concern of this change's own: the only two conditional things found are the view's monotone recompute and the dead nilability recompute, and both are recorded in doc comments at their sites rather than as separate notes. No accepted-tradeoff `NOTE:` was found at any site touched, so nothing here had already been weighed and declined. No existing ticket claimed any of the four files (checked by grep across `backlog/`, `fix/`, `plan/`, `implement/`, `review/` and `blocked/`; the one hit on `CatalogDeviceSession.cs` is `implement/bug-rolled-back-session-operator-breaks-disconnect`, a different region and a different undo), so the one new ticket is filed fresh rather than appended as an arm to an existing one.

## Known gaps

- **A cancelled change to a *type*'s constraint or default can still strand the summary of the tables that use that type**, if anything reads one of those tables inside the same transaction. Reproduced and filed as `bug-rolled-back-type-constraint-stops-the-column-check`, with the three ways out and the measurement. The same ticket is where the whole defect class — a derived summary cached on a mutable catalog object with no invalidation — would be retired.
- **Which compilation inside an `alter table` statement recomputes the summary was not pinned.** That it happens is measured; the site is not. It is why the forward path needs no change today and why the `NOTE:` above `AlterColumns` says "by accident".
- **A rolled-back `create default` or `create constraint` still leaves the opposite kind of staleness** — a flag raised with nothing behind it, costing a call that finds nothing to do. Harmless, unchanged by this ticket, and recorded in the migration-notes row.
- **No remote client was exercised.** `ServerProcess` reads the same family to decide what to tell a client about a table, so the fix reaches that too, but the tests are all in process.
