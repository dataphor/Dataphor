## What landed

`libraries/PGSQLDevice` is an SDK project, in `Dataphor.slnx` and in the layout's Library list, and its translation is pinned by 26 checked-in files under `tests/goldens/devices/PGSQL/`. **No PostgreSQL server took part and none is needed** - and equally, nothing here says a PostgreSQL server accepts any of the text. `device-pgsql-port` is the pass that connects.

The implement stage is commit `ticket(implement): device-pgsql-device-golden`; the review stage is this commit.

### The conversion

`DAEDevicePGSQL.csproj` is `DAEDeviceMSSQL.csproj` with this device's files: assembly name `AlphoraPGSQLDevice`, `RootNamespace` left empty (the device loads `SystemCatalog.d4` and `SystemCatalog.sql` by their bare names), the legacy constants set minus `SIGNASSEMBLIES`, the explicit `Compile` list, the two `EmbeddedResource` items. `AssemblyInfo.cs` is trimmed to title, description, `DAERegister` and `Guid`. One reference the legacy project did not have, `DAE.Connection.PGSQL.csproj`: nothing in the assembly binds to a type in it - the connection class is resolved from a string through the registered library - and it is there so that building the device builds the connection library and both reach the layout.

The `DataphorD4Library Remove` line for `PGSQLDevice.d4l` is gone from `tools/layout/Layout.csproj`, so **every library folder in `libraries/`, `samples/` and `tests/libraries/` is now assembled**; this was the last exclusion. `AlphoraPGSQLDevice` is in `areas.json`'s `reported` list beside `AlphoraMSSQLDevice`.

### The fixture and the one change to the shared corpus

`PGSQLDeviceTranslationGoldenTests` is the second subclass of `DeviceTranslationGoldenTests`, carrying `PGSQLConnection` in its library list because `PGSQLDevice.d4l` requires it. `Port` and `SearchPath` are deliberately left unset, so the goldens pin what a definition naming only a server and a database gets.

The shared fixture gained a third case kind, `TranslationCaseKind.Connection`, and one corpus case using it: the connection string the device handed its connection class, pinned character for character. **The SQL Server device gains one golden too** (`tests/goldens/devices/MSSQL/Connection.sql`), which is the point of putting the case in the shared corpus rather than in one subclass. Collecting those strings also turned the `NOTE:` on `RecordedConnections` - that each data-definition statement opens a fresh connection - into an assertion the set-up makes for every statement case.

### What the goldens show

Every one of the 26 cases generated, so the fixture's unsupported-boundary mechanism records no exceptions and no expected-failure table was needed. The two devices' case sets are identical, so a folder diff is a pure dialect diff: `character varying`, `timestamp`, `date`, `time`, `uuid` and `bytea` for the T-SQL spellings; `create unique index` without `clustered`; `for update` where SQL Server has `(updlock)`; `char_length` for `DataLength`; `union all` with an outer `distinct` for plain `union`; `nulls first` on an order column that can be nil; and no `option (fast 1)`.

Three facts came out of producing the files, each recorded as a `NOTE:` tripwire at its site and in the plan's WS7 row, none filed as a ticket: `TranslateOrder` sets a T-SQL `option (fast 1)` modifier that this emitter never writes; the emitter's dummy-`from` suppression covers only the algebraic clause, so the key-check select still carries `from (select 0 as "dummy1") as "dummy1"` (valid PostgreSQL); and only 2 of the 61 operator classes in `PostgreSQLOperators.cs` are reachable, the rest being dead rather than latent because the map translates through `Storage.TranslationString` tags instead.

### On the board

An arm was appended to `tickets/backlog/bug-mssql-device-drops-datetime2-columns.md` rather than a new ticket being filed: that ticket already names the root cause and the one site, and the PostgreSQL device is the next instance of the same class. The substance is that `PostgreSQLDevice.ShouldIncludeColumn` and `FindScalarType` are the SQL Server case lists with a few PostgreSQL spellings added, missing `bytea`, `uuid`, `time without time zone`, `character`, `double precision` and the two `with time zone` types - so the device drops column types it creates itself, which `Table.AllTypes.sql` makes visible.

## Review findings

The implement diff was read in full before the handoff summary: the project conversion, the shared-fixture change, the new fixture, all 26 PostgreSQL goldens, both `Connection.sql` files and every documentation edit. Every measured claim in the handoff was re-measured from the sources rather than taken on trust. The work holds up - nothing in the diff is wrong - and the one thing worth doing was to move the riskiest of its unverified observations to where the next agent will actually meet it.

### What was checked, and what it showed

- **Every claim the handoff numbered.** `SystemCatalog.d4` has 14 live `PostgreSQLDevice.*` class references naming 13 distinct classes, 11 of them device scalar types (which live in `PostgreSQLTypes.cs`, so the "2 of 61 in `PostgreSQLOperators.cs`" count is right). `SQLDevice.GetDummyTableSpecifier` is used in four places, three of them building a `CalculusFromClause` - the Emitter `NOTE:`'s claim. `MajorVersion` is read nowhere in translation, so the base class's parenthesis about it is right. `ShouldDetermineVersion` does default to false in this device and true in the SQL Server one.
- **Every golden, line by line, and the two folders diffed against each other.** The differences are exactly the dialect list above and nothing else. The `union all` plus outer `distinct` workaround is sound: `NestQueryExpression` projects the whole row of the union's result, so the `distinct` dedups on the same columns `union` would have.
- **`SQLDevice.PostgreSQLBinary` does not exist**, as the backlog arm says: `libraries/SQLDevice/Documents/Register.d4` declares `MSSQLBinary` and nothing else, and `FindScalarType`'s `binary` and `timestamp` arms resolve that missing name. Confirmed, and the arm's `repro: static` is the honest label.
- **The embedded-resource names in the built assembly**, since an empty `RootNamespace` is the fragile part of the conversion: `artifacts/layout/debug/Libraries/PGSQLDevice/AlphoraPGSQLDevice.dll` contains the bare strings `SystemCatalog.d4` and `SystemCatalog.sql` and no namespace-prefixed variant.
- **The project conversion against its sibling.** The `.csproj` is `DAEDeviceMSSQL.csproj`'s shape with this device's files; keeping `[assembly: Guid]` matches the other converted libraries, including `PGSQLConnection`. Line endings and byte-order-mark state are preserved in every edited file (`git ls-files --eol`).
- **The documentation the change should have touched, including the files it did not.** `docs/coverage-report.md` is correctly left alone: everything below its head is generated output of one measured run (2026-11-21, commit `f6200026`) and hand-adding a device row would be inventing data - its table already omits the ODBC and PostgreSQL connection assemblies for the same reason. `docs/architecture/what-is-alive.md` already classifies "PGSQL device and connection" under *Working, lightly used*, which is still the right row. `tools/net-spike` genuinely does not list `PGSQLDevice`.

### Minor - fixed in this pass

- **`AGENTS.md` sent the next reader to the wrong file.** Its runtime-layout paragraph said an unconverted library is left out "by a `DataphorD4Library Remove` line in that project". The line goes in `tools/layout/Layout.csproj`, as the plan's own paragraph says, and the comment that used to explain the mechanism was deleted from that file along with the `PGSQLDevice` entry - so a reader following `AGENTS.md` would have gone looking in the library's own project and found nothing. Corrected to name `Layout.csproj`.
- **The `Connection` golden's provenance was stated too narrowly.** Two of its six keywords, `User Id` and `Password`, come from the device session's user rather than from the device definition - for this fixture, the harness's `Admin` with an empty password (`TestServerInstance.Connect`) - so the golden moves if the harness ever connects as someone else. The fixture's remarks now say so, and say that the empty `SearchPath=` in it is a no-op rather than a request to empty the search path.
- **The keyword legend behind that golden barely fires, and nothing said so.** `PostgreSQLDeviceSession.InternalCreateConnection` names its tags with the driver's own keywords (`Server`, `Port`, `Database`, `SearchPath`, `User Id`, `Password`), and `ConnectionStringBuilder.Map` passes an unknown tag through unchanged - so of `PostgreSQLConnectionStringBuilder`'s five entries, three map to themselves and `HostName`/`UserName` match nothing and are dead. That is the opposite of the SQL Server device, whose session writes abstract names and relies on its legend to translate them. It is not a defect and must not be "tidied" in either direction - a deployment may name its own builder through the device's `ConnectionStringBuilderClass` attribute, and a builder written against 3.1 has to key on the keywords this session actually produces - so a `NOTE:` at the legend now records which half is live, which is dead, and why both stay.
- **The handoff's claim that the fixture is a standing check on both embedded resources is half right.** A rename of `SystemCatalog.d4` would show up as a golden diff, because the type mapping would stop being registered; `SystemCatalog.sql` is only read by `EnsureOperators`, which the fixture turns off, and both loads skip silently on a null stream. Measured directly instead (above), so nothing is latent - but this record should not claim a net the fixture has not got.

### Measured, and the worry dismissed

**The empty `SearchPath=` the device always emits is harmless.** Reading the golden, the obvious question is whether handing the driver an empty search path sets an empty `search_path` on the server, which would break every unqualified identifier the device emits. Measured on the pinned driver (Npgsql 10.0.4) against a loopback listener that answers the SSL request and dumps the startup packet: with `SearchPath=` in the string the driver's search-path property reads back `null` and the startup packet carries no `search_path` parameter at all, byte for byte what omitting the keyword produces, while `SearchPath=public` does send it. Recorded in the existing `NOTE:` in `libraries/PGSQLConnection/Source/PostgreSQLConnection.cs`, which already held the prerequisite's keyword-by-keyword measurement. The throwaway probe project was deleted.

### Major - the one finding, parked where it will be read

**The `for update` placement was recorded only in a ticket that is about to be archived.** The handoff correctly identified it as the construct of this device's translation most likely to be rejected by a real server, and as the one whose rejection would affect every insert into a PostgreSQL device table rather than an edge case - but it said so in the review ticket's prose, which ends up in `complete/` and is eventually pruned. The live pass would not have met it. No new ticket: `tickets/implement/22.1-device-pgsql-port.md` already owns the live verification, so this is an arm on its expectation list, naming the golden that pins the text and the two questions to settle - whether PostgreSQL accepts a locking clause nested in an `exists` in an outer select's select list at all, and whether it then takes the lock the key check is asking for. A matching `NOTE:` sits at the site, `PostgreSQLRetrieve`'s `ForSpecifier.Update` assignment, for whoever is debugging a rejected insert.

### Tests: none added, one considered and kept

The new fixture and the `Connection` corpus case are the ticket's deliverable - the project rules' characterization test for a re-hosted subsystem, at the lowest layer that shows the behaviour - and no defect found in this pass is reproducible without a PostgreSQL server, so there was nothing to add.

One existing test was weighed for removal and kept: `EveryConnectionCarriesTheDevicesCompatibilityDefaults` is now strictly subsumed by the `Connection` golden, which pins the whole string including `Encrypt=False`, and for the PostgreSQL subclass it is a bare `Assert.Pass`. It stays because a golden cannot explain itself: when that string changes, this test is what fails with the reason the text has to be there, and its `Assert.Pass` message is the statement that this device defaults nothing. That is worth one cheap case.

### Deliberately nothing here

- **No ticket was filed.** The one defect the implement stage found was already an instance of a filed class and went on as an arm; the three conditional observations are tripwires at their sites. Nothing else met the filing bar.
- **No type mapping was changed**, `System.Boolean` to `integer` above all. Changing a type mapping with no server to check it against is the mistake this ticket exists to avoid, and `device-pgsql-port`'s expectation list already owns the device-versus-catalog-store boolean disagreement.
- **The golden extension was left as `.sql`** for the connection case, as the handoff proposed and invited disagreement on. Agreed with, for a reason the handoff did not give: `ExistingGoldens()` deliberately enumerates *every* file in the folder so that a stray one is reported, and one extension per case kind buys a more honest filename at the cost of making that check's bookkeeping conditional. The case is named `Connection` and its content is unmistakable.
- **The `Connection` case kind carries an empty `D4` string**, which no other kind does, and that was weighed too. Kept: the fixture already dispatches on `Kind`, and both the enum member and the `D4` property say what empty means there. Modelling it away would cost more machinery than the one field is worth.
- **No source file was reformatted or re-encoded**, and the two devices' emitters were left alone - including the `TSQLTextEmitter` class name in the `Language.PGSQL` namespace, a copy-paste misnomer from 2008 that a custom extension could reference.
