## The verdict

**Feasible, and demonstrated.** `ClientServer` + `LocalServer` — the client code the product ships, on the binding `DataphorServiceUtility.GetBinding()` builds, with no hook touched and no channel hand-rolled — completes real work against a .NET 10 server whose `IDataphorService` and `IListenerService` are hosted by CoreWCF 1.9.1 on that same binding. Seven tests, all passing, about a second of test time.

The write-up the ticket asked for is `### CoreWCF proof`, the last subsection of WS5 in `docs/modernization-plan.md`. It carries the verdict, each researched answer with its source, which claims rest on a test and which on inspection, the dynamic-port decision, and six items handed to `protocol-corewcf-host`.

## Judgment calls, re-weighed in review and kept

**1. `RemoteServer`'s constructor is now public.** The ticket said to wrap the engine server in `RemoteServer` from the test project, which was not possible: the constructor was `internal` to `AlphoraDataphorServer` and `DataphorServiceHost` was its only caller. The alternatives were `InternalsVisibleTo` (needs the strong-name public key hard-coded into a shipped assembly) or moving the proof host into the server assembly (which the ticket forbade, for good reason). Public is the right call: `DataphorService`'s only public constructor already takes a `RemoteServer`, so the type was unusable from outside regardless, and `protocol-corewcf-host` needs exactly this if hosting moves to its own assembly. It is additive and has a migration-notes entry. `RemoteServer.Server` stays `internal`, so nothing new is readable from outside.

**2. The Generic Host, not `WebHostBuilder`.** The ticket specified `new WebHostBuilder()` and one `IWebHost`. On .NET 10 those are obsolete (`ASPDEPR004`, `ASPDEPR008`) and produced three warnings in a brand-new file. `new HostBuilder().ConfigureWebHost(…)` configures CoreWCF identically, warns about nothing, and is the host `host-generic-host` is going to anyway; it is still one host and one hosting model, which was the ticket's stated reason for the constraint. The comment at the site says this.

**3. The dynamic port: reserved in advance, not port 0.** The ticket's primary route (base address `net.tcp://127.0.0.1:0/` plus relative endpoint addresses) cannot work here, for two reasons now written at the `ReserveLoopbackPorts` site and in the plan: the address table is built from the endpoint address before Kestrel binds, so the real port is not known in time; and two endpoints with relative addresses would both resolve against the first base address of the scheme, collapsing the product's two ports into one. So the host binds and releases two ephemeral loopback ports and registers absolute addresses on them. The release-then-bind window is a `NOTE:` at the site. This was reasoned rather than tried both ways; a reviewer who wants the port-0 route attempted empirically has the symptom to look for (the client failing to find an endpoint).

**4. The stream case proves the handle protocol, not a byte round trip on the wire.** `Allocate`, the length probe the first write makes, the close and `Deallocate` are all calls on the wire; the bytes stay in `LocalStreamManager`'s deferred-write cache, because `CoverStream.Flush` is a no-op and no public client API forces a flush (`FlushStreams` is internal to the cursor paths). This is what the shipped client does, so the case is honest about what it covers, and the comment in the test says so. Review left it and recorded the gap in the plan's hand-off list instead; see the findings.

## Defects met along the way

**Fixed here, with its reproduction: `RemoteServerProcess.Execute` dropped every parameter value.** It called `RemoteParamsToDataParams(paramsValue.Params)`, which reads only names, types and modifiers, instead of `RemoteParamDataToDataParams(paramsValue)`, which also decodes the values from `paramsValue.Data.Data`. So a parameterized statement run through `IServerProcess.Execute(statement, params)` over a network connection behaved as though every parameter were nil — "Value required for column …" on an insert, at every value size, measured from 16 bytes to 3 MB. The client encoded correctly throughout, so this is purely the server-side conversion. `RemoteServerPlan.Execute`, `Evaluate`, the cursor opens and `RemoteServerBatch.Execute` all use the right converter and were never affected, and neither was in-process execution; the two `RemoteParamsToDataParams` calls that remain in `RemoteServerProcess` are *Prepare* calls handed a `RemoteParam[]` with no data, and are correct (re-checked in review, along with `RemoteServerBatch`'s two, which are also prepare-only). A wrong API call with a one-line fix, so it was fixed here as the rules direct, with `TestLargeMessageInBothDirections` as the reproduction and a migration-notes entry. A `NOTE:` beside it records that the write-back re-encodes every parameter and not only the var and out ones, which `RemoteServerPlan.Execute` has always done too — fine now, worth narrowing if large input parameters ever show up as slow.

**Filed, because the fix is a design change: `bug-object-id-counter-is-process-wide`.** `Schema.Object`'s next-object-id counter is a process-wide `static int` and `Engine.InitializeCatalog` resets it to zero. `LocalServer` starts an engine of its own for the client-side catalog cache, so a process that runs an in-process server and then connects to it over the network hands the server identifiers its catalog already holds; the first `create table` in the proof failed with `UNIQUE constraint failed: DAEObjects.ID`. Reachable in a shipped configuration (the IDE with an embedded alias and a connection alias open at once), not reachable out of process, which is why it has survived. `severity: corruption`, `likelihood: unusual`. The proper fix threads an allocator through about fifteen call sites in the compiler and the plan nodes, so it is not a local fix; the proof's client helper works around it in three lines that hand the counter back, with a comment pointing at the ticket.

## Review findings

The implement-stage commit is `ticket(implement): protocol-corewcf-proof`. The diff was read before the handoff summary, and every file it touched plus the ones it should have touched were re-read against the new reality.

**Checked and found sound.** The parameter fix is the right converter and matches `RemoteServerPlan.Execute`; its reproduction was confirmed to actually reproduce (the one-liner was reverted, the suite rebuilt, and `TestLargeMessageInBothDirections` failed with "Value required for column Value", then the fix was restored). The client-side write-back (`LocalProcess.RemoteParamDataToDataParams`) applies only to parameters whose modifier is not `In`, so the pre-fix server behaviour never corrupted a caller's own parameter values — the migration note's wording is accurate. `TestOneServiceInstanceServesEveryConnection`'s inference holds: `HandleManager` seeds `_nextHandle` from a constant, so two per-connection managers would have minted the *same* first handle, and different handles do prove one manager. Host teardown order is right and double-dispose-safe (`DataphorService.Dispose` is idempotent, `RemoteServer.Dispose` detaches rather than disposes the engine server, and the engine server stays the caller's). The constructor's failure path disposes what it built and leaks neither a port nor the host. Nothing in the diff touches a compatibility surface that the rules protect: the three contract interfaces, the action URIs, the class registrations, the assembly names, the file formats, the error codes and the default ports are all as they were.

**Fixed in this pass.**

- `TestListensOnlyOnTheReservedPorts` claimed in its summary that "neither service is reachable on 8060 or 8061" but compared both ports against `DataphorServiceUtility.DefaultListenerPortNumber` (8060) twice and never against 8061. It now checks both ports against both defaults (8061 is `ServerConfiguration.DefaultPortNumber`), and null-guards the listener endpoint the way it already guarded the service one.
- `CoreWcfProofHost.InstanceName` and `CoreWcfProofHost.Service` were public properties with no caller, each with a summary claiming a test use that does not exist (the test builds the address from its own constant and establishes the singleton through the server name on the wire). Both removed; the backing fields stay.
- The `NOTE:` on `TestServerInstance` still said `port-catalog-emitter-race` "found no other unsafe static". A third is now known. It names the object-id counter and its ticket.
- The AGENTS.md "Converted so far" line still said the server is built "without its WCF service and host classes". Two of those classes are compiled now; the line says which half is still out.
- The plan's `protocol-corewcf-host` scope row still told that ticket to bring back six files including `DataphorService` and `ListenerService`, and the `plan/` ticket `protocol-corewcf-host` repeated it in a table. Both now say four files, and the ticket says explicitly that the two service classes are already compiled, not to re-exclude them, and that `DataphorService` has a single constructor taking a started `RemoteServer`.

**Test added — one, for a contract the implementation left unverified.** The binding is declared twice, against the unrelated `Binding` hierarchies of `CoreWCF.Channels` and `System.ServiceModel.Channels`, and the implement stage shared only the four size limits (both copies read `DataphorServiceUtility.MaxMessageLength`) and handed "settle on a shared settings source or a test that compares the two" to `protocol-corewcf-host`. The whole proof rests on the two halves saying the same thing, and a one-sided edit to either would change the protocol silently. `TestHostBindingMatchesTheClientBinding` compares the element list and its order, the four limits, both timeouts, the transfer mode and the message version — and deliberately nothing the two stacks are free to default differently. It needed `CoreWcfProofHost.BuildBinding` to go from `private` to `internal` (same assembly). Confirmed to fail on drift: changing the host's `SendTimeout` to one minute failed it with the two values; restored. It also establishes, rather than assumes, that CoreWCF's defaults for transfer mode (`Buffered`) and message version match the client's. The plan's hand-off bullet now records that the test exists and that a shared settings source would retire it.

**Tests weighed and kept as they are.** All six original cases earn their place: five exercise protocol behaviour that nothing else covers, and `TestListensOnlyOnTheReservedPorts`, which is the one closest to testing configuration, is also the guard that the proof can never bind a port a real instance on a build machine owns — worth 1 ms. None restates the implementation, none verifies a mock, and none was cut.

**Tripwires parked (not tickets — each is fine now and only becomes work if its condition trips).**

- `RemoteServerProcess.Execute` (`NOTE:` at the site, written by the implement stage, re-read and kept): the parameter write-back re-encodes input parameters too, so a large input parameter is echoed back and discarded; narrow both this and `RemoteServerPlan.Execute` if that ever shows up as slow.
- `CoreWcfProofHost.ReserveLoopbackPorts` (`NOTE:` at the site, likewise): another process could take a reserved port between the release and CoreWCF's bind.
- The ASP.NET Core framework reference makes the *whole* `DAE.Server.Tests` assembly, not just the seven new cases, need the ASP.NET Core shared runtime to launch. Already stated in the csproj comment above the reference and in the plan; no further action, but it is the thing to look at first if the suite ever fails to start on a runtime-only machine.

**Measured and handed on, in the plan's hand-off list.**

- A client that connects by a host name resolving to IPv6 first pays **2.046 s per channel open** against a listener bound to IPv4 only, versus 0.016 s for the literal (isolated from Dataphor entirely with a bare socket test). Today's `ServiceHost` binds the IPv6 wildcard dual-stack and does not have this problem, and real clients connect by host name, so `protocol-corewcf-host` must get the listen address right. It is also why the test's client uses `127.0.0.1` rather than `localhost` — which means **the host-name wildcard path is not exercised** by any test here.
- `CoreWCF.Primitives` adds **31 packages** to `AlphoraDataphorServer`'s runtime closure that nothing else there needed — eight `Microsoft.AspNetCore.*` **2.3.10**, twelve `Microsoft.Extensions.*`, five `Microsoft.IdentityModel.*` (including SAML), `System.DirectoryServices`, `System.Web.Services.Description` and others — and they are in the layout's `bin/` now. `DAE.Client` references the server assembly, so the WinForms client and the IDE inherit them. Nothing runs from `bin/` until `host-generic-host`, so this costs only disk today, but shipping ASP.NET Core 2.3.10 assemblies beside .NET 10 is the kind of thing `security-dependency-audit` will object to. A separate hosting assembly is the obvious answer and is on `protocol-corewcf-host`'s list; no separate ticket, because that scope already owns the decision.
- **Added to the list in review:** streamed (non-native) values crossing the wire are unproven, for the reason in *Judgment calls* 4 above. A cursor update carrying an overflow value is the production path that flushes; it belongs with the real services, not with a proof host.

A full build (`--no-incremental`) reports 143 warnings, all pre-existing in other projects; an incremental build over an already-built tree reports 0 because nothing recompiles. The substantive claim — no warning from either new file — is true and was re-confirmed. Noted because a later ticket could otherwise read "0 warnings" as this repository's warning baseline, which it is not.

**No tickets filed by the review.** Every finding was either fixed in this pass, already owned by a scope on the board (`protocol-corewcf-host` for the listen address, the nested address, the dependency closure and the stream gap; `bug-object-id-counter-is-process-wide`, which a concurrent board move has already promoted to `plan/`, for the object-id counter), or genuinely conditional and parked as a tripwire. Nothing met the filing bar on its own.

**Gaps that remain, stated plainly.**

- **Nested addresses on one port are untested.** The native CLI endpoint `.../service/native` sits below the main endpoint `.../service`; this proof hosts two *sibling* addresses on two ports. CoreWCF's `UriPrefixTable` should resolve the longer registration first, but that is inference. First thing for `protocol-corewcf-host`.
- **Infinite timeouts are established by inspection only**, with the citations in the plan, because a test that is allowed to finish cannot demonstrate an infinite timeout and nothing here should add a sleep to the suite. The plan says this plainly rather than implying otherwise.
- **The native CLI service is not hosted.** Only the two services the ticket named are, so `NativeCLIService` and `INativeCLIService` are still out of the server's compile list. Its client contract is structurally identical to the other two (same contract-name and namespace pattern, every operation an `AsyncPattern = true` `Begin`/`End` pair with a `[FaultContract]`), so it is the same case and the same mechanism — but it is not proven.
- **`CoreWcfProofHost.Dispose` gives Kestrel a 10-second bounded stop** rather than waiting indefinitely, because a client channel may still be open and the binding's receive timeout is infinite. If a test ever leaves a channel open at teardown, that becomes a 10-second pause rather than a hang. No test does today; all seven close their clients.
- **`using System.Collections;` stays in `DataphorService.cs`.** It looks dead next to the deleted constructor but is not: `BitArray` in the `Insert` and `Update` operations needs it.
- **The fixture is not `[Parallelizable]`**, because two servers in one process share engine static state, and the object-id counter is a third instance of that class after the catalog emitter (K1) and the keyword tables (K25).
- **`tickets/.garden-report.md`** and the promotion of `bug-object-id-counter-is-process-wide` from `backlog/` to `plan/` were in the working tree during this run, done by something other than this ticket, and were left alone.
