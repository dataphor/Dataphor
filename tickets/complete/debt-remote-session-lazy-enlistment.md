## Vocabulary, for a reader without the context

A *server link* is a D4 object naming another Dataphor server. The first `ExecuteOn`, `EvaluateOn` or `select … on <link>` opens a connection to that server and the session's process keeps it; the engine calls such a connection a **remote session**, and `System.RemoteSessions` lists them. A process also holds one **device session** per back-end database it has used. Both are *participants* in the process's transactions. *Enlisting* a connection in a transaction means beginning a transaction on the other server, one begin per local transaction level.

This work was only about connections to other **Dataphor** servers. Device sessions are still enlisted eagerly and nothing about them changed.

## What landed

The eager begin is gone. `ServerProcess.InternalBeginTransaction` no longer speaks to any connection to another Dataphor server; such a connection joins the process's open levels when a statement uses that link, through the new `ServerProcess.EnlistRemoteSession`, which `RemoteConnect` calls on every use. A connection's open levels are therefore a contiguous prefix of the process's level stack, and the prepare, the commit and the rollback each ask a connection only about the level it is ending, through the existing `ServerProcess.HoldsEndingLevel`. The dead-connection reclaim moved with the begin: it now lives in `RemoteConnect`'s held-connection arm, where a connection whose catch-up fails while it holds no level of its own is let go and the same use reconnects once, and one that holds a level fails the use and is kept.

Implemented in `ticket(implement): debt-remote-session-lazy-enlistment`; reviewed and corrected in this ticket's own commit.

## What it costs and what it saves

Measured as a count of calls the process makes on the connection, with `ConnectionTransactionLevelTest`'s `RecordingRemoteSession` standing in for it - exact and deterministic, and each of those calls is one network round trip in a deployment. On a session holding one connection, under the default `UseImplicitTransactions`, for a statement that has nothing to do with the link: a statement that succeeds cost **3** calls (begin, prepare, commit) and now costs **0**; one that fails at run time cost **2** (begin, rollback) and now costs **0**; one the compiler rejects cost 0 before and after, because the implicit transaction is begun after compilation. Both "before" figures were read off a real pre-change run. No wall-clock figure: this suite has no second server on a network to measure one against. With implicit transactions off the saving is per *begin* rather than per statement, which is the smaller case.

The cost, accepted by the owner on 2026-11-22 and recorded in `docs/migration-notes.md`: a remote read inside a transaction now sees the other server's state as of this process's **first use of that link inside the transaction**, not as of the transaction's start. Two statements in one local transaction that both use the link are still consistent with each other - they share one remote transaction. An application that needs the old timing touches the link at the top of the transaction (`ExecuteOn('<link>', 'select 1;')` is enough). Nothing else changed: the remote half of a transaction is still committed and rolled back with its local half, and the sequential commit's partial-failure behaviour (`ServerTransaction.CommitBegun`, error 106213) is untouched.

## Review findings

Read the implement diff before the handoff summary: engine first, then the tests, then the docs. Lint here is the build's own analyzers; `dotnet build Dataphor.slnx` is clean with no new warnings.

**Checked and found sound.** The prefix invariant on `RemoteSession.TransactionCount` is the load-bearing claim, and its proof sketch holds against every site it names. `ServerTransactions.BeginTransaction` appends and `CurrentTransaction()` reads `Count - 1`, so `_transactions[j]` really is level *j* and `EnlistRemoteSession`'s ascending catch-up gives a prefix rather than an arbitrary subset. All three ending operations guard their remote loop with `HoldsEndingLevel` (the rollback's guard was already there before this work). The "never greater" half of the assertion the prepare used to carry survives inside `HoldsEndingLevel`, so the swap lost nothing. `RemoteConnect` retries exactly once - the discard falls through to the connect and a failure there reaches the caller, with no second path in - and `DiscardRemoteSession` disowns the entry before disposing it, so the fall-through `Add` cannot leave two entries for one link. The broad `catch` in the held-connection arm cannot launder an internal error into a silent reconnect: for `EnlistRemoteSession`'s `Error.AssertFail` to fire at all, the count must exceed the process's depth and so be at least 1, which makes `InTransaction` true and the arm rethrow. Traced the partial-commit interaction, a three-level partial enlistment, per-level isolation levels, and the nested transaction `ServerTransaction.InvokeDeferredHandlers` begins around deferred handlers: the prefix survives each. With `UseImplicitTransactions` off and no open transaction a use makes no call, so a dead connection is not reclaimed - unchanged from before this work, and correctly scoped in both the migration note and the `DiscardRemoteSession` note.

**The funnel claim was re-verified independently, not taken on the note's word.** It is the premise the whole design rests on, so all six callers of `RemoteConnect` were read. `select … on <link>` materialises the whole remote table through `Evaluate` at `TableNodes.cs:2562` and wraps it in a `LocalTable`, so no remote cursor is held across fetches; the one site that *does* hold a cursor, `Runtime.Data/SystemTableValues.cs:45`, is inside `#if OnExpression` and is not compiled. A held cursor would have been the one way work reached a connection outside the funnel, and there is none.

**The deferred-validation tripwire: the judgement is right, and one more way in was ruled out.** The `NOTE:` at `InternalPrepareTransaction` records that deferred handlers and deferred constraint validation run after the participant loops, so an expression there that uses a link enlists the connection into the level being prepared, after the prepare has passed it by. Chasing whether a wider, client-reachable path exists: `IServerProcess.PrepareTransaction()` is public (WCF, NativeCLI and Thrift all expose it), so `BeginTransaction`, `PrepareTransaction`, `ExecuteOn('<link>', …)`, `CommitTransaction` looked like a second and much simpler way in. It is not: `ServerProcess.BeginTransactionalCall` sets `CurrentTransaction().Prepared = false` on every statement, so the commit's own prepare re-runs and does reach the newly enlisted connection. The window is genuinely confined to the deferred paths, where the statements run on a *nested* transaction object (or on no transactional call at all) and so leave the outer level's `Prepared` untouched. And nothing is actually lost there: a Dataphor server's own commit prepares first, and remote sessions commit before any device session, so a remote failure still happens before anything local has committed. It is a lost early-failure *opportunity*, not a defect - correctly a tripwire, correctly not a ticket.

## Tests

### Five new cases in `tests/DAE.Server.Tests/ConnectionTransactionLevelTest.cs`

Each was seen to fail before the engine edit, and each pins something the call log alone would not show.

- `TestAStatementThatDoesNotUseALinkMakesNoCallOnItsConnection` - where the measurement above is taken; carries the successful and the run-time-failing statement under one `Assert.Multiple` so one path's count is not hidden by the other's failure.
- `TestALinkUsedAtTwoLevelsIsEnlistedAtEachAsItIsReached` - the connection joins the second level at the use, not at the begin, each level at its own isolation level. The discriminator is the count read between the begin and the use; the call log is identical before and after, because the only thing that moved is *when* the begin happens.
- `TestACommitOfALevelTheConnectionDoesNotHoldSkipsIt` - the case that would trip the assertion the prepare used to carry.
- `TestADeadConnectionHoldingNoLevelIsLetGoWhenTheLinkIsUsedAgain` - the moved reclaim. Deliberately runs a statement that does *not* use the link while the connection is dead and asserts nothing happened; without that arm the case passed both before and after, since the reclaim only changed site.
- `TestADeadConnectionHoldingALevelFailsTheUseAndIsKept` - the participant arm: the use fails reporting error 106212, the connection is kept, and the one level its part-way catch-up had already opened is kept too (a shorter prefix is legal; nothing is unwound).

`RecordingRemoteSession` gained `FailNextBegin` beside its `FailNextCommit`, and `ConstructionCount` so a case can tell a reconnect from a kept connection; both are reset in `[SetUp]` with the other statics.

### Four adapted cases

- `ConnectionTransactionLevelTest.TestRollbackAfterAFailedRemoteCommitKeepsTheOuterLevel` - one line added so the link is used again inside the inner level, which is what enlists the connection in it; everything it asserts is unchanged.
- `ServerLinkConnectionTest.TestADeadConnectionIsLetGoAndTheStatementRuns` became `TestADeadConnectionStopsFailingStatementsAndIsLetGoAtTheNextUse` - the statement still runs, but the connection is now kept, and the use that finds it dead is what lets it go.
- `ServerLinkConnectionTest.TestOnlyTheConnectionWhoseServerHasGoneIsLetGo` - same shape, name unchanged: both connections are kept after the child server stops, and using the dead link lets only it go.
- `ServerLinkConnectionTest.TestABeginOnADeadParticipantFailsNamingTheLink` became `TestAUseOfADeadParticipantFailsNamingTheLink` - the nested begin now succeeds (asserted) and the failure moved to the use. It also pins the asymmetry in the unwind: the rollback of the level the connection does not hold is quiet, the rollback of the level it does hold reports, and the session recovers afterwards.

### Verified by inspection only

Application transactions touch neither `RemoteSessions` nor the process's level stack (`ApplicationTransactionTest` passes but exercises no server link). `System.RemoteSessions` reports link name and process id only (`CatalogDevice.PopulateRemoteSessions`), so the change cannot affect its columns. The compile-time use through `Plan.RemoteConnect` enlists during compilation, and with a cached plan the enlistment comes from the runtime path instead - either way the connection is enlisted before any remote work runs; no test covers `select … on <link>` at all in this suite, the `ServerLink` coverage script using `ExecuteOn`/`EvaluateOn`. `CatalogDeviceSession.CloseRemoteSession` still defers the close on `ServerProcess.InTransaction` rather than on the connection's own count, which is conservative and correct, and its remarks now say why.

## Compatibility

Nothing on the compatibility list changed: no D4 semantics or operator signatures, no registered class names, no assembly names or namespaces, no file formats, no error codes (106212 and 106213 keep their meanings and their sites), no WCF contract shapes, no ports, no on-disk layout. No public type or member changed shape; `RemoteSession.TransactionCount`'s *range* widened, which `docs/migration-notes.md` covers. The three behaviour changes an application can notice - when a remote read's snapshot is taken, when a dead connection is released, and where error 106212 now sits in an exception chain - are all in `docs/migration-notes.md`.
