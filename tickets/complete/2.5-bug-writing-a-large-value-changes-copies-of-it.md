description: Changing the contents of a picture or document value used to change every copy taken of it earlier, so a value a routine had put aside for safekeeping silently became the new value too. Each copy now gets its own contents at the moment the original is written.

## What landed

The engine keeps the two D4 types too large to carry inline - `Binary` and `Graphic` - in a stream it owns, and copying such a value does not copy its bytes: the copy is a *reference* to the original's stream, and the two are meant to be given contents of their own the first time either is written. That separation only ran in one direction. `ServerStreamManager.Change` handled the write that goes *through a copy*, and did nothing for the write that goes *through the original*, so that write landed in the one stream every copy was still reading through, and every copy followed it.

`Change` now has a second arm for the stream that is a source with references outstanding: before the write lands, each outstanding reference is given a stream of its own in the provider, holding the source's current contents. Two things about it are not obvious and are commented at the site. The source's stream position has to be saved and restored around the copying, because the copy reads the source to its end and the caller has already positioned the source for the write it is about to make. And a reference that is not currently open is given its provider entry but has no stream object to repoint, which is correct: it is no longer a referencing header, so its next open takes the other arm and finds the entry made for it.

The re-parenting alternative - hand the provider entry to the references and give the source a fresh one, the way `Deallocate` does in the middle of a reference chain - was weighed in the fix stage and rejected as the larger change on the more delicate path. The cost difference is recorded at the site as a tripwire rather than paid now.

The implement stage is commit `ticket(implement): bug-writing-a-large-value-changes-copies-of-it`, over the research in `ticket(fix): bug-writing-a-large-value-changes-copies-of-it`. Review changed two things in that work and appended an arm to an open ticket; all three are below.

## Review findings

Read the implement diff first with no handoff in hand, then the handoff. The logic was then checked by reading every class the new arm touches - `ServerStream`, `CoverStream`, `ManagedStream`, `MemoryStreamProvider`, `StreamManager` - and by tracing the arm against each reference shape the manager can be in: a sibling set, a reference that is itself a source, a reference below a written middle, a reference that has been closed, a header whose provider is not the default one, and the two orders in which a client's local cache can flush a source and its copy.

### Checked and sound

- **The position save and restore is load-bearing, and the handoff's reason for it is the right one.** Every holder reaches the stream through a `CoverStream` (a `ManagedStream` is one), and a cover sets its source's position immediately *before* the call it is making - so the caller has already positioned the source for its write by the time `Change` runs, and the copying then moves that position to the end. The implement stage confirmed by removal that two cases fail without the restore, and the mechanism checks out by reading: without it the write appends past the old value instead of landing over it.
- **Both shapes of the new arm's one conditional are reached.** `ServerStreamManagerTest` drives references that are open, so it takes the repointing shape; the D4 case takes the other, because a copy that has never been read has no stream object yet. Neither was stated in the handoff; both were confirmed by reading the open path.
- **A reference that is itself a source, and a reference below one.** Traced four orders - write the source, write the middle, write the middle then the source, write the source then the middle - against the manager's two reference maps and `MoveReferences`. Every one leaves each holder reading the value it was taken from. The chain case had no test and now has one; see below.
- **Nothing leaks in the provider.** The new arm creates a provider entry per reference separated. A separated reference is no longer a referencing header, so its `Deallocate` takes the arm that destroys its provider entry rather than the arm that destroys nothing - which is what keeps the fixture's "the manager is holding nothing" assertions meaningful after the change.
- **A header whose provider is not the default one.** The arm mixes `_defaultProvider.Create` with `InternalCopy`'s use of each header's own `Provider`. That is safe because a reference's provider is always the default one (`Reference` registers it that way), and the one path that changes a header's provider - the re-parenting in `Deallocate` - also stops it being a reference. Same mix as the arm that was already there.
- **The client stack has no sibling of this defect.** `LocalStreamManager.Reference` either deep-copies a locally modified value at once or delegates to the server, so a client's write reaches `ServerStreamManager.Change` when its cache flushes and the fix covers it. Both flush orders - source first, copy first - were traced and both are correct.
- **Concurrency says nothing new.** Every public method of the manager is `lock (this)` and the new arm runs inside it; the one re-entrant call it makes (`ServerStream.Position`, which can call back into `Change`) is a no-op by then because the references have been cleared. Nothing here speaks to contention, and nothing in it is new.
- **Documentation.** No page under `docs/architecture/` mentions the stream manager, copy-on-write or stream references at all, and `docs/modernization-plan.md` has no entry this behaviour would date, so there was nothing to bring up to date beyond the migration-notes row the implement stage added. `python tools/docs-size-check/check_size.py` passes (11 files, 0 over the limit). The link checker reports 203 errors, all of them missing `docs/reference/system-library/` pages linked from the developers' and users' guides: pre-existing, nothing in this change's surface, and not yet gated by `.github/workflows/docs.yml` (`docs-link-check-ci` owns that).
- **Source hygiene.** `ServerStreamManager.cs` has no byte-order mark, CRLF throughout and tab indentation; `ServerStreamManagerTest.cs` has a mark. Both preserved, verified by byte count rather than by eye - an intermediate edit of mine had doubled the carriage returns in the engine file, and that was repaired before anything else was run.

### Fixed in this pass

- **The new arm duplicated the three-step the arm above it already does, and narrated itself.** "Create a provider entry, copy into it, point the stream at it" appeared twice in one method, and the second copy carried a comment per statement. `Change` had reached 70 lines, 20 of them a comment block inside one branch. Extracted two private methods - `GiveOwnCopy(sourceHeader, targetHeader)` for the three-step, used by both arms, and `SeparateReferences(header, stream)` for the loop and the position restore - leaving `Change` at 25 lines that read as its two cases. The narrating comments are gone, subsumed by the names; the two `NOTE:` tripwires and the position-restore comment moved with the code they belong to, reworded where they said "above" or "below" about a line that is now elsewhere. Both new members are `private`, not `protected` like the older helpers beside them: nothing subclasses `ServerStreamManager`, so this adds no surface a C# extension could notice and needs no migration note. Behaviour is identical - the one difference, a null check on the target's stream that the already-existing arm did not have, cannot fire there, because the stream being written is open by definition.
- **A contract the new arm has to honour had no test: a source with a *chain* of references below it.** Every existing case has siblings - references that are all in the written stream's own reference list. A reference taken from a reference is not in that list; it hangs off the one that is, and the loop never sees it. What keeps it reading the old value is that the reference above it does, through the indirection the open path builds. That is a different structure from the one the fixture covered, so `WritingASourceLeavesAReferenceChainBelowItReadingTheValueItWasTakenFrom` was added to `ServerStreamManagerTest` - one case, three assertions: the source reads its new value, the reference reads the old one, the reference two deep reads the old one. Confirmed discriminating: with the new arm left unreached, the case fails on the middle reference, alongside the three other cases this work owns.

### An arm appended to an open ticket

`tickets/implement/4-debt-streams-coverage.md` owns the D4-level stream coverage script and names `src/engine/DAE/Streams/ServerStreamManager.cs` in its `files:`, so the site-claim grep found it rather than anything new being filed. Its copy-on-write bullet asked only for writes through the *copy* and through the *middle of a chain* - the direction that already worked. The bullet now also asks for the write through the **original**, says that direction did nothing before this fix, and records that the engine's `StreamCount()` does not move for it either, because separating a copy gives it a stream in the provider but no new header and that operator counts headers. No new ticket: the script that would hold the assertion is already filed and not yet worked.

### Checked and deliberately left alone

- **The open-count bookkeeping is still one high per reference separated, and stays that way.** Repointing a reference's source drops the cover it was holding over the written stream without closing it and without the matching close on the manager's side. It is inert: the default provider's `Close` is a no-op, `Deallocate` removes a header whatever its count, and the only visible consequence is that the written stream's header object outlives its last holder until the deallocate. It is also exactly what the arm above it and the two "Shouldn't this close the old stream?" comments elsewhere in the file already do, so fixing it here would fix one of four sites. Left as the implement stage's tripwire, with the file-backed provider named as the condition that makes it real.
- **The arm is not atomic against an exception part-way through.** If copying the value for the second of two references threw, the first would be separated and the second would be dereferenced with no copy to read. Reaching it needs the copy itself to fail, which with the in-memory provider means running out of memory mid-copy, and the arm above it has the same shape. The position restore, which is the part that looks like it wants a `finally`, does not need one: the write that would have used it never happens, and every holder re-establishes the position through its cover before its next call. Judged below the bar for a ticket and below the bar for a third `NOTE:` at a site that already carries two; recorded here instead.
- **The cost claims in the first `NOTE:` are counts of copies read off the code, not timings.** The handoff says so and it is true: nothing in this work was measured. The note's own last sentence names what to reach for if it ever shows up as slow, which is the right shape for a tripwire and not something to turn into a performance ticket on no evidence.
- **The copy shapes other than declaration still have no automated case,** which the handoff flagged as a gap. It is not one. Every shape a stream-backed value is copied in - at declaration, by a later assignment, into a row column, into an operator argument - reaches the manager's `Reference` through `DataValue.CopyNative` or `DataValue.CopyValue`, and a grep for the callers of `Reference` across the engine confirms those are the only two value-copy sites. One site governs all of them, so a case per shape would assert the same thing four times. The chain case above was added instead, because reference *depth* changes the structure the new code walks where copy *shape* does not.
- **`StreamAllocation` stays skipped.** It is the one coverage script about stream counts, and it is recorded as a known failure for an unrelated reason - it loads documents from a `Coverage` library the coverage template does not register. Read it to be sure: nothing in it touches the copy-on-write path, and `test-pre-3-1-scripts-policy` owns its fate. `ScalarAllocation` and `RowAllocation`, which the implement stage ran, hold only comments and assert nothing; they were kept in the filter for continuity, not for coverage.

### Tripwires: none added

The two the implement stage left in the new arm were read and both still hold; they moved into `SeparateReferences` with the code, reworded only where they pointed at a line by position. Nothing new was parked - the two things this pass noticed and did not act on (the exception path and the unmeasured cost) are in the findings above rather than at the site, because the site already carries two notes and neither of these adds a condition a future reader would need to meet there.
