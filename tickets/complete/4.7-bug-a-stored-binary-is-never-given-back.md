## Outcome: withdrawal, not a fix. The engine was not changed.

The original report said that an insert of a `Binary` or `Graphic` value into a table column costs the server one managed stream that it holds until the table is dropped. It does not. The fix stage measured that a committed insert, update or delete leaves the server holding exactly as many streams as before it; the report had measured those statements from inside one open transaction, where the device session's undo log legitimately holds one stream per logged write. The rule that holds is:

> One managed stream per logged write of a stream-backed value, held for the life of the transaction that made the write, released when that transaction ends - on commit or on rollback alike. An ordinary statement is its own transaction, so an ordinary statement is balanced.

So the work was to stop the tracked files that asserted the withdrawn claim from saying it, and to pin the real rule with a test. Both done, in `ticket(implement): bug-a-stored-binary-is-never-given-back` and this review.

## What changed

**`tests/libraries/TestFramework.Coverage.Scripts/Documents/StreamValues.d4`** - the header bullet and the row section's "what is not asserted" paragraph now state the measured rule instead of naming a bug, and a new top-level section runs an insert, an update, a delete and a drop of a `Binary` table column, each as its own statement, each followed by a balance assertion against a floor taken after the table was created, with read-back assertions beside them so a balanced-but-wrong write cannot pass.

**`tests/DAE.Server.Tests/coverage-manifest.json`** - the `StreamValues` entry carries `"batches": true`, so the script runs batch by batch (one implicit transaction per statement) rather than nested inside one `ExecuteScript` statement whose transaction stays open for the whole file. Without it the new section's statements all fall inside that one transaction and the assertions fail.

**`src/engine/DAE/Runtime/Program.cs`** - the `NOTE:` listing the leaks that block a debug-only stream-balance check no longer names this one, and records that it was measured and is not a leak.

**`src/engine/DAE/Schema/Device.cs`** - a `NOTE:` at the `row.Copy()` in `DeviceSession.InsertRow` records why the undo entry costs a managed stream and what releases it.

## Review findings

Read the implement diff before the handoff, then the whole script, `DeviceSession.InsertRow`/`UpdateRow`/`DeleteRow`, `DeviceTransaction.Dispose`, `DeviceTransactions.EndTransaction`, the manifest's own documentation of `batches` in `CoverageManifest.cs`, and the batch path in `CoverageScripts.cs`.

### Fixed in this pass

- **The `Device.cs` `NOTE:` was imprecise about nested transactions and spoke only for the insert.** It said the stream is released "when the transaction ends, by `DeviceTransaction.Dispose` on either commit or rollback". A nested transaction that commits does not dispose its entries: `DeviceTransactions.EndTransaction` appends them to its parent, so the release waits for the outermost transaction. The note now says that, and also covers the two sibling methods a reader arrives at with the same question - `UpdateRow`, which logs two row copies and so one stream (the old row comes from the device and holds its value as bytes), and `DeleteRow`, whose copy is of such a device row and so costs none. Without that, the two sites beside the documented one say nothing.
- **A turned-back `batches` flag would have failed the new section with a message indistinguishable from the withdrawn claim.** The implementer's own first run produced `A committed insert of a Binary left 1 stream(s) held.` - which is precisely the sentence the whole ticket exists to deny, and the next reader to see it would reasonably re-open the bug. The three count assertions now append a hint naming the manifest entry, from one variable declared above them.
- **A `TransactionCount() = 0` guard was tried instead, and discarded, because it does not work.** `TransactionCount()` reads 1 at the script's top level in *both* modes (measured: the guard fired at depth 1 under `batches: true`); what differs between the modes is whether that transaction outlives the statement, which is the very thing the assertions measure. The comment at the site records this so the next reader does not spend the same hour on it.

### Checked and kept as written

- **The `batches: true` route, which the handoff flagged as its one judgement call.** Kept. The alternative - a C# test in `DAE.Server.Tests` over the in-process harness - is legitimate, but the project rules prefer the lowest layer that shows the behaviour, and the assertions belong beside the row section they correct. What the flip costs was checked rather than assumed: no manifest entry is a `fragment` of `StreamValues` and no other entry names it, so nothing else depends on how it runs; around 200 other entries still exercise the nested `ExecuteScript` route, so that route is not left uncovered; and the batch path (`process.ExecuteScript(text)` in `CoverageScripts.cs`) throws on the first failing batch, so a failure anywhere in the script is still detected exactly as before. The manifest's own documentation of `batches` names "must see a batch's work committed" as the case for it, which is this case.
- **The new section's teeth were demonstrated rather than assumed.** It failed under the nested route - that is how the need for `batches` was found - and passes under batch-by-batch execution.
- **The `USEMEMORYDEVICETRANSACTIONS` claim in the new `NOTE:` holds.** The symbol appears only in `#if` directives in `MemoryDevice.cs` and in no `.csproj`, `.props`, `.targets` or `.slnx` in the tree, so the memory device keeps no undo information of its own and the engine's log is load-bearing.
- **The corrected `Program.cs` note matches the board.** `bug-a-loop-variable-stays-borrowed-after-the-loop` and `bug-ifnil-leaks-the-value-it-copies` are both in `tickets/fix/`; the third slug it used to name is in `tickets/complete/`.
- **No migration note is owed**, as the handoff said: nothing here changes a surface an application, a deployment script or a C# extension could notice.

### Found and parked, not filed
