## Review findings

The implement diff was read before the handoff. Every claim the script's comments make about *why* an expression produces its result was traced through `Compiler.cs` lines 12582-12790, and two assertions were deliberately broken, built, run and reverted to show they are not vacuous.

### Checked and sound

- **The five error codes are the five throws.** `CompilerException.Codes` gives `AmbiguousTableIndexerKey = 105259`, `UnresolvedTableIndexerKey = 105260`, `InvalidTableIndexerKey = 105261`, `TooManyTermsForImplicitTableIndexer = 105264`, `PotentiallyAmbiguousImplicitTableIndexer = 105275`, and those are the names at `Compiler.cs` 12624, 12636, 12695, 12720 and 12724 — the same five line numbers the handoff measured, unchanged in the tree as reviewed.
- **Each error case reaches its throw for the reason its comment gives.** 105264 is thrown on `terms.Length > 5` before the loop over the table's keys, so the comment's "checked before any key is looked at" is right. 105275 comes from the signature-collision check inside that loop, which admits only keys whose column count equals the term count and compares their signatures by type, never by column name — so it fires for `TableIndexerSameTypeKeys` (two `Integer` keys) and not for `TableIndexerTwoKeys` (an `Integer` key and a `String` one), exactly as the two tables are set up to show. 105259 is the `PathLength == shortestPathLength` arm of the tie-break, which both orderings of two `Integer` terms against one `{ A, B }` key reach. 105260 is a single throw with two ways in, and the script exercises both: `operatorSignatures.Count == 0` when no key has that many columns, and `signatureIndex == -1` when a key of that width exists but no permutation of the terms resolves against it. 105261 is the `resolvedKey.Columns.Count != expression.Expressions.Count` check *after* the by-clause branch, which only the explicit form can fail, because the implicit form builds the resolved key from the terms themselves.
- **The type-mismatch arm of 105260 rests on a fact, not an assumption.** The script's header asserts the system's only implicit conversions are among the numeric types, `Date` to `DateTime`, and `String` to and from `Name`. That is the complete set: thirteen `create conversion` statements, `SystemCatalog.d4` 1118-1128 and `DataTypes.d4` 549-550. There is no `String` to `Integer`, so `TableIndexerSingle['One']` cannot be quietly converted into a match.
- **The permutation assertion covers what it claims.** For `TableIndexerWidths['x', 20]` the matching permutation is `[2, 1]`, and the rebuild (`signatureKey.Columns[IndexOf(permutation, index + 1)]`) therefore yields the key `{ B, A }` and the condition `B = 'x' and A = 20` — row `ID` 4, the same row as `[20, 'x']`. Traced by hand, then confirmed by mutation (below). All four combinations of `A` and `B` are rows, so a dropped term or a crossed pairing lands on a different row rather than on nothing.
- **Neither of the two mutated assertions is vacuous.** Changing the permutation case's expected `ID` from 4 to 3 fails the script with its own message. Changing the 105259 case to look for `:105260 --->` fails it too, and the failure text shows the real chain carries only `:105259 --->` and the `:104229 --->` runtime wrapper — which also confirms the header's account of the wrapping and of why the assertions match `":<code> --->"` rather than bare digits (the same text carries `…ServerBatch.cs:line 87` fragments). Both mutations were reverted and the file confirmed back to its committed content plus only this pass's three comment edits.
- **`Execute('...')` really is necessary.** `ServerBatch.Execute` prepares its batch and then executes it, one batch at a time, so a `try … except` written in the same batch as a bad expression would never run — the batch fails while compiling. The nested path is `SystemExecuteNode.ExecuteScript` → `PrepareScript` → `ServerScript.Execute` on the same process, which is why the nested script sees the tables this one creates.
- **The manifest entry was required, and the harness enforces it.** `CoverageScripts.Discover` unions the scripts on disk with the manifest's entries and emits a failing case for either side alone (`NotInManifest`, `FileMissing`), and `CoverageManifest.Validate` rejects an out-of-ordinal-order entry; `TableCallsWithStackReferences` < `TableIndexer` < `TableLibrary` ordinally, and the run reports no discovery problems.
- **The five tables' data is legal.** Checked each table's declared keys against its rows: every key value is unique, so no `insert` could have failed for a duplicate and then been read as an empty result.
- **Dropping the `All.Coverage.d4` marker changes nothing.** Nothing executable references that file — the only mention of it anywhere is a comment in `StreamValues.d4` — so it is the 2008 hand-wired run list and the edit is housekeeping, as the handoff said.
- **Source hygiene.** CRLF and no byte-order mark in the `.d4` file and the manifest, matching their siblings; tab indentation preserved; no file reformatted or re-encoded. 211 lines, with a header in the same style and of the same weight as `LibraryUpgrades.d4` (425 lines) and `LibraryAdministration.d4` (342) — the two scripts whose error-code idiom this one follows.

### Tests

No test added and none cut. The ticket's deliverable *is* a test, and the six error cases plus twelve working assertions each pin a distinct branch of the resolution — checked one by one for redundancy: the two forms of the same single-key lookup differ (explicit `by` versus implicit), the two `TableIndexerTwoKeys` cases are the two arms of type-driven key selection, `TableIndexerWidths[2]` pins that a *wider* key is filtered out by term count where `TableIndexerSingle[1]` cannot, and the paired `by`-clause assertions on `TableIndexerSameTypeKeys` and `TableIndexerPairKey` are each needed because a single one of the pair would still pass if the compiler ignored the clause and took the first key or the given term order. The one assertion that is not about resolution — a read after the six caught compile errors — is the only check that a caught compile error from a nested `Execute` leaves the enclosing implicit transaction usable, which is worth its one line.
