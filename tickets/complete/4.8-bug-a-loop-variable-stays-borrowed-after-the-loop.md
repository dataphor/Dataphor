## What landed

A `foreach` whose loop variable is a variable the enclosing block already declared (`foreach LB in ...`, not `foreach var LB in ...`) borrows that variable's stack slot: it lends the slot the row or element the iterator owns and goes on reading it. The engine got both ends of that loan wrong, and both are fixed.

**The mark ends with the loop.** `Symbols` has a new overload `SetIsBorrowed(int offset, bool value)`; the existing one-argument form is unchanged and delegates to it. The two non-allocating compile sites read the symbol's mark before setting it and restore that value in the `finally` that already runs after the body is compiled. Restore, not clear: the inner of two loops over one variable has to leave the outer loop's mark standing. Consequence: an assignment to the variable *after* the loop releases what it replaces, where it used to release nothing for the rest of the scope.

**The loop pays for the loan.** `ForEachNode`, `ListForEachNode` and `TableForEachNode` release the value their loop variable's slot already holds, once per loop, before iteration starts (`program.Stack.PokeOwned(stackIndex, null, program.ValueManager)`), in both the cursor and the list branch of each.

**Two guards, carried by one compile-time flag** (`ReleaseTargetBeforeLending`, named for what it does rather than for one of its reasons). The release does not happen where an enclosing loop over the same variable is already lending the slot - the inner loop would displace an element the outer loop's source still owns - nor where the slot is a `const` operand of the enclosing operator, whose value may have been lent to the call by the argument that produced it. The second was not in the fix ticket and was the implement stage's own finding: before the guard, `ZFEConst(LB)` failed with `StreamID (6) not found`.

A by-value (`in`) operand used as a loop variable needed the matching half: the compiler promotes an `in` operand the body never *assigns* to to `const` and then passes it by reference, and that promotion is decided after the body is compiled, so the compile-time const test cannot see it. The lending sites therefore mark the slot modified (`plan.Symbols.SetIsModified`), which keeps such an operand `in`, copied for the call, so the slot's value is the callee's own to release. Side effect: the operator's recorded operand modifier now keeps the `in` the source declared instead of showing `const`, which an emitted catalog script would show. Recorded in `docs/migration-notes.md`.

**Clone.** The three nodes had no `InternalClone`; each now copies all of its compile-time state. `Clone` is unreachable for these nodes today, and the remark at each override says so.

**`TableForEachNode` is dead code.** `Compiler.CompileForEachExpression` always builds a `ListForEachNode` and nothing in `src/`, `libraries/` or `tests/` names the type. It was changed in step with its two siblings anyway, with a `NOTE:` at the class naming `debt-ws12-hygiene-remainder` as the sweep that owns deciding whether it goes.

**Documentation.** `docs/architecture/value-lifetime.md` was at 1,497 words against its 1,500-word cap, so its two operand sections moved verbatim into a new page, `docs/architecture/operand-ownership.md`; `docs/architecture.md` indexes both and the three code comments that pointed at the old page for the operand rule now point at the new one.

**Four cases** in `tests/DAE.Server.Tests/AssignmentValueOwnershipTest.cs`, whose class comment carries the running account of this rule: an assignment after each of the four loop forms the compiler can produce; a loop over a variable that already holds a value; two loops over one variable; and a loop over the enclosing operator's own operand, one shape per modifier.

## Review findings

### Read and run

The implement diff (`ticket(implement): bug-a-loop-variable-stays-borrowed-after-the-loop`) was read before the handoff, then the surrounding code: both compile sites and their `finally` blocks, all six runtime release sites, `Stack.PokeOwned`, `AssignmentNode`, `CallNode.InternalExecute`'s operand push and hand-back, `InstructionNodeBase.CleanupOperand`, `StackReferenceNode.InternalExecute`, and the four documentation files.

Behaviour was checked by running scripts through a throwaway case on `InProcessTestFixture` reading `Diagnostics.StreamCount()` either side of each (added, measured, removed - nothing of it is left in the tree). The paths the four cases do not cover are all balanced: `break` out of a loop then assigning after it; a `raise` out of a loop caught by a D4 handler then assigning after it; two sequential loops over one variable; a loop in a nested block over a variable the outer block declared, with the assignment outside the inner block; a loop over a nil list; and a loop over a non-stream element type. None of these needed a test of its own - they are the same symbol and the same two code paths as the cases already pin.

The one guard whose failure would otherwise be silent was mutation-checked: dropping the already-lent term (`releaseTarget = !target.IsConstant`) makes `NestedForEachesOverOneVariableLeaveTheOuterLoopsValueAlone` fail on both arms, the list arm with `StreamID (4) not found` and the cursor arm with `A nil was encountered where a value was expected`, which is exactly what the handoff claimed. The mutation was reverted and the suite re-run.

`SetIsModified`'s reach was checked rather than taken on trust: across `src/`, `Symbol.IsModified` has one reader, the operand promotion at `Compiler.cs:6336`, which is gated on `Modifier.In`, so marking a `const` or `var` operand's slot - or an ordinary local's - changes nothing. The claim in the handoff holds.

### Fixed in this pass

- **`docs/migration-notes.md` named a property that does not exist.** The entry promised extension authors a public `TargetIsBorrowed` on the three nodes, with the opposite sense to the property that actually shipped (`ReleaseTargetBeforeLending`). Corrected, which matters more here than elsewhere: that file is the record of public surface a custom C# node compiles against.
- **The six release-site comments described a path that cannot run.** Each said the release was "a no-op on the null the allocating form has just pushed", but the compiler sets the flag only in the non-allocating branch, so the allocating form never reaches the release at all. Replaced with what is true, which is shorter.
- **The duplicated lending block in the compiler is now one named subroutine.** Both compile sites carried the same fourteen lines, eleven of them comment narrating the three statements. Extracted as `Compiler.LendForEachTarget`, which carries the explanation once and returns the mark to restore; the two call sites are three lines each, and the restore comment is now a pointer. The three node classes' property remarks point at it rather than each repeating the two reasons.
- **`docs/architecture/operand-ownership.md` overstated the `var` rule.** It said that for a `var` operand "nothing is copied and nothing is released", which the body contradicts: an assignment to a `var` parameter, and now a `foreach` over one, releases what the slot held. The bullet now says so, and says the limit of it (below).
- **Two broken line wraps**, one mid-sentence in `AssignmentNode`'s borrowed branch and one in the test fixture's class comment, where an insertion left a four-word line; both paragraphs reflowed.

### Filed

- **`fix/4.96-bug-a-var-parameter-written-in-the-body-can-release-a-callers-loop-value`.** A `var` parameter's slot is an alias of the caller's, and a body that writes it releases what it displaced - which is right only while the caller's slot owns that value. Where the caller passes its own `foreach` loop variable, the release takes a row or element the loop still owns. Measured: a two-row cursor loop calling an operator that assigns its `var` row parameter raises `A nil was encountered where a value was expected` on the second row; the list form raises `StreamID (6) not found`. This is **older than this ticket** - the release is `AssignmentNode`'s and that line is untouched by the loop work - but the loop work adds one more way to reach it, since a `foreach` inside the callee over the `var` parameter does the same thing for the same reason, where before it leaked instead. Filed as one ticket for the class rather than as an arm of `backlog/bug-a-loop-over-a-read-only-parameter-orphans-a-computed-argument`: that one is the same seam pointing the other way (a value the call owns released by nobody) and its triage metadata is for a leak, not for a release of a live value. The two now cross-reference each other, and `docs/migration-notes.md` records the one D4-visible consequence of this ticket's half.

### Tripwires

- A `NOTE:` at `AssignmentNode`'s owned branch - the exact site of the defect above - says that the borrowed mark is compiled per plan and so cannot see a value that reached the slot from a borrowed slot one frame up, and names the ticket. The test fixture's class comment says the same in one sentence, so a reader of `AForEachOverAnOperandLeavesTheCallersValueAlone` does not conclude that the `var` shape is settled.

### Checked and left alone, with the reason

- **The restore in the `finally` uses `node.Location`, a top-of-stack offset**, and assumes the body's compile left the symbol stack balanced. The `plan.Symbols.Pop()` it sits beside makes the same assumption and would do more damage if it were wrong, and an unbalanced compile means a plan that is being discarded. No change, and no `NOTE:` either - one at this site would only restate what the adjacent line already implies.
- **No test for `InternalClone` and none for `TableForEachNode`.** Agreed with the handoff: `Clone` cannot reach these nodes and the compiler cannot build a `TableForEachNode`, so the only way to exercise either is to construct the node by hand, which tests the test. The dead class stays for `debt-ws12-hygiene-remainder`.
- **Not one of the four cases was cut and none was added.** Each pins a distinct defect or guard end: the mark's extent across all four loop forms, the release, the already-lent guard, the const guard with the promotion change. None restates the implementation or verifies a mock, and the new behaviour this pass found belongs to another ticket, so a test for it here would fail the build.
- **`docs/migration-notes.md`'s landed entry for the earlier operand ticket still links `value-lifetime.md` for the operand rule.** The link resolves and that page points on to the new one; a landed record is left as it is.
- **The fact about a device session's undo log that `4.7-bug-a-stored-binary-is-never-given-back` asked whoever split `value-lifetime.md` to fold in was not folded in.** It is another subject and is recorded at its code site; the room now exists for whoever wants it there.
- **Everything the handoff flagged as a gap was checked and is as described**, except its claim that the release needs no allocating/non-allocating branch because it is "a no-op on the null the allocating form has just pushed" - the branch is the flag itself, and the comments that said otherwise are fixed.
