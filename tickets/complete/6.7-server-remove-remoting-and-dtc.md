# Remove remoting lifetimes (K6) and the DTC transaction class (K11)

This is the first half of `build-server-project`, split off because both parts are source deletions that the spike could already build and run. The K-numbers refer to the known-defects table in plan Appendix A. No project file changed format; `Server.csproj` is still a legacy project.

## What landed (`ticket(implement): server-remove-remoting-and-dtc`)

- **K6.** The .NET Remoting lease, tracking-handler and sponsor code is removed from `RemoteServerObject`, `RemoteServer`, `RemoteServerConnection` and `FileStreamHeader`, along with the remoting `using`s (including the unused one in the server's `SecurityNodes.cs`). `MarshalByRefObject` stays as the base class. Both `Dispose(bool)` methods still raise `Disposed` through `DoDispose()`.
- **K11.** `ServerDTCTransaction` and `IServerDTCTransaction` are deleted, together with their `Compile` entries and the DTC branches in `ServerProcess` begin, commit and rollback. Error 106119 (`DTCNotSupported`) now reads "Distributed transactions (UseDTC) are not supported." and is raised in three places:
  - the `ServerProcess.UseDTC` setter, given true. The check comes before the `InTransaction` check, because every D4 statement runs inside an implicit transaction;
  - `ServerCatalogDeviceSession.UpdateSessions`, when `DefaultUseDTC` is set to true;
  - `InternalBeginTransaction`, before any transaction state changes. This catches a true value that arrives through `ProcessInfo` or a session's `DefaultUseDTC`.
- **Bug fixed along the way.** `UpdateProcesses` read a column `MaxCallDepth` that `System.Processes` does not have (the column is `MaxNestingLevel`), so any whole-row update of `System.Processes` failed. It now reads `MaxNestingLevel`.
- **Spike.** The remoting and COM+ stubs are removed from `stubs/Server.cs`, and the spike README is updated.
- **Docs.** Plan K6 and K11 are marked fixed. The WS1/WS2 prose, the migration notes and the user documentation are updated.
- **Test.** The `DistributedTransactions` coverage script checks that true is rejected with 106119 and leaves the setting false, for both `UseDTC` and `DefaultUseDTC`, and that a whole-row update of `System.Processes` succeeds. That last check is the reproduction of the `MaxNestingLevel` bug.

## Review findings

**Read first: the implement diff.** I read it in full before the handoff. It deletes the code the ticket names and nothing else. The DTC removal in commit drops the `try { DTC commit } catch { RollbackTransaction(); throw; }` wrapper. That is correct: the DTC commit was the only statement inside the `try`, so the rollback-on-failure path for the remaining commit logic is unchanged. Every `InternalBeginTransaction` caller was checked: `BeginTransaction`, `BeginTransactionalCall` (whose `catch { EndCall(); throw; }` leaves the process consistent) and `ServerTransaction.InvokeDeferredHandlers`. The last one runs only inside a commit whose begin has already passed the check. `ServerProcess.InternalCreate` begins no transaction, so a process created with `UseDTC = true` is still constructed and fails only at its first transaction, as the handoff says.

**Found and fixed in this pass (minor):**
- **The migration note overstated the `MaxNestingLevel` fix.** It said setting the column "changes the process's maximum call depth". `ServerProcess.MaxCallDepth` (like `MaxStackDepth`) sets the stack of the *executing program*. When a process updates its own row, the new limit therefore applies only to that update statement. I verified this with a temporary probe in the coverage script: after `update System.Processes set { MaxNestingLevel := 777 } where ID = ProcessID()`, the next statement read 100. The probe was removed afterwards, and the script is byte-identical to the committed one. I reworded the migration note to describe the real behaviour. This is existing D4 behaviour that the column fix only made reachable, so it was not changed. It is parked as a `NOTE:` at `UpdateProcesses` in `src/engine/Server/Device.Catalog/ServerCatalogDeviceSession.cs`, with a revisit condition. No test pins it, on purpose: pinning a probable quirk would force a future fix to edit an expected value.
- **The user-facing text for `DefaultUseDTC` was left unchanged and said nothing about the change.** `SessionInfo.DefaultUseDTC` is what the alias editor's property grid shows (its `Description`), and `docs/users-guide/aliases.md` documents it. Both now say it is not supported and that true makes each process raise 106119 when it begins a transaction.
- **`process-defaults.md` said that setting `DefaultUseDTC` to true "through the CLI" raises 106119.** Through the CLI, or through a server alias, the error comes later, from each process's first transaction. The text now says which path raises when.

**Checked, nothing to change:**
- **Compatibility surfaces.** The `UseDTC`/`DefaultUseDTC` properties, the WCF `DataMember`s, the `System.Processes`/`System.Sessions` columns, the error code 106119 and `RemoteSessionImplementation` are unchanged. The `Description` attribute text is not part of the data contract.
- **Leftovers.** The remaining `System.Runtime.Remoting` hits under `src/` are `src/engine/DAE/Runtime.Instructions/GeneratorNodes.cs` (not in `DAE.csproj`, a stray), the client-side `ServerFactory.cs` and `DataphorConnectionFactory.cs`, and the Dataphoria reference. All are outside this ticket and belong to the client and IDE work. `Server.csproj` still has its `System.EnterpriseServices`/`System.Runtime.Remoting` `<Reference>` items, which `build-server-project` drops when it converts the project, as the handoff says.
- **Code comments.** The three new comments state reasons (why the check comes first, why the session update rejects true, why the column names differ). None of them narrates the code next to it.
- **Test quality.** The script asserts on `E.InnerError.Code`, because the statement-level re-raise wraps the error as 104229. It fails on "no error" and on any other inner code, including the old 106116. Its "false succeeds" block does not call the setter, since false to false is not a change. Its real value is the whole-row update that reproduces the column bug, as its comment says. No tests were cut: each one pins a behaviour the project rules require.
- **Line endings of the new script.** It is CRLF in the working tree but stored LF in the index (`git ls-files --eol`: `i/lf w/crlf`), because `core.autocrlf=true`. 70 of the repository's `.d4` files are already stored LF, and `.gitattributes` deliberately sets no `text` rule, so I left it alone.
- **Resource cleanup and threading.** `RemoteServer.Dispose` still runs `base.Dispose` in `finally`, and nothing else depended on the removed tracking handler. Abandoned remoting connections are no longer reclaimed, which is the open design point `port-abandoned-session-cleanup` owns (plan WS2).

**Accepted as the handoff stated, no new ticket:**
- The API path (`ProcessInfo.UseDTC = true` at `StartProcess`) is verified by reading the code only. A C# test belongs to the harness tickets.
- A multi-column update of `System.Processes`/`System.Sessions` that includes `UseDTC := true` applies the earlier columns before raising. This was already true of any failing column.

**Major findings / tickets filed:** none. Nothing found needs a design or compatibility change.
