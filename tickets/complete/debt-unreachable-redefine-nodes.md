## What landed

The node form of the D4 `redefine` operator is gone. `Compiler.EmitRedefineNode` rewrites `T redefine { A := A + A }` into `T add { A + A Temp } remove { A } rename { Temp A }`, and has done for the whole life of this repository; the three classes implementing the alternative - `RedefineNode`, `RowRedefineNode`, `RedefineTable` - were reachable only from a branch behind `#if USEREDEFINENODE`, a symbol defined nowhere, whose text would not have compiled anyway because it still used the `A`-prefixed parameter names this repository renamed away. The owner authorized retiring them on 2026-11-22, which is the explicit decision the compatibility rule requires before a registered D4 class name is withdrawn.

It had to be one change: the engine's two `create operator iRedefine(...)` declarations and their two `grant usage` lines, the two SQL devices' `System.iRedefine(table)` mappings and `SQLDevice.SQLRedefine` (which casts to `RedefineNode`) all fall together, because a device's operator map resolves each mapping's operator against the catalog before anything is translated, so a mapping left behind would fail the device's whole registration script. That mechanism was not written down anywhere; this review added it to [architecture/devices.md](../../docs/architecture/devices.md), where it is the general rule for retiring any built-in operator.

Measured removal: **775 lines of source** - `RedefineNode.cs` 396 (whole file), `RedefineTable.cs` 118 (whole file), `RowRedefineNode` in `RowNodes.cs` 192, `SQLRedefine` in `SQLOperators.cs` 56, the dead conditional in `Compiler.cs` 13. Of those, 446 are the coverable lines the 2026-11-21 instrumented run measured at exactly zero hits.

Implemented in `ticket(implement): debt-unreachable-redefine-nodes`; the corrections below are in this ticket's own commit.

## That the operators were dead was verified, not assumed

Before anything was deleted, a scratch fixture over `InProcessTestFixture` evaluated both operators by name on a real in-process engine (added, run, removed - nothing checked in):

| expression | before the change | after the change |
|---|---|---|
| `iRedefine(table { row { 1 A } })` | `CompilerException: Internal error: Unexpected exception encountered during compilation.` over a `NullReferenceException` | `CompilerException: Unable to resolve operator reference "iRedefine" with signature "(table{A:System.Integer})".` |
| `iRedefine(row { 1 A })` | the same pair | the same, with signature `(row{A:System.Integer})` |
| `table { row { 1 A } } redefine { A := A + A }` | evaluated | evaluated |

So retiring these operators removed nothing that worked: the only code that set the field their `DetermineDataType` reads first was the disabled branch, and a direct call died at compile time on that null. `docs/migration-notes.md` carries both halves of that, and both error wordings are the ones the engine's own resources hold (`CompilerException` 105149 for the second).

## Tests

**No new test, and none is owed.** `redefine` is the behaviour that must not change, and seven passing coverage scripts execute it - which is how the dead code was found. Nothing new became testable: after the change the operators do not exist, so a script naming them gets a compile error, and a test asserting that would only restate the deletion. `OperandOwnershipShapeTest` is the structural guard and fails if the deletion is partial.

## Review findings

**Read first, then the handoff.** The implement diff was read in full before the handoff summary, then every claim in the handoff was checked against the tree.

**What was checked and found sound.** The live rewrite is untouched and is now the method's whole body, with no locals or `#endif` left from the removed branch, and `ConvertTableNode`/`ConvertRowNode` still reach it. `Instructions.Redefine`'s removal does what the migration note says and no more: `Instructions.Contains` is reflection-populated over those consts and its only three callers set `Schema.Operator.IsBuiltin` when compiling `create operator`, so the sole behaviour change is that an operator a user creates under the name `iRedefine` is no longer flagged built-in. Nothing needed removing from a registration list: both the engine's and `SQLDevice`'s `DAERegister.GetClasses()` are reflection over the assembly, not hand lists. The `RowNodes.cs` seam reads correctly and the three surviving comments naming `Compiler.EmitRedefineNode` stay accurate. Catalog object identifiers do shift for a store created from these scripts, and nothing pins one - independently confirmed that `tests/goldens/` contains no object identifiers at all. Source hygiene held: compared blob to blob for all thirteen edited files, line endings and byte-order marks are unchanged (a working-tree comparison misleads here, because this checkout has `core.autocrlf=true`, which is also why `git diff --check` flags the added `NOTE:` lines).

**Found and fixed - the handoff's test set was narrower than the coverage it claimed.** The handoff says four coverage scripts execute `redefine`; ten mention it and **seven passing ones execute it**. The three the implement stage did not run are the interesting ones: `SerializationOperators` and `SerializationViews` define an operator and a view with `redefine` and round-trip their D4 text through the catalog, and `ViewUpdatability` inserts, updates and deletes through a view defined with `redefine`. All three pass. That is the contract the deleted `RowRedefineNode.EmitStatement` would have sat in, so it is worth more than the four that were run. `docs/coverage-report.md` is where the four came from - pre-existing text, not this ticket's error - and it now names all seven.

**Found and fixed - two stale hand-maintained counts.** `docs/migration-notes.md` still said `OperandOwnershipShapeTest` checks "a list of eighteen names"; it is seventeen now. And the registered-operator count the port records in four places was left at its old value: `tools/net-spike/README.md` and `AGENTS.md` carry it as the figure to expect from a run, so an agent running either check after this change would have read a regression into it. Corrected to 1,078 for the spike's smoke (derived: two fewer `create operator` declarations) and to **1,058 measured** for `EngineCheck`, which was run here - `dotnet run --project tools/net-spike/EngineCheck -c Debug` reports `RESULT: pass`, 1,058 operators, 23 scalar types, and is also an independent check that `SystemCatalog.d4` still executes on a bare engine. Left alone deliberately: `docs/modernization-plan.md`'s "Runtime results" paragraph, which is a dated record of one spike run (its coverage-script figures beside it are long superseded too), and `docs/architecture/assemblies.md`, which says "~1,080" with the tilde.

**Acted on, rather than deferred again - the implementer's own tripwire.** The handoff flagged that the counts in `docs/architecture/operand-ownership.md` and in `OperandOwnershipShapeTest`'s comments are prose restatements of a set the fixture reflects, and that a third correction should mean stopping writing the number down. The stale count above was that third correction, so the numerals are now gone from the three places where the adjacent list already showed them (the fixture's two doc comments and its inline comment, which read "the twelve after them", "The nine that re-override" and "seventeen namespace-qualified strings"). The counts stay in `docs/architecture/operand-ownership.md` alone, which is where the fixture's own failure message already sends whoever changes the set. Verified the page's arithmetic while there: 5 argument shapes + 12 operator nodes, of which `ExistsNode`, `TableToListNode` and `IfNilNode` derive from `InstructionNodeBase` directly, leaving 9 that re-override from a shape.

**Tripwire parked.** Two parked device catalogs under `legacy/libraries/` - Oracle and SAS - still map `System.iRedefine(table)` to `SQLDevice.SQLRedefine`, and by the registration rule above that mapping now fails the device's whole script. Not a ticket and not a code comment: those trees are not built or run, so nothing catches it first, and editing a parked `.d4` risks the parser round-trip corpus for no gain. It is a `NOTE:` in [architecture/devices.md](../../docs/architecture/devices.md) instead, beside the rule it violates, where whoever revives one of those devices will meet it. The implementer's other tripwire, the `NOTE:` above `EmitRedefineNode` recording that the rewrite is now the only implementation and that a node form is the known alternative if `redefine` plans ever profile slow, was read and left as written - it claims no magnitude, which is right, because none was measured.

**No ticket filed, and nothing met the bar.** Every finding above was a documentation or comment correction fixable in this pass. No latent defect, no class-level invariant worth a `debt-` ticket: the one invariant this work exposed - that retiring a built-in operator means editing every device that maps it, in the same change - is now written down in `docs/architecture/devices.md`, which is a better home for it than a ticket. The site-claim grep over `tickets/backlog`, `fix`, `plan`, `implement` and `review` for the paths in `files:` found nothing open on them.

**Known gaps, carried forward unchanged.** The two device mapping edits are still verified by inspection only: no test executes either device's `SystemCatalog.d4`, because `SQLDevice.InternalRegister` runs that script only when the device starts, which needs a reachable DBMS - the same reason the three `Transaction.Atomicity.TestMSSQL*` scripts are recorded as known failures. `ParserRoundTripCorpusTest` proves both files parse and round-trip, not that they are semantically whole. `PGSQLDevice`'s C# project is not converted yet, so its catalog edit is parsed and nothing more. A catalog store created before this change keeps its own object identifiers, is loaded rather than re-scripted, and still holds rows naming the removed class names; the migration note says to rebuild from scripts.
