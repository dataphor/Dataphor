description: When a table is first used inside an application transaction while a statement is already running (for example a script run through the D4 Execute operator), the engine made the transaction's private copy of the table while holding the catalog lock and then waited for the catalog store's write lock, an order that can deadlock and that failed a Debug build with an internal error. The copy writes nothing to the store, so the early store begin is now skipped when the catalog lock is already held.
architecture: docs/modernization-plan.md#ws4-catalog-store

## What was wrong

An application transaction (AT) is a long-lived editing transaction. The first time a statement references a table while the process has joined an AT, `ApplicationTransaction.AddTableVar` takes `lock (process.Catalog)` and, inside it, `ApplicationTransactionDevice.CopyTableVar` compiles and runs `create table .AT_<name>` (plus `alter table` / `attach` statements) for the AT's private copy. Every DDL node's `DDLNode.InternalBeforeExecute` calls `ServerCatalogDeviceSession.BeginStoreWriteTransaction`, which exists (K10, `store-sqlite-concurrency`) to take the store's write lock *before* the catalog's lock. Called inside the catalog's lock with a process transaction open and no store transaction yet, it did the forbidden wait: Debug failed with `Internal Error: The catalog store's write transaction is beginning inside the catalog's lock.`; Release could deadlock until the busy timeout (130103) against a session holding the store lock and wanting the catalog lock.

It needs a statement that compiles inside an already-open process transaction, which is what `Execute('…')` does; a batch run directly on a process compiles before its implicit transaction begins, so it never hit this. The copy's objects are AT objects (`IsATObject`), which `CatalogDeviceSession.ShouldSerializeCatalogObject` never writes to the store.

## The change

- `ServerCatalogDeviceSession.BeginStoreWriteTransaction`: added `&& !Monitor.IsEntered(Catalog)`. Inside the catalog's lock the early begin can no longer come before that lock, so it does nothing; a statement there that genuinely writes the store still reaches `BeginStoreTransactions` at its first write, whose Debug assertion is unchanged.
- Comments on `AcquireCatalogStoreConnection`, `BeginStoreTransactions`, `BeginStoreWriteTransaction` and `DDLNode.InternalBeforeExecute` say this; a `NOTE:` tripwire at `ApplicationTransaction.AddTableVar` says the copy relies on writing no store rows.
- `docs/architecture.md`, lock-order bullet under **Store transactions**: one sentence on DDL already inside the catalog's lock.
- No migration note: nothing observable changes except that the internal error no longer occurs.
- Test: `tests/DAE.Server.Tests/ApplicationTransactionTest.cs`, `TestEnlistInsideStatement`, the five-statement reproduction on `InProcessTestFixture`.

## Review findings

Read the diff of `ticket(implement): store-at-enlist-inside-catalog-lock` before the handoff.

- **Correctness of the skip.** Checked that `CatalogDeviceSession.Catalog`, `Program.Catalog`, `Plan.Catalog` and `ServerProcess.Catalog` are all the server's one `Schema.Catalog`, so `Monitor.IsEntered(Catalog)` tests the same lock that `AddTableVar` takes. The skip is safe in every case, not just the AT copy: if no store transaction is open, the early begin inside the lock would have done the forbidden wait anyway, and a real store write there still does it at its first write (same Release behaviour as before, Debug still asserts, now at the write); if a store transaction is already open, the early begin would only have caught up nested levels without waiting, and the first write still catches them up. Nothing found.
- **Other DDL inside the catalog's lock** (the handoff's open question). Walked every `lock (…Catalog)` site in `src/engine`: the compiler's name resolution and operator-resolution-cache sites (`Compiler.cs` about 1969, 6516, 6872, 9564) run no DDL except object loading, which is in a loading context and never reached the early begin; `SystemClearLibraryNode` and `SystemRoleExistsNode` run none; the DDL nodes' own locks run after their `InternalBeforeExecute`. `ApplicationTransaction.EnsureATTableVarMapped` and `AddOperator` copy AT objects (not persistent). `ReportTableChange` / `ReportOperatorChange` drop AT objects inside the lock, but are called from the source object's DDL, which already began the store transaction before its lock. Nothing found.
- **Test.** Re-verified on Debug that `TestEnlistInsideStatement` fails without the `Monitor.IsEntered` condition (the internal error) and passes with it; it is the bug's reproduction, which the project rules require, so kept. The Release two-session deadlock is not reproduced by a test; accepted as the implementer described (same shape as `CatalogStoreConcurrencyTest`, and an interleaving test would be slow and flaky). The cursor form of the reproduction goes through the same `AddTableVar` path; no second test added.
- **Docs.** `docs/architecture.md`'s new sentence read as if all DDL inside the catalog's lock writes nothing; reworded (minor, fixed) to state the rule — such DDL must write nothing, the AT copy writes none, and a store write there still meets the assertion. Code comments match the behaviour. No migration note needed (agreed). `docs/modernization-plan.md` has no entry this changes.
- **Source hygiene.** Encoding, byte-order mark, CRLF and tabs preserved in all edited files (checked with `file` against the previous commit); new test file is UTF-8 with BOM, CRLF, tabs, and is listed in the csproj. No narrating comments.
- **Tripwires.** The `NOTE:` at `ApplicationTransaction.AddTableVar` (if AT objects ever become persistent, begin the store write before that lock) is the right home; no further tripwires.
- **Error handling, resource cleanup, performance.** The change removes an acquire/release pair in one case; `Monitor.IsEntered` is cheap. No new error paths. Nothing found.
