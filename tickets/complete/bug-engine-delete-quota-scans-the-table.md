## What landed

**One clause removed**, at `src/engine/DAE/Device.Memory/MemoryDevice.cs:86`. `InternalPrepare` no longer requires `plan.Plan.CursorContext.CursorType != CursorType.Static` before offering an ordered scan over an index the device already keeps. A comment at the site says why: the device knows what it can serve, the requested cursor type says what the *consumer* needs and nothing about what sits in between, and where a snapshot is really required the engine already makes one itself with `Compiler.EmitCopyNode` above whatever has narrowed the row count. The same method's `BaseTableVarNode` branch had always reported a dynamic cursor regardless of what was asked for, so the two branches now follow one rule.

The plan shape, read off `Diagnostics.ShowPlan` before and after, is the whole of the change. `delete T return 1 by { ID }` was `DeleteNode(QuotaNode(OrderNode[DeviceSupported=False](BaseTableVarNode)))` - the engine's `OrderTable` materializing and sorting every row, once per statement - and is now `DeleteNode(CopyNode(QuotaNode(OrderNode[DeviceSupported=True, Device=System.Temp](BaseTableVarNode))))`: the device reads in order, the quota narrows to one row, the copy snapshots that one row.

**Nothing changed at `ParameterNode`**, which was the one open question the ticket carried, and a `NOTE:` at `src/engine/DAE/Runtime.Instructions/ImperativeNodes.cs:1034` records why. A genuine `var` table parameter leaves no `ParameterNode` to bind - `InstructionNodeBase.DetermineDataType` removes it and requires what remains to be a `StackReferenceNode`, a leaf - and a base table var cannot be passed by reference at all. What does survive binding is only `var` written on an operand the resolved operator declares `in`, and such an argument was never a snapshot: the engine hands the callee the live `BaseTableVarNode`, as it did before.

**The reproduction test** is `tests/DAE.Server.Tests/QuotaDeleteCostTest.cs`, one case. It warms the engine with a throwaway 50-row drain, then drains 250 rows and 1,000 rows (each twice, counting the cheaper) and asserts that one row of the larger drain costs at most three times one row of the smaller. A ratio, never a time, so the case says nothing about how fast the machine is. Validated by putting the device's old rule back, rebuilding and running it: it fails, ratio 5.2, in a 19 s run.

**Measured** on one slow development laptop in Debug: a 250-row drain went from 415 ms to 14-34 ms, a 1,000-row drain from 8,665 ms to 57-122 ms, and the `Timings` coverage script's 10,000-row drain from about a quarter of an hour (by extrapolation) to 1,294-1,485 ms. `Timings` is now a passing coverage case and a scenario of `PerfBaselineTest` rather than a recorded known failure, and its four blocks are several times faster than the 2008 notes the script itself carries - which is what the `Timing` calibration in `docs/perf-baseline.md` predicts. The documents updated: `docs/perf-baseline.md` (the scenario table, the `Timings` section, the drain-by-size before-and-after table), `docs/migration-notes.md` (one entry, under *D4, catalog and libraries*), `docs/modernization-plan.md` (known defect **K37**, and the `test-perf-baseline` row), `tests/goldens/perf/perf-baseline.json` (`dev-slow` re-recorded, six scenario keys) and `tests/DAE.Server.Tests/coverage-manifest.json`.

## Review findings

The implement diff (`ticket(implement): bug-engine-delete-quota-scans-the-table`) was read first and independently of the handoff. Everything below was run on 2026-11-22 in Debug on the same slow development laptop.

### What was checked

- **The central safety claim, by reading the code rather than trusting the handoff.** Removing a cursor-type guard is only safe if every consumer that asks for a static cursor gets a snapshot some other way, so every site that pushes a static cursor context was traced. `DeleteNode` (`TableNodes.cs:1106`) and `UpdateNode` (`:746`) insert `Compiler.EmitCopyNode` whenever their target's cursor type is not static; an `insert` statement's source gets the same copy at compile time (`Compiler.cs:2754`); `CursorNode.BindSourceNode` (`CursorNodes.cs:106`) does it for a declared cursor. That leaves `ParameterNode`, which the implementer's `NOTE:` accounts for, and `SystemGetNextGeneratorNode` (`GeneratorNodes.cs:142`), which compiles a restriction and never an order, so the branch that changed cannot be reached from it. No uncovered site.
- **That the snapshot is real at run time, not only in the plan.** `CopyTable.PopulateTable` (`src/engine/DAE/Runtime.Data/OrderTables.cs:301`) drains its source inside a `using` and disposes it before `InternalOpen` returns, so the device scan is closed before the first row is deleted. This is the point that mattered: scanning an in-memory tree while it is being modified is a known hazard here, recorded in the `NOTE:`s at `NativeTable.cs:71` and `RowTreeScan.cs:574`, and a live scan held across the deletes would have been a correctness bug rather than a slow plan.
- **Cursor-type propagation, so that a device scan cannot hide under a node that claims to be static.** `QuotaNode` takes its source's cursor type verbatim; union, difference and the join nodes report dynamic if either input is dynamic; `CopyNode` and the two table-variable nodes are the only ones that claim static unconditionally, and each of those materializes. So a device-served ordered scan anywhere beneath a modification target makes the target non-static and earns the copy.
- **Blast radius.** The four `MemoryDevice` subclasses inherit the change: `CatalogDevice`, `ApplicationTransactionDevice`, `FrontendDevice` and `SimpleDevice`. `CatalogDevice.InternalPrepare` and `ServerCatalogDevice.InternalPrepare` both delegate to the base method, so they inherit it in full. The application-transaction device's own two static compiles (`ApplicationTransaction.cs:1709`, `:1725`) compile a bare identifier and extract a `BaseTableVarNode`, so no order node is involved there.
- **Corpus evidence for the path that changed**, since no new test asserts a result. `ViewUpdatability.d4:295` inserts, updates and deletes through a quota view and asserts each outcome; `ApplicationTransactions.d4:354` and `:362` run a quota update inside an event handler; `DML.d4:1468-1484` and `TestProject.d4:68-72` assert the exact rows a quota reads, nils included. All four scripts are `pass` entries in the manifest and all four ran green.
- **Build**: `dotnet build Dataphor.slnx`, 0 errors, 143 warnings - the count the tree already carried. No analyzer suppression was added anywhere in the diff.
- **The whole suite, in the three parts the root `AGENTS.md` prescribes, each as its own foreground run.** Part 1: **565 passed, 0 failed** in `DAE.Server.Tests` (8 m 0 s) and 13 passed in `Common.Tests`. ### What was found, and fixed in this pass

- **The ratio bound of two was too tight, and this is measured rather than argued.** Five fresh runs of the new case gave ratios of 1.60, 1.12, 0.99, 0.91 and 1.01, and the first of those is outside the 0.95-1.18 the handoff recorded as the clean range - so the bound had about a quarter of its width in hand against an observation, not the 1.7x the handoff estimated. `MaxPerRowGrowth` is now **3.0**, which is roughly the geometric middle of 1.6 and the defect's 5.2: a drain whose cost is proportional to the table's size cannot plausibly reach it, and one proportional to the square cannot come under it, because four times the rows costs about four times as much per row. The remark now carries all twelve observations and that arithmetic, and keeps the handoff's advice to raise the bound rather than the row counts. The `SmallFloorMilliseconds` remark was corrected with it: its "the larger drain may take 80 ms" and "a hundred times faster" were arithmetic on the old bound.
- **A document the change should have touched and did not.** The remark over `DdlDmlMixScript` in `tests/Dataphor.Benchmarks/EngineBenchmarks.cs` still told the next reader that `delete T return 1 by { ID }` "costs time quadratic in the table's size (bug-engine-delete-quota-scans-the-table)" as the reason the benchmark mix uses a whole-table delete instead. Rewritten: the form was quadratic when the mix was written, the mix still does not use it for a different reason (`Timings` measures the drain, and a whole-table delete is the shape an application uses), and neither the mix nor its recorded numbers were affected by the fix, because no statement in it narrows a table in an order.
- **A stale count in a library that this ticket added a consumer to.** `tests/libraries/TestFramework.Perf/Documents/Register.d4` said its lifted row cap exists "for the two consumers that register this library"; `QuotaDeleteCostTest` is a third, and wants only the cap. Named.
- **The new case asserts cost and never a result, which a reader will ask about.** A remark on the fixture now says so and points at the four corpus scripts above, which are the record of correct behaviour for a quota and for modification through one.
- **`docs/perf-baseline.md` stated the old bound** ("at most twice") and the old five-run range. Updated with the bound, the twelve observations and why it is three and not two.
