## What landed

The third of four steps towards `bug-object-id-counter-is-process-wide`. The implementation is in `ticket(implement): engine-object-id-transient-tablevars`; the review pass is in this ticket's own commit.

**The rule the step applies:** an object that can reach `CatalogDeviceSession.CacheCatalogObject`, the catalog store, or `Schema.Catalog.Add` takes its identifier from the engine whose catalog it joins (`plan.GetNextObjectID()`); every other object carries `Schema.Object.UnassignedID`. The two changes that carry it:

- **`Schema.ResultTableVar`**, the schema stub for the intermediate result of every relational operator, is now constructed as `ResultTableVar(Plan, TableNode)` and the one-argument form is gone - so the build was the census. 59 live sites converted. It keeps a real allocation, because its identifier uniquifies derived reference names. `Runtime.Instructions.TableSelectorNode` builds one in its constructor and so takes the plan as its first argument too.
- **`Schema.Object(string name)`** now sets `UnassignedID` instead of allocating, and is kept. 52 sites now allocate, 10 pass `UnassignedID` explicitly, and six types that are never numbered say so in their own remarks rather than repeating the reason at each call site: `Schema.SessionObject`, both `OperatorMap` classes, `Schema.RegisteredClass`, the application transaction's `TableMap`, and - added by this review - `Schema.Library`.

The largest change in identifier consumption is `Schema.Column`: a column of a row or table type is never catalogued, never persisted and its identifier is never read, so all of its hundreds of sites are now unnumbered. An engine's start-up spends a few dozen identifiers where it used to spend several hundred.

`Schema.TableVarColumn` is the exception among sub-objects: a column's identifier *is* persisted, inside the creation script of the table variable that holds it, so `Schema.TableVar.CopyTableVar` numbers the copies it makes (`create table T from <expression>` and `create view` both go through it) while relational-operator inference onto a result table variable leaves them unnumbered.

**Behavioural consequence, unchanged from the implement handoff:** identifier *values* move, and by more than the previous step moved them. A catalog store written by an earlier build of 4.0 does not line up with an engine built from this one and must be rebuilt from its scripts - inside what the plan settled for 4.0, and 4.0 has not shipped. What holds, and is checked by `StoreRebuildWorkflowTest.RebuildRegistersLibrariesAndSurvivesRestart`, is that the numbering is identical on every start of this build.

**One suite failure the implementation produced, and fixed.** `AbandonedClientProcessTest.AKilledClientProcessIsReclaimedAndTheServerKeepsServing` went red with `An item with the same key has already been added. Key: 5` out of `CacheCatalogObject`. Traced to the fixture's own workaround for the process-wide counter: `TestEnvironment.WithTheObjectIDCounterRestored` was putting the counter back to the value it had saved while the `LocalServer` engine started inside its body was still running, handing that live engine identifiers its catalog already held. Latent before this step only because an engine used to spend several hundred identifiers on start-up. The workaround now raises the counter and never lowers it, which is all it can safely do; no production code changed for it. The measured mechanism is an arm on `tickets/fix/bug-client-catalog-rebuild-reuses-object-ids.md`.

**After this step the only users of the process-wide counter left in the tree are the two save-and-restore workarounds in `tests/DAE.Server.Tests/TestEnvironment.cs` and `tests/Dataphor.Benchmarks/BenchmarkServerInstance.cs`**, so the reason the chain shared one generator instance between every engine is spent. `bug-object-id-counter-is-process-wide` can now flip `Engine._objectIDGenerator` to a generator of its own, delete the three `Schema.Object` statics, `ObjectIDGenerator.SetLastAllocated` and both workarounds, as a self-contained change.

## Review findings

The implement diff was read first with the handoff set aside, then the handoff's own claims were re-derived from the tree. The handoff flagged three of its own judgements as the first things a reviewer should check; all three are covered below.

### Fixed in this pass (minor)

- **A union's run-time buffer reparented its left source's columns onto itself.** `UnionTable.InternalOpen` computed `newColumn = column.Inherit()` and then added the *source's* column to the buffer's table type and column list instead of the copy - a pre-existing typo on the line directly above the one this diff changed, and the two sibling buffers in the same layer (`ExplodeTable`, `OrderTables`) do it correctly. `Schema.TableVarColumns.Adding` sets `item._tableVar = _tableVar`, so opening a union over a base table made the buffer the owner of that table's compiled columns and left them pointing at it after the cursor closed. A column's owner is what its `CatalogObjectID` and `ParentObjectID` report, and those are what the catalog store records for a column's default and constraints. Fixed to add the copy, with a comment saying why it must be the copy. **Reproduced before the fix** - `Count(UnionLeft union UnionRight)` left both of `General.UnionLeft`'s columns owned by `Object_8f0e15b1_…` - and the reproduction is the new `tests/DAE.Server.Tests/BufferedOperatorColumnOwnershipTest.cs`. No data behaviour changes: `Inherit()` copies the nilability and computed flags the buffer reads, which is why the defect was latent.
- **`Schema.Library` was numbered at seven sites although nothing reads a library's identifier**, which is the implementer's own test applied to the wrong answer. A `Schema.Library` is not a `CatalogObject`, `Schema.Catalog.Validate`'s type list refuses it as a top-level object, every library table in the catalog store is keyed by library name (`InsertLibraryOwner`, `InsertLibraryVersion`, the `DAELibrary*` tables), `Schema.Object.ID` is get-only so BOP does not put it in the `.d4l` file (checked against three shipped `.d4l` files - no `id` attribute), and no call site in the tree reads `library.ID` or takes a dependency on a library. The implementer's own `Library.Clone()` comment said as much - "a clone … takes no identifier" - leaving one type treated two ways inside one file. The seven sites are back on the name-only constructor, the never-needed `Library(int, string)` is gone before it ships, and the reason now sits on the type as `SessionObject`'s does. `Schema.LoadedLibrary` *is* a catalog object and is still numbered at its three sites; that distinction is the point of the remark. `docs/migration-notes.md` updated to match.
- **The benchmark program still had the unguarded save-and-restore** that the implementation had just fixed next door in `TestEnvironment.cs`, and the handoff's reason for leaving it - "it is in a project no solution builds" - is wrong: `tests/Dataphor.Benchmarks/DAE.Benchmarks.csproj` is line 40 of `Dataphor.slnx`, every build compiles it, and the root `AGENTS.md` documents running it by hand. `BenchmarkServerInstance.Release()` lowered the process-wide counter on dispose while another of the program's engines could still be running - the same mechanism that reddened `AbandonedClientProcessTest`. Same one-line guard, same remark.

### Parked as a tripwire

- **`Compiler.cs`'s `#if USETYPEINHERITANCE` cast-operator block** adds its operator to `PlanCatalog`, which asserts `ID > 0`, but constructs it from a name alone. The handoff listed it as a known gap and left it alone because no build can check an edit to it - right, and it is safer than the handoff feared: the block is pre-4.0 source that would not compile even with the constant defined (`Schema.Objects` is generic now, the parameter names are the old ones), so reviving it is a port of its own and it is not a latent defect on any path that can run today. A `NOTE:` at the site now says what the revival owes. That is its durable home; nothing is filed.
- No other new tripwire. The one conditional concern in this area - that an engine spends catalog identifiers on compile-time objects no catalog will hold, so a long-lived engine moves towards `ObjectIDsExhausted` - is already recorded at `ObjectIDGenerator.Allocate` and weighed again in `bug-object-id-counter-is-process-wide`. This step reduces that consumption by a large factor. The run-time sites that allocate per cursor open rather than per compile (`OrderTables`, `ExplodeTable`, `UnionTable`, `TableValue`) allocated from the same counter before and after, and sit inside that estimate's "per statement" figure.

### Checked and found sound

- **The handoff's three self-flagged judgements.** The generated-operator sites in `Compiler.cs` (representation and special selectors, property accessors, `IsSpecial`, special comparers, `iEqual`/`iCompare`) are each added to `PlanCatalog` within a few lines, and `Schema.Catalog.Validate` asserts `ID > 0` with `USEOBJECTVALIDATE` defined in both configurations of `DAE.csproj` (read) - so numbering them was required, not optional. `NativeMarshal.NativeTableToTableVar` does have a `Plan`. And **`Schema.SessionObject` is right to be unnumbered**: it is not a `CatalogObject`, `Catalog.Validate`'s type list refuses it, it lives only in `ServerSession.SessionObjects` / `Plan.PlanSessionObjects` and is resolved by name, and no site reads its identifier. The departure the handoff offered to have reversed stands; `SessionTables` and `SessionAndProcessScopedTables` pass.
- **The `CheckDeviceReconcile` probe table variables** (`Compiler.cs` 1774, 9998, 10191 and `SystemNodes.cs` 1016) look like throwaways that could carry no identifier. They cannot: `Device.CheckReconcile` → `Reconcile(process, tableVar)` → `GetServerCatalog(process, tableVar)` does `serverCatalog.Add(tableVar)`, a `Schema.Catalog.Add`. Allocating there is correct.
- **The handoff's "what to exercise" list is mostly already exercised.** Every coverage-script server runs on the default SQLite catalog store (`TestServerInstance.CatalogStoreClassName`), so each `create` in a script writes a creation script through `TableVarColumn.EmitStatement(ForStorage)` → `SaveObjectID`, which throws `SchemaException` 113249 for an unnumbered column. `CreateTableFrom`, `Views`, `SerializationViews`, `References`, `EventHandlers`, `Constraints`, `SessionTables` and `SessionAndProcessScopedTables` all pass, and `StoreRebuildWorkflowTest` creates a view and restarts the server against its own store. The restart arm the handoff asked for adds nothing the creation arm has not already proved, because a column's identifier is written when the object is created, not when it is read back.
- **A view's derived references carrying `UnassignedID`.** `EmitTableVarStatement` emits keys, orders, row constraints and meta data - never references (read) - and `Reference.EmitStatement` only calls `SaveObjectID` for `EmitMode.ForStorage`. A view's inferred references are recomputed on every recompile and never persisted, so unnumbered is right, and the `RenameNode` / `TableNode` derived references that *do* allocate need their number for `GetGeneratedName`.
- **Two unnumbered objects colliding in one collection.** `BaseObjects<T>` indexes by name only - there is no identifier index on `Schema.Objects` or on `Schema.Libraries` (read) - so the `Dictionary` that produced `Key: 5` is `CacheCatalogObject`'s, which takes a `Schema.CatalogObject` and refuses `UnassignedID` outright.
- **`InsertPersistentChildren`** inserts a `DAEObjects` row only for persistent representations, defaults, constraints and specials, never for a column, a key or an order - so the three guards plus `Catalog.Validate` really are the whole net, as the handoff says.
- **The remaining name-only construction sites of catalogable types** are four, and all four are dead: `Compiler.cs:5304` above, plus `GeneratorNodes.cs:60` and `TestNodes.cs:1080`/`:1193` in two files no project compiles (`Directory.Build.props` sets `EnableDefaultItems=false` and `DAE.csproj` lists its sources explicitly; both files also use pre-4.0 APIs and `System.Runtime.Remoting`).
- **Source hygiene.** Every file the implement commit touched keeps its line endings and byte-order-mark state, and so does every file this review touched - all ten diffs are a handful of lines, with no whole-file rewrite (`git diff --stat`). The new comments say why rather than narrating the statement under them.

### Noticed and deliberately left

- **`TestEnvironment.WithTheObjectIDCounterRestored` now probes the counter with `Schema.Object.GetNextObjectID()`, which allocates**, so each wrapped body burns one identifier in the `finally`. The comparison is still correct (both sides are read the same way) and there is no non-allocating read on the static surface. Left: the whole method is deleted by `bug-object-id-counter-is-process-wide`, and a handful of identifiers per test run is not worth a new accessor.
- **The two identical three-line comments in `TableVar.CopyTableVar`'s derived-reference loop.** They sit in the pre-existing near-duplicate `if` / `else if` arms about twenty lines apart; de-duplicating the comment means de-duplicating the arms, which is a refactor of untested inference code on a port whose constraint is behaviour preservation. A reader in either arm needs the reason.
- **`Compiler.cs` is 15,710 lines** (`wc -l src/engine/DAE/Compiling/Compiler.cs`), and this commit added four net lines to it. Pre-existing, with no open ticket and no `NOTE:` claiming it. Not filed: splitting the compiler is a port-wide refactor that competes directly with behaviour preservation, and nothing in this diff makes it worse.

Nothing reached the filing bar. The three findings fixed here are each a single site with a local fix; the dormant-code concern is a comment; and nothing found names a class-level invariant that the chain's remaining ticket does not already carry.

### Tests

**One test added, one contract it pins, none cut.** The implement diff contained no tests, so there was nothing to review as code or to cut.

`BufferedOperatorColumnOwnershipTest.BufferingAUnionLeavesItsSourcesColumnsOnTheirOwnTableVars` is the reproduction of the `UnionTable` defect above, at the lowest layer that shows it: a D4 union through the in-process engine harness, then the left and right tables' columns read back off `Instance.Server.Catalog`. It fails on the code as the implement commit left it and passes after the fix. The contract is not an object-id rule but the one the whole chain leans on - that a run-time buffer owns copies and never the compiled plan's own schema objects - which is why it is worth a test where an implementation detail about identifiers is not.

**No test for the identifier rule itself, deliberately.** This step changes no behaviour on any engine path - every converted site drew from the same generator before and after - and "an object with no engine in reach carries no identifier" is an implementation choice rather than a contract. The three guards from `engine-object-id-generator` already enforce the half that matters, and `StoreRebuildWorkflowTest` already pins the property that does: an engine numbers its built-in objects the same on every start.

**The honest limit, as the handoff said:** a site on a path the suite never persists could be unnumbered and nothing would notice. By the design that is harmless; it is unproven rather than proven.

### Still unverified

**The SQL device's reconciliation of a device table into the server catalog** (`SQLDevice.cs` 2408, around 2443, and 2679) needs a real SQL Server. The reasoning behind numbering its table variable, its columns and its references is now confirmed statically from the other end - `Device.GetServerCatalog` does `serverCatalog.Add(tableVar)` and `CreateDeviceTableInServer` does `plan.PlanCatalog.Add(tableVar)`, both of which assert `ID > 0` - but the path has still never been run. `feat-ws7-devices-and-libraries` owns the arm that can.
