## What landed

A client outside the server answers three questions about the row a user is editing — what should this column default to, what follows from the user having changed this column, is this row acceptable — out of its own copy of the schema whenever the server has said it may. That permission is computed once, when the plan is prepared (`ServerProcess.CopyDataType` emits `DAE.IsChangeRemotable`, `DAE.IsDefaultRemotable` and `DAE.IsValidateRemotable`, each as "the work is remotable, **or** there is no work"), and `LocalCursor.Default`, `Change` and `Validate` read it back through `TableVar.Is*CallRemotable`. A form holds its plan for as long as the user keeps the form open, and nothing re-sends the permission or the copy it is exercised against, so a data type altered after the form opened was invisible to that form.

The fix is one extra condition at each of the three call sites: `LocalPlan.IsSchemaCurrent`, which compares the catalog generation recorded in the plan's own descriptor with the newest generation the client has been told about (`LocalServer._serverCacheTimeStamp`). A plan that is behind sends the proposal to the server, which answers from the live schema — which `bug-rolled-back-type-constraint-stops-the-column-check` (K43) made correct for an open server-side cursor, and `bug-remote-validate-validates-the-wrong-row` (K44) made correct for the remote `Validate` this now reaches.

The implement stage is commit `ticket(implement): bug-remote-form-is-never-told-about-a-type-change`. Review moved the predicate, tightened one test and corrected a documented condition in four places; all of it is listed below.

The behaviour was measured against an in-process server with the shipped client stack in front of it (a `LocalServer` over a `RemoteServer` over the engine), with the type altered on a session of the engine's own while the client's cursor stayed open. Four cases in `tests/DAE.Server.Tests/RemoteProposalStalenessTest.cs` pin it.

## Review findings

Read the implement diff first, then the handoff. The mechanism was checked by reading `LocalPlan`, `LocalCursor`, `LocalProcess`, `LocalServer`, `RemoteServerProcess`, `RemoteServerPlan`, `RemoteServerCursor`, `CatalogCache` and `PlanDescriptor`, and by two deliberate mutations of the predicate, each built, run and reverted.

### Checked and sound

- **The comparison's direction, and that it is load-bearing.** Neutralizing the predicate to `return true` fails exactly the three cases the handoff names, with the values it recorded (the created check not refused, the created default `null` where the engine proposed 7, the attached handler leaving 2 where the engine left 99) and passes the fourth. Inverting it to `return false` fails exactly the fourth and no other. So the handoff's claim that the fourth case is the only thing in the suite that would catch an inverted or always-false comparison is true as measured, and that case earns its place.
- **The plan's recorded generation is always populated.** Both `PlanDescriptor` constructions in `RemoteServerProcess` set `CacheTimeStamp` (the statement one directly, the expression one through `RemoteServerPlan.GetCatalog`), both `OpenCursor` overloads route through `PrepareExpression`, and the field is a `[DataMember]`, so it survives the CoreWCF transport. There is no path that leaves it at 0 and so no path where the optimization is silently disabled.
- **"Every write to that field is under the exclusive cache lock" is true.** Both callers of `LocalServer.EnsureCacheConsistent` — `LocalExpressionPlan.GetDataType` and `LocalProcess.CatalogLookupFailed` — hold `LockMode.Exclusive` across the call; the only other write is the `LocalServer` constructor, before anything holds a reference. The unsynchronized-read argument in the doc comment stands as written.
- **The condition-order hazard the handoff flagged does not exist, and would be harmless if it did.** `LocalExpressionPlan`'s constructor calls `GetDataType()`, so a cursor's plan always has its data type set and `TableVar` never triggers a lazy fetch. Even if it did, a plan whose own descriptor is newer than the client's value reads as current, which is the correct answer — the lazy fetch could only raise the client's value to the plan's own.
- **The remote fallback handles the null old row.** `LocalCursor.Validate` leaves `oldBody.Data` null when the caller passes no old row, and `RemoteServerCursor.InternalValidate` tests for exactly that. So the newly-reached remote `Validate` is not relying on an exception.
- **The three call sites are the only ones.** Nothing else in `src/` or `tests/` reads `Is*CallRemotable`, so there is no fourth proposal path left answering from a stale copy.
- **Source hygiene.** CRLF, the UTF-8 byte-order mark and tab indentation preserved in both `.cs` files; LF and no mark in the two documents. No file reformatted or re-encoded. `LocalCursor.cs` went 1156 → 1100 lines, `LocalPlan.cs` 439 → 495.

### Fixed in this pass

- **The predicate moved to the class that owns both of its operands.** Implement put `IsPlanSchemaCurrent` on `LocalCursor` and, to feed it, added `internal long PreparedCacheTimeStamp` to the public `LocalPlan` — a raw counter whose only correct use is this one comparison, and whose own doc comment has to warn the reader off the near-miss (`LocalServer.CacheTimeStamp`, which costs a round trip). Both values live on `LocalPlan`: the plan's own generation is in its descriptor, the client's highest-known one is reachable through its `LocalServer`. So the comparison is now `internal bool LocalPlan.IsSchemaCurrent`, the raw counter is not exposed at all, and the three call sites read `_plan.IsSchemaCurrent`. One new member instead of two, no number for a second site to compare differently, and the handoff's own open question about widening a public class's surface is answered: what is added is a predicate, not state.
- **One test case could have passed on the wrong exception.** `IsRefused` returned a bool from `catch (Exception)`, so any failure at all on the remote path a stale plan now takes — the path this change introduces — would have read as "the check refused the row". The sibling engine-side fixture `TypeChangeSummaryTest` does not accept that: it asserts the error text names the constraint. `IsRefused` is now `RefusalOf`, returning the exception or null, and the constraint case asserts `Does.Contain("IsPositive")` on it. It passes, which also confirms the client's refusal really is the new check arriving from the server rather than an incidental failure.
- **The documented window was stated too narrowly, in four places.** The `NOTE:`, the `docs/migration-notes.md` entry, the K43 record and the test's own remarks all said the window is a form that "prepares nothing at all" or "sits idle". The client's value is raised only where the catalog copy is rebuilt, which is reached by prepared or evaluated **expressions**: `LocalProcess.Execute` carries no plan descriptor at all, and `PrepareStatement` carries one that never reaches `EnsureCacheConsistent`. So a form that posts statements, or that only edits and posts rows through the cursor it already holds, is just as much inside the window as an idle one — which matters, because "idle" invites a reader to assume any activity closes it. All four now say "prepares or evaluates no expression", and name the statement case explicitly.
- **Four cross-references in `docs/migration-notes.md` pointed at "the last entry in this section".** Three of them were added by this change and one rewritten by it, all aimed at the new entry because it was last. The next entry appended to that section would have falsified all four silently. They now read "the entry below on an already-open form", which survives an append. One of them also said a form notices an attached handler "as long as it has prepared any query since the attach"; corrected to "prepared or evaluated", for the reason above.
- **Emphasis convention.** The moved doc comment used `<b>`/`<i>` where the removed original and the surrounding modernization comments use `*…*`; switched back.

### Weighed and left alone

- **The comment's length.** Roughly 50 lines of doc comment and `NOTE:` for a one-line predicate, which the handoff offered for cutting. Each paragraph carries something no other file states: what the permission is and why it exists, why `CacheTimeStamp` and not `ShouldCallProposablesTimeStamp`, that raising the client's value discards the whole client catalog copy (so the predicate also stops a local proposal running against detached schema objects), the synchronization argument, and the window. It says why rather than narrating statements, which is the bar the project's hygiene rule sets. Kept, now in one place instead of spread across two members.
- **The narrower of the two reading points.** The ticket offered `LocalServer._serverCacheTimeStamp` (recommended) or a second field recording the highest descriptor generation from anywhere. Implement took the first, and that is right: `LocalProcess.Execute` returns no descriptor, so the wider field would only help a client that *prepares* statements — not the form-shaped case anyone would reach for it to fix — in exchange for a second piece of state with a meaning a reader would confuse with the first. Recorded as a parked tripwire below rather than re-opened.
- **No `docs/migration-notes.md` entry for the new member.** `IsSchemaCurrent` is `internal`; no extension can see it. After the move there is no public-surface change at all, which settles the question the handoff raised more cleanly than an entry would have.
- **Unquantified round-trip cost.** The change makes no claim about it, and neither does this ticket. The `5.65 µs` figure in the K43 record is that ticket's server-side recompute measurement, labelled as such.

### Parked as a tripwire

- `LocalPlan.IsSchemaCurrent`, the `NOTE:` — the window left open: a session that prepares or evaluates no expression between the catalog change and the user's edit still answers locally, and still reports the change only when the row is saved. What would change the answer is named there: a per-proposal round trip becoming acceptable, or a server-to-client notification channel built for some other reason that this could ride on. Not a ticket: it is conditional on a cost decision or an architectural addition that does not exist, and the behaviour it produces is a late report of an error that is still raised correctly when the row is saved.

### Not filed, and why

No major findings. Nothing was found that serves a current-release anchor or names a class-level invariant, so no ticket was filed: the three defects above were a misplaced member, a test that could pass on the wrong exception, and a condition documented too narrowly — all fixed in this pass. The one conditional concern is the window, which was already parked at its site and is now stated precisely.
