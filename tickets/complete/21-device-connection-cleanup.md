## What landed

Two arms at one site.

**The seven uncompiled duplicates are gone** from `libraries/Connection/Source/`: `ConnectionException.cs`, `ConnectionException.resx`, `SQLConnection.cs`, `SQLTypes.cs`, `DotNetConnection.cs`, `MSSQLConnection.cs` and `ODBCConnection.cs`, with the leftovers comment in `DAE.Connection.csproj`. All six `.cs` files had drifted from the live copies under `src/engine/DAE/Connection` and in every case the live file was the newer one - old Hungarian naming (`FResourceManager`, `AErrorCode`), one monolith where the live tree has several files, and two error codes (127123, 127124) that only the live pair carries. Nothing was found that only a stale copy had. The Visual Studio 2003-format `DAE.Connection.ODBC.csproj` beside them went in the same change that converted the project it was a copy of, so no project file name is used twice in the tree any more (checked across the whole repository, `legacy/` included).

**The ODBC connection library is in the build again.** `libraries/ODBCConnection/Source/DAE.Connection.ODBC.csproj` is SDK-style, matching its sibling `DAE.Connection.csproj` in shape: assembly and root namespace `Alphora.Dataphor.DAE.Connection.ODBC`, the constants block, project references to Base, DAE, Server and the Connection library, explicit `Compile` items, one versionless `PackageReference` to `System.Data.Odbc` (pinned 10.0.15 in `Directory.Packages.props`, matching `System.Data.OleDb`). The project is in `Dataphor.slnx` and in the layout's Library list, the layout's `DataphorD4Library Remove` line for `ODBCConnection.d4l` is gone, and `Properties/AssemblyInfo.cs` is trimmed to title, description and `DAERegister` with its byte-order mark and CRLF endings intact. The library assembles to exactly four files in both configurations, the `System.Data.Odbc.dll` among them being the package's Windows implementation (298,280 bytes from `runtimes/win/lib/net10.0/`) rather than the 101,712-byte reference assembly, which is the layout's runtime-identifier ranking doing its job.

**OLE DB needed nothing**: `OLEDBConnection.cs` has been compiled by `DAE.Connection.csproj` against the `System.Data.OleDb` package since `build-server-project`. The plan's WS7 row for ODBC and OLE DB is closed on both halves.

One test came with the implementation and stayed: `ODBCConnectionLibraryRegistersWithoutADriverManager` in `tests/DAE.Server.Tests/LibraryLoadingTest.cs`, which registers the library on an in-process server and asserts it does not throw. Documents edited to match the new state: `AGENTS.md`, `docs/architecture/devices.md`, `docs/migration-notes.md` (the ODBC class is available again, on a package, and still needs a driver and driver manager at run time; OLE DB unchanged), `docs/modernization-plan.md` in six places, and both arms of `tickets/backlog/debt-ws12-hygiene-remainder.md`.

## Review findings

**What was checked.** The implement diff (`ticket(implement): device-connection-cleanup`) was read first, before the handoff. The deletions: a whole-tree grep for every deleted path and for `DAE.Connection.ODBC.csproj` found no live reference - the only hit outside build output and tickets is the legacy `Dataphor.sln`, and it names the *surviving* `libraries/ODBCConnection/Source` path, not a deleted one, so nothing to do there (that solution no longer builds and `build-remove-legacy-build` deletes it). The duplicate-project-file-name claim the change writes into `AGENTS.md` was verified by listing every `.csproj` basename in the repository: no duplicates. The new project was compared with its sibling `DAE.Connection.csproj` property by property, and its `AssemblyInfo.cs` with the ten other library `AssemblyInfo.cs` files (all eleven keep the same unused `using System.Runtime.CompilerServices;`, so that is the house style, not an oversight here). The library's `.d4l` declares a dependency on the `Connection` library, and the test fixture's `Libraries` list carries both, so the registration under test is the real dependency chain. Builds: `dotnet build Dataphor.slnx` in Debug and Release, 0 errors, 144 warnings each; a `-t:Rebuild` of the new project alone emits no warning of its own. Layout: both `artifacts/layout/<config>/Libraries/ODBCConnection/` folders hold the expected four files with the Windows runtime file. `python tools/docs-size-check/check_size.py` - 13 files checked, 0 over the limit. The documents' claims were re-counted rather than taken on trust: three unconverted libraries (PGSQLConnection, PGSQLDevice, Sample.Shipping) matches the layout's `Remove` list, and the `port-server-on-net10` audit row now reads as a dated record ("still excluded source files when this was measured"), which is the right shape - its "23 files across 26 projects" is explicitly historical, and the solution has 29 projects today.

**Tests run** (one ring wider than the implement stage's set, which was `LibraryLoadingTest|HostProgramTest|FormCustomizationTest`): the same three plus `LibraryAttachTest`, `LibraryDropTransactionTest`, `HostCommandLineTest`, `HostBindingHookTest`, `DeviceClassAttribute*` and `SamplesCorpusTest` - the neighbours a regression in library registration, library loading or the layout would show up in. 69 passed, 0 failed, 0 skipped, 1 m 41 s. Also `python -m unittest discover -s tools/coverage-report`, 14 tests, after editing that tool's data file. No coverage-manifest entry changed, so no D4 coverage script was run. No pre-existing failure surfaced.

**Major finding, fixed in this pass: a new shipping assembly was missing from the coverage map, which breaks the coverage report.** `tools/coverage-report/areas.json` lists every assembly the suite can load in one of three groups, and an assembly on no list makes `coverage_report.py` print `unlisted assembly`, **suppress the entire report** and exit 1 - deliberately, so that a hole cannot read as a healthy rollup. `Alphora.Dataphor.DAE.Connection.ODBC` was on no list. This was not theoretical: collecting coverage over the new test (`--collect:"Code Coverage;Format=cobertura"`) produced a report containing that assembly, and running the tool over it printed `unlisted assembly: Alphora.Dataphor.DAE.Connection.ODBC (92 lines)` with no report body. The new test is what makes it reachable - registering the library runs its `DAERegister.GetClasses()` - so this change both introduced the assembly and arranged for it to be measured. Fixed by adding the name to the `reported` list beside `Alphora.Dataphor.DAE.Connection`; the tool now exits 0 and the assembly appears in the table at 5.4 %.

Rather than leave that as a one-off, the step was added to the project-conversion checklist in `AGENTS.md`, next to the `Layout.csproj` and `Dataphor.slnx` steps, because every future library conversion walks into the same hole and nothing else would catch it: the build is green, the tests pass, and the breakage only appears the next time somebody collects coverage. No new test - `test_an_assembly_on_no_list_suppresses_the_report` in `tools/coverage-report/test_coverage_report.py` already pins the behaviour; what was missing was the data entry and the instruction to make it.

**Latent defect found, filed rather than fixed: `tickets/backlog/bug-odbc-money-parameter-precision.md`.** `ODBCCommand.PrepareParameters` describes a money parameter to the driver as a decimal with precision 8 and scale 28 - 28 digits after the point in an 8-digit number, which is not a number. The two values are transposed: the parked Oracle connection has the same pair the other way round, and every other connection in the tree uses its provider's own money or currency type. This is original 3.1 code that was never compiled before this ticket, so the defect is as old as the file and has only now reached a shipped build. It was filed instead of fixed because the one-line swap changes what a device sends to a database and there is no way to run an ODBC connection here (it needs a driver and a data source on the machine), so neither the defect nor the fix can be seen - and project policy is that behaviour is the specification and a fix comes with its reproduction. The ticket says what would settle it and that it belongs with whoever first gives ODBC a live test. Checked first that no open ticket claims the site; `device-mssql-string-parameters` discusses a *different* mapping defect in the same method and says to file nothing for the ODBC case, which is why the two are recorded separately rather than merged - that instruction was about the Unicode class it owns, not about a transposition.

**The implementer's one test was weighed and kept.** It departs from what the ticket asked for (a throwaway run, no test), and the handoff says so and invites the cut. Kept, for the reason the project's testing rule gives: this ticket re-hosts a subsystem onto .NET 10 and a NuGet package, and the behaviour at risk - one private managed package resolving out of a flat library folder through `LibraryAssemblyResolver` - is not something the compiler or the layout's `.d4l` check sees. It is four lines in a fixture that already does exactly this for the sibling library, and it is also what made the coverage-map hole above visible, which is a fair argument that it earns its keep. No test was added by this review: the finding that mattered is data and documentation, and the tool's own suite already covers the behaviour behind it.

**Noticed and deliberately left.** The test's name promises more than any run on Windows can show - `odbc32.dll`, the ODBC driver manager, is part of Windows, so a green run here cannot distinguish "does not need a driver manager" from "found one". What the test really pins is that registration does not construct a connection, which is exactly what the remarks block above it says, so the name was left alone rather than churned. `libraries/ODBCConnection/Source/obj/` still holds an untracked `AssemblyReference.cache` from the old project format; it is covered by `.gitignore` (`[Oo]bj/`) and the new project builds into `artifacts/obj/`, so it is harmless. The `build-globbing-cleanup` arm of `debt-ws12-hygiene-remainder` could in principle switch the Connection project to default globbing now that its folder has no uncompiled file left - its remaining prerequisites (`ui-dataphoria-port`, `library-frontend-web-leftovers`) are correct as written and that is that ticket's call, not this one's.

**Empty categories.** No tripwire was parked in code: the one conditional concern near this change - a private package whose Windows file ships under an older runtime-identifier name - already carries a `NOTE:` in `tools/layout/Layout.csproj` from `build-runtime-layout`, and `System.Data.Odbc` is not such a case (its Windows file is under `runtimes/win/`, which the ranking handles). No accepted-tradeoff `NOTE:` at any site this change touches had its revisit condition trip. Nothing was found wrong with the deletions, the project file, the layout entries, the package pin or the six document edits beyond what is written above, and no finding was left unresolved: the one major finding is fixed here, the one latent defect is filed, and everything else is a check that passed.
