## What landed

The engine keeps values too large to carry inline - the D4 types `Binary` and `Graphic`, and rows, lists and tables - in a stream or buffer the server owns, and a variable's slot owns its value. Releasing a scope's variables used to be a *statement the compiler appended to the end of the compiled block*, so only control reaching that end ran it. A raise, and equally D4's `exit`, `break` and `continue` (which the engine implements as .NET exceptions), skipped it and the values were held for the life of the session. A `continue` in a loop whose body declared one leaked once per iteration.

The release now lives in the `finally` that already pops the scope, driven by a run-time comparison of stack depths rather than a compile-time list of positions.

**One new public helper.** `Alphora.Dataphor.DAE.Runtime.Stack.ReleaseAbove(int depth, IValueManager manager)` releases the values of the slots above `depth`, nulling each slot before disposing its value. `Stack.Count` is window-relative and is read the same way at entry and exit, so the two depths are comparable; a scope needs no agreement with the compiler about where its variables sit. That is what makes it right for a block that raised before declaring all its variables, and for an operator body whose compile-time symbol frame does not line up with its run-time frame.

**Five call sites**, each in a `finally` that already existed except where noted:

- `FrameNode.InternalExecute` (`ImperativeNodes.cs`) - the D4 `begin ... end` statement.
- `ErrorHandlerNode.InternalExecute` (same file) - the handler's own variables and the copy of the error it pushes.
- `CallNode.InternalExecute` (same file) - an operator body is not a `FrameNode`, so its locals are leftovers in the call's stack window; this is the site that owns them.
- `AggregateCallNode.InternalExecute` (`AggregateNodes.cs`) - twice: around the per-row aggregation block, and around the whole initialization/aggregation/finalization sequence. The second needed a new `try`/`finally`.

**The compiled releases are deleted**, all of them: `DeallocateVariableNode`, `Compiler.CompileDeallocateFrameVariablesNode`, `Compiler.CompileDeallocateVariablesNode`, the inline release loop in `CompileOperatorBlock`, and all eight call sites (six in `Compiler.cs`, two in `DDLNodes.cs`). Two of them were not merely redundant - the `try ... except` handler's wrapper never executed at all, and an aggregate operator's aggregation-block releases ran past its own variables into the aggregate column slots - and both simply stop existing. `docs/migration-notes.md` gained two rows under *Custom C# extensions*, one for the new helper and one for the three removed members.

The `NOTE:` above `Program.Stop` still records the `DEBUG` stream-count check that cannot go in yet, and now names what blocks it.

## Review findings

The implement-stage diff (`ticket(implement): bug-an-error-inside-a-block-leaks-its-binary-values`) was read before the handoff summary, then the claims in it were checked by probing the engine with a throwaway fixture on `InProcessTestFixture` (nineteen scripts, built and run, fixture removed; `git status` shows only the five intended files).

### Fixed in this pass

**An operator's `result` was the one variable the new release could not reach, and it leaked on every path that does not return.** Found by probing, not by reading: a function that assigns `result` and then raises left one stream behind per call, and so did an aggregate whose initialization assigned `result` and whose aggregation then raised. The result slot sits below the depth both sites released above, deliberately - the normal path hands its value to the caller and must not release it - so the implement stage excluded it, as the compiled releases it replaced had (`CompileDeallocateVariablesNode` took a `resultVar` to skip, and `CompileOperatorBlock`'s `stackDepth` counted the result symbol in). The leak is therefore as old as the code, not introduced here, but it is the same defect this ticket exists to close and it is reachable from four lines of D4:

```
create operator ZF() : Binary begin result := Binary('0001'); raise Error('boom'); end;
begin var LB : Binary := ZF(); end;          -- one stream held for the life of the session, per call
```

Fixed at both sites by moving the release floor one slot down - to the depth recorded *before* the result slot is pushed - and having the return null the slot it reads, so a value the caller took is not released and a value nobody took is. The operand slots stay below the floor and are still left to the caller and to `InstructionNode`'s cleanup. Two cases added to `tests/DAE.Server.Tests/AssignmentValueOwnershipTest.cs`, one per release site (`AFunctionLeftByARaiseReleasesTheResultItAssigned`, `AnAggregateLeftByARaiseReleasesTheResultItAssigned`); both were confirmed load-bearing by putting the old floor back, rebuilding and watching exactly those two fail while the other fourteen passed.

Checked that the release cannot free a value something else still names. Reading a variable that is not passed by reference copies it (`StackReferenceNode.InternalExecute`), so `result := ALB` gives the result slot its own value for a `var`, a `const` and an `in` operand alike, and `result := LA` likewise for a body local. All three shapes were probed with the caller asserting its own value afterwards: none errored, none changed the caller's value, and all three now leave the stream count where they found it.

**Two `NOTE:`s named the wrong defect.** The `NOTE:` at `Program.Stop` and the one in `ForEachNode`'s list branch both attributed a leak to `foreach` over a list. Re-measuring with the loop removed gave the same counts (see below), so both now name `bug-a-list-value-never-releases-its-elements` and describe what actually leaks.

### Filed

**`bug-a-list-value-never-releases-its-elements`** (`tickets/fix/4-...`). The implement stage recorded a `foreach`-over-a-list leak, scoped out by the ticket, measured over five shapes, and left a `NOTE:` at the site. Re-measuring those shapes *without* the loop showed the leak is not in `foreach` at all: `begin var LL : list(Binary) := { Binary('0001'), Binary('0002') }; end;` leaves two streams behind, and so does `({ Binary('0001'), Binary('0002') }).Count()`, which declares no list variable and runs no loop. The site is `ListValue`, which has no `Dispose(bool)` override and so releases none of its elements, although the engine sets `ValuesOwned` on the lists it builds and `Row` honours exactly that flag. The ticket carries both arms - the list, and `foreach` not releasing the list it evaluated nor nulling the slot it lent - because fixing either alone turns today's single release of the lent element into a double release. It is filed past the bar on two counts: it serves the same current-release anchor, and the generalized test it asks for (the `ValuesOwned` contract across the `DataValue` subclasses, which `TableValue` also appears to omit) retires the class rather than the instance.

### Parked as a tripwire

**`Stack.Count` changes meaning under `AllowExtraWindowAccess`**, which the new depth-comparison idiom depends on: `Count` is window-relative only while that flag is off. Every caller today reads its entry depth and releases with it off, and the one runtime site that sets the flag (DEBUG-only, in `AggregateCallNode`'s row loop) sets and clears it inside a region that contains no `ReleaseAbove`, so nothing is wrong now. A future caller that recorded a depth outside such a region and released inside one would walk below its own window and release another window's values. Recorded as a `NOTE:` in `ReleaseAbove`'s remarks, where the next caller will read it.

### Checked and found nothing

- **Every deleted compiled release has a run-time replacement.** The eight deleted call sites were traced to the node that executes each block: `CompileFrameNode` and the delimited-block case to `FrameNode`, the `except` handler to `ErrorHandlerNode`, `CompileOperatorBlock` to `CallNode`, and the four aggregate-operator sites (two in `Compiler.cs`, two in `DDLNodes.cs`, plus the two `localPlan` copies) to `AggregateCallNode` - which is the only node that executes `Initialization`/`Aggregation`/`Finalization.BlockNode`, confirmed by grep. Nothing is left releasing nothing.
- **The aggregate's ordering argument holds.** The outer release is above a depth the aggregate column slots are also above, and they are safe only because the inner `finally` pops them first; they hold values borrowed from the row the cursor selects into. Checked by reading the nesting and by running an aggregate whose three blocks each declare a `Binary` and whose initialization leaves variables for the later blocks (0 streams left), plus the `AggregateOperators`, `Aggregates`, `LongAggregates` and `MinMaxOperators` coverage scripts.
- **`CallNode`'s release runs after the operand hand-back**, in the same `finally`, so the hand-back does not read slots already nulled. Unchanged by this pass and verified by the `var`-operand cases in the fixture.
- **Borrowed slots elsewhere.** Every runtime `Stack.Push` of a value a slot does not own that was examined (`CaseNode`'s selector and when-values, `ValueUtility.ValidateValue` and `DefaultValue`, `ForEachNode`'s cursor branch, the aggregate column slots) pops in a `finally`, so the slot is gone before any enclosing scope's release runs. The exception is `ForEachNode`'s list branch, which is the filed ticket.
- **Shapes probed, all leaving the stream count where they found it:** a block left by a raise with the error caught in D4 and uncaught; an error handler that declares a `Binary` and re-raises; a `var` operand assigned and then raised past; nested blocks raising from the innermost; `break` out of a `while`; `exit` from an operator body; a `try ... finally` whose `finally` block declares a `Binary` after the `try` raised; a function that assigns `result` and then `exit`s; a function that raises without assigning `result`.
- **Documentation.** `docs/migration-notes.md`'s two new rows are accurate, and the public surface this review pass changed is none - `ReleaseAbove`'s signature is unchanged and nothing an application can see behaves differently beyond the engine holding less memory - so no row was added. No page under `docs/architecture/` describes the stack, the streams or who releases a value, confirmed by grep over all ten pages; `bug-an-operator-argument-is-released-by-the-wrong-owner` names writing that page as its own deliverable, so starting it here would mean writing it twice.
- **Source hygiene.** `AggregateNodes.cs` 963 lines, `ImperativeNodes.cs` 2,128, `Stack.cs` 110. `Compiler.cs` is 15,669 lines, far past any reasonable cap, but this diff *shrank* it by 61 lines and no open ticket claims its size; not this ticket's to raise. Tabs, CRLF and byte-order-mark state preserved in every file edited (`ImperativeNodes.cs`'s eight pre-existing LF-only lines are untouched).
- **The implementer's four tests** were read as code under review. Each pins a distinct exit path rather than a distinct variable type, which is the right axis, and the fixture's exact-count assertion makes them arithmetic rather than thresholds; none restates the implementation or verifies a mock. None cut. The two added are reproductions of the defect found above.
- **Cost.** The implement stage's measurement (not separable from run-to-run noise on this machine; bounded at about 16 ns per two-slot block exit) was not re-run: this pass moves one release floor by one slot and adds one `Poke` per returning call, which is below what that measurement could resolve.
