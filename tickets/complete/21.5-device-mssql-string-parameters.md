## What landed

`MSSQLCommand` describes a parameter to SQL Server in two places, and the cursor location decides which one a statement goes through: `PrepareParameters` configures the provider's own `SqlParameter` for the client-side path, and `GetParamTypeDescriptor` writes a T-SQL type into the `@paramdef` string that `sp_cursoropen` is given for the server-side path. Both said single-byte - `varchar(n)` for a string, `text` for an `SQLText` - and SQL Server converts such a value to the database's collation code page on its way in, so every character that code page had no room for was stored as a question mark, with no error raised and nothing left to read back.

Both descriptions now say Unicode: `SqlDbType.NVarChar` and `SqlDbType.NText` on the client-side path, `nvarchar(n)` and `ntext` on the server-side one. They had to move together, because `DetectCursorLocation` decides which of them a statement takes, and a difference between them would be a device whose behaviour depended on whether its statement began with `select`. The `// Q: Should this be NText or text` that had stood at the site since 2008 is answered: `ntext`, checked against a live server for the two things the argument rests on (an `ntext` parameter declaration is accepted by `sp_executesql`, and an `ntext` parameter inserts into a `text` column without an explicit conversion).

One latent break came with the change and is guarded: `nvarchar` counts characters to 4,000 where `varchar` counted bytes to 8,000, so a `Storage.Length` tag between the two limits produced `nvarchar(5000)`, which the server refuses outright. `NVarCharDescriptor` substitutes `nvarchar(max)` past the limit and for a length of zero or less.

The precedence question that comes with Unicode was settled on measurements and recorded at the site as an accepted tradeoff: on SQL Server 2016 SP1 Express LocalDB (13.0.4001.0), collation `SQL_Latin1_General_CP1_CI_AS`, 200,000 rows and an index on a `varchar(50)` column, a `varchar` parameter seeks the index in 3 logical reads where an `nvarchar` parameter scans it in 625 - but against the same column in a *Windows* collation (`Latin1_General_CI_AS`) the `nvarchar` parameter seeks it through `GetRangeThroughConvert` in 3, so the regression is specific to SQL collations and a deployment has two measured remedies, both in `docs/migration-notes.md`. Unicode was kept: a character lost on the way in cannot be recovered, where a slow query can be seen and fixed.

The plan-cache question - one cached plan per distinct declared string length, measured as 6 entries against 2 - was recorded in a `NOTE:` at `SQLStoreConnection.NativeToParameter`, where it arises, rather than changed: the width worth declaring is the column's, and that method is handed a name and a value but no column.

Tests: `StoreContractTests.NonASCIIStringRoundTripsThroughWrites` (every store the contract runs against) and `MSSQLTextParameterTest` (6 cases - both parameter descriptions crossed with both text types, plus the over-4,000 width on both paths), the latter the only pass in the suite that reaches `GetParamTypeDescriptor` at all. Documentation: an entry in `docs/migration-notes.md`, the catalog-store paragraph of `docs/users-guide/dataphor-service.md` corrected, K47 and the WS7 row in `docs/modernization-plan.md`, and the `DATAPHOR_TEST_MSSQL` paragraph of `AGENTS.md` rewritten for the second fixture that now reads it.

The implement stage is commit `ticket(implement): device-mssql-string-parameters`. Review changed four things in that work and filed one ticket, listed below.

## Review findings

Read the implement diff first, with the handoff set aside until afterwards. The claims were checked by reading `MSSQLCommand`, `DotNetCommand`, `SQLStoreConnection`, `MSSQLDevice`, `MSSQLTypes`, `MSSQLOperators`, `SQLTypes` (the `SQLDevice` library's scalar types), the three stores' seed scripts and the SQL Server device goldens; by reverting the fix and watching the suite fail; and by two measurements against the live LocalDB instance.

### Checked and sound

- **The defect and the tests that pin it, reproduced independently.** With the four lines of the fix reverted and the engine rebuilt, 7 live cases fail and every one of them reports the same substitution the handoff recorded: expected `"中文 αβγ Привет é"`, got `"?? aß? ?????? é"`. That is the 4 non-ASCII cases of `MSSQLTextParameterTest`, its 2 over-4,000-width cases (which carry the same probe, so they fail on the characters before the width matters), and `NonASCIIStringRoundTripsThroughWrites` on the SQL Server store; the SQLite store's run of that last case passes either way, as the handoff says. The engine source was restored and verified byte-identical afterwards.
- **The two parameter descriptions do agree, and nothing else in the file describes a parameter.** Read line by line: `SQLStringType` and `SQLTextType` are the only two text arms in either method, and the remaining arms of each method match one another type for type.
- **The 4,000-character guard is load-bearing on real schemas, not just on the test's 5,000.** The device's own test corpus declares a `varchar(8000)` column (`tests/goldens/devices/MSSQL/Table.AllTypes.sql`), which is a `Storage.Length` of 8000 and so an `nvarchar(max)` descriptor. The `length <= 0` arm has a real case too: a `varchar(max)` or `nvarchar(max)` column reconciles with a length of -1 (measured below), which the old code would have described as `varchar(-1)`.
- **No second place loses the characters on the way out.** `MSSQLToString` translates to `Convert(varchar, …)`, which would convert a Unicode value to the code page; checked against `libraries/MSSQLDevice/Source/SystemCatalog.d4`, it is registered only for `Integer`, `Money`, `Short`, `Decimal`, `Byte`, `Long` and `Guid` overloads of `ToString`/`ToIString`, so no string is ever passed through it. Ruled out rather than assumed.
- **The catalog-store claim holds.** `src/engine/Store.MSSQL/SystemStoreCatalog.sql` declares its text columns `nvarchar` (41 of them) and `ntext` (3), so a catalog object, library or user name was indeed losing characters its column could have held, and is now safe - which is what the migration note and the user's guide now say.
- **The goldens are unchanged for the stated reason.** The golden pass drives the device over `TestFramework.SQLRecorder`, which prints the device's own abstract type (`String(30)` in `DML.Insert.sql`) and never reaches `MSSQLCommand`. `git status tests/goldens/` is empty.
- **The ODBC arm is parked where a reader will meet it.** `tickets/backlog/bug-odbc-money-parameter-precision.md` already carries the same-site relationship from the other side, in a section written for whoever takes either finding; nothing further was filed, and the site-claim grep finds it.
- **Source hygiene.** Every file edited in the implement commit keeps its line endings, indentation and byte-order-mark state; the new test file's deliberate byte-order mark is sensible for a file of non-ASCII literals.

### Fixed in this pass

- **A documentation sentence left stating the opposite of the new behaviour.** The `store-mssql-port` row of the plan still read "Its `varchar` parameter mapping … is still why non-ASCII catalog text is not safe on this store", in the present tense, two rows above the entry announcing that it is now safe. Corrected to say the mapping has since been fixed, by name.
- **The migration note's remedy is not available to every deployment.** It offers "declare that column `nvarchar`" without saying that a table the device created has no such column to declare: D4 cannot ask for a Unicode column, so the remedy means altering the column in SQL Server by hand. The note now says so, and the entry no longer implies that only a hand-written `varchar` schema is affected.
- **48 lines of copied test body.** `NonASCIIStringRoundTripsThroughWrites` was a near-exact clone of the neighbouring `AwkwardStringRoundTripsThroughWrites` - same table, same four cursor passes, same assertions, two different string literals. The sequence moved into `AssertStringRoundTripsThroughWrites(inserted, updated)` and both tests became one call each, keeping their own names and their own documentation of what their pair of strings is for. The case count is unchanged, which keeps `AGENTS.md`'s skip counts right.
- **A pointer at the accepted-tradeoff `NOTE:`**, so that the next reader of it learns that the first of its two remedies is closed to a table the device created, and where that is tracked.

### Filed

- **`tickets/backlog/bug-mssql-device-text-columns-lose-characters.md`** - the other half of this defect, one layer up and unexamined by the implement stage. The device's own `create table` declares a D4 string column `varchar(n)` (`SQLString.InternalNativeDomainName`) and an `SQLText` column `text` (`MSSQLText.InternalNativeDomainName`), visible in the goldens as `"Name" varchar(40)`. So a table D4 created on SQL Server still loses every character the database's code page cannot hold - the parameter now carries the characters faithfully to a column that cannot keep them - and those tables pay the measured index regression for correctness they do not get. That is the ordinary deployment shape, not an exotic one, which is why it is a ticket rather than a note. It carries a second arm measured here: reconciliation records a column's length from `sys.columns.max_length`, which is a **byte** count (measured on the LocalDB instance: `nvarchar(200)` reports 400, `nchar(10)` reports 20, `nvarchar(max)` reports -1), so a reconciled `nvarchar(200)` column becomes `Storage.Length = 400` and any `nvarchar` column wider than 2,000 characters is now described `nvarchar(max)` - no value is lost, but it is the one place the migration note's "nothing at all for a schema whose text columns are `nvarchar`" is not quite kept. Filed to `backlog/` rather than `fix/` because the fix is a deliberate change to generated DDL that a maintainer should weigh (storage doubles for ASCII text, every table created from then on changes shape, the device goldens churn) and because `test-device-live` is the ticket building the only harness that can reproduce it end to end; the ticket's `tradeoffs:` states the decline argument.

### Nothing to report

- **No tripwire was parked.** The only conditional concerns at these sites were already recorded by the implement stage - the plan-cache churn at `SQLStoreConnection.NativeToParameter`, the backstop line at `DotNetCommand.SetParameters`, and the accepted tradeoff at `GetParamTypeDescriptor` - and review found each accurate, so there was nothing to add beyond the pointer listed above. Both findings review did raise are unconditional today, so neither was demoted to a comment.
- **No test was cut and none added.** The three new cases each reproduce the defect at the lowest layer that shows it, which is a live SQL Server; the duplication between two of them was structural and is gone without losing a case.

## How to exercise it

```
dotnet build Dataphor.slnx
dotnet test tests/DAE.Server.Tests --no-build --filter "FullyQualifiedName~StoreContractTests|FullyQualifiedName~MSSQLTextParameterTest|FullyQualifiedName~MSSQLStoreConnectionStringTest|FullyQualifiedName~DeviceTranslationGoldenTests|FullyQualifiedName~CatalogStoreTest"
```

Without a server that is 51 passed and 21 skipped, each skip naming the variable to set. With one - `sqllocaldb start MSSQLLocalDB` and `DATAPHOR_TEST_MSSQL='Data Source=(localdb)\MSSQLLocalDB;Integrated Security=SSPI'` - it is **72 of 72 passed in 1 m 39 s**, which is the run review finished on. That is the implement stage's targeted set plus the ring around it: the catalog-store tests that drive a store through a running server, and both device golden fixtures. The D4 coverage scripts were deliberately not run: nothing in them reaches `MSSQLCommand` without a live SQL Server *device*, which is `test-device-live`'s, and the diff's only non-comment change is inside that class.

## What this does not show

- **One server, one collation.** Everything live was run against SQL Server 2016 SP1 Express LocalDB (13.0.4001.0) with collation `SQL_Latin1_General_CP1_CI_AS`. The collation decides which characters a `varchar` column would have lost, so it is part of the measurement; `device-sqlserver-version-matrix` owns the matrix and already carries a line telling it to record the collation with every row.
- **The device is still not driven live by anything.** The new fixture drives `MSSQLCommand` through `MSSQLConnection`, which the device and the store share, but no test writes a row to a SQL Server table *through the device* and reads it back - so neither the `ntext` half nor the filed ticket's created-column arm has an end-to-end proof. `test-device-live` owns that.
- **CI runs none of the 21 gated cases**; `DATAPHOR_TEST_MSSQL` is unset there by design, and `AGENTS.md` describes both fixtures that read it.
- **Existing damage is not repaired.** A catalog or a customer table written by an earlier build still holds the question marks stored in place of the characters it lost, and nothing converts them. Both documentation entries say so.
- **The plan-cache measurement was taken with `sp_executesql` by hand**, not through `MSSQLCommand`; the paramdef shape is the same one our client sends and the mechanism measured is the server's plan cache, but the number did not come through our own path.
