## What landed

The repository is public, and the name of the organization the codebase was originally written for had survived in six tracked files. All six are now neutral, and review found and scrubbed a seventh file carrying the same kind of detail under different names. **Read the removed tokens off the git history rather than from this ticket** — they are deliberately not written here, in a commit message, or in any tracked file either change touched.

Implemented by `ticket(implement): hygiene-scrub-inherited-identifiers`:

- **`src/engine/DAE/Language.D4/MetaData.cs`** — the last line of the comment block above the commented-out `USETAGNAMECACHE` switch now says the measurement came from a large customer catalog, matching the published note for that switch.
- **`libraries/System.Integration/Source/IntegrationNodes.cs`** — the `TODO` about cross-process row copies for streamed types keeps its whole technical point, including the following line's question about the existing marshalling call; only the attribution and project number are gone.

- **`samples/Sample.Shipping/Documents/RunTest.dfd`** — the two names in one `Form(...)` call inside a hand-run test script action are now obvious placeholders. Nothing else in that long attribute changed, and the encoding used throughout the file is untouched.

## What this does not change

- **No behaviour.** Three comments, one sample metadata tag with no live consumer, one placeholder in a sample script action, and four dead build properties across two project files that no in-repository solution builds.
- **The sample tag rename is inert either way.** A derived-form group tag only takes effect when its group name matches what derivation generates, and neither the old nor the new name can match anything here: review confirmed no library or document in the tree answers to the new name, so the rename did not accidentally make a dormant tag live.
- **No migration-notes entry.** Nothing here is visible to an application, a deployment script or a custom C# extension. The publish properties belong to two legacy project files that no in-repository solution builds and that the client port replaces; a ClickOnce publish cannot be performed from this repository at all.
- **No new test.** There is no behaviour to characterize, and the class-level guard that would be worth having cannot be written as a test over names — see the findings below.
- **`docs/reference/compiler-defines.md` was read and left unchanged** — both its affected rows already described the code accurately and still do.

## Review findings

**Checked.** The implement diff read before the handoff summary; every claim in that handoff verified against the tree rather than taken on trust. Both reworded comments compared word for word against the rows they claim to match in `docs/reference/compiler-defines.md` — both match, and the doc's own wording needed no change. The renamed sample tag checked for an accidental collision that would turn a dormant tag live — none exists. The hand-run script that the renamed `Form(...)` call lives in confirmed to be inside a block comment in the registration script, so the handoff's claim that no registration path runs it holds. The post-change search for the scrubbed name repeated over the whole tracked tree: 31 files, all false positives in the three categories the handoff names, each category spot-checked rather than assumed — the client hits are longer interface names that merely begin with the same four letters, the `.resx` hit is inside encoded bitmap data, and the rest are the vendored installer binaries that `installer-msi` deletes. Byte-order marks and line endings verified per file. Build and the test set above run.

**Found and fixed in this pass.** One finding, the sibling leak in `Frontend.Client.Windows.Executable.csproj` described above. Its root cause is not a missed file but a search scoped to a single token: the implementer looked for one organization's name, and the publish settings of a second project file carried an internal server path, two *different* outside organizations and a customer deployment name — none of which that search could see. Fixed inline as three lines in one file, since the deletion is as mechanical as the one the implement stage already made next door. After the fix, no tracked text file in the repository contains a network share path, and the only machine-local absolute paths left in build files are generic examples inside the vendored installer targets.

**Filed.** `backlog/debt-guard-internal-paths-in-tracked-files` — the class-level guard, at the boundary-invariant rung rather than as a point fix. Nobody typed those paths by hand; a publishing wizard wrote them into project files as a side effect, which can recur in any project file with nothing in the build or suite to notice. The guard has to be name-free, because writing the list of names to search for into a tracked file is precisely what the privacy rule forbids — so it asserts path *shapes*, not names, and that is also why this review added no test: a test over the actual names would itself be the leak.

**Found and corrected without a code change.** The handoff states that `Dataphoria.csproj` uses LF rather than CRLF. It does not — the index stores CRLF for that file, confirmed with `git cat-file blob` and `git ls-files --eol`; the working tree matches because this clone has the automatic conversion enabled. No harm was done, because the edit was a whole-line deletion, but the statement would have misled the next agent to touch the file, so it is corrected here rather than carried forward.

**Checked and deliberately not filed.** The retained script action in the edited `.dfd` still refers to a schema that does not exist in this sample — account, payment and check-number fields that came from the original application. The planning pass weighed deleting the action and kept it; review agrees and did not re-open it: the identifying tokens are gone, the remaining words are generic accounting vocabulary that identifies nobody, the document is the sample's own hand-run test runner which cannot run here whatever it says, and removing an action from a sample is an editorial change a privacy fix has no business making. The two engine files hosting the reworded comments are large — 3,012 and 1,683 lines, measured with `wc -l` — but this change added no code to either, and structural work on them belongs to the port tickets that rewrite them.

**Not reviewed, and why.** A general audit of the tracked tree for names belonging to outside parties, including the 601-file parked legacy tree. Both searches done here were for a specific token and a specific path shape; neither is that audit, no mechanical check can perform it, and it is outside what this ticket asked for. The follow-up ticket says so explicitly so the gap is not mistaken for coverage.

**Empty categories.** No tripwires: every concern found was either fixed outright or expressible as the name-free invariant now filed, so there was nothing conditional left to park at a code site. No accepted-tradeoff notes were encountered at any site touched, and none were added. No tests cut: the implement stage added none, and the existing corpus fixtures it leaned on are the right ones for a change with no behaviour in it.
