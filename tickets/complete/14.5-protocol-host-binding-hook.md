## What landed

`DataphorServiceHostHooks` (`src/engine/Server.Hosting/DataphorServiceHostHooks.cs`, namespace `Alphora.Dataphor.DAE.Service`, 106 lines) is the host's mirror of the client's `DataphorServiceUtility` hook surface. Both hosts in the assembly take their binding from it and both call its builder hook once their endpoints are added, so a deployment can again replace what a Dataphor server listens with from its own start-up code — the only route there has ever been to a secured Dataphor connection.

| Member | What it does |
|---|---|
| `Func<CoreWCF.Channels.Binding> BuildBindingCall` | the binding every endpoint of a host in this process is served on; default is `DataphorServiceHostBinding.Build` |
| `Action<CoreWCF.Configuration.IServiceBuilder> ServiceBuilderHook` | a last look at each host's service builder, once that host's endpoints are added; default does nothing |
| `bool HasCustomBinding` | false while `BuildBindingCall` is still the product's own; `protocol-transport-security` reads it to know whether a site has supplied a binding of its own |
| `void RevertHooksToDefault()` | puts both back, under a lock, as the client's does |
| `internal Binding BuildBinding()` | what the two hosts call: invokes the hook and refuses a null binding by naming the hook |

`DataphorServiceHostBinding` is unchanged as a declaration and is now documented as the hook's default. `CoreWcfProtocolTest.TestHostBindingMatchesTheClientBinding` still compares the two *default* declarations, not the hook. The host plumbing the hosted fixtures share moved out of `CoreWcfProtocolTest` into `tests/DAE.Server.Tests/HostedInstance.cs` as `internal sealed class HostedInstance` (that fixture's own size note had asked for it; 1009 lines down to 849). `tests/DAE.Server.Tests/HostBindingHookTest.cs` is a fixture of its own with five cases, reverting the process-wide hooks in `[TearDown]`.

Implement stage: commit `ticket(implement): protocol-host-binding-hook`. Review changed four things, below.

## Review findings

The implement diff was read before the handoff, and the three decisions the handoff asked to be weighed rather than re-derived — one internal `BuildBinding` reader instead of two call-site null checks, the default held as a method group rather than a `DefaultBuildBinding` wrapper, and `HasCustomBinding` asking about the binding alone — were each checked against `DataphorServiceUtility` and against what `protocol-transport-security` goes on to do with them. All three are right as built, and the `HasCustomBinding` reading agrees with that ticket's `CheckSecurityMode` and start-up-warning guards.

### Found and fixed in this pass

- **The specification still said this work had not been done.** `docs/modernization-plan.md`, the WS5 *CoreWCF hosting* hand-off bullet to `protocol-transport-security`, read "the hook … cannot reach the host half at all … Designing what replaces it is this work item's" — which is exactly what this ticket built. Left as it was, the next agent to work `protocol-transport-security` (in `implement/` now, with this ticket as its `prereq:`) would have read its own anchor section contradicting both reality and its own ticket body. Fixed in the shape that list already uses for a landed hand-off: a **Settled by `protocol-host-binding-hook`** clause appended to the bullet, naming the class, the three members and what is left for that work item. The implement ticket's task list named only `docs/architecture.md` and `docs/migration-notes.md`, which is how it was missed; both of those are accurate and complete.
- **The builder hook's whole purpose was asserted from metadata, never run — so it is run now.** The handoff named this as a known gap: that CoreWCF reaches service credentials through `ConfigureServiceHostBase<TService>` / `ConfigureAllServiceHostBase` was read off the CoreWCF.Primitives 1.9.1 metadata. That left a real risk, not a cosmetic one: the hook is called from inside the `Configure(application => application.UseServiceModel(…))` callback, which runs *after* the host's dependency-injection container is built, so a configuration route that had to register a service would have been too late there and the extension point could not have done the one thing it exists for. Established instead by reading the assembly (both methods are extensions on `IServiceBuilder` in `CoreWCF.Configuration.ServiceBuilderExtensions`; the delegate they take is `Action<CoreWCF.ServiceHostBase>`; `ServiceHostBase` carries `Credentials`; the delegates are held by a dependency-injection singleton, `ServiceConfigurationDelegateHolder`, and applied when each host opens) and then by running it: new case `TestTheBuilderHookReachesEachHostsServiceCredentials` installs a hook that calls `ConfigureAllServiceHostBase` and asserts the delegate reached a service host with credentials there to be set. It passes. No certificate is installed and none is needed — the suite has none, and a real secured deployment is WS11's. The `ServiceBuilderHook` remark now says the route is measured rather than inferred, names the declaring type and the namespace a hook needs, and points at the case.
- **The null-binding case no longer pays for an engine server.** The handoff flagged it as the thinnest of the four — it pins a message, and cost a full `DataphorServiceHost.Start` (engine server, catalog store, temporary instance directory) to do it. `DataphorServiceHostHooks.BuildBinding` is `internal` and the test project has no `InternalsVisibleTo`, but `ListenerServiceHost`'s constructor calls it as the first statement of a host with no engine behind it, so the case now reaches the same guard through that public type: no server start, no temporary directory, same assertion. The `using` is kept for the regression where the refusal does not happen and a host is built after all.
- **Wording.** The `ServiceBuilderHook` remark said `IServiceBuilder.ConfigureServiceHostBase<TService>` as though it were a member of that interface; a custom-host author following it would have got "no such method". It now names them as extension methods and says which namespace to import.

### Checked and sound

- **The extraction is behaviour-free.** Every line removed from `CoreWcfProtocolTest.cs` was accounted for mechanically: normalising whitespace and the three accessibility keywords, the removed set and `HostedInstance.cs` differ only by the new file's licence header, namespace, `using` lines and class remark, the two size `NOTE:`s, and the call sites that came back prefixed with `HostedInstance.`. No moved body line changed. The claimed line counts are accurate (`CoreWcfProtocolTest.cs` 849, still the largest file in the project; next is `StoreContractTests.cs` at 688).
- **Both hosts' failure paths.** `DataphorServiceHost.BuildHost` and `_host.Start()` are both inside the inner `try` whose outer `catch` calls `Stop()` and rethrows, so a throwing or null-returning hook on the instance's host stops the engine server rather than leaving it up. `ListenerServiceHost.BuildHost` is before its `try` and builds the binding eagerly as its first statement, so a binding-hook failure there propagates instead of being recorded as a taken port; nothing is leaked when it throws, because no `IHost` has been built yet. `Stop()` tolerates a half-built state and a second call, which is what the test helper's `finally` relies on.
- **Static-initialiser order**, which the handoff called load-bearing: the two defaults are declared before the public fields that start out holding them, with a comment saying why. Reordering them would leave both hooks null; nothing else in the file depends on order.
- **`HasCustomBinding` has no consumer in the repository yet.** Deliberate, and not dead code for long: `protocol-transport-security` (`tickets/implement/14.55-protocol-transport-security.md`) reads it in two places and mirrors it on the client half. Not a finding.
- **Documentation.** `docs/architecture.md`'s hosting paragraph and the amended `docs/migration-notes.md` entry both read accurately against the code, and the migration entry carries what a custom host actually has to change (the assembly, the namespace, the `CoreWCF.Channels.Binding`-rather-than-`System.ServiceModel.Channels.Binding` type, and installing hooks before starting a host). One amended entry is right rather than a second one: a second would have to contradict the first, which recorded the loss. `ListenerServiceHost`'s still-unread `requireSecureConnection` parameter, and `DataphorServiceHost` never reading `RequireSecureConnection`, are both `protocol-transport-security`'s — that ticket drops the parameter — and were not re-filed here.

### Weighed and left alone

- **A hook field set to `null`** gives a `NullReferenceException` rather than a named failure, for both hooks. Left as it is, deliberately: these are public mutable static fields shaped on the client's, which have had exactly this contract since 3.x, and the point of the class is that the two halves read as one extension point rather than as two inventions. The near miss a site would actually make — a hook that returns nothing — is the one that is named. Not worth a `NOTE:` at the site either; the class remark already frames both fields as "install your own".
- **`_syncHandle` is not `readonly`**, and `RevertHooksToDefault`'s lock guards nothing that is read under it. Both mirror `DataphorServiceUtility`, where the same lock also guards the memoized client binding, and the method's remark already says it gives no synchronisation guarantee rather than implying one. The handoff raised this itself; no change.

### Tripwires

- The implementer's `NOTE:` in `src/engine/Server.Hosting/ListenerServiceHost.cs`, at the `ServiceBuilderHook` call, stands as written and was re-checked rather than taken on trust. That call necessarily runs while the host is *starting*, which on this class is inside the `try` that tolerates a failed bind, so a builder hook that throws there reads as a listener that did not start. It is genuinely conditional rather than a latent defect: the instance's host is built and started first and shares the hook, so the realistic failure — a hook whose certificate lookup throws — fails the whole server start before the listener is reached. It would bite only a hook that throws *selectively* for the listener's host. The note's remedy (narrow that catch to the bind failure it exists for, rather than moving the call) is the right one.
- No new tripwire was added, and that is not for want of looking: the hooks are read once per host at start-up, nothing is memoized by design, and no serving path pays a per-call cost for any of this.
