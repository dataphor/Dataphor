## What landed

`libraries/PGSQLConnection` is an SDK project on the NuGet `Npgsql` package, in `Dataphor.slnx` and in the layout's Library list; the checked-in `external/Npgsql.dll` (2.0.4) and `external/Mono.Security.dll` (2.0) are deleted, leaving `external/` with only the three Windows UI binaries. No line of `Register.cs` changed and no D4 class name moved: the library still registers `PostgreSQLConnection.PostgreSQLConnection`. `PostgreSQLConnection.cs` and `PostgreSQLCommand.cs` compile against the current driver with no change to a statement - only comments were added to them.

The implement stage is commit `ticket(implement): device-pgsql-connection-port`.

`Directory.Packages.props` pins `Npgsql` **10.0.4** rather than the current 11.0.0, and that is the one substantive decision in the ticket. 11.0.0 also targets `net10.0` and compiles, but its dependency closure is a framework generation ahead of the host: `Microsoft.Extensions.DependencyInjection.Abstractions` and `Microsoft.Extensions.Logging.Abstractions` at 11.0.0, and through the latter `System.Diagnostics.DiagnosticSource` at 11.0.0, against the 10.0.x that `Microsoft.AspNetCore.App` and `Microsoft.NETCore.App` provide. A library folder is flat and has no `.deps.json`, so the default load context binds those simple names from the framework and the folder's own higher-versioned copies are unreachable - the driver throws `FileLoadException` while building its first data source, before it connects to anything. The constraint belongs to the layout rather than to this library, so it is a `NOTE:` in `tools/layout/Layout.csproj` beside the existing flat-folder notes, and a third measured fact in the plan's runtime-layout paragraph.

The assembled library folder holds exactly four files in both configurations - `Alphora.Dataphor.DAE.Connection.PGSQL.dll`, its `.pdb`, `Npgsql.dll` and `PGSQLConnection.d4l` - and nothing named `Npgsql` reaches `bin/`. `PGSQLConnection.d4l` drops `Mono.Security.dll` (the driver has carried its own TLS since 3.x) and keeps `Npgsql.dll` with `isassembly="False"`, the shape `System.Internet.d4l` already uses for `Newtonsoft.Json.dll`: the server runs `Assembly.LoadFrom` over the entry, so the driver loads while the library registers, and only the catalog-assembly registration is skipped.

One test guards it: `LibraryLoadingTest.PGSQLConnectionLibraryRegistersWithoutAPostgreSQLServer`, a fourth arm beside the `Connection` and `ODBCConnection` arms, asserting that registering the library on an in-process server with no PostgreSQL server in reach succeeds **and** that the driver assembly is loaded afterwards. This is a deliberate deviation from the implement ticket, which said "No new test"; the project rules' characterization-test rule for a re-hosted subsystem wins, and the review kept the test and strengthened it.

## Review findings

The implement diff was read before the handoff. Everything the handoff claimed to have measured was re-measured or re-derived; one of its two recorded defects turned out not to exist, which is the finding that mattered. Driver behaviour was checked three ways: a throwaway console project on the pinned package (in the session scratchpad, now deleted), the package's own metadata and dependency graph, and a scan of the driver assembly's type and member names.

### Major - a recorded defect that is not real, fixed in four places

**The connection string the PostgreSQL device builds is accepted by the current driver.** The handoff, the plan's WS7 row and a `NOTE:` in `PostgreSQLConnection.cs` all said the opposite: that the device's `SearchPath` keyword is spelled `Search Path` by the current driver, which throws on an unrecognised keyword, so a device connection would fail before reaching a server. Measured on the pinned driver with the exact six-keyword string `PostgreSQLDeviceSession.InternalCreateConnection` produces from the device defaults (`Server`, `Port`, `Database`, `SearchPath`, `User Id`, `Password`), with the search path both empty and set: every keyword is accepted and `SearchPath` lands on the driver's search-path property. The driver's canonical spelling does carry a space, but its keyword lookup ignores the spacing.

This mattered beyond the comment. `tickets/implement/22-device-pgsql-device-golden.md` carried the claim as a known defect, with a TODO item ordering a change to `PostgreSQLConnectionStringBuilder`'s keyword legend - and those tag names are a compatibility surface, since they are what a device's D4 definition writes. That ticket's paragraph and TODO item now record the measurement and say to leave the legend alone. The claim came from the plan stage rather than from the implement stage, so the correction is filed where it would have done damage rather than as a ticket against anyone.

The half of the claim that is true is kept: an unrecognised keyword now throws where the 2009 driver ignored one, and `SQLDevice.GetConnectionParameters` merges a deployment's `ConnectionParameters` tag into the string verbatim. That needs a live connection to matter, so the `NOTE:` and the golden ticket both hand it to `device-pgsql-port`.

### Minor - fixed in this pass

- **The `Time` defect was recorded for one direction only.** The driver carries converters for a PostgreSQL `time` to `TimeOnly` and `TimeSpan` and to nothing else (confirmed from the assembly's converter type names: `TimeOnlyTimeConverter`, `TimeSpanTimeConverter`, and no `DateTime` equivalent), so the device's `Time` scalar type is wrong in **both** directions, not just on the write: `PostgreSQLTime.FromScalar` hands a `DateTime` over to be bound, and `PostgreSQLTime.ToScalar` casts what comes back to `DateTime`. The `NOTE:` at the `SQLTimeType` arm of `PrepareParameters` and the plan's WS7 row now say both. Still not fixed here - what to send and what to read is the device scalar type's decision, and `PGSQLDevice` is not in this diff.
- **The pin rationale named the wrong dependencies.** Both the `Directory.Packages.props` comment and the `Layout.csproj` `NOTE:` said Npgsql 11.0.0 depends on `Microsoft.Extensions.Logging.Abstractions` and `System.Diagnostics.DiagnosticSource` 11.0.0. Its `net10.0` group actually depends on `Microsoft.Extensions.DependencyInjection.Abstractions` and `Microsoft.Extensions.Logging.Abstractions`; `System.Diagnostics.DiagnosticSource` arrives transitively through the second. The three-assembly count the handoff observed in the folder is right, but the list was not - and the note's own advice is to check a new package's versions, so it now says the transitive closure is what to check, not the package's own dependency list.
- **The migration note's in-place upgrade instruction would have broken registration.** It told an administrator upgrading a 3.1 installation to delete `Npgsql.dll` and `Mono.Security.dll` from the library folder. A server loads every file *its own* copy of the descriptor lists, and `LibraryUtility.RegisterLibraryFiles` has no existence check on that path - `FileUtility.IsAssembly` catches `FileLoadException` and `BadImageFormatException` but not `FileNotFoundException` - so deleting `Mono.Security.dll` while the 3.1 descriptor still names it stops the library registering at all. The entry now says to replace the whole library folder, descriptor included.
- **The registration test did not verify what its own documentation claimed.** Its remarks say the server loads the driver while registering the library; `Assert.DoesNotThrow` on the registration script would pass just as well with the `Npgsql.dll` entry missing from the `.d4l`. One assertion was added: the driver assembly is in the process's loaded set afterwards. Nothing else in the test host references the driver, so the check is meaningful. It passes, which is the first positive proof in the suite that the driver really loads out of a flat library folder.

### Checked and sound

- **The `DateTime` `Kind` analysis holds, and it is the claim the plan called the most likely source of a defect.** `NpgsqlDbType.Timestamp` is `timestamp without time zone`, which refuses only `DateTimeKind.Utc`. `DateTimeConveyor` rebuilds every value from its ticks, giving `Unspecified`; the nilary date nodes give `Local` through `DateTime.Today`, which `timestamp` accepts. Re-derived independently, including the negative that carries it: a search for `UtcNow`, `ToUniversalTime` and `DateTimeKind.Utc` across `src/` and `libraries/` returns nothing at all. A value from a custom C# extension could still be `Utc`; nothing in the tree produces one.
- **The `Size` analysis holds, and for a tighter reason than the handoff gave.** `PrepareParameters` sets `Size` on exactly one arm, the `Varchar` one, from `SQLStringType.Length`; the `Bytea` and `Text` arms leave it 0, where the driver's truncation does not apply. So the only parameter that can be truncated is a string, which is precisely the case `DotNetCommand.SetParameters` backstops - its growth is guarded by `parameter.Value is string`, which would not have covered a byte array.
- **`Precision` and `Scale` are present, not obsolete, and `byte` on both sides.** They round-trip on a parameter and decide nothing about what is sent.
- **Parameter names still match, which nothing in the handoff had checked.** The command sets `ParameterName` to `":" + name` while `SQLCommand` writes `:name` into the statement text. If the current driver had stopped stripping that prefix, every parameterized statement this library issues would fail. It has not: the driver carries a `TrimmedName` member on its parameter type, and a parameter added as `:p` is found by both `p` and `:p` in the collection. Measured.
- **The flat-folder constraint behind the pin is real and the mechanism is as described.** `Microsoft.Extensions.Logging.Abstractions` appears in neither `bin/` nor either host's `.deps.json`, and both hosts declare `Microsoft.NETCore.App` and `Microsoft.AspNetCore.App` at 10.0.0 - so the framework's copy is what the default load context holds, exactly as the note says. The 11.0.0 failure itself was not re-measured; the probe that produced it is gone, and the three-assembly difference in the restored package graph is consistent with it.
- **The project conversion follows the established pattern.** `DAE.Connection.PGSQL.csproj` is `DAE.Connection.ODBC.csproj` with a different package, including the constants block (`TRACE` in both configurations here, because that is what the legacy Release set carried for this project) and the explicit `Compile` list. The trimmed `AssemblyInfo.cs` keeps exactly what `Directory.Build.props` documents as per-project: title, description, `DAERegister`, `ComVisible`, `Guid`.
- **The `AssemblyDescription` correction is right to keep.** It said "ADO.NET Oracle Provider" - a copy/paste from the Oracle connection library - and now says PostgreSQL, matching the shape of ODBC's. Nothing reads an assembly description, so no migration note.
- **The residual claims in the handoff all check out.** A search over `legacy/` finds neither deleted binary; `Setup/Files.wxs` names both but harvests them from the 3.1 `Deploy` tree, not from `external/`; the untracked 2009 `Source/obj` leftovers are git-ignored and `ODBCConnection` and `PGSQLDevice` have the same, so leaving them is the precedent rather than an oversight; `areas.json` puts the new assembly name in the flat `assemblies.reported` list beside the ODBC one.

### Tripwires - all three left where the implement stage put them, none filed as a ticket

- `tools/layout/Layout.csproj`: a library folder cannot carry a different version of an assembly one of the host's shared frameworks provides. Text corrected (above) and kept as a `NOTE:`. **Deliberately not a ticket.** The obvious ticket would be a build-time check in the layout comparing a library folder's assemblies against the framework's - a real class-level guard - but the concern is conditional in exactly the sense the ticket rules reserve for a tripwire: nothing is wrong today, and it becomes work only if some future package's closure outruns the frameworks. The cheaper half-measure the handoff floated, a probe operator that constructs an `NpgsqlConnection` without connecting, was also declined: it would put the driver into a test library's dependencies to guard one deliberate act (a version bump) that `device-pgsql-port` will catch live.
- `PostgreSQLConnection.InternalWrapException`: flattening every driver exception loses `PostgresException.SqlState`, the only thing that separates a constraint violation from a connection failure. Left as 3.1 had it, as the implement ticket directed.
- `PostgreSQLCommand.PrepareParameters`: the `Size` truncation is harmless only because of `DotNetCommand.SetParameters`'s growth. Kept, with the tighter reasoning above folded in.

### Considered and declined

- **Collapsing the three `EnsureLibraryRegistered` arms of `LibraryLoadingTest` into one parameterized test.** They are near-identical bodies, but each carries its own name and its own paragraph of remarks saying which library and which risk it stands for, and the shape was set by `device-connection-cleanup`. Rewriting it would be churn in a file this ticket only extends.
- **A new test for the project conversion, the `.d4l` change or the package pin.** Wiring and a package version are what the build and the layout's `.d4l` check already enforce.

### Not checked

- **Nothing has executed a statement through this library**, and no review pass could change that without a PostgreSQL server. Every behavioural claim above comes from reading the driver, scanning its assembly, or exercising it in isolation - never from a database. `device-pgsql-device-golden` pins translation without a server and `device-pgsql-port` is the live pass; both will meet the `Time` defect, and the live one will meet the unrecognised-extra-keyword change.
- **The full test suite.** Per the project rules it is CI's job after each stage's push.
