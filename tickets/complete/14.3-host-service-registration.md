## What landed

Registering, removing and inspecting the Windows service for a Dataphor instance no longer goes through the .NET Framework installer classes (`System.Configuration.Install`, `TransactedInstaller`, `ServiceProcessInstaller`), which do not exist on .NET 10, and no longer lives inside the service executable. `ServiceUtility` talks to the Windows service control manager directly through `advapi32`, and it, the `ServiceStatus` enum and the service's string table now sit in a new assembly, `Alphora.Dataphor.DAE.Host` (`src/hosts/Host/DAE.Host.csproj`), which the service executable and the tray configuration utility both reference and which references nothing else in the repository.

What a registration carries is what 3.1 registered — service name and display name `Alphora Dataphor (<instance>)`, the same description, one service per process, automatic start, the LocalSystem account, and the command line `"<folder>\DAEService.exe" -name "<instance>"` — so replacing the files of an existing installation in place needs no re-registration. Failures reach the caller as a `System.ComponentModel.Win32Exception` carrying the service control manager's error code; no new Dataphor error codes were added. The five members that only described the registry layout the class no longer touches are gone, and reading a service's start mode no longer needs administrative rights, because it asks the service control manager instead of opening `HKLM\System\CurrentControlSet\Services\<name>` for write in order to read it.

The implement-stage commit `ticket(implement): host-service-registration` has the detail: the new project file and its one package (`System.ServiceProcess.ServiceController`), the deletions (`ServiceInstaller.cs`, two designer `.resx` files and the stray `ServerServices.cs`, which was in no compile list and was not valid C#), the caller changes, and the five documentation files it updated. Three deliberate deviations from the implement ticket are recorded there and all three were checked here: the instance-name default moved from the deleted installer class to the two `Main` call sites in `Service.cs`; the tray configuration utility and the new assembly were added to the .NET spike's project list; and `GetServiceStatus`/`GetServiceAutoStart` now dispose the `ServiceController` they open.

## Review findings

**What was read.** The whole implement diff before the handoff summary, then the current `src/hosts/Host/ServiceUtility.cs` line by line against the deleted `ServiceUtility.cs` and `ServiceInstaller.cs` and against the `winsvc.h` constants and the `advapi32` signatures; every caller of `ServiceUtility`, `ServiceStatus` and the five removed members across the tree (nothing left behind); `Service.cs` in full, including whether deleting `Service.resx` could matter (it has no `InitializeComponent`, so no); the tray configuration utility's install, uninstall, start, stop and auto-start paths; the new test; every project file, solution and layout change; and all five documentation files the change touched, plus the three it should have (below).

**Verified by running.** `dotnet build Dataphor.slnx` 0 errors / 143 warnings and `-c Release` 0 errors; `DAE.Host` built on its own, 0 warnings. The suite in the three parts `AGENTS.md` prescribes: 13 + 408 pass (part 1), 67 pass / 11 skipped (part 2), 48 pass / 14 skipped (part 3), 0 failures — the three extra over the implement run are this review's tests. The embedded string table resolves by the name `Strings.BaseName` spells (now a test, not a one-off inspection), and all seven `advapi32` declarations resolve (also now a test). The .NET spike was not re-run: this review's own diff is one test file and three documents, touches no product source and no project file, and what the spike measures is compilation of product source.

**Correctness.** No defect found in the rewritten code. Each access mask, service-type, start-type and configuration constant matches `winsvc.h`; each signature matches its `advapi32` function in parameter order, type and string marshalling; the last-error code is captured into a local immediately after every call and before any handle is closed; every handle opened is closed on every path, including the failure paths; `SERVICE_NO_CHANGE` and null arguments confine `ChangeServiceConfig` to the start type; and the two read members' catch-and-return-a-default reproduces what a missing registry key used to give the tray utility's timer. The behaviour the old code had and the new code keeps was checked member by member: manual start writes `SERVICE_DEMAND_START` (3) as the old registry write did, `SetServiceAutoStart` on an unregistered instance still silently does nothing, `GetServiceStatus` still answers `Unavailable` for every status that is not running or stopped, and the registered command line is the shape the old `ProjectInstaller` rewrote `ImagePath` into.

**Three questions raised and settled without a change.**

- *Does the default registration name the right executable?* `Install(instanceName)` registers `DAEService.exe` from `AppContext.BaseDirectory`, and the plan's WS5 target is one host program under two names. `host-generic-host`'s implement ticket settles it: `DAEService.exe` stays the registered binary and both executables run the same program. No tripwire needed, and the two-argument `Install` overload already covers a caller that must register a different binary.
- *Did 3.1's installer register anything the new code does not?* One thing: `ServiceInstaller` carries an `EventLogInstaller` child, so installing also created an Application-log event source named after the *service*. Nothing in Dataphor ever wrote to it — the service and the server both log under `Dataphor Server` — so nothing is lost. That name is duplicated in two assemblies, which this review pinned with a test rather than a comment.
- *`DAEService.exe -u` while the service is running.* The service control manager marks the registration for deletion and it disappears when the service stops; the tray utility refuses to uninstall a running service, so the only route is the switch. Whether the old installer stopped the service first cannot be established without the .NET Framework source, and the difference, if any, is one message to an operator who typed `-u` on a running service. Left alone; the elevated manual check that `host-generic-host` owns will show it.

**Three tests added** (the implementer's one kept as it was; nothing cut). Each pins a contract that nothing else checks and that only shows up at run time, which matters more than usual because no code path that registers a service has ever been run:

| Test | What it pins |
|---|---|
| `EveryServiceControlManagerImportResolves` | Reflects over `ServiceUtility`'s seven private `advapi32` declarations and `Marshal.Prelink`s each: a misspelled entry point or a wrong character set fails here instead of at the elevated manual check. Measured: it finds all seven, and `Marshal.Prelink` throws `EntryPointNotFoundException` on a deliberately bad declaration (checked in a scratch project outside the repository) |
| `StringTableIsEmbeddedUnderTheNameItIsLookedUpBy` | `DAE.Host.csproj` overrides `RootNamespace` so that `Strings.resx` keeps the manifest name `Strings.BaseName` spells. Nothing in the build checks that the two agree; a mismatch compiles and fails at the first lookup, which is the service's own console output |
| `EventLogSourceMatchesTheEngineConstantItCopies` | `ServiceUtility.EventLogSource` is a deliberate copy of `Engine.ServerSourceName`, kept so that this assembly needs no reference to the engine. Drift would split a deployment's event-log entries between two sources with neither assembly noticing |

## Still true after the review

- **No code path that registers a service has been run.** `Install`, `Uninstall` and `SetServiceAutoStart` change machine state and need administrative rights, and there is no runnable .NET 10 `DAEService.exe` until `host-generic-host`, which owns the elevated manual check (install, confirm name, description, start type, account and `ImagePath`, start, stop, set auto-start both ways, uninstall, and an instance name containing a space). The three tests added here narrow what that check is the first to exercise — entry points, the resource name and the source-name copy are now covered — but they do not replace it. Read this code as unrun code.
- **The unelevated `GetServiceAutoStart` improvement is argued from the two APIs' access requirements, not demonstrated.** Showing it needs a registered service and a non-elevated process, which is the same manual check.
- **`Setup/Files.wxs` still installs `DAEService.InstallLog`**, recorded on the WS9 umbrella as above.
- `tools/net-spike/EngineCheck`'s `ExpectedResources` dictionary still does not cover `DAE.Host`, and deliberately will not: the guard that matters is now a test in the suite rather than an entry in a throwaway harness.
