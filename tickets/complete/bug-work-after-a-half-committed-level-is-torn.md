## What landed

**The rule.** A transaction level whose commit has already failed after it began asking participants to commit accepts no new work on any participant - only a rollback. One predicate, `ServerProcess.CheckNotHalfCommitted` (`CommitBegun` set on the current transaction and `InRollback` not set), raising the existing error 106213, asked at five seams:

- `Schema.DeviceSession.Execute`, `InsertRow`, `UpdateRow`, `DeleteRow` (`src/engine/DAE/Schema/Device.cs`) - each before the method's own `try`, so the refusal never goes through `WrapException` and so never sets `StopError`.
- `ServerCatalogDeviceSession.AcquireCatalogStoreConnection` when `isUpdatable` is true - the funnel for every catalog-store write, and so for all of DDL.
- `ServerProcess.RemoteConnect` - the funnel for every use of a server link, compile-time path included.

**The deferred-handler arm.** `ServerTransaction.InvokeDeferredHandlers` now reads the nested transaction's `CommitBegun` before rolling it back and sets it on the enclosing level if it was set, so a commit retried after a partial commit inside the deferred-handler transaction is refused with 106213 instead of running every handler a second time. Its catch also tests the process's depth against the depth before its own begin rather than `InTransaction`, so a nested commit that threw after it had already ended its level does not get the enclosing transaction rolled back in its place.

**Two deviations from the fix ticket's design, both kept.** `CommitBegun` is now set in `InternalCommitTransaction`'s catch rather than before its participant loops, so that the commit's own work on the participants is not refused by the new predicate; and the deferred-handler catch tests depth rather than `InTransaction`. Both are reasoned at the code sites and in the plan's K41 row; review measured the first (below) and accepted the second.

Tests: eight cases in `tests/DAE.Server.Tests/PartialCommitTest.cs`, five of them new in this ticket, on the `FailingCommitDevice` seam K40 introduced. The implement stage is commit `ticket(implement): bug-work-after-a-half-committed-level-is-torn`; the fix-stage investigation is `ticket(fix): bug-work-after-a-half-committed-level-is-torn`.

Docs: a new row in `docs/migration-notes.md`, K41 in `docs/modernization-plan.md` with K40's open paragraph replaced by a pointer to it, and - added in review - the invariant itself in `docs/architecture.md`.

## Review findings

The implement diff was read before the handoff summary. Validation: `dotnet build Dataphor.slnx` clean (0 errors, 143 warnings on a full rebuild, unchanged), then the three suite parts each in the foreground - part 1 **692 passed, 0 failed**, 33 skipped, 8 m; part 2 **67 passed, 0 failed**, 11 skipped, 3 m 4 s; part 3 **50 passed, 0 failed**, 12 skipped, 3 m 3 s. No pre-existing failures surfaced, so `tickets/.pre-existing-error.md` was not written.

### Checked and sound

- **Deviation 1 is load-bearing, and now measured rather than argued.** The handoff asked a reviewer to look hardest here. Putting `transaction.CommitBegun = true` back before the participant loops (one added line, everything else left in place), rebuilding and running `--filter "Name~Atomicity|Name~References"` failed **9 of the 23 cases**, `Transaction.Atomicity.SetOne` among them, where all 23 pass with the set in the catch. The mechanism is as the handoff describes and a little broader than it says: `ServerTransactions.EndTransaction(true)` calls `ServerTableVar.DeleteCheckTableChecks`, which opens a cursor and deletes rows on a device, and a reference is a deferred constraint unless its `DAE.IsDeferred` tag says otherwise - so with implicit transactions on, which is the default, that is most commits an application makes, not an exotic case. The probe line was removed and the tree rebuilt before the suite run; the measurement is recorded in K41.
- **No other reader of `CommitBegun` wanted it set during the commit's own participant phase**, which was the specific question the handoff raised. `grep` over `src/` finds exactly four sites: the set, `InternalBeginTransaction`, `InternalPrepareTransaction` and `CheckNotHalfCommitted`. The first two are not re-entered from inside a commit's participant phase; the third is, by `DeleteCheckTableChecks`, which is what the deviation exists for. The `InCommit` flag the handoff offered as the alternative is not needed.
- **The device arm covers every live route.** `Program.DeviceExecute` reaches `Execute`; `TableNodes` insert, update and delete reach `InsertRow`, `UpdateRow` and `DeleteRow`; and the D4 cursor writes - `CursorInsertNode`, `CursorUpdateNode`, `CursorDeleteNode`, which looked like a possible sixth seam - go through `Table.Insert`/`Update`/`Delete` to `Node.Insert` and so to the same four. All four are non-virtual `public` methods over `protected virtual Internal*` ones, so no device subclass can bypass the check. The device's own rollback replay calls the `Internal*` methods directly and so is exempt by construction, not by the `InRollback` flag.
- **The exemption spans are right, including the one the implementer only noted.** `InternalRollbackTransaction` holds `InRollback` over its participant loops but drops it before its `finally { EndTransaction(false) }`. Read both: `EndTransaction(false)` only calls `RemoveAt` (the `DeleteCheckTableChecks` call is on the `success` branch alone), and the disposal it triggers reaches only `UnprepareDeferredHandlers`, which deallocates native rows. So the window the `NOTE:` at `ServerTransaction.Dispose` describes is real, currently harmless, and parked in the right place.
- **The refusal cannot mask the error that caused it.** After `InvokeDeferredHandlers` sets the record on the enclosing level and rethrows, the only code that runs before the exception leaves the engine is `InternalPrepareTransaction`'s `finally { program.Stop(null); }` and `CommitTransaction`'s `finally { EndCall(); }`. `Program.Stop` was read: it pops stack windows and process locals and touches no participant.
- **A refused statement rolls nothing back behind the client's back.** `BeginTransactionalCall` begins an implicit transaction only at depth 0, so on a half-committed level it adds none, `nestingLevel` equals the current depth and `EndTransactionalCall`'s `while (_transactions.Count > nestingLevel)` loop does not run. The tests' depth assertions say the same thing from outside.
- **Placing the check outside each method's `try` does what the comment claims.** `StopError` is set in exactly two places, both inside `Schema.DeviceSession.WrapException`, and only when the device's own `IsConnectionFailure`/`IsTransactionFailure` says so. A refusal that went through `WrapException` could reach them; one raised before the `try` cannot.
- **Refusing before `_acquireCount++` leaks no release.** All 83 `AcquireCatalogStoreConnection` call sites in the file were checked: none is the first statement of a `try` whose `finally` releases, so a throw from the acquire never leaves a release unpaired.
- **"The half-committed level is always the innermost one" holds.** A nested begin on such a level is refused, and `InvokeDeferredHandlers` sets the record on the enclosing level only after the nested level has been rolled back and popped - so `CheckNotHalfCommitted` asking about the *current* transaction is asking about the right one.
- **DDL is guarded at its earliest point.** `DDLNode.InternalBeforeExecute` calls `CatalogDeviceSession.BeginStoreWriteTransaction`, which on a full server calls `AcquireCatalogStoreConnection(true)` and so is refused before the statement does anything; in engine mode that hook is a no-op and the refusal lands on the first real store write instead. Both paths end in the same seam.
- **The remote arm's call graph is as the handoff states.** `ServerProcess.RemoteConnect`'s only callers are `Program.RemoteConnect` and `Plan.RemoteConnect`, covering the four live sites (`ExecuteOn`, `EvaluateOn`, and `TableNodes`' compile-time and runtime server-link paths). The apparent third caller in `SystemTableValues.cs` is inside `#if OnExpression`, and `OnExpression` is defined in no project file or props file in the tree. I agree with the implementer that standing a second Dataphor server up to pin a one-line check at that funnel would cost more than it pins.
- **The tests earn their places.** None restates the implementation or asserts against a repository-owned mock; the one test double is a device, which is an extension point the engine publishes, and K40 established it. `TestTheD4RollbackIdiomsStillWorkAfterAFailedCommit` cannot fail against the shipped design, but it is the case that stops a later "simplify this to one check in `BeginTransactionalCall`", which is the design this ticket rejected - it is worth its run time for that alone. No test was cut and none added: the one contract that looked uncovered, Deviation 1, turned out to be guarded by nine existing coverage-script cases, measured above.

### Found and fixed in this pass (minor)

- **`docs/architecture.md` never stated the invariant.** The change makes a rule that both device authors and client authors now meet - a transaction level spans every participant, the commit asks them one at a time, a failure part-way leaves the level half-committed, and such a level takes no further work - and it was written down only at the code site and in a changelog row. Added one paragraph to "Sessions, processes, plans", where the process's transaction stack is introduced. Nothing already in that file was contradicted by the change; this was a gap, not a staleness.
- **K41's central rationale was asserted where this project's rules ask for a measurement.** The sentence claiming the pre-deviation placement "would have refused every commit that had deferred checks" is now backed by the 9-of-23 figure above, with the command and the date, in K41 itself.
- **`CheckNotHalfCommitted`'s remarks did not say why `DeviceConnect` is not a seam** when `RemoteConnect` is - the first question the asymmetry invites, and the next reader's likely "oversight" ticket. Added a paragraph: a device session connected on a half-committed level is caught up to this process's depth, so the rollback ends the half-committed level on it like any other participant and the work after the connect is refused at the four methods below it; a connection to another Dataphor server is asked at the connect instead because its catch-up begins transactions on a *far* server this process may not be able to clean up if the link then fails.
- **A stray double comma** in K40's row of `docs/modernization-plan.md`, on a line this ticket had already edited.

### Tripwire parked (the analysis is at the site)

- `ServerTransaction.InvokeDeferredHandlers` - the depth test correctly declines to roll the enclosing level back when the nested commit threw *after* ending its own level, but in that same window the nested transaction object is gone, so `CommitBegun` cannot be read off it: the enclosing level stays retryable and a retried commit re-runs the handlers over work the nested commit had already committed on every participant. `NOTE:` at the site, with the shape of the real fix (carry the record out of the nested commit rather than reading it off an object that may be gone). It needs `ServerTransaction.Dispose` to throw, which nothing on that path does today - the existing `NOTE:` there says why - so it is conditional, not a latent defect.

### Considered and left alone

- **The non-updatable catalog-store acquire is still allowed,** which the handoff flagged as a slight inconsistency with "reads are refused too" and asked for a second opinion on. Keep it, and nothing needs writing down: every read a *client* can issue goes through a plan and so through `Schema.DeviceSession.Execute`, which refuses it - `Count(System.Operators)` included. The acquires that stay open are the catalog session's own internal reads, which are not work a session issued, and guarding them would refuse the compiler's own catalog reads during the rollback's plan work, which is the one thing the session must still be able to do. The asymmetry is internal only, and the predicate's remarks already frame refusing reads as a predictability choice rather than a guarantee about every internal lookup.
- **The surviving tear in `TestWorkAfterAFailedCommitSwallowedInsideOneStatementIsRefused`** - row 2 on the working device and not on the failing one - is the half-commit's own damage, which K40 records as unfixable without a two-phase recovery record. Asserting it would pin behaviour this project intends to change, and the test's comment already explains it. Left as the implementer wrote it.
- **The remote arm's missing test** and **`CheckNotHalfCommitted` being `public`** (`ServerCatalogDeviceSession` is in another assembly and the repository has no `InternalsVisibleTo` convention): both judged correctly by the implementer, for the reasons given there; nothing added.

### Majors

None. Nothing found in this pass met the filing bar, and no ticket was filed. The two deviations from the fix ticket's design were the likeliest candidates and both survived scrutiny - the first on a measurement, the second as a strictly narrower replacement for what it replaced.
