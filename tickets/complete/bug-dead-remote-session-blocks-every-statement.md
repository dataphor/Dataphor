## What landed

The rule: **a connection to another Dataphor server that is a participant in no transaction this process still has open may be let go at any time** - nothing has been done on it that this process's transaction protocol still owes an answer for. A connection that *is* a participant may not, because forgetting it would let the local commit believe the remote half committed. The reclaim sits at the transaction begin, which is the one call a process makes on every connection it holds whether the statement uses that connection or not, and the one point at which the far server has provably done nothing yet at the level being begun. Nothing was added to D4: no operator, no setting.

Five source files, in the order the implementation was written:

- **`src/engine/DAE/Server/ServerException.cs` and `.resx`** - the new error code `RemoteSessionTransactionFailed = 106212`, *A transaction operation failed on the connection to instance "{1}" on host "{2}" through server link "{0}".* Purely additive; no existing code's number or text changed.
- **`src/engine/DAE/Server/RemoteSession.cs`** - `TransactionCount` is a local count over a private field instead of a question asked of the other server, and is no longer abstract. The four public transaction methods are the base class's own and wrap four new `protected abstract` `Internal...` methods: the begin increments only on success, the commit and the rollback decrement in a `finally`, the prepare does not change the count, and all four turn a failure out of the `Internal...` method into error 106212 with the original as the inner exception. The invariant - every remote session in a process's `RemoteSessions` list has begun exactly as many transaction levels as the process has open - is recorded in the remarks on `TransactionCount`.
- **`src/engine/Server/Server/RemoteSessionImplementation.cs`** - lost its `TransactionCount` override; its four transaction methods are now the `Internal...` overrides.
- **`src/engine/DAE/Server/ServerProcess.cs`** - `InternalBeginTransaction` iterates a snapshot of `RemoteSessions` (the release removes entries) and, per session: records a success; releases and carries on when a failure finds `TransactionCount == 0`; rethrows when it finds a participant, leaving the existing all-or-nothing unwind to do the rest. The remote half of that unwind is now a `List<RemoteSession>` of the sessions that began rather than an index count. The release itself is the new `DiscardRemoteSession`: one `Warning` log entry naming the link, the instance, the host and the cause, then `RemoteSessions.Disown(session)` and `session.Dispose()` inside a guarded `try`. `InternalPrepareTransaction` asserts the invariant before preparing each session - prepare is the first of the three ending operations and a commit reaches it, so one check covers both.

Two `NOTE:`s, both "do not change this": why the reclaim is at the begin rather than at `Execute`, and that remote sessions committing before any device session is load-bearing, so the two loops in `InternalCommitTransaction` must not be reordered.

The failure is asserted by **code, not message**: a helper walks the exception and its `InnerException` chain for the first `DataphorException` and compares its `Code`. The implement pass recorded negative controls for all three (every case fails with the release arm removed; the third stops failing where it should with the participant guard removed).

Deliberately untested, each with a reason: the discard warning reaching the log (the fixture's servers log nothing, and asserting log text would pin wording rather than behaviour); a far server that comes back (`RemoteConnect`'s existing "no entry, so connect" path, already pinned by `TestLinkRecreatedUnderTheSameNameConnectsAfresh`, and `OutOfProcessInstance` reserves a fresh port per instance anyway).

## Review findings

**Major - one filed, as an arm on an existing ticket rather than as a new one.**

- **The assertion the implement pass added has exactly one way a correct engine can reach it, and chasing that found a pre-existing defect.** If a remote commit fails partway - the far server stops between a level's prepare and its commit, which is precisely this ticket's situation - the levels already ended stay ended and the process's own transaction is not popped, so the process is one level deeper than those connections. The rollback that follows guards on `remoteSession.InTransaction`, meaning "any level at all open", so for such a connection it rolls back the **outer** transaction - one the session has not finished with and may still commit - discarding work on the other server while the local half stays live. At a single level the state repairs itself; at two or more it does not, and the next commit then trips the new assertion. The assertion is the better of the two reports (before it, the same state produced "no transaction in progress" from the far server), so nothing regressed - but the level that was rolled back is a real defect. Appended as **arm 2 to `tickets/fix/bug-remote-catchup-uses-innermost-isolation`** rather than filed fresh: the site-claim grep over the board hit that ticket for `ServerProcess.cs`, and it is the same class of mistake - code addressing a connection's transaction level by the process's depth instead of by the connection's own - so it is evidence on an open ticket, not a new one. That ticket's header was widened with it: a plain-language `description:` covering both arms, `severity:` from wrong-result to corruption (arm 2's worst case is two servers disagreeing about work the user believes is in one transaction), and `tradeoffs:` rewritten. Not fixed inline: it changes error-path semantics in distributed-commit code, and this project's rule is that a bug fix owes its reproduction - which here needs either a fake `RemoteSession` (blocked on `RemoteSessionClassName` being internal with no `InternalsVisibleTo` convention in the repository) or a child server stopped inside a one-statement window. Both routes, and the one-guard fix, are written into that ticket so the fix stage does not start cold.

**Minor, fixed in this pass** - both in `ServerProcess.DiscardRemoteSession`, both comments stating something untrue:

- **The comment above the log call claimed an ordering constraint that does not exist**: "logged before the disposal, which clears the session's ServerProcess, so the link is read while the session is still live". Neither half binds. `RemoteSession.Dispose` clears `_serverProcess` but leaves `_serverLink`, so the link survives the disposal; and the log is reached through *this process's* `ServerSession`, not through the session being let go, so the remote session's state is irrelevant to it. (The constraint is real one layer down, in `RemoteSessionImplementation.ReportFailedRemoteStop`, which does read `ServerProcess` - presumably where it was borrowed from.) Replaced with the reason that does hold: the order puts the log in causal order, and nothing forces it. Left as a false "why", the next reader would defend an order that needs no defending.
- **"One warning per connection let go" undercounts.** A connection whose server has gone usually writes two: this one, then `ReportFailedRemoteStop`'s when `StopSession` fails against the server that is not there. The bound the remark exists to state - per connection let go, not per statement - is right; the count was not. Reworded to say both warnings and what each of them says.

**Checked and found clean** - read, and run where running it proved something:

- **`Error.AssertFail`'s sense.** Its name reads as "fail", not "assert", so the usage could easily have been inverted; it is not. `src/engine/Base/ExceptionUtility.cs:51` fails when the condition is **false**, and unlike its `AssertWarn` and `DebugAssertFail` neighbours it carries no `[Conditional("DEBUG")]`, so it is live in Release - as the handoff claimed.
- **`Disown` really removes by reference, and really leaves the list.** Re-derived rather than taken on trust: `RemoteSessions` declares `IndexOf(Schema.ServerLink)` as an overload, not an override, so `DisposableList<T>.Disown` reaches `BaseList<T>.IndexOf(T)` and matches on `Object.Equals`, which `RemoteSession` does not override; and `Removing` unhooks the item's `Disposed` handler while `_disowning` suppresses the disposal, so disown-then-dispose removes exactly once and a disposal that threw early cannot leave a dead entry behind.
- **The local count has no writer but this one.** A grep for every use of `RemoteSession`'s transaction members across `src/` finds only `ServerProcess`, and every begin in the tree funnels through `ServerProcess.InternalBeginTransaction` - including the application-transaction path and `ServerTransaction`'s own call - so the invariant has one gatekeeper.
- **A discard cannot orphan a session that is in use.** Every caller of `RemoteConnect` - in `Plan`, `Program`, `SystemNodes`, `TableNodes` - uses the returned session inside the same expression and stores nothing, so there is no long-lived reference that a release between statements could invalidate.
- **The keep-alive is untouched by the count change.** `NativeCLISession.GetTransactionCount` is still what the ping calls, and a failed ping is still ignored by design, so nothing on that thread reads or writes the new field.
- **The broad `catch (Exception)` in the begin is right, not lazy.** A begin refused by a far server that is perfectly alive - a session handle it has already reclaimed, say - also releases the connection, which is correct: the rule is about participation, not about why the call failed, and the next use reconnects.
- **The unguarded `LogMessage` in `DiscardRemoteSession`** matches every other engine log site, `ReportUnhonouredSecuritySettings` included. `ReportFailedRemoteStop`'s `catch { }` is the exception because it can run during a server's own shutdown, which a transaction begin cannot.
- **Error code 106212 is unique in the tree**, and the resx entry is appended without disturbing that file's missing trailing newline.
- **Source hygiene.** All five changed source files keep their tabs, CRLF endings and byte-order-mark state. `ServerProcess.cs` is 2302 lines, up from 2219 (`wc -l` on the file and on `8678a67a~1`); it was already the largest file in that folder, no ticket on the board claims its size, and this change adds one cohesive method, so nothing was split.
- **Statement-path allocation.** The snapshot and `remoteSessionsBegun` add two small objects per transaction begin - per statement, with implicit transactions on - where the counted version allocated the list's own enumerator (`BaseListEnumerator` is a class and `GetEnumerator` is an explicit interface implementation, so `foreach` already allocated one). Weighed against what a statement already allocates and left alone.
- **Documentation that should have gone stale and did not.** `docs/architecture.md` mentions server links only in its transport-security paragraph and describes nothing of the remote transaction protocol. `tickets/blocked/debt-remote-session-lazy-enlistment.md` already names this ticket's invariant as the thing lazy enlistment would replace, so it reads correctly after the change. K39 and both migration-note rows were re-read against the code and are accurate.

**Tripwires parked: none, and not for want of looking.** The one candidate was the per-begin allocation above; it was weighed, judged noise, and a `NOTE:` for it would be clutter rather than knowledge. Nothing else in the diff has the "fine now, work later if X" shape - the conditional concerns in this area are already owned, by `debt-remote-session-lazy-enlistment` in `blocked/` and by the existing `NOTE:` at `CatalogDevice.PopulateRemoteSessions` for unlocked reads of another process's list.

**Accepted tradeoffs: none found at any site touched**, so nothing was re-filed over a decision a human had already made.

**The handoff's own "what a reviewer might want to push on", answered:** the warning's volume bound stands, though its count did not (see above); wrapping all four transaction operations in 106212 rather than only the begin is right, since the release decision reads the count and never the exception, and the migration note carries the one visible consequence; the assertion's cost and placement are right, and its *reachability* is where the arm-2 finding came from.
