## What landed

Beside every table variable, and beside each of its columns, the engine keeps a three-flag summary of what a row of that table needs while a client is editing it - is there a default worth asking for, a check worth running, a change handler worth calling - and `TableNode.Default`, `Change` and `Validate` each return at once when the summary says there is nothing to do. The summary is derived from the column's own definition **and from its data type's**, and nothing recomputed it when a type changed: the statement holds the type, while the summaries that change with it belong to every table with a column of that type, and there is no index from a type to those tables. So after `alter type T { create constraint ... }` or `{ create default ... }`, or after `attach operator ... to T on { change }`, a cursor already open went on behaving as though the change had not happened - for a form, as long as the user keeps it open - and so did one open across a rolled-back drop of a type's check or default.

The summary is now a cache with a validity key:

- **`Schema.Catalog.ShouldCallProposablesTimeStamp`** (`src/engine/DAE/Schema/Catalog.cs`), a fifth coordination timestamp beside `TimeStamp`, `CacheTimeStamp`, `PlanCacheTimeStamp` and `DerivationTimeStamp`, with the same shape. It means "some definition a summary is derived from may have changed", and it is bumped in exactly two places: `DDLNode.InternalBeforeExecute`, which every statement that changes the catalog passes through, and `CatalogDeviceSession.InvalidateCachesAfterUndo`, which every rollback of one passes through. Complete by construction rather than by a list.
- **`Schema.TableVar.EnsureShouldCallProposables(Schema.Catalog)`** records the counter it last recomputed at (starting at -1, so a summary never yet ensured always recomputes) and recomputes only when the counter has moved. `DetermineShouldCallProposables` and `DetermineRemotable` deliberately do not record the stamp, because the counter is bumped *before* a statement runs and a statement can compile an expression over the table in the middle of its own work.
- **`protected abstract void RecomputeShouldCallProposables()`**, so the compiler forces every kind of table variable to state its own rule: a full recompute for a base table (the flags are a total function of its definition), raise-only for a view (its flags also carry what a compilation inferred from the expression, which only a compilation can produce), nothing for a plan-local stub (rebuilt by every compilation, so never stale).
- **Three read sites**, each immediately before its own `Should...` test: `TableNode.Validate`, `Change` and `Default`. Those three are also how a proposal descends a plan, so they cover every node of an open plan, not only its top - which matters, because the top of a plan over an operator is a stub whose flags all start raised, and the stale summary is the table's own one level down.

The nine hand-placed per-statement recomputes stay, against what the `fix/` ticket expected: the *stored* flags have two readers that are not proposals - `ServerProcess.CopyDataType`, which builds a client's copy of the table variable at prepare time, and `CatalogRollbackSnapshotTest`. What changed is that no proposal depends on that list being complete any more.

Docs: a `K43` row in the plan's known-defects register, and two rows in `docs/migration-notes.md` - the behaviour an application notices, and the new public members (including that a `Schema.TableVar` subclass in a source copy must now implement `RecomputeShouldCallProposables()`).

## How to see it

Against an in-process server, with a cursor opened **before** the statement and still open after it - that is how a form holds a table:

```
create type T { representation T { Value : Integer } };
create table Tbl { ID : Integer, Amount : T, key { ID } };
-- open an updateable cursor over Tbl here
alter type T { create constraint IsPositive value.Value > 0 };
-- ask the still-open cursor to validate { ID := 1, Amount := 0 }
```

Before: the call returns without complaint and the user meets the error on saving. After: the check is reported, as it is for a cursor opened afresh. The same shape holds for `{ create default T(7) }` (the cursor is now offered the default), for `attach operator ... to T on { change }`, and for the matching drops rolled back.

Nothing was ever stored wrong: the insert and the update check the constraint by a path that does not consult the summary, so what was lost was the early report.

## Tests

`tests/DAE.Server.Tests/TypeChangeSummaryTest.cs`, seven cases - the committed creation of a type constraint, a type default and a change handler; the rolled-back drop of a type constraint and a type default (these reach the invalidation through the catalog undo path rather than the statement); the same through a view (the one case that exercises the raise-only recompute); and the same through a restriction over the table (the one case that says the summary brought up to date is the one the proposal reaches by descending, not the one at the top of the plan). All seven fail with the three `EnsureShouldCallProposables` calls removed and the solution rebuilt, so none of them is a case that cannot fail.

Nothing else was added. One bullet was added to `CatalogRollbackSnapshotTest`'s recorded omissions, saying why its matrix does not pair a type change with a table that has a column of that type.

## Review findings

The diff of `ticket(implement): bug-rolled-back-type-constraint-stops-the-column-check` was read before its handoff summary.

**Checked and sound - the two claims the whole design rests on.** Both were re-derived rather than taken on trust. *Every statement that changes the catalog is a `DDLNode`*: `DDLNode` is the only override of `PlanNode.InternalBeforeExecute` that touches the catalog (`TableNode`'s is the other and does not), `InvalidateCachesAfterUndo` has one caller, and the `CatalogDeviceSession` methods that mutate a type's constraints, default and handlers are public API reached from DDL nodes and from the catalog's own lazy load, which also executes DDL nodes - extension code that calls them directly is covered by the migration note that tells it to bump. *A base table's flags are a total function of its definition, so the full reset is safe*: every writer of `ShouldChange`/`ShouldDefault`/`ShouldValidate` outside `Schema/TableVar.cs` was listed and each writes a plan-local stub's flags, never a catalog object's - so the reset cannot throw away state only a compilation could produce, which is the thing that forced raise-only for a view.

**Major - the handoff's reason for leaving the commonest plan shape untested is wrong, and one test was added.** The implement stage argued that a restriction or any other operator over the table needs no case, because such a plan puts a stub at its top whose flags all start raised, "so the proposal descends and meets the real definition whatever the summary says". The first half is right and the conclusion is not: what the proposal descends to is the *table's* summary, which is exactly the stale one. Measured by commenting the three calls out and rebuilding: a whole-row `Default` asked through `select Tbl where ID = 1` fails without them and passes with them. So the claim that the three calls cover every node of a plan and not only its top is a real contract, it was the one contract nothing pinned (all six original cases are single-node plans, and a later "optimization" that ensured only at the cursor's top node would have kept them all green), and it is the shape a form usually has. `TestCommittedCreateTypeDefaultIsOfferedThroughARestriction` now pins it, and the fixture's remarks say what is true. The check and the change-handler cases were tried through a restriction too and both pass with the three calls removed, so neither was added.

**Major - filed, not fixed here: the same staleness through a client.** `ServerProcess.CopyDataType` builds the `DAE.Is...Remotable` tags on the plan's table variable from the *stored* flags once, while the plan is being prepared, and `LocalCursor.Default`, `Change` and `Validate` each shortcut on them and answer out of the client's own copy of the schema without calling the server. Nothing re-sends that for an open plan, so a form in the Windows client still behaves as it did before this fix. Same symptom, different site and different mechanism (a snapshot that crossed the wire), and it needs a decision about how an open remote plan learns that a shortcut has been withdrawn - `tickets/fix/bug-remote-form-is-never-told-about-a-type-change`, `repro: static`, with what would make it verified. K43 names it as this defect's open arm, and the migration-notes row was corrected: it claimed the fix reaches "the forms that are already open", which overstates it.

**Minor - fixed in this pass.** Both new `docs/migration-notes.md` rows were separated from their tables by a blank line, so Markdown rendered them as paragraphs of pipe-delimited text rather than as table rows; the blank lines are gone. The plan's known-defects register had no row for this defect at all, which is the step every sibling ticket's implement stage takes and this one missed; `K43` is now there.

**Minor - a comment corrected.** The performance NOTE at the bump site read "and DDL is rare". Beginning an application transaction creates its copy of each table by executing a create-table statement and ending it drops them (`ApplicationTransactionDevice.AddTableVar`), so a form's own edit cycle passes through that bump - DDL is not rare in the workload this code serves. The note now says what is actually cheap about it: one recompute per table variable after a bump, not per proposal, 5.65 us against the 59.6 us of the proposal that reads it (the implement stage's measurement at `21f5105d`, not re-measured here, and the note says so).

**Tripwire parked, not filed.** The bump sits *before* the statement's own mutation, so a proposal from another session that lands between the two recomputes from the not-yet-changed definition and records the new stamp over it, leaving that one summary stale until the next catalog change. The window is one statement wide and needs a concurrent editing session to fall inside it; closing it means bumping again after the statement, and `PlanNode.Execute` offers only a before hook, whose cost on every node's hot path is why it carries the TODO it does. Recorded at the bump site in `DDLNodes.cs`, with the direction (give `DDLNode` its own after-execute hook; do not move this bump, which would reopen the compile-inside-a-statement case) and with the context that makes it tolerable for now: DDL and in-flight plans are unguarded against each other anyway - every `AcquireCatalogLock` call in `Compiler.cs` is commented out.

**Considered and declined, with reasons.** The handoff asked for a "do not stamp here" note on `BaseTableVar.DetermineRemotable` and `DerivedTableVar.DetermineRemotable` as well: declined, because both reach the stamp question only by calling `DetermineShouldCallProposables`, where the explanation already is, and three copies of one rule is how a rule starts disagreeing with itself. The three cases that assert `Does.Contain("IsPositive")` on the exception text couple them to how a type-constraint violation is reported: left as they are, because the sibling fixture `ColumnChangeRollbackTest` already has exactly that coupling and a reviewer's preference is not a reason to make two fixtures disagree about style. The view's raise-only recompute never lowering a flag: left as designed - a flag left raised costs a call that finds nothing to do, and recording which flags a compilation inferred so a reset could restore them is a larger change than this defect justifies.

**Nothing found in these, and why.** *Resource cleanup and error handling* - the whole change is a field increment, a timestamp comparison and a walk over a collection the object already holds; nothing is allocated, opened or thrown. *Type safety* - the new abstract method is what makes the per-kind rule a compile-time obligation rather than a convention, which is the opposite of a gap. *Error paths* - no new failure mode: a recompute that ran when it did not need to costs one walk of the columns, and `EnsureShouldCallProposables` reads the counter before recomputing and records that value afterwards, so a bump landing during a recompute leaves the stamp behind the counter (one extra recompute) and never a stale summary wearing a current stamp. *Overrides that could skip the three calls* - `TableVarNode` is the only class that overrides `Validate`, `Change` or `Default`, and each override calls base whenever it propagates the proposal at all. *Source hygiene* - no file grew into a new size bracket (`TableVar.cs` 3226 lines, `TableNode.cs` 3485, `DDLNodes.cs` 3393, all within the range they were already in), and the new comments say why rather than what. *Docs the change should also have touched* - `docs/architecture.md` describes none of the coordination timestamps, so there is nothing there to bring up to date.

**Known gaps carried forward, unchanged.** No case covers the library-loading path (the bump fires while a library loads, argued harmless and exercised incidentally by every fixture that starts a server) and none covers two sessions (the counter is per catalog, so a DDL in one session invalidates another's summaries; that follows from the design but is not pinned). Neither is filed: a loading-path case would assert the absence of an effect, and a two-session case belongs with the tripwire above, which is the part of the two-session story that is actually uncertain.
