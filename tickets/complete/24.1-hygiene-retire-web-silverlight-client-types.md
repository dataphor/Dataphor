## Review findings

**Read first:** the implement-stage diff (`ticket(implement): hygiene-retire-web-silverlight-client-types`) before the handoff summary.

### Major — fixed in this pass

**The migration note described a failure mode that does not happen.** It said an application passing `Web` or `Silverlight` to `GetNodeTypes`, `GetApplicationNodeTypes`, `GetLibraryNodeTypes` or `GetLibraryFiles` "now gets an error from the restriction on the table rather than a result". Three things were wrong with that, and the note even contradicted itself one clause later by noting that each document load is guarded by `DocumentExists`:

- None of the three node-type operators reads `ClientTypes` at all. Each builds a document name from the identifier (`<client type> + ".NodeTypes"`) and guards every load with `DocumentExists`, so an unknown client type returns an **empty** `<nodetypes/>` document — silently, with no error.
- `GetLibraryFiles` does not take a client type identifier; its first parameter is an *environment* string, and it is implemented by a C# node (`Frontend.GetLibraryFilesNode`) that never touches the table. What a client actually passes is `ClientTypes[<client type>].Environment` (`src/client/Frontend.Client/Session.cs:26`, `src/windows/Frontend.Client.Windows/Session.cs:32`).
- That key lookup is not an error either: the engine compiles `DAE` with `NILPROPOGATION` defined (`src/engine/DAE/DAE.csproj:18`), so a row extractor over an empty restriction yields nil rather than throwing, and `GetLibraryFiles` over a nil environment returns no rows.

Measured, not inferred: a throwaway probe fixture on an in-process server carrying `Frontend` reported `Count(ClientTypes)` = 1, `GetNodeTypes('Web', ...)` = the empty document, `ClientTypes['Web']` nil, and `GetLibraryFiles` over that nil environment = 0 rows. The note now states this, names the measurement date and says plainly that silence — not an error — is the shape of failure an application has to look for, which is the more useful warning and the harder one to diagnose. The shipped Windows client and the form designer both pass `Windows`, so neither is affected; the note says that too.

### Tests

One test file added, `FrontendClientTypesTest` (2 cases, 127 ms, its own small fixture carrying only `SimpleDevice` and `Frontend`). It exists because the corrected compatibility claim was verified nowhere: one case pins the single shipped row and its environment, the other pins that an unlisted client type yields the empty node-types document through both `GetNodeTypes` and `GetLibraryNodeTypes`, with a positive control asserting that `Windows` still returns real node types so the case cannot pass by the mechanism being broken everywhere. The implementer's judgement that no test was owed was reasonable on its own terms — the goldens do cover the schema — but the behaviour the migration note promises is a contract, and the new file is the record of that contract rather than of a data set.

No test was cut: the change added none.
