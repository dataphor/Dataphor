## What landed

No engine change. The fix ticket's premise - that the engine's right check gave a wrong answer - was wrong: the refusal was correct, and the defect was in how the coverage harness ran the script. `ticket(implement): bug-right-check-fails-for-granted-right` turned the `ServerLink` coverage entry from a recorded known failure into a passing one by running the script batch by batch, and rewrote the two passages in `docs/modernization-plan.md` that described this as an engine defect. The review corrected the mechanism those passages state, and parked one thing it noticed as a comment; the files are listed above.

**The behaviour, as the review confirmed by running the script nested again.** The script creates `TestUser` at its line 40 and at line 43 runs a block as that user through `ExecuteAs`, which connects a session of its own. `CreateUser` does two things: it caches the user (per engine, not per transaction) and it inserts the user's membership in the standard User role, which is where an ordinary user's rights come from. Nested inside one `ExecuteScript` statement, that membership is still inside the enclosing statement's open transaction, so the new session authenticates as `TestUser` and is then refused the `Execute` right on the `System.Name` operator that the role grants - the observed error is `User "TestUser" does not have access to right "System.Name0000001789Execute"`, which is a rights failure, not a missing user. Run batch by batch, one implicit transaction per batch commits both before the block runs as the user, and all 126 of the script's statements pass. The engine rule itself is already pinned by `UncommittedGrantNotUsableInOtherSession` in `tests/DAE.Server.Tests/CatalogStoreTest.cs`.

`batches` is a pre-existing manifest option documented on `CoverageManifest` for exactly this case and already used by `ApplicationTransactions`. Two other coverage scripts handle the same trap by hand: `AsyncExecution` and `SecurityLibrary` with a `SetUseImplicitTransactions(false)` preamble, and `SessionAndProcessScopedTables` by creating its user on a process it starts itself (its own comment says why). No new K row in the plan's *Known defects* table (no defect to record) and no `docs/migration-notes.md` entry: a test manifest, a doc comment and the plan are nothing an application, a deployment script or a C# extension can notice.

## Review findings

**Checked.** The implement diff read before the handoff. The manifest entry against the `batches` and `linkedServer` contracts on `CoverageManifest` and against `CoverageScripts.RunInProcess` (batch mode runs the server's own copy of the script text on the script's process, so each batch gets its own implicit transaction; a failing batch still throws out of `ServerScript.Execute`, so `pass` is not hollow). Manifest file still LF, no byte-order mark, strict JSON, sorted. Each coverage script runs on a fresh copy of the template instance, so committing per batch cannot leak state into another script's case. The mechanism itself, by reading `SystemExecuteAsNode` (it calls `Server.Connect`), `SystemCreateUserNode` (`InsertUser` plus `InsertUserRole`) and the pending-user machinery in `CatalogDevice`, and then by running the script nested again to see the actual error text. Every other coverage script that uses `ExecuteAs` with a user it creates, to see whether the manifest is now inconsistent: it is not, all three were already handled. The script's blocks after line 43, which this ticket runs for the first time - the link-user operators, `RemoteSessions`, the non-scalar results, the `like` types - and the `UseSessionInfo` assertion before it, which reads inverted and is not: `SetMaxCallDepth` sets the program's stack, not the session info a link copies, so the block is right to raise when the remote process reports 128. Lint and tests, below.

**Found and fixed in this pass.** The implement pass stated the mechanism as "a new session cannot see a user the enclosing statement's still-open transaction created", in both of its artifacts - the manifest `note` and the WS3 paragraph of the plan - and that is not what happens: the user *is* visible, because the users cache is per engine, and what the new session cannot see is the role membership that carries its rights. The next reader greps the error, which says *right*, and is told the user was invisible. The manifest note, the plan's WS3 paragraph and the K35 row's closing clause now say what the engine does. The `batches` field's own documentation on `CoverageManifest` named two reasons to use it; a block run as another user through `ExecuteAs` is the third and the one three scripts have now met, so it is named there too.

**Found and parked as a tripwire, not a ticket.** The users cache is per engine and filled before the creating transaction commits, so another session can authenticate as a user whose creation has not committed - harmless today, because the user holds no rights there (its role membership is transactional, and the pending-user machinery keeps another session from reading an uncommitted grant) and a rollback removes it again. It is also why this ticket's symptom was a rights error rather than "user not found". Recorded as a `NOTE:` on `CatalogDeviceSession.InsertUser`, which names the pending-user machinery as the model if an uncommitted user must ever stop being visible.

**Considered and not re-filed.** The implement pass declined a manifest guard that would fail any coverage entry whose script mentions `ExecuteAs`/`ExecuteOn`/`EvaluateOn` without `batches` or the preamble. The review agrees and did not re-open it: three scripts handle this by hand, each differently and for its own good reason, the failure mode is loud and names the script, and a textual guard over D4 source would misfire on comments and on scripts that pass anyway.

**Not found.** No correctness, resource-cleanup, error-handling or type-safety finding: the change adds no code. No file-size or duplication finding: `CoverageManifest.cs` is 290 lines (`wc -l`) and `CoverageScripts.cs` 566, both unchanged in structure. No test to cut and none owed beyond the script itself. Nothing filed as a ticket, because nothing found reaches the filing bar - the one prose defect was fixed here and the one latent concern is conditional.

**Known gap left open, deliberately.** The script's blocks after line 43 now run and pass, and the review read them, but "no error" is most of what they assert: the non-scalar-result and `like`-type blocks are bare `select` statements with no comparison. That is how the legacy script was written, and the plan already says to read the feature list as what the script executes rather than as a clean bill of health. Turning those blocks into assertions is coverage work for the WS3 workstream, not a defect in this ticket.
