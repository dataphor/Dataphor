## What landed

The last of the four steps the chain `engine-object-id-generator` began. The implementation is in `ticket(implement): bug-object-id-counter-is-process-wide`; this ticket's own commit carries the review pass.

`Engine`'s constructor now creates a `Schema.ObjectIDGenerator` of its own and keeps it for the engine's lifetime, so two engines in one program number their catalogs independently. The transition's shared instance and the three `Schema.Object` statics that drew from it - `GetNextObjectID()`, `SetNextObjectID(int)` and `GetObjectID(MetaData)` - are deleted, as is `ObjectIDGenerator.SetLastAllocated`, which existed only to serve `SetNextObjectID`. Nothing in the tree can move a generator's counter *down* any more, which is the capability the whole defect rested on.

`Engine.InitializeCatalog`'s `ObjectIDGenerator.Reset()` is unchanged, in the same place and under the same conditions; it now resets the engine's own generator. Whether a repository engine should reset at all on a catalog rebuild is still `bug-client-catalog-rebuild-reuses-object-ids`'s question, and the reset site now says so (below).

The four workarounds the chain had accumulated are gone: `TestEnvironment.WithTheObjectIDCounterRestored` and all four of its call sites (`ProtocolClient`'s constructor, `ConnectionKeepAliveTest.NewClient`, and two in `CoreWcfProtocolTest`), and the same save-and-restore in `tests/Dataphor.Benchmarks/BenchmarkServerInstance.cs`. The implement handoff corrected two factual claims the ticket had made, and both corrections are right: `tests/Dataphor.Benchmarks` **is** in `Dataphor.slnx` (line 40, so every build compiles it), and the failure the reproduction produces is the in-memory one (`CatalogDeviceSession.CacheCatalogObject`) rather than the store's `UNIQUE constraint failed: DAEObjects.ID`, which is the same collision arriving where the colliding object is not already in the engine's cache.

## Review findings

The implement diff was read first with the handoff set aside, then every claim in the handoff was re-derived from the tree, and the reproduction was re-measured independently in both directions.

### Fixed in this pass (minor)

- **Five more files still asserted that the object-id counter is shared.** The handoff said eleven files carried that prose and that each was corrected or deleted; the sweep was incomplete, and the five it missed are the ones a reader is most likely to meet, because four of them are the `// Not [Parallelizable]:` notes at the top of fixtures. `AbandonedClientProcessTest` and `OutOfProcessProtocolTest` both said the clients they build "share the object-id counter (see ProtocolClient)" - a dangling cross-reference as well as a false claim, since the same commit deleted the explanation in `ProtocolClient` they pointed at; both now say that two engines in one process share whatever engine statics are left and point at the authoritative list, the `NOTE:` on `TestServerInstance`. `HostBindingHookTest` explained that no case here restores the counter "unlike CoreWcfProtocolTest's second hosts", which no longer restore anything; that sentence is deleted. `OutOfProcessInstance` named the counter among the statics a separate process does not share. `tests/Dataphor.Benchmarks/Program.cs` justified its in-process toolchain by "BenchmarkServerInstance's object-id counter", a field the same commit deleted - the project's `README.md` was updated for exactly this sentence and the code comment beside it was not.
- **`docs/migration-notes.md` told an extension author the wrong thing about `SetNextObjectID`.** The new entry said "there is no replacement for `SetNextObjectID`, which only ever existed to put the shared counter back". It did not: before this chain it had two production callers, `Engine.InitializeCatalog`'s `SetNextObjectID(0)` and `Server.LoadServerState`'s `SetNextObjectID(GetMaxObjectID() + 1)` (both present at `f2a90103`, the commit that split `Server : Engine`), and both now have public counterparts on the generator - `Reset()` and `EnsureAllocatedThrough(int)`. This matters on a compatibility surface rather than being a wording nit: an extension with a catalog load path of its own is precisely the case `ObjectIDGenerator.Allocate(MetaData)`'s remarks warn must raise the generator itself, and the entry as written told that author there was nothing to raise it with. The entry now names both methods and keeps the real point - that nothing can lower a counter any more.

### Parked as a tripwire

- **`Engine.InitializeCatalog`'s `ObjectIDGenerator.Reset()` carried no sign that the method is called a second time.** The ticket required the reset be left exactly as it was, and it was; but `ClearCatalog` calls `InitializeCatalog` again, so a catalog rebuild restarts a *live* engine's generator from one - which for a client-side engine happens mid-life, whenever the server's catalog moves on. A `NOTE:` at the site now says this, says it is deliberately unchanged, and names `bug-client-catalog-rebuild-reuses-object-ids` as the ticket that owns the question. Nothing filed: that ticket is open in `tickets/fix/` and already carries the note the implement pass appended to it.
- No other new tripwire. The one standing conditional concern in this area, identifier exhaustion, is recorded at `ObjectIDGenerator.Allocate` and is made *less* likely by this change, not more - a long-lived client-side engine no longer shares its counter with anything.

### Checked and found sound

- **The reproduction, re-measured independently.** Every engine was put back on one static generator (a four-line patch to `Engine.cs`), the solution rebuilt, and `ObjectIDPerEngineTest.StartingASecondEngineLeavesTheFirstServersCatalogAlone` run: it fails, in `CatalogDeviceSession.CacheCatalogObject` by way of `CreateTableNode.InternalExecute`, exactly as the handoff recorded. The patch was reverted in the same command, and the suite below was run on the restored tree. So the handoff's two corrections to the ticket's predicted failure route are confirmed rather than taken on trust.
- **No reference to any removed member survives.** Grepped the whole tree (every `.cs`, `.md`, `.d4`, `.d4l`, `.dfd`, `.cfg`) for `GetNextObjectID`, `SetNextObjectID`, `GetObjectID`, `SharedObjectIDGenerator` and `SetLastAllocated`: the only hits are `Plan.GetNextObjectID`, which is the intended replacement, and one commented-out line at `src/engine/DAE/Runtime.Instructions/AdornNode.cs:178`. That line is left alone, as the handoff proposed: it is one line of a longer block of commented-out 3.1 alternative implementation, it cannot execute, and editing a single line of a dead block leaves the block inconsistent for no gain.
- **`ObjectIDGenerator.Allocate(MetaData)`'s invariant still holds, and it was worth checking.** Its remarks claim that every path which loads objects carrying `DAE.ObjectID` tags is a catalog store load, so the generator is raised afterwards by `Server.LoadServerState`. The obvious candidate for a second such path is the client-side catalog cache, which `LocalProcess` builds by *executing a D4 script* the server emits - and if that script carried the tags, the client's own generator would reissue identifiers the cached fragment already holds. It does not: the server emits the fragment with `EmitMode.ForRemote` (`RemoteServerProcess.GetCatalog`), and `EmitDefinition` writes the tag only under `EmitMode.ForStorage` and *removes* it otherwise. The client-side engine therefore numbers the fragment from its own generator. Stated here because `bug-client-catalog-rebuild-reuses-object-ids` will work from that remark and should not have to re-derive it.
- **Engine lifecycle and the generator.** A `readonly` field published in the constructor before the engine is reachable from another thread; nothing to dispose; `Stop()` followed by `Start()` renumbers through `InitializeCatalog`, which is what a store-backed engine requires. `Server : Engine` inherits the property and uses it at its two sites (`CreateCatalogDevice`, `LoadServerState`).
- **The reverse order the handoff asked a reviewer to weigh needs no test.** The handoff noted that the new case starts the second engine *after* the first server has allocated, and wondered whether the opposite order wants a case of its own. It does not: with a generator per engine there is no shared state for an order to matter to, and that follows from the construction rather than from any sequence a test could exercise. A case asserting it would restate the implementation.
- **`second.LoggingEnabled = false` in the new test is load-bearing.** `Engine._loggingEnabled` defaults to `true`, so without it the nameless second engine would log - which is what creates the `Dataphor Server` Windows event-log source in an elevated process. The comment beside it is correct.

### Tests

### Not re-opened

`src/engine/DAE/Schema/ObjectIDGenerator.cs`'s split locking - `Allocate` lock-free through `Interlocked`, `Reset` and `EnsureAllocatedThrough` under a monitor, deliberately not serialized against each other - is an accepted design from `engine-object-id-generator` with its reasoning on the `_syncRoot` field, and it rests on a condition this change does not alter: the two setters run during start-up and catalog rebuild, when nothing in that engine is allocating. Nothing here gives cause to revisit it.
