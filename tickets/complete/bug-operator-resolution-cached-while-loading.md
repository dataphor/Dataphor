## Outcome

`Compiler.ResolveOperator` splits on `plan.InLoadingContext()`: the loading arm resolves against `plan.PlanCatalog` then `plan.Catalog` and never touches the shared cache, and the non-loading arm keeps the previous lookup-then-resolve-then-add shape but gates the add on `plan.Catalog.Contains(context.Operator)`. `Compiler.FindScalarConversionPath` now scans the chosen `context.BestPath` for any `Schema.Conversion` in `plan.PlanCatalog` and skips the add when one is present. The XML remarks on `OperatorResolutionCache` and `ScalarConversionPathCache` state the new invariant, and `docs/modernization-plan.md` gets a K34 row describing the defect and the fix.

Two new tests in `tests/DAE.Server.Tests/SchemaCacheInvalidationTest.cs` cover the two operator arms (`LoadingContextOperatorResolutionDoesNotPoisonSharedCache`, `FailedCreateOperatorDoesNotCachePhantomResolution`); the conversion-path arm has no test, guarded by the `plan.PlanCatalog.Contains(conversion)` check at the site.

Shipped by `ticket(implement): bug-operator-resolution-cached-while-loading`.

**What was found.**

- *Minor — loading-context arm no longer acquires `lock (plan.Catalog)`.* The previous code held `lock (plan.Catalog)` over the whole cache read/write region, so even in a loading context the lock was held while iterating `plan.Catalog.Operators`. The new loading-context arm takes neither lock. That is consistent with the invariant the fix is enforcing — the loading arm must not touch the shared cache — and other compile sites also iterate `plan.Catalog` without this lock (`Compiler.cs` has many such sites). Loading-context work enters through `CatalogDeviceSession` paths that serialize against the catalog device, so the practical concurrent-iteration risk is low. Not a blocker; recorded here rather than as a tripwire because the cost of the removed lock was a serialization bottleneck for every loading-context resolve.
- *Minor — the invariant is stated three times (K34, `OperatorResolutionCache` remarks, `ScalarConversionPathCache` remarks).* The handoff offered to consolidate. Left as is: each site names its own responsibility, and the three statements are not contradictory. No change.
- *No conversion-path regression test.* Handoff flagged this as a known gap. The site assertion (`plan.PlanCatalog.Contains(conversion)` inside the `foreach`) is a cheap, local invariant that fails loudly if someone later breaks it. Reproducing the bug end-to-end would require compiling `create type … like` under `PrepareStatement`, tracing a conversion through the temporary conversion from another session's compile, then discarding the prepare — significant test machinery for an arm already guarded at the check site. Agreed: no new ticket.
- *Tripwires:* None worth filing. The one invariant worth parking (loading-context lock removal) is a performance choice, not a defect waiting to trip; the code itself documents the "shared cache" invariant adequately.

Nothing filed inline. No new tickets, no new tripwires, no doc edits.
