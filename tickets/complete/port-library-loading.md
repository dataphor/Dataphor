## What landed

The server now resolves a D4 library assembly's private managed packages and native dlls out of the library's own folder, and the folders of the libraries it requires transitively, through a per-process `LibraryAssemblyResolver` installed from `AssemblyUtility`'s static constructor. `LibraryUtility.RegisterLibraryFiles` builds a deduplicated probe-folder list once per register call and registers each library assembly with it before handing the assembly to the catalog device session; `UnregisterLibraryAssemblies` removes the probe entry together with the catalog entry. The two hooks — `AppDomain.AssemblyResolve` for managed, `AssemblyLoadContext.Default.ResolvingUnmanagedDll` for native — return nothing when the requesting assembly is not in the table, so the host's bin and anything else resolve as before.

`tools/layout/Layout.csproj` drops the error that failed the build on a private native asset: the existing RID flattening already assigned a flat `Libraries\<Name>\` destination for native files; the error was the only thing stopping them from reaching the layout. The `.d4l`-listed-files check stays.

A new test library `tests/libraries/LibraryLoadingProbe` exercises both hooks end-to-end: `ProbeManagedResolver()` touches `typeof(BsonDataWriter)` to force resolution of a private managed package (`Newtonsoft.Json.Bson`) that is not in the host's bin, and `ProbeNativeResolver()` calls `NativeLibrary.Load("Microsoft.Data.SqlClient.SNI", <probe assembly>, null)` which trips the unmanaged hook against the flattened native dll. `LibraryLoadingTest` in `DAE.Server.Tests` fires both operators and keeps a regression guard that still registers the Connection library (four private managed packages flattened by a prior ticket).

`Directory.Packages.props` adds the two centralized package versions referenced only by the probe. `docs/migration-notes.md` carries one entry for the behaviour change; `docs/architecture.md`'s *Libraries and class loading* paragraph names the resolver in the `LibraryUtility.RegisterLibrary` sequence.

- **Tripwires (handoff-recorded, not re-filed).** `ResolvingUnmanagedDll` fires only once per (assembly, name) per process — .NET caches the result, so the test's single call is enough and a future re-register inside the same process re-uses the native handle. The native resolver falls through on miss rather than throwing; no explicit regression test was added for the miss-path because the desired behaviour is just "runtime raises its own exception," which is observable the moment anyone deploys a library with a missing native dependency. No new comments needed beyond what landed; no backlog entries filed.
