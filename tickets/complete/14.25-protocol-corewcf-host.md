## What landed

`DataphorServiceHost.Start()` starts a .NET 10 Dataphor server and serves all three of its contracts on CoreWCF, at the addresses and ports the 3.1 server published, from the same instance configuration, through the entry points the console host, the Windows service and `DAE.Client`'s non-embedded in-process alias already call. The four questions the CoreWCF proof left open were answered by measurement in the plan ticket and are implemented here; three of the four are covered by tests, and the fourth (the machine-name listen address serving both address families) was re-measured by hand during implementation.

The implementation is `ticket(implement): protocol-corewcf-host`. Its own summary of the change is accurate and is not repeated here; what the review changed on top of it is in *Review findings* below.

## Review findings

### Checked

The implement diff was read in full before the handoff summary. Beyond the test run above:

- **Address compatibility, by reading both sides.** Both endpoint addresses and the listener address are built by `DataphorServiceUtility` from `HostName`, whose default is `Environment.MachineName` — which is what 3.1 passed — so a 4.0 server publishes the same addresses byte for byte, including the instance segment and the `/service/native` suffix. `TestNativeCliAnswersOnItsNestedAddress` establishes that the nested address dispatches.
- **The three entry points, at their call sites.** `src/hosts/DAEServer/Program.cs`, `src/hosts/DAEService/Service.cs` and `src/client/DAE.Client/ServerConnection.cs` use only `InstanceName`, `Start()`, `Stop()`, `IsActive` and `Server`, all of which kept their signatures and their order of work. Nothing in the tree constructs a `ListenerServiceHost` itself, so its changed constructor breaks no caller in the repository.
- **Logging stays as it was.** `ServerConfiguration.ApplyTo` does not touch `LoggingEnabled`, so the new property's `true` default leaves a hosted server logging exactly as before; only a caller that sets it (the test fixture) differs.
- **Instancing matches the registrations.** `DataphorService` and `NativeCLIService` carry `InstanceContextMode.Single` and are registered as dependency-injection singletons; `ListenerService` does not and is registered by type, so CoreWCF constructs it per session as `new ServiceHost(typeof(ListenerService))` did. `NativeServer` and `NativeCLIService` are not `IDisposable`, so `Stop()` nulling them leaks nothing.
- **`Stop()` against every half-built state `Start()` can leave**, and the stage order against the original: listener, then the instance's host, then the service, the `RemoteServer` and the engine server. A host error is captured and rethrown only after the engine server is stopped, so a host that will not stop cannot leave a server running. Two of the states are now covered by test rather than by inspection (below).
- **Documents, including the ones the change should have touched.** The known-defects table (K12, K14, K18, K22, K23, K27) is still accurate; nothing in it claimed the hosts were uncompiled. `AGENTS.md`'s runtime-layout paragraph is still true (`bin/` has no host until `host-generic-host`). The only stale text found anywhere was one code comment, fixed below.
- **The implementation's tests as code under review.** None restates the implementation, verifies a mock, or tests wiring, registration or a constant: each of the twelve drives real client code over the wire or asserts a port, address or binding fact that only the host can produce. Nothing was cut. `CoreWcfProtocolTest.cs` is 847 lines for thirteen heavily documented cases of one fixture, which is within reason; splitting it would separate cases from the fixture they share.

### Found and fixed in this pass

- **A test the ticket specified was missing.** The ticket's edge-case table asks for "a test that starts a host on a port already held by another socket (the instance port, not the listener port — that one must fail)", and the handoff lists that path as covered by inspection only. Added `TestTheInstancePortBeingTakenStopsTheServer`: the start raises `System.IO.IOException` naming the port — so the failure arrives as itself and is not masked by anything `Stop()` meets on the way out — `IsActive` is false afterwards, so the engine server that did start was stopped, and stopping a second time does nothing. Passes. Two helpers were extracted from the fixture so the new case does not duplicate it: the `ServerConfiguration` the suite hosts with, and the object-id counter guard `WithASecondHost` already had.
- **The two hosts duplicated the host shape, and depended on each other the wrong way round.** `ListenerServiceHost` reached into `DataphorServiceHost` for both the listen-address format and the stop timeout, while `DataphorServiceHost` owns a `ListenerServiceHost` — mutual coupling — and the twelve lines of Kestrel and CoreWCF configuration were written twice with a comment pointing from one copy to the other. Extracted `src/engine/Server.Hosting/NetTcpServiceHost.cs` (internal): `StopTimeout`, `ListenAddress`, `Build(hostName, portNumber, registerServices, addEndpoints)` and `Stop(IHost)`. Both hosts now state only what is theirs — the instance's two endpoints and its two singletons, the listener's one endpoint and its service type — and `host-generic-host`, which owns the logging these hosts discard and would want an asynchronous surface, has one file to change instead of two. Behaviour is unchanged; the thirteen cases and the whole suite pass after it.
- **A compatibility surface changed with no migration note.** The old host built its endpoints' binding with `DataphorServiceUtility.GetBinding()`, which routes through the public hook `DataphorServiceUtility.BuildBindingCall`; the new host builds it with `DataphorServiceHostBinding.Build()`. So replacing that hook — which the plan records as the only route a deployment has ever had to a secured transport, supplied from its own host code — now changes what a client connects with and no longer what a server listens with, and there is no host-side equivalent to replace, CoreWCF's `Binding` being an unrelated type to `System.ServiceModel`'s. The protocol itself is unchanged and `TestHostBindingMatchesTheClientBinding` holds the two declarations in step. Added the entry to `docs/migration-notes.md`, named the loss in the plan's hand-on bullet for `protocol-transport-security`, which owns what replaces it, and recorded in `docs/architecture.md` that the one binding is now declared twice and why.
- **A stale comment.** `src/engine/Server/Server/RemoteServer.cs` said its constructor is public because `protocol-corewcf-host` "needs it **if** hosting moves to an assembly of its own". It moved; the comment now says so.
- Two sentences the review's own refactor made inaccurate were corrected with it: `DataphorServiceHost`'s class remark on where the logging providers are cleared, and the plan's "the shutdown timeout is a constant in the class".

### Weighed and left alone

- **`IsListening` and `LoggingEnabled`,** the two members beyond what the ticket specified, which the handoff asked the reviewer to judge. Both kept. `IsListening` is the only way to read discovery status without turning the server's log on, it is what the ticket's own required listener test needs, and a future host will report it. `LoggingEnabled` exists because `DataphorServiceHost` creates the `Server` itself, so nothing can reach `Engine.LoggingEnabled` before it starts, and without it the suite would make an elevated process create the Windows event-log source — which the root `AGENTS.md` forbids the default suite run to do. The alternative the handoff offers, a logging setting on `ServerConfiguration`, would change a BOP-serialized compatibility surface and belongs to `host-instance-configuration`. Both are in `docs/migration-notes.md`.
- **`RequireSecureConnection` and `RequireSecureListenerConnection` still unused,** deliberately, with the configured-and-never-honoured evidence intact for `protocol-transport-security`.
- **`ServerLink`'s `known-failure` entry** in `tests/DAE.Server.Tests/coverage-manifest.json`, untouched: what it still needs is a second hosted instance to link to, which is `test-client-server`'s.
- **`TestListensOnlyOnTheReservedPorts`,** whose failure mode is environmental rather than a real defect. It compares two machine-wide snapshots of listening ports taken milliseconds apart, which is the only way to establish that Kestrel opened no HTTP endpoint of its own; the narrower assertion is already written down in the `NOTE:` at the site for whoever meets a flake.
- **`DAE.Client` pulling the hosting assembly in,** with `NU1902` and the ASP.NET Core shared-runtime requirement, and **the runtime layout's `bin/` now holding two generations of the `Microsoft.AspNetCore.*` assemblies.** Both are real and both are written up in the plan's hand-on list against the work items that own them (`ui-client-layering`, `security-dependency-audit`, `host-generic-host`).

### Tripwires

Three added by the review, at the site in each case:

- `src/engine/Server.Hosting/NetTcpServiceHost.cs`, on `ListenAddress` — the hosts spell `net.tcp` outright, where the addresses the endpoints and the clients use come from `DataphorServiceUtility`, whose `USENAMEDPIPES` compile-time switch would make them `net.pipe` and drop the port. Nothing defines it; if it is ever wanted, the hosts have to change with it and that is the work, not a one-line edit.
- `src/engine/Server.Hosting/NetTcpServiceHost.cs`, on `Stop` — both hosts are started and stopped by blocking on the asynchronous call, which the synchronous `Start`/`Stop` surface requires. That it does not deadlock on a thread with a synchronization context rests on Microsoft's hosting and Kestrel code awaiting with `ConfigureAwait(false)` throughout, and the Windows client and the IDE start a non-embedded in-process alias on the user-interface thread. If a hang ever turns up there, that is the assumption to check.
- `src/engine/Server.Hosting/DataphorServiceHost.cs`, on `Start`'s outer `catch` — `Stop()` runs there with the start failure in flight, and `Stop()` rethrows a failure of its own from either host, which would replace it and hide why the server did not start. No stage of `Stop()` is known to fail on that path, and the new test establishes that the common case (the instance port taken) reports the bind failure itself.

Two carried over from the implementation, unchanged, both in `tests/DAE.Server.Tests/CoreWcfProtocolTest.cs`: the machine-wide port snapshot in `TestListensOnlyOnTheReservedPorts`, and the window between releasing a reserved port and CoreWCF binding it in `ReserveLoopbackPorts`.
