## The vocabulary, for a reader without the context

One Dataphor transaction can span several places at once. A session's *process* holds one connection per back-end database it has used - a **device session**: a SQL Server or PostgreSQL database, Dataphor's in-memory store, and always the catalog, which is Dataphor's own store of its table, type, operator and user definitions - and one per other Dataphor server it has queried, a **remote session**. Each of those is a **participant**: every transaction level the session begins is begun on every participant, and ending the level ends it on every participant. Transactions nest: a session can hold an outer level and an inner level at once, finish the inner one, and carry on with the outer one.

The commit is sequential. The process asks each participant in turn - remote sessions first, then the back-end databases, the catalog last - and there is no protocol that can undo a participant that has already said yes. So if the fourth participant's commit fails, the first three have committed that level and the fourth has not. The engine had no explicit record of that state and read it off raw level counts, which is where the two defects came from.

## What landed

In `ticket(implement): bug-partial-commit-rolls-back-committed-participants`, plus the review's own edits listed under *Minor, fixed in this pass*.

**One predicate, asked at every site that ends a level.** `ServerProcess.HoldsEndingLevel` - a one-line helper for remote sessions, added by `bug-remote-catchup-uses-innermost-isolation`, which named this ticket as the owner of the rest - became a shared body plus two thin overloads, one naming a remote session and one naming a device session, and `InternalRollbackTransaction` now asks it in all three of its loops. The question is "does this participant still hold the level this rollback is ending?", answered as *participant levels == process depth*, with *participant levels <= process depth* asserted rather than assumed. The two device loops used to ask the weaker question `InTransaction` - "is this participant in a transaction at all?" - which after a partial commit is true of a committed participant **for the level outside the one being ended**. That level was then rolled back on it, silently. `RollbackBegunParticipants`, which unwinds a failed *begin*, deliberately still names the participants that began the level rather than counting them, and carries a comment saying so.

**One explicit record of a half-committed level.** `ServerTransaction.CommitBegun` is set in `InternalCommitTransaction` after the prepare returns and before the first participant commit, and is never cleared; the path that succeeds removes the transaction object, so a transaction object still carrying it is one whose commit failed part-way. Two operations are then refused with the new error **106213**, `TransactionCanOnlyBeRolledBack`: a retried commit, refused in `InternalPrepareTransaction` *before* the `Prepared` test so that it is refused whether or not the first prepare completed; and a nested begin, refused in `InternalBeginTransaction` beside the existing `UseDTC` check. A rollback is always allowed and is unchanged.

The existing `Error.AssertFail` on remote session counts in `InternalPrepareTransaction` stays: the one way a correct engine could reach it was a retried commit after a partial one, which is now refused in front of it, so it is back to meaning "the engine has lost count".

**The test seam.** `PartialCommitTest.FailingCommitDevice` is an in-memory device whose commit and whose prepare each fail once when told to, registered into the running engine at run time through the public `Catalog.ClassLoader.Classes` list - the same seam `TransactionBeginTest.FailingBeginDevice` already used to make a *begin* fail. No new library and no change to shipped code.

## Tests

Four cases in `tests/DAE.Server.Tests/PartialCommitTest.cs`:

| Case | What it pins |
|---|---|
| `TestRollbackAfterAFailedDeviceCommitKeepsTheOuterLevel` | The reproduction of the first defect: the depths after the failed commit (process 2, working device 1, failing device 2) and after the rollback (1, 1, 1), then that the outer commit succeeds and both rows are in the working device's table. |
| `TestARetriedCommitAfterAFailedOneIsRefused` | The reproduction of the second: the retry fails with error 106213 and the three depths are unchanged by the refused call. |
| `TestANestedBeginAfterAFailedCommitIsRefused` | The third face: same error, same unchanged depths. This is what keeps the predicate sound, because a begin on top of a half-committed level makes the level counts stop saying which level a participant holds. |
| `TestACommitThatFailsInItsPrepareStaysRetryable` | The boundary the design rests on: a commit that fails in its prepare phase has committed nothing and is still retryable. A deferred constraint violation is the ordinary way a commit fails, so this is the behaviour that must not change. |

# Review findings

**Read in this order:** the implement diff with no reference to the handoff; then `Schema.DeviceSession` and `RemoteSession`'s `BeginTransaction`/`PrepareTransaction`/`CommitTransaction`/`RollbackTransaction`, to settle what each participant's count means at each moment and whether the new `<=` assertion can fire; then `InternalBeginTransaction`, `InternalPrepareTransaction`, `InternalCommitTransaction` and `InternalRollbackTransaction` as one unit; then `BeginTransactionalCall`/`EndTransactionalCall` and `ServerTransactions.EndTransaction`, which are the paths that reach those four without a client asking; then the test fixture; then the handoff.

## Major: the hole the two refusals leave, filed

The two refusals sit at the points a transaction level is **begun** or **ended**. An ordinary statement does neither, so a session may still run statements in a transaction whose commit failed part-way - and the places that already committed are a level shallower, so each participant files the new work against whatever level it holds innermost: the failed level on the ones that did not commit, the **enclosing** level on the ones that did. One statement's work is then split, and the rollback keeps half of it.

Reproduced on the fixture's own seam, 2026-11-23. Two levels deep with the inner commit failed on the second device, then `insert row { 3 ID } into GoodTable; insert row { 3 ID } into FailTable;`: immediately afterwards the session held 2 levels, the working device 1 and the failing device 2 - the statement's two inserts went to different levels. Rolling back the failed level and committing the enclosing one left `GoodTable` with rows 1, 2 and 3 and `FailTable` with only row 1. The statement's row survived on one device and was gone from the other, permanently, with no error and nothing in the log.

Climbed the ladder rather than filing the instance: the root is one invariant - **a level whose commit has begun asking participants to commit accepts no new work, only a rollback** - and the engine already records exactly that state on `CommitBegun` and already refuses two operations on it. Filed as `tickets/fix/bug-work-after-a-half-committed-level-is-torn.md`, with a second arm at the same site (a deferred-handler transaction that half-commits leaves the enclosing commit retryable, so a retry re-applies every handler on the participants that already have its work - read from `ServerTransaction.InvokeDeferredHandlers`, not run).

Not fixed inline, and not for want of a one-line check: the fix has a real decision in it. The D4 statement `rollback transaction;` runs through `BeginTransactionalCall` like any other statement, so a refusal placed at the statement boundary would leave a session that drives transactions from D4 with no way out at all. That is research, which is what `fix/` is for; the ticket states the question and the cases that must keep working.

The site-claim grep over `tickets/backlog`, `tickets/fix`, `tickets/plan`, `tickets/implement` and `tickets/review` found `ServerProcess.cs` named by `debt-realsql-coverage` and `debt-remote-session-lazy-enlistment`; neither touches this theme, so the ticket is fresh rather than an arm on an existing one.

## Minor, fixed in this pass

- **`TestACommitThatFailsInItsPrepareStaysRetryable` discarded the exception it caught**, so the case would have passed on any failure at all - including one that had committed something, which is the opposite of what it claims. It now asserts the device's prepare-failure message, which also makes the already-declared `FailingCommitDeviceSession.PrepareFailureMessage` load-bearing rather than decorative.
- **The fail-on-command flags outlive a case that fails before using them.** They live on the device, which is server-wide and fixture-lifetime, and each clears itself only when the phase it arms actually runs; a case that failed earlier would leave one armed and the *next* case would fail inside its `[SetUp]`'s implicit commit, nowhere near the cause. Added `[TearDown] DisarmTheFailingDevice`. (The base `InProcessTestFixture` already gives each case a fresh session and process, so leftover *transactions* do not leak - checked.)
- **The seam was discoverable from only one side.** The handoff said both failing-device doubles name each other; only the new one did. Added the reciprocal one-line summary to `TransactionBeginTest.FailingBeginDevice`.
- **Two wrong counts in the `K40` plan row**: "one override" (the device has two, commit and prepare) and "three cases" (there are four). Corrected, and the fourth case's purpose stated.
- **`CommitBegun`'s `NOTE:` overstated what the fix contains.** It said the damage "stops at this level"; the major finding above shows new work inside that level is still torn. The paragraph now says what is and is not stopped and names the ticket.
- **The migration note's guidance column said only "roll back after a commit that fails".** It now says to roll back as the *next* call and not to run further statements in that transaction first, with the reason - which is the one thing an application author can act on while the filed ticket is open.

## Checked and clean

- **The new `<=` assertion cannot fire on any audited path**, re-derived rather than taken on trust. A participant can only be *at or below* the process's depth because every level is begun on every participant and only by the process: a grep for `.BeginTransaction(` over `src` and `libraries` gives participant begins at exactly four sites, all in `ServerProcess.cs` (the catch-up loops in `DeviceConnect` and `RemoteConnect`, both of which stop at `_transactions.Count`, and the remote and device loops of `InternalBeginTransaction`). Both kinds increment only on success - `Schema.DeviceSession.BeginTransaction` pushes the level then removes it again if `InternalBeginTransaction` throws, `RemoteSession.BeginTransaction` increments after its internal begin returns - and both decrement in a `finally` on commit and rollback. `Error.AssertFail` is unconditional, not `[Conditional("DEBUG")]`, so this would throw in Release too; that is correct for an internal-error guard, and it sits inside `InternalRollbackTransaction`'s per-participant `try`/`catch`, which logs and continues rather than abandoning the other participants.
- **The catalog arm, the one the handoff could only read.** Followed it to the end: `ServerTransactions.EndTransaction(true)` calls `DeleteCheckTableChecks` *before* `RemoveAt`, so a throw there leaves the level on the process's stack with every participant already a level shallower. The rollback then correctly ends it on nobody and pops, and a retried commit is refused. This is the strongest case for the fix and the one the old `InTransaction` guard got most wrong - it would have rolled back the enclosing level on *every* participant. Still not reproduced, since it needs `DeleteCheckTableChecks` to fail and that needs a seam in the check-table deletion, so the plan row's "static" marking is right.
- **The deliberate ordering of `CommitBegun = true`.** `ServerTransaction.InvokeDeferredHandlers` begins and commits a nested transaction from *inside* `InternalPrepareTransaction`, so a flag set before the prepare is seen by the prepare's own nested begin and refuses every ordinary commit - which is what the handoff measured. Confirmed from the call graph rather than re-measured, and `TransactionBeginTest.TestDeferredHandlerBeginFails` still passes.
- **The paths that end a level without a client asking.** `EndTransactionalCall`'s implicit-commit loop rolls back rather than retrying when a commit fails, and its `StopError` loop unwinds every level; at each level the predicate asks the right question, and the counts converge as the process pops (worked through by hand for the two-level partial-commit state). `ServerProcess`'s disposal, `while (InTransaction) RollbackTransaction()`, goes through the same predicate. `BeginTransactionalCall` clears `Prepared` but not `CommitBegun`, which is why the refusal had to go before the `Prepared` test.
- **The deferred device stop, which runs while `CommitBegun` is set.** Re-ran the audit: the four `InternalStop` overrides are the memory, catalog, Frontend and Simple devices, and none of the four files mentions `BeginTransaction` at all, so nothing in the stop path can hit the new refusal. `DeferredDeviceStopTest` passes unchanged.
- **Compatibility surfaces.** No D4 semantics, operator signature, registered class name, assembly name, file format, WCF contract or port changed. Error 106213 is an addition inside an existing prefix range, and `docs/reference/error-codes.md` lists prefixes only. `ServerTransaction.CommitBegun` is a new public property whose getter and setter match the shape of `Prepared` and `InRollback` beside it; nothing existing can notice an addition, so it gets no migration-notes entry of its own.
- **`ServerCatalogDeviceSession.StoreHasEndingLevel` is not duplication to collapse.** It asks the same question one layer down, of the catalog *store's* connection rather than of a device session, and `CheckStoreTransactionLevels` is the assertion the new one is modelled on. Two layers, two objects; leaving them separate is right.

## Considered and not filed

- **The half-applied level itself.** A failed commit still leaves the level applied on the participants that committed it, and nothing can undo them without a two-phase recovery record the engine does not write. That is an architectural limit rather than a defect in the fix, it is parked as a `NOTE:` in `CommitBegun`'s remarks at its own site, and making a distributed commit recoverable is a much larger piece of work. Left as the implement ticket's tripwire, with the correction above.
- **The predicate's dependence on full enlistment.** Comparing a participant's level count against the process's depth is sound only while every participant is enlisted at every level, and `debt-remote-session-lazy-enlistment` (in `plan/`, with an owner decision already recorded) would deliberately break that. The `NOTE:` saying so sits on the shared body, so that plan ticket has one place to change instead of three guards. Correct as parked; nothing added.
- **No case has both a remote session and a device session in one transaction.** Both kinds are covered separately - devices here, a connection to another Dataphor server in `ConnectionTransactionLevelTest.TestRollbackAfterAFailedRemoteCommitKeepsTheOuterLevel` - and a combined case would evaluate the same two expressions once more against the same two counts. Judged not to pay for itself rather than left by accident.
- **The two failing-device doubles share about ten lines of registration boilerplate.** Two instances of a small, obvious shape, in two fixtures, now cross-referenced from both sides; below the bar for either a ticket or a `NOTE:`. If a third fixture needs one, that is the moment to extract it.
