## What was wrong, in one paragraph

A *server link* is a D4 object naming another Dataphor server: its metadata says how to reach that server, and its *link users* say which remote account and password a given local user connects with. Six link user operators and `alter server` changed those in the running server's memory and in the saved catalog, but recorded no *undo instruction* - the record a session keeps of each in-memory catalog change inside a transaction, which a rollback replays backwards. So a rolled-back change was undone in the store (by the store's own transaction) and kept in memory. From then until a restart, the server used settings or credentials its own catalog did not contain. Two further consequences of the same missing records: the rollback concluded no catalog change had been made at all, so it never ran `InvalidateCachesAfterUndo`, and a nested rollback had nothing to undo for its own level either.

## What changed

**`src/engine/DAE/Device.Catalog/CatalogDeviceSession.cs`** - five new `DDLInstruction` classes in the *Instructions* region, inside the existing `#if LOGDDLINSTRUCTIONS` and after `SetCatalogObjectOwnerInstruction`, and a new `#region Server link` after `#region Device user` holding six public methods:

- `ResolveServerLinkUser(serverLink, userID)` - the mapping for a local user, or `SchemaException.Codes.ServerLinkUserNotFound` (113151) if it has none.
- `CreateServerLinkUser`, `DropServerLinkUser`, `SetServerLinkUserID`, `SetServerLinkUserPassword` - each changes `serverLink.Users` and then records its instruction under the file's standard `(!ServerProcess.InLoadingContext()) && ServerProcess.InTransaction` guard. `DropServerLinkUserInstruction` puts the removed `ServerLinkUser` *instance* back, not a copy, so instructions recorded earlier for the same mapping undo onto that same object.
- `ApplyServerLinkMetaData(serverLink)` - records the seven settings `ApplyMetaData` derives (`HostName`, `InstanceName`, `OverridePortNumber`, `UseSecureConnection`, `OverrideListenerPortNumber`, `UseSecureListenerConnection`, `UseSessionInfo`), then does `ResetServerLink()` + `ApplyMetaData()`. Its undo puts the *recorded values* back rather than recomputing from the link's metadata, because instructions are undone in reverse order: it runs before the `AlterMetaDataInstruction` that the same statement recorded restores the metadata, so a recomputation would read the metadata the rolled-back statement left in place. That ordering trap is stated in a comment on the instruction's `Undo`. The review stage moved the recording to before the change; see *Review findings*.

None of the new methods takes `lock (Catalog)` and none calls `UpdateCatalogObject`; the callers still do that, as they did before, keeping the existing order of memory, then store, then the connection close, and keeping the comments at `UpdateCatalogObject` that explain why the close is last. The cache-then-store order is forced here (the opposite of what `bug-set-object-owner-rollback-keeps-owner` could do): the store holds the link's own create script, which carries its link users, so the cache has to hold the new mapping before the store can be given the text for it. A remark on `CreateServerLinkUser` records that, and that a failed store write inside a transaction is put back by the instruction just recorded.

**`src/engine/DAE/Runtime.Instructions/SystemNodes.cs`** - the six operators (`CreateServerLinkUser`, `CreateServerLinkUserWithEncryptedPassword`, `SetServerLinkUserID`, `SetServerLinkUserPassword`, `ChangeServerLinkUserPassword`, `DropServerLinkUser`) now call the new methods instead of touching `serverLink.Users`. `ChangeServerLinkUserPassword` keeps its old-password check, reading the mapping through `ResolveServerLinkUser` first. `DropServerLinkUser` keeps its accepted-tradeoff `NOTE:` where it is.

**`src/engine/DAE/Runtime.Instructions/DDLNodes.cs`** - `AlterServerNode.InternalExecute` calls `ApplyServerLinkMetaData` in place of its `ResetServerLink()` / `ApplyMetaData()` pair; the comment about why the connection close comes last is untouched.

**`docs/migration-notes.md`** - one row under *D4, catalog and libraries* (after the `bug-server-link-user-change-keeps-old-connection` row, which it was read against and does not contradict: connection handling on rollback is unchanged, and the new row says so) and one under *Custom C# extensions* (the six new public members, and the error-code change below).

## The wart at the same site: fixed, with one deviation from the ticket

`SetServerLinkUserID`, `SetServerLinkUserPassword` and `ChangeServerLinkUserPassword` indexed `serverLink.Users[userID]` with no presence check, so an unmapped user id produced a bare `KeyNotFoundException` out of a D4 operator. All three now raise `ServerLinkUserNotFound` (113151) - the error `DropServerLinkUser` already raised. No new error code, no operator signature changed; it is in the migration note because an application could notice it.

**Deviation:** the ticket said to keep `DropServerLinkUser`'s not-found error where it is, in the node. It is now raised by the session's `DropServerLinkUser` instead, so all four operators raise it from one site rather than the node duplicating a check the session method already makes. Same error code, same message argument, still raised before anything is changed and after the node's `CheckAuthorized`. The node carries a one-line comment saying where it comes from. Accepted in review.

| `TestFailedAlterKeepsTheOldSettings` | added in review: an `alter server` that fails part-way on a tag value it cannot convert leaves the link's settings as they were |
| `TestNestedRollbackKeepsTheOuterChange` | an inner rollback undoes its own level only: the outer level's `CreateServerLinkUser` survives it, and is itself undone by the outer rollback |

The first seven fail at `84cce108` (confirmed before the fix: the four link user cases and the nested case with the rolled-back value still in place, the alter case with `elsewhere` for `localhost`, the not-found case with `KeyNotFoundException`) and pass after it; the review case fails at the implement commit and passes after the review's fix.

The rollback assertions read through D4 wherever the value is readable there (`ServerLinkUserExists`, `System.ServerLinkUsers`, `System.ServerLinks`), which is the lowest layer that shows the behaviour; only the password case reaches into the in-memory object, because nothing exposes it.

## Known gaps

- **A connection opened inside the rolled-back transaction is kept, with the credential the transaction set.** `_deferredRemoteSessionCloses.Rollback` discards the deferred close, and nothing closes the connection the rolled-back credential opened; that process's next use of the link reuses it. It did not turn out to be a one-liner: the undo would have to ask for a close during the rollback, which is the one moment the deferred-close machinery is draining, so it is a separate decision - whether a rollback should close such a connection at all, and if so where in the rollback sequence. Not filed as a ticket; the migration note's new row states the behaviour plainly ("including a connection the rolled-back transaction itself opened with the credential it set") so it is not a silent surprise.
- **Nothing is undone when no transaction is open** - these methods record only when `ServerProcess.InTransaction`, like every other logged DDL change in the file. In practice that is narrower than it sounds: every D4 statement runs inside an implicit transaction unless the process has turned implicit transactions off, so a statement that fails is undone. Measured in review by `TestFailedAlterKeepsTheOldSettings`, which opens no transaction of its own.
- **No locking was added around `serverLink.Users`.** Nothing locked it before, and `CatalogDevice.PopulateServerLinkUsers` enumerates `serverLink.Users.Values` to serve the catalog table `System.ServerLinkUsers`, so a read of that table concurrent with a link user change can throw a collection-modified error. Entirely pre-existing, at a site this ticket does not otherwise change, and a fix there owes a reproduction of a race that is not local to write - so it is parked as a `NOTE:` tripwire immediately above `PopulateServerLinkUsers` in `src/engine/DAE/Device.Catalog/CatalogDevice.cs`, in the same form as the pre-existing `NOTE:` a few lines below it that parks the identical question for `System.RemoteSessions`.
- The new in-memory values are visible to other sessions before the change commits, like every other in-memory DDL change.
- `CreateServerNode` still calls `ApplyMetaData()` directly on a brand-new link and was deliberately left alone: a rollback of the create removes the whole object through `DropCatalogObjectInstruction`, so there is nothing for a settings undo to restore.
- **The class behind this bug is already tracked.** `tickets/plan/debt-rollback-leaves-catalog-as-it-was.md` proposes the general test ("script the catalog, run a statement in a transaction, roll it back, script again, require the scripts identical") and names this ticket as its `prereq:`; it already lists both arms fixed here as its evidence, so nothing new was filed for the class. Its nested-rollback and cache-invalidation points are the same two this ticket's `TestNestedRollbackKeepsTheOuterChange` covers for the server link arm only.

## Review findings

Read the `ticket(implement): bug-server-link-user-change-survives-rollback` diff before the handoff, then the surrounding code: the *Instructions* and *Transactions* regions of `CatalogDeviceSession.cs` (the replay loop, `undidDDL`, `InvalidateCachesAfterUndo`, `UpdateCatalogObject`, `CloseRemoteSession`), `Schema/ServerLink.cs`, `Base/BaseList.cs` (`HashtableList`), the six operator nodes in `SystemNodes.cs`, `AlterServerNode` and `CreateServerNode` in `DDLNodes.cs`, `PopulateServerLinks` / `PopulateServerLinkUsers` in `CatalogDevice.cs`, and the `ServerLinks` / `ServerLinkUsers` declarations in `Schema/SystemCatalog.d4`.

**One defect found and fixed, with its reproduction.** `ApplyServerLinkMetaData` constructed its undo instruction before the change but *added it to the log after* - so when `ApplyMetaData` threw part-way, the log got nothing and the half-applied settings stood. It throws on a tag value it cannot convert (`Convert.ToInt32`, `Convert.ToBoolean`), and `ResetServerLink()` has already cleared four of the seven settings by then. Reproduced before the fix: `alter server L alter tags { alter OverridePortNumber = "not a number" }` on a link created with port 1 left `System.ServerLinks` reporting port 0 while the catalog still said 1 - the ticket's own bug, in the failure path of the statement the ticket fixes. Fixed by recording the instruction before the change, which is what `AlterMetaData` already does four hundred lines above; the local and the second `#if LOGDDLINSTRUCTIONS` block go away with it. New case `TestFailedAlterKeepsTheOldSettings`, which fails `Expected: 1 But was: 0` against the implement commit and passes after the fix.

That case also measures something the handoff had the other way round. It uses **no explicit transaction**, and the half-applied change is still undone - because every D4 statement runs inside an implicit transaction (`ServerProcess.UseImplicitTransactions`, on by default; the comment at `ServerProcess.UseDTC` states it), so `ServerProcess.InTransaction` is true while a statement runs and these changes are always recorded. "Nothing is undone outside a transaction" holds only for a process with implicit transactions turned off; the known-gaps entry above is corrected to say so.

**Undo correctness, checked by reading every order the five instructions can be replayed in.** All four interleavings of create / drop / set for one mapping undo to the right end state, because `DropServerLinkUserInstruction` puts the removed instance back rather than a copy - a `SetServerLinkUserID` recorded earlier then undoes onto the live object. `ApplyServerLinkMetaDataInstruction` restores all seven settings rather than leaning on `ResetServerLink`, which resets only four, and restores recorded values rather than recomputing, which is right because it is replayed before the `AlterMetaDataInstruction` of the same statement. `SetServerLinkUserID` changes the remote account and never the dictionary key, so no recorded instruction is left pointing at a key that moved. A rolled-back `create server` with link users undoes user-then-object; a rolled-back `drop server` restores the object instance with its `Users` intact. Nothing else found.

**The ticket's stated deviation is accepted.** `DropServerLinkUser`'s not-found error now comes from the session method rather than the node: same code (113151, `SchemaException.cs:165`), same argument, still raised before anything changes and after the node's `CheckAuthorized`, and all four operators that need it raise it from one site instead of one node duplicating a check the session method makes anyway. Putting the check back in the node would re-introduce the duplication the move removed.

**Docs.** Both migration-notes rows were read against the code and against the `bug-server-link-user-change-keeps-old-connection` row above them; they match and do not contradict it. One clause was added to the *D4, catalog and libraries* row for the defect fixed in review (a failed `alter server` no longer leaves the link's settings cleared) - an application could notice that, and it belongs in the row that already owns the subject rather than in a row of its own. No other document needed changing: `docs/architecture.md` does not describe the catalog undo log, and the plan's *Known defects* table is a catalogue of defects found while porting rather than a log of fixes - the sibling `bug-set-object-owner-rollback-keeps-owner` added no row to it either.

**Tests: one added, none cut.** The seven from the implement stage each pin a distinct instruction class or a distinct level semantic, each was reported failing against `84cce108`, and none restates the implementation or verifies a mock; the overlap between `TestRolledBackCreateLeavesNoUser` and the nested case's closing assertion is worth keeping, because cutting the simple case would leave the create undo covered only inside the nested-rollback machinery. The eighth is the reproduction above. Assertions go through D4 wherever the value is readable there; the one that reaches into the in-memory link is the password, which `System.ServerLinkUsers` deliberately does not expose. Worth knowing for the next reader of that table: its column `User_ID` is the local user and its column `UserID` is the remote account, which is why the `LinkUserID` helper selects `UserID`.

**Checked and found nothing, with the reason:**

- *Error handling.* Each of the four link user methods either cannot throw after its mutation or resolves before it; `UpdateCatalogObject` is still called by the nodes after the cache change, which the store's create script for the link forces.
- *Locking.* None of the new methods takes the catalog lock, which is required rather than an omission: `UpdateCatalogObject` makes a network call to the other server and no caller may hold that lock across it. The remarks in the new region say so.
- *Resource cleanup, type safety.* Nothing in the change allocates a disposable or widens a type; the instructions hold the link, the mapping and primitives.
- *DRY and source hygiene.* The five instruction classes and the four guarded recordings repeat the shape of the forty-odd that precede them in the file, which is the right call over inventing a local idiom. `CatalogDeviceSession.cs` is 4116 lines (`wc -l`) - large, but `AGENTS.md` sets no size rule and no split ticket is open against it, so nothing was filed. Comments in the new code state constraints and consequences rather than narrating statements. Tabs, CRLF and byte-order-mark state preserved in the three files this pass edited, checked at byte level (no lone LF, byte-order mark unchanged); the trailing-whitespace reports from `git diff --check` are this repository's CR artifact, which the implement commit produces 222 of.
- *The known gaps* stand as listed above. The unlocked `serverLink.Users` tripwire was challenged and kept: a fix there owes a reproduction of a race that is not local to write, and the site is otherwise untouched by this ticket.

**No tickets filed and no new tripwires.** The class behind the ticket is already `tickets/plan/debt-rollback-leaves-catalog-as-it-was.md`, which names this ticket as its `prereq:` and already lists both arms as evidence; the defect found in review is a third instance of that class at a site this ticket owns, so it was fixed rather than filed. Site-claim grep over `tickets/{backlog,fix,plan,implement,review}` for `CatalogDeviceSession.cs` and `ServerLink` returned that ticket plus `bug-dead-remote-session-blocks-every-statement` and `bug-object-id-counter-is-process-wide`, neither of which touches this code. Nothing conditional turned up that needed parking.
