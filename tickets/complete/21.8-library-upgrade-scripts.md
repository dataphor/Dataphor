This work item ran in two passes. The first (`debt-library-upgrades-coverage`, 2026-11-23) wrote the mechanism down in [docs/architecture/libraries-and-class-loading.md](../../docs/architecture/libraries-and-class-loading.md) and added the nine-section `LibraryUpgrades` coverage script, and named three gaps it could not reach from a script. `ticket(implement): library-upgrade-scripts` closed all three.

**A new C# fixture, `tests/DAE.Server.Tests/LibraryUpgradeRestartTest.cs` (3 cases, about 14 s).** Each case takes a `TestServerInstance` of its own, has the server create and register a library at 1.0.0, saves an upgrade script for 1.0.1 at an explicit version (which moves neither version number), stops the server, raises the library's **descriptor** version in the `.d4l` on disk, starts the server again, and upgrades. The descriptor is rewritten through the engine's own BOP deserializer and serializer rather than as text, so the fixture pins no idea of the descriptor format of its own; that is the honest stand-in for an installer unpacking a new release over the old folder, because the *files* are what claims the new version.

**The first case is the premise the whole coverage script rests on.** A D4 script cannot produce a pending upgrade honestly, so every section of `LibraryUpgrades.d4` stands in for "the new files arrived and the server was restarted" with an `update LibraryVersions`. What makes that legitimate is one line of `LibraryUtility.LoadLibrary`, which reads the recorded version before loading and writes *the same value* back afterwards so a restart does not swallow a pending upgrade. Nothing pinned it. The case asserts, after the restart, that the descriptor version is 1.0.1, that the recorded version is **still** 1.0.0, that an upgrade is required, and that the library is still registered - and then that the upgrade applies and records 1.0.1.

**Two cases carry a payload a release really ships**, rather than the one table in the default memory device that every section of the script uses: a **device with a table in it** (created inside the single transaction the upgrade machinery opened - the row reading back afterwards is what says the device started), and a **form document** through the Frontend device, asserted to exist, to load back character for character, and to be a file at `<library folder>\Documents\PayloadForm.dfd`, which is the second reason this fixture is C# - a script has no way to see a server-side path.

**A tenth section in `LibraryUpgrades.d4`** for `UpgradeLibraries()` across several libraries: two independent pending libraries, the first one's upgrade raising. It pins what an administrator is told about a half-finished server upgrade - the error carries the failing script's own message and does **not** name the second library, which stayed at its recorded version, still reports an upgrade as required, and whose table the upgrade would have created does not exist.

**Documentation.** The architecture page gained a sentence on the restart preservation being pinned and a short paragraph on what a new version's payload may be and the one thing a restart cannot pick up. The plan's WS7 row is marked Done and says which gaps closed and what stays open. No `docs/migration-notes.md` entry is owed: nothing an application, a deployment script or a C# extension could notice changed.

## The gap left open deliberately

**An upgrade whose payload needs a new build of the library's own assembly.** Assemblies are never unloaded, and `Assembly.LoadFrom` on another copy with the same identity returns the instance already loaded, so a `Server.Stop()`/`Start()` in one process goes on running the old build - a real deployment picks up a new one because the installer restarts the Windows service, not because the `Server` object restarted. An in-process case over it would look like coverage and prove nothing. The narrower case (a version that *adds* an assembly where the old version had none) would work but has no assembly in the suite to give it without repointing the process-wide assembly-resolver entry for a library that other fixtures register, which would make those fixtures depend on test order.

Review weighed filing this as a `debt-` ticket and **did not file it** - see the findings below. It is recorded as a tripwire at the fixture, naming the condition and the vehicle.

## Review findings

The implement diff was read before the handoff, then every claim in it was checked against the engine source, and the fixture's central claim was re-measured independently.

**Independently re-measured: the fixture is sensitive, and to the right thing.** The one line the premise rests on (`LibraryUtility.LoadLibrary`'s closing `SetCurrentLibraryVersion(library.Name, currentVersion)`) was changed to record `library.Version` instead, rebuilt, and the three cases run. All three fail, and each fails at the assertion that should catch it: the first on the recorded version (`Expected: "1.0.0.*" / But was: "1.0.1.*"`), the two payload cases on their `UpgradeRequired` guard. The probe was then reverted and the file confirmed byte-identical to `HEAD`. That also answers the handoff's question about whether the `UpgradeRequired` guard duplicated across the payload cases is worth keeping: **yes** - without it those two would have failed on a missing table and a missing document, which points at the payload rather than at the premise that actually broke. Kept in all three.

**Fixed in this pass (three findings, all minor).**

- **A remark that stated an engine behaviour wrongly.** The fixture's remarks said `SetLibraryDescriptor` "refuses to raise a registered library's version at all, and the descriptor bump it does make for an unregistered one carries the recorded version along with it". The first half is right (`CannotChangeRegisteredLibraryVersion`, in `SystemSetLibraryDescriptorNode.SetLibraryDescriptor`), the second is backwards: for an **unregistered** library `IsLoadedLibrary` is false, so no recorded version is written at all. What actually makes the bump useless as a stand-in is that `GetCurrentLibraryVersion` returns the *descriptor* version when there is no `LibraryVersions` row, so registering the library afterwards records whatever the descriptor then says and nothing is pending. Reworded to say that. A wrong "why" in a long remark block is worse than none - the next reader believes it.
- **A dated mutation measurement in an architecture page.** The page said the fixture "is sensitive rather than decorative: making the load record the descriptor version instead fails all three of its cases (measured 2026-11-25)". That is provenance about test quality, not architecture: the date and the case count both go stale, and it was the only dated measurement of its kind in the thirteen-page set (every other fixture reference there - `ContractParityTest`, `AbandonedClientProcessTest`, `DeviceTranslationGoldenTests` - says what the test pins and how, and nothing about how it was validated). Replaced with what the fixture actually does, which is the information a reader of that page needs. The measurement itself lives in this ticket and in the fixture's own remarks, which is where provenance belongs.
- **The coverage section's dependence on registration order was stated as a fact, not as an assumption.** The new section's comment said the two independent libraries are visited in registration order but not that nothing specifies that. `UpgradeLibraries()` enumerates `Catalog.LoadedLibraries`, which is `BaseObjects<T>` - array-backed, hence insertion-ordered - so the order holds, but by implementation rather than by contract. The comment now says so, and says that a change there makes the section fail loudly on the second library having been upgraded rather than quietly cover nothing. (Alphabetical order happens to agree here, so the section is doubly safe; that is luck and is not relied on.)

**Checked and left alone, with the reason.**

- **Whether the first case's negative assertion is the right one**, which the handoff asked. Right as it stands. Asserting only `UpgradeRequired` would be weaker, because that flag is derived from the two versions and a start that moved both would still satisfy it; the mutation run shows the current framing failing precisely on the recorded version while `UpgradeRequired` and the descriptor assertion are unaffected.
- **Whether `Frontend.LoadDocument` round-tripping the form character for character is a property of the device or an accident of the string**, also asked. A property of the device: `FrontendDevice.SaveDocument` is a bare `StreamWriter.Write` of the string into `Documents\<name>.<type>` and `LoadDocument` a bare `StreamReader.ReadToEnd` of the same file. No XML parse, no re-emit, nothing that could normalise attribute quoting. The assertion is sound for any string.
- **The `.d4l` round trip through `LoadFromStream` + `SaveToFile`.** `LoadFromStream` does not set `Name` (production's `LoadFromFile` sets it from the filename afterwards), but the `.d4l` carries `name=` as a serialized property, so the deserializer supplies it and the round trip is faithful. This is also the path the engine itself takes whenever it rewrites a descriptor, so its fidelity is something production already depends on. Nothing added.
- **Whether case 2 proves more than it claims.** It does not overclaim: it says the row reading back is what says the device *started*, not that the device committed transactionally. Memory-device transaction behaviour is a separate open question (`debt-memory-device-transaction-isolation`) and the case stays clear of it.
- **The `Could not delete ...` lines naming `Alphora.Dataphor.Frontend.Server.dll` and `Alphora.Dataphor.DAE.Connection.dll`.** Documented suite behaviour for any instance carrying a library with an assembly (`AGENTS.md`, under the test-run description), not new and not a leak. The fixture's remarks already note the related `DATAPHOR_TEST_LOGGING=1` difference. Nothing added.
- **The 3.1-era guides that talk about upgrades** - `docs/users-guide/dataphoria-libraries.md` (*Upgrading Libraries*) and `docs/developers-guide/working-with-libraries.md` - were read, because the review brief treats docs as out of date until checked. Both already describe the loaded-version-from-catalog behaviour this ticket pinned, and nothing in them became wrong. No edit.
- **Fixture size and style.** 292 lines, tabs, CRLF, no byte-order mark, matching `LibraryAttachTest.cs` beside it; the `var LInjected : VersionNumber := ...` idiom in the new script section matches the five sections above it. No hygiene finding.

**One finding declined rather than filed: the assembly gap.** The handoff asked the reviewer to weigh it as a `debt-` ticket and it does not clear the filing bar. It names no defect - nothing is known to be broken - and no class-level invariant; it is a coverage wish whose cost (a test library assembly of its own, meaning a new project, an entry in the layout's library list and one on the coverage report's areas, **plus** a harness that restarts a host process and reloads its libraries, which nothing in the suite does) is known while its benefit is one branch of library loading that `LibraryLoadingTest` already covers from the other side. Nor is it an arm of an existing ticket: `debt-test-shipped-host-executable` is about launching the shipped executable at all, and its own `tradeoffs:` line argues against widening it. So it is recorded where a future reader meets it, as a greppable `NOTE:` at `LibraryUpgradeRestartTest`, naming the condition that makes it worth doing (the suite growing a host restart), the vehicle (`OutOfProcessInstance`), and the work item that would reach it first. The paragraph the implement stage had put in `<remarks>` was moved into that `NOTE:` rather than duplicated - conditional knowledge belongs in the greppable set.

**Nothing blocked, nothing filed.** Everything the review found was minor and is fixed above; the one major-shaped finding was conditional and is parked as the tripwire described.
