## What landed

`DAEServer.exe` and `DAEService.exe` are one program under two names. `DataphorHost` in `src/hosts/Host` (assembly `Alphora.Dataphor.DAE.Host`) owns the process: it parses the command line once (`HostCommandLine`), registers or removes the Windows service through `ServiceUtility`, or builds and runs a .NET Generic Host around a `DataphorServiceHost`. Each executable is now a single `Main` that calls `DataphorHost.Run(args)`, so a 3.1 script and an existing service registration both keep working. Both projects are SDK-style, both are in `Dataphor.slnx` and in the runtime layout, and `artifacts/layout/<config>/bin/` holds a runnable server for the first time.

`UseWindowsService` is the whole of "the same executable runs as a Windows service": it replaces the host lifetime only when the service control manager really started the process, so there is one code path and `-r` is an alias for running. A console session is stopped with Ctrl+C; the old `Console.ReadLine()` is gone. The host's own logger carries host lifecycle only - starting, started, the listener state, stopping, stopped, failures - to a single-line console writer or to the event log the server already uses; the server's own log file and event-log writes are untouched.

Changes outside the hosting code: `PathUtility.GetInstallationDirectory()` no longer pops a second level for a binaries folder named `bin` (the 3.1 per-project output shape that no longer exists, and the pop put the runtime layout's default library directory one level too high); `src/engine/Server/Server.csproj` took `<FrameworkReference Include="Microsoft.AspNetCore.App" />` and dropped the now-prunable `System.Diagnostics.EventLog` package, which takes the audit-flagged ASP.NET Core 2.3.10 assemblies out of the layout's `bin/` (the choice `protocol-corewcf-host` left open); `Directory.Build.targets` now contributes an executable project's application host, `.deps.json` and `.runtimeconfig.json` to the layout (never `.runtimeconfig.dev.json`); and `ConnectionManager`'s idle watcher thread became a background thread. Deleted: `src/hosts/DAEServer/CommandLineArguments.cs` (K23's copy there, which nothing in the project called) and both `app.config` files (the service's being K12's other half).

The implement-stage commit `ticket(implement): host-generic-host` has the detail, including the one deviation from the implement ticket - `BuildHost` takes a delegate that *starts* the server rather than only creating it, because the parameterless `DataphorServiceHost.Start()` writes the machine-wide instance list and a test must not - and the smaller judgment calls (the string-table entries, the message templates in code, the single-line console writer, `[SupportedOSPlatform("windows")]`, the users-guide rewrite).

Then every document the change touched, and `tools/net-spike/run.py` and `projects.txt`, which the handoff's spike claims rest on.

**Verified by running.** `dotnet build Dataphor.slnx` 0 errors and 143 warnings, the same count the implement run reports. The suite in the three parts `AGENTS.md` prescribes: part 1 413 + 13 passed, part 2 67 passed / 11 skipped, part 3 48 passed / 14 skipped, 0 failures - the handoff's numbers exactly, so nothing here moved them and no pre-existing failure surfaced (`tickets/.pre-existing-error.md` not written). `python tools/docs-link-check/check_links.py` reports 203 errors, all of them K17's recorded set, none in a file this work touched.

**Two behaviours of the Generic Host were measured**, because two comments in the diff rest on them and both turned out to be wrong. A scratch console application on `Microsoft.Extensions.Hosting` 10.0.15 / `net10.0`, one hosted service, `ClearProviders` plus a console writer at minimum level Information, exactly as the program configures it:

- A hosted service whose `StopAsync` throws: the exception reaches the caller of the host's own `StopAsync` unchanged, and **nothing at all is logged** - the host logs a shutdown exception only at Debug level, which this program's minimum level does not pass.
- `HostOptions.ShutdownTimeout` set to 1 second against a `StopAsync` that blocks for 5 seconds synchronously: the call returned after 5,034 ms with the cancellation token observed as cancelled. The bound does not abandon a stop in progress.

**Fixed in this pass** (all minor; no behaviour of the product changes except the one new log line):

- **A failure to stop the server was reported nowhere.** `DataphorHostedService.StopAsync` let it out unlogged and `RunServer` swallowed it on the stated grounds that it had "already been reported twice" - true of the start path only. An operator would have seen `… is stopping.` and then nothing at all, with exit code 1 and no cause. `StopAsync` now logs the failure with the instance name and rethrows, symmetric with its start path, and `RunServer`'s comment says what is actually true. Root cause named at the one site; the old `Service.OnStop` did log such a failure to the event log, so this was a regression in observability, not a new gap.
- **`ShutdownTimeout`'s remarks claimed a consequence that cannot happen** ("the process exits with the engine's stop unfinished"). The value is kept at sixty seconds - it is still the deadline of the token the host passes down and, for a Windows service, how long `WindowsServiceLifetime` waits before telling the service control manager the service stopped - but the remarks now say that and no longer promise a bound on a synchronous stop.
- **`ConnectionManager`'s `NOTE:` rested on the same wrong premise.** Re-stated on the real one: `DataphorServiceHost.Stop` can throw before it reaches the `Dispose` that signals the watcher, the host program then exits on that failure, and a foreground thread waiting here would keep the process alive after `Main` returned. The background-thread change itself is right and stays.
- **`AGENTS.md` said the spike "wraps the other 12 of its 33 projects"**; it is 10 now that these two are converted (counted with the spike's own `is_converted` over `projects.txt`: 23 converted, 10 wrapped). The same paragraph still listed "the hosts" among what is unconverted, which the sentence before it contradicts; it now names `D4Runner`, the only host project left.
- **`tools/net-spike/README.md`'s list of projects built in place** gained `DAEServer` and `DAE.Service`; its table row was updated for them but that list was not.

**Parked as a tripwire, not filed** (the handoff asked for a judgment on it): the unexplained observation that a plain socket holding `0.0.0.0:8061` did not stop a host from binding that port. It is a bullet in the plan's *Generic host* "What was measured" list, with one measurement from this pass that narrows it - two plain .NET `TcpListener`s on the same address and port *do* fail with `AddressAlreadyInUse` on this Windows build at `ExclusiveAddressUse`'s default of false, so a shared-address-reuse explanation is out. The product-visible claim ("two instances on one machine") rests on the Kestrel-against-Kestrel measurement `protocol-corewcf-host` recorded, which is unaffected; it is the probe that is in doubt. Revisit condition written at the site: a second instance configured on a port another instance already serves that starts and then serves nothing.

**Considered and deliberately not changed.**

- `HostCommandLine` lowercases with `ToLower()`, so on a Turkish-locale machine `-I`/`-INSTALL` would not match. Both parsers it replaces did the same, so it is not a regression, and the repository spells it that way at 52 sites against 5 invariant ones - changing one of them is noise, and a `NOTE:` at one of 52 identical sites would mislead the next reader about the other 51.
- `BuildHost` being public and taking a delegate that starts the server. The ticket's justification was checked rather than taken: `DataphorServiceHost.Start()` does add a default instance to the machine-wide list and save it, `Start` is not virtual, and the repository has no `InternalsVisibleTo` convention. The deviation is forced and is documented at the parameter. `host-instance-configuration` retires it.
- `AddEventLog` only when the server's event source already exists, so a service's *first* start on a brand-new installation logs a start failure nowhere (the old `Service.LogException` wrote the event log, creating the source). The reason is already written at the site and the alternative is worse - writing to a source that does not exist creates it under this program's name and splits a deployment's event log across two sources. Left as it is.
- `GetDefaultImagePath` always registers `DAEService.exe` from `AppContext.BaseDirectory`, so `DAEServer.exe -i` registers exactly the command line the migration note promises. Established by reading; registering needs elevation, so it is part of the manual check still owed.
- No test for `GetInstallationDirectory`: it reads `AppContext.BaseDirectory`, which a test cannot vary, so there is nothing to characterize at that layer. What it changed was observed from outside, in the handoff's hand-run.

**Tests: none added, none cut.** The implementer's five are the right five - the two command-line cases are the compatibility record for what a script and a service registration may pass, the two lifecycle cases pin that building starts nothing, that starting brings a server up that answers D4 and stopping takes it down, and that a start failure is not swallowed, and the `.deps.json` case catches a failure mode no compiler can see and the handoff's error 115107 proves is real. Neither defect found here is testable at the right layer: the new log line could only be checked by asserting against a mock logger, and making `DataphorServiceHost.Stop()` throw would mean mocking a type this repository owns.

**Checked and clear.** Compatibility surfaces: nothing in the diff touches D4 semantics or operator signatures, a `DAERegister` class name, an assembly name or namespace, a file format, an error code, a WCF contract shape, the default ports or the on-disk instance layout; the service registration's own surface is unchanged and `DAEService.exe` is still the registered binary. The eight new `docs/migration-notes.md` entries were each checked against the code rather than read - the registered command line, the garbage-collection properties in both project files, the rejected switch, the `Service` class's new shape, the `app.config` removals, `GetInstallationDirectory`, and the ASP.NET Core framework reference now reaching anything that references the server assembly. Resource cleanup: `using (host)` on every path, the hosted service clears its reference before stopping, and `DataphorServiceHost.Stop` already captures a host failure and rethrows it only after the engine is stopped. Error paths: a parse failure, a `BuildHost` failure, a start failure and (now) a stop failure each report once and exit 1. Source hygiene: the largest new file is 320 lines, and the comments in it say why rather than what, except the three that said why incorrectly and are fixed above.
