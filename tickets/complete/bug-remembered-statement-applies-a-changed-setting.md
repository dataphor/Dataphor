## What landed

Some D4 objects are backed by a .NET class, and the statement that makes or alters one carries a *class definition*: a class name plus named attributes applied to the live object as properties. A storage device's settings are of that kind — a memory device's `MaxRowCount` row limit, a SQL device's server name. `alter device D alter class { create "MaxRowCount" = "100" }` used to put the statement's own attribute object into the device's live class definition, so the device and the statement shared it; a later `alter … alter "MaxRowCount" = "200"` wrote `200` into that shared object, which was also writing `200` into the first statement. The first statement, run again, applied 200.

The fix is one line: `AlterNode.AlterClassDefinition` (`src/engine/DAE/Runtime.Instructions/DDLNodes.cs:1010`) adds `attributeDefinition.Clone()` rather than the statement's own attribute. Alongside it, six catalog-side `ClassDefinition` setters now store `value == null ? null : (ClassDefinition)value.Clone()` so that the invariant — a catalog object owns its class definition and never shares one with a statement or with another catalog object — holds without each of the compiler's nine assignment sites having to remember: `Schema.DeviceOperator` and `Schema.DeviceScalarType` and `Schema.Device` (`src/engine/DAE/Schema/Device.cs:134`, `:240`, `:658`), `Schema.OperatorBlock` (`Schema/Operator.cs:109`), and `Schema.ScalarType.FromClassDefinition` and `.ClassDefinition` (`Schema/ScalarType.cs:1391`, `:1415`). Each carries a `<remarks>` saying the object owns its definition and that callers mutate it through the getter. `Schema.Object.MetaData` was deliberately left alone, as the implement ticket required.

Two reproductions landed in a new `tests/DAE.Server.Tests/DeviceClassAttributeRerunTest.cs`, covering both ways a client runs one statement twice: the engine's cache of compiled plans, and a plan the caller got from `IServerProcess.PrepareStatement` and executed again. The six device-probing helpers moved out of `DeviceClassAttributeRollbackTest` into a new `DeviceClassAttributeFixture` base that both fixtures derive from. One row was added to `docs/migration-notes.md`.

The implement stage is commit `ticket(implement): bug-remembered-statement-applies-a-changed-setting`. Review changed two comments and filed one finding; nothing in the shipped behaviour changed.

## Review findings

Read the implement diff first, then the handoff. Everything below was checked by reading the code and by running it; the central claim was re-measured by mutation.

### Checked and sound

- **Both new tests genuinely fail without the fix.** Reverted the one-line `.Clone()` at `DDLNodes.cs:1010`, rebuilt, ran the fixture: `TestStatementRunAgainFromThePlanCacheAppliesItsOwnValue` and `TestPreparedPlanExecutedAgainAppliesItsOwnValue` both red with `Expected: 100 / But was: 200`. Restored and rebuilt; the file is byte-identical to the implement commit. Worth re-running rather than trusting, because the whole ticket rests on it — and it also proves the first case really does reach a cached plan, since a recompile from the statement text would have applied 100 either way.
- **The invariant is complete, not partial.** There are exactly six `ClassDefinition` properties on catalog-side types, and all six now clone (the other seven in the tree are on the language statement classes in `Language.D4/Language.cs`, which must keep sharing because that is what the parser builds, plus the `IScalarType` interface declarations whose only implementer is `Schema.ScalarType`). Every one of the twelve `AlterClassDefinition` call sites in `DDLNodes.cs` passes `X.ClassDefinition` read through the getter, so the cloning setter never intercepts an alteration — the mutation still lands on the stored object. And every mutation of a class definition anywhere in `src/` and `libraries/` was enumerated (`Attributes.Add` / `RemoveAt` / `AddRange` / `Clear` / `[name]=` and `ClassName =`): the three loops in `AlterNode.AlterClassDefinition`, the rollback undo in `CatalogDeviceSession.AlterClassDefinitionInstruction`, `ClassDefinition.Clone` itself, and `Engine.cs:760` and `:771`. The last two are the assign-then-mutate pattern a cloning setter breaks, and both mutate through the getter, so both are fine.
- **Rollback still reaches the stored definition.** `AlterClassDefinitionInstruction` takes the live `ClassDefinition` reference from the getter and, in `Undo`, clears and refills its attribute list in place rather than assigning a new definition — so the cloning setter is not on that path at all, and `DeviceClassAttributeRollbackTest`'s five cases still pass unchanged.
- **The `virtual Clone()` loses nothing that matters.** No type in `src/` or `libraries/` derives from `ClassDefinition`, so a `Clone` returning a base instance is exact. `Clone` does drop the `Statement` line information, which is new for the assignment paths that previously stored the parsed object — checked: the only code that reads a line off a class definition is `Parser.cs:5325`, and that is the *language* `OperatorBlock`, which has no cloning setter. Nothing reads line information off a stored definition, and nothing anywhere compares a `ClassDefinition` by reference.
- **Leaving metadata alone is right for a stronger reason than the handoff gives.** The implement ticket excluded `Schema.Object.MetaData` to avoid disturbing 14 golden forms. In fact the `alter … alter tags` arm has no analogue of this defect at all: `USESTRUCTTAG` is defined at `MetaData.cs:14`, so `Tag` is a struct and `Tags.AddRange`/`AddOrUpdateRange` copy by value — a statement's tags cannot be written into by an alteration of the object's. What *is* shared is the whole `MetaData` object that create statements hand to the objects they build, and that is already an arm on `bug-view-tags-lose-to-tags-inherited-from-the-source` (moved to `blocked/` while this review ran), which lists all nine such sites. No new ticket.
- **The full suite that the implement stage skipped was run — by CI, as this project's rules intend.** GitHub Actions run `45213159163` on the implement commit: success, 19 m 39 s, Debug and Release. The handoff flagged the skipped three-part local run as the one thing a reviewer should weigh; it is settled, and the reasoning for skipping it matched the project's stage policy.
- **Source hygiene.** Every edited file kept its tabs, CRLF endings and byte-order-mark state (checked byte for byte: no LF-only line in any of them). The handoff's remark about "a single pre-existing LF line" in `docs/migration-notes.md` is simply wrong — the file is uniformly CRLF, 162 lines of 162 — but nothing turns on it. ### Fixed in this pass

- **A tripwire on the plan-cache case, which is on course to stop testing what its name says.** That case reaches a cached plan only because neither `alter device` nor `drop device` advances the plan cache's timestamp today. `implement/bug-recreated-device-comes-back-as-the-one-that-was-dropped` adds that bump to both; once it lands, the second run of the statement recompiles from its text and the case passes whether or not the attribute is cloned, leaving the prepared-plan case as the only one guarding the regression. There is no way to write the case so it survives — every other statement that could mutate the shared attribute already bumps the stamp — so a `NOTE:` at the case says this and asks whoever lands that ticket to decide whether the case still earns its keep. Indexed here, parked there.
- **A comment that contradicted its own file.** `DeviceClassAttributeFixture`'s summary said "no assertions of its own"; its `Device` helper calls `Assert.Fail`. Changed to "no test cases of its own", which is what it meant.

### Filed: one, as an arm on the ticket that already owns the site

`alter device D alter class { drop "Bogus" };` — a name the object has no setting for, which is what a typo looks like — fails with `Runtime error: Index was outside the bounds of the array.`, wrapping a raw `System.IndexOutOfRangeException`, naming neither the attribute nor the fact that a name was the problem. The `alter` arm of the same statement, given the same bogus name, reports it properly (`Class "MemoryDevice" does not contain a property named "Bogus".`). Both measured on an in-process server. The cause is the drop loop's `RemoveAt(IndexOf(name))`, two lines from the line this ticket changed: `IndexOf` returns `-1` and the list's indexer turns that into an array error. Nothing is corrupted — the index is read before the list is modified.

`backlog/bug-dropped-class-attribute-stays-on-the-live-object` already claims that exact loop, so this went in as a second arm on it rather than as a new ticket, with the measurement and the asymmetry written down. It was not fixed in this pass because it changes what error a D4 statement raises, which this project's rules treat as a compatibility surface needing a ticket that says so. The same edit corrected that ticket's closing section, whose path for the device helpers is now stale.

### Checked and deliberately left alone

- **No test for the six cloning setters** — agreeing with the handoff, and with a measured reason rather than an absence of one. The setters' effect is unobservable through D4 today. The only place in the tree where two *catalog* objects shared one class definition is `Compiler.cs:5213` and `:5249`, where a scalar type's generated `=` and `?=` take the component type's operator's definition; reaching it needs an `alter operator` on an operator marked `IsGenerated` and `IsBuiltin`, which no fixture or coverage script does and which `AlterOperatorNode`'s `CheckNoDependents` stands in front of. Every other sharing route is a create statement read a second time, which runs into the two sibling defects. A test here could only assert that a setter clones, which is a test of an implementation, and the invariant already has a home: the six `<remarks>`.
- **The double clone at `Compiler.cs:4861`**, which the handoff offered to a reviewer. `scalarType.ClassDefinition = (ClassDefinition)(…).ClassDefinition.Clone()` now clones twice. Left as it is: dropping the explicit `.Clone()` would also turn a null source definition from a `NullReferenceException` into a silently stored null, and the implement ticket directed that the compiler's assignments stay as they are. The extra clone costs one small allocation on a create path.
- **The repetition in the six setters** — the same four-line `<remarks>` and the same one-line ternary, six times. A shared helper would save a line each and move the explanation away from the property it is about, in files whose every property is a hand-written `get`/`set` pair. No change.
- **The unmeasured allocation on catalog load**, flagged by the handoff. Not parked as a tripwire: it is one small object per catalog object loaded, on a path that already parses and compiles that object's persisted create script, and the implement stage reports no slowdown observed when the setters were built. There is nothing conditional to trip here, so a `NOTE:` would be noise. `research-catalog-load-profile` remains the named scenario if catalog load ever wants measuring.
- **No docs changed.** Checked `docs/migration-notes.md`, `docs/modernization-plan.md`, `docs/architecture.md` and `AGENTS.md` against the diff. The plan's "Known defects" register is not the home for this: the last six tickets that fixed a pre-existing, non-port engine defect each added only a migration-notes row and no K entry, and nothing in the plan's WS2 text or work-item table refers to this slug. Neither `architecture.md` nor `AGENTS.md` describes class-definition ownership, and an ordinary NUnit fixture does not belong in the latter's list of fixtures with unusual run semantics.
