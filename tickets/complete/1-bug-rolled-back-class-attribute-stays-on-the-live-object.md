## What was wrong

Some D4 objects are backed by a .NET class, and the statement that makes one carries a *class definition*: a class name plus named attributes that are applied to the live object as properties. A memory device's row limit is one of those — `alter device D alter class { create "MaxRowCount" = "100" }` sets `MaxRowCount` on the running device object and records the attribute in the catalog.

Rolled back, the attribute came out of the class definition and the property stayed on the running object, so the server went on enforcing a row limit its own catalog did not hold until it was restarted. The cause was in the undo: `AlterClassDefinitionInstruction.Undo` built the inverse alteration and replayed it, and the inverse of a created attribute is a *drop* — and the drop loop in `AlterNode.AlterClassDefinition` only edits the class definition, where the create and alter loops also set the property on the live object.

A second defect at the same site: the instruction was built before the change but added to the log after it, and the inverse alteration could not have undone a half-applied change anyway. `ClassLoader.SetProperty` converts each attribute's string to the property's type and throws on one it cannot convert, so a statement with two attributes whose second value is bad had already applied the first — and with nothing in the log, neither the class definition nor the live object was put back.

## What changed

**`src/engine/DAE/Device.Catalog/ClassLoader.cs`** — new `public static bool TryGetProperty(object, string, out string)` beside `SetProperty`: the named property's value in the string form `SetProperty` takes, or false when the object exposes no readable property of that name.

**`src/engine/DAE/Device.Catalog/CatalogDeviceSession.cs`** — `AlterClassDefinitionInstruction` records, at construction, a copy of the class definition *and* the live instance's own value for every attribute the alteration names (create, alter and drop alike); `Undo` puts the copy back wholesale and then sets the recorded values on the instance. `CatalogDeviceSession.AlterClassDefinition` adds the instruction to the log **before** applying the change, as `AlterMetaData` has always done.

**`src/engine/DAE/Runtime.Instructions/DDLNodes.cs`** — one `NOTE:` above the forward `DropAttributes` loop, which is otherwise untouched: a forward drop still leaves the property the dropped attribute set, and whether it should is `backlog/bug-dropped-class-attribute-stays-on-the-live-object`.

**`docs/migration-notes.md`** — one row under *D4, catalog and libraries* (a rolled-back or half-applied device setting change no longer sticks) and one under *Custom C# extensions* (the new `TryGetProperty`).

Three deliberate deviations from the implement ticket, all three confirmed in review as the better call: the undo restores a recorded copy of the class definition instead of replaying the inverse alteration (the inverse would raise out of the undo on the part-way case, before the instance restore could run, and the rollback loop abandons the rest of an instruction's undo when one throws); `TryGetProperty` rather than a throwing `GetProperty` (the recording now runs *before* the alteration, so a throwing read would fail a statement where it did not fail before); and a new fixture rather than cases in `CatalogStoreTest.cs`, following the sibling `ServerLinkUserRollbackTest`.

## Review findings

Read the implement-stage diff (`ticket(implement): bug-rolled-back-class-attribute-stays-on-the-live-object`) before the handoff summary, then the surrounding code: the *Instructions* and *Transactions* regions of `CatalogDeviceSession.cs`, `AlterNode.AlterClassDefinition` and its four call sites in `DDLNodes.cs`, every `session.AlterClassDefinition` caller, `ClassDefinition`/`ClassAttributeDefinition`/`ClassAttributeDefinitions` and their `Clone` in `Language.D4/Language.cs`, `ValidatingBaseList.Clear`, `ClassLoader.SetProperty`/`CreateObject`, and the plan cache.

**Found and fixed in this pass (one, minor).** The comment above `RecordProperties` justified the skip with "the alteration raises PropertyNotFound for such a name itself" — true of the `propertyInfo == null` half of `TryGetProperty`'s condition, and **not** of the `!CanRead` half: a property with a setter and no getter is one `SetProperty` applies happily and the recording cannot capture, so the undo would silently leave the live object changed, which is the very defect this instruction exists to close. The comment now states both cases and carries a `NOTE:` for that hole and for a second one of the same shape (the recorded value is the property's *string* form, so a property type that does not round-trip through a string — a `double`, a `DateTime` — would be restored only approximately). Neither is reachable: a regular-expression scan of every `public` property declaration in `src/` found no write-only property anywhere, and a scan of the device and schema classes found none of a type whose string form is lossy, which is why this is a comment and not a ticket. A custom C# extension could bring either; the `NOTE:` says what to do then.

**Found and filed (one, major).** Not this change's defect, and not about rollback at all — found while probing the new undo for aliasing. A live catalog object's class definition is **the statement's own parsed object**: `AlterNode.AlterClassDefinition`'s create loop adds the statement's `ClassAttributeDefinition` straight into the live definition, and the compiler assigns a statement's whole `ClassDefinition` onto the device, scalar type or operator it is building. The `alter` loop then writes the new value through that shared object — which is also the first statement's remembered parsed text in the plan cache. Measured, through `IServerProcess.Execute` (the path that consults the cache), two sequences that each produced a device with `MaxRowCount` 200 from a statement that says 100: an `alter … create` re-run after an intervening alter and drop, and a `create device … attributes { … }` re-run after an intervening alter and `drop device`. Both with `Expected: 100 But was: 200`. Filed as `fix/bug-remembered-statement-applies-a-changed-setting` at the invariant — a catalog object must own its class definition — rather than as the one-line clone, because the create loop and the nine compiler assignment sites have to change together or the sequences still reproduce through whichever is left; that is a design call across `Compiler.cs`, which this project's rules put in its own ticket rather than in the ticket that met it. Pre-existing at every site read, by inspection of this diff: both sequences commit throughout, so no `Undo` runs and the new recording only clones and reads. This change in fact narrows the defect slightly — the new undo rebuilds the live definition from clones, so an object that has been through a rolled-back alteration no longer shares anything with a statement. No `NOTE:` left at the site: the ticket is in `fix/`, the stage worked next, and the fix deletes the line.

**Checked and correct, nothing to do.** The recording's placement before the alteration matches `AlterMetaData`, the only other instruction with the same hazard. `ClassDefinition.Clone` and `ClassAttributeDefinition.Clone` are deep, so the recorded copy survives the forward alter loop's in-place mutation of the live definition — the one thing that would have made the whole fix silently useless. `ClassAttributeDefinitions.Clear()` runs the base list's `Removing` hook and the collection overrides only `Validate`, which the re-added clones satisfy. `ClassName` being assigned unconditionally in the undo is the same value when the forward alteration did not change it, and the forward path still refuses a class-name change on an object with a live instance. Undoing a `drop` sets the property to the value it already has, so it adds no new way for an undo to throw; the only *new* `SetProperty` on the undo path is the undo of a create, which is the fix. Instructions are replayed in reverse within their level, and a nested commit promotes the inner ones, so the recorded pre-change values land in the right order — pinned by two of the five tests. An object dropped later in the same transaction is re-inserted by `DropCatalogObjectInstruction.Undo` as the same instance, so the reference this instruction holds stays live. `TryGetProperty`'s `null` result is only reachable for a reference-typed property, where `SetProperty`'s `Convert.ChangeType(null, …)` returns null rather than throwing. Both `docs/migration-notes.md` rows are in the right sections and say the right thing; `docs/architecture.md` does not enumerate the catalog's in-memory undo log and this change does not alter the mechanism, so there was nothing to update there, and the sibling rollback tickets set the precedent that these do not get a known-defect row in `docs/modernization-plan.md`. Source hygiene verified at byte level: tabs, CRLF and byte-order-mark state unchanged in every file, no lone LF anywhere.

**Checked on the tests.** Kept all five. The first two are the two defects' reproductions; the third and fourth pin contracts the first two do not (several instructions over one object in one transaction, and level scoping), each in about 20 ms. The fifth, which passes before and after and which the implementer invited cutting, stays: this change replaced how the no-live-instance path is restored (inverse alteration → recorded copy), and the project's rule asks for a characterization test for behaviour a ticket changes; the coverage scripts do not reach that path — their only three `alter class` lines are `alter "MaxRowCount"` on `System.Temp`, which is the live-instance path. Nothing was added: every contract worth pinning here is pinned, and the one defect found in review belongs to the ticket filed for it, with its reproduction described there.

## Known gaps

- **A forward `drop` of a class attribute still leaves the property it set on the live object.** Deliberate: it is a separate decision (should a drop restore the class's default, or the value the object held before the attribute was created?) and it is filed as `backlog/bug-dropped-class-attribute-stays-on-the-live-object`, with the `NOTE:` at the drop loop pointing there. The *undo* of a drop is correct.
- **A device started inside the rolled-back transaction** is stopped by the rollback's deferred device stops and has its `Registered` flag cleared by `StartDeviceInstruction` / `RegisterDeviceInstruction`. The implement ticket recorded those as already correct; this change touches neither, and they were not re-measured in review either.
- **No SQL device was exercised.** The fix is at the site both share and nothing in it is device-specific, but a test over a SQL device's own class attributes would need a database server.
- **Metadata tags may or may not share the statement's parsed form.** Probed with the same sequence that reproduced the class-definition aliasing (a table's tag created, altered, the table dropped and re-created from the same text) and it came out right, but whether that is because the metadata is copied somewhere or because that particular plan was not handed back from the cache was not established. Recorded in `fix/bug-remembered-statement-applies-a-changed-setting` as something that ticket has to settle rather than assume.
