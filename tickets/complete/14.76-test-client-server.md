## What landed

The last of the four tickets that build the test plan's layer 4 (client/server). It gives the `ServerLink` coverage script the second Dataphor server its own first comment has always asked for — *"Assumes a running default Dataphor instance"* — and the script runs for the first time in the history of the automated suite; it was `[Ignore("Integration test, needs server setup")]` in the legacy hand-wired list, so none of its assertions had ever been checked by a test run.

The product gained one member, `DataphorServiceUtility.ListenerPortNumber`: a settable process-wide default for the port a **client** looks on for a listener when the caller passes no override, read by `BuildListenerURI` where the constant used to be. `DefaultListenerPortNumber = 8060` is untouched and is still the initial value, so a deployment that sets nothing behaves exactly as before; it has no host-side counterpart, because a server's listener port is already an instance setting. It is needed rather than simply taking 8060 because WS3 requires that no test touch a fixed port, and the failure mode here is worse than a collision: on a machine with a real Dataphor installation a real listener would answer the script's lookup and point it at a **real instance**, in which the script then creates users, tables, types and operators.

On the test side, `OutOfProcessInstance` can now serve a listener (a second reserved port, `ShouldListen` written into the child's instance list, and a ready line the fixture requires to say `listening=true`, so a child whose listener port was taken fails the case at the start with its own output attached). The coverage manifest gained `linkedServer`, and `CoverageScripts` starts such a child around the script and points this process's client side at it for the length of that one case.

**What the script reported: 125 of its 126 statements pass; the one failure caught a real defect.** The assertion at line 34 wants a remote session whose maximum call depth is the 128 its link's tag asks for, and gets the product default of 100, because the link is created under a name an earlier link used and dropped, and nothing closes a cached remote connection when a link is dropped (`ServerProcess.RemoteDisconnect` exists for exactly that and has no caller in the tree) while the cache matches links by name. Filed as `tickets/fix/engine-server-link-session-outlives-drop.md`; the manifest entry is `known-failure` on `Server link with Session Info failed`, owned by that slug.

Documented in `docs/migration-notes.md` (the new member), `docs/modernization-plan.md` (the WS3 row marked Done, a new *Client/server tests* subsection for the layer, and the *CoreWCF hosting* hand-on bullet settled) and `AGENTS.md` (the manifest field and the listening child).

## Review findings

### Fixed in this pass

- **The process-wide listener port was restored before the child server was stopped.** `CoverageScripts.Execute` set the static inside a `using` and restored it in a `finally` nested inside that `using`. On the abandon path — the script times out, its server is abandoned and its worker thread is still running — the static therefore went back to the product's own 8060 while that thread could still resolve a server link, and on a machine with a real Dataphor installation a real listener answers there and points the script at a real instance. That is the single outcome the whole arrangement exists to prevent, reintroduced on the one path nobody watches. Reordered so the restore is in a `finally` *outside* the `using`: the static stays at the dead child's port until the case is over, and a late resolution fails instead of succeeding against something real. The reason is at the site, because the shape now looks like the accident rather than the intent. (This was the ordering the implement handoff asked a reviewer to weigh.)
- **`tests/TestHarness/Program.cs` still asserted something the ticket had just made false.** Its comment on the default host name said the fixtures "pass the loopback literal instead, so no port this suite opens is reachable from another machine" — while a listening child now passes that machine-name default deliberately, and is the suite's one exception. The exception and a pointer to `OutOfProcessInstance.HostName`, where the whole reason lives, are now in that comment. `OutOfProcessInstance`, `AGENTS.md` and the plan already carried it; this file was on the same seam and was missed.
- **A trap left at the one site that still reads the constant.** `ListenerServiceHost` resolves a server's own listener port from `DataphorServiceUtility.DefaultListenerPortNumber`, which is correct and deliberate, but a reader meeting that line next to a new `ListenerPortNumber` on the same class is one "tidy-up" away from coupling every server's listener to a client-side knob — moving a host's own listener because it only meant to reach another machine's. `NOTE:` at the site saying which half of the protocol each belongs to.
- **The plan read as a clean bill of health for the features the script touches.** *"125 of the script's 126 statements pass — default and tagged links, link users and their credentials, `alter server`, …"* is true of what executes and easy to over-read as verified behaviour, when the same defect makes the tags on every later link inert. Added one sentence saying so and pointing at the ticket.
- **The fix ticket understated how far the reuse reaches.** It named the one failing assertion and the `alter server` block that passes for the wrong reason. In fact all seventeen of the script's `create server` statements use the one name `Test`, the cache is keyed by that name, and nothing removes an entry on a drop — so the single remote session opened at line 10 serves every statement the script's **own** process sends (which is why the ticket's measured `Count(RemoteSessions where Process_ID = ProcessID())` is 1 at line 34). The blocks run through `ExecuteAs` are the exception: `SystemExecuteAsNode.ExecuteScript` connects a new session and starts a new process whose cache is empty, so the link-user blocks do open sessions of their own with the credentials they are testing. Added to the ticket as its own section, with the two consequences for whoever fixes it — the configuration half of the later blocks proves nothing today, and the script may fail in new places the moment the reuse stops — and with one block ruled out in advance: the `UseSessionInfo` assertion at line 23 holds either way, because `SetMaxCallDepth` sets the running process's stack depth while `UseSessionInfo` propagates `SessionInfo.DefaultMaxCallDepth`, which it leaves alone. All read from the code (`RemoteConnect`, `RemoteSessions.IndexOf`, `Schema.Object.Equals`, `SystemSetMaxCallDepthNode`, `RemoteSessionImplementation.GetDefaultNativeSessionInfo`), not measured in a new fixture.
- **The fix ticket's anchor pointed at the test suite.** It was filed against `#ws3-test-suite`, which is where its *evidence* lives; the work it asks for is in `src/engine`, and the plan section that owns the engine's session and connection lifetime — including the sibling defect `bug-native-cli-sessions-never-reclaimed`, named there beside server links — is WS2. Retargeted to `docs/modernization-plan.md#ws2-engine-and-server-port`, so a reader arriving by the anchor lands on the specification the fix serves rather than on the suite that found it.

### Checked and left alone

- **Filing the line-34 failure rather than fixing it here was right** — the judgement the handoff flagged first. The three-line fix (call `RemoteDisconnect` from the drop) repairs the dropping process and leaves every other session's cached connection wrong in the same way, says nothing about the name-based match, and contradicts the original author's two `TODO`s, which propose refusing the drop instead. The ticket is in `tickets/fix/`, the top-priority stage, so the engine answer lands next rather than later.
- **The product seam is the only route, and the asymmetry it claims is real.** The script creates its links with no port override; the `OverrideListenerPortNumber` tag exists on `Schema.ServerLink` but the script does not use it, and a coverage script may not be edited. Even the first statement needs the knob: an untagged link has no override port, so it resolves through a listener too. Every reader of `DefaultListenerPortNumber` was checked — `ListenerServiceHost` (the host half, unchanged) and one test assertion — so a deployment that sets nothing is untouched, as the remarks and the migration note say. No range guard added to the setter: the link tag beside it is a bare `Convert.ToInt32`, and a second floor is a floor that drifts.
- **The static is safe because one case runs at a time, and that was verified rather than assumed.** No `[assembly: Parallelizable]` or `LevelOfParallelism` anywhere in `tests/`; every fixture in `DAE.Server.Tests` carries an explicit `// Not [Parallelizable]:` comment, and `CoverageScripts` now carries one too, saying why it now matters.
- **The listening child's start check works as claimed.** Traced `host.IsListening` → `_listenerServiceHost != null && IsStarted`, which is false when the bind failed — a server whose listener port is held starts anyway, by design — so `CheckReadyLine`'s `listening=true` does fail the case at the start. The condition was read, not provoked; provoking it needs a socket held on a port the fixture has not yet chosen.
- **Failure and cleanup paths.** The constructor reserves, writes and starts inside `try { … } catch { Dispose(); throw; }`, and `Dispose` kills a started child and deletes its temporary root. An exception from the child's start escapes `Execute` and fails the case with the child's output attached; the coverage summary then counts that case in no bucket, which is harmless and loud. The new three-argument constructor did not orphan the two-argument one — `AbandonedClientProcessTest` still uses it.
- **Manifest validation.** `linkedServer` mirrors `batches` exactly: `false` rejected so the field is never written to mean the default, and forbidden on a `fragment` entry, which is not run. The four near-identical fragment checks are two lines each and read better than a helper that hid the four messages. The implementer hand-verified both arms and restored the entry; not re-run here.
- **`docs/architecture.md` was read and needs nothing.** Its endpoint table still gives the listener as `net.tcp://<host>:8060/listener/service`, which is the product's endpoint and whose default this ticket does not change; the new member is a client-side start-up knob and belongs in the migration notes, where it is.
- **The two tripwires the implementer left are respected.** The `NOTE:` on the port probe (reserved on the loopback literal while a listening child binds the wildcard, so a socket bound to one specific non-loopback address would probe free and then fail the bind) is the suite's existing convention and loud when it trips. The `NOTE:` on the abandoned server's background stop is unchanged. Neither revisit condition has tripped.
- **`HostName` returning one of two things** — the handoff's third question. The only listening child is the coverage one, no test code reads its `HostName`, and the property's remarks carry the measurement, the reason and the fact that it is forced. No change.
- **`tickets/.pre-existing-known.md`.** The `ServerLink` `one-off` record was updated rather than deleted, which is right: the script still fails, but on a different thing. Its new confirm protocol — a `HarnessTimeout` on this script is no longer the machine's closed-port behaviour and should be reported — matches what the fixture now does, and the "about 8 s" it records matches the 8 s measured here.

### Tests

**None added, none cut.** The script this ticket exists for *is* the test, and it now runs. A unit test for the setter would restate one assignment the case already exercises end to end; the manifest field is covered by the manifest's own validation. The one defect found in review is on a path no script reaches — the abandon path — and nothing in the harness can provoke it without a script written to hang, so there is no test to pin it; the reason is at the site instead. No expected value in any D4 script was changed, and nothing was skipped, loosened or disabled.

### Not filed

No new ticket. The one real defect belongs to `engine-server-link-session-outlives-drop`, already open in `tickets/fix/`, and this review's findings went onto it as an arm rather than into a second ticket for the same site. Considered and rejected: a ticket against the new mutable process-wide static. It is additive, defaults unchanged, documented at the site and in the migration notes, and the alternative that would retire the class — the engine resolving a server link through an injectable listener locator instead of a process-wide default — is a design with no anchor in the current release and no second caller asking for it.
