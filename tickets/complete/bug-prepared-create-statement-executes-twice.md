description: A program can ask the server to compile a statement once and then run it as many times as it likes. For a statement that creates something, the second run put back the very thing the first run made — carrying any change made to it since — instead of making what the statement describes. Such a statement is now compiled again before each run after the first.

## What landed

**The rule: a compiled plan containing a statement that changes the catalog is used for at most one execution; executing it again compiles its statement afresh first, and executes that.**

The implementation is commit `ticket(implement): bug-prepared-create-statement-executes-twice`. Four engine changes:

- `DDLNode.ContainsDDL(PlanNode)` (`src/engine/DAE/Runtime.Instructions/DDLNodes.cs:31`) — the predicate, a recursive walk for a `DDLNode` anywhere in the tree, so a statement nested in a block, an `if` or a loop counts. `DDLNode` is already the engine's name for "statements that change the catalog".
- `ServerStatementPlan.Execute` (`src/engine/DAE/Server/ServerPlan.cs:277`) — the rule's one site, with `_compilationExecuted` (set *before* the execution, so a statement that threw half-way still consumes its compilation) and the once-computed `_needsRecompilation`.
- `ServerProcess.RecompileStatementPlan` (`src/engine/DAE/Server/ServerProcess.cs:893`) — compiles the retained statement with the execute-time parameters, checks the new `Plan` for errors explicitly (`Compiler.Compile` collects them rather than throwing), and only then swaps. A failure executes nothing and leaves the plan holding the compilation it had.
- `ServerPlan.SourceStatement` and `ServerPlan.SourceContext` — what the plan keeps so it can be compiled again. The parsed statement, not the text, because a batch plan is handed the whole script's source context and recompiling from text would compile the entire script.

Tests: new fixture `tests/DAE.Server.Tests/PreparedPlanRecompileTest.cs` (3 cases, about 90 ms) covering the create arm, the drop arm and the refused recompilation over an object that still exists; one case added to `DeviceClassAttributeRerunTest`. Documentation: `K46` in the plan's *Known defects* register, a rewritten pointer sentence on K42, and one `done` row in `docs/migration-notes.md`.

Review changed four things in that work, all listed below.

## Review findings

The implement diff was read before the handoff. Beyond reading, the checks were: the whole `DDLNode` subclass set and every DDL compile entry in `Compiler.cs`; the plan cache's `Get`/`Add`/`Release` and `Plan`'s own construction, binding and disposal; two mutations of engine code, each built, run and reverted; and every document the change touches.

### Fixed in this pass

- **A failure in `Plan.Dispose` could have left the plan holding a disposed compilation.** `SwapCompilation` assigned the new pair and *then* disposed the old `Plan`, while the caller set its `swapped` flag only after `SwapCompilation` returned. A throw out of that disposal would therefore have run the caller's `finally` with `swapped` still false, and disposed `plan` — which by then was the plan's live compilation. `Plan.Dispose` does not throw today (it pops two guarded context stacks and clears a field), so this was latent rather than reachable; what makes it worth fixing is that the ordering trap is invisible at the call site and the next editor of `Plan.Dispose` would walk into it. `SwapCompilation` is now a pure field swap that *returns* the displaced `Plan`, and `RecompileStatementPlan` holds one `abandonedPlan` local — the new compilation until the swap goes through, the displaced one afterwards — and disposes it in its `finally`. Ownership is now stated rather than inferred from an ordering.
- **The two new properties' setters are `internal`.** `SourceStatement` and `SourceContext` were added as public settable properties on `ServerPlan`, which is a type a custom C# extension can see; nothing outside `Alphora.Dataphor.DAE` sets either one. The getters stay public (reading them is useful, and the follow-on expression-plan ticket will want `SourceStatement`), the setters are now `internal`, with a `NOTE:` saying to widen them if an extension ever needs to build a plan of its own. No migration-notes entry: these members exist only on this branch and have never been in a released build, so there is nothing an extension could already be writing to.
- **Two tripwires recorded at `RecompileStatementPlan`.** Neither is a defect today; both are conditions a future change could trip, and both were found by this review rather than carried over from the handoff. (1) *Compilation writes into the statement it compiles.* The handoff measured one such site (metadata tag defaults); reading `Compiler.cs` found two more — `CompileIndexerExpression` writes a resolved `HasByClause`/`ByClause` and replaces the indexer's own sub-expressions with emitted copies (`Compiler.cs:12708`), and `CompileCreateScalarTypeStatement` writes an inherited conveyor into the statement's `ClassDefinition` (`Compiler.cs:5612`). Every one found writes back a value the next compilation computes the same way, which is why compiling one statement twice yields the same program — but a compiler change that wrote something a recompilation read differently would make a re-executed plan diverge in silence. The remedy named in the `NOTE:` is to compile from a copy of the statement, which would need a deep clone of the D4 syntax tree; there is none (`Statement` has no `Clone`; only `MetaData` and `ClassDefinition` do), so the convergence is the design's load-bearing assumption and now says so at the site. (2) *The recompilation binds the execution's context, not the prepare's* — the process locals, the session's current library, an open application transaction. That is what compiling the statement *now* means and matches `ServerProcess.Execute` of the same text, but it has a visible edge: a session that calls `System.SetLibrary` between two executions of a held `create` plan builds into the library it has now, where before the fix it re-registered the original object.

### Checked and sound

- **The rule is in the one right place, and the place is complete.** Two independent sweeps. Every `DDLNode` subclass is in `DDLNodes.cs` — nothing derives from `DDLNode`, `CreateObjectNode`, `DropObjectNode` or `AlterNode` anywhere else in the tree — so the predicate's set is the whole set. And the other way a compiled node tree is executed many times, a D4 operator body, cannot contain DDL at all: all 39 `Compile(Create|Drop|Alter|Attach|Detach|Invoke)…Statement` entries in `Compiler.cs` refuse it with error 105234, "DDL statements must be dynamically executed within an operator block", and an operator that uses `System.Execute` instead compiles its statement at run time on every call. The catalog-mutating *operators* (`System.CreateLibrary` and the rest, in `SystemNodes.cs` and `LibraryNodes.cs`) are `InstructionNode`s that resolve their arguments from the stack at execute time and hold no compile-time-built object, so they need nothing. Statement plans really are the only place the defect lived.
- **A plan that goes through the plan cache is the same object, so the rule survives the round trip.** `PlanCache.Get` hands back the stored `ServerPlan` and calls `BindToProcess`; `Release` calls `UnbindFromProcess`. `_compilationExecuted` therefore persists, and a cached DDL plan that is prepared again and executed recompiles. The security-context push and pop in `Plan.BindToProcess`/`Dispose` stay balanced across a swap, because the replacement `Plan` is constructed in the bound state the plan is already in.
- **The recompilation is a faithful copy of the original preparation.** `CompileStatement` does nothing to its pair that `RecompileStatementPlan` omits: both set `ShouldPushLocals`, and both go through the same private `Compile`, which is what sets `Program.Code`, the source context, the process locals from `Plan.NewSymbols` and the plan catalog's dependencies. `IsCached` is carried from the old program, which matters because `ServerSession.AddCachedPlan` sets it at admission. Nothing in the engine holds a `ServerPlan.Plan` or `.Program` reference across calls for a statement plan; the two places that read `.Program.Code` are on `ServerExpressionPlan`, which never recompiles.
- **`ContainsDDL` costs nothing until it is needed and matches the house style.** The guard is `_compilationExecuted && NeedsRecompilation()`, so the tree is never walked on a plan executed once — which is every plan in a catalog rebuild script. It dereferences `Nodes[index]` without a null check, as `PlanNode.BindToProcess`, `ClearDeviceNode` and `Clone` all do; a null child would already crash those.
- **Both mutation measurements the handoff rests on were repeated, and both hold exactly.** Reverting `attributeDefinition.Clone()` at `DDLNodes.cs:1138` fails exactly two cases — `TestOneProgramRunningTheSameAlterTwiceAppliesItsOwnValue` and `TestPreparedPlanExecutedAgainAppliesItsOwnValue` (`Expected: 100 / But was: 200`) — and leaves the plan-cache case and all three recompilation cases green, which is what the handoff claims. Neutralizing the recompilation guard fails exactly the three `PreparedPlanRecompileTest` cases and leaves all three `DeviceClassAttributeRerunTest` cases green. So the new fixture is a real guard for this ticket's rule, and the three older cases genuinely do not depend on it. Both mutations reverted and the tree confirmed clean afterwards.
- **The documents say what the code does.** The migration note row and `K46` were read against the implementation: the error-code change (compiler 105214 in place of a runtime error wrapping schema 113106), the new object identifier, the one extra compilation per re-execution, and "expression plans are unchanged" are all accurate. K42's rewritten pointer names K46 and says why a plan-cache key could not have been the answer.
- **Source hygiene.** `ServerPlan.cs` and `ServerProcess.cs` are LF with no byte-order mark; both kept that way, tab indentation preserved, nothing reformatted. The files are 510 and 2,122 lines; neither grew enough to raise a size question.

### Weighed and left as it is

- **Two executable guards for the class-definition clone, where the implement ticket expected one or none — both kept.** The handoff asked a reviewer to decide, and measured that the prepared-plan case still reproduces the clone defect because the recompilation reads the *parsed statement* and the defect is an alteration writing into that statement. Kept, for two reasons. This project's testing rule is that a ported subsystem owes a characterization test and a bug fix owes its reproduction, which outweighs the general "one test per behaviour" default; and the fixture's premise is a matrix of the three ways one statement runs more than once, which cutting a row would leave half-stated. The honest cost, as the handoff asked be said plainly if both were kept: **the prepared-plan case's reproduction value is coupled to this ticket's choice of recompilation source** — change the recompilation to read the statement *text* and that case goes green with the clone reverted. `TestOneProgramRunningTheSameAlterTwiceAppliesItsOwnValue` is the uncoupled guard, and the durable one.
- **No architecture-page text.** `docs/architecture/sessions-processes-plans.md` owns sessions, processes and plans and is at 1,491 of its 1,500-word cap, so the one-execution rule cannot be written there without splitting the page. Not filed as a ticket: the rule is recorded in the plan's K46 and in the comment at `ServerStatementPlan.Execute`, no current-release anchor asks for the split, and the documentation-size question is already a human decision in flight (`blocked/debt-split-the-modernization-plan` and `blocked/debt-split-the-migration-notes`). The page says nothing that is now false.
- **`SourceStatement` is still set for expression plans, where nothing reads it.** `SourceContext` has to live on the shared `ServerPlan` base for the two cached-plan branches to record it, the assignment beside it is one line, and `backlog/bug-a-held-query-plan-keeps-answering-from-a-stale-catalog` is the ticket that will read it. Cutting and re-adding it would be churn.
- **No test for a prepared DDL plan executed twice inside one transaction with a rollback between.** The handoff is right that the outcome is one wasted compilation and never a wrong answer — a rollback does not clear `_compilationExecuted`, so the next execution recompiles, which after a rollback is also what is wanted. That is reasoning, not a measurement, and it stays reasoning.

The arm names the measurement and asks the same pass to check whether the other eight sites share a class definition too.
