description: Asking for a picture or document value with a fallback in case it is missing made the server keep a block of memory it never gave back, once per call. It now gives that memory back.
architecture: docs/modernization-plan.md#ws2-engine-and-server-port

## What was wrong

`IfNil(AValue, AReplacement)` returns its first argument unless that argument is nil, in which case it returns the second. It returned a *copy* of whichever argument it chose and never released the original. Where that original was a value the call owned - anything computed for the call rather than read out of a variable: a selector, a conversion, another call - nothing else named it and it was orphaned. For a `Binary` or a `Graphic`, the two types the engine keeps in a managed stream, that is one stream held for the life of the session per call.

The rule the engine already has for this - whether a call owns the value handed to a `const` operand is a property of the plan node that produced the argument, not of the modifier - lives in `InstructionNodeBase.CleanupOperand`. `IfNilNode` never reached it, because it overrides `InternalExecute(Program)` itself. The fix applies the same rule at the site by hand.

## What changed

**`src/engine/DAE/Runtime.Instructions/SystemNodes.cs`, `IfNilNode.InternalExecute`** - keep the node whose value was chosen, copy the value, and release the original where that node answers `ReturnsByReference` false. The copy is made inside a `try` whose `finally` holds the release, so the order is right on the way out (releasing first would leave the copy reading a stream the manager has forgotten, which reports as `StreamID (n) not found`) and the value is also released if the copy itself raises. The node read is the one left in `Nodes[index]` at run time rather than the one `base.DetermineDataType` asked, because `DetermineDataType` may replace either with a conversion; `CopyValue` and `DisposeValue` both fall through for a null, so `IfNil(nil, nil)` needs no special case. A `NOTE:` tripwire at the same site records the rejected alternative - returning a lent value as it stands - and why it is not done (it would make this node's own ownership per-execution, where `ReturnsByReference` is settled at compile time).

The node's allocation count is unchanged from before the fix, and what the caller receives is unchanged.

**`tests/DAE.Server.Tests/AssignmentValueOwnershipTest.cs`** - `IfNilReleasesTheValueComputedForIt` covers both shapes that leaked (a computed first argument, and a nil first argument with a computed replacement) over `AssignmentCount` calls, asserting the stream count balances *and* that the result is readable each iteration. `IfNilGivenAVariableLeavesTheCallersValueAlone` covers the loan, which the wrong fix breaks: a variable as the chosen argument, asserting the count balances and the caller's variable is still readable afterwards.

Both were checked against a deliberately broken engine. With the guard forced to never release, `IfNilReleasesTheValueComputedForIt` fails on both shapes and the loan case passes - the pre-fix behaviour. With it forced to always release, the loan case fails and the other passes - the rejected fix. So each case fails for exactly one of the two ways to get this wrong.

No generalised test was added: the reasoning is in `docs/architecture/operand-ownership.md` instead, and the review found that reasoning rested on a miscount and filed the generalised check as its own ticket (below).

**`docs/architecture/operand-ownership.md`** - the set of nodes that bypass `CleanupOperand` by overriding `InternalExecute(Program)`, what each of them does about it, and the fact that nothing checks the set. 1,161 words of the 1,500 limit; `python tools/docs-size-check/check_size.py` reports 13 files checked, 0 over.

**`docs/migration-notes.md`** - one entry at the end of *Custom C# extensions*, beside the three sibling ownership entries. Nothing changes for a D4 script; a custom C# node that passes a value to `IfNil` and reads that same value afterwards must copy it first.

## Review findings

Read `ticket(implement): bug-ifnil-leaks-the-value-it-copies` before the handoff summary.

**Correctness of the fix: confirmed.** Both operands of `IfNil` really are `const` (`create operator IfNil(const ANilableValue : generic, const AReplacementValue : generic)`, `src/engine/DAE/Schema/SystemCatalog.d4`), and `IfNilNode.DetermineDataType` calls `base.DetermineDataType`, so the `const` branch does ask each argument node to lend - which is what makes `ReturnsByReference` meaningful at this site. The judgement call the handoff flagged for a second opinion - reading `ReturnsByReference` off whatever is in `Nodes[index]` at run time, after a conversion may have replaced it - holds: a conversion node answers `ReturnsByReference` false and its own `const` cleanup leaves the inner lent value alone, so the wrapper's result is the call's own either way. A `ValueNode` (a stored constant) answers false and would be released, but that is the established rule at every other `const` operand, not something this site introduces. No new coverage was added for the conversion path, for the reason the handoff gave: no conversion between two stream-backed types exists to reach it.

**Fixed in this pass - the copy could raise and orphan the value (minor).** `DataValue.CopyValue` was called outside any `try`, so a copy that raised part way through - over a row or list of stream-backed columns it copies element by element - left the value this node owns released by nobody. Strictly better than before the fix, which leaked unconditionally, but it is the same error path the engine has already been taught to honour once (`InstructionNodeBase.ReleaseUncalledOperand`, for a call whose later argument raises). The copy now sits in a `try` and the release in its `finally`, which also makes the copy-before-release ordering structural rather than a matter of statement order, and removes the `copy` local.

**Fixed in this pass - two inaccurate comments (minor).** The class comment gave the signature as `IfNil(AValue : generic, AValue : generic)`, omitting the `const` modifiers that the whole ownership rule at this site turns on, and naming both operands the same thing. And the comment inside the method said "DetermineDataType below" for an override that is above it in the file. Both corrected.

**Filed as a ticket - the same defect class at a site the handoff reasoned was closed (major).** The handoff's reason for adding no generalised test was that "only four types bypass `CleanupOperand` by overriding `InternalExecute(Program)` ... the class is closed". The count is wrong, and the architecture page had it written down as fact. There are thirteen operator nodes of that shape, and `TableNode` - one of the four named - is not among them (its *subclasses* override the entry point; it does not). The nine the list missed all derive from one of the five argument shapes and re-override the entry point, so they read as ordinary instruction nodes while skipping their shape's own cleanup call.

  Two of the nine leak. `RowEqualNode` (`src/engine/DAE/Runtime.Instructions/RowComparisonNodes.cs`) misses both halves of the rule: its `DetermineDataType` calls `DetermineModifiers` instead of `base.DetermineDataType`, so nothing asks either argument node to lend and both copy the row, and its `InternalExecute(Program)` override then releases neither copy. Measured on a throwaway `InProcessTestFixture` case reading `Diagnostics.StreamCount()`: ten comparisons of `row { X : Binary }` left 20 streams behind, whether the rows were computed or read out of a variable; two stream-backed columns left 40; one `Binary` plus one `Integer` left 20; and column equality, row assignment and a discarded row selector each left none. Asking the two argument nodes to lend took the variable shape to 0 and left the computed shape at 20 - exactly the split the two missing halves predict - which attributes the defect precisely. `CompoundScalarEqualNode` has the identical shape and `const` operands, read rather than measured. Filed as `tickets/fix/4.97-bug-row-equality-leaks-the-rows-it-compares.md`, which carries the reflection check over the whole set as its class-level arm, per *Architecture first*: the set was counted by hand, counted wrong, and a hand-maintained list will miscount again. The probe and the experiment were both reverted; the working tree holds only the four files this ticket owns plus the new ticket.

**Checked and sound, so nothing done.**

  - *The tests.* Both earn their place under this project's rule (a bug fix owes its reproduction) and the second is not redundant with the first: it covers the other arm of the `if (!chosen.ReturnsByReference)` branch, which is the arm the wrong fix breaks, and the handoff verified each fails for exactly one of the two mutations. Neither mocks anything the repository owns. No test was cut and none added - the defect this review found needs its reproduction in its own ticket, beside the fix, not here.
  - *Double release.* Nothing else releases an `IfNil` argument: the node is the instruction node itself, so no shape's `CleanupOperand` runs for it, and an argument node that lends (`StackReferenceNode`, `StackColumnReferenceNode`, `ExtractColumnNode`) answers `ReturnsByReference` true and is skipped.
  - *`IfNil(nil, nil)`.* Both `CopyValue` and `DisposeValue` fall through for a null, as the comment claims - checked in `src/engine/DAE/Runtime.Data/DataValue.cs`.
  - *Short-circuiting.* The second argument is still evaluated only when the first is nil; the fix did not change that.
  - *Idiom.* The hand-applied rule matches the four existing sites that do the same thing (`ForEachNode` in `ImperativeNodes.cs`, and `ListNode`, `ListForEachNode` and `TableForEachNode` in `ListNodes.cs`), including the guard and the reason for it.
  - *Docs.* Every file the change touches was read rather than assumed current: the `docs/migration-notes.md` entry describes the new behaviour accurately and no new entry is owed for the review's own change, which is an error path that previously leaked and is covered by the same claim. `docs/architecture/value-lifetime.md` was checked and needs nothing - it covers a value in a slot, a row or a list, not an operand.
  - *Source hygiene.* `SystemNodes.cs` is still tabs, CRLF, no byte-order mark; the test file still tabs, CRLF, UTF-8 byte-order mark; both docs still CRLF with no lone line feeds. No file was reformatted or re-encoded.
  - *`Graphic` is not covered, only `Binary`.* Left as the handoff described it. The two are the same code path through the value manager and every existing case in the fixture is `Binary` for that reason; adding a parallel `Graphic` case would test the value manager twice rather than this node once.

**Recorded as a tripwire, not a ticket.** `AssignmentValueOwnershipTest.cs` is 1,333 lines with a fifty-line class summary that every ownership ticket extends, and three sibling tickets still have cases in flight against it. A `NOTE:` above `[TestFixture]` says to split it by the three rules the summary already names - a slot, a call's operands, a scope - if it outgrows roughly 1,500 lines, and says why the split is deferred for now.

**No accepted-tradeoff `NOTE:` was overridden.** The sites touched carry none, and `src/engine/DAE/Runtime.Instructions/RowComparisonNodes.cs` carries none either, so the new ticket is not re-filing a decision a human already made.
