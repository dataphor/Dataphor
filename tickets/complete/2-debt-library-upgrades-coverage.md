## What landed

One new D4 coverage script, `tests/libraries/TestFramework.Coverage.Scripts/Documents/LibraryUpgrades.d4` (425 lines, 9 sections), its one entry in `tests/DAE.Server.Tests/coverage-manifest.json`, three paragraphs on the upgrade mechanism in `docs/architecture/libraries-and-class-loading.md`, and two `NOTE:` comments in `src/engine/Server/Runtime.Instructions/LibraryNodes.cs`. **No engine behaviour change**: the C# diff is nine lines, all comment.

Implement stage: commit `ticket(implement): debt-library-upgrades-coverage`. Review added one section, corrected two comments and widened the architecture page; all listed below.

## What the script pins

One section per behaviour, each on its own library, each dropping what it created. A closing sweep asserts no library and no `LibraryVersions` row is left behind.

Two version numbers run the whole mechanism and the script keeps them apart throughout: the **descriptor** version (the `Version` column of `Libraries`, read from the library's `.d4l` file) is what the files on disk claim and is the ceiling of an upgrade run; the **recorded** version (`LibraryVersions`, which `LibraryView` exposes as `LoadedVersion`) is what the catalog believes is applied and is the floor.

| Library | What the section pins |
|---|---|
| `UpgradeArith` | Registering a library records its descriptor version as applied, so nothing is pending on a fresh register. `InjectUpgrade` returns the next revision, advances the descriptor version and carries the recorded version with it. `UpgradeVersions` lists exactly the injected upgrade; `LoadUpgrade` returns its text character for character. With the recorded version rolled back, `LibraryView` reports `LoadedVersion` and `UpgradeRequired`; `UpgradeLibrary` then applies the upgrade, records the descriptor version, clears `UpgradeRequired`, and the upgrade's table is in `CatalogObjects`. A second `UpgradeLibrary` and an `UpgradeLibraries()` change nothing. |
| `UpgradeNoRevision` | A library whose version stops at the minor cannot have upgrades tracked for it: `InjectUpgrade` raises `InvalidUpgradeLibraryVersionNumber` (113228), and the refusal comes before anything is written. |
| `UpgradeBadVersion` | An upgrade version carrying a build is refused by `SaveUpgrade` with `InvalidUpgradeVersionNumber` (113227). Then the nil-version arm of `SaveUpgrade`: it is an inject, and it advances the descriptor and writes the script at the next revision. |
| `UpgradeUnregistered` | `UpgradeLibrary` resolves the loaded library first, so a library that exists but is not registered raises `LibraryNotRegistered` (113242) - a plausible administrator mistake. |
| `UpgradeTeens` | `SaveUpgrade` with an explicit version writes the file and touches neither version number. Four upgrades at 1.0.1, 1.0.2, 1.0.10 and 1.0.11 on a library whose descriptor is 1.0.10: the trace reads `1;2;10;`, which pins version order rather than file-name order (`Upgrade.1.0.10.d4` sorts before `Upgrade.1.0.2.d4`) and pins that the upgrade above the descriptor version did not run even though `UpgradeVersions` lists it and `LoadUpgrade` returns it. The descriptor is the ceiling. |
| `UpgradeSkip` | Descriptor 1.0.5, one upgrade at 1.0.1: `UpgradeLibraries()` runs it and then records **1.0.5**, because the recorded version states which files are applied and not which scripts happened to exist. This is the behaviour a reader mistakes for a bug, and it is what lets a release skip revisions. |
| `UpgradeOrder` | The same ordering through the operator a developer uses: three successive `InjectUpgrade` calls, one `UpgradeLibrary`, trace `1.0.1;1.0.2;1.0.3;` - order, and exactly once each. |
| `UpgradeBase` / `UpgradeDependent` | Requisites are upgraded first, transitively: the dependent's upgrade appends to a table the requisite's upgrade creates, and the trace reads `base;dependent;`. |
| `UpgradeNested` / `UpgradeNesting` | **Added in review.** The two liberties `Frontend`'s shipped `Upgrades/Upgrade.2.0.8.d4` takes, neither of them covered before: an upgrade script may call `UpgradeLibrary` on a library that is not one of its own requisites, and it may discard the transaction the machinery gave it and hand back a fresh one. See *Fixed in this pass*. |
| `UpgradeFail` | **The case that matters most.** Three upgrades, the second raising on its first statement. `UpgradeLibrary` raises and carries the upgrade script's own error text out; the recorded version is left at **1.0.1** - the last upgrade that actually applied, not the descriptor version and not the version the run started from; the trace holds only the first upgrade's work; and the library is still in `LoadedLibraries`. Then `DeleteUpgrade` on the broken upgrade and a second `UpgradeLibrary`: it resumes from 1.0.1, applies only the third, and records 1.0.3. That resume is what proves the recorded version was left *usable* rather than merely unchanged, and it is the only meaningful cover for `DeleteUpgrade`. |

## The one artificial step

Each section reaches the pending state - registered, descriptor ahead of recorded - with `update LibraryVersions set { Version := ... } where LibraryName = '...';`, which stands for "the files of a newer version have arrived and the server has been restarted on them". A coverage script cannot restart its server, and `InjectUpgrade` cannot produce a pending upgrade because on a registered library the descriptor bump carries the recorded version with it. Every such line carries a comment saying what it stands for, and the script header says it is the only contrived step. Review weighed moving some sections to a C# fixture that really restarts a server and decided against it - see *Found and parked*.

## Review findings

Read the implement diff first, with the handoff set aside, then the engine sources it covers: `SystemUpgradeLibraryNode`, `InternalUpgradeLibrary`, `UpgradeUtility`, the four upgrade nodes, `LibraryUtility.LoadLibrary`, `ServerCatalogDeviceSession.GetCurrentLibraryVersion`/`SetCurrentLibraryVersion`, `SystemCatalog.d4`'s `LibraryView` and the registered operator signatures, and the coverage harness (`CoverageScripts.cs`, `CoverageManifest.cs`). Every claim the script's header and the new architecture paragraphs make was checked against those sources; three mutations were built and run, then reverted.

### Checked and sound

- **Every assertion in the script bites.** The equality assertions cannot be vacuous (a wrong value fails them), and the five error assertions cannot pass silently either: an operator that failed to raise leaves `LCaught` empty, `IndexOf` returns -1, and the assertion fires. The trace assertions are non-vacuous by construction - each dependent upgrade appends to a table an earlier upgrade creates, so an upgrade run out of order fails to compile rather than producing a wrong string. The implement stage's own two sensitivity checks (the `UpgradeTeens` ordering expectation, and removing the manifest preamble) were taken as reported and not re-run; review spent its mutation budget on the new section instead.
- **The header's five corrections to the planning ticket's recipe are right.** Rooted names do resolve across libraries (`Objects<T>.ResolveName` applies the library resolution path only to unrooted names), so the batching explanation - a script is executed one top-level statement at a time and each is compiled only when reached - is the real reason each section is "a block that does the work, then a bare assertion", and no `SetLibrary` is needed. `VersionNumber` does have a four-argument selector. `SaveUpgrade(name, nil as VersionNumber, script)` does reach the inject arm (`arguments[1] == null` in `SaveUpgradeNode.InternalExecute`). `SetLibraryDescriptor` does refuse to raise a registered library's version.
- **The error codes and messages are asserted in the same style as the sibling script.** `LibraryAdministration.d4` already asserts `":<code> --->"` plus a message fragment out of `GetDetailedErrorDescription()`; the new script follows it and explains why it does not assert the quoting of a library name.
- **No cross-script pollution.** Each coverage case runs on its own copy of one template instance (`CoverageScripts`), so the libraries a failed run would leave behind cannot reach another script. The manifest's `preamble` support, its ordinal-position rule and the 120 s default timeout were read rather than assumed.
- **Resource cleanup in the code under test.** `UpgradeLibrary`'s nested session, process and program are each released in a `finally`, and `InternalUpgradeLibrary` unprepares its plan in one; a failing upgrade leaks none of them. No new test - there is nothing a D4 script could assert about it.
- **Source hygiene.** CRLF and no byte-order mark in the `.d4` file, matching its siblings; CRLF with the mark preserved in `LibraryNodes.cs`; CRLF in the architecture page. Nothing reformatted or re-encoded. The script is 425 lines against `LibraryAdministration.d4`'s 342 - in range for this directory and for a subject this size.
- **No migration note is owed.** No public type or member, D4 semantics, class name, file format, error code or contract shape changed.
- **`library-ddl-inside-a-transaction` is unaffected either way.** That plan ticket proposes making `DropLibrary` refuse inside an *explicit* transaction. This script drops its libraries with no transaction open at all, so the guard as proposed leaves it alone. Recorded as an arm on that ticket (below) rather than repeated here.

### Fixed in this pass

- **Two shipped upgrade-script patterns had no cover, and one of them is a real contract.** `libraries/Frontend/Upgrades/Upgrade.2.0.8.d4` - the only upgrade script in the product that does anything unusual - opens with `RollbackTransaction()`, registers and upgrades `System.Internet`, and closes with `BeginTransaction()`. Nothing in the script covered either half, and both are the kind of thing that breaks silently: a future change to `InternalUpgradeLibrary`'s transaction handling would break a shipped upgrade with no test to say so. Added the `UpgradeNested`/`UpgradeNesting` section, which pins that an upgrade script may upgrade a library that is not one of its requisites and see its effects, and that it may replace its own transaction. Measured, not assumed: removing the closing `BeginTransaction()` fails the case with `ServerException: No transaction in progress for this process` - the machinery records the version and commits on the script's own process after the script returns, so a script that leaves its transaction and does not open another fails after its work has already been committed.
- **A causal claim I wrote in that section's comment was wrong, and is now the measured one.** The first draft said the opening `RollbackTransaction()` is what releases the catalog store's write lock and so is what lets the nested `UpgradeLibrary` run. Removing it leaves the case green: the transaction the machinery opens has written nothing to the catalog store at that point and therefore holds no write lock on it, which is also why this differs from the harness's implicit transaction that the manifest preamble exists to avoid. The comment now states both measurements with their date and claims nothing else about why the shipped script rolls back.
- **The architecture page said nothing about either contract, and was silent on partial failure across libraries.** Added a paragraph on what an upgrade script may do, including the must-leave-a-transaction-open rule and the nested `UpgradeLibrary` that `Frontend` relies on, and extended the `UpgradeLibraries()` sentence: it runs in requisite-first order and stops at the first library whose upgrade fails, leaving the libraries after it in that order un-upgraded at their own recorded versions, with nothing saying which they were. That last is read from `UpgradeLibraries(Program, string[])`, which has no catch around its loop; it is not run, and there is no test for it (see *Found and parked*). The page is 742 words of its 1,500-word cap; `python tools/docs-size-check/check_size.py` reports 11 files checked, 0 over the limit.
- **A stale operator signature in a comment.** The header comment on the live `UpgradeVersionsNode` declared `System.UpgradeVersions(const ALibraryName : Name, const ACurrentVersion : VersionNumber, const ATargetVersion : VersionNumber)`; the registered operator takes one argument (`SystemCatalog.d4:915`) and the node reads only `Nodes[0]`. One-line correction, in the file and the region this diff already touches, and it matters more now that a new `NOTE:` a few lines above refers the reader to "the second `UpgradeVersionsNode` below", which is the commented-out one.

### Found and parked

- **Nothing pins that a server restart preserves a pending upgrade, and that is the assumption the whole script rests on.** `LibraryUtility.LoadLibrary` reads the recorded version before loading and writes the same value back afterwards, deliberately, so that a restart does not swallow a pending upgrade (`src/engine/Server/Schema/LibraryUtility.cs`, the `GetCurrentLibraryVersion` at the top and the `SetCurrentLibraryVersion` at the bottom). The coverage script has to stand in for a restart by updating `LibraryVersions` directly, so if that read-and-write-back ever regressed, nothing would catch it and the script's premise would quietly become false. Not a new ticket: `feat-ws7-devices-and-libraries`'s `library-upgrade-scripts` work item already owns this subject, and it is recorded there as the remainder of that item, together with the second gap - no upgrade here carries a realistic payload (a device, an assembly, a form document) rather than one small memory-device table. A C# fixture that restarts a server is the shape, with `tests/DAE.Server.Tests/LibraryAttachTest.cs` as the precedent.
- **The partial-failure behaviour of `UpgradeLibraries()` across several libraries is now documented but untested.** One library's failure aborts the rest. Covering it means a section with two independent pending libraries, the first failing, and assertions on which recorded versions moved - a reasonable future addition, but a different behaviour from the single-library failure the `UpgradeFail` section pins. Parked with the item above rather than filed.
- **`LoadUpgrade` on a version with no file throws a raw `FileNotFoundException` carrying a server file path, while `DeleteUpgrade` on the same missing file is silently a no-op.** Left alone deliberately and not filed: the behaviour is unchanged from 3.1, the IDE is the only caller that can reach it, and both the message and the silence are themselves a compatibility surface, so a test here would freeze an unhelpful message and a change would need its own ticket.
- **A refused `SaveUpgrade` still creates the library's empty `Upgrades/` folder** - `EnsureUpgradeDirectory` runs before the version is validated. Harmless, and asserting it would pin a wart; mentioned here so the next reader does not spend time on it.
