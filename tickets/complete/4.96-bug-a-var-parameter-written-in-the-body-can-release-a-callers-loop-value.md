## What landed

An operator parameter declared `var` gives the callee a slot that is an alias of the caller's: nothing is copied, and whatever the callee leaves in the parameter is written back to the caller's variable when the call returns. A body that assigns to such a parameter therefore releases the value it displaced, which is right while the caller's slot owns that value - the ordinary case. A `foreach` loop variable does not own its value: the loop lends its slot the row or element the iterator owns and goes on reading it. So where the caller passed its own loop variable, the callee's assignment released a value the loop was still using and the next iteration read a released one - `A nil was encountered where a value was expected` over a cursor, `StreamID (n) not found` over a list. Neither end could see it alone: the mark that says a slot holds a value it does not own (`Symbol.IsBorrowed`) is compiled per plan, and an operator is compiled once, independently of its call sites.

The fix gives the callee a slot it really owns. Where the argument of a `var` operand names a borrowed caller slot, the call pushes a copy; the callee's own assignments, and any `foreach` inside it, then release that copy, and the caller's loop keeps the row or element the iterator owns. Four code sites, exactly as the implement ticket's design named them - `StackReferenceNode.ReferencesBorrowedSlot`, the `Modifier.Var` branch of `InstructionNodeBase.DetermineDataType`, `Stack.IsSameValue` made public, and the push loop and `finally` reconcile of `CallNode.InternalExecute(Program, object[])`. `AssignmentNode`, `ForEachNode` and `CleanupOperand` are untouched. The implementation is `ticket(implement): bug-a-var-parameter-written-in-the-body-can-release-a-callers-loop-value`; the review pass is the commit after it.

One characterization case, `AssignmentValueOwnershipTest.AVarOperandGivenTheCallersLoopVariableLeavesTheLoopsValueAlone`, covers the defect in five shapes: three balance outright (a cursor and a list where the operator only reads, and a `foreach` inside the callee over the `var` parameter), and two that assign are measured against the equivalent direct assignment to a loop variable, because the residual leak is the accepted tradeoff on the borrowed branch of `AssignmentNode`. `docs/architecture/operand-ownership.md` carries the rule and the mechanism; `docs/migration-notes.md` carries one `done` entry beside the entry whose closing claim it corrects.

## Review findings

### Read first, then the handoff

The implement diff was read before the handoff summary, and the four sites were checked against the code around them rather than against the ticket's description of them: `Stack.PokeOwned` and `ReleaseAbove`, `Stack.PopWindow` (which nulls without releasing, so a disposed copy left in an operand slot is simply dropped), `InstructionNodeBase.CleanupOperand` and `ReleaseUncalledOperand`, `DataValue.CopyValue` and `DisposeValue`, `ServerStreamManager.Reference`, `ForEachNode.InternalExecute` in both branches, and the two compiler sites that set `Symbol.IsBorrowed`. The compile-time ordering holds: both `foreach` compile paths set the mark before the body is compiled and restore it after, so a call inside the body sees it and a call after the loop does not.

### Found and filed as a ticket: one

**A cursor `foreach` does not restore its loop variable's slot between turns**, so anything that writes the loop variable makes every later turn read the written value instead of the row it is on - silently, with no error and nothing left behind. Filed as `backlog/bug-a-cursor-loop-variable-stays-stale-once-written`.

Measured with a throwaway case on `InProcessTestFixture` (added, run, removed): a two-row cursor loop that assigns to its variable on the first turn reports `99` where the list equivalent reports `92`. The root cause is one site - `ForEachNode.InternalExecute`'s cursor branch stores its row into the slot *before* the iteration and then refills that same row object in place, where the list branch stores into the slot once per turn - and the invariant it is missing is the one the list branch has: the loop variable's slot holds the loop's current row at the top of every turn. It went to `backlog/` rather than `fix/` because closing it changes what a D4 script observes, which on this project is a decision rather than a patch; the ticket carries `severity: wrong-result`, `likelihood: unusual` and the decline argument.

**It is pre-existing, not introduced here** - a plain assignment to a cursor loop variable has always done it, measured identically. But this fix does make it reachable through a second route (the `var` write-back, where the shape used to raise instead), and three statements written in this ticket and one older one assert the opposite of what happens, which is the next finding.

### Found and fixed in this pass: one, in five places

The claim that **"the next iteration overwrites it"** is false over a cursor, and it was load-bearing: it is the justification both for calling an assignment to a loop variable harmless and for the shape of the accepted-tradeoff leak. Corrected to say what the two loop branches actually do, in:

- `docs/migration-notes.md`, this ticket's new entry - the paragraph an application author reads to find out what changed said the next iteration overwrites the written value "as before". It now distinguishes the list case from the cursor case and names the new backlog ticket.
- `docs/architecture/operand-ownership.md`, the `var` bullet's second paragraph - same correction. The page is **1,417 words of the 1,500 cap**, up from 1,392; `python tools/docs-size-check/check_size.py` reports 13 files checked, 0 over.
- `AssignmentNode`'s borrowed-branch `NOTE:` - both the older sentence and the one this ticket added. This is the accepted-tradeoff record for the leak, so it now states the leak's actual mechanism (the next plain store into the slot, or the loop nulling it on the way out) and what a cursor loop's variable reads afterwards.
- `CallNode`'s reconcile `NOTE:`, the same sentence.
- `AssignmentValueOwnershipTest`'s class summary and the new case's own remark.

No behaviour changed for any of this; the code was right and the prose describing it was not.

### Found and recorded at the site, not filed: two

- **The one-borrowed-variable-passed-twice shape**, which the implement ticket left reasoned rather than tested and asked for a second opinion on. Measured, same throwaway case: `F(var LB, var LB)` over a list of two `Binary` leaves **two streams per iteration when the body assigns both - exactly what the two direct assignments to the loop variable it stands in for leave - and none when the body assigns neither, with the loop still reading its own element**. The ordering is right, and the reason is sharper than the ticket's: the two orders are *indistinguishable* when the body assigns, and differ only on the read-only shape, where the repeat arm's copy is not reconciled and the write-back would hand the caller's loop variable that copy and orphan the element the loop lent. The measurement and that reasoning are now in the comment at the ordering site. No test: the shape is a call that always loses one of its two writes, the fixture is already over its size threshold, and a comment carries the finding where the choice is made.
- **The push loop has no failure path of its own.** If `DataValue.CopyValue` threw part way through it, on either arm, a copy already pushed is nulled by the window pop rather than released - one leaked stream on a path that is already unwinding. The implement ticket decided against recording this; the decision looks right, but the code said nothing, so there is now a `NOTE:` on the `borrowedCopies` declaration giving the condition, why nothing guards it, and the fix if either arm is ever seen to throw there.

### Checked and found nothing: the rest

- **Ownership arithmetic on every path.** The reconcile's two branches are correct for a copy that survived, a copy the body replaced, a body that raised before writing (0 streams), a body that assigned and then raised (1, equal to the per-iteration baseline), a self-assignment of the parameter to itself (`PokeOwned` short-circuits on the same value, and the reconcile then disposes the copy once), a nil loop value (a copy of nil is nil, `IsSameValue(null, null)` is true, `DisposeValue(null)` is a no-op), and nested loops over one variable (8 streams over 4 calls, consistent, no crash).
- **Values whose copy is reference-identical to the original.** `CopyValue` returns the same reference for an immutable native (a `String` via `ICloneable`, a boxed scalar via the fall-through), which would make `IsSameValue` answer "unwritten" for a value the body did write. Harmless in every case, because `DisposeValue` is a no-op for exactly those values and every value that needs releasing - `IDataValue`, `StreamID`, `NativeRow`, `NativeList`, `NativeTable` - is genuinely allocated by `CopyValue`. `ServerStreamManager.Reference` returns a *new* `StreamID`, which is what lets `IsSameValue`'s by-value comparison tell the copy from the original.
- **Table-typed `var` operands**, which the implement ticket measured and asked for a second opinion on. Re-probed independently: a `foreach` over a list of two stream-backed tables passing the loop variable to a `var` table parameter left **0 streams** both read-only and assigning. The ticket's conclusion stands.
- **No other construct lends a slot a `var` operand could name.** `Symbol.IsBorrowed` is set only by the two `foreach` compile paths; the aggregate and list iteration slots `Stack.PokeOwned` mentions are row-context columns, which compile to something other than a `StackReferenceNode` and so cannot be a `var` argument at all (the `var` branch raises `ConstantObjectCannotBePassedByReference` otherwise). `Modifier.Out` exists in the language enum but reaches only the client and native-CLI parameter surfaces, never this switch.
- **Interaction with the surrounding cleanup.** `releaseDepth` is read before the result slot is pushed, so `ReleaseAbove` never walks down into the operand slots, and the disposed copy left in one is dropped by `PopWindow`. `CleanupOperand`'s `var` branch runs `ValueUtility.ValidateValue` on the caller's own value on the unwritten path, which is exactly what it did on that path before the fix.
- **Hygiene.** `ImperativeNodes.cs` and `AssignmentValueOwnershipTest.cs` still tabs, CRLF, UTF-8 byte-order mark; `InstructionNode.cs` and `Stack.cs` still tabs, CRLF, no mark; both docs still CRLF, no mark; every file still ends in a newline; the test project file is byte-identical to where it started (a probe fixture was added to it and removed). `git diff --check` reports the CR of every added line, which is what it does for every commit here.
