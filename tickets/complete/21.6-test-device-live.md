## What landed

`DATAPHOR_TEST_MSSQL` gates every pass in the suite that needs a live SQL Server, and `TestEnvironment` is the one place that reads and parses it.

**`TestEnvironment`, new region "The configured SQL Server".** `MSSQLConnectionString` (null when unset or empty), `MSSQLConfigured`, `MSSQLNotConfigured(whatWouldRun)` for the skip message, `MSSQLConnectionStringFor(database)` (parsed with `SqlConnectionStringBuilder`, the database substituted), `MSSQLDeviceAttributes(database)` (the D4 attribute list for a SQL Server device: server name, database, integrated security or user and password, and an `Encrypt`/`TrustServerCertificate` the variable names carried as the device's `ConnectionParameters`), `EmptyMSSQLDatabase(database)` (creates the database if absent, drops every foreign key and table) and `ExecuteOnMSSQL` for a pass's own housekeeping statement. Nothing connects in order to decide whether to connect: the variable being set is the only test anything makes.

**A fifth coverage-manifest status, `needs-database-server`.** Unconfigured: Inconclusive with the reason. Configured: the runner empties this pass's own database (`DataphorCoverageScripts`), registers `MSSQLDevice`, and prepends a device-creation preamble - `SetLibrary('TestFramework.Coverage.Base'); create device CoverageDevice reconciliation { mode = { command }, master = device } class "MSSQLDevice.MSSQLDevice" attributes { ... };` - before the entry's own preamble, and the script must pass. `ticket` and `error` are not allowed on the status. `MSSQLDevice` joined `CoverageScripts.Libraries` so its folder is carried; nothing registers it unless an entry asks, and `CheckNoExternalDevice` still holds the template to needing no database (K14).

The three entries `Transaction.Atomicity.TestMSSQL`, `TestDAEMSSQL` and `TestMSSQLDAE` moved to it from `known-failure` and the retiring slug `feat-ws7-devices-and-libraries` is gone from the manifest. All three pass on SQL Server 2016 LocalDB.

**`LiveDeviceTest`** (new). It builds a server carrying eight library folders, registers `Frontend`, `TestFramework`, `MSSQLDevice` and `TestFramework.Coverage.Base`, creates the two devices `TestFramework.Coverage.Devices` needs in `TestFramework.Coverage.Base`, registers that library and starts the device under test, then runs `TestMSSQLDevice` on a session whose default library is the corpus library and reports the whole roll-up. It is recorded as a **known failure against `test-pre-3-1-scripts-policy`**, because the script's third statement cannot succeed on any version: it raises an error naming every catalog object called `TestFramework.Coverage.Devices.TestDevice`-something, and the library's own `Logic.d4` creates an operator `TestDevice(Name, Integer)` whose catalog name is exactly that. A third arm on that ticket carries the evidence and the proposed one-statement change; the script itself was not edited.

**The two D4 documents.** The `SafeDrop`/`create device` block came out of `TestMSSQLDevice.d4` and the `create device` out of `DeviceMSSQL.d4`, each replaced by a comment saying where the device comes from now. Nothing else in either file changed.

**`SamplesCorpusTest`.** The three SQL Server samples are attempted where a server is configured instead of being skipped unattempted, and each is held to the failure it gives. **`StoreRebuildWorkflowTest`.** The retiring slug is gone; the remark records the decision that the SQL Server libraries stay out and names the gap that remains.

**CI.** A `Start SQL Server LocalDB` step with `continue-on-error`, and `DATAPHOR_TEST_MSSQL` set on the Test step only when that step succeeded, so a runner image that has dropped LocalDB leaves the live cases Inconclusive rather than failing the run.

**Documentation.** `AGENTS.md` (the variable's whole scope as a list, the fifth status, the skip inventory, the sample-corpus paragraph), `docs/migration-notes.md` (the stale `TestingDevice` entry corrected and a new entry for the two scripts), and the `test-device-live`, `test-samples-corpus`, `test-decouple-coverage-base`, `device-mssql-port`, `library-sample-shipping-convert`, WS2 audit and WS4 rebuild-workflow passages of `docs/modernization-plan.md`.

What the live run closed from `device-mssql-port`: the device's server-side cursor path is now driven (every device read whose statement begins with `select` takes it, and three coverage scripts read from a live SQL Server device), and a device's `ConnectionParameters` was proved to override the device's own `Encrypt=False` default on a real connection. What it did not close: no SQL Server reachable over a network with an untrusted certificate was available, so that `Encrypt=False` is what such a server needs is still unproved and passes to `device-sqlserver-version-matrix`.

The implement stage is commit `ticket(implement): test-device-live`. Review changed five things in that work, filed no ticket, and parked two concerns as tripwires; all of it is below.

## Review findings

The implement diff was read first, with the handoff set aside until afterwards. Checking was by reading `TestEnvironment`, `CoverageScripts`, `CoverageManifest`, `LiveDeviceTest`, `SamplesCorpusTest`, `StoreContractTests`, `MSSQLTextParameterTest`, the two edited D4 documents and the two `Device.d4` files beside them, the workflow, and `docs/architecture/catalog-and-store.md`; and by running the passes in both configurations against SQL Server 2016 LocalDB (13.1.4001.0).

### Fixed in this pass

- **The claim that the variable is read in one place was not true, and two documents asserted it.** `MSSQLStoreContractTests` and `MSSQLTextParameterTest` each kept their own `private const string ServerVariableName = "DATAPHOR_TEST_MSSQL"`, their own `Environment.GetEnvironmentVariable`, their own skip message, and - in the store contract's case - its own `ConnectionStringFor` (a `DbConnectionStringBuilder` that removed `Database` and set `Initial Catalog`) and its own three-line `Execute` helper, both duplicates of `TestEnvironment`'s. `AGENTS.md` ("It is read in one place, `TestEnvironment` ... so nothing else parses it") and the plan's `test-device-live` row both stated the single reader as a fact. Both fixtures now go through `TestEnvironment.MSSQLConfigured`, `MSSQLConnectionString`, `MSSQLNotConfigured`, `MSSQLConnectionStringFor` and `ExecuteOnMSSQL`, which was private and is now public for that one use; the store contract keeps its own `DropDatabase` and `DropTables`, which are its policy rather than shared plumbing. Fixing the code rather than the sentence, because the single reader is the design the ticket set out to build and a third fixture would otherwise copy the pattern. Proved live: the store contract's 15 cases and the parameter fixture's 6 pass against LocalDB through the shared parser, and both still skip with the shared message when the variable is unset.
- **`LiveDeviceTest`'s known-failure match was loose enough to swallow a regression.** It accepted any error containing `TestFramework.Coverage.Devices.TestDevice`, which an error raised anywhere inside the corpus operator would also contain - so a real failure in the 1180 cases could have been reported as the recorded known failure and the run would have stayed green. It is now a pattern that requires the object id, `TestFramework\.Coverage\.Devices\.TestDevice[0-9]+`: what the broken statement prints is a row of `Objects.Name`, which is the operator's name with its object id appended, and only the catalog spells an operator that way (an error from inside the corpus names the operator by its signature, or names a table). Verified: the live run still matches, on `TestFramework.Coverage.Devices.TestDevice0000018614`.
- **A `NOTE:` called a documented design rule a probable defect.** The note at `LiveDeviceTest.Registration` said that a SQL device started inside the script's single transaction has no rows in `DeviceOperators` for the rest of that transaction, that this "looks like a defect rather than a rule", and that a reviewer who could name the site should file it. The site is named and it is a rule: a D4 query over a catalog table the store answers (`CatalogDeviceTable`) opens a connection of its own and sees committed data only, never the calling transaction's uncommitted store writes - `docs/architecture/catalog-and-store.md`, "Store transactions", and the same sentence is already in `docs/migration-notes.md` as behaviour unchanged from 3.1. The script's next statement is exactly such a query (`if not exists (DeviceOperators where Device_Name = ObjectName('TestDevice'))`). The note now says so and cites the page. **No ticket**: nothing is wrong.
- **Two lists that had to agree, with a test asserting that they did.** `NeedsADatabaseServer` (name to reason) and `FailsWithADatabaseServer` (name to expected error) were separate dictionaries, and a new clause of `EverySampleIsAccountedFor` asserted that they held the same keys. One dictionary of `(string Reason, string FailsWith)` makes the disagreement unrepresentable, so the clause went with it - a test that existed only because of the representation. The three samples still report the same text in both configurations; `Lists()` now yields each list's `Keys`, which is all its two assertions use.
- **Two stale documentation passages the change should have touched.** `AGENTS.md`'s sample-corpus paragraph still said the three SQL Server samples are "reported Inconclusive without being attempted" and that the pass takes about 37 s, and the plan's `test-samples-corpus` row said the same - both written before this ticket made the attempt real. Both now say what happens in each configuration and carry the measured 1 m 40 s configured figure. The paragraphs the implement stage did rewrite (the `DATAPHOR_TEST_MSSQL` list, the coverage-script paragraph, five plan rows) were checked against the code and are accurate.

### Checked and sound

- **The unconfigured path costs nothing and reaches no server.** The three live coverage entries take 3 ms, 0 ms and 0 ms unconfigured and `LiveDeviceTest` 20 ms, because the only test made is whether the variable is set. Measured again here: the targeted fixture set is 30 passed and 25 skipped in 17 s unconfigured.
- **Carrying the `MSSQLDevice` folder for all 147 coverage servers disturbs nothing.** Coverage part one, which the implement stage did not measure, is 72 passed and 11 skipped in 3 m 33 s against the 3 m 28 s recorded in `AGENTS.md` before the folder was added; part two was measured by the implement stage at 52 passed either way. The template still refuses an external device (`CheckNoExternalDevice`, K14).
- **The manifest's new status is held to the same bargain as `pass`.** `Evaluate` shares the `Pass` arm, and the validator refuses `ticket` on it and (through the pre-existing rule that `error` belongs only to `known-failure`) refuses `error` too, so the status cannot quietly become a second known-failure channel.
- **The two D4 documents lost only the device creation.** Read whole, against the diff: `DeviceMSSQL.d4` still runs `SetDefaultDeviceName("TestingDevice")`, which is why registering the corpus library needs the device to exist first, and `TestMSSQLDevice.d4` still begins at `EnsureDeviceStarted('TestDevice')` with every assertion after it untouched. `Device.d4` in both libraries is consistent with the comments that now stand in the removed blocks' place.
- **The CI step fails safe.** `continue-on-error` with `steps.localdb.outcome` is the right pair - `outcome` is the result before `continue-on-error` is applied, so the variable is set only when LocalDB really started - and a missing `sqllocaldb`, a missing instance or an instance that does not report Running all leave the variable empty and the live cases skipped.
- **The claimed measurements were reproduced**: the three atomicity scripts pass configured (5 s each), `LiveDeviceTest` fails as recorded, the three sample attempts take 19-20 s each (58 s of a 1 m 40 s pass), and VSTest does not count an Inconclusive case, which is why the configured sample pass reports 11 passed and 3 skipped out of a "total" of 14.

### Parked as tripwires, not tickets

- **A password in the variable reaches the test server's catalog in clear text**, because it becomes an attribute of the device definition, and a run kept with `DATAPHOR_TEST_LOGGING=1` leaves that catalog on disk. Conditional: the values these passes are pointed at use integrated security. A `NOTE:` at `TestEnvironment.MSSQLDeviceAttributes` says what to do instead if a pass ever has to reach a server through a SQL login whose password matters (create the device with a device user rather than putting the password in the definition).
- **`needs-database-server` cannot also record a known failure.** Nothing needs that today - all three such scripts pass - and the implement handoff weighed it only in prose, which would have gone when the ticket was archived. A `NOTE:` at the validation site now records it, with the recommendation: if a fourth such script arrives failing, add a field orthogonal to the status rather than letting this status carry `ticket` and `error`.

### Weighed and left alone

- **The current library is left at `TestFramework.Coverage.Base` for the three live scripts.** Judged acceptable. The reason is in the code and was tested by the implementer: the engine refuses a reference from an object in `General` (which requires nothing) to a device in a library `General` does not require, and the scripts spell the device `Coverage.Base.CoverageDevice`, which resolves only as a suffix of its real name. Each script runs on a server of its own, so nothing else can see the difference.
- **Two databases are left on the configured server** (`DataphorCoverageScripts`, `DataphorDeviceCoverage`), emptied at the start of each pass and never dropped. The accepted-tradeoff reasoning at `EmptyMSSQLDatabase` - what the device left is the evidence of what the device did - stands, and the fixed names carry the same shared-resource `NOTE:` the store contract's database has.
- **The three sample attempts cost 58 s per configuration** to establish only that the failure is the recorded one. The ticket asked for the attempt explicitly and the tradeoff is recorded as a tripwire at the site; left as the first place to look if CI wall clock has to come down.
- **`AttemptTheSampleThatNamesItsOwnServer` repeats three lines of server construction** from the ordinary case. Too small to extract; the two bodies diverge immediately afterwards.

### Not done, and why

- **The device-coverage corpus itself still does not run.** One statement, one owner decision, on `test-pre-3-1-scripts-policy`. Behind it: 1180 cases, of which 8 to 12 fail in four families, triaged on `bug-mssql-device-live-coverage-failures` and as arms of `bug-binary-comparison-needs-the-mssql-device` and `bug-mssql-device-text-columns-lose-characters`.
- **The CI step is still unverified on a runner.** It was read off the image manifest, not run. The first CI run after this lands is the measurement: read the `Start SQL Server LocalDB` step's output and whether it was yellow, and the added wall clock against the estimate of about 95 s per configuration.
- **A SQL Server reached over a network with an untrusted certificate**, and **a SQL device's own catalog entries surviving a catalog restart** (named in `StoreRebuildWorkflowTest`'s remarks as the place to add it). Both out of scope and recorded with their owners.
