## What landed

Decision **D17** in [modernization-plan.md](../../docs/modernization-plan.md#decisions): 4.0 provides no transport security. The secured-connection settings are neither made to work nor removed — each of the three surfaces that offers one now gives the strongest honest response available at that surface, and a site that needs an encrypted channel still supplies its own binding through the client and host hooks, which is the only route there has ever been. Transport security as a designed capability moves to WS11 (`security-transport-design`, `security-transport`).

| Surface | Setting | Response |
|---|---|---|
| A client connection — a connection alias, or an extension building `ClientServer` / `NativeCLIClient` directly | `SecurityMode`, `ListenerSecurityMode` | **Refused**: `NotSupportedException` naming the setting and both remedies, thrown before any unsecured call is made |
| A hosted instance | `requiresecureconnection`, `requiresecurelistenerconnection` | **Warned** once in the instance's own log as it starts; the server starts anyway |
| A D4 server link | the tags `UseSecureConnection`, `UseSecureListenerConnection` | **Warned** once in the server's log per remote session; the link connects unsecured |

Each response is silent where a site has replaced the relevant binding hook, which is what `HasCustomBinding` is for on both halves: the product must not report a channel it did not build as unsecured. `src/engine/DAE/Schema/ServerLink.cs` is untouched, so the tags keep being read, keep their meaning, and keep round-tripping through the catalog and the D4 emitter.

One bug was fixed along the way, with its reproduction: the four-argument `NativeCLIClient` / `NativeSessionCLIClient` / `NativeStatelessCLIClient` constructor forwarded its caller's `securityMode` into the *listener's* slot and left the connection's at `Default`. Dormant while no mode was honoured anywhere; observable from this change on as the wrong setting named in a refusal, or as no refusal at all.

Documentation: `docs/architecture.md` (the hosting binding is "no security", and the posture spelled out beside the two binding hooks), `docs/users-guide/dataphor-service.md` (the warning an operator sees and what to do about it), `docs/users-guide/aliases.md` (a new paragraph under *Out-Of-Process Aliases* in the chapter's own voice), `docs/migration-notes.md` (five entries, filed by surface) and `docs/modernization-plan.md` (WS5 row Done, D17 added, Q8's answer amended, the two WS11 rows added).

Implement stage: commit `ticket(implement): protocol-transport-security`. Review changed five things, below.

## Review findings

The implement diff was read first, with the handoff summary read afterwards. The decision the ticket carried — report rather than implement or remove — was not re-opened, as the ticket directed. Everything the handoff listed under *Things already checked* was taken as given and not re-derived.

### Found and fixed in this pass

- **Reverting the client hooks did not revert the binding, so a site's own binding outlived the revert for the life of the process.** `DataphorServiceUtility.GetBinding()` memoizes the binding in `_binding` on first use, and `RevertHooksToDefault()` put `BuildBindingCall` back but left the memo holding whatever the replaced hook had returned — so every client built after the revert still connected with a binding the caller had just asked to be rid of. This is reachable today, not hypothetically: it is why the new fixture's site-supplied-binding case had to pre-warm the memo with the *product's* binding before installing its hook, to keep that hook from leaking into every fixture that runs later in the process. Fixed by clearing `_binding` inside the lock `RevertHooksToDefault` already takes — the same lock `GetBinding` double-checks under. Reproduction `TestRevertingTheHooksDiscardsTheMemoizedBinding` pins it at the lowest layer (no client, no connection) and was **confirmed to fail without the fix**: with the one line commented out and the solution rebuilt, it fails on `Is.Not.SameAs` having got the same instance back. The pre-warm's now-void second reason was trimmed out of its comment, and a `[SetUp]` added so the fixture starts from the product's hooks and an empty memo whatever ran before it. `docs/migration-notes.md` gained an entry: a custom extension that called `RevertHooksToDefault` and relied on its own binding staying in force would notice.
- **The refusal's own test could not tell which setting the message named.** `TestAConnectionAskingForTransportSecurityIsRefused` asserted `Does.Contain("SecurityMode")`, which the string `ListenerSecurityMode` satisfies too — so the assertion passed whichever of the two settings the refusal named, and naming the right one is the fixture's whole subject. Added `Does.Not.Contain("ListenerSecurityMode")`, which is what the native-CLI case already did and what caught the argument-order bug there.
- **The plan still described, in the present tense, code this ticket removed.** The WS5 *CoreWCF hosting* hand-off bullet read "the listener setting is passed to a `ListenerServiceHost` constructor parameter nobody reads, and `DataphorServiceHost` still never reads the instance one" — both false now, and that parameter no longer exists. The appended *Settled by* clause does not correct those sentences, so a reader would go looking for a parameter that is gone. Put into the past tense and attributed to `protocol-corewcf-host`, which is the state that bullet was recording; the *Settled by* clause now reads against a historical statement, as the other bullets in that list do.
- **A comment claimed the host hooks share the client's lock.** `DataphorServiceHostHooks.RevertHooksToDefault`'s remark said "The lock is the client's, where it also guards the memoized client binding", but `_syncHandle` there is that class's own object — the two classes are in different assemblies and share nothing. It landed with `protocol-host-binding-hook` and is harmless in itself, but this ticket makes the client's lock guard a clear of that memo as well, so the sentence now reads as a claim about this change. Corrected to say the lock mirrors the client's.
- **A fixture comment counted wrong.** "one case installs a client binding hook" — two do now.

### Checked and sound

- **Nothing is allocated before a refusal.** `ClientServer.Open` checks both modes before it builds a `ChannelFactory`, and the listener's mode before `ListenerFactory.GetInstanceURI`, so a refused connection makes no unsecured discovery call. `NativeCLIClient` throws from inside its own base-constructor argument, so `DataphorServiceClient`'s constructor never runs and there is nothing to dispose. `ClientObject` has no finalizer, so the test helper's `Close()` without a `Dispose()` leaks nothing.
- **The refusal reaches the caller intact.** `src/client/DAE.Client/ServerConnection.cs` wraps alias construction in `catch { CleanUp(); throw; }`, and its `ClientConfigurationName` branch throws before either mode could matter, so the mode checks sitting in `Open`'s `else` branch lose nothing.
- **Every construction site in the tree was read**, not just the ones the handoff named: `new ClientServer`, `new NativeCLIClient`, `new NativeSessionCLIClient`, `new NativeStatelessCLIClient`, `new NativeCLISession`. Outside the tests there are exactly two — the connection alias and the server link — and both are covered. `CoreWcfProtocolTest`'s two four-argument `NativeSessionCLIClient` calls pass `Default`, so the corrected argument order changes nothing for them.
- **Passing `None` for a server link changes nothing on the wire.** Every use of `ConnectionSecurityMode` in `src/` was enumerated: outside the new check it is only ever stored in a field and exposed as a property. Nothing reads it to choose a scheme, a port or a binding. So dropping the link's tags out of the `NativeCLISession` arguments is observable only through properties nothing reads.
- **The listener's mode is checked exactly where the listener is used,** and each surface's check agrees with its own branch: `_overridePortNumber == 0` in `ClientServer.Open`, matching the branch it guards, and `overridePortNumber <= 0` in `NativeCLIClient.GetNativeServerURI`, the complement of that method's own `> 0`. A negative port behaves as it did before on both.
- **`ListenerServiceHost`'s dropped parameter breaks nobody.** A tree-wide grep for `new ListenerServiceHost` — not restricted to `Dataphor.slnx` — finds the one production caller and the two in `HostBindingHookTest`. The amended migration entry is right rather than a second one, which would have had to contradict the first.
- **The memo defect above is one site, not a class.** `DataphorServiceHostHooks.BuildBinding` deliberately memoizes nothing and says so, so there is no host-side twin to fix and no invariant worth a `debt-` ticket: one hook caches, one does not, each documented at its own site.
- **The three messages read as actionable** to the person who has to act on them, which the handoff asked for. Each names the setting in the spelling that person sees — the alias-editor labels on the client, the instance file's lower-case attribute names in the instance warning, the tag names in the link warning — and each gives both remedies. The split `settingName` vocabulary between `ClientServer` and `NativeCLIClient` is right: a native-CLI caller has no alias to be pointed at, and the property name is what it set.
- **The duplicated `ReportUnhonouredSecuritySettings`** (the handoff asked for a second opinion): agreed, no shared helper. They log through different objects, name settings in two different vocabularies and carry different remedies; four lines each, in two assemblies. A helper would abstract over the only thing they have in common, which is the word "or".
- **Static-initialiser order** on both halves, and `HasCustomBinding` asking about the binding alone rather than about `ServiceEndpointHook` or `BuildEndpointIdentityCall` — neither of which secures a transport over an unsecured binding.
- **Documentation is complete, including what the change did not touch.** Every other `docs/` file that mentions security was read: `users-guide/security.md`, `users-guide/dataphoria-security.md`, `developers-guide/enforcing-security.md` and `developers-guide/d4-catalog.md` all describe the role-based model, not the transport, so none carried a stale claim. No converted page documents the server-link tags (the `create server` reference is still an unconverted stub), so migration notes are their only home, which is where they are.
- **Source hygiene.** The largest touched file is 485 lines (`ClientServer.cs`); nothing is near a split. Line endings, tabs and byte-order marks preserved in every edited file.

### Weighed and left alone

- **The instance warning fires for `requiresecurelistenerconnection` even when `ShouldListen` is false**, where the instance serves no listener at all and the setting is doubly inert. The sentence is still true as written — "nothing in this server acts on that" — and splitting the message to say "and this instance runs no listener anyway" buys an operator nothing they would act on differently.
- **The two server-side warnings are still verified by inspection only**, exactly as the handoff said. Both paths, both `HasCustomBinding` guards and both message texts were read again rather than executed, and no test was added: asserting a log line needs a server with logging on, which the root `AGENTS.md` records this suite deliberately avoids because a logging server in an elevated process creates and writes the `Dataphor Server` Windows event-log source, and the server-link warning additionally needs the second hosted instance that `test-client-server` owns. Whoever lands `test-client-server` is the one who can cheaply exercise the link warning.
- **The implementer's `NOTE:` on warning volume** in `RemoteSessionImplementation.cs` stands as filed: one warning per remote session, bounded by sessions rather than statements, with "dedupe on the `ServerLink`" as the remedy.

### Tripwire parked

- `src/protocol/Common/Contracts/DataphorServiceUtility.cs`, on `GetBinding`: the memo means `BuildBindingCall` is read exactly once, by the first connection built anywhere in the process. A hook installed after that reaches no channel — and because `HasCustomBinding` reports it as installed, `CheckSecurityMode` stays quiet too, so the connection is unsecured and says nothing. Conditional on a caller breaking the documented "install from start-up code" order, which both hook classes' own documentation states, and retired outright when WS11's `security-transport-design` makes the binding per-endpoint rather than one process-wide singleton. Recorded at the site rather than filed: it is knowledge for whoever does that work, and `security-transport-design` already names the singleton as something it has to change.

**None, and the reason is specific rather than "looks good".** One real defect was found and it had a local fix, so it was fixed here with its reproduction.
