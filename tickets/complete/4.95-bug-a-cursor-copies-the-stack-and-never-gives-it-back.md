## What was wrong

Opening a cursor takes a private copy of the whole current stack window (`Cursor.SnapshotContext`) and swaps that copy in as the program's stack around every cursor operation, so that the cursor's plan can still read the variables it was compiled against after the scope that opened it has gone. The copy has to be a copy - a cursor outlives its scope, and the scope releases its own variables on the way out - but `Cursor.Dispose` threw the copy away without releasing it: it set `_context = null` and nothing else. A copy of a `Binary` or a `Graphic`, or of a row or list holding one, is a new managed stream that something has to release, so every cursor a script opened held one stream for the life of the session per stream-backed variable then in scope. Every cursor paid it, the implicit one a `foreach` over a table opens as much as an explicit `cursor(...)`.

Releasing the copy is only half the fix. The releases run through the process's own value and stream managers, but the cursors live in a `CursorManager` on the **session**, which the session disposes *after* its processes - so a cursor the script never closed used to be disposed with its process already torn down, and releasing its copy there dereferenced the nulled managers. With the release alone, a script that opens a cursor and never closes it turns a test fixture's teardown into a `NullReferenceException` out of `Engine.Disconnect`.

## What changed

**`src/engine/DAE/Runtime.Data/CursorValue.cs`** - `Cursor` records the value manager *and* the process the snapshot was copied with (`_contextValueManager`, `_contextProcess`, both set in `SnapshotContext` from the same program at the same moment), and `Dispose` releases the snapshot with `_context.ReleaseAbove(0, _contextValueManager)` before nulling `_context`. `ReleaseAbove` rather than a loop, because it nulls each slot before disposing its value, so a dispose that throws cannot leave a disposed value reachable. `SnapshotContext` is now `private` - nothing outside the constructor called it, and a second call would orphan the first snapshot outright. `CursorManager` gains `CloseProcessCursors(ServerProcess)`, which walks `_cursors` backwards (because `Cursors` is a `DisposableList` that disowns a member that disposes itself) and disposes each cursor whose recorded process is that one (`Cursor.BelongsTo`, `internal`).

**`src/engine/DAE/Server/ServerSession.cs`** - a new `internal void CloseProcessCursors(ServerProcess)` that forwards to `_cursorManager` only if there is one; deliberately not through the `CursorManager` property, which creates a manager when there is none.

**`src/engine/DAE/Server/ServerProcess.cs`** - `InternalDispose` calls it, in its own `finally` beside the one that disposes each plan's `ActiveCursor`. That runs after the transaction rollback and before `CloseDeviceSessions`, so the cursor's table is closed against device sessions that are still open and the process's own managers are still alive for the release.

**`src/engine/DAE/Runtime/Program.cs`** - no behaviour change; the long `NOTE:` above `Program.Stop` listed this defect as one of the leaks blocking a DEBUG-only stream-count check, and it was rewritten to leave `bug-row-equality-leaks-the-rows-it-compares` as the one remaining blocker.

## Review findings

Read `ticket(implement): bug-a-cursor-copies-the-stack-and-never-gives-it-back` before the handoff summary.

**Correctness of the fix: confirmed.** `ReleaseAbove(0, manager)` over the snapshot stack releases exactly the slots the snapshot pushed into its one window at offset 0, and that stack is a fresh `Stack` whose `AllowExtraWindowAccess` is off, so the window-relative `Count` the `NOTE:` on `ReleaseAbove` warns about is read the same way at both ends. There is no aliasing to worry about: `SnapshotContext` deep-copies through `DataValue.CopyValue`, so a borrowed slot (an enclosing `foreach`'s loop variable, a `const` operand passed by reference) yields a copy the snapshot owns outright, and a `TableValue` copy releases nothing when disposed either way. `Dispose` cannot run while the snapshot is switched in - every `Cursor.SwitchContext` call in `CursorNodes.cs`, `ImperativeNodes.cs` and `ListNodes.cs` is a matched pair in a `try`/`finally`, and `ForEachNode` closes the cursor in an outer `finally` after those have unwound - so the release can never reach the program's live stack. `_context` and `_contextValueManager` are set and cleared together, so neither can be non-null without the other.

**Checked the choice the handoff flagged for a second opinion, and it holds.** The call's placement in `InternalDispose` - after the rollback, before `CloseDeviceSessions` - is the only window where the cursor's `_table.Dispose()` has open device sessions and the release has live managers, and the neighbouring `plan.ActiveCursor.Dispose()` has always disposed a server cursor from that same spot, which is the existing evidence that a table can be closed there. The two rejected alternatives are rejected for the right reasons: reordering `ServerSession.Dispose` does not help, because a process is usually stopped long before its session is disconnected, and there is no longer-lived manager to release through, because each copied `Row` or `ListValue` carries the process's own manager inside itself.

**Fixed in this pass - the process filter could miss a cursor, and the fix then crashes where it used to leak (major, resolved at the root).** `CloseProcessCursors` filtered on `cursor.Table.Program.ServerProcess`, and that is not a fixed answer: `ServerPlan.BindToProcess` re-points a cached plan's program at whichever process next takes that plan out of the server's plan cache (`ServerSession.GetCachedPlan` to `PlanCache.Get`, on by default for prepared statements and expressions, and the cache is server-wide, so the next process can even be in another session). A cursor whose plan had been reused that way would not match its own process's filter, would survive to `CursorManager.Dispose`, and would release its snapshot through the manager of a process already torn down - the `NullReferenceException` at disconnect that this ticket's second half exists to prevent. Before this ticket that path merely leaked; with the release in place it crashes, so it is the fix's own regression rather than a pre-existing one. Fixed at the root rather than by hardening the filter's reads: the cursor now records the process in `SnapshotContext` beside the value manager (`_contextProcess`, read through `internal bool BelongsTo(ServerProcess)`), so the process that must close the cursor and the manager the release runs through come from one capture at one moment and cannot drift apart. `Program._serverProcess` is otherwise stable - both paths that null it, `ServerProcessDisposed` and `UnbindFromProcess`, are behind disabled `#if` symbols - so rebinding was the only way those two facts could disagree.

**Fixed in this pass - a throw while closing plan cursors skipped the new call (minor).** The call shared a `finally` block with the `foreach (ServerPlan plan in _plans)` loop that disposes each plan's `ActiveCursor`, so a throw from that loop skipped it and left a D4 cursor holding the process - the same disconnect-time crash by a second door. The whole of `InternalDispose` is a tower of nested `try`/`finally` precisely so that one failing step cannot skip the next; the new call now has its own `finally` in that idiom, and its comment says why it is separate. The whitespace-only line of stray tabs the implement stage left between the two is gone with it.

**Fixed in this pass - wording that contradicted itself (minor).** The architecture page and the `SnapshotContext` remarks both argued that "a snapshot of the live values would leave the cursor reading released streams" - against a mechanism whose name is the snapshot. Both now say "sharing the live stack", which is the thing actually being rejected. One ragged line in the rewritten `Program.Stop` `NOTE:` was re-flowed.

**Recorded as a tripwire, not a ticket.** Nothing in `CursorManager` is synchronised and one manager is shared by every process in the session, so two processes creating, closing or walking cursors at once race on `_cursors`. That is pre-existing - `CreateCursor`, `GetCursor` and `CloseCursor` have always been reachable from any process of the session - and `CloseProcessCursors` is one more unsynchronised walk rather than a new exposure, so a `NOTE:` at the `_cursors` field says so, and says that the lock belongs in that class rather than at each caller if a client is ever seen using cursors from two processes of one session at once. The implement stage's own `NOTE:` at `CursorManager.Dispose` is left as it stands and remains accurate for the hole that is left: a future path that disposes a process without reaching `InternalDispose`. One more route to that same symptom was noticed and deliberately left uncommented: if one cursor's `Dispose` throws mid-loop, the cursors after it in `CloseProcessCursors` are skipped. Swallowing that would hide a real over- or under-release, the surrounding code does not swallow, and the symptom is already the one that `NOTE:` names.

**Checked and sound, so nothing done.**

  - *Is `Cursor` the only thing that copies a stack?* A search for `new Stack(` across the engine finds four sites: the program's own stack, this snapshot, and `ExplodeTable`'s `_sourceTables` and `_parentRows`. The last two release what they hold - `InternalClose` drains them through `PopSourceTable`, which disposes each table and each parent row - so this was the one outlier of its class and there is no class-level ticket to file.
  - *The tests.* Both earn their place under this project's rule that a bug fix owes its reproduction, and neither is redundant: the handoff's mutation experiment - each case failing for exactly one half of the fix - was re-read against the code and matches it, and the two halves fail in different places (a stream count, and a fixture teardown) which no single case could cover. Neither mocks anything the repository owns. No test was cut and none added: the two defects this review found are both in the release path these cases already cover, and the one that needed demonstrating - the plan-cache rebind - needs a cached prepared statement that leaves a cursor open across an unprepare, which is reasoning from the code rather than something the in-process fixture can stage; it is recorded in the `_contextProcess` remarks instead.
  - *`Graphic` is not covered, only `Binary`.* Left as the handoff described it. The two are the same `StreamID` path through the value manager and every case in the fixture is `Binary` for that reason; a parallel `Graphic` case would test the value manager twice rather than this release once.
  - *Docs.* Every file the change touches was read rather than assumed current. `docs/architecture/value-lifetime.md` is the page that owns the subject and the new section is accurate against the code, including the claim that `SwitchContext` is called in matched pairs. The `docs/migration-notes.md` entry describes the new behaviour accurately and needs nothing for the review's own changes: `BelongsTo` is `internal` and the rest is a comment or an exception path that previously leaked.
  - *Source hygiene.* `CursorValue.cs` is still tabs, CRLF, no byte-order mark and no trailing newline; `ServerProcess.cs`, `ServerSession.cs` and `Program.cs` are still tabs, CRLF, UTF-8 byte-order mark; both docs still CRLF with no byte-order mark. No file was reformatted or re-encoded. `AssignmentValueOwnershipTest.cs` is 1,378 lines, under the roughly-1,500 threshold its own `NOTE:` sets for splitting, and two sibling ownership tickets still have cases in flight against it, which is what that `NOTE:` defers the split for.
  - *The `SnapshotContext` visibility arm.* Kept. It is a `public` member of a `public` type, so it is a compatibility surface and carries its migration-notes line, but the trade is right: nothing outside the constructor called it, a second call would orphan the first snapshot outright, and `private` makes that unrepresentable rather than merely discouraged.
