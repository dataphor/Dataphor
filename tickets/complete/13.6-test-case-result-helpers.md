## What changed

The work landed in `ticket(implement): test-case-result-helpers`.

- `tests/libraries/TestFramework.Coverage.Base/Documents/Tables.d4` now defines the table `CurrentCaseItems` (`Name`, `Passed`, `Message`, key `{ Name, Message }`, on the library's default device `Temp`) and the operator `RaiseCurrentCaseItem(const AName : String, const APassed : Boolean, const AMessage : String)`. The operator inserts a row and, when `APassed` is false, raises `Error(AName + ": " + AMessage)`. Because `Transaction.Atomicity.Run`'s closing check is commented out, that raise is the only thing that makes a failed case fail its script. `Register.d4` already runs `Tables`, so it did not change.
- `tests/DAE.Server.Tests/coverage-manifest.json`: `Transaction.Atomicity.TestDAE` is now `pass`. `Transaction.Isolation.Run` is now a `known-failure` owned by `bug-memory-device-concurrent-access`, with the error `Lost Update (Browse, Browse): LostUpdate did not behave properly`.
- `docs/modernization-plan.md` K29: the memory device also takes no row locks for a transaction, and `Transaction.Isolation.Run` is the verified instance. The backlog ticket `bug-memory-device-concurrent-access` covers this in its third part, which the fix stage added.

No coverage script was edited, and no migration note was needed because only test libraries changed.

## Review findings

**What I checked.** I read the implement diff before the handoff. I also read both calling scripts in full (`Transaction.Atomicity.Run`, `Transaction.Isolation.Run`), the `TestDAE` driver, the helper library's `.d4l` and `Register.d4`, the backlog ticket's third part, and the plan rows and `AGENTS.md` text that describe the manifest. I ran the full `dotnet test tests/DAE.Server.Tests`: `Failed: 0, Passed: 140, Skipped: 25, Total: 165` (3 m 44 s). `Transaction.Atomicity.TestDAE` passed, and `Transaction.Isolation.Run` matched its known failure.

- **Correctness of the raise-on-failure design: no defect.** In `Transaction.Atomicity.Run`, every `RaiseCurrentCaseItem` call comes after its `try … commit` / `except` block, so no handler swallows the raise. In `Transaction.Isolation.Run` the raise runs on the main process, inside `try … finally StopProcess(…)` and `try … finally drop table`, so those cleanups still run when a case fails. The script stops only one of its two processes, but that defect is in the script and is already recorded in the backlog ticket's third part. The server is discarded after each case anyway.
- **The key `{ Name, Message }`: no defect.** Within one run, every call passes a distinct name/message pair: the isolation names include the pair of isolation levels, and every atomicity call passes `false`, so the first one stops the script. Each case runs on its own server copy, so rows never carry over between cases.
- **The manifest entry for `Transaction.Isolation.Run` depends on timing in theory, but I judged it not a concern.** The script's first case fails only if the second process's update finishes within 200 ms. On the memory device that is an update of a one-row table with no locking, which is far faster than 200 ms, and the failure matched in all of the implementer's runs and in mine. Since the failure is not a timing race, `known-failure` is the right status rather than `unstable`. I recorded nothing at the site.
- **Source hygiene: no issues.** `Tables.d4` stays UTF-8 without a byte-order mark, with CRLF line endings and tabs (checked with `file` and `od`). The two new comments state what the table and operator are for, rather than narrating the code.
- **Docs: up to date.** The `AGENTS.md` description of the manifest is unchanged and still accurate. The plan's K29 row now covers the isolation case. The plan's `test-triage-known-failures` row and the completed tickets that mention `CurrentCaseItems` are history and correctly left alone.
- **Tests: none added or cut.** `Transaction.Atomicity.TestDAE` passing exercises the helpers. `Transaction.Isolation.Run` matching its recorded failure exercises the raise path. Neither restates the implementation.
- **Major findings and tickets filed: none.** The only real gap (the memory device has no transaction locking) already belongs to `bug-memory-device-concurrent-access`.
- **Tripwires: none.** Nothing in the change is fine now but wrong under a foreseeable condition, apart from the timing point above, which I judged not a concern.
