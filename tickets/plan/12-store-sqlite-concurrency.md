# SQLite catalog store under concurrent sessions (K10)

**Paths.** This ticket runs after `repo-move-to-new-layout`; paths are in the target layout of the plan's [Repository layout](../../docs/modernization-plan.md#repository-layout) section (`src/engine/Store.SQLite` is today's `Dataphor/DAE.SQLite`, `src/engine/DAE` is `Dataphor/DAE`, `src/engine/Server` is `Dataphor/Server`). `tools/net-spike/` may have been deleted by the time this runs; the facts quoted from it below are the record.

## What this is for

The server keeps its catalog — object scripts, dependencies, loaded libraries, users, rights, device users, server settings — in the *catalog store*. After `store-remove-sqlce-references` the default store is SQLite (D3). With the store as it is, eight sessions running DDL at once produced 39–47 failures in 120 cycles and took 60–80 s; the causes and the measurements are in the plan's [WS4 diagnosis](../../docs/modernization-plan.md#ws4-catalog-store). The spike removed every failure with three changes: the emitter fix (K1, now landed by `port-catalog-emitter-race`), write-ahead logging (WAL) with a 30 s busy timeout, and beginning every store transaction with `BEGIN IMMEDIATE`. The last change serializes all store transactions, read-only ones included, and lets one long user transaction that has touched the catalog hold the write lock for its whole length.

This ticket designs and lands the production version: the plan's **target design**.

1. SQLite in WAL mode, one writer at a time by construction.
2. The SQLite write transaction is opened lazily, on the first store *write* inside a process transaction, not at the start of the process transaction.
3. Reads run outside any SQLite transaction (WAL gives each statement a consistent committed snapshot, and the engine's own catalog locks already serialize conflicting DDL) — except that reads issued by a session that has an open write transaction must see that transaction's own writes (see "Read-your-writes" below).
4. A busy timeout surfaces as a Dataphor error that names the blocking condition, not as a raw "database is locked".
5. SQLite stays the default store class (set by `store-remove-sqlce-references`); this ticket makes the default *connection* produce the validated configuration (WAL, busy timeout) with no instance settings.

Validated against the L1 suite (D4 coverage scripts), the L2 store tests that exist by then, a concurrency test and a long-running DDL transaction test (below).

## Facts verified in the code (saves rediscovery)

### Call path: process transaction → SQLite transaction

1. `ServerProcess.BeginTransaction` → `InternalBeginTransaction` (`src/engine/DAE/Server/ServerProcess.cs` ~line 1261) pushes a `ServerTransaction` and calls `deviceSession.BeginTransaction(isolationLevel)` on every device session of the process, including the catalog device session (obtained through `ServerProcess.CatalogDeviceSession`, ~line 591, which connects it like any device). Implicit transactions take the same path with the process's `DefaultIsolationLevel` (~line 1829). A device session connected *during* an open transaction is brought up to the current nesting level by `ServerProcess.DeviceConnect` (~line 546: `while (session.Transactions.Count < _transactions.Count) session.BeginTransaction(…)`).
2. `DeviceSession.BeginTransaction` → `ServerCatalogDeviceSession.InternalBeginTransaction` (`src/engine/Server/Device.Catalog/ServerCatalogDeviceSession.cs`, "Transaction" region, ~line 1622): calls the base (the in-memory catalog's own DDL undo log in `CatalogDeviceSession`) and then, **only if the session already holds an updatable store connection** (`_catalogStoreConnection != null && _isUpdatable`), `CatalogStoreConnection.BeginTransaction(isolationLevel)`. Commit and rollback mirror this in `InternalAfterCommitTransaction` / `InternalAfterRollbackTransaction`.
3. The updatable connection is acquired lazily by `AcquireCatalogStoreConnection(true)` (~line 90), which every store-writing method calls (insert/update/delete of persistent objects, loaded libraries, users, rights, server settings, `SnapshotBase`). The first time it is called with `true`, it connects a dedicated connection (`Device.Store.Connect()`) unless the session already holds a pooled one, sets `_isUpdatable = true`, and begins `ServerProcess.TransactionCount` nested store transactions to catch up with the process. Read-only methods call `AcquireCatalogStoreConnection(false)`, which takes a connection from the store's pool (`CatalogStore.AcquireConnection`) unless the session already holds one, and give it back on the last `ReleaseCatalogStoreConnection` — **unless** the session is updatable, in which case it keeps the connection.
4. **`_isUpdatable` is never reset.** After a session's first store write, it owns its connection for its lifetime, and every later process transaction of that session begins a store transaction at its start (step 2), whether or not it writes. Under the spike's "begin immediate for everything", every later transaction of such a session — even a read-only one — takes the SQLite write lock for its whole length. This is the concrete mechanism behind the plan's warning. (`docs/architecture.md` says each catalog device session "opens a store transaction for every process transaction"; that is only true after the session's first write — correct the sentence when this lands.)
5. `CatalogStoreConnection.BeginTransaction(IsolationLevel)` (`src/engine/DAE/Device.Catalog/CatalogStore.cs` ~line 754) flushes the cursor cache at the outermost level and maps the D4 level with `SQLUtility.IsolationLevelToSQLIsolationLevel` (`src/engine/DAE/Connection/SQLUtility.cs` ~line 58): `Isolated` → `Serializable`, `CursorStability` → `ReadCommitted`, anything else (`Browse`) → `ReadUncommitted`. The default process isolation is `CursorStability` (`src/engine/DAE/SessionInfo.cs` ~line 207).
6. `SQLStoreConnection.BeginTransaction(SQLIsolationLevel)` (`src/engine/DAE/Store/SQLStoreConnection.cs`) counts nesting in `_transactionCount`; only at level 0 → 1 does it call `_connection.BeginTransaction(level)` (it also disposes its cached execute command first). Nested levels get a `BeginTransactionOperation` marker in an in-memory operation log. Note: `SQLStoreConnection` declares `protected virtual InternalBeginTransaction`, but `BeginTransaction` does not call it — it calls `_connection.BeginTransaction` directly. Commit at level 1 commits the SQL transaction if `_connection.InTransaction`; rollback replays the log's undo statements back to the last marker, and at level 1 rolls back the SQL transaction if `_connection.InTransaction`.
7. `SQLConnection.BeginTransaction` (`src/engine/DAE/Connection/SQLConnection.cs` ~line 149) calls the provider-specific `InternalBeginTransaction` and sets `_inTransaction = true` whatever it did.
8. `SQLiteConnection.InternalBeginTransaction` (`src/engine/Store.SQLite/SQLiteConnection.cs`): for `ReadUncommitted` it sets `_inReadUncommittedTransaction` and starts **no** SQLite transaction (commit and rollback just clear the flag); otherwise it calls `DotNetConnection.InternalBeginTransaction` (`src/engine/Server/Connection/DotNetConnection.cs` ~line 77), which maps to `System.Data.IsolationLevel` and calls `IDbConnection.BeginTransaction(level)`. With `System.Data.SQLite`, `ReadCommitted` gives a deferred `BEGIN` (read lock on first read, write lock on first write — the lock-upgrade deadlock in the plan's diagnosis) and `Serializable` gives `BEGIN IMMEDIATE` (check the provider source for the exact mapping of the version you choose). The spike's patch forced `Serializable` for every non-read-uncommitted begin: `tools/net-spike/run.py`, `PATCHES`, entry for `SQLiteConnection.cs` (`base.InternalBeginTransaction(isolationLevel)` → `base.InternalBeginTransaction(SQLIsolationLevel.Serializable)`). `build-server-project` removed that entry when it converted the store project, so the spike no longer applies it; the change is quoted here in full.

### Nested-transaction undo and where writes happen

- Store writes go through `SQLStoreCursor` (`src/engine/DAE/Store/SQLStoreCursor.cs`, insert ~line 744, update ~788, delete ~833) or `CatalogStoreConnection.InsertRow`/`DeleteRows` (`PerformInsert`/`PerformDelete` with generated literal SQL). The cursor logs an undo statement only when `_connection.TransactionCount > 1` (nested); the outermost level relies on the SQL transaction.
- Consequence for `Browse` (read uncommitted): there is no SQLite transaction and no undo log at the outermost level, so the store writes of a `Browse`-level transaction autocommit one statement at a time, and rolling that transaction back undoes the in-memory catalog but not the store. The SQL CE store had the same mapping. This is an existing divergence (static finding, not reproduced). The lazy-write design must decide what isolation a store write transaction uses (see open choices).
- SQLite's store is configured with `_supportsMARS = true`, `_supportsUpdatableCursor = false` (`SQLiteStore.InternalInitialize`): many open readers per connection, writes by generated statements. `CatalogStoreConnection` caches closed cursors (open readers) while `TransactionCount > 0` and flushes them at the outermost begin, commit and rollback.

### Where reads happen, and read-your-writes

- Catalog reads through the catalog device session (`SelectObject…`, name resolution, dependency lookups) use `CatalogStoreConnection` cursors: on the session's own connection if it holds one (pooled or updatable), else on a pooled connection for the duration of the call. Readers are opened with `SQLStoreConnection.ExecuteReader` on that same connection.
- Today, **read-your-writes holds because a session that has written keeps using the same connection for its reads** (fact 3), and a SQLite connection's statements run inside that connection's open transaction. Any design that sends a writing session's reads to another connection (for example the pool) breaks it: the other connection would see only committed data. The lazy design must keep "once this process transaction has written, its reads go to its write connection".
- Separately, `CatalogDeviceTable` (`src/engine/Server/Device.Catalog/CatalogDeviceTable.cs` ~line 57), used when a D4 query over a catalog table is translated to store SQL, opens a **new** `SQLConnection` from the store for each open, begins `ReadUncommitted` (no SQLite transaction) and reads on it. It never sees the calling session's uncommitted store writes today. That is existing behaviour; keep it or fix it deliberately and say which.

### Spike configuration and loop

- Connection string used by the spike for both the smoke and coverage runs: `Data Source=%CatalogPath%\DAECatalog;Journal Mode=WAL;BusyTimeout=30000` (`tools/net-spike/run.py`, `SMOKE_CS`; `tools/net-spike/Cov/Program.cs` ~line 35). `%CatalogPath%` is substituted by `Server.GetCatalogStoreConnectionString`.
- The concurrency loop: `tools/net-spike/Smoke/Program.cs`, the threads section after the single-session checks: N threads (default 8), each connects as `Admin`/empty password, starts a process, and runs M iterations (default 15) of `create table` / `insert` / `create view` / `create operator`, an evaluation that also queries `System.Operators`, then `drop operator` / `drop view` / `drop table`; errors are collected per iteration and grouped by message. Results are in the plan's WS4 table (0 errors in 1.6 s with all three fixes; 16 × 25 in 8 s).
- The spike used `System.Data.SQLite.Core` 1.0.119 from NuGet; since `build-server-project` the converted store project references that package (version in `Directory.Packages.props`). The legacy project referenced a checked-in `System.Data.SQLite.DLL` 1.0.60 under the old `Dataphor/bin`.

### Errors

- `SQLiteConnection.IsTransactionFailure` returns false for every code and `IsUserCorrectableError` treats only `Constraint` as a user error; everything else is wrapped as an application error by `SQLConnection.WrapException`. A busy/locked failure therefore reaches the user as a generic wrapped provider message.
- `StoreException` (`src/engine/DAE/Store/StoreException.cs`, prefix 130 `DAE.Store` in `Error Message Prefix Codes.txt`, moved under `docs/reference/` by WS8) uses 130100–130102; 130103 is free (verified). `ConnectionException` (127) and `CatalogException` (115) are the other candidates.

### Dependency to note

- `Store.SQLite` references the `Server` project today: `SQLiteConnection` derives from `DotNetConnection`, which lives in `src/engine/Server/Connection/DotNetConnection.cs`. Any provider change touches that base class's contract too (it is shared with the server's other .NET connections).

## Open choices for the planner

1. **Provider: `System.Data.SQLite` or `Microsoft.Data.Sqlite`.** Default if nothing argues otherwise: stay on `System.Data.SQLite` (the spike's validated configuration, least code change). Facts to weigh, each to be checked against the current package versions rather than taken from here:
   - *Native assets.* `System.Data.SQLite.Core` ships its native `SQLite.Interop.dll` per runtime identifier; `Microsoft.Data.Sqlite` uses `SQLitePCLRaw` and ships `e_sqlite3.dll` per runtime identifier. Either way the native file must land in the runtime layout's `bin` (`build-runtime-layout`) and in self-contained publishes (`installer-publish-profiles`). The store assembly is loaded by name (`Type.GetType` in `CatalogStore.CreateStore`), so a host or test project that does not reference the store project may not get the native file copied; make each host reference it, and coordinate with `port-library-loading` (`feat-ws2-server-port-remainder`) if probing is needed.
   - *Error API.* `System.Data.SQLite`: `SQLiteException.ResultCode` (enum `SQLiteErrorCode`; the code already uses the enum). `Microsoft.Data.Sqlite`: `SqliteException.SqliteErrorCode` and `SqliteExtendedErrorCode` (integers). `SQLiteCommand.PrepareParameters` and `SQLiteStoreCursor` value conversions would need a rewrite for the latter.
   - *WAL and busy timeout.* `System.Data.SQLite`: connection-string keywords (`Journal Mode=WAL`, `BusyTimeout=<ms>`, also `Default Timeout=<s>` for commands) — what the spike used. `Microsoft.Data.Sqlite`: no journal-mode keyword (run `PRAGMA journal_mode=WAL` once on the database; the mode is persistent in the file); `Default Timeout` (seconds) drives its busy retry.
   - *Transactions.* Check how each maps `BeginTransaction(IsolationLevel)` and whether it offers an explicit deferred/immediate choice (`Microsoft.Data.Sqlite` has `BeginTransaction(deferred: …)`); the lazy design may issue `BEGIN IMMEDIATE` itself instead of relying on the isolation mapping.
   - *Type round trip.* The store holds integers, strings, booleans (stored as `tinyint`, converted in `SQLiteStoreCursor`) and long text/binary. Check that the chosen provider round-trips each store column type unchanged, since `SQLStoreCursor` builds literal SQL and reads values back by ordinal.
   - *Layout and licence.* Package name and version under central package management (D11); check the current licence and distribution terms of `System.Data.SQLite` packages beyond 1.0.119 before committing to a newer version.
2. **Where lazy begin lives.** Options: in `ServerCatalogDeviceSession` (begin the store transaction at the first `AcquireCatalogStoreConnection(true)` of each process transaction, and reset `_isUpdatable` — or a per-transaction "has written" flag — at the outermost commit/rollback); or in the SQLite store connection (keep the logical nesting count, issue `BEGIN IMMEDIATE` before the first write statement and skip commit/rollback if none was issued). The first keeps the store layer generic; the second keeps the change inside the SQLite store. In either case: the outer level's begin must happen before the first write statement *and* before any cursor of that transaction is used for a write; the cursor cache must not hold a reader opened outside the write transaction across the `BEGIN` (decide whether to flush it at the lazy begin); nested levels' undo logging keys on the logical count and must keep working when the SQLite transaction starts at a nested level.
3. **Read-your-writes under lazy begin.** Required. State the rule ("a process transaction that has written reads only through its write connection until it ends") and where it is enforced. Before the first write, reads may go to pooled connections in autocommit mode.
4. **Isolation of the store write transaction.** Whether a store write always takes a real SQLite write transaction regardless of the D4 isolation level (this would close the `Browse` divergence above: store writes would roll back with the in-memory catalog), or keeps today's "read uncommitted means no transaction". Recommended: always a real write transaction — the store's integrity should not depend on the user's isolation choice. If chosen, it is a behaviour change visible only as "rollback now also rolls back the store"; add a migration-notes line.
5. **Busy-timeout error.** Default: a new `StoreException` code 130103, severity Environment, message naming the condition, for example "The catalog store is locked by another session's open transaction and did not become available within {0} seconds." Raise it where the provider reports busy/locked (`SQLITE_BUSY`, `SQLITE_LOCKED`) on begin or on a write. Decide the timeout's default (the spike used 30 s) and whether it is configurable (through the connection string is enough). Decide whether the error should carry which session holds the lock (only possible if the store tracks the owner of the write transaction itself; nice, not required).
6. **Default connection string.** `store-remove-sqlce-references` made the default `Data Source=<instance>\Catalog\DAECatalog.sqlite`. Decide whether WAL and the busy timeout go into the default connection string (visible in configuration, overridable) or are applied by `SQLiteStore` regardless of the connection string (cannot be misconfigured). Recommended: apply WAL in code at store initialization (it is required for the design to be correct) and take the timeout from the connection string with a default.
7. **Where the concurrency loop test lives.** Decided here: the spike's loop becomes a test **in this ticket** (L2), because it is the reproduction for K10 and a bug fix owes its reproduction. `test-store-contract` later covers the store contract (cursors, ranges, undo, restart) and may reuse its helpers.

## Required tests (name them in the implement tickets)

- **Concurrency (K10 reproduction).** The spike's loop as an NUnit test on the in-process harness: at least 8 sessions × 15 cycles of create/query/drop, released together; expected result: zero errors of any kind; time recorded in the handoff (not asserted, or asserted only with a generous bound). It must fail on the current store (lock errors) — record that.
- **Long-running DDL transaction.** One session begins a transaction, performs a store write (for example `create table`), then waits (holding the transaction open) for longer than the time the others need; meanwhile other sessions (a) read the catalog — name resolution, `select` from catalog tables, evaluating existing operators — and must not block or fail, and (b) attempt their own DDL, which must either wait and succeed after the first transaction commits (if the wait is inside the busy timeout) or fail with the new busy error naming the condition (if the test sets a short timeout). Run both variants. Then the first session commits and all its objects are visible to the others.
- **Read-your-writes.** In one transaction: create an object, then resolve and use it (for example create a table and insert into it, or create an operator and call it) before commit; then roll back and confirm it is gone from the in-memory catalog and from the store (restart, or read the store directly).
- **Tighten K1's test.** `port-catalog-emitter-race` added a concurrent-DDL test that tolerates "database is locked" errors until this ticket lands; remove that tolerance (its `NOTE:` marks the place) so it requires zero errors.
- The whole L1 manifest unchanged or better, on the default (no settings) store configuration.

## Risks

- Lock upgrade moved, not removed: if any path writes through a connection that read first inside an open deferred SQLite transaction, the deadlock returns. The design must make every write transaction begin `IMMEDIATE` (or equivalent) before its first statement.
- Readers opened before the lazy begin and still open after it (cursor cache, open table cursors handed to plans) may behave differently once the connection enters a transaction; SQLite requires care with active statements around `BEGIN`/`COMMIT`. Cover with the read-your-writes test and inspection of the cursor cache.
- WAL needs the `-wal` and `-shm` files beside the catalog file and does not work on network file systems; document that the instance directory must be local (docs: `docs-admin-guide`).
- A session that disappears while holding the write lock blocks all DDL until it is reclaimed; this is where `port-abandoned-session-cleanup` matters. Note the interaction in the design.
- K3 may reappear once writes are no longer serialized from the start of each transaction (see Out of scope).
- Changing the provider changes native-asset handling for every host and test project; it touches the build layout tickets' assumptions.
