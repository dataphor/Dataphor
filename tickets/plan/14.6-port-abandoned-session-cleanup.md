## What this is

Before the port, a client that vanished — a crashed process, a pulled network cable, a powered-off workstation — was eventually noticed because the server's remote objects were .NET Remoting objects with leases, and a lease that stopped being renewed let the object go. `server-remove-remoting-and-dtc` removed all of that for known defect K6 (the lease calls throw on .NET 10) and kept `MarshalByRefObject` as an inert base class. What now reclaims an abandoned session is therefore an open point, and the plan makes this item establish it and pin it with a test.

It is scheduled after `protocol-corewcf-host` because it can only be shown over a real connection: the reclaiming path runs in the WCF-facing layer, and whether a connection stays open between calls at all depends on what the host and binding do with the infinite timeouts (a question `protocol-corewcf-proof` answers — read its write-up).

## What is already there, and what is doubtful about it

A reaper exists. `ConnectionManager` (`src/engine/Server/Service/ConnectionManager.cs`), constructed by `DataphorService`, runs a thread that wakes every 300 seconds, and relinquishes every `RemoteServerConnection` whose `LastActivityTime` is older than 300 seconds. `RemoteServer.Relinquish` closes the connection's sessions, disowns it and disposes it; each session's processes are disposed, and `ServerProcess.Dispose` rolls back every active transaction before unpreparing deferred constraint checks (`src/engine/DAE/Server/ServerProcess.cs`, about line 114). So on paper the chain is complete.

Four things about it need establishing rather than assuming:

- **`LastActivityTime` is only ever moved by `Ping()`.** `RemoteServerConnection` sets it once in its constructor and then only in `Ping` (`src/engine/Server/Server/RemoteServerConnection.cs`, about line 138). No ordinary operation touches it. So the reaper measures time since the last *ping*, not time since the last activity, and a connection is kept alive solely by the client's keep-alive thread — `LocalSession.KeepAlive` pings every 120 seconds (`src/protocol/Client/Server/LocalSession.cs`), which is started per session. Consequences to check: a connection with no open session has nothing pinging it and is reaped after five minutes; a single call that runs longer than five minutes with no concurrent ping may have its own connection relinquished underneath it. Both may be fine, both may be defects; find out which before changing anything.
- **Relinquishing a connection in use.** `Relinquish` calls `CloseSessions` before taking the server's lock, and nothing bars a call from being in flight on that connection at the same time. Establish what happens when the reaper and an active call meet, and whether the result is a clean error to the client or a corrupted handle table (`HandleManager` maps the client's integer handles to these objects).
- **Does a rolled-back abandoned transaction actually release the catalog store's write lock?** This is the sharp case, carried over from `store-sqlite-concurrency`: the SQLite catalog store allows one writer at a time, and a process transaction that has written to the catalog holds that write lock until the transaction ends. A session abandoned in that state blocks every other session's DDL, each failing with error 130103 after the busy timeout, until the server rolls the transaction back. The rollback path exists; whether the reaper reaches it within a bounded time, and whether rolling back really closes the store transaction and frees the lock, is what has to be shown.
- **Five minutes is a long time to hold a DDL lock.** Whether the interval should stay at 300 seconds, become configurable, or be shortened when a connection holds the catalog write lock, is a decision this ticket makes. `IdleTimeInSeconds` is a `const` today; making it configurable means a new instance-configuration setting, which is a compatibility surface and has to be coordinated with `host-instance-configuration`.

## The test this owes

The project's testing rule applies: this changes the behaviour of a subsystem, so it owes a characterization test, at the lowest layer that shows the behaviour. The one the plan and the WS5 umbrella both call for:

- Open a session over a real connection, begin a transaction, `create table` so that the catalog store write transaction is held, then abandon the session — the client stops pinging and goes away, without a clean close.
- Another session's DDL then fails, as it must while the lock is held.
- After the cleanup has run, that second session's DDL succeeds.

Make the wait deterministic rather than sleeping past 300 seconds in a test: whether that means a configurable interval, an internal seam to drive the reaper directly, or a test-only hook is part of what this ticket settles. A test that sleeps five minutes is not acceptable — the suite is already at the edge of the runner's limits, and `AGENTS.md` records the whole suite at over eleven minutes on a slow machine.

Decide also at which layer the test lives. `test-client-server` builds the layer-4 harness (a hosted server in a child process, a real client, dynamically allocated ports) and is the natural home for "the client machine vanished"; `tests/DAE.Server.Tests` can reach `RemoteServer`, `ConnectionManager` and the catalog store in process, which is cheaper and lower. Prefer the in-process layer for the lock-release behaviour and leave to `test-client-server` only what genuinely needs a separate process. The two tickets must not each write the same test; say in the ticket which owns what.

## Scope boundaries

- `port-server-on-net10` is the WS2 item that closes out after this one; it is not a place to defer findings to.
- A defect found here with a local, obvious fix is fixed here with its reproduction, per the project rules. One whose fix changes the connection or handle design becomes its own ticket.
- `docs/migration-notes.md` gets an entry for anything an operator or a custom extension could notice: a changed idle interval, a new setting, a changed public member on `ConnectionManager` or `RemoteServerConnection`.
