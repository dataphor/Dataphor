## What this is

Layer 4 of the test plan: *hosted server in a child process, real WCF client — connect, plans, cursors, streams, catalog cache synchronization, abandoned-session cleanup; ports allocated dynamically.* It is the only layer that exercises the protocol end to end, and nothing covers it today.

There is an old test project to learn from and largely to replace. `tests/DAE.Client.Tests` is still in the legacy project format, is not in `Dataphor.slnx` and is not built. It is known defect K18 in concentrated form: `OutOfProcessTestFixture` registers an instance in the **machine-wide** instance configuration, starts `DAEServer.exe` from a hard-coded relative path (`<installation>\Dataphor\bin\DAEServer.exe`), waits for the server by retrying a connection three times with half-second sleeps, uses the default port 8061, and `Provider/ConnectionTest.cs` connects through a machine alias called `LocalInstance`. It also uses the `ServerConfigurationManager` family (`SQLCEServerConfigurationManager` among them) that lived in `tests/DAE.Server.Tests/Utilities` and that `test-server-fixture` deleted — read them from git history if you want to see what they did, do not restore them.

What to build on instead: `TestEnvironment` and `TestServerInstance` in `tests/DAE.Server.Tests`, which already give a fresh run directory under `%TEMP%\Dataphor.Tests\`, a copy of the runtime layout's library folders, logging off by default, and cleanup afterwards. The cross-cutting isolation requirement stands: a fresh temporary instance directory, libraries from the layout rather than from source, and no test touching `%ProgramData%`, the registry or a fixed port.

## The problems to solve, in the order of how much they shape the design

**1. A child-process server needs a private instance configuration, and there is no way to give it one.** `InstanceManager` computes a machine-wide path and offers no override (`GetInstanceDirectory`, and `Server.cs` for the default per-instance directory). A child-process host started with `-n <instance>` loads that machine-wide file; if the instance is not in it, `DataphorServiceHost.Start` *adds it and saves the file* — so merely starting a test server writes to machine state. Either a redirection seam exists by the time this ticket runs or this ticket needs one. `host-instance-configuration` is the ticket that owns that seam and is asked to settle it; read what it decided before designing around it. If it decided not to add one, this ticket has to say how a child-process test gets isolation anyway, and that is a design decision, not an implementation detail.

**2. Dynamic ports versus the two fixed default ports.** The main service's port comes from the instance configuration and can be set per test. The listener's cannot in the same way: it is fixed at 8060 unless `OverrideListenerPortNumber` is set, and the client resolves an instance name through the listener whenever no port override is given. Settle how a test gets a listener on a port of its own on both sides of the connection, given that the two sides are different processes.

**3. The `ServerLink` coverage script, which is the hard case.** The script is recorded in `tests/DAE.Server.Tests/coverage-manifest.json` as a known failure owned by this ticket, and `tests/libraries/TestFramework.Coverage.Scripts/Documents/ServerLink.d4` requires a *second* Dataphor server: it does `create server Test tags { HostName = "localhost", InstanceName = "Dataphor" }` and also a default link with no tags at all, and sets no port override on either. So resolution goes through the listener on port 8060 to an instance literally named `Dataphor`, and the connection is made by `NativeCLIClient` from inside the server process running the script (`src/engine/Server/Server/RemoteSessionImplementation.cs`). The script is an assertion of correct behaviour and must not be edited — the project rules are explicit, and there is no reference runtime to re-derive it from.

   That leaves a real choice, and it is this ticket's to make:
   - make the default listener port settable process-wide (it is a `const` on `DataphorServiceUtility` today) so that the script's server, the linked server and the test all agree on a dynamically chosen port, with the script unchanged — this touches a compatibility surface (the default port) and so needs the change to be opt-in and invisible to a normal deployment;
   - or run `ServerLink` only in a mode that owns the default ports and a machine instance named `Dataphor`, reported visibly as not-run otherwise, which keeps the suite honest but leaves the script uncovered on a normal machine and in CI;
   - or leave it a known failure and say which ticket owns it next — which has to be justified, because this ticket is its recorded owner.

   Note also what `tickets/.pre-existing-known.md` records: on some machines the script's failure mode is a 120-second harness timeout rather than its recorded `SocketException`, because a loopback connect to a closed port is dropped rather than refused. Any design must not make the suite depend on how the machine treats closed ports.

**4. `DAE.Client` is not converted, so two of the old project's three test classes cannot come back yet.** `src/client/DAE.Client` (the `DataSession`/`DataView` data-binding layer) and `DAE.Client.Provider` (the ADO.NET provider) are still legacy projects outside `Dataphor.slnx`, and WS6 owns them. `CLI/CLITest.cs` happens to use `DataSession` only to reach a server session, so its coverage — a cursor over a table larger than the fetch count, navigated forwards, reset, re-navigated — can be written against `src/protocol/Client` (`ClientServer`/`LocalServer`, which is converted and gives `IServer`). `Frontend/DataViewTest.cs` and `Provider/ConnectionTest.cs` genuinely need the unconverted projects. Decide what happens to them: carried as a new ticket that waits on WS6, or recorded in this ticket's handoff for WS6 to pick up. Do not leave the old files sitting unbuilt with no owner, which is how K18 survived this long.

**5. What the layer must cover**, beyond reviving the old tests: connect and disconnect, a prepared plan executed more than once, a cursor fetched across more than one fetch batch with its capabilities exercised, a stream allocated, written, read back and deallocated, catalog cache synchronization (a DDL statement on one connection becoming visible to another), and a message well above WCF's default 64 KB cap so the 2 GB quotas are shown to be in effect. Plus the two specific cases other tickets have handed to this one:
   - **Abandoned-session cleanup across a process boundary.** `port-abandoned-session-cleanup` owns the behaviour and is asked to keep the lock-release test in process; only what genuinely needs a separate process belongs here. Agree the split with that ticket rather than duplicating its test.
   - **A deeply nested payload.** The server now references Newtonsoft.Json 13 where 3.1 used 9, and version 13 changed defaults — among them a default `MaxDepth` of 64 when reading JSON. Nothing that runs today exercises the server's JSON paths (`src/engine/Server/REST/RESTMarshal.cs` and the native interface's serialization), so include a native-interface call or REST payload nested deeply enough to cross that boundary, and say what the result was.

## Shape of the deliverable

A test project that builds and runs under `dotnet test` as part of the normal suite, in `Dataphor.slnx`, out of `tools/layout/Layout.csproj` (test projects stay out of the layout). Whether that is `tests/DAE.Client.Tests` revived under its own name or a new project named for what it tests is this ticket's call; if the old project is replaced, delete it rather than leaving it unbuilt, and record in the handoff what each deleted test intended — the same discipline `test-server-fixture` used.

Budget it against the runner's ten-minute idle limit and the suite's existing cost: starting a server process per fixture is expensive, so say how many child processes the design starts and roughly what that adds. If the layer cannot fit the existing three-part split, say which part it joins or whether a fourth part is needed, and update the commands in the root `AGENTS.md` and `tickets/rules/10-dataphor.md` accordingly.

## Sizing

Almost certainly more than one agent run. Split along seams that each leave a green suite, chained with `prereq:`, with the piece that finishes the work item keeping this slug — a plausible first cut is: the child-process fixture and one end-to-end session; then cursors, streams and catalog cache synchronization; then `ServerLink` and whatever its decision requires.
