## What this is

The largest remaining piece of WS8, and known defect **K17** in the plan: 203 links in the converted documentation under `docs/` point at reference pages that have never been converted. The material those links want - a page per built-in operator, a page per built-in scalar type, a page per shipped library, and the Frontend component reference - exists only in the old DocBook publishing tree under `legacy/Documentation/`, which the plan deletes once this work item has taken what it needs.

`docs-convert-asciidoc` (landed) converted the three AsciiDoc books and left those links recorded rather than broken: each one is listed in `tools/docs-convert/legacy-links.tsv` with the page it should go to, and the link checker reports them as *pending* instead of as errors while the list is passed to it.

This is a **plan** ticket: the material is large and the choice of source is not settled. Everything below is specification and measurement, not a design.

## What finished looks like

- Every page named in the `target` column of `tools/docs-convert/legacy-links.tsv` exists under `docs/reference/`, or the row has been retargeted to a page that does.
- `python tools/docs-link-check/check_links.py docs` - with **no** `--pending` argument - reports 0 errors.
- The four placeholder pages the conversion left behind are filled or replaced: `docs/reference/libraries/README.md`, `docs/reference/frontend-nodes/README.md`, `docs/reference/call-level-interface.md`, `docs/reference/data-access-components.md`. All four currently say "Under construction" and link the dead dataphor.org archive.
- Nothing in `docs/reference/` depends on a file under `legacy/Documentation/` any more, so `docs-remove-old-sources` can delete that tree.

## The page layout is already fixed

`docs-convert-asciidoc` chose the target paths and the converted pages already link to them, so this work item fills a layout it does not get to redesign:

| Old page name | Target page |
|---|---|
| `O-<Name>.html` | `reference/system-library/operators/<Name>.md` |
| `T-<Name>.html` | `reference/system-library/types/<Name>.md` |
| `DR<Name>Library.html` | `reference/libraries/<Name>.md` |
| `dilrefAlphora.Dataphor.Frontend.Client.I<Name>.html` | `reference/frontend-nodes/<Name>.md` |
| `Alphora.Dataphor.DAE.Client.<Name>.html` | `reference/data-access-components.md` |

Retargeting a row in `legacy-links.tsv` and fixing the link in the page is allowed and sometimes necessary (see *the four links with no source*); wholesale renaming of the scheme is not, because 203 links in landed pages use it.

## What the links actually ask for

Measured 2026-11-26 at commit `e414e316` from `tools/docs-convert/legacy-links.tsv`:

- 204 link occurrences, pointing at **107 distinct pages**: 88 operator pages, 19 type pages, 1 library page (`SimpleDevice`), 1 Frontend component page (`Frame`), and 1 to the Data Access Components placeholder.
- 203 of the 204 are still pending; the one that is not already resolves to the `data-access-components.md` placeholder.
- The source survey counted 206 occurrences of a legacy `.html` link; two of those sit inside broken markup in the operator-precedence table of the Developer's Guide and were never links.

**107 distinct pages is the link-repair minimum, not the work item's scope.** The plan's WS8 current-state paragraph describes the DocBook tree as the only source for "the system library reference (341 operator sections, plus 275 per-operator files), types and tables reference, device and connection library references, the Frontend and form-node (DIL) reference, keyboard shortcuts and several topic chapters." A reference that documents 88 of about 340 operators is not a reference. How much of the remainder to convert, and whether in one pass or several, is the first thing planning has to decide; the spec is that a reader can look up any built-in operator, type or shipped library.

## The sources, measured

Three candidate sources, all under `legacy/Documentation/` (81 MB, 786 files, excluded from the build and from the code-search index).

### 1. `legacy/Documentation/Docs2.0/` - the maintained DocBook, dated 2006-2007

62 XML files. The relevant ones:

| File | Size | Holds |
|---|---|---|
| `SystemOperators.xml` | 702 KB | **339 operator sections**, ids `O-<Name>`, each with Remarks, an Example with input and output, and See Also links |
| `SystemTypes.xml` | 60 KB | 20 type sections, ids `T-<Name>` |
| `SystemTables.xml` | - | the system tables reference |
| `FrontendOperators.xml`, `SQLDeviceOperators.xml`, `MSSQLDeviceOperators.xml`, `SimpleDeviceOperators.xml`, `SystemIntegrationOperators.xml` | - | the other libraries' operators |
| 14 `*LibraryReference.xml` / `*DeviceReference.xml` files | 8-18 KB each | one chapter per shipped library and device |
| `Keys.xml`, `TypeConventions.xml`, `TagsReference.xml`, `D4LanguageGuide.xml`, `RealSQLLanguageGuide.xml`, `ProgrammingTopics.xml` | - | keyboard shortcuts, conventions, and topic chapters, some of which the AsciiDoc books already cover |

Coverage of the 88 linked operators: **85**. Missing: `System.IndexOf`, `System.iXor`, and `System.SecurityOperartors` (a misspelling - see below).

### 2. `legacy/Documentation/DocBookManuals/OperatorDocs/` - 275 per-operator files, dated 2004

One `<sect2>` per operator, `<Name>.xml`, each with Remarks, an Example and See Also. These are the *external document* fragments the generator splices in, and they map one file to one page, which is the shape the target layout wants. Older than source 1, and 64 operators thinner. Coverage of the 88 linked operators: **80**; it does have `System.IndexOf` and `System.iXor`, which source 1 lacks.

### 3. `legacy/Documentation/Dataphor.chm` - the published help file, 3.2 MB

The compiled HTML help that was shipped. Its directory lists **3,335 pages**, including **389 `O-*` operator pages**, **22 `T-*` type pages** and **89 `DR*Library*` pages**, plus the Data Access Components API pages (`Alphora.Dataphor.DAE.Client.*.html`) that `reference/data-access-components.md` stands in for. Of the 107 pages the links want, **103 are in it**.

Its advantage is decisive for one thing and one thing only, described next.

### The generated-content gap

The DocBook under `Docs2.0/` is a **template**, not a finished document. Across its files there are 544 `<?DocLib D4ExpressionBlock …?>` and 688 `<?DocLib D4Field …?>` processing instructions - placeholders that the D4 operator in `legacy/libraries/Documentation` fills from a live catalog at publishing time. In `SystemOperators.xml` alone there are 596, two per operator section: every operator's **Declarations** block (its signatures) is a placeholder. So a straight DocBook conversion of source 1 produces 339 operator pages whose prose is right and whose signatures are empty. The same is true of each library chapter's Version, Requisites, Files, Registered Assemblies and Registered Classes sections.

The CHM has those placeholders already filled, because it was published through that generator. That is the trade: source 1 is the newest prose in an editable format with holes in it; source 3 is the same material a release older, rendered, with the holes filled, in a format (compiled HTML) that has to be unpacked and that pandoc reads as HTML rather than as DocBook.

A third route exists: fill the holes from the **live catalog** rather than from either document, which is what `docs-reference-generator` is for. That ticket is downstream of this one and its own planning ticket; the two have to agree on who produces the signatures, and the decision belongs to whichever is planned first - so say in this ticket's output which it is.

### The four links with no source

- `O-System.SecurityOperartors.html`, linked from `docs/users-guide/security.md` line 153. The misspelling is the AsciiDoc source's. No such page exists anywhere; retarget the link to the real security-operators page.
- `O-System.IndexOf.html` and `O-System.iXor.html` - in `OperatorDocs/` only, not in `Docs2.0/` and not in the CHM.
- `dilrefAlphora.Dataphor.Frontend.Client.IFrame.html`, linked from `docs/users-guide/tutorial-movie-rental.md` line 21. The Frontend component (DIL) reference is **entirely generated**: both copies of `DilReference.xml` are 300-byte stubs that say "This sect1 is generated through automation", there is no committed output, and the CHM has no `dilref` pages. So `docs/reference/frontend-nodes/` has no document source at all - it is either generated from the Frontend node types, written by hand, or the one link is retargeted. Whichever, decide it here; the folder's `README.md` placeholder is in the same position.

## The tooling that already exists

- **`python tools/docs-convert/convert.py docbook FILE.xml … --out DIR`** is the standalone DocBook stage: pandoc 3.14's DocBook reader plus the same tree-rewriting clean-up pass the AsciiDoc conversion used (headings, admonitions to GitHub alerts, footnotes, tables, code fences, image conversion, link resolution). Its options cover this work item on purpose: `--base`, `--pages TSV` (a page map of source to output), `--code-table`, `--xref-fixes`, `--match-heading-text`, `--global-ids`, `--legacy-html` and `--legacy-table`. `tools/docs-convert/README.md` documents all of it, and the prerequisites (Node, pandoc 3.14, Pillow, Python 3.12+) are pinned.
- **One known shape mismatch.** The DocBook stage writes **one page per input file**. Source 1's 339 operator sections are in a single file, so converting it as it stands gives one enormous page, not 339. Either the file is split before conversion (its sections are cleanly delimited by `<section id="O-…">`), or the stage grows a split mode, or source 2's one-file-per-operator shape is used instead. This is the main tooling question and it is why the item is marked *hard*.
- **`python tools/docs-link-check/check_links.py docs`** is the acceptance gate. Drop `--pending` once the pages exist. Note that `docs-link-check-ci` lands the CI step *with* `--pending`, so a partial landing here is safe: a pending target that starts existing is simply a valid link.

## Sizing: this must be split

One agent run cannot convert, review and land several hundred reference pages. Expect the plan's output to be a chain, with the ticket that finishes the work item keeping the `docs-convert-legacy-reference` slug and the earlier pieces taking new slugs chained to it with `prereq:` (the project's splitting rule). A natural seam set, for the planner to confirm or replace:

- the tooling change (whatever the split-or-not decision needs) and the page map, proved on a handful of pages;
- the operator pages;
- the type and system-table pages;
- the library and device reference pages;
- the four placeholder pages, the Frontend component question, and the link-list retargeting that closes K17.

## Questions planning must settle

1. **Which source for the operator and type prose** - `Docs2.0/` (newest, templated), `OperatorDocs/` (older, right shape), or the CHM (rendered, complete, needs unpacking)? Decide with evidence: compare the same operator across all three and say which text a reader is better served by.
2. **Where the signatures come from** - unpacked from the CHM, generated from a live catalog (which makes this item depend on work that `docs-reference-generator` owns), or left out of the first pass with the sections marked as missing. Leaving a *Declarations* heading with nothing under it on 339 pages is not an acceptable answer; either fill it or do not emit the heading.
3. **How much of the 341-section reference is in scope**, and if not all of it, what the rest is tracked as.
4. **One page per operator, or one page per operator group?** The link targets force a page per operator for at least the 88 that are linked. Whether the unlinked remainder gets the same treatment, and what the `reference/system-library/` index pages look like, is open.
5. **`docs/reference/frontend-nodes/`** - generated, hand-written, or the one link retargeted (see above).
6. **`reference/call-level-interface.md` and `reference/data-access-components.md`** - the CHM holds the DAC API pages; whether a .NET API reference belongs in this documentation set at all, or whether these two pages become short hand-written overviews that point at the source, is a judgment call. The CLI placeholder has no link pointing at it, so it is the cheapest one to settle.

## Edge cases & interactions the implement tickets will have to cover

- **Letter case.** The link checker compares every path component against the real directory listing, because Windows ignores case and GitHub does not. Page names here are `System.Abs.md`, mixed case, generated from ids - a case slip produces a link that works on the developer's machine and breaks on GitHub. CI runs the checker on Linux, which is the guard.
- **Page names with dots.** `System.Abs.md`, `System.iLike.md`, `System.VersionNumber.md`. Dots in a file name are fine, but the page-name rule in `convert.py` splits camel case and non-alphanumerics into kebab case (`SQLDevice` → `sql-device`), so these pages must come from an explicit `--pages` map, not from the rule.
- **Duplicate and ambiguous headings.** The AsciiDoc conversion hit this (two `Metadata` headings, two `Security` sections) and `xref-fixes.tsv` exists to settle it. A reference with 339 similarly-shaped sections will hit it harder.
- **Cross-links between the new pages.** Every operator page's *See Also* block links other reference pages (`<ulink url="O-System.Any.html">`) and back into the guides (`D4LGTableExpressions-Aggregate.html`). Those are the same rewrite rule as the pending list, applied in the other direction, and they must land resolved - this is where a silent drop would hide.
- **Two overlapping sources means duplicate text.** If both `Docs2.0/` and `OperatorDocs/` are used, each operator can be documented twice with different wording. One page per operator, one source per page.
- **Images.** The DocBook trees carry their own images (`Docs2.0/Images`, `DocBookManuals/images`); any image a converted page uses must land in `docs/images/` with its name through the same rule, and `docs/images/` currently has no orphans - a property worth keeping.
- **Reproducibility.** The AsciiDoc conversion is rerunnable and reproduces its output byte for byte, which is how it was verified. Keep that property for the DocBook pass until `docs-remove-old-sources`, because it is the only cheap check that a rerun did not quietly change hundreds of pages.
- **Size.** 339 operator pages plus types, tables and libraries is a large number of small files, and `docs/` is currently 73 pages. Check nothing in the repository enumerates `docs/**` with an assumption about its size (the size checker reads only `docs/architecture/`; the link checker scales fine at 90 files but should be timed at the new size, since it becomes a CI step).
- **The CHM, if it is used, is a binary extracted at planning time.** `.gitattributes` already marks `*.chm` binary. Whatever is extracted from it must be converted and committed as Markdown; do not commit an intermediate HTML dump, and do not leave an extraction artifact anywhere in the tree (`tickets/.logs/` is for logs, not for artifacts).
- **No compatibility surface is touched.** This is documentation only. But the reference *describes* operator signatures, which are a compatibility surface, so a signature that disagrees with the code is a finding worth reporting rather than silently "corrected" to match the code - the old reference disagreeing with 4.0 is itself information.
- **Privacy.** The repository is public and this is the project's own published documentation; there is no customer material in it. Check anyway when unpacking the CHM, which has 3,335 pages nobody has read recently.

## Tests

Converted documentation is checked by the link checker, not by unit tests, and the project's testing rule asks for a characterization test when behaviour is ported - no behaviour is. Two exceptions worth naming to whoever plans this:

- **A tooling change gets a test.** If `convert.py` grows a split mode or a new page-map rule, that branch takes a case in `tools/docs-convert/test_convert.py`, the way the ambiguous-reference branch did in `docs-convert-asciidoc`. One test per behaviour, at the resolver, with no pandoc or Node needed.
- **Nothing else.** A test that counts pages, or asserts that a particular operator page exists, pins a number that the next pass changes; the link checker already fails if a page a document references is missing, which is the property that matters.
