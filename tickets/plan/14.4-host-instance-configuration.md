## What this is

Two things, both about the machine-wide instance configuration file:

1. **Known defect K27 — the file is shared with 3.1, and must not be.** `InstanceManager` keeps the list of server instances in `ServerConfigurations.config` under a directory built by `PathUtility.CommonAppDataPath(String.Empty, VersionModifier.None)`, which produces `%ProgramData%\Alphora\Dataphor\Instances` with no version in it. `Server.cs` (about line 728) defaults an instance's own directory under the same path. A 4.0 server installed beside a 3.1 server — which is what WS9 and open question Q9 intend — therefore reads 3.1's instance list, writes to it, and defaults its catalog and per-instance data into 3.1's folders.
2. **Keep the file readable and writable, and document it.** The format is BOP XML over `InstanceConfiguration`/`ServerConfiguration`, which is a compatibility surface: existing deployments have hand-edited and tool-edited copies. Every setting in it needs a plain-language description in the user documentation, which today describes none of them (`docs/users-guide/dataphor-service.md`, `dataphor-server.md`).

## The decision, with the evidence and a proposal

**This is a change to the on-disk instance layout, which the project rules list as a compatibility surface. Take it to `blocked/` with the proposal below for the owner to accept or edit; do not decide it inside an implement ticket.** The proposal is drafted here so that the blocked ticket is quick to write and the owner gets one crisp choice.

What the code already does, which is the strongest evidence available:

| What | Path modifier | Result for 4.0 | Shared with 3.1? |
|---|---|---|---|
| Client alias list, `Aliases.config` (`src/client/DAE.Client/AliasManager.cs`, machine and user copies) | `MajorSpecific` | `…\Alphora\Dataphor\4\Aliases.config` | no |
| Server instance list, `ServerConfigurations.config` (`InstanceManager`) | `None` | `…\Alphora\Dataphor\Instances\` | **yes** |
| Default per-instance directory (`Server.cs`) | `None` | `…\Alphora\Dataphor\Instances\<name>\` | **yes** |
| Large-value overflow streams (`Streams/FileStreamProvider.cs`) | `VersionSpecific` | `…\Alphora\Dataphor\4.0\<guid>\` | no |
| Configuration utility settings (`src/windows/ConfigurationUtility/ApplicationForm.cs`) | `VersionSpecific` | `…\Alphora\Dataphor\4.0\` | no |

So 3.1 already separated three of these five by version and left the instance configuration behind. The anomaly is the instance list, not the alias list.

**Proposed:** change both `None` call sites to `VersionModifier.MajorSpecific`, giving `%ProgramData%\Alphora\Dataphor\4\Instances\`, matching the alias file the client has always kept that way. A 4.0 server then never reads, writes or inherits 3.1's instance list, and the two can run side by side on one machine.

**What it costs.** An operator upgrading from 3.1 does not see their existing instances: a 4.0 server started with no instance registered creates a default one (`DataphorServiceHost.Start` already does this, adding `ServerConfiguration.DefaultInstance` and saving the file). Their port numbers, library directories and device settings have to be re-entered, by hand or by the installer. This is consistent with decision D3 — existing catalogs are not brought across and are rebuilt from library scripts — because the catalog lives under the instance directory, so an inherited instance list would point a 4.0 server at a 3.1 catalog it cannot open anyway.

**Alternatives to put to the owner:**

- *Read the old file once and copy it forward* — the installer, or the server on first start, migrates `…\Dataphor\Instances\ServerConfigurations.config` into the versioned location. Keeps the operator's settings; costs a migration step that can half-succeed, and silently adopts settings that 4.0 may no longer honour (`UseServiceConfiguration`, `AllowSilverlightClients`).
- *Keep the shared path and refuse a 3.x file* — detect a configuration written by an older version and fail to start with an error naming the file. Smallest code change; makes side-by-side installation impossible, which contradicts Q9.
- *Do nothing* — a 4.0 server silently writes into 3.1's configuration. A 3.1 server then reads instance entries it may not understand, and the two compete for the same per-instance directories and catalog files. This is the status quo and the defect.

Reversibility: high. The path is computed in two call sites and changing it back is a one-line edit, but any instance registered at the new path has to be re-registered if it is reverted.

Whichever is chosen, it needs a `docs/migration-notes.md` entry — an operator and an installer both notice it — and WS9's installer work has to be told, since the installer registers the service and creates these directories.

## Interactions to settle at the same time

- **Known defect K12, the other half.** `DataphorService`'s parameterless constructor reads `ConfigurationManager.GetSection("instance")` to find an instance name, while the shipped `DAEService/app.config` declares a section called `dataphor` — so that section has never been read, and the instance name has always come from the command line. `host-generic-host` decides whether a configuration file survives at all; this ticket owns whatever is left of the *settings* question. Do not have both tickets claim it: say in this ticket which half it covers, and check what `host-generic-host` actually did before assuming.
- **`InstanceManager` is a static with no way to redirect it.** The configuration path is machine-wide and computed, which is why the in-process test fixture avoids `InstanceManager` entirely and why `tests/DAE.Client.Tests` had to register a machine-wide instance (known defect K18). `test-client-server` needs a child-process host that reads a private instance configuration. Settle here whether a redirection seam exists — an environment variable, a settable static, a host option — because this is the natural place for it and both the test ticket and anyone diagnosing a deployment need it. If it is added, it is a public surface and a migration-notes entry.
- **Settings that may no longer exist.** `UseServiceConfiguration` and `AllowSilverlightClients` are gone already: `protocol-corewcf-host-prepare` deleted both properties, with migration-notes entries. `protocol-transport-security` still decides the fate of `RequireSecureConnection` and `RequireSecureListenerConnection` (both of which the server ignores today — see that ticket). The documentation this ticket writes has to describe the settings as they actually are after that lands, not as the property list looks. Read its outcome before writing the page.
- **BOP and unknown attributes — settled.** A `ServerConfigurations.config` that carries an attribute the current `ServerConfiguration` does not declare loads, and every other setting on the instance is still read: the deserializer records the unknown attribute as an error in a list that `InstanceConfiguration.Load` never consults. `protocol-corewcf-host-prepare` established this and pinned it with `LoadReadsAFileCarryingSettingsThatNoLongerExist` in `tests/DAE.Server.Tests/InstanceConfigurationTest.cs`, which is the rule for every later removal from the file. What is still only established by inspection is the other direction: the unknown attribute disappears the next time the list is saved, because the serializer writes properties and there is no longer one. Document both.

## What the documentation has to say

One section, in the user guide rather than in the modernization plan, listing every setting in `ServerConfiguration` — `Name`, `PortNumber`, `ShouldListen`, `OverrideListenerPortNumber`, `LibraryDirectories`, `InstanceDirectory`, `CatalogStoreClassName`, `CatalogStoreConnectionString`, `DeviceSettings`, plus whichever security and compatibility settings survive — with for each: what it does, its default, what an operator would change it for, and what happens when it is absent. Say where the file lives, that it is machine-wide, and that the configuration utility and the server itself both write it. Defaults are in `ServerConfiguration` (`DefaultPortNumber` 8061, `DefaultLocalInstanceName` `LocalInstance`, `DefaultLocalPortNumber` 8062, `ShouldListen` true) and in `Server` (`DefaultLibraryDirectory`, `DefaultInstanceDirectory`); the SQLite store default was set by `store-remove-sqlce-references` — read it from the code rather than from this list.
