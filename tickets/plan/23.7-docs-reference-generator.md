## What this is

The plan's WS8 work item `docs-reference-generator`: "Markdown emitter for the catalog documentation operator; regenerate and diff."

A reference that lists every built-in operator's signature by hand goes stale the first time an operator changes, and nothing notices. Dataphor shipped a tool against exactly that problem: a D4 operator that walks a *running server's* catalog and writes the reference pages, splicing hand-written prose in from separate files. That is how the published 3.x reference was built, and it is why the DocBook source under `legacy/Documentation/Docs2.0/` has placeholders where every operator's signature should be. This work item brings that tool forward so the reference under `docs/reference/` can be regenerated and compared with the text `docs-convert-legacy-reference` lands - the comparison being the point, not the regeneration.

This is a **plan** ticket because the main question is where the tool should live, and the answer decides how much work it is.

## The tool, measured

`legacy/libraries/Documentation/`, parked there by the repository reorganization. 1,859 lines in all.

```
Documentation.d4l                 library descriptor: one file reference (DocSamples.dll), requires MSSQLDevice
Documents/Register.d4      139    registers the two operators; creates a DocumentationDevice on MSSQL and
                                  the review-workflow tables (ObjectType, Category, TextClass, CatalogObject,
                                  CatalogObjectText) with roles Documenter and Reviewer
Documents/Documentation.d4  67    seed rows for those tables
Documents/DocLibraries.d4  163    driver script
Documents/GenSysDocs.d4     82    driver script: the two calls that produced the published reference
Source/Samples.cs         1245    DocCatalogObject, DocOperator, DocOperatorOrdered, DocLibrary
Source/ObjectMetaDataNode.cs 57
Source/Register.cs          29    DAERegister.GetClasses(): DocSamples.DocOperator, DocSamples.DocLibrary,
                                  DocSamples.ObjectMetaDataNode
Source/DocSamples.csproj          .NET Framework 4.5.2, non-SDK
```

What it does, from `GenSysDocs.d4`:

- `DocOperator(template, title, outputPath, cursor)` - given a cursor of catalog object names, writes one document describing them. The published run passed `"Docbook"` as the template and a cursor over `Operators over {Name} where 'System.'.Pos(Name) = 0`, and wrote `Docs2.0/SystemLibrary.xml`. A second call did the same for `TableVars`.
- `DocLibrary(libraryName, xmlTemplate, extDocPath, outputPath, traceOn)` - takes a DocBook template, splices in the hand-written per-operator fragments from a folder (`DocBookManuals/OperatorDocs/`, 275 files) and the live catalog's own facts, and writes the finished chapter. This is the call that filled the 544 `<?DocLib D4ExpressionBlock …?>` and 688 `<?DocLib D4Field …?>` placeholders in the DocBook sources.

So the catalog supplies the *facts* - operator signatures and declarations, library version, requisites, files, registered assemblies and classes - and the documents supply the *prose*. The emitter is `System.Xml.Xsl`-based and writes DocBook.

### Two things that are not obstacles, and one that is

- **The MSSQL dependency is not for generation.** `Register.d4` creates a `DocumentationDevice` on SQL Server holding `CatalogObject`, `CatalogObjectText` and friends - a *review workflow* (proposed text, approved text, who approved it, when) with its own roles. None of it is read to produce a page. A Markdown emitter needs none of it.
- **The prose is in the repository.** The hand-written fragments are the 275 files under `legacy/Documentation/DocBookManuals/OperatorDocs/` and the inline sections of `Docs2.0/SystemOperators.xml`, both tracked. Nothing has to be recovered from a customer database.
- **`legacy/` is excluded from the build and "not to be fixed"** (`AGENTS.md`). A parked library cannot be run, so either it moves back into `libraries/` and into `Dataphor.slnx` as an SDK-style `net10.0` project, or the emitter is written somewhere else.

## The question this ticket exists to answer

**Where does the Markdown emitter live?** Three candidates, with what each costs:

1. **Move `legacy/libraries/Documentation` back to `libraries/Documentation` and into the build.** Convert `DocSamples.csproj` to SDK-style `net10.0`, add it to `Dataphor.slnx` and to the runtime layout, add a Markdown template beside the DocBook one. Cost: a new shipped library and a new assembly name, with everything that implies - `DAERegister.GetClasses()` class names become a compatibility surface the moment the library ships, the library folder joins `tools/layout/Layout.csproj`, and the installer eventually carries it. Benefit: the tool is a D4 operator again, driven by a script, exactly as the product documented it.
2. **Write the emitter as a test-only or tool-only program** against the in-process engine harness (`test-harness-inprocess`, landed), reading the catalog through the existing fixtures and writing Markdown. Cost: the operator-registration mechanism is not reused, so `Samples.cs` is a reference rather than a base; the generator is not something an administrator can run against their own catalog. Benefit: nothing new ships, no new compatibility surface, and the comparison runs where the suite already starts servers.
3. **Make it a check rather than a generator** - a test that walks the catalog and asserts that each operator page under `docs/reference/system-library/operators/` names the signature the catalog actually has, reporting the differences instead of rewriting the pages. Cost: the pages still have to be written by hand once. Benefit: it is the smallest thing that stops the reference drifting, and drift-detection is what the "regenerate and diff" in the plan row is for.

Decide with the evidence, and say plainly what is given up. One consideration that cuts across all three: the plan's WS10 table lists a `dataphor docs generate` command under "WS8 reference generation", which argues for option 1 or something an administrator can invoke; weigh that against it being a line in a table of future commands, not a commitment.

### A sequencing trap to settle in the same breath

The existing generator reads the **DocBook templates** under `legacy/Documentation/Docs2.0/` - and `docs-remove-old-sources` deletes that tree. A generator that still needs those templates stops working the day that ticket lands, which means either this item runs first (it cannot: it waits on `docs-convert-legacy-reference`, which that ticket also waits on) or the Markdown emitter must not read them at all.

**The shape that avoids the trap**, as a starting hypothesis rather than a decision: emit Markdown directly from the catalog - names, signatures, library facts - and keep the prose in the converted `docs/reference/` pages as the hand-written half, so "regenerate and diff" compares generated facts against committed pages and needs no template. That also answers question 2 of `docs-convert-legacy-reference` ("where do the signatures come from"), so the two tickets have to agree; whichever is planned second adopts the other's answer rather than re-deciding it.

## What finished looks like

- The reference's generated half can be produced from a running 4.0 server by a documented command, and the command is written down where a reader will find it.
- Running it against the committed `docs/reference/system-library/` pages reports the differences, and that report has been read: a difference is either a stale page, a real behaviour change since 3.x worth a line in `docs/migration-notes.md`, or a defect.
- The decision above is recorded in `docs/modernization-plan.md` the way other settled WS8 decisions are, including what was given up.
- `legacy/libraries/Documentation` is either moved (option 1) or explicitly left parked with the reason, so the next reader does not re-open the question.

## Edge cases & interactions the implement tickets will have to cover

- **A move and an edit are separate commits** (project rule). Option 1 means one rename-only commit, then the conversion.
- **Class names and assembly name.** If the library ships, `DocSamples.DocOperator`, `DocSamples.DocLibrary` and `DocSamples.ObjectMetaDataNode` and the assembly name `DocSamples` become compatibility surfaces. Renaming them to match current conventions is the kind of change that has to be deliberate and recorded in `docs/migration-notes.md`, not a tidy-up. `ObjectMetaDataNode`'s own comment says "registered for testing/proof of concept, todo: move to System later" - deciding whether it ships at all is part of option 1.
- **`DocOperatorOrdered`** (a subclass of `DocOperator`) is registered by none of the scripts. Whether it is dead or was driven by a script that was not committed is worth five minutes before anything is ported.
- **A backward-navigable cursor is required.** `GenSysDocs.d4` says so in a comment, because overloaded operators are found by navigating backwards; its cursor asks for `capabilities {navigable, backwardsnavigable}`. Any replacement has to produce every overload of an operator, and a generator that silently emits one overload per name is the likely defect.
- **Determinism.** Generated output has to be stable across runs on the same catalog or the diff is worthless: a fixed order (the cursor's `order by {Name}`), no timestamps (the DocBook emitter wrote a `<date>` into every section - a Markdown emitter must not), and LF line endings with no byte-order mark like every other file under `docs/`.
- **Which catalog.** A generated reference describes whatever libraries are registered in the server it ran against. The published run used `'System.'.Pos(Name) = 0` to take the System library only; any other library's operators appear or not depending on what was loaded, which makes "the diff is clean" meaningless unless the set of registered libraries is pinned. Name the set.
- **Signatures are a compatibility surface.** A generated signature that differs from the 3.x reference is evidence about the port, and the first place it should be looked at. Do not "fix" a page to match the code without asking whether the code is what changed.
- **One disagreement is already known, and it is not a port regression.** `docs-reference-operators` compared the signatures it published against `src/engine/DAE/Schema/SystemCatalog.d4`: of the 282 operator names both carry, 262 have identical parameter lists once the help file's `generic list`, `row` and `cursor` spellings are read as the bare types the script writes. Twelve more are overloads the script declares and the 2007 help file never listed, and seven are selectors and comparison operators a scalar type's `representation` generates rather than a script declaring them (their parameter names have no `A` prefix, which is the tell). The twentieth is real: the page `docs/reference/system-library/operators/System.Execute.md` publishes `System.Execute(const AScript : String)`, and no such overload exists - the script declares five `Execute` overloads, none of them the one-argument form, and `git show 361ebd83:Dataphor/DAE/Schema/SystemCatalog.d4` (the 2008 open-source import) already lacks it, so the gap predates this modernization. The page was left as what shipped. This is the first case the generated-versus-published diff should explain. Note the sweep covers only the names the catalog script declares; many operators are registered in C# instead, so it is a spot check, not a proof that nothing else disagrees.
- **The library pages drift too, and by more than the core library does.** Measured while reviewing `docs-reference-libraries`, by counting the distinct operator names each library's own `Documents/*.d4` declares against the operator sections its page carries: `Frontend` declares 36 and documents 29; `SQLDevice` declares 19 and documents 6 (the 13 missing are mostly the `SQLText` type's own comparison and string operators, plus `DeviceReconciliationScript`); `SimpleDevice` and `System.Integration` document all of theirs. Three more libraries - `Connection`, `Security` and `System.Internet`, 77 declarations between them - have no operator documentation at all, because the 2007 chapter pulled it in from a file this repository does not contain. So the generated-versus-published diff is not only a check on the System library: for `docs/reference/libraries/` it is the only route to a complete page, which is worth weighing when deciding which catalog the generator runs against (the published run took `'System.'.Pos(Name) = 0`, i.e. the System library alone).
- **The engine must not be mutated to make generation convenient.** The facts the generator wants (`Operators`, `TableVars`, `LibraryRequisites`, `LibraryFiles`, `RegisteredAssemblies`, `RegisteredClasses`, `Script(Name)`) are all queryable today; `GenSysDocs.d4` and `SystemLibraryReference.xml` between them show every expression the published run used.
- **Privacy.** A generator run against a real deployment's catalog would name that deployment's libraries. Whatever is committed comes from a server started on this repository's own sample libraries, and the documented procedure says so.

## Tests

The project's testing rule applies: a subsystem whose behaviour is re-hosted owes a characterization test. What that means here depends on the decision, so stated conditionally rather than prescribed:

- **If the generator runs in-process** (options 2 and 3), its one test is that generating from a server with a known registered library set produces the expected pages' facts - the lowest layer that shows the behaviour, which is a D4 script through the in-process harness where possible and a C# fixture where it is not.
- **If the library moves into the build** (option 1), the port owes a characterization test that the operator still produces what it produced before for one small, pinned catalog - not a test per operator.
- **Not worth a test either way:** that the operators are registered (`GetClasses()` is checked by the library loading at start), the emitter's formatting beyond one golden page, or the count of pages produced.
- **Never edit an expected value in an existing D4 test script to make a run pass.** There is no reference runtime; those assertions are the record.
