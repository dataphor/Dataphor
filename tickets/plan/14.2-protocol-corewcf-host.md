## What this is

`protocol-corewcf-proof` shows that one session works over the existing binding on a minimal host. This item turns that into the real thing: all three services, every operation, started and stopped by the same `DataphorServiceHost` entry points the console host and the Windows service already call, with the addresses, ports and instance configuration unchanged.

Plan it only after the proof has landed, and read the proof's write-up (a section under WS5 in `docs/modernization-plan.md`) first — it settles the binding, instancing, message-size, fault and timeout questions, and this ticket must not re-open them.

## What has to come back

Four files are excluded from `src/engine/Server/Server.csproj`, each marked by an XML comment that names this ticket. The compile list and the comment block above it both have to end up clean — no leftover comment claiming something is still excluded:

| File | What it holds |
|---|---|
| `Service/DataphorServiceHost.cs` | the start/stop lifecycle: loads the instance, starts the `Server`, opens the three hosts in order, and tears them down |
| `Service/ListenerServiceHost.cs` | the listener's own host, on the shared default port |
| `Service/CustomServiceHost.cs` | reads endpoints from `<system.serviceModel>` when `UseServiceConfiguration` is set |
| `NativeCLI/NativeCLIService.cs` | the eleven native-CLI operations |

`Service/DataphorService.cs` (the main service, 88 operations over the handle manager and connection manager) and `Service/ListenerService.cs` (the three listener operations, answered from the machine instance configuration) are **already compiled**: `protocol-corewcf-proof` brought them back on CoreWCF's behaviour and fault attributes and ran the shipped client against them over the wire. Do not re-exclude them and do not change their `using CoreWCF;` back; the proof's write-up says why. `DataphorService` now has a single constructor taking a started `RemoteServer`, the configuration-reading parameterless one having been removed.

`Service/ConnectionManager.cs` and `Service/HandleManager.cs` are already compiled and use no WCF; leave them alone here (`port-abandoned-session-cleanup` owns the connection manager's behaviour).

## Decisions this ticket has to make, and the facts behind them

- **`CustomServiceHost` and `UseServiceConfiguration` go.** The plan removes the "endpoints from `app.config`" path, Q8 is answered "use unknown, assumed unused", and the client half of it already throws `NotSupportedException` with a message telling the user to connect by host, instance and port (see `ClientServer.Open`, and the `docs/migration-notes.md` entry for the three client constructors). So `CustomServiceHost.cs` is deleted rather than ported, `ServerConfiguration.UseServiceConfiguration` is removed, and the three call sites in `DataphorServiceHost` and `ListenerServiceHost` lose their branch. `ServerConfiguration` is a BOP-serialized compatibility surface: a deployed `ServerConfigurations.config` may carry a `UseServiceConfiguration` attribute, so settle — and state in the ticket — whether BOP ignores an unknown attribute or fails the load, and if it fails, keep the property as an ignored no-op instead of removing it. Check the behaviour, do not guess it. `src/windows/Frontend.Client.Windows/Forms/EditInstanceForm.cs` has the checkbox that writes it and belongs to WS6; removing the property means that form stops compiling, so either leave the property as a no-op or hand WS6 the edit — decide, and say which in the ticket.
- **The client's endpoint-configuration constructors.** The plan's row says "client constructors fixed". They currently exist and throw. Decide between deleting them (a source-breaking change for a custom C# extension, needing a `docs/migration-notes.md` entry) and leaving them throwing (already noted in the migration notes, nothing further owed). Prefer the smaller change unless the proof found a reason otherwise.
- **How the three hosts are opened.** `DataphorServiceHost.Start` currently opens them in a fixed order — main, native, then the listener if `ShouldListen` — and `Stop` closes them in reverse, using `BeginClose` on the two service hosts and a plain `Close` on the listener. On CoreWCF the hosting model is a Generic Host with services registered up front, which does not naturally give a mid-process "open this one now". Settle whether `DataphorServiceHost` keeps its own small host internally (so `DAEServer` and the Windows service keep working with no change, and `host-generic-host` reshapes them next) or whether this ticket already hands the services to a host built outside it. The first keeps this ticket to one subsystem; the second overlaps `host-generic-host`. Pick the first unless the proof found it impossible, and say so.
- **The listener's port conflict is a feature.** `ListenerServiceHost`'s constructor catches and discards the exception from `Open()` with the comment that another process is already listening. One listener per machine serves every instance on it, which is why its port is fixed. Whatever CoreWCF reports when the port is taken must still be swallowed, and a server whose listener could not start must still start and still serve its own endpoint. Keep this; do not "fix" it into a failure.
- **The two dead security parameters.** `ListenerServiceHost` takes `requireSecureConnection` and `useCrossDomainService` and uses neither, and `DataphorServiceHost.Start` never reads `instance.RequireSecureConnection`. Do not start honouring them here and do not delete the settings: `protocol-transport-security` owns that question and needs the evidence intact. If a parameter has to go to make the signature compile, record it for that ticket.
- **`AllowSilverlightClients`** existed for the removed Silverlight cross-domain policy service. The setting is still read in `DataphorServiceHost` and passed to a parameter nobody uses. Removing it is a `ServerConfigurations.config` compatibility question with the same shape as `UseServiceConfiguration`; settle both the same way.

## What must still be true afterwards

- An existing client, with no edits and no configuration change, connects to a 4.0 server on the default ports and completes everything it does today: sessions, prepared plans, cursors with their capabilities, streams, catalog cache synchronization, the debugger operations, and native-CLI calls.
- The addresses and default ports are byte-for-byte what `DataphorServiceUtility` builds today, including the instance name segment and the `/service/native` suffix.
- A server link from one Dataphor server to another still works — it goes out through `NativeCLIClient` from inside the server process (`src/engine/Server/Server/RemoteSessionImplementation.cs`), so the native service has to be reachable, not merely hosted. The `ServerLink` coverage script is the acceptance of that, and it is owned by `test-client-server`; this ticket is not expected to turn it green on its own, but it should say what remains.
- `docs/migration-notes.md`: the interim entry about the server assembly not containing the WCF service and host classes gets its final wording, and anything removed (`UseServiceConfiguration`, a client constructor, a public type) gets an entry of its own.
- `docs/architecture.md`'s hosting section and the AGENTS.md "Converted so far" line, which both say the server is built without its WCF classes, stop saying that. The net-spike expectations in AGENTS.md also name `DataphorServiceHost` as the reason `DAE.Client`, `DAEServer` and `DAE.Service` fail to build; re-measure and correct that line rather than assuming it is now clean.
