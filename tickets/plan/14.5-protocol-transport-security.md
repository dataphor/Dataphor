## What this is

The plan's item reads "make the secured-connection options work on CoreWCF, or document their removal (Q8)". Before either can be planned, one fact has to be in front of the reader, because it changes the whole shape of the ticket:

**As the product ships, none of the secured-connection settings do anything.** They are read, stored, passed down several layers, exposed as public properties — and never reach a binding. Verified by reading every use:

| Setting | Where a user sets it | What the code does with it |
|---|---|---|
| `SecurityMode`, `ListenerSecurityMode` | client alias, `Aliases.config` (`src/client/DAE.Client/Alias.cs`) | passed to `ClientServer`'s constructor, stored in a field, exposed as a property. `ClientServer.Open` ignores it and always calls `DataphorServiceUtility.GetBinding()` |
| `RequireSecureConnection` | instance configuration, `ServerConfigurations.config`; the checkbox in `EditInstanceForm` | nothing reads it. `DataphorServiceHost.Start` never mentions it |
| `RequireSecureListenerConnection` | same | passed to `ListenerServiceHost`'s constructor as `requireSecureConnection` and never used in the body |
| `UseSecureConnection`, `UseSecureListenerConnection` | **D4**, as metadata tags on `create server` (`src/engine/DAE/Schema/ServerLink.cs`) | converted to `ConnectionSecurityMode.Transport` and handed to `NativeCLIClient` (`src/engine/Server/Server/RemoteSessionImplementation.cs`), which stores it in a field and exposes a property. The binding comes from `GetBinding()` regardless |

The only machinery that could ever have produced a secured channel is the three public hooks on `DataphorServiceUtility` — `BuildBindingCall`, `BuildEndpointIdentityCall` and `ServiceEndpointHook` — which replace the binding and the endpoint identity wholesale. Nothing in the repository sets them, so a deployment that wanted transport security had to supply its own binding through them from its own host code. Those hooks are public static API and may be in use: open question Q8 records the answer as "not known", and the plan's instruction is to proceed as if neither `UseServiceConfiguration` nor secured transport is used.

So this ticket is not "port a working feature". It is: decide whether to make these settings mean what they say, or to say plainly that they never did.

## What has to be settled

- **Make them work, or retire them?** Weigh: implementing transport security means the binding stops being one process-wide memoized singleton (`GetBinding` caches one `Binding` in a static) and becomes per-endpoint, on both sides, plus a certificate story for the server, plus the endpoint identity the hooks hint at — a real feature, in a workstream whose job is to not change the protocol. Retiring them means a `docs/migration-notes.md` entry and a documented statement that connections are unsecured unless a host supplies its own binding. Note that WS11 owns security as a workstream; if the answer is "make them work", consider whether the item belongs there instead, and say so rather than silently expanding WS5.
- **Whatever is decided, the hooks stay.** They are the one extension point by which a deployment could already have secured the channel, and removing them would break exactly the deployment that cared. If the hooks stay, a retirement is honest: the capability is still reachable, just not through the settings.
- **The settings are each on a compatibility surface, and they are not alike.** The client alias and the instance configuration are BOP files whose unknown-attribute behaviour decides whether a property can be removed at all (`host-instance-configuration` and `protocol-corewcf-host` establish this; read their outcome). The two `create server` tags are **D4**: a customer library can contain `create server X tags { UseSecureConnection = "true" }`, and the project rules forbid changing D4 semantics or dropping a tag without a ticket that says so explicitly. Settle what happens to a library that uses the tag: ignored as today, a warning, or an error. "Ignored as today" is the only option that cannot break an existing library, and it is what the code does now.
- **Does `protocol-corewcf-host` change the answer?** Read the proof's write-up and the host ticket's outcome first: if CoreWCF's NetTcp transport cannot be configured without security at all, or configures it differently, that constrains this decision rather than being decided by it.
- **If a setting is retired, what does a user who set it see?** Silence is the current behaviour and the worst one — a user who ticks "Require Secure Connection" today gets an unsecured server and no hint. Prefer a path where the setting's presence is at least reported: a warning in the server log at start when `RequireSecureConnection` is set and nothing honours it, say. Decide, and name the cost.

## What the deliverable is

Either an implement ticket that makes the settings produce a secured channel, with a test that shows an unsecured client being refused by a server that requires security (and the reverse) — or an implement ticket that retires them, consisting of: the removals, the surviving hooks documented as the way to supply a binding, a `docs/migration-notes.md` entry, a line in the user-guide section that `host-instance-configuration` writes, and whatever reporting was chosen for a setting that no longer does anything. In the retirement case the `docs/architecture.md` hosting section, which describes the binding as "no security by default", should say "no security" without the qualifier.

If the choice between the two turns on something only the owner can answer — whether any deployment actually relies on secured transport, which is Q8 — note that the plan has already answered it ("proceed as if neither is used") and decide on that basis. Do not route Q8 to `blocked/` again.
