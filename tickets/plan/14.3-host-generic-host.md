## What this is

Today the server ships as two executables over the same `DataphorServiceHost`:

- `src/hosts/DAEServer` → `DAEServer.exe`, a console program. `Program.Main` reads `-n`/`-name`, starts the host, waits on `Console.ReadLine()`, stops it. Its vendored `CommandLineArguments.cs` is compiled but never used by `Program.cs`, and is the file that fails to compile on .NET 10 because it uses `field` as a variable name inside a property accessor (known defect K23, owned by WS10 `tool-cli-skeleton`).
- `src/hosts/DAEService` → `DAEService.exe`, a Windows service. `Service` derives from `System.ServiceProcess.ServiceBase`; `-i`/`-u` install and uninstall it through `System.Configuration.Install` (`TransactedInstaller`, `ProjectInstaller` in `ServiceInstaller.cs`), which no longer exists on .NET 10; `-r` runs it in a console. `ServiceUtility` names the service `Alphora Dataphor (<instance>)`, reads and writes its start mode directly in `HKLM\System\CurrentControlSet\Services\<service name>`, and reports status through `ServiceController`.

Neither project has been converted to the SDK format. The target is one executable on the .NET Generic Host that runs in a console or, with `UseWindowsService`, as a service, shuts down gracefully, and registers or unregisters the service from a command of its own instead of from an installer class.

## Why this needs planning rather than a TODO list

Four questions have to be settled before anyone writes code, and each has a visible cost:

**One executable or two?** The plan says "one host built on the .NET Generic Host: `DAEServer` runs in a console; the same executable runs as a Windows service". Both file names are deployment surface: the installer registers `DAEService.exe` as the service binary (WS9 `Setup/`), `ConfigurationUtility` drives that service, and `tests/DAE.Client.Tests` starts `DAEServer.exe` by relative path. Settle what exists after this ticket — `DAEServer.exe` only, with `DAEService.exe` gone; or `DAEServer.exe` plus a thin `DAEService.exe` that forwards for compatibility — and say what an existing installed service does on upgrade. WS9 and WS10 both depend on the answer, so it belongs in the ticket, not in the implementer's head.

**What replaces the installer class.** `ServiceUtility.Install`/`Uninstall` are called from `src/windows/ConfigurationUtility/MainForm.cs` (lines 435 and 457) as well as from the service's own `-i`/`-u`. Removing them stops the configuration utility compiling, which is WS6's project. Decide between: a new CLI verb on the host (`DAEServer --install-service -n <instance>`) with `ServiceUtility` keeping its signatures and shelling out to it; `ServiceUtility` calling the service-control API directly; or moving registration entirely into the installer and deleting the utility's buttons. The first keeps WS6 compiling and keeps one implementation; weigh it against needing elevation from a GUI process. Whatever is chosen, `GetServiceName`, `GetServiceStatus`, `GetServiceAutoStart` and `SetServiceAutoStart` are public members that a deployment script or a custom tool could call — any change to them is a `docs/migration-notes.md` entry.

**The registry start-mode read and write.** `ServiceUtility` opens `HKLM\System\CurrentControlSet\Services\<name>` for write to read and set the `Start` value. That needs administrative rights, hard-codes the service-key layout, and duplicates what the service-control manager exposes. Decide whether to keep it as-is (smallest change, same behaviour) or move to the service-control API. Note the service name contains spaces and parentheses, which the key name carries.

**Logging.** The plan asks for logging through `Microsoft.Extensions.Logging` to the existing log file format and the Windows event log. The `Server` class already does both itself: `Server.LogMessage` writes to a rolling per-instance log file (`GetLogFileName`, `MaxLogs`, `_log` as an auto-flushing `StreamWriter`) and, for errors and warnings, to the event source `Dataphor Server`, creating the source if it does not exist — which needs elevation and is why the test fixture runs with logging off. Settle what the host's `ILogger` is *for*: host lifecycle messages only (start, bind, stop, failure), with the server's own log untouched; or a provider that the server's logging is rerouted through, which changes the log file format and so changes a surface operators read. The first is the smaller change and the one to prefer unless there is a reason found in the proof. Either way, say explicitly that the event-log source creation keeps its platform guard and is not made unconditional.

## What must still be true afterwards

- Starting the host with `-n <instance>` or with no argument (`Engine.DefaultServerName`) starts the same instance from the same `ServerConfigurations.config` and serves the same addresses as before.
- Ctrl+C in a console, and a stop from the service-control manager, both stop the server through `DataphorServiceHost.Stop` — the catalog store closed, the services closed, sessions ended — rather than killing the process. `Stop` currently closes the two service hosts with `BeginClose` and never waits for completion; a graceful shutdown has to wait for them, and for the connection manager's watcher thread, which is a plain foreground `Thread` signalled by a `ManualResetEvent` (`src/engine/Server/Service/ConnectionManager.cs`). Decide the shutdown ordering and a bounded timeout, and say what happens when it expires.
- A started server whose listener port is already taken still starts (see `protocol-corewcf-host`).
- Both host projects become SDK-style, follow the conversion rules in the root `AGENTS.md`, are added to `Dataphor.slnx` and to the Bin list in `tools/layout/Layout.csproj`, and put a real host into `artifacts/layout/<config>/bin/` — which today has no `.exe`, `.deps.json` or `.runtimeconfig.json` at all. The AGENTS.md "Runtime layout" paragraph says nothing runs from `bin/` until this ticket; that sentence comes out when it does.
- The two `app.config` files go. `src/hosts/DAEServer/app.config` carries a `<system.serviceModel>` section (commented-out services and a `customBinary` binding) and a `supportedRuntime` element for .NET Framework 4.5.2; `protocol-corewcf-host` removes the code that could read it. `src/hosts/DAEService/app.config` is where known defect K12 lives — the service reads configuration section `instance` while the shipped file declares `dataphor`, so the section has never been read. Settle whether anything still needs a configuration file; if not, say so, and record K12 as resolved by removal with a migration-notes entry telling deployments to check for a hand-edited `DAEService.exe.config`. `host-instance-configuration` is the ticket that finishes K12's half about settings; keep the two from both claiming it.
- `CommandLineArguments.cs` is dead in `DAEServer` (nothing calls it) and must not block the conversion. Dropping it from the compile list resolves K23 for this project at no cost; its sibling copy in `src/hosts/D4Runner` and the vendored parser itself stay with WS10. Check `D4Runner` actually uses its copy before assuming the two are the same case.

## Out of scope

The Windows service's `Strings.resx` localization, `ConfigurationUtility`'s own port to .NET 10 (WS6), the installer (WS9), and the general command-line tooling (WS10 `tool-cli-skeleton`). Where this ticket has to touch `ConfigurationUtility` to keep it compiling, keep the edit to the smallest signature-preserving change and say so in the handoff.
