Read the root `AGENTS.md` first; it has the layout, the build/test commands and the compatibility rules. The specification for the current work is `docs/modernization-plan.md` (with `docs/architecture.md` for how the system fits together) — set `architecture:` on every ticket to the plan section it serves, e.g. `architecture: docs/modernization-plan.md#ws3-test-suite`.

**Testing rule for this project (overrides "default is no new test").** This is a port of a working system whose behaviour is the specification, and it had almost no automated safety net. A ticket that ports, re-hosts or changes the behaviour of a subsystem owes a characterization test for it unless one already covers it; a bug fix owes its reproduction. Prefer the lowest layer that shows the behaviour: a D4 script run through the in-process engine harness over a client or UI test. Still no tests for wiring, getters or what the compiler already checks. Never edit an expected value in an existing D4 test script to make it pass: there is no reference runtime, so those assertions are the record of correct behaviour.

**Which tests to run, by stage (owner, 2026-11-23).** Full-suite runs were about half of every implement and review stage, and each stage ran every part of the suite at least once. CI (`.github/workflows/build.yml`) runs the whole suite in Debug and Release on every push, and the runner pushes after each stage, so the full run is CI's job, not the agent's. Always build first (`dotnet build Dataphor.slnx`); a build error is never left for CI.

- **Fix and implement: targeted tests only.** Run the tests the ticket adds or changes and the existing tests that cover the files you changed: the fixtures by name and the coverage scripts for that area, with `--filter` (see "One script, or a few" in the root `AGENTS.md`). This should take a few minutes. If you flip a coverage-manifest entry, run that script. Name the filters you used in the handoff.
- **Review: one ring wider.** Rerun the implement stage's targeted set, then add the neighbouring tests a regression would show up in: the other fixtures in the same test area and the coverage scripts for every engine area the diff touches (for example, all `Transaction.*` scripts for a transaction change). Aim for under about 8 minutes and list what you ran and why in the review notes. Run the part commands under "Agents run the suite in parts" in the root `AGENTS.md` only when the change cuts across everything: the build or test infrastructure, `Directory.Build.props` or `Directory.Packages.props`, the coverage runner or manifest format, or a change to the lexer, parser or compiler that every script goes through. Say so when you do.
- **Full suite: CI, and the gardener.** CI runs everything after each push. The tending agent checks each CI result (`gh run list --branch modernization`) and turns a red run into a fix ticket that names the failing tests and the commit range. It also runs the parts locally when the board drains, before it promotes the next umbrella.

Never run `dotnet test Dataphor.slnx` as one command: on a slow machine it takes over 11 minutes and the runner kills the ticket at 10.

**Compatibility is the constraint.** Existing applications are D4 libraries, catalog rebuild scripts and form documents. Never change, without a ticket that says so explicitly: D4 language semantics or operator signatures; D4 class names registered through `DAERegister`/`GetClasses()`; assembly names and namespaces; the `.d4l`, `.dfd`, `.dfdx`, `.dnt` and BOP file formats; error codes; WCF contract shapes; default ports and on-disk instance layout. If a change must break one of these, stop and route the question to `blocked/` with the proposed text.

**Migration notes.** A change that an application, a deployment script or a custom C# extension could notice — including a public type or member that extensions use — adds an entry to `docs/migration-notes.md` in the same commit.

**Architecture documentation.** A ticket that adds architecture text names the page under `docs/architecture/` that owns the subject and puts the text there, never in the short root `docs/architecture.md`. Every page in that set is capped at 1,500 words: run `python tools/docs-size-check/check_size.py` after editing one, and split a page that outgrows the cap rather than raising it.

**Bugs met along the way.** A defect with a local, obvious fix (a race, an off-by-one, a wrong API call) is fixed in the ticket that meets it, with its reproduction test, and listed in the handoff. A defect whose fix changes a design or a compatibility surface becomes its own ticket.

**Source hygiene.** Source files here mostly use tabs and CRLF line endings; some `.cs` and `.d4l` files have a UTF-8 byte-order mark and others do not. Preserve each file's indentation, line endings and byte-order-mark state in files you edit, and never reformat or re-encode a file you are not otherwise changing. Moving a file and editing it are separate commits. On .NET 10 several removed APIs compile and then throw at run time: never suppress `WFDEV006` or `SYSLIB` warnings to get a build green.

**Privacy.** This repository is public. Never write a customer's name, file paths, schema, library names or data into any tracked file, ticket or commit message; describe needs generically.

**Splitting keeps the slug.** Other tickets wait on a work item by naming its slug in `prereq:`, and the runner treats a slug it cannot find on the board as already done. So when a `plan/` ticket splits into several tickets, the ticket that *finishes* the work item keeps the original slug, and the pieces before it get new slugs and are chained to it with `prereq:`. Never name a slug in `prereq:` that is not on the board or in `tickets/.pruned-tickets.jsonl`; if the work you depend on has not been filed yet, file it (or name the umbrella ticket in `backlog/` that will) rather than inventing its slug.
