# Known pre-existing failures (tess)

- `tools/net-spike/run.py --smoke (Concurrency: 8 threads x 15 iterations of DDL+query)` — K3, "InvalidOperationException: Collection was modified; enumeration operation may not execute", 1 error in the 8x15 step, roughly 1 per several thousand create/drop-operator cycles. Located with a first-chance stack: Dictionary enumerator in `OperatorResolutionCache.Clear(String)` called from `Compiler.CompileCreateOperatorStatement` with no lock while another session's resolution added to the cache. Fixed 2026-11-14 by a private lock in `Dataphor/DAE/Compiling/OperatorResolutionCache.cs`; the smoke run's new "Resolution cache" step reproduces it deterministically (0 errors expected; about 1.4M errors in 5 s before the fix). Confirm protocol: if the concurrency step fails again, set the harness to print the innermost exception's full stack. If the stack does NOT pass through `OperatorResolutionCache`, it is a different site, not this one; if it does, this fix has regressed. → no tracking ticket | one-off | 2026-11-14
- `tests/DAE.Server.Tests/ConcurrentDDLTest.cs` — ConcurrentSessionsStoreTheirOwnScripts, intermittent (1 of 2 full runs): "Concurrent DDL failed other than on a store lock: … CompilerException: Errors occurred while attempting to resolve the default device name "System.Temp" … SchemaException: Duplicate object name "General"", stack through `LoadedLibrary.GetNameResolutionPath` from `ServerSession.get_NameResolutionPath`. Cause: two sessions on the same current library built its cached name resolution path into one shared object with no lock. Fixed 2026-11-14 in `src/engine/DAE/Schema/Library.cs` (build into a local under a private lock, publish when complete; `ClearNameResolutionPath` takes the same lock). New test `NameResolutionPathAllowsConcurrentFirstUse` in the same file reproduces it every run without the fix (Duplicate object name / NullReferenceException within 400 ms). Confirm protocol: if this test or a "Duplicate object name" through `GetNameResolutionPath` appears again, the fix has regressed; a failure in ConcurrentSessionsStoreTheirOwnScripts whose stack does not pass through `GetNameResolutionPath` is a different defect. → no tracking ticket | one-off | 2026-11-14
- `tests/DAE.Server.Tests` coverage script `ServerLink` — on some machines it fails with "HarnessTimeout: script did not finish within 120 s; it did not stop when aborted and its server was abandoned" instead of its manifest's known failure (`SocketException`, owned by `feat-ws5-protocol-and-hosting`), and adds about 2.5 minutes to the run. Cause is the machine, not the code: on the machine where it was seen, a TCP connect to any closed loopback port (`127.0.0.1` or `::1`, port 8061 or any other) is never refused and sits in SYN_SENT, so the script's server link waits instead of getting a SocketException. Do not change the manifest entry or the script for it. Confirm protocol: in PowerShell, time `(New-Object Net.Sockets.TcpClient).ConnectAsync('127.0.0.1',8061).Wait(5000)`; if it returns False after 5 s, the machine drops loopback connects and this record applies; if it throws "actively refused" promptly and `ServerLink` still times out, it is a real defect and should be reported. → no tracking ticket | one-off | 2026-11-18
