# Dataphor

Dataphor is a relational application platform: a database engine with its own language (**D4**) that federates SQL back ends, plus a declarative UI layer (**Frontend**) that derives forms from the schema, a WinForms client that renders them, and an IDE (**Dataphoria**). C#, ~400k lines, written 2000–2019 for .NET Framework. Customer applications are *D4 libraries + form documents*, not C# — their behaviour is what must not break.

**The repo is mid-modernization (.NET Framework 4.5.2 → .NET 10).** Before any non-trivial work read:

- [docs/modernization-plan.md](docs/modernization-plan.md) — the master plan: workstreams, decisions, sequencing, known defects. Tickets anchor to its sections.
- [docs/architecture.md](docs/architecture.md) — how the pieces fit, what talks to what, where things live on disk.
- [docs/migration-notes.md](docs/migration-notes.md) — running list of changes an application or custom extension will notice. If your change is one, add it there in the same commit.

Settled direction (details in the plan): .NET 10 only, no .NET Framework build; SQLite catalog store, SQL CE deleted, catalogs rebuilt from scripts rather than migrated; SQL Server and PostgreSQL are the supported devices; WinForms client and IDE kept; web client, Silverlight removed; FHIR and web prototypes parked.

## Build and test

Needs only the .NET 10 SDK that `global.json` pins.

```
dotnet build Dataphor.slnx
dotnet build Dataphor.slnx -c Release
dotnet test Dataphor.slnx
```

CI (`.github/workflows/build.yml`, GitHub Actions on `windows-latest`) runs these same commands in Debug and Release on every push and pull request to `master` and `modernization` that changes more than `tickets/` or `docs/`, and uploads the TRX test results as the artifacts `test-results-Debug` and `test-results-Release`; change the workflow when you change these commands.

`dotnet test Dataphor.slnx` (add `-c Release` for Release, `--no-build` after a build) runs every test project in the solution through VSTest; test projects reference `Microsoft.NET.Test.Sdk`, `NUnit` and `NUnit3TestAdapter` directly (no shared test props file: `tests/` also holds library projects) and stay out of `tools/layout/Layout.csproj`. `DAE.Server.Tests` starts its servers in-process, each in a fresh folder under `%TEMP%\Dataphor.Tests\` with its own copy of the library folders it needs, logging off, and deletes the folder afterwards (a folder it cannot delete, because the process still has a library assembly from it loaded, is deleted by the next run). Set `DATAPHOR_TEST_LOGGING=1` to diagnose a failure: the servers then log, every folder is kept with its instance log, catalog and library copies (their paths print with `--logger "console;verbosity=normal"`), and the next run without the variable deletes them. The cost: in an elevated process a logging server also creates the Windows event-log source `Dataphor Server` and writes to the event log, which the default run never does. One other variable gates tests rather than diagnoses them: `DATAPHOR_TEST_MSSQL` names a **SQL Server** (not a database) for `MSSQLStoreContractTests`, which runs the catalog store contract against the SQL Server store and puts its own database, `DataphorStoreContract`, on whatever is set - for example `Data Source=(localdb)\MSSQLLocalDB;Integrated Security=SSPI`, after `sqllocaldb start MSSQLLocalDB`. Unset, which is how CI runs, the fixture's 14 cases are skipped and each says so; nothing else in the suite needs a database server.

`DATAPHOR_UPDATE_FRONTEND_GOLDENS=1` is one of the three other variables the suite reads. `FrontendDerivationGoldenTest` derives every page type of every table variable the sample and shipped libraries define and compares each form with a checked-in file under `tests/goldens/frontend/`; with the variable set it **writes** those files instead, deletes the ones no case produces, and then fails the run anyway, so an update can never be mistaken for a pass. The diff is the review, so read it before committing it.

`DATAPHOR_PERF_BASELINE` and `DATAPHOR_UPDATE_PERF_BASELINE` are the last two. `PerfBaselineTest` runs the coverage corpus's timing scripts batch by batch and records how long each takes; with neither variable set it writes the numbers to `artifacts/perf/perf-run.json`, prints them and passes, which is what every ordinary run does. Set `DATAPHOR_PERF_BASELINE=<label>` to compare them with the numbers checked in under that label in `tests/goldens/perf/perf-baseline.json` - past 3× a recorded number the case warns, past 10× it fails - and add `DATAPHOR_UPDATE_PERF_BASELINE=1` to rewrite that label's entry and then fail the run, as the goldens update does. A label stands for a machine class, not for a machine, because absolute times are not comparable across machines and this repository is public. The numbers, the factors and the by-hand procedure for comparing with 3.1 are in [docs/perf-baseline.md](docs/perf-baseline.md).

**The benchmark program.** `tests/Dataphor.Benchmarks` (assembly `DAE.Benchmarks`) measures what a script inside an already-started server cannot: engine start, a mix of database work on the in-memory device, and the catalog store cold and warm. It is in `Dataphor.slnx`, so every build compiles it, but it is not a test project and `dotnet test` does not run it; run it by hand, in Release (`artifacts/bin/DAE.Benchmarks/release/DAE.Benchmarks.exe`), which takes about 100 seconds and writes its export under the git-ignored `artifacts/benchmarks/`. Its numbers are in the same document, in a section of their own because they are Release and the timing scripts' are Debug. See [tests/Dataphor.Benchmarks/README.md](tests/Dataphor.Benchmarks/README.md).

**Out-of-process client/server tests.** `DAE.Server.Tests` also starts a server as a *separate program* (`OutOfProcessProtocolTest` and `AbandonedClientProcessTest`, through the helper `OutOfProcessInstance`), so that the client code the product ships reaches it over a real socket with the two engines in different processes - which is how the product runs, and what no in-process fixture can show. The program is the suite's own, `tests/TestHarness` (assembly `DAE.Test.Harness`), and it has a mode for each side. In its `serve` mode it builds a production `DataphorServiceHost`, sets the host-object properties that are not instance settings (logging off, the host name the loopback literal, and - only when a case asks for it, with `--idle-seconds` - a connection idle threshold short enough that a reclamation can be watched rather than waited five minutes for) and starts it through the production `Start()`, taking its instance from a list the fixture writes in a temporary folder that the child's `DATAPHOR_INSTANCE_DIRECTORY` points at - so no run reads or writes this machine's instance list. It prints one line, `READY <instance> <port> listening=<true|false>`, and then stops when a line arrives on its standard input *or* that input reaches its end, so the child goes when the test run does, however that run ends. Its `client` mode is the other side: the shipped client stack, connecting to a server given on the command line, opening a transaction that changes the catalog, printing `HOLDING <table> <session-id>` and then blocking for ever, so that a fixture can kill it and watch what the server does about a client process that dies holding a session (`AbandonedClientProcessTest`, started through `OutOfProcessInstance.StartAClientHoldingATransaction`). That mode has no stop path on its standard input, deliberately: being killed is the only way it ends. A child server can also serve a **listener** - the service that answers "where is instance X" - on a second reserved port, for a case whose client cannot be told a port and has to discover one; the coverage runner starts one that way for the `ServerLink` script (see *D4 coverage scripts*), and points this process's client side at it with `DataphorServiceUtility.ListenerPortNumber` for the length of that one case. A listening child is the suite's one deliberate exception to "no port another machine can reach": it listens on the machine's own name rather than the loopback literal, because a *name* makes CoreWCF bind both address families while a literal leaves a client whose name resolves to the other one paying about two seconds per channel open (measured; recorded under *CoreWCF hosting* in the plan), and the script connects by `localhost` and opens tens of sessions. It is deliberately not the shipped `DAEServer.exe`: a hosted server logs unless its host turns logging off, a logging server in an elevated process (CI runners are elevated) creates the Windows event-log source `Dataphor Server`, and the shipped host has no way to be told otherwise - neither a command-line switch nor an instance setting. `debt-test-shipped-host-executable` owns covering the published executable and names the knob it needs. The harness project is not in `tools/layout/Layout.csproj` and nothing ships it; `DAE.Server.Tests.csproj` records its build output as `AssemblyMetadata` (`DataphorTestHarnessPath`, the way it records the layout directory) and `TestEnvironment.TestHarnessPath` finds it - never spell that path in code.

**In-process client stack tests.** The other side of that coin, for a defect that is in the client stack rather than in the transport under it: `ClientStackTestFixture` stands the shipped client stack up in this process - a `LocalServer` over a `RemoteServer` over the server of `InProcessTestFixture`, which it derives from - and gives each test a client session and process beside the inherited engine-side pair, so a case can ask the same question of both and compare. That is what makes `RemoteServerCursor` and `LocalCursor` reachable at all: they are the same objects a client over the wire talks to, because the protocol layer only marshals the calls they already make. No port, no WCF host, and no second process - which is also what it cannot show, so a defect at the boundary itself belongs above. Note that `LocalServer` starts an engine of its own, so every test on this fixture runs two engines in one process (see the note on `TestServerInstance` for what they share). `RemoteValidateTest` is the first fixture on it.

**D4 parser corpus (`ParserRoundTripCorpusTest`).** `DAE.Server.Tests` also runs one L0 case per `.d4` file in the repository (387 at the time of writing) that parses the file, emits the parse tree through `D4TextEmitter`, re-parses the emitted text and asserts the two trees are structurally equal. No server; the test holds the parser and emitter in agreement as the codebase evolves. Files the current parser/emitter cannot round-trip sit in the fixture's `AllowList` with a one-line category; the ticket `test-parser-roundtrip-corpus` and its review-stage handoff list the follow-up tickets that drain them.

**Form document corpus (`FormDocumentCorpusTest`, `FormCustomizationTest`).** `DAE.Server.Tests` also runs one L5 case per `.dfd` and `.dfdx` form document in the repository (76 at the time of writing) that reads the file and checks it parses as the format its extension claims; no server. `FormCustomizationTest` then loads each `.dfdx` of a library its fixture carries through an in-process server and asserts that differencing the loaded form against its ancestors and merging the difference back reproduces it. Two lists keep that pass honest and both are asserted against the tree: `LibrariesNotCarried` names the libraries whose documents are out of scope with a reason each, and `Exclusions` the individual documents that still fail, each with the text its failure must carry. The shared fixture is `FrontendFixture` (one server, ten libraries, `Frontend` registered before `System.Internet`). Both read source files rather than the runtime layout, which holds only what the build assembles: the repository root comes from `TestEnvironment.RepositoryDirectory`, over the `DataphorRepositoryDir` `AssemblyMetadata` entry that `DAE.Server.Tests.csproj` records — never spell that path in code either.

**Derived form goldens (`FrontendDerivationGoldenTest`).** The other half of L5, on the same `FrontendFixture` server: every page type of every table variable the carried libraries define (52 surfaces × 8 page types = 416 cases) is derived through `Frontend.Derive` and compared, character for character, with a file under `tests/goldens/frontend/<Library>/<Surface>.<PageType>.xml`, so that a change anywhere in the derivation engine shows up as a reviewable difference rather than as a form a user finds wrong. A golden is the derived document *printed* — indented, one element per line — because what `Derive` returns is a single line, and a single-line file makes every change look like a whole-file rewrite. The sets must agree exactly: a case with no golden, a golden no case produces, a failure with no entry in the fixture's expected-failure table and a table entry no failing case matches each fail the run. The table is empty today: every case of the corpus derives, so every case has a golden. Set `DATAPHOR_UPDATE_FRONTEND_GOLDENS=1` to rewrite the files, as above.

**Sample application corpus (`SamplesCorpusTest`).** Layer L7: one case per library folder under `samples/` - twelve today - and nine of them get a server of their own, carrying that sample's requisite closure and nothing else, are registered there, and have a form derived from every page type of every table variable they then define (the other three are reported Inconclusive with the reason; the nine define 16 surfaces between them, so 128 derivations). This is breadth and isolation rather than a second golden set - the derivation check only asks that a form is produced, parses as XML and has the right root element (`<report>` for the `Report` page, `<interface>` for the other seven), because the goldens above already cover every surface any sample defines. What it adds: the libraries are **discovered** by walking a directory, so a sample library added to `samples/` becomes a case with no code change, where `FrontendFixture`'s library list is hand-written; and one server per sample catches a sample that only registers because a sibling created something first. Three recorded lists keep it honest, each asserted against the tree in both directions: the samples whose registration needs a running SQL Server (`Sample.Forum`, `Sample.Pubs`, `Sample.Shipping` - reported Inconclusive without being attempted, an accepted tradeoff recorded at the site), the samples that expose no table variable once registered (four, each with the reason), and the samples the build does not assemble into the runtime layout (empty since `library-sample-shipping-convert`, and kept for the next sample that arrives with an unconverted C# project). A sample in none of the three must register, enumerate and derive. The pass takes about 37 s. `samples/` is reached through `TestEnvironment.RepositoryDirectory` - the layout mixes the shipped, sample and test libraries in one folder and leaves out the ones it cannot assemble, so it can neither name the sample set nor notice that one is missing - while the folders a server carries still come from the layout. The discovery rule and the requisite-closure walk are in `CorpusLibrary.cs` and know nothing about samples, this repository or NUnit: `compat-corpus-harness` (WS13) points the same two at an application corpus outside the repository.

**D4 coverage scripts.** `DAE.Server.Tests` runs every script in the layout's `Libraries/TestFramework.Coverage.Scripts/Documents/` as its own test case (named after the script), each on a fresh server copied from one template instance that the run builds first, and checks it against `tests/DAE.Server.Tests/coverage-manifest.json` (embedded in the test assembly; the format is described on `CoverageManifest` in `CoverageManifest.cs`). Each entry says `pass`, `known-failure` (with the slug of the ticket that owns the cause and a substring the error must contain), `unstable` (varies between identical runs; reported, never fails) or `fragment` (a step that other scripts run, named in its `partOf`; not run on its own, reported as Skipped). An entry may also carry `timeoutSeconds`, a `preamble` of D4 to run first, `register` for libraries to register first, `batches` to run the script batch by batch as Dataphoria does, and `linkedServer` - a second Dataphor server in a child process, named `Dataphor` and serving a listener on a reserved port, started before the script and stopped after it, which is what a script creating a *server link* with no port override needs (today only `ServerLink`). A green run means every `pass` script passed and every `known-failure` script failed in its recorded way; a known failure that now passes, or fails differently, fails the run, as does a script with no entry or an entry with no script. VSTest reports known, unstable and fragment cases as **Skipped**; the only other skips in the suite are the three sample-corpus cases above that report Inconclusive. Change the manifest with the code: a fix that makes a script pass flips its entry to `pass` in the same commit, and a new script needs an entry (entries are sorted by script name in ordinal order). Never edit a coverage script to make it pass. The template registers `Frontend` and the helper library `TestFramework.Coverage.Base`, which needs no database server; if either fails to register, every script case fails with that error. The whole suite takes from about 3.5 minutes on a fast machine to over 11 on a slow one (measured 2026-11-18), most of it in the coverage scripts; the template takes a few seconds.

**Agents run the suite in parts.** The ticket runner kills an agent that prints nothing for 10 minutes, and the agent's shell does not show a command's output until the command ends, so one `dotnet test Dataphor.slnx` can get a ticket killed. After `dotnet build Dataphor.slnx`, run these five commands (Bash syntax), each as its own foreground command; together they run every test once:

```
dotnet test Dataphor.slnx --no-build -- "NUnit.Where=class !~ '^Alphora\.Dataphor\.DAE\.Server\.Tests\.' || class =~ '^Alphora\.Dataphor\.DAE\.Server\.Tests\.[^A-N]'"
dotnet test tests/DAE.Server.Tests --no-build -- "NUnit.Where=class =~ '^Alphora\.Dataphor\.DAE\.Server\.Tests\.[ABD-N]'"
dotnet test tests/DAE.Server.Tests --no-build -- "NUnit.Where=class =~ '^Alphora\.Dataphor\.DAE\.Server\.Tests\.C' && class != Alphora.Dataphor.DAE.Server.Tests.CoverageScripts"
dotnet test tests/DAE.Server.Tests --no-build -- "NUnit.Where=test =~ '^Alphora\.Dataphor\.DAE\.Server\.Tests\.CoverageScripts\.(Script\.)?(?!Script$)[A-Ra-r]'"
dotnet test tests/DAE.Server.Tests --no-build -- "NUnit.Where=test =~ '^Alphora\.Dataphor\.DAE\.Server\.Tests\.CoverageScripts\.(Script\.)?(?!Script$)[^A-Ra-r]'"
```

The first three are the NUnit fixtures - everything except the coverage scripts - split by the first letter of the test class's name; the last two are the coverage scripts, split by the first letter of the script's name. On the slow machine the five took about 3, 3, 4, 3.5 and 4 minutes at best (the three fixture parts are best of two rounds measured 2026-11-25: 3 m 11 s, 3 m 01 s and 4 m 04 s, for 494 + 18, 252 and 210 passing cases; the two coverage parts were last measured 2026-11-21 at 3 m 28 s and 3 m 48 s). The five filters **partition the suite by construction**, which is the property to keep: every test class either is outside the `Alphora.Dataphor.DAE.Server.Tests` namespace, or is inside it and starts with a character outside `A`-`N`, or with `C`, or with one of `A`, `B`, `D`-`N`; `CoverageScripts` is a `C` and is excluded there, because the last two parts split it by script name. So a fixture added in a new namespace, in a new test project of the solution, or with a lower-case or underscore-led class name still lands in the first part rather than nowhere - which is why that part is the one command that runs the whole solution and why its last clause is the negated range `[^A-N]` rather than `[O-Z]`. And because CI runs the whole suite on every push, a mistake in one of these filters costs false confidence in a local run, not lost coverage. **Do not read one measurement as the part's cost.** Over several runs of the same build on 2026-11-21 the same machine gave the then-undivided fixture part anywhere from 5 m 20 s to 7 m 32 s, the first coverage part from 3 m 28 s to 6 m 35 s and the second from 3 m 48 s to 5 m 54 s, with no pattern that was chased down - so a part can take half again as long as the figure above for reasons that have nothing to do with the change being tested. Take the best of two runs when you are comparing, and treat a single slow run as noise until it repeats. The coverage-script filters match the full test name (`test`), not `name`: NUnit runs every child of a suite whose own name matches, and the fixture `CoverageScripts` and the method `Script` would match a first-letter test on `name`. If a part grows past about 6 minutes, split it further; the next cut is already chosen. The `C` part splits at `Ca`: `class =~ '^Alphora\.Dataphor\.DAE\.Server\.Tests\.Ca'` holds the three `Catalog*` fixtures, which are 140 s of that part's 224 s of measured test time, and `class =~ '^Alphora\.Dataphor\.DAE\.Server\.Tests\.C(?!a)'` with the `CoverageScripts` exclusion holds the rest.

One script, or a few:

```
dotnet test tests/DAE.Server.Tests --filter Name=Lexer
dotnet test tests/DAE.Server.Tests --filter "Name=Lexer|Name=Transaction.Atomicity.Run" --logger "console;verbosity=normal"
```

The per-ticket summary (pass and known-failure counts per ticket) and each known failure's error text print only with `--logger "console;verbosity=normal"`; at the default verbosity `dotnet test` shows the totals.

**Coverage, on demand.** Adding `--collect:"Code Coverage;Format=cobertura" --results-directory artifacts/coverage/<part>` to any of the test commands above writes one Cobertura file per run. It needs no extra package - `Microsoft.NET.Test.Sdk`, which every test project already references, brings Microsoft's own collector - it coexists with the NUnit filters as long as its arguments stay before the `--`, and it follows the out-of-process children, so their coverage counts too. The cost is small: measured 2026-11-21 on the slow machine in Debug, a two-case run took 20.5 s of wall clock with collection against 20.2 s without, both reporting 7 s of test time (expect a one-off warm-up on the first collected run). Then `python tools/coverage-report/coverage_report.py artifacts/coverage` merges the parts' reports and prints line coverage per assembly and per engine area, worst first, then every source file the run never entered at all, then the files of each gap; it reports and never gates, and CI deliberately does not collect it. See [tools/coverage-report/README.md](tools/coverage-report/README.md).

Name the `.slnx`: the legacy `Dataphor.sln` is still at the root, and it no longer builds (its .NET Framework projects reference the converted `net10.0` ones); `build-remove-legacy-build` deletes it. Output goes to `artifacts/bin/<project file name>/<debug|release>/`, intermediate files to `artifacts/obj/`; nothing is built into source folders. Shared settings are in `Directory.Build.props`, package versions in `Directory.Packages.props`.

**Runtime layout.** The build also assembles `artifacts/layout/<debug|release>/` (lower case, like the `artifacts/bin` folders): `bin/` holds the core and server assemblies with their package runtime files, and `Libraries/<Name>/` holds each library's tracked files (`.d4l`, `Documents/`, `Upgrades/`, …) with its assembly and that assembly's private package files, flattened for Windows x64. `Libraries/` combines the shipped, sample and test libraries (`libraries/`, `samples/`, `tests/libraries/`) in one folder, as the server expects, minus the two whose C# project is not converted yet (PGSQLConnection, PGSQLDevice). `tools/layout/Layout.csproj` is the only project that writes there; it mirrors the folder (deletes what it did not put there) and fails the build if a `.d4l` lists a file the layout does not provide. Find the folder through the MSBuild property `DataphorLayoutDir` (`dotnet msbuild tools/layout/Layout.csproj -getProperty:DataphorLayoutDir`), never by spelling the path. `bin/` also holds the two host executables, `DAEServer.exe` and `DAEService.exe` (one program under two names), each with its `.deps.json` and `.runtimeconfig.json`: `artifacts/layout/<config>/bin/DAEServer.exe -n <name>` starts that instance, and Ctrl+C stops it. Mind what that costs: an instance not already in the machine's instance list (`%ProgramData%\Alphora\Dataphor\4\Instances\ServerConfigurations.config`) is **added to it** with a default configuration whose library directory is the layout's own `Libraries\`, and a running server writes into its library directory - so run the host against a *copy* of the layout, as the tests do with `Libraries/`. **Converting another project.** The reasons are in the `Directory.Build.props` comments and plan WS1.

- Generate the new file from the legacy one and keep its explicit `Compile` and `EmbeddedResource` items, in order: default items are off in `Directory.Build.props`, because uncompiled files sit next to compiled ones.
- Copy each resource's `DependentUpon` metadata. The SDK's dependent-upon naming convention is off, so resource names follow the legacy rules; verify them by listing `Assembly.GetManifestResourceNames()` against the legacy names, as the engine check does for the converted assemblies.
- Constants: the legacy Release set minus `SIGNASSEMBLIES` and `DISABLE_PERFORMANCE_COUNTERS`, the same in both configurations (so `TRACE` only where legacy Release had it), plus `DEBUG;TRACE` in Debug. Set `DefineConstants` outright, never appended to `$(DefineConstants)`.
- No `OutputPath`. `PackageReference` items carry no version; add the version to `Directory.Packages.props`.
- Warnings stay visible. Never suppress `CS0618`, `SYSLIB*`, `WFDEV*`, `CA1416` or `NU1900`–`NU1904`; any `NoWarn` code goes in `Directory.Build.props` with a reason.
- Output is keyed by project file name, so two projects with the same file name collide; no project file name is used twice today, and a new project must keep it that way.
- Version, company, product, copyright and signing come from `Directory.Build.props` (version `4.0.0-preview`, `AssemblyVersion` `4.0.0.0`, signed with `Dataphor.snk` in every configuration, deterministic). In the project's `Properties/AssemblyInfo.cs` delete `AssemblyVersion`, `AssemblyFileVersion`, `AssemblyCompany`, `AssemblyProduct`, `AssemblyCopyright`, `AssemblyTrademark`, `AssemblyCulture`, `AssemblyConfiguration`, `AssemblyDelaySign`, `AssemblyKeyFile`, `AssemblyKeyName`, the `#if SIGNASSEMBLIES` block and the template comments about them; keep `AssemblyTitle`, `AssemblyDescription`, `DAERegister`, `ComVisible` and `Guid`, and the file's encoding and line endings. A leftover attribute fails the build with CS0579, a leftover `3.1.*` with CS8357.
- Add the project to `tools/layout/Layout.csproj`: to the Library list for a library project (in `<Name>/Source/`, next to `<Name>.d4l`), to the Bin list for anything else that ships (test projects stay out; a `net10.0-windows` project first needs the change the `NOTE:` in that file describes). ## Rules that are easy to break

- **Compatibility surfaces — do not change without a ticket that says so:** D4 semantics and operator signatures; D4 class names (the strings in `create operator … class "Lib.XNode"`, registered by each assembly's `DAERegister.GetClasses()`); assembly names; `.d4l`/`.dfd`/`.dfdx`/`.dnt`/BOP formats; error codes (`docs/reference/Error Message Prefix Codes.txt`); WCF contracts, declared twice — the server's in `src/engine/Server/Contracts`, the client's asynchronous copies in `src/protocol/Client/Contracts`, `src/protocol/Common/Contracts` and `src/protocol/NativeCLI` — and the two copies must stay in step (`ContractParityTest` in `DAE.Server.Tests` compares them and fails on a drift; its `KnownFaultDifferences` list, empty today, is where a difference that cannot be fixed at once is recorded, and it fails once a recorded difference is gone, so a fix must drain its entry); ports 8060/8061.
- **Formatting:** tabs and CRLF in most source files; a UTF-8 byte-order mark in some `.cs` and `.d4l` files and not others (about 40 % of `.cs` files have one). Preserve whatever each file has. The root `.editorconfig` and `.gitattributes` describe this and deliberately set no charset, final-newline or `text=auto` rule. Never reformat or re-encode a file you are not otherwise changing.
- **Architecture documentation is hierarchical.** `docs/architecture.md` is a short overview and the detail lives in one page per subsystem under `docs/architecture/`; new architecture text goes on the child page that owns the subject, never in the root. Every page in that set has a word limit - 1,500 words today, `LIMIT` in `tools/docs-size-check/check_size.py` - checked by `python tools/docs-size-check/check_size.py` and gated by `.github/workflows/docs.yml`. A page that outgrows the limit is **split** into a parent page beside a folder of the same name holding its children (the shape `architecture.md` has beside `architecture/`); the limit is not raised and the page is not added to the checker's exception list, which is empty and meant to stay empty.
- **A file on disk is not necessarily compiled.** Legacy csproj files list sources explicitly; strays exist (`src/client/DAE.Client/View-263.cs`, most of `libraries/Connection/Source`). Check the csproj before trusting or fixing a file.
- **Same-named files exist in both `src/engine/DAE` and `src/engine/Server`** (`SecurityNodes.cs`, `LibraryNodes.cs`, `CatalogNodes.cs`, …). They are different files; check both.
- **Behaviour switches are `#define`s at the top of individual files** plus csproj constants; `docs/reference/CompilerDefines.txt` is the index. `NILPROPOGATION` (sic) etc. are load-bearing.
- **A running server writes into its library directory** (creates `General/`, may rewrite `.d4l` files) and defaults its instance directory to `%ProgramData%\Alphora\Dataphor\4\Instances\<name>` - versioned since `host-instance-directory`, so a 3.1 installation on the same machine is not disturbed. Tests and experiments must set `InstanceDirectory` to a temp path and point `LibraryDirectories` at a *copy* of the runtime layout's `Libraries/` (or of the library folders they need), never at the layout or the repo; `DATAPHOR_INSTANCE_DIRECTORY` does the first of those for a process started from outside, and only that: the default configuration a host registers for an unknown instance still points `LibraryDirectories` at the layout's own `Libraries\`, so a run against a copy is still the only thing that keeps the layout from being written to.
- **Catalog store ≠ device.** A *store* persists the server's own catalog (SQLite by default). A *device* is a D4 object that maps tables to an external DBMS or to memory.
- **On .NET 10, "it compiles" does not mean "it runs".** WinForms' old `ContextMenu`, `MenuItem`, `MainMenu`, `ToolBar` and `StatusBar` types exist again but throw `PlatformNotSupportedException` when constructed (warning `WFDEV006`); remoting and `Delegate.BeginInvoke` members compile and throw the same way. Never silence `WFDEV006` or `SYSLIB` warnings to get a build green.
- The engine's built-in admin user is `Admin` with an empty password; tests connect as `new SessionInfo("Admin", "")`.

## Code search (tess)

**First tool** for any "where / how / why" question about this codebase: local code-aware index wired to `mcp__code-search__*`. Reach for `grep`/`Glob` only when you know exact filename or literal string. Pick right sub-tool — not interchangeable.

**Decision rule:**

- Query identifier-shaped (single symbol, camelCase, snake_case, or name list like `fooBar bazQux`)? → `find_references`.
- Query prose ("where do we evict pages", "what handles JWT refresh", identifier unknown)? → `search_code`.
- About to run more than one `grep` to reconstruct context? → run `search_code` first instead. Payoff moment, even when you know an identifier.

`search_code` embeds query as natural language. Identifier-bag queries can work when identifiers co-locate in real code, but prose phrasing more reliable. If `search_code` returns weak-top warning, relative-percentage ranking unreliable — switch to `find_references` or rephrase as prose. Do **not** trust ordering on noisy results.

**Tools:**

- `search_code(query, k?, path_filter?)` — semantic search. Scores relative within each result set, not absolute. `k` defaults to 5 (max 50) — raise for broad sweeps, lower when top hit enough. `path_filter` is SQL LIKE pattern, e.g. `"packages/lamina/%"`.
- `find_references(symbol, max?, path_filter?)` — literal substring; `|` ORs alternatives (`Foo|Bar`). Returns every hit (capped by `max`, default 50, max 500). Indexed replacement for `grep` on identifiers.
- `read_chunk(path, start_line, end_line)` — expand snippet from either tool without separate `Read`.

**Fallbacks:**

- Use `grep`/`Glob` only for filename patterns, regex with anchors/lookarounds, or when you need *every* literal hit (index is chunk-granular, may miss adjacent matches inside one chunk).
- Never fall back to `grep` when `find_references` suffices — strictly slower, pulls more bytes.
- If the `mcp__code-search__*` tools are not connected in your session, the same index is reachable from a shell: `node tess/scripts/search.mjs "<prose query>"`, `node tess/scripts/search.mjs --refs "<symbol>"`.

**What's indexed:** git-tracked project source, minus `node_modules/`, `dist/`, `build/`, `.git/`, `tickets/`, `team/`, `docs/`, few cache dirs. If query about prose-heavy material (long-form architecture docs, design notes, nested READMEs) returns nothing, file may be outside indexed set — fall back to `Read`/`Glob` for those paths. Projects can override filter via `tickets/index-config.json` (see tess README § Customize what gets indexed).

This project's `tickets/index-config.json` adds D4 sources (`.d4`, `.d4l`) and WiX/MSBuild files (`.wxs`, `.props`, `.targets`), and drops dead, vendored or bulky trees (`legacy/`, `Utilities/`, `external/`, `Documentation/`, `tests/libraries/TestFramework.Coverage.Devices/Documents/`). Use `Read`/`Glob` for those.

## Mannered prose

Mannered prose substitutes metaphor and flourish for direct statement. Instead of "a parameter worth varying," the mannered writer produces "a dial worth turning." Instead of "this point still matters," they write "this point earns its keep." The phrases exist to display the writer, not to convey the idea, and readers can tell. That is why mannered prose irritates: it makes the reader work harder so the writer can perform. It is also imprecise. Metaphors drag in connotations the writer did not choose and cannot control. The fix is to say what you mean. When a literal phrase is available, use it.
